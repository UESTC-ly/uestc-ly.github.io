1. MCP 的基本概念

MCP（Model Context Protocol）可以理解为一种让 AI 应用以统一方式发现和使用外部能力的协议。它把“模型应用如何连接工具、资源和提示模板”从某个具体业务代码中抽象出来。

常见角色包括：

  • Host：用户使用的 AI 应用或 Agent 宿主，负责整体会话、策略和用户体验；
  • MCP Client：Host 中负责连接某个 MCP Server 的客户端；
  • MCP Server：对外暴露工具、资源或提示模板的服务进程；
  • Tools：可调用的动作，可能读取或修改外部系统；
  • Resources：可读取的上下文资源，例如文件、文档或业务数据；
  • Prompts：可复用的提示模板或工作流入口。

MCP 解决的是能力发现和协议互操作，不自动解决权限、数据可信度、业务正确性或副作用安全。

2. MCP 与直接 Tool Calling 的关系

模型厂商 Tool Calling：模型如何表达“调用工具”
MCP：应用如何发现、描述和连接外部工具/资源

二者可以组合：MCP Client 发现工具并转换成模型 API 所需的工具 Schema；模型提出调用；Host 再通过 MCP Client 请求 Server 执行；执行结果回到 Host，最后由模型生成答案。

MCP 不应被当作“让模型直接接入任意电脑”的授权机制。Host 仍需决定：

  • 哪些 Server 可信；
  • 哪些工具向当前会话暴露；
  • 当前用户和租户是否有权调用；
  • 是否需要审批、沙箱、网络限制或人工确认；
  • 工具返回的数据哪些可以进入上下文。

3. 接入 MCP 时的安全边界

  • 对 Server 和工具做来源登记、版本管理和能力审查；
  • 连接凭据由 Host 或服务端安全保存，不交给模型；
  • 对工具参数做本地 Schema 与业务验证；
  • 对资源读取做租户隔离、路径限制和数据脱敏；
  • 对写操作设置默认拒绝、审批、额度和幂等；
  • 限制 Server 的网络、文件和进程权限；
  • 记录工具发现、调用、返回和审批审计；
  • 将外部返回值作为不可信数据，防止 Prompt Injection；
  • 处理协议版本、断线、超时和 Server 不可用。

4. MCP 的学习顺序

  1. 先手写一个本地 Tool Registry，理解工具 Schema 和执行边界；
  2. 再把 Registry 的发现和调用过程替换为 MCP Client；
  3. 对比直接函数、HTTP API 和 MCP Server 的生命周期、权限与错误处理；
  4. 最后加入审批、沙箱、审计和多 Server 管理。

如果没有理解直接 Tool Calling，直接使用 MCP 容易把协议层误认为安全层。

5. 多 Agent 何时有价值

多 Agent 适用于以下情况：

  • 子任务具有清晰边界，所需工具和权限不同；
  • 需要隔离上下文，例如研究、编码、审核各自独立；
  • 可以并行执行互不依赖的只读任务；
  • 不同角色拥有不同的提示、模型或质量标准；
  • 有明确的协调者、输入输出契约和失败策略。

常见结构：

Coordinator
 ├─ Researcher：检索和整理候选资料
 ├─ Analyst：按固定 Schema 分析
 └─ Reviewer：检查事实、格式和风险

协调者不应只凭自然语言转发一切结果，而应使用结构化任务契约：任务 ID、输入范围、输出 Schema、截止时间、允许工具和完成条件。

6. 多 Agent 的适用边界

不适合拆分的情况：

  • 任务简单，单次模型调用或一个 Workflow 就能完成；
  • 子 Agent 之间共享大量上下文，拆分后反而增加传输和同步成本；
  • 没有独立权限、模型、工具或质量标准；
  • 需要严格事务一致性，却让多个 Agent 直接修改同一资源；
  • 无法定义谁负责最终事实、错误和用户沟通。

多 Agent 会增加：调用次数、Token 成本、延迟、状态同步、Prompt Injection 面积和调试难度。拆分不是越多越好。

7. 多 Agent 协调原则

  • 每个 Agent 只拥有完成自身任务所需的最小工具集合；
  • 共享状态用数据库或事件协议管理，不依赖隐式聊天；
  • 中间结果包含来源、版本、置信度和待验证标记；
  • 协调者验证 Schema、超时和权限，不盲信子 Agent；
  • 关键写操作集中到一个确定性执行器；
  • 子任务失败可以重试、跳过、降级或转人工，策略由应用决定；
  • 为每个子任务设置独立预算，同时受总任务预算约束。

8. 一个保守的多 Agent 流程

Coordinator 生成子任务
  ↓ 应用校验任务范围和工具权限
并行执行只读 Researcher
  ↓ 保存带来源的结果
Coordinator 汇总并生成候选方案
  ↓ Reviewer 做结构和事实检查
确定性业务层执行副作用动作
  ↓
统一返回结果与审计记录

先使用并行只读子任务验证收益，再考虑让多个 Agent 参与写操作。写操作应尽量由单一、可审计的服务执行。

9. MCP 与多 Agent 的区别

  • MCP 是连接和能力暴露协议；
  • 多 Agent 是任务分解和角色协作架构；
  • MCP 可以被单 Agent 使用；
  • 多 Agent 可以不使用 MCP，直接调用内部服务；
  • 二者叠加时，权限控制仍应位于 Host、服务端和业务系统，不应由模型承担。
