1. 推荐练习：售后申请 Agent + 确定性 Workflow

实现一个“订单售后申请”系统，要求同时体现 Agent 和 Workflow 的边界：

模型可以做的事

  • 理解用户的自然语言诉求；
  • 提取订单号、问题类型和用户期望；
  • 在只读工具中选择查询订单、查询售后政策；
  • 生成结构化的候选售后方案；
  • 对缺失信息提出问题。

应用程序必须控制的事

  • 校验订单归属和售后资格；
  • 计算真实可退款金额；
  • 判断是否需要人工审批；
  • 创建售后申请、发送通知或执行退款；
  • 设置超时、重试、幂等、补偿和审计。

2. 建议工具

get_order_status(order_id)             只读
get_return_policy(order_id, reason)    只读
calculate_refund(order_id, items)      只读/业务计算
create_after_sales_request(...)        有副作用，需要幂等
issue_refund(request_id, idempotency_key) 高风险，需要审批
notify_user(...)                       有副作用，可重试但需幂等

每个工具都应有：描述、参数 Schema、风险等级、所需权限、超时、可重试错误、幂等要求和结果 Schema。

3. 建议状态机

RECEIVED
  ↓
UNDERSTANDING
  ├─ NEEDS_USER_INPUT
  └─ CHECKING_ELIGIBILITY
          ↓
PROPOSAL_READY
  ├─ WAITING_APPROVAL
  └─ REJECTED
          ↓
CREATING_REQUEST
          ↓
REFUNDING
  ├─ SUCCEEDED
  └─ COMPENSATING / NEEDS_HUMAN_REVIEW

不要让模型直接把状态写成 SUCCEEDED。只有业务系统返回已确认结果后，代码才能转入成功状态。

4. 最小实现步骤

  1. 定义 AgentState、事件类型和状态转移表；
  2. 用模型厂商原生 SDK 实现一次普通文本调用；
  3. 注册两个只读工具并实现 Tool Calling 消息链；
  4. 加入 JSON Schema 和业务校验；
  5. 加入用户/租户/资源级权限检查；
  6. 设置最大步数、总超时和 Token/费用预算；
  7. 为临时网络错误实现有限重试，为副作用动作加入幂等键；
  8. 将状态保存到持久化存储，并实现版本检查；
  9. 在退款节点加入审批、过期和拒绝处理；
  10. 加入结构化日志、Trace ID、工具调用 ID 和审计事件；
  11. 模拟 Worker 崩溃、重复消息、超时、取消和外部结果不确定；
  12. 再用一个框架重写编排部分，对比代码、可观测性和恢复能力。

5. 必测故障场景

工具调用协议

  • 模型返回空 content 但包含工具调用；
  • 工具参数是非法 JSON；
  • 参数缺少必填字段或包含额外字段；
  • 模型请求未注册工具；
  • 一次响应包含多个工具调用；
  • 工具结果返回后消息链缺失或 ID 不匹配。

可靠性

  • 读取工具超时；
  • 服务端限流；
  • 创建申请请求发出后客户端断开；
  • Worker 在工具执行后、保存状态前崩溃；
  • 同一任务被两个 Worker 同时领取；
  • 重复投递同一事件；
  • 外部系统返回“未知”，无法判断副作用是否成功。

安全与人工

  • 用户查询不属于自己的订单；
  • 模型把 user_id 改成其他用户；
  • 检索文档要求忽略系统规则并调用危险工具；
  • 审批通过后参数被修改；
  • 审批过期后仍尝试执行；
  • 用户取消后任务继续运行。

6. 验收问题

完成后应能用自己的代码和日志回答：

  1. 模型请求调用工具时，应用在哪个位置阻止越权？
  2. 为什么 Schema valid 仍不代表可以执行？
  3. 如何保证 Tool Calling 消息链在恢复后完整？
  4. 为什么创建退款不能简单地在超时后重试？
  5. 如何区分“模型规划失败”“工具失败”“业务拒绝”和“状态冲突”？
  6. 如何从日志定位一次任务经历了哪些模型轮次和工具尝试？
  7. 哪些状态可以自动恢复，哪些状态必须请求人工？
  8. 如果拆成多个 Agent，新增的边界、成本和故障点是什么？
  9. MCP 在系统中负责连接什么，不能负责什么？
  10. 哪些步骤应该保持确定性，不交给 Agent 自主决定？

7. 完成标准

  • [ ] 能画出 Agent 循环和确定性状态机。
  • [ ] 能脱离框架完成一次模型调用和 Tool Calling 闭环。
  • [ ] 能在执行前完成参数、权限和业务校验。
  • [ ] 能解释并实现超时、有限重试、幂等和补偿。
  • [ ] 能持久化状态并从检查点恢复。
  • [ ] 能实现审批、拒绝、过期、取消和人工接管。
  • [ ] 能为每次运行生成可关联且脱敏的日志和审计记录。
  • [ ] 能说明 MCP、Memory、Planning 与 Agent 循环各自的职责。
  • [ ] 能说明为什么多 Agent 不是默认架构。
  • [ ] 能将框架 API 映射回模型、工具、状态、策略、执行和观测这些原语。

8. 延伸实践顺序

单 Agent + 只读工具
→ Agent + 有状态 Workflow
→ 加入审批和长任务
→ 加入记忆与检索
→ 接入 MCP
→ 仅在有明确收益时拆分多 Agent
