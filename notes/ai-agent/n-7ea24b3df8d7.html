1. 学习结果，而不只是知识清单

面向 AI Agent 的 Python 学习可以分为四层：

层次 核心问题 对应章节
语言表达 如何可靠地表达数据和行为？ 01～04
工程边界 如何处理错误、日志、模块、依赖和测试？ 05、09
运行模型 如何同时等待多个慢 I/O，并避免资源失控？ 06
产品接口 如何处理数据、暴露 API、组织 Agent 循环？ 07、08、10

真正的学习目标是把这四层连接起来。例如，一个“搜索并总结”的 Agent 不只是调用两次 API，它还需要：

  • 用 Pydantic 验证工具参数；
  • 用 asyncio 并发搜索并设置超时；
  • 用异常类型区分可重试错误和永久错误；
  • 用上下文管理器关闭 HTTP 客户端；
  • 用日志记录请求 ID、工具耗时和结果状态，但不泄露密钥；
  • 用 pytest 和假模型验证调度逻辑；
  • 用 FastAPI 暴露稳定的请求/响应协议。

1.1 用一条请求串起整套知识

当客户端发送“比较上海和北京的天气”时，代码大致经历下面的路径：

HTTP JSON
  │ FastAPI + Pydantic：验证字段、长度和权限
  ▼
Agent.run(request)
  │ list 保存消息；dataclass 保存运行状态；dict 查找工具
  ▼
模型适配器
  │ async/await 等待网络；timeout 控制单次预算
  ▼
结构化工具决策
  │ Pydantic 再次验证模型生成的工具名和参数
  ▼
并发工具执行
  │ TaskGroup + Semaphore + 异常边界 + 日志上下文
  ▼
结果聚合
  │ 生成器可流式输出；上下文管理器关闭连接
  ▼
API 响应、日志与评测数据
  │ pytest 验证控制流；Pandas 分析成功率和延迟

这说明章节不是孤立课程。容器决定状态如何表达，类型和 Pydantic 决定边界是否可靠，异步决定等待期间系统能否处理其他请求，日志和测试决定失败是否可定位、行为是否可复现。

1.2 三类学习目标

每个知识点都从三个角度验收：

角度 要回答的问题 示例
语义 代码在 Python 中究竟如何工作？ 列表赋值复制的是引用，不会自动深拷贝对象
工程 这种能力如何减少真实项目故障？ Pydantic 在工具执行前拒绝多余字段和错误类型
Agent 它在模型、工具、状态或服务哪一层出现？ asyncio.Semaphore 限制同时调用外部模型的数量

只会背 API 属于“语法记忆”；能解释语义、判断选型并处理失败路径，才属于可迁移能力。

2. 环境准备

先确认 Python 版本：

python --version

建议使用 Python 3.11 或更高版本。创建一个练习目录和虚拟环境：

mkdir python-agent-lab
cd python-agent-lab
python -m venv .venv
source .venv/bin/activate

Windows PowerShell 激活命令：

.venv\Scripts\Activate.ps1

最小练习依赖可以使用 uv 安装：

下面命令假设已经安装 uv；可先执行 uv --version 检查。若未安装，请按第 9 章的环境管理说明选择 uv，或直接使用后面的标准 venv + pip 方案。

uv init
uv add pydantic fastapi uvicorn numpy pandas
uv add --dev pytest pytest-asyncio httpx ruff mypy

也可以使用标准 venv + pip：

python -m pip install pydantic fastapi uvicorn numpy pandas
python -m pip install pytest pytest-asyncio httpx ruff mypy

工具选型与锁文件见第 9 章。此处只需选一种方式，不要在同一个练习项目里混用多个依赖管理器的锁文件。

2.1 验证解释器与虚拟环境

激活环境后执行：

python -c "import sys; print(sys.executable); print(sys.version)"
python -m pip --version

第一条显示当前解释器路径和版本；第二条确认 pip 属于同一个 Python。若路径没有指向项目的 .venv，说明环境没有正确激活。使用 uv 时，可以不激活环境而统一写成：

uv run python -c "import sys; print(sys.executable)"
uv run pytest -q

uv run 会按项目配置准备并使用环境。一个项目选择一种稳定工作流即可；“激活环境”和“通过工具运行”只是两种入口。

2.2 建立最小反馈循环

开始学习前确保四条命令可用：

python -m pytest -q
ruff check .
ruff format --check .
mypy src

项目初期某些目录可能还不存在，可以在创建源文件后再运行。它们分别回答：行为是否正确、代码是否有明显缺陷、格式是否一致、类型契约是否自洽。不要等项目写完才第一次运行。

2.3 编辑器只做辅助

让编辑器选择项目虚拟环境的解释器，以获得补全、跳转和类型提示。但最终以命令行检查为准，因为 CI 不会共享你的编辑器缓存和个人插件配置。

3. 建议目录

学习时可以建立一个贯穿全程的小项目：

python-agent-lab/
├── pyproject.toml
├── README.md
├── src/
│   └── mini_agent/
│       ├── __init__.py
│       ├── models.py       # Pydantic 请求、响应和工具参数
│       ├── tools.py        # 工具与注册表
│       ├── runtime.py      # Agent 循环与调度
│       ├── log_config.py   # 日志配置，避免与标准库 logging 同名
│       └── api.py          # FastAPI 应用
└── tests/
    ├── test_tools.py
    ├── test_runtime.py
    └── test_api.py

采用 src 布局能避免测试时意外导入工作区根目录中的同名模块。项目还很小时无需创建大量分层；上面的边界对应明确职责，足够支撑练习。

各文件的依赖方向应尽量清楚：

文件 可以依赖 不应承担
models.py Pydantic、标准类型 网络调用、数据库写入
tools.py 参数模型、外部客户端接口 HTTP 路由、模型供应商响应类
runtime.py 模型协议、工具注册表、状态对象 FastAPI Request、全局密钥读取
log_config.py logging、上下文字段 业务决策
api.py FastAPI、请求响应模型、runtime 服务 完整 Agent 控制循环
tests/ 公共接口、fake/mock 真实生产密钥和不受控网络

依赖方向不是为了“分层看起来专业”，而是为了让核心控制流能脱离 Web 服务器和真实模型独立测试。

3.1 从单文件开始，再按变化原因拆分

练习第一天可以只有 main.py。出现下列信号后再拆文件：

  • 同一数据模型被 API、工具和测试共同使用；
  • 更换模型 SDK 时不希望修改 Agent 循环；
  • 工具数量增加，需要注册表和权限策略；
  • 测试需要单独替换网络边界；
  • 一个文件同时频繁因 API、业务逻辑和日志配置而修改。

不要按代码行数机械拆分，也不要为每个类创建单独文件。

4. 八周路线参考

第 1 周：数据容器与函数

  • 掌握列表、元组、字典、集合及其选择原则；
  • 理解对象引用、可变性、浅拷贝；
  • 写出有明确输入、输出和异常契约的函数。

里程碑：实现一个“工具注册表”，支持注册、查询、去重和列出能力。

验收标准：重复工具名会失败；未知名称有明确异常；能解释为什么注册表使用 dict，能力标签使用 set，工具展示顺序可使用 list。

第 2 周：类与 Python 协议

  • 用组合组织对象，知道什么时候才需要继承；
  • 掌握常见魔术方法；
  • 学会迭代器、生成器和上下文管理器。

里程碑：实现可迭代的消息历史，以及记录工具耗时的上下文管理器。

验收标准：消息历史不会暴露内部可变列表；上下文管理器在工具抛错时仍记录耗时；能说明组合为什么通常比深继承更容易替换模型与工具。

第 3 周：类型与数据边界

  • 给业务代码添加类型标注；
  • 用 dataclass 表达内部状态；
  • 用 Pydantic 验证外部请求、模型结构化输出和工具参数。

里程碑：错误输入不能进入工具实现，并能返回清晰验证错误。

验收标准：缺字段、错类型、多余字段和跨字段不变量均有测试；能说明静态类型检查不能替代 Pydantic 的运行时验证。

第 4 周：工程化

  • 设计异常层级；
  • 配置模块化日志；
  • 使用 pyproject.toml、虚拟环境和锁文件；
  • 用 pytest 编写单元测试。

里程碑：项目能被全新环境安装，测试不依赖网络和真实密钥。

验收标准：删除 .venv 后可从声明文件和锁文件重建；日志包含请求 ID 但不含密钥；正常路径和异常路径都有 pytest 用例。

第 5 周：并发与异步

  • 区分并发和并行；
  • 使用 asyncio.TaskGroup、超时、取消、信号量；
  • 知道阻塞代码如何影响事件循环；
  • 理解 GIL 对线程和进程选择的影响。

里程碑：并发执行三个模拟工具，限制并发为 2，并在总超时后取消剩余任务。

验收标准：记录显示同时运行数从不超过 2；超时后没有遗留任务；把阻塞函数直接放进事件循环的反例能够被测试或计时发现。

第 6 周：数据处理

  • 使用 NumPy 处理向量和批量数值；
  • 使用 Pandas 清洗 Agent 日志、统计耗时和成功率；
  • 避免逐行循环和链式赋值等常见问题。

里程碑：从 CSV 日志生成按工具分组的 P50/P95 延迟与失败率报告。P50 通常就是中位数，P95 表示约 95% 的观测值不超过该值。

验收标准：非法类型、重复调用 ID 和缺失字段会被发现；报告同时展示样本量，避免用很小样本的百分位数误导决策。

第 7 周：Agent API

  • 用 FastAPI 建模请求与响应；
  • 使用依赖注入和生命周期管理共享客户端；
  • 理解 Uvicorn、流式响应和 WebSocket 的边界。

里程碑：Agent API 具备健康检查、结构化错误、请求 ID、超时和测试。

验收标准：请求模型拒绝未知字段；工具错误不会泄露内部异常；流式连接断开能传播取消；多个 Uvicorn worker 不依赖进程内会话字典共享状态。

第 8 周：综合 Agent

  • 实现最小 ReAct 风格循环；
  • 工具调用有白名单、参数验证、步数限制和错误边界；
  • 使用假模型完成确定性测试；
  • 写出运行说明和风险清单。

里程碑：通过第 10 章的综合验收。

验收标准：核心循环能用假模型确定性复现；工具调用有白名单、参数模型、步数/并发/结果大小/时间上限；真实模型只存在于适配器层。

4.1 每周的日常节奏

可用下面的五天循环，不要求一次读完整章：

  1. 第一天读概念并手敲最小示例；
  2. 第二天改变输入，主动制造错误和边界条件；
  3. 第三天完成小练习并写测试；
  4. 第四天把知识点接入贯穿项目；
  5. 第五天在不看笔记的情况下重新实现，并记录仍然含糊的问题。

每次学习控制在一个可验证问题，例如“取消如何传播”，而不是笼统地写“今天学习 asyncio”。

5. 学习时必须建立的五种习惯

5.1 先定义数据契约

在写逻辑前回答：输入是什么类型？哪些字段必需？输出是否稳定？错误如何表示？Agent 系统大量问题来自字符串和松散字典在边界间无约束传播。

可以先写一张契约卡：

能力：search
输入：query: 非空字符串；top_k: 1..20
输出：至多 top_k 个 {title, snippet, source_id}
错误：invalid_arguments / timeout / temporary_failure
副作用：只读
资源限制：3 秒、最大 64 KiB 结果

契约明确后，Pydantic 模型、工具函数、测试和日志字段都会更容易设计。

5.2 把外部系统视为不可靠

模型、搜索服务、数据库和网络都可能超时、限流、返回畸形数据。调用它们时至少考虑：

  • 超时；
  • 有界重试；
  • 取消；
  • 并发限制；
  • 错误分类；
  • 幂等性；
  • 可观测性。

这些保护不是平均堆在每一层。HTTP 客户端负责连接/读取超时，工具执行器负责工具总预算，Agent runtime 负责整轮步数和时间，API 层负责请求身份、配额和稳定错误响应。

5.3 核心逻辑与 I/O 分离

让“选择哪个工具、如何更新状态”尽量成为可测试的纯逻辑，让网络调用留在边界。这样测试不需要真实模型，失败也更容易定位。

例如，不要让 choose_next_action() 内部自己创建模型客户端。把客户端或 Model 协议作为参数传入，测试时替换为返回固定决策的假实现。

5.4 示例必须运行

不要把“看懂”当成“掌握”。每段关键代码至少运行一次，再主动构造：空输入、错误类型、超时、重复数据、大数据量或任务取消。

运行时记录三件事：实际输出、与你预测不同的地方、导致差异的语义。只复制终端结果而不写预测，学习效果有限。

5.5 每周做一次重构

重构前先补测试，然后检查：

  • 是否有重复逻辑可以删除？
  • 函数是否同时承担验证、I/O、计算和展示？
  • 异常是否被无差别吞掉？
  • 类型标注是否揭示了一个含糊的数据模型？
  • 并发是否有上限和退出路径？

一次只围绕一个问题重构，并在前后运行同一组测试。若同时改数据模型、并发结构和日志，很难判断失败来自哪里。

5.6 先读异常的最后一行，再沿调用链定位

Python traceback 通常从调用入口逐层展示，最后一行给出异常类型和消息。调试顺序可以是：

  1. 确认异常类型、消息和触发输入；
  2. 找到 traceback 中第一个属于自己项目的行；
  3. 用更小输入稳定复现；
  4. 检查数据类型、对象身份、状态和边界条件；
  5. 修复前先写一个会失败的测试；
  6. 修复后同时运行目标测试和相关回归测试。

异步错误还要检查任务是在何处创建、谁在等待、取消/异常由谁接收。

6. 如何判断一个知识点已经掌握

使用四级标准：

级别 表现
识别 看到代码能说出它在做什么
使用 能参考文档完成常规任务
解释 能说明选择它而非其他方案的原因
迁移 能在新的 Agent 场景中识别并正确应用

例如，“会 asyncio”不是能写出 await，而是能解释某段工作为什么是 I/O 密集、如何限制并发、取消会传播到哪里、阻塞函数该如何隔离。

6.1 使用“无提示复现”测试掌握程度

合上笔记，从空文件实现一个缩小版任务。如果只能照抄语法，说明还停留在“使用”层级以下；如果能自行设计边界并解释取舍，才接近“迁移”。

以 Pydantic 为例：

  • 识别：看懂 Field(ge=1, le=20)；
  • 使用：能定义工具参数模型；
  • 解释：能说明为何工具参数使用 extra="forbid"；
  • 迁移：面对新的邮件工具，能自行加入跨字段验证、副作用策略和脱敏错误。

6.2 建立错误样例库

为每章保存少量反例：共享可变默认值、宽泛 except、在 async def 中调用阻塞函数、Pandas 链式赋值、模型生成未知工具等。能解释反例为什么错，通常比只收藏正确模板更能帮助迁移。

7. 暂时不必过早学习的内容

初学阶段可以暂缓：

  • 元类、描述符的复杂用法；
  • 手写事件循环；
  • 过早研究某个 Agent 框架的所有抽象；
  • 为简单项目引入复杂的分布式任务系统；
  • 没有评测目标就进行大规模提示词“优化”；
  • 一开始就搭建复杂微服务或 Kubernetes。

先完成可测试的单进程 Agent，再根据真实瓶颈扩展。

判断是否需要继续深入的依据应该是：当前项目出现了真实需求、性能测量显示瓶颈，或基础抽象已经不能表达业务，而不是“高级主题看起来更厉害”。

8. 进入真实模型 SDK 前的检查表

  • [ ] 能用 Pydantic 定义并验证嵌套工具参数；
  • [ ] 能把模型客户端注入 Agent，而不是在函数内部创建全局客户端；
  • [ ] 能对调用设置超时并处理取消；
  • [ ] 能隐藏 API 密钥并避免记录敏感内容；
  • [ ] 能使用假模型重放预设响应；
  • [ ] 能限制工具白名单、调用次数、结果大小和并发；
  • [ ] 能区分用户错误、工具错误、模型错误和系统错误；
  • [ ] 能用日志把一次请求中的模型调用和工具调用串起来；
  • [ ] 能通过锁文件重建开发环境。

满足后，再学习具体 SDK 的消息格式、流式接口、工具调用协议和结构化输出，会容易很多。
