完成本章后，你应该能够：

  • 解释为什么快速召回之后还可能需要重排；
  • 区分双编码器（Bi-Encoder）与交叉编码器（Cross-Encoder）的输入和复用方式；
  • 说明候选数量、排序质量和延迟之间的基本权衡；
  • 识别重排不能修复的漏召回、权限、版本与来源问题。

从“找一篮子候选”到“仔细排队”

第一阶段检索面对的常常是成千上万甚至更多文本块。它需要快速缩小范围，因此会采用可以 预先建立索引、快速比较或高效匹配的方法。这个阶段更像从仓库里挑出一篮子“可能有关” 的资料，而不是逐条做完整阅读理解。

问题在于，快速相似并不等于精确支持。问题“试用期员工能申请远程办公吗？”可能同时 召回以下候选：

  1. 现行制度中明确说明适用员工范围的条款；
  2. 只出现“试用期”的考勤说明；
  3. 已过期的远程办公通知；
  4. 讨论正式员工远程办公设备的条款；
  5. 其他部门的试行方案。

重排器会接收问题和较小的候选集，再计算一组更适合细粒度排序的信号。它可以把同时覆盖 问题关键条件的候选提前，但是否需要重排，应由实际错误、评估结果和运行预算决定。若第一 阶段已经满足任务要求，增加重排只会增加复杂度。

双编码器：分别表示，快速比较

双编码器分别处理查询和文档。概念流程是：

查询 -> 查询向量

文档 -> 文档向量

然后系统比较两个向量的相似度。文档向量通常可以预先计算并建立索引，同一个文档表示也 可以被许多查询复用。这使双编码器很适合大规模候选召回。

“双”不一定表示必须有两个完全不同的模型实例，而是强调查询与文档先各自得到表示， 两者在最后比较。由于文档表示在看见当前查询之前已经生成，它不能针对每个问题重新审视 文档中的具体词序、否定、数字和条件组合。

双编码器的优势通常来自可复用表示和高效比较；它的限制来自交互发生得较晚、较简单。 不能据此断言所有双编码器都比所有交叉编码器差，实际结果还受训练数据、语言、领域、 输入截断和任务定义影响。

交叉编码器：把问题与候选一起阅读

交叉编码器把一个查询和一个候选组成联合输入，再输出这个查询—候选对的相关性分数。 模型处理候选时已经知道当前问题，因此可以更直接地观察两者之间的细粒度关系。

对于前面的例子，联合输入使模型有机会区分：

  • 候选是否同时讨论“试用期”和“远程办公”；
  • 条款是在允许、禁止还是仅描述申请流程；
  • 候选中的“试用”是在说员工身份还是某项工具试用；
  • 否定词、例外条件和适用范围是否与问题对应。

代价是每个查询都要与每个候选组成新的输入。候选越多，计算次数和输入量通常越大； 文档侧结果也难以像双编码器向量那样直接跨查询复用。因此交叉编码器常放在快速召回之后， 而不是对整个语料逐条运行。

两种方法不是互相替代的敌人

一个常见的两阶段管线是：

  1. 稀疏、稠密或混合检索取得候选；
  2. 执行权限、租户、时间和撤回状态过滤；
  3. 用交叉编码器为允许返回的候选重新打分；
  4. 选择少量候选进入上下文组织与回答阶段。

第一阶段重视在预算内不要漏掉重要资料，第二阶段重视把已有的相关资料排到前面。双编码器 可以承担第一阶段，交叉编码器可以承担第二阶段，但这只是常见组合，不是强制架构。 关键词检索也可以产生第一阶段候选，规则排序也可以成为第二阶段的一部分。

最重要的限制：未召回就无法重排

设第一阶段返回候选集合 C。重排器只能为 C 中的项目重新评分和排序，不能自动访问 集合外的资料。若正确条款不在 C 中，无论重排器多强，输出仍然缺少正确条款。

这条限制对排障很重要。最终答案错误时，应先问：

  1. 正确证据是否存在于知识库并且是当前版本？
  2. 正确文本块是否进入第一阶段候选？
  3. 是否被权限、时间或其他过滤错误移除？
  4. 若仍在候选中，重排是否把它压低？
  5. 若排在前面，后续上下文与回答是否正确使用？

跳过前四步，只调整重排模型或阈值，可能把漏召回问题误诊为排序问题。

一个纸面排序例子

问题是：“试用期员工能申请远程办公吗？”候选如下：

候选 内容概述 初排位置 需要进一步检查
A 现行制度：适用范围含试用期员工，但需主管批准 4 生效时间、适用地区、权限
B 考勤制度：试用期每日打卡要求 1 与远程办公关系很弱
C 两年前通知：试用期不参加远程办公试点 2 是否已失效或被替代
D 设备制度：正式员工借用远程办公设备 3 员工范围不匹配

仅看词语重合，B 和 C 可能靠前。细粒度重排可能把 A 提到第一，但系统仍需要用版本字段 确认 C 的状态，并在回答时保留 A 的批准条件。相关性排序不能替代这些检查。

候选输入怎样影响结果

候选文本边界

若文本块只保留“可以申请”，却把前一句“仅限转正员工”切到另一个块，重排器看到的内容 已经不完整。改进重排模型不能恢复被切断的限定条件，需要回到切分或父文档回取设计。

输入长度与截断

联合输入有长度限制时，系统需要记录查询、标题、正文和元数据怎样组合及截断。静默删除 候选末尾的例外条款，可能让排序分数看似正常却含义错误。

候选重复

相同内容的多个版本或重叠文本块会占用候选预算，也可能挤掉其他证据。去重应考虑来源、 版本和位置，不能只按相似度随意删除法律或制度上不同的条款。

权限与不可信内容

受限候选不应为了“先算分再说”而发送到外部重排服务。候选文本中的“忽略系统规则” 之类句子只是数据，不应成为重排流程的指令。

什么时候先不要加重排

  • 还不知道错误来自召回、过滤、排序还是回答；
  • 没有带相关性标注或至少可人工复核的代表性查询；
  • 第一阶段候选中经常没有正确证据；
  • 权限、版本和删除链路尚未可靠；
  • 延迟或费用预算无法容纳额外阶段；
  • 没有超时、失败和回退策略。

先建立简单基线，保存每个阶段的候选与原因，再判断重排是否解决了真实问题。

候选排序练习

为纸面例子中的 A、B、C、D 写出你的目标顺序。对每次位置调整注明理由，理由必须来自 问题与候选内容，不能只写“模型分数更高”。然后回答：如果 A 不在候选表里，你会检查 哪一个上游阶段？如果 C 没有版本字段，重排器缺少了什么判断依据？

最后写一个两阶段方案，明确第一阶段候选数、过滤位置、重排后保留数和失败时回退行为。 数字只是实验起点，不要把纸面练习中的数量当作生产默认值。

自测

  1. 双编码器为什么适合大规模候选召回？

  3. 为什么相关候选未进入第一阶段时，重排无法补救？
  4. 权限过滤为什么必须在候选发送给重排服务之前完成？
  5. 文本切分错误怎样被误判成重排器错误？
