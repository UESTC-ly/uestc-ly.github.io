1. 本节定位

在 RAG 中，检索质量不只取决于向量库或关键词算法。用户说出来的问题往往是口语化的、缺少上下文的，或者同时包含多个子问题；即使召回了候选文档，候选结果的顺序也未必适合直接交给生成模型。

本节关注检索链路中的三个环节：

  1. Query Rewrite（查询改写）：把用户原始问题转换成更适合检索的查询；
  2. 意图识别（Intent Recognition）：判断用户想查什么、应使用哪种检索策略，以及是否需要结构化过滤或路由；
  3. Rerank（重排）：对初步召回的候选结果进行更精细的相关性排序。

可以把它们概括为：

先理解问题，再生成适合检索的表达，最后从候选证据中选出最相关的内容。

2. 学习目标

完成本节后，应能够：

  • 识别用户问题中的检索意图、时间范围、实体、约束条件和多个子问题；
  • 区分查询改写、查询扩展、查询分解和答案生成；
  • 处理多轮对话中的指代、省略、口语化表达和歧义；
  • 理解初步召回与精排的职责边界；
  • 选择适合的 Rerank 方法，并在效果、延迟和成本之间做权衡；
  • 设计可观测、可回退、可评估的查询理解与重排链路。

3. 在 RAG 流程中的位置

一个常见的检索链路如下：

用户问题
  ↓
查询理解与意图识别
  ↓
查询改写 / 查询分解 / 过滤条件提取
  ↓
初步召回（关键词、向量或混合检索）
  ↓
候选集合
  ↓
Rerank 重排
  ↓
上下文压缩、去重与组装
  ↓
答案生成与引用

三个环节的边界可以这样理解：

环节 主要问题 典型输出
查询改写 用户的表达是否适合检索 一个或多个检索查询
意图识别 用户要查什么、怎么查 意图、实体、过滤器、路由决策
初步召回 哪些文档可能相关 候选文档集合
Rerank 候选文档中哪些最相关 带新排序分数的候选列表
生成 如何基于证据回答 最终答案与引用

需要特别注意：Query Rewrite 和 Rerank 都可能提升检索效果，但它们作用在不同位置。改写改变的是检索输入；重排改变的是候选结果的顺序。

4. 为什么原始查询经常不适合直接检索

4.1 口语化和省略

用户可能说：

这个配置怎么改？

如果没有上一轮对话或当前页面信息，“这个配置”缺少可检索的实体。查询理解阶段需要补全上下文，而不能让向量检索自行猜测。

4.2 指代和多轮上下文

例如：

用户：如何配置文档权限？
助手：可以按租户和用户角色配置。
用户：那它和数据过滤有什么区别？

第二个问题中的“它”需要结合上一轮确定指代对象。适合检索的独立查询可以是：

文档权限控制与数据过滤的区别是什么？

4.3 一个问题包含多个检索目标

例如：

介绍混合检索的原理，并说明它在延迟和召回率方面有什么影响。

它至少包含“原理”和“性能影响”两个目标。如果只使用整句检索，某些系统可能只召回其中一部分证据。可以将其拆为多个子查询，再合并和去重结果。

4.4 使用了文档中的别名或不同术语

用户说“重排”，文档可能使用“二阶段排序”；用户说“知识库”，文档可能使用“文档索引”。查询扩展可以补充同义词、缩写或相关术语，但不能无限添加概念，以免引入无关结果。

4.5 查询包含非检索内容

“请用通俗的语言、分三点回答，并举一个例子”主要是回答格式要求，不一定应该原样送入检索器。可以把问题拆成：

  • 检索目标：需要查找的事实或规则；
  • 回答约束：语言、格式、长度、受众等生成阶段要求。

5. 意图识别：先判断用户想做什么

5.1 常见检索意图

在一个 RAG 应用中，可以根据业务定义意图。通用示例包括：

意图 说明 可能的检索策略
事实查询 查找某个定义、数值或规则 直接检索，优先返回精确证据
操作指南 询问如何配置、安装或排障 按步骤、版本和环境过滤
比较分析 比较两个或多个对象 分别召回对象资料，再做对齐比较
多跳问题 需要连接多份文档或多个事实 分解查询，分阶段检索
摘要归纳 总结某篇文档或一组材料 先定位目标文档，再做范围受限的总结
代码或配置查询 查找 API、参数、示例或错误原因 保留版本、语言、框架等结构化条件
闲聊或无须检索 不依赖项目知识即可回答 直接回答或走普通对话链路
无法判断 信息不足或存在多种解释 追问澄清，或使用低风险回退策略

意图分类不是为了给所有问题贴上唯一标签，而是为了帮助系统做出后续决策：是否检索、检索哪些数据源、使用哪些过滤条件、是否拆分查询以及需要多少候选结果。

5.2 从问题中提取结构化信息

一个实用的意图识别输出可以包含：

{
  "intent": "操作指南",
  "query": "如何配置文档权限",
  "entities": ["文档权限"],
  "filters": {
    "product": null,
    "version": null,
    "tenant": null,
    "time_range": null
  },
  "needs_retrieval": true,
  "needs_clarification": false,
  "sub_queries": []
}

字段不应为了“看起来完整”而随意增加。每个字段都应该能影响路由、过滤、检索或生成，否则会增加解析失败和维护成本。

5.3 结构化输出的工程约束

如果使用模型做意图识别，建议：

  • 预先定义有限的意图枚举，而不是允许模型自由发明类别；
  • 规定字段类型、必填字段和空值表达方式；
  • 对 JSON 解析失败设置回退路径；
  • 保存原始问题，不能只保留模型改写结果；
  • 低置信度时优先追问或使用原始查询，不要静默地做高风险路由；
  • 对权限、租户、时间和版本等过滤条件进行程序侧校验，不能完全信任模型提取结果。

6. Query Rewrite 的主要类型

6.1 查询规范化

目标是消除不影响语义的表达差异，例如：

  • 统一大小写、空白和标点；
  • 处理常见缩写、别名和产品名称；
  • 纠正明显的拼写错误；
  • 将相对时间转换为明确时间，但需要结合当前时间和业务时区；
  • 保留代码、版本号、错误码等不能被随意改写的字符串。

规范化通常是低风险、低延迟操作，可以优先用规则和词典完成，避免每个查询都调用模型。

6.2 指代消解与上下文补全

把依赖对话历史的短问题改写为独立问题。例如：

历史：项目使用混合检索。
当前：它为什么还需要向量检索？
改写：在混合检索中，为什么还需要使用向量检索？

补全时应遵守两个原则：

  1. 只补全已有上下文能够支持的信息；
  2. 无法确定时保留歧义或发起澄清，不能把猜测当成事实。

6.3 查询扩展

在原始查询之外生成相关表达，用于提高召回覆盖面。常见扩展包括：

  • 同义词和术语别名；
  • 缩写的全称；
  • 领域中的上下位词；
  • 用户问题中隐含但必要的检索关键词。

扩展查询应与原始查询一起保留，并在结果合并阶段记录每个候选来自哪个查询。扩展过度会扩大噪声集合，因此需要控制数量并评估收益。

6.4 查询分解

将复杂问题拆成能够分别检索的子问题。例如：

原问题：比较 BM25 和向量检索的原理、优缺点以及适用场景。

子查询 1：BM25 的原理和相关性计算依据是什么？
子查询 2：向量检索的原理和相关性计算依据是什么？
子查询 3：BM25 和向量检索各自的优缺点及适用场景是什么？

查询分解适合比较题、多跳题和包含多个实体的问题，但会带来额外请求和结果合并成本。分解后还需要确认所有子问题共同覆盖了原问题，避免只召回局部证据。

6.5 假设性答案或文档导向的查询

某些方法会先根据问题生成一个假设性答案、摘要或可能出现的文档表述，再用它进行向量检索。这类方法可能改善“问题语言”和“文档语言”差异较大的场景，但也可能把模型幻觉带入检索。因此：

  • 生成的假设内容只能作为检索表示，不能作为事实证据；
  • 仍应保留原始查询作为召回分支；
  • 必须通过离线评估确认它确实提升了召回，而不是只让结果更像模型预期。

7. 改写的输入、输出与安全边界

7.1 推荐保留多种表示

不要把原始问题直接覆盖掉。建议在一次请求中保留：

raw_query       用户原始问题
conversation    参与改写的有限对话上下文
standalone_query 独立可检索问题
search_queries  实际执行的一个或多个查询
intent          识别出的意图
filters         结构化过滤条件
rewrite_reason  改写原因或版本

这样可以在检索效果下降时判断问题来自用户表达、改写、过滤、召回还是重排。

7.2 改写提示词的核心要求

用于改写的提示词应明确：

  • 任务是生成检索查询，不是回答问题；
  • 不得凭空添加历史中不存在的实体、时间、版本或结论；
  • 需要保留专有名词、错误码、代码标识符和数字；
  • 如果信息不足，输出澄清标记或原始查询；
  • 输出固定格式，避免将解释性文字混入检索查询。

7.3 防止查询注入和越权扩展

用户输入、历史消息和被检索文档都可能包含不可信文本。查询改写器不应因为用户或文档中的指令而泄露系统提示、访问不该访问的资料或改变权限过滤器。

尤其要注意：

  • 权限条件应由可信的应用上下文注入，并在服务端强制执行；
  • 用户可以改变查询内容，但不能通过改写要求绕过租户或文档权限；
  • 文档中的“请忽略之前规则”等文本应被当作资料内容，而不是系统指令；
  • 记录改写前后的查询，便于审计和定位异常。

8. 初步召回与 Rerank 的职责边界

8.1 初步召回：追求覆盖面

初步召回通常需要在较大的文档集合中快速找到可能相关的候选。它更关心：

  • 相关文档是否进入候选集合；
  • 能否在可接受延迟内处理大规模数据；
  • 是否同时覆盖精确术语和语义相近表达。

如果真正相关的文档没有被召回，后续 Rerank 无法凭空恢复它。这就是为什么需要关注 Recall@K 等召回指标。

8.2 Rerank：追求前排精度

Rerank 接收初步召回的候选集合，对“查询—候选文本”的匹配关系进行更精细的判断。它更关心：

  • 最相关的证据能否排在前面；
  • 候选是否真正回答了当前问题，而不只是主题相似；
  • 是否识别了实体、数值、时间、否定和条件等细节。

Rerank 不应被当成“扩大召回范围”的替代品。它只能重排已经进入候选集合的内容。

8.3 两阶段检索的直觉

全量文档：数量大、单个文档处理成本必须低
    ↓ 低成本初步召回
候选文档：数量小、允许更复杂的匹配
    ↓ 高精度 Rerank
最终上下文：数量更小、交给生成模型

因此，Rerank 一般不直接对全量文档运行，而是在初步召回的有限候选上运行。

9. Rerank 的常见实现方式

9.1 词法打分

可以使用关键词匹配、BM25 分数、字段权重和规则分数进行重排。优点是速度快、解释相对直接；缺点是对同义表达、隐含语义和复杂语境的理解有限。

9.2 向量相似度重排

使用查询向量和候选向量的相似度重新排序。它能够识别一定程度的语义相近，但如果初步召回本身已经使用相同的向量分数，重复计算未必带来明显收益。

9.3 Cross-Encoder Rerank

Cross-Encoder 将查询和候选文本一起输入模型，直接预测二者相关性。由于模型可以同时观察两段文本的细节，通常比单独计算两个向量的相似度更适合精细判断；代价是每个候选都需要一次更昂贵的交互计算。

适用思路：

  • 初步召回数量较小；
  • 相关性比极低延迟更重要；
  • 文档片段长度和候选数量可控。

9.4 LLM Rerank

让大模型比较查询和多个候选，输出相关性判断或排序。它在复杂语义、规则解释和多跳问题上可能有帮助，但通常存在成本高、延迟高、输出不稳定和排序一致性不足等问题。

如果使用 LLM Rerank，应考虑：

  • 固定候选输入格式；
  • 要求输出可解析的候选 ID 和分数或等级；
  • 不要让模型把候选中的指令当成需要执行的指令；
  • 对排序结果做格式和范围校验；
  • 与更便宜的模型或规则方案比较增量收益。

9.5 规则与模型的组合

实际系统常采用组合评分，例如：

  • 先按权限、租户、版本和数据源做硬过滤；
  • 再融合 BM25、向量相似度和字段匹配分数；
  • 最后使用 Rerank 模型精排；
  • 对标题命中、最新版本、权威来源或用户指定文档增加经过验证的业务权重。

硬过滤和软排序必须区分：权限条件不能因为相关性分数高而被软排序覆盖。

10. 一个可落地的检索链路示例

以问题“上一版的 API 超时配置怎么改，和重试参数有什么关系？”为例，可以设计如下流程：

第一步：识别上下文

从会话和用户权限上下文中确定：

  • “上一版”对应的具体产品版本；
  • “API”对应的产品或服务；
  • 用户有权访问哪些文档。

如果版本无法确定，应该追问，而不是随意选择一个版本。

第二步：识别意图和约束

意图：操作指南 + 参数关系解释
实体：API 超时配置、重试参数
过滤器：产品版本 = 已确认的上一版
需要检索：是
是否需要分解：可能需要

第三步：生成检索查询

查询 1：上一版 API 超时配置修改方法
查询 2：API 超时参数与重试参数的关系
查询 3：上一版 API 超时配置和重试参数示例

第四步：初步召回

分别使用关键词、向量或混合检索召回候选，并记录每个候选来自哪一个子查询。随后进行去重，避免同一文档片段因多个查询重复出现。

第五步：Rerank

使用查询与候选片段的联合相关性判断，优先保留：

  • 明确属于目标版本的内容；
  • 同时解释超时与重试关系的内容；
  • 包含具体参数名、取值和操作步骤的内容。

第六步：生成与核验

生成阶段只使用通过权限过滤、重排和上下文整理后的证据。如果候选证据只能解释配置方法，不能证明二者关系，就应明确指出证据不足，而不是自行补充结论。

11. 结果合并与排序策略

当一个原始问题生成多个查询时，需要处理多个结果列表。常见策略包括：

11.1 直接合并后按统一分数排序

适合多个查询使用同一种检索器、分数尺度一致的情况。不同检索器或不同查询的分数往往不可直接比较，使用前需要验证分数含义。

11.2 轮流取各列表前排结果

可以先取每个查询的前几个结果，再进行去重和后续重排。这样能防止某一个查询的结果完全占据候选集合。

11.3 Reciprocal Rank Fusion

当不同检索器或查询的分数不可比时，可以利用候选在各列表中的名次进行融合。其直觉是：一个结果在多个列表中都排名靠前，通常更值得保留。融合参数和候选数量需要通过验证集调优。

11.4 按子问题设置配额

对比较题或多跳题，可以为每个子问题保留一定数量的候选，确保最终上下文不会只覆盖其中一个方面。之后再通过 Rerank、去重和上下文压缩控制总量。

12. 参数与延迟的权衡

检索链路中常见的可调参数包括：

  • 改写生成的查询数量；
  • 初步召回的候选数量；
  • Rerank 的候选数量；
  • 最终送入生成模型的片段数量；
  • 是否并行执行多个子查询；
  • 是否根据意图选择不同的模型和链路。

通常存在以下权衡：

调大参数 可能收益 可能代价
查询数量 提高覆盖面 模型调用和合并成本增加，噪声变多
初步召回数量 降低漏召回概率 传输、去重和重排成本增加
Rerank 候选数 有更多机会找出高相关片段 延迟与推理成本增加
最终上下文长度 可包含更多证据 可能稀释重点、增加生成成本

不要只以“召回越多越好”为目标。系统最终需要的是足够覆盖、前排准确、可被生成模型正确使用的证据。

13. 评估：不要只看最终答案

13.1 查询改写评估

可以检查：

  • 改写后是否保留了原问题的核心约束；
  • 指代是否正确消解；
  • 是否引入了原问题没有的实体、版本或时间；
  • 分解后的子查询是否覆盖原问题；
  • 改写是否让召回结果更好，而不是只让文本更通顺。

13.2 初步召回指标

  • Hit@K：正确证据是否出现在前 K 个结果中；
  • Recall@K：标注的相关证据有多少被前 K 个结果覆盖；
  • 候选覆盖率：正确答案所需的关键片段是否至少进入候选集合。

13.3 重排指标

  • MRR：第一个相关结果出现得有多靠前；
  • nDCG@K：考虑不同相关等级的排序质量；
  • Precision@K：前 K 个结果中相关结果的比例；
  • Top-K 相关性分布：观察高相关、部分相关和无关片段的构成。

13.4 端到端指标

还要评估：

  • 答案是否正确、完整并且直接回应问题；
  • 答案中的结论能否由引用证据支持；
  • 是否出现无依据扩展、版本混用或权限泄露；
  • P50、P95 延迟和单次请求成本；
  • 改写失败、解析失败、超时和回退的比例。

一个重要的诊断顺序是：

答案错误
  ↓
相关证据是否进入候选集合？
  ├─ 否：检查查询、过滤器和初步召回
  └─ 是：检查 Rerank、上下文组装和生成

14. 常见误区

误区一：改写得越详细越好

改写加入过多背景或推测内容，可能把检索方向带偏。改写的目标是提升可检索性，不是写一段完整答案。

误区二：只保留改写结果

一旦改写错误，系统就失去原始查询这一条回退路径。应保留原始查询，并在必要时并行召回原始查询和改写查询。

误区三：把 Rerank 当成召回器

真正相关的文档未进入候选集合时，Rerank 无法找回它。应先确认候选覆盖率，再判断重排模型是否有效。

误区四：只按主题相似度排序

“都在讲 RAG”不等于“能回答这个具体问题”。重排需要关注实体、版本、时间、参数、否定和问题约束。

误区五：让模型决定权限

权限过滤必须由可信的应用逻辑强制执行。模型可以帮助理解查询，但不能授权用户访问文档。

误区六：忽略多查询带来的重复和冲突

查询分解、同义词扩展和多路召回可能找到重复片段或不同版本的冲突内容。后续需要去重、版本处理、来源排序和引用溯源。

误区七：只用最终答案评价链路

最终答案变好或变坏，可能来自多个环节。应分别记录原始查询、改写结果、意图、过滤器、候选列表、Rerank 分数和最终上下文。

15. 推荐的最小实现路径

如果正在从零搭建一个 RAG 原型，可以按以下顺序迭代：

  1. 先实现原始查询的基础召回，并保存候选和分数；
  2. 加入对话历史截取和独立问题改写；
  3. 对改写结果与原始查询并行召回，比较候选覆盖率；
  4. 增加少量稳定的意图和过滤字段；
  5. 在固定候选数量上加入 Rerank；
  6. 增加去重、版本优先级和引用信息；
  7. 建立包含事实题、操作题、比较题、多轮指代题和歧义题的评估集；
  8. 只有在数据表明存在收益时，才增加查询分解、查询扩展或更昂贵的模型。

一个简单但可观测的记录结构可以是：

{
  "raw_query": "用户原始问题",
  "rewritten_queries": ["查询 1", "查询 2"],
  "intent": "事实查询",
  "filters": {},
  "retrieval_candidates": [
    {"id": "doc-1", "source": "vector", "score": 0.82}
  ],
  "reranked_candidates": [
    {"id": "doc-1", "score": 0.91}
  ],
  "fallback": null
}

实际项目中还应加入请求 ID、模型版本、索引版本、延迟和错误信息，但不应记录不必要的敏感内容。

16. 实践检查清单

  • [ ] 是否保留了用户原始问题？
  • [ ] 多轮问题是否被改写成了能够独立检索的表达？
  • [ ] 指代、版本、时间和实体是否有明确来源？
  • [ ] 无法消解的歧义是否会触发澄清，而不是被模型猜测？
  • [ ] 查询扩展是否同时带来了噪声和成本？
  • [ ] 多个子查询的结果是否去重并保留来源？
  • [ ] 权限、租户、版本等硬过滤是否在程序侧强制执行？
  • [ ] 相关证据如果未进入候选集合，是否有方法定位原因？
  • [ ] Rerank 是否只处理有限候选，而不是直接扫描全量文档？
  • [ ] 是否分别评估了召回、重排、引用支持和端到端答案？
  • [ ] 是否记录了延迟、成本、失败率和回退路径？

17. 小结

Query Rewrite、意图识别与 Rerank 是互相配合但不能互相替代的能力：

  • 意图识别回答“用户想完成什么，以及系统应该走哪条路”；
  • Query Rewrite把原始表达转换为更适合检索的一个或多个查询；
  • 初步召回负责尽量把可能相关的证据带入候选集合；
  • Rerank负责在候选集合中提高前排相关性；
  • 后续上下文处理负责去重、压缩、处理冲突并建立引用。

高质量的检索链路不是让模型“更会猜”，而是让每一步都有明确边界、可验证输入、可观测输出和可回退方案。
