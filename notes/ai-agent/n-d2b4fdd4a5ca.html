本节讨论 RAG 检索层中三类核心能力：基于倒排索引的 BM25、稠密向量与稀疏检索的混合检索，以及多个检索通道协同工作的多路召回。重点不在“选择某一个最好的检索器”，而在于构建能够同时覆盖关键词、语义、结构化条件和上下文关系的候选集。

1. 为什么 RAG 需要多种检索方式

RAG 的检索目标不是找一段“看起来相似”的文本，而是为当前问题找到足以支撑答案的证据。不同类型的问题依赖的匹配信号并不相同：

问题类型 更重要的信号 典型检索方式
“什么是向量数据库？” 语义相似性 向量检索
“错误码 E-1042 的处理方法是什么？” 精确词项匹配 BM25、字段检索
“2024 年华东区的报销规定” 时间、地域、业务字段 元数据过滤 + 关键词/向量检索
“某产品的安装步骤” 标题、章节和主题关系 标题检索 + 向量检索
“这段话中的它指什么？” 上下文和实体关系 相邻块、父块、实体检索
“用户以前问过类似问题吗？” 历史高质量问答 问答库检索

单一向量检索容易漏掉版本号、错误码、专有名词和数字条件；单一 BM25 又容易因为词语改写、同义表达或较长的自然语言问题而漏召回。因此，实际系统通常采用“多个通道召回，再统一排序”的架构。

2. BM25：基于词项匹配的稀疏检索

2.1 BM25 解决什么问题

BM25 属于基于倒排索引的稀疏检索方法。它不直接理解句子的语义，而是根据查询词和文档词项之间的统计关系计算相关性。

它特别适合以下场景：

  • 错误码、订单号、产品型号、版本号等精确词项；
  • 用户问题与文档使用相同术语的场景；
  • 标题、标签、章节名等短字段检索；
  • 需要解释“为什么召回这篇文档”的可解释检索；
  • 向量模型对低频专有名词、数字和符号表示不稳定的场景。

BM25 的“稀疏”并不是指文档很短，而是指一个文档在词项空间中通常只有少量非零特征。倒排索引会记录每个词出现在哪些文档中，以及该词在文档中出现的位置或次数。

2.2 倒排索引的基本过程

构建倒排索引通常包括以下步骤：

  1. 对文档进行分词或词法分析；
  2. 对词项进行规范化，例如统一大小写、处理全角半角、去除无意义符号；
  3. 记录词项到文档的映射；
  4. 保存词频、文档频率和文档长度等统计量；
  5. 查询时先根据词项找到候选文档，再计算相关性分数。

例如，假设文档集合中出现了“退款”“申请”“审核”等词，倒排索引可以记录：

退款 -> doc_01, doc_07, doc_13
申请 -> doc_01, doc_03, doc_07
审核 -> doc_01, doc_05

真实搜索引擎还会保存词频、位置、字段和权重等信息，以支持短语查询、字段查询和更精确的排序。

2.3 BM25 公式

BM25 对查询中的每个词项分别计算贡献，然后求和。常用形式如下：

\[ \operatorname{BM25}(D,Q)=\sum_{t\in Q}\operatorname{IDF}(t)\cdot\frac{f(t,D)(k_1+1)}{f(t,D)+k_1\left(1-b+b\frac{|D|}{\operatorname{avgdl}}\right)} \]

其中：

  • \(D\)：候选文档；
  • \(Q\)：用户查询；
  • \(t\)：查询中的词项；
  • \(f(t,D)\)：词项 \(t\) 在文档 \(D\) 中的出现次数；
  • \(|D|\)：文档长度；
  • \(\operatorname{avgdl}\)：语料库中的平均文档长度；
  • \(k_1\)：词频饱和参数；
  • \(b\)：文档长度归一化参数；
  • \(\operatorname{IDF}(t)\)：词项的逆文档频率。

一种常见的 IDF 定义为：

\[ \operatorname{IDF}(t)=\ln\left(1+\frac{N-\operatorname{df}(t)+0.5}{\operatorname{df}(t)+0.5}\right) \]

其中 \(N\) 是文档总数，\(\operatorname{df}(t)\) 是包含词项 \(t\) 的文档数。一个词出现在很多文档中时，区分度较低，IDF 也较小；一个低频且具有辨识度的词，往往能带来更高的匹配贡献。

2.4 参数含义与调优思路

\(k_1\)：词频饱和程度

词项第一次出现通常很重要，但同一个词重复几十次并不意味着文档相关性也线性增加。\(k_1\) 控制词频贡献的饱和速度：

  • 较小的 \(k_1\)：词频很快饱和，适合不希望重复词影响过大的场景；
  • 较大的 \(k_1\)：更重视词频，适合词频与主题相关性较强的语料。

\(b\)：文档长度归一化程度

\(b\) 控制长文档惩罚：

  • \(b\) 接近 1：更强地纠正文档长度，长文档中的偶然匹配不容易得高分；
  • \(b\) 接近 0：弱化长度影响，适合文档长度差异不大或长文档本身更有价值的语料。

工程上可以先使用搜索引擎的默认值，再根据离线评测集调参。不要把某组参数当成所有语料的固定最优解。技术文档、客服问答、法律条款和新闻语料的词频分布差异很大。

2.5 中文语料中的 BM25

中文不像英文那样天然以空格分隔单词，因此分词策略会显著影响 BM25 效果。常见做法包括：

  • 使用中文分词器生成词项；
  • 对产品名、错误码、版本号和组织名称增加自定义词典；
  • 同时保留字粒度或 n-gram 字段，以减少分词错误造成的漏检；
  • 对标题、正文、标签分别建立字段并设置不同权重；
  • 对英文缩写、数字、连字符和大小写制定统一规范。

例如，“RAG-2024.1 部署失败”不能只依赖普通中文分词。RAG-2024.1、部署失败 等整体词项或 n-gram 特征都可能是重要信号。

分词器必须在索引阶段和查询阶段保持一致。索引时使用一种分词规则、查询时使用另一种规则，可能造成看似相同的词实际上无法匹配。

2.6 BM25 的字段设计

与其把所有文本简单拼成一个字段，不如根据业务语义拆分字段：

- title：标题
- headings：章节标题、路径标题
- content：正文
- keywords：关键词和标签
- identifiers：产品型号、错误码、版本号
- author / department：作者或所属部门

可对不同字段设置不同权重。例如：

  • 标题命中通常比正文命中更有区分度；
  • 错误码和产品型号可以使用精确匹配或高权重字段；
  • 标签适合用于补充召回，但不应无条件压过正文证据；
  • 章节路径可以帮助判断同名术语所处的上下文。

字段权重需要通过评测验证，而不是仅凭直觉设置。标题很短时，过高的标题权重可能让一篇正文完全不相关的文档排在前面。

3. 稠密向量检索与 BM25 的互补关系

向量检索将查询和文档编码为向量，再通过相似度寻找语义接近的内容。它可以处理以下表达差异：

  • 查询和文档使用同义词；
  • 用户使用口语，文档使用正式术语；
  • 查询与答案之间存在一定改写；
  • 词面不完全重合，但主题和意图相近。

但向量检索也有明显局限：

  • 对错误码、版本号、数字和罕见实体可能不敏感；
  • 语义相近不等于能够回答问题；
  • 长文档或主题混杂的块可能产生平均化表示；
  • 相似度分数通常不能直接解释为“包含了哪些证据”；
  • 不同 embedding 模型生成的向量不能直接混用。

BM25 和向量检索的差异可以概括为：

维度 BM25 向量检索
匹配依据 词项、词频、文档频率 向量空间中的语义相似度
擅长内容 精确术语、数字、实体、版本号 同义表达、主题和意图
可解释性 较强 相对较弱
对分词依赖 较强 依赖 embedding 模型和文本切分
常见问题 词面不同就可能漏召回 语义相近但事实不匹配
典型用途 精确召回、补充召回 语义召回、泛化召回

因此，混合检索的目标不是简单地让两种分数相加，而是利用它们不同的错误模式扩大高质量候选集。

4. 混合检索

4.1 基本流程

一个典型的混合检索流程如下：

用户问题
  -> 查询预处理
  -> BM25 召回一批候选
  -> 向量检索召回一批候选
  -> 按稳定的 chunk_id 去重
  -> 合并或融合排序
  -> 可选的 reranker 重排
  -> 上下文压缩与组装
  -> 交给生成模型

两路检索应尽量并行执行，以降低整体延迟。融合前需要统一候选的标识、来源、文档版本和权限信息。

4.2 分数加权融合

最直接的方法是先对不同通道的分数进行归一化，再进行加权：

\[ S(d)=\alpha S_{dense}^{norm}(d)+(1-\alpha)S_{sparse}^{norm}(d) \]

其中：

  • \(S_{dense}^{norm}(d)\)：归一化后的向量相似度；
  • \(S_{sparse}^{norm}(d)\)：归一化后的 BM25 分数；
  • \(\alpha\)：向量通道的权重；
  • \(S(d)\)：融合后的候选分数。

不能直接把原始 BM25 分数和向量距离相加，因为：

  • 两种分数的取值范围不同；
  • 不同查询的 BM25 分布可能差异很大；
  • 向量库可能返回余弦相似度、内积或距离，方向甚至相反；
  • 候选数量、过滤条件和索引实现会影响分数分布。

可选的归一化方法包括 min-max、z-score、分位数归一化和基于历史查询的校准。min-max 形式为：

\[ S^{norm}(d)=\frac{S(d)-S_{min}}{S_{max}-S_{min}+\epsilon} \]

但 min-max 对单个查询中的异常值较敏感。线上系统应通过离线数据观察分数分布，并验证归一化策略是否稳定。

4.3 RRF：基于排名的融合

当不同检索器的分数难以校准时，可以使用 Reciprocal Rank Fusion，即倒数排名融合。其基本形式为：

\[ \operatorname{RRF}(d)=\sum_{i=1}^{m}\frac{w_i}{k+\operatorname{rank}_i(d)} \]

其中：

  • \(i\) 表示第 \(i\) 个召回通道；
  • \(\operatorname{rank}_i(d)\) 是文档 \(d\) 在通道 \(i\) 中的排名；
  • \(w_i\) 是通道权重；
  • \(k\) 是平滑常数，用于避免第一名权重过度集中；
  • 如果文档没有出现在某个通道的结果中，则该通道不贡献分数。

RRF 的优点是只依赖排名，不要求不同检索器的分数具有相同量纲，通常是混合检索的稳健基线。它的不足是丢失了原始分数中的部分信息，因此在已经完成良好分数校准的系统中，学习排序或加权分数融合可能更有上限。

一个概念性实现如下：

from collections import defaultdict


def rrf_fuse(result_lists, weights=None, k=60):
    """result_lists: [ [(doc_id, score), ...], ... ]"""
    if weights is None:
        weights = [1.0] * len(result_lists)

    fused = defaultdict(float)
    details = defaultdict(list)

    for channel_id, results in enumerate(result_lists):
        for rank, (doc_id, original_score) in enumerate(results, start=1):
            contribution = weights[channel_id] / (k + rank)
            fused[doc_id] += contribution
            details[doc_id].append({
                "channel": channel_id,
                "rank": rank,
                "original_score": original_score,
                "contribution": contribution,
            })

    ranked = sorted(fused.items(), key=lambda item: item[1], reverse=True)
    return ranked, details

生产实现还需要补充权限过滤、索引版本、文档状态和重复块处理，不能只依赖 doc_id 的字符串排序结果。

4.4 混合检索的参数

常见参数包括：

  • BM25 初始召回数量 top_k_sparse；
  • 向量初始召回数量 top_k_dense；
  • 融合后候选数量 top_k_fused；
  • reranker 输入数量 top_k_rerank；
  • 最终送入模型的上下文数量 top_k_context；
  • 稀疏与稠密通道的权重；
  • 是否对不同查询类型采用不同权重。

不要只调最终上下文数量。若初始召回数量太小，后续融合和重排无法挽回漏召回；若初始数量过大，则会增加去重、重排和上下文压缩成本。更合理的做法是通过评测观察各阶段的召回覆盖率和延迟，再共同确定参数。

5. 多路召回

5.1 多路召回的含义

多路召回是在 BM25 和向量检索之外，根据数据结构和业务特征增加多个候选来源。每个通道都应该有明确的职责，而不是简单复制同一种检索。

常见通道包括：

  1. 向量检索：覆盖同义表达、概念表达和语义相关内容；
  2. BM25：覆盖精确词项、关键词、错误码和版本号；
  3. 标题或章节检索：优先定位主题明确、结构清晰的内容；
  4. 标签与元数据过滤：按产品、部门、时间、权限、语言和文档状态缩小范围；
  5. 实体或知识图谱检索：根据实体、关系和属性查找相关内容；
  6. 历史高质量问答：召回经过人工确认或用户反馈良好的问答；
  7. 父子块扩展：先命中细粒度子块，再补充其父块或相邻块；
  8. 链接和引用扩展：沿文档引用、相关文档或知识库链接补充证据；
  9. 规则通道：对错误码、SKU、合同条款编号、API 路径等结构化模式进行专门匹配。

5.2 过滤与召回要区分

元数据过滤和内容召回不是同一个阶段：

  • 硬过滤：权限、租户、文档状态、有效期等条件必须满足，通常应在检索前或检索过程中执行；
  • 软偏好：部门、主题、文档类型等条件可以作为排序特征，但不一定要完全排除其他结果；
  • 内容召回：根据文本、向量、实体和关系找到候选证据。

例如，用户只能访问某个租户的文档，这是权限约束，不能通过“召回后再过滤”来冒险处理，尤其不能让无权限文本进入重排或生成上下文。相反，“优先展示内部操作手册”可能是软偏好，可以通过字段权重或通道权重实现。

5.3 通道设计示例

以企业内部技术问答为例，可以设计如下候选通道：

A. dense_content：正文向量检索，top 50
B. bm25_all：正文和关键词 BM25，top 50
C. title_exact：标题或章节标题精确匹配，top 20
D. identifier：错误码、产品名、版本号匹配，top 20
E. metadata_filter：按租户、产品、版本和文档状态过滤
F. parent_expand：对命中的子块补充父块，top 10
G. sibling_expand：补充同章节前后相邻块，top 10
H. faq_history：高质量历史问答，top 20

这些结果首先通过稳定的 chunk_id 合并。对于同一个 chunk 被多个通道命中的情况，应保留命中来源、原始排名和分数，以便融合和调试，而不是简单覆盖。

5.4 多路召回的融合策略

可以采用以下几种策略：

方案一：并集后统一重排

将每个通道的结果取并集，去重后交给 cross-encoder 或其他 reranker。该方案简单、效果通常稳定，但重排成本可能较高。

方案二：每路设置配额

为关键通道保留最低数量，例如至少保留若干个精确匹配结果，再将剩余位置交给综合排序。这可以避免一个强势通道完全挤占候选集。

方案三：按查询类型动态路由

先识别查询特征，再调整通道：

  • 包含错误码、版本号或 API 路径：提高 BM25 和规则通道权重；
  • 以“什么是”“如何理解”开头：提高向量通道权重；
  • 包含“哪个部门”“截至某日期”：优先使用元数据过滤；
  • 询问“上一步”“其中的它”：增加父块和相邻块扩展；
  • 命中高置信度历史问答：将问答通道作为补充证据，但仍需检查版本和权限。

动态路由不应只依靠一个分类器的判断。分类错误会导致重要通道被关闭，因此关键系统通常保留一个基础 BM25 通道和一个基础向量通道作为兜底。

方案四：学习排序

当积累了足够的查询—文档相关性标注后，可以将以下特征交给排序模型：

  • BM25 分数及排名；
  • 向量相似度及排名；
  • 标题命中、关键词命中和实体命中；
  • 文档时间、版本和质量分；
  • 用户权限和业务优先级；
  • 文档与查询的长度、语言和字段匹配情况。

学习排序的效果依赖标注质量。没有可靠的相关性标签时，先使用 RRF 等稳健方法通常比盲目训练复杂排序模型更合适。

6. 去重、块扩展与上下文组装

6.1 去重

多路召回后可能出现三类重复：

  • 同一个 chunk 被多个通道命中；
  • 同一段内容因为不同版本或不同切分方式重复出现；
  • 相邻 chunk 内容高度重叠。

至少应区分以下标识：

document_id：逻辑文档标识
version_id：文档版本标识
chunk_id：当前切分块标识
parent_id：父块或章节标识

去重不能只按文本字符串完全相等判断，因为轻微空格、换行和格式差异也可能表示同一内容。可以先按稳定 ID 去重，再根据文档版本、内容指纹和重叠比例做二次处理。

6.2 父子块和相邻块扩展

细粒度 chunk 有利于精确召回，但可能缺少定义、前提、表格标题或结论。命中子块后，可以补充：

  • 父章节标题；
  • 同一段落的前后文；
  • 表格的表头和说明；
  • 代码块的语言、文件路径和上下文；
  • 引用的定义或前置条件。

扩展要有边界。盲目把整篇文档塞入上下文会引入噪声、增加 token 成本，并可能让模型忽略真正的证据。可为每次扩展设置最大字符数、最大块数和最大层级。

6.3 上下文排序

最终上下文不一定按检索分数简单降序排列。可以考虑：

  • 先放高置信度的核心证据；
  • 将同一文档或同一章节的相关块适当聚合；
  • 将标题、表头、定义放在对应正文之前；
  • 保留来源、版本和更新时间；
  • 避免把相互矛盾的版本混在一起；
  • 对过长内容进行压缩，但不要删除关键限定条件。

7. 一个可落地的检索流程

7.1 离线阶段

原始文档
  -> 清洗和格式规范化
  -> 提取标题、章节、表格、代码和元数据
  -> 切分为父块和子块
  -> 建立 BM25 倒排索引
  -> 生成 embedding 并写入向量索引
  -> 写入 document_id、version_id、chunk_id、权限和时间字段
  -> 执行索引质量检查

索引质量检查至少包括：

  • 是否存在空 chunk 或异常短 chunk；
  • 是否保留了标题和章节路径；
  • 是否丢失表格表头、代码语言和列表层级；
  • BM25 和向量索引中的 ID 是否一致；
  • 文档版本和权限字段是否完整；
  • 更新或删除文档后旧版本是否仍会被召回。

7.2 在线阶段

用户问题
  -> 查询清洗、语言识别和实体抽取
  -> 识别过滤条件与查询类型
  -> 并行执行 BM25、向量、标题、实体和历史问答检索
  -> 应用权限和元数据约束
  -> 合并候选并按 chunk_id 去重
  -> 使用 RRF、加权融合或学习排序
  -> 补充必要的父块和相邻块
  -> reranker 重排
  -> 过滤低相关候选
  -> 组装有限上下文

一个简单的伪代码如下：

def retrieve(query, user_context):
    query_info = analyze_query(query)
    filters = build_hard_filters(user_context, query_info)

    dense_results = dense_search(
        query=query,
        filters=filters,
        top_k=50,
    )
    sparse_results = bm25_search(
        query=query_info.normalized_query,
        filters=filters,
        top_k=50,
    )
    title_results = title_search(
        query=query_info.normalized_query,
        filters=filters,
        top_k=20,
    )

    candidates, trace = fuse_and_deduplicate([
        ("dense", dense_results),
        ("bm25", sparse_results),
        ("title", title_results),
    ])

    candidates = expand_context(candidates, max_neighbors=1)
    candidates = rerank(query, candidates, top_k=20)
    context = pack_context(candidates, token_budget=6000)

    return context, trace

其中 trace 很重要。它应记录每个候选来自哪些通道、初始排名、融合分数、最终排名以及被过滤或截断的原因，便于定位“为什么没有召回”与“为什么排在前面”。

8. 评估与调优

8.1 检索指标

建立一组具有代表性的查询集，并为每个查询标注相关文档或相关 chunk。常用指标包括：

  • Recall@K：前 \(K\) 个结果是否覆盖了至少一个相关证据；
  • HitRate@K：前 \(K\) 个结果中是否命中目标；
  • MRR：第一个相关结果出现位置的倒数；
  • nDCG@K：考虑相关性等级和排名位置的综合指标；
  • Precision@K：前 \(K\) 个结果中相关结果的比例。

RAG 还应评估答案层指标：

  • 答案是否被检索证据支持；
  • 是否遗漏了关键限定条件；
  • 是否混用了不同版本；
  • 是否引用了无权限或过期内容；
  • 引用是否与答案中的具体结论对应。

8.2 推荐的实验顺序

不要同时修改所有组件。可以按以下顺序做消融实验：

  1. 只测试 BM25；
  2. 只测试向量检索；
  3. 测试 BM25 + 向量的 RRF；
  4. 测试分数归一化后的加权融合；
  5. 增加标题、标签和实体通道；
  6. 增加父子块或相邻块扩展；
  7. 加入 reranker；
  8. 最后评估上下文压缩和动态路由。

每次实验都应同时记录召回率、答案质量、延迟、索引成本和 token 成本。只看最终回答准确率，可能掩盖检索变好但上下文变长、延迟显著增加的问题。

8.3 典型诊断方式

  • 精确词命中但排序靠后：检查 BM25 字段、分词、字段权重和融合策略；
  • 语义相关内容没有召回：检查 chunk 粒度、embedding 模型、查询改写和向量索引参数；
  • 召回很多相似但不能回答的问题：增加 reranker、提高标题和实体特征权重，或优化 chunk 边界；
  • 结果集中在同一篇文档：增加文档多样性约束或每文档配额；
  • 旧版本压过新版本：将版本、有效期和文档状态作为硬过滤或强排序特征；
  • 相邻内容缺失：检查 parent_id、章节路径和块之间的顺序信息；
  • 混合后效果反而下降：检查原始分数是否被错误相加，以及低质量通道是否产生大量噪声；
  • 线上偶发结果异常：记录查询、索引版本、过滤条件、各路排名和最终上下文，进行可复现分析。

9. 常见误区

误区一：BM25 已经过时，不需要保留

BM25 对精确术语、数字、代码和专有名词仍然非常有价值。它通常不是向量检索的替代品，而是重要的互补通道。

误区二：只要增加召回数量，效果就会更好

候选数量增加可能提高 Recall@K，但也会增加噪声、重排成本和上下文长度。真正目标是提高“包含正确证据的候选覆盖率”，再通过排序和上下文组装控制噪声。

误区三：不同通道的分数可以直接相加

BM25 分数、余弦相似度、内积和距离的尺度不同。未经校准直接相加，通常会让某个通道因为数值范围更大而获得不合理的支配地位。

误区四：命中父块就把整篇文档返回

父块扩展应服务于补足上下文，而不是取消 chunk 化。需要设置范围、去重和 token 预算。

误区五：把元数据当作普通文本拼进 embedding

有些元数据适合硬过滤，有些适合排序，有些适合展示。全部拼入文本向量可能使模型过度关注格式字段，反而损害正文语义表示。

误区六：检索结果多就代表 RAG 可靠

检索结果必须具备相关性、时效性、权限正确性和可引用性。低质量结果过多时，生成模型可能把相似但错误的内容拼接成貌似合理的答案。

10. 实践建议

可以先采用一个简单、可解释、容易评估的基线：

  1. 对正文建立 BM25 索引；
  2. 对相同 chunk 建立向量索引；
  3. 使用租户、权限、文档状态和版本等硬过滤；
  4. 两路各召回一批候选；
  5. 使用 RRF 合并并去重；
  6. 对候选做父块或相邻块的有限扩展；
  7. 使用 reranker 排序；
  8. 按 token 预算组装上下文；
  9. 保存完整检索链路日志；
  10. 用离线查询集持续做消融实验。

在此基础上，再根据错误样本增加标题检索、实体规则、历史问答、文档多样性约束和动态路由。最重要的不是堆叠尽可能多的检索器，而是让每个通道承担清晰职责，并通过可观测、可评估的融合流程把正确证据稳定地送入生成模型。
