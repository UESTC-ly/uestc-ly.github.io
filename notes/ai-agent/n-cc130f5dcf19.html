目标读者：准备把一次性的 Python 脚本演进为可运行、可观测、可测试的 AI Agent 服务的学习者。

本章示例按 Python 3.11+ 编写。命令默认在项目根目录执行；涉及路径时会明确指出当前目录。

学习目标

学完本章后，你应当能够：

  1. 看懂 Python 异常层级，正确使用 try/except/else/finally、raise 和 raise from。
  2. 定义有意义的自定义异常，在不同层级设置异常边界，并保留原始错误上下文。
  3. 使用 logging 的 logger、handler、formatter、级别和上下文，避免泄露 Agent 的敏感信息。
  4. 理解模块、包、__init__.py、__main__.py、绝对/相对导入和 python -m 的关系。
  5. 组织 src/ 布局的项目，降低循环导入、导入副作用和“在某目录能运行、换目录就失败”的风险。

0. 运行本章示例

异常和日志示例只使用 Python 标准库，可以直接保存并运行：

mkdir -p examples
# 将对应代码块保存为 examples/error_logging_demo.py
python examples/error_logging_demo.py

上面的 mkdir -p 适用于 macOS/Linux；Windows PowerShell 可使用 New-Item -ItemType Directory -Force examples，也可以手动创建目录。

模块与包的示例使用下面的目录结构：

project-root/
├── pyproject.toml
├── src/
│   └── agent_app/
│       ├── __init__.py
│       ├── __main__.py
│       ├── errors.py
│       └── cli.py
└── tests/

从 project-root/ 执行 python -m agent_app 前，先让项目进入当前环境：开发阶段可执行 python -m pip install -e .；如果还未配置项目元数据，也可以临时设置 PYTHONPATH=src（Windows PowerShell 为 $env:PYTHONPATH = "src"）。

1. 异常模型与异常层级

1.1 异常是什么

异常是函数无法按约定完成操作时传递给调用者的控制流。它携带异常类型、消息和 traceback（调用栈信息）。正常情况下，业务函数应返回正常结果；无法满足前置条件、外部系统失败或程序存在 bug 时，才进入异常路径。

Python 的主要层级可以简化为：

BaseException
├── SystemExit       # sys.exit()，通常不要捕获
├── KeyboardInterrupt # Ctrl-C，通常不要吞掉
├── GeneratorExit
└── Exception        # 应用层通常捕获这一支
    ├── ValueError
    ├── TypeError
    ├── LookupError
    │   ├── KeyError
    │   └── IndexError
    ├── OSError
    │   ├── FileNotFoundError
    │   └── TimeoutError
    └── RuntimeError

一般写 except Exception，而不是 except BaseException。捕获 BaseException 很容易把 Ctrl-C 或进程退出信号吞掉，让服务无法正常停止。除非确实要在最外层做清理和重新抛出，否则不要捕获 SystemExit/KeyboardInterrupt。

常见判断：

  • ValueError：类型正确，但值不符合要求，例如 int("abc")。
  • TypeError：操作或参数类型不对，例如把字符串当函数调用。
  • KeyError/IndexError：字典键或序列下标不存在。
  • FileNotFoundError、ConnectionError、TimeoutError：外部 I/O 失败。
  • AssertionError：assert 条件不成立；不要用 assert 做用户输入校验，因为 Python 优化模式可能移除断言。

1.2 捕获具体异常

def parse_top_k(raw: str) -> int:
    try:
        value = int(raw)
    except ValueError as exc:
        raise ValueError(f"top_k 必须是整数，收到：{raw!r}") from exc

    if not 1 <= value <= 20:
        raise ValueError("top_k 必须在 1 到 20 之间")
    return value

print(parse_top_k("5"))

捕获异常时要保留足够窄的范围。下面这种写法会把函数内部的 bug 也包装成“输入错误”，从而掩盖问题：

# 不推荐：范围太大，无法区分 int 转换失败和后续代码 bug
def unsafe_parse(raw: str) -> int:
    try:
        value = int(raw)
        result = 100 // value
    except Exception:
        return 0
    return result

1.3 try/except/else/finally 的执行顺序

def read_first_line(path: str) -> str | None:
    file = None
    try:
        file = open(path, encoding="utf-8")
        line = file.readline().strip()
    except FileNotFoundError:
        print(f"文件不存在：{path}")
        return None
    else:
        # 只有 try 没有异常时执行；不要把正常逻辑塞进 try 的大区块
        return line or None
    finally:
        # 无论成功、异常还是 return，都会执行
        if file is not None:
            file.close()
  • try：放可能抛出目标异常的最小代码区间。
  • except：匹配异常并处理、转换或重新抛出。
  • else：try 成功时执行；可避免把 else 代码自身的异常误认为被捕获的异常。
  • finally：无论是否异常都会执行，适合释放资源。若 finally 中再次 return 或抛异常，会覆盖原来的返回值/异常，应避免。

涉及文件、锁、网络响应等资源时，优先使用上下文管理器（见第 4 节），而不是手写 finally。

1.4 raise、raise from 与异常链

class ToolInputError(ValueError):
    """工具参数无法满足格式或业务约束。"""

def load_top_k(raw: str) -> int:
    try:
        return int(raw)
    except (TypeError, ValueError) as exc:
        # 让上层看到领域异常，同时保留底层转换错误
        raise ToolInputError("top_k 不是合法整数") from exc

def retry_once(operation):
    try:
        return operation()
    except TimeoutError:
        # 裸 raise 保留当前 traceback；不要写成 raise exc
        raise

raise NewError(...) from exc 明确表示“新异常由原异常导致”，traceback 会出现 The above exception was the direct cause...。这对于 Agent 服务将底层 SDK 异常映射到领域异常非常有用。若底层错误含有敏感信息且不应暴露给用户，可使用 raise PublicError("...") from None，同时在日志中记录内部 traceback。

1.5 自定义异常与异常边界

异常类应表达调用者可以处理的分类，而不是每一种内部实现细节：

class AgentError(Exception):
    """Agent 应用可预期错误的基类。"""

class ToolError(AgentError):
    """工具执行相关错误。"""

class ToolInputError(ToolError):
    """工具参数格式或业务约束错误。"""

class ToolPermissionError(ToolError):
    """工具调用未被授权。"""

class ModelProviderError(AgentError):
    """模型供应商或网关错误。"""

class TransientModelError(ModelProviderError):
    """短暂失败，可能适合重试。"""

可按层设置异常边界：

外部输入/HTTP 层 ── 把校验错误转成 4xx，隐藏内部细节
       │
应用服务层 ─────── 决定是否重试、降级、结束任务
       │
领域层 ────────── 抛出 AgentError 的稳定子类
       │
基础设施层 ────── 把 SDK/数据库/网络异常转换成领域异常

边界的原则：

  1. 越靠近底层，越了解具体异常；在边界处转换为上层稳定的异常类型。
  2. 只在能采取不同动作时捕获异常。不能处理时让它继续向上冒泡。
  3. 最外层任务入口应记录 traceback，并将用户可见消息与内部诊断分离。
  4. 对 TimeoutError、限流、临时网络错误和永久参数错误区别处理；不能对所有异常无限重试。

1.6 Python 3.11 的异常组（了解）

并发执行多个任务时可能同时失败，可以用 ExceptionGroup 与 except* 分别处理：

def validate_batch() -> None:
    raise ExceptionGroup(
        "批量工具参数错误",
        [ValueError("query 为空"), TimeoutError("检索超时")],
    )

try:
    validate_batch()
except* ValueError as group:
    print("处理参数错误：", group.exceptions)
except* TimeoutError as group:
    print("处理超时：", group.exceptions)

实际业务中要避免异常组层层嵌套；先为批处理定义清晰的结果协议，只有需要保留多项失败信息时才使用它。

1.7 匹配顺序、异常上下文和控制流细节

except 按源码从上到下尝试匹配；匹配的是异常类的继承关系，而不是异常消息：

def read_config(path: str) -> str:
    try:
        with open(path, encoding="utf-8") as file:
            return file.read()
    except FileNotFoundError:
        return "{}"
    except PermissionError as exc:
        raise ToolError("配置文件不可读取") from exc
    except OSError as exc:
        raise ToolError("文件系统暂时不可用") from exc

FileNotFoundError 和 PermissionError 都是 OSError 的子类，所以具体异常必须写在 OSError 前面；否则后面的分支永远不会执行。多个同级异常可以写成元组：except (TimeoutError, ConnectionError) as exc:。不要根据 str(exc) 判断异常类别，消息可能随操作系统、库版本和语言环境变化。

try 中的 return 会先计算返回值，再执行 finally；finally 中的 return 会覆盖它：

def bad_return() -> int:
    try:
        return 1
    finally:
        return 2  # 不推荐：覆盖 try 的返回值，也会吞掉 try 中的异常

print(bad_return())  # 2

finally 应只做不会改变控制流的清理。若清理也可能失败，应该记录清理异常，并根据资源的重要性决定是否让它覆盖原始异常；不要为了“看起来完整”在 finally 中无条件捕获并忽略所有错误。

异常对象的 __context__、__cause__ 和 __suppress_context__ 形成异常链。裸 raise 保留当前 traceback；raise exc 虽然仍会抛出同一异常，但通常会增加一个重新抛出的栈位置，降低诊断清晰度。转换底层异常时优先：

def call_provider(client) -> str:
    try:
        return client.complete()
    except TimeoutError as exc:
        raise TransientModelError("模型供应商超时") from exc

如果调用方可以处理，应保留结构化属性而不把信息全部编码进字符串：

class RetryableToolError(ToolError):
    def __init__(self, message: str, *, retry_after_s: float | None = None) -> None:
        super().__init__(message)
        self.retry_after_s = retry_after_s

error = RetryableToolError("上游限流", retry_after_s=2.0)
print(error.retry_after_s)

1.8 异常组和取消语义（Python 3.11+）

ExceptionGroup 用于一次携带多个独立异常，except* 会从异常组中提取匹配部分；每个 except* 分支可能被执行，因此不要把它当成普通 except 的“只进一个分支”：

def run_batch() -> None:
    errors = [ValueError("参数错误"), TimeoutError("超时")]
    raise ExceptionGroup("batch failed", errors)

try:
    run_batch()
except* ValueError as group:
    print("参数错误数量：", len(group.exceptions))
except* TimeoutError as group:
    print("超时数量：", len(group.exceptions))

批处理 API 若需要同时报告成功和失败，返回带有 ok/error 字段的结果列表通常比把所有情况都塞入 ExceptionGroup 更易使用。异常组适合并行任务在同一边界集中报告多个失败。

异步 Agent 还要留意 asyncio.CancelledError 的取消语义：它属于 BaseException 分支，不能依靠 except Exception 处理，也不应被无意吞掉。清理可以放在 finally，完成后重新抛出取消，让上层知道任务确实被取消；只有最外层任务协调器明确决定转换状态时才捕获它。

1.9 异常边界的决策模板

可按“谁知道怎么处理”设计边界：

层 了解的信息 应做的事 不应做的事
基础设施（HTTP/SDK/数据库） 连接、协议、供应商异常 转换为少量稳定的领域异常，附原异常 向用户返回 SDK 原始消息
领域/工具层 参数、不变量、权限和业务状态 抛 ToolInputError、ToolPermissionError 等 自己决定 HTTP 状态码
应用编排层 是否可重试、是否降级、步数/预算 有界重试、记录运行状态、选择降级 无限重试或吞掉取消
API/CLI 边界 用户协议和公开错误格式 映射状态码/退出码，返回安全消息 暴露 traceback、密钥和内部路径
任务入口 整个 run 的最终结果 记录未处理异常和关联 ID，保证资源关闭 继续运行未知的损坏状态

一个异常分类至少要回答：调用者能否重试？是否应提示用户修改输入？是否需要报警？是否可公开原始细节？如果这些问题答案相同，就不必继续拆更多异常类。

2. 日志：让 Agent 任务可追踪

2.1 logging 的组成

Python 日志系统可以理解为：

代码调用 logger.info/error(...)
          │
logger（按名称分层，向父 logger 传播）
          │
handler（输出到控制台、文件、日志服务）
          │
formatter（把 LogRecord 格式化为文本或 JSON）

级别从低到高通常是：DEBUG、INFO、WARNING、ERROR、CRITICAL。记录一条消息前会检查 logger 与 handler 的有效级别。库代码不应擅自配置 root logger；应用入口统一配置。

2.2 最小可运行日志配置

import logging
import logging.config


class RequestContextFilter(logging.Filter):
    """保证没有 LoggerAdapter 的普通日志也拥有默认 request_id。"""

    def filter(self, record: logging.LogRecord) -> bool:
        if not hasattr(record, "request_id"):
            record.request_id = "-"
        return True


LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "standard": {
            "format": "%(asctime)s %(levelname)s %(name)s "
                      "request_id=%(request_id)s %(message)s",
        },
    },
    "filters": {
        "request_context": {
            "()": RequestContextFilter,
        },
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "level": "INFO",
            "formatter": "standard",
            "filters": ["request_context"],
            "stream": "ext://sys.stdout",
        },
    },
    "loggers": {
        "agent_app": {
            "level": "DEBUG",
            "handlers": ["console"],
            "propagate": False,
        },
    },
}

logging.config.dictConfig(LOGGING)
logger = logging.getLogger("agent_app.tool")
adapter = logging.LoggerAdapter(logger, {"request_id": "req-001"})

adapter.info("开始调用工具 %s", "search")
try:
    raise TimeoutError("demo")
except TimeoutError:
    adapter.exception("工具调用失败")  # 自动包含 traceback

要点：

  • 每个模块使用 logger = logging.getLogger(__name__)，不要每次调用 basicConfig()。
  • 使用懒格式化 logger.info("count=%d", count)，而不是 logger.info(f"count={count}")；禁用该级别时可避免不必要的格式化。
  • logger.exception() 应在异常处理上下文中使用：普通 except 块里会自动记录当前异常堆栈；如果异常对象来自框架异常处理器而不在当前 except 上下文中，应显式传入 exc_info=exc。普通业务错误日志使用 logger.error()。
  • propagate=False 可以防止同一记录被 root logger 重复输出；是否关闭要根据应用整体配置决定。

2.3 上下文与结构化日志

Agent 调试通常需要 request_id、run_id、user_id、tool_name、step 等字段。可以使用 LoggerAdapter：

import logging

logger = logging.getLogger(__name__)
log = logging.LoggerAdapter(
    logger,
    {"request_id": "req-001", "run_id": "run-007", "tool_name": "search"},
)
log.info("开始执行，第 %d 步", 1)

在异步任务或跨层调用中，contextvars.ContextVar 比全局变量更合适：每个任务有自己的上下文。也可以在日志过滤器中从 ContextVar 注入字段，或使用项目选定的 JSON 日志库输出 {"level":"INFO", ...}。无论文本还是 JSON，都要保证字段稳定，便于检索和聚合。

自定义结构化 formatter（只使用标准库）的示例：

import json
import logging

class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "time": self.formatTime(record, "%Y-%m-%dT%H:%M:%S%z"),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }
        for key in ("request_id", "run_id", "tool_name"):
            value = getattr(record, key, None)
            if value is not None:
                payload[key] = value
        if record.exc_info:
            payload["exception"] = self.formatException(record.exc_info)
        return json.dumps(payload, ensure_ascii=False)

实际生产环境可直接使用日志平台或团队已选的结构化日志方案；不要为了“JSON”而重复造一套不兼容的协议。

2.4 日志安全与可观测性清单

  1. 绝不记录 API key、Authorization header、密码、完整 Cookie、个人隐私和未脱敏的用户输入。
  2. 记录模型调用时，通常只记录供应商、模型别名、token 统计、延迟、状态和截断后的安全摘要；不要默认记录完整 prompt/response。
  3. URL、文件路径和工具参数可能包含秘密；在 formatter 前做脱敏或只记录白名单字段。
  4. 让 ERROR 表示需要关注的失败；可预期的用户输入错误可用 INFO/WARNING，不要把正常分支刷成错误。
  5. 结构化字段保持低基数；不要把完整自由文本作为 label/tag 发送到指标系统。
  6. 生产环境通常输出到 stdout，由运行平台收集；需要文件轮转时选择合适的 handler，避免无限增长。

2.5 logger 层级、级别和传播的计算方式

logger 通过点号形成层级：agent_app 是 agent_app.tool 的父 logger，agent_app.tool.search 又是它的子 logger。记录一条日志时可以按以下顺序理解：

  1. 调用 logger.debug/info/...，logger 的有效级别先决定是否创建/处理该级别记录。
  2. 记录交给当前 logger 的 handler；handler 还有自己的级别，可能再次过滤。
  3. 当前 logger 的 handler 处理后，如果 propagate=True，记录向父 logger 传播，父级 handler 继续处理。
  4. 到 root logger 或遇到 propagate=False 为止。

这意味着“logger 级别开了 DEBUG”不保证 DEBUG 一定输出：handler 仍可能只接受 INFO；反过来，在 logger 上没有 handler 时，记录也可能由父级 handler 输出。重复日志通常来自子 logger 和 root logger 都有 handler，或应用初始化函数被调用多次。

import logging

parent = logging.getLogger("agent_app")
child = logging.getLogger("agent_app.tool")
print(child.parent is parent)  # True（已创建相应层级时）
child.setLevel(logging.DEBUG)

库代码通常只创建命名 logger 并添加 logging.NullHandler()，不修改 root logger；可执行应用在唯一入口配置 handler。这样使用者可以决定输出格式、目的地和级别。

2.6 handler、filter 和 formatter 的职责分离

  • handler 决定输出去哪里，并可有独立的级别：stdout、stderr、文件、轮转文件或日志收集器。
  • filter 决定某条 LogRecord 是否通过，也可以补充上下文字段；过滤器应快速且无副作用。
  • formatter 把 record 变成文本/JSON；不要在 formatter 中做网络请求或昂贵查询。

extra 会把字段放进单条 LogRecord。如果 formatter 要求 %(request_id)s，某处却直接调用 logger 而没有该字段，格式化可能触发内部 logging 错误。两种稳妥方式是：所有调用都通过 adapter；或用 filter 为缺失字段提供默认值：

import logging

class ContextDefaults(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        if not hasattr(record, "request_id"):
            record.request_id = "-"
        if not hasattr(record, "run_id"):
            record.run_id = "-"
        return True

handler = logging.StreamHandler()
handler.addFilter(ContextDefaults())
handler.setFormatter(
    logging.Formatter("%(levelname)s request_id=%(request_id)s run_id=%(run_id)s %(message)s")
)
logger = logging.getLogger("demo.context")
logger.handlers.clear()
logger.addHandler(handler)
logger.propagate = False
logger.warning("没有显式上下文也不会格式化失败")

生产项目不要在多个模块中随意 handlers.clear()；这里仅为独立示例避免重复输出。配置应集中、幂等，并在测试中验证日志路由。

2.7 ContextVar 与异步请求上下文

LoggerAdapter 适合调用链显式传递上下文；异步服务中若不想给每个函数都加参数，可用 ContextVar 保存当前任务上下文：

下面两个代码块属于同一个逐步示例：将它们按顺序放进一个 .py 文件后，在已激活虚拟环境中运行。

import asyncio
import logging
from contextvars import ContextVar

request_id_var: ContextVar[str] = ContextVar("request_id", default="-")

class RequestFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True

handler = logging.StreamHandler()
handler.addFilter(RequestFilter())
handler.setFormatter(logging.Formatter("%(request_id)s %(message)s"))
logger = logging.getLogger("agent.contextvar")
logger.handlers.clear()
logger.addHandler(handler)
logger.propagate = False

async def handle(request_id: str) -> None:
    token = request_id_var.set(request_id)
    try:
        logger.info("开始")
        await asyncio.sleep(0)
        logger.info("结束")
    finally:
        request_id_var.reset(token)

# 不要把 asyncio.gather(...) 直接传给 asyncio.run；下面的 main() 才是可运行入口。

asyncio.gather() 返回 awaitable/future，而 asyncio.run() 需要协程入口；可运行的写法是包一层协程：

async def main() -> None:
    await asyncio.gather(handle("r1"), handle("r2"))

asyncio.run(main())

ContextVar 的值会随任务上下文传播，但创建后台任务、线程或进程时要确认上下文是否按预期复制。请求结束一定要 reset(token)，避免在复用执行上下文时串号。

2.8 结构化日志和脱敏策略

结构化日志的重点不是“把字符串包成 JSON”，而是让字段可检索、可聚合、可脱敏：

from collections.abc import Mapping

SENSITIVE_KEYS = {"api_key", "authorization", "password", "access_token"}

def redact(value: object) -> object:
    if isinstance(value, Mapping):
        return {
            str(key): "***" if str(key).lower() in SENSITIVE_KEYS else redact(item)
            for key, item in value.items()
        }
    if isinstance(value, list):
        return [redact(item) for item in value]
    return value

print(redact({"tool": "search", "api_key": "secret", "args": {"q": "Python"}}))

脱敏应在日志边界完成，且采用“白名单优先”：工具参数只记录需要诊断的字段，用户原文和模型响应默认截断或不记录。仅按键名脱敏并不完备，秘密也可能出现在 URL、异常文本、嵌套字符串或 header 值中；生产系统需要单元测试、日志抽样审查和访问控制。

日志质量可以用三个维度检查：

  1. 可关联：有 request_id、run_id、step，能串起模型和工具调用。
  2. 可行动：错误包含稳定异常类别、供应商/工具、延迟和重试次数，能帮助决定修复动作。
  3. 可安全共享：没有密钥、完整凭证、未经同意的个人数据和不必要的模型原文。

3. 模块、包与导入机制

3.1 模块和包的概念

  • 模块（module）：一个 .py 文件，导入后对应一个模块对象，例如 agent_app.errors。
  • 包（package）：组织多个模块的目录。传统包含 __init__.py；现代 Python 也支持 namespace package，但应用项目通常仍保留 __init__.py 以明确边界。
  • 顶层包：项目的公共导入名字，例如 agent_app，不应与标准库或第三方包重名。

推荐使用 src 布局：

project-root/
├── pyproject.toml
├── src/
│   └── agent_app/
│       ├── __init__.py
│       ├── __main__.py
│       ├── cli.py
│       ├── errors.py
│       ├── domain/
│       │   ├── __init__.py
│       │   └── models.py
│       └── infrastructure/
│           ├── __init__.py
│           └── model_client.py
└── tests/

src 布局能避免测试时不小心直接导入项目根目录中的同名文件，从而更早暴露打包和安装问题。

3.2 __init__.py、__main__.py 与 __name__

__init__.py 在包首次导入时执行。它应保持轻量，避免网络请求、读取密钥、初始化连接池等副作用。可以只暴露稳定 API：

# src/agent_app/__init__.py
__all__ = ["__version__"]
__version__ = "0.1.0-dev"  # 若项目发布，版本应由构建元数据统一管理

__main__.py 让包可以这样运行：

# src/agent_app/__main__.py
from .cli import main

if __name__ == "__main__":
    raise SystemExit(main())

# src/agent_app/cli.py
def main() -> int:
    print("agent_app started")
    return 0

安装项目后，从项目根目录执行：

python -m agent_app

if __name__ == "__main__" 的含义是：仅当文件被直接作为入口执行时运行；被其他模块导入时不运行入口逻辑。优先使用 python -m package.module，它会按包上下文执行，通常比 python src/agent_app/cli.py 更不容易触发相对导入问题。

3.3 绝对导入与相对导入

包内推荐：

# src/agent_app/cli.py
from agent_app.errors import AgentError  # 推荐：绝对导入，意图清晰

也可以二选一写成包内相对导入 from .errors import AgentError。团队应统一风格。大型项目通常使用绝对导入，跨包移动时更直观；包内部的相邻模块也可用单点相对导入表达“同一包”。不要在同一模块同时写两种导入，也不要使用难以判断来源的裸导入，如 from utils import x，因为它可能导入错误的同名顶层模块。

相对导入只有在模块作为包的一部分加载时才有效，因此直接执行 python src/agent_app/cli.py 可能出现 ImportError: attempted relative import with no known parent package。改用 python -m agent_app，或先安装可编辑项目。

3.4 导入发生了什么

执行 import agent_app.errors 时，Python 大致会：

  1. 在 sys.path 中搜索顶层包；sys.path 包括当前运行上下文、环境中的 site-packages 等。
  2. 加载包并执行 agent_app/__init__.py（首次导入）。
  3. 搜索并执行 errors.py，把模块对象放入 sys.modules 缓存。
  4. 后续再次导入通常复用缓存，不会重新执行顶层代码。

因此，模块顶层代码应尽量是定义（类、函数、常量），避免不可预测的副作用。大型模块间循环导入时，常见改法是：

  • 提取两边都需要的类型到更底层模块；
  • 依赖倒置，通过 Protocol 或函数参数注入能力；
  • 将仅用于类型的导入放进 if TYPE_CHECKING:，必要时使用字符串标注或 from __future__ import annotations；
  • 最后的局部导入只应作为明确权衡，不要用来掩盖架构循环。

3.5 pyproject.toml 中的项目布局

以下是最小项目元数据示意（构建后端可按团队选择）：

[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"

[project]
name = "agent-app"
version = "0.1.0"
description = "An educational Python Agent application"
requires-python = ">=3.11"
dependencies = []

[tool.setuptools.packages.find]
where = ["src"]

[project.scripts]
agent-app = "agent_app.cli:main"

把项目安装到当前虚拟环境：

python -m pip install -e .
agent-app

-e（editable）适合开发：修改 src/agent_app 后通常无需重新安装。打包发布前应在干净环境验证普通安装，确保包声明、入口点和依赖完整。

3.6 模块缓存、查找顺序和导入副作用

导入不是“把另一个文件复制到这里”。Python 会先查找模块，再创建模块对象并执行其顶层代码；执行完成后通常放入 sys.modules 缓存：

import sys

import agent_app

print("agent_app" in sys.modules)
same_object = __import__("agent_app") is agent_app
print(same_object)

第二次导入通常直接复用缓存，因此修改模块文件后，在同一解释器进程里再次 import 不会自动重新执行。交互式调试时可使用 importlib.reload()，但它不会可靠地更新所有已有引用，也不适合作为应用的热更新方案。

查找顶层模块时，Python 会使用导入器和 sys.path；sys.path 的第一项受启动方式影响，之后包括标准库、虚拟环境和 site-packages。可以用下面的方式确认实际导入来源：

import logging

print(logging.__file__)

若输出指向项目中的 logging.py 而非标准库路径，说明名称遮蔽已经发生。不要用修改全局 sys.path 的方式长期修复打包问题；应安装项目、修正 pyproject.toml 和导入路径。

3.7 __all__、包 API 和重导出

包的内部目录结构不一定等于公共 API。可以在 __init__.py 中重导出少量稳定名称：

# src/agent_app/domain/__init__.py
from .models import RunState

__all__ = ["RunState"]

调用方可以写 from agent_app.domain import RunState，不用知道具体文件；但重导出也会让 __init__.py 产生更多导入和潜在循环。只把稳定、低副作用的名称放入公共 API，内部实现继续使用明确的模块路径。__all__ 主要影响 from package import * 和文档工具，不是访问控制机制。

3.8 循环导入的识别与修复

循环导入通常表现为“部分初始化的模块没有属性”或导入过程中递归失败：

a.py 导入 b.py
  b.py 又导入 a.py
    a.py 尚未执行完，b.py 看不到 a.py 的完整定义

排查步骤：

  1. 阅读 traceback 的导入链，找出回到已出现模块的边。
  2. 将共享的类型、常量或协议提取到更低层模块。
  3. 通过构造函数参数/Protocol 注入依赖，而不是模块顶层创建实例。
  4. 仅用于类型检查的导入放进 if TYPE_CHECKING:，并确认运行时不需要该名称。
  5. 把入口、副作用和注册动作放到 main() 或显式工厂里。
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from agent_app.domain.models import RunState

def summarize(state: "RunState") -> str:
    return state.run_id

TYPE_CHECKING 在静态工具中为真、正常运行时为假；如果函数执行时确实要访问类型对象，应在局部导入或重新设计依赖，而不是盲目隐藏导入。

3.9 python -m、入口点与启动目录

python -m package.module 先按包导入规则找到模块，再以 __main__ 语义执行，因而能保留包上下文。可执行脚本入口点则由打包工具生成，最终调用 package.module:function：

# 以下命令均在 project-root 执行，前置条件是已激活虚拟环境并执行 python -m pip install -e .
python -m agent_app
agent-app
python -m agent_app.cli

不要依赖从某个偶然的当前目录执行 python src/agent_app/cli.py；它改变了 sys.path[0] 和包上下文，常导致相对导入在开发机“有时可以、有时失败”。测试和 CI 应从项目根目录或安装后的环境启动。

4. 上下文管理器：自动管理资源

4.1 内置上下文管理器

with 会调用对象的 __enter__ 和 __exit__，即使代码块抛异常也能执行清理：

from pathlib import Path

path = Path("agent_input.txt")
path.write_text("query=iterator\n", encoding="utf-8")

with path.open(encoding="utf-8") as file:
    content = file.read()

print(content)

常见上下文管理器有文件、线程锁、数据库事务、临时目录/环境修改等。若 __exit__ 返回真值，它会吞掉异常；除非这是清晰且有文档的行为，否则让异常继续传播。

4.2 自定义上下文管理器

类写法：

import logging
import time

logger = logging.getLogger(__name__)

class TimedStep:
    def __init__(self, name: str) -> None:
        self.name = name

    def __enter__(self) -> "TimedStep":
        self.started = time.perf_counter()
        logger.info("step.start name=%s", self.name)
        return self

    def __exit__(self, exc_type, exc_value, traceback) -> bool:
        elapsed = time.perf_counter() - self.started
        logger.info("step.end name=%s elapsed=%.3fs", self.name, elapsed)
        return False  # 不吞异常

with TimedStep("retrieve"):
    pass

简单场景可用 contextlib.contextmanager：

from contextlib import contextmanager
from collections.abc import Iterator

@contextmanager
def named_step(name: str) -> Iterator[None]:
    print(f"begin: {name}")
    try:
        yield
    finally:
        print(f"end: {name}")

with named_step("tool"):
    print("execute")

异步资源使用 async with，需要实现 __aenter__/__aexit__ 或使用 @asynccontextmanager。例如异步 HTTP 客户端、数据库连接和 Agent 的生命周期管理都应确保在取消或异常时关闭。

5. 一个可运行的异常与日志示例

将以下代码保存为 examples/error_logging_demo.py，在项目根目录执行 python examples/error_logging_demo.py：

import logging
import logging.config
from dataclasses import dataclass

LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "console": {
            "format": "%(asctime)s %(levelname)s %(name)s "
                      "request_id=%(request_id)s %(message)s",
        }
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "level": "INFO",
            "formatter": "console",
            "stream": "ext://sys.stdout",
        }
    },
    "loggers": {
        "demo": {
            "level": "DEBUG",
            "handlers": ["console"],
            "propagate": False,
        }
    },
}

logging.config.dictConfig(LOGGING)
logger = logging.getLogger("demo")

class ToolError(Exception):
    """工具执行失败。"""

@dataclass(frozen=True)
class SearchArgs:
    query: str
    top_k: int = 5

def search(args: SearchArgs) -> list[str]:
    if not args.query.strip():
        raise ToolError("搜索词不能为空")
    if not 1 <= args.top_k <= 20:
        raise ToolError("top_k 超出范围")
    return [f"result-{i}: {args.query}" for i in range(1, args.top_k + 1)]

def run() -> None:
    log = logging.LoggerAdapter(logger, {"request_id": "req-demo"})
    for args in (SearchArgs("iterator", 2), SearchArgs("", 2)):
        try:
            results = search(args)
        except ToolError as exc:
            log.warning("工具输入不可用：%s", exc)
        else:
            log.info("搜索成功，结果数=%d", len(results))
        finally:
            log.debug("本次调用结束")

if __name__ == "__main__":
    run()

6. 常见坑与排查清单

  1. 捕获过宽。 except Exception: pass 会吞掉 bug、取消和诊断信息；至少记录并重新抛出，或只捕获能处理的异常。
  2. 捕获 BaseException。 它会拦截 Ctrl-C 和进程退出，服务可能无法优雅停止。
  3. finally 覆盖异常。 在 finally 中 return 或抛新异常会覆盖原始异常；资源清理函数本身也要谨慎。
  4. 丢失 traceback。 raise SomeError(str(exc)) 会丢失因果关系；需要转换时写 raise SomeError(...) from exc。
  5. 用异常控制常规分支。 对高频可预期状态优先返回结果对象或显式状态；异常应保留给真正的异常路径。
  6. 无限重试。 只对可恢复的超时/限流做有限次数、带退避和总超时的重试；参数错误、权限错误不要重试。
  7. 日志秘密泄露。 logger.exception 会包含异常文本；异常消息和请求参数都要经过脱敏。
  8. 重复配置日志。 每个模块调用 basicConfig() 或重复添加 handler，会造成重复输出；应用入口统一配置。
  9. 字符串拼接日志。 用 logger.info("x=%s", x)，不要用 % 或 f-string 提前构造敏感内容。
  10. 日志没有上下文。 没有 request_id/run_id 时，很难把一次 Agent 运行的多步日志串起来。
  11. 直接运行包内文件。 python src/agent_app/cli.py 容易导致相对导入失败；使用安装后的 python -m agent_app。
  12. __init__.py 副作用。 导入包就连接数据库、调用网络或读取密钥，会让测试和工具扫描变得不可预测。
  13. 模块名遮蔽。 不要命名为 logging.py、typing.py、asyncio.py 或与项目依赖同名；否则可能导入项目文件而非标准库。
  14. 循环导入。 用分层、依赖注入、协议和共享底层模块解决；局部导入只是有意的最后手段。
  15. 修改了 PYTHONPATH 却没意识到。 “本地能跑”可能依赖临时路径；在干净虚拟环境安装项目并运行测试。

7. 练习题

  1. 定义 AgentError、ToolInputError、ToolPermissionError 和 TransientModelError，为每类异常写一个调用方可采取的不同处理动作。
  2. 重写一个包含文件读取的函数，使它只捕获 FileNotFoundError，使用 else 返回内容，并通过 with 自动关闭文件。
  3. 写一个函数把底层 TimeoutError 转换为 TransientModelError，使用 raise from 保留原始异常；再在最外层打印完整 traceback。
  4. 使用 ExceptionGroup 构造一批工具调用的多个失败，并分别处理参数错误和超时；思考什么时候用返回结果列表会更简单。

7.1 练习提示与验收标准

练习 提示 最低验收标准
1 先画异常继承树，再为每类异常写“能否重试/是否告警/公开消息” 调用方不依赖字符串匹配；至少有一类可重试和一类不可重试错误
2 with 负责文件生命周期，else 只放成功路径 文件不存在、权限失败和成功读取分别可测试；无资源泄漏
3 用 raise NewError(...) from exc，在入口用 logger.exception 公共异常稳定，traceback 仍能追溯底层原因，用户消息不含路径/密钥
4 只在多个独立任务同时失败且需要一起报告时用 ExceptionGroup ValueError 与超时分支分别处理；取消不会被吞掉
5 先设计日志字段表，再配置 logger/handler/formatter 有 request/run ID；同一条记录不重复；级别过滤符合预期
6 脱敏函数递归处理映射/列表，优先白名单字段 密钥和 authorization 不出现在捕获日志中；普通字段仍可检索
7 先写 __main__.py，再用 python -m 从根目录运行 包安装后模块入口和 console script 都成功，退出码明确
8 用 traceback 找循环边，将共享类型下移或改用 Protocol 修复后导入顺序不依赖局部导入副作用，并有最小测试
9 @contextmanager 的 yield 前后分别获取/释放资源 成功和异常都执行清理，异常原样传播
10 把“处理者”画成层级边界，区分日志、用户消息和重试 每层的捕获动作有理由；未知异常不会静默继续运行

小结

  • 异常是有分类的控制流；捕获最具体、能处理的异常，避免吞掉 KeyboardInterrupt、traceback 和真正的 bug。
  • else 用于成功路径，finally 用于清理；跨层转换异常时用 raise ... from ... 保留因果关系。
  • Agent 应建立稳定的领域异常层级，在边界处区分参数错误、权限错误、临时失败和永久失败，重试必须有限且有退避。
  • logging 由 logger、handler、formatter 和级别组成；应用入口集中配置，模块用 getLogger(__name__)，日志应带请求/运行上下文并严格脱敏。
  • 模块是 .py 文件，包是模块的组织边界；__main__.py 配合 python -m 提供可靠入口，src 布局和低副作用导入有助于测试与发布。
  • 上下文管理器把资源的获取与释放绑定在一起，是文件、锁、连接和 Agent 生命周期管理的基础工具。
