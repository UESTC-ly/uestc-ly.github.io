1. 先掌握原语，再学习框架

不同框架的命名不同，但核心原语通常相同：

原语 LangChain LangGraph LlamaIndex 模型厂商原生 SDK
模型调用 Chat Model 图节点中的模型调用 LLM/Agent 抽象 Chat/Responses API 客户端
工具定义 Tool / Structured Tool 节点或 ToolNode Tool / Function Tool tools Schema
Agent 循环 Agent Executor 等 State Graph + 条件边 Agent / Workflow 应用代码自行循环
状态 消息与运行上下文 显式 Graph State、Checkpoint Workflow/Agent Context 应用数据库或内存
检索与索引 可接入 Retriever 通常作为节点调用 Index、Retriever、Query Engine 通常自行接入
人工介入 回调或自定义逻辑 图节点暂停/恢复 Workflow 自定义状态 应用 API、队列和数据库
追踪 回调与观测平台 节点/边执行记录 回调与日志 自己生成 Trace 和审计

具体类名和行为会随版本变化，学习时应以实际版本文档和源码为准。表格只用于建立概念映射，不是 API 兼容承诺。

2. 四类工具的定位

LangChain

适合快速组合模型、Prompt、工具、输出解析器和检索组件。学习重点是理解每个 Runnable、Agent 和 Tool 背后的输入输出，而不是只记装配代码。

LangGraph

更适合显式表达有状态、可暂停、可恢复、带条件分支和循环的 Agent Workflow。它的核心思想与本目录中的状态机、检查点和事件转移相近。

LlamaIndex

在文档、数据连接、索引、检索和知识库型应用上较有优势，也可以承载 Agent 和 Workflow。要特别区分“检索到的资料”和“可信业务事实”。

模型厂商原生 SDK

最接近模型服务的真实协议，适合掌握消息、工具调用、流式响应、结构化输出、错误码和用量。不同厂商在工具字段、并行调用、上下文和响应格式上可能不同。

3. 脱离框架的最小组件

from dataclasses import dataclass, field
from typing import Any

@dataclass
class AgentState:
    task_id: str
    messages: list[dict[str, Any]] = field(default_factory=list)
    status: str = "RUNNING"
    step: int = 0
    artifacts: dict[str, Any] = field(default_factory=dict)
    retry_counts: dict[str, int] = field(default_factory=dict)

class ModelClient:
    def complete(self, *, messages, tools, deadline):
        raise NotImplementedError

class ToolExecutor:
    def invoke(self, *, name, args, context, deadline):
        raise NotImplementedError

class StateStore:
    def load(self, task_id) -> AgentState:
        raise NotImplementedError

    def save(self, state: AgentState, expected_version: int):
        raise NotImplementedError

class PolicyEngine:
    def check(self, *, principal, name, args, state):
        raise NotImplementedError

class Tracer:
    def event(self, name, **fields):
        raise NotImplementedError

这些接口分别代表：模型边界、真实执行边界、持久化边界、安全边界和观测边界。测试时可以替换为 Fake 实现，不必调用真实模型或真实支付系统。

4. 原生 Agent Runner 的结构

def run_agent(*, task_id, principal, model, executor, store, policy, tracer, deadline):
    state = store.load(task_id)

    while state.status == "RUNNING":
        if state.step >= 8 or now() >= deadline:
            state.status = "FAILED"
            state.artifacts["reason"] = "budget_exhausted"
            store.save(state, expected_version=state.version)
            return state

        tracer.event("model_started", task_id=task_id, step=state.step)
        response = model.complete(
            messages=state.messages,
            tools=available_tool_schemas(principal),
            deadline=deadline,
        )
        state.messages.append(response.assistant_message)

        calls = response.tool_calls
        if not calls:
            state.status = "SUCCEEDED"
            state.artifacts["answer"] = response.text
            store.save(state, expected_version=state.version)
            tracer.event("task_succeeded", task_id=task_id)
            return state

        for call in calls:
            args = parse_and_validate(call.name, call.arguments)
            policy.check(
                principal=principal,
                name=call.name,
                args=args,
                state=state,
            )
            result = executor.invoke(
                name=call.name,
                args=args,
                context={"task_id": task_id, "principal": principal},
                deadline=deadline,
            )
            state.messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": safe_serialize(result),
            })
            tracer.event("tool_finished", task_id=task_id, tool=call.name)

        state.step += 1
        store.save(state, expected_version=state.version)

    return state

这是学习用骨架，生产实现还需要：流式响应聚合、并行工具调用、取消信号、重试分类、幂等、人工审批、状态迁移、敏感数据脱敏和队列租约。

5. 原生实现的模块职责

  • ModelClient：封装供应商 SDK、模型名、超时、流式/非流式和响应归一化；
  • ToolRegistry：保存名称、描述、Schema、风险和执行器引用；
  • PolicyEngine：用户、租户、资源、额度、审批和工具白名单；
  • ToolExecutor：调用 HTTP、数据库或内部服务，处理超时和错误分类；
  • StateStore：保存状态、事件、版本和检查点；
  • TaskQueue：投递、租约、重试、延迟和死信；
  • ApprovalStore：创建、批准、拒绝、过期和审计；
  • Tracer：统一 Trace、Span、结构化事件和指标。

6. 选择框架的判断标准

  • 需要快速验证 Prompt、工具和检索组合：可先用 LangChain 或原生 SDK；
  • 需要显式循环、分支、暂停、恢复和检查点：重点比较 LangGraph 或自建状态机；
  • 主要问题是文档接入、索引、检索和数据连接：重点比较 LlamaIndex；
  • 需要最小依赖、精确控制协议、成本和安全边界：优先原生 SDK 加自建编排层；
  • 业务副作用强、审计要求高：无论使用什么框架，都要把权限、幂等和状态持久化放在框架之外或框架明确可控的边界上。

7. 框架评估清单

试用一个框架时，不只看 Demo 是否能跑，还要验证：

  • 能否查看和修改完整消息链；
  • Tool Calling 参数是否能在执行前拦截；
  • 是否支持自定义权限和业务校验；
  • 状态能否持久化、版本控制和恢复；
  • 如何实现 HITL、取消和长任务；
  • 失败重试是否可配置且不会重复副作用；
  • 日志能否关联模型、工具、任务和用户；
  • 升级版本后 Schema 和状态是否兼容；
  • 是否可以替换模型供应商和存储实现。

8. 学习结论

框架的价值主要在于减少胶水代码、提供常用组件和统一观测；框架不能替代：

  • 业务状态机；
  • 资源级权限；
  • 事务与幂等；
  • 错误分类和补偿；
  • 人工审批；
  • 数据治理与审计。
