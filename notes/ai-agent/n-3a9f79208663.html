上一节：检索与生成评测｜导航：RAG 学习路线｜下一节：向量存储选型

1. 本节定位

RAG 知识库不是一次导入后就不再变化的静态数据。业务文档会新增、修改、移动、失效、删除，用户权限也会发生变化。源数据库已经更新，并不代表解析结果、Chunk、关键词索引、向量索引和缓存同时更新。

如果只更新源数据而不更新派生数据，系统可能出现：

  • 用户检索不到刚发布的内容；
  • 已修改的文档仍以旧版本参与召回；
  • 已删除或已失权的文档仍出现在答案中；
  • 向量索引、BM25 索引和元数据索引看到的版本不一致；
  • 查询缓存或答案缓存继续返回旧答案；
  • 更新任务重复执行时产生重复 Chunk、重复向量或脏数据；
  • 某个中间步骤失败后，系统无法判断应该重试、回滚还是修复。

本节关注的重点不是某一种数据库的 API，而是如何设计一条可重试、可观测、可恢复、最终一致且不会暴露旧数据的知识库更新链路。

2. 学习目标

完成本节后，应能够：

  1. 区分源数据、规范化数据和各种派生索引的职责；
  2. 为文档、版本和 Chunk 设计稳定且可追踪的标识；
  3. 设计新增、更新、删除、恢复和失效的处理流程；
  4. 理解软删除、物理删除、墓碑记录和延迟回收的区别；
  5. 使用幂等键、版本号、事件顺序和 Outbox 降低重复执行与乱序更新的风险；
  6. 在向量索引、关键词索引、缓存和权限数据之间建立一致性检查；
  7. 为增量管道配置重试、死信、监控、审计和对账任务；
  8. 通过故障注入测试验证“旧内容不可见”和“删除最终完成”。

3. 先建立正确的数据模型

3.1 源数据与派生数据

一个实用的分层方式如下：

业务源数据 / 文档管理系统
        ↓
规范化文档与版本元数据
        ↓
解析结果、段落、表格、图片、Chunk
        ↓
关键词索引、向量索引、过滤索引
        ↓
查询缓存、答案缓存、统计与审计记录

建议明确一个事实来源（source of truth）。例如，文档管理系统中的当前版本和权限状态是事实来源；解析结果、Chunk、Embedding、BM25 倒排索引和缓存都是可以重建的派生数据。

这一区分带来两个重要结论：

  • 派生索引损坏时，应能够从事实来源重新构建，而不是人工修改索引；
  • 查询时必须验证文档的当前状态和权限，不能因为某条旧向量仍存在就认为它可以被使用。

3.2 推荐的标识体系

不要只用文件名或 URL 作为索引主键。文件可能被重命名、移动或重新上传，名称并不等于身份。

标识 作用 是否应稳定
tenant_id 租户隔离边界 稳定
document_id 逻辑文档身份 跨版本稳定
version_id 某次内容版本 每次内容变更生成新值
chunk_id 某个版本中的 Chunk 至少在版本内稳定
content_hash 内容去重与变更检测 内容相同则相同
event_id 变更事件幂等键 事件生命周期内稳定
operation_id 一次处理任务的追踪键 任务生命周期内稳定

一种常见的 Chunk 主键形式是：

{tenant_id}:{document_id}:{version_id}:{chunk_no}

如果 Chunk 的位置会频繁变化，也可以把规范化文本片段的哈希纳入标识。但无论采用哪种方案，都应同时保存 document_id 和 version_id，这样才能回答“这段文本属于哪份文档的哪个版本”。

3.3 版本元数据

每个文档版本至少应保留以下信息：

DocumentVersion
├── tenant_id
├── document_id
├── version_id
├── source_updated_at
├── ingested_at
├── content_hash
├── parser_version
├── chunker_version
├── embedding_model
├── status
├── visibility
├── acl_version
└── created_by / source_uri

parser_version、chunker_version 和 embedding_model 很重要。处理逻辑或模型变化后，即使原文没有变化，也可能需要重建派生数据。只记录文档更新时间，无法判断某条向量是由什么规则生成的。

4. 文档生命周期与状态机

4.1 常见生命周期

发现变更
  ↓
接收事件
  ↓
读取并确认源版本
  ↓
解析与切分
  ↓
生成 Embedding / 关键词字段
  ↓
写入新版本索引
  ↓
校验完整性
  ↓
发布为当前版本
  ↓
失效旧缓存
  ↓
异步清理旧版本

可以为文档版本设计类似下面的状态：

状态 含义
RECEIVED 已接收变更事件，尚未开始处理
PROCESSING 正在读取源数据、解析或切分
INDEXING 正在写入一个或多个派生索引
VERIFYING 正在检查索引数量、版本和元数据
PUBLISHED 已通过校验，可参与检索
TOMBSTONED 已不可见，等待物理清理
FAILED 本次处理失败，等待重试或人工介入
PURGED 所有要求清理的副本均已处理并验证

状态机不是为了让流程看起来复杂，而是为了让系统在进程崩溃、网络超时和重复事件之后仍然知道下一步该做什么。

4.2 更新操作的推荐顺序

更新文档时，优先采用“新版本先构建、校验后切换”的方式：

  1. 读取源系统的最新内容和版本号；
  2. 计算 content_hash，如果内容和处理配置都没有变化，则可以直接结束；
  3. 创建新的 version_id；
  4. 重新解析、切分并生成派生字段；
  5. 将新版本写入向量索引、关键词索引和元数据索引；
  6. 检查新版本的 Chunk 数量、版本字段、租户字段和权限字段；
  7. 通过条件更新或版本指针，把新版本发布为当前版本；
  8. 让查询缓存和答案缓存失效；
  9. 异步清理旧版本，并记录清理结果。

不要在新版本还没有完整写入时，先删除唯一的旧版本。否则处理过程中的短暂失败会把文档变成“既没有旧版本，也没有新版本”。

5. 事件驱动的增量更新

5.1 事件应携带什么

一个更新事件不应只携带“文档发生变化”这一句模糊信息。建议包含：

{
  "event_id": "evt-...",
  "operation_id": "op-...",
  "tenant_id": "tenant-1",
  "document_id": "doc-1",
  "source_version": 42,
  "source_updated_at": "2025-01-01T12:00:00Z",
  "operation": "upsert",
  "occurred_at": "2025-01-01T12:00:01Z"
}

事件中的内容不一定要携带完整文档，但应能定位到源数据，并携带可比较的版本信息。消费者读取源数据时仍要再次确认版本，避免事件产生后源数据又发生了变化。

5.2 Outbox 与消息投递

如果业务事务已经提交，但“发送索引更新消息”失败，就会出现源数据已变更、索引永远不更新的问题。常见解决方案是 Transactional Outbox：

  1. 在同一个数据库事务中更新业务数据并写入 Outbox 记录；
  2. 独立投递器读取未发送的 Outbox 记录；
  3. 成功投递后标记记录；
  4. 投递超时可以安全重试；
  5. 消费者使用 event_id 或业务版本保证幂等。

Outbox 不能让所有外部索引获得真正的分布式事务，但可以避免业务提交与变更事件之间出现不可追踪的空洞。

5.3 乱序事件

同一文档可能先后产生版本 42 和版本 43，但消息系统不一定按顺序交付。消费者应：

  • 比较事件中的 source_version 与当前已处理版本；
  • 对更旧的事件直接标记为已处理或跳过；
  • 对无法确认源版本的事件重新读取源数据；
  • 不允许旧事件覆盖已经发布的新版本；
  • 必要时按 tenant_id + document_id 分区，降低同一文档的并发冲突。

“消息到达得更早”不等于“内容版本更新得更晚”。排序依据应是源系统的单调版本或更新时间，而不是消费者收到消息的时间。

6. 增量管道中的一致性边界

向量索引、BM25 索引、缓存和源数据库通常不在同一个事务中。因此工程目标通常不是瞬间强一致，而是明确以下边界：

  • 可见性安全：旧版本或已删除版本不能继续被查询使用；
  • 最终完整：新版本经过重试后最终出现在所有要求的索引中；
  • 状态可解释：能够知道当前处于处理中、失败、待清理还是已完成；
  • 可恢复：可从源数据重新构建，不依赖一次成功写入；
  • 可验证：可以通过对账任务发现漏写、重复写和残留数据。

可以把一致性拆成三个层面：

6.1 业务状态一致

源系统中的文档是否存在、是否有效、当前版本是多少、用户是否有权限访问，这些信息决定文档是否有资格进入检索结果。

6.2 索引内容一致

向量索引和关键词索引中的文本、版本号、租户号、权限标签是否与规范化文档一致，Chunk 数量是否完整。

6.3 可见性与缓存一致

即使旧向量暂时还没有物理删除，也必须通过过滤条件、墓碑记录或当前版本指针使它不可见；同时还要使会返回旧答案的缓存失效。

7. 删除：软删除与物理删除

7.1 软删除

软删除是先把文档标记为不可见，而不是马上从所有存储中抹除。例如：

visibility = hidden
status = TOMBSTONED
deleted_at = 当前时间

检索时必须过滤：

tenant_id = 当前租户
AND visibility = visible
AND status = PUBLISHED

软删除的优点是速度快、可恢复、适合处理异步索引；缺点是数据仍然占用存储，如果过滤条件遗漏，就可能造成已删除内容泄漏。因此软删除不能代替权限过滤和最终清理。

7.2 物理删除

物理删除需要覆盖所有副本和路径：

源索引元数据
向量索引
关键词索引
查询缓存
答案缓存
临时文件
导出文件
备份或快照

不同存储的删除接口可能具有不同语义：有的只是标记删除，有的会延迟回收，有的还需要手动触发段合并。因此系统应记录删除请求、实际完成时间和验证结果，而不是把“删除 API 返回成功”直接等同于“数据已经完全消失”。

7.3 删除任务的幂等性

删除任务也必须可以安全重试：

  • 删除不存在的 Chunk 应视为成功或可接受状态；
  • 同一个 document_id 的删除任务重复执行不能产生错误状态；
  • 不能因为一个副本已经删除，就跳过其他副本；
  • 删除条件必须包含租户和文档范围，避免误删其他租户；
  • 物理删除失败时保留待清理记录，而不是伪装成完成；
  • 恢复文档时应生成新的可发布版本，不要盲目复活未知状态的旧索引。

8. 缓存失效策略

8.1 查询缓存

查询缓存的键至少要考虑：

tenant_id
用户或权限上下文的稳定摘要
规范化查询
过滤条件
知识库版本或文档版本摘要
检索配置版本

不能只使用原始问题作为键。相同问题在不同租户、不同权限或不同知识库状态下，结果可能完全不同。

文档更新时，可以采用以下策略：

  • 精确删除受影响文档相关的查询缓存；
  • 按租户或知识库版本提升缓存命名空间；
  • 读取缓存后再次验证其中的文档版本和可见性；
  • 对无法精确定位的缓存使用短 TTL 作为兜底，而不是永久保留。

8.2 答案缓存

答案缓存比查询缓存更危险，因为它可能直接绕过检索。如果答案引用了文档版本 41，那么文档更新到版本 42 后，旧答案不应继续直接返回。

答案缓存应保存：

答案文本
引用的 document_id / version_id / chunk_id
生成时的权限上下文摘要
检索配置版本
创建时间与过期时间

返回答案前应验证引用仍然存在、仍然可见、仍然对当前用户授权。涉及删除、权限收紧或敏感内容的场景，缓存失效应优先于普通 TTL。

9. 一个可落地的最小实现

下面是与具体消息系统和向量数据库无关的伪代码，重点是处理顺序和幂等边界：

def handle_change(event):
    if already_processed(event.event_id):
        return "duplicate"

    source = load_source(event.tenant_id, event.document_id)

    # 事件可能早于源数据库事务提交，不能把“暂时读不到”直接当成删除。
    if source is None and not source_is_confirmed_deleted(event):
        retry_later("source_not_caught_up")
        return "retry"

    if source is None or source.deleted:
        mark_invisible(event.tenant_id, event.document_id)
        delete_all_index_versions(event.tenant_id, event.document_id)
        invalidate_caches(event.tenant_id, event.document_id)
        record_tombstone(event)
        mark_processed(event.event_id)
        return "deleted"

    if is_older_than_current(event, source):
        mark_processed(event.event_id)
        return "stale_event"

    if content_and_pipeline_unchanged(source):
        publish_current_version_if_needed(source)
        mark_processed(event.event_id)
        return "unchanged"

    version = build_new_version(source)
    chunks = parse_and_chunk(source, version)
    write_keyword_index(chunks)
    write_vector_index(chunks)
    verify_version(version, chunks)
    publish_with_compare_and_set(version)
    invalidate_caches(event.tenant_id, event.document_id)
    schedule_old_versions_cleanup(event.tenant_id, event.document_id, version.version_id)
    mark_processed(event.event_id)
    return "published"

这个实现仍然需要补充：任务租约、超时、指数退避、死信队列、索引写入超时、部分成功记录、指标和对账任务。伪代码中的 publish_with_compare_and_set 也不能简单覆盖当前指针，而应确保新版本不会把更高版本降级。

10. 部分失败与重试设计

10.1 常见失败点

失败点 可能结果 建议处理
源文件暂时不可读 错误地判断为删除 延迟重试，区分“未同步”和“已确认删除”
解析器失败 没有新 Chunk 保留旧版本可见，任务进入失败状态
Embedding 服务超时 只有部分向量写入 使用版本批次或写入清单，重试缺失部分
BM25 写入成功、向量写入失败 两路召回看到不同版本 未完成前不发布，或查询端使用统一版本门槛
发布成功、缓存失效失败 返回旧答案 记录失效任务，读取缓存时再做版本校验
物理删除超时 索引中残留旧数据 保持墓碑与过滤，加入清理队列

10.2 重试原则

  1. 任务必须幂等，重试不能重复产生不可区分的数据；
  2. 可恢复错误使用指数退避和最大重试次数；
  3. 不可恢复错误进入死信队列，并保留原始事件和错误原因；
  4. 重试时重新读取源版本，不能盲目重复使用过期快照；
  5. 重试次数、最后错误和下次重试时间必须可查询；
  6. 对同一文档设置并发控制，避免多个任务互相覆盖状态。

一个简单的幂等键可以是：

{tenant_id}:{document_id}:{source_version}:{parser_version}:{chunker_version}:{embedding_model}

如果同一输入和同一处理配置已经成功，重复收到事件时可以复用结果或直接跳过；如果处理配置改变，则应视为新的构建任务。

11. 索引写入的两种策略

11.1 原地更新

直接根据 document_id 覆盖旧 Chunk 或向量。

优点：实现简单、临时存储较少。
缺点：批量写入过程中容易出现部分新、部分旧；更新失败时回滚困难；难以审计具体版本。

11.2 新版本写入后切换

先将所有新 Chunk 写入带有 version_id 的索引，再更新一个当前版本指针。

优点：容易校验、失败时可以继续使用旧版本、适合重试和灰度发布。
缺点：短时间内会保留多个版本，需要额外清理和存储空间。

对于需要较高可用性和可追溯性的 RAG 系统，通常更推荐第二种策略。关键是查询端必须同时执行版本和可见性过滤，不能只依赖“当前指针”在所有查询路径上都被正确使用。

12. 对账与修复

增量事件链路即使设计得很好，也需要周期性对账，因为消息丢失、索引接口异常和人工操作都可能造成偏差。

12.1 文档级对账

从事实来源抽样或全量扫描，比较：

  • 当前版本是否已发布；
  • 文档是否应该可见；
  • 每个版本的 Chunk 数量是否合理；
  • tenant_id、document_id 和 version_id 是否一致；
  • 解析器、切分器和 Embedding 配置是否符合当前要求；
  • 是否存在源中已删除、索引中仍可见的文档。

12.2 索引级对账

从索引侧反向扫描，寻找：

  • 不存在于源系统的文档；
  • 已过期或已删除但未进入墓碑状态的版本；
  • 没有对应元数据的孤立向量；
  • 有向量但没有关键词记录，或反之；
  • 跨租户的错误字段；
  • 同一 Chunk ID 对应多个不应并存的内容版本。

12.3 修复任务

修复不要直接修改单条索引记录，而应重新生成标准事件或构建任务：

发现不一致
  ↓
记录 discrepancy
  ↓
生成 repair operation_id
  ↓
从事实来源重新读取
  ↓
按正常增量流程构建
  ↓
校验并发布
  ↓
记录修复前后状态

这样修复逻辑与正常更新逻辑保持一致，减少“线上补丁”和“正常管道”行为不一致的问题。

13. 监控、日志与审计

13.1 建议监控的指标

  • 事件消费延迟与源数据到索引的延迟；
  • 各状态任务数量和最老任务年龄；
  • 成功率、重试率和死信数量；
  • 解析失败、Embedding 失败、索引写入失败数量；
  • 新版本发布耗时；
  • 删除请求到不可见、到物理清理的耗时；
  • 对账发现的不一致数量；
  • 缓存命中率与旧版本命中次数；
  • 向量索引和关键词索引的版本覆盖率。

13.2 日志与审计字段

每次处理至少应能通过 operation_id 串起：

event_id
operation_id
tenant_id
document_id
source_version
version_id
old_version_id
pipeline_config_version
attempt
state_before
state_after
error_type
started_at
finished_at

删除和权限变更尤其需要审计。审计记录不应包含不必要的正文或敏感信息，但要足以回答“谁在什么时候让哪份文档变得不可见，以及所有副本何时完成清理”。

14. 测试清单

14.1 幂等与顺序

  • 同一个事件投递两次；
  • 同一个文档的版本 43 先于版本 42 到达；
  • 两个相同内容但不同事件 ID 的事件到达；
  • 任务在发布前、发布后和缓存失效前崩溃；
  • 删除任务重复执行；
  • 删除不存在的文档或 Chunk。

14.2 部分失败

  • 解析成功但 Embedding 服务超时；
  • 向量写入成功但关键词索引写入失败；
  • 新版本部分写入后进程退出；
  • 发布成功但缓存系统不可用；
  • 物理删除接口返回超时但实际已经完成；
  • 源数据暂时不可读，不能被误判为删除。

14.3 安全与租户隔离

  • 租户 A 的删除不能影响租户 B 的同名文档；
  • 失权后不能通过旧查询缓存获取答案；
  • 已删除文档不能通过向量近邻结果绕过元数据过滤；
  • 答案缓存中的旧引用在权限收紧后不能继续返回；
  • 对账和修复任务也必须带租户边界。

15. 常见错误

错误一：只监听文件上传，不监听更新和删除

文件上传只是生命周期的一部分。应同时处理内容更新、移动、失效、权限变化和删除事件。

错误二：用文件名作为唯一 ID

重命名或同名文件会造成覆盖和误删。应使用稳定的 document_id，并把路径作为可变元数据。

错误三：收到删除事件后只删向量

关键词索引、元数据、查询缓存、答案缓存和备份也可能保留内容。删除范围必须根据数据生命周期明确列出。

错误四：把索引 API 成功当成全链路成功

一次写入成功只说明一个副本完成。系统仍需校验其它索引、当前版本指针、缓存和可见性。

错误五：处理失败时先删除旧版本

这会把可用文档变成空白。更稳妥的方式是保留旧版本可见，直到新版本完整、校验通过并发布。

错误六：缓存键只有用户问题

不同租户、不同权限和不同版本不应共享同一个答案缓存。缓存键或缓存返回前的校验必须包含这些上下文。

错误七：没有周期性对账

事件驱动保证及时性，对账任务保证最终可发现性。两者缺一不可。

16. 一条最小可行落地路径

如果系统还处于早期阶段，可以按以下顺序实现：

  1. 为文档引入稳定的 tenant_id、document_id 和 version_id；
  2. 把源数据当前版本作为唯一事实来源；
  3. 先实现新增和更新，采用新版本写入后切换；
  4. 查询端强制过滤租户、可见性和当前版本；
  5. 增加幂等事件表和失败重试；
  6. 实现删除墓碑和缓存失效；
  7. 增加物理清理队列及清理验证；
  8. 增加每日或定期对账；
  9. 最后再优化批量处理、并行度、索引合并和成本。

不要一开始就追求复杂的分布式事务。先把“旧数据不可见、任务可重试、失败可定位、结果可修复”做扎实，再根据规模选择消息系统、任务编排器和索引存储。

17. 小结

增量更新的核心不是“监听一个事件，然后调用一次写索引接口”，而是建立一条完整的生命周期管理链路：

稳定身份
→ 可比较版本
→ 幂等事件
→ 新版本构建
→ 多索引校验
→ 条件发布
→ 缓存失效
→ 旧版本清理
→ 对账修复

需要特别记住：

  • 源数据是事实来源，索引和缓存是可重建的派生数据；
  • 新版本应尽量先构建、校验，再切换为当前版本；
  • 删除首先要保证不可见，然后再完成物理清理；
  • 事件、更新和删除都必须支持幂等和安全重试；
  • 版本、权限、租户和缓存必须作为同一条一致性链路考虑；
  • 增量处理负责及时性，对账修复负责发现和纠正遗漏。
