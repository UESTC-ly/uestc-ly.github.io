先从一个具体问题开始

假设你要回答“示例系统怎样重置访问密码”。回答程序本身没有这家系统的最新说明， 但本地知识库里有一段经过批准的操作文档。

一种做法是让程序只凭训练时记住的内容回答。它可能不知道这份新文档，也可能把别的 系统的步骤混进来。另一种做法是先在本地知识库中找到与问题最相关的文本，再要求回答 步骤只使用这些文本作为证据。

第二种做法就是本章要建立的直觉：先找证据，再组织答案。

RAG 的定义

检索增强生成（Retrieval-Augmented Generation，RAG）是一组先从外部知识源检索 相关内容，再把选定上下文交给生成步骤回答的方法。

这里有两个不能混淆的动作：

  1. 检索（retrieval）负责从候选知识中找出可能有用的内容。
  2. 生成（generation）负责根据回答规则、用户问题和检索上下文组织结果。

“生成”不一定要求在线大语言模型。本章的离线试点使用确定性回答器，让同一输入得到 同一输出。这样可以先观察 RAG 的数据流，而不把 API、费用、网络波动或模型随机性混入 第一个实验。

RAG 使用的外部知识可以更新和核对，但这不代表结果自动正确。检索可能漏掉关键内容， 找回的内容可能过期或互相冲突，回答步骤也可能错误理解证据。因此，RAG 只能帮助降低 部分无依据回答风险，不能消除幻觉。

一条最小链路里有哪些东西

先认识本章会用到的九个位置。你暂时不需要推导公式，只要知道每一步接收什么、产出 什么。

位置 直觉解释 在离线试点中观察什么
语料（corpus） 程序允许查找的本地知识集合 固定、可阅读的输入文档
文本块（Chunk） 从文档切出的检索单位 每块内容及其来源位置
嵌入向量（Embedding） 把文本变成可比较的数值表示 确定、可重复的向量
相似度（similarity） 衡量查询与文本块在该表示下有多接近 每个候选的分数
Top-K 只保留得分最高的 K 个候选 排序后的有限候选列表
上下文（context） 最终交给回答步骤的检索内容 被选中的文本和来源位置
提示词（Prompt） 回答规则、问题和上下文的组合 指令区与知识区保持分隔
回答（answer） 回答步骤产生的用户可读结果 有证据时回答，证据不足时说明无答案
引用位置（citation positions） 指向答案实际使用的文本块 可回查的块编号或位置

完整流程见 D01：RAG 端到端流程。

第一步：准备可检索的知识

程序先接收一组本地文档。文档中的内容不会直接全部塞进回答步骤，而是被切成更小的 文本块。文本块是实际参与检索的单位，所以每一块都需要保留来源位置。

接着，程序为每个文本块生成嵌入向量。你可以暂时把向量理解为“用于比较文本的一串 数字”。离线试点采用确定性算法，不声称具有生产 Embedding 模型的语义能力；它只需 保证规则透明、输出可重复，并让相似度排序可以被测试。

这部分通常叫准备或索引阶段。最小试点把数据放在内存中，没有引入向量数据库。

第二步：查询、检索与回答

用户提交问题后，程序依次执行：

  1. 校验查询不是空字符串。
  2. 用同一套确定性规则生成查询向量。
  3. 计算查询与各文本块的相似度。
  4. 按分数排序，并选择 Top-K 个候选。
  5. 把候选文本与来源位置组成上下文。
  6. 明确分隔回答规则、用户问题和不可信的知识库上下文，形成 Prompt。
  7. 生成回答，并返回实际使用的引用位置。

Top-K 中的 K 是上限，不是“必须凑够”的数量。如果只存在两个文本块，即使请求 top_k=5，程序也只能返回最多两个真实候选，不能复制内容或制造不存在的结果。

为什么要把检索文本当作不可信数据

知识库内容可能包含错误信息，也可能出现“忽略之前规则”之类的句子。那句话属于被 检索的数据，不应该自动升级为系统指令。

因此，Prompt 需要清楚分隔：

  • 回答规则告诉程序允许做什么；
  • 用户问题说明要回答什么；
  • 检索上下文只提供待核对的证据。

这种分隔是必要的安全默认值，但不是绝对防护。它不能单独解决投毒、越权读取或所有 Prompt Injection 问题。

回答为什么还要带引用位置

只输出一句自然语言答案，读者无法知道它来自哪个文本块。返回引用位置后，可以回到 具体 Chunk 检查：

  • 引用是否真的包含答案所述事实；
  • 是否漏掉了冲突或更新的来源；
  • 回答是否超出了证据能够支持的范围。

引用位置提高可核对性，但“有引用”不等于“引用支持结论”。判断支持关系仍然需要测试 或人工审查。

五条必须明确的失败边界

情况 最小试点应怎样处理 为什么不能假装成功
空语料 明确报错或返回无答案状态 没有候选知识可检索
空查询 拒绝继续并给出具体错误 无法定义用户真正要找什么
Top-K 超过块数量 只返回现有候选 不能制造或重复候选来凑数
查询形成零向量 返回无答案或零匹配状态 相似度排序没有可靠区分信息
证据不足 明确说明无法从语料回答 猜测会把不确定性伪装成事实

这些边界的可执行证据位于 单元测试和 命令行冒烟测试。

第一次离线试跑

进入 minimal-rag 项目 README，按其中唯一维护的 启动命令运行示例。运行时按顺序寻找：

  1. 固定语料和切分后的 Chunk；
  2. 查询与确定性向量表示；
  3. 相似度分数和 Top-K 排序；
  4. 被选中的上下文；
  5. 分隔后的 Prompt；
  6. 回答和引用位置；
  7. 无答案边界的可观察结果。

本章不复制项目 README 的命令和预期输出，因为可执行入口应只有一个维护位置。

常见误解

误解一：用了 RAG，模型就不会幻觉。

不成立。RAG 增加了外部证据路径，但检索、数据、上下文构造和回答任何一段都可能失败。

误解二：相似度最高的文本一定正确。

不成立。分数只表示在当前表示与算法下更接近，不代表事实正确、最新或有权限使用。

误解三：Top-K 越大越好。

不成立。更多候选可能带来噪声、冲突和更高处理成本。K 需要结合语料与任务评估。

误解四：这个最小实现代表所有 RAG 技术。

不成立。生产系统还可能涉及复杂 Chunking、稀疏或混合检索、索引、重排、权限、评估、 监控和安全治理。本试点只建立最小主链路。

自测

不看上文，尝试回答：

  1. 检索和生成各自负责什么？
  2. 为什么 Chunk 必须保留来源位置？
  3. 当查询得到零向量时，为什么不应该随便返回第一个文档？
  4. 为什么知识库中的句子不能直接当作系统指令？
  5. 为什么“有引用”仍然需要检查证据是否支持答案？

如果你能解释这些问题，并在示例输出或代码中指出九个位置，就完成了本章的可观察学习 目标。
