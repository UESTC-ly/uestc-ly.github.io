完成本章后，你应该能够：

  • 识别需要可更新、可检索、可引用资料的 RAG 候选场景；
  • 识别更适合普通搜索、数据库查询、规则程序、工具调用或纯生成的场景；
  • 根据错误成本、权限、延迟和维护能力做出初步取舍；
  • 说明 RAG 在一个产品中负责什么、不负责什么。

不要从“我想用 RAG”开始

技术选型最容易犯的错误，是先决定答案，再寻找问题。看到向量数据库、Embedding 或聊天 界面后，很容易把所有“根据资料回答”的需求都称为 RAG。

更好的起点是业务约束：用户需要什么结果，权威事实在哪里，资料是否经常变化，是否需要 引用，错误会造成什么后果，谁有权查看哪些内容，以及团队能否持续维护数据和评估。

RAG 是一组解决手段，不是项目目标。即使最终采用 RAG，也常常需要与数据库、搜索、业务 API、权限系统和人工流程配合。

适合考虑 RAG 的信号

信号一：答案依赖一批可读取的外部资料

例如产品手册、内部流程、课程资料、支持文档或研究档案。资料中确实包含用户问题所需的 内容，并且系统可以合法、稳定地访问它们。

如果根本没有可靠资料，RAG 没有证据可检索。把零散传言放进知识库不会自动变成事实。

信号二：资料会更新，且更新速度快于模型迭代

产品版本、政策和操作步骤会变化。通过更新资料和索引，系统有机会较快反映变化，而不必 等待重新训练模型。

但必须同时设计同步延迟、版本切换和旧数据清理。否则“可以更新”只是能力，不是结果。

信号三：用户需要来源和上下文

在学习、支持和内部知识场景中，用户往往不仅要一句答案，还要知道依据来自哪一节、哪个 版本。RAG 可以把来源位置带入回答链路，提升可核对性。

引用仍需验证。一个链接存在，不代表它支持答案中的每个结论。

信号四：知识范围能够被清楚限定

例如“只回答当前产品帮助中心”“只检索本租户已授权文档”。范围越清楚，越容易构建测试 集、判断无答案并治理权限。

“回答世界上一切问题”通常不是一个可验证的 RAG 范围。

信号五：团队愿意维护数据与评估

RAG 不只是接入一次模型。资料会新增、失效、重复和冲突；查询分布也会变化。团队需要有人 负责数据、权限、索引更新、评估、监控和错误修复。

没有维护责任人的知识库，会逐渐变成另一套过时资料。

三类常见候选场景

产品与客服知识助手

用户询问安装步骤、功能限制或故障处理，答案依据版本化帮助文档。RAG 可以先找到对应产品 和版本的章节，再生成简明解释并附来源。

边界是：退款状态、账户余额等实时个人数据不应仅从静态文档推测，需要调用受控业务系统。

组织内部知识导航

员工查询制度、流程和模板位置。RAG 可以减少手工翻找，但必须继承现有权限，区分草稿与 正式文件，并对冲突版本进行治理。

边界是：它不能替代人力、法务或安全部门作最终专业判断。

有资料范围的学习助手

学习者围绕指定教材提问，系统检索相关章节，给出解释和复习路径。范围明确、来源可见， 适合训练“答案回到教材核对”的习惯。

边界是：资料本身可能不完整，系统应允许说明“教材中没有足够信息”。

不适合或不能只靠 RAG 的场景

1. 权威答案来自结构化实时状态

“我的订单现在在哪里”“账户还剩多少钱”需要读取当前业务状态。搜索说明文档只能解释 规则，不能替代订单或账务 API。此时可以让 RAG 解释字段含义，但真实数值应由权威系统返回。

2. 任务是确定性计算或严格规则执行

税率计算、日期换算、权限判定和配置校验通常应由可测试的程序执行。让模型从文档中读到 规则再心算，会引入不必要的不确定性。RAG 可以帮助找到规则说明，但计算结果应由代码给出。

3. 没有可用或可授权的知识源

如果资料不存在、质量很差、版权或隐私不允许使用，就不应该把“先建一个向量库”当作解决 方案。先解决数据来源和治理问题。

4. 任务主要追求开放式创作

写故事、头脑风暴或改写语气不一定需要检索。强行加入资料可能限制创意，还增加延迟与维护 成本。只有当创作必须遵循品牌资料、世界观设定或事实背景时，外部知识才可能有帮助。

5. 错误成本极高且没有复核机制

医疗、法律、金融和安全等场景可能需要专业判断、完整记录和责任边界。RAG 可以辅助查找资料， 但不能描述为专业人员的替代品。若无法设置拒答、复核、审计和升级路径，不应把自动生成的 答案直接当作最终决策。

6. 数据规模很小且规则稳定

如果只有十条固定问答或几个配置项，简单映射、搜索或规则程序可能更可靠、更便宜、更容易 测试。系统复杂度应与问题规模相称。

RAG 与其他方法不是互斥选项

需求 更直接的首选思路 RAG 可能承担的辅助角色
查找包含关键词的原文 普通全文搜索 对候选做语义补充和回答组织
读取实时订单状态 业务 API 或数据库查询 解释状态含义和相关政策
执行确定性计算 普通程序或规则引擎 检索规则出处供核对
改变长期输出风格 提示设计、模板或模型适配 提供品牌资料作为上下文
开放式写作 直接生成与人工编辑 在需要事实或设定时检索材料
基于文档问答 搜索或 RAG，按需求评估 检索证据、组织答案并返回引用

长上下文也不是“无需检索”的自动答案。把全部资料一次塞入请求，可能遇到输入限制、成本、 噪声、权限和更新问题；但对于很小、固定且完整的材料，直接提供全文可能比建设检索系统更 简单。需要通过真实任务评估，而不是靠口号选择。

六个决策问题

在立项前依次回答：

  1. 权威事实在哪里？ 文档、数据库、API，还是根本不存在？
  2. 资料怎样变化？ 谁更新，多久更新，旧版本何时失效？
  3. 需要怎样核对？ 是否必须展示来源、版本和证据片段？
  4. 谁可以看到？ 权限是在检索前执行，还是可能把未授权内容带入上下文？
  5. 错误代价是什么？ 可以提示用户核对，还是一次错误就会造成严重损失？
  6. 怎样证明有效？ 是否有代表性问题、相关性标注、无答案样例和人工复核流程？

如果第一问没有可靠答案，先治理数据。如果第四问没有设计，先处理权限。如果第六问只能用 “感觉回答不错”作答，先建立最小评估集。

场景选择练习

判断下面场景中 RAG 的角色，并说明理由：

  1. 根据当前产品手册回答安装问题，并返回章节链接。
  2. 查询用户今天的银行卡余额。
  3. 从五条固定规则计算会员折扣。
  4. 围绕指定教材解释概念，教材没有答案时明确说明。
  5. 自动生成医疗诊断，且没有专业人员复核。

一种合理分析是：场景 1 和 4 是 RAG 候选；场景 2 需要权威实时系统；场景 3 优先使用规则 程序；场景 5 不能把 RAG 当成专业判断替代品。真正项目还需结合权限、数据质量和错误成本。

常见误解

误解一：只要资料很多，就一定需要向量 RAG。

不成立。普通搜索、结构化查询或分层导航可能已经足够，必须用代表性问题比较。

误解二：RAG 和工具调用只能选一个。

不成立。一个助手可以用 RAG 查说明，用工具读取实时状态，并分别标明证据来源。

误解三：演示能回答三个问题，就证明场景适用。

不成立。还需要无答案、冲突、权限、更新、延迟和错误成本等测试。
