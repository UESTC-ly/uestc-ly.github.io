适用版本：Python 3.11+。这四组机制都围绕“协议”工作：迭代器协议按需产生值，装饰器协议包装调用，上下文管理器协议保证进入/退出。它们分别对应 Agent 的流式输出、工具包装、重试/观测和资源释放。

学习目标

完成本章后，你应该能够：

  1. 区分可迭代对象与迭代器，理解 for 循环背后的 iter/next/StopIteration 协议。
  2. 使用生成器、yield、yield from 和生成器表达式构建惰性数据管道。
  3. 编写保留函数元数据的无参数、带参数和类装饰器。
  4. 使用 contextlib.contextmanager 或 enter/exit 实现可靠的资源管理。
  5. 把这些机制应用到 Agent 的工具调用计时、重试、流式 token、文件/连接清理和执行上下文中。

核心概念

  • 迭代器协议定义“如何取得下一个值”，生成器用惰性暂停/恢复实现低内存和流式处理。
  • 装饰器在不改动核心函数的前提下添加横切行为；上下文管理器把资源清理绑定到退出路径。
  • 这些机制都依赖明确协议和生命周期，异常、取消、背压及元数据保留必须显式设计。
  • Agent 中它们分别对应 token/事件流、工具观测与重试、文件和连接释放。

可运行示例

本章带有 python 标记的代码块均可复制到 Python 3.11+ 中单独运行；输出示例可能包含计时数值等运行时变化。

1. 可迭代对象和迭代器

两个概念

  • 可迭代对象（iterable）：能被 iter(obj) 转成迭代器的对象，例如列表、元组、字典、字符串、文件对象。
  • 迭代器（iterator）：同时实现 iter 和 next 的对象。每次 next 返回一个值，耗尽时抛 StopIteration。

列表可以反复产生新的迭代器；迭代器自身通常是一次性的：

items = ["检索", "调用工具", "回答"]

iterator = iter(items)
print(iter(items) is items)             # False：列表不是自己的迭代器
print(iter(iterator) is iterator)       # True：迭代器返回自身

print(next(iterator))                   # 检索
print(next(iterator))                   # 调用工具
print(next(iterator))                   # 回答
try:
    next(iterator)
except StopIteration:
    print("迭代结束")

print(list(items))                      # 列表仍可重新遍历

for 循环大致等价于：

items = ["检索", "调用工具", "回答"]
iterator = iter(items)
while True:
    try:
        item = next(iterator)
    except StopIteration:
        break
    print(item)

实际开发中通常使用 for，而不是手写 while；理解协议有助于实现自定义迭代器和定位“迭代器被消费后为空”的问题。

iter/next/StopIteration 的精确行为

iter(obj) 先请求对象的迭代器；对容器通常每次返回新的游标，对迭代器则返回自身。next(iterator) 请求一个值，迭代器耗尽时抛出 StopIteration；for 循环内部捕获这个异常并正常结束，所以它不是“业务失败”。

iter(callable, sentinel) 是一个实用的哨兵形式：反复调用无参数函数，直到返回与哨兵相等的值，并且不把哨兵交给循环体。这适合读到固定结束标记的文件/协议，但 callable 的异常仍会向外传播。

source = iter(["first", "second"])
for item in iter(lambda: next(source, "END"), "END"):
    print(item)
# first
# second

iterator = iter([1])
print(next(iterator))  # 1
try:
    next(iterator)
except StopIteration as exc:
    print(type(exc).__name__)  # StopIteration：正常耗尽

可迭代容器应把游标放在新建的迭代器里，而不是放在容器本身；这样两个消费者可以独立遍历。自定义迭代器的 __next__ 每次必须返回一个值或抛出 StopIteration，不要返回 None 来表示“结束”，因为 None 可能本来就是合法数据。

自定义迭代器

下面的迭代器把一个序列按固定大小分成批次：

from collections.abc import Iterator, Sequence
from typing import TypeVar


T = TypeVar("T")


class BatchIterator(Iterator[list[T]]):
    def __init__(self, items: Sequence[T], size: int) -> None:
        if size <= 0:
            raise ValueError("批大小必须为正数")
        self._items = items
        self._size = size
        self._index = 0

    def __iter__(self) -> "BatchIterator[T]":
        return self

    def __next__(self) -> list[T]:
        if self._index >= len(self._items):
            raise StopIteration
        end = self._index + self._size
        batch = list(self._items[self._index:end])
        self._index = end
        return batch


for batch in BatchIterator(["a", "b", "c", "d", "e"], 2):
    print(batch)
# ['a', 'b']
# ['c', 'd']
# ['e']

迭代器对象把当前位置放在自身内部，因此同一个对象不能安全地被两个消费者同时独立遍历。若需要每次 for 都从头开始，应实现一个可迭代容器的 iter，每次返回新的迭代器，而不是让容器本身承担游标状态。

2. 生成器与 yield

生成器函数包含 yield，调用它时不会立即运行函数体，而是返回生成器对象。每次 next 或 for 才执行到下一个 yield，暂停并保留局部变量；结束时自动抛 StopIteration。

def countdown(start: int):
    print("生成器开始")
    while start:
        yield start
        start -= 1
    print("生成器结束")


numbers = countdown(3)
print("对象已创建")          # 对象已创建；函数体还没有执行
print(next(numbers))         # 生成器开始 / 3
print(list(numbers))         # 2, 1, 生成器结束

生成器的优势是惰性和低内存：它可以处理很大的文件、无限事件流或模型 token 流，而不用一次性把所有结果装入列表。

生成器帧、状态与 send/throw/close

生成器对象保存暂停位置、局部变量和异常处理栈。调用 next(g) 或 g.send(None) 从暂停点继续；send(value) 把值作为当前 yield 表达式的结果送回生成器。throw(exc) 在暂停点注入异常，close() 注入 GeneratorExit，通常用于提前终止并触发 finally。

def accumulator():
    total = 0
    try:
        while True:
            try:
                amount = yield total
            except ValueError as exc:
                print(f"rejected:{exc}")
                continue
            if amount is not None:
                total += amount
    finally:
        print("cleanup")


stream = accumulator()
print(next(stream))                 # 0：启动到第一次 yield
print(stream.send(3))               # 3：amount=3
print(stream.throw(ValueError("bad")))  # rejected:bad，然后仍返回 3
print(stream.send(2))               # 5
stream.close()                      # cleanup：finally 一定执行

throw 注入的异常若没有被生成器处理，就会传播给调用者；close 之后再 next 会得到 StopIteration。不要吞掉 GeneratorExit 或在清理后继续产出值，否则会破坏关闭语义。生成器内部若要“返回最终结果”，使用 return value，它会成为 StopIteration.value；不要显式抛 StopIteration，Python 3 会按 PEP 479 将生成器中的意外 StopIteration 转为 RuntimeError。

这些控制方法适合构造同步协程式管道、解析器和测试替身，但不自动带来并发：在哪个线程调用 next()/send()，生成器就在哪个线程继续执行；同一个生成器也不能被多个执行流同时推进。生成器里的阻塞 I/O 仍会阻塞调用线程。需要多个消费者、超时、取消或真正的异步 I/O 时，使用 asyncio 任务和异步生成器更合适。

生成器表达式

列表推导式立即构造列表；生成器表达式只保存计算规则：

values = (number * number for number in range(5))
print(next(values))           # 0
print(sum(values))            # 30，消费剩余的 1、4、9、16
print(list(values))           # []：生成器已经耗尽

large_ids = (f"doc-{i}" for i in range(1_000_000))
print(next(large_ids))        # doc-0；不会立即创建一百万个字符串

需要重复遍历、随机访问或调试中查看全部结果时，用列表更合适。生成器只能向前消费一次；若需要重新开始，重新调用生成器函数。

yield from：委托子生成器

yield from 把另一个可迭代对象的值逐个转发给外层生成器，并且能接收子生成器的返回值：

def emit(label: str, values: list[str]):
    for value in values:
        yield f"{label}:{value}"
    return f"{label} 完成"


def all_events():
    result = yield from emit("工具", ["开始", "完成"])
    yield f"状态:{result}"
    yield from emit("模型", ["首 token", "末 token"])


print(list(all_events()))
# ['工具:开始', '工具:完成', '状态:工具 完成', '模型:首 token', '模型:末 token']

生成器还支持 send(value)、throw(exc) 和 close()，可做协程式的数据管道，但现代异步 I/O 应优先使用 asyncio 的 async def/await。普通生成器中的 yield 不会自动并发，也不会让阻塞网络调用变成异步。

yield from 的传播与选择

yield from child 不只是一个循环简写：它会把子迭代器的值直接转发给调用者，并把 send、throw、close 传递给子生成器；子生成器正常 return value 时，表达式结果是这个 value。若 child 只是列表等普通可迭代对象，没有可供读取的业务返回值。

这使得解析器和 Agent 事件管道可以按阶段拆成小生成器，同时保留“阶段完成结果”。但 yield from 仍是同步控制流；对异步生成器，应在 async def 中使用 yield 并由 async for 消费，不能直接把普通生成器接到异步消费者。

流式 Agent 还要考虑背压：生成器每次只在消费者请求下一个事件时继续，消费者变慢会自然暂停生产；如果生产端已经在后台线程/任务中不断推送，则需要队列、容量上限和取消协议，单靠 yield 无法限制外部缓冲。

3. 装饰器：为调用添加可复用行为

装饰器接收一个函数或类并返回替换对象。语法结构是：

def decorator(func):
    return func


@decorator
def function():
    return "装饰器后的函数"


print(function())  # 装饰器后的函数

大致等价于：

def decorator(func):
    return func


def function():
    return "显式替换后的函数"


function = decorator(function)
print(function())  # 显式替换后的函数

装饰器适合日志、计时、缓存、权限、重试、指标等横切逻辑；不要把核心业务流程藏在多层装饰器里。

装饰器执行时机与叠加顺序

装饰器表达式在函数定义完成后立即求值，通常发生在模块导入阶段；它不是每次调用函数时才“查找并应用”。此时外层装饰器先求值，装饰应用从离函数最近的一层向外进行；调用包装函数时则从最外层进入，再向内层执行。

events: list[str] = []


def mark(label: str):
    def decorate(func):
        events.append(f"decorate:{label}")

        def wrapper() -> str:
            events.append(f"call:{label}:before")
            result = func()
            events.append(f"call:{label}:after")
            return result

        return wrapper

    return decorate


@mark("outer")
@mark("inner")
def answer() -> str:
    events.append("body")
    return "ok"


print(events)       # ['decorate:inner', 'decorate:outer']
print(answer())     # ok
print(events)
# ['decorate:inner', 'decorate:outer', 'call:outer:before',
#  'call:inner:before', 'body', 'call:inner:after', 'call:outer:after']

注册表、路由和权限装饰器如果在导入阶段就产生副作用，会影响测试隔离和模块导入顺序。对插件系统可考虑显式注册；对每次调用才应发生的日志、计时和重试，则把逻辑放进 wrapper。

基础装饰器与 functools.wraps

from functools import wraps
from time import perf_counter
from typing import Any, Callable, TypeVar


R = TypeVar("R")


def timed(func: Callable[..., R]) -> Callable[..., R]:
    @wraps(func)
    def wrapper(*args: Any, **kwargs: Any) -> R:
        started = perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            elapsed_ms = (perf_counter() - started) * 1000
            print(f"{func.__name__} 耗时约 {elapsed_ms:.2f} ms")

    return wrapper


@timed
def normalize_query(text: str) -> str:
    """清理用户查询。"""
    return " ".join(text.split()).lower()


print(normalize_query("  Python   Agent  "))  # python agent
print(normalize_query.__name__)               # normalize_query
print(normalize_query.__doc__)                # 清理用户查询。

如果不使用 wraps，被包装函数的 name、doc、模块等元数据会被 wrapper 覆盖，调试、文档生成和框架依赖的反射信息会变差。

类型安全的签名保留

functools.wraps 复制名称、文档和模块信息，并设置 __wrapped__；inspect.signature 通常会沿着它看到原函数签名。对 Python 3.11+ 的静态检查，可用 ParamSpec 保留任意参数列表，用 TypeVar 保留返回值类型。运行时仍要确保 wrapper 真正把参数传给原函数。

from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar


P = ParamSpec("P")
R = TypeVar("R")


def trace(func: Callable[P, R]) -> Callable[P, R]:
    @wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(f"enter:{func.__name__}")
        return func(*args, **kwargs)

    return wrapper


@trace
def join_parts(left: str, right: str, *, separator: str = "-") -> str:
    return separator.join((left, right))


print(join_parts("tool", "call", separator=":"))  # enter:join_parts / tool:call
print(join_parts.__name__)  # join_parts

如果装饰器改变了参数结构（例如新增必填参数），就不能只用原始 Callable[P, R] 标注；应显式写出新签名，或在接口层使用对象/协议。对框架依赖反射的函数，缺少 wraps 可能导致路由、依赖注入或工具 schema 生成错误。

带参数的装饰器

带参数的装饰器需要三层函数：最外层接收配置，中间层接收函数，最内层执行包装逻辑：

from collections.abc import Callable
from functools import wraps
from typing import Any, TypeVar


R = TypeVar("R")


def require_role(role: str) -> Callable[[Callable[..., R]], Callable[..., R]]:
    def decorate(func: Callable[..., R]) -> Callable[..., R]:
        @wraps(func)
        def wrapper(*args: Any, **kwargs: Any) -> R:
            actual_role = kwargs.get("role")
            if actual_role != role:
                raise PermissionError(f"需要角色 {role}，实际为 {actual_role}")
            return func(*args, **kwargs)

        return wrapper

    return decorate


@require_role("admin")
def delete_memory(key: str, *, role: str) -> str:
    return f"已删除 {key}"


print(delete_memory("session-1", role="admin"))  # 已删除 session-1
try:
    delete_memory("session-1", role="user")
except PermissionError as exc:
    print(type(exc).__name__, exc)                # PermissionError ...

真实 Agent 系统中的授权不能只依赖一个装饰器：身份认证、资源权限、审计记录和工具参数验证应在可信边界实施。装饰器适合统一执行已有的策略，不应成为绕过安全审查的魔法入口。

同步与异步装饰器不能混用

同步函数的 wrapper 应直接调用原函数；异步函数的 wrapper 应定义为 async def 并 await 原函数。用普通 def 包装异步函数只会返回 coroutine，计时/异常处理可能在真正执行前就结束；用 async def 包装同步函数又会把普通结果变成需要等待的协程，改变调用契约。

import asyncio
from collections.abc import Awaitable, Callable
from functools import wraps
from typing import ParamSpec, TypeVar


P = ParamSpec("P")
R = TypeVar("R")


def async_observe(
    func: Callable[P, Awaitable[R]],
) -> Callable[P, Awaitable[R]]:
    @wraps(func)
    async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(f"start:{func.__name__}")
        try:
            return await func(*args, **kwargs)
        finally:
            print(f"end:{func.__name__}")

    return wrapper


@async_observe
async def get_chunk(text: str) -> str:
    await asyncio.sleep(0)
    return text.upper()


async def main() -> None:
    print(await get_chunk("token"))


asyncio.run(main())
# start:get_chunk / end:get_chunk / TOKEN

需要兼容同步和异步两套工具时，通常写两个明确装饰器或在装饰阶段用 inspect.iscoroutinefunction 选择 wrapper；不要在事件循环中用 asyncio.run 强行调用异步函数。装饰器还要决定取消语义：CancelledError 通常应继续传播，清理放在 finally，而不是被“统一重试”无条件捕获。

类装饰器

类装饰器接收类对象，可以修改类或返回一个包装类。下面的例子为工具类自动登记名称：

TOOL_REGISTRY: dict[str, type] = {}


def register_tool(name: str):
    def decorate(cls: type) -> type:
        if name in TOOL_REGISTRY:
            raise ValueError(f"工具重复注册: {name}")
        TOOL_REGISTRY[name] = cls
        cls.tool_name = name
        return cls

    return decorate


@register_tool("echo")
class EchoTool:
    def run(self, text: str) -> str:
        return text


print(sorted(TOOL_REGISTRY))              # ['echo']
print(TOOL_REGISTRY["echo"]().run("hi"))  # hi
print(EchoTool.tool_name)                 # echo

类装饰器会在类定义时执行，因此重复导入、测试隔离和注册顺序要设计清楚。对于大型插件系统，显式注册函数或入口点机制有时比隐式副作用更易追踪。

类装饰器的注册副作用

类装饰器在类对象创建后、模块继续执行前运行；它可以挂元数据、登记工具或返回代理类。登记类时应校验名称冲突、保证测试可清理注册表，并避免在导入时建立网络连接。若注册顺序会影响安全策略，显式调用 register_tool(cls) 通常比隐式装饰器更容易审计。

函数装饰器包装的是调用协议，类装饰器修改的是类定义协议；二者都可能改变 isinstance、序列化和反射结果。对需要被框架识别的工具，优先保留原类/函数身份，或者明确记录包装前后的类型。

4. 上下文管理器与 with

上下文管理器定义进入和退出上下文的协议：

  • enter 在 with 开始时运行，返回值绑定到 as 后的变量。
  • exit 在离开 with 时运行，即使代码块抛出异常也会运行。
  • exit 返回 True 表示已处理该异常，异常会被抑制；通常应谨慎使用。

协议与异常语义

with manager as value 大致展开为先调用 manager.__enter__()，把返回值绑定给 value，再执行代码块，最后无论正常返回还是异常都调用 manager.__exit__(exc_type, exc_value, traceback)。如果 __enter__ 自身失败，代码块没有开始，__exit__ 不会被调用；如果 __exit__ 返回真值，当前异常被抑制，否则继续传播。

class Observe:
    def __enter__(self) -> "Observe":
        print("enter")
        return self

    def __exit__(self, exc_type, exc_value, traceback) -> bool:
        name = None if exc_type is None else exc_type.__name__
        print(f"exit:{name}")
        return exc_type is ValueError  # 只抑制已知输入错误


with Observe():
    print("normal")

with Observe():
    raise ValueError("bad")

print("after")  # 异常已被抑制，所以能继续执行

上下文管理器的职责是资源/状态的进入与退出，不是自动保证远端操作成功或可回滚。__exit__ 中记录异常时应避免泄露敏感参数；清理自身若失败，要决定是保留原异常还是报告清理错误。通常不要无条件返回 True，否则工具失败会被伪装成成功。

contextlib.contextmanager

contextlib.contextmanager 把一个包含单个 yield 的生成器函数变成上下文管理器。yield 前是进入逻辑，yield 后是退出/清理逻辑：

from contextlib import contextmanager
from time import perf_counter


@contextmanager
def measure(label: str):
    started = perf_counter()
    print(f"{label}: start")
    try:
        yield
    finally:
        elapsed_ms = (perf_counter() - started) * 1000
        print(f"{label}: cleanup ({elapsed_ms:.2f} ms)")


with measure("tool-call"):
    print("执行工具")

try:
    with measure("failed-call"):
        raise RuntimeError("工具失败")
except RuntimeError as exc:
    print(type(exc).__name__, exc)

即使工具抛异常，finally 仍会执行，所以计时、锁、临时目录和连接关闭都应放在清理路径中。contextmanager 适合短小、线性的进入/退出逻辑；需要复杂状态或多个方法时用显式类更清楚。

contextmanager 的 yield 与异常注入

被 @contextmanager 装饰的函数必须在一次进入/退出流程中恰好 yield 一次：yield 前是 __enter__，yield 后是 __exit__；没有 yield 或二次 yield 都会在运行时报告协议错误。代码块的异常会在 yield 所在位置重新注入生成器，只有生成器捕获后正常结束时才会被抑制；捕获后再次抛出则继续传播。

因此清理逻辑应放在 finally，不要只写在 yield 后的“正常返回”路径。每次 with context(): 都会创建新的上下文管理器实例；不要把同一个已使用的生成器上下文对象跨请求复用。需要公开多个资源操作、重入或复杂状态时，显式类通常比生成器装饰器更好读。

自定义同步上下文管理器

class FakeSession:
    def __init__(self, name: str) -> None:
        self.name = name
        self.closed = False

    def __enter__(self) -> "FakeSession":
        print(f"{self.name}: open")
        return self

    def request(self, path: str) -> str:
        if self.closed:
            raise RuntimeError("session 已关闭")
        return f"GET {path}"

    def __exit__(self, exc_type, exc_value, traceback) -> bool:
        self.closed = True
        print(f"{self.name}: close")
        return False  # 不吞掉异常


with FakeSession("search") as session:
    print(session.request("/docs"))
print("会话已退出")

输出为：

search: open
GET /docs
search: close
会话已退出

显式类实现适合需要公开 request、commit、rollback 等多个操作的资源对象。exit 的三个异常参数可用于记录错误，但记录后通常返回 False，让调用者继续看到原始异常。

异步上下文管理器与取消

异步上下文管理器实现 __aenter__/__aexit__，进入和退出方法可以 await 网络握手、连接关闭等 I/O。contextlib.asynccontextmanager 是同步 contextmanager 的异步对应物；在 async with 中使用，不能与普通 with 混用。

import asyncio
from contextlib import asynccontextmanager


@asynccontextmanager
async def async_session(name: str):
    print(f"{name}:open")
    try:
        await asyncio.sleep(0)
        yield name
    finally:
        await asyncio.sleep(0)
        print(f"{name}:close")


async def main() -> None:
    async with async_session("search") as session:
        print(f"request:{session}")
    try:
        async with async_session("failed"):
            raise RuntimeError("network")
    except RuntimeError as exc:
        print(type(exc).__name__)  # 连接关闭后原异常仍传播


asyncio.run(main())
# search:open / request:search / search:close
# failed:open / failed:close / RuntimeError

任务被取消时，退出路径通常会进入 finally，但清理本身也是可取消的异步操作；对必须完成的极短清理应谨慎使用 asyncio.shield，并设置超时，避免既泄露资源又无限等待。不要在事件循环中调用阻塞的同步 close；必要时把阻塞清理移到线程。

多资源与 ExitStack

当资源数量动态变化时，contextlib.ExitStack 可以按注册顺序进入并在退出时逆序清理：

from contextlib import ExitStack, contextmanager


@contextmanager
def session(name: str):
    print(f"{name}: open")
    try:
        yield name
    finally:
        print(f"{name}: close")


with ExitStack() as stack:
    sessions = [stack.enter_context(session(name)) for name in ("a", "b")]
    print([f"GET /health via {name}" for name in sessions])

这对于 Agent 按配置打开多个文件、临时目录、数据库会话或工具连接很有用。不要手动拼接一长串 close；把每个资源交给上下文管理器统一托管。

ExitStack 的动态清理边界

ExitStack.enter_context(cm) 进入一个上下文并登记其退出；stack.callback(fn, *args) 登记一个无异常语义的清理回调；stack.push(exit) 可登记已有的 __exit__。退出时按后进先出顺序清理，适合“根据模型/配置动态决定要打开哪些资源”的流程。

如果资源进入过程中途失败，已经成功进入的资源仍会由 ExitStack 清理；因此应把创建与登记尽量靠近，并在资源真正获取后立刻调用 enter_context。它只负责本地清理顺序，不会自动协调远端事务提交、重试或分布式回滚。

5. 面向 Agent 的组合示例

用装饰器包装工具调用

工具调用常需要统一计时、记录事件和把异常转成结构化结果。包装器应保留原函数元数据，并明确哪些异常会向上抛出：

from functools import wraps
from time import perf_counter
from typing import Any, Callable


def observe_tool(func: Callable[..., str]) -> Callable[..., dict[str, Any]]:
    @wraps(func)
    def wrapper(*args: Any, **kwargs: Any) -> dict[str, Any]:
        started = perf_counter()
        try:
            result = func(*args, **kwargs)
        except Exception as exc:
            return {
                "ok": False,
                "error_type": type(exc).__name__,
                # 异常文本可能包含参数或敏感数据；对外使用稳定消息。
                "error": "tool execution failed",
            }
        else:
            return {"ok": True, "result": result}
        finally:
            elapsed_ms = (perf_counter() - started) * 1000
            print(f"tool={func.__name__} elapsed_ms={elapsed_ms:.2f}")

    return wrapper


@observe_tool
def lookup(query: str) -> str:
    if not query.strip():
        raise ValueError("查询不能为空")
    return f"找到与 {query} 相关的结果"


print(lookup("Python"))  # {'ok': True, 'result': '找到与 Python 相关的结果'}
print(lookup(" "))       # {'ok': False, 'error_type': 'ValueError', ...}

生产环境还应限制异常信息长度、避免把敏感参数写入日志，并区分可重试错误、用户输入错误和系统故障。不要捕获 BaseException；KeyboardInterrupt、SystemExit 等不应被普通工具包装吞掉。

用生成器输出流式事件

from collections.abc import Iterable, Iterator


def stream_answer(chunks: Iterable[str]) -> Iterator[dict[str, str]]:
    """把文本片段转换为统一的流式事件。"""
    for index, chunk in enumerate(chunks):
        if not chunk:
            continue
        yield {"type": "token", "index": str(index), "text": chunk}
    yield {"type": "done", "index": "", "text": ""}


for event in stream_answer(["你", "", "好"]):
    print(event)
# {'type': 'token', 'index': '0', 'text': '你'}
# {'type': 'token', 'index': '2', 'text': '好'}
# {'type': 'done', 'index': '', 'text': ''}

生成器让消费者边产生边发送事件，可以降低首 token 延迟和内存占用。但它不是网络传输协议本身；HTTP/SSE、WebSocket、队列等边界还需要处理断连、背压、取消和心跳。

上下文管理器保证工具资源释放

工具可能打开文件、临时目录、数据库连接或浏览器会话。把资源生命周期包在 with 中：

from contextlib import contextmanager
from typing import Iterator


@contextmanager
def tool_context(tool_name: str) -> Iterator[dict[str, str]]:
    context = {"tool": tool_name, "status": "open"}
    print("开始:", context)
    try:
        yield context
    finally:
        context["status"] = "closed"
        print("结束:", context)


with tool_context("search") as context:
    context["request_id"] = "req-1"
    print("调用中:", context)

如果 Agent 在上下文内部提前 return 或抛出异常，finally 仍会执行。若资源是异步客户端，应使用异步上下文管理器 async with，不能把同步 close 假设成 awaitable。

事件协议、追踪与提前取消

流式 Agent 不应只产出裸字符串；建议每个事件至少包含 type、run_id、单调递增的 seq 和业务 payload。这样消费者可以区分开始、增量、工具结果、错误和完成事件，也能在重连/重试时做幂等处理。生成器天然提供“消费者要一个，生产者才推进一步”的背压，但客户端断连时必须显式关闭生成器或让上层取消任务。

from contextlib import contextmanager


@contextmanager
def connection(run_id: str):
    print(f"open:{run_id}")
    try:
        yield
    finally:
        print(f"close:{run_id}")


def stream_agent(text: str, run_id: str):
    with connection(run_id):
        yield {"type": "started", "run_id": run_id, "seq": 0, "payload": None}
        for seq, chunk in enumerate(text, start=1):
            yield {"type": "chunk", "run_id": run_id, "seq": seq, "payload": chunk}
        yield {
            "type": "completed",
            "run_id": run_id,
            "seq": len(text) + 1,
            "payload": text,
        }


stream = stream_agent("你好", "run-1")
print(next(stream))
stream.close()  # 模拟客户端断连；with 的 close 仍执行
# open:run-1
# {'type': 'started', ...}
# close:run-1

for event in stream_agent("好", "run-2"):
    print(event["type"], event["seq"])
# open:run-2 / started 0 / chunk 1 / completed 2 / close:run-2

事件中的 seq 要在重试策略中定义清楚：是每次尝试重新从 0 开始，还是全局单调递增；工具副作用要用调用 ID 做幂等保护。生成器 close 只能清理本地上下文，不能撤销已经发送给远端的请求；异步 HTTP/WebSocket 场景应把断连映射到任务取消，并在 async with 的退出路径关闭客户端。

组合案例的边界检查

把装饰器、生成器和上下文管理器叠加时，先画出边界：装饰器负责一次调用的观测/错误映射，生成器负责事件的产生时机，上下文管理器负责资源寿命。重试应包住“可重试的执行单元”，不要把已发送的每个流式 chunk 无脑重放；错误事件也要有稳定 schema，不能仅把异常文本直接发给用户。

常见坑

  1. 列表的迭代器是一次性的；调试时先把 iterator 转成 list 可能已经把它消费掉。
  2. 迭代期间修改列表或字典可能跳过元素、抛异常或造成难以解释的结果；遍历快照或构造新容器。
  3. 生成器只在 next/for 时运行；只创建生成器而不消费它，不会触发副作用。
  4. 生成器不是异步任务；其中的阻塞 I/O 仍会阻塞线程。
  5. yield from 转发值，但子生成器的 return 值不会自动成为外层输出，需要显式接收。
  6. 装饰器的执行顺序从下到上应用、调用时从上到下进入；多层装饰器要写测试确认顺序。
  7. 忘记使用 functools.wraps 会损坏 name、doc 等元数据，影响日志、测试和框架注册。
  8. 带参数装饰器要有三层闭包；少一层常导致“配置对象被当成函数调用”的 TypeError。
  9. 装饰器捕获可变全局注册表或计数器时，测试之间可能互相污染；提供清理机制或注入依赖。
  10. exit 返回 True 会吞掉异常；只有确实处理完且调用者不需要知道时才这么做。
  11. 资源清理不能只写在正常路径；使用 finally、contextmanager 或 with。
  12. 上下文管理器只能保证退出逻辑被调用，不能保证远端服务已提交、请求已成功或操作可回滚。

生命周期排错清单

遇到“流第一次有值、第二次为空”“装饰器日志缺失”或“连接偶尔未关闭”时，依次检查：

  1. 这是可迭代容器还是已经消费过的迭代器/生成器？记录对象类型和当前消费方，不要在调试打印中再次把它转换成 list。
  2. 生成器是否真正被 for、next 或异步消费者驱动？只创建对象不会运行函数体。
  3. 装饰器是在导入/定义时注册，还是在调用时执行？检查装饰器叠加顺序及 wraps 的 __wrapped__ 链。
  4. 资源是否在生成器尚未消费完就被客户端断连？对同步生成器显式 close，对异步任务传播取消并依靠 finally/async with 清理。
  5. __exit__/__aexit__ 是否错误地返回真值吞掉异常？先保留原始异常，再决定是否转换为结构化错误事件。

每条流都应有终止事件或明确的错误/取消状态；不能只依赖“消费者最终会遍历完”。测试时至少覆盖正常耗尽、消费一半后关闭、工具抛异常和任务取消四条路径。

面向 AI Agent 的应用提示

  • 工具观测：用装饰器统一记录工具名、请求 ID、耗时、成功/失败和重试次数；参数日志要脱敏并限制长度。
  • 工具协议：工具的同步版本可返回值，流式版本可返回生成器；接口命名要区分 run、stream、arun，避免把不同执行模型混在一起。
  • 流式输出：用生成器把模型片段转换为事件，消费者负责发送和背压；长流必须考虑取消和客户端断连。
  • 资源生命周期：文件、临时目录、HTTP 客户端、数据库连接和浏览器页面都应有明确 with/async with 边界。
  • 上下文传播：把 request_id、用户身份、超时和追踪信息放入显式上下文对象；不要只依赖隐式全局变量。
  • 异常语义：工具包装器可以把已知失败转成结构化结果，但权限错误、取消信号和系统级异常不能被无条件吞掉。
  • 可测试性：装饰器包装后的函数仍应能直接单测；上下文管理器应测试正常退出和异常退出两条路径。

练习题

  1. 实现一个可迭代的 Batch 类：每次 for 返回新的迭代器，支持任意可索引序列和正整数 batch size，并为非法大小写测试。
  2. 编写生成器 filter_events(events)，只输出 type 为 tool_result 且 status 为 ok 的事件；说明它与返回列表的内存差异。
  3. 使用 yield from 组合“检索事件”和“模型事件”两个子生成器，并让外层产生一个 done 事件；写出事件顺序。
  4. 编写带参数的 retry(max_attempts) 装饰器，只对指定异常重试，并使用 wraps；为成功、耗尽和非目标异常分别测试。
  5. 实现一个上下文管理器，进入时记录开始时间，退出时记录耗时，并保证代码块异常不会被吞掉；用日志或打印验证两条路径。
  6. 综合题：设计一个 Agent 工具执行管道：装饰器负责计时和结构化错误，生成器负责发出 started/chunk/completed 事件，上下文管理器负责打开和关闭一个假连接。要求正常调用和工具异常都释放连接，并讨论事件、异常和资源的边界。
  7. 综合题：实现一个可取消的流式消费模拟：生产者生成 token，消费者在收到指定 token 后停止。讨论生成器 close、客户端断连、背压与真实异步流之间的差异。

练习提示与验收标准

  • 第 1 题：提示：把数据容器和游标迭代器分开，__iter__ 每次返回新的迭代器。验收：两个 for 可以独立从首项开始；batch size 为 0 或负数时抛出明确异常。
  • 第 2 题：提示：用生成器条件过滤，不要先构造中间列表。验收：输入是大迭代器时仍按需消费；空事件、错误状态不会误输出。
  • 第 3 题：提示：让子生成器 return 一个阶段统计，再由 yield from 接收。验收：事件顺序可断言，阶段返回值不会误当成普通事件。
  • 第 4 题：提示：区分“装饰时读取配置”和“调用时计数”，使用 wraps 和目标异常元组。验收：成功、目标异常耗尽、非目标异常分别验证调用次数和传播行为。
  • 第 5 题：提示：在 try/finally 或 __exit__ 中记录清理，返回 False 保留异常。验收：正常和异常路径都记录耗时；异常类型仍能被调用者捕获。
  • 第 6 题：提示：先定义事件 schema，再决定装饰器、生成器和上下文管理器各自的责任。验收：正常/异常均释放假连接；事件序号单调；敏感参数不出现在日志。
  • 第 7 题：提示：消费者提前停止后显式关闭同步生成器，异步版本用任务取消和 async with。验收：生产者不会继续无限产出；清理发生一次；能说明背压和真实网络断连的差异。

小结

迭代器把“如何取得下一个值”标准化，生成器以暂停/恢复的方式实现惰性和流式；装饰器把计时、重试、权限等横切行为包装到调用边界；上下文管理器把资源的进入和退出绑定到 with，保证异常路径也能清理。理解这些协议后，Agent 的工具封装、流式响应、观测和资源生命周期就能用少量、可测试的 Python 代码表达清楚。
