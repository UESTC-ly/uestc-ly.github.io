Agent 与工作流：学习总览

目标：不依赖具体框架，能够说明并实现模型调用、工具调用、状态流转、错误处理、权限控制、人工介入、长任务调度和日志追踪；在此基础上再理解 LangChain、LangGraph、LlamaIndex 与模型厂商原生 SDK 的抽象。

1. 本组笔记导航

  1. ReAct 与 Tool Calling：理解 Agent 的基本循环，以及模型如何提出工具调用请求。
  2. Planning 与 Memory：学习任务拆解、重新规划和记忆读写边界。
  3. Agent、Workflow 与状态机：区分自主决策与确定性编排，并设计可持久化状态。
  4. 工具权限控制与可靠性：覆盖鉴权、超时、重试、幂等、补偿和可观测性。
  5. Human-in-the-loop 与长任务：处理审批、暂停恢复、队列、异步任务和取消。
  6. MCP 与多 Agent：掌握 MCP 的基本角色，并判断何时需要多 Agent。
  7. 框架映射与原生实现：把概念映射到常见框架，并给出脱离框架的实现蓝图。
  8. 综合练习与验收清单：通过一个端到端练习验证是否真正掌握。

2. 总体心智模型

一个可控的 Agent 系统不是“把模型放进循环”这么简单，而是由以下部分组成：

用户请求
   ↓
输入整理与上下文加载
   ↓
模型决策：直接回答 / 生成计划 / 请求工具 / 请求人工确认
   ↓
策略层：校验参数、检查权限、预算与风险
   ↓
执行层：调用工具或提交异步任务
   ↓
状态层：保存消息、结果、阶段、重试次数和检查点
   ↓
观测层：日志、Trace、指标、审计记录
   ↓
继续决策或生成最终答案

关键边界是：

  • 模型决定建议什么：例如选择工具、生成参数、提出计划。
  • 应用程序决定允许什么：例如工具是否存在、参数是否合规、用户是否有权限、是否需要确认。
  • 真实系统决定执行结果：数据库、业务 API、队列和人工审批才是事实来源。
  • 工具返回值、检索内容和用户输入都应视为不可信数据，不能自动升级为系统指令。

3. 推荐学习顺序

第一阶段：最小闭环

先手写一个只支持 2～3 个只读工具的循环：模型请求工具 → 本地校验 → 执行 → 回传结果 → 模型回答。暂时不引入复杂 Agent 框架。

第二阶段：可控性

加入最大步数、工具白名单、参数 Schema 校验、超时、有限重试、错误分类、结构化日志和调用 ID。

第三阶段：状态与可靠性

把内存中的消息列表改成显式状态；增加状态机、检查点、幂等键、断点恢复和人工审批。

第四阶段：扩展能力

再学习 Planning、Memory、MCP、长任务和多 Agent，并比较它们与确定性 Workflow 的适用边界。

第五阶段：框架映射

最后把已经理解的原语映射到 LangChain、LangGraph、LlamaIndex 和模型厂商 SDK。框架是实现加速器，不是概念本身。

4. 核心原则清单

  • 先定义状态和边界，再决定是否使用 Agent。
  • 能用确定性 Workflow 表达的步骤，不要交给模型自由决定。
  • 工具调用必须经过本地解析、Schema 校验、权限控制和审计。
  • 有副作用的工具必须考虑人工确认、幂等和补偿。
  • 所有循环都要有预算：最大步数、总耗时、Token、费用和并发数。
  • 失败处理要区分参数错误、权限错误、超时、限流、临时故障和业务拒绝。
  • 长任务必须持久化状态，不能只依赖一次 HTTP 请求或进程内内存。
  • Memory 不是“把所有聊天记录都塞回 Prompt”，而是带来源、范围、时效和删除策略的状态管理。
  • 日志既要能追踪一次任务的完整链路，也要避免记录密码、令牌和不必要的敏感数据。

5. 最小验收目标

完成本组学习后，应能独立画出并解释以下链路：

请求 → 状态加载 → 模型调用 → 工具请求 → Schema 校验
     → 权限判断 → 工具执行 → 错误分类/重试/补偿
     → 状态持久化 → 必要时人工审批 → 最终响应

还应能够回答：

  1. 这个任务为什么需要 Agent，而不是普通 Workflow？
  2. 模型生成的工具参数为什么不能直接执行？
  3. 进程重启后如何从上一个安全检查点继续？
  4. 哪些错误可以重试，哪些错误必须停止或请求人工处理？
  5. 何时应该拆成多个 Agent，何时拆分只会增加成本和故障面？
