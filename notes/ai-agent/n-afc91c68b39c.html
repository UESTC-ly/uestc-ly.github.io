记忆句：开关店用 lifespan，每单前后用中间件，回单后的小事用后台任务。

1. 先问“这件事什么时候做”，再选工具

假设一个接口需要记录耗时、使用共享 HTTP 客户端，并在处理完毕后写一条通知。这三件事都不是核心业务计算，但发生的时间不同：客户端应该在应用启动时准备，计时要包住每一次请求，通知可以在响应发送后执行。

如果把它们都写进路由，会出现重复代码和生命周期混乱。例如每来一个请求就创建共享资源，会失去复用价值；把每次请求的计时放到启动阶段，又根本测不到单个请求。

工具 作用范围 适合解决的事
lifespan 一个应用进程的运行周期 创建和关闭共享客户端、连接池等资源
中间件 每个经过它的请求/响应 统一加响应头、记录请求信息
BackgroundTasks 当前响应发送后的进程内工作 不要求持久可靠的小任务

把应用想成餐厅：开店时准备公共设备，对应 lifespan；每单经过收银台，对应中间件；给顾客回单后补记一条内部记录，对应后台任务。类比只帮你定位时间，不代表后台任务另有一支独立、可靠的工作队伍。

2. 中间件为什么能同时处理请求和响应？

中间件像包在路由外的一层处理逻辑。请求进入时先经过它；它调用 call_next(request)，把请求交给后续处理；拿到响应对象后，再加工响应并返回。于是可以在调用前记录开始时间，在调用后添加耗时头。

不是每个公共功能都应写成中间件。需要全局观察请求或统一处理响应头时，中间件很合适；需要为某个接口提供“当前用户”“数据库会话”等有明确类型与依赖关系的业务资源时，Depends 往往更清晰。区别是你在处理整个请求外层，还是在为业务函数准备输入。

多个中间件会形成嵌套，响应回程与请求进入时的顺序相反。排查“响应头为什么被覆盖”等问题时，要想到这个套层关系，而不能把它们当成互不影响的独立回调。

3. 最小 demo：只观察中间件前后两段

保存为 main.py，运行 python -m uvicorn main:app --reload。

from time import perf_counter
from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def timer(request: Request, call_next):
    started = perf_counter()
    response = await call_next(request)
    response.headers["X-Process-Time"] = f"{perf_counter() - started:.6f}"
    return response

@app.get("/ping")
def ping():
    return {"message": "pong"}

打开 /docs 调用 /ping，响应正文仍是 {"message":"pong"}，在响应头区域查看 x-process-time，其值是本次测量的秒数。换一个路由时，同一个中间件也会参与处理，所以不必在每个函数中复制计时代码。

这个数字测量到 call_next 返回响应对象为止，不是浏览器收到全部内容的总耗时。网络传输不在其中，流式响应后续持续产生和发送内容的时间也不能据此完整判断。理解测量边界，比记住计时 API 更重要。

可选配套文件：demos/ch11.py。它同时演示 lifespan、CORS 和后台任务，与正文精简例不完全相同；可用 python -m uvicorn demos.ch11:app --reload 启动。

4. lifespan：共享资源的“出生与销毁”

有些资源值得在多个请求间复用，例如支持复用的 HTTP 客户端或数据库连接池。它们在应用开始接收请求前创建，在应用退出时关闭。lifespan 使用异步上下文管理器表达这个过程：yield 前负责准备，yield 后负责收尾。

这里的 yield 可以记作“把控制权交给应用正常运行”。它不是每来一个请求就执行一次，也不是把 HTTP 内容流给客户端。共享资源可以放到 app.state 等明确位置供请求处理访问，但“能全局访问”不等于“适合全局共享”。例如一个请求专用的数据库会话，通常仍应按请求创建和释放。

尤其要记住：这里的“共享”通常指同一进程内。启动多个 worker 时，每个 worker 都有自己的内存和启动过程，可能各自创建一个连接池、各自加载一份模型。不能靠一个全局布尔变量协调所有 worker，也不能假定集群只会执行一次初始化操作。

5. BackgroundTasks：响应之后做，但仍在当前服务中

BackgroundTasks 让接口登记一个随后执行的函数，响应发送后再运行它。调用方可以更早拿到响应，但这件事仍然占用当前服务的资源；它不是自动创建独立服务，也不提供持久任务存储。

判断是否适合它，可以问：“服务此刻重启，任务丢了能接受吗？”一条可丢失的辅助记录可以考虑这种方式；必须可靠完成的账务处理、需要重试的大批量作业，则需要持久任务机制。返回了“已接受”只表示接口接受请求，不能证明后续任务已经成功。

后台函数还应自行获取和释放所需资源。请求结束后，请求专用的数据库会话等资源可能已经关闭；把会话对象直接塞给后台任务，很容易形成生命周期错误。更稳妥的是传任务所需的 ID 或简单数据，让后台工作在自己的资源范围内执行。

6. CORS 为什么也常放在这一章？

CORS 通过响应头告诉浏览器：哪些来源的前端可以跨域读取响应。来源由协议、主机、端口组成，所以 http://localhost:5173 与 http://localhost:8000 不同，localhost 和 127.0.0.1 也不能混为一谈。

浏览器对某些跨域请求会先发送 OPTIONS 预检，询问目标接口是否允许指定来源、方法和头部。CORS 中间件可以统一处理这类协议要求，不必在每个路由中编写同样的逻辑。前端需要读取自定义响应头时，还可能需要在 CORS 配置的 expose_headers 中明确列出。

CORS 是浏览器的跨域访问规则，不是身份认证。 curl、其他服务器等客户端不会因为浏览器的同源策略就失去发请求的能力。因此“只允许我前端的来源”不能替代认证和资源权限检查。携带 Cookie 等凭证时，要明确配置允许来源及凭证规则，不能简单把所有配置都设成通配符。

7. 合上笔记再回答

  1. 共享 HTTP 客户端应该在哪创建？ 通常在 lifespan 中准备，并在退出时关闭。
  2. 每个接口都要加同一个响应头，应该放哪里？ 通常放中间件，统一处理。
  3. 接口返回成功，后台任务是否一定成功？ 不一定，两者发生在不同时间，后台任务还可能失败或丢失。
  4. 两个 worker 共用一个 app.state 吗？ 不共用，它们是不同进程，各有自己的状态。
