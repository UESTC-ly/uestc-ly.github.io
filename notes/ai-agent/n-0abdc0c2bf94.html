1. 为什么登录成功了，还不能随便访问接口？

假设任务系统里有小李和小王。小李登录后，把地址中的任务编号从自己的改成小王的。如果服务器只检查“有没有登录”，就可能把小王的数据交给小李。

这里有两道不同的判断。认证判断“这份凭证能代表谁”；授权判断“这个人能对这个资源做什么”。认证成功只说明身份可信，不能推出拥有全部资源的访问权。实际业务里，授权常常需要同时看当前用户、资源所有者和操作类型，而不只是看一个 is_admin 字段。

可以把 token 想成门票。拿着票来到检票口，不等于票是真的；票是真的，也不等于可以坐所有座位。这个类比的边界是：Bearer token 通常“谁拿到谁就能使用”，不一定像实名票那样自动核对持有人本人。因此它本身就是需要保护的凭证。

2. 一次受保护的请求经过什么流程？

客户端通常在请求头里携带 Authorization: Bearer <token>。服务器先从头部提取 token，再验证其有效性，找出对应用户，最后执行接口所需的权限判断。通过所有判断后，才进入业务操作。

FastAPI 的 HTTPBearer 负责识别 Bearer 格式、提取凭证，并在接口文档中描述这种安全方式。它不负责证明 token 可信。 真正的认证需要应用自己的逻辑，例如查服务端会话，或验证身份系统签发的凭证。

这正适合使用依赖注入：把“取得当前用户”写成依赖，路由通过 Depends 获得已经验证的用户。这样业务函数关注“为谁处理任务”，而不用每次重新抄一遍请求头解析代码。依赖抛出异常时，当前请求会提前失败，业务函数不会继续执行。

3. 最小 demo：只看懂认证链条

以下固定 token 只用于本地理解流程，没有登录、签发、过期、撤销，也不构成生产认证方案。保存为 main.py，运行 python -m uvicorn main:app --reload。

from fastapi import Depends, FastAPI, HTTPException
from fastapi.security import HTTPBearer

app = FastAPI()
bearer = HTTPBearer(auto_error=False)

def current_user(credentials=Depends(bearer)):
    if credentials is None or credentials.credentials != "demo-token":
        raise HTTPException(
            401, "凭证缺失或无效", headers={"WWW-Authenticate": "Bearer"}
        )
    return {"id": 1, "name": "学习者"}

@app.get("/me")
def me(user=Depends(current_user)):
    return user

这里使用传统的 =Depends(...) 写法压缩示例；它和前文 Annotated[..., Depends(...)] 表达的是同一种依赖关系。auto_error=False 让缺少或不符合预期的凭证交给依赖统一处理；读取 .credentials 取得的是去掉 Bearer 前缀后的内容。

打开 /docs，先直接调用 /me：预期返回 401。再点 Authorize，只填入 demo-token 后重试：预期得到用户信息。把 token 改成其他内容会重新得到 401。这三个结果对应“未提供、已验证、验证失败”，没有实现资源授权。

可选配套文件：demos/ch09.py。它保留更明确的类型声明，与正文精简例不完全相同；可以用 python -m uvicorn demos.ch09:app --reload 启动。

4. 认证通过之后，权限应该在哪里判断？

对于“查看我的任务”，先通过认证得到用户 ID，再取目标任务，比较任务的所有者与当前用户。对于“管理员删除任意任务”，还要判断角色或相应操作权限。检查应该在服务器端进行，前端隐藏按钮只是交互设计，不能替代服务器的授权。

情况 通常返回 需要表达的意思
没有有效凭证 401 当前请求尚未建立可信身份
身份有效，但没有所需权限 403 已经知道你是谁，但不允许此操作
资源不存在 404 没有这个资源

有些系统对无权访问的资源也返回 404，避免暴露资源是否存在。关键是采用一致的策略，而不是把每种失败都写成“登录失败”。

5. token、JWT、OAuth2 为什么不是同一个概念？

Token 是凭证的统称，JWT 是一种 token 格式，OAuth2 是授权框架。 一个 token 可以是服务端数据库中随机字符串的索引，也可以采用 JWT 格式；“用了 token”并不等于“用了 JWT”或“实现了 OAuth2”。

JWT 常通过签名帮助接收方判断内容是否被篡改，常见的签名 JWT 内容可被解码读取，因此不要把密码放进 payload。仅仅成功解码也不代表可信，还需要验证签名、有效期，以及应用要求的签发者和受众等条件。

同样，OAuth2PasswordBearer(tokenUrl="token") 会声明获取 token 的地址并提取 Bearer token，但不会替你生成 /token 登录接口，更不会自动校验 JWT。这些工具帮你接通流程，身份规则仍需明确实现。

真正的系统还要解决凭证如何安全签发、传输、保存和失效，以及用户被禁用后如何处理。先记住本章的边界：示例只演示“提取 → 验证 → 返回用户”，没有覆盖完整身份系统。

6. 合上笔记再回答

  1. 为什么 HTTPBearer 取出了字符串，还不能直接当作已登录？ 因为格式正确不代表凭证真实有效，应用还没有完成验证。
  2. 为什么 /tasks/{id} 比 /me 多一道权限检查？ 前者指定了某个资源，必须判断当前用户与这个资源的关系。
  3. 把权限写在前端够吗？ 不够。客户端可以绕过界面直接发请求，服务器必须独立检查。
