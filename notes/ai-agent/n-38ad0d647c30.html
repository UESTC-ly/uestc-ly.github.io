完成本章后，你应该能够：

  • 区分事实、论文结论、工程经验、建议和推测；
  • 看懂“已编写、已静态检查、已运行、已审查”之间的差别；
  • 识别关于 RAG、安全和生产能力的绝对化表述；
  • 判断一个会变化的技术结论为什么需要版本、日期和一手来源。

先看两句话

句子 A：“用了 RAG，模型就不会幻觉。”

句子 B：“在检索到相关且可信的证据、上下文构造正确、回答规则有效的条件下，RAG 可能降低部分无依据回答的风险；检索和生成仍可能失败。”

句子 A 更短，也更像广告，但它把条件、失败路径和证据都删掉了。句子 B 没有承诺 万能效果，却更能指导设计和测试。技术写作中的“诚实”不是处处加一句“可能”，而是 明确说明：结论属于哪一类、在什么范围成立、证据在哪里、哪些边界还没有验证。

五类信息不要混写

类型 含义 例子 写作要求
事实 可直接核查的稳定或版本化信息 某次实际命令返回的 Python 版本 给出环境、命令或可靠来源
论文结论 论文在特定数据、模型和方法下报告的观察 某方法在论文实验中优于基线 保留实验范围，不能泛化为所有场景
工程经验 在实践中经常有效但依赖条件的做法 先做小规模离线闭环更容易排错 说明适用条件和权衡
建议 为当前教程目标选择的行动 零基础阶段先用本地确定性示例 不伪装成唯一正确方案
推测 尚未获得足够证据的解释或预测 性能下降可能来自切分策略 明确标注并安排验证

当一句话同时包含多类信息时，应拆开写。例如：“测试显示这个实现处理了空查询”是 本次测试事实；“生产环境也足够安全”则是一个范围远大得多、尚未得到支持的结论。

来源等级解决什么问题

会变化的事实包括软件版本、API 行为、价格、许可证、模型能力、服务区域和框架接口。 这类信息不能只靠记忆，也不能因为某篇文章搜索排名靠前就视为当前事实。

一般优先顺序是：

  1. 官方文档或正式规范；
  2. 原始论文；
  3. 官方代码仓库、发布记录；
  4. 官方技术博客；
  5. 权威研究机构资料；
  6. 可靠二手资料，用于补充而不是独自支撑关键可变结论。

“官方”也不等于永远正确。你还需要记录适用版本和核查日期，并在发布前重新检查会 变化的内容。正文中的来源链接应让读者就近追溯；仓库登记表不能代替读者可见的解释。

内容成熟度不是装饰标签

一个文件存在，只说明“有人写了文件”。为了避免把进度当质量，本教程区分内容状态和 验证状态：

  • planned：已规划，还没有实质交付；
  • drafting：正在编写，结构或结论可能变化；
  • reviewing：已有内容，正在接受适用审查；
  • verified：指定门禁已有可定位证据；
  • complete：所有适用门禁都满足，不表示未来无需维护；
  • static-checked：只检查了静态结构，不等于运行或生产验证；
  • unit-passed / integration-passed：测试在记录的范围和环境内通过。

作者自己的检查很重要，但作者不能同时充当唯一的独立审查者。独立审查也必须说明 范围：编辑审查通过，不代表安全测试自动通过；一次 macOS 运行通过，不代表 Windows、 Linux 和云端环境全部通过。

看见这些表述先停一下

高风险表述 问题 更诚实的改写方向
“RAG 消除幻觉” 忽略检索、数据和生成失败 说明可能降低哪些风险，以及不能保证什么
“覆盖所有 RAG 技术” 技术边界不断变化，课程必然有取舍 明确主线、选修和未覆盖范围
“这是唯一最佳方案” 缺少数据、约束和比较基线 写出评价维度与适用场景
“绝对安全” 单一控制无法覆盖全部威胁 说明信任边界、剩余风险和纵深防御
“生产验证通过” 本地示例或单次测试远小于生产门禁 只陈述实际运行环境和已通过的检查
“命令可以正常运行” 如果未实际运行，就是无证据承诺 给出验证记录，或明确标注未运行

RAG 是一组方法，不是一种固定产品。即使本教程以后加入稀疏检索、混合检索、重排、 图结构或 Agent 模式，也不能因此声称穷尽所有 RAG 技术。

一个版本变化的例子

假设一篇章节写道：“框架 X 的函数 old_call() 接受参数 Y。”半年后框架升级，函数被 移动或弃用。读者照抄失败，不一定是读者操作错误，也可能是教程没有记录适用版本。

更可靠的写法应包含：

  • 结论针对哪个产品和版本；
  • 何时查阅了哪份官方资料；
  • 示例在哪个环境运行；
  • 如果版本不匹配，读者应从哪里核对迁移说明；
  • 是否存在不依赖该框架的最小替代。

本章没有引入具体产品版本，因此不需要制造一个“最新版本”数字来显得精确。

练习：给结论贴标签

请为下面四句话选择“事实、论文结论、工程经验、建议、推测”中的一个，并写出缺少的 条件：

  1. “我在 Python 3.12 的本机环境运行了三次测试，三次都通过。”
  2. “所有向量数据库都适合任何规模的 RAG。”
  3. “对于第一次实验，先用内存数据有助于减少排错变量。”
  4. “这次回答错误可能是因为检索到了过期文档。”

第 1 句是有范围的事实；第 2 句是无法由现有范围支持的绝对结论；第 3 句更接近工程 经验或教程建议；第 4 句是需要继续验证的推测。

自测

  1. 为什么论文中的一次优势不能直接写成“在所有场景都更好”？
  2. static-checked 能证明代码运行通过吗？
  3. 一个价格或 API 行为结论至少要记录哪些信息？
  4. 为什么“有引用”仍可能不支持答案？
  5. 怎样把“绝对安全”改写成可验证的工程陈述？
