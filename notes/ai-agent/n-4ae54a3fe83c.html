1. 本节定位

RAG 的初步召回结果不能直接等同于“可以交给大模型的上下文”。候选片段可能存在以下问题：

  • 片段之间重复，浪费上下文窗口；
  • 片段过长，真正有用的信息只占其中一小部分；
  • 片段缺少标题、来源或页码，模型即使答对也无法给出可核验引用；
  • 不同文档或不同版本之间存在冲突；
  • 检索分数很高，但候选内容并不能直接支持答案。

因此，一个完整的 RAG 检索链路通常还需要经过：

初步召回
  ↓
候选过滤与排序
  ↓
上下文压缩
  ↓
重复内容处理
  ↓
证据分组与上下文组装
  ↓
答案生成与引用
  ↓
引用及答案质量评估

本节重点回答四个问题：

  1. 如何在有限 Token 预算内保留最有价值的证据？
  2. 如何识别并处理重复、近似重复和互相冲突的内容？
  3. 如何让生成答案中的每个关键结论都能追溯到原始资料？
  4. 如何区分“检索到了证据”“引用了证据”和“答案确实被证据支持”？

2. 先区分几个概念

2.1 候选文档、证据片段和上下文

这三个概念经常被混用，但在系统中最好分开：

概念 含义 典型用途
候选文档 初步检索返回的文档或 Chunk 供后续筛选
证据片段 能够支持某个问题或子问题的最小文本单元 排序、压缩、引用
上下文 最终拼接并发送给生成模型的内容 生成答案

例如，一篇 20 页的技术文档可以是一个候选文档；其中关于“异常处理”的两段文字是证据片段；将这两段文字连同标题、来源信息拼接后的内容才是最终上下文。

2.2 检索相关性不等于证据充分性

检索模型判断的是“这段文本与查询是否相关”，而答案生成需要判断的是“这段文本是否足以支持某个具体结论”。

例如，查询是“系统是否支持增量更新？”：

  • “系统包含索引管理功能”可能具有相关性；
  • “系统支持按文档版本增量更新索引，并在更新完成后切换别名”才更接近可直接引用的证据。

因此，压缩和引用阶段需要关注支持关系，而不只是相似度。

2.3 溯源、引用和可验证性

  • 溯源（provenance）：记录一条内容来自哪个文档、哪个版本、哪个 Chunk 或页码。
  • 引用（citation）：在答案中把结论与来源标识关联起来。
  • 可验证性（verifiability）：用户能够依据引用定位到原始内容，并判断引用是否真的支持该结论。

只有保存了完整的溯源信息，才有可能生成可靠的引用；只有引用位置准确，引用才具有验证价值。

3. 上下文压缩

3.1 为什么需要压缩

上下文窗口并不是越满越好。候选片段过多会造成：

  • Token 成本增加，响应延迟变高；
  • 关键证据被大量无关内容稀释；
  • 生成模型更容易受到位置、顺序和噪声影响；
  • 不同片段之间的重复或冲突更难识别；
  • 超出上下文窗口后，系统可能被迫截断重要内容。

压缩的目标不是简单地“删得越多越好”，而是在预算约束下最大化证据价值：

\[ \max_{C \subseteq D} \; \operatorname{EvidenceValue}(C) - \lambda \operatorname{TokenCost}(C) \]

其中：

  • \(D\)：候选证据集合；
  • \(C\)：最终保留的上下文；
  • \(\operatorname{EvidenceValue}(C)\)：上下文对回答问题的支持价值；
  • \(\operatorname{TokenCost}(C)\)：上下文的 Token 成本；
  • \(\lambda\)：成本与证据价值之间的权衡系数。

3.2 压缩的几个层次

层次一：文档级筛选

先决定哪些文档值得保留，例如：

  • 根据权限、租户、文档状态和版本进行过滤；
  • 过滤已删除、已过期或不适用于当前用户的文档；
  • 对同一文档的多个 Chunk 进行聚合；
  • 保留与查询最相关的若干文档。

文档级筛选适合在早期执行，因为它可以减少后续重排序和压缩的工作量。

层次二：Chunk 级筛选

在文档内部，只保留与查询直接相关的 Chunk。常见做法包括：

  • 使用初步检索分数和 Rerank 分数排序；
  • 设置最小相关性阈值；
  • 对比较题、多跳题按子问题分配候选配额；
  • 对同一文档保留若干相邻 Chunk，以避免上下文断裂；
  • 优先选择包含定义、条件、结论、步骤和限制的片段。

层次三：句子级筛选

如果 Chunk 较长，可以进一步拆成句子或段落，再保留能够支持当前问题的部分。句子级筛选的优点是节省 Token，缺点是容易丢失上下文。

需要特别保留的内容包括：

  • 所属章节标题；
  • 条件、例外和限定词，例如“仅当”“不包括”“通常”“截至某日期”；
  • 指代对象，例如“该方案”“上述接口”所指的内容；
  • 公式、表格列名和列表上下文；
  • 与结论相邻的解释或定义。

层次四：内容级压缩

内容级压缩可以将原始片段转换为更短的证据表示，例如：

  • 提取与查询相关的原句；
  • 删除寒暄、重复介绍和无关示例；
  • 把多个相邻句子合并成简短摘要；
  • 生成“事实 + 条件 + 来源”的结构化证据；
  • 使用模型对片段进行查询感知摘要。

内容级压缩风险最高，因为模型生成的摘要可能出现遗漏、改写错误或无依据推断。对于高风险领域，应优先使用抽取式压缩，或保留原文并把摘要作为辅助字段。

3.3 抽取式压缩与抽象式压缩

方法 做法 优点 风险
抽取式压缩 从原文中选择句子或连续片段 可回溯性强，较少引入新事实 压缩率有限，可能不够流畅
抽象式压缩 由模型重新概括候选内容 压缩率高，适合合并多个片段 可能遗漏条件或产生幻觉
结构化压缩 输出字段、事实、条件、证据 ID 便于程序消费和审计 需要设计稳定的数据结构
查询感知压缩 只保留与当前问题相关的内容 节省 Token，降低噪声 可能误删对多跳推理有用的背景

实用策略通常是：先做规则过滤和抽取式压缩，再视任务风险和 Token 预算决定是否使用抽象式压缩。

3.4 压缩时不能删除的内容

压缩不应只保留“看起来像答案”的句子，还必须保留可能改变结论的限定信息：

结论 = 主张 + 适用条件 + 例外情况 + 时间/版本范围

例如，以下两句话的含义并不相同：

  • “系统支持自动重试。”
  • “系统仅在网络错误且请求幂等时支持自动重试。”

如果压缩时删除“仅在网络错误且请求幂等时”，就会把有条件的事实错误地扩展为无条件事实。

3.5 Token 预算分配

上下文预算可以按任务类型分配，而不是对所有问题使用同一个固定的 Top-K：

任务类型 预算策略
单事实问答 少量高置信度片段，优先抽取相关句
比较题 为每个比较对象保留相对均衡的证据
多跳问题 为每个子问题预留候选和推理所需背景
总结题 允许更多片段，但仍需去重和按主题分组
高风险问答 保留原文、版本和限定条件，宁可减少回答范围

可以把预算分成三部分：

  1. 指令预算：系统提示词和任务说明；
  2. 证据预算：真正用于回答的检索内容；
  3. 输出预算：模型生成答案和引用所需的空间。

不要把全部上下文窗口都分配给证据，否则答案可能因输出空间不足而被截断。

4. 去重与多样性控制

4.1 重复内容的来源

RAG 中的重复通常来自以下几类情况：

  • Chunk 切分时存在重叠窗口；
  • 同一段内容出现在正文、摘要、FAQ 和附录中；
  • 多个检索器返回同一个 Chunk；
  • 同一文档存在多个版本；
  • 不同网页复制了相同的模板或公告；
  • 查询改写生成了多个相似查询。

重复内容不一定完全无用。重复可能表明某个事实在多个来源中得到确认，但直接把所有副本放入上下文会浪费预算，并可能让模型误以为同一来源是多个独立证据。

4.2 精确去重

精确去重适合处理完全相同或经过简单规范化后相同的文本。常见步骤：

  1. 去除首尾空白；
  2. 统一换行、空格和标点形式；
  3. 视场景决定是否统一大小写；
  4. 对规范化后的文本计算 Hash；
  5. 使用稳定的 chunk_id 或内容 Hash 保留唯一副本。

伪代码：

seen = set()
unique_chunks = []

for chunk in ranked_chunks:
    key = normalize(chunk.text)
    if key in seen:
        continue
    seen.add(key)
    unique_chunks.append(chunk)

实际系统中，去重键最好同时考虑文档身份和版本。例如，同一段文字在两个不同版本中出现时，不应简单地把版本信息抹掉。

4.3 近似去重

近似重复的文本在字面上可能略有不同，但表达相同事实。可以使用：

  • 字符级或词级编辑距离；
  • MinHash、SimHash 等指纹；
  • TF-IDF 或 BM25 相似度；
  • Embedding 余弦相似度；
  • 专门的句子级重复检测模型。

需要设置相似度阈值，并根据文本类型调节：

  • API 文档、法律条款和配置项对细微差异敏感，阈值不宜过于激进；
  • 新闻、公告和模板化页面可以更积极地合并；
  • 含有数字、日期、版本号和条件的内容，不能仅凭整体相似度去重。

4.4 基于 MMR 的相关性与多样性平衡

最大边际相关性（MMR）可以在相关性和新颖性之间取得平衡：

\[ \operatorname{MMR}(d)=\lambda \operatorname{Rel}(q,d)-(1-\lambda)\max_{d'\in S}\operatorname{Sim}(d,d') \]

其中：

  • \(q\)：用户查询；
  • \(d\)：待选择的候选片段；
  • \(S\)：已经选择的片段集合；
  • \(\operatorname{Rel}(q,d)\)：片段与查询的相关性；
  • \(\operatorname{Sim}(d,d')\)：候选片段与已选片段的相似度；
  • \(\lambda\)：相关性与多样性的权重。

当候选片段高度重复时，降低 \(\lambda\) 可以鼓励选择更多不同内容；当问题只需要一个精确事实时，可以提高 \(\lambda\)。

4.5 去重不能破坏证据覆盖

去重前需要判断两个片段是否真的支持同一个主张。以下情况不应简单合并：

  • 一个片段说明“支持”，另一个片段说明“存在限制”；
  • 两个片段来自不同时间或不同版本；
  • 一个片段是一般规则，另一个片段是特殊例外；
  • 两个片段分别回答多跳问题的不同子问题；
  • 文本相似，但实体、数字、单位或适用范围不同。

安全的做法是：

  1. 先识别候选片段的主张或主题；
  2. 仅对主张相同且版本、时间和权限范围一致的片段合并；
  3. 为合并结果保留全部来源 ID；
  4. 对存在差异的片段保留并标记差异，而不是静默删除。

5. 证据组织与上下文组装

5.1 不要只按检索分数拼接

简单地将 Top-K 片段按分数拼接，可能导致：

  • 同一文档的片段占满上下文；
  • 比较题只覆盖其中一个对象；
  • 多跳问题缺少某个中间步骤；
  • 相邻片段顺序混乱；
  • 低分但必要的限定条件被丢弃。

上下文组装应同时考虑：

  • 相关性；
  • 证据覆盖；
  • 内容多样性；
  • 文档和版本一致性；
  • 时间有效性；
  • 权限范围；
  • 片段之间的逻辑顺序；
  • Token 成本。

5.2 推荐的上下文单元

每个送入模型的证据单元至少可以包含：

[证据 ID]
标题：...
来源：...
文档版本：...
位置：页码/章节/段落/字符区间
内容：...

示例：

[证据 E03]
标题：索引增量更新
来源：search-guide.md
文档版本：v2.1
位置：第 4 节
内容：系统会先写入新索引，待构建完成后再切换查询别名，以避免读取到不完整索引。

证据 ID 应稳定、简短且不依赖模型自行猜测。答案只需要引用 [E03]，系统再把它映射到用户可访问的来源链接。

5.3 对多跳问题按子问题分组

对于“先比较 A 和 B，再说明哪一种更适合 C”的问题，可以按以下方式组装：

问题拆分：
- 子问题 1：A 的特征和限制
- 子问题 2：B 的特征和限制
- 子问题 3：C 的约束条件

证据分组：
- 组 A：E01, E02
- 组 B：E03, E04
- 组 C：E05

这样可以防止某一组证据因分数较高而挤占其他子问题的预算。生成阶段还应要求模型在证据不足时明确指出缺口，而不是用其他组的内容补全。

5.4 相邻片段的合并

Chunk 重叠或相邻时，可以在上下文组装阶段合并，但要注意：

  • 合并前按原文位置排序；
  • 去除重叠区域的重复句子；
  • 保留章节标题和结构层级；
  • 记录合并后包含的所有原始 Chunk ID；
  • 不跨越过大的章节边界；
  • 不把不同版本的内容合成一个无版本标识的片段。

5.5 上下文顺序

常见的排序方式包括：

  • 按相关性从高到低；
  • 按文档结构和原文顺序；
  • 先给结论性证据，再给背景证据；
  • 按子问题分组；
  • 将高置信度证据放在开头和结尾，减少长上下文中的位置影响。

不存在适用于所有任务的唯一顺序。应通过评测比较不同排序策略，而不是凭直觉确定。

6. 引用溯源设计

6.1 需要保存哪些元数据

一个可审计的证据对象可以包含以下字段：

字段 作用
evidence_id 本次回答中使用的短引用 ID
chunk_id 稳定的原始 Chunk 标识
document_id 文档标识
document_title 展示给用户的文档名称
version 文档或索引版本
source_uri 原始来源或项目内链接
location 页码、章节、段落或字符区间
text 实际送入模型的文本
original_text 必要时用于核验的原始文本
retrieval_method 向量、BM25、混合检索等
retrieval_score 初步召回分数
rerank_score 重排序分数
content_hash 用于检测内容变化
access_scope 用户、租户或权限范围
ingested_at 进入索引的时间
valid_from / valid_to 内容的有效时间范围

并不是所有字段都必须直接展示给用户，但系统应保留足够信息来回答：

  • 这条证据来自哪里？
  • 当时使用的是哪个版本？
  • 模型实际看到了哪段文本？
  • 这段文本是否在回答时对当前用户可见？

6.2 Chunk ID 必须稳定

如果每次重建索引都会生成新的随机 ID，就很难：

  • 对比索引更新前后的内容；
  • 追踪引用是否失效；
  • 排查重复召回；
  • 重放历史回答；
  • 对引用进行缓存。

稳定 ID 可以由文档 ID、版本、章节位置和内容 Hash 等信息组合生成。若文档内容发生变化，应明确决定是沿用 ID 还是生成新版本 ID，并在系统中保持一致。

6.3 引用的三种粒度

文档级引用

只标注文档名称或 URL。实现简单，但用户很难快速定位具体依据。

Chunk 级引用

引用具体 Chunk 或段落。粒度和实现成本较为平衡，适合大多数 RAG 应用。

句子级引用

把每个关键结论关联到具体句子或字符区间。可验证性最好，但需要更精细的证据抽取和引用对齐。

推荐根据风险选择粒度：普通问答可以使用 Chunk 级引用；法律、医疗、财务、运维变更等场景应尽量提供句子、页码、版本或时间范围。

6.4 生成阶段的引用约束

可以在生成提示词中明确要求：

回答要求：
1. 只使用提供的证据回答；
2. 每个重要事实后附一个或多个证据 ID；
3. 如果证据不能支持结论，明确说明信息不足；
4. 不要编造不存在的证据 ID；
5. 如果证据之间冲突，分别说明来源、版本和差异；
6. 引用应紧跟被支持的句子，而不是只在答案末尾列出来源。

需要注意：提示词只能约束模型，不能自动保证引用正确。生产系统仍应对引用 ID 做格式校验，并检查引用内容是否与答案存在基本的语义支持关系。

6.5 引用链接的安全性

引用链接也属于数据访问链路的一部分，必须：

  • 在生成引用前或展示引用时再次校验访问权限；
  • 避免把其他租户的内部路径暴露给当前用户；
  • 对临时签名 URL 设置合理过期时间；
  • 防止引用跳转到已删除或已过期的内容；
  • 记录引用展示和访问日志；
  • 区分用户可见的来源信息与系统内部调试字段。

权限过滤的完整设计将在下一节 07-文档权限与多租户隔离 中讨论。

7. 冲突、版本和时间有效性

7.1 冲突不是重复

两个片段讨论同一主题，但结论不同，不能简单按照相似度去重。例如：

  • 旧版本说明接口 A 可用，新版本说明接口 A 已废弃；
  • 一般配置允许某个操作，特殊环境禁止该操作；
  • 不同租户或不同部署环境有不同限制；
  • 两份资料的统计数字对应不同时间区间。

系统应把它们识别为“同一主题下的不同主张”，并保留冲突关系。

7.2 处理冲突的优先规则

具体规则要由业务定义，但通常可以按以下因素排序：

  1. 当前用户是否有权访问该来源；
  2. 文档是否处于有效状态；
  3. 版本是否更新；
  4. 来源是否具有更高权威性；
  5. 内容是否适用于当前环境、租户或产品版本；
  6. 资料是否明确给出发布时间或生效时间。

不能把“发布时间较晚”机械地当成“内容一定正确”。在生成答案时，应把决定依据和剩余不确定性说明出来。

7.3 面向时间的问题

对于“目前”“截至某日期”“历史上”等查询，检索和压缩阶段都需要携带时间条件：

  • 在检索过滤中加入生效时间；
  • 将时间范围放入证据元数据；
  • 在答案中明确使用的时间点；
  • 不要把不同时间点的数据直接合并成一个结论；
  • 对当前状态和历史状态分别组织证据。

8. 从证据到答案：支持关系检查

8.1 三个层次的质量判断

可以把 RAG 回答质量拆成三个层次：

  1. 证据召回：相关证据是否被检索到？
  2. 证据使用：模型是否实际使用了这些证据？
  3. 结论支持：引用的证据是否真的支持对应结论？

只检查第一层会高估系统质量。例如，候选列表中包含正确资料，但模型最终引用了无关片段，答案仍然是不可靠的。

8.2 原子化主张

为了检查引用是否准确，可以先把答案拆成原子化主张：

答案：系统支持增量更新，但不会直接覆盖在线索引。

主张 1：系统支持增量更新。
主张 2：系统不会直接覆盖在线索引。

然后为每个主张建立映射：

主张 1 → E03
主张 2 → E03, E04

检查时分别判断：

  • 引用是否存在；
  • 引用内容是否包含相关证据；
  • 是否遗漏了适用条件；
  • 是否有主张超出了证据范围；
  • 是否需要多个来源共同支持。

8.3 证据不足时的回答策略

当证据不足时，可靠系统应降低回答范围，而不是强行补全。可以使用以下表达：

  • “提供的资料只能确认……，无法确认……”；
  • “资料中没有说明……；如果需要确定该点，需要查阅……”；
  • “当前证据存在版本差异，分别是……”；
  • “以下是基于 E01 的推断，不是资料中的直接结论。”

如果系统允许推理，也应把“原文事实”和“基于事实的推断”分开表示。

9. 一个可落地的处理流程

1. 接收初步召回结果
2. 执行权限、租户、状态和时间过滤
3. 根据文档版本和来源规则处理候选
4. 对精确重复内容去重
5. 对近似重复内容计算相似度
6. 使用 Rerank、MMR 或配额策略选择证据
7. 对长 Chunk 做句子级或结构化压缩
8. 保留标题、条件、例外、版本和位置
9. 为每个证据生成本次回答内稳定的 evidence_id
10. 按子问题、文档结构或相关性组装上下文
11. 生成带引用的答案
12. 校验引用 ID、权限和引用-主张对应关系
13. 记录检索、压缩、生成和引用日志

一个简化的数据结构示例：

from dataclasses import dataclass


@dataclass
class Evidence:
    evidence_id: str
    chunk_id: str
    document_id: str
    title: str
    text: str
    source_uri: str
    location: str | None = None
    version: str | None = None
    retrieval_score: float | None = None
    rerank_score: float | None = None
    content_hash: str | None = None

上下文组装时，建议同时返回两份结果：

context_text：发送给生成模型的文本
provenance_map：evidence_id 到原始来源元数据的映射

这样可以避免把所有内部字段暴露给模型，也方便在答案生成后渲染用户可见引用。

10. 参数与延迟的权衡

调大参数 可能收益 可能代价
初步召回数量 提高召回覆盖率 后续重排、压缩和去重成本增加
Rerank 候选数量 更有机会找到高质量证据 模型调用延迟和费用增加
最终片段数量 降低漏掉关键证据的概率 噪声、重复和上下文成本增加
句子保留比例 保留更多背景信息 压缩效果变差
近似去重阈值 更积极地减少重复 可能误删细微但重要的差异
每个子问题的配额 提高多跳题覆盖率 单个子问题可用的预算减少
引用校验强度 提高可审计性 增加额外模型或规则处理

调参时不要只看最终答案是否“读起来不错”，还应同时观察：

  • Token 使用量；
  • 检索和生成延迟；
  • 重复率；
  • 证据覆盖率；
  • 引用准确率；
  • 无证据主张比例；
  • 用户点击引用后的可验证性。

11. 常见失败模式

11.1 只保留分数最高的片段

问题：高分片段可能来自同一文档，或只覆盖问题的一部分。

改进：加入文档多样性、子问题配额、MMR 和证据覆盖约束。

11. 过度压缩

问题：删除了条件、例外、时间和版本，导致答案范围被错误扩大。

改进：保留限定词和上下文；高风险场景优先抽取原文，不只保留模型摘要。

11. 把相似内容全部合并

问题：不同版本、不同环境或相反结论被错误合并。

改进：去重前比较来源、版本、时间和主张；对冲突内容显式标记。

11. 只在答案末尾列出一串来源

问题：用户不知道哪个来源支持哪个结论，无法快速核验。

改进：让引用紧跟原子化主张，并保留精确位置。

11. 允许模型自由生成引用编号

问题：可能产生不存在的 ID，或把正确 ID 放在错误结论后面。

改进：只允许模型从给定证据 ID 中选择；生成后进行格式、存在性和语义支持检查。

11. 忽略删除和版本变化

问题：引用指向已失效的内容，或新旧版本混杂。

改进：在元数据中记录版本、状态和内容 Hash，并设计引用失效处理策略。

11. 先生成摘要，再丢弃原文

问题：摘要无法证明没有遗漏或改写错误。

改进：保存原始证据与压缩结果的映射；需要审计时能够回到原文。

12. 评测指标

12.1 检索和上下文指标

  • Context Recall：回答所需的证据是否被召回；
  • Context Precision：召回内容中有多少与问题相关；
  • Evidence Coverage：各个子问题是否都有证据覆盖；
  • Redundancy Rate：最终上下文中重复内容的比例；
  • Compression Ratio：压缩前后的 Token 或字符比例；
  • Lost-in-Context Rate：关键证据被压缩或组装过程丢失的比例。

12.2 引用和生成指标

  • Citation Precision：引用的来源是否确实支持对应主张；
  • Citation Recall：重要主张是否都附有必要引用；
  • Citation Completeness：答案中的可验证事实有多少被引用覆盖；
  • Faithfulness：答案是否忠实于提供的证据；
  • Answer Correctness：最终答案是否回答了问题；
  • Abstention Quality：证据不足时是否正确拒答或限定回答范围。

评测集应包含：

  • 单事实问题；
  • 需要比较多个来源的问题；
  • 多跳问题；
  • 带时间和版本条件的问题；
  • 证据冲突的问题；
  • 检索不到答案的问题；
  • 容易受到重复内容干扰的问题。

12.3 人工评测问题

可以让评审者逐项回答：

  1. 答案中的每个关键结论是否有引用？
  2. 引用是否真的支持该结论？
  3. 是否遗漏了重要条件或例外？
  4. 引用是否能定位到原始内容？
  5. 证据之间是否存在未说明的冲突？
  6. 如果没有足够证据，系统是否诚实说明了不确定性？

13. 实践检查清单

上下文压缩

  • [ ] 是否有明确的 Token 预算？
  • [ ] 是否根据问题类型动态分配预算？
  • [ ] 是否保留标题、条件、例外和版本信息？
  • [ ] 抽象式摘要是否能回溯到原文？
  • [ ] 是否评估了压缩导致的证据丢失？

去重与组织

  • [ ] 是否使用稳定的 chunk_id 或内容 Hash？
  • [ ] 是否同时处理精确重复和近似重复？
  • [ ] 是否避免误删不同版本、时间或环境的内容？
  • [ ] 是否为比较题和多跳题保留多样化证据？
  • [ ] 相邻 Chunk 合并后是否仍能定位到原文？

引用溯源

  • [ ] 每个证据是否保存文档、版本和位置？
  • [ ] 生成模型是否只能使用给定的证据 ID？
  • [ ] 重要主张是否都有就近引用？
  • [ ] 是否检查了引用存在性和引用-主张支持关系？
  • [ ] 引用链接是否经过权限和有效性校验？
  • [ ] 是否能够重放当时的检索和生成过程？

14. 小结

上下文压缩、去重和引用溯源不是 RAG 的附属功能，而是把“检索结果”转化为“可用证据”的关键环节：

  1. 先过滤无权访问、失效或不适用的候选内容；
  2. 再通过相关性、多样性和子问题覆盖选择证据；
  3. 对重复内容进行安全去重，但保留版本和冲突信息；
  4. 在压缩时保留条件、例外、时间和结构上下文；
  5. 为证据保存稳定 ID、原文位置和版本信息；
  6. 让答案中的原子化主张与证据建立明确映射；
  7. 对引用的存在性、权限和支持关系进行后处理校验；
  8. 通过上下文、引用和答案三层指标评估整个链路。

最重要的原则是：上下文不是越多越好，引用也不是越多越可靠；真正重要的是，每个关键结论都能由少量、相关、完整且可定位的证据支持。
