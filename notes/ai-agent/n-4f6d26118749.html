完成本章后，你应该能够：

  • 区分逻辑文档、来源版本、处理版本和索引版本；
  • 设计创建、更新、删除与失败的可审计状态转换；
  • 解释增量更新为什么需要幂等、差异识别和检查点；
  • 说明删除为什么必须传播到 Chunk、向量、缓存和引用。

知识库不是一次性导入的文件夹

真实资料会修改、移动、撤回和删除。若系统只会“把全部文件再导入一遍”，小规模实验也许 能工作，但数据变大后会产生重复、长时间不可用和难以解释的旧版本。更严重的是，原文已 撤回而索引仍保留旧 Chunk，用户仍可能检索到失效内容。

因此摄取管线需要把文档生命周期当成核心数据，而不是后台脚本的附带行为。

四种版本不要混成一个字符串

逻辑文档身份

表示“这是同一份业务文档”，例如退货政策。标题或路径可能改变，逻辑身份仍可保持。

来源版本

表示源系统中的一次业务修订，例如版本号、更新时间、事件序列号或文件修订 ID。来源 时间戳的精度和可靠性需由源系统定义。

内容版本

由规范化内容摘要或等价方法识别“实际内容是否变化”。它能避免重复处理，但不能替代 业务版本，因为权限变化可能不改变正文。

处理与索引版本

Parser、清洗、切分或 Embedding 配置改变时，同一来源内容会产生不同派生结果。处理版本 记录怎样生成，索引版本记录当前查询使用哪一批产物。

把四者分开，系统才能解释“原文没变，但因为解析器修复而重新索引”这种情况。

变更检测先判断变了什么

一次同步可以遇到：

  • 新来源出现；
  • 正文改变；
  • 只有元数据改变；
  • 只有权限改变；
  • 路径移动但逻辑文档不变；
  • 来源暂时读取失败；
  • 来源明确删除或撤回。

不同事件需要不同动作。权限改变应尽快影响检索范围，即使正文摘要相同；临时读取失败 不应自动解释为删除；路径移动也不一定需要重新生成全部内容表示。

增量更新的最小闭环

一个保守流程可以是：

  1. 从源系统读取带顺序或游标的变更事件；
  2. 校验事件所属来源和权限；
  3. 比较逻辑身份、来源版本、内容摘要和处理配置；
  4. 只生成受影响的派生产物；
  5. 在新产物完整可用后切换当前版本；
  6. 记录成功检查点；
  7. 按策略清理旧产物，但保留必要审计证据。

检查点表示“已确认处理到哪里”。只有某批结果持久化并可查询后才能推进检查点，否则 进程崩溃可能跳过未完成事件。

幂等让重试不制造副本

幂等（idempotency）指同一个已识别操作重复执行，最终状态仍与执行一次一致。例如事件 source-7/version-12 因网络超时被重放，不应生成两组都标成当前的 Chunk。

实现通常需要稳定事件标识、期望版本或条件写入，并把外部副作用纳入设计。幂等不等于 “永远不会失败”，而是让失败后的有限重试可以恢复到可解释状态。

更新时避免半新半旧

若先删除旧 Chunk，再逐个写入新 Chunk，处理中断会让查询只看到半份文档。若直接把新 旧记录都标成当前，查询又可能得到冲突版本。

一种常见思路是先在新版本命名空间构建完整产物，验证数量、来源和权限后，再原子地或 通过明确状态切换当前指针。具体数据库是否支持事务、别名或版本过滤，需要按实际能力 验证。本章只说明责任，不假定所有存储都有相同机制。

删除是需要传播的业务事件

删除不只是移除原始文件。由它派生的内容可能存在于：

  • Document 与结构节点；
  • Chunk 与检索索引；
  • Embedding 与关键词表示；
  • 查询缓存和回答缓存；
  • 评估样本、调试副本与备份；
  • 引用地址和审计记录。

不同存储的保留要求可能不同，但“还能否被普通查询找回”必须有明确的完成条件。对于法律 保留、审计和备份，应由授权政策定义保留范围，不能把“为了审计”当作无限保留的理由。

墓碑记录表达已经删除

在异步系统中，立即物理删除所有记录可能无法保证各下游同时收到事件。墓碑（tombstone） 是一条表示某逻辑对象已删除或不可用的状态记录。消费者看到墓碑后撤回派生产物，并记录 处理完成情况。

墓碑不应包含不必要的原文，但需要有足够身份、版本、原因类别和事件顺序，防止旧的创建 事件稍后到达又把文档复活。何时物理清除墓碑取决于系统同步与保留策略。

具体例子：政策从 30 天改为 15 天

旧政策版本 V1 已经产生 12 个 Chunk，新版本 V2 只修改其中一段。管线可以比较结构或 内容差异，只重建受影响部分，但必须确保：

  1. 未变化 Chunk 仍引用 V2 的有效文档关系；
  2. 被修改的 V1 Chunk 不再进入当前查询；
  3. 权限与生效时间随 V2 更新；
  4. 版本切换前 V2 产物完整；
  5. 缓存不会继续返回“30 天”；
  6. 引用能够指向 V2，并在需要时解释旧版本已失效。

若 V2 随后撤回，删除事件还要传播到所有可查询派生物。只删除上传目录里的文件远远不够。

失败、重放与人工处理

事件处理需要区分可重试临时错误、确定性输入错误和策略冲突。连续失败的事件应进入可见 队列或人工处理状态，不能阻塞所有后续无关文档，也不能静默跳过。

最少可观察信息包括：事件 ID、文档 ID、期望版本、当前阶段、尝试次数、最后错误、下一 动作和检查点。日志仍需避免泄露正文和访问凭证。

状态机练习

为一份文档画出 discovered -> processing -> active -> superseded -> deleted 状态，并补充 解析失败、权限冲突和删除处理中三种状态。对每条转换回答：

  1. 谁触发；
  2. 需要哪些前置条件；
  3. 失败能否重试；
  4. 查询此时能看到哪个版本；
  5. 哪个证据证明转换完成。

自测

  1. 来源版本与内容摘要为什么不能互相替代？
  2. 权限变化为什么可能要求更新，即使正文没变？
  3. 检查点为什么必须在结果持久化后推进？
  4. 删除为什么需要墓碑或等价的传播机制？
  5. 更新时怎样避免查询看到半新半旧的数据？
