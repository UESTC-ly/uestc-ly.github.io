1. 明明都是提交数据，为什么不能都用请求体模型？

前面的 Pydantic 模型适合接收 JSON：客户端把一组结构化数据编码成 JSON，服务器再按照模型解释它。但网页表单和文件上传经常采用另一种编码。如果发送的是 multipart，却让接口按常规 JSON 读取，双方对“这包数据怎么拆”就没有达成一致。

先区分两个问题：数据的位置和请求体的格式。路径、查询参数、请求头和请求体是不同位置；JSON、URL 编码表单、multipart 则是请求体的不同格式。Content-Type 请求头告诉服务器正文采用哪种格式，不能仅靠变量名猜测。

传什么 常见声明 理解方式
JSON 对象 Pydantic 模型 按结构和字段规则解释正文
表单文本字段 Form() 从表单正文中取字段
上传文件 UploadFile 配合 File() 获得文件内容的读取接口
请求附带的元信息 Header() 从请求头取值
浏览器携带的 Cookie Cookie() 从 Cookie 中取指定值

这些声明描述的是读取规则。例如参数叫 token 并不会自动从请求头读取，参数叫 filename 也不会自动变成文件。

2. multipart 可以理解成“分格包装”

普通表单常采用 application/x-www-form-urlencoded，适合键值文本。上传文件时常采用 multipart/form-data：同一个请求体拆成多个部分，每个部分可以有自己的字段名、文件名和内容。文本备注和文件就能放在同一个请求里。

可以把 multipart 想成一个有隔间的快递箱：一个隔间装文件，另一个装备注。隔间由编码中的 boundary 区分，客户端库或浏览器会替你生成。手工只写一个 Content-Type: multipart/form-data、却不正确提供 boundary，反而可能导致解析失败。

这个类比只说明编码结构，不意味着文件会自动保存到你的业务目录。框架帮你解析请求并提供文件对象，保存到哪里、用什么名字、是否允许上传，仍然由应用决定。

3. 最小 demo：文件加一句备注

表单解析需要 python-multipart。按照学习地图安装依赖后，将下面保存为 main.py，运行 python -m uvicorn main:app --reload。

from fastapi import FastAPI, File, Form, UploadFile

app = FastAPI()

@app.post("/upload")
async def upload(file: UploadFile = File(), note: str = Form("")):
    size = 0
    try:
        while chunk := await file.read(64 * 1024):
            size += len(chunk)
        return {"filename": file.filename, "bytes": size, "note": note}
    finally:
        await file.close()

打开 /docs 中的 /upload，选择一个很小的文本文件，填写备注并提交。预期响应包含原文件名、文件字节数和备注；不选择文件会因为缺少必填参数而返回 422。这里统计的是字节，不是中文字符数。

这个例子只读取和统计，不保存文件。while 每次读取最多 64 KiB，累计读到的字节数；读到末尾时得到空字节串，循环结束。finally 确保成功或异常时都执行关闭动作。这里使用 =File()、=Form(...) 的简洁写法，与 Annotated 写法表达相同的参数来源。

可选配套文件：demos/ch10.py。它还展示请求头，与正文精简例不完全相同；可用 python -m uvicorn demos.ch10:app --reload 启动。

4. 为什么使用 UploadFile，而不是直接接收 bytes？

声明为 bytes 时，应用通常直接拿到完整文件内容，使用简单，但较大文件会占用相应的内存。UploadFile 提供文件式接口，可以逐段读取；其底层临时文件机制能在达到阈值后使用磁盘，适合不想一次持有全部内容的场景。

但不要把“逐段读取”理解成“上传被限制在 64 KiB”。示例每次读取 64 KiB，循环仍然可能累计很多次，上传总量并没有因此受限。文件解析也不等于你的业务函数正在直接从网络实时逐块接收。实际文件大小限制需要结合入口、代理、解析器及应用规则设置。

客户端提供的文件名和类型只是线索。不能把 file.filename 直接拼进任意保存路径，也不能只凭扩展名认定内容安全。业务保存通常需要生成受控名称，并按需要检查内容、类型和大小。

5. 请求头如何记忆？为什么同一请求体不能既当 JSON 又当表单？

请求头像包裹外的说明：可放追踪 ID、认证信息、缓存条件等元信息。Header() 默认把 Python 参数名里的下划线转换成连字符，因此 x_request_id 对应 X-Request-ID，头部名称本身不区分大小写。没有写 Header() 的普通标量参数，通常会按查询参数处理。

一次请求有一个整体的请求体格式。采用 multipart 上传文件时，不能同时要求 FastAPI 把整个请求体再当作一个普通 JSON 对象解析。如果确实需要“文件 + 复杂元数据”，可以把元数据作为一个表单字段中的 JSON 字符串传入，再显式解析与校验。别混淆“其中一部分包含 JSON 文本”和“整个正文就是 JSON”。

Cookie 的读取也需要显式声明 Cookie()。浏览器如何携带 Cookie 与服务器从哪里读取 Cookie 是不同问题；读到一个 Cookie 同样不代表其中的身份信息已通过验证。

6. 合上笔记再回答

  1. Form() 与 Header() 的核心差别是什么？ 数据来源不同，前者读表单正文，后者读请求头。
  2. 本例能上传 1 MB 文件吗？ 读取块大小不会阻止它累计读取 1 MB；能否接收还取决于服务其他限制。
  3. 返回了文件名，是否表示已经保存成功？ 没有，本例只解析、读取并返回信息。
