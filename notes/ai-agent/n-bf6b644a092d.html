完成本章后，你应该能够：

  • 区分描述性元数据、控制性元数据和来源血缘；
  • 说明权限为什么必须随文档与文本块传播；
  • 设计最小的来源、位置、租户、版本和处理记录；
  • 识别“检索后再隐藏”造成的越权暴露风险。

图书馆标签不只是方便查找

书脊标签可以记录分类和位置，也可能标明“仅馆内阅览”。前两项帮助查找，后一项决定 谁能使用。若复印书中一页却没有复制“仅馆内阅览”的限制，这张纸就失去了原来的控制。

RAG 中的元数据（metadata）同样不仅用于展示。标题、页码和语言帮助定位；租户、访问 组、保密等级和有效期则参与控制。Document 被切成 Chunk 后，这些约束仍然必须存在， 否则细粒度记录可能成为无权限的孤儿数据。

三类信息承担不同责任

描述性元数据

它帮助理解与引用，例如标题、作者、语言、页码、章节路径、发布时间和来源地址。描述性 字段通常可用于过滤和展示，但并不自动代表授权。

控制性元数据

它参与访问决策，例如租户 ID、资源所有者、允许的角色或组、地域限制、保密级别、失效 时间和法律保留状态。控制字段的语义必须由授权系统定义，不能由摄取脚本随意猜测。

来源血缘

来源血缘（provenance）描述内容从哪里来、经过了哪些处理、由什么版本的规则生成。它可以 连接原始对象、解析结果、清洗结果、Document 和后续 Chunk，让引用、排错、更新与撤回 有据可循。

三类信息可以位于同一个元数据对象，但字段含义和可信来源不能混淆。网页自报的“公开” 标签不应覆盖平台授权策略。

一个最小字段集合

不同项目字段会变化，但可以先回答以下问题：

问题 可能字段 注意点
这是谁 document_id、source_id 逻辑身份与具体来源可分开
从哪里来 source_uri、source_system 地址本身可能敏感
在哪里 页码、章节、节点 ID 位置应能回到原文
哪个版本 内容摘要、业务版本、处理版本 三者不是同一概念
谁能访问 tenant_id、策略或资源标识 不要只存展示用角色名
怎样产生 Loader、Parser、清洗规则版本 支持复现与撤回
当前状态 成功、部分、隔离、删除 状态转换应可审计

字段名称并不重要，重要的是定义：谁写入、何时写入、谁能修改、缺失时怎么办。

权限过滤要在内容暴露之前

一个危险流程是先跨所有租户检索，再在最终界面隐藏不允许的结果。未授权内容可能已经 进入候选列表、重排器、模型上下文、缓存或日志，即使用户界面没有显示，也已经发生边界 外处理。

更保守的原则是让授权范围在检索前或检索执行中生效，并在每个下游阶段维持约束：

  1. 请求身份由可信认证系统提供；
  2. 授权层把身份转换为当前可访问资源范围；
  3. 检索只在该范围内寻找候选，或使用等效的强制过滤；
  4. 重排、缓存、上下文和日志继续保持租户隔离；
  5. 返回引用时再次校验资源仍可访问。

具体方案取决于存储与授权架构。本章不声称某个元数据过滤器单独就能构成完整授权系统。

继承、覆盖与冲突

一份文档可能继承文件夹权限，某个附件又有更严格限制。摄取时需要明确：

  • 权限来自哪个权威系统；
  • 是复制策略快照，还是保存资源引用并实时查询；
  • 父级变化如何传播到子文档和 Chunk；
  • 多个来源权限冲突时采用什么规则；
  • 权限字段缺失时默认拒绝还是默认允许。

安全默认值通常是缺失或冲突时不发布，并记录可处理的错误。默认允许虽然减少失败，却会 扩大越权风险。

具体例子：两个租户都有“员工手册”

租户 A 与租户 B 上传了标题相同、部分内容相似的员工手册。若去重系统只按正文摘要保留 一份记录，并覆盖 tenant_id，其中一个租户可能检索到另一个租户的段落。

合理模型可以共享受控的内容实体，但必须保留两个独立来源记录与授权关系。查询 A 时， 系统只允许 A 的来源进入候选；引用也回到 A 的资源。若 B 删除文档，不应顺带删除 A 仍然 拥有的来源，反之亦然。

这个例子说明去重、存储优化和授权是不同责任。优化不能改变访问语义。

血缘让修复和撤回成为可能

假设清洗规则错误地删除了所有小数点。通过血缘记录，可以找到由该规则版本产生的文档 与 Chunk，回到原始来源，重新处理并替换旧结果。若只保存最终文本，团队可能既不知道 哪些内容受影响，也无法证明修复是否完整。

最小血缘链可以记录：原始来源标识 -> Loader 运行 -> Parser 运行 -> 清洗运行 -> Document 版本。后续章节会继续连接 Chunk、Embedding 与索引版本。

日志与元数据也可能泄露信息

文件路径可能包含姓名，来源地址可能含访问令牌，租户 ID 与错误信息可能暴露组织结构。 因此元数据不是天然无敏感信息。应按用途最小化收集，限制访问和保留期，并对密钥、令牌 和不必要的正文进行遮蔽。

审计日志要能回答谁在何时改变了什么，但不能成为一个权限更弱的全文副本。

权限建模练习

画一张包含两个租户、三个用户、两个用户组和四份文档的表。为每份文档写出权威来源、 允许范围和缺失权限时的默认行为。然后模拟：

  1. 用户从一个组中移除；
  2. 文档移动到更严格的文件夹；
  3. 一个 Chunk 丢失 document_id；
  4. 缓存中仍有旧候选。

说明每种变化如何阻止未授权内容进入上下文。
