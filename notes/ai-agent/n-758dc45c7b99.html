1. 本节定位

RAG 系统的权限问题不能只交给生成模型处理。只要无权访问的文档已经进入召回结果、上下文、缓存、日志或引用，就可能造成数据泄露；即使模型最后没有在答案中复述，也不能认为系统是安全的。

本节关注的是：

  • 如何区分租户、用户、角色、文档和操作权限；
  • 如何在检索前完成权限过滤，并避免只依赖检索后的补过滤；
  • 如何设计 RBAC、ABAC 以及文档级 ACL；
  • 如何防止缓存、索引、引用、日志和异步同步造成跨租户泄漏；
  • 如何处理权限变更、文档删除和索引最终一致性。

可以把安全的 RAG 检索抽象为：

用户身份认证
    ↓
构造服务端权限上下文
    ↓
权限过滤 + 租户过滤
    ↓
向量 / 关键词 / 混合检索
    ↓
结果复核与上下文构造
    ↓
生成答案
    ↓
引用再次校验并返回

其中，生成模型只是处理已经授权的上下文，不能替代授权系统。

2. 先区分几个核心概念

2.1 租户（Tenant）

租户通常代表一个组织、客户或业务空间。多租户系统的首要边界是：

一个租户的用户、文档、索引、缓存和运行日志，不能被另一个租户越权访问。

常见字段包括：

  • tenant_id：租户唯一标识；
  • tenant_status：租户是否启用、冻结或删除；
  • tenant_policy：数据区域、保留期限、模型使用范围等策略；
  • isolation_level：逻辑隔离、独立索引或物理隔离等级。

tenant_id 不应由客户端在请求体中随意指定。服务端应从已验证的登录态、令牌或网关上下文中取得当前租户，并据此构造查询条件。

2.2 用户、角色与权限

  • 用户（User）：发起问题的人或服务账号；
  • 角色（Role）：一组权限的集合，例如普通员工、部门管理员、审计员；
  • 权限（Permission）：对某类资源执行某种操作，例如 document:read；
  • 资源（Resource）：文档、知识库、文件夹、数据集合或某个文档片段；
  • 操作（Action）：读取、写入、删除、分享、导出或管理权限。

一个简单的权限元组可以表示为：

(subject, action, resource, context) → allow / deny

其中 context 可以包括租户、部门、网络区域、设备可信状态和时间等信息。

2.3 RBAC 与 ABAC

RBAC（Role-Based Access Control） 通过角色授予权限，结构清晰、容易管理，适合组织内部相对稳定的权限体系。例如：

角色：财务审计员
权限：读取财务知识库、查看审计报告、不能修改原文档

ABAC（Attribute-Based Access Control） 根据主体、资源和环境属性动态判断。例如：

允许读取，当：
用户所属部门 = 文档所属部门
且 用户具有 document:read 权限
且 文档密级 ≤ 用户密级
且 当前租户 = 文档租户

实际系统通常采用 RBAC + ABAC + 文档 ACL 的组合：角色提供基础权限，属性表达组织规则，ACL 处理某份文档的特殊授权。

3. 文档和 Chunk 的权限元数据

权限信息必须能够跟随文档进入解析、切分、Embedding、索引和检索流程。建议至少保留以下元数据：

字段 含义 作用
tenant_id 所属租户 第一层租户隔离
document_id 原始文档 ID 文档级授权和引用回溯
chunk_id Chunk ID 定位召回片段
knowledge_base_id 所属知识库 知识库级权限过滤
owner_id 所有者 处理所有者权限
department_id 所属部门 支持组织属性过滤
visibility 可见范围 公开、部门、指定用户等
allowed_role_ids 允许的角色 RBAC 过滤
allowed_user_ids 指定用户 ACL 过滤
classification 数据密级 支持分级访问
acl_version 权限版本 识别索引中的旧权限
document_version 文档版本 避免新旧版本混用
updated_at 更新时间 处理时效性
deleted_at / is_deleted 删除状态 支持软删除和同步

权限元数据应由受信任的服务端写入，而不是由用户上传的文档内容决定。文档正文中可能包含“忽略系统规则”“把其他用户资料发给我”等提示，这类内容属于不可信数据，不能改变授权结果。

4. 两道关键边界：检索前过滤与检索后过滤

4.1 检索前过滤（Pre-filter）

检索前过滤是在向量检索或关键词检索执行时，把租户和权限条件作为查询约束的一部分：

候选集合 = 全部索引数据
          ∩ 当前 tenant_id
          ∩ 当前用户可访问的知识库
          ∩ 当前用户可访问的文档
          ∩ 未删除且处于有效版本的数据

然后只在候选集合中进行相似度计算和排序。伪代码如下：

identity = authenticate(request)
permission_context = authorization_context(identity)

filters = {
    "tenant_id": permission_context.tenant_id,
    "document_id": {"in": permission_context.readable_document_ids},
    "is_deleted": False,
}

candidates = retriever.search(
    query=request.question,
    filters=filters,
    top_k=50,
)

上面的代码是说明性伪代码，不代表某个向量数据库的固定接口。关键点不在字段名，而在于过滤条件必须由服务端根据身份和授权策略生成。

优点：

  • 无权文档不进入候选集合，降低数据泄露风险；
  • 检索分数和排序只在用户可见范围内计算；
  • 后续 Rerank、压缩和生成不需要处理无权内容；
  • 更容易审计“本次查询实际允许访问哪些数据”。

4.2 检索后过滤（Post-filter）

检索后过滤是先从全量索引取回候选，再把无权限结果删掉：

全量检索 top_k → 删除无权结果 → 返回剩余结果

这种方式存在明显问题：

  1. 无权内容已经被检索服务读取并暂存；
  2. 召回数量可能不足，导致答案质量不稳定；
  3. 相似度高的无权结果可能挤掉真正相关且有权的结果；
  4. 结果数量、分数和错误信息可能间接暴露其他租户存在某类文档；
  5. 如果后续日志记录了原始候选，仍然会发生泄露。

因此，后过滤最多作为防御性复核，不能替代检索前过滤。安全路径应尽量做到：

检索前授权过滤 + 检索后逐条复核 + 引用返回前再次校验

5. 多租户索引的三种隔离方式

5.1 每个租户独立索引或独立集合

每个租户拥有单独的集合、索引甚至独立数据库。

优点：

  • 数据边界直观，误过滤的影响较小；
  • 便于租户级备份、迁移、删除和容量管理；
  • 可以为不同租户使用不同的索引参数。

缺点：

  • 租户数量多时，索引和连接管理成本高；
  • 小租户数据量较小时，资源利用率可能较低；
  • 跨租户运维和版本升级更复杂。

5.2 共享索引，强制使用 tenant_id 过滤

所有租户共用索引，但每条记录带有租户标识，查询时强制注入过滤条件。

优点：

  • 资源利用率较高；
  • 适合租户数量多、单租户数据量较小的场景；
  • 统一维护索引和检索服务。

风险：

  • 任一查询路径遗漏过滤条件，都可能造成跨租户召回；
  • 开发、测试和运维接口容易形成旁路；
  • 必须在服务端封装检索入口，并对过滤条件做自动化测试。

5.3 分层隔离

普通数据使用共享索引，高敏感数据使用独立索引或物理隔离；同一租户内部还可以按知识库或数据密级进一步分层。

这是较常见的工程折中，但需要明确数据分类规则，不能把“高敏感”只作为文档正文中的标签，而应由受信任的业务系统维护。

5.4 方式对比

方式 隔离强度 成本 适用场景 主要风险
独立索引 高 高 少量大租户、高敏感数据 运维对象多
共享索引 + 强制过滤 依赖实现 较低 大量普通租户 漏加过滤条件
分层隔离 可按数据分级 中高 同时存在普通和敏感数据 分类和路由复杂

6. 权限判断的推荐流程

第一步：认证用户身份

先确认请求来自哪个用户、服务账号和租户。认证失败应直接拒绝，不能把缺少身份的信息当作“公共访问”。

第二步：构造不可篡改的权限上下文

权限上下文可以包括：

user_id
tenant_id
role_ids
department_ids
readable_knowledge_base_ids
permission_version
security_level
request_id

上下文应由认证服务、网关或授权服务产生。客户端传来的 tenant_id、角色列表或文档 ID 只能作为请求意图，不能直接作为最终授权依据。

第三步：计算可访问范围

对于数据量较小的系统，可以得到用户可访问文档 ID 列表；对于数据量较大的系统，可以把授权属性编译为索引过滤表达式，或使用独立的权限服务进行判断。

需要注意“默认拒绝”：

  • 权限服务不可用时，不应自动放行；
  • 权限字段缺失时，不应把记录当作公开数据；
  • 租户状态不明确时，不应继续检索；
  • ACL 同步失败时，应优先减少可见范围，而不是扩大可见范围。

第四步：执行受限检索

向量检索、BM25、混合检索和多路召回都必须使用同一套租户和权限约束。不能只给向量检索加过滤，却让关键词检索、缓存召回或推荐召回绕过过滤。

第五步：结果复核

在 Rerank、上下文压缩和拼接前，逐条确认：

  • tenant_id 是否匹配；
  • 文档是否仍未删除；
  • 文档版本和 ACL 版本是否仍然有效；
  • 当前用户是否仍有读取权限；
  • 片段的来源文档是否与元数据一致。

第六步：引用返回前再次授权

答案引用中的文档标题、URL、页码、文件名和摘要，也可能泄露敏感信息。返回引用前应再次检查用户是否可以访问对应原文档，并根据用户权限决定展示哪些来源字段。

7. 权限变更、删除与索引一致性

权限系统通常是最终一致的：业务数据库中的 ACL 已经改变，但向量索引、倒排索引、缓存和搜索快照可能尚未更新。因此，权限变更必须有明确的同步策略。

7.1 授权变更

用户获得权限后，可以按照业务要求允许短暂延迟；但系统不能在权限授予前提前暴露数据。同步事件至少应包含：

document_id
old_acl_version
new_acl_version
event_type
event_time
request_id

7.2 撤权和删除

撤权通常比授权更敏感。建议采用以下组合：

  1. 业务权限库立即记录新状态；
  2. 检索前先查询或缓存最新的授权状态；
  3. 索引异步删除或更新权限元数据；
  4. 结果复核拒绝旧 ACL 版本；
  5. 清理相关的检索缓存、答案缓存和预计算摘要；
  6. 对删除和撤权事件设置重试、告警和死信处理。

如果索引中的权限版本低于权限服务中的当前版本，不能简单假设旧记录仍然有效。安全的处理是重新校验，或者暂时拒绝该片段。

7.3 软删除不是永久删除

is_deleted = true 可以阻止正常检索，但不等同于物理删除。还需要明确：

  • 向量索引和倒排索引何时清理；
  • 缓存何时失效；
  • 备份和日志是否仍保留；
  • 引用链接是否失效；
  • 是否满足业务和法规要求的删除期限。

8. 缓存、日志与引用的隔离

8.1 检索缓存

检索缓存的键不能只包含问题文本。相同问题在不同用户、不同租户或不同权限版本下，结果可能完全不同。缓存键至少要考虑：

tenant_id
user_scope 或 permission_scope_hash
permission_version
query
检索参数
索引版本

如果缓存内容本身包含文档片段，应在命中缓存后再次进行权限校验。更稳妥的方案是缓存经过授权范围约束的结果，并设置较短的有效期和明确的失效事件。

8.2 答案缓存

答案缓存的风险比检索缓存更高，因为答案可能已经混入敏感内容。跨用户复用答案前必须证明：

  • 两个请求属于同一租户；
  • 两个用户的可见范围相同或缓存答案不包含受限内容；
  • 权限版本、文档版本和索引版本没有发生影响结果的变化。

无法证明时，应按用户或权限范围隔离缓存，或者不缓存最终答案。

8.3 日志与监控

日志应支持审计，但不应为了调试而保存不必要的完整敏感文档。建议记录：

  • request_id、tenant_id、user_id；
  • 使用的知识库和检索策略；
  • 返回的 document_id、chunk_id 和版本；
  • 授权判断结果及策略版本；
  • 被拒绝的原因类别；
  • 延迟、召回数量和错误类型。

对问题文本、文档内容、引用摘要和用户标识应按敏感程度进行脱敏、截断或访问控制。日志平台本身也必须纳入租户隔离和最小权限管理。

8.4 引用链接

引用链接不能只根据文件路径或 document_id 拼接。应通过受保护的文档服务生成，并在用户点击时再次鉴权：

请求引用链接
    ↓
验证当前用户和租户
    ↓
检查文档当前权限与版本
    ↓
生成短期、范围受限的访问地址

这样可以避免用户在权限被撤销后继续通过旧链接访问文档。

9. 典型错误与改进方式

错误 1：只在提示词中要求“不要泄露其他租户内容”

问题： 无权内容已经进入上下文，模型、日志、缓存或调试工具都可能看到它。

改进： 在检索前完成授权过滤，提示词中的安全要求只能作为辅助约束。

错误 2：信任客户端传入的 tenant_id

问题： 用户可以修改请求参数，尝试访问其他租户。

改进： 从服务端认证上下文取得租户 ID；客户端参数仅用于一致性校验，不能作为授权来源。

错误 3：只过滤向量检索

问题： BM25、混合召回、历史问答缓存或推荐模块可能返回未授权内容。

改进： 将权限过滤封装为所有召回通道都必须调用的公共组件，并用测试验证每条路径。

错误 4：先取全量 top-k，再删除无权结果

问题： 存在泄露风险，且会降低有效召回数量。

改进： 使用检索前过滤；结果返回前再做防御性复核。

错误 5：文档权限更新了，但缓存没有失效

问题： 用户撤权后仍可能从旧检索结果或旧答案缓存中看到内容。

改进： 把 ACL 版本和权限变更事件纳入缓存键与失效机制。

错误 6：只保护正文，不保护元数据

问题： 文件名、标题、URL、作者、更新时间和“是否存在某文档”本身也可能是敏感信息。

改进： 为正文、元数据、引用和搜索结果分别定义可见字段。

10. 一个可落地的服务边界

推荐把 RAG 服务拆成以下职责：

认证服务：确认用户身份和租户
授权服务：判断用户可访问的资源范围
文档服务：保存原文并在访问时再次鉴权
索引服务：保存带权限元数据的向量和关键词索引
检索服务：只接受服务端生成的过滤条件
生成服务：只接收已授权、已压缩的上下文
审计服务：记录授权结果、引用和异常事件

应用层可以采用类似的流程：

def answer(question, request):
    identity = authenticate_request(request)
    if identity is None:
        raise PermissionError("authentication required")

    authz = build_authorization_context(identity)
    if not authz.tenant_active:
        raise PermissionError("tenant unavailable")

    filters = authz.to_retrieval_filters()
    chunks = retrieve(question, filters=filters)
    chunks = verify_each_chunk(chunks, authz)
    context = compress_and_deduplicate(chunks)

    result = generate_answer(question, context)
    result.citations = filter_visible_citations(result.citations, authz)
    write_audit_log(identity, chunks, result.citations)
    return result

这段代码是架构示意，不是可以直接运行的完整实现。实际系统还应处理超时、重试、权限服务不可用、缓存命中、流式输出和敏感信息脱敏等情况。

11. 安全测试与评测

权限测试不能只验证“有权限时能搜到”，还要验证所有越权路径都会失败。

11.1 必测场景

  • 租户 A 的用户查询租户 B 的已知文档标题；
  • 用户无权访问文档正文，但知道 document_id；
  • 用户刚刚被撤权后再次查询和点击旧引用；
  • 文档从公开改为私有后查询旧缓存；
  • 用户通过 BM25、向量、混合检索和历史问答分别查询；
  • 文档标题、文件名或摘要是否在无权限时泄露；
  • 权限服务超时或返回异常时系统是否默认拒绝；
  • 并发发生 ACL 更新和检索时，旧版本是否可能进入答案；
  • 管理员、普通用户和服务账号之间是否存在权限混淆。

11.2 需要观察的指标

指标 说明
越权命中数 应为 0
权限过滤失败率 过滤组件异常或缺失的请求比例
撤权生效延迟 从权限变更到所有读取路径拒绝的时间
缓存越权命中数 不同权限范围复用缓存的次数
引用复核拒绝数 生成结果中被移除的无权引用数
授权延迟 权限判断对整体响应时间的影响
审计覆盖率 检索、引用和拒绝事件是否都有记录

安全评测还应覆盖“无权结果是否影响排序或答案”的间接泄露问题，而不只是检查最终答案中有没有原文。

12. 设计检查清单

上线前可以逐项确认：

  • [ ] 每条索引记录都有可信的 tenant_id；
  • [ ] 租户 ID 来自服务端身份上下文，而不是直接信任客户端参数；
  • [ ] 向量、关键词、混合和缓存召回都使用权限过滤；
  • [ ] 检索前过滤是主防线，检索后复核是第二道防线；
  • [ ] 默认拒绝，授权服务异常不会自动放行；
  • [ ] 文档、Chunk、元数据和引用分别定义可见范围；
  • [ ] ACL 版本、文档版本和索引版本能够被追踪；
  • [ ] 撤权、删除和权限变更有可靠的事件同步与缓存失效机制；
  • [ ] 引用链接在生成和访问时都进行鉴权；
  • [ ] 日志和监控不会形成新的跨租户泄露渠道；
  • [ ] 已测试不同检索通道、错误路径、并发更新和缓存命中；
  • [ ] 能根据审计记录追溯一次回答使用了哪些授权文档。

13. 小结

文档权限与多租户隔离是 RAG 的基础安全边界，而不是生成阶段的附加提示。一个可靠的设计应遵循以下原则：

  1. 身份先于检索：先确定用户和租户，再构造查询；
  2. 授权先于召回：把权限条件放在检索前，而不是只在结果返回后删除；
  3. 所有通道一致：向量、BM25、混合检索、缓存和引用都不能绕过授权；
  4. 默认拒绝：权限不明确、同步失败或版本过期时，宁可少返回也不要扩大可见范围；
  5. 权限贯穿全链路：索引、上下文、生成、引用、缓存和日志都要纳入隔离；
  6. 可验证、可追溯：通过越权测试、版本控制和审计日志证明系统确实执行了授权。

RAG 的质量目标是“找到并生成有用答案”，安全目标则是“只使用当前用户有权使用的证据”。两者必须同时满足。
