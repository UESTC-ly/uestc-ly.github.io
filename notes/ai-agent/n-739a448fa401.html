1. 学习目标

完成本章后，应能够：

  1. 解释 Planning 为什么是 Agent 能够处理复杂任务的关键能力；
  2. 区分“计划”“状态”“工具调用结果”和“最终答案”；
  3. 根据任务目标拆分子任务，并判断哪些步骤必须串行、哪些步骤可以并行；
  4. 设计一次性规划、迭代规划和分层规划；
  5. 说明工作记忆、短期状态、情节记忆、语义记忆、程序记忆和用户偏好的区别；
  6. 设计记忆的写入、检索、更新、过期和删除策略；
  7. 处理计划失效、信息缺失、工具失败、记忆冲突和上下文过长等问题；
  8. 为 Planning 与 Memory 建立权限边界、人工确认点和可观测性；
  9. 设计一个既能利用历史信息、又不会盲目信任历史信息的 Agent。

2. 先给结论：计划不是事实，记忆也不是事实

Planning 与 Memory 经常被一起讨论，是因为复杂 Agent 通常需要同时回答两个问题：

  • Planning：接下来应该做什么？
  • Memory：为了做出这个决定，需要知道什么？

但是，这两个模块都不能直接替代应用程序的事实校验：

  • 计划只是对后续步骤的候选安排，不是已经发生的事情；
  • 记忆只是过去保存下来的信息或经验，不一定仍然正确；
  • 工具返回的结果也需要验证，不能因为工具名看起来可信就跳过校验；
  • 是否完成、是否有权限、是否产生副作用，最终应由应用程序和外部系统确认。

可以用下面的关系理解整个执行过程：

用户目标
   ↓
规划器：提出计划
   ↓
应用程序：校验计划、权限和前置条件
   ↓
工具或 Workflow：执行一个受控步骤
   ↓
外部系统：返回观察结果
   ↓
状态管理器：更新当前状态
   ↓
规划器：继续、修订、询问用户、转人工或停止

最重要的工程原则：

模型可以提出“下一步做什么”的建议，但应用程序必须决定“是否允许做、如何做以及做完是否真的成功”。

3. Planning 解决什么问题

3.1 单轮问答为什么不够

简单问题通常可以直接回答：

用户：Python 中列表和元组有什么区别？
模型：解释可变性、语法和适用场景。

复杂任务则往往包含多个相互依赖的步骤：

用户：帮我检查这笔订单是否符合退货条件，如果符合就提交申请，并通知我结果。

这个请求至少涉及：

  1. 识别订单号或询问缺失的订单号；
  2. 查询订单基本信息；
  3. 验证当前用户是否拥有该订单；
  4. 查询退货政策；
  5. 判断时间、商品状态和售后类型是否满足条件；
  6. 计算实际可退金额；
  7. 如果需要，向用户确认申请内容；
  8. 创建售后申请；
  9. 发送通知；
  10. 返回申请编号和当前状态。

如果模型只生成一段自然语言，很容易出现以下问题：

  • 忘记某个必要步骤；
  • 在查询之前就假设订单符合条件；
  • 把“准备提交申请”说成“申请已经提交”；
  • 没有区分可以并行的查询和必须串行的写操作；
  • 工具失败后仍然继续执行；
  • 一次任务循环过多，产生重复操作或成本失控。

Planning 的作用不是让模型“想得更长”，而是让系统显式管理：

  • 目标是什么；
  • 需要完成哪些子任务；
  • 子任务之间有什么依赖；
  • 每一步需要哪些输入；
  • 每一步完成的证据是什么；
  • 失败后如何恢复；
  • 何时应停止、询问用户或转人工。

3.2 Planning 的输入与输出

一个规划过程通常接收以下输入：

输入 说明 示例
用户目标 用户希望最终得到什么结果 完成订单退货申请
当前状态 已经知道什么、完成了什么 已确认订单号，尚未查询订单
可用工具 当前应用允许调用的能力 查询订单、查询政策、创建申请
约束条件 权限、预算、时间、合规要求 创建申请前必须获得用户确认
历史信息 与本次任务有关的可信记忆 用户偏好短信通知
停止条件 什么情况下算完成或必须停止 返回申请编号或说明无法申请

规划输出不一定是自然语言。更适合执行的形式是结构化计划：

{
  "goal": "判断订单是否符合退货条件，并在获得确认后提交申请",
  "steps": [
    {
      "id": "query_order",
      "action": "查询订单",
      "depends_on": [],
      "side_effect": "read",
      "completion_evidence": "获得订单归属、购买时间和商品状态"
    },
    {
      "id": "query_policy",
      "action": "查询退货政策",
      "depends_on": [],
      "side_effect": "read",
      "completion_evidence": "获得适用政策版本和判断条件"
    },
    {
      "id": "evaluate",
      "action": "校验退货资格并计算金额",
      "depends_on": ["query_order", "query_policy"],
      "side_effect": "read",
      "completion_evidence": "得到明确的 eligible、reason 和 refundable_amount"
    },
    {
      "id": "confirm",
      "action": "向用户展示申请摘要并获取确认",
      "depends_on": ["evaluate"],
      "side_effect": "none",
      "completion_evidence": "获得明确确认或拒绝"
    },
    {
      "id": "create_request",
      "action": "创建售后申请",
      "depends_on": ["confirm"],
      "side_effect": "write",
      "completion_evidence": "外部系统返回申请编号"
    }
  ]
}

注意：这个 JSON 只是候选计划。应用程序仍然需要检查：

  • 工具是否存在；
  • 参数是否完整；
  • 当前用户是否有权限；
  • 当前状态是否满足依赖；
  • 写操作是否需要人工或用户确认；
  • 是否已经执行过同一个不可重复操作。

4. Planning 的基本概念

4.1 目标、子目标和完成标准

一个可执行的目标至少应包含三部分：

目标 = 想达到的结果 + 必要约束 + 可验证的完成标准

例如：

模糊目标：帮我处理退货。

可执行目标：
- 结果：提交指定订单的退货申请；
- 约束：只能操作当前用户拥有的订单；
- 完成标准：外部售后系统返回申请编号，且通知发送成功或明确记录通知失败。

如果没有完成标准，Agent 很难判断什么时候应该停止。常见的完成标准包括：

  • 获得某个外部系统的唯一编号；
  • 生成一份通过格式校验的文件；
  • 所有必需字段都已收集；
  • 只读查询已返回足够证据；
  • 用户明确确认下一步；
  • 已明确说明无法完成的原因和可行替代方案。

4.2 计划、状态和观察结果

这三个概念要严格区分：

概念 含义 示例
计划 Plan 对未来步骤的安排 先查订单，再查政策，然后评估资格
状态 State 当前已经确认的事实和执行进度 订单归属已确认，政策查询失败
观察 Observation 某次工具或外部系统返回的结果 售后政策接口返回超时
记忆 Memory 跨任务保存、以后可能复用的信息 用户偏好邮件通知
答案 Answer 面向用户的最终表达 当前无法查询政策，请稍后重试

一个可靠的系统不会把计划直接写入状态，也不会把模型猜测直接写入记忆：

计划中的“将创建申请” ≠ 申请已经创建
模型生成的“用户通常选择短信” ≠ 用户本次选择短信
工具调用成功返回 ≠ 业务状态一定符合预期

4.3 前置条件、后置条件和不变量

每个步骤都可以描述为：

步骤 = 前置条件 + 输入 + 动作 + 后置条件 + 失败处理

例如“创建售后申请”：

  • 前置条件：订单归属已验证；退货资格已判断为符合；用户已确认；必填字段完整；没有重复申请；
  • 输入：订单号、商品明细、售后原因、退款方式；
  • 动作：调用创建申请接口；
  • 后置条件：外部系统返回申请编号；
  • 失败处理：记录错误码，不能把失败说成成功，必要时允许安全重试。

不变量是执行过程中始终必须成立的条件，例如：

  • 不能操作不属于当前用户的订单；
  • 未经确认不能执行高风险写操作；
  • 读取到的敏感信息不能原样放进日志；
  • 工具返回错误时，不能伪造成功结果；
  • 同一个不可重复操作不能因为重试而重复创建。

5. 常见的 Planning 方式

5.1 一次性规划（Single-shot Planning）

一次性规划是在执行前先生成完整计划，然后按计划执行。

用户目标
  ↓
生成完整计划
  ↓
校验计划
  ↓
按顺序或依赖关系执行
  ↓
完成或失败

适合：

  • 步骤相对稳定；
  • 外部环境变化不大；
  • 任务可以预先明确完成标准；
  • 希望先向用户展示计划并获得确认。

优点：

  • 容易审查和记录；
  • 用户可以提前发现计划不符合预期；
  • 预算和最大步骤数容易估算。

缺点：

  • 中途出现新信息后，原计划可能失效；
  • 计划过长时，后面的步骤可能建立在错误假设上；
  • 模型可能生成看起来完整、但无法执行的步骤。

5.2 迭代规划（Re-planning）

迭代规划不要求一开始决定全部步骤，而是每执行一部分就根据新状态重新判断。

观察当前状态
  ↓
选择下一步
  ↓
执行并获得结果
  ↓
更新状态
  ↓
判断：继续、改计划、询问、转人工或停止

适合：

  • 工具返回结果具有不确定性；
  • 外部数据可能变化；
  • 任务路径取决于前一步结果；
  • 需要在执行过程中处理异常。

迭代规划与 ReAct 的关系可以这样理解：

  • ReAct 更强调“思考/判断—行动—观察”的循环；
  • Planning 更强调目标分解、依赖、完成标准和重新规划；
  • 实际 Agent 通常把两者结合起来。

每次重新规划时，应用程序应该保留：

  • 原始用户目标；
  • 已确认的事实；
  • 已成功完成的步骤；
  • 失败的步骤和错误信息；
  • 尚未满足的前置条件；
  • 剩余预算和最大循环次数。

5.3 分层规划（Hierarchical Planning）

复杂任务可以拆成多个层级：

总目标：完成一次售后
├─ 获取事实
│  ├─ 获取订单信息
│  └─ 获取政策信息
├─ 做出判断
│  ├─ 判断是否符合条件
│  └─ 计算可退款金额
├─ 执行变更
│  └─ 创建售后申请
└─ 完成收尾
   ├─ 发送通知
   └─ 返回申请状态

上层负责确定阶段和边界，下层负责完成具体步骤。这样可以避免把几十个细节一次性塞给模型。

分层规划的一个重要原则是：

上层计划描述“要完成哪些阶段”，下层 Workflow 负责保证每个阶段的具体规则。

例如，上层模型可以判断“需要验证售后资格”，但以下内容更适合由确定性代码实现：

  • 日期差计算；
  • 金额计算；
  • 订单归属判断；
  • 枚举值校验；
  • 是否已有未完成的售后申请。

5.4 计划与确定性 Workflow 的组合

不是所有步骤都需要由模型决定。常见的组合方式是：

模型：理解目标、提取信息、选择候选路径
代码/Workflow：校验条件、执行规则、管理副作用
模型：解释结果、询问缺失信息、生成用户可读回复

例如：

模型识别“用户想退货”
  ↓
确定性 Workflow 检查订单归属和退货期限
  ↓
模型根据结构化结果生成解释
  ↓
应用程序要求确认
  ↓
确定性 Workflow 创建申请

这比让模型直接决定所有业务规则更容易测试、审计和控制风险。

6. 如何把一个目标拆成可执行计划

6.1 第一步：明确最终结果

先不要急着列工具。先回答：

  1. 用户真正想得到什么？
  2. 是要信息、建议，还是要改变外部系统状态？
  3. 哪些结果必须由外部系统确认？
  4. 用户是否表达了时间、范围、预算或格式限制？
  5. 哪些信息缺失会阻止任务继续？

例如“帮我安排会议”可能有完全不同的目标：

  • 只推荐几个时间段；
  • 查询所有人的日历；
  • 创建会议事件；
  • 发送邀请；
  • 只生成邀请草稿但不发送。

如果没有澄清目标，Agent 可能执行超出用户授权范围的操作。

6.2 第二步：列出必要事实

把“必须知道的事实”和“可以猜测的偏好”分开：

类型 例子 能否猜测
身份事实 当前登录用户是谁 不能猜测，来自认证上下文
资源归属 订单是否属于该用户 不能猜测，必须查询
业务事实 订单何时购买、是否已发货 必须查询
用户偏好 更喜欢邮件还是短信 可以作为候选默认值，但需允许用户修改
表达偏好 希望回答简短还是详细 可以参考，但不应覆盖本次明确要求

6.3 第三步：列出动作并标记副作用

每个动作都应标记风险和副作用：

动作类型 示例 通常的控制方式
只读 查询订单、读取文档 权限校验、参数校验
低风险变更 保存草稿、更新临时状态 用户可撤销、记录版本
高风险变更 转账、删除数据、提交申请 明确确认、幂等键、审计日志
对外沟通 发邮件、发短信、发布内容 展示发送对象和正文，获得确认
不可逆操作 删除、取消、正式提交 通常需要二次确认或人工审批

模型可以提出调用“发送通知”，但不能仅凭自然语言判断“用户一定同意现在就发送”。

6.4 第四步：建立依赖图

用依赖关系表示哪些步骤必须先完成：

提取订单号
    ↓
查询订单 ─────┐
              ├─> 判断资格 ─> 用户确认 ─> 创建申请
查询政策 ─────┘

这里：

  • 查询订单和查询政策在满足权限条件后可以并行；
  • 判断资格必须等待两者完成；
  • 创建申请必须等待资格判断和用户确认；
  • 如果查询订单失败，后续步骤不能假装继续。

6.5 第五步：为每一步定义完成证据

不要使用“看起来做完了”作为完成标准，而要定义可检查的证据：

步骤 不可靠的完成描述 可靠的完成证据
查询订单 已经看过订单了 返回订单 ID、归属、状态和时间
判断资格 应该可以退 返回 eligible=true/false 和规则依据
创建申请 已帮你提交 返回外部系统申请编号
发送通知 已经提醒你了 通知服务返回发送记录或状态

6.6 第六步：定义失败分支和停止条件

每个外部动作都应提前考虑：

  • 参数错误怎么办？
  • 权限不足怎么办？
  • 超时怎么办？
  • 返回空结果怎么办？
  • 结果与记忆冲突怎么办？
  • 重试会不会产生重复副作用？
  • 是否需要用户补充信息？
  • 是否应该转人工？

常见停止条件：

成功停止：已获得完成标准所要求的证据。
询问停止：缺少只有用户才能提供的信息。
安全停止：当前操作风险过高或未获得授权。
失败停止：重试预算耗尽或外部系统不可用。
人工停止：规则冲突、金额异常、用户提出申诉等情况。

7.1 步骤状态机

步骤状态不要只用布尔值。至少可以区分：

pending       尚未执行
ready         前置条件已经满足
running       正在执行
succeeded     已获得成功证据
failed        本次执行失败
blocked       因前置条件或权限问题无法执行
waiting_user  等待用户输入或确认
needs_review  需要人工审核
cancelled     已取消

状态转换应由应用程序控制：

pending → ready → running → succeeded
                         └→ failed
                         └→ waiting_user
                         └→ needs_review

模型可以建议“把步骤标记为完成”，但应用程序只有在验证了工具结果后才能真正写入 succeeded。

7.2 计划版本

迭代规划时不要覆盖原计划而不留痕迹。建议保留版本：

plan v1：先查询库存，再下单
plan v2：库存接口显示缺货，改为登记到货提醒
plan v3：用户拒绝登记提醒，任务取消

版本记录有助于回答：

  • 为什么路线发生变化？
  • 是工具结果导致变化，还是模型自行改变了目标？
  • 用户是否在中途修改了要求？
  • 是否存在重复调用？

8. Planning 的执行循环

8.1 通用执行流程

1. 解析用户目标
2. 读取认证上下文和当前任务状态
3. 检查是否需要澄清
4. 生成或恢复计划
5. 对计划做结构和权限校验
6. 找出所有前置条件已满足的步骤
7. 选择一个或一组可执行步骤
8. 对工具参数进行 Schema 校验
9. 如果有副作用，检查确认和幂等条件
10. 执行工具或 Workflow
11. 验证结果并更新状态
12. 判断是否完成、失败、需要重规划或需要人工介入
13. 生成用户可见的进度或最终回复

8.2 伪代码

state = load_task_state(task_id)

while not state.is_terminal():
    if state.rounds >= MAX_ROUNDS:
        state.stop_reason = "budget_exhausted"
        break

    missing = find_required_information(state)
    if missing:
        state.status = "waiting_user"
        ask_user_for(missing)
        break

    plan = create_or_revise_plan(
        goal=state.user_goal,
        facts=state.confirmed_facts,
        completed_steps=state.completed_steps,
        failures=state.failures,
    )

    validate_plan_structure(plan)
    validate_plan_permissions(plan, state.auth_context)

    ready_steps = get_ready_steps(plan, state)
    if not ready_steps:
        state.status = "needs_review"
        record_block_reason(state)
        break

    step = select_step(ready_steps)
    args = build_tool_arguments(step, state)
    validate_tool_arguments(step.tool, args)

    if step.has_side_effect and not confirmation_is_valid(step, state):
        state.status = "waiting_user"
        ask_for_confirmation(step, args)
        break

    result = execute_with_timeout_and_idempotency(step.tool, args)
    observation = validate_tool_result(step.tool, result)
    state = apply_observation(state, step, observation)

    if should_replan(state):
        continue

save_task_state(state)
return render_user_response(state)

这段伪代码体现了几个边界：

  • 模型负责提出计划或下一步建议；
  • 计划必须通过应用程序校验；
  • 工具参数必须通过 Schema 校验；
  • 副作用操作必须检查确认和幂等；
  • 工具结果必须转换为结构化观察结果；
  • 任务状态必须持久化，不能只存在于模型上下文中。

8.3 什么时候应该重新规划

满足以下情况之一时，通常需要重新规划：

  1. 工具返回了计划中没有考虑的新分支；
  2. 关键前置条件不满足；
  3. 外部状态发生变化；
  4. 用户修改了目标或约束；
  5. 工具失败且重试策略不能解决；
  6. 继续执行会产生未确认的副作用；
  7. 记忆与当前事实冲突；
  8. 已经接近最大步骤数或时间预算。

重新规划不等于重新开始。应保留已验证的事实和成功步骤，只重新安排受影响的部分。

8.4 什么时候不应该继续循环

Agent 不是循环次数越多越好。以下情况应及时停止：

  • 已满足完成标准；
  • 缺少用户才能提供的信息；
  • 没有可用工具可以推进；
  • 工具权限不足；
  • 失败重试已经超过预算；
  • 继续调用可能重复产生副作用；
  • 模型开始重复提出相同动作；
  • 任务超出应用程序的授权范围。

9. Memory 解决什么问题

9.1 为什么需要记忆

单次请求的上下文只覆盖当前对话和当前检索到的资料。跨任务时，应用可能需要保留一些稳定信息，例如：

  • 用户明确要求以后使用某种输出格式；
  • 某个项目的目录结构和命名约定；
  • 一次任务产生的申请编号和后续状态；
  • 已经确认的领域术语或业务规则；
  • 某次失败的原因以及已验证的替代路径。

如果所有历史内容都直接塞回 Prompt，会带来：

  • 上下文长度增加；
  • 无关内容干扰当前任务；
  • 旧信息覆盖新事实；
  • 敏感信息被不必要地暴露；
  • 模型难以判断哪些内容是事实、偏好还是旧计划。

因此，Memory 不是“把所有聊天记录保存下来”，而是对跨任务信息进行有范围、有来源、有生命周期的管理。

9.2 记忆的基本属性

一条可管理的记忆最好至少包含：

{
  "memory_id": "mem_001",
  "scope": "project",
  "content": "项目 Markdown 公式使用 $...$ 和 $$...$$ 定界符",
  "source": "user_explicit",
  "confidence": 1.0,
  "created_at": "2025-01-01T00:00:00Z",
  "updated_at": "2025-01-01T00:00:00Z",
  "expires_at": null,
  "sensitivity": "normal",
  "consent": "explicit",
  "status": "active"
}

这里的字段不是固定标准，而是帮助系统回答：

  • 这条信息属于谁、属于哪个项目或会话？
  • 它从哪里来？
  • 可信度如何？
  • 什么时候创建和更新？
  • 什么时候应该过期？
  • 是否包含敏感信息？
  • 用户是否明确同意保存？
  • 当前是否仍然有效？

10. Memory 的分类

不同类型的记忆应该使用不同的生命周期和使用方式。

10.1 工作记忆（Working Memory）

工作记忆是当前任务临时使用的信息，例如：

  • 当前用户目标；
  • 本轮已经提取出的订单号；
  • 当前计划及步骤状态；
  • 最近一次工具返回结果；
  • 当前等待用户确认的内容。

特点：

  • 生命周期通常只覆盖一次任务或一次会话；
  • 应及时清理；
  • 不应自动升级为长期记忆；
  • 可以包含执行所需的临时数据，但应遵守最小化原则。

10.2 对话记忆（Conversational Memory）

对话记忆用于维持当前会话的连贯性，例如：

用户：把报告改成表格。
助手：可以。你希望保留原来的三列吗？
用户：保留。

“保留原来的三列”需要结合当前会话理解，但不一定需要跨会话永久保存。

对话记忆应注意：

  • 最近消息不一定比明确事实更可信；
  • 长对话需要摘要，而不是无限追加原文；
  • 摘要必须区分用户明确说过的事实和模型推断；
  • 用户更改偏好后，当前明确要求应优先于旧偏好。

10.3 情节记忆（Episodic Memory）

情节记忆描述“以前发生过什么”：

2025-01-10：用户在订单 A100 上提交过退货申请，申请编号为 R200，当前状态为待审核。

它适合回答：

  • 上次任务做到了哪一步？
  • 某个问题以前是否处理过？
  • 某项操作产生了什么结果？

情节记忆应保留时间、来源和外部系统标识。状态型信息尤其需要允许更新，不能把旧事件当成当前状态。

10.4 语义记忆（Semantic Memory）

语义记忆保存相对稳定的知识或事实，例如：

  • 项目术语定义；
  • 用户明确维护的项目约定；
  • 经审核的业务规则摘要；
  • 某个系统的字段含义。

语义记忆也会过时，所以最好保存：

  • 来源；
  • 版本；
  • 生效时间；
  • 适用范围；
  • 更新或失效条件。

10.5 程序记忆（Procedural Memory）

程序记忆描述“如何做某件事”，例如：

生成发布说明时：先读取版本变更，再按固定模板归类，最后运行格式校验。

程序记忆不能替代实际权限和工具契约。它只是候选流程，执行时仍应以当前代码、配置和工具 Schema 为准。

10.6 用户偏好记忆（Preference Memory）

用户偏好包括：

  • 输出语言；
  • 文档格式；
  • 通知渠道；
  • 解释详细程度；
  • 常用的时间或单位表示方式。

偏好必须与本次请求区分：

长期偏好：用户通常希望答案简洁。
本次要求：请详细解释 Planning 与 Memory。

本次明确要求应优先于长期偏好。

10.7 外部事实状态（External State）不是普通记忆

订单状态、账户余额、库存数量、审批状态等信息，虽然可以被缓存，但本质上属于外部系统状态：

  • 需要查询来源系统；
  • 必须考虑时效性；
  • 应保存查询时间和版本；
  • 不能只依据过去的记忆执行高风险操作。

可以缓存“上次查询结果”，但要明确标记为缓存：

缓存事实：2025-01-10 10:00 查询时库存为 3。
当前事实：需要再次查询库存接口确认。

11. 什么应该写入 Memory

11.1 推荐写入的内容

适合写入长期记忆的内容通常具有以下特征：

  • 跨会话仍然可能有用；
  • 来源明确；
  • 内容范围清晰；
  • 不会因为一次偶然对话就轻易改变；
  • 用户明确要求保存，或应用有清晰、可解释的保存规则；
  • 保存后能显著减少重复沟通或提高一致性。

例如：

用户明确要求：以后项目笔记中的数学公式使用美元符号定界符。

11.2 不应自动写入的内容

以下内容不应因为模型“觉得有用”就自动保存：

  • 密码、API Key、访问令牌和私钥；
  • 完整的敏感身份信息；
  • 没有来源的模型猜测；
  • 一次性的临时情绪或随口表达；
  • 未经确认的用户画像；
  • 大段原始对话；
  • 只适用于当前任务的计划草稿；
  • 可能造成歧视或不公平决策的敏感属性；
  • 没有明确用途的冗余数据。

11.3 记忆写入决策

可以用一个简单的判断流程：

这条信息是否跨会话仍有价值？
  ├─ 否：只放入当前任务状态或丢弃
  └─ 是
      ↓
是否来自用户明确表达、可信工具或经过审核的资料？
  ├─ 否：不要写入长期记忆，或标记为待确认
  └─ 是
      ↓
是否包含敏感信息？
  ├─ 是：最小化、脱敏，必要时不保存
  └─ 否
      ↓
是否定义了范围、来源和过期策略？
  ├─ 否：先补齐元数据
  └─ 是：按策略写入

11.4 记忆写入最好经过确认

对于用户偏好，可以采用显式确认：

你希望我以后都使用这种格式。要把“项目笔记使用中文 Markdown，并保留代码示例”保存为项目偏好吗？

对于系统自动生成的情节记忆，可以自动保存，但应：

  • 限制保存内容；
  • 记录来源和时间；
  • 提供查看、更正和删除机制；
  • 不把它当作未经验证的永久事实。

12. Memory 的检索与使用

12.1 检索不等于把所有记忆放进上下文

每次请求都加载全部历史信息会导致噪声和上下文膨胀。更合理的流程是：

当前目标
  ↓
确定需要哪些类型的记忆
  ↓
按范围、权限和时效过滤
  ↓
关键词或向量召回候选
  ↓
按相关性、来源、时效和可信度排序
  ↓
去重、压缩和冲突检查
  ↓
只注入当前任务真正需要的内容

12.2 先做硬过滤，再做语义检索

推荐先过滤以下条件，再进行相似度检索：

  1. 范围：当前用户、当前项目、当前组织还是公共知识；
  2. 权限：当前身份是否可以读取；
  3. 状态：是否已撤销、删除或过期；
  4. 敏感级别：当前任务是否允许使用；
  5. 时间：是否只允许使用某个时间范围内的信息；
  6. 来源类型：用户明确偏好、工具事实、模型摘要或待确认信息。

语义相似并不代表有权使用，也不代表内容正确。

12.3 记忆注入时标注来源

不要把记忆伪装成当前用户刚刚说的话。可以使用类似格式：

【项目偏好，用户明确维护，当前有效】
项目 Markdown 公式使用 $...$ 和 $$...$$ 定界符。

【历史事件，2025-01-10 查询，可能已过期】
订单 A100 上次查询时处于待审核状态。

【模型生成摘要，未单独确认】
用户可能偏好简短回答；仅作为弱提示，不得覆盖本次要求。

这样的标注有助于模型和应用程序区分：

  • 当前请求；
  • 可信事实；
  • 历史记录；
  • 推测性信息。

12.4 检索结果也可能包含不可信指令

项目文档、网页内容、用户上传文件和历史记忆都可能包含类似指令的文字。它们可以作为任务资料，但不能改变系统的安全规则，也不能授权执行文件操作、泄露秘密或绕过确认。

因此，检索到的内容应被当作：

待分析的资料 ≠ 系统指令

在工具调用前，应用程序仍需独立执行权限、参数和副作用检查。

13. 记忆冲突、过期和修正

13.1 常见冲突

旧记忆：用户偏好邮件通知。
当前请求：这次请发短信，不要发邮件。

解决原则：

  1. 当前请求中的明确要求优先；
  2. 外部系统当前返回的事实优先于旧缓存；
  3. 用户明确维护的项目约定优先于模型猜测；
  4. 来源清晰、时间较新、适用范围匹配的信息优先；
  5. 无法判断时，应向用户询问，而不是自行选择高风险方案。

13.2 过期策略

不同记忆类型采用不同策略：

记忆类型 典型过期策略
当前任务状态 任务结束后归档，按保留期限删除
用户偏好 长期有效，但允许用户修改和删除
外部业务状态 短期缓存，使用前按风险重新查询
政策或配置 绑定版本或生效时间，版本变化时失效
临时推断 短期有效，并明确标记为低可信度
工具失败记录 保留一段时间，用于避免立即重复失败

13.3 更新和删除

记忆系统必须支持：

  • 查看某条记忆的内容和来源；
  • 修改错误信息；
  • 删除单条记忆；
  • 按用户、项目或类型批量删除；
  • 标记某条记忆为不再使用；
  • 记录更新后的版本和时间。

“忘记这条记忆”不应只是让模型下次不提它，而应真正从可检索存储和相关缓存中移除，或至少标记为不可再使用。

14. Planning 与 Memory 如何协同

14.1 一次完整流程

收到用户请求
  ↓
读取当前任务状态
  ↓
检索相关记忆
  ↓
区分当前事实、历史事实和偏好
  ↓
生成候选计划
  ↓
校验工具、权限、预算和副作用
  ↓
执行可执行步骤
  ↓
验证观察结果并更新任务状态
  ↓
必要时重新规划
  ↓
任务完成后选择性写入记忆

14.2 记忆应该怎样影响计划

记忆可以影响计划的表现形式，但不应绕过业务校验：

用户偏好：回答使用中文
→ 影响最终回复语言

历史记录：上次用户选择邮件通知
→ 可以作为本次通知方式的候选默认值
→ 但如果本次请求说“发短信”，必须使用短信

历史状态：订单上次为待审核
→ 可以提示需要查询当前状态
→ 不能直接据此创建或取消申请

14.3 计划本身是否应该保存为记忆

通常应区分：

  • 当前任务计划：放入任务状态，随任务生命周期管理；
  • 可复用流程模板：可以作为程序记忆或配置保存；
  • 一次性计划结果：除非以后确实有用，否则不应长期保存；
  • 执行事件：如果需要审计或恢复，可以保存为情节记录。

不要把每一次模型生成的计划都永久写入长期记忆，否则记忆库会快速充满过时方案和模型猜测。

15. 示例：售后申请 Agent 的 Planning 与 Memory

这个例子与本组综合练习中的“订单售后申请 Agent + 确定性 Workflow”一致。

15.1 用户请求

用户：帮我把上次买的耳机退掉，退款后用原支付方式，结果发邮件通知我。

15.2 信息提取

模型可以提取候选信息：

{
  "intent": "申请退货",
  "product_description": "上次买的耳机",
  "refund_method": "原支付方式",
  "notification_channel": "email"
}

但“上次买的耳机”可能对应多个订单，不能直接猜订单号。应用程序应查询当前用户的订单，或者询问用户选择哪一笔。

15.3 相关记忆

可能检索到：

【情节记忆】用户曾咨询过订单 A100，但没有提交申请。
【用户本次明确要求】退款使用原支付方式，通知渠道为邮件。
【项目规则】创建售后申请前必须完成订单归属、资格和金额校验。

本次明确要求优先于任何旧通知偏好。

15.4 候选计划

1. 查询当前用户最近的耳机订单。
2. 如果只有一笔，展示订单摘要；如果有多笔，请用户选择。
3. 查询该订单的当前状态和商品明细。
4. 查询适用的退货政策。
5. 由确定性逻辑判断是否符合条件，并计算实际退款金额。
6. 向用户展示订单、商品、原因、退款方式和金额。
7. 获得用户明确确认。
8. 使用幂等键创建售后申请。
9. 等待外部系统返回申请编号。
10. 按用户本次要求发送邮件，并记录通知结果。
11. 返回申请编号、状态和后续说明。

15.5 哪些步骤由模型做，哪些步骤由程序做

步骤 模型可以做的事 应用程序必须控制的事
理解请求 提取意图和候选字段 检查字段格式和歧义
查询订单 选择查询工具 当前用户身份、订单归属和查询范围
判断政策 解释规则 依据当前政策版本计算资格
计算金额 组织结果说明 真实金额、优惠、运费和币种计算
提交申请 提议调用 确认、权限、幂等、接口结果
发送通知 组织通知内容 收件人、授权、脱敏、发送结果
最终回复 生成自然语言 只能陈述已验证的状态

15.6 失败分支

订单查询超时
→ 安全重试一次
→ 仍失败：停止，不创建申请，向用户说明当前无法查询

找到多笔符合描述的订单
→ 不猜测
→ 展示最小必要信息，请用户选择

订单不属于当前用户
→ 不披露订单详细信息
→ 说明无法处理该订单

资格不符合
→ 不创建申请
→ 说明规则依据和可行的人工申诉路径

创建申请超时
→ 使用相同幂等键查询申请结果
→ 不直接重复创建

邮件发送失败
→ 申请状态仍应与通知状态分开
→ 返回申请编号，并说明通知失败

这个例子体现了一个重要原则：

一个子步骤失败，不一定意味着整个任务都失败；但系统必须准确区分“申请已创建”和“通知未发送”等部分完成状态。

16. 记忆系统的工程化接口

下面是概念接口，不要求直接照抄实现：

class MemoryStore:
    def add(self, item, *, scope, source, expires_at=None):
        """保存经过策略检查的记忆。"""
        pass

    def search(self, query, *, scope, user_id, filters, limit=5):
        """按权限、范围、时效和相关性检索候选记忆。"""
        pass

    def update(self, memory_id, changes, *, actor):
        """更新记忆并保留必要的版本信息。"""
        pass

    def delete(self, memory_id, *, actor):
        """删除或撤销一条记忆。"""
        pass

    def mark_expired(self, now):
        """根据生命周期策略处理过期记忆。"""
        pass

计划执行器也可以抽象为：

class Planner:
    def create_plan(self, goal, state, memories, available_tools):
        """生成候选计划，不直接执行副作用。"""
        pass

    def revise_plan(self, plan, state, observation):
        """根据新观察结果生成修订建议。"""
        pass


class PlanExecutor:
    def validate(self, plan, state, auth_context):
        """检查结构、依赖、权限、预算和副作用。"""
        pass

    def execute_next(self, plan, state):
        """只执行当前 ready 且已通过校验的步骤。"""
        pass

无论使用什么框架，都建议把以下职责分开：

Planner       生成或修订计划
State Store   保存当前任务状态
Memory Store  保存跨任务信息
Policy Layer  做权限、风险和确认判断
Tool Runner   执行工具并处理超时、重试、幂等
Evaluator     验证工具结果和完成标准
Renderer      生成用户可见回复

如果这些职责全部塞在一个 Agent 类中，后续通常很难测试：你无法判断错误来自模型、状态管理、权限判断还是工具执行。

17. 失败处理与恢复策略

17.1 工具失败分类

工具失败不能全部用“再试一次”处理：

失败类型 是否适合重试 处理建议
网络暂时超时 通常可以有限重试 使用退避策略和总预算
参数校验失败 不应原样重试 修正参数或询问用户
权限不足 不应反复重试 停止并说明权限问题
资源不存在 通常不应重试 检查输入或说明不存在
服务限流 可以稍后重试 等待、降低频率或排队
写操作超时 不能盲目重试 先查询幂等结果
返回格式异常 谨慎重试 记录原始响应，必要时转人工
业务规则拒绝 不应重试 告知原因和替代路径

17.2 重试、回滚和补偿

需要区分三种动作：

  • 重试：再次执行同一动作，适用于临时失败；
  • 回滚：将已经发生的变更恢复，前提是外部系统支持；
  • 补偿：无法回滚时，执行另一项动作降低影响。

例如：

创建订单成功，但发送通知失败
→ 不能回滚订单，只能记录通知失败
→ 可以提供重新发送通知的补偿操作

17.3 幂等性

对于创建、支付、发送、删除等副作用操作，必须考虑重复执行：

幂等键 = 用户/任务标识 + 业务动作 + 目标资源 + 版本

重试前应先查询：

  1. 上一次调用是否已经被外部系统接受；
  2. 是否存在同一幂等键对应的结果；
  3. 当前状态是否已经达到目标；
  4. 如果无法确认，是否应该暂停并转人工。

18. 安全、权限与人工介入

18.1 Planning 不能绕过权限

计划中出现某个工具，不代表当前用户有权调用它。权限检查至少应覆盖：

  • 用户身份；
  • 资源归属；
  • 组织或租户范围；
  • 工具本身的访问权限；
  • 操作类型的风险级别；
  • 当前会话是否具有有效确认；
  • 是否需要人工审批。

18.2 记忆也需要访问控制

不同范围的记忆不能混用：

会话记忆：只在当前会话可见
用户记忆：只对该用户可见
项目记忆：对项目授权成员可见
组织记忆：按组织权限共享
公共知识：不包含私密业务信息

检索时不能只按语义相似度返回结果，必须先做权限过滤。

18.3 高风险操作的确认点

建议把确认放在副作用发生之前，并明确展示：

  • 将要操作的资源；
  • 将要执行的动作；
  • 可能产生的影响；
  • 金额、收件人、公开范围等关键参数；
  • 是否可撤销；
  • 用户确认后系统会做什么。

确认不应是模糊的：

即将向 user@example.com 发送包含订单号和退款金额的邮件。确认发送吗？

而不是：

要继续吗？

18.4 人工介入条件

以下情况适合转人工或进入审核队列：

  • 金额超过阈值；
  • 规则冲突或资料不完整；
  • 用户提出申诉；
  • 外部状态无法确认；
  • 多次重试仍失败；
  • 涉及敏感数据或高影响决定；
  • Agent 无法证明完成标准已经满足。

19. 常见错误与改进方式

错误 产生原因 改进方式
计划列得很长但无法执行 只描述自然语言，没有工具和 Schema 为每一步定义输入、工具、前置条件和完成证据
把模型计划当作执行结果 没有独立状态管理 只有验证过的外部结果才能更新状态
遇到失败就无限重试 没有错误分类和预算 按错误类型设计重试、停止和人工分支
记忆库保存所有聊天 没有写入策略 只保存跨任务有价值且来源明确的信息
旧偏好覆盖当前要求 没有优先级规则 当前明确请求优先于历史偏好
旧订单状态被当成当前事实 混淆缓存与外部状态 使用前按风险重新查询并标记时间
语义相似就使用记忆 忽略范围和权限 先硬过滤，再做相关性排序
记忆摘要包含模型猜测 未标记来源 区分用户事实、工具事实和模型推断
计划失败后从头重跑 没有持久化状态 保存已完成步骤和已验证事实，只重算受影响部分
写操作重复执行 没有幂等键 为副作用操作设计幂等和结果查询
最终回复夸大成功 回复直接依赖模型语言 回复只能使用已验证状态和工具结果
把流程规则交给模型自由判断 确定性逻辑不够清晰 将金额、权限、资格等规则放入代码或 Workflow

20. 如何评估 Planning 与 Memory

20.1 Planning 评估

不要只看最终答案是否流畅，还要检查执行轨迹：

  1. 目标理解率：是否正确识别用户目标和约束；
  2. 步骤覆盖率：是否包含所有必需步骤；
  3. 依赖正确率：是否遵守前置条件；
  4. 工具选择准确率：是否选择了适合的工具；
  5. 参数正确率：参数是否完整、合法、最小化；
  6. 完成判断准确率：是否只在有证据时宣布完成；
  7. 失败恢复率：遇到错误后能否选择合理分支；
  8. 重复操作率：是否发生重复调用或重复副作用；
  9. 成本和延迟：模型轮数、工具调用数、总耗时是否在预算内；
  10. 安全违规率：是否在没有权限或确认时执行高风险操作。

20.2 Memory 评估

记忆质量至少包含四个维度：

  • 召回率：需要的信息是否能被找回；
  • 精确率：找回的信息是否真的相关；
  • 新鲜度：信息是否仍然有效；
  • 可追溯性：能否说明来源、时间和适用范围。

还应测试：

  • 错误记忆会不会被当作事实；
  • 用户删除后是否仍能被检索；
  • 不同用户或项目之间是否发生越权泄露；
  • 当前请求能否覆盖旧偏好；
  • 记忆过多时是否造成上下文污染；
  • 检索到的资料是否包含诱导性指令。

20.3 必须覆盖的测试场景

理想路径：所有工具成功，任务正常完成。
缺字段：用户没有提供必要标识，Agent 应该询问。
歧义：多个资源匹配，Agent 不应自行猜测。
权限失败：用户无权访问目标资源。
空结果：查询成功但没有匹配记录。
超时：读操作和写操作分别测试。
重复执行：同一任务重复提交，不能产生重复副作用。
状态变化：计划生成后，外部资源状态发生改变。
记忆冲突：历史偏好与本次明确要求不同。
记忆过期：只能使用当前有效的信息。
提示注入：检索资料试图改变工具权限或系统规则。
人工介入：达到金额、风险或不确定性阈值。

20.4 调用轨迹

排查 Agent 时，最有价值的资料通常不是最后一句回答，而是这一轮任务的调用轨迹：

请求 ID
├─ 用户身份与授权上下文（脱敏）
├─ 原始目标摘要
├─ 使用了哪些记忆（记录 ID、来源和版本，不记录不必要的敏感正文）
├─ 每轮模型调用：模型、耗时、token、结束原因
├─ 计划版本和步骤状态变更
├─ 每次工具请求：工具名、校验结果、参数摘要（脱敏）
├─ 每次工具执行：耗时、结果状态、错误码
├─ 用户确认和审批记录
└─ 最终回复或停止原因

日志本身也要遵守最小化、脱敏和访问控制原则。

21. 一个更稳妥的实现架构

可以把系统分成以下层：

┌──────────────────────────────────────┐
│ User Interface                       │
│ 采集请求、展示进度、获取确认          │
└──────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────┐
│ Task State                           │
│ 目标、事实、步骤状态、错误、预算       │
└──────────────────────────────────────┘
          ↓                    ↓
┌───────────────────┐  ┌───────────────────┐
│ Memory Layer      │  │ Planning Layer    │
│ 检索与生命周期     │  │ 分解与重新规划     │
└───────────────────┘  └───────────────────┘
          └──────────────┬──────────────┘
                         ↓
┌──────────────────────────────────────┐
│ Policy / Guardrail Layer             │
│ 权限、确认、风险、预算、Schema 校验   │
└──────────────────────────────────────┘
                         ↓
┌──────────────────────────────────────┐
│ Tool / Workflow Layer                │
│ 只读查询、确定性规则、副作用操作       │
└──────────────────────────────────────┘
                         ↓
┌──────────────────────────────────────┐
│ External Systems                     │
│ 数据库、API、消息服务、文件系统等      │
└──────────────────────────────────────┘

21.1 关键边界

  • Memory Layer 不直接调用高风险工具；
  • Planning Layer 不直接绕过 Policy Layer；
  • Tool Layer 不信任模型生成的任意参数；
  • UI Layer 不把“模型说成功”当作“系统已成功”；
  • External Systems 的结果需要被解析、校验和记录；
  • Task State 应能够在进程重启后恢复。

21.2 最小可行版本

学习或原型阶段不必一开始就实现复杂的向量数据库和多 Agent。可以先做：

  1. 一个结构化任务状态对象；
  2. 一个有限步骤的 Workflow；
  3. 一个只保存明确用户偏好的简单 Memory Store；
  4. 一个工具参数校验层；
  5. 一个最大循环次数和超时机制；
  6. 一个副作用确认点；
  7. 一组理想路径和失败路径测试。

在边界稳定后，再增加：

  • 向量检索；
  • 记忆摘要；
  • 计划版本；
  • 异步任务队列；
  • 人工审核；
  • 多 Agent 协作；
  • 更细粒度的指标和回放系统。

22. 练习：设计一个“会议安排 Agent”

22.1 需求

实现一个系统，帮助用户安排一次会议。系统可以：

  • 识别参会人、主题和期望时长；
  • 查询用户有权访问的日历；
  • 推荐可用时间；
  • 在用户确认后创建会议；
  • 发送邀请；
  • 记录会议编号和通知状态。

22.2 请先回答

  1. 哪些信息必须从用户获得？
  2. 哪些步骤可以并行？
  3. 哪些工具是只读工具？
  4. 哪些工具会产生副作用？
  5. 创建会议前需要展示哪些确认信息？
  6. 如果两个参会人的日历没有共同空闲时间，如何重新规划？
  7. 哪些内容可以写入长期记忆？
  8. 如果历史记忆显示用户常用 30 分钟，但本次说“安排 60 分钟”，采用哪个时长？
  9. 创建会议接口超时后，如何避免重复创建？
  10. 什么情况需要转人工？

22.3 参考计划

1. 提取主题、参会人、时长、时间范围和时区。
2. 对缺失或歧义字段向用户提问。
3. 校验当前用户是否有权读取相关日历。
4. 并行查询允许访问的日历和工作时间规则。
5. 计算共同可用时间段。
6. 如果没有结果，询问用户是否扩大时间范围或调整时长。
7. 展示候选时间、时区、参会人和会议主题。
8. 获取用户明确确认。
9. 使用幂等键创建会议。
10. 查询创建结果，确认会议编号和链接。
11. 发送邀请并记录发送状态。
12. 向用户返回已验证的结果。

22.4 适合保存的记忆

可以保存：用户明确要求默认使用某个时区；
可以保存：用户明确要求会议邀请使用某种固定模板；
不应直接保存：本次会议的完整私密内容，除非有明确用途和授权；
不应覆盖本次请求：历史默认时长不能覆盖本次明确的 60 分钟要求。

24. 本章小结

  1. Planning 负责把目标转化为有依赖、有约束、有完成证据的步骤；
  2. 一次性规划适合稳定任务，迭代规划适合不确定环境，分层规划适合复杂任务；
  3. 计划是候选方案，只有经过应用程序校验和工具执行，状态才会发生变化；
  4. 工作记忆服务于当前任务，长期记忆只应保存跨任务仍有价值且来源明确的信息；
  5. 外部订单、余额、库存和审批状态属于外部事实，不能盲信旧记忆；
  6. 记忆检索必须同时考虑相关性、权限、范围、时效和来源；
  7. 当前明确请求优先于历史偏好，当前外部事实优先于旧缓存；
  8. 任何副作用操作都需要权限、确认、参数校验、幂等和结果验证；
  9. Agent 的质量要通过计划、状态、工具轨迹和失败恢复来评估，而不只是看最终回答是否自然；
  10. 最稳妥的架构是让模型负责理解和建议，让确定性代码负责规则、权限、状态和副作用。
