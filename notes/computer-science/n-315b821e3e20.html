7. 分布式系统与微服务

  • [ ] ★★★ CAP 定理和 BASE 理论是什么？
  • 完整回答：
    • CAP 定理讨论的前提是一个会跨节点复制或协作的分布式系统，并且网络分区可能发生。这里的 C 通常指线性一致性或单副本一致视图：某次写入一旦对外成功，之后相关读取必须看到这次写入或更新结果；A 指每个到达非故障节点的请求都能在有限时间得到非错误响应；P 指网络分区发生时系统仍继续运行。因为分区时不同节点之间无法可靠通信，如果两侧都继续接受读写，就可能出现互相不知道的并发更新，破坏线性一致；如果为了确认最新状态而阻塞或拒绝部分请求，就牺牲可用性。因此 CAP 不是“永远只能三选二”，而是在 P 这个现实故障存在时，C 与 A 必须按业务选择。CP 系统常在多数派不可达、租约失效、主节点不确定时拒绝写入，适合余额、库存、配置中心等不能接受错误状态的场景；AP 系统倾向继续响应，之后用版本、合并、补偿或对账收敛，适合评论、点赞、缓存、动态计数等可容忍短暂不一致的场景。BASE 是 Basically Available、Soft state、Eventually consistent 的缩写，表示系统在压力或故障下保持基本可用，允许中间状态暂时漂移，并承诺在没有新写入且故障恢复后最终收敛。它不是随意丢数据，也不是没有约束的“最终会好”，必须明确不一致窗口、冲突解决规则、重试上限、幂等键、补偿任务、监控告警和人工对账边界。实际设计还要把读路径和写路径分开看：有些系统写入要求多数派确认，普通读取却可能读本地副本；有些系统只在特定表、特定操作或特定隔离级别下提供更强语义。常见误区是把某个产品直接贴成 CP 或 AP，实际还要看读写配置、确认级别、副本数、故障模式和业务使用方式。

  • 原理解析：

    • CAP 的系统模型是多副本或多节点协作，核心故障假设是网络分区：节点还活着，但彼此消息延迟、丢失或不可达。若没有分区，系统可以同时追求较强一致和可用；一旦分区发生，跨分区确认最新写入变成不可靠，取舍才被迫出现。
    • 因果链是“写成功返回”建立了对外承诺，后续读若必须看到它，就要确认读到的副本包含该写；分区下确认需要通信，通信失败就只能等待、拒绝或冒着读旧值风险继续服务。等待/拒绝偏 CP，继续响应并后续合并偏 AP。
    • C 在 CAP 里通常不是数据库 ACID 的一致性约束，而是接近线性一致的外部可见顺序；A 也不是永不出错，而是非故障节点对请求给出有限时间响应；P 不是可选功能，而是必须面对的故障环境。
    • BASE 是 AP 取向下的工程纪律：基本可用只保核心能力，软状态承认副本会临时漂移，最终一致依赖复制恢复、冲突解决和补偿收敛。它的前提是业务能接受不一致窗口，并且有幂等、重试、对账和告警兜底。
    • 记忆抓手：CAP 问的是“分区时还要不要同步确认”，BASE 问的是“放松一致后如何可恢复”。资金、库存更怕错，常牺牲可用；点赞、浏览量更怕不可用，常接受短暂旧值。面试和设计题里要先声明故障前提、读写范围和成功确认条件，再谈某系统偏哪一侧；同一产品在不同配置下可能写路径偏 CP、读路径偏 AP。真正落地还要把冲突合并、最大延迟、降级展示和人工修复写成可观测流程，否则只是口头上的最终一致。还要避免把分区外的普通延迟、宕机、业务约束混为 CAP 本身；库存不能超卖是业务不变量，需要数据库约束或状态机支持，而不是靠一句选择 CP 自动成立。判断标准最终落在可验证行为。

  • [ ] ★★★ 强一致性、弱一致性和最终一致性有什么区别？

  • 完整回答：
    • 一致性模型描述的是写入完成后，其他读写在什么条件下可以观察到该结果。强一致性在工程讨论中常指线性一致性：系统表现得像只有一个副本，操作按某个全局顺序生效，写入成功返回后，后续读取不能再看到旧值。它通常依赖单主串行化、同步复制、共识协议或数据库事务，代价是写延迟更高、跨地域成本更大，并且在网络分区、主从切换或多数派不可用时可能拒绝服务。弱一致性则只提供更松的承诺，读取可能看到旧版本，不同客户端也可能看到不同顺序；它并不是错误实现，而是在可用性、延迟和吞吐之间做出的放松。最终一致性是弱一致性中最常见的一类，前提是系统停止接收新的相关写入、消息和复制链路最终恢复、冲突能够被解决，那么多个副本会收敛到同一状态。实现上可能依赖异步复制、消息队列、事件日志、版本号、向量时钟、最后写入胜出、业务合并或补偿任务。失败模式包括消息丢失、重复投递、乱序、复制延迟、冲突合并错误和补偿失败，因此必须设计幂等消费、重试、死信、对账和可观测性。业务上还可以介于二者之间，例如读己之写保证用户写后自己能读到，单调读保证同一用户不会读到时间倒退的状态，因果一致性保证有因果关系的操作按顺序可见。实际落地时还要说明读写范围：是单 key、单分区、单表事务，还是跨分片、跨服务、跨地域；范围越大，强一致的协调成本通常越高。余额扣减、库存售卖、权限配置通常更偏强一致；浏览量、推荐特征、消息未读数可以接受最终一致。误区是把“最终一致”当成不用管一致性，或把“写主读从”直接称为强一致，实际读从库必须面对复制延迟和故障切换边界，客户端缓存也可能继续放大旧读。

  • 原理解析：

    • 一致性模型先限定对象范围：单 key、单分区、单数据库事务和跨服务流程的语义不同。强一致通常要求操作能被排成一个实时顺序，写返回后所有后续相关读都不能倒退；这个承诺需要主节点串行化、共识多数派或同步复制来维持。
    • 弱一致放松的是“何时、由谁能看到最新写入”的约束，因此读取旧副本、不同客户端观察到不同顺序都可能是模型允许的结果。它不是脏数据的借口，而是用更低延迟、更高可用和更少协调成本换取较弱承诺。
    • 最终一致的因果链是：本地写先成功，异步消息或复制日志传播到其他副本，冲突通过版本、时间戳、向量时钟或业务规则合并，系统在没有新写且链路恢复后收敛。这个“最终”有前提，不包含消息永久丢失、冲突无法判定或补偿任务长期失败。
    • 介于强弱之间还有读己之写、单调读、因果一致性等模型，它们按用户会话或因果关系增加局部保证。设计时要把用户体验和数据风险拆开：用户刚改头像希望自己马上看到，报表统计允许延迟，扣款余额不能乱序。
    • 记忆抓手：强一致像“全局单本账”，弱一致像“各副本先各自服务”，最终一致像“异步抄账后对齐”。范围越大、距离越远、故障越多，强保证越昂贵。回答时不要只背概念，要说明写成功返回点、读从哪里读、客户端是否带缓存、故障切换时是否可能回退。最终一致也要给出收敛机制、冲突策略和异常兜底；强一致也要承认多数派不可用、跨地域写延迟和吞吐下降这些边界。验证一致性时应看可观察行为，例如写后立即读、故障切主、读从延迟和并发更新冲突，而不是只看产品宣传。不同接口可以选择不同模型。

  • [ ] ★★★ 分布式事务有哪些常见方案？

  • 完整回答：
    • 分布式事务解决的是一次业务操作跨多个数据库、服务或消息系统时，如何让结果满足一致性目标。常见方案包括 2PC、TCC、Saga、本地消息表、Outbox/CDC 和 MQ 事务消息。2PC 有协调者和参与者，第一阶段参与者执行准备并持有资源，返回可提交或不可提交；第二阶段协调者统一发送提交或回滚。它更接近强一致，但参与者在准备后可能长期锁资源，协调者故障、网络分区或参与者超时会带来阻塞和恢复复杂度，适合参与方少、资源可锁定、延迟可接受的场景。TCC 把业务拆成 Try、Confirm、Cancel，Try 预留资源，Confirm 确认生效，Cancel 释放预留。它的前提是业务资源可预留，且 Confirm/Cancel 必须幂等、可重试，并处理空回滚、悬挂、重复确认和超时补偿，侵入性较强但可控性高。Saga 把长事务拆成一系列本地事务，每步成功后推进下一步，失败时执行已完成步骤的补偿；它适合跨服务长流程，但补偿只是业务反向操作，不等于数据库回滚，例如发出的优惠券、通知、外部扣款未必完全可逆。本地消息表和 Outbox 通过同一个本地数据库事务同时写业务状态和待发送事件，再由后台任务或 CDC 投递消息，消费端用幂等和重试达成最终一致。事务消息通常由 MQ 提供半消息、提交/回滚和回查机制，但仍要处理回查幂等、消息重复和下游失败。所有方案都需要事务状态表、超时扫描、重试退避、死信处理、补偿失败告警和人工修复入口，否则协调器或消费者崩溃后无法判断下一步动作。选型必须先定义一致性强度、可补偿性、锁资源成本、失败恢复时限和人工对账要求；常见误区是认为引入 MQ 就自动解决分布式事务，事实上它通常只是把跨系统强一致改造成可恢复的最终一致。

  • 原理解析：

    • 分布式事务的系统模型是一个业务动作跨多个资源管理器，单个本地事务无法覆盖全部状态。故障假设包括服务崩溃、协调者失联、网络分区、消息重复或乱序，因此目标不是“永不失败”，而是在失败后能判断状态并继续提交、回滚、补偿或人工修复。
    • 2PC 的因果链是先准备后决议：参与者在 prepare 后承诺能提交并持有锁，协调者再广播 commit/rollback。它接近强一致，但前提是参与者支持 XA 或等价准备语义；若协调者在决议前后故障，参与者可能阻塞等待，资源占用和恢复日志成为主要成本。
    • TCC 把锁资源变成业务预留，Try 冻结额度或库存，Confirm 生效，Cancel 释放。它要求 Confirm/Cancel 幂等且可重试，还要处理 Try 未执行却收到 Cancel 的空回滚、Cancel 后又 Confirm 的悬挂、重复通知和超时扫描。
    • Saga、Outbox 和事务消息通常选择最终一致：每一步本地提交后用事件驱动下一步，失败则补偿或重试。补偿是业务反向动作，不一定能还原现实世界副作用，所以要明确哪些步骤可逆、哪些只能对账、退款或人工介入。
    • 记忆抓手：2PC 是“大家先锁住再统一表决”，TCC 是“先预留再确认/取消”，Saga 是“一步步做，失败往回补”，Outbox 是“业务和事件同库落地再可靠投递”。选型看一致性强度、锁成本和可补偿性。还要检查参与方数量、外部系统是否支持事务语义、用户是否能接受中间态、补偿失败后谁处理。任何方案都离不开事务状态表、幂等键、重试退避、死信、告警和对账；没有这些恢复链路，协调器或消费者一崩溃就会留下无法解释的半完成状态。评审方案时应画出每一步的已提交、未提交、未知三种状态，并为每种状态给出可重复执行的下一步动作。这样才能从异常恢复角度证明方案闭环。

  • [ ] ★★★ 什么是服务注册与发现？

  • 完整回答：
    • 服务注册与发现用于解决微服务实例动态变化时“调用方如何找到可用服务”的问题。一个服务实例启动后，会把服务名、地址、端口、协议、版本、权重、机房、标签和健康状态注册到注册中心，并通过心跳、租约或主动探测维持可用性；实例下线、崩溃或健康检查失败后，注册中心会把它标记为不可用或摘除。调用方可以采用客户端发现，即从注册中心拉取实例列表并在本地按轮询、权重、最少连接、一致性哈希等策略负载均衡；也可以采用服务端发现，即请求先到网关或负载均衡器，由中间层查询服务目录并转发。常见注册中心包括 Nacos、Eureka、Consul、ZooKeeper、etcd 和 Kubernetes Service/Endpoint，不同实现的一致性、可用性、租约模型和配置治理能力并不相同。正常流程是实例启动注册、周期续约、健康检查、调用方缓存服务列表、监听或轮询变更、失败实例摘除、恢复后重新加入。失败模式包括注册中心不可用、心跳延迟导致误摘除、实例假死但端口仍通、网络分区形成两套视图、缓存过期导致调用旧地址，以及发布时新旧版本流量不兼容。恢复设计通常要求调用方保留本地缓存、设置过期和熔断策略、对慢实例做探测、支持优雅下线和预热，并让配置变更可灰度和回滚。微服务发布时还要配合 readiness、preStop、连接排空和版本标签，避免实例刚启动就承接流量或已经下线仍被调用。服务发现只解决地址发现，不直接保证业务成功；调用仍要配置超时、重试、幂等、限流和链路追踪。误区是把注册中心当数据库强依赖，实际高可用架构下注册中心短暂故障不应让全部存量调用立即失败。

  • 原理解析：

    • 服务发现的模型是服务实例会动态扩缩容、重启、漂移地址，调用方不能把地址写死。注册中心保存的是“某服务名到一组候选实例”的目录状态，健康检查和租约负责让目录尽量接近真实可用状态。
    • 因果链是实例启动后注册并续约，调用方拉取或监听列表，本地负载均衡选择实例；实例下线先停止接新流量，再摘除注册并排空连接。若顺序反了，新实例可能未就绪就被打流量，旧实例也可能在退出时继续收到请求。
    • 故障假设包括注册中心短暂不可用、心跳延迟、网络分区、假健康和客户端缓存过期。注册中心目录本身也有一致性/可用性取舍：强一致目录更能避免过期视图，但故障时可能不可写；可用优先目录更易继续服务，但调用方会看到短暂旧列表。
    • 服务发现只给出“去哪儿调用”，不保证“调用一定成功”。因此调用侧仍要有超时、熔断、重试预算、幂等和观测；注册中心故障时通常依赖本地缓存继续调用存量实例，并对新发布和摘除保持保守策略。
    • 记忆抓手：注册是“我在哪、我是否健康”，发现是“我要找谁、怎么选一个”。发布安全靠 readiness、优雅下线、连接排空和版本标签，不靠注册中心单独兜底。设计时还要区分控制面和数据面：注册中心负责变更传播，真实请求仍由调用方或代理执行。控制面短暂故障时，存量调用应依赖缓存和熔断继续工作；数据面发现慢实例、版本不兼容或跨机房延迟时，要靠负载均衡、健康探测和灰度规则逐步纠偏。健康状态也要分层：进程存活、端口可连、依赖就绪和业务可写不是同一件事，检查过粗会把坏实例留在流量池。调用方也要容忍短暂旧视图。

  • [ ] ★★★ API 网关通常承担哪些职责？

  • 完整回答：
    • API 网关是外部客户端或跨域流量进入后端服务的统一入口，它的价值在于把横切能力集中治理，并屏蔽内部服务拓扑。典型职责包括 TLS 终止、域名和路径路由、协议转换、请求大小限制、认证鉴权、JWT 或签名校验、黑白名单、CORS、限流、熔断、灰度发布、流量镜像、版本路由、日志、指标、Trace 上下文注入和统一错误格式。面向移动端或前端页面时，还可能存在 BFF 网关，用于按端聚合多个后端接口、裁剪字段和适配展示模型；它与通用网关不同，可以带少量端侧适配逻辑，但仍不应承载核心业务状态变更。一次请求进入网关后，网关先完成协议和安全校验，再按路由规则选择上游服务，应用超时、重试、限流和熔断策略，转发时传播 Trace ID、用户身份和租户上下文，最后记录访问日志和指标。失败模式包括网关成为单点瓶颈、规则配置错误造成大面积不可用、鉴权绕过、重试放大下游故障、响应包装掩盖真实错误、过度聚合导致延迟上升。恢复和治理要求网关多实例部署、配置版本化、灰度发布、快速回滚、管理面和数据面隔离，并限制插件或脚本的执行成本。对写接口，网关重试必须非常谨慎，只有在请求有幂等键、下游明确未处理或协议支持安全重放时才适合启用，否则客户端超时后的重复转发可能造成重复下单或重复扣款。网关还要把管理权限、审计日志和配置发布流程纳入治理，避免一条错误路由或限流规则影响全站。网关可以统一入口策略，但不能替代服务自身的权限校验和资源保护，因为内部调用、消息消费和后台任务也可能触发同样的业务能力。误区是把所有复用逻辑都塞进网关，结果形成强耦合中心服务，既难测试又难扩展。

  • 原理解析：

    • 网关的系统模型是边界代理：外部客户端面对统一入口，内部服务保持独立演进。它适合承载协议、安全、路由和流量治理等横切逻辑，因为这些逻辑需要在请求进入业务服务前统一执行并产生审计证据。
    • 请求因果链通常是 TLS/协议处理、认证鉴权、限流、路由匹配、上游选择、超时控制、上下文透传、响应整理和日志指标上报。顺序很重要：未鉴权的请求不应进入业务，限流应在昂贵处理前发生，Trace ID 要在转发前注入。
    • 故障假设包括网关实例宕机、配置错误、插件异常、下游变慢和重试放大。网关集中治理也集中风险，所以需要多实例、配置版本化、灰度、回滚、管理面权限控制和数据面资源隔离。
    • 一致性和安全边界不能全部压给网关。网关认证的是入口请求，服务自身仍要校验权限、租户和资源归属，因为内部调用、消息消费、后台任务或绕过网关的运维流量也可能触发业务能力。
    • 记忆抓手：网关做“入口治理”，BFF 做“端侧适配”，核心业务规则仍在服务内。写接口重试必须有幂等键或明确未执行证据，否则超时重放会制造重复副作用。网关的取舍边界是集中能力与集中风险并存：集中鉴权、限流和日志能降低重复建设，但过度聚合、脚本化业务和复杂转换会让网关成为隐形单体。更稳的做法是让网关保持薄治理层，复杂领域规则下沉到拥有数据和事务边界的服务。网关配置属于高风险变更，应有审计、回滚、灰度和自动校验；一条错误路由或鉴权规则的影响面常大于单个服务发布。内部服务仍要保留最小权限校验和资源保护，防止旁路调用破坏边界，并纳入统一审计。

  • [ ] ★★★ 什么是限流、熔断和降级？三者有什么区别？

  • 完整回答：
    • 限流、熔断和降级都是保护系统可用性的手段，但触发条件和目标不同。限流关注进入系统的流量是否超过容量，按用户、接口、租户、IP、应用、全局或下游资源维度控制请求速率或并发数，超过阈值时排队、拒绝或返回稍后重试。它的前提是系统有可估算的容量边界，常用于入口网关、热点接口、写库保护和第三方调用配额。熔断关注下游依赖是否已经不健康，当错误率、慢调用比例、超时数或并发堆积超过阈值时，调用方从关闭状态进入打开状态，快速失败而不继续占用线程和连接；经过冷却时间后进入半开状态，放少量探测流量，成功则恢复，失败则继续打开。降级关注功能优先级，在故障或压力下主动牺牲非核心能力，例如推荐改默认列表、评论延迟展示、图片低清、报表暂停、优惠计算简化，以保护支付、下单、登录等核心链路。三者常组合：入口限流防止总流量压垮系统，依赖熔断隔离故障扩散，业务降级维持可接受体验。失败模式包括阈值设置过紧导致误杀正常流量，过松导致保护太晚；多层限流和重试叠加引发震荡；降级逻辑缺少演练，真正故障时不可用。恢复设计要包括动态配置、灰度开关、告警、指标看板、重试预算和幂等处理，并在压测和演练中验证触发阈值、恢复条件、兜底数据是否真的可用。用户侧返回也要区分限流、依赖故障和功能降级，避免所有问题都包装成成功。三者都应有退出条件，压力下降或依赖恢复后逐步放量，不能立即全量恢复造成二次冲击。数据类降级还要标明时效和来源，防止用户把兜底旧数据误认为实时结果。误区是认为熔断能修复下游问题，它只是快速失败和隔离，根因仍需扩容、修复慢查询、隔离资源或调整业务流程。

  • 原理解析：

    • 三者的模型都是故障隔离，但观察对象不同：限流看入口或资源容量，熔断看依赖健康度，降级看业务功能优先级。它们的前提是系统已经知道容量边界、依赖指标和核心链路，否则阈值只是经验数字。
    • 限流的因果链是请求到达超过令牌、窗口或并发阈值，于是排队、拒绝或削峰；它防止流量超过处理能力。熔断的因果链是下游错误率或慢调用升高，调用方打开熔断器快速失败，冷却后半开探测，避免线程和连接继续被拖死。
    • 降级的因果链是压力或故障触发开关，非核心功能改用默认值、旧数据、异步处理或暂停，以便核心链路保留资源。降级必须说明数据来源和时效，不能把兜底旧数据包装成实时正确结果。
    • 取舍边界在误杀与保护太晚之间：阈值太紧会拒绝正常请求，太松会等到资源耗尽才动作；重试若没有预算，会抵消限流和熔断效果。写请求还要有幂等前提，否则失败后重试或切流可能重复产生副作用。
    • 记忆抓手：限流挡“太多请求”，熔断躲“坏依赖”，降级舍“低优先级功能”。三者都要有退出条件、灰度开关、演练和监控，不会自动修复根因。设计时要把保护目标写清楚：保护入口、线程池、数据库、第三方额度还是核心业务转化率。返回语义也要清楚，限流应提示退避，熔断应暴露依赖不可用，降级应标明兜底来源；若全部伪装成成功，会掩盖故障并误导用户和运营判断。还要检查多层策略是否冲突：入口限流、客户端重试和服务熔断若没有统一预算，可能反复开关形成震荡。恢复放量同样要渐进，避免刚恢复又被积压流量压垮。核心链路应单独验收。

  • [ ] ★★★ 常见限流算法有哪些？

  • 完整回答：
    • 常见限流算法包括固定窗口、滑动窗口、漏桶、令牌桶和并发数限制。固定窗口按自然时间片计数，例如每秒最多 100 次，实现简单，适合低成本统计，但在窗口边界可能前一秒末尾和后一秒开头各通过 100 次，形成短时突刺。滑动窗口通过请求时间戳或多个小桶统计最近一段时间内的请求量，可以减少边界突刺；时间戳方式更精确但存储多，小桶方式成本低但有近似误差。漏桶把请求先放入容量有限的桶，再按固定速率流出，适合保护处理能力稳定的下游，缺点是对突发流量不够友好，桶满后只能排队或拒绝。令牌桶按固定速率生成令牌，桶中可积累一定令牌，请求必须拿到令牌才能通过；它限制长期平均速率，同时允许短时突发，是网关和服务端常用方案。并发数限制控制同时执行的请求数量，更适合保护线程池、连接池和慢依赖。分布式限流还要明确前提：单机本地限流性能高但全局不精确；集中式 Redis 或限流服务能做全局控制，但会引入网络开销、中心瓶颈、时钟一致性、热 key 和故障降级问题；网关限流适合入口保护，服务内限流适合资源精细保护。实现时要决定超过阈值后的动作：直接拒绝、短队列等待、降级返回、削峰入队或按优先级放行；不同动作对应不同延迟和一致性风险。限流规则也要支持按租户、会员等级、接口成本和业务优先级分层，否则低价值流量可能挤占核心交易流量。还要监控通过量、拒绝量、排队时间和下游错误率，用真实容量反馈阈值，而不是长期依赖静态经验值。恢复和补偿上，被限流请求应返回明确状态、重试建议和退避时间，客户端重试必须有上限和抖动，写操作还要幂等。误区是只看 QPS 阈值，不区分接口成本、用户优先级、冷启动预热和下游真实容量。

  • 原理解析：

    • 限流算法的共同模型是把“请求到达过程”映射到可控资源消耗，前提是能估计资源容量并定义拒绝、等待或降级动作。只设 QPS 不够，因为不同接口的 CPU、数据库、锁等待和第三方配额成本可能完全不同。
    • 固定窗口按时间片计数，状态少但边界会突刺；滑动窗口用时间戳或小桶近似最近一段时间，状态更多但更平滑。它们本质上限制一段时间内的数量，适合入口流量统计和简单配额。
    • 漏桶把流量按固定速率流出，因果链是突发请求先排队，桶满拒绝，保护下游稳定处理；令牌桶按速率生成令牌，桶内积累允许短时突发，长期平均速率仍受控。二者区别可以记成漏桶“匀速出水”，令牌桶“攒票放行”。
    • 并发限制控制同时执行数量，更贴近线程池、连接池和慢依赖保护。分布式限流还要面对状态一致性：本地限流快但全局不准，Redis/集中式限流准一些但有网络开销、热 key、时钟误差和中心故障降级问题。
    • 记忆抓手：窗口管“单位时间多少个”，漏桶管“稳定流出”，令牌桶管“平均速率加突发”，并发管“同时占用多少资源”。客户端重试必须退避和限次，写请求还要幂等。选算法时要先问容量曲线：下游能否吃短突发、是否有队列缓冲、是否按租户公平、是否需要全局精确。全局精确往往牺牲延迟和可用，本地近似则可能超卖额度；工程上常用分层限流，把入口粗保护和服务内细保护组合起来。阈值还应随压测、实例数、依赖配额和业务活动动态调整，不能长期使用上线初期的静态经验值。监控拒绝量和排队时间才能判断规则是否伤害正常用户，并用于反向修正容量模型和优先级策略。

  • [ ] ★★★ 如何设计幂等接口？

  • 完整回答：
    • 幂等接口的目标是在客户端超时重试、网关重放、MQ 重复投递、第三方回调多次到达等场景下，同一个业务请求执行一次和多次的最终业务效果一致。它的前提是先定义“同一个请求”的业务身份，例如订单号、支付流水号、请求幂等键、消息 ID 或由客户端生成的唯一 token，而不是简单用 HTTP 连接或时间窗口判断。设计流程通常是：请求到达后先校验幂等键格式和业务归属，再尝试写入幂等记录或依赖数据库唯一约束登记；若首次处理，则执行业务状态变更并保存结果；若重复到达，则返回首次处理结果或当前稳定状态；若前次处于处理中，则返回处理中、阻塞短暂等待或让客户端稍后查询。可靠边界优先使用数据库唯一索引、条件更新和状态机，例如支付单只能从待支付变为已支付，不能重复扣款；Redis SET NX 可作为高性能防重，但必须考虑 TTL、持久化、主从切换和锁过期后业务仍执行的问题。失败模式包括幂等记录写成功但业务失败、业务成功但结果未记录、请求参数相同 key 不同内容、记录过早过期、并发重复请求同时进入，以及重试把下游故障放大。恢复方案包括本地事务包住幂等记录和业务状态、处理中状态超时扫描、结果补录、对账补偿和人工排查字段。接口还应校验同一幂等键下的请求体摘要，防止客户端复用 key 提交不同业务内容；幂等记录的过期时间要覆盖最大重试窗口、消息堆积时间和对账周期。幂等不等于拒绝重复请求，也不等于不重试；正确做法是允许有限重试，并让重复执行收敛到同一结果。创建订单、支付回调、退款、发券、MQ 消费都需要显式幂等，查询天然幂等但仍要注意读一致性。

  • 原理解析：

    • 幂等的系统模型是调用方和服务端之间存在不可靠网络：请求可能已执行但响应丢失，消息可能重复投递，网关或客户端可能重放。前提是必须有稳定的业务身份来判定“同一次请求”，例如订单号、支付流水、消息 ID 或幂等键。
    • 因果链是先登记幂等身份，再执行业务状态变更，最后记录稳定结果；重复请求到来时根据幂等记录、唯一约束或状态机返回原结果。若业务先执行而幂等记录未落地，或记录落地但业务失败，就需要处理中状态、超时扫描和结果补录。
    • 可靠边界通常放在数据库唯一索引、条件更新和状态机上，因为它们和业务数据在同一事务域内更容易证明。Redis SET NX 只能在 TTL、持久化、主从切换和业务执行时长都受控时作为防重辅助，不能单独保证资金类正确性。
    • 幂等不是不执行重复请求，而是让重复执行的最终业务效果收敛。还要校验同一 key 的请求摘要，防止一个幂等键提交两种业务；记录保留时间要覆盖最大重试窗口、消息积压和对账周期。
    • 记忆抓手：先定义“同一个请求”，再保证“首次和重复走同一状态机”。超时不等于失败，重试不等于安全；写操作要靠业务唯一号、状态转移和对账兜底。接口还要决定重复请求返回什么：返回首次结果、当前稳定状态，还是处理中状态；不同选择影响客户端体验和恢复逻辑。对 MQ 消费、第三方回调和支付通知，幂等记录应包含来源、业务键、请求摘要、处理状态、结果和错误，方便补偿任务判断下一步。并发场景要用唯一约束或条件更新挡住双写，仅靠先查再写会在竞态下失效。幂等键过期也要谨慎，过早删除会让迟到重试重新生效。

  • [ ] ★★★ 什么是分布式锁？它有哪些实现方案和风险？

  • 完整回答：
    • 分布式锁用于多个进程、机器或服务实例竞争同一资源时，尽量保证同一时刻只有一个持有者执行临界区逻辑，例如定时任务单实例执行、库存批处理、缓存重建和资源迁移。它成立的前提是锁服务本身提供足够的原子写入、租约或一致性语义，并且业务能承受锁失效后的补救方式。Redis 实现常用 SET key value NX PX ttl 原子加锁，value 是唯一令牌，释放时用 Lua 先比较 value 再删除，避免误删他人锁；长任务需要续期，但续期也可能因 GC 暂停、网络抖动或进程假死失败。Redis 单主加异步复制在主从切换时可能丢失刚写入的锁，网络分区或租约过期后旧持有者继续写，会破坏严格互斥。ZooKeeper 或 etcd 可用临时节点、租约、顺序节点和会话机制实现，基于多数派一致性语义更强，适合配置变更、主节点选举等场景，但延迟、运维和可用性成本更高。数据库锁可用唯一索引、select for update 或租约表实现，简单直观并能和业务事务结合，但吞吐和死锁处理有限。关键风险包括锁过期、锁误删、客户端暂停、脑裂、时钟依赖、临界区过长和异常退出。恢复策略包括短租约、唯一令牌、续期上限、异常清理、重试退避，以及更重要的 fencing token：每次成功获得锁生成递增令牌，下游资源只接受最新令牌写入，从而拒绝旧持有者。使用锁前还要评估是否能改成无锁方案，例如数据库条件更新、唯一约束、乐观版本号或单分区串行消费，这些方案往往比跨节点互斥更容易验证。分布式锁不能替代数据库唯一约束、状态校验、幂等和补偿；对资金、库存等关键业务，应把锁视为降低冲突的手段，而不是绝对正确性的唯一来源。

  • 原理解析：

    • 分布式锁的模型是多个客户端竞争同一临界资源，但锁服务、客户端和网络都可能失败。它的前提不是“拿到锁就绝对互斥”，而是锁服务提供原子创建、租约过期和足够一致的可见性，业务还要能处理锁失效后的重复执行。
    • Redis 锁的因果链是 SET NX PX 原子占位，value 作为持有者令牌，释放时比较令牌再删除；租约避免死锁，但也引入过期风险。若客户端 GC 暂停、网络卡顿或任务超时，锁过期后新持有者进入，旧持有者恢复继续写，就会出现双写。
    • ZooKeeper/etcd 借助会话、临时节点、顺序节点或租约，并通过多数派复制获得更强一致语义，适合选主和配置变更；代价是延迟、运维复杂度和多数派不可用时的可用性损失。数据库锁简单，但容易受事务时间、死锁和吞吐限制影响。
    • 关键补救是 fencing token：每次获锁得到递增令牌，下游资源只接受最新令牌，从而把“旧持有者复活”挡在写入边界外。没有下游令牌校验时，锁只能降低并发概率，不能单独证明严格互斥。
    • 记忆抓手：锁要防误删、过期、脑裂和旧持有者；更稳的方案常是唯一约束、条件更新、乐观版本或单队列串行化。资金、库存不能只靠分布式锁兜底。判断锁是否适用时，要看临界区能否在租约内完成、续期失败会怎样、释放是否只删自己的锁、下游是否能拒绝旧令牌。若业务状态本身可以用数据库条件更新表达，通常比引入跨节点锁更容易测试、审计和恢复。锁失败后的业务结果也要可观测：谁持有、何时过期、是否续期、失败后是否重试，都应能追踪。临界区越长，租约模型越脆弱，越需要把正确性放到最终写入资源校验和状态机约束，并保留补偿入口。

  • [ ] ★★★ 负载均衡算法有哪些？

  • 完整回答：
    • 负载均衡的目标是把请求分配到多个后端实例，在吞吐、延迟、故障隔离和资源利用之间取得平衡。常见算法有轮询、加权轮询、随机、加权随机、最少连接、最少请求、一致性哈希、基于延迟或 EWMA 的策略，以及按地域、标签、版本的路由。轮询默认实例能力相同，简单稳定；加权轮询适合实例规格不同或灰度放量；随机在实例数多时效果接近均匀，配合权重实现成本低；最少连接或最少请求会优先选择当前负载较低的实例，适合请求耗时差异大的服务，但依赖统计准确性，长连接、HTTP/2 多路复用和异步任务可能让连接数失真。一致性哈希把 key 映射到固定实例，适合缓存、会话亲和、分片路由和有状态服务，代价是负载可能倾斜，需要虚拟节点和热点治理。基于延迟的策略会避开慢实例，但如果采样窗口和惩罚规则不合理，可能产生流量震荡或让刚恢复实例长期无流量。完整流程通常包括健康检查、实例发现、本地缓存、选择算法、连接复用、超时和失败重试。失败模式包括把流量继续打到“可用但很慢”的实例、重试到同一故障节点、局部热点 key 压垮单实例、权重配置错误、发布期间新实例未预热。恢复设计要支持主动/被动健康检查、慢启动、熔断摘除、跨可用区容灾、重试预算和可观测指标。对于写请求，负载均衡还要关注会话一致性、幂等和主从路由，不能因为失败重试到另一个实例就默认业务没有执行。跨地域负载均衡还要权衡就近访问和数据一致性，不能把强一致写请求随意路由到没有写权限或复制滞后的区域。误区是认为算法本身决定效果，实际 P99 常被超时、连接池、实例预热、下游容量和重试策略共同决定。

  • 原理解析：

    • 负载均衡的模型是调用方面对一组能力、状态和位置可能不同的实例。算法输入不只是实例列表，还包括权重、健康状态、连接数、延迟、地域、版本和请求 key；目标是在均匀性、稳定性、亲和性和故障隔离之间取舍。
    • 轮询和随机默认实例近似同质，加权版本用权重表达容量或灰度比例；最少连接/最少请求依赖实时负载统计，适合耗时差异大的请求，但长连接、HTTP/2 多路复用和异步处理会让“连接数”等指标失真。
    • 一致性哈希的因果链是把请求 key 固定映射到实例，节点变化时只迁移相邻区间，适合缓存和会话亲和；缺点是热点 key 和节点倾斜，需要虚拟节点、副本、热点拆分和限流。
    • 延迟/EWMA 策略试图避开慢实例，但要处理采样窗口、惩罚时间和恢复慢启动，否则容易在实例之间来回摆动。失败重试也要有预算，并避开同一故障节点；写请求重试必须满足幂等或能确认前次未执行。
    • 记忆抓手：轮询看“均分”，权重看“容量”，最少连接看“当前忙不忙”，哈希看“同 key 固定去处”，延迟策略看“谁最近更快”。P99 往往由超时、连接池、预热和重试共同决定。设计时还要把健康检查分成主动探测和被动摘除：端口通不代表业务快，少量错误也不一定要立即踢出。新实例需要慢启动，故障实例恢复要逐步放量；跨地域路由还要尊重数据主写区域和复制延迟。算法选择还要看请求是否有状态，缓存和会话需要亲和，纯无状态接口更适合均衡分散。发布灰度时权重变化也要小步推进，并持续观察错误率和尾延迟，及时回滚异常权重。写流量还要确认主写权限和幂等重放条件，避免路由错误放大数据问题和审计缺口。

  • [ ] ★★ 一致性哈希解决了什么问题？为什么需要虚拟节点？

  • 完整回答：
    • 一致性哈希解决的是分布式缓存、分片存储或有状态路由中，节点数量变化时大量 key 重新映射的问题。普通取模通常用 hash(key) % N 选择节点，当 N 从 10 变成 11 或 9 时，大部分 key 的结果都会变化，导致缓存大面积失效、数据迁移量暴增或会话路由混乱。一致性哈希把节点和 key 都映射到同一个哈希环上，key 顺时针找到的第一个节点就是目标节点；当节点下线时，只有该节点负责的区间迁移到下一个节点，当节点上线时，也只接管相邻区间的一部分，因此迁移范围显著缩小。它的前提是哈希函数分布足够均匀，并且业务能处理节点变化期间的短暂迁移、双读或回源。虚拟节点是把一个真实节点映射为多个环上位置，用更多小区间平摊负载，缓解真实节点数量少或哈希分布不均带来的数据倾斜；还可以通过给高配置机器分配更多虚拟节点实现权重。失败模式包括热点 key 集中、虚拟节点过少导致倾斜、过多增加路由表维护成本、节点频繁抖动引发迁移风暴。它适合缓存路由、分片定位和会话亲和，但不能自动解决副本一致性、数据恢复和热点保护，仍需配合副本、限流、预热和迁移校验。

  • 原理解析：

    • 一致性哈希的模型是 key 到节点的稳定映射，主要故障或变化是假设节点会增删。普通取模把节点数 N 放进公式，N 一变大量 key 重算到别处；哈希环把变化限制在相邻区间，因此迁移和缓存失效率更小。
    • 因果链是 key 顺时针找节点，节点下线时它负责的区间交给后继，节点上线时只从后继切走一段。这个机制的前提是哈希分布较均匀，并且业务能处理迁移期间的回源、双读或短暂 miss。
    • 虚拟节点把一个真实节点拆成多个环上位置，用更多小区间摊平随机不均；给大机器更多虚拟节点还能表达权重。虚拟节点过少会倾斜，过多会增加路由表和变更维护成本。
    • 记忆抓手：一致性哈希解决“节点数变了别全乱”，虚拟节点解决“环上点太少不均匀”。它不负责副本一致、热点 key 和数据恢复，这些还要另配副本、限流和迁移校验。扩缩容时还要设计预热和回源保护，否则虽然迁移范围小，被迁移的区间仍可能瞬间打爆数据库；对有状态存储还要有迁移进度、校验和回滚策略。若某些 key 天然热门，还需要热点拆分或多副本读，虚拟节点只能缓解节点级倾斜，不能消除业务热点。节点抖动时应限制频繁迁移，避免路由表不断变化。

  • [ ] ★★ 什么是服务雪崩？如何防止？

  • 完整回答：
    • 服务雪崩是指某个依赖、数据库、缓存或下游服务故障后，调用链上的等待、重试和资源占用被不断放大，最终引发大范围不可用。它的前提通常是服务之间存在同步调用、共享线程池或连接池、超时过长、重试无预算，以及核心与非核心链路没有隔离。典型流程是下游变慢，调用方线程阻塞，连接池被占满，请求排队变长，客户端和网关开始重试，重试流量进一步压垮下游，最终连原本健康的服务也因为资源耗尽而失败。防止雪崩首先要设置合理超时，超时必须小于整体调用链预算，并区分连接、读写和总超时；重试只针对瞬时故障，必须有次数上限、指数退避、随机抖动和全局重试预算，写操作还要幂等。其次要做资源隔离，如按依赖拆线程池、连接池、舱壁和队列长度，避免一个慢依赖耗尽全局资源。再次要使用限流、熔断和降级，对高错误率或慢调用依赖快速失败，对非核心功能返回默认值或延迟处理。恢复上需要健康检查、慢启动、容量预案、压测、故障演练、指标告警和人工开关。缓存、配置中心和数据库这类共享依赖还要有本地缓存、只读降级或保护开关，否则一个基础组件抖动会同时影响大量服务。误区是只增加机器或只加重试，前者可能扩大故障面，后者在下游不可用时会制造更多压力。

  • 原理解析：

    • 服务雪崩的模型是同步调用链和共享资源池相互耦合，故障假设是某个下游变慢或不可用。慢比直接失败更危险，因为线程、连接和队列会被长时间占住，导致上游也失去处理新请求的能力。
    • 因果链是下游变慢、调用方等待、资源池耗尽、排队延长、上层超时重试、重试流量继续压垮下游，最后无关功能也被拖垮。没有超时预算和重试预算时，多层重试会把一次故障放大成指数级压力。
    • 防护边界包括入口限流、依赖熔断、业务降级和资源隔离。隔离的关键是线程池、连接池、队列和舱壁按依赖拆开，让非核心或故障依赖不能耗尽核心链路资源。
    • 记忆抓手：雪崩不是单点坏，而是“等待和重试传染”。防止它靠短超时、有预算重试、快速失败、非核心降级、慢启动恢复和演练；写请求重试必须有幂等前提。还要把核心与非核心资源分开，例如推荐、报表、通知不能和支付、登录共享无界线程池。恢复时不要故障一消失就全量放开，应半开探测、逐步放量，避免积压请求造成二次冲击。监控上重点看慢调用比例、队列长度、连接池等待和重试量，而不只是错误率。基础依赖要准备本地缓存或只读兜底，预案必须提前演练。

  • [ ] ★★ 重试机制应该如何设计？

  • 完整回答：
    • 重试用于处理短暂、可恢复且结果不确定的失败，例如网络抖动、连接重置、临时超时、限流后的可重试错误、主从切换瞬间失败。它不适合参数错误、权限失败、余额不足、库存不足、唯一约束冲突等确定性业务失败。设计时要先明确操作是否幂等：查询和幂等更新可以直接重试；创建订单、扣款、发券、发送通知等写操作必须有幂等键、业务唯一号、状态机或去重表，否则一次成功但响应超时后再次重试会造成重复效果。重试策略要包含最大次数、总超时时间、指数退避、随机抖动和重试预算，避免所有客户端在同一时间重试形成尖峰，也避免正常请求被重试流量挤占。跨层调用要统一治理，客户端、网关、服务框架、SDK 和 MQ 消费者不能各自默认重试，否则 3 层各重试 3 次会把一次请求放大成多次下游调用。失败恢复上，应记录最后错误、尝试次数和业务键，必要时进入死信队列、补偿任务或人工处理。对外部支付、短信、物流等第三方接口，还要保存请求流水和响应状态，用查询接口确认最终结果，不能靠无限重发猜测是否成功。误区是把超时等同失败：超时只说明调用方没等到结果，下游可能已经执行成功，因此重试前必须能识别重复请求并返回稳定结果。

  • 原理解析：

    • 重试的系统模型是不可靠调用：请求、响应或连接可能短暂失败，调用方无法直接知道下游是否执行。它只适合临时性、可恢复、结果不确定的失败；参数错误、权限拒绝、余额不足这类确定性失败重试不会变好。
    • 因果链是首次调用失败或超时，调用方等待退避时间后再次发送；若所有客户端同步重试，会形成新尖峰，所以要指数退避、随机抖动、最大次数、总超时和全局重试预算。
    • 写操作的前提是幂等：订单号、支付流水、幂等键、状态机或去重表能让重复请求返回同一稳定结果。超时不等于失败，下游可能已扣款或发券，不能靠再次发送来猜测结果。
    • 记忆抓手：重试救“偶发抖动”，不救“确定错误”。跨客户端、网关、SDK、MQ 的重试层数要统一治理，否则三层各三次会把一次请求放大很多倍；外部接口还要用查询和对账确认最终状态。限流后的重试要尊重退避时间，服务端也可返回可重试标记。记录尝试次数、最后错误和业务键，才能把失败请求送入死信、补偿或人工处理。判断一次重试是否安全，要同时看错误类型、剩余超时预算、下游容量和业务幂等条件。重试失败后的结果也要可查询，避免状态悬空。

  • [ ] ★★ RPC 和 HTTP REST 有什么区别？

  • 完整回答：
    • RPC 和 HTTP REST 的核心区别在抽象模型。RPC 强调远程过程调用，让调用方像调用本地方法一样调用远程服务，通常通过接口定义文件或服务契约生成客户端和服务端代码，常见实现有 gRPC、Dubbo、Thrift。它常使用二进制序列化、长连接、多路复用和强类型契约，适合内部服务之间高频、低延迟、接口明确的调用，也便于做服务治理、负载均衡、超时和熔断。REST 强调资源建模，用 URI 表示资源，用 HTTP 方法表达语义，例如 GET 查询、POST 创建或触发处理、PUT/PATCH 更新、DELETE 删除，并借助状态码、Header、缓存和代理生态，适合开放 API、跨语言接入、浏览器和第三方调试。二者没有绝对优劣：内部微服务调用更偏 RPC，对外公共接口更偏 REST，复杂系统也会混用。失败模式上，RPC 容易因接口强契约导致版本兼容问题，需要字段向前向后兼容、灰度和治理；REST 如果设计不当，也会退化为 /doSomething 式动作接口，失去资源语义。两者都必须处理网络不可靠、超时、重试、认证、限流、幂等、链路追踪和错误结构。误区是认为 RPC 一定比 REST 快或 REST 一定更松耦合，真实性能取决于协议、序列化、连接复用、负载均衡和服务实现，耦合程度也取决于契约和版本治理。

  • 原理解析：

    • RPC 的模型是“调用远程方法”，REST 的模型是“操作资源状态”。RPC 以接口契约和方法签名为中心，REST 以 URI、HTTP 方法、状态码、Header 和缓存语义为中心；差异主要是抽象边界，不只是传输协议。
    • RPC 的因果链通常由 IDL 生成客户端和服务端桩，调用方序列化请求，经长连接或多路复用发到服务端，再反序列化返回。它适合内部高频调用，但强契约要求字段兼容、版本灰度和服务治理，否则升级容易互相卡住。
    • REST 借助 HTTP 生态表达资源的查询、创建、更新和删除，适合开放接口、浏览器、代理缓存和第三方调试。若接口全写成动作路径，REST 也会退化成松散的 RPC，资源语义和缓存优势都会变弱。
    • 记忆抓手：RPC 像“调函数”，REST 像“管资源”。性能没有绝对结论，取决于序列化、连接复用、负载均衡和实现；两者都必须处理超时、重试、鉴权、限流、幂等和链路追踪。选择时要看调用方是谁、契约是否稳定、是否需要浏览器和代理生态、是否要求强类型生成代码。对外接口通常更重兼容和可调试，内部接口通常更重治理和效率。版本演进时都要保持向前向后兼容，不能删除仍被旧客户端使用的字段。错误码和超时语义也要统一，否则调用方很难治理失败和重试策略，也难排查故障。

  • [ ] ★★ 如何实现分布式链路追踪？

  • 完整回答：
    • 分布式链路追踪用于把一次请求跨网关、服务、数据库、缓存、消息队列和第三方依赖的执行路径串起来，帮助定位慢调用、错误传播和容量瓶颈。核心概念是 Trace 和 Span：Trace 表示一次端到端请求，Trace ID 在整条链路中保持不变；Span 表示一个具体操作，如 HTTP 调用、RPC 方法、SQL 查询或 MQ 消费，记录父子关系、开始结束时间、状态、错误、服务名、接口名和标签。实现流程是入口服务接收或生成 Trace ID，把上下文写入 HTTP Header、RPC Metadata 或消息头，后续服务继续透传并创建子 Span，最终由 SDK 或 Agent 上报到采集器，再存入 Jaeger、Zipkin、Tempo 等后端；OpenTelemetry 常用于统一埋点 API、上下文传播和导出协议。异步消息要特别处理生产和消费之间的上下文传递，否则链路会断；批处理和定时任务也应生成独立 Trace。高流量系统不能无脑全量采集，需要头部采样、按错误采样、尾部采样或动态采样，并避免记录身份证、手机号、令牌等敏感数据。失败模式包括 Trace ID 没透传、线程切换丢上下文、采样导致关键错误缺失、标签基数过高压垮存储、时钟漂移影响耗时判断。链路追踪应与日志和指标关联，日志带 Trace ID，指标提供整体趋势，Trace 给出单次请求细节；它帮助定位问题，但不能替代超时、限流、熔断和容量治理。
  • 原理解析：
    • 链路追踪的模型是一次业务请求会跨多个进程和依赖，单机日志无法还原全路径。Trace ID 表示端到端请求，Span 表示一个局部操作，父子关系把调用因果串起来。
    • 因果链是入口生成或接收上下文，把 Trace ID、Span ID 写入 HTTP Header、RPC Metadata 或消息头，后续服务继续透传并创建子 Span，最后由 SDK/Agent 上报采集器。线程池、异步回调和消息队列若不显式传播上下文，链路就会断。
    • 故障和成本假设包括高流量、采样丢细节、标签基数爆炸、时钟漂移和敏感信息泄露。采样策略要兼顾成本和定位能力，错误请求可提高采样率，标签不能放手机号、令牌等高敏或高基数字段。
    • 记忆抓手：指标告诉“整体是否异常”，日志告诉“发生了什么”，Trace 告诉“这一次请求走到哪里慢或错”。追踪只提升可观测性，不能替代超时、熔断、限流和容量治理。落地时要统一传播标准和字段命名，并把日志中的 Trace ID、指标标签和 Span 标签关联起来；否则三个系统各看各的，排障仍要人工拼图。异步消息的生产和消费最好分别建 Span，并保留消息 ID 作为关联线索。采样策略也要可调，故障期间能提高关键链路采样率。高基数字段要受控，避免拖垮存储。敏感字段应脱敏或禁止采集，权限访问也要审计留痕。
