传输层位于应用层与网络层之间，核心任务是把主机之间的进程通信组织起来。网络层负责“把分组送到哪台主机”，传输层负责“交给这台主机上的哪个进程”，并根据协议提供复用分用、可靠传输、流量控制和拥塞控制等能力。

1. 传输层的主要功能

1.1 进程到进程的通信

网络层使用 IP 地址标识主机，但一台主机上可能同时运行浏览器、数据库、Web 服务器等多个网络程序。传输层通过端口号标识具体进程，从而实现端到端的进程通信。

  • IP 地址：定位主机或网络接口。
  • 端口号：定位主机上的应用进程。
  • 套接字：通常可抽象为“IP 地址 + 端口号”，用于标识一个通信端点。

一次 TCP 连接通常由四元组唯一确定：

源 IP + 源端口 + 目的 IP + 目的端口

服务器通常使用固定或知名端口监听连接，客户端一般使用操作系统临时分配的临时端口。

1.2 复用与分用

  • 复用：发送端多个应用进程可以共享同一个传输层协议，通过不同端口发送数据。
  • 分用：接收端根据目的端口，将收到的数据交给对应的应用进程。

UDP 主要依据目的端口进行分用；TCP 依据连接四元组区分不同连接，因此同一个服务器端口可以同时服务大量客户端。

1.3 面向连接与无连接

  • 面向连接：通信双方在传输数据前先建立逻辑连接，数据传输结束后再释放连接。TCP 属于面向连接协议。
  • 无连接：发送数据前不需要建立连接，每个数据报独立处理。UDP 属于无连接协议。

“连接”是传输层维护的逻辑状态，并不等同于物理链路或网络层的专用线路。

2. UDP：简单、快速的无连接传输

2.1 UDP 的特点

UDP（User Datagram Protocol，用户数据报协议）在 IP 之上提供了非常轻量的传输服务，主要特点如下：

  1. 无连接：发送前无需三次握手，减少建立连接的开销。
  2. 面向报文：应用交给 UDP 的数据通常作为一个完整报文发送，UDP 不负责把应用报文拆成字节流后再重新组织。
  3. 尽力而为：不保证数据一定到达、不保证按序到达，也不保证不重复。
  4. 没有可靠重传机制：丢包、乱序、重复等问题通常由应用层自行处理。
  5. 没有拥塞控制：UDP 本身不会像 TCP 那样根据网络拥塞主动降低发送速率。
  6. 首部开销较小：UDP 首部固定为 8 字节，处理路径较短。
  7. 支持广播和多播：适用于一对多或多对多通信场景。

2.2 UDP 首部

UDP 首部包含 4 个字段，每个字段占 16 位：

字段 作用
源端口 标识发送端应用进程，可选使用
目的端口 标识接收端应用进程
长度 UDP 首部与数据的总长度
校验和 检测 UDP 首部和数据在传输过程中是否损坏

UDP 校验和在 IPv4 中可以选择关闭，但在 IPv6 中通常要求使用。校验和只能发现部分传输错误，不能保证数据可靠到达，也不能负责重传。

2.3 UDP 适用场景

UDP 适合对实时性、简单性或广播能力有要求，而不希望被 TCP 的连接建立、可靠重传和拥塞控制过多限制的场景，例如：

  • DNS 查询：请求通常较短，追求低延迟。
  • DHCP：主机初始化时可能还没有可用 IP 地址，需要使用广播或特殊通信过程。
  • 实时音视频、在线游戏：部分旧数据即使重传也可能已经失去意义。
  • QUIC：在 UDP 之上自行实现可靠传输、加密、连接迁移等能力。
  • 广播和多播：UDP 更适合一对多发送。

需要注意：UDP“速度快”并不是因为它能够突破网络带宽，而是因为协议处理简单、没有连接建立和可靠重传等额外机制。若应用需要可靠性、顺序性和拥塞适应能力，就必须由应用层或其他上层协议补充。

3. TCP：面向连接的可靠字节流

3.1 TCP 的主要特点

TCP（Transmission Control Protocol，传输控制协议）为应用提供可靠、有序、面向连接的字节流服务。

  1. 面向连接：通信前需要建立连接，通信结束后需要释放连接。
  2. 可靠传输：通过序列号、确认、重传和校验等机制尽量保证数据正确到达。
  3. 按序交付：应用读取到的是有序字节流，而不是任意顺序的数据段。
  4. 面向字节流：TCP 不保留应用层消息边界。
  5. 全双工：连接两端可以同时发送和接收数据。
  6. 流量控制：根据接收方处理能力限制发送方速度，避免接收缓存溢出。
  7. 拥塞控制：根据网络拥塞程度调整发送速率，避免大量数据压垮网络。

3.2 TCP 是字节流而不是报文协议

应用程序调用 send 或 write 写入的数据，在 TCP 中只是连续字节流。TCP 可能对数据进行拆分、合并或延迟发送，接收端一次 read 读到的数据量也不一定与发送端一次 send 的数据量相同。

例如，发送端连续写入：

send("hello")
send("world")

接收端可能读到：

helloworld

也可能先读到 hel，再读到 loworld。因此，如果应用存在明确的消息边界，需要在应用层设计协议，例如：

  • 固定长度消息；
  • 长度字段 + 消息体；
  • 特殊分隔符；
  • 独立的帧格式。

3.3 TCP 首部中的重要字段

TCP 首部最小为 20 字节，带选项时可以更长。常见字段如下：

字段 作用
源端口、目的端口 标识通信两端的应用进程
序列号 Sequence Number 标识本报文段中数据的起始字节位置
确认号 Acknowledgment Number 表示接收方期望收到的下一个字节序号
首部长度 指示 TCP 首部长度，便于找到数据起始位置
标志位 控制连接建立、释放和数据处理过程
接收窗口 Window 通告接收方当前还能接收多少字节
校验和 检测首部和数据是否损坏
紧急指针 与 URG 标志配合使用，现代应用中较少使用
选项 支持 MSS、窗口扩大、SACK、时间戳等能力

常见标志位包括：

  • SYN：建立连接时同步初始序列号。
  • ACK：确认号字段有效。
  • FIN：发送方没有更多数据，申请关闭自己的发送方向。
  • RST：异常复位连接。
  • PSH：提示尽快将数据交给应用，具体行为受实现影响。
  • URG：紧急指针字段有效，现代应用中使用较少。

4. TCP 连接管理

4.1 三次握手

TCP 建立连接通常需要三次握手：

客户端                                      服务端
  | -------- SYN, seq = x --------------> |
  | <--- SYN + ACK, seq = y, ack = x+1 -- |
  | -------- ACK, ack = y+1 ------------> |

具体过程：

  1. 客户端发送 SYN，随机选择初始序列号 x，进入 SYN-SENT 状态。
  2. 服务端收到后发送 SYN + ACK，选择自己的初始序列号 y，并确认客户端的 SYN，确认号为 x + 1，进入 SYN-RECEIVED 状态。
  3. 客户端发送 ACK，确认号为 y + 1，双方进入 ESTABLISHED 状态。

SYN 本身会消耗一个序列号，即使没有携带应用数据。因此对 SYN 的确认号要加 1。

4.2 为什么不是两次握手

两次握手无法让双方都明确确认以下信息：

  • 双方的发送和接收能力是否正常；
  • 双方初始序列号是否已被对方确认；
  • 当前握手报文是否是旧连接中的延迟报文。

如果网络中滞留了一个旧 SYN，只有两次握手时，服务端可能误以为它是新的连接请求并建立连接。第三次握手让客户端确认服务端的 SYN，并使服务端知道客户端已经收到自己的响应，从而降低历史连接请求造成错误建立的风险。

三次握手主要解决的是连接建立时的双方确认和序列号同步，并不能保证之后的数据永不丢失。

4.3 SYN Flood

SYN Flood 利用 TCP 服务端在收到 SYN 后需要暂存半连接状态的特点，伪造大量源地址发送 SYN，使服务端的半连接队列被占满，正常客户端无法建立连接。

常见防护思路包括：

  • SYN Cookie：不立即为半连接分配完整状态，利用编码后的序列号验证客户端的 ACK。
  • 限制单源或整体 SYN 速率。
  • 扩大或优化半连接队列。
  • 使用防火墙、负载均衡或清洗设备分担攻击流量。
  • 缩短不完整连接的超时时间，但不能过度影响正常网络中的高延迟客户端。

4.4 四次挥手

TCP 是全双工通信，两个方向可以独立关闭，因此常见的正常关闭过程需要四次报文交换：

主动关闭方                                  被动关闭方
  | -------- FIN, seq = u ---------------> |
  | <------------- ACK, ack = u+1 -------- |
  | <-------- FIN, seq = v --------------- |
  | ----------- ACK, ack = v+1 ----------> |

过程说明：

  1. 主动关闭方发送 FIN，表示自己不再发送数据，进入 FIN-WAIT-1。
  2. 对方确认 FIN，主动关闭方进入 FIN-WAIT-2；此时对方仍然可以继续向主动关闭方发送数据。
  3. 对方数据发送完毕后发送 FIN，进入关闭流程。
  4. 主动关闭方发送 ACK，等待一段时间后进入 CLOSED。

FIN 也会消耗一个序列号，因此确认 FIN 时同样需要将序列号加 1。

4.5 为什么通常需要四次挥手

TCP 连接是全双工的，一方发送 FIN 只代表该方向不再发送数据，并不代表双方两个方向都已经结束。被动关闭方收到 FIN 后，可能还有数据需要发送，所以通常先回复 ACK，待剩余数据发送完毕后再单独发送 FIN。

如果某一方已经没有待发送数据，也可以在实现层面把 ACK 和 FIN 合并到一个报文中，因此实际抓包中不一定总是严格看到四个独立报文。

4.6 TIME_WAIT

主动关闭方发送最后一个 ACK 后通常进入 TIME_WAIT，常见原因有两个：

  1. 保证最后的 ACK 能够重传：如果对端没有收到最后的 ACK，会重传 FIN；处于 TIME_WAIT 的一方可以重新发送 ACK。
  2. 让旧连接中的重复报文在网络中自然消失：避免旧连接的延迟报文影响后续使用相同四元组建立的新连接。

TIME_WAIT 不是简单的“连接还没有关闭”，而是 TCP 为可靠释放和防止旧报文干扰而保留的过渡状态。短连接、高并发服务中大量 TIME_WAIT 可能造成端口和内核资源压力，需要从连接复用、连接模型、内核参数和负载架构等方面综合处理，不能仅靠盲目缩短等待时间。

5. TCP 如何保证可靠

TCP 可靠性来自一组机制组合：

机制 作用
序列号 标识字节位置，支持重排和去重
确认 ACK 告诉对方哪些数据已收到
超时重传 ACK 超时后重新发送
快速重传 收到重复 ACK 后提前重传
校验和 检测数据损坏
滑动窗口 控制未确认数据量

5.1 序列号与确认号

TCP 为字节流中的每个字节编号。一个 TCP 数据段的序列号通常表示该段第一个数据字节的编号。

确认号采用累计确认方式，表示接收方已经连续收到的最后一个字节之后的序号，也就是“接收方下一步期望收到的字节序号”。

例如：

  • 接收方已经按序收到序号 1000 到 1499 的字节；
  • 接收方发送 ACK = 1500；
  • 这表示序号小于 1500 的数据已经连续收到，并期待从 1500 开始的数据。

累计确认可以用一个确认号确认一段连续数据，减少确认报文数量。但如果中间发生丢包，后续数据即使已经到达，也可能只能重复确认缺失位置，除非启用 SACK 等扩展机制。

5.2 校验和

TCP 校验和用于发现首部或数据在传输过程中发生的比特错误。校验和通常还会结合 IP 层伪首部，以便检测源地址、目的地址、协议号和长度等信息是否出现异常。

校验和只能回答“收到的内容是否可能损坏”，不能解决以下问题：

  • 数据是否丢失；
  • 数据是否重复；
  • 数据是否乱序；
  • 损坏的数据如何恢复。

这些问题需要由序列号、确认和重传机制共同解决。

5.3 超时重传

发送方发送数据后，如果在规定时间内没有收到相应确认，就认为数据可能丢失并进行重传。

TCP 的重传超时时间不能固定为一个常数，而要根据网络往返时间动态估计。通常会维护：

  • SRTT：平滑后的往返时间估计；
  • RTTVAR：往返时间波动程度；
  • RTO：重传超时时间。

常见思想是：

RTO ≈ SRTT + 若干倍的 RTT 波动量

RTO 设置过短会导致网络只是暂时变慢时发生误重传；设置过长则会使真正丢包后的恢复速度变慢。发生超时后，TCP 通常会降低发送速率，并采用退避策略扩大后续等待时间。

5.4 快速重传

如果某个数据段丢失，但后续数据段已经到达接收方，接收方会因为缺少中间数据而反复发送相同的累计 ACK。发送方收到若干个重复 ACK 后，可以推断某个数据段很可能丢失，不必等待 RTO 到期，就提前重传该段。

经典快速重传通常以收到 3 个重复 ACK 作为触发条件。它的优点是恢复速度比超时重传快，但重复 ACK 也可能由乱序、路径变化或接收端处理方式引起，因此快速重传本质上是基于现象进行的丢包推断。

5.5 选择确认 SACK

没有 SACK 时，TCP 的累计 ACK 只能明确指出“最早缺少的连续字节位置”。启用 SACK 后，接收方可以在 ACK 中告知已经收到的其他非连续数据块，使发送方只重传真正缺失的部分。

例如：

已收到：1000~1999、3000~3999
缺少：2000~2999

SACK 能减少多丢包场景下的重复重传，提高高带宽、高延迟网络中的恢复效率。

6. 滑动窗口与流量控制

6.1 为什么需要窗口

如果每发送一个数据段就等待 ACK，再发送下一个数据段，链路利用率会很低。TCP 使用滑动窗口允许发送方在未收到确认前连续发送多个数据段，从而让网络中同时存在多个未确认字节。

窗口向前移动的条件是：

  • 新数据已经发送并得到确认；
  • 接收方通告了新的可用接收空间；
  • 发送方的拥塞窗口允许继续发送。

6.2 接收窗口 rwnd

接收窗口（Receive Window，rwnd）由接收方根据自身接收缓存剩余空间通告给发送方，用于进行流量控制。

  • 接收缓存快满时，接收方通告较小窗口，发送方应降低发送量。
  • 接收缓存没有空间时，可以通告零窗口，要求发送方暂时停止发送普通数据。
  • 应用及时读取数据，接收缓存释放后，接收方可以通过窗口更新通知发送方继续发送。

流量控制解决的是“发送方不要把接收方的缓存撑爆”。

6.3 零窗口与窗口探测

当接收方通告零窗口时，发送方不能一直被动等待，因为窗口更新报文也可能丢失。TCP 通常会使用窗口探测机制，周期性发送很小的数据或探测报文，促使接收方重新通告窗口状态。

这可以避免因窗口更新丢失导致连接永久停滞。

6.4 窗口扩大与带宽时延积

TCP 首部中的窗口字段长度有限。对于高带宽、高延迟网络，仅靠基本窗口大小可能无法充分利用链路。窗口扩大选项允许以更大的实际窗口表达能力支持更大的在途数据量。

理想情况下，为了让链路持续有数据发送，发送窗口至少应接近带宽时延积：

带宽时延积 = 链路带宽 × 往返时延

窗口过小会使发送方频繁等待 ACK；窗口足够大，才可能把链路容量充分利用起来。

7. 拥塞控制

7.1 流量控制与拥塞控制的区别

对比项 流量控制 拥塞控制
关注对象 接收方 整个网络
解决问题 防止接收缓存溢出 防止网络中的路由器和链路过载
主要依据 接收窗口 rwnd 拥塞窗口 cwnd、丢包、RTT 等
控制结果 发送方受接收能力限制 发送方受网络承载能力限制

TCP 实际允许发送的未确认数据量通常受两者共同限制：

发送窗口 = min(rwnd, cwnd)

即使接收方处理能力很强，只要网络拥塞窗口较小，发送方仍然不能无限发送；反过来，即使网络空闲，接收方窗口太小也会限制发送速率。

7.2 拥塞窗口 cwnd 与慢启动阈值 ssthresh

  • cwnd：发送方根据网络状况维护的拥塞窗口。
  • ssthresh：慢启动与拥塞避免之间的切换阈值。

cwnd 并不表示接收方真实缓存大小，而是发送方对网络可承载在途数据量的估计。

7.3 慢启动

慢启动并不意味着发送速度很慢，而是指拥塞窗口从较小值开始，并根据确认逐步扩大。

典型过程：

  • 初始 cwnd 较小；
  • 每收到一个 ACK，拥塞窗口增加一定量；
  • 在一个 RTT 内，窗口规模大致呈指数增长；
  • 当 cwnd 达到 ssthresh，或检测到拥塞时，退出慢启动阶段。

慢启动能够让连接在不了解网络容量的初始阶段逐步探测可用带宽，降低一开始就大量发送造成拥塞的风险。

7.4 拥塞避免

达到 ssthresh 后，TCP 通常进入拥塞避免阶段。此时拥塞窗口增长速度明显变慢，经典算法中大致表现为每经过一个 RTT 增加一个 MSS 左右，近似线性增长。

慢启动阶段可以概括为“指数探测”，拥塞避免阶段则是“线性探测”。实际现代 TCP 实现可能采用 CUBIC、BBR 等不同算法，具体增长曲线不完全相同。

7.5 丢包时的处理

经典 TCP 通常把丢包视为网络拥塞的重要信号，但不同丢包现象对应的处理方式不同。

超时丢包

超时通常说明网络状况更严重，经典处理一般包括：

  1. 将 ssthresh 调低，常见做法是设置为当前拥塞窗口的一部分；
  2. 将 cwnd 降低到较小值；
  3. 重新进入慢启动；
  4. 超时时间采用退避方式逐渐增大。

快速重传触发的丢包

收到多个重复 ACK 表明后续数据仍能到达，网络可能并未完全失效，因此经典 TCP 通常进行较温和的窗口调整，并进入快速恢复阶段，而不是完全退回最初的慢启动状态。

7.6 快速恢复

快速恢复的目标是利用重复 ACK 说明网络仍在传输数据这一信息，在重传丢失段的同时尽量保持一定发送能力。

典型思路是：

  • 适当降低 ssthresh；
  • 重传疑似丢失的数据段；
  • 暂时调整 cwnd，反映重复 ACK 表示仍有数据离开网络；
  • 收到新的累计 ACK 后退出快速恢复，进入拥塞避免。

不同 TCP 版本和实现的具体细节可能不同，面试中应区分“经典 TCP Reno 的概念流程”和现代内核中实际使用的算法。

7.7 AIMD 思想

经典拥塞控制常用 AIMD（Additive Increase Multiplicative Decrease，加性增大、乘性减小）：

  • 没有检测到拥塞时，窗口缓慢增加；
  • 检测到拥塞时，窗口按比例明显下降。

这种策略有助于多个 TCP 连接在共享网络资源时逐步趋于相对公平，但它不是所有现代 TCP 拥塞控制算法的完整描述。

7.8 现代拥塞控制算法

常见算法包括：

  • Reno：基于慢启动、拥塞避免、快速重传和快速恢复的经典方案。
  • CUBIC：通过立方函数调整拥塞窗口，适合高带宽或高延迟网络，许多系统中作为常见默认算法。
  • BBR：主要根据带宽和 RTT 建模网络状态，不完全依赖传统丢包信号判断拥塞。

因此，“TCP 通过丢包进行拥塞控制”是经典 TCP 的重要总结，但不能简单概括所有现代 TCP 实现。

8. TCP 连接状态

常见 TCP 状态及含义如下：

状态 含义
LISTEN 服务端等待连接请求
SYN-SENT 已发送 SYN，等待对端响应
SYN-RECEIVED 已收到 SYN 并发送 SYN+ACK，等待最终 ACK
ESTABLISHED 连接已建立，可以双向传输数据
FIN-WAIT-1 已发送 FIN，等待 ACK 或对端 FIN
FIN-WAIT-2 自己的 FIN 已被确认，等待对端 FIN
CLOSE-WAIT 已收到对端 FIN，等待本地应用关闭
CLOSING 双方几乎同时发送 FIN，等待确认
LAST-ACK 被动关闭方发送 FIN，等待最终 ACK
TIME-WAIT 主动关闭方等待旧报文消失并保证 ACK 可重传
CLOSED 连接不存在

CLOSE-WAIT 长时间堆积通常表示本地应用收到对端关闭通知后，没有及时关闭自己的连接；TIME-WAIT 较多则常见于主动关闭连接较多的服务端或客户端。排查时要结合连接方向、业务模型和系统资源判断，不能只看到状态数量就直接认定为故障。

9. TCP 粘包与拆包

9.1 问题本质

TCP 提供的是连续字节流，不提供应用层消息边界，因此可能出现：

  • 一次发送的数据被拆成多次接收；
  • 多次发送的数据被一次接收合并；
  • 一部分消息与下一部分消息合并到同一个读取结果中。

这通常被称为“粘包和拆包”，本质上不是 TCP 传输错误，而是应用层没有定义或正确解析消息边界。

9.2 解决方法

应用协议需要明确一条消息如何结束，常见方案包括：

  1. 固定长度：每条消息都占用固定字节数。
  2. 长度前缀：先发送消息长度，再发送指定长度的消息体。
  3. 分隔符：使用换行符、特殊字节序列等作为消息结束标记。
  4. 自描述格式：使用带长度或边界信息的序列化协议。

接收端不能假设“一次 read 就是一条完整消息”，而应维护缓冲区，循环读取并按照协议解析完整帧。

11. 常见问题辨析

11.1 TCP 的可靠性是否意味着绝对不丢数据

不是。TCP 只能通过确认、重传、校验等机制在连接有效期间尽力提供可靠字节流。如果连接最终失败、达到重传上限或对端不可达，TCP 仍会向应用报告错误。可靠性是协议提供的服务语义，不代表网络中每个报文都一定不丢失。

11.2 TCP 为什么还需要校验和，链路层不是已经校验了吗

不同网络设备、链路和中间处理过程可能存在错误，链路层校验通常只覆盖某一段链路，而 TCP 校验可以在端到端范围内检查传输内容。端到端校验是对下层校验的补充，而不是完全重复。

11.3 收到 ACK 是否说明数据已经被应用读取

通常不意味着应用已经读取。ACK 主要表示 TCP 接收端已经接收并确认了相应数据，数据可能仍然位于内核接收缓存中，尚未被应用程序读取。

11.4 TCP 能否保证低延迟

TCP 的首要目标是可靠、有序传输，并不保证低延迟。丢包重传、按序交付和拥塞控制都可能增加延迟。对实时性特别敏感的应用可能使用 UDP，并在应用层自行决定是否丢弃过期数据；也可能使用基于 UDP 的 QUIC 等协议。

11.5 为什么连接建立后还可能收到旧报文

网络中的报文可能因为排队、重传或路径变化而延迟到达。TCP 使用序列号、确认号、连接状态和 TIME_WAIT 等机制识别过期或不属于当前连接的数据，避免旧报文直接破坏新的通信状态。

11.6 TCP 如何处理乱序数据

接收方可以暂存已经到达但位于缺口之后的数据，并继续向发送方发送累计 ACK 或携带 SACK 信息。只有当缺失的前置数据到达后，TCP 才会按序向应用交付连续字节。若乱序持续存在，可能导致接收缓存占用增加和应用层读取停顿。

12. 一次 TCP 数据传输的完整过程

下面以“客户端 A 已经与服务端 B 建立 TCP 连接，A 向 B 发送一段应用数据”为例，串联 TCP 从应用写入、分段发送、确认重传，到应用读取和连接关闭的完整过程。

需要先明确两点：

  1. TCP 是全双工字节流协议。A→B 和 B→A 各自拥有独立的序列号空间、发送缓冲区和接收缓冲区，两个方向可以同时传输。
  2. TCP 连接已经通过三次握手建立。握手不仅确认双方具备收发能力，还交换了初始序列号、MSS、窗口扩大、SACK 是否允许、时间戳等参数。

12.1 应用把数据写入 TCP 发送缓冲区

应用程序通过 socket 调用 send、write 等接口，将数据交给操作系统内核中的 TCP 模块。

应用程序
   │  send/write
   ▼
Socket 发送缓冲区
   │
   ▼
TCP 协议栈

此时需要注意：

  • send 成功通常只表示数据已经被复制到本机内核的发送缓冲区，并不表示数据已经到达对端，更不表示对端应用已经处理完毕。
  • 如果发送缓冲区空间不足，阻塞 socket 的写操作可能等待；非阻塞 socket 则可能只写入一部分数据，或者返回“暂时不可写”。
  • TCP 只把应用写入的内容看作连续字节流，不记录每次 send 的边界。连续两次写入的数据可能被合并发送，一次写入的数据也可能被拆成多个 TCP 报文段。
  • 应用若需要识别一条完整消息，必须自行使用固定长度、长度前缀、分隔符等方式定义消息边界。

12.2 TCP 为字节流编号并划分报文段

TCP 会为字节流中的每个字节分配序列号。某个 TCP 报文段首部中的 Sequence Number，表示该报文段第一个数据字节的序号。

假设 A 在三次握手中选择的初始序列号为 1000。由于 SYN 会占用一个序列号，所以 A 发送的第一个应用数据字节通常从 1001 开始编号。

TCP 会综合以下因素决定每个报文段携带多少数据：

  • MSS（Maximum Segment Size）：单个 TCP 报文段通常允许携带的最大 TCP 数据长度；
  • 路径 MTU：链路能够承载的 IP 数据报大小；
  • 当前发送窗口与拥塞窗口；
  • 发送缓冲区中的待发送数据量；
  • Nagle 算法、TCP_NODELAY、TCP 分段卸载等实现和性能优化机制。

MSS 只计算 TCP 数据部分，不包含 TCP 首部和 IP 首部。以常见的以太网 MTU 1500 字节、IPv4 首部 20 字节、TCP 基本首部 20 字节为例：

MSS ≈ 1500 - 20 - 20 = 1460 字节

如果应用写入 4000 字节，TCP 在不考虑选项和硬件卸载的简化情况下，可能将其组织成 1460 + 1460 + 1080 三个数据段。分段方式是 TCP 的内部实现细节，应用不能依赖它来判断消息边界。

12.3 TCP 判断当前可以发送多少数据

发送方不能仅因为发送缓冲区中有数据就无限发送。它同时受接收方处理能力和网络承载能力约束。

  • rwnd：接收方通告的接收窗口，用于流量控制；
  • cwnd：发送方维护的拥塞窗口，用于拥塞控制；
  • FlightSize：已经发送但尚未被确认的在途数据量。

发送方允许存在的未确认数据量大致满足：

FlightSize ≤ min(rwnd, cwnd)

因而当前还能继续发送的数据量可以粗略理解为：

可发送量 = min(rwnd, cwnd) - 已发送但未确认的数据量

发送端还会维护几个重要位置：

  • SND.UNA：最早尚未被确认的字节序号；
  • SND.NXT：下一个准备发送的字节序号；
  • 两者之间通常对应已经发送但尚未被累计确认的数据。

如果 rwnd 很小，说明接收方缓存紧张；如果 cwnd 很小，说明发送方判断网络当前无法安全承载更多在途数据。两者中更小的一个构成实际限制。

12.4 TCP 报文段被封装并进入网络

TCP 为数据添加首部，主要包括：

  • 源端口和目的端口；
  • 序列号和确认号；
  • ACK、PSH 等标志位；
  • 接收窗口；
  • 校验和；
  • 时间戳、SACK 等可选字段。

TCP 校验和会覆盖 TCP 首部、TCP 数据以及由 IP 层部分字段组成的伪首部。TCP 报文段随后被交给 IP 层，封装为 IP 数据报，再由数据链路层封装成帧并发送。

应用数据
  → TCP 报文段
  → IP 数据报
  → 数据链路层帧
  → 物理信号

沿途路由器主要根据 IP 地址转发数据报，并不替 TCP 完成端到端的确认与重传。数据可能因为拥塞、链路错误、路由变化等原因发生丢失、重复、延迟或乱序。

12.5 接收端校验、去重和重排数据

B 收到数据后，数据从网卡逐层向上传递。IP 层确认数据属于本机后，将 TCP 报文段交给 TCP 模块；TCP 再根据源 IP、源端口、目的 IP、目的端口组成的四元组找到对应连接。

TCP 首先检查报文段是否合法，包括连接状态、序列号范围和校验和等。随后根据序列号处理数据：

  1. 数据正好是当前期望的字节：将数据加入接收缓冲区，并推进连续接收位置。
  2. 数据重复：识别为已经接收过的数据，不会把同一批字节重复交给应用，但通常仍会回复 ACK。
  3. 数据乱序到达：可以暂存在乱序队列中，同时继续确认当前连续数据的末尾；缺口补齐后，再把连续数据合并起来。
  4. 数据校验失败：通常直接丢弃，由发送方通过超时或其他丢包信号触发重传。
  5. 数据超出当前接收窗口：通常不会作为有效的新数据正常接收。

TCP 向应用提供的是按序字节流。即使后面的数据已经到达，只要前面仍有缺口，后面的字节通常也不能越过缺口先交付给应用，这会形成传输层的队头阻塞。

12.6 接收端生成 ACK 和接收窗口

接收端通过 ACK 告诉发送端自己已经连续收到哪些字节。TCP 使用累计确认：

ACK = N

表示序号小于 N 的字节已经连续收到，下一步期望收到序号为 N 的字节。

例如，B 已经连续收到序号 1001～1500 的 500 个字节，就会发送：

ACK = 1501

ACK 并不一定对每个报文段立即单独发送：

  • 接收端可能使用延迟确认，在较短时间内等待更多数据；
  • 如果 B 同时有数据发给 A，可以把 ACK 搭载在反向数据段中；
  • 如果发现乱序或缺口，B 可能立即发送重复 ACK；
  • 启用 SACK 后，ACK 选项还可以描述已经收到的非连续数据块。

ACK 中的窗口字段会通告当前 rwnd。它通常与接收缓冲区剩余空间有关：应用读取越及时，空闲空间越多；应用处理过慢，窗口就可能逐渐缩小，甚至降为零。

需要特别区分：

收到 TCP ACK，通常只说明数据已经到达对方 TCP 协议栈并被接收，不代表对方应用已经调用 read，更不代表业务处理已经成功。

如果业务必须确认“订单已经落库”或“消息已经处理”，还需要应用层响应，不能只依赖 TCP ACK。

12.7 发送端收到 ACK 后推进窗口

A 收到有效的新 ACK 后，通常会执行以下操作：

  1. 将已确认数据从重传队列中移除；
  2. 推进 SND.UNA，释放发送缓冲区空间；
  3. 唤醒可能因发送缓冲区已满而等待的应用；
  4. 根据符合条件的 RTT 样本更新 SRTT、RTTVAR 和 RTO；
  5. 读取 ACK 中的新接收窗口，更新对端 rwnd；
  6. 根据当前拥塞控制算法调整 cwnd；
  7. 如果窗口仍有空间，继续发送发送缓冲区中的后续数据。

ACK 不只是“确认收到了”，还是滑动发送窗口、估计网络时延和调整发送速率的重要反馈信号。

12.8 丢包、乱序与重传如何发生

情况一：数据段丢失，但后续数据到达

假设 B 正在等待序号 1501，但包含 1501 开始的数据段丢失，后面从 1801 开始的数据却到达了。由于连续字节流仍存在缺口，B 会继续返回：

ACK = 1501

多个相同的 ACK 会形成重复 ACK。发送端收到足够多的重复 ACK 后，可以执行快速重传，在 RTO 到期前重传缺失数据。若启用了 SACK，接收端还能告诉发送端哪些后续区间已经收到，使发送端更准确地只重传缺失部分。

情况二：数据段丢失，且没有足够的后续数据

如果没有足够的重复 ACK 触发快速重传，发送端会等待重传计时器。当 RTO 到期时，发送端重新发送最早未确认的数据，并通常认为网络出现了较严重的拥塞：

  • 降低 cwnd；
  • 调低 ssthresh；
  • 对后续 RTO 使用指数退避；
  • 按所使用的拥塞控制算法重新探测网络容量。

情况三：ACK 丢失

ACK 丢失不一定会导致数据重传。由于 TCP 使用累计确认，后续更大的 ACK 可能一并确认前面的数据。只有在发送端长时间收不到能够覆盖该数据的确认时，才可能因超时而重传。

情况四：重传后原报文又到达

网络中的原报文可能只是严重延迟，并未真正丢失。接收端通过序列号识别重复数据，不会将同一字节重复交给应用，但可以再次发送 ACK，帮助发送端确认当前接收进度。

无论是原始发送还是重传，同一批字节在逻辑上使用相同的字节序号。重传解决的是“这些位置的数据尚未被确认”，而不是创建一批新的应用数据。

12.9 接收应用从缓冲区读取数据

当连续数据进入 B 的 TCP 接收缓冲区后，B 的应用程序可以通过 recv、read 等接口读取。

一次读取返回多少字节，取决于：

  • 当前接收缓冲区中有多少可交付数据；
  • 应用提供的缓冲区大小；
  • socket 是阻塞还是非阻塞；
  • 是否设置超时以及具体操作系统行为。

因此，发送端的一次 send 与接收端的一次 read 没有一一对应关系。接收端必须维护应用层缓冲区，并按照自己的协议反复解析完整消息。

应用读取数据后，内核接收缓冲区释放空间，接收端可以通告更大的 rwnd。如果此前通告过零窗口，还会通过窗口更新或响应窗口探测恢复传输。

12.10 一个带序列号的完整例子

假设 A 的第一个应用数据字节序号是 1001，A 依次发送三段数据：

报文段 1：seq = 1001，len = 500，覆盖 [1001, 1501)
报文段 2：seq = 1501，len = 300，覆盖 [1501, 1801)
报文段 3：seq = 1801，len = 200，覆盖 [1801, 2001)

正常情况下：

A                                              B
| -- seq=1001, len=500 ----------------------> |
| <-------------------------------- ACK=1501 -- |
| -- seq=1501, len=300 ----------------------> |
| <-------------------------------- ACK=1801 -- |
| -- seq=1801, len=200 ----------------------> |
| <-------------------------------- ACK=2001 -- |

如果报文段 2 丢失、报文段 3 到达：

A                                              B
| -- seq=1001, len=500 ----------------------> |
| <-------------------------------- ACK=1501 -- |
| -- seq=1501, len=300 --------X               |  丢失
| -- seq=1801, len=200 ----------------------> |  乱序到达
| <-------------------------------- ACK=1501 -- |  仍期待 1501
| -- 重传 seq=1501, len=300 -----------------> |
| <-------------------------------- ACK=2001 -- |  缺口补齐，累计确认

若启用 SACK，B 在重复确认 ACK=1501 的同时，还可以说明 [1801, 2001) 已收到。报文段 2 重传到达后，接收数据成为连续区间，B 就能用 ACK=2001 一次性累计确认全部 1000 个字节。

12.11 双向通信中的确认与数据

TCP 是全双工的，因此 B 不仅能确认 A 的数据，也能同时向 A 发送自己的数据。一个 TCP 报文段可以既携带 B→A 的应用数据，又通过 ACK 字段确认 A→B 的数据。

两个方向的序列号不能混为一谈：

A → B：使用 A 的序列号空间，B 对其发送 ACK
B → A：使用 B 的序列号空间，A 对其发送 ACK

一端停止发送并不意味着另一端也必须停止。TCP 支持半关闭：一方发送 FIN 关闭自己的发送方向后，仍然可以继续接收另一方的数据。

12.12 数据发送完毕后的连接释放

当应用调用 close 或执行半关闭时，TCP 通常会先处理发送缓冲区中已经排队的数据，然后发送 FIN，表示该方向以后不再有新的字节发送。

正常关闭大致经历：

  1. 主动关闭方发送 FIN；
  2. 被动关闭方确认该 FIN，此时仍可继续发送剩余数据；
  3. 被动关闭方完成发送后，也发送 FIN；
  4. 主动关闭方回复最后一个 ACK，并进入 TIME_WAIT；
  5. 等待足够时间后释放连接状态。

FIN 与 SYN 一样会占用一个序列号。接收端只有在 FIN 之前的所有字节都按序处理后，才会向应用表现出完整的流结束；应用读取接口通常在剩余数据读完后返回 0，表示对端进行了正常关闭。

如果发生协议错误、访问一个不存在的连接、应用异常终止或使用复位方式关闭，连接也可能通过 RST 被立即终止。RST 与 FIN 的语义不同：FIN 表示有序结束字节流，RST 通常表示连接被异常复位，尚未处理的数据可能丢失。

12.13 全流程总览

应用调用 send/write
        ↓
数据复制到本机 TCP 发送缓冲区
        ↓
为字节编号，并根据 MSS、窗口等条件组织报文段
        ↓
受 min(rwnd, cwnd) 限制，将允许的数据发送到网络
        ↓
接收端校验、去重、重排并放入接收缓冲区
        ↓
接收端返回累计 ACK、可选 SACK 和新的 rwnd
        ↓
发送端推进窗口，更新 RTT、RTO 和 cwnd
        ↓
发现重复 ACK、SACK 缺口或超时后重传缺失数据
        ↓
接收应用按应用层协议读取并恢复消息边界
        ↓
双方发送 FIN/ACK，完成半关闭或完整连接释放

可以把各机制的职责概括为：

序列号：定位字节、重排和去重
ACK：确认连续接收进度
SACK：描述非连续的已接收区间
校验和：发现传输损坏
重传：恢复可能丢失的数据
滑动窗口：允许多个未确认数据同时在途
rwnd：保护接收方，防止接收缓存溢出
cwnd：保护网络，控制在途数据规模
RTT/RTO：决定超时判断与重传时机
应用层协议：在 TCP 字节流上恢复业务消息边界
TCP 状态机：管理建立、传输、半关闭和释放过程

面试时尤其要强调三个容易混淆的结论：

  1. send 成功不等于数据已经到达对端；
  2. 收到 TCP ACK 不等于对端应用已经读取或处理成功；
  3. 一次 send 不对应一次 read，消息边界必须由应用层协议定义。

## 14. 总结

传输层的核心是提供进程之间的通信服务。UDP 以低开销、无连接和数据报形式为代价，放弃了标准化的可靠传输、流量控制和拥塞控制；TCP 则通过连接管理、序列号、累计确认、超时重传、快速重传、滑动窗口、流量控制和拥塞控制，为应用提供可靠有序的字节流。

理解 TCP 时可以按以下主线组织：

```text
端口实现进程寻址
  → 三次握手建立连接
  → 序列号和 ACK 组织字节流
  → 重传与校验实现可靠性
  → 滑动窗口提高传输效率
  → rwnd 实现流量控制
  → cwnd 实现拥塞控制
  → 四次挥手与 TIME_WAIT 释放连接

在实际问题中，应先判断问题属于哪一层：

  • 数据损坏：优先看校验和；
  • 丢包或乱序：看序列号、ACK、重传和 SACK；
  • 接收端处理不过来：看 rwnd 和流量控制；
  • 网络本身拥塞：看 cwnd 和拥塞控制；
  • 消息边界错误：看应用层协议，而不是把问题归咎于 TCP。
