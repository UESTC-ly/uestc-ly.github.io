Git 和分支协作

学习目标

  • 理解工作区、暂存区、本地仓库、远端仓库之间的关系。
  • 能用分支、提交、变基或合并完成日常协作。
  • 能安全处理冲突、回滚本地错误、整理提交历史。
  • 能读懂 git status、git log、git diff 提供的证据。

核心概念

  • 工作区：你正在编辑的文件。
  • 暂存区：下一次提交将包含的快照。
  • 提交：不可变的项目快照，包含父提交、作者、时间和说明。
  • 分支：指向某个提交的可移动指针。
  • 远端：另一个仓库位置，常见名称是 origin。
  • 上游分支：本地分支默认拉取和推送的远端分支。
  • 合并：保留两个分支历史并生成合并结果。
  • 变基：把当前分支的提交重新放到新的基底上，历史更线性，但会重写提交 ID。

常用命令与示例

查看状态。风险低，只读命令。

git status

查看未暂存改动。风险低，只读命令。

git diff

查看已暂存改动。风险低，只读命令。

git diff --staged

创建并切换分支。会改变当前 HEAD 和工作分支；运行前确认没有未保存的重要改动。

git switch -c feature/login-rate-limit

暂存指定文件。会改变暂存区，不会改变文件内容。

git add src/rate_limit.cpp tests/rate_limit_test.cpp

提交。会在本地仓库生成新提交；提交信息应说明“为什么改”和“影响什么”。

git commit -m "Add login rate limiting"

拉取远端更新并变基。会重放本地提交，可能产生冲突；不要对已经被他人基于的共享提交随意变基。

git fetch origin
git rebase origin/main

推送当前分支并设置上游。会写入远端仓库；推送前确认分支名和提交内容。

git push -u origin feature/login-rate-limit

撤销暂存。只影响暂存区，不删除工作区改动。

git restore --staged src/rate_limit.cpp

丢弃单个文件的工作区改动。会覆盖本地未提交内容，风险高；运行前用 git diff 确认不要这些改动。

git restore src/rate_limit.cpp

安全保存临时改动。会把当前改动放入 stash；包含未跟踪文件时要显式加 -u。

git stash push -u -m "wip before rebase"

典型工作流

  1. 从主干更新本地基线。
git switch main
git fetch origin
git pull --ff-only

风险说明：--ff-only 只允许快进，避免无意创建合并提交；如果失败，说明本地和远端历史已经分叉，需要先查清原因。

  1. 新建功能分支。
git switch -c feature/add-health-check
  1. 小步提交。
git status
git diff
git add src/health.cpp tests/health_test.cpp
git commit -m "Add health check endpoint"
  1. 同步主干并处理冲突。
git fetch origin
git rebase origin/main

如果冲突出现，Git 会停止在冲突提交处。解决文件里的冲突标记后执行：

git add src/health.cpp
git rebase --continue
  1. 推送并发起评审。
git push -u origin feature/add-health-check

常见坑

  • 把生成文件、密钥、日志、大型二进制文件提交进仓库。
  • 在未确认差异时运行 git restore、git clean、reset --hard 等丢弃类命令。
  • 对已推送且被别人基于的分支强推，导致协作者历史失效。
  • 把巨大、不相关改动混入同一个提交，评审和回滚都会变困难。
  • 冲突解决后没有重新运行测试，只确认了文本能合并。
  • 误以为 git pull 永远安全；它可能执行 merge 或 rebase，取决于配置。

排障步骤

  1. 先确认当前位置和分支。
git status
git branch --show-current
  1. 看本地分支和上游分支的分叉情况。
git branch -vv
git log --oneline --graph --decorate --all -20
  1. 找出某个文件是谁改的。
git blame src/health.cpp
git log --follow -- src/health.cpp
  1. 回到 rebase 或 merge 前的状态。风险中等，会改变当前操作状态；只在你确认要放弃当前合并或变基时使用。
git rebase --abort
git merge --abort
  1. 推送被拒绝时，不要立刻强推。先获取远端再检查差异。
git fetch origin
git log --oneline --left-right HEAD...@{upstream}

练习

  • 建一个临时仓库，完成初始化、首次提交、新建分支、合并分支。
  • 故意在两个分支修改同一行，练习冲突解决和 git merge --abort。
  • 用 git rebase -i 合并两个本地提交；只在未共享的练习分支上做。
  • 写一个 .gitignore，忽略构建目录、日志、虚拟环境和编辑器缓存。

检查清单

  • 我能解释工作区、暂存区、本地提交和远端分支的区别。
  • 我能在提交前用 git diff 和 git diff --staged 审查改动。
  • 我知道哪些命令会丢弃本地改动，并会先备份或确认差异。
  • 我能处理一次简单冲突并继续 rebase 或 merge。
  • 我不会对共享历史随意强推。

深化学习说明

前半部分是日常速查：先帮助你识别对象、命令和常见流程。下面的内容是原理、实验和排障深化，用来把“会用命令”推进到“能解释命令影响、能在异常状态下恢复”。

前置知识和完成标准

学习本章前，最好已经能在终端中进入目录、查看文件、编辑文本，并理解“本地文件”和“远端服务”的区别。Git 不是网盘同步工具，而是内容寻址的版本数据库；它关心的是一次次快照之间的关系。

完成本章后，应能做到：

  • 面对一个陌生仓库，先用 git status、git branch -vv、git log --oneline --graph --decorate --all -20 判断当前状态。
  • 提交前能分别解释“工作区差异”和“暂存区差异”。
  • 能在本地练习仓库中完成一次冲突制造、冲突解决、继续合并或变基、验证结果。
  • 知道 restore、reset、clean、push --force 这类命令的风险边界，并在生产仓库中先备份或询问维护者约定。

核心概念分层

第一层是文件状态：未跟踪、已修改、已暂存、已提交。git status 看到的是文件相对索引和 HEAD 的状态，不等于“远端是否有新代码”。

第二层是提交图：每个提交指向父提交，分支名只是指向某个提交的标签。切换分支本质上是让 HEAD 指向另一个分支，并把工作区更新成该提交的快照。

第三层是协作关系：本地分支和上游分支通过 fetch/push 交换提交对象。git fetch 只更新远端跟踪分支，不改工作区；git pull 是 fetch 后再 merge 或 rebase，行为取决于配置。

第四层是历史改写：rebase、commit --amend、reset 会生成或移动提交关系。它适合整理尚未共享的个人分支，不适合随意改写多人已经基于的公共历史。

从零开始实验：制造并解决一次冲突

教学边界：以下命令在系统临时目录下创建唯一练习仓库，不用于生产仓库。生产分支发生冲突时，应先确认团队合并策略和 CI 要求。

lab_dir="$(mktemp -d "${TMPDIR:-/tmp}/git-conflict-lab.XXXXXX")"
cd "$lab_dir"
git init -b main
git config user.name "Lab User"
git config user.email "lab@example.com"
printf "mode=dev\n" > app.conf
git add app.conf
git commit -m "Initial config"

git switch -c feature-a
printf "mode=feature-a\n" > app.conf
git commit -am "Change mode in feature A"

git switch main
git switch -c feature-b
printf "mode=feature-b\n" > app.conf
git commit -am "Change mode in feature B"

git merge feature-a

预期结果：最后一步会报告 CONFLICT，app.conf 中出现 <<<<<<<、=======、>>>>>>>。这是 Git 告诉你“同一祖先行被两个分支改成了不同结果”，它不会猜测业务上哪个正确。

解决方式：

printf "mode=feature-a-and-b\n" > app.conf
git add app.conf
git merge --continue
git log --oneline --graph --decorate --all -5

验证方式：git status 应显示工作区干净，git log --graph 能看到一次合并提交。若你决定放弃本次合并，使用 git merge --abort；它会回到合并开始前的状态，但不会替你保存合并过程中额外手工创建的新文件。

命令逐段解释

git fetch origin
git rebase origin/main

git fetch origin 从名为 origin 的远端下载新对象，并更新 origin/main 等远端跟踪分支。它不改变当前分支文件。git rebase origin/main 把当前分支中“不在 origin/main 上的提交”逐个重新应用到 origin/main 之后，因此新提交 ID 会变化。

git push --force-with-lease origin feature/login-rate-limit

这是有风险的远端写入命令，只适合你明确要更新自己分支的已推送历史时使用。--force-with-lease 会先检查远端分支是否仍是你上次看到的状态；如果别人已经推送了新提交，它会拒绝覆盖。不要用普通 --force 覆盖共享分支。

git restore --staged src/rate_limit.cpp
git restore src/rate_limit.cpp

第一行只把文件从暂存区拿出来，工作区内容仍保留。第二行会把工作区文件恢复到 HEAD 中的版本，未提交修改会丢失。生产仓库执行第二行前，应先用 git diff -- src/rate_limit.cpp 确认差异不需要。

常见坑的机制和排障决策路径

遇到“我不知道现在仓库发生了什么”，先不要继续提交或回滚，按下面路径缩小问题：

  1. git status 是否显示正在 merge/rebase/cherry-pick？如果是，先完成、跳过或 abort 当前操作。
  2. git branch -vv 是否显示当前分支落后或领先上游？领先代表本地有未推送提交，落后代表远端有新提交。
  3. git diff 和 git diff --staged 是否还有未提交内容？有就先决定提交、暂存、stash 或丢弃。
  4. git log --oneline --left-right HEAD...@{upstream} 是否显示双方都有提交？双方都有提交说明历史分叉，需要 merge/rebase，而不是强推。
  5. 若冲突反复出现，找共同祖先和相关提交：git merge-base HEAD @{upstream}、git log --follow -- path。

失败现象和含义：

  • non-fast-forward：远端包含本地没有的提交，直接推送会丢历史。
  • You have not concluded your merge：上一次合并未完成，索引仍有冲突状态。
  • would be overwritten by checkout：切换分支会覆盖当前未提交改动，需要先提交、stash 或清理。
  • detached HEAD：HEAD 直接指向提交，不在分支名上；可用 git switch -c rescue-branch 保存当前位置。

练习答案要点

基础练习：初始化仓库后至少应看到一次提交。

git init -b main
printf "hello\n" > README.md
git add README.md
git commit -m "Initial commit"
git log --oneline -1

进阶练习：冲突解决不是删除标记这么简单，答案必须说明最终保留哪一方或如何合并两方语义，并运行相关测试或最小验证命令。

综合练习：交付一个评审友好的分支应包含清晰提交、干净工作区、已同步主干、测试结果和可解释的风险说明。答案要点包括 git status 干净、git log --oneline @{upstream}..HEAD 只包含本次任务提交、git diff origin/main...HEAD 没有无关文件。

章节小结

Git 的核心不是背命令，而是理解“快照、指针、索引、远端跟踪分支”之间的关系。任何危险操作前，先问三个问题：它会移动哪个指针、会改哪个文件状态、是否会覆盖别人已经看见的历史。
