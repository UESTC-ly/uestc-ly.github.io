学习目标

  • 理解内存池、对象池、连接池的适用边界。
  • 掌握吞吐、延迟、并发、错误率和资源占用等指标。
  • 能设计基准测试和压测，避免错误结论。
  • 会使用 perf、火焰图和 sanitizer 定位常见问题。

核心原理

资源池的适用边界

资源池不是默认优化，它适合“创建昂贵、可复用、生命周期可控”的资源。

资源池 适用 风险
内存池 大量固定大小对象、频繁分配释放 内存滞留、碎片、越界更难发现
对象池 初始化昂贵、状态可重置对象 脏状态复用、并发安全
连接池 数据库/RPC 连接复用 连接泄漏、队头阻塞、过期连接

不要为了“看起来高性能”过早引入池。现代 allocator、内核和框架已经很强，先测量再优化。

池化解决的是容量控制

连接池最重要的作用是限制并发访问下游，而不只是复用连接。池太小会让请求排队，池太大会把数据库或 RPC 服务打满。对象池和内存池也类似：它们减少创建/销毁成本，但会引入重置状态、生命周期归还和容量上限问题。

池化资源要定义：

  • acquire 超时；
  • release 时健康检查；
  • 最大空闲时间和最大生命周期；
  • 请求取消后如何归还或丢弃；
  • 池关闭时等待、取消还是强制释放。

性能指标

核心指标：

  • QPS/TPS：吞吐。
  • latency：平均、P50、P95、P99、最大值。
  • concurrency：同时在途请求数。
  • error rate：超时、连接错误、协议错误、业务错误。
  • CPU：user/sys、上下文切换、软中断。
  • memory：RSS、分配速率、峰值。
  • network：带宽、包量、重传。

只看平均延迟会掩盖长尾。网络服务更关注 P95/P99。

指标之间的约束

吞吐、延迟和并发由 Little's Law 近似关联：在稳定系统里，在途请求数约等于吞吐乘以平均响应时间。压测时如果并发固定，延迟上升会限制可达到吞吐；如果继续加并发，系统可能进入队列积压，P99 和错误率先恶化。

不要只看 QPS 峰值。一个可上线的结果需要同时给出吞吐、P95/P99、错误率、CPU、内存、连接数和下游负载。

基准与压测

基准测试关注单点能力，压测关注系统在真实流量下的容量和退化方式。

基本要求：

  • 明确目标：测吞吐上限、延迟、容量还是稳定性。
  • 固定环境：CPU、内核参数、编译选项、日志级别。
  • 预热：避免冷启动影响。
  • 逐步加压：观察拐点。
  • 记录错误率：不要只看成功请求。
  • 区分客户端瓶颈和服务端瓶颈。

压测方法

压测前先确认客户端机器是否足够强，网络是否可能成为瓶颈，连接复用模式是否符合线上。压测时逐级加压，记录拐点：延迟明显上升、错误开始出现、CPU 接近满、队列增长或下游饱和。容量结论只对相同代码、配置、机器、内核和流量模型近似成立。

火焰图与 perf

perf 可采样 CPU 调用栈，火焰图把热点可视化。典型流程：

perf record -> perf script -> flamegraph -> inspect hot paths

看火焰图时：

  • 宽度代表采样占比，不代表单次调用耗时。
  • 先找意外热点，例如日志格式化、锁竞争、内存分配。
  • 优化前后用同一压测条件对比。

sanitizer

常用 sanitizer：

  • AddressSanitizer：越界、use-after-free。
  • UndefinedBehaviorSanitizer：未定义行为。
  • ThreadSanitizer：数据竞争。
  • LeakSanitizer：内存泄漏。

sanitizer 适合测试和预发，不适合直接代表生产性能。

perf 与火焰图边界

perf 采样看到的是 CPU 上正在运行的栈；如果线程大部分时间在等待网络、磁盘或锁，火焰图可能看不到真正等待原因。此时要结合 off-CPU 分析、线程状态、队列耗时和 trace。优化 CPU 热点前，先确认它位于关键请求路径，而不是压测工具、日志或调试开关制造的热点。

常见性能陷阱

  • IO 线程做阻塞数据库/RPC 调用。
  • 日志同步刷盘或高频格式化。
  • 每个请求创建线程。
  • 输出缓冲区无限增长。
  • 小包过多，没有批量发送策略。
  • 锁粒度过粗，所有连接共享一把锁。
  • 内存频繁分配，且对象跨线程释放造成缓存抖动。
  • 压测客户端先达到瓶颈，却误判服务端性能。

工程实践/示例

连接池伪代码

class ConnectionPool {
public:
    PooledConn acquire(Deadline deadline) {
        while (!deadline.expired()) {
            if (auto c = tryPopIdle()) return PooledConn(std::move(c), this);
            if (total_ < max_) return PooledConn(create(), this);
            waitForReturn(deadline.remaining());
        }
        throw Timeout{};
    }

    void release(Connection c) {
        if (!c.healthy() || c.expired()) {
            close(c);
            --total_;
            return;
        }
        pushIdle(std::move(c));
    }
};

关键点：连接池要处理健康检查、过期、最大连接数、等待超时和归还。

acquire/release 错误路径

连接池 acquire 超时应返回明确错误，调用方不能继续假装请求已提交。release 发现连接不健康时应减少总数并关闭连接，而不是放回 idle 队列。池关闭后新 acquire 应失败，已借出的连接归还时直接关闭。

请求被取消时，如果连接上仍有未读响应或未完成查询，不能简单归还给下一个请求；应先取消底层操作、读到协议边界，或丢弃连接。

性能优化顺序

  1. 复现瓶颈。
  2. 采集指标和 profile。
  3. 找到最大热点或资源上限。
  4. 做最小改动。
  5. 同条件复测。
  6. 记录结论和副作用。

故障排查/观测

定位性能瓶颈

按资源分类看：CPU 满看 perf 和锁竞争；内存涨看分配速率、连接缓冲区和池容量；sys CPU 高看系统调用频率、小包和拷贝；网络差看重传、带宽、窗口和负载均衡；下游慢看连接池等待和 RPC/SQL trace。

优化报告要写什么

每次优化都记录基线、改动、复测命令、指标变化和副作用。比如“QPS +20%”不足以说明问题，还要写 P99 是否变化、错误率是否变化、CPU 是否从 user 转到 sys、内存是否上升、是否牺牲了公平性或一致性。

推导示例

判断客户端瓶颈

如果服务端 CPU 只有 30%，网络未满，但压测 QPS 上不去，先看压测客户端 CPU、连接数、端口耗尽、DNS/日志开销和请求生成逻辑。可以用多台客户端、降低客户端日志、预生成 payload、复用连接来验证。只有确认客户端不是瓶颈，服务端容量结论才可信。

连接池大小估算

连接池大小要从下游可承受并发反推。假设数据库允许某业务服务总共 200 个活跃连接，线上有 10 个实例，单实例池上限就不能随意设成 100。还要预留迁移、运维和突发连接，并通过 acquire timeout 防止请求无限等待。

如何讲性能优化

先说基线和瓶颈证据，再说改动和复测。没有 profile 的优化通常只是猜测；只有 QPS 没有 P99、错误率和资源占用，也不能证明优化有效。性能结论必须绑定环境、配置和负载模型。

最小验收清单

  • 压测报告含命令、环境和配置。
  • 指标同时覆盖吞吐、延迟、错误率和资源。
  • 连接池 acquire/release 都有错误路径。
  • 优化前后使用同一负载模型复测。

常见误区

  • 没有 profile 就凭感觉优化。
  • 只跑本机 loopback 压测，直接推导线上容量。
  • QPS 提高但 P99 和错误率恶化。
  • 引入内存池后没有 sanitizer 覆盖。
  • 连接池无上限，故障时把下游打垮。

自测题

  1. 对象池为什么可能引入脏状态 bug？
  2. 为什么 P99 比平均延迟更能反映用户体验？
  3. 如何判断压测瓶颈在客户端还是服务端？
  4. 火焰图宽度代表什么？
  5. 连接池为什么必须有 acquire timeout？

实践任务

  • 给服务加入 QPS、P99、错误率和连接数指标。
  • 用 perf 采样一次 CPU 热点并生成火焰图。
  • 开启 ASan/UBSan 跑单元测试。
  • 实现一个有最大容量和超时的连接池。
