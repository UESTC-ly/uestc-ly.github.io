参考答案

1. const 和 constexpr 的区别是什么？

  • 答：const 的核心是“只读”，限制对象在语义上不能被修改；constexpr 的核心是“可作为编译期常量”，要求初始化表达式在满足条件时能在编译期求值。
  • 要点：const 不等于编译期常量，constexpr 通常既是常量，又是常量表达式候选。
  • 例子：
const int a = getValue();     // a 只读，但可能运行期才确定
constexpr int b = 2 * 3;      // b 必须能在编译期求值
  • 易混点：const 修饰“能不能改”，constexpr 修饰“能不能在编译期确定”。
  • 追问 1：const int*、int* const、const int* const 分别是什么意思？
  • 答：const int* 是“指向常量的指针”；int* const 是“常量指针”；const int* const 是“常量指针指向常量”。记忆法：const 看它修饰谁。
  • 追问 2：constexpr 函数和普通函数在编译期行为上有什么差异？
  • 答：constexpr 函数在参数、函数体都满足要求时，可以参与编译期求值；普通函数通常只能在运行期执行。

2. 左值、右值、右值引用分别是什么？

  • 答：左值通常表示“有身份、能持续存在、能取地址”的对象；右值通常表示“临时值、将亡值、可被移动的值”；右值引用 T&& 用来绑定右值，从而触发移动语义。
  • 要点：左值关注“身份”，右值关注“值本身”或“即将被销毁”。
  • 易混点：有名字的右值引用变量本身是左值，因为它一旦有了名字，就能被反复引用。
  • 追问 1：为什么“有名字的右值引用变量”本身是左值？
  • 答：因为表达式分类看的是“这个表达式有没有稳定身份”。变量一旦有名字，就有身份，所以它是左值；若想继续按右值传递，要显式 std::move(x)。
  • 追问 2：左值/右值分类和移动语义之间是什么关系？
  • 答：移动语义本质上是“看到右值时，认为资源可以被安全搬走”。所以值类别决定了编译器会优先走拷贝还是移动。

3. std::move 到底做了什么？

  • 答：std::move 本质上只是一个类型转换：把表达式转成右值引用，从而让后续代码有机会调用移动构造或移动赋值。
  • 要点：std::move 自己不移动资源，真正搬资源的是被调用的移动构造/移动赋值。
  • 例子：
std::string s = "abc";
std::string t = std::move(s); // 真正移动的是 string 的移动构造
  • 易混点：被 move 之后的对象不是“废了”，而是“有效但状态未指定”。
  • 追问 1：为什么说 std::move 本身不移动资源？
  • 答：因为它只是 static_cast<T&&> 的语义包装，本质上不做内存复制、释放或转移操作。
  • 追问 2：move 后对象还能不能用？什么叫“有效但未指定状态”？
  • 答：还能析构、赋值、重新初始化；只是不要再依赖它原来的内容，比如不要假设 std::string 仍保留原字符串值。

4. std::forward 和 std::move 的区别是什么？

  • 答：std::move 是“无条件把对象当右值”；std::forward 是“在模板转发场景里保留原值类别”。
  • 要点：包装函数、工厂函数、转发构造函数里通常用 forward，因为它不会错误地把左值强行移动掉。
  • 例子：
template <class T>
void wrapper(T&& x) {
    foo(std::forward<T>(x));
}
  • 易混点：离开模板参数推导语境，forward 往往没有意义。
  • 追问 1：什么场景必须用 forward 而不能直接用 move？
  • 答：凡是“参数可能是左值也可能是右值，而你想原样转交”的场景，都必须用 forward。
  • 追问 2：完美转发为什么依赖模板参数推导？
  • 答：因为只有在 T&& 是转发引用时，T 才能根据实参推导出左值/右值信息，forward<T> 才知道该转成左值还是右值。

5. 什么是深拷贝？什么是浅拷贝？

  • 答：浅拷贝只复制成员值；若成员里有指针，就只是复制地址。深拷贝则会重新申请资源，把内容也复制过去，让两个对象真正独立。
  • 要点：一旦类拥有堆内存、文件句柄、socket 等资源，就必须明确拷贝策略。
  • 例子：
struct A { int* p; };
// 默认拷贝会让两个对象的 p 指向同一块内存
  • 易混点：如果类里全是值成员（如 int、string、vector），默认拷贝通常就是安全的。
  • 追问 1：什么时候默认拷贝其实是安全的？
  • 答：当成员本身就遵循值语义、不会共享底层资源时，默认生成的拷贝构造和赋值往往没问题。
  • 追问 2：为什么资源类通常不能接受浅拷贝？
  • 答：因为两个对象会误以为自己都拥有同一份资源，最终容易导致重复释放、悬空指针、状态串扰。

6. 拷贝构造函数和拷贝赋值运算符有什么区别？

  • 答：拷贝构造发生在“新对象创建时”，拷贝赋值发生在“对象已经存在后再覆盖内容”。
  • 要点：T b(a);、T b = a; 都是拷贝构造；b = a; 才是拷贝赋值。
  • 易混点：拷贝赋值往往要处理“先释放旧资源，再接收新资源”的问题，而拷贝构造没有旧资源。
  • 追问 1：拷贝赋值为什么通常要处理自赋值？
  • 答：因为 a = a; 时如果先释放自己资源，再从自己读取内容，就会读到已经失效的数据。
  • 追问 2：拷贝构造和拷贝赋值在触发时机上最容易混淆的点是什么？
  • 答：最容易混淆的是 T b = a;，它虽然写了等号，但本质仍是“定义新对象”，所以走的是拷贝构造。

7. 三法则、五法则、零法则分别是什么？

  • 答：三法则说：如果类需要自定义析构、拷贝构造、拷贝赋值中的一个，通常另外两个也要认真考虑；五法则在此基础上再加移动构造和移动赋值；零法则则鼓励不要自己直接管理裸资源，把资源交给标准库类型。
  • 要点：现代 C++ 最推崇的是零法则，因为它能显著减少手写资源管理 bug。
  • 易混点：五法则不是“必须五个都手写”，而是“如果你直接管资源，这五个都要考虑清楚”。
  • 追问 1：为什么现代 C++ 更推荐零法则？
  • 答：因为 string、vector、unique_ptr 等类型已经替你把资源生命周期处理好了，业务类更应该关注语义而不是内存管理细节。
  • 追问 2：什么场景下一定要自己实现五法则？
  • 答：当类直接拥有裸资源，且资源的拷贝、移动、销毁规则不能简单依赖默认行为时，就需要自己实现。

8. unique_ptr、shared_ptr、weak_ptr 的区别是什么？

  • 答：unique_ptr 表达独占所有权；shared_ptr 表达共享所有权；weak_ptr 不拥有对象，只观察 shared_ptr 管理的对象。
  • 要点：默认优先用 unique_ptr，因为它语义最清晰、开销最小。
  • 易混点：shared_ptr 看起来方便，但会引入引用计数成本和循环引用风险。
  • 追问 1：为什么 unique_ptr 通常应该是默认选择？
  • 答：因为大多数对象只有一个明确拥有者，独占所有权最符合直觉，也最不容易把生命周期搞乱。
  • 追问 2：shared_ptr 的引用计数会带来哪些代价？
  • 答：会有额外控制块、原子计数开销，还可能让对象“被谁持有”变得隐蔽，排查生命周期问题更难。

9. 为什么会有 weak_ptr？它主要解决什么问题？

  • 答：weak_ptr 主要解决 shared_ptr 的循环引用问题，同时表达“我只观察，不拥有”。
  • 要点：树、图、观察者模式、双向关联结构里很容易出现环，这时必须有人“弱持有”。
  • 易混点：weak_ptr 不能直接解引用，要先 lock() 成 shared_ptr。
  • 追问 1：如果不用 weak_ptr，循环引用为什么无法自动释放？
  • 答：因为两个对象都拿着对方的 shared_ptr，引用计数永远不归零，即使外部已经没人再用它们。
  • 追问 2：weak_ptr::lock() 的返回值为什么是 shared_ptr？
  • 答：因为访问对象前，必须先临时获得一个“强引用”，这样才能保证使用期间对象不会被销毁。

10. RAII 是什么？为什么它是现代 C++ 的核心思想？

  • 答：RAII（Resource Acquisition Is Initialization）就是把“资源的获取与释放”绑定到“对象的构造与析构”上。
  • 要点：资源包括内存、文件、锁、socket、事务句柄等，不仅仅是 new/delete。
  • 易混点：RAII 不是某个语法点，而是现代 C++ 最重要的设计哲学之一。
  • 追问 1：RAII 为什么特别适合异常环境？
  • 答：因为异常发生时栈会自动展开，局部对象的析构函数仍会被调用，所以资源不会因为异常路径而泄漏。
  • 追问 2：除了内存，RAII 还能管理哪些资源？
  • 答：例如 std::lock_guard 管锁、文件流管文件、数据库连接包装类管连接、事务对象管回滚/提交。

11. new/delete 和 malloc/free 的区别是什么？

  • 答：new/delete 是 C++ 的对象分配机制，负责“分配内存 + 调用构造/析构”；malloc/free 是 C 的原始内存分配机制，只负责字节级内存。
  • 要点：new 失败通常抛异常，malloc 失败通常返回 nullptr。
  • 易混点：不能 malloc 后用 delete，也不能 new 后用 free，因为两套体系对对象生命周期的理解不同。
  • 追问 1：new/delete 和 malloc/free 在构造析构层面差异是什么？
  • 答：new 会构造对象，delete 会析构对象；malloc/free 完全不知道“对象”这回事。
  • 追问 2：为什么 C++ 项目里一般不建议混用这两套体系？
  • 答：因为一旦混用，最容易出的问题就是对象没构造好、没析构干净，或者释放方式错误。

12. 什么是虚函数？它的作用是什么？

  • 答：虚函数是支持运行时多态的成员函数。通过基类指针或引用调用时，会根据对象的真实类型动态决定执行哪个版本。
  • 要点：虚函数解决的是“接口统一，但实现因子类而不同”的问题。
  • 易混点：只有通过基类指针/引用调用，虚分派才有意义；按值调用不会体现多态。
  • 追问 1：虚函数表（vtable）通常是怎么参与调用分派的？
  • 答：对象内部通常有一个虚表指针 vptr，它指向所属动态类型的虚表 vtable；调用虚函数时，会先通过 vptr 找到正确函数地址。
  • 追问 2：什么情况下不应该把函数设计成虚函数？
  • 答：当类根本不打算被继承、函数不需要多态、或对调用开销和对象布局极度敏感时，不应滥用虚函数。

13. 多态的本质是什么？

  • 答：多态的本质是“同一接口，不同实现”。调用方依赖抽象接口，而实际行为由对象真实类型决定。
  • 要点：编译期多态主要靠模板/重载，运行时多态主要靠虚函数。
  • 易混点：多态不只是“子类重写父类函数”，关键是“通过抽象接口调用时，行为还能自动切到真实类型”。
  • 追问 1：编译时多态和运行时多态的区别是什么？
  • 答：编译时多态在编译阶段就把具体实现选好了；运行时多态要等程序运行时，根据对象动态类型做分派。
  • 追问 2：多态为什么通常和基类指针/引用一起讨论？
  • 答：因为只有基类指针/引用才能在“统一接口”下指向不同派生对象；按值传递会发生对象切片。

14. 为什么基类析构函数通常要写成 virtual？

  • 答：因为如果通过基类指针 delete 一个派生类对象，必须保证先调用派生类析构，再调用基类析构，否则派生类资源可能泄漏。
  • 例子：
Base* p = new Derived();
delete p; // 若 Base 析构非虚，可能只调到 ~Base()
  • 要点：只要一个类打算作为多态基类使用，析构函数通常就应当是虚的。
  • 易混点：不是“所有基类都必须虚析构”，而是“所有可能通过基类指针删除派生对象的基类，都应该虚析构”。
  • 追问 1：如果基类析构函数不是虚函数，会出现什么具体后果？
  • 答：可能只执行基类析构，派生类新增资源不释放，严重时还会导致清理逻辑不完整。
  • 追问 2：是不是所有基类都必须写虚析构函数？
  • 答：不是。如果类不打算被多态使用，或者根本不允许外部通过基类指针删除对象，就不一定需要。

15. 纯虚函数和抽象类是什么？

  • 答：纯虚函数是声明时写成 virtual void f() = 0; 的函数，表示“这个接口必须由派生类实现”；含有纯虚函数的类叫抽象类，不能直接实例化。
  • 要点：抽象类的价值不只是“不能创建对象”，而是用来定义统一接口和框架边界。
  • 易混点：纯虚函数所在的基类仍然可以有成员变量、普通函数，甚至某些纯虚函数也可以提供定义，但类本身仍是抽象的。
  • 追问 1：纯虚函数的类为什么不能直接实例化？
  • 答：因为它的接口还不完整，语言层面禁止你创建一个“功能没补齐”的对象。
  • 追问 2：抽象类除了约束接口，还有什么设计价值？
  • 答：它能强制业务层依赖抽象、隔离实现变化、统一上层调用方式，是很多框架和插件系统的基础。

16. 继承和组合的区别是什么？

  • 答：继承表达“is-a”关系，组合表达“has-a”关系。继承强调类型层次和多态，组合强调能力复用和低耦合。
  • 要点：现代设计里常说“优先组合，谨慎继承”。
  • 易混点：想复用代码不等于就该继承；如果语义上不是“某物就是某类”，通常更适合组合。
  • 追问 1：什么时候应该优先用组合而不是继承？
  • 答：当你只是想复用某个功能模块，而不是想建立稳定的类型层次时，优先用组合。
  • 追问 2：如果继承层次太深，会带来什么问题？
  • 答：会带来高耦合、脆弱基类问题、理解困难、测试困难，稍微改动基类就可能波及整条继承链。

17. vector 和 list 的区别是什么？

  • 答：vector 底层是连续内存，随机访问快、缓存友好；list 是链表，中间插删稳定，但随机访问慢、内存碎片多。
  • 要点：工程上 vector 是默认首选，list 只在非常特定的插删场景才值得考虑。
  • 易混点：别只看时间复杂度，CPU 缓存局部性往往比理论复杂度更影响真实性能。
  • 追问 1：为什么很多场景下 vector 实际比 list 更快？
  • 答：因为 vector 连续内存更容易命中 CPU cache，而 list 需要频繁指针跳转，常数开销很大。
  • 追问 2：vector 的扩容策略为什么重要？
  • 答：因为扩容会引发重新分配和元素搬迁，既影响性能，也会导致迭代器/指针/引用失效。

18. map 和 unordered_map 的区别是什么？

  • 答：map 通常基于红黑树，元素有序，查找/插入/删除是 O(log n)；unordered_map 基于哈希表，平均复杂度接近 O(1)，但元素无序。
  • 要点：是否需要“顺序”和“范围能力”，往往比单纯看均摊复杂度更重要。
  • 易混点：unordered_map 的最坏复杂度可能退化，而且它的迭代顺序不稳定、内存开销通常更大。
  • 追问 1：什么时候即使无序也不该直接用 unordered_map？
  • 答：当你需要稳定性能、担心哈希退化、要和外部结果按顺序对齐，或者键类型哈希代价很高时，不一定比 map 更好。
  • 追问 2：map 的有序性在什么场景是优势？
  • 答：做范围查询、前驱后继、按键排序遍历、区间统计时，map 的有序性非常有价值。

19. 什么是迭代器失效？

  • 答：迭代器失效指的是：容器发生某些结构性修改后，原来的迭代器、引用或指针不再安全可用。
  • 要点：最常见的触发源是扩容、擦除、插入导致底层存储重新布局。
  • 例子：
for (auto it = v.begin(); it != v.end(); ) {
    if (*it == x) it = v.erase(it);
    else ++it;
}
  • 易混点：不是“程序没崩就没事”，失效后继续用，很多时候属于未定义行为。
  • 追问 1：哪些容器的插入/删除最容易导致迭代器失效？
  • 答：vector 扩容、string 扩容、deque 两端操作、各类容器的 erase 都很常见。
  • 追问 2：如何在遍历时安全删除元素？
  • 答：最常用的写法是接住 erase 的返回值，让它指向删除位置之后的新有效迭代器。

20. emplace_back 和 push_back 的区别是什么？

  • 答：push_back 是“把一个已经存在的对象压进去”；emplace_back 是“直接在容器尾部原地构造对象”。
  • 要点：emplace_back 的优势主要在“省掉临时对象”或“直接转发构造参数”。
  • 易混点：emplace_back 不一定比 push_back 快，特别是当你本来就有一个现成对象时，它们差别很小。
  • 追问 1：emplace_back 一定比 push_back 快吗？
  • 答：不一定。真正决定性能的是对象类型、构造代价、是否触发扩容，以及编译器优化情况。
  • 追问 2：在哪些场景 push_back 和 emplace_back 几乎没区别？
  • 答：当插入的本来就是已经构造好的对象，比如 T obj; v.push_back(obj); 与 v.emplace_back(obj);，差别通常很小。

21. 模板的本质是什么？

  • 答：模板本质上是“生成代码的规则”，编译器会在实例化时根据具体类型生成对应版本，所以它更像编译期的泛型机制。
  • 追问 1：模板为什么常被说成是“编译期多态”？
  • 答：因为同一套接口能在不同类型上展开成不同实现，而且绑定发生在编译期，不依赖虚函数表。
  • 追问 2：为什么模板错误往往报得很长？
  • 答：因为错误通常出现在实例化展开链路里，编译器会把推导过程、候选重载和失败原因一起打印出来。

22. 函数模板和类模板有什么区别？

  • 答：函数模板主要解决“同一种操作适配多种类型”，支持重载和类型推导；类模板主要解决“同一种数据结构适配多种类型”，实例化时通常要显式给出模板参数。
  • 追问 1：函数模板支持重载，类模板为什么不能像函数那样做偏重载？
  • 答：类模板没有“重载决议”这套机制，只有主模板、偏特化、全特化三种匹配方式。
  • 追问 2：类模板实例化时机和函数模板有什么区别？
  • 答：类模板在你声明具体类型时就形成实例，函数模板通常在真正调用且需要生成代码时才实例化。

23. typename 和 class 在模板参数中有什么区别？

  • 答：在模板参数列表里，typename T 和 class T 大多数场景等价，都是声明“这里有一个类型参数”。
  • 追问 1：模板参数列表里 typename 和 class 为什么大多等价？
  • 答：因为标准专门规定了它们在类型形参位置语义一致，只是历史写法不同。
  • 追问 2：在哪些地方 typename 不是可替换的？
  • 答：在依赖名场景里，typename T::value_type 用来告诉编译器它是类型，这里不能换成 class。

24. 什么是 SFINAE？

  • 答：SFINAE 是“替换失败并非错误”，意思是模板参数替换失败时，这个候选模板会被静默丢弃，而不是直接让编译报错。
  • 追问 1：SFINAE 主要解决了哪类问题？
  • 答：主要用于做模板约束、重载选择和根据类型特性启用/禁用某些实现。
  • 追问 2：concepts 出来后为什么很多场景不再优先用 SFINAE？
  • 答：因为 concepts 可读性更好、报错更直接，表达“这个模板需要什么能力”也更自然。

25. auto 和 decltype 的区别是什么？

  • 答：auto 是“根据初始化表达式推导变量类型”，decltype 是“精确获取一个表达式声明出来的类型”，两者关注点不同。
  • 追问 1：decltype(x) 和 decltype((x)) 有什么区别？
  • 答：decltype(x) 更像看变量声明类型；decltype((x)) 看表达式类别，若 x 是左值，结果通常会变成引用类型。
  • 追问 2：为什么 auto 有时会丢掉引用和顶层 const？
  • 答：因为它的推导规则默认按值推导，顶层 const 和引用常被去掉；想保留要写成 auto&、const auto& 等形式。

26. Lambda 表达式的本质是什么？

  • 答：Lambda 本质上是一个匿名函数对象，编译器会为它生成一个带 operator() 的闭包类型。
  • 追问 1：Lambda 底层更像函数还是对象？
  • 答：更像对象，因为它可以持有捕获状态，也有自己独立的闭包类型。
  • 追问 2：捕获列表和闭包对象的关系是什么？
  • 答：捕获列表决定闭包对象里要存哪些成员，以及这些成员是按值保存还是按引用绑定。

27. [=] 和 [&] 捕获有什么区别？

  • 答：[=] 默认按值捕获外部变量，Lambda 内拿到的是副本；[&] 默认按引用捕获，直接操作外部对象本身。
  • 追问 1：值捕获和引用捕获在生命周期风险上有什么区别？
  • 答：值捕获更安全但可能有拷贝成本；引用捕获没有拷贝，但一旦外部对象先销毁，就容易留下悬空引用。
  • 追问 2：为什么 [=] 和 [&] 在异步回调里要特别小心？
  • 答：因为回调执行时机可能晚于外部作用域结束，尤其 [&] 很容易引用到已经失效的局部变量。

28. std::function 有什么作用？

  • 答：std::function 是一个通用可调用对象包装器，可以统一保存函数、Lambda、仿函数、bind 结果等不同调用实体。
  • 追问 1：std::function 为什么有类型擦除成本？
  • 答：因为它要把不同具体类型统一包装到同一个接口下，通常会引入额外间接调用、对象包装甚至动态分配开销。
  • 追问 2：什么时候更适合直接用模板参数而不是 std::function？
  • 答：在性能敏感、调用频繁或只在编译期组合的泛型代码里，模板通常更高效。

29. static_cast、dynamic_cast、const_cast、reinterpret_cast 的区别是什么？

  • 答：static_cast 做常规静态类型转换；dynamic_cast 做带运行时检查的多态转型；const_cast 用来增删 const/volatile 限定；reinterpret_cast 做底层按位解释式转换，风险最大。
  • 追问 1：C 风格强转和四种 C++ cast 相比最大问题是什么？
  • 答：它把多种转换语义混在一起，可读性差，也更容易掩盖危险转换。
  • 追问 2：哪一种 cast 最容易隐藏严重 bug？
  • 答：通常是 reinterpret_cast，因为它最容易绕过类型系统，制造别名、对齐和对象模型相关问题。

30. 什么是未定义行为（UB）？为什么它危险？

  • 答：未定义行为是标准没有规定结果的行为，比如越界访问、解引用悬空指针、数据竞争等；一旦发生，程序可能看起来“偶尔正常”，也可能彻底失控。
  • 追问 1：为什么 UB 比普通逻辑错误更危险？
  • 答：普通逻辑错误通常只是结果不对，而 UB 会让编译器合法地做出任何假设，导致行为不可预测。
  • 追问 2：编译器优化为什么会放大 UB 的风险？
  • 答：因为优化器会基于“程序没有 UB”这个前提重排、删除或合并代码，一旦前提被破坏，结果可能和源码直觉完全不一致。

31. 编译、链接、运行三个阶段分别做了什么？

  • 答：编译阶段把源码翻译成目标文件；链接阶段把多个目标文件和库拼成可执行文件；运行阶段再由操作系统加载执行。
  • 追问 1：预处理、编译、汇编、链接分别产出什么？
  • 答：预处理展开宏和头文件，编译生成汇编，汇编生成目标文件，链接生成最终可执行文件或库。
  • 追问 2：为什么有些错误出现在编译阶段，有些只在链接阶段暴露？
  • 答：语法、类型等问题编译期就能发现；符号未定义、重复定义这类跨文件问题通常要到链接时才知道。

32. 什么是 ODR（One Definition Rule）？

  • 答：ODR 要求同一个实体在整个程序里只能有一个一致的定义，否则就可能出现链接错误或更隐蔽的未定义行为。
  • 追问 1：ODR 违反最常见的触发方式是什么？
  • 答：常见是把非 inline 的函数或变量定义写进头文件，并被多个源文件同时包含。
  • 追问 2：模板和 inline 为什么经常和 ODR 一起讨论？
  • 答：因为它们往往需要写在头文件里，而标准对“多个翻译单元里相同定义共存”专门给了例外规则。

33. 为什么头文件要加保护宏？

  • 答：为了避免同一个头文件在单个翻译单元里被重复包含，从而导致重复声明或重复定义问题。
  • 追问 1：头文件保护和 #pragma once 有什么关系？
  • 答：两者目标一样，都是防重复包含；前者是标准写法，后者更简洁但属于实现支持。
  • 追问 2：头文件保护为什么不能解决所有重复定义问题？
  • 答：因为它只能防“同一翻译单元内重复包含”，不能解决多个源文件都各自看到同一个错误定义的问题。

34. inline 的作用是什么？它真的一定会内联吗？

  • 答：现代 inline 的核心作用是允许同一个函数定义出现在多个翻译单元中而不违反 ODR；至于是否真正做函数内联优化，由编译器自行决定。
  • 追问 1：inline 的现代核心作用和“建议内联”有什么区别？
  • 答：前者是语言层面的链接规则，后者只是性能优化层面的实现选择，两者不要混为一谈。
  • 追问 2：为什么头文件里的函数定义常常要加 inline？
  • 答：因为头文件会被多个源文件包含，不加 inline 容易在链接时出现重复定义。

35. static 在局部变量、全局变量、类成员中的含义分别是什么？

  • 答：局部 static 表示生命周期延长到整个程序期间；全局/命名空间级 static 表示内部链接，只在当前翻译单元可见；类里 static 成员属于类本身而不属于某个对象。
  • 追问 1：类静态成员和普通成员的存储位置有何不同？
  • 答：普通成员跟着对象走，每个对象一份；静态成员独立存储，整个类共享一份。
  • 追问 2：静态局部变量为什么常被用于单例实现？
  • 答：因为它天然只初始化一次，生命周期覆盖整个程序，而且现代 C++ 还保证其初始化具备线程安全。

36. volatile 是什么？它和并发安全有什么关系？

  • 答：volatile 告诉编译器“这个对象的值可能被外部环境改变，不要随便优化掉读写”；它解决的是优化可见性问题，不保证原子性，也不保证线程同步。
  • 追问 1：volatile 为什么不能替代 atomic 或锁？
  • 答：因为它不提供互斥、顺序保证和复合操作原子性，多线程下仍然可能发生数据竞争。
  • 追问 2：它真正解决的是哪类问题？
  • 答：更适合内存映射寄存器、硬件状态位、信号处理等“值会被程序外部改变”的场景。

37. 什么是对象切片（object slicing）？

  • 答：对象切片是把派生类对象按值赋给基类对象时，派生类那部分状态被“切掉”，最后只剩一个纯基类对象。
  • 追问 1：对象切片后到底丢掉了什么？
  • 答：丢掉的是派生类新增的数据成员以及与动态类型相关的那部分语义。
  • 追问 2：为什么按值传递基类对象会破坏多态？
  • 答：因为一旦拷成了独立的基类对象，动态类型信息就不再代表原派生类，自然无法再分派到派生类行为。

38. 构造函数和析构函数的调用顺序是什么？

  • 答：构造时先基类、再成员、最后派生类自身；析构顺序正好相反，先析构派生类自身，再成员，最后基类。
  • 追问 1：派生类构造时，父类和成员对象的初始化顺序如何确定？
  • 答：先按继承列表构造基类，再按成员声明顺序构造成员，不是按初始化列表书写顺序。
  • 追问 2：析构顺序为什么和构造顺序相反？
  • 答：因为后构造的对象往往依赖先构造的对象，逆序销毁才能保证依赖关系安全拆除。

39. 临时对象什么时候销毁？

  • 答：大多数临时对象会在包含它的完整表达式结束时销毁，也就是这条语句求值完成后销毁。
  • 追问 1：临时对象的生命周期延长有哪些典型规则？
  • 答：最典型的是用 const T& 绑定临时对象时，可把它的生命周期延长到该引用的生命周期结束。
  • 追问 2：为什么返回局部引用几乎总是错的？
  • 答：因为函数返回后局部对象已经销毁，返回的引用会立刻变成悬空引用。

40. 什么是返回值优化（RVO / NRVO）？

  • 答：RVO/NRVO 是编译器直接在调用方构造返回对象，省掉中间临时对象拷贝/移动的一类优化。
  • 追问 1：RVO/NRVO 和 move 语义是什么关系？
  • 答：两者都想减少不必要复制，但 RVO 是“直接不产生那个中间对象”，move 是“对象已存在时尽量搬资源”。
  • 追问 2：现代编译器做了返回值优化后，还需要手写 move 吗？
  • 答：通常不需要，尤其 return local; 时乱写 std::move(local) 反而可能阻碍优化或让语义更差。

41. 为什么现代 C++ 强调值语义？

  • 答：因为值语义让“谁拥有资源、对象什么时候销毁、拷贝后是否独立”都更清晰。对象像普通值一样使用，更容易推理、测试和组合。
  • 追问 1：值语义相比引用语义的主要优势是什么？
  • 答：所有权明确、生命周期独立、接口副作用更少，也更符合 RAII 和异常安全设计。
  • 追问 2：哪些类型天然更适合值语义？
  • 答：配置对象、数学对象、字符串、容器，以及封装后能独立管理资源的业务对象。

42. string 和 string_view 的区别是什么？

  • 答：string 拥有字符串内容；string_view 只是一个“指针 + 长度”的非拥有视图，不负责内存生命周期。
  • 追问 1：string_view 为什么快？它的风险又在哪里？
  • 答：因为通常不分配也不拷贝内容；风险在于底层字符串一旦失效，string_view 就悬空了。
  • 追问 2：什么时候不该把 string_view 存起来？
  • 答：当它引用的是临时字符串、局部变量、会被修改或释放的缓冲区时。

43. optional 的作用是什么？

  • 答：optional<T> 用来表达“要么有一个 T，要么没有值”，比用 -1、空字符串之类魔法值更清晰。
  • 追问 1：optional 为什么比返回魔法值更好？
  • 答：因为“无值”成为类型语义的一部分，调用方必须显式处理，语义更安全。
  • 追问 2：什么时候 optional 不如异常或错误码？
  • 答：当你不仅要表示失败，还要携带详细失败原因、错误上下文或恢复策略时。

44. variant 和 any 的区别是什么？

  • 答：variant 是“有限类型集合中的一个”，编译期就知道备选类型；any 是“任意类型都能装”，但要运行时再判断具体类型。
  • 追问 1：variant 和多态对象设计分别适合什么场景？
  • 答：variant 适合类型集合固定、分支清晰的场景；多态适合行为扩展、类型开放增长的场景。
  • 追问 2：访问 variant 时为什么要小心当前持有类型？
  • 答：因为取错类型会抛异常或失败，通常要先 holds_alternative、get_if 或用 visit。

45. span 的用途是什么？

  • 答：span 表示一段连续内存的非拥有视图，适合作为函数参数统一接收数组、vector、string 等连续数据。
  • 追问 1：span 为什么被称为“非拥有视图”？
  • 答：因为它只记录起始地址和长度，不分配、不释放，也不保证底层数据存活。
  • 追问 2：为什么它特别适合做函数参数？
  • 答：因为它既保留长度信息，又不强绑定具体容器类型，接口更通用。

46. if constexpr 和普通 if 的区别是什么？

  • 答：普通 if 是运行时分支；if constexpr 是编译期分支，不满足条件的分支会在模板实例化时被直接丢弃。
  • 追问 1：if constexpr 为什么能避免无效分支编译报错？
  • 答：因为未选中的分支根本不会参与当前模板实例的语义检查。
  • 追问 2：它和模板实例化有什么联系？
  • 答：它常用来根据类型特征在编译期选择实现，是模板元编程的常用简化手段。

47. concept / requires 解决了什么问题？

  • 答：它们解决的是“模板参数到底需要满足什么条件”这个问题，把原来隐晦的 SFINAE 约束写成更直观的接口约束。
  • 追问 1：concepts 为什么比 enable_if 更易读？
  • 答：因为约束直接写在模板签名上，语义像自然语言，报错也更友好。
  • 追问 2：concepts 只是语法糖吗？
  • 答：不只是。它不仅改善写法，还改善重载决议和错误诊断体验。

48. set 和 unordered_set 的区别是什么？

  • 答：set 通常基于平衡树，元素有序；unordered_set 基于哈希表，元素无序但平均查找更快。
  • 追问 1：set 和 unordered_set 在复杂度和顺序性上怎么取舍？
  • 答：要顺序、范围能力、稳定最坏复杂度时选 set；更看重平均查找性能时选 unordered_set。
  • 追问 2：什么时候哈希集合反而不是更优选择？
  • 答：当键哈希代价高、需要有序遍历、最坏性能敏感或内存占用受限时。

49. deque 和 vector 的区别是什么？

  • 答：vector 是整块连续内存；deque 是分段连续结构。vector 更适合随机访问和尾部增长，deque 更适合两端插删。
  • 追问 1：deque 为什么两端操作比 vector 更友好？
  • 答：因为它不要求整个存储区保持单块连续，头尾扩展成本更低。
  • 追问 2：它的内存布局和 vector 有什么本质差别？
  • 答：vector 完全连续；deque 通常是多块缓冲区加索引表。

50. stack 和 queue 为什么叫容器适配器？

  • 答：因为它们不是完整容器，而是在底层容器之上包装出“栈”或“队列”接口。
  • 追问 1：为什么 stack/queue 叫适配器而不是完整容器？
  • 答：因为它们只暴露特定操作，不提供完整遍历、随机访问等容器能力。
  • 追问 2：它们默认底层容器是什么？能不能替换？
  • 答：默认常是 deque，也可以替换成满足接口要求的其他容器，如 vector 或 list 的某些组合。

51. sort 的底层一般是什么思想？

  • 答：标准库 sort 常见实现是 introsort：以快速排序为主，递归太深时切换堆排序，小区间再用插入排序优化。
  • 追问 1：sort 为什么通常要求随机访问迭代器？
  • 答：因为它要高效做下标跳转、区间划分和中间位置访问。
  • 追问 2：稳定排序和不稳定排序分别适合什么场景？
  • 答：需要保留相等元素原始顺序时用稳定排序；更偏性能时常用不稳定排序。

52. remove 和 erase 为什么常常一起使用？

  • 答：因为 remove 只是把“不需要的元素”移动到后面，并不真正删掉容器尾部；真正缩容要靠 erase。
  • 追问 1：为什么 remove 后元素看似还在容器里？
  • 答：因为容器 size 没变，只是有效元素区间变短了。
  • 追问 2：erase-remove 惯用法本质是在做什么？
  • 答：先重排保留元素，再一次性删除尾部无效区间。

53. reserve 和 resize 的区别是什么？

  • 答：reserve 改的是容量 capacity，不改元素个数；resize 改的是大小 size，会增加或删除实际元素。
  • 追问 1：reserve 影响 capacity，resize 影响 size，这对迭代器有什么影响？
  • 答：reserve 若触发重分配会让旧迭代器失效；resize 则会改变有效元素范围，缩小时尾部元素失效。
  • 追问 2：为什么提前 reserve 常常能提升性能？
  • 答：因为减少多次扩容和元素搬迁，降低分配次数。

54. 为什么 vector 通常比 list 更快？

  • 答：因为 vector 连续内存更符合 CPU 缓存访问模式，而 list 节点分散、指针跳转多、分配开销高。
  • 追问 1：list 理论复杂度看起来很好，为什么实践中却常输给 vector？
  • 答：因为真实机器更看重常数开销和缓存局部性，而不只是大 O。
  • 追问 2：缓存局部性在这里扮演什么角色？
  • 答：连续内存更容易被预取和缓存命中，遍历速度通常明显更快。

55. 为什么不要随便用裸指针表达所有权？

  • 答：因为裸指针只表达“能访问”，不表达“谁负责释放”，容易造成生命周期不清晰。
  • 追问 1：裸指针适合表达什么，不适合表达什么？
  • 答：适合表达非拥有观察、可空引用；不适合表达独占或共享所有权。
  • 追问 2：为什么现代接口设计特别强调所有权语义？
  • 答：因为一旦边界上谁拥有资源不清楚，排查泄漏和悬空问题会非常痛苦。

56. 什么是悬空指针？什么是野指针？

  • 答：悬空指针原本指向合法对象，但对象后来被销毁了；野指针则是从一开始就没被正确初始化，指向未知地址。
  • 追问 1：悬空指针和野指针的本质区别是什么？
  • 答：前者“曾经合法，后来失效”；后者“从一开始就不可信”。
  • 追问 2：智能指针能不能完全避免悬空问题？
  • 答：不能完全避免，尤其是外部还保留原始引用、迭代器或 view 时，逻辑上仍可能悬空。

57. 什么是内存泄漏？

  • 答：内存泄漏是已经分配的内存不再可达，但也没有被释放，导致进程长期占用越来越多资源。
  • 追问 1：内存泄漏怎么系统定位？
  • 答：常结合 ASan、Valgrind、堆快照、日志和分配回溯一起定位。
  • 追问 2：为什么异常路径和早返回路径特别容易泄漏？
  • 答：因为这些路径最容易绕过手工释放代码，所以 RAII 特别重要。

58. 异常处理的基本结构是什么？

  • 答：基本结构是 try 包住可能出错的代码，throw 抛异常，catch 按类型接住并处理。
  • 追问 1：catch 顺序为什么重要？
  • 答：因为异常匹配从上到下进行，若先写基类异常，后面的派生类异常分支就永远到不了。
  • 追问 2：异常对象为什么通常建议按 const& 捕获？
  • 答：这样能避免不必要拷贝，也能保留动态类型信息。

59. 为什么析构函数里通常不建议抛异常？

  • 答：因为析构函数常发生在清理阶段，如果此时再抛异常，特别是在栈展开过程中，程序很容易直接终止。
  • 追问 1：析构函数抛异常时为什么危险？
  • 答：它会破坏“清理阶段尽量稳定完成”的假设，让资源回收逻辑变得不可靠。
  • 追问 2：栈展开期间再次抛异常会发生什么？
  • 答：通常会触发 std::terminate()。

60. noexcept 的作用是什么？

  • 答：noexcept 表示函数承诺不抛异常，既影响接口语义，也会影响编译器优化和标准库的策略选择。
  • 追问 1：noexcept 对标准库容器移动优化有什么影响？
  • 答：如果移动构造是 noexcept，容器扩容时更愿意移动而不是退回拷贝。
  • 追问 2：什么时候不要轻易承诺 noexcept？
  • 答：当函数内部调用链可能抛异常，且你又无法完全兜住时，不要随便承诺。

61. thread、进程、协程三者有什么区别？

  • 答：进程是资源隔离单位；线程是进程内的执行流，多个线程共享地址空间；协程是用户态的轻量控制流切换机制，不等同于操作系统线程。
  • 追问 1：线程和协程在调度层面最大的不同是什么？
  • 答：线程通常由内核调度，切换较重；协程通常由用户态框架调度，切换更轻。
  • 追问 2：什么时候线程过重，协程更合适？
  • 答：高并发 I/O、任务数量特别多但单个任务不重的场景，协程往往更合适。

62. mutex 和 atomic 的区别是什么？

  • 答：mutex 提供互斥，适合保护临界区；atomic 提供单个变量级别的原子操作，适合轻量同步。
  • 追问 1：什么场景更适合 mutex，什么场景更适合 atomic？
  • 答：涉及多个变量不变式、复杂临界区时用 mutex；单变量计数、标志位时常用 atomic。
  • 追问 2：atomic 能不能替代所有锁？
  • 答：不能。它很难直接维护复杂状态一致性。

63. 什么是数据竞争（data race）？

  • 答：当两个线程并发访问同一内存位置，且至少一个是写操作，又没有同步手段约束时，就发生了数据竞争。
  • 追问 1：数据竞争为什么属于 UB？
  • 答：因为标准不保证并发无同步读写的行为，编译器和硬件都可做超出直觉的重排。
  • 追问 2：只要结果偶尔错了才算数据竞争吗？
  • 答：不是。即便结果“看起来没错”，只要并发读写无同步，它就是数据竞争。

64. 什么是死锁？如何避免？

  • 答：死锁是多个执行单元互相等待对方持有的资源，最终谁都走不下去。
  • 追问 1：死锁形成通常满足哪些条件？
  • 答：常见有互斥、占有且等待、不可抢占、循环等待四个条件。
  • 追问 2：如何从设计上降低死锁概率？
  • 答：统一加锁顺序、缩小锁粒度、避免嵌套锁、用 RAII 锁工具和更高层并发模型。

65. 条件变量 condition_variable 的典型使用场景是什么？

  • 答：它常用于“一个线程等待某个条件成立，另一个线程在条件满足时唤醒它”，典型如生产者-消费者模型。
  • 追问 1：条件变量为什么必须和锁配合？
  • 答：因为等待条件和修改共享状态必须受保护，否则会出现丢通知或状态竞争。
  • 追问 2：为什么 wait 通常要写成带谓词的形式？
  • 答：因为条件变量可能伪唤醒，所以醒来后必须再次检查条件是否真的成立。

66. future、promise、async 的关系是什么？

  • 答：promise 负责生产结果，future 负责消费结果；async 是更高层封装，帮你启动任务并直接返回 future。
  • 追问 1：promise 是怎么把结果交给 future 的？
  • 答：它们共享同一个状态对象，promise 设置值或异常，future 再去等待和获取。
  • 追问 2：async 默认启动策略有什么坑？
  • 答：默认策略可能是延迟执行，也可能新开线程，不同实现下时机和并发度可能不完全一致。

67. memory_order_relaxed、acquire、release、seq_cst 分别是什么？

  • 答：它们是原子操作的内存序约束：relaxed 只保证原子性；release/acquire 建立同步关系；seq_cst 提供最强的全局一致顺序直觉。
  • 追问 1：为什么 relaxed 内存序看起来最简单，却最难用对？
  • 答：因为它没有顺序与可见性保证，稍有不慎就会写出逻辑上错但很难复现的代码。
  • 追问 2：acquire/release 最典型的配对场景是什么？
  • 答：一个线程发布数据后 release 写标志，另一个线程 acquire 读标志后再安全读数据。

68. 什么是 C++ 内存模型？

  • 答：C++ 内存模型规定了多线程下读写何时可见、何时有序、什么算数据竞争、同步操作如何建立 happens-before 关系。
  • 追问 1：内存模型里“可见性”和“顺序”分别是什么意思？
  • 答：可见性是“一个线程写的值何时能被另一个线程看到”；顺序是“多个读写操作在其他线程看来是否保持某种先后关系”。
  • 追问 2：为什么单线程直觉经常不适用于多线程？
  • 答：因为编译器和 CPU 都可能重排指令，多线程观察到的顺序不一定等于源码顺序。

69. 为什么并发 bug 比普通 bug 更难查？

  • 答：因为并发 bug 往往依赖时序、调度、缓存和优化条件，具有随机性和低可复现性。
  • 追问 1：并发 bug 为什么往往难复现？
  • 答：因为只在非常特定的线程切换时机、负载、机器环境下才触发。
  • 追问 2：为什么日志有时会改变并发 bug 的表现？
  • 答：因为加日志会改变时序、内存布局和调度，从而“掩盖”或“制造”问题。

70. 什么是 cache-friendly？为什么连续内存更重要？

  • 答：cache-friendly 指的是数据布局和访问模式更适合 CPU cache，能减少缓存未命中。
  • 追问 1：什么是 cache-friendly 设计？
  • 答：例如连续存储、顺序访问、减少指针跳转、尽量让热点数据紧凑。
  • 追问 2：为什么连续内存布局常常更快？
  • 答：因为 CPU 更容易预取连续数据，缓存命中率更高。

71. 什么是对齐（alignment）？什么是 padding？

  • 答：对齐是对象按某种地址边界放置的要求；padding 是编译器为了满足对齐插入的额外空字节。
  • 追问 1：对齐要求是谁决定的？
  • 答：通常由平台 ABI、处理器访问特性和编译器实现共同决定。
  • 追问 2：为什么错误对齐会影响性能甚至正确性？
  • 答：某些平台上未对齐访问更慢，甚至直接导致硬件异常。

72. 为什么结构体大小可能大于成员大小之和？

  • 答：因为编译器会插入 padding 来满足成员和整体对象的对齐要求。
  • 追问 1：成员顺序为什么会影响结构体大小？
  • 答：因为不同顺序会改变 padding 插入位置和总量。
  • 追问 2：什么时候需要刻意关心 padding？
  • 答：做网络协议、文件格式、内存映射、性能敏感数据结构时需要特别关注。

73. reinterpret_cast 为什么最危险？

  • 答：因为它几乎是“强行按另一种类型解释比特”，很容易绕过类型系统，触发别名、对齐和对象模型问题。
  • 追问 1：reinterpret_cast 常见于哪些底层场景？
  • 答：序列化、驱动开发、协议解析、与硬件或外部 ABI 直接交互时。
  • 追问 2：为什么它几乎总是最后手段？
  • 答：因为一旦用错，bug 往往隐蔽且后果严重，通常没有更高层类型安全保障。

74. dynamic_cast 的底层依赖什么机制？

  • 答：它依赖 RTTI（运行时类型信息）和多态类型的对象布局，用来在运行时检查类型转换是否合法。
  • 追问 1：dynamic_cast 为什么需要 RTTI/多态类型支持？
  • 答：因为它必须知道对象真实动态类型，才能判断向下转型是否安全。
  • 追问 2：和 static_cast 做向下转型相比差别在哪？
  • 答：dynamic_cast 会做运行时检查，失败可返回空指针或抛异常；static_cast 不检查，风险更大。

75. vtable 和 vptr 是什么？

  • 答：vtable 是虚函数表，存虚函数地址；vptr 是对象内部指向 vtable 的指针。
  • 追问 1：vtable 是每个对象一份还是每个类一份？
  • 答：通常一个多态类一份 vtable，而每个对象一份 vptr。
  • 追问 2：多继承时虚表模型会发生什么复杂化？
  • 答：可能出现多个 vptr、this 调整和更复杂的布局规则。

76. 为什么构造函数里调用虚函数通常不会表现出多态？

  • 答：因为构造/析构期间，对象还没完全变成“最终派生类视角”，语言规则会限制虚调用只看到当前构造层级。
  • 追问 1：构造/析构中调用虚函数为什么不表现出最终派生类多态？
  • 答：因为那时派生部分可能还没构造好或已经析构掉，调用最终派生版本会有安全问题。
  • 追问 2：这会导致哪些设计误判？
  • 答：最常见误判是“以为基类构造里调虚函数就能自动走到子类逻辑”，结果行为和预期不一致。

77. 什么是 ABI？为什么 C++ 二进制兼容更复杂？

  • 答：ABI 是二进制接口约定，规定函数调用、对象布局、名字修饰、异常机制等。C++ 因模板、重载、虚函数、异常等特性，ABI 兼容比 C 更复杂。
  • 追问 1：ABI 不兼容通常会在什么场景暴露？
  • 答：不同编译器、不同标准库版本、动态库升级、插件系统和跨模块二进制交互时。
  • 追问 2：为什么 C++ 动态库升级比 C 更棘手？
  • 答：因为类布局、虚表、模板实例、异常边界等细节一变，就可能破坏二进制兼容。

78. allocator 是干什么的？

  • 答：allocator 是 STL 容器的内存分配策略接口，负责申请、释放和对象构造/销毁相关支持。
  • 追问 1：allocator 在 STL 容器中扮演什么角色？
  • 答：它把“容器逻辑”和“内存获取方式”解耦，让容器可用不同分配策略。
  • 追问 2：为什么大多数业务代码不需要自己手写 allocator？
  • 答：因为标准默认分配器已经够用，自定义分配器成本高、收益只在特定性能场景明显。

79. pmr（polymorphic memory resource）解决了什么问题？

  • 答：pmr 解决的是“如何更灵活地给一批容器/对象统一切换内存资源”的问题，让内存策略在运行时可配置。
  • 追问 1：pmr 相比传统 allocator 的最大价值是什么？
  • 答：它把分配策略抽象成可多态替换的资源对象，使用和传递都更灵活。
  • 追问 2：它更适合哪类性能敏感场景？
  • 答：短生命周期对象很多、批量分配明显、需要内存池或 arena 优化的场景。

80. 如何设计一个异常安全、资源管理清晰的类？

  • 答：核心原则是：资源由对象拥有、用 RAII 自动释放、接口清楚表达所有权、尽量满足强异常安全或基本异常安全保证。
  • 追问 1：你会如何设计一个异常安全的资源类？
  • 答：优先用标准库资源类型封装；若必须手写，就把获取放构造、释放放析构，拷贝/移动语义明确，修改状态前先完成可能失败的操作。
  • 追问 2：怎样判断一个类的所有权边界是否清晰？
  • 答：看接口能否一眼看出“谁创建、谁销毁、是否共享、是否可空、是否可转移”。

81. 偏特化和全特化的区别是什么？

  • 答：全特化是“把某个模板参数组合完全定死”；偏特化是“只把一部分条件定死，剩下的仍保持泛型”。
  • 追问 1：偏特化和全特化谁的匹配优先级更具体？
  • 答：越具体的匹配优先级越高，全特化通常最具体。
  • 追问 2：为什么函数模板不能像类模板那样做偏特化？
  • 答：因为函数模板已经有重载机制，语言设计上主要靠重载而不是偏特化解决这类问题。

82. 变参模板怎么工作？

  • 答：变参模板通过模板参数包接收任意数量参数，再用递归展开或折叠表达式逐步处理。
  • 追问 1：变参模板常和递归展开、折叠表达式如何配合？
  • 答：早期常用递归拆包，现代 C++17 以后更常用折叠表达式直接对参数包做聚合操作。
  • 追问 2：为什么它对现代泛型库如此重要？
  • 答：因为很多通用接口都需要接收任意数量、任意类型参数，比如转发构造和格式化工具。

83. 什么是引用折叠？

  • 答：引用折叠是模板推导中“引用的引用最终如何合并”的规则，本质上是 & 和 && 组合后的归并规则。
  • 追问 1：引用折叠的四条规则分别是什么？
  • 答：& & -> &，& && -> &，&& & -> &，&& && -> &&，也就是“只要有左值引用，结果就是左值引用”。
  • 追问 2：它为什么是完美转发的基础？
  • 答：因为 T&& 在推导后能根据实参类别折叠成正确引用类型，从而保留左值/右值信息。

84. 什么是万能引用 / 转发引用？

  • 答：当 T&& 出现在类型推导上下文中时，它不是单纯的右值引用，而是转发引用，能同时绑定左值和右值。
  • 追问 1：万能引用为什么只在模板推导场景成立？
  • 答：因为只有发生类型推导时，T 才能根据实参被推导成 U& 或 U。
  • 追问 2：T&& 在普通函数和模板里语义为什么不同？
  • 答：普通函数里的 T 已经确定，所以 T&& 就是普通右值引用；模板推导时它才有“可变身份”。

85. 什么是 CRTP？它有什么用途？

  • 答：CRTP（Curiously Recurring Template Pattern）是“派生类把自己作为模板参数传给基类”的模式，常用于静态多态。
  • 追问 1：CRTP 为什么被称为静态多态？
  • 答：因为行为分派发生在编译期，不依赖虚函数和运行时开销。
  • 追问 2：它和虚函数多态相比的优缺点是什么？
  • 答：优点是零运行时分派开销、可内联；缺点是耦合更强、接口更复杂、类型开放性较差。

86. ranges 和传统 STL 算法相比，优势是什么？

  • 答：ranges 把“容器 + 算法 + 视图管道”组合得更自然，可读性更高，也减少了手写 begin/end 的样板代码。
  • 追问 1：ranges 为什么被认为是 STL 风格升级？
  • 答：因为它让算法更声明式，也更容易组合过滤、映射、切片等操作。
  • 追问 2：传统算法 + begin/end 和 ranges 管道风格如何取舍？
  • 答：老风格更兼容旧代码；新代码里若编译器和标准支持足够，ranges 往往更清晰。

87. view 和容器的区别是什么？

  • 答：容器拥有数据；view 通常不拥有数据，只是对已有数据做惰性观察和变换。
  • 追问 1：view 为什么不是容器？
  • 答：因为它通常不负责存储和生命周期管理，只表达“如何看这批数据”。
  • 追问 2：惰性求值会带来哪些优点和哪些坑？
  • 答：优点是少拷贝、少中间结果；坑是调试更绕、生命周期和求值时机更容易踩坑。

88. coroutine 的核心思想是什么？

  • 答：coroutine 的核心是“函数可以在中途挂起，并在之后从挂起点恢复继续执行”。
  • 追问 1：coroutine 里的挂起点意味着什么？
  • 答：意味着当前执行状态会被保存下来，未来恢复时不用从头再跑。
  • 追问 2：为什么说 coroutine 更像控制流机制而不是并发原语？
  • 答：因为它本身只解决“如何暂停与恢复”，至于是否并发、在哪个线程跑，要看调度器和运行时。

89. coroutine 和线程的区别是什么？

  • 答：线程是操作系统调度的执行单元；coroutine 是语言/库层面的可挂起函数，切换通常更轻量。
  • 追问 1：coroutine 能完全替代线程吗？
  • 答：不能。CPU 并行仍需要线程或进程，协程更多是高效组织异步流程。
  • 追问 2：生成器和异步任务是 coroutine 的哪两大典型应用？
  • 答：一个是按需产出序列，一个是写出像同步代码一样的异步流程。

90. 三路比较运算符 <=> 的作用是什么？

  • 答：<=> 用来一次性定义对象的比较结果，编译器可据此自动生成 <、<=、>、>=、有时还包括 == 等逻辑。
  • 追问 1：<=> 为什么能简化比较运算实现？
  • 答：因为你不必手写一整套比较函数，只要给出统一的三路比较语义。
  • 追问 2：默认三路比较生成的条件是什么？
  • 答：成员本身也要可比较，且比较语义对编译器来说可自动推导。

91. filesystem 常见能解决哪些工程问题？

  • 答：它常用于跨平台路径拼接、目录遍历、文件存在性检查、扩展名处理、创建目录等工程文件操作。
  • 追问 1：filesystem 为什么比手拼路径字符串更可靠？
  • 答：因为它把路径分隔符、规范化、平台差异等细节封装掉了。
  • 追问 2：跨平台路径处理最容易错在哪？
  • 答：最容易错在分隔符、相对/绝对路径、编码、符号链接和大小写差异。

92. chrono 中 system_clock 和 steady_clock 的区别是什么？

  • 答：system_clock 表示系统时间，会被校时影响；steady_clock 单调递增，适合测量耗时。
  • 追问 1：为什么性能计时通常用 steady_clock 而不是 system_clock？
  • 答：因为系统时间可能跳变，导致测量结果不稳定；单调时钟更可靠。
  • 追问 2：时间点和持续时间在 chrono 里怎么区分？
  • 答：time_point 表示某个时刻，duration 表示两个时刻之间的时间长度。

93. 为什么 format 比 printf 更现代？

  • 答：因为 format 类型安全、可扩展、和 C++ 类型系统结合更自然，不像 printf 那样依赖格式字符串和可变参数匹配。
  • 追问 1：format 相比 printf 在类型安全上体现在哪里？
  • 答：参数类型和格式化规则更早被检查，减少 %d 配错类型这类问题。
  • 追问 2：为什么现代 C++ 更倾向统一格式化接口？
  • 答：因为统一接口更易组合、国际化、扩展，也更符合泛型设计。

94. 宏和内联函数有什么区别？

  • 答：宏是预处理阶段的文本替换；内联函数是语言层面的函数，有类型检查和作用域规则。
  • 追问 1：宏为什么容易出副作用？
  • 答：因为它只是替换文本，参数可能被展开多次，运算优先级和副作用都容易出问题。
  • 追问 2：内联函数在哪些方面优于宏，哪些方面又不能完全替代？
  • 答：内联函数更安全、可调试、可重载；但宏还能做条件编译、字符串化、拼接标记等预处理能力。

95. 命名空间的作用是什么？

  • 答：命名空间用于组织名字、隔离模块边界、避免命名冲突，也是大型工程表达架构边界的重要手段。
  • 追问 1：命名空间只是在防重名吗？
  • 答：不止。它还能表达模块层级、约束可见范围、改善接口组织。
  • 追问 2：大型工程里如何用命名空间表达模块边界？
  • 答：通常按产品域、子系统、组件层级来划分，让名字本身携带结构信息。

96. using namespace std; 为什么在工程代码里不推荐滥用？

  • 答：因为它会把整个命名空间都引进当前作用域，容易造成命名冲突、污染头文件、降低可读性。
  • 追问 1：using namespace std; 在头文件里为什么尤其危险？
  • 答：因为任何包含这个头文件的源码都会被一并污染，影响范围非常大。
  • 追问 2：局部 using 声明和全局 using namespace 有什么差别？
  • 答：局部 using std::string; 更精确，影响范围小；全局 using namespace std; 太宽泛。

97. 为什么模板实现通常写在头文件里？

  • 答：因为模板只有在实例化时编译器才真正生成代码，而实例化常发生在使用点，所以实现通常必须对使用点可见。
  • 追问 1：模板实现为什么常写头文件？
  • 答：因为不放头文件，其他翻译单元在实例化模板时看不到实现。
  • 追问 2：如果把模板实现放 cpp，会遇到什么链接问题？
  • 答：常见是“声明能看到，定义看不到”，最后链接阶段报未定义引用。

98. 如何理解“接口设计中的所有权表达”？

  • 答：就是在 API 上清楚表达“这个参数/返回值谁拥有、谁销毁、是否共享、是否可空、是否只是观察”。
  • 追问 1：接口中的拥有型参数和非拥有型参数该怎么表达？
  • 答：独占所有权常用 unique_ptr，共享所有权常用 shared_ptr，非拥有观察常用引用、裸指针、span、string_view。
  • 追问 2：为什么现代 API 设计越来越强调 view / reference / smart pointer 的区分？
  • 答：因为这能把生命周期责任写进类型里，减少靠注释猜语义。

99. 如果让你设计一个现代 C++ API，你会优先遵守哪些原则？

  • 答：优先语义清晰、所有权明确、默认安全、少惊讶、易组合、性能成本可见；能用值语义就不用复杂指针语义。
  • 追问 1：一个好的 C++ 接口应该如何兼顾性能、可读性和安全性？
  • 答：先保证语义正确，再让性能优化建立在清晰语义之上，而不是靠隐式约定和技巧堆起来。
  • 追问 2：你会优先暴露值语义、引用语义还是指针语义，为什么？
  • 答：通常优先值语义，其次引用表达非空借用，最后才是指针表达可空或复杂所有权。

100. 如果只给你 10 分钟介绍“现代 C++ 和旧式 C++ 的核心区别”，你会怎么讲？

  • 答：现代 C++ 的核心变化是：从“手工管理资源、到处裸指针、靠约定写代码”，转向“用类型表达语义、用 RAII 自动管理资源、用模板和标准库构建抽象、用移动语义和值语义兼顾性能与安全”。
  • 追问 1：如果让你用现代 C++ 重构一套旧式 API，你最先改哪三件事？
  • 答：先梳理所有权并去掉裸资源管理；再引入 RAII/智能指针/标准库容器；最后改接口语义，让值类别、错误处理、资源边界更清晰。
  • 追问 2：现代 C++ 和旧式 C++ 在设计哲学上最核心的差异是什么？
  • 答：旧式 C++ 更依赖程序员手工维护约定；现代 C++ 更强调“让类型系统和库帮你把约束写进代码里”。
