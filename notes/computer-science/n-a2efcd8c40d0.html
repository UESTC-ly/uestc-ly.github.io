9. 安全与接口设计

  • [ ] ★★★ SQL 注入产生的原因是什么？如何防止？
  • 完整回答：
    • SQL 注入产生的前提是服务端把外部输入、请求参数、Cookie、Header、导入文件字段或上游服务返回值当成 SQL 语句片段拼接执行，使攻击者有机会改变原本的查询结构。它不是“输入里有特殊字符”这么简单，而是代码与数据边界被打破：例如登录、搜索、动态排序、批量查询、报表筛选、IN 条件和 ORDER BY 字段如果直接拼字符串，攻击者可能让条件恒真、联合查询额外字段、绕过租户条件、修改或删除数据，甚至借助数据库函数、文件权限或扩展能力扩大影响。防护的核心是参数化查询或预编译语句，让用户输入只作为绑定变量传给数据库，不能参与 SQL 语法解析；ORM 也要遵守这个原则，手写原生 SQL、动态条件构造和字符串模板仍然可能注入。对于无法参数化的结构性片段，如排序字段、排序方向、表名、报表维度，应使用服务端白名单映射，不能把客户端传来的字段名直接放进 SQL。输入校验负责限制业务格式和长度，不能替代参数化；转义也容易因数据库方言、字符集、编码和拼接上下文出错，只能作为补充。还要做分层防护：应用账号按最小权限授权，读写分离账号不要拥有 DDL、跨库、文件和高危管理权限；错误信息对外收敛，避免泄露表结构和 SQL 细节；日志记录异常模式、来源、请求 ID 和失败次数，但不记录密码、Token 等敏感明文；网关或 WAF 可拦截部分明显攻击，但不能保证覆盖所有业务语义。测试也应覆盖恶意输入、边界字符、多租户隔离条件和权限边界。失败边界也要清楚：参数化只能保护值位置，保护不了错误设计的字段拼接；只隐藏前端参数、只依赖 ORM、只做黑名单过滤或只靠数据库防火墙，都不能作为可靠的单一防线。

  • 原理解析：

    • SQL 注入的根因是信任边界放错：HTTP 参数、Cookie、Header、导入数据和上游返回都属于不可信输入，进入数据库前必须被当作“数据”。一旦程序把它们拼进 SQL 文本，数据库解析器无法知道哪些词来自业务模板、哪些词来自攻击者，代码与数据的边界就被打穿。
    • 参数化查询的安全点在协议和驱动层：SQL 模板先确定语法结构，绑定变量再作为值传入，数据库不会把绑定值重新解析成关键字、运算符或子查询。它能保护 where name = ? 这类值位置，但保护不了表名、列名、排序方向等结构位置，所以这些位置只能由服务端白名单映射产生；动态报表和排序最容易在这里破功。
    • 攻击链通常是“小拼接”导致“大越权”：条件恒真绕过登录，union 探测字段，错误回显暴露表结构，多租户条件被注释掉，写接口被改成批量更新。最小权限、错误收敛、审计和 WAF 是降低爆炸半径的防线，不是参数化的替代品；多租户系统还要把租户条件放在服务端可信上下文中，避免被客户端参数覆盖。
    • 记忆抓手：输入校验管“业务格式”，参数化管“语法边界”，授权管“能不能看这条数据”。不要把转义、黑名单、ORM 或前端隐藏参数当成单一保险，因为 SQL 方言、编码上下文和手写原生 SQL 都可能让这些措施漏掉真实攻击面；可靠答案一定是参数化优先，再叠加白名单、最小权限和可观测性。

  • [ ] ★★★ XSS 和 CSRF 有什么区别？如何防护？

  • 完整回答：
    • XSS 和 CSRF 都利用浏览器环境，但攻击前提不同。XSS 的前提是攻击者控制的内容被页面当成脚本、HTML、事件属性、URL 或 DOM 代码执行，执行位置在受害者浏览器中，风险包括读取页面可见数据、劫持交互、发起带用户凭证的请求、篡改页面和窃取非 HttpOnly 凭证。它分为存储型、反射型和 DOM 型，富文本、评论、搜索回显、错误页、Markdown 渲染、前端模板和第三方脚本都是常见入口。防护要按输出上下文编码，HTML 文本、属性、JavaScript 字符串、CSS 和 URL 的编码规则不同，不能用一个转义函数通吃；富文本要使用成熟白名单净化器，禁止危险标签、事件属性和脚本 URL；前端避免 innerHTML、字符串拼模板和不可信 DOM 注入；CSP、Trusted Types、HttpOnly、Secure 和依赖完整性校验能降低成功后的影响，但 CSP 配错、放宽 unsafe-inline 或信任过多域名会削弱效果。CSRF 的前提是用户已在目标站点登录，浏览器会自动携带 Cookie、客户端证书或某些 HTTP 认证信息，攻击者诱导浏览器向目标站点提交请求，自己不一定能读取响应，但可能完成转账、改邮箱、下单等状态变更。防护重点是让服务端能区分用户真实意图：使用不可预测、与会话绑定并在服务端校验的 CSRF Token；校验 Origin 或必要时校验 Referer；Cookie 设置 SameSite=Lax/Strict 主要限制跨站自动携带 Cookie，HttpOnly 主要降低 XSS 读取 Cookie 的风险，二者不能替代 CSRF Token 与 Origin/Referer 校验；关键操作要求二次确认或重新认证。接口还要避免用 GET 做状态变更，并正确配置 CORS，因为 CORS 只控制跨站读取和某些跨站请求权限，不等于 CSRF 防护。一旦 XSS 成功，攻击脚本可能在同源内读取页面 Token 或直接代用户发请求，所以防住 XSS 是 CSRF 防线的重要前提，但二者不能互相替代。

  • 原理解析：

    • XSS 的信任边界在“页面把什么当代码执行”：攻击者输入从评论、搜索词、富文本或 URL 进入页面后，如果落在 HTML、属性、脚本、CSS、URL 或 DOM API 的代码上下文，就会变成同源脚本。CSRF 的信任边界在“请求是否代表用户真实意图”：攻击站点不能读目标站响应，却能借浏览器自动带 Cookie 的行为发起状态变更。
    • 浏览器机制决定了两者防法不同。XSS 要按输出上下文编码、净化富文本、少用 innerHTML，再用 CSP、Trusted Types、HttpOnly 降低脚本成功后的收益；CSRF 要让服务端验证新鲜的 CSRF Token、Origin/Referer 和关键操作确认，因为攻击者构造的跨站表单或图片请求缺少这些业务意图证明。
    • SameSite、HttpOnly、CORS 容易混淆：SameSite 限制部分跨站自动带 Cookie，HttpOnly 主要防脚本读取 Cookie，CORS 主要管跨源读取和非简单请求权限。它们都不是通用安全开关，尤其 XSS 一旦进入同源页面，脚本可直接代用户调用接口，甚至读取页面里的 CSRF Token。
    • 记忆抓手：XSS 是“把输入变脚本”，重点防输出执行；CSRF 是“借浏览器带身份”，重点防伪造意图。二者都用浏览器和用户身份，但攻击因果链不同，不能用 CSRF Token 解决 XSS，也不能只靠 CSP 或 CORS 解决 CSRF。

  • [ ] ★★★ 身份认证和权限授权有什么区别？

  • 完整回答：
    • 身份认证解决“请求者是谁”，权限授权解决“这个已识别主体能不能做这件事”。认证的前提是系统收到某种身份凭据，例如密码、短信验证码、邮箱链接、OAuth/OIDC 登录结果、客户端证书、Session ID、Access Token 或多因素认证因子；认证流程要验证凭据的真实性、有效期、绑定关系和风险状态，然后产生会话、票据或安全上下文。授权发生在认证之后，但不能只在登录时做一次，因为用户访问不同资源、执行不同操作、跨租户切换、权限变更、账号封禁或数据状态变化时，结论都可能不同。授权要同时判断主体、资源、动作、数据范围、租户边界和环境条件，例如“用户 A 是否能修改租户 T 下订单 O 的退款状态”，而不是只看是否登录。常见模型中，RBAC 用角色承载权限，适合岗位清晰的后台系统，但角色膨胀时要治理；ABAC 根据用户属性、资源属性、时间、地域、设备、风险等级等条件决策，表达能力更强但规则可解释性和测试成本更高；ACL 直接维护主体与资源关系，适合细粒度共享场景。安全边界必须在服务端执行，前端隐藏按钮只是体验优化，网关粗粒度校验也不能替代业务服务的数据级授权。分布式系统还要区分用户授权和服务间授权：服务拿到调用凭证不代表可代表任意用户访问任意数据，必要时要传递并校验用户上下文、作用域和租户。常见误区是把认证成功等同于管理员权限，把 JWT 签名有效等同于权限仍然有效，把菜单权限当成接口权限，或只在查询列表时过滤数据却在详情、导出、更新接口漏做校验。失败边界包括缓存权限过久、权限变更无法及时生效、越权对象 ID 可猜测、后台任务绕过检查和审计缺失，因此应配合最小权限、拒绝默认、集中策略、单元/集成测试和授权失败日志。

  • 原理解析：

    • 认证的信任边界是凭据到身份的转换：密码、验证码、证书、Session 或 Token 只能说明系统按规则识别出某个主体。授权的信任边界是身份到资源动作的决策：同一个主体面对不同租户、订单、字段、状态和操作时，答案可能完全不同。
    • 认证机制关注凭据真实性、有效期、绑定设备、风险状态和会话建立；授权机制关注主体、资源、动作、数据范围、环境条件和策略版本。JWT 签名有效只是说明令牌没被篡改，不说明用户仍有权限；登录成功也不说明可访问任意对象，尤其不说明可跨租户、跨部门或跨数据状态操作。
    • 攻击链常见于“只认身份不查资源”：攻击者登录普通账号，猜测订单 ID，详情接口没做数据级校验，就形成水平越权；或后台菜单隐藏了按钮，但导出接口仍可直接调用，形成垂直越权。网关适合做粗粒度准入，业务服务必须做贴近数据的授权判断。
    • 防线关系要分层：默认拒绝、最小权限、集中策略、权限缓存短时有效、变更可失效、审计可追踪，分别解决误放行、权限膨胀、规则分散、状态滞后和事后追责。任何单点措施都可能被缓存、异步任务、内部接口或遗漏接口绕开，所以授权检查要贴近业务数据写在服务端关键路径上。
    • 记忆抓手：认证问“你是谁”，授权问“你能否对这个资源做这个动作”。RBAC 管岗位，ABAC 管条件，ACL 管具体关系；前端权限是显示控制，不是安全边界。

  • [ ] ★★★ 如何安全地存储用户密码？

  • 完整回答：
    • 安全存储密码的前提是承认数据库、备份、日志或内部账号将来可能泄露，因此服务端不能保存明文密码，也不能保存可逆加密后的密码作为常规方案；一旦密钥和密文同时泄露，可逆加密会让所有密码暴露。正确做法是对每个密码使用专用密码哈希算法，例如 Argon2id、bcrypt、scrypt 或合适参数的 PBKDF2，并为每个用户生成随机、足够长、唯一的盐。盐不是秘密，作用是让相同密码得到不同结果并抵抗彩虹表；真正提高离线破解成本的是慢哈希的 CPU、内存和迭代成本。普通快速哈希如 MD5、SHA-1、单次 SHA-256 或简单加盐 SHA-256 速度太快，不适合密码存储。成本参数要根据线上登录延迟、服务器容量和攻击成本定期评估，过低会失去保护意义，过高会造成登录接口被低成本拖垮，所以还要配合限速、验证码、设备指纹、风险控制、账号锁定策略和告警。可以增加 pepper 作为服务端全局秘密，但它应存放在 KMS、HSM 或独立密钥系统中，并有轮换和故障预案，不能和用户表或配置文件一起泄露。密码校验时只比较重新计算后的哈希，避免把明文写入日志、链路追踪、异常、埋点或消息队列；密码重置应使用短有效期、一次性、与账号和场景绑定的 Token，不能把原密码发给用户。注册和改密流程要校验弱密码、常见泄露密码和历史复用，同时不要用错误提示泄露账号是否存在。传输层必须使用 HTTPS，防止登录凭据在网络中被窃听，但 HTTPS 只保护传输过程，不解决服务端存储泄露后的离线破解。还要准备算法升级路径：在哈希记录中保存算法和参数版本，用户下次登录成功后渐进迁移，避免一次性强制重置带来可用性风险和集中故障风险。

  • 原理解析：

    • 密码存储的基本假设是数据库终有可能泄露，所以边界不能放在“库永远安全”。加密是可逆的，适合需要恢复明文的数据；密码校验不需要恢复原文，只需要验证用户输入是否一致，因此应使用不可逆、专门抗离线破解的密码哈希。
    • 哈希和加密要分清：普通 SHA-256 这类快速哈希适合完整性校验，不适合密码，因为攻击者拿到哈希后可高速枚举口令。Argon2id、bcrypt、scrypt、PBKDF2 通过迭代、内存或计算成本拖慢猜测；每用户随机盐让相同密码结果不同，防彩虹表和批量预计算，但盐不是秘密。
    • pepper、KMS、限速和风控是补充防线。pepper 作为服务端秘密可增加泄露后的破解门槛，但若和配置、日志或数据库一起泄露就失效；登录限速、验证码和账号锁定主要防在线猜测；HTTPS 保护传输中的明文密码，不解决服务端哈希表泄露后的离线攻击。
    • 攻击链经常从非数据库路径泄露：异常日志打印密码、链路追踪记录表单、重置链接可复用、弱密码无限尝试、错误提示暴露账号存在性。安全存储要覆盖注册、登录、改密、重置、审计和备份，而不只是选一个算法。
    • 记忆抓手：密码要“慢哈希 + 唯一盐 + 合理成本 + 可升级参数”。不能保存明文，不能把可逆加密当常规方案，也不能认为用了 bcrypt 就覆盖所有风险，参数、限速、密钥隔离、重置流程和日志卫生同样决定实际风险。

  • [ ] ★★ JWT 有哪些常见安全问题？

  • 完整回答：
    • JWT 的常见风险来自把它误认为“加密会话”或“天然安全凭证”。标准 JWS 形式的 JWT 通常只是 Base64URL 编码加签名，payload 可被任何拿到 Token 的人解码读取，签名只证明内容未被篡改且由可信密钥签发，不提供保密性，因此不能放密码、身份证号、手机号、密钥或其他敏感明文；需要保密时应使用服务端会话引用或专门的加密方案。服务端验证时必须固定允许的算法、校验签名、exp、nbf、iss、aud、sub、作用域和密钥版本，不能信任 Header 中客户端声明的 alg 或 kid 并任意取密钥，否则可能出现算法混淆、空算法、密钥注入或错误租户密钥问题。过期时间过长会扩大泄露后的窗口，过短又影响体验，所以常见设计是短期 Access Token 配合可撤销、可轮换的 Refresh Token。JWT 的难点是撤销和权限变更：用户登出、封禁、改密、角色调整后，已签发 Token 在过期前可能仍被接受，需要黑名单、Token 版本号、会话版本、短过期或集中校验来收敛风险。存储位置也有取舍：localStorage 不会自动跨站携带，但容易被 XSS 读取；Cookie 可配 HttpOnly、Secure、SameSite 降低读取和 CSRF 风险，但仍要处理跨站提交和域配置。JWT 负责认证凭据表达，不等同于授权决策，每个接口仍要根据资源、动作、租户和数据范围做服务端授权。日志、URL 参数、Referer、监控和代理缓存也可能泄露 Token，所以应避免放在查询串，并对日志脱敏。

  • 原理解析：

    • JWT 的边界是“签名凭据”，不是“加密保险箱”。常见 JWS 只做 Base64URL 编码和签名校验，任何持有者都能读 payload；签名证明内容由可信方签发且未被改动，不提供保密性。因此敏感明文应留在服务端或使用合适加密方案，不能因为看起来像乱码就当安全。
    • 验证链必须由服务端固定规则：允许算法、密钥来源、iss、aud、exp、nbf、sub、作用域和租户都要校验。若信任 Header 里的 alg 或不受控 kid，攻击者可能引入空算法、算法混淆或错误密钥，绕过认证凭据校验。
    • JWT 最大工程难点是生命周期：短期 Token 减少泄露窗口，Refresh Token 负责续期但要可撤销和轮换；登出、封禁、改密、权限变化需要版本号、黑名单或集中校验收敛风险。认证成功后仍要逐接口做授权，不能把 Token 中的角色字段当永久事实。
    • 存储位置是权衡：localStorage 避免自动 CSRF，但遇到 XSS 容易被读；Cookie 配 HttpOnly、Secure、SameSite 可降低部分风险，但仍要考虑 CSRF 和域范围。记忆抓手：JWT 防篡改，不防泄露；表达身份，不替代授权。

  • [ ] ★★ RESTful API 应该如何设计？

  • 完整回答：
    • RESTful API 设计的核心是围绕资源而不是页面或函数建模，用稳定 URI 表示资源，用 HTTP 方法表达操作语义，并让协议特性服务于可理解性、缓存、幂等和演进。典型设计中，GET /users/{id} 查询用户，POST /users 创建用户，PUT /users/{id} 整体替换，PATCH /users/{id} 局部更新，DELETE /users/{id} 删除或标记删除；路径尽量使用名词和层级关系，避免把 getUser、createOrder 这类动作塞进 URI。GET 应无副作用，不能用来扣款、下单或修改状态；PUT 和 DELETE 通常应设计为幂等，即重复请求最终效果一致；POST 默认不幂等，但支付、下单、提交表单等接口应支持幂等键、业务流水号或状态机，防止超时重试造成重复处理。状态码要表达协议层结果，例如 400 表示请求格式或参数错误，401 表示未认证，403 表示已认证但无权限，404 可用于资源不存在或按策略隐藏存在性，409 表示状态冲突，429 表示限流，5xx 表示服务端或依赖异常；响应体再提供稳定业务错误码、可读信息、字段错误和请求 ID。分页、过滤、排序要有明确约定，大数据和实时变化列表通常更适合游标分页；版本管理可放在路径、Header 或媒体类型中，关键是兼容策略、弃用周期和错误结构稳定。认证、授权、限流、审计、CORS、CSRF、签名和重放防护要按接口风险分层配置。REST 不是只能做 CRUD，复杂业务动作可以建模为子资源或命令资源，但不要为了形式牺牲事务边界和业务可读性。

  • 原理解析：

    • REST 的边界是资源语义和 HTTP 协议语义的对齐。URI 表示“哪个资源”，方法表示“怎么操作”，状态码表示协议层结果；如果把 createOrder、payNow 都塞进路径，客户端、网关、缓存、监控和文档就难以理解接口行为。
    • 浏览器、代理和网关会基于 HTTP 语义做缓存、重试和预取，所以 GET 必须避免状态变更；PUT、DELETE 设计成幂等可降低网络重试风险；POST 默认不幂等，但支付、下单这类业务仍要用幂等键、唯一流水号和状态机保护，不能把“HTTPS 已保护传输”误认为“重复提交不会发生”。
    • 认证和授权也要体现在接口层：401 是未认证，403 是已识别但无权限，404 可按策略隐藏资源存在性。CORS、CSRF、限流、签名和审计按风险配置，它们分别处理跨源读取、跨站伪造、流量滥用、请求完整性和追踪追责，不应混成一个安全开关。
    • 记忆抓手：REST 不是机械 CRUD，而是让资源、方法、状态码、幂等和版本演进可预测。复杂动作可以建成子资源或命令资源，但事务边界、错误结构和兼容策略要比形式上的“像 REST”更重要。

  • [ ] ★★ 接口如何防止重放攻击？

  • 完整回答：
    • 重放攻击的前提是攻击者获得了一次合法请求或合法凭证，并在稍后再次发送，使服务端误以为这是新的有效操作。HTTPS 能降低链路窃听和篡改风险，是基础传输保护，但它不能处理客户端泄露、日志泄露、代理误存、恶意内部调用或攻击者已经拿到完整请求后的业务重复执行。因此高风险接口通常需要时间戳、Nonce、签名和服务端去重组合使用。时间戳用于限制有效窗口，例如几分钟内有效，但要允许合理时钟偏差，并拒绝过旧或明显来自未来的请求；Nonce 应唯一、不可预测，并与调用方、Token、时间窗口或业务场景绑定，服务端在有效期内记录已使用值，重复出现就拒绝。请求签名应覆盖 HTTP 方法、路径、规范化查询参数、关键 Header、请求体摘要、时间戳和 Nonce，避免攻击者只替换未签字段；服务端要用共享密钥或非对称密钥验签，并管理密钥轮换、权限范围和泄露处置。对支付、下单、退款、发券等操作，仅有防重放还不够，还要设计业务幂等：使用幂等键、订单号、支付流水号、状态机和唯一约束，让客户端超时重试、网关重试或消息重复投递不会造成重复扣款或重复发货。认证、授权和重放防护要区分开：Token 证明调用身份，授权判断是否能操作资源，签名和 Nonce 判断请求是否新鲜，幂等保证重复请求不会重复产生业务效果。失败边界包括 Nonce 存储过期太短、集群节点不共享去重状态、签名前参数规范化不一致、把签名密钥打印到日志、允许 GET 修改状态、0-RTT 请求被重放以及只在网关校验但内部接口可绕过，所以应配合审计、限流、告警和关键操作二次校验。
  • 原理解析：
    • 重放攻击利用的是“合法请求再次出现”而不是单纯篡改内容。HTTPS 保护传输链路上的窃听和篡改，但请求可能来自客户端泄露、日志泄露、代理缓存、内部调用或攻击者已获得的完整报文，所以传输保护不能替代业务层新鲜性校验。
    • 时间戳解决有效窗口，Nonce 解决同一窗口内唯一性，签名解决关键字段未被替换。签名应覆盖方法、路径、规范化参数、请求体摘要、时间戳和 Nonce；服务端要按调用方和时间窗口记录 Nonce，集群内共享或一致，否则攻击者可换节点重放。
    • 认证、授权、防重放、幂等分别回答不同问题：Token 证明“谁在调用”，授权判断“能不能操作该资源”，Nonce/签名判断“这次请求是否新鲜完整”，幂等键和状态机保证“重复到达也不重复产生业务效果”。支付、退款、发券尤其不能只靠其中一种。
    • 误区是把所有重复都当安全攻击，或把所有安全问题都交给 HTTPS。真实系统还会有客户端超时重试、网关重试、消息重复投递和 0-RTT 重放；记忆抓手是“链路防窃听，签名防篡改，Nonce 防旧包，幂等防重复效果”。
