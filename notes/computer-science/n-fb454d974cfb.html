1. 数据库

1.1 索引与 SQL 优化

  • [ ] ★★★ 为什么数据库索引通常使用 B+ 树，而不是二叉树、红黑树或普通哈希表？

    • 简答：数据库索引通常面向磁盘页或缓存页访问，核心目标是用尽量少的随机 I/O 找到数据。B+ 树是多路平衡树，单个节点可以容纳大量键，树高通常很低，比二叉树、红黑树更适合页式存储。相比普通哈希表，B+ 树天然支持有序遍历、范围查询、排序和前缀匹配，这些都是数据库查询里的高频场景。

    • 原理/对比/实践注意：

      • 二叉树和红黑树每个节点分支少，同样数据量下树高更高；如果节点分散在磁盘页上，查询会产生更多随机 I/O。

      • B+ 树非叶子节点主要存键和指针，叶子节点存完整索引项；一个页能放更多键，扇出大，通常 3～4 层就能覆盖很大数据量。

      • B+ 树叶子节点按键有序并通过链表相连，范围扫描只需定位起点后顺序向后读，适合 BETWEEN、ORDER BY、GROUP BY 等场景。

      • 哈希索引适合等值查询，但不适合范围查询、排序和最左前缀匹配；还要处理哈希冲突。MySQL InnoDB 的主流二级索引和聚簇索引都是 B+ 树结构。

  • [ ] ★★★ 聚簇索引和非聚簇索引有什么区别？

    • 简答：聚簇索引决定数据行的物理组织方式，叶子节点直接保存完整数据行；非聚簇索引的叶子节点通常保存索引键和指向数据行的引用。InnoDB 中主键索引就是聚簇索引，二级索引叶子节点保存的是主键值，因此通过二级索引查不到所需列时还要再按主键查一次，这叫回表。PostgreSQL 的普通表不是按主键组织的聚簇表，索引项通常指向堆表中的行位置，和 InnoDB 的聚簇组织不同。

    • 原理/对比/实践注意：

      • InnoDB 表数据本身存放在主键 B+ 树的叶子节点中，所以主键范围查询通常局部性较好。

      • InnoDB 二级索引叶子节点不直接存整行，而是存二级索引列和主键值；二级索引查询如果需要非索引列，就要回到主键树查询完整行。

      • 覆盖索引可以避免回表，因为查询所需列都在二级索引里。

      • 聚簇索引通常一张表只能有一个，因为数据只能按一种主顺序组织；主键过大或随机会增加二级索引体积和页分裂成本。

  • [ ] ★★★ 什么是联合索引的最左前缀原则？

    • 简答：联合索引按定义时的列顺序组成有序键，例如 (a, b, c) 先按 a 排，再在相同 a 内按 b 排，最后按 c 排。查询条件必须从最左列开始连续使用，才能有效利用索引定位。遇到范围条件后，范围列右侧的列通常不能继续用于精确定位，但仍可能用于覆盖、过滤或部分排序，具体要看数据库优化器。

    • 原理/对比/实践注意：

      • (a, b, c) 可支持 a = ?、a = ? AND b = ?、a = ? AND b = ? AND c = ?，通常不能高效支持只按 b 或只按 c 定位。

      • 等值条件可以连续向右推进；a = ? AND b > ? AND c = ? 中，c 一般不能继续缩小 B+ 树定位范围。

      • 排序也受列顺序影响，WHERE a = ? ORDER BY b, c 可能利用索引顺序；如果排序列顺序、方向或过滤条件破坏索引有序性，可能需要额外排序。

      • MySQL 8.0 有 skip scan 等优化，PostgreSQL 也可能通过 bitmap scan 等方式组合索引，但面试和设计时仍应按最左前缀原则建立基础判断。

  • [ ] ★★★ 哪些情况可能导致索引失效？

    • 简答：索引失效通常不是索引完全不能用，而是优化器认为无法用索引高效定位，或使用索引代价高于全表扫描。常见原因包括对索引列做函数/计算、隐式类型转换、前导模糊匹配、联合索引不满足最左前缀、范围条件后列无法继续定位等。低选择性字段即使用了索引，也可能因为回表成本高而被优化器放弃。

    • 原理/对比/实践注意：

      • WHERE DATE(create_time) = ?、WHERE age + 1 = ? 会让索引列参与表达式计算，通常难以直接利用原有 B+ 树顺序；可改为范围条件或函数索引/生成列。

      • 字符串列和数字常量比较可能触发隐式转换，导致无法按索引值原样查找；应保证字段类型和参数类型一致。

      • LIKE '%abc' 不能利用普通 B+ 树从左到右的有序性，LIKE 'abc%' 通常可以利用前缀范围。

      • OR、不等于、IS NOT NULL、低选择性状态字段不一定失效，但要结合执行计划和统计信息判断。

      • 不要只背规则，最终以 EXPLAIN、扫描行数、回表次数和实际执行耗时为准。

  • [ ] ★★★ 什么是覆盖索引、回表和索引下推？

    • 简答：覆盖索引是指查询需要的列都能从某个索引中直接得到，不必再读取完整数据行。回表是指通过二级索引找到主键或行位置后，还要再访问聚簇索引或堆表取其他列。索引下推是 MySQL 中由优化器和存储引擎协作完成的优化，InnoDB 支持该能力：它把部分可在索引层判断的条件下推到存储引擎，减少无效回表。

    • 原理/对比/实践注意：

      • InnoDB 二级索引查询如果只返回索引列和主键列，可直接在二级索引完成，避免随机回表。

      • 例如索引 (name, age)，查询 SELECT age FROM t WHERE name = ? 可能是覆盖索引；如果还查 address，通常需要回表。

      • 索引下推适合联合索引中前导列用于范围定位、后续列可在索引记录上过滤的场景，可减少进入 server 层和回表的行数。

      • 覆盖索引不是越宽越好，索引列越多，写入、更新、缓存占用和页分裂成本越高，应围绕高频查询设计。

  • [ ] ★★★ 如何定位并优化一条慢 SQL？

    • 简答：先确认慢 SQL 的真实表现，包括执行时间、扫描行数、返回行数、锁等待和发生频率，再用执行计划分析访问路径。优化时优先处理过滤条件、索引、连接顺序、排序/分组、分页和不必要的数据读取。最后必须用同等数据量和实际参数复测，不能只看改写后的直觉。

    • 原理/对比/实践注意：

      • 定位入口包括慢查询日志、数据库性能视图、APM、SHOW PROCESSLIST、PostgreSQL pg_stat_statements 等。

      • EXPLAIN 关注访问类型、使用的索引、估算行数、过滤比例、排序方式、临时表和 join 方法；MySQL 可结合 EXPLAIN ANALYZE 看实际执行。

      • 常见优化包括补充合适索引、改写不可索引条件、避免 SELECT *、减少回表、调整 join 驱动表、拆分大查询、优化深分页。

      • 如果慢在锁等待，要看事务持锁时间、隔离级别、热点行和死锁日志，而不是盲目加索引。

      • 优化后检查写入成本和其他查询是否受影响，避免为一个低频查询建立过多宽索引。

  • [ ] ★★ 为什么不建议使用 SELECT *？

    • 简答：SELECT * 会读取和传输不必要的列，增加 I/O、网络和反序列化成本。它还可能破坏覆盖索引，让本来只读索引即可完成的查询变成回表查询。字段变更后，SELECT * 还可能把新增大字段或敏感字段带到业务层，增加稳定性和安全风险。

    • 原理/对比/实践注意：

      • 大字段如 TEXT、BLOB、JSON 会显著增加行读取和网络传输成本。

      • 明确列名能让接口契约更稳定，避免表结构变化影响调用方。

      • 排查慢 SQL 时，先确认是否只需要少量字段；只查必要列常常能减少回表和内存占用。

  • [ ] ★★ 深分页为什么慢？如何优化？

    • 简答：LIMIT offset, size 在 offset 很大时，数据库通常仍要扫描并丢弃前 offset 行，再返回后面的 size 行。即使走索引，也可能产生大量索引扫描和回表。优化思路是避免大 offset，改用游标分页、基于上一次最大/最小键继续查询，或先在窄索引中定位主键再延迟关联取完整行。

    • 原理/对比/实践注意：

      • ORDER BY id LIMIT 1000000, 20 需要跳过大量记录，耗时随 offset 增大。

      • 游标分页示例：WHERE id > last_id ORDER BY id LIMIT 20，适合按稳定顺序向前/向后翻页。

      • 延迟关联可以先用覆盖索引查出目标主键，再 join 原表取详情，减少大规模回表。

      • 对搜索类业务可限制最大可翻页深度，深层数据改用搜索条件收窄范围。

  • [ ] ★★ COUNT(*)、COUNT(1) 和 COUNT(column) 有什么区别？

    • 简答：COUNT(*) 统计结果集行数，不关心列值是否为 NULL；COUNT(1) 也是统计每行常量表达式，语义上通常等价于统计行数。COUNT(column) 只统计该列非 NULL 的行。性能不能简单背成某一个永远最快，现代数据库优化器通常会对 COUNT(*) 和 COUNT(1) 做等价优化。

    • 原理/对比/实践注意：

      • SQL 语义上，COUNT(expr) 统计表达式不为 NULL 的行数。

      • InnoDB 不像 MyISAM 对全表行数维护精确计数，无条件精确 COUNT(*) 通常需要扫描索引或数据。

      • 优化器可能选择最小的可用索引来完成计数，减少 I/O。

      • 如果业务接受近似值，可用统计信息或单独计数表，但要说明一致性边界。

  • [ ] ★★ IN、EXISTS 和 JOIN 应该如何选择？

    • 简答：优先按业务语义选择：需要返回关联表字段时用 JOIN，只判断是否存在时用 EXISTS 或半连接语义，只匹配一组离散值时可用 IN。现代优化器常会把 IN、EXISTS、半连接改写成相近的执行计划，所以不能只凭固定口诀判断性能。真正选择要看数据量、索引、重复行语义和执行计划。

    • 原理/对比/实践注意：

      • JOIN 可能放大结果行数，尤其是一对多关系；如果只要判断存在，EXISTS 更贴近语义。

      • IN 子查询在不少数据库中可被改写为半连接；小的常量 IN 列表通常很直观。

      • 相关子查询是否慢取决于优化器能否去相关化、是否有索引支撑。

      • 注意 NOT IN 遇到 NULL 的 SQL 三值逻辑问题，很多场景用 NOT EXISTS 更安全。

1.2 事务、锁与日志

  • [ ] ★★★ 什么是事务的 ACID？数据库如何实现它们？

    • 简答：ACID 分别是原子性、一致性、隔离性和持久性。原子性保证事务内操作要么全部成功要么全部回滚，隔离性保证并发事务之间不会以破坏规则的方式互相干扰，持久性保证提交后的结果在崩溃后仍能恢复。一致性更多是目标属性，由数据库约束、事务机制和业务规则共同保证。

    • 原理/对比/实践注意：

      • 原子性通常依赖 Undo Log 或类似回滚机制，失败时按旧版本撤销修改。

      • 持久性依赖 Redo Log/WAL，提交前按规则把日志落盘，崩溃后重放恢复。

      • 隔离性依赖锁、MVCC、谓词锁或序列化机制，不同隔离级别成本不同。

      • 一致性不是单个日志就能实现的；数据库能保证约束、触发器等规则，跨系统业务一致性还需要应用层设计。

  • [ ] ★★★ 数据库有哪些事务隔离级别？分别解决什么问题？

    • 简答：SQL 标准定义了读未提交、读已提交、可重复读和可串行化四个隔离级别，隔离性依次增强。读未提交可能脏读；读已提交避免脏读但可能不可重复读；可重复读避免同一行前后读取不一致；可串行化目标是让并发结果等价于串行执行。具体数据库实现有差异，不能把标准现象和某个数据库实现混为一谈。

    • 原理/对比/实践注意：

      • 脏读是读到其他事务未提交数据；不可重复读是同一事务两次读同一行结果不同；幻读是同一范围两次查询出现新增/消失的行。

      • InnoDB 默认可重复读，通过 MVCC 一致性读和 next-key lock 在很多当前读场景下抑制幻读，但普通快照读看到的是事务快照。

      • PostgreSQL 的 Read Committed 每条语句获取一个快照，Repeatable Read 使用事务级快照、语义接近快照隔离；Serializable 才通过 Serializable Snapshot Isolation（SSI）检测并阻止不可串行化的执行。

      • 隔离级别越高，通常并发冲突、锁等待、回滚重试或性能成本越高。

  • [ ] ★★★ MVCC 是什么？它如何提高并发性能？

    • 简答：MVCC 是多版本并发控制，通过为数据保留多个版本，让读操作按事务可见性规则读取合适版本。它让普通读不必阻塞写，写也不必阻塞普通快照读，从而提高读写并发能力。MVCC 不能替代所有锁，更新、删除、唯一约束检查和当前读仍可能需要加锁或冲突检测。

    • 原理/对比/实践注意：

      • InnoDB 通过隐藏事务 ID、回滚指针和 Undo 版本链构造一致性视图；PostgreSQL 通过行版本上的 xmin/xmax 等元数据判断可见性。

      • 快照读根据事务开始或语句开始时的快照读取可见版本，具体取决于隔离级别和数据库实现。

      • MVCC 带来版本清理成本：InnoDB 需要 purge 清理 Undo 历史版本，PostgreSQL 需要 vacuum 回收死元组。

      • 长事务会阻碍旧版本清理，导致 Undo 或表膨胀，进而影响性能。

  • [ ] ★★★ 快照读和当前读有什么区别？

    • 简答：快照读读取事务可见的一致性版本，通常不加锁，也不一定是数据库中最新提交的版本。当前读读取最新已提交并符合隔离规则的数据，通常会对读到的记录或范围加锁，以便后续修改安全。普通 SELECT 多数情况下是快照读，SELECT ... FOR UPDATE、UPDATE、DELETE 属于当前读。

    • 原理/对比/实践注意：

      • InnoDB 在可重复读下，事务第一次一致性读会建立 Read View，后续普通读复用该快照。

      • 当前读必须看到最新可修改版本，否则会基于过期数据更新，破坏并发正确性。

      • SELECT ... LOCK IN SHARE MODE/FOR SHARE、FOR UPDATE 会加锁，常用于扣库存、抢任务等场景。

      • 快照读适合报表和普通查询；涉及“读后马上改”的业务，应使用条件更新、当前读或乐观锁方案。

  • [ ] ★★★ 行锁、表锁、间隙锁、临键锁分别是什么？

    • 简答：行锁锁定具体记录，表锁锁定整张表或表级操作范围；行锁并发度更高，但依赖索引定位时效果最好。间隙锁锁定索引记录之间的范围，防止其他事务在范围内插入新记录。临键锁是记录锁加间隙锁，InnoDB 在可重复读的部分当前读场景用它防止幻读。

    • 原理/对比/实践注意：

      • InnoDB 的行锁本质上锁索引记录；条件没有有效索引时，可能扫描并锁住大量记录，表现得接近表级阻塞。

      • 间隙锁只锁范围不锁已有记录本身，主要限制插入。

      • 临键锁覆盖左开右闭或类似的索引区间，既锁记录也锁相邻间隙。

      • PostgreSQL 不使用 InnoDB 这种 next-key lock 实现幻读控制；它在可串行化中使用 SSI 和谓词锁等机制。

  • [ ] ★★★ 数据库死锁是如何产生的？如何排查和避免？

    • 简答：死锁是多个事务互相持有对方需要的锁，形成循环等待，导致谁都无法继续。数据库一般会检测死锁并回滚其中一个事务，让另一个继续执行。处理死锁既要看错误日志和事务锁等待信息，也要在业务上统一加锁顺序、缩短事务和降低锁范围。

    • 原理/对比/实践注意：

      • 典型例子：事务 A 先锁用户 1 再锁用户 2，事务 B 先锁用户 2 再锁用户 1。

      • MySQL 可看 SHOW ENGINE INNODB STATUS、Performance Schema；PostgreSQL 可看日志、pg_locks、pg_stat_activity。

      • 避免方式包括固定资源访问顺序、按主键排序批量更新、拆小事务、建立合适索引、避免事务内调用慢外部接口。

      • 应用层要把死锁错误视为可重试的并发异常，但重试必须有次数上限和幂等保证。

  • [ ] ★★★ Redo Log、Undo Log 和 Binlog 分别有什么作用？

    • 简答：Redo Log 记录物理页或近似物理层面的修改，用于崩溃恢复，保证已提交事务的持久性。Undo Log 记录回滚所需的旧版本，用于事务回滚和 MVCC 一致性读。Binlog 是 MySQL server 层的逻辑日志，主要用于主从复制、时间点恢复和审计归档。

    • 原理/对比/实践注意：

      • InnoDB 写入通常遵循 WAL 思想：先写日志，再在合适时机刷脏页。

      • Undo 不只是回滚日志，也支撑旧版本读取；长事务会使 Undo 版本长期不能清理。

      • Binlog 有 statement、row、mixed 等格式；生产复制通常更偏向 row 格式以减少歧义。

      • MySQL 为保证 Redo 和 Binlog 一致提交，引入两阶段提交；PostgreSQL 对应崩溃恢复和复制主要依赖 WAL，不存在 MySQL Binlog 这一层。

  • [ ] ★★ 为什么大事务风险较高？

    • 简答：大事务会长时间持有锁，占用大量日志和版本资源，失败时回滚成本也高。它还可能阻碍 MVCC 旧版本清理，造成 Undo 膨胀或表膨胀。对于复制系统，大事务会形成大日志批次，增加主从延迟和恢复时间。

    • 原理/对比/实践注意：

      • 批量更新、批量删除应分批提交，控制每批行数和事务时长。

      • 事务内不要做慢网络调用、用户交互等待或大文件处理。

      • 大事务失败后的回滚可能比执行更慢，并持续占用资源。

      • 需要配合监控事务时长、锁等待、复制延迟和 Undo/WAL 增长。

  • [ ] ★★ 什么是乐观锁和悲观锁？各适用于什么场景？

    • 简答：悲观锁假设冲突经常发生，所以先加锁再操作，例如 SELECT ... FOR UPDATE 或数据库行锁。乐观锁假设冲突较少，先读数据，提交时用版本号、时间戳或 CAS 条件检查是否被别人修改。冲突少、读多写少适合乐观锁；冲突高、必须串行化的关键资源更适合悲观锁或原子条件更新。

    • 原理/对比/实践注意：

      • 乐观锁常见 SQL：UPDATE t SET stock = stock - 1, version = version + 1 WHERE id = ? AND version = ?。

      • 悲观锁减少重试，但会增加等待、死锁和连接占用。

      • 乐观锁失败后要重试或返回冲突，重试必须有限制，业务操作要幂等。

      • 高并发扣库存常用条件更新、Redis 原子脚本、队列串行化等组合方案。

  • [ ] ★★ 主从复制的基本原理是什么？如何处理复制延迟？

    • 简答：主从复制通常是主库提交变更日志，从库拉取或接收日志后重放，从而获得主库数据副本。MySQL 主要基于 Binlog 复制，PostgreSQL 常见物理流复制基于 WAL。复制延迟来自日志传输、从库重放速度、长事务、大事务、网络和从库负载。

    • 原理/对比/实践注意：

      • 异步复制性能好但主库宕机时可能丢失未复制数据；半同步复制降低丢失风险但增加提交延迟。

      • 读写分离场景要处理“写后读”一致性，关键读可走主库、按用户短时间读主库，或等待复制位点追上。

      • 大事务会让从库长时间重放一个事务，造成延迟尖刺。

      • 监控复制延迟不能只看秒数，还要结合日志位点、重放队列和业务读一致性要求。

1.3 数据库设计

  • [ ] ★★★ 数据库三大范式是什么？为什么实际项目中有时会反范式设计？

    • 简答：第一范式要求字段原子化，第二范式要求非主属性完全依赖主键，第三范式要求非主属性不传递依赖主键。范式化能减少冗余、更新异常、插入异常和删除异常。实际项目有时会为了查询性能、减少 join、降低跨库访问成本而反范式，但必须配套一致性维护方案。

    • 原理/对比/实践注意：

      • 范式适合核心事实数据建模，例如订单、用户、商品基础信息应避免无意义重复。

      • 反范式常见于订单快照、报表宽表、搜索索引、缓存表，把查询所需字段冗余存储。

      • 冗余字段会带来一致性问题，可通过事务内同步、异步事件、CDC、定期校验和补偿修复。

      • 面试回答要强调“先保证正确模型，再针对明确性能瓶颈反范式”，不是一开始就无约束堆宽表。

  • [ ] ★★★ 如何设计一个合理的主键？自增 ID、UUID 和分布式 ID 如何选择？

    • 简答：合理主键应稳定、唯一、尽量短、不可变，并与存储引擎的索引组织相匹配。InnoDB 中主键也是聚簇索引，趋势递增的短主键通常有更好的插入局部性和更小的二级索引。自增 ID 简单高效但可能暴露规模且不适合多写节点直接生成；UUID 全局唯一但较长且随机；分布式 ID 适合多节点生成，需关注时钟、趋势性和可用性。

    • 原理/对比/实践注意：

      • 自增 ID 适合单库单主或由数据库统一生成的场景，页分裂少、索引紧凑。

      • 随机 UUID 写入 InnoDB 聚簇索引可能导致页分裂和缓存命中下降；可使用有序 UUID、UUIDv7、ULID 或数据库函数改善局部性。

      • Snowflake 类 ID 趋势递增、可分布式生成，但依赖时间，需处理时钟回拨和机器号分配。

      • 不建议使用会变化的业务字段作主键；业务唯一性可用唯一索引约束。

  • [ ] ★★ 分库分表会带来哪些问题？

    • 简答：分库分表能缓解单库容量和吞吐瓶颈，但会显著增加系统复杂度。它会带来路由、跨库事务、跨库 join、全局唯一 ID、分页排序、扩容迁移和数据倾斜问题。只有在单库优化、索引、缓存、读写分离等手段不足时，才应认真考虑分库分表。

    • 原理/对比/实践注意：

      • 分片键选择决定数据分布和查询路由，选错会造成热点或大量广播查询。

      • 跨分片事务通常要用最终一致性、事务消息、Saga/TCC 等方案，成本高于单库事务。

      • 全局排序和分页需要多分片归并，深分页尤其昂贵。

      • 扩容要考虑重分片、双写、数据校验、灰度切流和回滚方案。

  • [ ] ★★ 水平分表和垂直分表有什么区别？

    • 简答：水平分表是按行拆分，把同一结构的数据按用户 ID、时间、哈希等规则分到多个表或库。垂直分表是按列或业务模块拆分，把不同字段或不同实体拆到不同表或库。水平拆主要解决单表数据量和读写吞吐问题，垂直拆主要解决表过宽、冷热字段混杂或业务边界不清的问题。

    • 原理/对比/实践注意：

      • 水平拆后要处理分片路由、跨分片查询、扩容和全局 ID。

      • 垂直拆常把大字段、低频字段拆出去，减少主表行宽，提高缓存命中。

      • 垂直分库还涉及服务和业务边界拆分，跨库 join 和事务会变复杂。

      • 选择拆分方式要基于瓶颈：容量和写入压力偏水平，表宽和模块耦合偏垂直。

2. 操作系统与 Linux

  • [ ] ★★★ 进程、线程和协程有什么区别？

    • 简答：进程是资源分配和隔离的基本单位，拥有独立地址空间、文件描述符等资源。线程是 CPU 调度的基本单位，同一进程内线程共享地址空间和大部分进程资源。协程通常由用户态运行时调度，切换成本低，适合大量 I/O 等待任务，但是否能并行取决于运行时和底层线程模型。

    • 原理/对比/实践注意：

      • 进程隔离强，一个进程崩溃通常不直接破坏另一个进程，但进程间通信成本更高。

      • 线程共享内存，通信方便，但需要锁、原子操作等同步机制；一个线程的内存错误可能影响整个进程。

      • 协程切换一般不需要内核调度，适合高并发网络服务；遇到阻塞系统调用时需要非阻塞 I/O 或调度器接管。

      • 多核并行需要多个内核线程同时运行；单线程协程更多是并发而不是并行。

  • [ ] ★★★ 进程间通信有哪些方式？应该如何选择？

    • 简答：常见 IPC 包括管道、命名管道、消息队列、共享内存、信号、Socket、Unix Domain Socket、文件和内存映射等。选择时看通信范围、数据量、延迟、吞吐、可靠性和同步复杂度。高吞吐同机通信常用共享内存加同步机制，跨机器通信通常用 Socket 或 RPC。

    • 原理/对比/实践注意：

      • 匿名管道适合有亲缘关系进程的单向字节流通信；命名管道可用于无亲缘关系进程。

      • 消息队列提供消息边界，使用简单，但可能有内核队列容量和拷贝开销。

      • 共享内存通常数据拷贝最少、吞吐潜力最高，但实际性能仍受同步、缓存一致性和数据布局影响，并且必须额外处理互斥、可见性和生命周期。

      • 信号适合事件通知，不适合传输大量数据。

      • Unix Domain Socket 适合同机服务间通信，保留 Socket 编程模型且通常比 TCP 本地通信开销更低。

  • [ ] ★★★ 用户态和内核态有什么区别？系统调用的过程是什么？

    • 简答：用户态运行普通应用代码，权限受限，不能直接访问硬件和关键内核数据；内核态运行操作系统内核代码，拥有更高权限。系统调用是用户程序请求内核服务的标准入口，例如文件 I/O、网络 I/O、进程管理。调用过程通常是用户态准备参数，通过特定指令陷入内核，内核校验参数并执行服务，再把结果返回用户态。

    • 原理/对比/实践注意：

      • CPU 通过特权级隔离用户程序和内核，避免应用随意破坏系统。

      • 系统调用不是普通函数调用，会发生模式切换，并可能伴随调度、阻塞或数据拷贝。

      • 参数来自用户空间时，内核必须校验地址、权限和长度，防止非法访问。

      • 频繁系统调用会带来开销，因此高性能 I/O 常用批量、缓冲、零拷贝或异步接口减少切换。

  • [ ] ★★★ 什么是上下文切换？为什么频繁切换会影响性能？

    • 简答：上下文切换是 CPU 从一个执行流切换到另一个执行流时，保存当前寄存器、程序计数器、栈指针、调度状态并恢复另一个执行流状态的过程。进程切换通常还涉及地址空间切换，线程切换相对轻一些。频繁切换会消耗 CPU 时间，并破坏缓存和 TLB 局部性，导致有效业务计算下降。

    • 原理/对比/实践注意：

      • 上下文切换可能由时间片耗尽、阻塞 I/O、锁等待、中断或更高优先级任务触发。

      • 进程切换可能需要切换页表；线程共享地址空间，但仍需保存和恢复寄存器、栈等状态。

      • 模式切换是用户态和内核态之间的切换，不等同于调度到另一个线程，但也有开销。

      • 排查时可关注 vmstat 的 cs、pidstat -w、perf sched 等指标。

  • [ ] ★★★ 什么是虚拟内存？它解决了什么问题？

    • 简答：虚拟内存为每个进程提供独立、连续的虚拟地址空间，再由页表映射到物理内存或磁盘。它解决了进程隔离、地址空间管理、内存不足时的按需加载和换出问题。应用看到的是虚拟地址，操作系统和 MMU 负责地址转换、权限检查和页面管理。

    • 原理/对比/实践注意：

      • 虚拟内存让每个进程都像独占一大片连续内存，简化编程模型。

      • 分页机制支持按需加载，只有访问到的页才需要调入物理内存。

      • 内存映射文件可把文件内容映射到虚拟地址空间，常用于高效文件访问和共享内存。

      • swap 能缓解物理内存不足，但大量换入换出会导致性能急剧下降。

  • [ ] ★★★ 什么是缺页中断？页面置换算法有哪些？

    • 简答：缺页中断是进程访问的虚拟页当前不在物理内存，CPU 触发异常进入内核处理。内核会检查访问是否合法，若合法则从磁盘、文件映射或零页分配中把页面准备好，更新页表后恢复执行。若物理内存不足，系统需要选择一些页面换出，这就涉及页面置换算法。

    • 原理/对比/实践注意：

      • 缺页可分为轻微缺页和重大缺页；重大缺页需要磁盘 I/O，成本高。

      • 常见置换算法包括 FIFO、LRU、Clock/Second Chance、LFU 等；真实操作系统常用近似 LRU 的工程实现。

      • FIFO 简单但可能出现 Belady 异常；LRU 符合局部性但精确实现成本高；Clock 用引用位近似 LRU。

      • 频繁缺页和 swap 抖动通常说明工作集超过物理内存，需要优化内存占用或扩容。

  • [ ] ★★★ 什么是死锁？死锁产生的四个必要条件是什么？

    • 简答：死锁是多个执行实体因互相等待对方持有的资源而永久无法推进。死锁产生通常需要四个必要条件：互斥、占有且等待、不可抢占、循环等待。破坏任意一个条件都可以预防死锁，但实际系统常结合避免、检测和恢复策略。

    • 原理/对比/实践注意：

      • 互斥：资源一次只能被一个线程或进程使用。

      • 占有且等待：持有部分资源时继续等待其他资源。

      • 不可抢占：资源不能被强制夺走，只能由持有者释放。

      • 循环等待：A 等 B，B 等 C，C 又等 A。

      • 工程上常用固定加锁顺序、一次性申请资源、锁超时、死锁检测、事务回滚等手段处理。

  • [ ] ★★★ Linux 的 I/O 多路复用是什么？select、poll、epoll 有何区别？

    • 简答：I/O 多路复用允许一个线程同时监听多个文件描述符的就绪事件，适合大量网络连接。select、poll 每次调用都需要把关注集合传给内核，并线性扫描判断就绪；select 还受 fd_set 大小限制。epoll 把关注集合保存在内核中，通过就绪队列返回事件，通常更适合大量连接、少量活跃的场景。

    • 原理/对比/实践注意：

      • select 使用位图集合，文件描述符数量受限制，且每次要重新设置集合。

      • poll 使用数组结构，没有 select 那种固定数量限制，但仍需线性扫描。

      • epoll 通过 epoll_ctl 注册事件，通过 epoll_wait 等待就绪事件，避免每次重复传递完整集合。

      • epoll 支持水平触发和边缘触发；边缘触发要配合非阻塞 I/O 并循环读写到 EAGAIN，否则可能丢处理机会。

      • I/O 多路复用解决的是等待大量 I/O 的调度问题，不代表业务处理本身不会阻塞。

  • [ ] ★★ 阻塞、非阻塞、同步和异步分别是什么？

    • 简答：阻塞/非阻塞描述调用方在操作不能立即完成时是否等待；同步/异步描述结果完成是由调用方主动等待/轮询，还是由系统通过回调、事件或通知告诉调用方。它们是两个维度，不能简单混为一谈。网络编程里，非阻塞 I/O 加事件循环通常是同步非阻塞模型，而真正异步 I/O 是提交请求后由内核或运行时完成并通知。

    • 原理/对比/实践注意：

      • 阻塞读：没有数据时线程挂起等待。

      • 非阻塞读：没有数据立即返回 EAGAIN/EWOULDBLOCK。

      • 同步 I/O：数据拷贝完成通常仍由调用线程参与等待或发起。

      • 异步 I/O：提交请求后立即返回，完成后通过完成队列、信号或回调通知。

  • [ ] ★★ 零拷贝是什么？常见实现方式有哪些？

    • 简答：零拷贝是减少数据在用户态和内核态之间来回复制的技术目标，不一定是绝对零次复制。它通过让数据尽量在内核缓冲区、页缓存和设备之间流转，减少 CPU 拷贝和上下文切换。常见方式包括 mmap、sendfile、splice、DMA、以及支持 scatter-gather 的网卡发送。

    • 原理/对比/实践注意：

      • 传统文件发送可能经历磁盘到页缓存、页缓存到用户缓冲、用户缓冲到 socket 缓冲、socket 到网卡多次复制。

      • sendfile 可把文件页缓存直接发送到 socket，常用于静态文件服务。

      • mmap 把文件映射到用户空间，减少 read 复制，但仍要注意缺页和内存压力。

      • 零拷贝优化的是数据搬运路径，不会消除协议处理、磁盘 I/O 或业务计算成本。

  • [ ] ★★ 堆和栈有什么区别？内存泄漏和内存溢出有什么区别？

    • 简答：栈主要保存函数调用帧、局部变量和返回地址，通常由编译器和运行时自动管理；堆用于动态分配对象，生命周期更灵活，需要由 GC 或程序显式释放。内存泄漏是已不再需要的对象仍被引用或未释放，导致内存持续占用。内存溢出是可用内存或某个区域容量不足，无法继续分配。

    • 原理/对比/实践注意：

      • 栈分配和释放速度快，但容量通常较小，递归过深可能栈溢出。

      • 堆容量更大，但分配、回收和碎片管理成本更高。

      • Java/Go 等 GC 语言也会内存泄漏，例如对象被全局 map、缓存、goroutine 或 listener 持有。

      • 内存溢出可能由泄漏引起，也可能由瞬时峰值、配置过小或大对象分配导致。

  • [ ] ★★ 什么是孤儿进程和僵尸进程？如何处理？

    • 简答：孤儿进程是父进程先退出而子进程仍在运行的进程，它会被 init/systemd 等进程接管。僵尸进程是子进程已经退出，但父进程还没有通过 wait/waitpid 回收其退出状态，进程表项暂时保留。孤儿进程通常不是问题，僵尸进程大量堆积会耗尽进程表资源。

    • 原理/对比/实践注意：

      • 僵尸进程本身不再占用大量内存和 CPU，但占用 PID 和进程表项。

      • 父进程应处理 SIGCHLD，或定期调用 wait/waitpid 回收子进程。

      • 如果父进程异常，子进程被接管后通常会被新的父进程回收。

      • 排查可用 ps 查看状态为 Z 的进程，并定位其父进程。

  • [ ] ★★ CPU 使用率很高时，你会如何排查？

    • 简答：先确认是整机 CPU 高还是某个进程高，再细分到线程、系统态/用户态、中断、I/O wait 等维度。对业务进程，要结合线程栈、火焰图、GC 日志、锁等待和请求流量判断原因。常见原因包括计算热点、死循环、锁竞争、自旋、频繁 GC、异常日志风暴和中断过高。

    • 原理/对比/实践注意：

      • top/htop 看整机和进程，pidstat 看进程/线程 CPU，top -H -p <pid> 看线程。

      • Java 可用 jstack 把高 CPU 线程 ID 转十六进制后匹配栈；Go 可用 pprof。

      • us 高偏业务计算，sy 高偏系统调用/内核开销，wa 高偏 I/O 等待，si/hi 高偏软/硬中断。

      • 优化前先保留现场，包括流量、发布版本、慢接口、线程栈和性能采样。

  • [ ] ★★ 服务器内存持续上涨时，你会如何排查？

    • 简答：先区分是进程 RSS 增长、语言堆增长、堆外内存增长，还是 Linux 页缓存增长。页缓存增长不一定是泄漏，通常可被回收；进程 RSS 持续增长才更需要关注。排查时结合 OOM 日志、对象快照、连接数、缓存大小、线程数、文件映射和直接内存使用。

    • 原理/对比/实践注意：

      • free 中 buff/cache 高不等于内存泄漏，要看 available 和是否持续触发 swap/OOM。

      • Java 关注 heap、metaspace、direct memory、线程栈；可用 heap dump、GC 日志、NMT。

      • Go 关注 heap、goroutine、cgo、mmap；可用 pprof 和 runtime 指标。

      • 常见原因包括无界缓存、连接未关闭、对象被全局集合引用、大请求堆积、日志/监控队列积压。

3. 计算机网络

  • [ ] ★★★ 从浏览器输入一个 URL 到页面返回，中间发生了什么？

    • 简答：浏览器先解析 URL，查缓存和 DNS 得到目标 IP，然后根据路由和 ARP/NDP 找到下一跳，建立传输连接。HTTP/1.1 和 HTTP/2 通常基于 TCP，HTTPS 还要进行 TLS 握手；HTTP/3 基于 QUIC/UDP，把传输和加密握手做了整合。请求到达负载均衡和应用服务后，服务可能访问缓存、数据库和下游系统，生成响应返回浏览器，浏览器再解析 HTML、CSS、JS 并渲染页面。

    • 原理/对比/实践注意：

      • DNS 查询会先查浏览器和系统等本地缓存；未命中时客户端通常请求递归解析器，再由递归解析器按需迭代查询根、顶级域和权威 DNS 服务器。

      • 同网段通信需要 ARP 获取 MAC；跨网段发送给网关，由路由器逐跳转发。

      • TCP 建连经历三次握手；TLS 握手验证证书并协商密钥；已有连接可能复用或使用会话恢复。

      • 服务端链路可能包括 CDN、WAF、L4/L7 负载均衡、网关、应用、缓存、数据库和消息队列。

      • 浏览器渲染包括构建 DOM/CSSOM、布局、绘制、合成；外部资源加载和 JS 执行会影响首屏时间。

  • [ ] ★★★ OSI 七层模型和 TCP/IP 模型分别是什么？

    • 简答：OSI 七层模型从下到上是物理层、数据链路层、网络层、传输层、会话层、表示层、应用层，用于清晰描述网络职责分层。TCP/IP 模型更贴近互联网实现，常划分为链路层、网络层、传输层、应用层。实际协议栈并不总是严格对应 OSI 七层，但分层思想有助于定位问题和理解封装/解封装。

    • 原理/对比/实践注意：

      • 物理层处理比特传输；数据链路层处理帧、MAC、同链路通信；网络层处理 IP 和路由。

      • 传输层处理端到端连接、可靠性、端口和拥塞控制，典型协议是 TCP/UDP/QUIC 的传输部分。

      • 应用层包括 HTTP、DNS、SMTP、RPC 等；TLS 通常夹在应用协议和传输层之间，不必机械归类。

      • 发送数据时从应用层逐层加头封装，接收端逐层解析并交给上层。

  • [ ] ★★★ TCP 和 UDP 有什么区别？分别适用于哪些场景？

    • 简答：TCP 是面向连接的字节流协议，提供可靠传输、顺序交付、流量控制和拥塞控制。UDP 是无连接的数据报协议，不保证可靠性、顺序和不重复，但保留消息边界，头部小、延迟低、应用控制空间更大。需要可靠有序传输的场景常用 TCP，需要低延迟、可容忍丢包或应用自定义可靠性的场景常用 UDP。

    • 原理/对比/实践注意：

      • TCP 适合 Web、文件传输、数据库连接、邮件等。

      • UDP 适合 DNS、实时音视频、游戏、监控上报等；QUIC 也基于 UDP 实现可靠传输和拥塞控制。

      • TCP 是字节流，没有消息边界，应用层需要自行 framing。

      • UDP 单个数据报过大可能 IP 分片，丢任一分片会导致整个报文不可用，实践中应控制报文大小。

  • [ ] ★★★ TCP 为什么需要三次握手？两次可以吗？

    • 简答：三次握手用于确认双方的发送和接收能力，并同步双方初始序列号。两次握手只能让服务端确认客户端能发、服务端能收，也让客户端确认服务端能收，但服务端还不能确认客户端能收自己的响应。三次握手还能避免历史重复连接请求导致服务端误建立连接。

    • 原理/对比/实践注意：

      • 第一次：客户端发送 SYN 和客户端初始序列号。

      • 第二次：服务端返回 SYN+ACK，确认客户端序列号并发送服务端初始序列号。

      • 第三次：客户端 ACK 服务端序列号，服务端确认客户端能收到自己的报文。

      • 如果只有两次，旧 SYN 到达服务端可能让服务端分配连接资源，而客户端并不知情或不需要该连接。

  • [ ] ★★★ TCP 为什么通常需要四次挥手？

    • 简答：TCP 是全双工协议，两个方向的数据流可以独立关闭。一方发送 FIN 只表示自己不再发送数据，但仍可以接收对方数据；对方收到后先 ACK，等自己数据也发送完再发送 FIN。因此关闭过程通常表现为 FIN、ACK、FIN、ACK 四个报文。

    • 原理/对比/实践注意：

      • 第一次 FIN：主动关闭方表示本方向发送结束。

      • 第二次 ACK：被动关闭方确认收到 FIN，但可能还有数据要发。

      • 第三次 FIN：被动关闭方也发送完毕，请求关闭自己的发送方向。

      • 第四次 ACK：主动关闭方确认对方 FIN，随后进入 TIME_WAIT。

      • 如果被动方收到 FIN 时也正好无数据要发，ACK 和 FIN 可能合并，所以“四次”是通常情况，不是每次都必须拆成四个独立报文。

  • [ ] ★★★ TIME_WAIT 状态有什么作用？过多时如何分析？

    • 简答：TIME_WAIT 通常出现在主动关闭连接的一方，用来保证最后一个 ACK 可重传，并让旧连接中的迟到报文在网络中自然消失。它持续 2MSL，避免相同四元组的新连接被旧报文干扰。TIME_WAIT 过多要先判断是谁主动关闭、连接创建频率是否异常、是否缺少连接复用，而不是直接调内核参数。

    • 原理/对比/实践注意：

      • 如果最后 ACK 丢失，被动关闭方会重发 FIN，主动关闭方在 TIME_WAIT 中可再次 ACK。

      • 高并发短连接客户端或网关主动关闭时，容易积累大量 TIME_WAIT。

      • 分析维度包括本地/远端地址端口、应用连接池、HTTP keep-alive、上游超时、负载均衡行为和发布变更。

      • 治理方式优先是连接复用、调整主动关闭方、扩展端口范围、优化超时；内核参数调整要理解版本语义和风险。

  • [ ] ★★★ TCP 如何保证可靠传输？

    • 简答：TCP 通过序列号、确认应答、重传机制、校验和、滑动窗口、流量控制和拥塞控制共同保证可靠传输。序列号让接收方能按序重组和去重，ACK 告诉发送方哪些数据已收到。超时重传、快速重传等机制处理丢包，窗口机制控制发送速率和在途数据量。

    • 原理/对比/实践注意：

      • 校验和用于发现传输中的比特错误，但不是加密完整性保护。

      • 累积 ACK 表示某个序号之前的数据都已收到；SACK 可更精确告知缺失片段。

      • 流量控制看接收方缓冲区能力，避免把接收方打爆。

      • 拥塞控制看网络承载能力，常见机制包括慢启动、拥塞避免、快速重传、快速恢复，具体算法如 Reno、CUBIC、BBR。

  • [ ] ★★★ TCP 流量控制和拥塞控制有什么区别？

    • 简答：流量控制解决“接收方来不来得及收”的问题，拥塞控制解决“网络链路承不承受得住”的问题。流量控制主要依赖接收窗口 rwnd，由接收方通告剩余缓冲区。拥塞控制主要依赖拥塞窗口 cwnd，由发送方根据丢包、延迟和 ACK 反馈估计网络容量。

    • 原理/对比/实践注意：

      • 实际可发送窗口通常受 min(rwnd, cwnd) 限制。

      • 接收方应用读取慢会导致 rwnd 变小，甚至出现零窗口。

      • 网络拥塞时，丢包或延迟上升会使拥塞算法降低发送速率。

      • 慢启动并不是一直慢，而是指数增长探测容量；拥塞避免阶段增长更保守。

  • [ ] ★★★ TCP 为什么会发生粘包和拆包？如何解决？

    • 简答：TCP 是面向字节流的协议，不保留应用层消息边界。发送方多次写入的数据可能被合并成一个 TCP 段，接收方一次读取也可能只读到半个应用消息或多个消息。解决方式是在应用层协议中明确消息边界，例如固定长度、分隔符、长度字段或自描述格式。

    • 原理/对比/实践注意：

      • “粘包/拆包”不是 TCP 错误，而是应用层把字节流误当成消息流。

      • 固定长度实现简单但浪费空间且扩展性差。

      • 分隔符适合文本协议，但要处理转义和内容中出现分隔符的问题。

      • 长度字段最常见，先读固定头部得到 body 长度，再循环读取完整 body。

      • HTTP、Redis RESP、gRPC/HTTP2 都有自己的 framing 规则。

  • [ ] ★★★ HTTP/1.1、HTTP/2 和 HTTP/3 的主要区别是什么？

    • 简答：HTTP/1.1 引入持久连接和管线化，但同一连接上的响应仍按顺序返回，容易出现应用层队头阻塞。HTTP/2 使用二进制分帧、多路复用和 HPACK 头部压缩，一个 TCP 连接上可并发多个流，但 TCP 层丢包仍会阻塞整个连接的数据交付。HTTP/3 基于 QUIC/UDP，提供传输层多路复用、TLS 1.3 集成和更快连接迁移，减少 TCP 队头阻塞影响。

    • 原理/对比/实践注意：

      • HTTP/1.1 通常通过多个 TCP 连接提高并发，但连接数过多会增加开销。

      • HTTP/2 的多路复用解决了 HTTP 层的请求排队问题，但底层 TCP 仍按字节流保序。

      • HTTP/3 的不同流在 QUIC 层独立处理，某个流丢包不必阻塞其他流的应用数据交付。

      • HTTP/2 和 HTTP/3 都支持头部压缩，但算法不同：HTTP/2 是 HPACK，HTTP/3 是 QPACK。

  • [ ] ★★★ HTTPS 的 TLS 握手过程是什么？

    • 简答：TLS 握手的目标是验证服务端身份、协商加密参数和生成会话密钥，之后用对称加密保护 HTTP 数据。客户端会发送支持的 TLS 版本、密码套件和随机数，服务端返回证书、选择的参数并完成密钥协商。TLS 1.3 简化了握手并默认使用前向安全的密钥交换，通常比 TLS 1.2 少一次往返。

    • 原理/对比/实践注意：

      • 证书验证包括检查域名、有效期、签名链、用途和吊销状态等。

      • TLS 1.2 常见 ECDHE 握手会交换临时公钥，双方结合随机数计算会话密钥。

      • TLS 1.3 移除了许多旧算法，握手消息更少，并支持 0-RTT，但 0-RTT 有重放风险。

      • 非对称加密主要用于身份认证和密钥协商，业务数据传输主要用对称加密和 AEAD 完整性保护。

  • [ ] ★★★ DNS 解析的完整过程是什么？

    • 简答：DNS 解析通常先查浏览器缓存、操作系统缓存、hosts、路由器或本地 DNS 缓存，未命中时请求递归解析器。递归解析器如果也没有缓存，会从根域名服务器开始，依次查询顶级域、权威域名服务器，最终得到目标记录。解析结果会按 TTL 缓存一段时间，以减少后续查询开销。

    • 原理/对比/实践注意：

      • 根服务器告诉递归解析器 .com、.cn 等 TLD 服务器地址。

      • TLD 服务器告诉对应域名的权威 DNS 服务器地址。

      • 权威服务器返回 A、AAAA、CNAME、MX、TXT 等记录。

      • CNAME 需要继续解析其目标域名，最终得到 A/AAAA 地址。

      • 客户端通常和递归解析器交互，不会亲自逐级查询所有权威服务器；递归和迭代是不同角色视角。

  • [ ] ★★ GET 和 POST 的区别是什么？

    • 简答：GET 的 HTTP 语义是获取资源，通常应是安全且幂等的；POST 的语义是提交数据给目标资源处理，常用于创建或触发非幂等操作。GET 参数常放在 URL 查询串中，POST 数据常放在请求体中，但协议并不把“有无 body”作为二者绝对区别。缓存、重试和浏览器行为主要基于方法语义，而不是参数位置。

    • 原理/对比/实践注意：

      • 安全是指不应产生用户可感知的服务端状态改变；幂等是指执行一次和多次效果相同。

      • GET URL 长度限制多来自浏览器、服务器或代理实现，不是 HTTP 协议给出的统一固定值。

      • POST 默认不适合被缓存，但在明确缓存头支持下也可能被缓存。

      • 敏感信息不应放 URL，因为会进入历史记录、日志和 Referer；但放 body 也仍需 HTTPS 才能防窃听。

  • [ ] ★★ HTTP 常见状态码有哪些？

    • 简答：HTTP 状态码按类别分为 1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误和 5xx 服务端错误。面试中重点说明常见码的语义和使用边界，不要把业务错误都塞进 200。合理状态码能帮助客户端、代理、网关和监控系统正确处理响应。

    • 原理/对比/实践注意：

      • 200 OK：请求成功；201 Created：资源已创建；204 No Content：成功但无响应体。

      • 301 Moved Permanently：永久重定向；302 Found：临时重定向；304 Not Modified：缓存仍有效。

      • 400 Bad Request：请求格式或参数错误；401 Unauthorized：未认证；403 Forbidden：已认证但无权限；404 Not Found：资源不存在。

      • 409 Conflict：资源状态冲突；429 Too Many Requests：触发限流。

      • 500 Internal Server Error：服务端内部错误；502 Bad Gateway：网关收到无效上游响应；503 Service Unavailable：服务暂不可用；504 Gateway Timeout：上游超时。

  • [ ] ★★ Cookie、Session、Token 和 JWT 有什么区别？

    • 简答：Cookie 是浏览器保存并随请求自动携带的小段数据；Session 通常是服务端保存会话状态，客户端只保存 session id。Token 是泛指访问凭证，可以放在 Header、Cookie 等位置；JWT 是一种自包含的 Token 格式，包含声明和签名。Session 易撤销但依赖服务端存储，JWT 易扩展但撤销和失效控制更复杂。

    • 原理/对比/实践注意：

      • Cookie 可设置 HttpOnly、Secure、SameSite 降低 XSS 读取和 CSRF 风险。

      • Session 适合需要强撤销、集中管理登录态的系统，但分布式部署要共享会话或使用粘性会话。

      • JWT 签名只能防篡改，不等于加密；载荷默认可被解码，不应放敏感明文。

      • Token 泄露后在过期前可能被滥用，需配合短有效期、刷新令牌、黑名单或版本号撤销机制。

  • [ ] ★★ 长连接、短连接、WebSocket 和 SSE 分别适用于什么场景？

    • 简答：短连接是每次请求建立连接、完成后关闭，简单但连接成本高；长连接复用同一连接处理多个请求，适合频繁请求。WebSocket 在一次 HTTP 升级后建立全双工通道，适合双向实时通信。SSE 是服务端通过 HTTP 持续向客户端推送文本事件，适合单向实时更新。

    • 原理/对比/实践注意：

      • HTTP keep-alive 是典型长连接，可减少 TCP/TLS 握手开销。

      • WebSocket 适合聊天、协同编辑、实时游戏、行情等客户端和服务端都要主动发送消息的场景。

      • SSE 基于普通 HTTP，浏览器原生支持自动重连，适合通知、进度、日志流、价格更新等服务端到客户端单向推送。

      • 长连接会占用文件描述符、内存和负载均衡连接资源，需要心跳、超时、限流和连接治理。

4. 并发编程

  • [ ] ★★★ 并发和并行有什么区别？

    • 简答：并发强调一段时间内多个任务都在推进，可能通过时间片切换交替执行；并行强调同一时刻多个任务真正同时执行。单核 CPU 可以通过调度实现并发，但不能让多个 CPU 指令流真正并行运行；多核 CPU 才能让多个线程在不同核心上同时运行。并发是程序结构和调度能力，并行是硬件执行能力与任务可拆分程度共同决定的结果。

    • 原理/对比/实践注意：

      • 并发解决“同时处理很多事”的组织问题，例如一个服务同时处理多个连接。

      • 并行解决“更快完成计算”的执行问题，例如把大计算拆成多份在多个核心上跑。

      • 并发程序不一定更快，因为上下文切换、锁竞争和同步开销可能抵消收益。

      • 面试回答时可以用例子区分：单核系统里两个线程轮流运行是并发；四核上四个线程同时计算是并行。

  • [ ] ★★★ 线程安全是什么意思？常见的线程安全问题有哪些？

    • 简答：线程安全是指多个线程同时访问同一段代码或共享状态时，程序结果仍然符合预期，不依赖偶然的调度顺序。常见问题来自原子性、可见性、有序性被破坏，例如多个线程同时修改计数器导致丢失更新，或一个线程修改的值另一个线程迟迟看不到。更复杂的问题包括竞态条件、死锁、活锁和饥饿。

    • 原理/对比/实践注意：

      • 原子性问题：一个逻辑操作由多个步骤组成，中间被其他线程插入，例如 i++ 不是天然原子操作。

      • 可见性问题：线程本地缓存、寄存器优化或内存模型导致修改没有及时对其他线程可见。

      • 有序性问题：编译器、CPU 或运行时重排序让执行顺序和源码顺序不完全一致，但单线程语义通常不变。

      • 竞态条件：结果依赖线程执行时序，是并发 bug 的主要来源。

      • 死锁：多个线程互相等待对方持有的资源，所有相关线程都无法继续。

      • 活锁：线程没有阻塞，但不断让步或重试，实际工作没有进展。

      • 饥饿：某些线程长期拿不到 CPU 或锁资源，常见于不公平锁或优先级调度不当。

      • 常见解决手段包括不可变对象、减少共享状态、加锁、原子变量、线程安全容器、消息传递和明确的内存可见性机制。

  • [ ] ★★★ 互斥锁、读写锁、自旋锁和信号量有什么区别？

    • 简答：互斥锁保证同一时间只有一个线程进入临界区，适合保护普通共享资源。读写锁允许多个读线程并发、写线程独占，适合读多写少的场景。自旋锁获取不到锁时不阻塞而是循环等待，适合临界区极短且线程不宜睡眠的场景；信号量通过许可数量控制同时访问资源的线程数。

    • 原理/对比/实践注意：

      • 互斥锁竞争失败通常会阻塞或挂起线程，避免 CPU 空转，但上下文切换有成本。

      • 读写锁在读多写少时提高并发度，但写多或读持锁时间长时可能退化，甚至造成写饥饿；具体取决于实现是否公平。

      • 自旋锁避免线程睡眠和唤醒开销，但竞争激烈或临界区长时会浪费 CPU。

      • 信号量适合连接池、限流、资源池等“最多 N 个并发访问者”的场景，不只用于互斥。

      • 实践中先缩短临界区、降低共享数据范围，再选择锁；不要只靠更复杂的锁掩盖设计问题。

  • [ ] ★★★ 什么是 CAS？它有什么问题？

    • 简答：CAS 是 Compare-And-Swap，先比较内存中的当前值是否等于预期值，若相等就原子地更新为新值，否则失败。它常用于实现无锁原子变量、乐观并发控制和部分并发容器。CAS 不代表没有成本，常见问题有 ABA、循环重试导致 CPU 开销高，以及难以表达多个变量的一致更新。

    • 原理/对比/实践注意：

      • CAS 的核心是硬件原子指令，比较和写入在一个不可分割的步骤中完成。

      • ABA 问题：值从 A 变成 B 又变回 A，CAS 只看到仍然是 A，却不知道中间发生过变化；可用版本号、时间戳或带标记引用缓解。

      • 自旋开销：高竞争下大量 CAS 失败会不断重试，占用 CPU，吞吐反而下降。

      • 复合操作困难：多个字段或多个对象需要一起更新时，单个 CAS 不够，需要锁、事务、状态封装或更复杂的无锁算法。

      • CAS 适合冲突较少、操作很短的场景；冲突很高时，阻塞锁可能更稳。

  • [ ] ★★★ 什么是乐观并发控制和悲观并发控制？

    • 简答：悲观并发控制假设冲突经常发生，因此在操作前先加锁，阻止其他线程或事务同时修改。乐观并发控制假设冲突较少，操作过程中不加排他锁，提交或更新时再检查版本号、时间戳或条件是否变化。悲观方式更直接但可能阻塞，乐观方式并发度高但冲突时需要失败重试。

    • 原理/对比/实践注意：

      • 悲观控制适合写冲突高、失败代价大、必须强互斥的场景，例如库存扣减的关键行锁。

      • 乐观控制适合读多写少、冲突概率低的场景，例如用 version 字段做条件更新。

      • 乐观控制必须设计重试上限、失败提示和幂等逻辑，否则高冲突下会形成重试风暴。

      • 悲观锁要注意锁粒度、持锁时间和死锁风险。

      • 数据库中的 SELECT ... FOR UPDATE 更偏悲观控制；UPDATE ... WHERE id=? AND version=? 更偏乐观控制。

  • [ ] ★★★ 线程池的核心参数有哪些？应该如何设置？

    • 简答：线程池常见核心参数包括核心线程数、最大线程数、任务队列、非核心线程存活时间、线程工厂和拒绝策略。设置时要区分 CPU 密集型和 I/O 密集型任务：CPU 密集型通常接近 CPU 核数，I/O 密集型可根据阻塞比例适当增大。最终参数不能只靠公式，需要结合任务耗时、下游容量、延迟目标和压测结果调整。

    • 原理/对比/实践注意：

      • 核心线程数决定常驻处理能力，最大线程数决定突发时可扩展到的上限。

      • 队列容量决定削峰能力，但队列越长，排队延迟和内存风险越大。

      • 拒绝策略是背压手段，常见策略包括抛异常、调用者执行、丢弃、丢弃最旧任务，也可以自定义降级或告警。

      • CPU 密集型任务主要消耗计算资源，线程数过多会增加上下文切换。

      • I/O 密集型任务存在等待网络、磁盘、数据库的时间，线程数可以高于核心数，但不能超过下游承载能力。

      • 线程工厂应设置有意义的线程名，便于日志、监控和问题定位。

      • 生产环境应监控活跃线程数、队列长度、拒绝次数、任务耗时、下游错误率和系统负载。

  • [ ] ★★★ 为什么不建议无界队列或无限创建线程？

    • 简答：无界队列会把处理不过来的任务无限堆积，表面上没有拒绝请求，实际会带来内存膨胀和延迟失控。无限创建线程会消耗内存、文件描述符和调度资源，严重时导致频繁上下文切换甚至进程崩溃。两者都会掩盖系统已经过载的事实，缺少对上游的背压。

    • 原理/对比/实践注意：

      • 排队不是免费的，队列越长，请求越可能在处理前就已经超时或失去业务价值。

      • 线程过多会增加调度开销，降低 CPU 缓存命中率，还可能把压力继续打到数据库、缓存和外部服务。

      • 无界设计容易让局部故障扩大成雪崩：上游持续写入，下游越来越慢，最终内存或连接资源耗尽。

      • 更合理的做法是使用有界队列、有限线程数、明确拒绝策略、超时控制、限流降级和监控告警。

      • 容量应该围绕服务目标和下游极限设计，而不是让系统在不可控位置失败。

  • [ ] ★★ 如何实现一个生产者—消费者模型？

    • 简答：生产者—消费者模型通常用一个有界阻塞队列连接生产端和消费端，生产者把任务放入队列，消费者从队列取出处理。队列为空时消费者等待，队列满时生产者等待或被拒绝，从而形成背压。实现时还要定义关闭语义，保证停止生产后消费者能处理完剩余任务并正常退出。

    • 原理/对比/实践注意：

      • 共享队列需要互斥保护，条件变量或信号量用于等待和唤醒。

      • 优先使用语言或框架提供的阻塞队列，减少手写并发原语出错的概率。

      • 有界队列能限制内存占用，也能让生产速度超过消费能力时及时暴露问题。

      • 关闭时可以使用关闭标记、特殊结束消息或上下文取消机制，但要避免消费者永久阻塞。

      • 消费失败要明确重试、丢弃、转移到失败队列或告警策略。

  • [ ] ★★ 如何保证多个线程按指定顺序执行？

    • 简答：可以用条件变量、信号量、屏障、倒计时器、Future/Promise 等同步工具，让后续线程等待前置线程完成后再继续。核心思路是把“顺序”表示成明确的状态或依赖关系，而不是依赖线程调度的偶然顺序。应避免用空循环忙等，因为它浪费 CPU 且不可靠。

    • 原理/对比/实践注意：

      • 两三个线程固定顺序执行时，信号量或条件变量足够直接。

      • 多个任务存在依赖图时，Future、Promise、CompletableFuture 或任务编排框架更清晰。

      • 多线程分阶段同时到达再继续时，可以使用屏障或倒计时器。

      • 状态变量要配合锁或原子可见性机制，否则可能出现看不到状态变化的问题。

      • 如果必须严格串行，单线程执行器或队列往往比多个线程互相等待更简单。

  • [ ] ★★ 什么是伪共享？如何避免？

    • 简答：伪共享是指多个线程修改不同变量，但这些变量恰好落在同一个 CPU 缓存行里，导致缓存行在多个核心之间频繁失效和同步。变量本身没有逻辑共享，却因为硬件缓存粒度产生了性能竞争。避免方式包括缓存行填充、调整对象布局、拆分热点变量或使用运行时提供的防伪共享机制。

    • 原理/对比/实践注意：

      • CPU 缓存一致性通常以缓存行为单位维护，而不是以单个变量为单位。

      • 多核频繁写同一缓存行会导致缓存行所有权来回迁移，降低吞吐。

      • 高性能计数器、环形队列、并发框架底层结构更容易遇到伪共享。

      • 普通业务代码不应过早优化伪共享，通常先通过性能分析确认热点。

5. 缓存与 Redis

  • [ ] ★★★ 为什么 Redis 很快？

    • 简答：Redis 快的核心原因是主要数据在内存中，常用操作的数据结构实现高效，单条命令执行路径短。Redis 经典命令执行模型以单线程为主，避免了大量锁竞争和线程切换，同时通过 I/O 多路复用处理大量连接。需要注意的是，Redis 后续版本引入了后台线程和 I/O 线程等能力，但命令执行的原子串行模型仍是理解 Redis 行为的重要基础。

    • 原理/对比/实践注意：

      • 内存访问比磁盘访问低很多数量级，适合做热点数据缓存。

      • String、Hash、List、Set、Sorted Set 等结构根据不同编码和规模做了优化。

      • 单线程命令执行让单个命令天然具备原子性，也减少锁竞争，但长命令会阻塞后续命令。

      • I/O 多路复用让一个线程可以管理大量 socket 事件，适合高并发网络请求。

      • Redis 快不代表所有使用方式都快，大 Key、复杂 Lua、全量扫描、慢持久化配置和网络瓶颈都会影响性能。

  • [ ] ★★★ Redis 常用数据结构及其典型场景有哪些？

    • 简答：Redis 提供多种数据结构，不只是简单 KV。String 适合缓存对象字符串、计数器和分布式锁值；Hash 适合存储对象字段；List、Set、Sorted Set 分别适合队列、去重集合和排行榜等场景。Bitmap、HyperLogLog、Stream 则适合位状态统计、基数估算和消息流处理。

    • 原理/对比/实践注意：

      • String：最通用，可存 JSON、数字计数、令牌等；注意大对象会形成大 Key。

      • Hash：适合对象字段独立读写，例如用户资料；字段过多或单个 Hash 太大会带来迁移和阻塞问题。

      • List：适合简单队列、时间线片段；复杂消息队列场景更推荐 Stream 或专用 MQ。

      • Set：适合去重、共同好友、标签集合、随机抽样。

      • Sorted Set：适合排行榜、延迟队列、按分数范围查询；写入和范围操作有额外维护成本。

      • Bitmap：适合签到、在线状态等二值统计，本质上仍基于 String。

      • HyperLogLog：适合 UV 等基数估算，占用小但有误差，不能列出具体元素。

      • Stream：适合轻量消息流、消费组、可回放消息；但运维和语义不能简单等同 Kafka。

  • [ ] ★★★ 什么是缓存穿透、缓存击穿和缓存雪崩？如何解决？

    • 简答：缓存穿透是请求的数据既不在缓存也不在数据库，导致每次都打到数据库；缓存击穿是某个热点 Key 过期后大量请求同时打到数据库；缓存雪崩是大量 Key 同时失效或缓存服务异常，导致数据库瞬间承压。解决思路分别是拦截不存在数据、控制热点重建、分散失效时间并提供降级保护。

    • 原理/对比/实践注意：

      • 穿透：可缓存空值、使用布隆过滤器、做参数校验和非法请求拦截；空值缓存要设置较短 TTL，避免真实数据新增后长期不可见。

      • 击穿：可用互斥锁只允许一个请求回源重建，其他请求等待或返回旧值；也可用逻辑过期异步刷新。

      • 雪崩：TTL 加随机抖动，热点分批预热，多级缓存，限流、熔断、降级和数据库保护。

      • 缓存服务故障也是雪崩来源，需要连接池隔离、超时、快速失败和本地兜底策略。

      • 工程上不能只靠缓存保护数据库，还要评估数据库在缓存失效时的最低承载能力。

  • [ ] ★★★ 如何保证缓存与数据库的一致性？

    • 简答：缓存和数据库通常无法在普通缓存架构下做到强一致，工程上更多追求最终一致和可控的不一致窗口。常见旁路缓存模式是读时先查缓存，未命中查数据库并写缓存；写时先更新数据库，再删除缓存。为了提高可靠性，需要删除失败重试、消息或变更日志驱动失效、合理 TTL，以及业务幂等和对账补偿。

    • 原理/对比/实践注意：

      • 不推荐简单“先删缓存再更新数据库”，因为并发读可能在数据库更新前把旧值重新写入缓存。

      • “先更新数据库再删缓存”也不是绝对强一致：删除失败、主从延迟、并发读写仍可能产生短暂脏缓存。

      • 删除缓存比更新缓存更常见，因为更新缓存可能基于复杂聚合计算，且并发顺序更难控制。

      • 延迟双删可缓解部分并发读写问题，但依赖延迟时间估计，不是严格证明的一致性方案。

      • 订阅数据库 binlog、CDC 或业务事件删除缓存更适合多服务写入场景，但要处理消息丢失、乱序和重复。

      • 对强一致要求极高的数据，不应依赖普通缓存读路径；可以降低缓存使用、走数据库事务或专门的一致性架构。

  • [ ] ★★★ Redis 的过期删除和内存淘汰策略有哪些？

    • 简答：Redis 过期删除主要有惰性删除和定期删除：访问 Key 时发现过期再删除，或后台周期性抽样清理过期 Key。内存达到 maxmemory 限制时，Redis 会按配置的淘汰策略选择删除哪些 Key。常见策略包括 LRU、LFU、随机、按 TTL 淘汰以及不淘汰直接报错。

    • 原理/对比/实践注意：

      • 惰性删除节省后台扫描成本，但长期不访问的过期 Key 可能暂时占用内存。

      • 定期删除通过抽样控制成本，不保证过期 Key 到点立即消失。

      • LRU 近似淘汰最近最少使用 Key，适合缓存场景。

      • LFU 近似淘汰低频访问 Key，适合保留长期热点，但对访问模式变化有滞后。

      • volatile-* 类策略只淘汰设置了过期时间的 Key，allkeys-* 类策略可从所有 Key 中淘汰。

      • noeviction 会在内存不足时拒绝写入，适合不允许自动丢数据的场景。

      • 策略选择要区分 Redis 是纯缓存、会话存储、计数服务还是混合用途。

  • [ ] ★★★ Redis 的 RDB 和 AOF 有什么区别？

    • 简答：RDB 是某个时间点的数据快照，文件紧凑、恢复快，但两次快照之间的数据可能丢失。AOF 是追加写命令日志，通常数据丢失窗口更小，但文件可能更大，恢复时需要重放命令。现代 Redis 可使用混合持久化，用 RDB 快照作为基础，再追加增量 AOF，兼顾恢复速度和数据完整性。

    • 原理/对比/实践注意：

      • RDB 适合备份、全量复制和快速恢复，但生成快照时会有 fork、写时复制和磁盘 I/O 成本。

      • AOF 可配置刷盘策略，例如每次写、每秒写、由操作系统决定；可靠性和性能随配置不同而变化。

      • AOF 需要 rewrite 压缩日志，否则文件会不断增长。

      • RDB 与 AOF 都不是关系数据库事务日志，不能把 Redis 当作天然零丢失存储。

      • 如果 Redis 只做缓存，持久化要求可以较低；如果承载重要状态，要评估丢失窗口、备份和恢复演练。

  • [ ] ★★★ Redis 主从复制、哨兵和 Cluster 分别解决什么问题？

    • 简答：主从复制解决数据副本和读扩展问题，从节点复制主节点数据，可用于读分担和故障恢复基础。哨兵在主从复制基础上提供监控、自动故障转移和主节点发现。Cluster 通过分片把数据分布到多个主节点上，解决容量和写入扩展问题，并提供一定的故障转移能力。

    • 原理/对比/实践注意：

      • 主从复制通常是异步复制，主节点写成功不代表从节点已经收到，因此主从切换时可能丢最近写入。

      • 读从库可能读到旧数据，涉及一致性敏感业务要谨慎。

      • 哨兵解决高可用，不解决单主容量瓶颈；故障转移期间可能短暂不可用或发生客户端路由更新。

      • Cluster 使用槽位分片，客户端需要支持重定向和拓扑感知。

      • Cluster 不是强一致分布式数据库，跨槽多 Key 操作有限制，故障和网络分区下仍有一致性边界。

      • 选择方案时先明确目标：读扩展、高可用、水平扩容，还是多目标组合。

  • [ ] ★★★ 如何使用 Redis 实现分布式锁？

    • 简答：Redis 分布式锁常用 SET key value NX PX ttl 原子加锁，其中 value 是唯一令牌，ttl 防止客户端崩溃后锁永久不释放。解锁时必须用 Lua 脚本先校验令牌再删除，避免误删他人的锁。它能满足很多“防重复执行”的工程场景，但在主从异步复制、网络分区、GC 暂停和锁过期后继续执行业务时，并不能提供绝对互斥保证。

    • 原理/对比/实践注意：

      • 加锁必须原子完成“只有不存在时设置值”和“设置过期时间”，不要用分开的 SETNX 和 EXPIRE。

      • 唯一令牌用于确认锁归属，通常使用随机 UUID 或业务唯一请求 ID。

      • 解锁要原子校验加删除，避免线程 A 锁过期后线程 B 加锁成功，线程 A 又删除线程 B 的锁。

      • 长任务需要续期机制，但续期也要校验令牌，并设置最大执行边界，防止无限占锁。

      • Redis 主从切换可能丢失刚写入的锁，导致两个客户端都认为自己持锁；强互斥场景应考虑数据库锁、ZooKeeper/etcd 等一致性系统或业务层幂等补偿。

      • 分布式锁只能降低并发冲突概率，关键业务仍应设计幂等、唯一约束和状态校验。

  • [ ] ★★ Redis 大 Key 和热 Key 有什么危害？如何发现和处理？

    • 简答：大 Key 会导致单次读写、删除、迁移或持久化成本过高，阻塞 Redis 事件循环并占用大量网络带宽。热 Key 会让大量请求集中到单个 Key 或单个节点，造成 CPU、网卡或分片负载倾斜。处理时通常要先发现热点或大对象，再拆分、限流、缓存本地副本或调整数据模型。

    • 原理/对比/实践注意：

      • 大 Key 可通过 redis-cli --bigkeys、内存分析、慢日志、监控和离线扫描发现；生产扫描要控制频率和范围。

      • 删除大 Key 应优先使用异步删除能力或分批删除，避免 DEL 阻塞。

      • 大集合可按业务维度拆分成多个 Key，或改为分页、分桶、压缩存储。

      • 热 Key 可用本地缓存、读副本、请求合并、限流、热点探测和预热处理。

      • Cluster 中热 Key 不会因分片自动变快，因为同一个 Key 仍落在一个槽和一个节点上。

  • [ ] ★★ 布隆过滤器的原理是什么？有什么局限？

    • 简答：布隆过滤器用一个位数组和多个哈希函数表示集合，插入元素时把多个哈希位置置为 1，查询时如果某个位置为 0 则元素一定不存在。若所有位置都为 1，只能说明元素可能存在。它空间效率高，但有假阳性，且普通布隆过滤器不能直接精确删除元素。

    • 原理/对比/实践注意：

      • 假阳性是“判断存在但实际不存在”，不会出现“判断不存在但实际存在”的假阴性，前提是没有错误删除或数据损坏。

      • 误判率与容量、位数组大小、哈希函数数量有关，超出设计容量后误判率会上升。

      • 如果需要删除，可考虑计数布隆过滤器，但会增加空间和复杂度。

      • 布隆过滤器适合缓存穿透防护、黑名单初筛、去重预判等场景，不适合需要精确成员列表的场景。

      • 布隆过滤器本身也需要初始化、更新和一致性维护，否则可能放大误判或漏拦截。

  • [ ] ★★ 为什么 Redis 事务不等同于关系数据库事务？

    • 简答：Redis 事务通过 MULTI/EXEC 把一组命令按顺序串行执行，中间不会被其他客户端命令插入。它不像关系数据库事务那样提供完整的 ACID 语义，尤其没有运行时错误后的自动回滚机制。WATCH 可提供乐观锁式的条件执行，Lua 脚本可保证脚本内命令原子执行，但都不能直接等同于数据库事务。

    • 原理/对比/实践注意：

      • MULTI 后命令先入队，EXEC 时依次执行。

      • 入队阶段语法错误可能导致事务失败；执行阶段某条命令报错，其他命令通常仍会执行。

      • Redis 单线程命令执行保证原子执行片段，但不提供数据库级隔离级别、回滚日志和复杂约束检查。

      • WATCH 监控 Key 是否被修改，若被修改则 EXEC 失败，需要客户端重试。

      • Lua 适合把“检查再修改”合成一个原子逻辑，但脚本过长会阻塞 Redis，且仍要处理外部系统一致性。

6. 消息队列（MQ）

  • [ ] ★★★ 为什么使用消息队列？它会带来哪些问题？

    • 简答：消息队列常用于系统解耦、异步处理和削峰填谷，让生产者不必同步等待消费者完成全部工作。它可以提高系统抗突发能力，也能让多个下游独立订阅同一类业务事件。但引入 MQ 后会带来一致性、消息丢失、重复消费、延迟、顺序性和运维复杂度等问题。

    • 原理/对比/实践注意：

      • 解耦：订单服务只发送“订单已创建”事件，库存、积分、通知等服务各自消费。

      • 异步：把非核心链路从主请求中拆出去，降低用户等待时间。

      • 削峰：生产流量短时突增时，队列缓存请求，消费者按能力处理。

      • 问题：异步后调用方无法立即知道最终结果，需要状态查询、回调、补偿或对账。

      • MQ 不是免费加速器，如果消费者长期处理不过来，只会把压力变成积压。

      • 选型时要同时考虑业务语义、吞吐延迟、可靠性、顺序性、运维和团队经验。

  • [ ] ★★★ 如何保证消息不丢失？

    • 简答：消息不丢失要覆盖生产、Broker 存储和消费三个阶段。生产端要等待发送确认并处理失败重试，Broker 要开启持久化和副本机制，消费端要在业务处理成功后再确认消息。即使这样也通常只能做到工程上的高可靠，还需要监控、告警、补偿和幂等来兜底。

    • 原理/对比/实践注意：

      • 生产端：使用同步确认、异步回调或事务发送机制；发送失败要重试，但重试可能产生重复消息。

      • Broker：开启消息持久化、副本复制、高可用配置；不同 MQ 对刷盘、副本确认和事务消息的语义不同。

      • 消费端：不要先 ack 再执行业务；应在业务成功落库或状态更新后提交 ack/offset。

      • Kafka 中还要关注 acks、副本 ISR、生产者重试、幂等生产者和 offset 提交时机。

      • RabbitMQ 中要关注 publisher confirm、队列和消息持久化、手动 ack、死信和镜像/仲裁队列等能力。

      • RocketMQ 中可结合同步发送、刷盘策略、副本、事务消息和消费重试。

      • 没有任何单点配置能证明端到端永不丢失，最终还要靠业务对账、补偿任务和可观测性。

  • [ ] ★★★ 如何处理重复消息，保证消费幂等？

    • 简答：MQ 系统在重试、网络超时、消费者崩溃和 offset/ack 提交异常时都可能产生重复消息，所以消费者必须按“可能重复”设计。幂等的核心是让同一业务消息处理一次和处理多次的最终结果一致。常见方法包括业务唯一键、数据库唯一约束、幂等表、去重记录和状态机流转校验。

    • 原理/对比/实践注意：

      • 使用业务唯一键，例如订单号、支付流水号、请求 ID，而不是只依赖 MQ 的消息 ID。

      • 数据库唯一约束是强有力的幂等手段，例如插入支付记录时用流水号唯一索引防重复。

      • 幂等表可记录已处理消息 ID 或业务键，但要考虑存储膨胀、过期清理和并发插入。

      • 状态机适合订单、退款、审批等业务：只允许从合法旧状态转移到新状态。

      • 外部副作用如发短信、调用第三方支付、发货，要结合去重键、查询确认和补偿流程。

      • 幂等不等于不重试；正确做法是允许重试，但让重复执行不会破坏数据。

  • [ ] ★★★ 如何保证消息顺序？

    • 简答：保证顺序通常要把同一业务键的消息路由到同一个分区、队列或顺序通道，并由同一消费者按序处理。全局顺序代价很高，会显著限制吞吐，工程上更多保证同一订单、同一用户或同一资源维度的局部顺序。处理失败时不能简单跳过，否则后续消息可能先执行，需要在顺序和可用性之间取舍。

    • 原理/对比/实践注意：

      • Kafka 通常保证单分区内有序，不保证跨分区全局有序；同一业务键应使用相同 key 路由到同一分区。

      • RabbitMQ 可通过单队列单消费者维持顺序，但多消费者并行和重试会破坏严格顺序。

      • RocketMQ 支持顺序消息语义，但也依赖同一队列串行消费和正确路由。

      • 如果某条消息失败，严格顺序要求阻塞后续同 key 消息；这会降低吞吐并放大单点慢消息影响。

      • 对只要求最终状态正确的业务，可通过版本号、状态机和幂等更新弱化对顺序的依赖。

  • [ ] ★★★ 消息积压通常是什么原因？如何处理？

    • 简答：消息积压通常是生产速度长期大于消费速度，原因可能是流量突增、消费者逻辑变慢、下游数据库或接口故障、消费并发不足、分区/队列数量不够。处理时先定位瓶颈，再扩容消费者、提高批处理能力、保护下游或对生产端限流。若积压已经影响线上恢复，可以采用临时转储、跳过非关键消息或补偿处理，但要经过业务风险评估。

    • 原理/对比/实践注意：

      • 先看生产速率、消费速率、消费者错误率、单条耗时、下游延迟和队列分区负载。

      • 消费慢若是下游数据库慢，单纯扩消费者可能把下游打崩。

      • Kafka 中消费并行度受分区数影响，同一消费组内消费者数超过分区数通常不能继续提升并行消费能力。

      • 可通过批量拉取、批量写库、减少同步外部调用、异步化内部步骤提高吞吐。

      • 对非核心链路可降级、限流或暂停生产；对核心链路要保障数据可回放和补偿。

      • 积压清理后还要复盘容量水位、告警阈值和压测模型。

  • [ ] ★★★ 什么是消息确认、重试队列和死信队列？

    • 简答：消息确认表示消费者告诉 MQ 某条消息已经处理完成，MQ 可以提交消费进度或删除投递记录。重试队列用于处理临时失败的消息，按一定次数和退避策略重新投递。死信队列用于隔离多次失败、过期或无法路由的消息，便于告警、排查和人工补偿。

    • 原理/对比/实践注意：

      • 确认时机通常应在业务处理成功之后，过早确认会增加丢消息风险。

      • 重试要设置上限和退避间隔，避免故障期间立即高频重试压垮下游。

      • 死信不是垃圾桶，进入死信的消息要有监控、查询、修复和重放流程。

      • 不同 MQ 的确认模型不同：Kafka 提交 offset，RabbitMQ 使用 ack/nack，RocketMQ 有消费状态返回和重试主题等机制。

      • 重试和死信会改变消息顺序，顺序敏感业务要单独设计阻塞、跳过或人工处理策略。

  • [ ] ★★★ 消息队列如何实现最终一致性？

    • 简答：MQ 实现最终一致性的核心是把本地状态变更和消息发送可靠关联起来，再让消费者通过重试和幂等最终完成下游状态变更。常见方案有本地消息表、Outbox/CDC、事务消息和业务事件重试。最终一致性不是立即一致，必须接受短暂中间状态，并配套查询、对账和补偿。

    • 原理/对比/实践注意：

      • 本地消息表：业务数据和待发送消息在同一个数据库事务中落库，后台任务扫描发送，成功后标记已发送。

      • Outbox/CDC：业务事务写入 outbox 表，通过 CDC 订阅数据库变更并投递 MQ，降低业务代码直接发送失败的风险。

      • 事务消息：部分 MQ 提供半消息和事务状态回查机制，但具体语义和限制因产品不同。

      • 消费端必须幂等，因为生产重试、投递重试和补偿都可能产生重复。

      • 对账任务用于发现长期未完成的中间状态，补偿任务负责重试、回滚或人工介入。

      • 如果业务要求同步强一致，MQ 最终一致方案可能不适合，需要数据库事务或同步一致性协议。

  • [ ] ★★ At-most-once、At-least-once 和 Exactly-once 分别是什么？

    • 简答：At-most-once 表示最多投递一次，可能丢但不会重复；At-least-once 表示至少投递一次，不轻易丢但可能重复；Exactly-once 表示效果上恰好一次。工程里端到端 Exactly-once 很难单靠 MQ 保证，通常需要生产、Broker、消费、存储系统处在同一事务边界，或通过幂等把重复处理收敛为一次效果。

    • 原理/对比/实践注意：

      • At-most-once 常见于先提交消费进度再处理业务，处理失败就可能丢。

      • At-least-once 常见于业务成功后再提交 ack/offset，失败会重试，因此要求消费者幂等。

      • Kafka 的 Exactly-once 语义主要覆盖 Kafka 内部生产和消费到生产链路的事务边界；写外部数据库时仍要结合外部事务或幂等。

      • RabbitMQ、RocketMQ 等也有各自的确认、事务或重试能力，但不能把产品特性泛化成所有外部副作用都恰好一次。

      • 面试中应强调“消息投递恰好一次”和“业务效果恰好一次”是两回事。

  • [ ] ★★ Kafka 为什么吞吐量高？

    • 简答：Kafka 吞吐量高主要因为它把消息追加写入日志文件，充分利用磁盘顺序写和操作系统页缓存。生产和消费都支持批处理、压缩和分区并行，减少网络与磁盘开销。传输文件数据时还可利用零拷贝等机制降低用户态和内核态之间的数据复制成本。

    • 原理/对比/实践注意：

      • 顺序写比随机写更适合磁盘和 SSD 的吞吐模型。

      • 页缓存让 Kafka 能借助操作系统管理缓存，热点数据消费可能直接从内存返回。

      • 批处理把多条消息合并发送和落盘，提高吞吐但可能增加少量延迟。

      • 压缩减少网络和磁盘传输量，但会增加 CPU 成本。

      • 分区让不同分区在多个 Broker、磁盘和消费者之间并行处理。

      • 高吞吐依赖合理配置和业务模式，不能忽略副本数、确认级别、消息大小、分区数和消费者处理能力。

  • [ ] ★★ Kafka 的分区、副本、消费者组和 Offset 分别是什么？

    • 简答：分区是 Kafka Topic 的并行日志单元，用于扩展吞吐和存储容量；副本是分区的数据冗余，用于容错和高可用。消费者组是一组共同消费 Topic 的消费者，同一组内一个分区通常同一时刻只分配给一个消费者处理。Offset 是消费者在分区日志中的消费位置，用于记录进度和支持重放。

    • 原理/对比/实践注意：

      • 分区内消息有序，跨分区不保证全局顺序。

      • 每个分区有 Leader 副本负责读写，Follower 副本复制数据；具体一致性取决于确认和副本配置。

      • 同一消费者组用于负载均衡，不同消费者组可独立消费同一 Topic。

      • 消费者数量超过分区数时，多出来的消费者通常空闲，不能继续提高同组并行度。

      • Offset 可自动提交或手动提交；提交过早可能丢，提交过晚可能重复。

      • 再均衡会在消费者加入、离开或分区变化时重新分配分区，期间可能带来短暂停顿和重复处理风险。

  • [ ] ★★ RabbitMQ、Kafka 和 RocketMQ 如何选型？

    • 简答：RabbitMQ 更偏传统消息代理，路由能力灵活，适合复杂交换机路由、任务队列和中等吞吐场景。Kafka 更偏高吞吐分布式日志，适合日志采集、事件流、数据管道和可回放消费。RocketMQ 常用于业务消息场景，在顺序消息、延迟消息、事务消息等方面有较多工程化能力，尤其在国内 Java 生态中使用较多。

    • 原理/对比/实践注意：

      • RabbitMQ：Exchange、Queue、Binding 模型灵活，确认机制成熟；超高吞吐和长期海量堆积通常不是它的最强项，具体也取决于队列类型和部署配置。

      • Kafka：吞吐高、可扩展、适合多消费者回放；单条低延迟、复杂路由和传统命令式任务分发不是主要优势。

      • RocketMQ：面向业务消息的功能较完整，支持顺序、延迟、事务等常用能力；需要考虑团队运维经验、语言生态和版本特性。

      • 选型不要只看性能榜，应结合消息量、消息大小、延迟目标、顺序要求、事务需求、回放需求、云服务可用性和团队熟悉度。

      • 已有稳定基础设施时，优先复用现有 MQ；只有现有产品无法满足关键语义或容量目标时再迁移。

7. 分布式系统与微服务

  • [ ] ★★★ CAP 定理和 BASE 理论是什么？

    • 简答：CAP 定理描述的是分布式系统在发生网络分区时，一致性（Consistency）和可用性（Availability）不能同时完全满足，系统必须做取舍。它不是说 C、A、P 三者永远只能选两个，而是网络分区不可避免时，需要在读写一致和继续服务之间选择。BASE 是对强一致 ACID 的一种工程化放松，强调基本可用、软状态和最终一致。最终一致性不是不要一致性，而是允许短时间不一致，并通过重试、补偿、对账等手段收敛。

    • 原理/对比/实践注意：

      • C 在 CAP 语境中通常指线性一致性或单副本视图：操作一旦成功，之后的读取能看到该结果或更新的结果，而不是要求所有物理节点每时每刻内容完全相同。A 指每个到达非故障节点的请求都能在有限时间内得到非错误响应，P 指网络分区发生时系统仍能继续运行。

      • CP 系统倾向于拒绝或阻塞部分请求来保证一致性，适合库存、余额、配置中心等场景；AP 系统倾向于继续响应并事后收敛，适合评论、点赞、缓存等场景。

      • BASE 不是随意丢数据，必须定义业务可接受的不一致窗口、补偿策略、幂等机制和监控对账。

  • [ ] ★★★ 强一致性、弱一致性和最终一致性有什么区别？

    • 简答：强一致性要求写入成功后，后续读取都能看到最新结果，用户理解简单但实现成本和延迟较高。弱一致性不保证读到最新值，只承诺系统按某种较弱规则返回结果。最终一致性是弱一致性的一种常见形式，即在没有新写入且系统正常恢复后，各副本最终收敛到相同状态。

    • 原理/对比/实践注意：

      • 强一致通常依赖同步复制、共识协议、主节点串行化或事务机制，牺牲部分可用性和性能。

      • 最终一致常依赖异步复制、消息队列、补偿任务、版本号和冲突解决策略。

      • 选择一致性模型要从业务容忍度出发：余额扣减、库存扣减更偏强一致；浏览量、推荐特征、消息未读数可接受最终一致。

      • 面试中要说明读己之写、单调读、因果一致性等用户体验约束，不要只说“最终一致即可”。

  • [ ] ★★★ 分布式事务有哪些常见方案？

    • 简答：常见方案包括 2PC、TCC、Saga、本地消息表和事务消息。2PC 偏强一致但阻塞和协调者风险明显；TCC 通过 Try、Confirm、Cancel 明确预留和确认，业务侵入较强；Saga 和本地消息表通常追求最终一致，通过正向步骤和补偿步骤完成跨服务协作。选型取决于一致性要求、业务可补偿性、实现成本和失败恢复能力。

    • 原理/对比/实践注意：

      • 2PC 第一阶段询问各参与者是否可提交，第二阶段统一提交或回滚，适合少量资源、强一致要求高但可接受阻塞的场景。

      • TCC 的 Try 要预留资源，Confirm/Cancel 必须幂等、可重试，并能处理空回滚和悬挂。

      • Saga 可分为编排式和协同式，适合长事务，但补偿不等于真正回滚，必须确认业务上可逆。

      • 本地消息表把本地事务和消息落库放在同一数据库事务中，再异步投递；事务消息由 MQ 提供半消息和回查机制。

      • 所有方案都要处理幂等、重试、超时、补偿失败、人工对账和监控告警。

  • [ ] ★★★ 什么是服务注册与发现？

    • 简答：服务注册与发现用于让服务实例动态上线、下线并被调用方找到。服务启动时向注册中心登记地址、端口、元数据和健康状态，调用方通过注册中心获取可用实例列表，再结合负载均衡发起调用。它解决了微服务实例数量变化、弹性扩缩容和故障摘除的问题。

    • 原理/对比/实践注意：

      • 注册中心常见实现有 Nacos、Eureka、Consul、ZooKeeper、etcd 等。

      • 健康检查可以是心跳、主动探测或服务自检，摘除策略要避免误杀和频繁抖动。

      • 客户端发现由调用方拉取实例并负载均衡，服务端发现由网关或负载均衡器统一转发。

      • 客户端通常会缓存服务列表，注册中心异常时应优先使用本地缓存并限制故障扩散。

  • [ ] ★★★ API 网关通常承担哪些职责？

    • 简答：API 网关是外部流量进入后端服务的统一入口，通常负责路由转发、认证鉴权、限流、协议转换、灰度发布和观测埋点。它可以屏蔽内部服务拓扑，统一处理跨服务的通用能力。网关不应承载过多业务逻辑，否则会变成高耦合的中心瓶颈。

    • 原理/对比/实践注意：

      • 常见职责包括 TLS 终止、请求签名校验、JWT 校验、黑白名单、CORS、限流熔断、日志追踪和响应包装。

      • BFF 与通用网关不同，BFF 可以面向具体端做聚合适配，通用网关应保持通用和薄。

      • 网关本身要高可用，避免单点；配置变更、灰度规则和限流规则需要可回滚、可观测。

  • [ ] ★★★ 什么是限流、熔断和降级？三者有什么区别？

    • 简答：限流是控制进入系统或某个资源的请求速率，防止超过处理能力。熔断是在下游持续失败或变慢时快速失败，避免调用方线程和资源被拖垮。降级是在压力或故障下关闭非核心功能或返回兜底结果，优先保护核心链路。

    • 原理/对比/实践注意：

      • 限流关注“流量是否太多”，常按用户、接口、租户、IP、全局维度控制。

      • 熔断关注“依赖是否不健康”，通常有关闭、打开、半开状态，并根据错误率、慢调用比例恢复。

      • 降级关注“功能是否可牺牲”，例如推荐降级为默认列表、评论延迟展示。

      • 三者常组合使用：先限流控入口，再熔断隔离故障依赖，最后降级保核心体验。

  • [ ] ★★★ 常见限流算法有哪些？

    • 简答：常见限流算法有固定窗口、滑动窗口、漏桶和令牌桶。固定窗口实现简单但窗口边界可能产生突刺；滑动窗口更平滑但存储和计算成本更高。漏桶强调恒定速率流出，令牌桶允许一定突发流量，是工程中很常用的方案。

    • 原理/对比/实践注意：

      • 固定窗口按自然时间片计数，例如每秒最多 100 次，边界两侧可能瞬间通过接近 200 次。

      • 滑动窗口可用多个小窗口或请求时间戳实现，准确性和成本可以折中。

      • 漏桶适合平滑处理能力固定的下游；令牌桶适合允许短时突发但限制长期平均速率。

      • 分布式限流要考虑中心 Redis/网关的性能、时钟一致性、局部限流与全局限流的误差。

  • [ ] ★★★ 如何设计幂等接口？

    • 简答：幂等接口要求同一个业务请求执行一次和执行多次的最终效果一致。常见做法是使用幂等键、唯一约束、防重表、状态机流转和结果复用。幂等不是简单地拒绝重复请求，而是要让客户端在超时重试、网络抖动和消息重复投递下得到稳定结果。

    • 原理/对比/实践注意：

      • 创建订单、支付回调、MQ 消费等场景都需要幂等，查询天然幂等，新增和扣减通常不天然幂等。

      • 幂等键可以由客户端生成，也可以由业务唯一字段生成，例如订单号、支付流水号。

      • 数据库唯一索引是可靠边界，Redis 防重可作为性能优化但要考虑过期和持久化风险。

      • 状态机要限制非法跳转，例如已支付不能再次扣款，已取消不能变为已发货。

      • 重复请求最好返回首次处理结果，幂等记录要设置合理过期并支持排查。

  • [ ] ★★★ 什么是分布式锁？它有哪些实现方案和风险？

    • 简答：分布式锁用于在多个进程或节点之间保护同一份共享资源，避免并发执行导致冲突。常见实现包括 Redis、ZooKeeper/etcd 和数据库锁。它的核心风险在于租约过期、客户端暂停、网络分区、锁误删和脑裂，因此不能只看“加锁成功”。

    • 原理/对比/实践注意：

      • Redis 常用 SET key value NX PX 加锁，用 Lua 校验 value 后删除；需要处理超时、续期和主从切换丢锁。

      • ZooKeeper/etcd 可基于临时节点、租约和顺序节点实现，语义更强，但延迟和运维成本更高。

      • 数据库可用唯一索引或悲观锁实现，简单可靠但吞吐有限。

      • 对关键资源建议使用 fencing token，让资源服务拒绝旧 token 的写入，降低锁过期后旧持有者继续写的风险。

      • 分布式锁不应覆盖过长事务，也不能替代业务状态校验和唯一约束。

  • [ ] ★★★ 负载均衡算法有哪些？

    • 简答：常见负载均衡算法包括轮询、加权轮询、随机、加权随机、最少连接、一致性哈希和基于延迟的策略。轮询简单，权重适合实例配置不同，最少连接适合请求耗时差异大，一致性哈希适合会话或缓存亲和。实际效果还取决于健康检查、超时、重试和连接复用。

    • 原理/对比/实践注意：

      • 轮询默认认为实例能力相同；加权轮询可按 CPU、内存、实例规格分配流量。

      • 最少连接会把请求发给当前连接数较少的实例，但要注意长连接和统计准确性。

      • 一致性哈希能减少节点变化时的路由迁移，适合缓存、分片和有状态路由。

      • 负载均衡必须结合故障摘除和慢实例探测，否则“可用但很慢”的实例会拖累整体 P99。

  • [ ] ★★ 一致性哈希解决了什么问题？为什么需要虚拟节点？

    • 简答：一致性哈希主要解决节点增删时大量 key 重新映射的问题。普通取模在节点数量变化时会导致大部分 key 迁移，而一致性哈希只影响环上相邻区间。虚拟节点用于把真实节点映射到哈希环上的多个位置，缓解数据倾斜并提升负载均衡效果。

    • 原理/对比/实践注意：

      • key 和节点都映射到同一个哈希环，key 顺时针找到的第一个节点就是目标节点。

      • 节点下线时只迁移该节点负责的区间，节点上线时只接管相邻区间的一部分。

      • 虚拟节点数量需要结合节点规模和负载测试调优，过少可能倾斜，过多会增加维护成本。

  • [ ] ★★ 什么是服务雪崩？如何防止？

    • 简答：服务雪崩是一个服务或依赖故障后，引发调用链上大量超时、重试、线程耗尽和级联失败，最终导致大范围不可用。它通常不是单点故障本身，而是故障被重试、等待和资源争抢放大。防止雪崩要从超时、隔离、限流、熔断、降级和容量保护多层入手。

    • 原理/对比/实践注意：

      • 设置合理超时，避免请求无限等待；重试要有上限、退避和预算。

      • 使用线程池、连接池、舱壁隔离，避免单个依赖耗尽全局资源。

      • 对慢调用和高错误率依赖开启熔断，对非核心功能提供降级结果。

      • 通过背压、队列长度限制、预案演练和监控告警提前发现风险。

  • [ ] ★★ 重试机制应该如何设计？

    • 简答：重试只适合处理瞬时故障，例如网络抖动、短暂超时、限流后的可恢复错误，不适合重试确定性业务错误。重试必须设置次数上限、总超时时间、指数退避和随机抖动，避免把故障放大。被重试的操作应具备幂等性，或至少能识别重复请求。

    • 原理/对比/实践注意：

      • 不要对所有错误无差别重试，例如参数错误、余额不足、权限失败不应重试。

      • 指数退避降低下游压力，抖动避免大量客户端同时重试形成尖峰。

      • 重试预算用于限制整体重试流量，防止正常流量被重试挤占。

      • 跨层重试要协调，避免客户端、网关、服务、SDK 各自重试导致倍增。

  • [ ] ★★ RPC 和 HTTP REST 有什么区别？

    • 简答：RPC 更强调像调用本地函数一样调用远程服务，通常有明确接口定义、二进制序列化和较高性能。HTTP REST 更强调资源建模和标准 HTTP 语义，易于开放、调试和跨语言接入。两者没有绝对优劣，内部高性能服务调用常用 RPC，对外开放 API 常用 REST。

    • 原理/对比/实践注意：

      • RPC 常见如 gRPC、Dubbo，接口契约强，适合内部服务治理和代码生成。

      • REST 使用 URI 表示资源，结合 GET、POST、PUT、DELETE 等方法表达操作。

      • RPC 可能带来较强耦合，版本兼容要设计好；REST 也可能因设计不当退化成面向动作的接口。

      • 可观测性、超时、重试、认证和限流都需要统一治理。

  • [ ] ★★ 如何实现分布式链路追踪？

    • 简答：分布式链路追踪通过 Trace ID 把一次请求在多个服务中的调用串起来，通过 Span 记录每段调用的耗时、状态和上下文。请求进入系统时生成或接收 Trace ID，并在 HTTP Header、RPC Metadata、消息头中继续传播。最终把 Trace、日志和指标关联起来，用于定位慢调用、错误和依赖瓶颈。

    • 原理/对比/实践注意：

      • Span 通常包含父子关系、服务名、接口名、开始结束时间、错误状态和标签。

      • 异步消息链路也要传播上下文，否则调用链会断。

      • 高流量系统需要采样，常见有固定采样、按错误采样、尾部采样。

      • 标准可采用 OpenTelemetry，后端可对接 Jaeger、Zipkin、Tempo 等。

8. 高并发系统设计

  • [ ] ★★★ 设计一个高并发系统时，应该从哪些方面入手？

    • 简答：先澄清业务目标和指标，例如峰值 QPS、P99、可用性、数据一致性、成本和故障容忍范围。核心方案通常围绕无状态水平扩容、缓存、异步削峰、分片、限流降级、热点治理和容量规划展开。高并发设计不是单纯加机器，而是让入口、应用、缓存、数据库和下游依赖都能承受峰值并可观测。

    • 原理/对比/实践注意：

      • 需求澄清：读写比例、峰谷模型、核心链路、是否允许延迟处理、是否允许最终一致。

      • 核心方案：接入层负载均衡，应用无状态扩容，热点数据缓存，写请求异步化，数据库分库分表或读写分离。

      • 关键风险：缓存击穿/雪崩、数据库热点、队列堆积、下游拖垮、重试风暴、数据不一致。

      • 验证指标：QPS/TPS、P95/P99、错误率、CPU、连接池、队列堆积、缓存命中率、数据库慢 SQL。

  • [ ] ★★★ QPS、TPS、吞吐量、并发数、响应时间和 P99 分别是什么？

    • 简答：QPS 是每秒查询或请求数，TPS 是每秒完成的业务事务数，吞吐量表示单位时间内系统处理的工作量。并发数是同一时刻正在被处理或连接中的请求数量，响应时间是单次请求从发起到收到结果的耗时。P99 表示 99% 的请求响应时间不超过该值，比平均值更能反映长尾延迟。

    • 原理/对比/实践注意：

      • 粗略关系可用 Little's Law 理解：并发数约等于吞吐量乘以平均响应时间。

      • QPS 不一定等于 TPS，一个业务事务可能包含多个接口请求。

      • 平均响应时间容易掩盖少量极慢请求，高并发系统要关注 P95、P99、P999。

      • 压测时必须说明统计窗口、成功率、数据规模和资源配置，否则指标不可比较。

  • [ ] ★★★ 如何估算系统容量？

    • 简答：容量估算要从业务峰值流量、请求大小、读写比例、数据增长、目标延迟和可用性要求出发。先估算入口 QPS/TPS，再拆到应用、缓存、数据库、存储、带宽和下游依赖。最后要预留冗余、增长量和故障切换容量，不能只按平均流量设计。

    • 原理/对比/实践注意：

      • 需求澄清：日活、峰值系数、活动峰值、请求路径、读写比例、数据保留周期。

      • 核心方案：用压测得到单机能力，再按峰值流量、目标利用率和冗余倍数计算实例数。

      • 存储容量要考虑原始数据、索引、副本、日志、备份和增长周期。

      • 关键风险：低估热点、忽略下游限额、忽略连接数、带宽、磁盘 IOPS 和缓存容量。

  • [ ] ★★★ 如何发现系统瓶颈？

    • 简答：发现瓶颈要先建立指标和基线，再从用户入口沿调用链逐层排查。观察吞吐、延迟、错误率和资源利用率，结合日志、链路追踪、火焰图和数据库慢查询定位。瓶颈通常出现在 CPU、内存、锁竞争、I/O、网络、数据库、缓存或外部依赖中。

    • 原理/对比/实践注意：

      • 先确认是整体慢、部分接口慢、部分用户慢，还是特定时间段慢。

      • 应用层关注线程池、连接池、GC、锁等待、队列堆积和慢调用。

      • 数据层关注慢 SQL、索引失效、锁等待、连接数、主从延迟和热点行。

      • 每次只改变一个变量做验证，避免同时改多处导致无法判断原因。

  • [ ] ★★★ 如何应对突发流量？

    • 简答：突发流量要同时考虑事前准备、入口保护和后端削峰。事前做容量预估、缓存预热和弹性扩容；入口用限流、防刷和排队保护系统；后端用缓存、异步队列、降级和热点隔离保护核心链路。目标不是让所有请求都成功，而是在可控范围内保证核心业务可用。

    • 原理/对比/实践注意：

      • 需求澄清：突发是否可预测、是否允许排队、核心功能是什么、失败时返回什么。

      • 核心方案：CDN/缓存承接读流量，令牌桶限流，MQ 削峰填谷，非核心功能降级。

      • 关键风险：缓存同时失效、队列无限堆积、扩容不及时、下游配额被打满。

      • 验证指标：入口拒绝率、排队时长、核心接口成功率、P99、队列积压和恢复时间。

  • [ ] ★★★ 什么是背压？为什么高并发系统需要背压？

    • 简答：背压是让上游感知下游处理能力，并在下游过载时减慢、排队、拒绝或降级请求。它的目的不是提升单次处理速度，而是避免无界排队、内存耗尽和级联故障。高并发系统中，如果没有背压，上游会持续灌入请求，把局部慢依赖扩散成整体不可用。

    • 原理/对比/实践注意：

      • 背压可以通过有界队列、限流、连接池上限、消费者拉取速率、Reactive Streams 等方式实现。

      • 队列必须有长度上限和超时策略，无界队列只是把失败延后并放大。

      • 背压信号可以是错误码、Retry-After、慢启动、动态限流或消费者 lag。

      • 指标要关注队列长度、等待时间、拒绝数、消费速率和下游延迟。

  • [ ] ★★★ 如何设计秒杀系统？

    • 简答：秒杀系统要先澄清商品数量、峰值流量、是否允许排队、支付时限、防刷要求和一致性目标。核心方案是将读流量尽量前置到 CDN/缓存，入口限流和资格校验，库存预热到高速存储中做原子扣减，再通过消息队列异步创建订单。关键是防超卖、防重复下单、防刷和失败补偿。

    • 原理/对比/实践注意：

      • 核心流程：活动预热、用户校验、令牌/资格发放、库存原子扣减、写入订单消息、异步落库、支付超时回补库存。

      • 库存扣减可用数据库条件更新、Redis Lua、单线程队列或分段库存，必须有最终对账。

      • 防刷包括验证码、风控、限频、黑名单、设备指纹和活动链接动态化。

      • 关键风险：缓存热点、Redis 单 key 热点、MQ 堆积、重复消费、支付回调乱序、少卖和超卖。

      • 验证指标：下单成功数与库存一致、超卖为零、核心链路 P99、MQ 积压恢复时间、异常订单比例。

  • [ ] ★★★ 如何防止库存超卖？

    • 简答：防超卖的核心是让库存扣减具备原子性，并在并发下保证库存不能从大于等于零变成负数。常见方案有数据库条件更新、乐观锁、悲观锁、Redis Lua 原子脚本、串行化队列和 MQ 异步扣减。不同方案在性能、一致性和复杂度上不同，还要同时关注少卖、重复扣减和补偿。

    • 原理/对比/实践注意：

      • 数据库条件更新示例：update sku set stock = stock - 1 where id = ? and stock > 0，依赖行锁和影响行数判断。

      • 乐观锁通过版本号或库存条件防并发覆盖，失败后是否重试要控制，避免放大压力。

      • Redis Lua 性能高，但要考虑 Redis 与数据库最终一致、持久化和故障恢复。

      • 队列串行化能简化并发控制，但可能增加排队延迟和单分区热点。

      • 支付超时、订单取消、重复消息都要幂等处理并对账。

  • [ ] ★★★ 如何设计短链接系统？

    • 简答：短链接系统要把长 URL 映射成短码，访问短码时快速跳转到原始 URL。设计时要澄清写入量、跳转 QPS、短码长度、是否自定义短码、过期时间、统计需求和防滥用要求。核心方案通常是唯一 ID 生成加 Base62 编码，读多写少场景用缓存加速跳转，并对恶意链接做风控。

    • 原理/对比/实践注意：

      • 短码生成可用自增 ID、号段发号器、雪花 ID、随机码加冲突检测。

      • 存储表至少包含短码、长 URL、创建者、过期时间、状态、创建时间等字段。

      • 跳转接口要低延迟，可用本地缓存/Redis 缓存热门短码，数据库兜底。

      • 统计可异步上报点击事件，避免影响跳转延迟。

      • 关键风险：短码枚举、恶意 URL、缓存穿透、热点短链、隐私泄露和过期清理。

  • [ ] ★★★ 如何设计一个支持大文件上传的系统？

    • 简答：大文件上传通常采用分片上传、断点续传和对象存储直传，避免单个请求过大导致失败后重传成本高。设计时要澄清文件大小、并发量、校验要求、权限、存储周期和是否需要秒传。核心流程是初始化上传任务、上传分片、校验分片、完成合并或通知对象存储合并，并清理过期任务。

    • 原理/对比/实践注意：

      • 客户端按固定大小切片，每片带分片序号、文件 ID、校验值和上传凭证。

      • 服务端记录上传任务和已完成分片，支持查询进度以实现断点续传。

      • 完整性校验可用 MD5、SHA-256 或分片 ETag，秒传可基于文件哈希但要注意权限边界。MD5 仅适合非对抗场景的快速一致性校验；涉及恶意篡改、防碰撞或合规要求时应使用 SHA-256、HMAC 或服务端可信校验。

      • 大文件建议直传对象存储，业务服务只签发临时凭证并接收回调。

      • 关键风险：重复分片、乱序上传、并发合并、恶意占用存储、过期垃圾清理和病毒扫描。

  • [ ] ★★ 为什么异步化可以提高吞吐量？它的边界是什么？

    • 简答：异步化可以让请求线程不用等待慢操作完成，从而更快释放资源并承接更多请求。消息队列还能削峰填谷，把瞬时高峰转换成后端可处理的稳定流量。但异步化会引入排队延迟、最终一致性、失败补偿和观测复杂度，不适合所有强同步场景。

    • 原理/对比/实践注意：

      • 适合邮件短信、日志、积分、通知、报表、非核心状态同步等场景。

      • 不适合用户必须立即知道确定结果的强一致核心步骤，除非产品接受“处理中”状态。

      • 要处理消息丢失、重复消费、乱序、积压、死信和补偿。

      • 监控要覆盖生产速率、消费速率、lag、失败率和端到端延迟。

  • [ ] ★★ 多级缓存应该如何设计？

    • 简答：多级缓存通过 CDN、客户端缓存、本地缓存、分布式缓存和数据库逐层承接读流量，降低延迟和后端压力。设计时要明确数据更新频率、一致性要求、热点分布和失效策略。越靠近用户的缓存越快但一致性越弱，越靠近数据库的缓存越可控但承压更大。

    • 原理/对比/实践注意：

      • 常见层次：浏览器/客户端、CDN、网关缓存、应用本地缓存、Redis、数据库。

      • 更新策略包括 Cache Aside、写穿、写回、TTL 过期、主动失效和版本号。

      • 风险包括缓存穿透、击穿、雪崩、脏读、热点 key 和本地缓存不一致。

      • 核心数据要定义最大可接受过期时间，并通过监控缓存命中率和回源量验证效果。

  • [ ] ★★ 热点数据和热点用户如何处理？

    • 简答：热点数据是大量请求集中访问少量 key 或资源，热点用户是单个用户或少量用户产生异常高流量。处理思路是先识别热点，再通过复制、拆分、局部缓存、请求合并、隔离和限流降低冲击。不能只靠扩容，因为热点可能集中打到单个 key、单行或单分区。

    • 原理/对比/实践注意：

      • 识别方式包括访问日志、缓存 hot key 监控、数据库慢查询、分区负载和用户维度 QPS。

      • 热点 key 可做本地缓存、多副本、随机过期、请求合并或逻辑拆分。

      • 热点写可通过分段计数、队列串行化、批量聚合和异步落库处理。

      • 热点用户要限频、风控、隔离资源池，避免影响正常用户。

  • [ ] ★★ 什么是读写分离？它可能导致什么问题？

    • 简答：读写分离是把写请求发到主库，把读请求分发到一个或多个从库，以扩展读能力并降低主库压力。它适合读多写少场景，但会引入复制延迟和一致性问题。用户刚写完立即读从库时，可能读不到自己的最新写入。

    • 原理/对比/实践注意：

      • 常见策略是主库负责写和强一致读，从库承接普通读、报表读和低一致性读。

      • 复制延迟会影响读己之写、分页结果和状态判断。

      • 解决方式包括写后短时间读主、按用户会话路由读主、等待位点、关键读强制读主。

      • 故障切换时要处理主从角色变化、数据丢失窗口、连接池刷新和路由更新。

  • [ ] ★★ 系统如何做到高可用？

    • 简答：高可用的目标是在部分组件故障时，系统仍能提供核心服务，并把故障影响控制在可接受范围内。核心手段包括消除单点、冗余部署、故障检测与自动切换、隔离、限流降级、备份恢复和演练。高可用不是只部署多台机器，还要验证故障真的能被发现、切换和恢复。

    • 原理/对比/实践注意：

      • 需求澄清：目标 SLO/SLA、RTO、RPO、核心功能、降级边界和成本约束。

      • 核心方案：多实例、多可用区、负载均衡、健康检查、数据副本、熔断隔离、自动扩缩容。

      • 关键风险：共享依赖单点、配置中心故障、数据库主从切换失败、缓存雪崩、误判摘除。

      • 验证方式：故障演练、压测、混沌测试、备份恢复演练、告警到恢复链路检查。

9. 安全与接口设计

  • [ ] ★★★ SQL 注入产生的原因是什么？如何防止？

    • 简答：SQL 注入产生的根本原因是把用户输入当作 SQL 语句的一部分拼接执行，攻击者可以改变原本的查询语义。防护核心是使用参数化查询或预编译语句，让输入只作为数据而不是代码。还要配合最小权限、输入校验、错误信息收敛和审计监控。

    • 原理/对比/实践注意：

      • 不要用字符串拼接构造 where、order by、in 等片段；动态排序字段要用白名单映射。

      • ORM 不等于天然安全，手写原生 SQL 或拼接条件仍可能注入。

      • 数据库账号应按业务最小授权，避免应用账号拥有高危 DDL 或跨库权限。

      • 安全日志要记录异常参数、失败次数和来源，但不要记录密码、Token 等敏感明文。

  • [ ] ★★★ XSS 和 CSRF 有什么区别？如何防护？

    • 简答：XSS 是攻击者把恶意脚本注入页面，让脚本在用户浏览器中执行；CSRF 是利用用户已登录状态，诱导浏览器向目标站点发起非预期请求。XSS 防护重点是输出编码、输入净化和 CSP；CSRF 防护重点是 SameSite Cookie、CSRF Token、Origin/Referer 校验和关键操作二次确认。两者攻击入口不同，但都依赖浏览器安全边界。

    • 原理/对比/实践注意：

      • XSS 分为存储型、反射型和 DOM 型，富文本场景要使用可靠白名单过滤。

      • 输出编码要按上下文区分 HTML、属性、JavaScript、URL，不能一个转义函数通吃。

      • CSRF Token 应不可预测、与会话绑定，并在服务端校验。

      • SameSite 可降低 Cookie 被跨站携带的风险，但兼容性和业务跨站场景要评估。

      • 防住 XSS 很重要，因为一旦 XSS 成功，攻击者可能读取页面内容并发起带凭证请求。

  • [ ] ★★★ 身份认证和权限授权有什么区别？

    • 简答：身份认证解决“你是谁”，例如账号密码、短信验证码、OAuth 登录和多因素认证。权限授权解决“你能做什么”，即认证后的主体是否有权访问某资源或执行某操作。认证通过不代表拥有所有权限，授权应遵循最小权限原则。

    • 原理/对比/实践注意：

      • 认证结果通常产生会话、Token 或票据，授权在每次敏感资源访问时判断。

      • RBAC 按角色授权，适合组织和岗位明确的系统；ABAC 按属性、环境和资源条件授权，表达能力更强。

      • 权限模型要覆盖用户、角色、资源、操作、数据范围和租户边界。

      • 服务端必须做授权校验，不能只依赖前端隐藏按钮。

  • [ ] ★★★ 如何安全地存储用户密码？

    • 简答：用户密码不能明文存储，也不应使用普通快速哈希如 MD5、SHA-1 或单次 SHA-256。应使用专用慢哈希算法，例如 Argon2、bcrypt、scrypt 或 PBKDF2，并为每个用户生成随机盐。合理设置成本参数，配合登录限速、多因素认证和泄露监测，降低撞库和离线破解风险。

    • 原理/对比/实践注意：

      • 盐用于防止彩虹表和相同密码哈希相同，必须随机且每个密码不同。

      • 慢哈希通过增加 CPU/内存成本提高攻击者离线爆破成本，参数要随硬件能力调整。

      • 可增加 pepper 作为服务端全局秘密，但要放在密钥管理系统中，不能和数据库放一起。

      • 密码重置应使用短有效期一次性 Token，不应把原密码发给用户。

      • 登录接口要限速、风控和告警，错误提示避免泄露账号是否存在。

  • [ ] ★★ JWT 有哪些常见安全问题？

    • 简答：JWT 常见问题包括签名校验不严格、算法混淆、密钥泄露、过期时间过长、难以撤销、载荷放敏感信息和客户端存储不安全。JWT 默认只是编码和签名，不等于加密，任何拿到 Token 的人通常都能读取 payload。使用 JWT 时要明确有效期、签名算法、密钥轮换和撤销策略。

    • 原理/对比/实践注意：

      • 服务端必须固定允许的签名算法，不能信任 Header 中传入的 alg。

      • payload 不放密码、身份证号、手机号等敏感信息；需要保密时应使用加密方案或只放引用 ID。

      • 短期 Access Token 搭配 Refresh Token 更常见，Refresh Token 要可撤销和轮换。

      • 存储在 localStorage 易受 XSS 影响，存储在 Cookie 要关注 CSRF 和 SameSite/HttpOnly/Secure。

      • 登出、封禁和权限变更需要黑名单、版本号、短过期或集中会话校验支持。

  • [ ] ★★ RESTful API 应该如何设计？

    • 简答：RESTful API 应围绕资源建模，用 URI 表示资源，用 HTTP 方法表达操作语义。GET 用于查询，POST 常用于创建或非幂等操作，PUT/PATCH 用于更新，DELETE 用于删除。还要规范状态码、分页、排序、过滤、版本、错误结构、认证和幂等。

    • 原理/对比/实践注意：

      • URI 建议使用名词和层级关系，例如 /users/{id}/orders，避免把动作塞进路径。

      • GET、PUT、DELETE 通常应设计为幂等，POST 默认不幂等但可通过幂等键保护。

      • 分页要明确游标分页或页码分页，大数据和实时变化场景更适合游标分页。

      • 错误响应应包含稳定错误码、可读信息、请求 ID 和必要字段错误详情。

      • 版本管理可通过路径、Header 或媒体类型，关键是兼容策略清晰。

  • [ ] ★★ 接口如何防止重放攻击？

    • 简答：重放攻击是攻击者截获一次合法请求后，在之后重复发送以再次触发业务效果。防护通常使用时间戳、Nonce、请求签名、短有效期和服务端去重记录。传输层还应使用 HTTPS，避免请求内容和凭证被窃听或篡改。

    • 原理/对比/实践注意：

      • 时间戳用于限制请求有效窗口，例如 5 分钟内有效，但要考虑客户端和服务端时钟偏差。

      • Nonce 必须唯一且不可预测，服务端在有效期内记录已使用 Nonce，重复则拒绝。

      • 签名应覆盖方法、路径、查询参数、请求体摘要、时间戳和 Nonce，避免部分字段被篡改。

      • 对支付、下单等接口还要结合幂等键、业务流水号和状态机，防止合法重复提交造成重复处理。

      • Token 泄露、日志打印敏感参数和代理缓存都可能绕开设计，需要一起治理。

10. 工程实践、排障与项目题

  • [ ] ★★★ 线上接口突然变慢，你会如何排查？

    • 简答： 先止损、再定位，按“现象确认 → 范围划分 → 链路分段 → 根因验证 → 修复复盘”的顺序处理。不要一上来就重启或猜数据库，而应先确认开始时间、受影响接口、实例、地域、用户比例，以及平均值、P95、P99 和错误率是否同时变化。

    • 排查步骤：

      1. 查看监控和告警，判断是单实例、单接口、单机房还是全局问题，并对比近期发布、配置、流量和依赖变化。

      2. 沿网关、应用、缓存、数据库、消息队列和外部依赖逐段查看指标、结构化日志与 Trace，找出耗时增长的 Span。

      3. 检查 CPU、内存、GC、线程池、连接池、锁等待、磁盘和网络，区分资源耗尽、排队、慢查询、热点和依赖超时。

      4. 用回滚、摘除异常实例、限流、降级或扩容先恢复服务，再通过日志、Profile、执行计划等证据验证根因。

    • 实践注意： 每次只改变一个关键变量，并保留时间线。复盘应补齐监控、容量阈值、自动止损和回归测试，避免只记录“重启后恢复”。

  • [ ] ★★★ 服务出现大量 502、503 或 504 时如何定位？

    • 简答： 这些状态码通常由网关或代理返回，但含义不同：502 表示收到了无效的上游响应，503 表示服务暂时不可用，504 表示等待上游超时。先确认错误由哪一层产生，再检查该层到上游之间的连接和上游处理能力。

    • 定位重点：

      • 502：上游进程崩溃或重置连接、协议不匹配、响应头非法、端口或服务发现错误。

      • 503：无健康实例、过载保护、连接池或线程池耗尽、发布期间容量不足、熔断或主动拒绝。

      • 504：上游处理过慢、数据库或外部依赖超时、网关超时小于实际处理时间、网络丢包和重试放大。

    • 排查方法： 对齐网关访问日志、上游应用日志、Trace ID 和负载均衡健康检查，查看错误发生时的实例数量、连接数、队列长度、超时配置及最近发布。恢复后应统一各层超时预算，并通过容量测试验证。

  • [ ] ★★★ 如何设计日志、指标和链路追踪？

    • 简答： 三者分别回答“发生了什么”“整体是否异常”和“请求慢在哪里”。应通过统一的服务名、环境、版本、Trace ID 和业务标识将它们关联起来，而不是建设三套彼此割裂的观测系统。

    • 日志： 使用结构化字段，记录时间、级别、事件、请求 ID、错误码和必要上下文；避免重复打印大对象、密码、令牌和个人敏感信息。错误日志要保留堆栈，业务拒绝与系统异常要分开。

    • 指标： 请求侧关注 RED——Rate、Errors、Duration；资源侧关注 USE——Utilization、Saturation、Errors。延迟使用直方图和分位数，并按服务、接口和错误类型建立有节制的标签，防止高基数。不要把各实例的 P99 简单求平均；应聚合直方图桶，或使用监控后端支持的全局分位数计算。

    • 追踪： 每个跨服务调用建立 Span 并传播上下文，记录关键事件、状态和依赖耗时。高流量系统可采样，但错误和慢请求应提高采样率。

    • 告警： 围绕用户影响和 SLO 设计告警，包含现象、范围、仪表盘和操作手册，避免仅对瞬时资源波动告警。

  • [ ] ★★★ 超时应该如何设置？

    • 简答： 超时是容量与故障隔离机制，应从用户可接受的端到端延迟反向分配预算。调用方总超时要覆盖自身处理和下游调用，但不能层层设置为同一个大值；通常外层剩余预算应大于单次内层调用超时，并为网络抖动和收尾留空间。

    • 分类： 分别设置连接超时、TLS/握手超时、单次读取或请求超时、连接池获取超时和整个业务截止时间。长任务应改为异步任务或流式返回，而不是无限增大 HTTP 超时。

    • 确定方法： 结合依赖的正常 P99、SLO、历史长尾和压测数据设置，并在请求链路中传递 Deadline，让下游知道剩余预算。

    • 实践注意： 超时后不代表下游一定停止执行，因此写操作必须幂等。重试只用于可恢复且幂等的失败，使用次数上限、指数退避、抖动和重试预算，防止故障时流量放大。

  • [ ] ★★★ 什么是优雅停机？如何实现？

    • 简答： 优雅停机是实例退出时不再接收新工作，同时让已经接收的请求和任务在限定时间内完成或安全移交。目标不是永远等待，而是在数据正确性和停机时限之间做可控取舍。

    • 实现流程：

      1. 收到终止信号后把实例标记为不就绪，从注册中心或负载均衡摘除，并等待流量传播窗口。

      2. 停止接受新连接、请求和队列任务，保留已有连接完成在途工作。

      3. 等待请求、事务和后台任务结束，提交消费者 Offset 或把未完成任务重新入队。

      4. 刷新必要日志和缓冲区，关闭连接池等资源；超过截止时间后记录未完成工作并强制退出。

    • 实践注意： Kubernetes 等环境中要协调 readiness、preStop 和终止宽限期；客户端仍需重试和幂等，因为发布、宕机和网络故障不可能全部优雅。

  • [ ] ★★★ 灰度发布、滚动发布和蓝绿发布有什么区别？

    • 简答： 三者主要区别在流量切换方式、资源成本与回滚速度。滚动发布逐批替换实例；蓝绿发布维护两套完整环境后整体切换；灰度发布让少量用户或流量先进入新版本，观察后再逐步扩大。

    • 对比：

      • 滚动发布资源增量较小、流程通用，但新旧版本会共存，回滚需要再次滚动。

      • 蓝绿发布切换和回滚快、环境清晰，但接近双倍资源成本，数据库等共享状态仍需兼容。

      • 灰度发布最适合降低未知业务风险，可按用户、地域或比例路由，但需要稳定的流量标记、指标对照和自动回退。

    • 共同要求： API、消息和数据库结构必须向前/向后兼容；发布前定义成功指标和停止条件，发布中监控错误率、延迟和业务指标，异常时能自动或一键回滚。

  • [ ] ★★★ 如何保证数据库表结构变更不影响线上服务？

    • 简答： 使用“扩展—迁移—收缩”模式，把一次破坏性变更拆成多个向后兼容步骤。任何时刻都要允许新旧应用版本短期共存，不要在同一次发布中直接删除、重命名或改变旧代码依赖的字段语义。

    • 典型流程：

      1. 先新增可空或带安全默认值的字段/新表，并评估 DDL 是否会锁表、重写数据或产生大量日志。

      2. 发布兼容新旧结构的代码；需要时双写或使用变更数据捕获。

      3. 小批量、可暂停地回填历史数据，控制数据库负载，并校验数量、校验和及业务一致性。

      4. 将读取切到新结构，观察稳定后停止旧写入，最后在独立发布窗口删除旧字段或索引。

    • 实践注意： 大表变更应使用数据库支持的在线 DDL 或经过验证的在线迁移工具；准备回滚与备份，但应优先设计无需回滚数据格式的兼容方案。

  • [ ] ★★ 连接池为什么能提升性能？连接池应该如何配置？

    • 简答： 连接池通过复用已建立的数据库或网络连接，减少 TCP/TLS/认证和数据库会话创建成本，同时用池上限保护下游。它不会让数据库容量变大，池过大反而会增加上下文切换、锁竞争和排队。

    • 配置方法： 池大小应结合应用实例数、每实例并发、请求持有连接的时间和数据库允许连接数确定，保证所有实例连接上限之和不超过数据库安全容量。CPU 密集型数据库的有效并发通常远小于“请求数量”。

    • 关键配置： 设置获取连接超时、连接/空闲最大生命周期、健康检查和泄漏检测；监控活跃数、空闲数、等待数和等待时间。连接使用完必须在 finally 或等价机制中归还。

  • [ ] ★★ 单元测试、集成测试和端到端测试有什么区别？

    • 简答： 单元测试验证小范围逻辑并隔离外部依赖，速度快、定位准；集成测试验证多个模块或真实基础设施之间的协作；端到端测试从用户入口验证完整链路，最接近生产但速度慢、成本高且更易受环境影响。

    • 选择原则： 用大量单元测试覆盖分支、边界和纯业务规则；用集成测试验证 SQL、序列化、消息、缓存和框架配置；用少量端到端测试覆盖登录、下单、支付等关键用户路径。

    • 实践注意： 不要机械追求覆盖率。测试应可重复、独立并有明确断言；外部服务可在单元测试中使用替身，但关键协议兼容性必须由契约测试或集成测试证明。

  • [ ] ★★ 什么是 CI/CD？一条可靠的发布流水线应包含什么？

    • 简答： CI 是持续集成，即频繁合并并自动构建、检查和测试；CD 可指持续交付或持续部署，前者保证制品随时可发布，后者进一步自动发布到生产。核心是让每次变更都通过可重复、可审计的质量门禁。

    • 典型流水线： 代码检查 → 依赖与密钥扫描 → 编译构建 → 单元/集成测试 → 生成不可变且带版本的制品和 SBOM → 部署测试环境 → 冒烟/契约测试 → 分阶段生产发布 → 健康与业务指标验证 → 自动回滚或推进。

    • 实践注意： 同一制品应在各环境间提升而非重复构建；配置和密钥与制品分离；发布要有权限控制、审批策略、变更记录、数据库迁移顺序和经过演练的回滚方案。

项目经历追问

以下题目没有脱离个人经历的“标准答案”。回答时必须替换为自己的真实项目、职责和数据，可使用 STAR（情境、任务、行动、结果）组织语言，不要虚构规模或成果。

  • [ ] ★★★ 介绍一个你最熟悉的项目：背景、目标、架构、个人职责和最终结果。

    • 回答模板： “这是一个为 [用户/业务] 解决 [问题] 的系统，核心目标是 [可量化目标]。整体由 [入口、核心服务、存储、缓存、消息、部署方式] 组成，主链路是 [简述请求或数据流]。我负责 [明确模块和决策]，完成了 [关键行动]，最终 [延迟、吞吐、稳定性、成本或业务结果] 从 [基线] 改善到 [结果]。”

    • 展开顺序： 先用 30～60 秒讲清全貌，再根据面试官兴趣深入。明确“团队做了什么”和“我做了什么”，准备架构取舍、数据规模、故障和复盘等证据。

  • [ ] ★★★ 项目中最难的问题是什么？你如何定位、决策和验证？

    • 回答模板： 先说明问题为何难——例如低概率、跨服务、数据不一致或缺少观测；再给出影响范围和成功标准。按照“收集现象 → 提出可证伪假设 → 设计实验 → 排除干扰 → 锁定根因 → 比较方案 → 小流量验证”的时间线讲述。

    • 关键点： 展示证据而非英雄叙事，例如 Trace、火焰图、执行计划、压测或数据对账。解释为什么选择最终方案、放弃了什么，以及修复后如何用监控和回归测试证明问题消失。

  • [ ] ★★★ 你做过哪些性能优化？优化前后的指标分别是多少？

    • 回答模板： “在 [固定数据量和压测模型] 下，[接口/任务] 的 P99 为 [值]、吞吐为 [值]。通过 Profile/Trace/执行计划定位到 [瓶颈]，我采取 [优化措施]，结果 P99 变为 [值]、资源或成本变为 [值]，且错误率与一致性满足 [约束]。”

    • 关键点： 给出同口径基线、测试环境、流量模型和副作用。优化结果不只看平均延迟，也看 P95/P99、吞吐、CPU、内存、错误率和成本；说明是否经过线上灰度验证。

  • [ ] ★★★ 为什么选择当前技术方案？还比较过哪些方案？

    • 回答模板： 先列决策约束：一致性、吞吐、延迟、数据规模、团队经验、交付时间、成本和运维能力。说明至少两个候选方案，以相同维度比较其收益和风险，再解释当前选择为何最符合当时约束，而不是声称它“最好”。

    • 关键点： 补充决策的可逆性和退出方案，例如接口抽象、数据导出、灰度迁移和触发重新评估的阈值。若技术由团队既有平台决定，也应说明如何验证其适用性。

  • [ ] ★★★ 系统的流量规模、数据规模、机器规模和核心 SLA/SLO 是多少？

    • 回答模板： 准备日均与峰值 QPS/TPS、并发连接数、读写比例、日增数据量、存量及保留周期、应用与存储实例数量、单实例规格，以及可用性、P99 延迟和错误率目标。说明数据来自监控、容量平台还是估算，并注明统计周期。

    • 关键点： 区分 SLA（对外承诺）、SLO（内部目标）和 SLI（实际测量指标）。不了解精确数字时应给出可信区间和计算方式，不要编造；同时说明当前容量余量及峰值保护策略。

  • [ ] ★★★ 如果流量增长 10 倍，当前架构首先会在哪里遇到瓶颈？

    • 回答模板： 先说明不能只凭架构图判断，要基于每层利用率、排队时间和压测结果推断。按入口带宽与网关、应用 CPU/线程池、缓存热 Key、数据库连接/锁/I/O、消息分区和外部依赖逐层估算，指出最可能先达到饱和的资源及证据。

    • 扩展方案： 短期通过限流、缓存、批处理、扩容和降级获得余量；中长期用无状态横向扩展、读写分离、分片、异步化和热点隔离解决结构瓶颈。还要评估 10 倍数据增长、故障时冗余和成本，而不仅是正常流量。

  • [ ] ★★★ 项目发生过什么线上故障？如何止损、定位、修复和预防复发？

    • 回答模板： 用时间线说明发现方式、用户影响、持续时间和严重级别。依次讲立即止损（回滚、摘流、限流或降级）、证据和根因、永久修复、数据补偿，以及如何验证恢复。

    • 复盘要求： 区分直接原因、促成因素和系统性根因，避免归咎个人。行动项应有负责人和截止时间，覆盖监控告警、容量、测试、发布门禁、操作手册和演练；说明哪些改进已经落地并证明有效。

  • [ ] ★★ 如果重新设计这个项目，你会改变什么？

    • 回答模板： 先肯定原方案在当时约束下的合理性，再基于已知流量、故障和维护成本指出一到三个最有价值的改变。例如收紧服务边界、简化不必要的异步链路、补齐幂等和观测、调整数据模型，而不是为了“新技术”整体重写。

    • 关键点： 对每个改变说明收益、迁移成本、风险、优先级和分阶段方案。也可说明哪些设计虽然不完美但无需改变，以体现成本意识。

  • [ ] ★★ 你如何证明自己负责的功能正确、稳定且可维护？

    • 回答模板： 正确性由需求验收、单元/集成/契约测试、数据约束和边界用例证明；稳定性由压测、故障注入、灰度指标、SLO 和线上告警证明；可维护性由清晰接口、代码评审、静态检查、文档、运行手册和低风险发布流程证明。

    • 关键点： 给出实际证据，例如关键路径覆盖、连续运行周期、错误预算、故障恢复时间或变更失败率。不要只说“代码规范好”，要说明团队如何持续发现回归并安全演进。
