学习目标

  • 区分泄漏、仍可达增长、碎片、缓存和高峰驻留。
  • 建立从趋势观测到分配定位再到回归测试的证据链。
  • 使用稳定基准和统计方法拦截性能回归。

前置知识与完成标准

建议先理解虚拟内存、RAII、智能指针、容器资源限制和基本统计。完成本章后，你应能把“内存一直涨”分解成可检验假设，选择泄漏检测或 heap profiling 工具，并设计能区分真实回归与测量噪声的性能门禁。

1. 核心概念：“内存上涨”不等于泄漏

常用观察量：

  • RSS：当前驻留在物理内存中的页，包含堆、栈、映射等。
  • 虚拟内存：地址空间映射规模，不等于实际物理占用。
  • allocator 已分配/保留内存：应用对象与 allocator arena/cache 可能不同。
  • 容器工作集/限制：受 cgroup 统计和回收语义影响。

常见原因：

现象 解释
对象失去引用但未释放 真正的泄漏
容器/缓存无限增长 对象仍可达，是生命周期或容量策略问题
负载下降后 RSS 不降 allocator 保留、碎片或内核页回收行为
线程数增长伴随内存增长 线程栈、TLS 或线程生命周期问题
mmap/文件缓存增长 映射或页缓存，不一定是 C++ 堆
瞬时峰值导致 OOM 峰值工作集超过限制，即使最终会释放

因此先画时间线：负载、RSS/工作集、堆统计、线程、文件描述符、缓存条目和 OOM 事件是否共同变化。

1.1 进程、allocator 与容器是三套视角

  • /proc/<pid>/status 的 VmRSS/VmSize 从进程视角汇总，/proc/<pid>/smaps_rollup 可进一步区分匿名、文件映射和共享页。
  • allocator 视角区分应用正在使用的 bytes 与为复用而保留的 arena/page；应用已 delete 不保证 RSS 立即归还内核。
  • cgroup v2 的 memory.current、memory.stat、memory.events 和 memory.peak 描述容器/工作负载整体；oom 与 oom_kill 能区分分配压力和实际杀进程事件。

三个值口径不同，不能直接互相减得出“泄漏量”。正确做法是在同一时间轴对齐请求量、对象数、allocator 指标、进程映射和 cgroup 事件。

1.2 四类增长的验证方式

假设 关键证据 反证
不可达泄漏 LSan/Memcheck 报告失去根指针的分配栈 退出时无报告不等于长驻服务无问题
仍可达无界增长 业务对象/缓存/队列计数随操作轮次持续增大 达到明确上限并稳定
allocator 保留/碎片 活跃堆下降而 RSS 不降，size class/arena 保留高 活跃对象本身仍增长
非堆资源增长 线程、mmap、文件、socket 或页缓存同步增加 相关计数稳定

“重启恢复”对四类情况都可能成立，因此不能作为泄漏证明；它只是确认增长属于进程/容器生命周期。

2. 典型工作流：泄漏排查流程

2.1 建立可重复场景

  1. 固定版本、配置、输入数据和请求序列。
  2. 预热后执行 N 轮相同操作。
  3. 每轮回到近似空闲，观察长期斜率而非单个点。
  4. 同时记录对象/缓存业务计数，区分预期保留。
  5. 缩小到测试或预生产的最小复现，再使用重型工具。

2.2 首选动态检查

ASan/LeakSanitizer 适合在可复现测试中发现直接/间接泄漏：

cmake -S . -B build/asan \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DENABLE_ASAN_UBSAN=ON
cmake --build build/asan --parallel
ctest --test-dir build/asan --output-on-failure

具体泄漏检测支持和环境变量依赖平台/工具链。先阅读当前编译器文档；不要把本章示例当作所有平台的统一开关。

Valgrind Memcheck 可用于未插桩的部分 Linux 用户态程序：

valgrind --leak-check=full --show-leak-kinds=all ./build/test_scenario

它通常非常慢，会显著改变时序，不适合直接套在高负载生产服务上；优先用于缩小后的测试场景。

2.3 分配 profile

若对象仍可达或 RSS 与堆不一致，使用与当前 allocator/平台匹配的 heap profiler，比较时间点或操作轮次间的分配栈。采集时记录：

进程与制品 ID、allocator、采样率、开始/结束时间
请求数、数据规模、负载阶段、RSS/工作集
profile 原始文件、符号与分析命令

工具显示“谁分配”不一定显示“谁本该释放”。最终仍要回到所有权、生命周期和容量边界。

2.4 从零实验：不可达泄漏与仍可达增长

#include <chrono>
#include <iostream>
#include <memory>
#include <string>
#include <thread>
#include <vector>

std::vector<std::unique_ptr<int[]>> cache;

int main(int argc, char** argv) {
  const std::string mode = argc > 1 ? argv[1] : "leak";
  if (mode == "leak") {
    new int[1024];  // 故意丢失最后一个指针
    return 0;
  }

  for (int round = 1; round <= 10000; ++round) {
    cache.emplace_back(std::make_unique<int[]>(1024));
    if (round % 100 == 0) std::cout << "cache=" << cache.size() << '\n';
    std::this_thread::sleep_for(std::chrono::milliseconds(2));
  }
}

clang++ -O1 -g -fsanitize=address -fno-omit-frame-pointer leak.cpp -o leak
ASAN_OPTIONS=detect_leaks=1 ./leak leak

# 另开终端观察这个长运行模式的对象计数与 RSS：
./leak grow

leak 模式预期由 LSan 报告不可达分配。grow 模式在运行期间持续打印 cache.size()，应同时用 ps、进程/cgroup 指标观察 RSS；进程正常退出后全局容器会析构释放，因此退出时报告不能证明或否定运行期间的无界增长。这个实验明确区分：泄漏工具寻找失去引用的分配，容量/生命周期监控寻找仍可达但无界的对象。

2.5 读懂 Memcheck 泄漏分类

  • definitely lost：找不到指向块的指针，优先修复。
  • indirectly lost：只被已经丢失的块引用，常随根块修复而消失。
  • possibly lost：只找到内部指针，需要结合数据结构判断。
  • still reachable：存在根路径；可能是有意常驻，也可能是无界缓存。

报告里的分配栈回答“从哪里申请”，不会自动回答“在哪丢失指针”。先处理最上游 definitely lost，再重跑，避免同一棵对象图产生大量次级记录。

3. C++ 所有权设计检查

  • 用 RAII 将资源释放绑定对象生命周期。
  • 默认用值语义或 std::unique_ptr 表示唯一所有权。
  • std::shared_ptr 只在确有共享所有权时使用，并检查环；反向观察可用 std::weak_ptr。
  • 明确回调、定时器、任务队列和协程捕获对象的生命周期。
  • 为缓存设置容量/TTL/淘汰策略及可观测计数。
  • 文件描述符、socket、线程、mmap 和 GPU/外部句柄同样会泄漏，不要只盯 C++ 堆。

3.1 用所有权图审查异步代码

对每类长寿命对象画有向边：谁拥有谁、边是 unique/shared/observer、何时断开。常见环包括“对象持有定时器，定时器回调捕获对象的 shared_ptr”和两个对象互持 shared_ptr。将回调改捕获 weak_ptr 时还要在执行时 lock() 并处理对象已销毁，而不是假定一定存在。

RAII 只保证拥有 RAII 成员的对象析构时释放资源；若该对象永不析构、线程被永久阻塞或所有权形成环，RAII 本身不会解决生命周期错误。

3.2 缓存必须有数学边界

至少定义最大条目/字节数、TTL、淘汰策略、单对象上限和拒绝行为。仅有 TTL 但流入速度高于过期速度，仍可能在窗口内耗尽内存；仅有条目数但对象大小无界，也没有字节上限。指标应同时记录条目、估算 bytes、命中/淘汰、拒绝和加载并发。

4. 性能回归的基线设计

性能回归需要可比较的基准：

  • 微基准：定位函数/算法变化，快但容易脱离系统现实。
  • 组件基准：包含序列化、存储、线程池等真实边界。
  • 端到端负载测试：验证用户可见吞吐和延迟，噪声与成本更高。

至少跟踪：吞吐、p50/p95/p99、CPU 时间/请求、分配字节/请求、峰值/稳态内存。根据系统加入磁盘、网络、锁等待或能耗。

4.1 微基准最容易测错什么

  • 编译器发现结果未使用而删除被测工作；需用框架提供的优化屏障或可验证输出。
  • 把输入构造、I/O 或日志算进算法时间，测到的不是目标代码。
  • 数据过小全部驻留 cache，或数据排列与生产完全不同。
  • 只测单线程，却把结果外推到有锁竞争的服务。
  • 使用 wall time 但受调度干扰，或使用 CPU time 却忽略真实等待。

微基准用于定位局部成本，不自动代表用户体验。任何声称影响发布的结果都应在组件或端到端层复验。

5. 示例：降低基准噪声与结果表

  1. 固定机器类型、CPU 配额、编译器、flags、依赖、数据与后台负载。
  2. 预热并明确是否测冷启动。
  3. 每个候选与基线多轮交错运行，避免时间漂移偏向一方。
  4. 保存每轮原始值，报告中位数、分布/置信区间，而不只写单次百分比。
  5. 防止编译器消除无副作用工作；校验结果正确。
  6. 微基准异常后，用 profile 定位，并用更高层测试确认用户影响。

5.1 比较而不是只看百分比

若基线为 100 ns、候选为 103 ns，+3% 是否可信取决于轮次波动和环境噪声。至少保存每轮样本，报告中位数、均值、标准差/变异系数，并查看分布是否有异常双峰。基线与候选交错或随机顺序运行，可降低温度、频率和后台任务随时间漂移造成的偏差。

性能差异还要有实际意义：3 ns 的稳定差异可能对十亿次热循环重要，对每秒一次管理操作无关紧要。门禁同时设置统计可信度、相对阈值和绝对业务影响更合理。

使用 benchmark 框架时，明确 warm-up、最短运行时间、重复次数与输出格式。先 dry run 验证正确性，再进行正式重复；不要为了得到期望结论反复挑选最好的一轮。

6. CI 中的性能门禁

共享 CI 主机的噪声通常不足以支持“任何一次慢 3% 就失败”。可采用分层策略：

每个提交：快速正确性 + 粗粒度性能 smoke，明显退化才阻断
每日/合并后：受控 runner 上重复基准，统计比较并保存趋势
发布前：端到端容量场景 + CPU/内存 profile 对比
生产：每请求资源、延迟与错误预算趋势，发现环境真实回归

阈值应结合历史波动、业务影响和测量成本。失败任务要保留环境、原始样本、基线提交、候选提交和 profile，以便复验。

6.1 性能门禁状态机

候选结果越界
├─ 正确性失败：直接阻断
├─ 测量环境异常：标记无效并重建干净 runner
├─ 落在历史噪声灰区：自动重复/配对复验
├─ 稳定回归且超业务阈值：阻断并采 profile
└─ 稳定改善：仍检查正确性、资源转移和代表性

基线应是可追溯的稳定提交或同机交错运行结果，不应使用数月前不同硬件的一个常数。更新基线必须保留审计记录，防止通过“接受新基线”掩盖回归。

7. 常见坑与排障步骤

  • 只看最终 RSS：补充斜率、堆/映射、allocator、线程和缓存计数。
  • 把有界缓存当泄漏：验证是否到达稳定上限以及淘汰是否正确。
  • Debug 与 Release 比性能：使用一致的优化、符号、断言和依赖配置。
  • 微基准快了但服务变慢：检查锁竞争、分配、缓存局部性和下游交互。
  • 基准输入过小：数据全在缓存，未覆盖生产工作集。
  • 自动门禁频繁抖动：先量化 runner 噪声，增加重复、配对运行和灰区复验。
  • 修复泄漏后性能退化：检查所有权变更是否增加拷贝、锁或频繁释放；同时验证正确性和性能。

排障顺序：先核对口径和时间轴；对象计数增长就追业务生命周期，LSan 报告就追分配/所有权，活跃堆下降而 RSS 高就看 allocator/映射，cgroup 触发 high/max/oom 就看限制与回收；性能门禁失败先验证 runner 和构建一致性，再重复测量，确认稳定后才 profile。不同问题不要一上来都用同一个 heap 工具。

8. 练习

  1. 基础：完成不可达/仍可达实验。答案要点：工具未报告全局 cache 不代表其增长可接受。
  2. 进阶：写一个 shared_ptr 环，用所有权图定位并以 weak_ptr 修复。答案要点：说明 observer 边及对象已销毁时的行为。
  3. 进阶：创建有字节上限与无上限缓存做浸泡测试，对齐 RSS、活跃堆、对象计数和淘汰数。
  4. 综合：为字符串解析建立微基准，引入额外分配后交错运行至少五轮，用分配 profile 定位，并在组件测试确认影响。

9. 检查清单

  • [ ] 已区分 RSS、堆、虚拟内存、缓存、线程栈和映射。
  • [ ] 泄漏场景可重复，观察了多轮操作后的增长斜率。
  • [ ] 动态工具在受控环境运行，报告关联精确符号和版本。
  • [ ] 所有权、回调、缓存和非内存资源生命周期均检查。
  • [ ] 性能基线固定构建、环境、数据与负载，并保存原始样本。
  • [ ] 候选与基线重复、可比，结果同时包含吞吐、尾延迟与资源成本。
  • [ ] CI 门禁阈值基于历史噪声，失败可复验并有 profile 证据。

10. 小结

内存问题要先分口径再选工具：泄漏检测找不可达分配，heap profile 找分配热点和仍可达增长，进程/cgroup 指标解释总工作集与 OOM。性能回归同样是测量问题：固定环境、重复交错、保留原始样本，再用 profile 解释差异并在更高层验证业务影响。
