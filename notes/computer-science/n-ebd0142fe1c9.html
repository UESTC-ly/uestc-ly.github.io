03 可观测性与配置发现

本组笔记面向有 C++/后端基础的学习者，目标是把“系统怎么被配置、怎么找到彼此、怎么被观察”串成一条可实践的工程链路。建议按下面顺序学习：

  1. 配置中心与服务发现
  2. 日志、指标、Trace 三类信号
  3. Prometheus 与 Grafana
  4. ELK 与 Loki
  5. OpenTelemetry

推荐学习路径

先理解配置与发现，因为它们决定服务实例如何启动、如何注册、如何被调用。再学习可观测性三类信号，区分日志、指标、Trace 的用途和数据模型。随后分别看指标可视化栈 Prometheus/Grafana、日志栈 ELK/Loki，最后用 OpenTelemetry 统一采集链路和上下文传播。

本组共同关注点

  • 配置中心解决“运行参数从哪里来、如何变更、如何回滚”。
  • 服务发现解决“调用方如何找到健康的服务实例”。
  • 日志适合解释离散事件，指标适合低成本聚合趋势，Trace 适合还原一次请求跨服务路径。
  • 三类信号需要用统一的服务名、环境、版本、实例 ID、Trace ID 等字段关联。
  • 标签和字段不是越多越好，高基数会直接推高存储、查询和告警成本。
  • C++ 接入通常通过 SDK、sidecar/agent、日志库、Prometheus exporter、OpenTelemetry C++ SDK 或网关代理完成，不应绑定单一厂商。

最小实践环境

可以用一个 C++ HTTP 服务或任意后端服务作为练习对象：

  • 暴露 /metrics 给 Prometheus 抓取。
  • 日志输出 JSON 到 stdout 或文件，由采集器转发。
  • 在入口生成或接收 Trace 上下文，并把 Trace ID 写入日志。
  • 通过配置文件或配置中心控制端口、依赖地址、采样率和日志级别。

学习完成检查

  • 能说清配置中心和服务发现的职责边界。
  • 能为一个服务设计基础日志字段、指标名、Trace span 名称。
  • 能判断一个标签是否可能造成高基数风险。
  • 能用 PromQL 查询错误率、延迟分位数和实例健康状态。
  • 能解释 ELK 与 Loki 的索引模型差异。
  • 能画出 OpenTelemetry 从 SDK 到 Collector 再到后端的链路。
