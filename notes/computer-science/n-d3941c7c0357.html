8. 高并发系统设计

  • [ ] ★★★ 设计一个高并发系统时，应该从哪些方面入手？
  • 完整回答：
    • 设计高并发系统首先要把目标量化：峰值 QPS/TPS、读写比例、请求包大小、P95/P99 延迟、错误率、可用性等级、数据一致性要求、可接受排队时间、成本上限和故障恢复目标。架构上通常从入口到存储逐层拆解，入口层用 DNS、CDN、负载均衡、WAF 和限流承接流量；应用层保持无状态，按水平扩容部署，并用线程池、连接池、超时和熔断控制资源；读链路用 CDN、浏览器缓存、本地缓存和 Redis 降低回源；写链路用分库分表、批量写入、异步队列和幂等机制削峰；核心数据通过主从、副本、分片和备份保障可用性。容量估算要按峰值而不是日均值设计，例如活动峰值可能是日均的几十倍，并且要预留 N+1、跨可用区故障和下游限额的冗余。高并发的关键不是单点性能最大化，而是让每个环节都有限制、有降级、有观测，避免某个慢依赖拖垮全链路。数据流上应区分同步强一致路径和异步最终一致路径，订单支付、库存扣减等核心状态必须有原子约束和对账，通知、日志、统计等可异步处理。热点数据要单独治理，不能假设请求均匀分布；大客户、活动页、热门商品和热门短链都可能让单个 key、单行或单分区先被打满。部署上还要考虑发布期间容量下降、扩容预热、配置回滚和跨机房流量调度，避免设计只在静态架构图中成立。安全和风控也属于高并发边界，异常流量、爬虫和恶意重试会消耗真实容量，入口识别能力必须纳入设计。异常路径包括缓存失效、数据库热点、队列堆积、连接池耗尽、重试风暴和下游超时，需要提前定义限流、快速失败、只读模式、降级返回和补偿任务。验证方法包括容量压测、热点压测、故障演练、降级演练和长稳测试，指标覆盖吞吐、延迟、错误率、饱和度、队列 lag、缓存命中率、慢 SQL、GC、连接数和资源利用率。

  • 原理解析：

    • 高并发设计的底层不是“多加机器”，而是把系统看成一串排队服务台：入口、应用、缓存、数据库、队列和第三方依赖每一段都有到达率、服务率和等待队列。只要某一段服务率低于到达率，等待时间就会按非线性方式上升，P99 先恶化，随后线程、连接和内存被等待请求占住，吞吐反而下降。因此先量化峰值、延迟和错误率，是为了知道每个服务台需要多大的处理能力和多长的缓冲。
    • 容量、瓶颈和扩展性是一组因果关系：容量估算给出目标负载，压测发现最先饱和的资源，扩容或拆分只是把瓶颈向后移动。应用无状态化之所以能水平扩展，是因为请求不依赖某台机器的本地状态，负载均衡可以把流量均匀分摊；代价是会话、缓存、本地任务和幂等状态要外置，否则扩容后会出现状态不一致或重复处理。
    • 缓存、异步和分片分别解决不同方向的压力：缓存减少读请求回源，异步把瞬时写入变成可控消费，分片把单个存储节点的 CPU、I/O、锁和索引容量拆开。它们都不是免费的，缓存带来一致性和失效风暴，异步带来最终一致和补偿，分片带来路由、聚合查询、热点倾斜和迁移成本。设计能扩展，是因为让负载按层、按时间或按数据空间被摊开；代价是复杂度和一致性边界上升。
    • 失败边界要从“资源会满”出发记忆：线程池满要拒绝，连接池满要快速失败，缓存失效要限流回源，队列堆积要有过期和降级，下游慢要熔断。记忆抓手是“峰值定容量，瓶颈定架构，状态定一致性，故障定边界”：先算量，再找窄口，再决定同步还是异步，最后把超过能力的请求明确挡在系统外，并用监控水位证明边界仍然有效。

  • [ ] ★★★ QPS、TPS、吞吐量、并发数、响应时间和 P99 分别是什么？

  • 完整回答：
    • QPS 是每秒请求数或查询数，常用于衡量接口、网关、缓存或数据库查询入口承受的请求频率；TPS 是每秒完成的业务事务数，一个事务可能包含多个接口调用、数据库操作和消息投递，因此 TPS 往往比单接口 QPS 更接近业务处理能力。吞吐量表示单位时间内系统完成的工作量，可以用请求数、事务数、消息数、字节数或订单数描述，必须说明统计口径。并发数是某一时刻正在系统内处理、等待或保持连接的请求数量，不等同于每秒请求量。响应时间是单次请求从客户端发出到收到结果的耗时，通常拆成网络耗时、排队耗时、应用处理、下游调用和序列化返回。P99 是 99 分位响应时间，表示 99% 的请求耗时不超过该值，剩下 1% 更慢，它比平均值更能暴露长尾延迟。粗略关系可用 Little 定律理解：稳定系统中的平均并发数约等于吞吐量乘以平均响应时间，例如 1000 QPS、平均响应 100ms 时，系统内平均并发约为 100。实际系统还要区分活跃请求并发、连接并发、线程并发和用户在线并发，因为 WebSocket、长轮询、慢查询会让连接数和处理并发差异很大。容量判断还要看饱和度，吞吐增长到某个点后如果 CPU、锁、连接池或 I/O 打满，继续加压只会推高响应时间和超时率。统计时还要说明失败请求是否计入 QPS、超时请求如何归类、客户端限速是否开启，否则指标会被压测工具口径扭曲。线上还要按接口、租户、地域和依赖拆分指标，整体 QPS 平稳时局部热点仍可能导致少数用户不可用。压测报告中这些指标必须绑定成功率、数据规模、机器配置、统计窗口、预热时间和限流策略，否则两个 QPS 数值不可比较。高并发优化不能只追求平均响应更低，还要压低 P95、P99 和超时率，因为少量长尾请求会占住线程、连接和队列，进一步降低吞吐并触发级联故障。

  • 原理解析：

    • 这些指标描述的是同一条排队链路的不同侧面：QPS/TPS 是单位时间进入或完成的流量，吞吐量是系统实际完成工作的速率，并发数是系统内同时滞留的请求数，响应时间是请求停留时间。Little 定律把它们连起来：稳定状态下，并发数约等于吞吐量乘以平均响应时间。响应时间变长时，即使 QPS 不变，系统内滞留请求也会增多，于是线程、连接、队列被占住。
    • QPS 与 TPS 的区别来自“接口”和“业务事务”的粒度不同。一次下单 TPS 可能包含查商品、校验库存、扣库存、建订单、发消息等多个请求，所以接口 QPS 高不代表业务 TPS 高。容量设计必须按关键事务链路估算，因为真正限制业务成功率的可能是其中最慢的扣库存或支付确认，而不是入口接口。
    • P99 的价值在于揭示长尾。平均响应时间会把少数慢请求摊薄，但高并发下慢请求会长期占用资源，并通过排队影响后续请求。一个数据库慢查询、一次 GC、一个下游超时都可能只影响 1% 请求，却足以耗尽连接池并把尾部延迟传染到整体吞吐。看 P99 本质上是在看系统最脆弱的拥塞边界。
    • 记忆抓手是“速率、存量、时长、尾部”：QPS/TPS 看速率，并发数看存量，响应时间看时长，P99 看尾部风险。失败边界是系统进入饱和后，吞吐不再随并发提升而提升，只会把更多请求压进队列；因此调优不能只加并发，还要缩短服务时间、隔离慢依赖或主动拒绝超额流量。压测报告必须同时绑定成功率、资源水位和统计窗口，否则高 QPS 可能只是大量失败或客户端等待堆出来的表面数字。
    • 指标之间还要按层拆口径：入口 QPS、应用成功 QPS、数据库查询 QPS 和业务 TPS 可能完全不同。只有把失败、超时、重试和缓存命中都放进同一张因果图，才能判断系统是真的变快，还是把等待转移到了客户端或后台队列。

  • [ ] ★★★ 如何估算系统容量？

  • 完整回答：
    • 容量估算从业务规模开始，而不是从机器数量开始。先确定日活、月活、峰值在线、核心操作频次、活动峰值系数、读写比例、请求和响应大小、数据保留周期、目标 P99、可用区故障冗余和增长预期。入口容量按峰值 QPS/TPS 估算，例如日均请求要换算成高峰小时、高峰分钟甚至秒级突发，并额外乘以活动、重试和爬虫流量系数。应用容量需要通过基准压测得到单实例在目标延迟和资源利用率下的稳定 QPS，再按目标利用率计算实例数，通常不能让 CPU、连接池或线程池长期接近满载，要为发布、故障摘除和扩容延迟留冗余。缓存容量按热点 key 数量、对象大小、TTL、命中率和副本开销估算，还要考虑大 key、热 key、淘汰策略和缓存回源峰值。数据库容量分读、写、存储、索引、连接数、事务锁和 IOPS 估算，写入还要考虑 binlog、WAL、主从复制、备份、归档和分片增长。带宽按 QPS 乘以平均响应大小并叠加 TLS、压缩、图片或文件流量估算。队列容量按生产峰值、消费能力、最大可接受积压时间和消息大小估算，同时确保磁盘和重放速度足够。还要估算数据增长后的二阶影响，例如索引膨胀导致缓存命中下降、历史表变大导致备份恢复变慢、日志量上升导致磁盘和链路成本增加。容量模型要沉淀成可复算表格，标出假设、峰值系数和安全系数，便于业务增长或架构调整后快速更新。估算结论要转成告警水位，例如 60% 观察、75% 扩容、90% 降级，使容量规划能在运行期落地。下游依赖要核对第三方接口限额、支付通道、短信通道和对象存储限速，因为全链路容量取决于最窄的一段。估算之后必须用压测校准，单机压测、全链路压测、容量水位压测和故障场景压测都要覆盖，最终形成资源水位、扩容阈值和降级阈值。

  • 原理解析：

    • 容量估算的本质是把业务事件转换成资源消耗。用户量和操作频次生成入口 QPS/TPS，请求大小生成带宽，读写比例生成缓存和数据库压力，数据保留周期生成存储、索引和备份成本。只用日均值会低估排队风险，因为系统在峰值窗口才会饱和；平均一天 8640 万次请求只是 1000 QPS，但如果集中在 1 小时就是 24000 QPS。
    • 队列论上，资源利用率越接近 100%，等待时间增长越陡。容量规划常把目标利用率控制在 60% 到 75%，不是浪费，而是给抖动、发布、故障摘除、GC、慢 SQL 和下游波动留空间。N+1 的意义也在这里：少一批实例或一个可用区时，剩余服务率仍大于核心到达率，系统才不会进入无限排队。
    • 各层容量不能孤立相加，而要按数据流传导校验。缓存命中率下降 5%，可能把大量读请求转移到数据库；队列生产峰值大于消费能力，会把压力变成 lag 和磁盘占用；数据库写入不仅消耗行更新，还消耗索引维护、WAL/binlog、复制和备份带宽。容量模型要记录假设，是因为任何一个假设变化都会沿链路放大。
    • 设计方案能扩展，通常靠水平加实例、增加缓存副本、拆分分区或增加消费者；代价是负载均衡、缓存一致性、跨分片查询、消息顺序和运维成本。记忆抓手是“人次转请求，请求转资源，峰值乘系数，水位定动作”。失败边界是最窄依赖的限额，例如短信通道或支付网关只有固定 TPS，即使内部机器足够也无法提高全链路成功率。估算还要反推恢复窗口：队列积压多久能排空、备份多久能恢复、扩容多久能生效，这些时间决定容量冗余是否真的可用。
    • 估算结果要能落到运行动作上。比如实例数对应扩容阈值，数据库 IOPS 对应慢查询和归档策略，队列积压时间对应降级开关。不能触发告警和决策的容量数字，只是静态表格，无法在业务增长或故障发生时保护系统。

  • [ ] ★★★ 如何发现系统瓶颈？

  • 完整回答：
    • 发现瓶颈要先定义现象和基线：是吞吐上不去、P99 变差、错误率升高、部分租户慢、某个接口慢，还是在固定时间段退化。排查顺序应沿请求链路从入口到依赖逐层收敛，入口看负载均衡、网关限流、连接数、TLS 握手和网络丢包；应用看 CPU、内存、GC、线程池、连接池、锁等待、队列长度、异步任务堆积和下游调用耗时；缓存看命中率、热 key、大 key、慢命令、连接数和网络带宽；数据库看慢 SQL、执行计划、索引命中、锁等待、事务时长、连接耗尽、主从延迟和磁盘 I/O；消息队列看生产速率、消费速率、lag、重试、死信和分区倾斜。瓶颈的典型特征是某个资源先达到饱和，继续增加压力时吞吐不再增长而延迟和错误率快速上升。定位工具包括指标看板、结构化日志、分布式追踪、线程栈、火焰图、慢查询日志、数据库执行计划和压测曲线。需要避免只看平均值，平均 CPU 不高并不代表没有单核打满、锁竞争或短时尖峰；平均延迟正常也可能掩盖少数接口的 P99 超时。验证瓶颈时每次只改变一个变量，例如增加应用实例、扩大连接池、加索引、调整缓存 TTL 或隔离下游调用，并观察目标指标是否改善；如果吞吐随应用扩容线性提升，瓶颈在应用层的概率高，如果扩容后数据库 CPU、锁等待或慢 SQL 同步恶化，则瓶颈转移到了数据层。线上排障还要关联发布、配置、流量来源和数据分布变化，很多瓶颈由新 SQL、新索引缺失、热点租户或批任务叠加触发。对于偶发瓶颈，要保留现场快照和采样数据，事后仅凭日志很难还原锁等待、线程堆积和连接耗尽的瞬间。修复后要重新压测并更新告警阈值，因为瓶颈会转移到下一层，原来的局部优化可能暴露新的容量上限。最终要把瓶颈定位为具体资源、具体代码路径和具体触发条件，而不是停留在“系统慢”。

  • 原理解析：

    • 瓶颈是排队链路中最先达到服务率上限的环节。它的典型曲线是：压力上升初期吞吐随之上升，接近饱和后吞吐趋平，延迟、排队长度和错误率开始陡增。CPU、磁盘、网络、锁、连接池、线程池、分区和下游限额都可能成为服务台，只看某一个全局指标容易误判。
    • 定位要沿数据流看“请求在哪里等”。入口层等待表现为连接建立慢、TLS 握手堆积、限流命中；应用层等待表现为线程池队列、GC、锁竞争、连接池 borrow 慢；缓存层等待表现为 hot key、大 key、网络带宽或命中率下降；数据库等待表现为锁、慢 SQL、IOPS、执行计划和连接耗尽；队列等待表现为 lag、重试和分区倾斜。每一类等待都对应不同的修复方向。
    • 验证瓶颈要做受控变量实验。增加应用实例后吞吐线性上升，说明应用层还有横向扩展空间；增加实例后数据库锁等待暴涨，说明瓶颈已转移到数据层；加缓存后 P99 下降但一致性问题增加，说明读路径压力被缓存吸收。瓶颈不是一次定位永久消失，而是系统扩容后不断迁移。
    • 失败边界来自“局部饱和导致全局阻塞”：一个慢下游会占住上游线程，一个热 key 会拖慢整个 Redis 节点，一个单行锁会让数据库连接堆满。记忆抓手是“四看”：看吞吐是否平台化，看延迟是否尾部化，看队列是否增长，看资源是否饱和；最终答案必须落到具体资源、具体调用和具体触发条件。若只说“数据库慢”或“网络慢”，没有对应 SQL、分区、接口、时间段和触发流量，就还没有真正定位瓶颈。
    • 观测数据要按时间对齐。发布、配置变更、活动流量、批任务和依赖抖动都可能改变同一条链路的排队点；追踪看单请求因果，指标看群体趋势，日志看具体参数，三者合起来才能区分代码慢、数据倾斜和资源不足。

  • [ ] ★★★ 如何应对突发流量？

  • 完整回答：
    • 突发流量要按可预测和不可预测两类处理。可预测流量如秒杀、直播、营销活动，需要提前容量评估、缓存预热、活动资源隔离、压测演练和扩容；不可预测流量如热点事件、爬虫、防刷攻击，需要入口保护、动态限流和快速降级。入口层通过 CDN、静态化、WAF、黑白名单、令牌桶、漏桶、滑动窗口和人机校验先挡住无效或超出承诺的请求，避免流量直接进入核心服务。应用层要将核心链路和非核心链路隔离，核心链路保留线程池、连接池和数据库配额，非核心功能如推荐、统计、弹窗、个性化排序可以降级或关闭。读流量用多级缓存和热点副本承接，写流量用队列、批量处理、合并写和异步化削峰，但队列必须有最大积压、过期策略和消费者扩容策略，不能变成无限缓冲。对于需要公平性的场景，可以使用排队页、资格令牌、预约、分批放量和库存令牌，把瞬时竞争转成可控处理。弹性扩容要考虑启动时间、镜像拉取、预热、注册发现和连接建立，不能假设机器一创建就具备完整承载能力。突发期间还要限制客户端和服务端重试，使用退避、抖动和重试预算，避免失败请求被重复放大。流量恢复后要有排水策略，逐步恢复降级功能并处理积压任务，防止峰值结束后的补偿流量再次冲击数据库。对于核心交易场景，还要提前约定可拒绝比例和排队时长，保证系统保护策略符合业务承诺，并将这些阈值写入监控。异常路径要定义清楚：超过限流返回明确错误或排队状态，下游超时快速失败，缓存不可用时限制回源，数据库压力过高时进入只读或保护模式，队列积压超过阈值时暂停低优先级生产。验证突发流量能力要做突刺压测，而不只是平稳压测，观察系统在流量陡增、缓存失效、消费者宕机、下游超时后的拒绝率、P99、核心成功率、恢复时间和数据一致性。

  • 原理解析：

    • 突发流量的危险在于到达率瞬间超过系统服务率，排队时间没有线性增加，而是迅速吞掉线程、连接和内存。限流、排队、缓存和异步化分别从入口、等待、读路径和写路径控制到达率。系统保护的目标不是让所有请求都成功，而是让核心请求在资源边界内成功，让超额请求被明确拒绝或延迟处理。
    • CDN、静态化和多级缓存能承接突发读流量，是因为它们把重复读取从源站转移到更近、更轻的节点；代价是一致性变弱、刷新延迟和缓存失效时的回源冲击。热点副本和预热解决的是“峰值刚来时缓存为空”的冷启动问题，否则第一波请求会同时穿透到数据库。
    • 队列和异步削峰的原理是把时间维度拉长：生产者的瞬时高峰进入有界缓冲，消费者按稳定服务率处理。它能扩展的前提是业务允许最终一致或处理中状态；代价是 lag、重放、幂等、过期和补偿。无界队列不是扩展能力，只是把失败从入口推迟到磁盘、恢复时间和用户等待。
    • 失败边界要把“拒绝”设计成正常路径：令牌桶控制平均速率和短时突发，漏桶输出平滑流量，熔断阻断慢依赖，降级释放非核心资源，重试预算防止失败放大。记忆抓手是“挡、缓、削、降、排”：入口挡无效流量，缓存缓读，队列削写，非核心降级，峰后排水。突发流量结束后仍要限制补偿、重试和异步消费速度，因为尾部积压也可能再次压垮数据库。
    • 方案能扩展的前提是核心链路和非核心链路资源隔离。推荐、统计、排行榜和弹窗如果共享线程池、连接池或数据库配额，即使被逻辑降级，也可能在高峰时抢占核心交易资源；隔离让降级真正释放容量。

  • [ ] ★★★ 什么是背压？为什么高并发系统需要背压？

  • 完整回答：
    • 背压是下游处理能力不足时，通过明确的信号让上游降低发送速度、排队、拒绝、降级或切换路径的一种流量控制机制。它解决的问题不是让下游变快，而是防止请求无限进入系统后占满内存、线程、连接、磁盘和重试队列，最终把一个局部慢点扩散成全站故障。高并发系统中每一层都可能成为下游：网关相对客户端是下游，应用相对网关是下游，数据库相对应用是下游，消费者相对消息队列也是下游。没有背压时，上游会继续按照峰值速度写入，请求在中间层无界排队，用户等待时间越来越长，超时后又触发重试，形成放大流量。常见实现包括有界队列、线程池拒绝策略、连接池上限、令牌桶限流、消费者按能力拉取、MQ lag 控制、Reactive Streams 的 request 模型、HTTP 429/503 和 Retry-After。背压必须和超时、熔断、降级配合：队列满了要快速失败或返回排队状态，不能静默堆积；下游 P99 超过阈值要降低并发或摘除实例；重试必须有退避、抖动和次数上限。背压策略还要区分优先级，核心请求可以保留配额，低优先级批任务、报表和通知应先被限速。实现时要避免把背压信号吞掉，例如异步框架、网关或 SDK 自动重试如果不尊重拒绝结果，就会破坏限流效果。背压阈值应基于下游延迟、错误率、队列等待时间和资源水位动态调整，而不是只用固定 QPS。用户侧返回也要可解释，明确是限流、排队还是稍后重试，否则客户端会盲目刷新并制造额外压力。数据一致性边界也要明确，已经进入队列的消息要保证最终处理或进入死信，未进入队列的请求可以明确失败。验证背压有效性要在压测中故意降低消费者速度或拖慢数据库，观察入口拒绝率是否上升、系统内存是否稳定、队列是否受控、核心请求是否仍可用，以及压力解除后是否能按预期恢复。

  • 原理解析：

    • 背压来自生产者-消费者模型：上游生产速率大于下游消费速率时，中间缓冲会持续增长。缓冲有限时会排队、丢弃或拒绝；缓冲无限时看似没有失败，实际把资源耗尽推迟到内存、磁盘或连接池层面。背压就是让下游服务率反向约束上游到达率，使系统重新回到稳定区间。
    • 在同步链路中，背压表现为线程池拒绝、连接池上限、HTTP 429/503、超时和熔断；在异步链路中，表现为消费者主动拉取、暂停分区、限制生产、按 lag 调速。它和限流的关系是：限流多按入口策略控制流量，背压按下游实际处理能力反馈；它和熔断的关系是：熔断是在依赖异常时快速切断，背压是在依赖变慢或队列增长时提前减速。
    • 背压能扩展系统稳定性，但不会增加总处理能力。它的收益是防止慢点扩散，保住核心资源；代价是部分请求被延迟或拒绝，用户体验必须通过排队状态、重试时间和降级结果解释清楚。如果 SDK 自动重试、网关吞掉 429、消息队列无限堆积，背压信号就会断裂，上游仍会制造放大流量。
    • 失败边界是“积压是否有界”。有界队列满了返回失败是可控故障，无界堆积导致 OOM、磁盘满和恢复时间不可预测是不可控故障。记忆抓手是“下游喊慢，上游收手”：任何一层变慢，都要把信号传回上一层，并配合超时、退避、优先级和幂等来避免重试风暴。背压是否有效，要看压力解除后系统能否按有限时间恢复，而不是只看峰值时没有立刻崩溃。
    • 背压阈值要接近真实饱和信号，而不是单纯固定 QPS。下游延迟升高、错误率上升、队列等待变长、连接池可用数下降，都说明服务率正在变小；用这些指标联动调速，才能在雪崩前把请求挡住。

  • [ ] ★★★ 如何设计秒杀系统？

  • 完整回答：
    • 秒杀系统的核心目标是在极高瞬时流量下保证库存不超卖、用户不重复下单、核心链路低延迟，并把失败控制为明确的“未抢到”或“排队中”。需求指标要先量化商品数、预约人数、峰值 QPS、下单成功上限、支付时限、活动持续时间、防刷强度、是否允许排队和最终一致延迟。架构上应把活动页、商品详情和规则说明静态化，通过 CDN 承接读流量；活动开始前预热商品、库存、用户资格和风控规则；入口层使用动态链接、验证码、人机校验、设备指纹、IP/账号限频和令牌发放过滤无效流量；核心扣减链路尽量短，只做资格校验、幂等校验、库存原子扣减和下单消息投递。库存可以预加载到 Redis，通过 Lua 脚本完成“校验库存、校验用户、扣减库存、记录用户”原子操作，也可以用数据库条件更新或单分区串行队列；无论哪种方案，都要有订单落库、支付回调、取消超时、库存回补和最终对账。订单创建通常异步化，扣减成功后写入 MQ，消费者创建待支付订单，用户看到“抢购成功，待支付”或“处理中”；支付超时后释放库存或回补资格，重复消息和重复回调通过订单号、用户商品唯一键和幂等表处理。热点风险包括 Redis 单 key 热点、库存分段不均、MQ 分区倾斜、数据库唯一键冲突、缓存雪崩、支付通道限额和风控误杀。活动结束和售罄后要及时关闭入口、清理令牌并冻结库存快照，避免尾部补偿和迟到请求继续改变结果。降级路径包括关闭非核心查询、暂停实时排行榜、限制订单查询频率、只保留下单核心接口、库存售罄后直接短路返回。验证时要模拟活动开始瞬间突刺、防刷流量、Redis 故障、MQ 堆积、订单消费者重启、支付回调乱序和补偿任务，最终以库存不为负、成功订单数不超过库存、重复下单被拦截、P99 和恢复时间达标作为通过标准。

  • 原理解析：

    • 秒杀的核心矛盾是“极高到达率竞争极少成功名额”。大部分请求天然会失败，所以系统设计要把失败尽早、尽轻地返回，而不是让所有人都进入数据库排队。活动页静态化和 CDN 承接读流量，资格令牌和风控过滤无效请求，售罄标记短路尾部请求，本质上都是把核心扣减服务台前的到达率降到接近库存规模。
    • 库存扣减必须是原子操作，因为“查库存”和“减库存”分开会在并发间隙产生超卖。Redis Lua、数据库条件更新或同商品单队列串行化都能把判断和扣减合成一个不可交错的步骤。如果 Redis 是扣减事实源，Lua 原子步骤不能只减库存，还要同时记录 reservation 或 order token，再由可靠 relay 投递 MQ；如果数据库是事实源，则用条件更新和 outbox 同事务提交。发送失败必须能重试、查询和回补，不能只做扣减后直接发 MQ。
    • 秒杀链路能扩展，是因为把读、校验、扣减、建单、支付拆成不同压力面：读走 CDN 和缓存，入口用令牌限流，扣减只处理少量有效请求，订单落库异步消费，支付回调独立幂等处理。代价是用户可能看到“处理中”，订单状态要有待支付、已支付、已取消、已回补等状态机，不能再用一次同步请求解释全部结果。
    • 失败边界集中在热点和补偿：单个 Redis key、单个 MQ 分区、数据库唯一键、支付通道和风控都会成为窄口；relay 停摆、消费者失败或回调乱序会导致少卖、重复建单或库存回补错误。记忆抓手是“读静态、入限流、扣原子、留凭证、后对账”：先挡流量，再保证扣减事实源和待投递凭证同时成立，再靠状态机和对账兜底。秒杀方案的扩展能力来自让只有接近库存数量的请求进入强一致区，而不是让所有请求争同一把锁。
    • 防刷和公平机制本质上也是容量治理。验证码、设备指纹、预约和资格令牌把机器流量、重复点击和无资格用户过滤在外，同时让成功名额按业务规则分配；代价是误杀、排队体验和风控规则维护成本，需要灰度和回滚。

  • [ ] ★★★ 如何防止库存超卖？

  • 完整回答：
    • 防止库存超卖的本质是让“判断库存充足”和“扣减库存”成为同一个并发安全的原子操作，并且让重复请求、失败重试和异步补偿不会重复扣减。数据库方案通常使用条件更新：update sku set stock = stock - 1 where id = ? and stock > 0，依赖行锁保证同一行扣减串行化，应用根据影响行数判断成功或售罄；也可以使用乐观锁版本号，但高冲突下大量失败重试会放大压力。悲观锁能保证强一致，但在秒杀热点商品上容易造成锁等待和连接耗尽。Redis 方案常用 Lua 脚本原子执行库存判断、扣减和用户购买记录，性能高但一致性边界变成 Redis 与数据库的最终一致，需要持久化、消息可靠投递、失败恢复和对账。队列串行化方案把同一商品的扣减请求发送到同一分区，由单消费者顺序处理，逻辑简单但吞吐受分区和消费者限制。分段库存可以把一个商品库存拆成多个桶降低单点热点，但要处理分配不均、尾部库存合并和对账复杂度。防超卖还必须处理防重：同一用户同一商品建立唯一约束或幂等键，请求重试返回同一结果；支付超时、订单取消和风控拦截要走可审计的库存回补流程，不能随意加回库存导致重复释放；消息重复消费通过业务唯一键和状态机保证幂等。库存状态还要区分已占用、待支付、已支付、已取消和已释放，否则只看一个剩余数字很难解释异常。工程上还要防止缓存库存和数据库库存双写乱序，通常以一方作为扣减事实源，另一方通过事件或对账修正。验证方法包括并发扣减压测、故障注入、重复请求、消费者重启、数据库写失败、Redis 主从切换和支付取消回补测试，最终对账商品初始库存、成功订单、待支付订单、取消订单、剩余库存和补偿流水，保证不超卖且少卖在可解释范围内。

  • 原理解析：

    • 超卖产生于并发读写的竞态：多个请求同时看到库存大于 0，然后分别扣减。解决原理是把库存条件判断和扣减放进同一个临界区，使并发请求只能串行通过。数据库条件更新依靠行锁和影响行数，Redis Lua 依靠单线程脚本原子性，分区队列依靠同商品请求有序消费，它们的共同点都是消除“先查后改”的时间窗口。
    • 强一致和吞吐之间有明确代价。数据库行锁事实源清晰，但热点商品会让锁等待和连接数成为瓶颈；Redis 预扣库存吞吐高，但数据库订单落库失败、消息丢失、主从切换都可能造成缓存库存和真实订单不一致；分段库存降低热点，但会出现某些桶耗尽、某些桶剩余的少卖和尾部合并问题。
    • 幂等是防超卖的另一半。库存扣减只防“库存不为负”，不能防同一用户重试重复成功；用户商品唯一键、订单号、幂等表和状态机把重复请求折叠成同一个结果。支付超时和订单取消必须通过可审计流水回补，因为库存从待支付释放到可售，本质上又是一次并发状态变更。
    • 失败边界是事实源选择。一旦决定 Redis 是扣减事实源，数据库就要通过消息和对账追平；如果数据库是事实源，缓存只能做展示或限流参考，不能反向覆盖库存。记忆抓手是“判断扣减一起做，重复请求同结果，释放库存走流水，对账解释少卖”：防超卖优先于卖满库存。少卖通常可以通过补偿或二次释放解释，超卖会直接破坏履约承诺，所以一致性策略要先保证库存下界。
    • 分段库存和队列串行化都是把热点锁拆开或排队。它们能提高吞吐，但会牺牲部分实时性和全局最优分配；尾部库存要合并，对账要能证明初始库存等于成功占用、已释放、剩余和异常冻结的总和。

  • [ ] ★★★ 如何设计短链接系统？

  • 完整回答：
    • 短链接系统把长 URL 映射为较短的 code，用户访问短码时快速返回 301 或 302 跳转。需求要明确写入 QPS、跳转 QPS、短码长度、域名数量、自定义短码、过期时间、访问统计、防滥用、隐私和可用性目标。短码生成常见方案是全局递增 ID 加 Base62 编码，优点是无冲突、短码短、易扩展；ID 可来自数据库自增、号段发号器或 Snowflake。随机码方案需要冲突检测，适合避免枚举但在码空间接近饱和时冲突成本上升。存储模型至少包含短码、长 URL、租户或创建者、状态、过期时间、创建时间、更新时间、风控状态和可选统计配置，短码字段必须唯一索引，长 URL 可以按归一化哈希辅助去重。读链路是系统瓶颈，流程应为网关接收短码、本地缓存或 Redis 查询映射、未命中查数据库、校验状态和过期时间、返回跳转；热门短链可本地缓存，普通短链用 Redis，数据库兜底。统计不应阻塞跳转，可以异步写日志或消息队列，再聚合 PV、UV、地区、设备和来源。301 可让浏览器长期缓存，适合永久链接但不利于变更统计；302 更灵活，常用于营销和统计场景。分库分表通常按短码哈希或 ID 范围切分，避免所有跳转查询集中到单库；短码生成服务要支持号段缓存和故障切换，防止写入入口成为单点。短码长度要按码空间和增长年限估算，Base62 的 6 位约有 568 亿组合，但还要扣除保留词、自定义码和风控封禁。异常与降级包括短码不存在返回 404，过期或封禁返回安全提示，Redis 故障时限制回源并保护数据库，数据库故障时对已缓存链接继续跳转。安全边界包括防止短码枚举、恶意 URL、钓鱼、开放重定向、批量创建和隐私泄露。验证方法包括短码唯一性测试、跳转 P99 压测、缓存穿透测试、热点短链压测、统计异步延迟测试和恶意 URL 拦截测试。

  • 原理解析：

    • 短链接的核心数据流是“code 到 URL 的高频读映射”。写入生成短码并持久化，读取按短码查映射后返回跳转。系统瓶颈通常在读链路，因为一个热门短链会被海量访问；所以本地缓存、Redis 和数据库形成分层服务台，命中越靠前，单次服务时间越短，对后端连接和 I/O 的占用越少。
    • 短码生成的原理是把大 ID 空间压缩到更短字符空间。递增 ID 加 Base62 无冲突、易估算容量，适合高写入；号段发号器把数据库自增压力转成批量取号，提升扩展性。随机码更难枚举，但必须做唯一索引冲突检测；当码空间使用率上升，生日悖论式冲突概率会提高，写入成本会变得不可控。
    • 分库分表按短码哈希或 ID 范围扩展，是把映射表的索引、连接和存储压力分摊到多个节点。代价是跨分片去重、自定义短码唯一性、迁移和路由复杂度增加。统计异步化能保证跳转低延迟，因为跳转只需查映射和返回响应，PV/UV 聚合进入日志或队列；代价是统计存在延迟和重复消费，需要幂等聚合。
    • 失败边界包括缓存穿透、热门短码、恶意 URL 和跳转语义。301 会让浏览器缓存结果，降低服务压力但不利于修改和精确统计；302 每次回源更灵活但压力更大。记忆抓手是“写唯一，读缓存，统异步，码估算，恶意拦截”：短链接看似简单，本质是高 QPS KV 查询加安全风控。缓存失效时要限制回源并保护数据库，否则大量不存在短码或热门短码过期会把读扩展层瞬间打穿。
    • 安全边界不能后置。短链隐藏真实 URL，天然容易被用于钓鱼、跳转欺骗和批量探测；创建时审核、访问时封禁校验、异常访问限频，会增加一次判断开销，但能避免系统成为恶意流量放大器和风险入口。

  • [ ] ★★★ 如何设计一个支持大文件上传的系统？

  • 完整回答：
    • 大文件上传系统要避免单请求上传失败后整体重传，因此通常采用分片上传、断点续传、并发上传、完整性校验和对象存储直传。需求指标包括单文件最大大小、并发上传用户数、总带宽、分片大小、上传成功率、断点保留时间、权限模型、病毒扫描、秒传、跨端续传和存储生命周期。推荐流程是客户端先向业务服务发起初始化，提交文件名、大小、内容哈希、分片数量和业务归属；服务端校验权限、创建上传任务，返回 uploadId 和对象存储临时凭证；客户端按固定大小分片并发上传到对象存储或上传网关，每片带序号、大小、校验值和凭证；上传过程中服务端记录已完成分片或通过对象存储查询分片列表；客户端断线后可查询进度继续上传；所有分片完成后发起合并，服务端校验分片数量、大小、ETag 或 SHA-256，再提交对象存储合并并生成文件记录。秒传可以用文件哈希判断已有对象，但必须校验用户是否有权限复用该文件，不能因哈希命中泄露他人文件存在性。数据流上业务服务不应承接大文件流量，主要负责签名、元数据、权限、回调和状态机，对象存储承担实际带宽和持久化。分片大小需要折中，太小会放大请求数和元数据压力，太大则弱网失败重传成本高，通常结合移动端网络、浏览器并发限制和对象存储接口限制确定。元数据表要记录任务状态、分片清单、所有者、过期时间和最终对象地址，合并接口必须幂等，避免重复生成文件记录。异常路径包括重复分片、乱序上传、分片损坏、合并超时、客户端重复完成、凭证过期、存储回调丢失和临时分片垃圾，均需幂等处理和定期清理。安全上要限制文件类型、大小、上传频率、临时凭证作用域和有效期，必要时合并后进入异步扫描，扫描通过前不对外提供下载。验证要覆盖弱网断点续传、并发分片、重复提交、超大文件、对象存储失败、任务过期清理、哈希校验失败和带宽压测。

  • 原理解析：

    • 大文件上传的核心瓶颈是带宽、连接占用和失败重传成本。单请求上传把整个文件绑定到一次长连接，任何网络抖动都要从头再来；分片上传把大任务拆成多个可重试的小任务，失败只重传某个分片。断点续传的原理是服务端或对象存储保存已完成分片集合，客户端重新查询后只补缺口。
    • 对象存储直传能扩展，是因为业务服务退出大流量数据面，只保留控制面：签名、权限、元数据和状态机。真正的文件字节流走对象存储的带宽和多副本能力，应用服务器不再被长连接和网卡吞吐拖垮。代价是临时凭证范围、回调可信度、分片清理和最终文件记录的一致性都要单独设计。
    • 分片大小体现排队和开销折中。分片太小，请求数、签名校验、元数据记录和合并清单急剧增加；分片太大，弱网失败后的重传时间长，用户体验差。并发上传能提高单用户吞吐，但会占用更多连接和带宽，所以必须有客户端并发上限、服务端限速和任务级配额。
    • 失败边界包括重复分片、乱序到达、合并重试、哈希冲突、凭证过期和扫描异步延迟。合并接口必须幂等，否则客户端重复点击完成会生成多条文件记录。记忆抓手是“控制面管权限，数据面走存储，分片降重传，哈希验完整，状态机管异常”：扩展能力来自把大流量从应用层移走。真正的容量指标应看总上传带宽、并发连接、临时分片数量和合并耗时，而不是只看初始化接口 QPS。
    • 秒传和断点续传都依赖元数据可信。文件哈希只能说明内容相同，不能说明用户有权复用；已上传分片清单只能说明对象存在，不能说明合并一定完成。权限、任务状态和对象校验必须共同决定最终可见性。

  • [ ] ★★ 为什么异步化可以提高吞吐量？它的边界是什么？

  • 完整回答：
    • 异步化能提高吞吐量，是因为请求线程不用一直等待慢操作完成，可以更快释放 Web 线程、数据库连接和下游连接，把同步链路中的长等待变成后台处理。消息队列还能把瞬时高峰平滑成消费者可承受的稳定流量，生产者在完成必要校验和消息持久化后即可返回“已受理”或“处理中”。适合异步化的场景包括短信、邮件、日志、埋点、积分、通知、搜索索引更新、报表生成和非核心状态同步，这些任务通常允许秒级或分钟级延迟，并能通过补偿保证最终完成。边界在于异步化不会减少总工作量，消费者能力不足时只是把压力转移到队列，最终表现为 lag 增长、端到端延迟变长和磁盘占用上升。对于用户必须立即得到确定结果的强一致步骤，例如支付扣款确认、库存原子扣减、权限变更生效，不能简单异步后直接返回成功，只能返回处理中或保留同步确认。异步系统必须处理消息丢失、重复消费、乱序、延迟、死信、补偿和幂等，业务状态机也要支持中间态。队列容量、消息保留时间和消费者扩容速度都要有上限设计，否则高峰后恢复时间可能超过业务可接受窗口。验证时不仅看接口 QPS 是否提升，还要看消息持久化成功率、消费速率、lag、死信率、端到端完成时间和故障恢复后的重放能力，同时保留状态查询入口。

  • 原理解析：

    • 异步化提高入口吞吐，是因为把请求停留时间缩短了。按 Little 定律，并发数约等于吞吐量乘以响应时间；如果同步链路里有短信、索引、通知等慢步骤，请求线程会一直等待。改成写入可靠消息后返回，Web 线程和连接更快释放，同样数量的实例就能承接更多入口请求。
    • 队列削峰的原理是时间搬移：生产者把瞬时高峰写入有界缓冲，消费者按稳定能力处理。它没有减少总工作量，只是把“现在必须完成”改成“稍后完成”。因此真正要看端到端完成时间、lag 和死信，而不能只看接口返回变快。
    • 边界是业务语义。强一致结果不能被异步假装成功，最多返回“处理中”；已经返回成功的动作必须保证消息可靠、消费幂等、失败补偿。记忆抓手是“释放等待，不减工作；削峰填谷，接受延迟”。队列满、消费者慢、消息重复和乱序，就是异步系统最常见的失败边界。判断是否适合异步，要看用户是否能接受中间态、业务是否能重试补偿、状态查询是否能解释最终结果。
    • 扩展消费者也有代价：并行度提高可能打乱顺序、增加数据库写压力或触发下游限额。按 key 分区能保序但会遇到热点分区；批量消费能提升吞吐但会增加单批失败回滚成本，所以异步链路仍要按瓶颈限速。

  • [ ] ★★ 多级缓存应该如何设计？

  • 完整回答：
    • 多级缓存通过把数据放在更靠近用户或应用的位置来降低延迟和后端压力，常见层次包括浏览器缓存、App 缓存、CDN、网关缓存、应用本地缓存、Redis 或 Memcached、数据库缓冲池。设计时要先划分数据类型：静态资源适合长期 CDN 缓存并通过版本号更新；商品详情、配置、排行榜等读多写少数据适合 Redis 和本地缓存；强一致账户余额、订单状态只能使用短 TTL 或读主库兜底。常见策略是 Cache Aside，即应用先读缓存，未命中查数据库并回填，更新时先写数据库再删除或失效缓存；写穿和写回适合特定场景，但要承担写延迟或丢失风险。越靠前的缓存性能越高，一致性越弱；越靠近数据库的缓存越可控，但承压更集中。因此每类数据要定义最大可接受过期时间、主动失效机制、版本号或逻辑过期策略。本地缓存要控制容量和过期时间，避免多实例之间长期不一致；CDN 缓存要配合 URL 版本、刷新和回源保护。异常路径包括缓存穿透、击穿、雪崩、热 key、本地缓存不一致和大 key 拖慢网络，需要使用空值缓存、布隆过滤器、互斥重建、随机 TTL、热点副本、请求合并和限流保护。验证缓存设计要看命中率、回源 QPS、热 key 分布、缓存重建耗时、数据库压力和更新后可见延迟，不能只看平均响应时间。

  • 原理解析：

    • 多级缓存的原理是把读请求挡在离用户更近、服务时间更短的层。浏览器和 CDN 减少跨网请求，本地缓存减少网络调用，Redis 减少数据库 I/O。命中率每提升一点，都会沿链路减少后端到达率；反过来，缓存失效会把请求集中回源，形成击穿或雪崩。
    • 缓存层级越靠前，性能越好但一致性越弱；越靠近数据库，一致性越可控但容量更集中。Cache Aside 的因果链是读未命中查库回填，写先落库再失效缓存；它把数据库作为事实源，把缓存作为加速层。TTL、版本号和主动失效决定了数据最多旧多久。
    • 失败边界是“不命中时后端是否扛得住”。穿透用空值和布隆过滤器，击穿用互斥重建和逻辑过期，雪崩用随机 TTL 和分批预热，热 key 用副本和本地缓存。记忆抓手是“越近越快越旧，越后越准越重”：缓存设计永远是在延迟、容量和一致性之间取舍。更新策略要按数据重要性分级，静态资源可长期缓存，价格库存要短 TTL 或主动失效，余额权限则通常读事实源。
    • 本地缓存和 CDN 还会放大版本管理问题。多实例本地缓存不能靠单机删除保证全局生效，CDN 节点刷新也有传播时间；所以变更频繁的数据更适合短 TTL、逻辑版本或读主兜底，而不是层层长缓存。

  • [ ] ★★ 热点数据和热点用户如何处理？

  • 完整回答：
    • 热点数据是大量请求集中访问少数 key、记录、页面或分区，热点用户是单个用户、设备、IP 或租户产生远高于正常水平的流量。处理第一步是识别，依据访问日志、网关指标、Redis hot key、数据库慢查询、分片负载、租户 QPS 和错误率找到具体热点对象。热点读可以通过本地缓存、Redis 多副本、CDN、逻辑过期、请求合并和预热来分散压力；对特别热的 key，可以拆成多个副本 key 或在应用内短时间缓存，减少集中访问 Redis 单节点。热点写更难，因为写入通常不能简单复制，常见办法是分段计数、批量聚合、队列串行化、按业务维度拆分记录或降低实时性，例如点赞数先写入多个桶再异步汇总。热点用户要通过限频、配额、风控评分、隔离线程池、租户级资源池和黑名单处理，避免异常用户占满公共资源。处理热点时要保留一致性边界，例如计数类可以最终一致，库存、余额和权限不能为了分散热点而放弃原子约束。异常与降级包括热点 key 过期导致击穿、分片倾斜、单行锁等待和大客户流量突增，需要设置自动发现、动态缓存、限流阈值和告警。验证时要构造少数 key 承担大部分流量的压测模型，观察单节点 CPU、网络、P99、数据库锁等待、限流命中和正常用户成功率。

  • 原理解析：

    • 热点问题违反了“请求均匀分布”的扩容假设。即使总 QPS 不高，少数 key、行、分片或租户也可能先打满单节点 CPU、网络、锁或连接。热点识别要按对象维度看指标，因为整体平均值会把局部拥塞隐藏掉。
    • 热点读可以复制，因为读结果通常可共享：CDN、本地缓存、Redis 副本、请求合并和逻辑过期都在减少同一数据源的重复访问。热点写不能简单复制，因为多个副本会产生冲突，所以常用分桶、批量聚合、队列串行化或降低实时性，把单点写压力改造成多个桶或时间窗口。
    • 热点用户处理的是资源公平性。限频、租户配额、隔离线程池和风控评分把异常流量关在独立资源池里，避免它占满公共服务台。失败边界是强一致对象不能随意拆散，例如余额、库存、权限仍要保留原子约束。记忆抓手是“读可复制，写要合并，用户要隔离，热点先识别”。治理是否有效，要看热点被限制后正常用户的成功率和 P99 是否恢复，而不是只看热点本身有没有被完全消除。
    • 热点治理常常是动态的。活动页、热门商品和大客户流量会突然出现，靠静态分片规则不够；需要热 key 发现、临时副本、动态限流和自动预热，把热点从事故现场变成可观测、可回收的运行状态。

  • [ ] ★★ 什么是读写分离？它可能导致什么问题？

  • 完整回答：
    • 读写分离是将写请求路由到主库，将普通读请求路由到一个或多个从库，用副本扩展读能力并降低主库压力。它适合读多写少、读一致性要求不高或可按场景区分强弱一致的系统，例如商品浏览、内容列表和报表查询。核心机制是主库提交事务后通过 binlog、WAL 或复制协议同步到从库，路由层根据 SQL 类型、业务标签或会话状态选择主库或从库。主要问题是复制延迟，用户刚写完订单、资料或状态后立即读从库，可能读到旧数据，影响读己之写、分页、状态判断和幂等校验。解决方式包括关键读强制读主、写后短时间内同一用户读主、按复制位点等待、从库延迟超过阈值摘除、对低一致性查询明确使用从库。另一个问题是故障切换复杂，主从角色变化后连接池和路由规则要及时刷新，旧主恢复后不能产生双写；如果采用异步复制，主库宕机时还可能存在数据丢失窗口。从库还可能因报表慢查询被拖慢，因此只读分析流量最好使用独立副本或数仓，不应和在线查询混用。读写分离也不能解决写瓶颈，写压力过高仍需要分库分表、批量写、异步化或业务拆分。验证读写分离要压测读扩展能力，同时模拟主从延迟、从库宕机、主库切换和写后立即读，确认路由、降级和一致性边界符合业务要求，且路由决策可观测。

  • 原理解析：

    • 读写分离的扩展原理是复制读副本。写入仍进入主库，主库把变更日志传给从库；普通读被路由到多个从库后，读服务率近似随副本数增加。它适合读多写少，因为写路径没有被拆开，主库提交、锁和日志仍是写瓶颈。
    • 复制延迟是核心代价。数据流是“主库提交成功 -> 日志传输 -> 从库重放 -> 从库可读”，中间任何排队都会让从库短暂落后。用户写后立刻读从库，就可能读不到自己的修改；分页、状态判断和幂等校验也会被旧数据干扰。
    • 高可用边界在主从切换。旧主、新主和路由层必须对角色达成一致，否则可能双写或读到回滚数据；异步复制还存在主库宕机前日志未同步的 RPO 窗口。记忆抓手是“读扩副本，写仍单主；延迟读旧，切换防双写”：读写分离提升读容量，不解决写容量和强一致问题。设计时要给每类查询打上一致性标签，不能让路由层只按 SQL 读写粗暴分流。
    • 从库也不是免费容量。慢报表会占用从库 CPU、I/O 和缓存，影响在线读；复制线程落后时继续路由读请求，会把旧数据问题扩大。延迟监控和从库摘除，是读写分离能稳定运行的关键边界，也是保护用户读一致性的必要措施，必须持续观测和告警。

  • [ ] ★★ 系统如何做到高可用？

  • 完整回答：
    • 高可用的目标是在部分组件故障、发布变更或流量波动时，核心服务仍然可用，并把影响范围、恢复时间和数据损失控制在约定范围内。设计前要明确 SLO/SLA、RTO、RPO、核心功能、可降级功能和成本约束。架构层面要消除单点：应用多实例无状态部署，负载均衡健康检查，跨可用区或多机房冗余，数据库主从或集群，缓存哨兵或集群，消息队列多副本，配置中心和注册中心高可用。运行时要有超时、重试、熔断、限流、隔离、降级和背压，防止一个慢依赖拖垮所有请求；重试必须有次数、退避和幂等保护。数据层要有备份、恢复演练、复制延迟监控和故障切换流程，明确哪些数据要求强一致，哪些可以最终一致。发布层面使用灰度、滚动、蓝绿或金丝雀发布，配合自动回滚和配置开关。高可用还包括可观测性，告警要覆盖延迟、错误率、饱和度、依赖状态和业务成功率。容量上要预留故障冗余，例如单可用区或一批实例下线后，剩余资源仍能承接核心流量。验证不能只看部署了几台机器，而要做故障演练、混沌测试、备份恢复、单可用区失效、依赖超时、缓存雪崩和流量突刺测试，确认系统能发现故障、隔离故障、切换流量并恢复数据，同时定期演练人工接管流程，检查预案是否可执行且具备可追踪性。
  • 原理解析：
    • 高可用的底层是避免单个故障让服务率跌破核心到达率。多实例、跨可用区、副本和健康检查让某个节点失效后仍有服务台可用；N+1 容量保证摘除故障实例后剩余容量仍能承载核心流量。它提升的是故障期间的可服务性，代价是资源冗余、复制延迟和切换复杂度。
    • 超时、重试、熔断、隔离、降级和背压是一套故障传播控制链。超时限制等待时间，重试处理瞬时失败但必须有预算，熔断阻止慢依赖继续占资源，隔离把故障限制在线程池或租户内，降级释放非核心功能，背压让上游减速。没有这些运行时机制，多副本也可能被重试风暴同时打垮。
    • 数据层可用性要同时看 RTO 和 RPO：RTO 是多久恢复服务，RPO 是最多丢多少数据。同步复制降低丢数据风险但增加写延迟，异步复制性能好但有丢失窗口；备份只存在不等于可恢复，必须演练恢复时间和数据完整性。记忆抓手是“冗余抗坏，限流抗挤，熔断抗慢，备份抗丢，演练抗假”：高可用是工程闭环，不是架构图上的多节点。没有告警、预案和演练的冗余，只能说明资源存在，不能证明故障时会按预期接管。
    • 发布也是高可用风险源。灰度、金丝雀、蓝绿和配置开关的作用，是把错误版本的影响面限制在小流量内，并保留快速回滚路径。系统能否高可用，要看故障发现、隔离、切流和恢复是否形成闭环。
