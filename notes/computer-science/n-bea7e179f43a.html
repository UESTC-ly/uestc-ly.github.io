学习目标

学习本章后，你应该能够：

  • 理解 Redis key 的通用规则、过期机制和基础管理命令。
  • 掌握 String、Hash、List、Set、Sorted Set 五种核心数据类型的典型用法。
  • 了解 Bitmap、HyperLogLog、Geospatial、Stream 的适用场景。
  • 能根据业务问题选择合适的数据结构，而不是把所有内容都塞进 String。
  • 能识别常见命令误用：大 key、阻塞命令、无界集合、错误的过期策略。

核心概念

Redis 的 key 设计

Redis 中每条数据都以 key 作为入口。一个好 key 应该具备：

  • 可读：能看出业务含义。
  • 规范：统一分隔符和命名层级。
  • 有界：避免单个 key 对应无限增长的数据。
  • 可治理：便于统计、清理、迁移和排查。

常见命名方式：

业务:实体:标识:属性
user:1001:profile
user:1001:session
article:2026:rank:daily
order:lock:8899

建议：

  • 使用 : 分隔层级。
  • 避免过长 key，key 本身也占内存。
  • 避免包含空格、换行和不可见字符。
  • 缓存型 key 默认设置 TTL。
  • 不同环境或应用可以增加前缀，例如 prod:shop:user:1001。

value 的数据类型

Redis 的“类型”是 value 的类型，而不是 key 的类型。

TYPE user:1001:profile

常见类型：

类型 适合场景 典型命令
String 缓存、计数器、分布式锁、简单状态 GET、SET、INCR
Hash 对象字段、用户资料、配置项 HSET、HGET、HGETALL
List 队列、时间线、最近记录 LPUSH、RPOP、BLPOP
Set 去重集合、标签、共同关注 SADD、SISMEMBER、SINTER
Sorted Set 排行榜、延迟队列、按分值检索 ZADD、ZRANGE、ZREVRANGE
Bitmap 用户签到、布尔状态集合 SETBIT、GETBIT、BITCOUNT
HyperLogLog 大规模基数估算 PFADD、PFCOUNT
Geo 地理位置半径查询 GEOADD、GEOSEARCH
Stream 消息流、消费组、事件日志 XADD、XREADGROUP

通用 key 命令

EXISTS key
DEL key
UNLINK key
TYPE key
EXPIRE key seconds
PEXPIRE key milliseconds
TTL key
PTTL key
PERSIST key
RENAME old new
SCAN cursor MATCH pattern COUNT count

要点：

  • DEL 同步删除，删除大 key 时可能阻塞；UNLINK 会异步释放内存，更适合删除大 value。
  • TTL = -1 表示 key 存在但没有过期时间。
  • TTL = -2 表示 key 不存在。
  • SCAN 是渐进式遍历，不保证一次返回所有 key，也可能在迭代期间受数据变化影响。
  • 生产环境避免使用 KEYS *、FLUSHDB、FLUSHALL 等高风险命令。

关键命令/配置

1. String

String 是 Redis 最基础的类型，value 可以是文本、数字、JSON、二进制内容，但最大 value 不应无限增大。

常用命令：

SET key value
GET key
MSET key1 value1 key2 value2
MGET key1 key2
SET key value EX seconds
SET key value PX milliseconds
SET key value NX
SET key value XX
GETSET key value
INCR key
INCRBY key increment
DECR key
APPEND key value
STRLEN key

示例：缓存文章摘要。

SET article:1001:summary "Redis data types" EX 600
GET article:1001:summary

示例：计数器。

INCR page:home:pv
INCRBY page:home:pv 10
GET page:home:pv

示例：基础分布式锁写法。

SET lock:order:8899 "request-uuid-001" NX EX 30

释放锁时不要简单 DEL lock:order:8899，应先校验 value 是否为自己的 token，再原子删除。常见做法是使用 Lua 脚本或 Redis Functions。

2. Hash

Hash 适合存储对象的多个字段，例如用户资料、商品属性、配置项。

常用命令：

HSET key field value [field value ...]
HGET key field
HMGET key field [field ...]
HGETALL key
HDEL key field [field ...]
HEXISTS key field
HINCRBY key field increment
HLEN key
HSCAN key cursor MATCH pattern COUNT count

示例：用户资料。

HSET user:1001 name "Ada" age 28 city "Shanghai"
HGET user:1001 name
HMGET user:1001 name city
HINCRBY user:1001 login_count 1
HGETALL user:1001

使用建议：

  • 字段较多但经常整体读取时，Hash 很自然。
  • 如果每个字段需要不同 TTL，Hash 不适合直接表达，因为 TTL 作用在整个 key 上。
  • HGETALL 对大 Hash 可能很重，生产排查优先 HSCAN。

3. List

List 是按插入顺序排列的字符串列表，底层实现适合两端 push/pop。

常用命令：

LPUSH key element [element ...]
RPUSH key element [element ...]
LPOP key
RPOP key
LRANGE key start stop
LLEN key
LTRIM key start stop
BLPOP key [key ...] timeout
BRPOP key [key ...] timeout

示例：最近浏览记录。

LPUSH user:1001:recent article:9
LPUSH user:1001:recent article:8
LPUSH user:1001:recent article:7
LTRIM user:1001:recent 0 49
LRANGE user:1001:recent 0 9

示例：简单队列。

LPUSH queue:email "job-1"
BRPOP queue:email 5

使用建议：

  • List 适合简单队列，但缺少完整的确认、重试、消费组语义。
  • 更复杂的消息流优先考虑 Stream。
  • 避免超长 List 无限制增长，配合 LTRIM 或消费清理。

4. Set

Set 是无序去重集合，适合标签、去重、共同好友、权限集合等。

常用命令：

SADD key member [member ...]
SREM key member [member ...]
SISMEMBER key member
SMEMBERS key
SCARD key
SPOP key [count]
SRANDMEMBER key [count]
SINTER key [key ...]
SUNION key [key ...]
SDIFF key [key ...]
SSCAN key cursor MATCH pattern COUNT count

示例：文章标签。

SADD article:1001:tags redis cache database
SISMEMBER article:1001:tags redis
SCARD article:1001:tags
SMEMBERS article:1001:tags

示例：共同关注。

SADD user:1:follows user:2 user:3 user:4
SADD user:9:follows user:3 user:4 user:8
SINTER user:1:follows user:9:follows

使用建议：

  • 小集合可以用 SMEMBERS，大集合优先 SSCAN。
  • 集合运算很方便，但对超大集合可能造成 CPU 和内存压力。

5. Sorted Set（ZSet）

Sorted Set 是“成员 + 分数”的有序集合。成员唯一，分数可重复。

常用命令：

ZADD key score member [score member ...]
ZSCORE key member
ZINCRBY key increment member
ZRANGE key start stop [WITHSCORES]
ZREVRANGE key start stop [WITHSCORES]
ZRANGEBYSCORE key min max [WITHSCORES] [LIMIT offset count]
ZRANK key member
ZREVRANK key member
ZREM key member [member ...]
ZCARD key
ZCOUNT key min max

Redis 6.2+ 对有序集合范围命令做了统一增强，ZRANGE 支持更多参数；旧教程中的 ZRANGEBYSCORE、ZREVRANGE 仍常见，但新项目可逐步熟悉统一形式。

示例：排行榜。

ZADD rank:game:daily 100 user:1 250 user:2 180 user:3
ZINCRBY rank:game:daily 30 user:1
ZREVRANGE rank:game:daily 0 9 WITHSCORES
ZREVRANK rank:game:daily user:1

示例：延迟队列的基本思路。

ZADD delay:jobs 1716600000 job:1001
ZRANGEBYSCORE delay:jobs -inf 1716600000 LIMIT 0 10
ZREM delay:jobs job:1001

注意：延迟队列需要处理并发抢占、失败重试、幂等性，不能只靠三条命令就认为生产可用。

6. Bitmap

Bitmap 本质上是在 String 上进行 bit 位操作，适合大量布尔状态。

SETBIT sign:2026-05 userIndex 1
GETBIT sign:2026-05 userIndex
BITCOUNT sign:2026-05

示例：用户签到可以按“用户 + 月份”或“日期 + 用户索引”设计，取决于查询模式。

7. HyperLogLog

HyperLogLog 用于估算基数，例如 UV。它节省内存，但结果是近似值。

PFADD uv:2026-05-25 user:1 user:2 user:3
PFCOUNT uv:2026-05-25
PFMERGE uv:2026-05 uv:2026-05-24 uv:2026-05-25

适合：大规模去重计数，允许少量误差。

不适合：需要精确列出成员或精确计数的场景。

8. Geospatial

Geo 用于存储经纬度并做位置查询。

GEOADD city:shops 121.4737 31.2304 shop:shanghai-1
GEOADD city:shops 116.4074 39.9042 shop:beijing-1
GEOSEARCH city:shops FROMLONLAT 121.4737 31.2304 BYRADIUS 5 km WITHDIST

Redis 6.2+ 推荐使用 GEOSEARCH 替代部分旧的 GEORADIUS 用法。

9. Stream

Stream 是 Redis 的消息流结构，支持消息 ID、阻塞读取、消费组和确认。

常用命令：

XADD key * field value [field value ...]
XRANGE key start end
XREAD COUNT count BLOCK milliseconds STREAMS key id
XGROUP CREATE key group id MKSTREAM
XREADGROUP GROUP group consumer COUNT count BLOCK milliseconds STREAMS key >
XACK key group id [id ...]
XPENDING key group

示例：订单事件流。

XADD stream:orders * type created orderId 8899 userId 1001
XRANGE stream:orders - + COUNT 10

消费组：

XGROUP CREATE stream:orders group:billing 0 MKSTREAM
XREADGROUP GROUP group:billing consumer-1 COUNT 10 BLOCK 5000 STREAMS stream:orders >
XACK stream:orders group:billing 1716600000000-0

使用建议：

  • Stream 比 List 更适合需要确认、重试、多消费者协作的场景。
  • Stream 不是 Kafka 的完全替代品，持久化、吞吐、保留策略和运维模型都要单独评估。
  • 使用 XTRIM 或 MAXLEN 控制长度，避免无限增长。

示例：如何选择数据类型

场景 1：缓存用户详情

如果应用每次整体读取用户详情：

SET user:1001:profile '{"name":"Ada","age":28}' EX 600

如果应用经常单独读取或更新字段：

HSET user:1001:profile name "Ada" age 28 city "Shanghai"
EXPIRE user:1001:profile 600

选择依据：字段级操作是否重要、序列化成本是否可接受、是否需要字段级 TTL。

场景 2：记录每日热门文章榜

ZINCRBY rank:article:2026-05-25 1 article:1001
ZREVRANGE rank:article:2026-05-25 0 9 WITHSCORES
EXPIRE rank:article:2026-05-25 604800

Sorted Set 能天然表达“成员 + 分数 + 排序”。

场景 3：防止重复提交

SET dedup:submit:request-abc 1 NX EX 60

如果返回 OK，说明首次提交；如果返回空，说明 60 秒内重复。

场景 4：维护固定长度时间线

LPUSH user:1001:timeline event:5001
LTRIM user:1001:timeline 0 99
LRANGE user:1001:timeline 0 19

用 LTRIM 控制长度，避免 List 无界增长。

常见误区

误区 1：所有对象都应该存成 JSON String

JSON String 简单，但字段级修改需要整体反序列化和重写。对象字段经常独立更新时，Hash 更合适。反过来，如果对象总是整体读写，String 可能更简单。

误区 2：Hash 的每个 field 都能单独过期

Redis 的 TTL 作用在 key 上，不作用在 Hash field 上。如果需要字段级过期，通常要拆 key，或用 Sorted Set/定时清理等方案表达过期逻辑。

误区 3：LRANGE key 0 -1、SMEMBERS、HGETALL 很安全

这些命令对小数据没问题，但对大 key 可能一次返回大量数据，造成阻塞、网络尖峰和客户端内存压力。

误区 4：Sorted Set 排行榜不需要清理

排行榜如果按天、周、活动周期生成，需要设置 TTL 或定期归档。否则历史榜单会持续占用内存。

误区 5：HyperLogLog 可以拿回去重后的用户列表

HyperLogLog 只能估算基数，不能列出成员。如果需要成员列表，应使用 Set 或其他存储方案。

误区 6：SCAN 一定不会影响线上

SCAN 比 KEYS 安全，但仍然会消耗 CPU 和网络。COUNT 不是精确数量，而是遍历提示。线上排查应控制频率、范围和客户端处理速度。
