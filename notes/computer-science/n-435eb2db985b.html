本篇用于快速校正术语。每组概念都要先看“讨论维度”，因为很多误解来自把不同维度的词放在同一条轴上比较。

1. 所有权、生命周期与线程安全

概念 回答的问题 不自动保证
所有权 谁负责最终释放资源 资源当前是否可用
生命周期 对象在何时存在 多线程访问安全
shared_ptr 多方共同延长对象存活 对象字段无数据竞争
mutex 临界区互斥与同步 业务多步骤一定原子
atomic 单个原子对象的指定操作不可分割 多字段不变量和业务事务

连接对象被 shared_ptr 保活后，fd 仍可能已经逻辑关闭；回调必须检查连接状态或代数。对象“活着”与资源“仍代表原请求”是不同性质。

2. 数据竞争与竞态条件

  • 数据竞争：缺少规定同步的冲突内存访问，在 C++ 中通常导致未定义行为。
  • 竞态条件：结果依赖时序。程序可以没有数据竞争，却仍在“先检查再执行”之间被其他线程改变业务状态。

数据库“先查库存再扣减”即使每条 SQL 各自线程安全，也可能发生业务竞态；需要事务、条件更新、锁或唯一约束保护整体不变量。

3. 阻塞、非阻塞、同步、异步

维度 两端
调用在资源未就绪时是否等待 阻塞 / 非阻塞
I/O 完成由谁推进、以何种方式通知 同步 / 异步

Linux epoll Reactor 常见组合是同步非阻塞：epoll 通知“现在可能可读/可写”，应用再调用 read/write 完成操作。把非阻塞直接叫异步会混淆就绪通知与完成通知。

4. 并发与并行

  • 并发：多个任务在重叠时间内推进，是程序结构和调度问题。
  • 并行：多个任务在同一时刻使用不同执行资源运行。

单线程 event loop 能并发管理多个 I/O，但不并行执行多个 CPU 任务。增加线程可并行，却可能增加锁竞争、上下文切换和缓存失效。

5. Reactor 与 Proactor

模型 通知内容 应用后续动作
Reactor fd 就绪 应用执行非阻塞读写
Proactor I/O 已完成 应用处理完成结果

框架可能用内部线程或运行时把底层就绪接口包装成“异步 API”，讨论时要区分对应用暴露的模型和内核原语。

6. LT 与 ET

  • LT：条件仍满足就可能再次通知，容易写对。
  • ET：主要在状态边沿通知，非阻塞读写必须 drain 到 EAGAIN。

ET 不等于一定更快；它降低某些重复通知，但增加状态机约束。事件循环若一直监听可写，无论 LT/ET 都可能产生错误或空转风险。

7. TCP 半包、粘包与丢包

  • 半包/粘包：应用消息边界与 TCP 字节到达批次不一致，是字节流的正常现象。
  • 丢包：网络层报文可能丢失，TCP 在连接语义内进行重传和排序；应用仍可能因连接中断不知道业务结果。

长度字段、分隔符或固定长度解决消息 framing，不解决业务幂等、数据校验和跨连接重试。

8. FIN、RST 与半关闭

  • FIN：一方有序关闭发送方向；对端 read 在读完已到达数据后返回 0。
  • 半关闭：一方不再发送但仍可接收，协议是否允许继续响应取决于状态机。
  • RST：连接被复位，未发送/未读取数据的语义与具体时刻有关。

看到 HUP/RDHUP 时不能机械地先丢弃所有缓冲；应结合可读事件、协议和输出排空策略。

9. 超时、截止时间与取消

概念 含义
单次超时 一次 connect/read/RPC 尝试最多等多久
deadline 整个操作剩余预算的绝对或可传递边界
取消 请求停止仍在进行的工作

超时只说明调用方在时间内没获得结果，不证明服务端没执行。取消通常是协作式，也可能迟到或不被下游支持，所以写操作仍需幂等键和状态查询。

10. 限流、背压、熔断与降级

机制 主要触发 目标
限流 到达率/并发超过预算 保护本服务或租户配额
背压 下游消费跟不上 把“慢”向上游显式传播，保持队列有界
熔断 某依赖持续失败/变慢 快速失败，避免继续消耗资源
降级 完整能力不可用或成本过高 返回较弱但可接受的能力

四者可以组合，但不能互相替代。熔断器打开不会自动限制所有入口流量，限流也不会让失败依赖恢复。

11. 吞吐、并发与延迟

  • 吞吐：单位时间完成的工作量。
  • 并发：同一时间在途工作量。
  • 延迟：单项工作从开始到完成的时间。

在稳定系统中可用 Little 定律直觉 L = λW：平均在途数约等于到达率乘平均停留时间。下游变慢时，即使 QPS 不变，并发和内存也会增长；若容量有界，就表现为排队或拒绝。

12. 平均延迟与尾延迟

平均值可能被大量快速请求稀释。P99 表示 99% 样本不超过该值，并不表示“最慢 1% 的平均”。报告分位数还要说明样本量、窗口、是否包含错误和压测模型。

13. 缓存穿透、击穿与雪崩

问题 典型原因 主要影响
穿透 查询本就不存在的数据，缓存和 DB 都 miss 持续回源
击穿 单个热点 key 过期/失效 瞬时大量回源同一数据
雪崩 大量 key 同时失效或缓存整体不可用 大范围回源和级联故障

布隆过滤器、空值缓存、互斥重建、随机 TTL、预热和降级分别处理不同成因，不能用一个术语包办所有缓存故障。

14. 过期删除与内存淘汰

  • 过期：key 的 TTL 到期，语义上不应再返回；实现可惰性或主动回收。
  • 淘汰：内存达到策略阈值时，为容纳新数据而选择 key 删除；未过期 key 也可能被淘汰。

所以“都设置 TTL”不能保证不会触发淘汰，淘汰策略也不负责精确准时删除所有过期 key。

15. Redis 命令原子性、事务与 Lua

能力 保证范围 主要边界
单命令原子 单实例的一条命令执行不被其他命令穿插 不覆盖多步骤业务
MULTI/EXEC 排队命令顺序执行 不提供传统回滚，不跨外部系统
WATCH 乐观检查被观察 key 是否变化 冲突需客户端重试
Lua 单实例脚本执行期间原子 长脚本阻塞事件循环，集群 key 有 slot 约束

它们都不能自动让 Redis 与数据库、MQ 或对象存储成为一个事务。

16. 分布式锁、幂等与事务

  • 锁：减少并发进入临界区；租约过期后旧持有者可能继续执行。
  • 幂等：同一业务操作重复执行不产生额外效果。
  • 事务：在声明范围内提供原子性、隔离性等保证。
  • fencing token：让外部资源拒绝旧持有者迟到写入，前提是下游校验 token。

重试问题通常首先需要幂等，而不是首先加锁。唯一约束/条件更新能在数据最终落点裁决时，往往比仅依赖外部锁更可靠。

17. RDB 与 AOF

  • RDB：某时点数据快照，恢复加载紧凑，但两次快照间有数据窗口。
  • AOF：记录写操作并按刷盘策略持久化，恢复需重放或加载重写后的基线。

两者都要讨论 fork/COW、刷盘、rewrite、磁盘故障和恢复演练；“开启持久化”不等于零数据损失。

18. 主从、Sentinel 与 Cluster

  • 主从复制：数据副本和读扩展基础。
  • Sentinel：监控、故障判断和主从切换，不做数据分片。
  • Cluster：用 hash slot 分片并提供集群内故障转移，但多 key、客户端路由和 reshard 更复杂。

三者不是同一层面的替代词。复制异步窗口和故障切换仍可能影响最新写入。

19. Queue 与 Log

  • 传统 queue 强调一条消息由某个消费者取得并确认，路由和每消息状态较突出。
  • Kafka 类 log 强调分区内追加记录，消费者用 offset 表示位置，不同 group 可独立重放。

实际产品可能混合能力。选型应看顺序范围、重放、路由、延迟、吞吐和运维，而不是只看“都能发消息”。

20. Ack、Offset 与业务成功

生产 ack 说明 broker 在配置语义下接受消息；消费者 offset/ack 说明消费位置或交付状态推进；业务数据库提交说明副作用成功。三者位于不同系统，默认不构成一个原子事务。

业务提交后 offset 失败会重投，因此常用至少一次 + 幂等。先提交 offset 再做业务则可能在崩溃时丢失业务处理。

21. At-most-once、At-least-once 与 Exactly-once

语义 可能丢 可能重复 常见实现直觉
至多一次 是 否 先推进位置或不重试
至少一次 否（在声明故障模型内） 是 成功后确认，失败重投
恰好一次 取决于明确范围 在范围内抑制可见重复 事务、去重、幂等与状态协调

Exactly-once 必须问“对哪个状态、在哪些组件、什么故障模型下”。Kafka 内部事务不能自动让外部支付、数据库或邮件只执行一次。

22. 分区顺序与全局顺序

Kafka 等系统通常只保证单分区内的记录顺序；同一个业务 key 使用稳定分区策略可获得 key 范围顺序。增加分区、改变 hash、并行处理或失败重试都可能改变业务观察顺序。全局顺序需要单一排序点，通常牺牲吞吐和可用性。

23. 倒排索引与正排存储

  • 倒排：term → 文档/位置列表，适合从词找到文档。
  • 正排：文档 → 字段/内容，适合读取命中文档的详细数据。

搜索查询先用倒排/向量结构召回候选，再读取字段、计算分数和返回结果；它不是简单地遍历全文做 LIKE。

24. Refresh、Flush 与 Merge

  • refresh：让新 segment 对搜索可见，形成近实时语义。
  • flush：与事务日志/持久化检查点相关，具体由引擎实现定义。
  • merge：合并 segment、清理删除标记，消耗 CPU/I/O。

“已经能搜到”与“发生何种持久化”不是同一事件。频繁 refresh 可降低可见延迟，但增加 segment 和 merge 压力。

25. BM25、向量召回与重排

  • BM25：依赖词项匹配、频率和文档长度，适合专有名词与精确词信号。
  • 向量：按语义表示的距离找近邻，能召回不同措辞，但可能忽略精确词和权限过滤成本。
  • 重排：对少量候选使用更昂贵模型重新评分。

混合检索通常先并行召回，再用 RRF/归一化融合，最后可选重排。不同分数不可在没有标定时随意直接相加。

26. 分片与副本

  • 分片：把数据/请求分布到不同节点，扩大容量和并行度。
  • 副本：保存相同逻辑数据的多个拷贝，提高容错或读能力。

增加分片会增加协调、元数据、segment 和重平衡成本；增加副本会增加写入、存储和一致性成本。二者解决的问题不同。

27. 强一致、线性一致与最终一致

“强一致”常被含糊使用，讨论时应改用具体模型：

  • 线性一致：每次操作看起来在调用与返回之间某个瞬间生效，并尊重实时先后。
  • 顺序一致：存在所有操作的统一顺序，保持每个进程自身顺序，但不要求尊重真实时间。
  • 因果一致：有因果关系的操作保持顺序，无因果操作可不同序。
  • 最终一致：停止更新并满足传播条件后副本最终收敛，不规定中间读到什么或多久收敛。

28. CAP 与 PACELC

CAP 讨论网络分区发生时，系统无法同时对每个请求提供线性一致的单副本体验与持续可用响应。它不是把系统永久贴成 CP/AP，也不说明无分区时延迟与一致性的取舍。

PACELC 提醒：有分区时在可用性与一致性间取舍；无分区时也常在延迟与一致性间取舍。实际系统还要说明具体操作、配置和故障模型。

29. Quorum 与共识

  • Quorum 是读写副本数量的交集思路；R + W > N 在特定复制模型下帮助读写集合相交。
  • 共识让多个节点对一系列值/日志达成一致，处理任期、选举和安全性。

集合相交不自动等于线性一致，还需版本选择、并发写处理、故障检测和读写协议。Raft 也不是简单的“多数派数据库写”。

30. Leader 选举与 Raft 提交

选出 leader 只解决“谁协调”，安全性还依赖 term、投票限制、日志匹配和提交规则。Raft leader 对当前 term 条目在多数派复制后推进提交；旧 term 条目通常随当前 term 条目提交而间接确认。

31. 高可用与容灾

  • 高可用：减少日常组件故障导致的服务不可用。
  • 容灾：面对机房、地域、数据损坏等大故障恢复服务和数据。
  • RTO：允许多长时间恢复。
  • RPO：允许丢失多长时间窗口的数据。

多实例不等于容灾；共享数据库、配置错误和相关性故障仍可能击穿全部副本。备份只有通过恢复演练才能证明作用。

32. 蓝绿、滚动、金丝雀与 A/B

  • 滚动：分批替换实例，资源较省但新旧版本共存。
  • 蓝绿：两套环境切换，回滚流量快但数据兼容仍复杂。
  • 金丝雀：少量真实流量验证可靠性指标后逐步扩大。
  • A/B：比较产品效果，不等同于故障风险灰度。

所有发布方式都需要 schema/协议兼容、连接排空、自动停止条件和数据回滚策略。

33. 日志、指标与追踪

信号 优势 局限
日志 详细离散事件和上下文 成本高、聚合困难
指标 低成本趋势、告警和聚合 高基数受限、细节少
Trace 跨服务请求路径与分段耗时 采样、异步关联和成本

三者通过 request/trace/业务 ID 关联。指标发现症状，trace 缩小路径，日志解释具体事件，但实际排障并非固定顺序。

34. SLA、SLO、SLI 与 Error Budget

  • SLI：实际测量指标，如成功率或延迟达标比例。
  • SLO：内部/产品希望达到的目标。
  • SLA：对外协议及违约后果。
  • Error budget：1 - SLO 对应的可接受失败预算，用于平衡发布速度与可靠性。

资源利用率不是用户 SLI；CPU 高可能仍满足 SLO，CPU 低也可能因下游等待而大量超时。

35. 使用检查

遇到术语时连续问：

  1. 它讨论的是所有权、时序、持久化、可见性还是可用性？
  2. 保证范围是单线程、单进程、单实例、单分区、集群内还是跨外部系统？
  3. 依赖哪些故障模型、时钟、网络和下游校验假设？
  4. 超时、重试、重启、旧请求迟到时还成立吗？
  5. 用什么测试和指标能证明实现满足声明？
