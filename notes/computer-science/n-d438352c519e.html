2. 操作系统与 Linux

  • [ ] ★★★ 进程、线程和协程有什么区别？
  • 完整回答：
    • 进程是操作系统进行资源分配、保护和故障隔离的基本单位，通常拥有独立的虚拟地址空间、文件描述符表、信号处理状态、当前工作目录和权限凭证。
    • 线程是 CPU 调度的基本执行单位，同一进程内的线程共享地址空间和大部分资源，但各自有寄存器上下文、栈、线程局部存储和调度状态。
    • 协程通常由语言运行时或用户态框架调度，它把一个线程中的执行流拆成可挂起、可恢复的任务，切换时主要保存用户态栈或状态机上下文，避免频繁进入内核。
    • 选择上，进程强调隔离，线程强调并行执行和共享内存，协程强调在用户态组织并发；Linux 底层都用 task_struct 表示，fork 偏隔离，clone 可按标志共享地址空间、文件表、信号处理等资源。
    • 协程不能突破 CPU 核数限制，单线程协程只能并发推进 I/O 等待任务；要真正并行计算，仍需要多个内核线程或多个进程。
    • 常见误区是把“协程切换便宜”理解成“任何场景都更快”，实际上阻塞系统调用、长时间计算、运行时调度器实现、栈增长和调试观测成本都会影响最终效果。

  • 原理解析：

    • 操作系统先要回答“谁拥有资源、谁被调度、谁保存执行位置”这三个问题。进程对应资源容器，地址空间和文件表形成隔离边界；线程对应可被内核调度的执行流，多个线程共享容器但各自有寄存器、栈和调度状态；协程对应用户态把执行流切成可挂起片段，更多是运行时抽象。
    • 硬件层面，真正运行在 CPU 上的是寄存器、程序计数器和栈指针所描述的上下文。进程切换可能要换页表，导致 TLB 和缓存局部性受损；同进程线程切换通常不换地址空间，但仍要保存恢复寄存器和内核调度状态；协程切换多数不陷入内核，只在用户态保存少量状态，所以成本低但调度权也受所在内核线程限制。
    • Linux 的实现容易让人误解：它用 task_struct 统一表示进程和线程，不是说二者没有区别，而是通过 clone 的共享标志决定是否共享 mm_struct、文件表、信号处理等资源。协程不由 Linux CFS 直接调度，Go、Java、Python 等运行时会把大量协程映射到较少的内核线程上。
    • 选择时看因果链：需要故障隔离和独立部署，用进程；需要多核并行且共享数据，用线程但要处理锁和可见性；需要海量 I/O 等待任务，用协程减少阻塞线程数。记忆抓手是“进程管家产，线程跑 CPU，协程管等待”，但 CPU 密集型协程若不让出执行权，会拖住整个事件循环。

  • [ ] ★★★ 进程间通信有哪些方式？应该如何选择？

  • 完整回答：
    • 进程间通信是让地址空间相互隔离的进程交换数据、事件或共享状态的机制，常见方式有管道、命名管道、消息队列、共享内存、信号、Socket、内存映射文件、普通文件和 RPC。
    • 先看通信范围：父子进程或同一主机可用管道、Unix Domain Socket、共享内存；跨主机通常需要 TCP/UDP Socket 或 RPC。
    • 再看数据形态：简单字节流适合管道和 Socket，有明确消息边界可用消息队列或应用层协议，大块高频交换适合共享内存加同步原语。
    • 还要看可靠性、顺序性、背压、权限控制、可观测性和失败恢复成本。匿名管道适合亲缘进程单向字节流，FIFO 让无亲缘进程通过路径通信，System V/POSIX 消息队列保留边界但容量受限且有内核拷贝。
    • 共享内存减少复制但必须配合互斥锁、信号量、futex 或无锁结构解决并发访问、可见性和生命周期问题；信号只适合通知状态变化；Unix Domain Socket 支持权限校验和传递文件描述符，常用于本机守护进程通信。
    • 工程上不能只按“最快”选择，共享内存协议和清理更复杂，Socket 吞吐未必最高，但更容易跨语言、跨机器和纳入监控。

  • 原理解析：

    • IPC 的根源是虚拟内存隔离：进程默认看不到彼此地址空间，必须通过内核中介、共同映射的物理页，或外部持久介质交换信息。所谓“通信方式”本质是在复制成本、同步成本、边界清晰度和失败恢复之间取舍，而不是简单背几个 API 名字。
    • 管道、消息队列和 Socket 的共同点是数据经过内核对象，内核负责缓冲、权限、阻塞唤醒和生命周期，优点是语义清楚、错误边界明显，代价是可能发生用户态和内核态之间的数据拷贝。共享内存则绕开大量拷贝，把同一批物理页映射到多个进程，但一致性、互斥、内存屏障、崩溃清理都要应用自己处理。
    • Linux 里匿名管道适合父子进程流水线，FIFO 用路径把无亲缘进程连起来，Unix Domain Socket 适合本机服务并能传 fd，TCP/UDP 适合跨主机，mmap/POSIX 共享内存适合大块高频数据。信号只是一种异步通知，容量小且语义粗，不适合传业务负载。
    • 选择链路可以按四问：通信是否跨机器，数据是否有消息边界，吞吐和延迟瓶颈是否在复制，异常恢复是否要简单。记忆抓手是“小数据要语义，大数据要少拷贝，跨语言跨机器要 Socket/RPC”。共享内存最快的说法只在同步协议正确、访问模式匹配时成立，否则排障成本可能高于性能收益。

  • [ ] ★★★ 用户态和内核态有什么区别？系统调用的过程是什么？

  • 完整回答：
    • 用户态和内核态是 CPU 特权级与操作系统保护机制共同形成的执行权限边界。用户态运行普通应用代码，不能直接访问物理内存、设备寄存器、页表和调度器等关键资源。
    • 内核态运行操作系统内核代码，拥有更高特权，可以管理硬件、中断、内存、进程、文件系统和网络协议栈。硬件特权级、页表权限和异常机制一起阻止应用破坏系统稳定性。
    • 系统调用是受控入口：应用在用户态放好系统调用号和参数，再执行陷入指令进入内核；内核保存必要上下文，校验调用号、地址、权限和长度，再执行内核逻辑。
    • 如果操作能立即完成就返回结果；如果需要等待 I/O、锁或事件，当前任务可能被挂起并由调度器切换出 CPU。x86-64 常用 syscall，用户空间指针会经过安全拷贝函数处理，不同架构入口指令和调用约定不同，但流程一致。
    • 系统调用不是普通函数调用，它有特权级切换、参数校验、可能的数据拷贝和调度成本，但不一定每次都发生进程切换。高性能程序常通过批量 I/O、缓冲、sendfile、mmap、io_uring 减少过门次数。

  • 原理解析：

    • 用户态和内核态是硬件特权级、页表权限和异常入口共同构成的保护边界。应用如果能直接改页表、设备寄存器或调度队列，一个普通 bug 就可能破坏整个系统；因此 OS 把危险操作收进内核，只暴露受控入口，让应用通过系统调用“申请服务”。
    • 系统调用的关键不是函数名，而是 CPU 执行特殊陷入指令后改变特权级和入口地址。以 Linux x86-64 为例，用户态按 ABI 把调用号和参数放进寄存器，执行 syscall，CPU 进入内核入口；内核保存必要现场，检查调用号、权限和用户指针，再执行文件、网络、内存或进程相关逻辑，最后把返回值放回约定寄存器并返回用户态。
    • 参数校验是因果链中的安全核心。用户传来的指针属于用户虚拟地址，内核不能直接相信它可读、可写、长度合法或在拷贝过程中不变化，所以 Linux 会使用安全拷贝路径，并在失败时返回错误码。若操作等待磁盘、网络或锁，任务可能睡眠并触发调度；若立即完成，则只有模式切换，没有任务切换。
    • 对比普通函数调用，系统调用多了特权级切换、入口分发、权限检查和可能的数据拷贝；对比中断，它由应用主动发起，目的明确。记忆抓手是“用户态不能碰硬件，系统调用是带安检的门”。优化不是拒绝系统调用，而是通过缓冲、批量、零拷贝或异步接口减少不必要过门次数。

  • [ ] ★★★ 什么是上下文切换？为什么频繁切换会影响性能？

  • 完整回答：
    • 上下文切换是 CPU 从一个执行流转去执行另一个执行流时保存旧状态并恢复新状态的过程。要保存的上下文包括程序计数器、通用寄存器、栈指针、浮点或向量寄存器、调度状态和内核栈位置。
    • 进程切换还可能涉及地址空间切换、页表基址切换和 TLB 失效；线程切换因为共享同一进程地址空间通常少一些内存管理成本，但仍有寄存器、栈和调度成本。
    • 触发原因包括时间片耗尽、线程主动阻塞、等待锁、等待 I/O、中断唤醒高优先级任务或抢占调度。性能损失来自保存恢复和调度器开销，以及 cache、分支预测和 TLB 局部性被破坏。
    • Linux 可用 vmstat 的 cs、pidstat -w、perf sched 观察上下文切换和调度延迟；us 高常指用户态热点，sy 高常指内核处理，cs 异常高常见于线程过多、锁竞争、短任务拆分、阻塞 I/O 或小包过多。
    • 误区是把用户态到内核态的模式切换等同于上下文切换。优化应减少无意义线程数量、批量处理小任务、降低锁竞争、使用事件驱动或异步模型，并用采样验证效果。

  • 原理解析：

    • CPU 一次只能执行一个硬件线程上的一个上下文。上下文包含“从哪里继续执行”和“继续执行需要什么状态”，包括程序计数器、寄存器、栈、内核栈、调度信息以及进程地址空间。切换的本质是把旧执行流冻住，再把新执行流恢复到好像从未离开过的位置。
    • 性能损失有显性和隐性两类。显性成本是进入内核、运行调度器、保存恢复寄存器和更新运行队列；隐性成本是新任务的代码和数据未必在 CPU cache 中，进程切换还可能换页表并冲击 TLB。后者常比保存几个寄存器更痛，因为内存访问延迟会持续影响切换后的若干指令。
    • 触发原因决定排查方向：自愿切换多，通常是等待 I/O、锁、条件变量或睡眠；非自愿切换多，可能是线程太多、时间片竞争、CPU 饱和或优先级抢占。Linux 的 vmstat cs 只能看整机趋势，pidstat -w 能分进程看自愿/非自愿切换，perf sched 才能进一步看调度延迟和唤醒链。
    • 边界误区是把“系统调用”直接等同“上下文切换”。系统调用一定发生用户态到内核态的模式切换，但只有当当前任务阻塞、被抢占或调度器选择其他任务时，才发生任务上下文切换。记忆抓手是“换权限不一定换人，换人一定要换现场”。优化要减少锁争用、小任务抖动和过量线程，而不是盲目追求零切换。

  • [ ] ★★★ 什么是虚拟内存？它解决了什么问题？

  • 完整回答：
    • 虚拟内存是操作系统为每个进程提供的抽象地址空间，进程用虚拟地址访问代码、堆、栈、共享库和映射文件，MMU 根据页表翻译成物理地址并检查权限。
    • 它解决三个核心问题：隔离，让不同进程的同一虚拟地址映射到不同物理页；地址空间管理，让应用看到近似连续的范围；按需加载和超额承诺，程序不必一开始装入全部代码和数据。
    • Linux 采用分页虚拟内存，每个进程有自己的内存描述结构和虚拟内存区域，页表项记录物理页框、权限、脏位、访问位和是否存在等信息。mmap 可把文件映射到内存，fork 的写时复制可让父子进程先共享物理页。
    • 虚拟内存不等于无限内存，地址空间、物理内存、cgroup 限制、overcommit 和 swap 都会影响结果，权限位还会限制可写和可执行。大量 swap 换入换出会把系统拖入抖动状态。
    • 常见误区是看到 VIRT 很大就认定占了同等物理内存；排查应结合 RSS、PSS、page cache、swap 和缺页指标。

  • 原理解析：

    • 虚拟内存把“程序看到的地址”和“真实物理内存位置”分开。应用发出的地址先经过 MMU 查页表，得到物理页框和权限结果；如果页表不存在或权限不符，就触发异常交给内核。这一层间接性带来了隔离、连续地址假象、权限控制和按需分配。
    • 三个问题是一条因果链：隔离让进程互不破坏；映射让零散物理页组织成连续虚拟空间，降低应用和分配器复杂度；按需加载让可执行文件、共享库、匿名页和映射文件不必一次性占满内存。fork 的写时复制也是这个机制的延伸：父子进程先共享只读映射，写入时再复制物理页。
    • Linux 实现中，进程通过内存描述结构管理多个虚拟内存区域，页表项记录物理页、权限、脏位、访问位等。共享库的只读代码页可以被多个进程映射到各自地址空间，mmap 可以把文件页缓存映射进进程，匿名堆栈页则通常在首次访问时才真正分配。
    • 常见排障误区是把 VIRT 当作真实占用。VIRT 只是虚拟地址范围，RSS 才接近当前驻留物理页，PSS 更适合摊分共享页；page cache 可回收，swap 活跃则说明内存压力已经进入慢路径。记忆抓手是“虚拟地址是门牌号，物理页是房间，页表是门牌到房间的登记簿”，缺页则是登记簿暂时查不到时的补办流程。

  • [ ] ★★★ 什么是缺页中断？页面置换算法有哪些？

  • 完整回答：
    • 缺页中断是进程访问某个虚拟页时，MMU 发现页表项不可用或权限不满足而触发的异常，CPU 进入内核由操作系统处理；它不一定表示错误。
    • 合法缺页包括按需分配匿名页、首次访问映射文件、写时复制、栈增长、被换出的页重新调入等；非法缺页如访问未映射地址、写只读页或违反执行权限，通常会导致段错误。
    • 处理流程是：内核查故障地址对应的虚拟内存区域，判断访问是否合法；合法则准备物理页，可能从磁盘读取文件页或 swap 页，也可能分配清零页，再更新页表和权限并返回用户态重试。
    • Linux 区分 minor fault 和 major fault，前者成本低，后者需要慢速磁盘 I/O。频繁 major fault、swap in/out 增长和 vmstat 里的 si/so 往往说明工作集超过可用内存。
    • 页面置换算法都在回答“内存不够时牺牲谁”，经典算法有 FIFO、LRU、LFU、Clock/Second Chance、NRU。Linux 采用基于活跃/非活跃链表、引用位和回收扫描的近似 LRU 机制。

  • 原理解析：

    • 缺页中断的名字容易误导，它是 CPU 访问虚拟地址时由 MMU 发现“页表无法直接完成本次访问”而产生的异常，不天然代表程序错误。合法场景包括懒分配、文件页首次映射、写时复制和 swap 换入；如果 PTE 只读但所在 VMA 可写，可能只是合法 COW。只有地址未映射，或 VMA 不允许本次写入、执行等访问类型时，才属于非法访问并通常触发 SIGSEGV。
    • 处理链路是：硬件带着故障地址和访问类型进入内核，内核查该地址是否落在合法 VMA 中，再决定分配清零页、读取文件页、从 swap 读回，或复制 COW 页；随后更新页表和 TLB 相关状态，返回用户态重试原指令。原指令通常无感继续，所以缺页是虚拟内存“按需兑现”的核心机制。
    • minor fault 与 major fault 的区别在是否需要慢速 I/O。minor fault 可能只是建立页表或从已有页缓存映射，成本相对低；major fault 要等磁盘或块设备，延迟高很多。因此排障时 majflt、vmstat si/so、延迟尖刺能指向工作集超内存、冷文件频繁读取或 swap 抖动，而不是单纯“程序崩了”。
    • 页面置换算法都在回答“内存不够时牺牲谁”。FIFO 简单但不懂局部性，LRU 符合近期使用假设但精确维护昂贵，Clock 用访问位近似 LRU，LFU 看频率但容易被旧热点污染。Linux 使用近似 LRU 和活跃/非活跃链表，是工程折中。记忆抓手是“缺页负责补页，置换负责腾页”。

  • [ ] ★★★ 什么是死锁？死锁产生的四个必要条件是什么？

  • 完整回答：
    • 死锁是多个进程、线程或事务在竞争资源时形成永久等待关系，每个参与者都持有一部分资源并等待其他参与者释放资源，系统无法靠它们自身继续推进。
    • 四个必要条件是：互斥、占有且等待、不可抢占、循环等待。资源只能被一个实体占用，持有者继续请求新资源，资源不能被系统强行拿回，等待关系形成环。
    • 破坏任一条件都能预防死锁，但工程代价不同。最常用的是固定全局加锁顺序，因为它直接破坏循环等待；一次性申请所有资源、允许抢占也能破坏其他条件，但适用面更窄。
    • Linux 用户态常见于锁顺序不一致、读写锁升级、线程池任务互等、持锁调用外部接口；内核态还涉及自旋锁、中断上下文和不可睡眠区域。数据库通常会检测等待图并回滚一方事务。
    • 排查要收集线程栈、锁等待信息和死锁日志，定位谁持有锁、谁在等待、是否成环。常见误区是把长时间等待都叫死锁；没有循环等待时，问题类型可能完全不同。

  • 原理解析：

    • 死锁不是“慢”，而是等待图形成了无法自行打破的环。每个节点持有某些资源，又等待环上其他节点释放资源；由于参与者都在等待，没人能执行到释放动作，系统局部进入永久停滞。这个定义适用于线程锁、进程资源、数据库事务和部分分布式锁场景。
    • 四个必要条件分别对应四个支点：互斥说明资源不能共享；占有且等待说明持有者还要更多资源；不可抢占说明系统不能强行拿回；循环等待说明等待关系闭环。只要破坏任一支点，理论上就不会形成死锁，但工程上最常破坏循环等待，也就是规定全局加锁顺序。
    • Linux 用户态普通互斥锁通常不会自动替你发现业务死锁，线程只会卡在 futex 等待、条件变量或系统调用上；内核态还要考虑自旋锁、关中断、不可睡眠上下文等约束。数据库则常维护锁等待图，检测到环后回滚一个事务，这是“检测并恢复”，不是“预防”。
    • 排障要找证据链：线程栈显示谁卡在锁上，锁调试或日志显示谁持有锁，等待关系能否闭环。CPU 不高但请求不返回、线程池满、栈停在 pthread_mutex_lock 或数据库死锁日志，才逐步指向死锁。记忆抓手是“互占不抢再成环”，误区是把所有长等待、I/O 慢或资源耗尽都叫死锁；没有等待环时，优化方向通常完全不同。

  • [ ] ★★★ Linux 的 I/O 多路复用是什么？select、poll、epoll 有何区别？

  • 完整回答：
    • I/O 多路复用是一个线程同时等待多个文件描述符就绪事件的机制，核心是连接很多但大多数时间都在等 I/O 时，避免为每个连接阻塞一个线程。
    • 它返回的是“就绪”，不是“操作必然一次完成”，所以通常要配合非阻塞 fd 和循环读写。select 用位图，受 FD_SETSIZE 限制；poll 用数组，突破限制但每次都要全量传入并线性扫描。
    • epoll 先用 epoll_ctl 注册关注集合，epoll_wait 主要返回就绪事件，适合大量长连接、少量活跃的网络服务。它支持水平触发和边缘触发。
    • 边缘触发下必须使用非阻塞 I/O 并一直读写到 EAGAIN，否则剩余数据可能长期得不到处理。epoll 不是任何场景都优于 poll，fd 少、活跃率高或跨平台要求强时，简单模型可能更合适。
    • I/O 多路复用只减少等待线程数，业务回调里如果做 CPU 密集计算、慢数据库访问或阻塞文件 I/O，事件循环仍会被拖慢。

  • 原理解析：

    • I/O 多路复用解决的是等待模型问题：大量连接多数时间没有数据，如果每个连接一个阻塞线程，线程栈、调度和上下文切换会被连接数放大。多路复用把“等多个 fd 就绪”交给内核，一个线程睡在一个等待点，醒来后处理一批就绪事件。
    • select、poll、epoll 的差异主要在关注集合如何传递、内核如何记录、用户态如何取结果。select 每次传位图且有 fd 数量限制；poll 用数组突破固定限制，但仍每次全量传入并线性扫描；epoll 先用 epoll_ctl 注册兴趣集合，等待时主要返回就绪列表，适合 fd 很多但活跃比例低的场景。
    • “就绪”不是“读写一定完成”。可读只表示内核缓冲区当前有数据或连接状态可处理，可写只表示当前有发送空间；应用仍要调用 read/write。边缘触发下状态变化只通知一次，所以必须配合非阻塞 fd 并循环读写到 EAGAIN，否则缓冲区剩余数据可能不再触发新事件。
    • Linux 的 epoll 是本机高并发网络服务常用实现，但不是通用银弹。fd 数量少、活跃率高、跨平台或逻辑简单时，poll 甚至阻塞线程模型可能更易维护。记忆抓手是“select 位图，poll 数组，epoll 注册加就绪队列”。真正瓶颈若在业务计算或数据库阻塞，多路复用也救不了事件循环。

  • [ ] ★★ 阻塞、非阻塞、同步和异步分别是什么？

  • 完整回答：
    • 阻塞和非阻塞描述的是调用发起后操作是否让线程停在原地等待。阻塞读没数据时会睡眠，非阻塞读没数据时会立即返回错误码如 EAGAIN 或 EWOULDBLOCK。
    • 同步和异步描述的是完成结果由谁推进和通知。同步 I/O 仍由应用线程在就绪后主动执行读写；异步 I/O 则由内核或运行时在后台推进，完成后用回调、完成队列或事件通知结果。
    • 这两个维度是正交的，不能把非阻塞等同于异步。epoll + nonblocking socket 属于同步非阻塞，io_uring、POSIX AIO 或部分运行时封装更接近异步提交/完成。
    • 阻塞模型代码简单但线程消耗大；非阻塞同步模型适合大量连接但状态管理复杂；异步模型能减少等待线程和阻塞路径，但对内核支持、完成语义、错误处理和调试能力要求更高。

  • 原理解析：

    • 阻塞/非阻塞看“操作没准备好时调用者是否停住”，同步/异步看“最终完成由谁推进并通知”。这是两个正交维度，混在一起会误判模型。阻塞同步最直观：调用读，没有数据就睡眠，数据到达后返回；非阻塞同步则是没有数据立即返回，调用者之后自己重试或等就绪通知。
    • Linux socket 设置 O_NONBLOCK 后，read 返回 EAGAIN 表示暂时不能完成，不是连接错误。epoll 只是告诉应用 fd 当前就绪，真正把数据从内核缓冲区取到用户缓冲区的仍是应用线程调用 read，所以常见 Reactor 模型属于同步非阻塞。
    • 异步 I/O 的核心是提交请求后，完成过程由内核或运行时在后台推进，应用通过回调、future、完成队列或事件拿结果。io_uring 更接近这种提交/完成模型，但具体操作是否真正异步还受文件类型、内核版本和配置影响。
    • 记忆抓手是“阻塞问等不等，同步问谁干完”。边界误区是把“用了事件循环”叫异步，事件循环可以管理异步回调，也可以只是同步非阻塞 I/O 的调度器；另一个误区是认为非阻塞一定更快，它只是避免线程睡死，代价是状态机和重试逻辑更复杂。

  • [ ] ★★ 零拷贝是什么？常见实现方式有哪些？

  • 完整回答：
    • 零拷贝是一类减少数据在用户态、内核态和设备之间重复复制的技术目标，不一定字面上一次 CPU 拷贝都没有。
    • 传统发送路径里，磁盘数据经 DMA 到页缓存，再从页缓存拷到用户缓冲区，写 socket 时又拷回内核缓冲区，最后由网卡 DMA 发送，这会消耗内存带宽、CPU 和系统调用开销。
    • 常见方式包括 mmap、sendfile、splice、tee、直接 I/O、DMA 和支持分散聚集发送的网卡能力。sendfile 直接把文件页缓存送到 socket，mmap 减少 read 复制，splice 在管道和文件描述符之间移动页引用。
    • 零拷贝适合大文件传输、日志转发、消息系统顺序读写等数据搬运占比较高的场景，但不能消除磁盘读、网络协议处理、TLS 加密、业务解析和内存页管理成本。
    • 需要逐字节修改、压缩加密或小数据频繁操作时，收益可能被复杂度抵消。误区是把零拷贝理解成没有任何拷贝；DMA、页映射和协议栈处理仍然存在。

  • 原理解析：

    • 零拷贝要减少的是 CPU 在用户缓冲区和内核缓冲区之间搬数据的次数，以及相关系统调用和缓存污染。传统 read 加 write 发送文件时，数据经过磁盘 DMA 到页缓存、页缓存拷到用户态、用户态再拷回 socket 缓冲区、最后网卡 DMA 发出，中间两次 CPU 拷贝很浪费。
    • sendfile 的思路是让文件页缓存直接接到 socket 发送路径，应用只描述“从哪个文件到哪个 socket”；mmap 是把文件页映射到用户地址空间，避免 read 复制到用户缓冲区；splice/tee 则利用管道在内核对象之间移动页引用。direct I/O 是绕过 page cache 的相关优化，可能减少缓存复制，但不等同于 sendfile/splice 这种内核对象间零拷贝路径；底层还依赖 DMA 和网卡 scatter-gather 能力减少连续缓冲要求。
    • 通用 OS 原理是“移动引用比移动字节便宜”，Linux 实现则受文件系统、socket、TLS、页缓存和设备能力限制。开启 TLS 后数据常要加密，业务需要压缩、过滤或逐字节解析时也必须触碰内容，零拷贝收益会下降。
    • 记忆抓手是“数据少过用户态，CPU 少搬字节”。它适合静态文件、日志转发、大块顺序数据，不适合小包复杂处理。误区是把零拷贝理解成没有任何拷贝：磁盘和网卡 DMA、页表映射、协议栈处理仍然存在，只是尽量避免无意义的 CPU 内存复制。

  • [ ] ★★ 堆和栈有什么区别？内存泄漏和内存溢出有什么区别？

  • 完整回答：
    • 栈是线程执行函数调用时使用的内存区域，保存调用帧、返回地址、参数、局部变量和部分寄存器保存区，通常随函数进入和返回自动增长、回收。
    • 堆用于动态分配生命周期不固定的对象，容量通常比栈大，但需要分配器、GC 或程序员显式释放来管理，可能带来碎片、停顿和元数据开销。
    • Linux 里的堆和栈都是进程虚拟地址空间中的区域，物理页按需分配，线程栈大小受 pthread 属性、ulimit -s 和运行时策略影响。
    • 内存泄漏是已经不再有业务意义的内存仍无法释放；内存溢出是申请内存失败或超过某个内存区域限制。泄漏可能导致溢出，但溢出也可能来自瞬时峰值、大对象、配置过小、碎片或并发过高。
    • 排查时要区分虚拟内存、RSS、语言堆、堆外内存、线程栈和页缓存，不能只看内存上涨就认定为泄漏。

  • 原理解析：

    • 栈服务于函数调用链，生命周期天然嵌套：进入函数压入调用帧，返回时整体弹出，所以快、局部性好、管理简单。堆服务于不规则生命周期：对象可能跨函数、跨线程、放入集合或异步回调中，因此需要分配器、引用关系、GC 或手动释放来决定何时回收。
    • 在 Linux 中，堆和栈都是进程虚拟地址空间里的区域，不是启动时一次性占满物理内存。线程栈通常有大小限制，递归过深或大局部数组会触发栈溢出；堆增长受地址空间、物理内存、cgroup、overcommit 和运行时参数影响，分配失败可能表现为 OOM。
    • 泄漏和溢出的因果不同。泄漏是“该释放却仍被占着”，长期趋势会抬高基线；溢出是“这次申请或使用超过限制”，可能由泄漏累积导致，也可能由瞬时峰值、大对象、线程暴涨或配置过小导致。GC 语言也会泄漏，只要对象仍被可达引用链挂住，GC 就不能释放。
    • 记忆抓手是“栈管调用，堆管对象；泄漏是回不去，溢出是装不下”。排障不能只看内存上涨，要拆分语言堆、堆外内存、线程栈、RSS、PSS 和 page cache，否则容易把正常缓存、碎片或延迟回收误判为泄漏。

  • [ ] ★★ 什么是孤儿进程和僵尸进程？如何处理？

  • 完整回答：
    • 孤儿进程是父进程已经退出而子进程仍在运行的进程。Linux 通常由 PID 1 的 init/systemd 或配置为 subreaper 的进程接管，之后子进程退出时由新的父进程回收退出状态。
    • 孤儿进程本身不一定异常，守护进程早期就常通过父进程退出、子进程继续运行来脱离控制终端。
    • 僵尸进程是子进程已经结束执行，但父进程还没有调用 wait、waitpid、waitid 读取退出码，内核必须保留进程表项、PID、退出状态和资源统计，状态显示为 Z。
    • 少量短时间僵尸是正常过渡状态，大量长期僵尸会占用 PID 和进程表资源。处理时先找 Z 状态进程及其 PPID，再检查父进程是否卡死、是否忽略了 SIGCHLD、是否没有循环回收多个子进程。
    • 正确修复通常在父进程中安装 SIGCHLD 处理、使用非阻塞 waitpid(-1, ..., WNOHANG) 循环回收，或限制子进程创建；父进程无法修复时，只能重启父进程让僵尸被 PID 1 接管并回收。

  • 原理解析：

    • 子进程退出时，内核不能立刻丢掉所有信息，因为父进程还需要知道退出码和资源统计；因此会保留一个轻量进程表项，直到父进程 wait。僵尸进程就是“已经死了但报告没人签收”，孤儿进程则是“父进程先退出但子进程还活着”。
    • Linux 会把孤儿进程托管给 PID 1 或 subreaper，这是为了保证将来它退出时仍有人回收。孤儿本身不消耗异常资源，也可能是守护进程设计的一部分。僵尸则不再运行、不占普通内存和 CPU，但占 PID、进程表项和退出状态；数量多时会影响 fork。
    • 处理链路要找父进程。ps 中状态 Z 指向僵尸，PPID 指向没有回收它的父进程。正确修复在父进程：处理 SIGCHLD，循环 waitpid(-1, ..., WNOHANG)，或限制子进程创建。直接 kill 僵尸无效，因为它没有可调度实体；重启父进程只是让其被 PID 1 接管后回收。
    • 记忆抓手是“孤儿还在跑，僵尸等收尸”。边界误区是看到父进程不存在就认为异常，孤儿会被接管；看到僵尸就 kill 子进程，也不会改变状态。真正要问的是父进程为什么没有 wait，以及是否有大量长期 Z 状态。

  • [ ] ★★ CPU 使用率很高时，你会如何排查？

  • 完整回答：
    • 先分层确认范围，再定位到可解释的执行路径。看 top、uptime、vmstat 1、mpstat -P ALL 1，判断是单核打满还是多核都高，并区分 us、sy、wa、hi、si、st。
    • us 高通常是用户态热点、死循环、序列化压缩加密或流量突增；sy 高常见于系统调用密集、网络协议栈、文件系统或锁竞争；wa 高表示在等 I/O；hi/si 高说明中断压力大。
    • 第二步定位进程和线程，用 pidstat -u -p ALL 1、top -H -p <pid> 找高 CPU 线程。Java 可用 jstack，Go 可用 pprof，C/C++ 可用 perf top、perf record、火焰图或 gdb 采样。
    • 第三步结合发布、流量、错误日志、GC、锁等待、自旋、线程池耗尽和 Linux 特有的 /proc/interrupts、sar -n DEV、perf sched 线索判断根因。
    • 不能一看到 CPU 高就扩容或重启，必须先保留现场。后续优化可能是修正死循环、降低锁竞争、批量系统调用、调整线程池、优化 GC 或隔离中断。

  • 原理解析：

    • CPU 使用率要先拆成“CPU 在哪里花时间”。us 是用户态业务代码，常指向算法热点、死循环、序列化、压缩加密或流量增加；sy 是内核态，常指向系统调用、网络/文件系统、锁竞争或内核协议栈；wa 是等待 I/O，不代表算力满；hi/si 指向硬/软中断压力。
    • 从整机到线程是为了缩小因果链。单核满可能是单线程热点或绑核问题，多核满更像全局流量或并行计算；找到进程后还要找线程，因为一个进程 CPU 高可能只有某个线程在自旋。Java 用十进制 TID 转十六进制匹配 jstack，Go 用 pprof，C/C++ 用 perf，本质都是把指标落到代码栈。
    • 指标能指向根因是因为运行位置不同：用户态热点会在采样火焰图中集中到业务函数；系统调用密集会抬高 sy 并出现频繁内核栈；软中断高常伴随网卡包量和 /proc/softirqs 增长；锁自旋可能表现为 CPU 高但吞吐不升。
    • 记忆抓手是“先分 us/sy/wa/si，再找进程线程栈”。误区是一看到 CPU 高就重启或扩容，这会丢现场；也不能把 wa 高当成 CPU 算力不足，它常要求查磁盘、网络存储或下游阻塞。

  • [ ] ★★ 服务器内存持续上涨时，你会如何排查？

  • 完整回答：
    • 先区分“系统可回收缓存增长”和“进程不可控占用增长”。Linux 会用空闲内存做页缓存、目录项和 inode 缓存，buff/cache 变大不等于泄漏，重点看 available、swap、OOM 和进程 RSS/PSS。
    • 第一层看整机：free -h、vmstat 1、sar -r、dmesg 或 journal 中的 OOM 记录，确认是否触发回收、swap in/out、cgroup memory limit。
    • 第二层看进程：ps aux --sort=-rss、top、smem、pmap -x <pid>、/proc/<pid>/smaps 判断是哪个进程的匿名内存、文件映射、共享库、线程栈或映射区域在涨。
    • 第三层进入运行时：Java 区分 heap、metaspace、direct memory、线程栈、JNI/native；Go 看 heap、goroutine、mspan/mcache、cgo、mmap；C/C++ 看 malloc 泄漏、碎片和未释放 mmap。
    • 第四层回到业务原因，常见包括无界本地缓存、连接或文件句柄未关闭、请求队列堆积、大对象反序列化、日志异步队列积压、线程数暴涨、图片或压缩缓冲未释放、内存映射文件生命周期过长。
    • 判断泄漏要看随时间和流量归一化后的趋势；单次峰值后能回落通常不是持续泄漏。修复前保留 OOM 日志、堆快照、对象引用链、进程 smaps 和发布/流量时间线。
  • 原理解析：
    • Linux 内存上涨先分“可回收”和“不可回收”。页缓存、dentry、inode 缓存会主动占用空闲内存提升 I/O 性能，压力来时可回收；进程匿名内存、语言堆、线程栈、部分 mmap 和 cgroup 内占用则可能真正挤压可用内存。因此 free 的 used 变大不够，available、RSS/PSS、swap 和 OOM 才更关键。
    • 分层排查的因果是：整机指标判断是否真的有压力，进程指标找谁在涨，运行时指标解释为什么涨。vmstat si/so 持续出现说明换入换出；dmesg OOM 能给出被杀进程和 cgroup 限制；smaps 可拆匿名页、文件映射、共享页；Java/Go/C++ 工具再把内存归因到堆对象、堆外、goroutine、native 分配或碎片。
    • 泄漏要看趋势和可达性。无界缓存、队列堆积、连接未关闭、监听器未移除、线程暴涨会让对象持续可达或资源无法释放；瞬时流量峰值、GC 尚未触发、页缓存增长则可能回落。把时间线与发布、流量、错误日志、GC 和 smaps 快照对齐，才能区分“正常高水位”和“基线持续抬升”。
    • 记忆抓手是“先看 available，再看谁的 RSS/PSS，再进运行时”。误区是把 buff/cache 当泄漏，或只看语言堆忽略 direct memory、线程栈、JNI/cgo、mmap 和 cgroup 限制。修复前保留快照，否则重启后证据链会断。
