分章节讲解

1. 主从复制

核心定义： 主从复制由主节点处理写入并把变更传播给从节点，从节点提供冗余、读扩展或故障接管。

底层原理 / 机制拆解： - 异步复制延迟低但主挂时可能丢最近写入；同步复制更安全但增加写延迟和不可用风险。 - 复制日志需要记录顺序、位置、事务边界和幂等应用，故障切换要处理脑裂和旧主回归。 - 读从库会遇到复制延迟，需要读己之写、会话一致或强制读主等方案。

适用场景： 适用于读多写少、容灾备份、读扩展、冷热分离和同城高可用。

不适用场景 / 失败边界： 不适合把异步从库当最新数据来源，也不适合无仲裁机制自动双主写入。

工程实践或做题/面试理解： 工程上监控复制延迟、半同步状态、binlog 位点和切换演练；面试中讲清同步/异步差异。

常见误区与纠正方式： 有从库就不会丢数据；纠正方式是说明复制模式、提交确认点和故障切换窗口。

速记： 主写从读要看延迟，切主防脑裂。

2. 分片

核心定义： 分片把数据按范围、哈希或业务维度分布到多个节点，以提升容量、吞吐和故障隔离。

底层原理 / 机制拆解： - 范围分片便于区间查询但易热点；哈希分片均匀但范围查询困难；业务分片贴近访问模式但迁移复杂。 - 分片路由可由客户端、代理或元数据服务完成，扩缩容需要数据迁移和双写/回放校验。 - 跨分片查询、聚合、事务和唯一约束会显著提高复杂度。

适用场景： 适用于单机容量/吞吐瓶颈、数据天然按租户/用户分隔、热点可拆分的系统。

不适用场景 / 失败边界： 不适合早期数据量小但查询关系复杂的系统；过早分片会增加运维和开发成本。

工程实践或做题/面试理解： 工程上先定义 shard key，评估基数、倾斜、查询模式和扩容路径；面试中说明“分片键决定未来代价”。

常见误区与纠正方式： 随机哈希一定均衡；纠正方式是分析热点 Key、明星用户、大租户和时间集中写入。

速记： 分片先问键，热点看分布。

3. 两阶段提交

核心定义： 两阶段提交通过准备阶段和提交阶段协调多个参与者，使分布式事务要么全部提交要么全部回滚。

底层原理 / 机制拆解： - 准备阶段协调者询问参与者能否提交，参与者持久化预提交并锁定资源。 - 提交阶段协调者根据投票发送 commit/abort；参与者按决定完成。 - 若协调者在参与者 prepared 后失效，参与者可能阻塞等待最终决定。

适用场景： 适用于参与者少、强原子性要求高、可接受锁等待和阻塞风险的内部事务。

不适用场景 / 失败边界： 不适合长事务、跨组织服务、用户交互流程和高可用优先的互联网业务链路。

工程实践或做题/面试理解： 工程上控制事务范围、设置超时和人工恢复通道；面试中突出“强原子性换阻塞和锁持有”。

常见误区与纠正方式： 2PC 能解决所有分布式一致；纠正方式是说明阻塞、协调者单点、长锁和性能成本。

速记： 先问能不能，再通知做不做。

4. Saga

核心定义： Saga 把长事务拆成一系列本地事务，每步成功后推进，失败时通过补偿动作尽量恢复业务一致。

底层原理 / 机制拆解： - Saga 可编排式集中控制，也可协同式事件驱动。 - 每个本地事务提交后不可简单回滚，需要设计语义正确的补偿，例如取消订单、释放库存、退款。 - Saga 保证的是最终业务一致，不是数据库层原子隔离。

适用场景： 适用于跨服务长流程、订单履约、支付后处理、库存预占、审批和外部系统调用。

不适用场景 / 失败边界： 不适合不可补偿或必须瞬时强一致的核心约束，例如同一余额的严格扣减。

工程实践或做题/面试理解： 工程上为每一步设计幂等键、状态机、补偿动作和人工兜底；面试中强调“补偿不是反向 SQL，而是业务动作”。

常见误区与纠正方式： 把 Saga 当自动回滚事务；纠正方式是逐步定义可补偿性、失败窗口和用户可见状态。

速记： 长流程走本地事务，失败靠补偿收敛。

深度扩展：底层原理与应用边界

1. 本章在「分布式系统」中的位置

  • 核心定位： 在网络不可靠、节点会失败、时钟不一致的条件下组织多节点协同。
  • 本章作用： 「分布式系统：复制分片与事务」负责把总纲落到可操作的判断框架：先确认问题边界，再拆解机制，最后根据代价和风险选择方法。
  • 主要风险： 最大风险是把远程调用当本地调用，忽视超时、重试、幂等、分区和一致性语义。
  • 实践抓手： 设计时先声明系统模型和一致性要求，再选择复制、分片、共识或异步补偿方案。

专题深化：具体机制、案例与追问

1. 具体案例：把「复制分片与事务」放进真实问题

例如下单链路要考虑请求超时、重复提交、消息至少一次投递、库存扣减幂等、读写一致性和补偿任务。

2. 本章关键机制细化

  • 复制提升可用性但带来副本延迟和冲突。
  • 分片提升容量但跨分片查询和事务更贵。
  • 2PC 保原子但可能阻塞，Saga 用业务补偿换可用性。

本轮扩写：复制、分片与事务的工程边界

1. 复制延迟不是一个“监控数字”，而是读写语义的一部分

复制带来读扩展和容灾，但也带来读旧值、写冲突、故障切换和回放顺序问题。

flowchart LR
  W["写主库"] --> L["写入日志"]
  L --> R1["同步到副本A"]
  L --> R2["同步到副本B"]
  R1 --> Q["读请求"]
  R2 --> Q
读策略 优点 风险 适用场景
读主 语义简单，读己之写容易保证 主库压力大 订单支付状态、账户余额
读从 扩展读吞吐 复制延迟导致旧读 商品详情、内容浏览
会话粘滞 用户体验更稳定 路由复杂 用户刚写完马上查看
quorum 读 可提升一致性 延迟高，实现复杂 多副本 KV、配置存储

2. 分片的难点是“后续变化”

分片不是把 key hash 一下就结束，真正难点在扩容、热点、跨分片事务和二级索引。

问题 触发条件 机制 误区
热点分片 明星用户、秒杀商品、递增 ID key 打散、预分片、队列削峰 只看平均 QPS
扩容迁移 数据量增长或节点故障 一致性哈希、虚拟节点、在线迁移 停机全量搬迁
跨分片查询 查询条件不是分片键 全局索引、查询改写、异步索引 让所有请求都 fanout
跨分片事务 不变量跨多个 key 2PC、Saga、业务冻结 默认本地事务能覆盖全局

3. 2PC 与 Saga 的选择

  • 2PC 适合： 参与方少、事务短、强一致要求高、协调者高可用且参与方能锁定资源。
  • 2PC 不适合： 长流程、人为审批、外部支付、库存物流等不可长期锁资源的链路。
  • Saga 适合： 长业务流程、每步可补偿、允许中间状态暴露但最终业务收敛。
  • Saga 不适合： 补偿不可逆、要求强隔离、外部副作用不能撤销且没有冻结机制。

4. 案例：下单链路的状态拆解

flowchart LR
  A["创建订单"] --> B["冻结库存"]
  B --> C["发起支付"]
  C --> D{支付结果}
  D -->|成功| E["确认库存"]
  D -->|失败/超时| F["释放库存"]
  E --> G["发货事件"]
  • 冻结库存比直接扣减更利于补偿。
  • 支付回调必须幂等，因为回调可能重复或乱序。
  • 订单状态机要禁止非法跳转，如“已取消”不能再变“已支付”。
  • 对账任务是最终兜底，不是主流程的替代品。

5. 面试追问路径

  1. “如何避免超卖？”——先讲单分片原子扣减，再讲热点削峰和异步确认。
  2. “跨分片如何保证一致？”——先说明是否真的需要强一致，再比较 2PC、Saga 和业务冻结。
  3. “扩容时如何不影响线上？”——回答双写/迁移标记、增量追平、校验、灰度切流和回滚。
  4. “副本落后怎么办？”——回答复制延迟监控、读路由、读己之写和降级策略。
