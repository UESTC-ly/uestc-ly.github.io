Redis 7.x 通用视角。本文关注“如何发现瓶颈、如何安全优化、如何持续监控”。性能优化不是堆参数，而是围绕 延迟、吞吐、内存、网络、持久化、数据结构 做闭环。

学习目标

学完本篇，你应该能够：

  • 说清 Redis 为什么通常很快，以及常见性能瓶颈来自哪里。
  • 使用 INFO、SLOWLOG、LATENCY、MONITOR、redis-cli --latency 等工具定位问题。
  • 从命令复杂度、Key 设计、内存、网络、持久化、客户端连接池等角度进行优化。
  • 建立一套适合生产环境的 Redis 监控指标和告警思路。
  • 避免“只看 QPS、不看延迟”“在线上滥用大 Key 命令”等常见误区。

核心概念

1. Redis 性能模型

Redis 单实例处理命令的主路径通常是：

客户端请求 -> 网络 I/O -> Redis 事件循环 -> 执行命令 -> 返回响应

影响性能的因素主要有：

维度 常见瓶颈 优化方向
命令复杂度 KEYS、大集合 SMEMBERS、大范围 LRANGE 用游标、分页、拆分数据结构
Key/Value 大小 大 Key、热 Key、Value 过大 拆分、压缩、分片、限流
内存 内存碎片、淘汰频繁、fork 复制开销 合理设置 maxmemory、监控碎片率
持久化 AOF fsync、RDB fork、重写阻塞 调整持久化策略、避开高峰
网络 RTT 高、请求过多、小包过多 Pipeline、批量命令、就近部署
客户端 连接泄漏、连接池过大/过小、重试风暴 连接池治理、超时、熔断
CPU 单线程命令执行耗时、Lua 脚本过重 降低命令复杂度、拆分脚本

Redis 6 开始支持 I/O threads 辅助网络读写，但命令执行主逻辑仍以单线程模型为核心。Redis 7.x 中仍应避免单条重命令阻塞事件循环。

2. 延迟与吞吐

  • 吞吐：单位时间内处理多少请求，常用 QPS/OPS 表示。
  • 延迟：一次请求从发送到收到响应的耗时，关注平均值、P95、P99、最大值。

生产中更应该关注尾延迟：

平均延迟 1ms 不代表没问题；如果 P99 是 200ms，用户仍会感知卡顿。

3. 大 Key、热 Key、慢命令

  • 大 Key：单个 Key 对应的 Value 很大，或集合元素过多。
  • String 超过数百 KB、Hash/List/Set/ZSet 元素数过多都可能成为问题。
  • 热 Key：某个 Key 被大量并发访问，导致单节点压力集中。
  • 慢命令：执行时间超过阈值，被记录到 SLOWLOG。

4. 监控闭环

推荐闭环：

采集指标 -> 设置基线 -> 发现异常 -> 定位原因 -> 小步优化 -> 验证效果 -> 继续监控

不要在没有基线和验证的情况下盲目调参。

关键命令/配置

1. 查看整体状态：INFO

redis-cli INFO
redis-cli INFO server
redis-cli INFO clients
redis-cli INFO memory
redis-cli INFO stats
redis-cli INFO persistence
redis-cli INFO replication
redis-cli INFO commandstats

重点字段：

分类 字段 含义
CPU/吞吐 instantaneous_ops_per_sec 当前每秒命令数
连接 connected_clients 当前客户端连接数
阻塞 blocked_clients 被阻塞的客户端数量
内存 used_memory_human Redis 实际使用内存
内存 maxmemory_human 内存上限
内存 mem_fragmentation_ratio 内存碎片率
淘汰 evicted_keys 被淘汰的 Key 数量
过期 expired_keys 过期删除的 Key 数量
命中率 keyspace_hits / keyspace_misses 缓存命中/未命中
持久化 rdb_last_bgsave_status 最近 RDB 后台保存状态
持久化 aof_last_bgrewrite_status 最近 AOF 重写状态
命令 cmdstat_* 各命令调用次数与耗时统计

缓存命中率可粗略计算：

hit_rate = keyspace_hits / (keyspace_hits + keyspace_misses)

2. 慢日志：SLOWLOG

# 查看慢日志配置
redis-cli CONFIG GET slowlog-log-slower-than
redis-cli CONFIG GET slowlog-max-len

# 查看最近 10 条慢命令
redis-cli SLOWLOG GET 10

# 查看慢日志长度
redis-cli SLOWLOG LEN

# 清空慢日志（生产谨慎，清空前建议先采集）
redis-cli SLOWLOG RESET

常用配置：

# 单位：微秒。10000 表示超过 10ms 的命令会记录到慢日志
slowlog-log-slower-than 10000

# 慢日志最多保存条数
slowlog-max-len 128

慢日志记录的是命令执行耗时，不包含网络传输和客户端排队时间。

3. 延迟诊断：LATENCY

# 开启延迟监控阈值，单位毫秒
redis-cli CONFIG SET latency-monitor-threshold 100

# 查看延迟事件摘要
redis-cli LATENCY LATEST

# 查看某类延迟历史
redis-cli LATENCY HISTORY command

# 诊断延迟问题并给出建议
redis-cli LATENCY DOCTOR

# 生成延迟图
redis-cli LATENCY GRAPH command

常见延迟事件包括：

  • command：命令执行导致延迟。
  • fork：RDB/AOF 重写 fork 子进程导致延迟。
  • aof-write / aof-fsync：AOF 写入或刷盘导致延迟。
  • expire-cycle：过期 Key 清理导致延迟。

4. redis-cli 延迟工具

# 测试当前连接延迟
redis-cli --latency -h 127.0.0.1 -p 6379

# 以更直观的统计方式显示延迟
redis-cli --latency-history -h 127.0.0.1 -p 6379

# 检测内在延迟，通常在 Redis 服务器本机执行
redis-cli --intrinsic-latency 100

说明：

  • --latency 反映客户端到 Redis 的请求响应延迟。
  • --intrinsic-latency 更偏向检查机器本身调度、虚拟化、系统噪声带来的延迟。

5. 命令统计：commandstats

redis-cli INFO commandstats

示例输出片段：

cmdstat_get:calls=100000,usec=35000,usec_per_call=0.35,rejected_calls=0,failed_calls=0
cmdstat_hgetall:calls=2000,usec=600000,usec_per_call=300.00,rejected_calls=0,failed_calls=0

关注：

  • calls：调用次数。
  • usec：总耗时，单位微秒。
  • usec_per_call：单次平均耗时。
  • failed_calls：失败次数，Redis 6+ 相关统计中常见。

6. 采样观察命令：MONITOR

redis-cli MONITOR

MONITOR 会打印 Redis 收到的所有命令，适合短时间排查。生产环境要慎用，因为它会增加 Redis 压力，并可能泄露敏感数据。

7. 内存分析命令

# 查看某个 Key 估算占用内存
redis-cli MEMORY USAGE user:1001

# 查看内存统计
redis-cli MEMORY STATS

# 查看内存碎片信息
redis-cli MEMORY DOCTOR

# 扫描 Key，不要用 KEYS 扫全库
redis-cli --scan --pattern 'user:*'

大 Key 排查示例：

# redis-cli 自带大 Key 扫描，会遍历数据库，生产低峰期执行
redis-cli --bigkeys

# Redis 7.x 中也可以使用 --memkeys 观察内存占用较大的 Key
redis-cli --memkeys

8. 性能测试：redis-benchmark

# 本机简单压测
redis-benchmark -h 127.0.0.1 -p 6379 -n 100000 -c 50

# 测试指定命令
redis-benchmark -t get,set -n 100000 -c 100

# 使用 pipeline
redis-benchmark -t set,get -n 100000 -c 50 -P 16

# 指定 value 大小，单位字节
redis-benchmark -t set,get -n 100000 -d 1024

注意：压测结果只代表特定环境和参数，不等于生产真实性能。

9. 常用优化配置

# 最大内存，建议生产必须设置，避免 Redis 吃满机器内存
maxmemory 4gb

# 淘汰策略，缓存场景常见 allkeys-lru 或 allkeys-lfu
maxmemory-policy allkeys-lru

# 客户端最大连接数
maxclients 10000

# 慢日志阈值，单位微秒
slowlog-log-slower-than 10000
slowlog-max-len 256

# 延迟监控阈值，单位毫秒
latency-monitor-threshold 100

# TCP keepalive，帮助清理异常断开的连接
tcp-keepalive 300

# Redis 6+ 网络 I/O 线程，是否启用要结合压测验证
io-threads 4
io-threads-do-reads yes

io-threads 不是银弹。若瓶颈来自慢命令、大 Key、Lua 脚本或持久化 fork，开启 I/O 线程通常不能根治。

示例

示例 1：定位一次 P99 延迟升高

现象：业务接口偶发从 20ms 升到 500ms，怀疑 Redis 抖动。

排查步骤：

# 1. 看实时延迟
redis-cli --latency-history -h 127.0.0.1 -p 6379

# 2. 看 Redis 延迟事件
redis-cli LATENCY LATEST
redis-cli LATENCY DOCTOR

# 3. 看慢日志
redis-cli SLOWLOG GET 20

# 4. 看命令统计
redis-cli INFO commandstats

# 5. 看持久化状态，确认是否 fork / AOF fsync 抖动
redis-cli INFO persistence

可能结论：

  • SLOWLOG 出现大量 HGETALL big:hash：说明大 Hash 全量读取阻塞。
  • LATENCY LATEST 出现 fork：说明 RDB/AOF 重写时 fork 带来延迟。
  • aof_fsync_delayed_fsync 增长：说明磁盘刷盘压力影响 AOF。

优化动作：

# 将全量 HGETALL 改为按字段读取
HGET user:1001 name
HMGET user:1001 name age level

# 对大集合使用游标分批扫描
HSCAN big:hash 0 COUNT 100

示例 2：用 Pipeline 降低网络往返成本

未使用 Pipeline：

SET k1 v1 -> 等响应
SET k2 v2 -> 等响应
SET k3 v3 -> 等响应

使用 Pipeline：

一次发送多条命令 -> 批量读取响应

Python 伪代码：

pipe = redis_client.pipeline(transaction=False)
for i in range(1000):
    pipe.set(f"batch:{i}", i)
pipe.execute()

适用场景：

  • 批量写入。
  • 批量读取多个独立 Key。
  • 网络 RTT 明显时效果更明显。

注意：

  • Pipeline 批量过大可能造成客户端或 Redis 输出缓冲区压力。
  • 建议按 100～1000 条一批起步，并结合实际 Value 大小压测。

示例 3：排查缓存命中率下降

redis-cli INFO stats | grep -E 'keyspace_hits|keyspace_misses|evicted_keys|expired_keys'
redis-cli INFO memory | grep -E 'used_memory_human|maxmemory_human|mem_fragmentation_ratio'
redis-cli INFO keyspace

可能原因：

  • TTL 设置过短，导致频繁过期。
  • maxmemory 不足，触发大量淘汰。
  • Key 命名不一致，业务读写不是同一批 Key。
  • 缓存穿透：大量请求查询不存在的数据。

优化方向：

  • 为热点缓存设置合理 TTL，并增加随机抖动。
  • 使用空值缓存或布隆过滤器缓解缓存穿透。
  • 评估 maxmemory 与淘汰策略是否匹配业务场景。

示例 4：发现并处理热 Key

现象：Redis CPU 高，但慢日志不明显，某些业务 Key 请求量巨大。

排查方法：

# 短时间观察线上命令，谨慎使用
redis-cli MONITOR

# 如果使用 Redis Cluster，可观察各节点 ops、CPU、网络是否不均衡
redis-cli -c -p 7000 CLUSTER NODES
redis-cli -p 7000 INFO stats

治理方式：

  • 本地缓存：对极热且短期可接受不一致的数据，在应用内缓存几十到几百毫秒。
  • Key 拆分：例如 hot:item:1:{0..N} 多副本分散读压力。
  • 限流降级：对热点接口增加限流、熔断和兜底值。
  • 使用 Redis Cluster 时，确认热点是否集中在单个 slot / 节点。

常见误区

误区 1：Redis 是内存数据库，所以所有命令都很快

错误。Redis 快是因为数据在内存、事件模型简洁、数据结构高效；但 O(N) 命令、大 Key、复杂 Lua 仍可能阻塞主线程。

误区 2：线上排查可以随便执行 KEYS *

错误。KEYS * 会遍历所有 Key，可能阻塞 Redis。生产中优先使用：

redis-cli --scan --pattern 'prefix:*'
SCAN 0 MATCH prefix:* COUNT 100

误区 3：只看平均延迟

平均值会掩盖尾延迟。生产监控应关注：P95、P99、最大延迟、慢日志数量、延迟事件。

误区 4：Pipeline 越大越好

Pipeline 减少 RTT，但批量过大会增加内存、输出缓冲区和单次响应处理压力。应分批压测。

误区 5：内存碎片率高就一定要重启

mem_fragmentation_ratio 高需要结合 used_memory、allocator、业务负载判断。可先观察 MEMORY DOCTOR，必要时评估主动碎片整理配置。

# Redis 4+ 支持，Redis 7.x 可用；是否启用需压测验证 CPU 成本
activedefrag yes

误区 6：开启 I/O 线程就能解决所有性能问题

I/O 线程主要缓解网络读写压力，对慢命令、热 Key、持久化 fork、磁盘 fsync 等问题帮助有限。
