1. C++ 文件和流

1.1 一句话抓本质

文件和流的本质，就是让程序和外部世界交换数据。

基础阶段你已经见过 cin 和 cout，它们是标准输入输出流。到了文件阶段，流的目标从“屏幕”换成了“磁盘文件”。你可以把“流”理解成一条数据管道：数据从一头流进去，从另一头流出来。

1.2 为什么文件很重要

内存里的数据一关闭程序就没了，而文件可以长期保存，所以文件是程序和现实世界之间最常见的“存档方式”。常见用途包括： - 日志记录：保存程序运行过程，方便排错 - 配置文件：把参数放到文件里，方便修改 - 数据导出：把结果写成表格或文本 - 状态保存：程序重启后还能恢复进度

1.3 常见文件流

ifstream  // 读文件
ofstream  // 写文件
fstream   // 读写文件

你可以把它们记成： - ifstream：输入文件流，负责“读” - ofstream：输出文件流，负责“写” - fstream：文件流，读写都能做

1.4 最小读文件示例

#include <iostream>
#include <fstream>
#include <string>
using namespace std;

int main() {
    ifstream fin("input.txt");
    if (!fin.is_open()) {
        cout << "打开文件失败" << endl;
        return 1;
    }

    string line;
    while (getline(fin, line)) {
        cout << line << endl;
    }

    fin.close();
    return 0;
}

这个例子里最值得关注的不是语法，而是思路： 1. 先打开文件 2. 再判断是否成功 3. 成功后逐行读取 4. 结束时关闭文件

1.5 最小写文件示例

#include <iostream>
#include <fstream>
using namespace std;

int main() {
    ofstream fout("output.txt");
    if (!fout.is_open()) {
        cout << "打开输出文件失败" << endl;
        return 1;
    }

    fout << "Hello file" << endl;
    fout << 123 << endl;

    fout.close();
    return 0;
}

写文件时要理解一件事：输出到文件和输出到屏幕很像，区别只是“接收者”不同。cout 的接收者是终端，ofstream 的接收者是磁盘文件。

1.6 读写文件时最关键的习惯

  • 打开前想清楚模式：读、写、还是读写
  • 每次打开后都检查是否成功
  • 用完及时关闭
  • 资源型对象尽量交给作用域管理

如果你把这些习惯养成了，文件相关 bug 会少很多，因为很多问题根本不是“算法错了”，而是“文件没打开成功”或者“模式选错了”。

1.7 文件模式先认识几个常见名字

ios::in     // 读
ios::out    // 写
ios::app    // 追加
ios::ate    // 打开时定位到末尾
ios::binary // 二进制模式

补充理解： - ios::app：每次都写到末尾，适合日志 - ios::ate：一打开就定位到末尾，但你仍然可以重新 seek - ios::binary：按字节处理，不做文本转换

1.8 文本文件与二进制文件

  • 文本文件：按字符/行处理，方便阅读和调试
  • 二进制文件：直接按字节处理，适合图片、音频、结构体数据

初学阶段建议先吃透文本文件，因为它最直观；二进制文件更像“原样搬运”，常常要结合结构体、序列化、平台差异一起理解。

1.9 常用读取方式

（1）按行读

string line;
while (getline(fin, line)) {
    cout << line << endl;
}

适合：文本、日志、配置文件。

（2）按空白分隔读

string word;
while (fin >> word) {
    cout << word << endl;
}

适合：单词、简单数据、标准化输入。

（3）按格式读

int id;
string name;
double score;
fin >> id >> name >> score;

适合：字段固定、结构简单的数据。

1.10 读写文件的工程思维

文件操作不是“会调用函数就行”，而是要考虑： - 文件是否存在 - 路径是否正确 - 权限是否允许 - 数据格式是否稳定 - 读写后是否要刷新缓冲

真正工程里，经常会把“文件打不开”“格式不对”“内容空了”都当成必须处理的分支。

1.11 常见坑

  • 忘记判断 is_open()
  • 路径写错
  • 忘记 close()
  • 读写模式混淆
  • 以为 getline 和 >> 永远可以无脑混用
  • 用二进制方式打开文本文件后发现内容“像乱码”

1.12 记忆口诀

ifstream 负责读，ofstream 负责写，fstream 两边都能来；打开先检查，结束别忘关。

1.13 小练习

  1. 读取一个文本文件并逐行输出。
  2. 把程序输出写到新文件里。
  3. 尝试读取不存在的文件并输出错误。
  4. 用追加模式写一个简单日志文件。

2. C++ 异常处理

2.1 一句话抓本质

异常处理的本质，是把“出错”和“正常流程”分开处理。

程序里最怕的不是出错，而是出错后整段逻辑一起乱掉。异常机制就是为了给错误单独开一条通道，让正常代码保持清晰，让错误处理统一收口。

2.2 为什么要学异常

如果每一步都手动 if 检查，代码会非常碎；异常可以把错误集中到统一位置处理。它最适合处理“当前函数无法继续，但上层可能知道怎么办”的情况。

2.3 基本结构

try {
    // 可能出错的代码
    throw runtime_error("出错了");
} catch (const exception& e) {
    cout << e.what() << endl;
}

它的执行逻辑是： - try 中运行正常逻辑 - 一旦 throw，程序立即跳到匹配的 catch - catch 负责收尾、记录、恢复或终止

2.4 throw / catch / try

  • try：包住可能出问题的代码
  • throw：抛出异常
  • catch：捕获并处理异常

可以把它们想成： - try 是“试运行区” - throw 是“报警” - catch 是“应急处理室”

2.5 常见异常类型

#include <stdexcept>
throw runtime_error("运行时错误");
throw invalid_argument("参数不合法");
throw out_of_range("越界");

这些异常名字本身就很有帮助： - runtime_error：运行时出现问题 - invalid_argument：传入参数不合理 - out_of_range：访问越界

2.6 自定义异常

你也可以自己定义异常类型，适合项目里做统一错误管理。

#include <iostream>
#include <exception>
using namespace std;

class MyException : public exception {
public:
    const char* what() const noexcept override {
        return "自定义异常";
    }
};

自定义异常适合： - 统一项目错误风格 - 让错误信息更业务化 - 让上层更容易判断具体问题

2.7 异常处理的思维方式

  • 正常流程尽量清晰
  • 只有真的“不可继续”或“必须交给上层处理”的情况才抛异常
  • 不要用异常代替正常判断
  • 不要让异常变成“万能跳转”

很多新手会把异常当成“if 的替代品”，其实这是反过来的：异常是给少数真正非正常情况准备的。

2.8 捕获方式要注意

try {
    // code
}
catch (const out_of_range& e) {
    cout << e.what() << endl;
}
catch (const exception& e) {
    cout << e.what() << endl;
}

建议： 1. 先抓具体异常 2. 再用更通用的基类兜底 3. 避免只写 catch(...) 却不分析问题

2.9 常见坑

  • 捕获类型不对
  • 只 catch(...) 不分析错误
  • 乱抛异常，把异常当流程控制
  • 异常对象写得太复杂，反而不好定位问题
  • 析构函数里随便抛异常，导致更难收拾

2.10 记忆口诀

有风险的代码放 try，真正出错就 throw；catch 负责收尾，别让程序直接崩。

2.11 小练习

  1. 写一个除法函数，分母为 0 时抛异常。
  2. 捕获异常并输出错误信息。
  3. 比较“异常方式”和“返回错误码方式”的差别。
  4. 为一个数组访问函数设计越界异常。

3. C++ 动态内存

3.1 一句话抓本质

动态内存的本质，是程序运行时再向系统申请空间。

当你运行前不知道到底要多大空间时，就要用动态内存。它的核心价值是灵活，但代价是：你必须自己负责申请和释放。

3.2 为什么要学动态内存

静态变量、栈空间虽然方便，但大小和生命周期受限。动态内存常用于： - 大小运行时才知道的数据 - 生命周期需要跨函数保存的数据 - 需要手动控制释放时机的数据

3.3 new 和 delete

int* p = new int(10);
cout << *p << endl;
delete p;
p = nullptr;

new 做了两件事： 1. 申请内存 2. 调用构造或初始化

delete 做了两件事： 1. 释放内存 2. 结束对象生命周期

3.4 数组动态分配

int* arr = new int[5];
for (int i = 0; i < 5; i++) {
    arr[i] = i;
}
delete[] arr;
arr = nullptr;

这里最关键的是： - 单个对象用 new / delete - 数组对象用 new[] / delete[]

3.5 为什么要成对释放

  • new 对应 delete
  • new[] 对应 delete[]

如果写错，结果可能很危险。因为数组对象和单对象的释放方式不一样，运行时可能只释放了一部分信息，或者破坏了内存管理结构。

3.6 三种经典问题

  • 内存泄漏：申请后忘记释放
  • 悬空指针：释放后继续使用旧地址
  • 野指针：根本没初始化就拿来用

这三个问题经常一起出现。很多 bug 不是“内存太少”，而是“内存生命周期管理失控”。

3.7 更安全的写法习惯

int* p = new int(10);
// 使用...
delete p;
p = nullptr;

释放后置空的意义是： - 避免继续误用旧地址 - 让“已经释放”这件事更显眼 - 方便后续判空

3.8 现代 C++ 的趋势

更现代的代码更喜欢用： - 智能指针 - 容器 - RAII

也就是说，尽量让资源“跟着对象生命周期自动管理”。如果能不用裸 new，通常就尽量不用。

3.9 RAII 可以怎么理解

RAII 的意思是：资源在对象构造时获取，在对象析构时释放。这样资源不需要你手动盯着，离开作用域就自动回收。

这是现代 C++ 最重要的思想之一：把“会忘记的资源释放”变成“不会忘记的对象析构”。

3.10 常见坑

  • new[] 配 delete
  • new 配 delete[]
  • 释放后没置空
  • 以为内存回收一定“自动帮你兜底”
  • 多个指针同时指向同一块内存，却不知道谁负责释放

3.11 记忆口诀

申请要负责，释放要成对；删完记清零，别拿旧地址再用。

3.12 小练习

  1. 动态创建一个整型变量并修改它。
  2. 动态创建一个 10 个元素的数组。
  3. 故意制造一次泄漏，观察为什么危险。
  4. 尝试把动态数组改成 vector 管理。

4. C++ 命名空间

4.1 一句话抓本质

命名空间的本质，是给名字加“分区”，避免重名冲突。

当项目变大、库变多时，名字冲突非常常见。命名空间就是 C++ 的“区域隔离”。它不是为了“炫技”，而是为了让大型程序中的名字有秩序。

4.2 为什么需要命名空间

如果两个库都叫 print()，编译器怎么知道你要用哪一个？命名空间就是答案。它把“名字”放到不同的盒子里，告诉编译器：你要去哪个盒子里找。

4.3 基本写法

namespace A {
    void print() {
        cout << "A" << endl;
    }
}

namespace B {
    void print() {
        cout << "B" << endl;
    }
}

调用时：

A::print();
B::print();

4.4 :: 的含义

:: 可以理解成“范围限定符”。它告诉编译器：这个名字不是随便找，而是去某个明确范围里找。

常见用法： - std::cout - A::print() - ::global_name

4.5 using namespace 的取舍

using namespace std;

优点：写起来短。缺点：在大项目里容易污染名字空间。

更稳妥的方式是： - 小代码、教学代码可以适当使用 - 生产代码尽量显式写前缀

4.6 匿名命名空间

匿名命名空间常用于当前文件内部私有化名字。

namespace {
    int helper() {
        return 42;
    }
}

它的作用很像“只在当前文件可见的内部工具区”。

4.7 命名空间的实际价值

命名空间最常见的场景就是： - 项目模块分层 - 第三方库隔离 - 解决重名函数、类、变量 - 让代码的来源一眼可见

4.8 常见坑

  • 直接全局 using namespace 滥用
  • 不知道某个名字到底从哪来
  • 跨文件维护时名字冲突越来越多
  • 过度嵌套命名空间，导致调用路径太长

4.9 记忆口诀

命名空间像文件夹，名字先分区，再按路径找。

4.10 小练习

  1. 定义两个命名空间，各写一个同名函数。
  2. 用 :: 和命名空间前缀调用它们。
  3. 把一个工具函数放进匿名命名空间里。

5. C++ 模板

5.1 一句话抓本质

模板的本质，是把“类型”也交给编译器帮你参数化。

以前我们把值当参数，模板则进一步把“类型”也变成参数。它解决的问题很简单：如果逻辑一样，只是数据类型不同，那就写一份代码就够了。

5.2 为什么模板很重要

如果一个函数、一个类只差在“类型不同”，那就没必要写很多重复版本。模板让代码更通用，也更不容易重复出错。

5.3 函数模板

template<typename T>
T add(T a, T b) {
    return a + b;
}

调用：

cout << add(1, 2) << endl;
cout << add(1.5, 2.5) << endl;

这里的好处是：同一个 add，可以用于整数、浮点数，甚至自定义类型（只要支持 +）。

5.4 类模板

template<typename T>
class Box {
public:
    T value;
    Box(T v) : value(v) {}
};

类模板适合做“通用容器”或“通用工具类”。你可以把它理解成一个类的“类型版本参数”。

5.5 模板参数的理解方式

模板里最常见的是类型参数：

template<typename T>

但模板也可以接收非类型参数，比如数组长度：

template<typename T, int N>

这说明模板不仅能抽象“类型”，也能抽象“编译期常量”。

5.6 类型推导

调用函数模板时，编译器常常可以根据参数自动推导类型，这也是模板很方便的原因。

不过也要注意： - 参数类型不一致时，可能推导失败 - 有时需要手动指定模板参数

5.7 模板和编译期

模板大多是在编译期展开和实例化的，所以错误信息往往会很长、很复杂。模板出错并不代表运行时出了问题，而通常是“编译器在帮你生成代码时发现不合理”。

5.8 适合用模板的场景

  • 容器类：保存任意类型数据
  • 算法函数：对任意类型执行同样逻辑
  • 工具组件：对多种类型复用一套实现

5.9 常见坑

  • 以为模板是运行时机制，其实主要是编译期展开
  • 模板参数推导失败
  • 只会用，不知道模板怎么减少重复代码
  • 模板过度复杂，导致可读性变差

5.10 记忆口诀

模板先写样板，类型交给编译；一份代码，多种类型都能用。

5.11 小练习

  1. 写一个模板函数求两个值的最大值。
  2. 写一个模板类保存一对数据。
  3. 写一个带数组长度参数的模板。

6. C++ 预处理器

6.1 一句话抓本质

预处理器是在编译之前先做文本级处理。

它不是“运行时逻辑”，而是编译前的准备步骤。你可以把它理解成“代码进入编译器前，先做一次机械替换和筛选”。

6.2 常见指令

#include
#define
#ifdef
#ifndef
#if
#endif

6.3 预处理器最常见的用途

  • 引入头文件
  • 定义宏常量
  • 控制条件编译
  • 根据不同平台/环境切换代码

6.4 宏定义

#define PI 3.14159

宏本质上是文本替换，不是变量。

#define SQUARE(x) ((x) * (x))

这个例子说明：宏虽然方便，但一定要加括号，不然容易出错。

6.5 条件编译

#ifdef DEBUG
cout << "debug mode" << endl;
#endif

条件编译适合： - 调试输出 - 平台区分 - 功能开关 - 临时代码屏蔽

6.6 预处理器的优点

  • 统一配置
  • 简化重复代码
  • 控制不同编译环境的行为
  • 让某些代码在特定环境下完全不参与编译

6.7 预处理器和函数的区别

宏和函数很像，但本质不同： - 宏：编译前文本替换，没有类型检查 - 函数：真正的语言实体，有类型检查

因此，能用函数就尽量用函数，宏只在确实需要时再用。

6.8 常见坑

  • 宏没有类型检查
  • 宏展开后出错难查
  • 条件编译过多，代码碎片化
  • 宏参数没加括号，运算优先级出问题
  • 头文件保护没做好，导致重复包含

6.9 头文件保护

常见写法：

#ifndef MY_HEADER_H
#define MY_HEADER_H

// 内容

#endif

它的作用是防止头文件被重复包含，避免重复定义错误。

6.10 记忆口诀

预处理先展开，宏像文本替换；条件编译很方便，但别让代码太魔法。

6.11 小练习

  1. 用宏定义一个圆周率。
  2. 用条件编译控制调试输出。
  3. 给一个头文件加上保护宏。

7. C++ 信号处理

7.1 一句话抓本质

信号处理是在程序收到系统事件时做出响应。

它更偏底层和系统交互，初学阶段先认识概念和基本用途即可。信号不是普通函数调用，而是一种“外部通知”。

7.2 常见信号

  • SIGINT：通常是 Ctrl+C
  • SIGTERM：终止信号
  • SIGABRT：异常终止

7.3 基本思路

#include <csignal>
#include <iostream>
using namespace std;

void handler(int signum) {
    cout << "收到信号：" << signum << endl;
}

然后把它注册成处理函数：

signal(SIGINT, handler);

7.4 信号处理的作用

信号处理常用于： - 优雅退出程序 - 清理临时资源 - 处理中断请求 - 响应系统状态变化

你可以把它理解成：程序运行过程中，外界拍了拍你，说“先别往下跑了，处理一下这个事件”。

7.5 信号处理函数的限制

信号处理函数里不要做太复杂的事，因为它不是普通业务逻辑。很多系统级函数在信号上下文里并不安全，所以更稳妥的做法是： - 只做轻量标记 - 或者设置一个停止标志 - 然后由主流程去做真正清理

7.6 典型思路

#include <csignal>
#include <iostream>
using namespace std;

volatile sig_atomic_t stopFlag = 0;

void handler(int) {
    stopFlag = 1;
}

int main() {
    signal(SIGINT, handler);
    while (!stopFlag) {
        cout << "working..." << endl;
    }
    cout << "exit gracefully" << endl;
}

这个模式很常见：信号处理函数只负责发信号，主循环负责真正收尾。

7.7 常见坑

  • 信号处理函数里做太复杂的事
  • 对信号的触发场景不了解
  • 误以为信号和普通异常一样
  • 没考虑退出时资源清理

7.8 记忆口诀

信号像外部提醒，处理函数来接收；别把它想太复杂，先知道它会打断程序。

7.9 小练习

  1. 写一个简单的信号处理器。
  2. 观察 Ctrl+C 时程序的行为。
  3. 用标志位实现“收到信号后优雅退出”。

8. C++ 多线程

8.1 一句话抓本质

多线程的本质，是让程序同时处理多个任务。

它适合： - 耗时任务 - 希望提升响应速度 - 任务彼此可以并行处理

8.2 为什么要学多线程

单线程程序像一个人排队做所有事；多线程则像同时安排多个工位。只要任务之间没有强依赖，就可以把工作拆开，提高吞吐量和响应速度。

8.3 基本写法

#include <thread>
#include <iostream>
using namespace std;

void work() {
    cout << "thread working" << endl;
}

8.4 启动和等待

thread t(work);
t.join();
  • thread t(work);：启动线程执行 work
  • join()：等待子线程结束

如果不 join()，线程对象析构时可能触发程序错误，因此“启动之后记得收尾”非常关键。

8.5 join 和 detach

  • join()：主线程等它结束
  • detach()：放手让线程自己跑

一般来说，新手更建议先掌握 join()，因为它更可控。detach() 虽然方便，但一旦共享资源处理不好，就更容易出问题。

8.6 多线程最常见问题

  • 数据竞争
  • 死锁
  • 资源同步复杂
  • 多线程调试困难

多线程最大的问题不是“怎么开线程”，而是“多个线程同时访问同一份数据时怎么办”。

8.7 互斥和同步的直觉

如果多个线程要改同一份数据，就要想办法让它们“轮流来”，而不是“同时乱改”。这就是互斥锁、条件变量等机制存在的原因。

8.8 一个简单的线程示例

#include <iostream>
#include <thread>
using namespace std;

void printNum(int n) {
    cout << "n = " << n << endl;
}

int main() {
    thread t1(printNum, 10);
    thread t2(printNum, 20);

    t1.join();
    t2.join();
    return 0;
}

8.9 常见坑

  • 启动线程后忘记 join() 或 detach()
  • 多线程同时写共享变量
  • 以为线程越多越快
  • 忽略锁的粒度，导致性能变差或死锁

8.10 记忆口诀

开线程很容易，管共享才是难题；先会 join，再学互斥。

8.11 小练习

  1. 启动一个线程打印信息。
  2. 让主线程等待子线程结束。
  3. 做一个两个线程分别输出不同内容的小程序。

9. C++ Web 编程

9.1 一句话抓本质

Web 编程就是让 C++ 程序和网络、浏览器、服务器进行通信。

C++ 在 Web 场景里通常更偏后端、网络服务、高性能模块。它不一定是最容易上手的 Web 语言，但在高性能、底层控制、服务性能要求高的场景里很有价值。

9.2 常见方向

  • HTTP 服务
  • 网络请求
  • 服务器编程
  • 高性能中间件
  • 网关或底层组件

9.3 初学阶段要记住

Web 编程通常离不开： - 文件 - 网络 - 多线程 - 数据库 - JSON / 协议

所以它不是单独一章就能“精通”的内容，而是前面很多知识的组合应用。学 Web 时，最重要的不是背框架，而是先理解请求、响应、连接、并发这些基础概念。

9.4 Web 的核心概念

  • 请求：客户端发给服务器的数据
  • 响应：服务器返回给客户端的数据
  • HTTP：最常见的应用层协议
  • 路由：不同 URL 对应不同处理逻辑
  • 状态码：告诉客户端结果是成功、失败还是重定向

9.5 为什么 C++ 也能做 Web

虽然很多人学 Web 会先接触脚本语言，但 C++ 仍然很重要，因为它适合： - 对性能要求高的服务 - 高频网络处理 - 资源控制严格的系统 - 与底层模块深度结合的场景

9.6 一个 Web 学习路径

如果你以后想把 C++ 用到 Web 上，建议按这个顺序理解： 1. 先会读写文件 2. 再理解网络 socket 3. 再理解 HTTP 协议 4. 再结合多线程做并发处理 5. 最后再看框架和工程化封装

9.7 一个简单认知示例

你可以先把 Web 服务想象成这样的流程：

浏览器发请求 -> 服务器解析请求 -> 执行业务逻辑 -> 返回响应 -> 浏览器展示结果

这背后虽然细节很多，但本质就是“收请求、做处理、回结果”。

9.8 常见坑

  • 不了解 HTTP 基本概念就直接看框架
  • 混淆请求和响应
  • 忽略并发和线程安全
  • 忽略协议、编码、异常处理
  • 只会“跑通示例”，不理解真实通信流程

9.9 记忆口诀

Web 不是单点技能，而是基础知识的组合题。

9.10 小练习

  1. 了解 HTTP 请求和响应的基本概念。
  2. 试着看懂一个简单的 C++ 网络服务示例。
  3. 画出一次浏览器访问服务器的完整流程图。

复习小抄

  • 文件和流：让程序和文件交换数据
  • 异常处理：把错误和正常流程分开
  • 动态内存：运行时申请空间，记得成对释放
  • 命名空间：给名字分区，避免冲突
  • 模板：让类型也能参数化
  • 预处理器：编译前的文本处理
  • 信号处理：响应系统事件
  • 多线程：并行处理任务
  • Web 编程：网络与服务的组合应用

学习建议

高级内容不要死背定义，最好按这条线理解： 基础语法 → 类/对象 → 文件/异常/内存 → 线程/网络 → 工程化写法。

当你能把每章和真实场景对应起来时，高级教程才真正开始“有用”。
