Kubernetes 基础：声明式部署与服务编排

学习目标

  • 理解 Kubernetes 中 Pod、Deployment、Service、ConfigMap、Secret、Ingress 的关系。
  • 能读写基本 YAML，并使用 kubectl 查看资源状态和事件。
  • 能理解滚动更新、健康检查、资源限制和配置注入。
  • 能识别把服务部署到生产集群前必须补齐的安全和可靠性设置。

核心概念

Kubernetes 是声明式编排系统。你提交期望状态，控制器持续把实际状态调整到期望状态。Pod 是最小调度单元，通常包含一个主容器和少量辅助容器。

Deployment 管理一组 Pod 副本，负责滚动更新和回滚。Service 为一组 Pod 提供稳定访问入口，因为 Pod IP 会变化。ConfigMap 存放非敏感配置，Secret 存放敏感配置，但默认不等于完整加密方案，生产环境要结合 KMS、RBAC 和审计。

Ingress 描述外部 HTTP/HTTPS 流量如何进入集群，实际转发由 Ingress Controller 实现，例如 Nginx Ingress Controller、Traefik 或云厂商负载均衡器。

示例

Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: user-api
  template:
    metadata:
      labels:
        app: user-api
    spec:
      containers:
        - name: api
          image: registry.example.com/user-api:1.2.3@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: user-api-config
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 20
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"

Service

apiVersion: v1
kind: Service
metadata:
  name: user-api
spec:
  selector:
    app: user-api
  ports:
    - port: 80
      targetPort: 8080

生产注意事项：生产 Deployment 应设置资源 requests/limits、readiness/liveness probe、PodDisruptionBudget、镜像 digest 或不可覆盖 tag、最小权限 ServiceAccount、NetworkPolicy 和合理的副本数。不要把数据库当作普通无状态 Deployment 直接裸跑，除非明确设计了持久化、备份和恢复。

典型工作流

  1. 构建并推送镜像到 Registry，记录 digest 或不可覆盖 tag。
  2. 编写 ConfigMap、Secret、Deployment、Service 和 Ingress。
  3. kubectl apply -f 提交资源。
  4. 用 kubectl get pods、kubectl describe pod、kubectl logs 观察状态。
  5. 修改镜像版本触发滚动更新，观察新旧 Pod 替换。
  6. 如果发布异常，使用 kubectl rollout undo deployment/user-api 回滚。

常见坑

  • 只配置 livenessProbe，不配置 readinessProbe，导致未准备好的 Pod 接收流量。
  • selector 标签写错，Service 找不到 Pod。
  • 没有资源限制，服务异常时影响同节点其他工作负载。
  • 把 Secret 当成绝对安全存储，忽略 RBAC、审计和加密配置。
  • 镜像拉取策略和可变 tag 不匹配，集群实际运行旧镜像或不可追溯镜像。
  • 应用启动慢但探针过早触发，造成反复重启。

排障步骤

  1. kubectl get pods -o wide 查看 Pod 状态、节点和重启次数。
  2. kubectl describe pod <pod> 查看调度失败、镜像拉取失败、探针失败等事件。
  3. kubectl logs <pod> --previous 查看上一次崩溃前日志。
  4. kubectl get endpoints <service> 确认 Service 是否匹配到 Pod。
  5. kubectl rollout status deployment/<name> 查看发布进度。
  6. 对网络问题检查 DNS、Service 名称、端口、NetworkPolicy 和 Ingress Controller 日志。

练习

  1. 用 kind 或 minikube 部署一个 HTTP 服务，暴露为 Service。
  2. 给服务增加 readinessProbe，并制造启动延迟观察流量切换。
  3. 修改镜像 tag 触发滚动更新，再执行回滚。
  4. 故意写错 Service selector，使用 kubectl get endpoints 定位问题。

检查清单

  • Deployment、Service、ConfigMap、Secret 职责分离明确。
  • Service selector 与 Pod label 一致。
  • readinessProbe、livenessProbe 和资源限制已配置。
  • 镜像版本使用 digest 或不可覆盖 tag，可追溯且可回滚。
  • 排障时会查看状态、事件、日志、端点和 rollout 状态。

前置知识与完成标准

前置知识：会使用 Docker 镜像；理解 YAML、HTTP 健康检查、端口、环境变量；知道服务实例可能随时重启、迁移或扩缩容。

完成标准：

  • 能解释 API Server、etcd、controller、scheduler、kubelet 与容器运行时的协作。
  • 能说明 Deployment 如何通过 ReplicaSet 管理 Pod，并用 Service 提供稳定访问入口。
  • 能配置 readiness、liveness、startup probe，理解各自失败后的动作。
  • 能使用 kubectl get/describe/logs/events/rollout 定位 Pending、CrashLoopBackOff、ImagePullBackOff、探针失败和 Service 无端点。

对象协调循环与生命周期

Kubernetes 的核心不是“执行一次命令”，而是控制循环。用户把期望状态提交到 API Server，状态保存在 etcd；Deployment controller 发现需要 ReplicaSet，ReplicaSet controller 发现需要 Pod；scheduler 为未绑定节点的 Pod 选择节点；目标节点上的 kubelet 拉取镜像、创建容器并持续汇报状态。

组件关系可以简化为：

kubectl/apply
  -> API Server
  -> etcd 保存期望状态
  -> controllers 创建/修正 Deployment、ReplicaSet、Pod
  -> scheduler 绑定 Pod 到 Node
  -> kubelet 调用容器运行时启动容器
  -> Service/EndpointSlice 根据 label 暴露就绪 Pod

Deployment 的滚动升级本质是逐步扩大新 ReplicaSet、缩小旧 ReplicaSet。maxSurge 控制最多额外创建多少新 Pod，maxUnavailable 控制升级期间最多允许多少 Pod 不可用。readiness 失败的 Pod 不进入服务端点；liveness 失败会被 kubelet 重启；startup probe 给慢启动应用争取初始化时间，成功前会抑制其他探针。

调度不是看实时 CPU 使用率，而是主要根据资源 request、节点容量、亲和性、污点容忍、拓扑约束等做放置决策。limits 则由 kubelet 和容器运行时交给内核 cgroup 执行，内存超限通常导致 OOMKilled，CPU 超限通常表现为被限速而不是杀进程。

从零可复现实验

目标：用 kind 或 minikube 部署 HTTP 服务，观察 Service 端点、探针和滚动更新。

  1. 准备本地集群：
kind create cluster --name delivery-demo
kubectl cluster-info
  1. 保存 demo.yaml：
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
  1. 应用并验证：
kubectl apply -f demo.yaml
kubectl rollout status deployment/web
kubectl get pods -l app=web -o wide
kubectl get endpoints web
kubectl port-forward service/web 8080:80
curl -i http://127.0.0.1:8080/

预期结果：Deployment 可用，Service 有端点，curl 返回 Nginx 页面。失败现象：Pending 多为资源或调度约束；ImagePullBackOff 多为镜像名、网络或凭据；CrashLoopBackOff 多为进程退出；Service 空端点多为 label selector 或 readiness 失败。

配置与命令逐段讲解

selector:
  matchLabels:
    app: user-api
template:
  metadata:
    labels:
      app: user-api

selector 是控制器选择 Pod 的条件，template.metadata.labels 是新建 Pod 的标签。二者必须匹配；Deployment 创建后 selector 通常不可随意变更，避免控制器接管错误 Pod。

readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  failureThreshold: 30
  periodSeconds: 2

readiness 回答“能否接流量”，liveness 回答“是否需要重启”，startup 回答“是否还在启动窗口”。不要把依赖数据库短暂失败直接等同于 liveness 失败，否则会把可恢复的下游故障放大成重启风暴。

kubectl describe pod <pod>
kubectl logs <pod> --previous
kubectl events --for pod/<pod>
kubectl rollout undo deployment/user-api

describe 看调度、拉镜像、探针等事件；logs --previous 看上一次崩溃前日志；events 适合按对象追踪近期事件；rollout undo 回到上一版 ReplicaSet，但前提是旧镜像仍可拉取、数据库迁移仍兼容。

教学配置与生产配置边界

教学集群可以使用 kind/minikube、默认命名空间、NodePort 或 port-forward、简单 Secret。生产集群应拆命名空间、RBAC、NetworkPolicy、PodDisruptionBudget、ResourceQuota、LimitRange、镜像准入、审计日志和 Secret 加密；公网入口应由 Ingress Controller 或云负载均衡统一治理。

教学中可用单个 YAML 展示对象关系；生产中通常使用 Helm、Kustomize 或 GitOps 管理环境差异。教学中可直接 kubectl apply；生产发布应走 CI/CD、审批、回滚记录和可观测性验证。

排障决策树

Kubernetes 发布异常
├─ Pod Pending？
│  ├─ 是：看 describe 的 FailedScheduling、requests、节点污点、PVC
│  └─ 否：继续
├─ ImagePullBackOff？
│  ├─ 是：检查镜像名、tag/digest、Registry 凭据、节点网络
│  └─ 否：继续
├─ CrashLoopBackOff？
│  ├─ 是：看 logs --previous、启动命令、配置、Secret、依赖连接
│  └─ 否：继续
├─ Service 无法访问？
│  ├─ endpoints 为空：检查 selector、label、readiness
│  └─ endpoints 正常：检查端口、DNS、NetworkPolicy、Ingress
└─ rollout 卡住？
   ├─ 新 Pod 未就绪：看探针、资源、应用日志
   └─ 指标异常：暂停发布或回滚，保留事件和日志

练习与答案要点

基础练习：故意把 Service selector 写成 app: wrong，观察 kubectl get endpoints web。答案要点：Pod 正常但 Service 无端点；修复 selector 后端点出现。

进阶练习：给慢启动服务配置 startupProbe，再比较只有 livenessProbe 时的重启次数。答案要点：startup 成功前 liveness 不执行；慢启动不应被误杀。

综合练习：配置 Deployment 的 maxSurge: 1、maxUnavailable: 0，发布新镜像并模拟新版本 readiness 失败。答案要点：旧 Pod 保持服务；rollout 不完成；可用 rollout undo 回滚；监控应能看到新 ReplicaSet 未就绪。

小结与官方延伸阅读

Kubernetes 通过声明式对象和控制循环持续修正实际状态。学习重点不是背 YAML 字段，而是理解控制器、调度、探针、资源和网络对象如何共同决定一个服务能否稳定接收流量。
