学习目标

  • 理解镜像、容器、Dockerfile、Registry、Volume、Network 的职责。
  • 能为后端服务编写可读、可缓存、体积合理的 Dockerfile。
  • 能用 Docker Compose 在本地组织服务、数据库和缓存。
  • 能识别生产使用 Docker 时的安全、配置和可观测性注意事项。

核心概念

镜像是不可变的运行包，包含程序、依赖、运行时和默认配置。容器是镜像的运行实例。Dockerfile 描述如何构建镜像，Registry 用来存储和分发镜像。

镜像层会被缓存，稳定且变化少的步骤应放在前面，例如安装系统依赖、复制依赖清单；变化频繁的源码复制放在后面。这样能减少重复构建时间。

容器应尽量无状态。业务数据放在数据库、对象存储或挂载卷中，日志输出到 stdout/stderr，由平台采集。配置通过环境变量、配置文件挂载或平台 Secret 注入。

示例

Python 服务 Dockerfile

FROM python:3.12-slim AS runtime

WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd --create-home --shell /usr/sbin/nologin appuser
USER appuser

EXPOSE 8080
CMD ["python", "-m", "my_service"]

C++ 多阶段构建

FROM ubuntu:24.04 AS build
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential cmake ninja-build ca-certificates \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /src
COPY . .
RUN cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
RUN cmake --build build

FROM ubuntu:24.04 AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=build /src/build/my_service /app/my_service
RUN useradd --create-home --shell /usr/sbin/nologin appuser
USER appuser
EXPOSE 8080
CMD ["/app/my_service"]

生产注意事项：不要把编译工具链、测试数据、源码缓存和密钥留在运行镜像里；使用固定基础镜像版本，定期扫描漏洞；容器进程不要用 root；镜像标签除 latest 外应包含 Git SHA 或版本号。

Docker Compose（仅本地演示）

下面示例只用于本地开发和教学演示，便于快速启动 API 与 PostgreSQL。本地密码可放在不提交到版本库的 .env 中；生产或共享测试环境不要使用明文密码、默认弱密码或直接提交的连接串，应改用平台 Secret、外部密钥管理、最小权限账号和独立的配置注入流程。

services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      DATABASE_URL: postgres://app:${POSTGRES_PASSWORD:?set local POSTGRES_PASSWORD}@db:5432/app
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set local POSTGRES_PASSWORD}
      POSTGRES_DB: app
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      timeout: 3s
      retries: 10

典型工作流

  1. 写 .dockerignore，排除 .git、构建产物、缓存、测试报告和本地配置。
  2. 编写 Dockerfile，把依赖安装和源码复制分层处理。
  3. 本地 docker build 构建镜像，用版本号或提交 SHA 打标签。
  4. docker run 或 Compose 启动服务，检查端口、环境变量和日志。
  5. 在 CI 中构建、测试、扫描并推送镜像到 Registry。
  6. 在部署平台按镜像 digest 或不可变 tag 发布，保留回滚版本。

常见坑

  • 把密钥写入 Dockerfile 或构建参数，最终进入镜像历史。
  • 把本地 Compose 示例原样搬到共享环境，导致明文密码、默认账号或测试数据泄漏。
  • 使用 latest 部署生产，导致无法确定实际运行版本。
  • 容器内写本地文件保存业务状态，重启或迁移后数据丢失。
  • .dockerignore 缺失，导致构建上下文巨大且泄漏本地文件。
  • 只使用 depends_on，误以为数据库已经可用；应配合健康检查和重试。
  • 镜像内时区、证书、glibc/musl 差异导致线上行为与本地不同。

排障步骤

  1. docker build --no-cache 判断是否为缓存问题。
  2. docker image history 检查镜像层大小和是否包含异常文件。
  3. docker logs 查看容器启动失败、端口绑定和配置读取错误。
  4. docker exec 进入容器检查文件路径、用户权限、证书和 DNS。
  5. docker inspect 查看环境变量、网络、挂载和健康检查状态。
  6. 若服务间访问失败，确认使用 Compose 服务名而不是 localhost。

练习

  1. 为一个 Python API 写 Dockerfile，并用非 root 用户启动。
  2. 为一个 C++ CMake 项目写多阶段构建，比较单阶段和多阶段镜像大小。
  3. 写 .dockerignore，观察构建上下文大小变化。
  4. 用 Compose 启动 API + PostgreSQL，并给 API 增加连接重试。

检查清单

  • Dockerfile 层顺序利于缓存，运行镜像不包含无关构建依赖。
  • 镜像标签可追溯到源代码版本，生产不依赖 latest。
  • 容器以非 root 用户运行，密钥不进入镜像。
  • 日志输出到 stdout/stderr，配置来自环境或挂载。
  • 本地 Compose 能复现依赖，健康检查和重试机制明确。

前置知识与完成标准

前置知识：了解 Linux 进程、端口、文件系统、环境变量和基本网络访问；能读 Dockerfile、YAML 和 shell 命令；知道镜像构建和容器运行是两个阶段。

完成标准：

  • 能说明镜像层、容器可写层、Volume 和 bind mount 的差异。
  • 能解释 namespace 提供隔离、cgroup 提供资源约束，二者不等于虚拟机。
  • 能从零构建一个最小 HTTP 服务镜像，并用日志、端口和 inspect 验证运行状态。
  • 能区分教学 Compose 与生产容器平台在密钥、网络、存储和安全上的边界。

镜像层、运行时与组件关系

Dockerfile 每条会改变文件系统的指令通常生成一层镜像层。镜像层只读，可被多个镜像和容器复用；容器启动后会叠加一个可写层，容器内临时写入默认落在这里。容器删除后，可写层随之消失，所以业务数据应进入 Volume、外部数据库或对象存储。

运行链路可以理解为：Docker CLI -> Docker daemon/containerd -> 镜像存储 -> 容器运行时 -> Linux kernel。namespace 隔离 PID、网络、挂载点、用户等视图；cgroup 限制和统计 CPU、内存、IO 等资源；capabilities、seccomp、AppArmor/SELinux 再收窄进程能做的系统调用和权限。

Docker 网络默认常见是 bridge：容器有自己的网络命名空间，通过虚拟网卡接入宿主机 bridge，再由 NAT 或端口映射对外访问。Compose 服务之间应使用服务名访问，例如 http://api:8080 或 db:5432；容器内的 localhost 指向容器自己，不是宿主机也不是另一个服务。

存储要分三类：镜像层保存发布内容；容器可写层保存临时运行变化；Volume 保存需要跨重启保留的数据。bind mount 适合本地开发同步源码，生产更偏向 Volume、CSI、对象存储或数据库。

从零可复现实验

目标：观察镜像层缓存、端口映射、容器可写层和 Volume 差异。

  1. 创建空目录并写入 app.py：
from http.server import BaseHTTPRequestHandler, HTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"hello docker\n")

HTTPServer(("0.0.0.0", 8080), Handler).serve_forever()
  1. 写入 Dockerfile：
FROM python:3.12-slim
WORKDIR /app
COPY app.py .
USER 65532:65532
EXPOSE 8080
CMD ["python", "app.py"]
  1. 构建、运行、验证：
docker build -t hello-docker:demo .
docker run --rm -p 8080:8080 hello-docker:demo
curl -i http://127.0.0.1:8080/

预期结果：curl 返回 200 和 hello docker。失败现象包括端口被占用、镜像拉取失败、容器立即退出、curl 连接拒绝。验证方法：docker logs <container> 看应用日志，docker ps 看端口映射，docker inspect 看用户、网络、挂载和环境变量。

配置与命令逐段讲解

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER appuser
CMD ["python", "-m", "my_service"]
  • FROM 选择基础镜像，也是后续层的起点；生产应固定主版本并定期升级。
  • WORKDIR 设置后续命令目录，减少路径错误。
  • 先复制依赖清单再安装依赖，可复用缓存；源码变化不必重装依赖。
  • RUN 在构建阶段执行并写入新层；不要在这里写入密钥。
  • COPY . . 会把构建上下文复制进镜像，必须配合 .dockerignore。
  • USER 降低容器进程权限；生产还应配合只读根文件系统和能力裁剪。
  • CMD 是默认启动命令，可被 docker run 的命令覆盖。
docker run --rm --name api -p 8080:8080 --memory 256m --cpus 0.5 hello-docker:demo
  • --rm 退出后删除容器，适合实验；生产应由平台负责生命周期。
  • --name 便于 logs、inspect 和 exec 定位。
  • -p 8080:8080 把宿主机端口映射到容器端口，和 Dockerfile 的 EXPOSE 不是一回事。
  • --memory 和 --cpus 通过 cgroup 限制资源，能提前暴露 OOM 或 CPU 饥饿问题。

教学配置与生产配置边界

教学环境可用 latest 快速拉镜像、用 Compose 明文 .env、开放本机端口、挂载源码目录。生产环境应使用不可变 tag 或 digest、Registry 权限控制、Secret 管理、镜像漏洞扫描、非 root 用户、只读文件系统、资源限制、健康检查和集中日志。

教学中可以使用单机 bridge 网络理解服务发现；生产中要考虑跨节点网络、DNS、NetworkPolicy、服务网格或云负载均衡。教学中 Volume 可直接保存数据库数据；生产中必须补备份、恢复演练、容量告警、加密和迁移策略。

排障决策树

容器不可用
├─ 构建失败？
│  ├─ 是：检查 Dockerfile 指令、构建上下文、网络、包源、基础镜像
│  └─ 否：继续看运行阶段
├─ 容器立即退出？
│  ├─ 是：docker logs，确认 CMD、入口文件、权限、环境变量
│  └─ 否：继续看访问路径
├─ 端口访问失败？
│  ├─ 宿主机访问失败：检查 -p 映射、防火墙、服务监听 0.0.0.0
│  └─ 容器间访问失败：检查网络、服务名、端口、DNS
├─ 数据丢失？
│  ├─ 写在容器层：改用 Volume 或外部存储
│  └─ 使用 Volume：检查挂载目标、权限、备份
└─ 资源异常？
   ├─ OOMKilled：提高内存、降低并发、检查泄漏
   └─ CPU 慢：设置 requests/limits，观察应用线程与阻塞

练习与答案要点

基础练习：为 Python HTTP 服务写 .dockerignore，排除 .git、.venv、__pycache__、测试报告。答案要点：构建上下文变小；镜像不包含本地虚拟环境和缓存；重新构建输出中可看到 context 变化。

进阶练习：把单阶段 C++ 镜像改成多阶段，运行镜像只保留二进制和运行依赖。答案要点：构建工具链不进入 runtime；镜像体积下降；docker history 可解释主要层大小。

综合练习：用 Compose 启动 API、PostgreSQL 和 Redis，为 API 设置健康检查和连接重试。答案要点：服务间用 Compose 服务名；数据库有 pg_isready；API 启动时依赖未就绪也能重试；生产说明替换 Secret 和持久化方案。

小结与官方延伸阅读

Docker 解决的是交付一致性：同一镜像在不同环境获得尽可能接近的运行时文件系统和启动方式。它依赖 Linux 内核隔离和资源控制，但安全边界仍需要最小权限、镜像治理、密钥管理和平台策略共同完成。
