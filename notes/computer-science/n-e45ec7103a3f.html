学习目标

  • 理解 Linux 文件、进程、权限、环境变量和文本流模型。
  • 能用 Shell 高效查看日志、组合命令、编写小脚本。
  • 能识别命令的读写范围和破坏性风险。
  • 能用系统命令定位路径、权限、端口、进程和磁盘问题。

核心概念

  • 一切皆文件：普通文件、目录、设备、管道和 socket 都通过文件描述符访问。
  • 标准流：stdin、stdout、stderr 分别代表输入、正常输出、错误输出。
  • 管道：把前一个命令的标准输出接到后一个命令的标准输入。
  • 重定向：把输入或输出改到文件或其他描述符。
  • 权限：读、写、执行三类权限分别作用于用户、用户组、其他人。
  • 进程：运行中的程序，有 PID、父进程、当前目录、环境变量和打开的文件。
  • Shell 展开：变量、通配符、命令替换会在程序执行前由 Shell 处理。

常用命令

查看当前目录。风险低，只读。

pwd

列出文件。风险低，只读。

ls -la

查看文本文件前后内容。风险低，只读。

head -50 app.log
tail -100 app.log

持续观察日志。风险低，只读；长时间运行时用 Ctrl-C 退出。

tail -f app.log

按文本搜索。风险低，只读。

rg "connection refused" logs/

查看磁盘和目录占用。风险低，只读；大目录上可能较慢。

df -h
du -sh build/ logs/

查看进程。风险低，只读。

ps -ef
pgrep -af nginx

查看端口监听。风险低，只读。

lsof -iTCP -sTCP:LISTEN -n -P

修改权限。会改变文件访问能力；不要递归修改不确定的目录。

chmod +x scripts/run-tests.sh

创建目录。会写入文件系统；确认路径不是系统目录或错误变量展开结果。

mkdir -p build

删除文件。不可轻易恢复，风险高；删除前先用 ls 或 find 精确确认目标。

rm build/temp.o

Shell 示例

管道组合：找出最近日志中的错误行。风险低，只读。

tail -1000 app.log | rg "ERROR|FATAL"

重定向：把标准输出和错误输出分别保存。会覆盖同名文件，运行前确认输出路径。

./run-tests.sh > test.out 2> test.err

追加输出。会写入文件但不覆盖已有内容。

./run-tests.sh >> test.log 2>&1

安全脚本骨架。set -euo pipefail 会让未处理错误、未定义变量和管道失败更早暴露。

#!/usr/bin/env bash
set -euo pipefail

project_dir="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
cd "$project_dir"

cmake --build build
ctest --test-dir build --output-on-failure

风险说明：脚本里的 cd、变量展开和删除命令尤其需要谨慎。不要写 rm -rf "$some_dir"，除非已经校验变量非空、路径在预期目录内。

典型工作流

  1. 定位服务为什么启动失败。
pwd
ls -la
./server --config config/dev.yaml
  1. 查看错误和依赖文件。
rg "ERROR|failed|exception" logs/ config/
ls -l config/dev.yaml
  1. 检查端口占用。
lsof -iTCP:8080 -sTCP:LISTEN -n -P
  1. 检查环境变量。
env | sort

风险说明：env 可能输出敏感信息，不要把完整结果粘贴到公开 issue 或聊天中。

常见坑

  • 在错误目录运行命令，导致生成文件或删除目标落在非预期位置。
  • 未给变量加引号，路径中含空格时行为改变。
  • 混淆 > 和 >>，意外覆盖日志。
  • 以为 sudo 只是“权限更高”；它也会扩大误操作影响范围。
  • 使用通配符删除文件前没有确认展开结果。
  • 脚本依赖交互式 Shell 配置，到了 CI 或容器中就失败。

排障步骤

  1. 确认命令实际执行的位置和身份。
pwd
whoami
id
  1. 确认命令是否存在以及来自哪里。
command -v cmake
cmake --version
  1. 确认文件权限和路径每一级目录权限。
ls -ld .
ls -l scripts/run-tests.sh
  1. 确认进程、端口和打开文件。
pgrep -af server
lsof -p 12345
  1. 复现最小命令，去掉管道和重定向后直接观察错误。
./server --config config/dev.yaml

练习

  • 写一个脚本，检查构建目录是否存在，不存在则创建。
  • 用 rg 在日志目录里搜索指定错误码，并把结果追加到报告文件。
  • 故意创建一个没有执行权限的脚本，观察错误，再用 chmod +x 修复。
  • 用 lsof 找一个监听端口的进程，再解释每一列含义。

检查清单

  • 我能解释标准输入、标准输出、标准错误和管道的关系。
  • 我知道 > 会覆盖文件，>> 会追加文件。
  • 我会在删除、递归、sudo、通配符命令前确认目标。
  • 我能用 ps、pgrep、lsof 定位进程和端口。
  • 我能写一个带 set -euo pipefail 的基础脚本。

延伸阅读

  • 学完 Shell 后建议阅读：Git 和分支协作。

深化学习说明

前半部分是命令速查和常见工作流，适合快速定位文件、进程、端口和日志。下面的内容补足 Shell 的执行机制、可复现实验和排障路径，重点解释为什么同一条命令在不同环境会产生不同结果。

前置知识和完成标准

学习本章前，应能区分文件、目录和路径，知道命令行中空格用于分隔参数。Shell 的难点不在命令多，而在“哪些内容由 Shell 先展开，哪些内容交给程序自己处理”。

完成本章后，应能做到：

  • 对任意命令说清它读取哪里、写入哪里、是否会删除或覆盖内容。
  • 能用 pwd、ls -ld、command -v、env 判断执行环境。
  • 能把一次“服务启动失败”拆成路径、权限、环境变量、端口、依赖文件、日志六类检查。
  • 能写一个小脚本，并用 set -euo pipefail 暴露常见错误。

核心概念分层

第一层是路径模型：相对路径依赖当前目录，绝对路径不依赖。脚本中最常见事故是当前目录和作者预期不同。

第二层是标准流模型：程序默认从 stdin 读，向 stdout 写正常结果，向 stderr 写诊断信息。管道只连接 stdout；如果要把错误也送入后续命令，需要显式处理 2>&1。

第三层是权限模型：文件的执行权限决定能否把它当程序运行；目录的执行权限决定能否进入或穿过该目录。chmod +x file 修复脚本执行权限，不能修复解释器不存在或 shebang 错误。

第四层是进程模型：进程继承父进程环境变量、当前目录和打开文件。source script.sh 在当前 Shell 执行，./script.sh 在子进程执行；因此激活虚拟环境必须用 source 影响当前 Shell。

从零开始实验：观察 stdout、stderr、管道和退出码

教学边界：实验在系统临时目录下创建唯一目录。不要把示例中的覆盖重定向用于真实日志文件，除非已经确认目标路径。

lab_dir="$(mktemp -d "${TMPDIR:-/tmp}/shell-lab.XXXXXX")"
cd "$lab_dir"
printf '#!/usr/bin/env bash\nset -euo pipefail\nprintf "normal output\\n"\nprintf "error output\\n" >&2\nexit 7\n' > demo.sh
chmod +x demo.sh

./demo.sh > out.txt 2> err.txt
printf "exit=%s\n" "$?"

预期结果：因为脚本 exit 7，最后一行不会在 set -e 的交互上下文中自动停止你的 Shell，但 $? 会是 7。out.txt 保存 stdout，err.txt 保存 stderr。

继续观察管道：

set -o pipefail
./demo.sh 2>&1 | rg "output"
printf "pipeline_exit=%s\n" "$?"
set +o pipefail

set -o pipefail 让管道中左侧 ./demo.sh 的失败也影响整个管道退出码。若不启用 pipefail，Bash 默认返回最后一个命令的退出码；本例中只要 rg 匹配成功，管道状态就可能是 0，从而掩盖 demo.sh 的 exit 7。2>&1 的顺序也很重要：它把 stderr 指向当前 stdout，然后 stdout 再进入管道。若写成 > out.txt 2>&1，stdout 和 stderr 都进入文件；若写成 2>&1 > out.txt，stderr 仍留在终端，因为它先复制了旧 stdout。

验证方式：wc -l out.txt err.txt 应各有 1 行；cat err.txt 应只包含错误输出。

命令逐段解释

tail -1000 app.log | rg "ERROR|FATAL"

tail -1000 app.log 读取文件最后 1000 行并写到 stdout。| 只把 stdout 交给右侧命令。rg "ERROR|FATAL" 使用正则匹配两类关键字。若 app.log 不存在，错误会写到 stderr，不会成为 rg 的输入。

Bash 默认把整条管道的退出码设为最后一个命令的退出码。脚本中如果需要让 tail 读取失败也导致整条管道失败，应在脚本开头启用 set -o pipefail，或显式检查 ${PIPESTATUS[@]}。

set -euo pipefail

-e 让未处理的非零退出码尽早停止脚本；-u 使用未定义变量时报错；pipefail 让管道中任一失败影响整个管道结果。它们能暴露错误，但不是异常处理系统；需要预期失败时，应显式写 if command; then ... fi。

find build -type f -name "*.o" -print

这是删除前的只读确认命令。危险操作不要直接从通配符开始，先打印匹配集合。如果之后要删除，也应限定在明确目录内，并避免对变量未校验的路径执行递归删除。

常见坑的机制和排障决策路径

当命令在本机成功、CI 或服务器失败时，按下面顺序定位：

  1. 路径：pwd、ls -la、realpath file，确认当前目录和文件是否存在。
  2. 解释器：head -1 script.sh、command -v bash，确认 shebang 指向存在的程序。
  3. 权限：ls -l script.sh，若缺少执行位再用 chmod +x script.sh。
  4. 环境：env | sort 只在安全环境中查看；分享日志前删除 token、密码、内部地址。
  5. 参数展开：用 printf '<%s>\n' "$var" 检查变量是否为空或包含空格。
  6. 资源：df -h、ulimit -n、lsof -iTCP -sTCP:LISTEN -n -P 检查磁盘、文件描述符、端口。

失败现象和含义：

  • Permission denied：可能是文件无执行位，也可能是目录不可穿越或挂载为 noexec。
  • command not found：PATH 找不到命令，或脚本第一行解释器路径不存在。
  • No such file or directory：既可能是目标文件缺失，也可能是 shebang 中解释器缺失。
  • argument list too long：通配符展开后参数过多，应改用 find ... -exec 或流式处理。

练习答案要点

基础练习：脚本应先定位项目目录，再创建构建目录。

#!/usr/bin/env bash
set -euo pipefail
project_dir="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
mkdir -p "$project_dir/build"

进阶练习：搜索日志并追加报告时，应区分覆盖和追加。

rg "ERR42" logs/ >> report.txt

综合练习：定位端口占用的答案要包含进程名、PID、监听地址、是否可以停止。生产环境不能直接 kill -9；先确认进程归属、流量影响和服务管理方式，例如 systemd、容器或进程主管。

章节小结

Shell 的可靠使用来自三个习惯：先确认位置，再确认展开结果，最后执行有副作用命令。管道和重定向能极大提高效率，但也会隐藏失败和覆盖文件，所以脚本要把失败路径写清楚。
