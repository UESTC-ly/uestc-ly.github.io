1. 数据库

1.1 索引与 SQL 优化

  • [ ] ★★★ 为什么数据库索引通常使用 B+ 树，而不是二叉树、红黑树或普通哈希表？
  • 完整回答：
    • 索引目标： 数据库索引首先服务于页式存储和缓存体系，目标不是让 CPU 比较次数最低，而是用尽量少的随机 I/O 找到目标记录，并同时支持范围扫描、排序、分组、分页等常见 SQL 访问模式。
    • B+ 树结构： B+ 树是多路平衡搜索树，一个节点通常对应一个或多个数据库页；非叶子节点主要保存键和子节点指针，叶子节点保存完整索引项，并按键有序连接成链。
    • I/O 优势： 一个页可以容纳大量键，所以 B+ 树扇出远大于二叉树或红黑树。同样数据量下，树高通常很低，几层访问就能覆盖百万到亿级记录，磁盘随机读取次数可控。
    • 二叉树和红黑树的局限： 二叉树、红黑树在内存结构里表现很好，但每个节点分支少；如果节点离散分布到数据库页中，查找路径会变长，缓存局部性也差，不适合大规模磁盘索引。
    • 哈希表的局限： 普通哈希表等值查询理论上很快，但不维护顺序，难以直接支持 BETWEEN、ORDER BY、范围分页、前缀匹配和按索引顺序扫描，还要处理哈希冲突和扩容。
    • 范围查询优势： B+ 树叶子节点有序，相邻叶子可顺序读取；定位范围起点后可以连续向后扫描，正好匹配关系数据库中大量范围查询和排序需求。
    • 适用边界： 哈希索引并非没有价值，内存数据库、临时哈希连接、PostgreSQL 的 hash index、MySQL MEMORY 引擎都可能使用哈希结构。InnoDB 聚簇索引和主流二级索引采用 B+ 树，是因为它在等值查询、范围查询、顺序访问、页利用率和更新维护成本之间更通用。
    • 维护成本： B+ 树不是零成本结构，写入和删除需要维护平衡，可能触发页分裂或合并，所以索引数量和索引列宽仍然要受控。

  • 原理解析：

    • 核心概念： 索引结构要服务的是页式存储而不是单次内存比较。数据库一次 I/O 读入的是页，B+ 树把大量键压在同一页中，用高扇出降低树高；树高越低，从根到叶的随机页访问越少，Buffer Pool 或 shared buffers 命中后也更容易复用上层节点。
    • 运行机制： 查询先在非叶子节点做路由，再到叶子节点找到索引项。叶子有序并通过链表连接，等值查询能定位单点，范围查询能定位起点后顺序扫叶子页；这种“先随机定位、再顺序读取”的路径契合磁盘和 SSD 的访问特征。
    • 概念关联： 二叉树、红黑树适合内存对象指针追踪，但分支少导致路径长；哈希表适合点查却破坏顺序。B+ 树把等值、范围、排序、分组和分页统一在一种有序结构上，因此成为 InnoDB 聚簇索引、二级索引和 PostgreSQL B-tree 索引的通用选择。
    • 边界与误区： “B+ 树一定最快”不准确。MySQL MEMORY 的 hash、PostgreSQL hash index、哈希连接和临时哈希表都有价值；只是 OLTP 表索引通常需要有序访问和稳定维护成本。B+ 树写入会产生页分裂、合并和重平衡，索引越宽、越多，写放大越明显。
    • 记忆抓手： 可以把 B+ 树理解成“按页组织的多级目录”：上层目录只负责快速缩小页范围，叶子目录才保存可扫描的完整索引项。这个类比的局限是目录通常静态，而数据库索引会在并发写入中持续分裂、合并、加锁和刷脏页；因此真正要记住的是页大小、扇出、树高、叶子有序链表这条因果链，而不是目录这个比喻本身。若题目追问为什么不是红黑树，就回到“每层一次页访问”和“顺序范围扫描”两个关键词；若追问为什么不是哈希，就回到“哈希无序，难以天然支持范围和排序”。

  • [ ] ★★★ 聚簇索引和非聚簇索引有什么区别？

  • 完整回答：
    • 基本区别： 聚簇索引决定数据行的组织顺序，索引叶子节点就是数据记录或包含完整行数据；非聚簇索引不决定表数据的主组织方式，叶子节点保存索引键以及指向数据行的引用。
    • 实现差异： 聚簇和非聚簇必须结合具体数据库理解，不能把 InnoDB 的行为泛化到所有关系数据库。
    • InnoDB 聚簇索引： MySQL InnoDB 中，表数据存放在主键 B+ 树的叶子节点上，主键索引就是聚簇索引；如果没有显式主键，InnoDB 会选择非空唯一索引或生成隐藏 row id 作为聚簇键。
    • InnoDB 二级索引和回表： InnoDB 二级索引叶子节点保存二级索引列和主键值，不直接保存整行。通过二级索引查到记录后，如果查询列不在二级索引里，还需要按主键到聚簇索引查完整行，这个过程叫回表。
    • 覆盖索引作用： 覆盖索引能避免回表，因为查询需要的列已经在二级索引中，数据库可以直接从索引项返回结果。
    • PostgreSQL 对比： PostgreSQL 默认是堆表组织，普通 B-tree 索引项指向堆表 tuple 位置，主键只是唯一索引加约束，不会天然把表永久组织成主键顺序。CLUSTER 命令可以按某个索引重排表，但不是 InnoDB 这种持续维护的聚簇组织。
    • 收益和代价： 聚簇索引让主键查找和主键范围扫描局部性更好，但数据只能按一种顺序组织；主键过大或随机会放大所有二级索引体积，并增加页分裂、缓存抖动和写入成本。
    • 设计建议： InnoDB 常推荐短小、稳定、趋势递增的主键，业务唯一性可通过唯一索引表达。二级索引返回大量行时，回表随机读取会成为主要成本，这也是覆盖索引和索引条件过滤有价值的原因。

  • 原理解析：

    • 核心概念： 聚簇索引回答“数据行本身按什么顺序存放”，非聚簇索引回答“如何从某个键找到行的位置”。二者不是索引类型名字的简单对立，而是表组织方式与辅助访问路径的差异。
    • 运行机制： InnoDB 的表就是主键 B+ 树，叶子页保存完整行；二级索引叶子保存二级键加主键值，所以二级索引命中后要用主键再走一次聚簇树。这个回表过程本质是从一个有序结构跳到另一个有序结构，命中少时划算，命中多且分散时随机 I/O 和缓存抖动会放大。
    • 概念关联： 覆盖索引之所以有用，是因为它让二级索引叶子已经含有查询所需列，省掉第二次定位。主键设计会影响所有二级索引，因为 InnoDB 二级索引把主键当作行定位符；主键过长不只影响主键索引，也会传导到每个二级索引。
    • 边界与误区： PostgreSQL 默认堆表中，主键只是唯一约束背后的索引，普通索引指向 heap tuple，不会持续按主键重排数据。CLUSTER 是一次性物理重排，后续写入不会自动保持同样聚簇程度。不能把 InnoDB 的“主键即数据”直接套到所有数据库。
    • 记忆抓手： 判断一个查询是否会“多跳一次”，先问索引叶子里有没有完整行或所需列。InnoDB 主键命中就是到达数据，二级索引缺列就要拿主键再找；PostgreSQL 普通索引通常先到 heap，再由可见性规则决定行版本。这个记忆法的边界是各数据库可提供覆盖、包含列或 index-only scan，但它们仍绕不开“叶子内容是否足够”和“版本是否可见”这两个判断。主键选择也要放进这个模型：InnoDB 的主键不仅是约束字段，还是所有二级索引的定位载荷，过宽会把成本扩散到整张表的访问路径。

  • [ ] ★★★ 什么是联合索引的最左前缀原则？

  • 完整回答：
    • 联合索引排序方式： 联合索引把多列按定义顺序组合成一个有序键。例如 (a, b, c) 会先按 a 排序，在 a 相同的记录内部再按 b 排序，b 相同后再按 c 排序。
    • 最左前缀含义： 最左前缀原则描述的是这种复合有序性如何被查询利用。查询条件从最左列开始连续匹配时，数据库才能用索引快速缩小扫描范围。
    • 可有效定位的条件： 对 (a, b, c) 来说，WHERE a = ?、WHERE a = ? AND b = ?、WHERE a = ? AND b = ? AND c = ? 通常都能有效定位。只写 WHERE b = ? 时，索引整体并不是按 b 全局有序，无法像单列 b 索引那样直接定位。
    • 范围条件边界： 范围条件会改变后续列的定位能力。例如 a = ? AND b > ? AND c = ? 中，索引可以用 a 和 b 确定扫描区间；但 b 已经是范围后，c 不能继续作为连续精确定位条件，只能在扫描过程中做过滤，或作为覆盖列减少回表。
    • 排序影响： 排序也受最左前缀影响。WHERE a = ? ORDER BY b, c 可能直接利用索引顺序；如果排序列方向混乱、缺少前导等值条件，或过滤条件破坏有序性，就可能需要额外排序。
    • 优化器边界： 优化器并不机械套口诀。MySQL 8.0 有 skip scan、index condition pushdown 等优化，PostgreSQL 可能用 bitmap scan 组合多个索引，表达式索引也可能改变可用路径。
    • 设计原则： 建索引和判断执行计划时，仍应先从联合键的物理排序出发，再结合高选择性、等值过滤、排序分组和覆盖需求综合确定列顺序。

  • 原理解析：

    • 核心概念： 联合索引不是多个单列索引的简单拼接，而是把多列序列化成一个复合键。(a,b,c) 的全局顺序首先由 a 决定，只有在 a 相同的小区间里，b 才有序；只有 a、b 都相同时，c 才有序。
    • 运行机制： 优化器能利用连续前缀，是因为 B+ 树可根据前缀计算扫描边界。等值条件会把前导列压缩成一个窄区间，范围条件会把当前列变成一段区间；进入范围后，后续列不再形成全局连续边界，只能参与过滤、索引下推或覆盖返回。
    • 概念关联： 最左前缀同时影响过滤和排序。a = ? ORDER BY b,c 可以借助 (a,b,c) 的局部有序性；如果少了 a，数据库面对的是按不同 a 分散排列的 b，无法直接得到全局 b 顺序。
    • 边界与误区： 口诀不能代替执行计划。MySQL 8.0 skip scan 可能在缺少最左列时枚举前导列，PostgreSQL bitmap scan 可合并多个索引位图，但这些通常不是联合索引连续定位的低成本路径。建索引仍应从复合键物理排序、选择性、排序分组和覆盖收益推导。
    • 记忆抓手： 记 (a,b,c) 时不要把它想成三棵树，而要想成一本先按省、再按市、再按街道排序的通讯录。知道省能快速找市，知道市但不知道省只能翻很多省。这个类比的局限是数据库优化器可能用 skip scan 或位图组合做补救，但补救路径通常比直接命中连续前缀更依赖数据分布和成本估算。范围条件相当于在某一级目录打开了一段连续页，后面的列虽然仍写在条目上，却不能再决定这段页的起止位置，只能帮助过滤或避免回表。排序题也同理：只有前导列被等值固定后，后续列的索引顺序才会变成结果集所需顺序。

  • [ ] ★★★ 哪些情况可能导致索引失效？

  • 完整回答：
    • 失效含义： 索引失效通常不是索引文件损坏或完全不能用，而是优化器无法用该索引高效定位，或估算走索引的代价高于顺序扫描、全表扫描、位图扫描等路径。
    • 函数和表达式包装： 对索引列做函数、计算或表达式包装会削弱定位能力，例如 WHERE DATE(create_time) = ?、WHERE age + 1 = ?。普通 B+ 树按原列值排序，不按表达式结果排序；可改写为范围条件，或使用函数索引、表达式索引、生成列索引。
    • 隐式类型转换： 字符串列与数字常量比较时，某些数据库可能转换列值而不是参数，导致索引顺序无法直接使用，从而破坏定位。
    • 前导通配符： LIKE '%abc' 有前导通配符，无法从 B+ 树左侧前缀确定起点；LIKE 'abc%' 通常可以转为前缀范围，索引可用性更好。
    • 联合索引和条件形态： 联合索引不满足最左前缀、范围条件右侧列无法继续精确定位、OR 条件无法被优化器拆成有效索引路径、低选择性字段导致大量回表，都会让索引价值下降。
    • 非绝对失效条件： !=、<>、IS NOT NULL 不一定绝对失效；如果命中比例很高，优化器可能认为走索引不划算而放弃索引。
    • 统计和环境因素： 统计信息过旧、参数分布倾斜、排序分页需要回表过多、字符集或排序规则不一致，也可能导致计划不理想。MySQL/InnoDB、PostgreSQL 对表达式索引、部分索引、位图扫描、类型转换的处理也不同。
    • 验证方式： 不应只背固定规则，最终要通过 EXPLAIN 或 EXPLAIN ANALYZE 查看访问路径、扫描行数、过滤比例、回表成本和实际耗时，并结合真实参数验证。

  • 原理解析：

    • 核心概念： 所谓索引失效，多数是“不能用索引快速缩小搜索空间”或“用了也不划算”。B+ 树保存的是已排序的原始键值，查询条件必须能转化为这个排序上的点、前缀或范围，才能发挥定位能力。
    • 运行机制： 对列做函数、计算、隐式转换时，数据库看到的是表达式结果，而普通索引没有按该结果排序；前导通配符则让起始边界不可确定。低选择性条件即使能扫索引，也可能命中大量行，InnoDB 二级索引还要回表，总代价可能高于顺序扫描。
    • 概念关联： 统计信息连接了“可用”和“会用”。优化器根据基数、直方图、相关性、过滤率和 I/O 成本选计划；统计过旧或参数分布倾斜时，计划可能错误。PostgreSQL 的 bitmap scan、partial index、expression index 与 MySQL 的生成列索引、ICP 等能力，会改变某些条件的可用路径。
    • 边界与误区： !=、IS NOT NULL、OR 不是绝对禁忌，关键是结果比例和优化器能否拆分成低成本路径。判断时看 EXPLAIN ANALYZE 的实际扫描行数、过滤行数、回表或 heap fetch，而不是只看是否出现某个索引名。
    • 记忆抓手： 判断索引能否有效使用，可以连问三步：条件能不能映射到索引键的连续区间，命中比例是否足够低，取列是否会造成大量回表或 heap 访问。第一步解决“能不能定位”，第二步解决“值不值得走”，第三步解决“后续代价是否被低估”。这个顺序比背“哪些写法失效”更稳定，也更适合比较 MySQL 和 PostgreSQL 的差异。若条件写法破坏第一步，可通过改写范围、表达式索引、生成列或部分索引修复；若问题在第二、三步，加索引未必有效，可能要减少返回列或调整查询形态。最终以真实执行计划为准，因为优化器会在索引扫描、全表扫描和位图路径之间做成本选择。

  • [ ] ★★★ 什么是覆盖索引、回表和索引下推？

  • 完整回答：
    • 覆盖索引定义： 覆盖索引指某个索引已经包含查询需要读取、过滤、排序或返回的列，数据库可以只访问索引，而不读取完整数据行。
    • InnoDB 覆盖示例： InnoDB 二级索引叶子节点保存二级索引列和主键值。查询 SELECT age FROM user WHERE name = ? 时，如果存在 (name, age) 索引，name 和 age 都在索引中，主键也天然在二级索引叶子里，就可能直接完成，从而减少随机 I/O。
    • 回表含义： 回表是覆盖索引的相反情况：数据库先通过二级索引找到主键或行引用，再访问聚簇索引或堆表读取其他列。
    • 不同数据库实现： InnoDB 的回表是按主键回到聚簇索引；PostgreSQL 普通索引通常指向堆表 tuple，查询非索引列要访问 heap。PostgreSQL 也有 index-only scan，但需要列被索引覆盖，并且可见性信息允许避免堆表检查。
    • 索引下推含义： 索引下推通常指 MySQL 的 Index Condition Pushdown，优化器把能在存储引擎索引层判断的条件下推给 InnoDB，减少不满足条件的索引记录返回 server 层，也减少后续回表。
    • 索引下推示例： 联合索引 (name, age) 上查询 WHERE name LIKE '张%' AND age = 30，前导条件可能形成范围扫描，age = 30 可以在索引记录上进一步过滤。
    • 收益和代价： 覆盖索引和索引下推都能降低读取完整行的次数，但索引变宽会增加写入、更新、页分裂、缓存占用和维护成本。
    • 设计边界： 覆盖索引应围绕高频、稳定、收益明确的查询建立，不应为了少数低频查询把大量列塞入索引，尤其要避免长字符串、大字段和频繁更新字段。

  • 原理解析：

    • 核心概念： 覆盖索引解决“列是否够用”，回表解决“行在哪里取”，索引下推解决“过滤在哪里做”。三者都围绕同一件事：减少从索引命中到完整行读取之间的无效工作。
    • 运行机制： InnoDB 二级索引叶子有二级键和主键，若查询列都在叶子中，server 层可直接得到结果；若缺列，就用主键访问聚簇树。ICP 则把可由索引列判断的条件交给存储引擎，在回表前筛掉不合格索引项，减少 server 层交互和随机读取。
    • 概念关联： PostgreSQL 的 index-only scan 还受可见性映射影响：即使列被索引覆盖，如果页面不能证明所有 tuple 对当前快照可见，仍可能访问 heap。InnoDB 借助 Undo 和 Read View 判断版本，二级索引是否覆盖主要决定是否访问聚簇记录。
    • 边界与误区： 把所有查询列都塞进索引会让索引页更少容纳键，树更胖，写入、更新和缓存成本更高。覆盖适合高频、返回列少且稳定的查询；长文本、大 JSON、频繁更新列通常不适合为了覆盖而加入索引。
    • 记忆抓手： 可以把一次二级索引查询拆成“找线索、验条件、取正文”三段。覆盖索引让线索本身就是答案，索引下推在线索阶段先过滤，回表才是去取正文。类比的局限是数据库不是文本检索系统，真正成本由页访问、版本可见性、锁和优化器估算决定；但这三段能帮助快速判断优化点落在减少回表、减少返回 server 层，还是减少索引扫描。看到 Using index、Using index condition 或 PostgreSQL 的 index-only scan 时，也要结合实际 heap fetch、扫描行数和返回列判断收益。若覆盖索引让写入明显变慢，说明读优化已经把成本转移到维护索引上，设计时要按读写比例取舍，避免过度覆盖。

  • [ ] ★★★ 如何定位并优化一条慢 SQL？

  • 完整回答：
    • 先确认现象： 定位慢 SQL 不能一上来就加索引，需要先确认执行时间、调用频率、扫描行数、返回行数、锁等待、是否偶发、参数分布，以及发生时数据库整体负载。
    • 常用入口： MySQL 可看慢查询日志、Performance Schema、SHOW PROCESSLIST、EXPLAIN ANALYZE；PostgreSQL 可看 pg_stat_statements、pg_stat_activity、日志和执行计划；线上还可以结合 APM 链路追踪。
    • 看执行计划： 拿到 SQL 后先判断访问类型是索引查找、范围扫描还是全表扫描，使用了哪个索引，估算行数与实际行数是否偏差大，是否出现临时表、额外排序、哈希聚合、嵌套循环放大、回表过多或错误 join 顺序。
    • 常见 SQL 优化： 可改写不可索引条件，补充或调整联合索引，只查询必要列，让排序和过滤共享索引顺序，减少回表，拆分复杂查询，调整连接驱动表，避免深分页，分批处理大范围更新。
    • 非 SQL 本身原因： 如果慢的根因是锁等待、连接池耗尽、I/O 饱和、统计信息过旧或缓存未命中，单纯改 SQL 可能无效；还要查看事务持锁时间、死锁日志、等待事件、表膨胀和磁盘指标。
    • 复测要求： 优化后必须用相近数据量、真实参数和冷/热缓存条件复测，比较执行计划、扫描行数、P95/P99 和资源消耗。
    • 索引成本： 新增索引要评估写入成本、存储成本和其他查询的计划变化，避免为了一个低频查询制造长期维护负担。
    • 参数敏感性： 对参数敏感 SQL，还要检查不同参数是否触发截然不同的计划，防止只优化了样例值。

  • 原理解析：

    • 核心概念： 慢 SQL 的本质可能是访问路径差、估算错误、锁等待、资源饱和或返回数据过多。优化要先把“慢在哪里”拆成 CPU、I/O、锁、网络、计划选择和应用调用频率，避免把所有问题都归因于缺索引。
    • 运行机制： 执行计划描述数据如何被取出和组合：扫描多少行、用什么索引、如何 join、是否排序或临时聚合。MySQL 的 EXPLAIN ANALYZE 能看实际执行耗时；PostgreSQL 还能看到实际行数、loop 次数、buffer 命中等，估算与实际差距大通常指向统计信息或参数分布问题。
    • 概念关联： SQL 改写、联合索引、覆盖索引、分页策略和 join 顺序都服务于减少“无效扫描”和“昂贵回表”。若等待事件显示锁或 I/O 才是瓶颈，改 SQL 文本可能只治表象，必须同时处理事务时长、热点行、存储压力或连接池排队。
    • 边界与误区： 新增索引是有写入成本和计划副作用的变更。正确闭环是定位、假设、改动、复测，并用真实参数比较 P95/P99、扫描行数和资源消耗；只在开发库小数据量上看单次耗时，容易得到误导性结论。
    • 记忆抓手： 慢 SQL 排查可以按“现象、路径、瓶颈、改动、复测”记忆：先确认慢的是延迟、频率还是等待；再看计划如何取数；再判断主耗在扫描、排序、回表、锁或资源；然后只改一个主要因素；最后用同量级数据验证。这个流程的局限是线上问题可能同时有多个瓶颈，但分层记录证据能避免把偶发锁等待误判成索引问题。优化后的计划还要观察估算行数和实际行数是否贴近，否则统计信息或参数敏感问题可能在另一组参数下重新暴露。高频短 SQL 的总成本也可能超过低频慢 SQL，调用频率必须和单次耗时一起看。

  • [ ] ★★ 为什么不建议使用 SELECT *？

  • 完整回答：
    • 读取范围变大： SELECT * 会把表中所有列都纳入读取和返回范围，而业务通常只需要一部分字段。
    • 资源成本增加： 它会增加磁盘或缓存页读取、网络传输、驱动解码、对象映射和应用内存占用。字段越宽代价越明显，尤其是 TEXT、BLOB、JSON、大 varchar 或冷门扩展字段。
    • 破坏覆盖索引： 原本查询只需要索引列即可完成时，SELECT * 会迫使数据库读取完整行。InnoDB 中常表现为大量回表，PostgreSQL 中也可能从 index-only scan 退化为访问 heap。
    • 接口契约不稳定： 表新增列后，调用方会无意识接收更多数据，可能把敏感字段、大字段或语义未准备好的字段带到日志、缓存和 API 响应中。
    • 可接受场景： 临时排查、交互式查询、小表脚本中使用 SELECT * 通常可以接受，但生产代码应显式列出需要的字段。
    • 工程收益： 显式列名能让查询意图、权限边界和性能特征更清晰，也有利于代码评审和迁移；删除或改名字段时，影响范围能更早暴露。
    • 常见误区： 不能认为数据库内部总会读取整行，所以写不写 * 无所谓。列式存储、覆盖索引、延迟读取、大字段页外存储和网络返回都会受列数量影响。

  • 原理解析：

    • 核心概念： SELECT * 把“需要哪些数据”从业务意图变成表结构的当前偶然状态。数据库和应用都必须按返回列集合分配读取、传输、解码和对象映射成本，列越宽、越多，浪费越明显。
    • 运行机制： 在 InnoDB 中，若二级索引已覆盖过滤和返回列，显式列名可能只扫二级索引；* 要求完整行，通常触发回表。PostgreSQL 中，index-only scan 也依赖返回列被索引覆盖和可见性条件，* 往往迫使访问 heap。
    • 概念关联： 性能问题和接口契约问题相互关联。新增列后，* 会让旧代码自动取到更多字段，可能增加网络包、缓存对象大小，也可能把敏感列带入日志或 API。显式列名则让字段依赖在代码审查、迁移和权限控制中可见。
    • 边界与误区： 临时排查、小表脚本、一次性管理查询可以用 *。但生产路径应按场景列字段；“数据库反正读整行”不是通用事实，大字段页外存储、覆盖索引、列式存储和网络返回都会因列数量发生变化。
    • 记忆抓手： 记住 SELECT * 的三个隐性耦合：耦合表结构、耦合性能路径、耦合数据暴露边界。表一加列，查询结果、对象映射和敏感字段风险都跟着变。这个抓手的局限是小表和排查场景确实不敏感，但生产代码通常需要稳定契约。

  • [ ] ★★ 深分页为什么慢？如何优化？

  • 完整回答：
    • 慢的根因： 深分页慢来自 LIMIT offset, size 的语义：数据库必须跳过前 offset 条符合排序和过滤条件的记录，再返回后续 size 条。
    • 索引也要扫描： ORDER BY id LIMIT 1000000, 20 即使能走索引，通常也要扫描一百万零二十条索引记录并丢弃前一百万条；如果返回列不在索引中，还可能产生大量回表。
    • 成本随页码恶化： offset 越大，扫描和丢弃的成本越高，响应时间会随着页码变深而变差。
    • 游标分页： 常见优化是 keyset pagination，也就是记录上一页最后一条的排序键，下一页用 WHERE id > last_id ORDER BY id LIMIT 20 继续读取，使成本与页深基本解耦。
    • 稳定排序： 如果排序键不是单调唯一键，可以使用复合游标，例如 (created_at, id)，保证翻页顺序稳定。
    • 延迟关联： 另一种方式是先在窄覆盖索引中找到目标页主键，再 join 或回表取详情，减少宽行读取。
    • 产品和场景限制： 搜索、后台列表、日志类场景可以限制最大翻页深度，引导用户用筛选条件缩小范围。游标分页不适合任意跳页，数据插入删除也会影响连续浏览体验，因此必须定义稳定排序和边界条件。
    • 重型报表方案： 如果必须精确跳页，可能需要预计算、搜索引擎、物化视图或离线分页索引，而不是让 OLTP 主库承担无限深分页。

  • 原理解析：

    • 核心概念： offset 不是直接跳到物理位置，而是在排序后的逻辑结果集中丢弃前 N 条。数据库必须确认哪些记录排在前面，才能知道目标页从哪里开始，因此页码越深，已扫描但不返回的记录越多。
    • 运行机制： 如果排序列有索引，数据库可按索引顺序扫，但仍要走过 offset 加 size 条索引项；如果查询列不覆盖，还可能对被丢弃的大量记录回表或至少维护排序状态。没有合适索引时，还可能先过滤、排序、再截取，成本更高。
    • 概念关联： keyset pagination 把“第几页”改成“从上次最后一个键之后继续”，利用 B+ 树范围扫描直接定位边界。延迟关联则先用窄索引找主键，再取详情，核心都是减少宽行读取和无效回表。
    • 边界与误区： 游标分页牺牲任意跳页能力，并要求稳定、唯一的排序键，例如 (created_at,id)。数据并发插入删除会影响浏览连续性，需按业务接受程度设计。无限深翻页常是产品需求和数据检索方式问题，不只是 SQL 技巧问题。
    • 记忆抓手： offset 分页是在数“跳过多少条”，游标分页是在问“从哪个键之后继续”。前者成本随页深增长，后者成本主要随每页大小增长。这个记忆法的局限是游标不能天然支持任意跳页，也不能自动解决排序键不稳定或并发插入导致的浏览偏移。

  • [ ] ★★ COUNT(*)、COUNT(1) 和 COUNT(column) 有什么区别？

  • 完整回答：
    • 语义区别： 按 SQL 语义，COUNT(*) 统计结果集中的行数，不关心任何列是否为 NULL；COUNT(1) 统计常量表达式 1 非空的行数，由于每行该表达式都非空，通常等价于统计行数；COUNT(column) 只统计该列值不为 NULL 的行。
    • NULL 影响： 如果列允许 NULL，COUNT(column) 的结果可能小于 COUNT(*)，所以三者首先是语义区别，不是性能口诀。
    • 优化器处理： 现代数据库优化器通常会把 COUNT(*) 和 COUNT(1) 优化为相近甚至相同的执行路径，不能简单说 COUNT(1) 永远更快。
    • InnoDB 特点： InnoDB 不像 MyISAM 那样为普通事务表维护可直接返回的精确总行数。MVCC 下不同事务能看到的行版本不同，无条件精确 COUNT(*) 往往需要扫描可见记录，优化器可能选择最小的二级索引来降低 I/O。
    • PostgreSQL 特点： PostgreSQL 也通常需要扫描表或索引并判断可见性，因此大表上的精确全表计数并不便宜。
    • 近似计数方案： 如果业务只需要近似值，可以使用统计信息、缓存计数、汇总表或异步维护的计数器，但要明确一致性和延迟边界。
    • 判断依据： 计数优化不能写成固定规则，实际要看数据库版本、存储引擎、隔离级别、索引宽度、过滤条件和执行计划。

  • 原理解析：

    • 核心概念： COUNT 的差异先是 SQL 语义差异。COUNT(*) 数行，COUNT(1) 数每行的非空常量，COUNT(column) 数非空列值；当列可为 NULL 时，第三种表达的是另一个问题。
    • 运行机制： MVCC 让“表有多少行”变成事务视角下的可见行数。InnoDB 不能像 MyISAM 那样对普通事务表返回一个全局精确计数，因为不同 Read View 看到的版本不同；PostgreSQL 也要根据 tuple 可见性判断当前事务可见行。
    • 概念关联： 优化器常把 COUNT(*) 和 COUNT(1) 归约成类似计划，并可能选择最窄的可用索引来减少 I/O。带过滤条件时，索引是否能缩小范围比写 * 还是 1 更重要；COUNT(column) 若列在索引中，也可能借助索引判断非空。
    • 边界与误区： 近似统计、缓存计数和汇总表可以提升性能，但牺牲实时精确性或增加维护逻辑。面向分页展示时，很多场景不需要每次精确全量计数，应先确认业务是否需要强一致数字。
    • 记忆抓手： 先把三种写法翻译成一句话：数所有行、数每行常量、数非空列。再把性能问题翻译成另一句话：在当前事务视角下找到多少可见行。这个抓手能避免把语义和优化混在一起，但具体快慢仍要看索引、过滤条件和 MVCC 可见性。

  • [ ] ★★ IN、EXISTS 和 JOIN 应该如何选择？

  • 完整回答：
    • 语义优先： IN、EXISTS 和 JOIN 首先表达不同语义。需要返回关联表字段或组合两张表的数据时，应使用 JOIN；只关心外层记录是否存在匹配记录时，EXISTS 更贴近半连接语义；匹配一组离散常量或子查询结果时，IN 语义清晰。
    • 优化器会改写： 现代优化器常会把 IN、EXISTS、半连接和部分 JOIN 改写成相近执行计划，所以不能按“外表大用 IN、内表大用 EXISTS”这类固定口诀判断。
    • 真正影响因素： 执行差异主要来自数据量、索引、重复行、NULL 语义和优化器能力。
    • JOIN 的结果放大： JOIN 在一对多关系中会放大结果集。如果只是判断存在，可能还需要 DISTINCT 去重，反而增加排序或哈希聚合成本。
    • EXISTS 的优势： EXISTS 通常可以在找到第一条匹配记录后停止，适合存在性判断。
    • IN 的适用边界： 小的常量 IN 列表往往简单高效，但超大列表会增加解析、计划和传输成本，可考虑临时表或批量 join。
    • NOT IN 风险： NOT IN 要特别注意 SQL 三值逻辑；子查询结果中只要包含 NULL，整体判断可能变成 unknown，导致结果不符合直觉，很多反关联场景用 NOT EXISTS 更稳妥。
    • 最终验证： MySQL 和 PostgreSQL 都有半连接、去相关化、哈希连接或嵌套循环等优化，但具体版本和统计信息会影响计划，选择后应通过执行计划和实际耗时验证。
  • 原理解析：
    • 核心概念： 三者的首要区别是关系语义。JOIN 产生组合行，EXISTS 表达存在性，IN 表达值属于集合。先选能准确表达需求的写法，再看优化器是否能改写成更低成本计划。
    • 运行机制： 存在性判断常可转为半连接，找到第一条匹配就停止；普通 inner join 必须产生所有匹配组合，一对多会放大行数。IN 子查询可能被去相关化、物化、哈希化或改写成半连接，具体取决于数据库版本、统计信息和索引。
    • 概念关联： NULL 语义会改变结果。NOT IN 与三值逻辑绑定，集合中出现 NULL 时，比较结果可能是 unknown；NOT EXISTS 检查是否找不到匹配行，通常更贴近反关联。性能和正确性在这里不能分开讨论。
    • 边界与误区： “大表用 EXISTS、小表用 IN”是过度简化。MySQL 和 PostgreSQL 都可能对写法做等价变换，也可能因统计错误选择差计划。真正的选择依据是返回列、重复行、空值语义、索引路径和实际计划。
    • 记忆抓手： 先问“我要组合数据，还是只判断有没有”。组合数据用 JOIN，判断存在优先想半连接语义，离散集合匹配再考虑 IN。这个抓手的局限是优化器可能把它们改写成相同计划，但语义先行能避免 JOIN 放大行数和 NOT IN 空值陷阱。

1.2 事务、锁与日志

  • [ ] ★★★ 什么是事务的 ACID？数据库如何实现它们？
  • 完整回答：
    • ACID 含义： ACID 描述事务系统希望提供的四类性质：原子性、一致性、隔离性和持久性。
    • 原子性实现： 原子性保证事务内多个操作作为整体成功或失败，不能留下半完成状态。数据库通常用 Undo Log 或旧版本记录支持回滚，事务失败时按修改前镜像撤销已执行变更。
    • 持久性实现： 持久性保证事务提交后，即使数据库进程崩溃或机器重启，已提交结果仍能恢复。InnoDB 依赖 Redo Log 和 WAL 思想，PostgreSQL 依赖 WAL，提交路径按刷盘策略保证日志先于脏页成为恢复依据。
    • 隔离性实现： 隔离性处理并发事务之间的相互影响，常见实现包括锁、MVCC、谓词锁、Serializable Snapshot Isolation 等，不同隔离级别在并发性和异常防护之间取舍。
    • 一致性来源： 一致性是事务执行前后数据库从一个合法状态转到另一个合法状态，由约束、外键、唯一索引、触发器、隔离机制和业务规则共同保证，不是单靠某个日志实现。
    • 实现差异： SQL 标准定义的是隔离级别和异常现象，具体实现差异很大。InnoDB 可重复读结合 MVCC 与 next-key lock，PostgreSQL 的 Repeatable Read 更接近快照隔离，Serializable 通过 SSI 检测危险结构。
    • 成本边界： ACID 不是免费能力；隔离越强、持久性刷盘越严格，通常会带来更多锁等待、冲突重试、日志 I/O 或吞吐下降。
    • 跨系统一致性： 跨数据库、缓存、MQ 的业务一致性不会自动由单库 ACID 覆盖，需要事务消息、Outbox、幂等和补偿设计。

  • 原理解析：

    • 核心概念： ACID 是事务承诺的性质，不是四个彼此独立的功能开关。原子性处理失败后的撤销，持久性处理提交后的恢复，隔离性处理并发交错，一致性则要求这些机制和约束共同维护业务不变量。
    • 运行机制： 写入通常先生成日志和版本信息。InnoDB 用 Undo 支撑回滚和一致性读，用 Redo 按 WAL 原则保证崩溃恢复；PostgreSQL 以 WAL 作为恢复和复制基础，旧行版本由 tuple 元数据配合 vacuum 管理。提交时日志持久化策略决定宕机后能恢复到什么边界。
    • 概念关联： 隔离性和一致性经常被混淆。唯一约束、外键、检查约束能阻止非法状态；隔离级别则决定并发事务是否会绕开这些规则形成异常。比如写偏斜不一定违反单行约束，却可能违反跨行业务不变量，需要更强隔离或显式锁。
    • 边界与误区： SQL 标准定义隔离级别和异常现象，但实现不同。InnoDB Repeatable Read 结合 next-key lock 抑制部分幻读；PostgreSQL Repeatable Read 是快照隔离，Serializable 用 SSI 检测危险结构。跨库、缓存和消息队列不在单库 ACID 自动保护范围内。
    • 记忆抓手： 可以把 ACID 记成“失败可撤、提交可恢复、并发有边界、状态守规则”。类比的局限是这四句不是实现方案：撤销依赖 Undo 或旧版本，恢复依赖 Redo/WAL，边界依赖锁和 MVCC，守规则还依赖约束和业务代码。尤其一致性不是数据库替业务兜底，跨资源一致性必须额外设计消息、幂等、补偿和重试。回答时可按故障路径组织：语句失败靠回滚，进程崩溃靠 WAL/Redo，事务并发靠隔离，业务非法状态靠约束和应用不变量共同拦截。隔离和持久性越强，通常越会增加等待、重试或刷盘成本，需要结合业务风险选择。

  • [ ] ★★★ 数据库有哪些事务隔离级别？分别解决什么问题？

  • 完整回答：
    • 四个级别： SQL 标准定义四个隔离级别：读未提交、读已提交、可重复读和可串行化。
    • 读未提交： 读未提交允许事务读到其他事务尚未提交的数据，可能发生脏读。主流数据库很少把它作为常用选择；PostgreSQL 即使设置 Read Uncommitted，也按 Read Committed 处理。
    • 读已提交： 读已提交保证只能读到已提交数据，避免脏读；但同一事务中两次读取同一行，可能因为其他事务提交而得到不同结果，即不可重复读。PostgreSQL Read Committed 每条语句获得一个新快照。
    • 可重复读： 可重复读要求同一事务内对同一数据的读取稳定。SQL 标准仍可能允许幻读，即同一范围两次查询出现新增或消失的行，但具体实现不同。
    • InnoDB 可重复读： InnoDB 默认 Repeatable Read，普通一致性读使用事务级 Read View，当前读在合适索引范围上可能使用 next-key lock 抑制幻读。
    • PostgreSQL 可重复读： PostgreSQL Repeatable Read 使用事务级快照，语义接近快照隔离，能避免很多读现象，但仍不等价于真正串行执行，写偏斜等异常需要 Serializable 才能阻止。
    • 可串行化： 可串行化要求并发执行结果等价于某个串行顺序，隔离最强，成本也最高，可能带来更多阻塞、谓词锁、冲突检测或事务重试。
    • 工程选择： 脏读、不可重复读、幻读只是入口，工程上还要关心丢失更新、写偏斜、唯一约束冲突和锁等待。隔离级别应按业务不变量选择，例如余额扣减、库存、审批流通常需要条件更新、锁或可重试的串行化方案，普通列表查询可接受较低隔离换取吞吐。

  • 原理解析：

    • 核心概念： 隔离级别描述并发事务能观察和影响彼此到什么程度。级别越高，越接近串行执行，但并发度、等待、冲突检测和重试成本通常越高；它本质上是在正确性和吞吐之间划边界。
    • 运行机制： Read Committed 常以语句为单位建立可见性边界，PostgreSQL 每条语句拿新快照；Repeatable Read 常以事务为单位固定快照。InnoDB 在 Repeatable Read 下普通读用事务级 Read View，当前读可能加 next-key lock；PostgreSQL Repeatable Read 不用 InnoDB 式间隙锁，而是依赖快照隔离语义。
    • 概念关联： 脏读、不可重复读、幻读是标准中的现象描述，不覆盖所有业务风险。写偏斜、丢失更新、约束竞争和读后写决策更贴近工程问题。例如两个医生同时请假、两个事务各自看到还有一人值班，就可能在快照隔离下破坏跨行不变量。
    • 边界与误区： PostgreSQL 设置 Read Uncommitted 仍按 Read Committed 处理；InnoDB 的 Repeatable Read 与 PostgreSQL 的 Repeatable Read 也不等价。不要只按级别名称推断行为，关键场景应用条件更新、锁定读或可重试 Serializable 验证。
    • 记忆抓手： 读未提交看见“未确定事实”，读已提交每句话只看“已提交事实”，可重复读在事务内固定“观察窗口”，可串行化要求结果像“排队执行”。这个类比的局限是不同数据库固定窗口的实现不同：InnoDB 还会在当前读范围上加锁，PostgreSQL 快照隔离不等于完整串行化，写偏斜要靠 Serializable 或显式约束处理。面试或设计时不要只列现象，还要说明每一级允许哪些并发异常，以及业务不变量需要用条件更新、锁定读还是可重试事务来兜住。普通查询、库存扣减和跨行审批的隔离需求不同，不能用同一默认级别解释所有场景；还要区分快照读和当前读路径。

  • [ ] ★★★ MVCC 是什么？它如何提高并发性能？

  • 完整回答：
    • MVCC 定义： MVCC 是多版本并发控制，通过保存数据的多个历史版本，让读操作按事务可见性规则读取某个一致版本，而不是总是等待最新写入完成。
    • 并发收益： 它的直接收益是普通读和写在很多场景下互不阻塞。写事务创建新版本或标记旧版本，读事务仍可读取自己快照中可见的旧版本，从而提高读多写多系统的并发能力。
    • InnoDB 实现： InnoDB 在记录中维护隐藏事务 ID、回滚指针等信息，旧版本主要通过 Undo 版本链重建；Read View 记录活跃事务集合、最小和最大事务边界，用于判断某个版本对当前事务是否可见。
    • PostgreSQL 实现： PostgreSQL 采用更显式的行版本模型，tuple 上有 xmin、xmax 等元数据，新版本通常以新 tuple 形式写入，旧 tuple 等待 vacuum 清理。
    • 不是没有锁： MVCC 不意味着没有锁。更新同一行、删除、唯一约束检查、外键检查、SELECT ... FOR UPDATE、InnoDB 当前读和 PostgreSQL 可串行化冲突检测，都可能阻塞或失败重试。
    • 版本清理代价： MVCC 的代价是版本存储和清理。InnoDB 长事务会阻碍 purge 清理 Undo 历史，PostgreSQL 长事务会阻碍 vacuum 回收死元组，造成表膨胀、索引膨胀、扫描变慢和存储上升。
    • 使用边界： 快照读可能看到旧数据，不适合“读后立即基于结果修改”的关键判断；这类场景应使用条件更新、当前读、乐观锁版本号或更高隔离级别。
    • 本质理解： MVCC 提高并发的本质不是让冲突消失，而是把不必要的读写等待转化为按版本读取，同时把真正的写写冲突交给锁或冲突检测处理。

  • 原理解析：

    • 核心概念： MVCC 的关键是“同一逻辑行可有多个版本，事务按可见性规则选版本”。它不是让数据复制很多份给每个事务，而是在记录元数据、Undo 或旧 tuple 上维护版本链，让读者能回到自己应该看到的时间点。
    • 运行机制： InnoDB 新版本留在数据页，旧值通过 Undo 链重建，Read View 用活跃事务集合判断版本是否可见。PostgreSQL 更新通常写出新 tuple，旧 tuple 通过 xmin、xmax 标记生命周期，之后由 vacuum 回收不可见的死元组。
    • 概念关联： MVCC 减少的是读写互相等待，不取消写写冲突。两个事务更新同一行仍要争行锁；唯一索引、外键检查、锁定读和 Serializable 冲突检测仍可能阻塞或失败。快照读适合一致视图，当前读适合读后修改。
    • 边界与误区： 长事务会延长旧版本保留时间：InnoDB purge 不能清理仍可能被读到的 Undo 历史，PostgreSQL vacuum 不能回收仍可能可见的 dead tuple。结果是存储膨胀、扫描变慢和复制压力，并不是“多版本没有成本”。
    • 记忆抓手： MVCC 可以记成“写新不挡旧读，旧读按快照找旧版，真正写冲突再由锁或检测处理”。类比成文档修订历史有帮助，但局限是数据库版本不是人工保存的副本，而是带事务 ID、可见性边界和清理规则的数据结构。只要有长事务占着旧快照，历史版本就不能随意删除。解释 InnoDB 时抓住隐藏事务 ID、回滚指针、Undo 链和 Read View；解释 PostgreSQL 时抓住 xmin/xmax、新旧 tuple 和 vacuum，这样差异会更清楚。它提高并发的因果不是消灭冲突，而是让读者少等待写者，并把真正会破坏一致性的写写竞争交给锁、约束或串行化冲突检测处理。因此 MVCC 与锁是互补关系，不是替代关系，工程上必须同时理解。

  • [ ] ★★★ 快照读和当前读有什么区别？

  • 完整回答：
    • 基本区别： 快照读读取事务可见的一致性版本，通常不加行锁，也不保证看到数据库中最新提交的记录；当前读读取符合隔离规则的最新可修改版本，通常会对读到的记录或范围加锁。
    • InnoDB 常见语句： InnoDB 中，普通 SELECT 在 Read Committed 和 Repeatable Read 下通常是快照读；SELECT ... FOR UPDATE、SELECT ... FOR SHARE、UPDATE、DELETE 属于当前读。
    • Repeatable Read 快照： Repeatable Read 下，InnoDB 第一次一致性读会创建 Read View，后续普通查询复用同一事务快照，因此另一个事务提交的新数据不一定可见。
    • Read Committed 快照： Read Committed 下每条语句创建新快照，所以同一事务内两次普通查询可能看到不同的已提交版本。
    • 当前读的必要性： 当前读不能只看历史快照，因为它要锁定并修改真实最新记录。扣库存如果先快照读库存为 1，再基于旧值更新，可能造成并发错误。
    • 正确修改方式： 读后修改的关键场景应使用 UPDATE sku SET stock = stock - 1 WHERE id = ? AND stock > 0、SELECT ... FOR UPDATE 或乐观锁条件，确保判断和修改建立在当前状态上。
    • PostgreSQL 对比： PostgreSQL 也有普通快照读取和锁定读取的区别，SELECT FOR UPDATE 会锁定返回行，但它的 MVCC 与锁实现细节不同于 InnoDB 的 next-key lock。
    • 适用和误区： 快照读适合普通查询、报表和一致视图，代价是可能读旧版本并增加版本保留压力；当前读适合读后修改和资源抢占，代价是锁等待、死锁和并发下降。不能认为可重复读下所有读取都不受幻读影响，还要区分快照读、当前读、索引范围和数据库实现。

  • 原理解析：

    • 核心概念： 快照读问的是“按我的快照，这行是什么样”，当前读问的是“现在我要锁定或修改的最新可操作行是什么”。前者重一致视图和并发，后者重修改正确性和资源占有。
    • 运行机制： InnoDB 普通 SELECT 根据 Read View 选择可见版本；Read Committed 每条语句建快照，Repeatable Read 通常复用事务快照。UPDATE、DELETE、SELECT FOR UPDATE 必须面向最新可修改版本，并在索引记录或范围上加锁，否则后续修改可能建立在过期判断上。
    • 概念关联： 扣库存、抢任务、余额变更属于读后写业务，不应先快照读再无条件更新。条件更新把判断和修改合并到同一当前读写路径；锁定读则先占有资源，再由业务逻辑决定修改。
    • 边界与误区： PostgreSQL 也有 SELECT FOR UPDATE 锁定行，但不像 InnoDB 主要靠 next-key lock 处理范围幻读；Serializable 下会通过 SSI 等机制检测不可串行化风险。可重复读不等于所有读法、所有范围都天然安全。
    • 记忆抓手： 快照读适合“看报表”，当前读适合“抢座位”。看报表希望视图稳定，不一定最新；抢座位必须面对当前可用资源并锁住它。这个类比的局限是数据库锁粒度由索引和执行计划决定，不是业务对象本身；因此抢资源时还要检查条件更新是否命中索引、是否可能锁范围过大。判断一条语句属于哪类，重点看它是否要修改或锁定最新版本：普通 SELECT 多是快照读，UPDATE/DELETE/FOR UPDATE 多是当前读。读后写业务若只依赖旧快照，容易把已经变化的现实状态当成决策依据；条件更新能把判断和修改放进同一个原子写路径，减少并发判断漏洞，也更便于重试和观察影响行数。这是并发正确性的关键分界。

  • [ ] ★★★ 行锁、表锁、间隙锁、临键锁分别是什么？

  • 完整回答：
    • 行锁和表锁： 行锁锁定具体记录，允许不同事务并发修改不同行，适合高并发 OLTP；表锁锁定整张表或表级操作范围，并发度低但实现简单，常见于 DDL、元数据操作、显式锁表或某些存储引擎。
    • InnoDB 行锁本质： InnoDB 的行锁本质上锁的是索引记录，而不是抽象的物理行。如果查询条件不能使用合适索引，数据库可能扫描大量索引记录并逐个加锁，表现出接近表级阻塞的效果。
    • 间隙锁： 间隙锁是 InnoDB 在索引记录之间的空隙上加锁，限制其他事务向该范围插入新记录，主要用于 Repeatable Read 的当前读场景中抑制幻读。
    • 临键锁： 临键锁即 next-key lock，通常可理解为记录锁加相邻间隙锁，锁住一个索引记录以及它前面的间隙，覆盖一段索引范围。
    • 范围锁示例： 如果索引中已有 10 和 20，范围查询 WHERE id BETWEEN 10 AND 20 FOR UPDATE 可能不只锁住已有记录，还锁住相关间隙，防止其他事务插入 15。
    • 锁的细节边界： 间隙锁只限制插入，不一定阻止更新已有记录本身；记录锁才针对已有索引项。
    • PostgreSQL 对比： PostgreSQL 不用 InnoDB 这种 next-key lock 作为主要幻读控制方式，而是在 Serializable 中使用 SSI 和谓词锁等机制检测不可串行化风险。
    • 工程误区： 锁粒度越细并发越高，但管理成本、死锁风险和索引依赖越强；锁范围越大实现越直接，但更容易阻塞。不能认为“用了行锁就只锁一行”，实际锁范围取决于访问路径、隔离级别、索引条件和数据库实现。

  • 原理解析：

    • 核心概念： 锁粒度决定并发边界：行锁保护具体索引记录，表锁保护整表或表级操作，间隙锁保护“两个索引值之间不能插入”，临键锁把记录和相邻间隙合在一起保护一段范围。
    • 运行机制： InnoDB 行锁挂在索引记录上。当前读按访问路径扫描到哪些索引项，就可能锁住哪些项；没有合适索引时，扫描范围扩大，锁范围也随之扩大。Repeatable Read 下的 next-key lock 通过锁记录和间隙，防止范围查询后被其他事务插入幻影行。
    • 概念关联： 锁和索引不是分离的调优点。索引越精准，当前读扫描和加锁范围越小，死锁和阻塞概率越低。间隙锁主要限制插入到范围中，不等同于锁住一切已有行；记录锁才保护已有索引项本身。
    • 边界与误区： PostgreSQL 不以 InnoDB next-key lock 作为主要幻读方案，Serializable 使用 SSI 和谓词锁相关机制检测风险。不能只说“行锁并发高”，还要看隔离级别、where 条件、执行计划和是否命中索引。
    • 记忆抓手： InnoDB 锁范围可按“索引记录加两侧空隙”来想：记录锁管已有键，间隙锁管能否插入新键，临键锁把两者合并保护范围。这个类比的局限是实际边界受唯一索引、范围条件、隔离级别和优化器访问路径影响；看锁问题必须回到执行计划和真实锁等待记录。若题目追问为什么无索引会锁很多行，答案是存储引擎必须沿扫描路径检查候选记录，当前读会在扫描到的索引项上加锁，访问路径扩大就会放大锁范围。锁粒度越小越依赖准确访问路径，索引设计直接影响并发控制效果，也影响死锁概率和等待时长。

  • [ ] ★★★ 数据库死锁是如何产生的？如何排查和避免？

  • 完整回答：
    • 死锁定义： 数据库死锁是多个事务之间形成循环等待：每个事务都持有一部分锁，同时等待另一个事务持有的锁释放，导致所有参与者都无法继续。
    • 典型例子： 事务 A 先更新账户 1 再更新账户 2，事务 B 先更新账户 2 再更新账户 1；两个事务各自拿到第一把锁后，都在等待对方释放第二把锁。
    • 数据库处理： 数据库通常会进行死锁检测，发现循环等待后选择一个代价较低的事务回滚，让另一个事务继续执行；应用层会收到死锁或序列化失败错误。
    • 排查信息： 排查时要收集死锁发生的 SQL、事务开始时间、持锁语句、等待语句、索引访问路径和隔离级别。
    • 排查工具： MySQL 可看 SHOW ENGINE INNODB STATUS、Performance Schema 的锁等待表、错误日志；PostgreSQL 可看 pg_locks、pg_stat_activity、日志中的 deadlock detail。
    • 避免思路： 减少死锁的核心是降低循环等待概率，例如固定资源访问顺序，批量更新前按主键排序，缩短事务，避免事务内调用慢外部接口，建立合适索引以减少扫描和锁范围。
    • 热点处理： 大批量操作可拆小，降低不必要的当前读范围；热点资源可通过队列或条件更新串行化。
    • 恢复和误区： 死锁不能完全消灭，高并发写入系统应把它视为可恢复并发异常，应用层有限重试，并保证幂等和退避。不能一出现死锁就认为数据库坏了，也不能盲目扩大锁粒度；排查结论要落到具体语句和资源顺序。

  • 原理解析：

    • 核心概念： 死锁成立需要循环等待：事务 A 等 B，B 又直接或间接等 A。普通锁等待只有先后关系，持锁者提交后即可继续；死锁没有外力打破就无法前进，所以数据库必须检测并牺牲一个事务。
    • 运行机制： InnoDB 会维护等待图，检测到环后回滚代价较低的事务；PostgreSQL 在等待超过检测阈值后检查死锁并报错。应用看到异常不代表数据损坏，而是数据库为了恢复可进展性主动终止了其中一个并发分支。
    • 概念关联： 访问顺序、事务时长和锁范围共同决定死锁概率。固定资源顺序能减少环；合适索引能减少被锁记录和间隙；短事务能缩短等待窗口。大批量更新若无序扫热点范围，容易与在线请求形成交叉持锁。
    • 边界与误区： 死锁不能在高并发写系统中完全消除，正确做法是降低概率并让应用幂等、有限重试、退避。盲目改成表锁可能减少某些环，但会制造更大范围阻塞和吞吐下降，必须有明确证据。
    • 记忆抓手： 死锁排查按“谁持有、谁等待、等什么索引记录、为什么顺序相反”四问展开。账户转账例子只说明循环等待形态，局限是线上死锁常由范围锁、二级索引扫描、外键检查或批量更新顺序引发。只有把等待资源映射回具体 SQL 和访问路径，才能制定可验证的修复。修复手段也要对应原因：顺序相反就排序访问，锁范围过大就补索引或改条件，事务过长就拆出外部调用和批量任务。应用层捕获死锁后应按可恢复并发异常处理，而不是无限重试或直接报失败。

  • [ ] ★★★ Redo Log、Undo Log 和 Binlog 分别有什么作用？

  • 完整回答：
    • 职责区别： Redo Log、Undo Log 和 Binlog 解决的问题不同，不能因为都和事务或日志有关就混为一谈。
    • Redo Log： Redo Log 是 InnoDB 存储引擎层的崩溃恢复日志，记录页级或近似物理层面的修改，遵循 WAL 思想。数据页可以延迟刷盘，但提交相关日志必须按策略先持久化；宕机后通过重放 redo 把已提交修改恢复到数据页中，保证持久性。
    • Undo Log： Undo Log 记录修改前的旧值或回滚所需信息，用于事务回滚，也支撑 MVCC 一致性读。事务失败时可按 undo 撤销修改；长事务存在时，旧版本不能过早清理。
    • Binlog： Binlog 是 MySQL server 层逻辑日志，记录数据库变更事件，主要用于主从复制、时间点恢复和审计归档。
    • Binlog 格式： Binlog 有 statement、row、mixed 等格式，生产复制通常偏向 row 格式，因为它记录行变更结果，能减少函数、触发器、非确定性语句带来的歧义。
    • 两阶段提交： Redo 和 Binlog 分属不同层。MySQL 为保证事务提交后两者一致，引入两阶段提交：prepare redo、写 binlog、commit redo，崩溃恢复时据此判断事务是否完整提交。
    • PostgreSQL 对比： PostgreSQL 没有 MySQL Binlog 这一层，它的崩溃恢复、物理复制和部分逻辑复制基础主要围绕 WAL。
    • 记忆边界： Redo 负责崩溃后重做，Undo 负责回滚和版本可见性，Binlog 负责复制和逻辑恢复；它们的持久化策略、清理时机、粒度和使用场景都不同。

  • 原理解析：

    • 核心概念： 三类日志分别回答三个问题：崩溃后怎么把已提交修改做回来，事务失败怎么撤回，其他节点或恢复工具怎么知道发生过哪些逻辑变更。Redo 面向重做，Undo 面向撤销和版本，Binlog 面向 MySQL server 层复制与时间点恢复。
    • 运行机制： WAL 的因果链是先保证日志落到持久介质，再允许数据页延迟刷盘。宕机时，如果脏页没写完，InnoDB 可重放 Redo；如果事务未提交，可借助 Undo 回滚。Binlog 记录逻辑事件，row 格式记录行级变更结果，减少 statement 格式的非确定性风险。
    • 概念关联： MySQL 有 Redo 与 Binlog 两套提交事实，必须用两阶段提交保持一致：Redo prepare、写 Binlog、Redo commit。否则可能出现主库恢复认为提交了、从库却没有日志可复制，或相反的提交边界不一致。
    • 边界与误区： PostgreSQL 没有 MySQL Binlog 这一层，WAL 同时支撑崩溃恢复、物理复制，并可作为逻辑解码来源。不要把 Undo 说成持久性日志；它主要服务回滚和 MVCC，可见性清理还受长事务影响。
    • 记忆抓手： Redo 像“已付款但货架未摆好时的补货凭证”，Undo 像“撤销本次改价的原价记录”，Binlog 像“给其他系统看的业务流水”。类比的局限是日志不是业务单据：Redo 更接近物理页修改，Binlog 是 MySQL 逻辑事件，Undo 还参与版本可见性。真正要记住的是重做、撤销、复制三条因果链。MySQL 两阶段提交的重点是让 Redo 和 Binlog 对同一事务达成一致提交判断；PostgreSQL 则主要围绕 WAL 统一恢复和复制基础。把三者混称事务日志会掩盖层级、粒度和用途差异，也会误判故障恢复与复制恢复的边界。提交、回滚、复制分别查哪类日志，要按问题类型区分，不要混用概念和恢复流程。这能避免因果链混乱。

  • [ ] ★★ 为什么大事务风险较高？

  • 完整回答：
    • 大事务定义： 大事务指持续时间长、修改行数多或产生大量日志的事务，不一定只看 SQL 条数。
    • 锁风险： 大事务会长时间持有锁，其他事务访问相同记录、索引范围或元数据时会等待，热点表上可能迅速放大为连接堆积和接口超时。
    • 日志和回滚成本： 大事务会产生大量 Undo、Redo/WAL 和 Binlog；如果中途失败，回滚需要逐条撤销，耗时可能比执行更长，并且回滚期间仍会占用资源。
    • MVCC 清理压力： InnoDB 长事务会阻碍 Undo 历史被 purge，PostgreSQL 长事务会阻碍 vacuum 回收死元组，最终可能表现为存储膨胀、扫描变慢和复制压力上升。
    • 复制延迟： 复制系统中，大事务会形成大日志批次，从库必须重放完整事务，容易出现延迟尖刺；基于行复制时，批量修改会产生大量行事件。
    • 实践处理： 批量更新、删除、回填应分批提交，控制每批行数、耗时和影响范围；事务内不应夹杂外部接口调用、用户等待、大文件处理或复杂计算。
    • 监控指标： 需要监控事务时长、锁等待、Undo/WAL 增长、复制延迟和回滚状态。
    • 设计误区： “一个事务包住全部操作才最安全”并不总成立。过大的原子边界会牺牲可用性和恢复能力，很多批处理更适合可重入、可校验、可分批补偿的设计。

  • 原理解析：

    • 核心概念： 事务边界越大，数据库必须同时保留的锁、版本、日志和恢复信息越多。原子性增强的是这一批操作的整体提交语义，但也把失败、等待和复制延迟集中成一个更大的风险单元。
    • 运行机制： 大事务修改期间会持有行锁或范围锁，生成大量 Undo、Redo/WAL 和 MySQL Binlog。失败时回滚要按 Undo 逐步撤销；提交后从库还要按事务边界重放日志，单个巨大事务会让复制延迟呈尖刺。
    • 概念关联： MVCC 清理与事务生命周期直接相关。InnoDB 长事务让 purge 不能移除仍可能被快照读取的 Undo 版本；PostgreSQL 长事务让 vacuum 不能回收死元组。于是一个“只读但很长”的事务也可能造成膨胀和扫描变慢。
    • 边界与误区： “全部包在一个事务里最安全”忽视了可用性和恢复成本。批处理通常更适合分批提交、记录进度、幂等重跑和补偿校验；这会牺牲一次性全局原子性，但提升故障恢复和线上稳定性。
    • 记忆抓手： 大事务可以记成“四大拖累”：锁拖累并发，日志拖累提交和恢复，版本拖累清理，复制拖累从库追赶。这个抓手的局限是不同业务对原子边界要求不同，不能为了拆小而破坏不可拆的不变量；正确做法是先识别哪些操作必须同一事务，哪些可分批、可重试、可校验。

  • [ ] ★★ 什么是乐观锁和悲观锁？各适用于什么场景？

  • 完整回答：
    • 悲观锁含义： 悲观锁假设并发冲突经常发生，因此在读取或修改前先锁住目标资源，其他事务必须等待或失败。数据库中的 SELECT ... FOR UPDATE、行锁、表锁都属于悲观控制思路。
    • 悲观锁场景： 它适合冲突概率高、资源必须串行修改、重试成本高的场景，例如抢任务、关键库存行、账户余额的强约束更新。
    • 悲观锁代价： 悲观锁会带来锁等待、死锁、连接占用和吞吐下降，事务越长问题越明显。
    • 乐观锁含义： 乐观锁假设冲突较少，读取时不加排他锁，提交修改时通过版本号、时间戳、状态条件或 CAS 判断数据是否仍是自己读到的版本。
    • 典型 SQL： 乐观锁常见写法是 UPDATE t SET value = ?, version = version + 1 WHERE id = ? AND version = ?，影响行数为 0 表示发生并发修改。
    • 乐观锁场景： 它适合读多写少、冲突少、业务允许失败重试或提示冲突的场景，例如配置编辑、资料更新、低冲突订单状态流转。
    • 重试边界： 乐观锁冲突发生时需要重试或放弃，重试必须有上限和退避，业务操作也要幂等。高并发扣库存不一定适合简单版本号反复重试，因为失败重试会放大流量；常用数据库条件更新、Redis Lua、队列串行化、分段库存等组合。
    • 常见误区： 乐观锁不是没有锁，数据库执行 UPDATE 时仍会加行锁，只是冲突检测从“读前阻塞”变成“写时校验”。

  • 原理解析：

    • 核心概念： 悲观锁把冲突前置为等待或互斥，乐观锁把冲突后置为提交时校验。二者不是数据库有锁和无锁的区别，而是冲突检测发生在读前、读中还是写入条件匹配阶段的区别。
    • 运行机制： SELECT FOR UPDATE 会锁住当前读返回的行或范围，让其他事务等待。版本号乐观锁先读出版本，更新时用 WHERE id=? AND version=? 校验未被改过；影响行数为 0 表示自己的读依据已过期，需要重试或提示冲突。
    • 概念关联： 乐观锁执行 UPDATE 时数据库仍会加行锁，只是锁持有时间通常集中在写入阶段。悲观锁适合高冲突、必须串行的资源；乐观锁适合低冲突、可重试或可合并的业务。库存扣减常用条件更新，是把校验和写入合成一个原子 SQL。
    • 边界与误区： 乐观重试不是免费能力，高冲突下会放大数据库压力和应用流量，必须有上限、退避和幂等。悲观锁也不等于更安全，事务过长会带来死锁和连接占用，关键在于冲突概率、重试成本和业务可接受行为。
    • 记忆抓手： 悲观锁像“先拿钥匙再进门”，乐观锁像“出门结账时确认没人改过账单”。类比的局限是数据库执行乐观更新时仍会拿行锁，只是锁的时机更靠近写入。选型时不要问哪种高级，而要问冲突多不多、失败能不能重试、重试会不会放大热点。

  • [ ] ★★ 主从复制的基本原理是什么？如何处理复制延迟？

  • 完整回答：
    • 基本原理： 主从复制的基本思想是主库提交变更日志，从库接收或拉取日志并按顺序重放，使自己成为主库的数据副本。
    • MySQL 复制： MySQL 常见复制基于 Binlog：主库写 binlog，从库 I/O 线程获取日志，SQL 线程或多线程复制执行日志事件。
    • PostgreSQL 复制： PostgreSQL 常见物理流复制基于 WAL，从库持续接收并重放 WAL；它也支持逻辑复制发布订阅。
    • 复制模式： 复制可以是异步、半同步或同步。异步吞吐好，但主库故障时可能丢失尚未复制的事务；半同步或同步能降低丢失风险，但会增加提交延迟。
    • 延迟来源： 复制延迟可能来自网络传输、从库重放速度、单线程或分区并行限制、大事务、长事务、锁等待、从库查询负载、磁盘 I/O 和参数配置。
    • 监控方式： 处理延迟要先监控日志位点、重放位置、延迟秒数、队列长度和从库资源，而不是只看一个 seconds behind 指标。
    • 写后读一致性： 读写分离中最常见问题是写后读不一致。关键读可走主库，或按用户/会话短时间读主，或等待复制位点追上；也可以在业务上明确接受短暂旧读。
    • 降低延迟和边界： 减少延迟可拆小大事务、优化从库慢 SQL、提升从库 I/O、开启并行复制、隔离报表查询、合理配置刷盘和复制参数。不能把从库当成完全实时副本；只要不是严格同步复制，就必须在业务层定义可接受延迟和一致性兜底。
  • 原理解析：
    • 核心概念： 复制是“提交事实的日志传播和重放”。主库先接受写入并形成日志，从库按日志顺序把状态推进到相同或近似相同的位置；延迟就是从库重放位置落后于主库提交位置。
    • 运行机制： MySQL 经典复制以 Binlog 为核心，从库接收后由 SQL 线程或并行 worker 执行事件；PostgreSQL 物理流复制传输 WAL，从库持续恢复这些 WAL 记录。异步复制不等待从库确认，半同步或同步复制把部分确认纳入提交路径，因此延迟和丢失风险互相制约。
    • 概念关联： 大事务、慢查询、锁等待和 I/O 饱和会阻碍重放。读写分离的写后读问题来自“写已在主库提交，但从库尚未重放到对应位点”；解决方式要么读主，要么等待位点，要么让业务接受短暂旧读。
    • 边界与误区： seconds behind 只能粗略反映延迟，排查要看日志位点、relay 队列、replay LSN、worker 阻塞和资源指标。从库不是天然实时副本，除非业务接受同步复制带来的提交延迟和可用性取舍。
    • 记忆抓手： 主从复制按“主库记账、日志传输、从库重放、读请求命中某个进度”理解。写后读不一致发生在读请求落到尚未重放到账本位置的从库。这个抓手的局限是同步复制、逻辑复制、并行复制的等待点不同，但所有方案都要定义提交延迟、丢失风险和读一致性边界。

1.3 数据库设计

  • [ ] ★★★ 数据库三大范式是什么？为什么实际项目中有时会反范式设计？
  • 完整回答：
    • 第一范式： 第一范式要求字段保持原子性，即每个字段表达不可再分的单一值，不在一个字段里塞逗号分隔列表或结构混乱的复合数据。
    • 第二范式： 第二范式建立在有主键的关系上，要求非主属性完全依赖整个候选键，主要避免联合主键场景中某些字段只依赖主键的一部分。
    • 第三范式： 第三范式要求非主属性不传递依赖主键，即非主属性之间不应形成事实依赖，避免一个字段变化时必须同步更新多处冗余。
    • 范式化价值： 范式化可以减少数据冗余、更新异常、插入异常和删除异常，让核心事实只有一个权威来源。例如用户基础信息、商品基础信息、订单明细应有清晰实体边界和约束。
    • 反范式原因： 实际项目有时会反范式，是因为范式化模型在高频查询、复杂 join、跨库访问、报表聚合或历史快照上成本太高。
    • 典型反范式场景： 订单快照会冗余商品名、价格、地址，是为了保留交易发生时的事实；报表宽表会冗余维度字段，是为了减少在线多表 join；搜索索引和缓存表会复制部分字段，是为了满足低延迟查询。
    • 一致性代价： 反范式需要维护冗余字段一致性，可能涉及事务内同步、异步事件、Outbox/CDC、定期校验、补偿任务和版本字段约束，以处理更新失败、延迟或乱序。
    • 设计边界： 反范式不能成为随意堆宽表的理由。通常应先建立正确、约束清晰的事实模型，再针对明确性能瓶颈或历史语义做受控冗余，并说明权威来源、修复机制、字段命名和更新责任。还要区分 OLTP 与 OLAP，前者更重视写入一致性，后者常为分析查询接受宽表和预聚合。

  • 原理解析：

    • 核心概念： 范式化的目标是让事实只存一处，并用键和依赖关系表达实体边界。第一范式处理字段内部结构，第二范式处理联合键的部分依赖，第三范式处理非主属性之间的传递依赖。
    • 运行机制： 当同一事实被复制到多处，更新必须同步所有副本，否则会出现更新异常；删除某条记录时若顺带丢失仍需要的事实，就是删除异常；无法插入某个事实因为缺少另一个事实，就是插入异常。范式通过拆表和约束减少这些异常。
    • 概念关联： 反范式不是否定范式，而是在明确读性能、历史快照或跨系统边界后有意复制数据。订单快照保存交易当时价格，权威事实从“当前商品价格”变成“订单发生时价格”；报表宽表则常属于 OLAP 读取模型，不应反向污染 OLTP 权威模型。
    • 边界与误区： 受控冗余必须说明来源、更新路径、延迟边界和修复机制。事务内同步适合强一致小范围冗余，Outbox/CDC 和异步校验适合跨服务或报表。没有维护责任的宽表最终会变成不可信数据源。
    • 记忆抓手： 范式化问“这个事实的主人是谁”，反范式问“复制这个事实为谁服务、错了谁修”。类比成主本和副本有帮助，但局限是订单快照这类冗余不是副本，而是历史事实本身。只要分清权威来源、历史语义、查询模型和修复责任，就不容易把反范式变成无边界的字段堆积。设计表时可先画实体和依赖，再标注哪些冗余为性能服务、哪些为历史语义服务，两类字段的更新规则完全不同。这样也能区分 OLTP 的事实模型和 OLAP 的读取模型。

  • [ ] ★★★ 如何设计一个合理的主键？自增 ID、UUID 和分布式 ID 如何选择？

  • 完整回答：
    • 主键基本要求： 合理主键应稳定、唯一、尽量短、不可变，并适合数据库索引组织和业务生命周期。
    • 避免业务可变字段： 主键不应使用会变化的业务字段，例如手机号、邮箱、用户名，因为它们变化时会牵动外键、缓存和下游引用；业务唯一性可以用唯一索引单独约束。
    • InnoDB 成本： InnoDB 中主键是聚簇索引，所有二级索引叶子节点都会保存主键值，所以主键越长，二级索引越大，缓存命中越差。
    • 自增 ID： 趋势递增的短主键写入局部性好，页分裂少。自增 bigint 在单库单主场景简单高效，但可能暴露数据规模；多写节点或分库分表时，需要额外号段、步长或中心发号方案。
    • UUID： UUID 的优势是全局唯一、离线生成、无需中心协调，适合跨系统合并和客户端生成；代价是 128 位较长，随机 UUID 写入 InnoDB 聚簇索引会造成随机插入、页分裂和缓存抖动。可用 UUIDv7、ULID、有序 UUID 或数据库特定函数改善时间有序性。
    • 分布式 ID： Snowflake 类分布式 ID 通常由时间戳、机器号、序列号组成，趋势递增且可多节点生成，适合分布式系统；风险是时钟回拨、机器号冲突、时间位耗尽和实现不一致，需要监控和降级策略。
    • PostgreSQL 差异： PostgreSQL 默认堆表不按主键聚簇组织，但主键索引大小、外键引用和缓存成本仍受主键宽度影响。
    • 选择原则： 选择主键要结合写入模式、分片方案、可观测性、安全性、排序需求和运维能力，不能只按“自增快、UUID 分布式”简单二分。外部暴露标识也可与内部主键分离，用公开编号降低枚举和迁移风险。

  • 原理解析：

    • 核心概念： 主键既是逻辑身份，也是很多数据库内部访问路径的核心引用。稳定性保证外键和下游引用不被业务属性变化牵动；短小性降低索引、缓存和网络传输成本；唯一性和不可变性保证实体身份清晰。
    • 运行机制： InnoDB 主键就是聚簇索引键，行按主键组织，二级索引叶子保存主键值作为回表指针。因此随机、过长主键会放大二级索引并增加页分裂。PostgreSQL 默认堆表不按主键存行，但主键索引、外键索引和连接缓存仍受主键宽度影响。
    • 概念关联： 自增 ID 适合单主写入和局部性，UUID 适合去中心化生成和跨系统合并，Snowflake 类 ID 在分布式唯一性和趋势递增之间折中。选择时要同时看写入拓扑、分片路由、是否暴露给外部、排序需求和运维复杂度。
    • 边界与误区： 业务唯一键不必等于主键，手机号、邮箱、订单号可用唯一索引约束。UUIDv7、ULID、有序 UUID 能缓解随机写入，但仍更宽；Snowflake 依赖时钟和机器号管理，时钟回拨与节点冲突必须有防护。
    • 记忆抓手： 主键选择可按“四问”记忆：会不会变，够不够短，写入是否有序，是否需要跨节点生成。自增偏向单库简单高效，UUID 偏向去中心化，Snowflake 偏向分布式趋势递增。这个抓手的局限是安全暴露、分片路由、审计排序和迁移合并也会改变选择，外部编号和内部主键常需要分离。特别在 InnoDB 中，主键还是聚簇键和二级索引载荷，所以“短、稳定、趋势递增”不是审美偏好，而是会落到页分裂、缓存命中和索引体积上。PostgreSQL 虽不按主键聚簇，宽主键仍会影响索引和外键引用成本。

  • [ ] ★★ 分库分表会带来哪些问题？

  • 完整回答：
    • 收益和本质代价： 分库分表可以缓解单库容量、单表索引膨胀、写入吞吐和热点压力，但也会把数据库原本提供的许多简单能力变成分布式问题。
    • 路由复杂度： 所有查询都要根据分片键定位目标库表；没有分片键的查询可能退化为广播，成本和故障面都会变大。
    • 分片键选择： 按用户、订单、时间或哈希分片都有取舍，选错会造成热点、数据倾斜或大量跨分片访问。
    • 查询能力下降： 跨库 join、跨分片聚合、全局排序和分页都需要应用层或中间件归并，深分页尤其昂贵。
    • 事务复杂化： 单库事务无法天然覆盖多个分片，通常要使用最终一致性、事务消息、Saga/TCC、幂等和补偿，开发成本高于本地事务。
    • 全局约束重设计： 全局唯一 ID、唯一约束、外键约束都要重新设计。例如手机号全局唯一不能只靠单分片唯一索引。
    • 扩容和运维成本： 扩容迁移需要重分片、双写、数据校验、灰度切流和回滚预案；备份恢复、监控告警、SQL 审计、数据修复和故障定位也会更难。
    • 使用前提： 分库分表通常应放在单库索引优化、SQL 优化、冷热拆分、读写分离、缓存和硬件升级之后考虑，并且要有明确容量指标和增长预测支撑。

  • 原理解析：

    • 核心概念： 分库分表把一个数据库内的局部问题，换成多个节点之间的路由、一致性和运维问题。它能分散容量与写入压力，但也削弱单库天然提供的 join、事务、唯一约束和统一查询能力。
    • 运行机制： 查询必须先根据分片键定位分片；缺少分片键时只能广播或维护额外索引表。聚合、排序、分页要在各分片局部执行后再归并，全局深分页会让每个分片都扫描和返回候选集，成本随分片数放大。
    • 概念关联： 本地事务只覆盖单分片，多分片写入需要最终一致性、事务消息、Saga/TCC、幂等和补偿。全局唯一约束也不再天然成立，若手机号要全局唯一，就需要中心校验、唯一键服务、全局索引或按手机号路由。
    • 边界与误区： 分库分表不是性能优化第一步。单库索引、SQL、冷热拆分、归档、读写分离、缓存和硬件扩展成本更低。只有容量、吞吐或增长预测明确超过单库可承受范围时，才值得承担迁移、扩容、备份和故障定位复杂度。
    • 记忆抓手： 分库分表可以记成“容量换复杂度”。容量压力、索引膨胀和写入热点被分散，但查询路由、全局约束、跨分片事务和运维恢复都要应用或中间件接手。这个抓手的局限是某些 SaaS 多租户或合规隔离会因组织边界提前分库，那时目标不是纯性能，而是隔离性和治理。

  • [ ] ★★ 水平分表和垂直分表有什么区别？

  • 完整回答：
    • 水平分表定义： 水平分表是按行拆分，把结构相同的数据按某种规则分散到多张表或多个库中，例如按用户 ID 哈希、订单 ID 取模、创建时间分月。每个分片保存部分行，表结构通常一致。
    • 水平分表解决的问题： 它主要解决单表数据量过大、索引层级和维护成本上升、单点写入吞吐不足等问题。
    • 水平分表代价： 水平拆分后需要分片路由、跨分片查询、全局排序分页、扩容迁移和分布式事务处理。
    • 垂直分表定义： 垂直分表是按列或业务实体拆分，把一张宽表中访问频率、字段体积或业务归属不同的字段拆到不同表中，例如用户基础表与用户扩展表、订单主表与订单备注/大 JSON 表。
    • 垂直分表解决的问题： 它主要解决表过宽、冷热字段混杂、缓存页利用率低和模块边界不清的问题。
    • 垂直分库： 垂直分库进一步按业务域拆到不同数据库或服务，能隔离负载和权限，但跨库 join、跨库事务和数据一致性会变复杂。
    • 选择依据： 如果瓶颈是单表行数、写入压力和容量增长，偏向水平拆；如果瓶颈是行太宽、大字段拖慢主查询、业务模块耦合，偏向垂直拆。
    • 拆分边界： 两者可以组合使用，但不应过早拆分，因为拆分后的查询能力、事务边界和运维复杂度都会显著上升。
  • 原理解析：
    • 核心概念： 水平拆分改变的是行的归属，把同构数据分散到多个分片；垂直拆分改变的是列或业务边界，把不同访问频率、字段体积或领域责任的数据拆开。判断维度是“行太多”还是“行太宽、职责太混”。
    • 运行机制： 水平分表依赖分片键路由，命中单分片时收益明显；跨分片查询则需要广播和归并。垂直分表常用同一主键一对一拆出扩展表，大字段或低频字段不再拖累主表页缓存，提高高频查询的页利用率。
    • 概念关联： 垂直分库比垂直分表更进一步，把业务域和负载隔离到不同库或服务，同时也把本地 join 和事务变成跨库问题。水平拆分常与分布式 ID、全局索引、路由中间件和扩容迁移方案绑定。
    • 边界与误区： 两种拆分可以组合，但拆得越早，查询能力和开发复杂度越早受限。应先用指标确认瓶颈：单表行数、索引大小、写入 TPS 指向水平拆；宽行、大字段、冷热字段混杂和模块耦合指向垂直拆。
    • 记忆抓手： 水平拆分问“这批行去哪个分片”，垂直拆分问“这些列是否属于同一访问路径或业务责任”。前者像按地区分仓，后者像把前台柜台和后台档案室分开；类比的局限是数据库拆分还涉及事务、索引、路由和迁移，不只是物理摆放。判断时回到瓶颈指标比凭表名直觉更可靠。
