学习目标

  • 理解半包、粘包的本质来自 TCP 字节流。
  • 掌握定长、分隔符、长度字段三类 framing 方法。
  • 能设计包含字节序、校验、版本兼容和序列化选择的协议。
  • 能写出健壮解码器的核心逻辑。

核心原理

半包粘包本质

TCP 只保证字节顺序，不保证业务消息边界。

发送端：

send(msg1) send(msg2)

接收端可能看到：

read: msg1 的一半
read: msg1 剩余 + msg2
read: msg2 的一部分

这不是 TCP 的 bug，而是字节流协议的正常行为。应用层必须定义 framing。

增量解析的状态

健壮解码器不能依赖一次 read 得到完整消息。它通常维护一个可增长输入缓冲区和解析游标，每次读入新字节后尝试解析零个、一个或多个 frame。解析失败要区分“数据还不够”和“协议错误”，前者保留缓冲区等待下次读，后者关闭连接并记录原因。

append bytes -> while can parse header/body -> emit frame -> compact buffer

如果解析器在半包时丢弃缓冲区，或者把协议错误当成 NeedMore，都会造成请求丢失、连接卡住或内存被恶意输入拖大。

三类 framing

方法 格式 优点 风险
定长 每条消息固定 N 字节 解析简单 浪费空间，不适合变长
分隔符 payload 后跟 \n 或 \r\n 文本协议友好 payload 转义、超长行攻击
长度字段 header 中写 payload 长度 通用高效 要校验长度、字节序和整数溢出

网络服务最常见的是长度字段协议。

framing 的攻击面

分隔符协议要限制最大行长，否则对端一直不发送分隔符会让缓冲区无限增长。长度字段协议要先检查 header，再检查 len <= maxFrameSize，再判断完整 payload 是否到达。任何乘法、加法或 readableBytes - headerSize 都要先防止整数溢出和无符号下溢。

字节序

协议中的整数要明确端序。常见选择是网络字节序，即大端。不要把主机内存结构体直接 send 出去，因为结构体有字节序、对齐、padding 和 ABI 问题。

校验

校验用于发现数据损坏或协议错位。常见层次：

  • TCP checksum：传输层已有，但应用无法依赖它做业务完整性。
  • magic number：快速判断是否对齐到本协议。
  • header checksum 或 payload checksum：发现应用层数据损坏。
  • 认证码或签名：防篡改，需要密码学设计，不能用普通 CRC 替代。

版本兼容

协议演进要考虑：

  • header 带 version。
  • 增加字段时保持旧客户端可忽略。
  • 删除字段要经历兼容窗口。
  • 长度字段允许跳过未知扩展。
  • 错误码和能力协商比“猜对端版本”更可靠。

序列化与 Protobuf

序列化解决对象到字节的映射。常见选择：

  • JSON：可读，调试友好，体积和解析成本较高。
  • Protobuf：二进制紧凑，IDL 明确，跨语言友好。
  • FlatBuffers/Cap'n Proto：强调少拷贝访问，使用复杂度更高。

Protobuf 负责消息体结构，不负责 TCP framing。即使用 Protobuf，外层仍然需要长度字段或其他边界定义。具体语法和兼容规则以官方文档为准。

Protobuf 演进边界

Protobuf 的字段编号是兼容性的核心资产，删除字段后不要复用 tag；新增字段通常能被旧端忽略，但“字段含义改变”“必填语义改变”“枚举默认值改变”仍可能破坏业务。协议演进应配合版本、能力协商或灰度发布，而不是只依赖序列化库。

工程实践/示例

一个长度字段协议

0        4        6        8        12
+--------+--------+--------+--------+-----------+
| magic  | ver/u16| type/u16| len/u32 | payload  |
+--------+--------+--------+--------+-----------+

规则：

  • 所有整数使用网络字节序。
  • magic 固定为协议标识。
  • len 是 payload 长度，不包括 header。
  • len 必须小于等于配置的 maxFrameSize。
  • 解码器必须能在数据不足时保留缓冲区等待下次读。

健壮解码器思路

enum class DecodeResult {
    NeedMore,
    GotFrame,
    ProtocolError
};

DecodeResult tryDecode(Buffer& in, Frame& out) {
    constexpr size_t kHeaderSize = 12;
    constexpr uint32_t kMagic = 0x12345678;
    constexpr uint32_t kMaxFrame = 8 * 1024 * 1024;

    if (in.readableBytes() < kHeaderSize) return DecodeResult::NeedMore;

    uint32_t magic = in.peekU32BE(0);
    if (magic != kMagic) return DecodeResult::ProtocolError;

    uint16_t version = in.peekU16BE(4);
    uint16_t type = in.peekU16BE(6);
    uint32_t len = in.peekU32BE(8);

    if (!isSupportedVersion(version)) return DecodeResult::ProtocolError;
    if (len > kMaxFrame) return DecodeResult::ProtocolError;
    if (in.readableBytes() - kHeaderSize < len) return DecodeResult::NeedMore;

    in.retrieve(kHeaderSize);
    out.version = version;
    out.type = type;
    out.payload = in.readBytes(len);
    return DecodeResult::GotFrame;
}

注意 in.readableBytes() - kHeaderSize 前必须保证 readableBytes >= kHeaderSize，避免无符号下溢。

解码循环

void onBytes(Buffer& input) {
    while (true) {
        Frame frame;
        DecodeResult r = tryDecode(input, frame);
        if (r == DecodeResult::NeedMore) break;
        if (r == DecodeResult::ProtocolError) {
            closeConnection();
            break;
        }
        dispatch(frame);
    }
}

编码路径

编码也要做边界检查。发送前先序列化 payload，检查大小，再写 header 和 payload：

bool encode(const Frame& frame, Buffer& out) {
    if (frame.payload.size() > kMaxFrame) return false;
    out.appendU32BE(kMagic);
    out.appendU16BE(frame.version);
    out.appendU16BE(frame.type);
    out.appendU32BE(static_cast<uint32_t>(frame.payload.size()));
    out.append(frame.payload);
    return true;
}

这段省略了 checksum 和压缩。返回 false 表示本地要发送的消息已经违反协议上限，通常应转成内部错误，而不是把超大 frame 写给对端。

故障排查/观测

协议错误定位

协议日志不要直接打印完整 payload，容易泄露隐私并放大日志量。建议记录连接 id、frame type、version、payload length、decode result、错误 offset、magic 是否匹配和缓冲区长度。必要时用采样十六进制 dump 头部少量字节。

测试矩阵

最小测试应覆盖：空输入、半个 header、完整 header 半个 body、一次多个 frame、错误 magic、不支持版本、超大 len、len 边界值、随机分片输入。对长度字段解码器，属性测试可以验证“任意分片后的输出消息序列等于完整输入解析结果”。

推导示例

为什么先检查长度再分配

错误做法是读取 len 后立即 resize(len)。恶意客户端只要发送一个很大的长度字段，就能让进程分配巨量内存。正确顺序是：确认 header 完整，解析长度，检查 len <= maxFrameSize，确认缓冲区里已有足够 payload，再移动或复制 payload。

header complete -> validate magic/version/len -> wait body -> emit frame

协议升级的灰度窗口

新增字段时，先让服务端能读旧新两种格式，再灰度客户端发送新字段，最后观察旧版本流量归零后才清理兼容路径。删除字段或改变枚举语义更危险，需要保留 reserved tag、兼容错误码和回滚方案。

如何讲粘包

“粘包”不是 TCP 把包粘坏了，而是应用把字节流误认为消息流。回答时先说明 TCP 只保证有序字节，再说明应用层 framing，最后给出增量解析和最大 frame 限制，才能覆盖正确性和安全边界。

最小验收清单

  • 解码器能返回 NeedMore/GotFrame/ProtocolError。
  • 长度字段有端序、上限和溢出检查。
  • Protobuf 外层仍有 framing。
  • 测试覆盖随机分片和多 frame 输入。

常见误区

  • 认为 Protobuf 自动解决粘包。
  • 直接发送 C++ 结构体内存。
  • 不限制 frame 长度，给恶意客户端 OOM 入口。
  • 忽略整数溢出和无符号下溢。
  • 协议升级时只改服务端，不考虑旧客户端和灰度窗口。

自测题

  1. 半包和粘包为什么是应用层必须处理的问题？
  2. 分隔符协议如何防止超长行攻击？
  3. 长度字段为什么要有最大值？
  4. Protobuf 的 tag 兼容机制能解决哪些问题，不能解决哪些问题？
  5. 为什么不能直接 send(&obj, sizeof(obj), 0)？
