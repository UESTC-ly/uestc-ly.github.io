5. 缓存与 Redis

  • [ ] ★★★ 为什么 Redis 很快？
  • 完整回答：
    • Redis 快首先来自访问路径短：核心数据常驻内存，普通读写不需要像数据库那样先做磁盘页定位、事务日志协调和复杂执行计划，内存随机访问延迟远低于磁盘和网络存储。
    • 其次，Redis 的数据结构实现针对缓存场景做了大量工程优化，String、Hash、List、Set、Sorted Set 会根据对象大小和元素数量选择紧凑编码或跳表、哈希表等结构，常见命令的时间复杂度可控。
    • 经典 Redis 的命令执行线程是单线程串行模型，配合事件循环和 I/O 多路复用处理大量连接，避免了多线程共享状态下的锁竞争、上下文切换和内存可见性成本，也让单条命令具备天然原子性。
    • Redis 6 之后可以启用 I/O 线程分担读写网络数据，RDB、AOF 重写、惰性释放、异步删除等工作也可能由后台线程处理，但命令逻辑执行仍主要按串行原子片段理解。
    • 它的快也有边界：大 Key、KEYS、SMEMBERS 这类全量操作、复杂 Lua、慢磁盘持久化、网络包过大、客户端连接池配置不当、Cluster 热点槽位和主从复制积压，都会把瓶颈从内存访问转移到 CPU、网络、磁盘或事件循环阻塞上。
    • Pipeline 和批量命令能减少网络往返，但批量过大也会造成单次响应过慢和缓冲区膨胀。
    • 部署在云 Redis 或跨机房链路时，网络延迟还可能超过命令本身成本。
    • 把 Redis 当缓存时要关注命中率、P99 延迟、慢日志、内存碎片、淘汰次数和网络吞吐，而不是只看“单线程内存数据库”这个标签。

  • 原理解析：

    • 核心抽象是“内存数据结构服务器”，不是带缓存功能的关系库。一次命令通常沿着客户端连接、事件循环、命令解析、对象操作、响应写回这条短路径走完，避开磁盘页、SQL 优化器、锁管理和事务隔离的大量成本。
    • 数据结构层用 SDS、dict、quicklist、listpack、skiplist、intset 等实现承接上层类型，小对象走紧凑编码，大集合再切换到通用结构，所以快来自“数据在内存里”加“常见操作复杂度低”，不是所有命令都天然 O(1)。
    • 事件循环和 I/O 多路复用把大量连接映射为少量线程处理；Redis 6 起网络读写可用 I/O 线程分摊，但命令执行仍按串行原子片段理解。因果链是少锁竞争、少上下文切换、状态集中，换来单命令快和行为可预测，也让慢命令影响容易沿同一个事件循环扩散。
    • 失败边界在“阻塞事件循环”：大 Key、全量扫描、慢 Lua、fork 写时复制、AOF fsync、复制积压、Cluster 热点槽都会让 CPU、网络、磁盘或单槽位成为瓶颈。Pipeline 只能减少往返，不能消除单次命令本身的 CPU 和响应体成本。记忆抓手：Redis 快是短路径、好结构、事件循环，慢也常慢在这三处被拉长。

  • [ ] ★★★ Redis 常用数据结构及其典型场景有哪些？

  • 完整回答：
    • Redis 不是单纯的字符串 KV，而是提供一组带操作语义的数据结构。
    • String 是最基础结构，可保存字节串、JSON、序列化对象、计数器、验证码、令牌和分布式锁随机值，INCR、SET NX PX 等命令适合做原子计数和租约式写入，但把完整大对象都塞进一个 String 会形成大 Key，增加网络和阻塞风险。
    • Hash 用字段组织对象，适合用户资料、配置项、商品属性等字段级读写，字段数量较少时编码紧凑，字段过多或单字段很大时同样会拖累迁移、删除和持久化。
    • List 按插入顺序组织元素，可做简单队列、最新列表和时间线片段，但可靠消息、重复消费、堆积监控等能力不如 Stream 或专用 MQ。
    • Set 适合去重集合、标签、共同好友、抽奖候选池和随机抽样；Sorted Set 给每个成员维护分数，常用于排行榜、延迟任务、时间范围索引和优先级队列，代价是写入、重排和范围查询需要维护有序结构。
    • Bitmap 本质上基于 String 的位操作，适合签到、在线状态、布尔特征统计；HyperLogLog 适合 UV 等基数估算，占用小但有误差且不能列元素；Geo 基于 Sorted Set 编码地理位置；Stream 提供消息 ID、消费组、确认和回放，适合轻量事件流。
    • 选择结构时要同时看操作复杂度、元素规模、过期策略、是否跨 Key、Cluster 槽位限制和后续删除迁移成本，不能只按名字套场景。

  • 原理解析：

    • Redis 类型是“命令语义 + 底层编码”的组合：String 负责字节串和原子数值操作，Hash 负责字段级对象，List 表达顺序，Set 表达无序去重，ZSet 表达“成员 + 分数”的有序集合；Bitmap、HLL、Geo、Stream 是在这些基础结构上延伸出的特化抽象。
    • 选择结构要先看访问模式。计数用 INCR，对象字段更新用 Hash，排行榜和延迟队列常用 ZSet，轻量事件流用 Stream，签到用 Bitmap，UV 估算用 HLL。结构选错会把本来局部更新变成大对象整体读写，也会让过期、复制和持久化都按更粗粒度承压。
    • 底层数据会随规模切换：小 Hash/List/ZSet 可用 listpack 这类紧凑编码，放大后转成哈希表、quicklist、跳表等结构。因果链是节省内存与维持复杂度之间折中，元素越大，迁移、复制、持久化和删除成本越突出。
    • Cluster 部署下还要看 Key 分布和跨槽限制，多 Key 命令、事务和 Lua 通常要求同槽；Hash Tag 虽能把相关 Key 放到同槽，但也可能制造热点。缓存场景的记忆抓手是“按操作语义选类型，按规模边界拆 Key”，不要把 Redis 当万能 JSON 仓库。

  • [ ] ★★★ 什么是缓存穿透、缓存击穿和缓存雪崩？如何解决？

  • 完整回答：
    • 缓存穿透是查询的数据在缓存和数据库中都不存在，攻击流量或异常参数每次都绕过缓存打到数据库，例如随机用户 ID、非法商品 ID。
    • 常见处理是入口参数校验、权限和格式拦截、缓存空值、布隆过滤器或预加载合法 ID 集合；空值缓存要设置较短 TTL，并在真实数据新增时主动删除或刷新，否则会让新数据短时间不可见。
    • 缓存击穿是单个热点 Key 过期或被删除后，大量并发请求同时回源重建，把数据库或下游服务压垮。
    • 解决方式包括互斥重建、请求合并、逻辑过期加异步刷新、热点 Key 续期、后台预热和返回短时间旧值；互斥锁要设置超时，避免重建线程失败后所有请求长期等待。
    • 缓存雪崩是大量 Key 在相近时间失效，或 Redis 节点、网络、客户端连接池整体异常，导致海量请求同时回源。
    • 治理手段包括 TTL 加随机抖动、分批预热、多级缓存、本地兜底、限流、熔断、降级、连接池隔离和数据库保护阈值。
    • 如果是 Cluster 或主从架构，还要考虑节点故障、槽位迁移和读副本延迟造成的局部雪崩。
    • 逻辑过期方案能改善可用性，但会允许短时间返回旧值，需要业务接受这个一致性边界。
    • 三者的差异在于穿透关注“不存在数据”、击穿关注“单个热点失效”、雪崩关注“大范围失效或缓存层不可用”。
    • 工程误区是只给 Redis 加机器而不控制回源路径：当缓存完全不可用时，数据库是否能承受最低核心流量、服务是否能快速失败、降级返回是否符合业务预期，都必须提前压测和演练。

  • 原理解析：

    • 三个概念都描述“缓存未挡住流量后，下游被放大”的不同形态。穿透是数据本就不存在，命中不了任何缓存；击穿是单个热点 Key 突然失效；雪崩是大量 Key 或缓存层整体同时失效，影响面从点扩大到面。判断时先问“问题数据是否存在、是否只有一个热点、是否是成片失效”，再决定是拦请求、护重建还是保容量与降级演练预案。
    • 穿透的因果链是非法请求绕过缓存直接查库，所以用参数校验、空值缓存、布隆过滤器把“不可能存在”挡在入口。空值和过滤器都要处理新增数据，否则会把后来的真数据短期挡掉；空值 TTL 过长还会扩大这种不可见窗口。
    • 击穿的关键是“热点 + 失效 + 并发回源”，互斥重建、逻辑过期、请求合并和旧值兜底是在保护重建路径。互斥锁必须有超时和失败回退，否则保护机制本身会变成排队点；逻辑过期则要接受短时间旧值。
    • 雪崩更像容量事故，需要 TTL 抖动、多级缓存、限流熔断、降级和数据库保护阈值一起工作。Cluster、主从、读副本也可能因节点故障、槽位迁移或复制延迟形成局部雪崩。所有方案都要压测“Redis 不可用时数据库能扛多少核心流量”。记忆抓手：穿透防不存在，击穿护热点，雪崩保全局，最终都要保护回源链路。

  • [ ] ★★★ 如何保证缓存与数据库的一致性？

  • 完整回答：
    • 普通缓存架构很难保证缓存和数据库强一致，因为两者不是同一个事务系统，网络失败、并发读写、主从延迟、进程崩溃和消息乱序都会制造不一致窗口。
    • 常见的旁路缓存模式是读请求先查缓存，未命中再查数据库并写入缓存；写请求先更新数据库，再删除缓存，让后续读按新数据重建缓存。
    • 这个顺序通常比“先删缓存再更新数据库”更稳，因为后者可能在数据库更新前被并发读查到旧值并回填旧缓存。
    • 但“先更新数据库再删缓存”也不是绝对保证，删除失败、删除后旧读请求晚到、数据库从库延迟、缓存重建乱序都会产生短暂脏读。
    • 增强手段包括删除失败重试、把删除操作写入可靠消息或本地事务表、订阅 binlog/CDC 进行失效、给缓存设置合理 TTL、对读写链路做幂等和版本号校验、在缓存值中携带更新时间或逻辑版本，并定期对账修复。
    • 延迟双删可以缓解部分并发场景，但延迟时间依赖经验和业务耗时，不是形式化的一致性证明。
    • 更新缓存而不是删除缓存适合简单、单写源、计算确定的场景；如果缓存是聚合结果或多服务都能写数据库，直接更新缓存更容易被并发顺序覆盖。
    • 多级缓存还要同步处理本地缓存、网关缓存和 CDN 的失效顺序，否则 Redis 删除成功也可能继续返回旧数据。
    • 对余额、库存最终扣减、权限生效等强一致要求高的路径，不应依赖普通缓存作为唯一读依据，可以降低缓存参与度、走数据库事务、加唯一约束或使用具备一致性协议的专门系统。
    • 缓存一致性设计的目标通常是限定最大脏读时间、保证最终收敛和失败可补偿，而不是承诺永远读到最新值。

  • 原理解析：

    • 核心抽象是旁路缓存的“双系统状态”：数据库是真实写入源，Redis 是可丢失、可重建的派生副本。两者没有共享事务日志，也没有统一提交点，所以一致性只能设计成有界不一致和最终收敛。
    • 常见因果链是读 miss 后回填，写先落库再删缓存。先删缓存再写库容易被并发读用旧库值回填；先写库再删缓存把旧值窗口压到删除失败、晚到读、从库延迟和重建乱序这些边界。这个顺序减少风险，但并不消灭并发窗口，因此需要把失败重试和版本校验放进设计。
    • 补偿机制要围绕失败点布置：删除失败可重试或写本地事务表，数据库 binlog/CDC 可异步失效，缓存值可带版本号或更新时间，TTL 负责兜底收敛。延迟双删只是经验性缓解，不是强一致证明。
    • 多级缓存会扩大失效链路，本地缓存、网关、CDN 与 Redis 都可能各自残留旧值。余额、权限、库存最终扣减等强一致路径不能把 Redis 命中当最终裁决，应回到数据库事务、唯一约束、状态机和幂等补偿。
    • 记忆抓手：缓存一致性不是“永远最新”，而是回答三个问题：谁是事实源、旧值最多活多久、删除或消息失败后怎么补。能把脏读时间、补偿路径和对账机制说清楚，比承诺强一致更符合普通 Redis 缓存模型。

  • [ ] ★★★ Redis 的过期删除和内存淘汰策略有哪些？

  • 完整回答：
    • Redis 的过期删除解决“设置了 TTL 的 Key 到期后何时移除”，主要由惰性删除和定期删除配合完成。
    • 惰性删除是在访问 Key 时检查是否过期，过期则删除并返回不存在，优点是只处理被访问的数据，缺点是长期不被访问的过期 Key 可能继续占内存。
    • 定期删除由服务端周期性抽样检查带过期时间的 Key，并在时间预算内清理过期数据；它不是全量实时扫描，所以 Key 到期不代表物理内存立即释放。
    • 内存淘汰发生在实例达到 maxmemory 限制且需要写入时，Redis 按 maxmemory-policy 选择牺牲哪些 Key。
    • 常见策略有 noeviction，内存不足时拒绝会增加内存的写命令；volatile-lru、volatile-lfu、volatile-random、volatile-ttl 只在设置了过期时间的 Key 中淘汰；allkeys-lru、allkeys-lfu、allkeys-random 可从全体 Key 中淘汰。
    • LRU 和 LFU 都是近似实现，不是精确全局排序，LRU 更关注最近访问，LFU 更关注访问频次并带衰减机制，适合稳定热点但对流量突变有滞后。
    • 纯缓存通常选择 allkeys-lru 或 allkeys-lfu，避免没有 TTL 的 Key 挤占空间；会话、配置、计数或混合用途要谨慎使用自动淘汰，否则可能删除业务仍需要的数据。
    • 过期和淘汰还会影响复制、AOF、RDB 和延迟表现，大量同时过期可能造成 CPU 抖动，大 Key 被删除可能阻塞或产生异步释放压力，因此 TTL 应避免集中，删除大对象应优先考虑 UNLINK 或分批拆分。

  • 原理解析：

    • 过期删除和内存淘汰解决的是两个不同问题：TTL 到期后如何清走无效 Key，实例触达 maxmemory 后如何为新写入腾空间。前者由过期字典驱动，后者由淘汰策略驱动，不能混成“过期就等于释放内存”，也不能以为设置 TTL 就不会触发淘汰。
    • 惰性删除把检查放在访问时，定期删除按时间预算抽样扫描过期 Key。因果链是减少全量扫描成本，但代价是过期 Key 可能短暂留在内存里，集中到期时还会带来 CPU 抖动。因此 TTL 设计要加随机抖动，不能让大批 Key 在同一秒集中失效。
    • 淘汰策略按候选范围和选择算法组合：volatile-* 只淘汰有 TTL 的 Key，allkeys-* 面向全体 Key，noeviction 直接拒绝增量写入。LRU/LFU 是采样近似，不是全局精确排名，LFU 还有频次衰减。
    • 失败边界在混合用途实例：自动淘汰可能删除会话、配置或计数状态；大 Key 淘汰或过期删除可能阻塞事件循环、放大复制和 AOF 压力。UNLINK 和分批拆分能降低删除阻塞，但不能改变对象过大带来的复制与迁移成本。记忆抓手：到期靠过期机制，内存满靠淘汰策略，二者都受大 Key 和集中 TTL 影响。

  • [ ] ★★★ Redis 的 RDB 和 AOF 有什么区别？

  • 完整回答：
    • RDB 是快照持久化，把某一时刻的数据集保存成紧凑的二进制文件，适合备份、全量复制和快速恢复。
    • 它通常由后台 fork 子进程生成，子进程遍历内存写文件，主进程继续处理请求；代价是 fork 本身、写时复制带来的额外内存峰值以及磁盘 I/O。
    • RDB 的弱点是两次快照之间的数据在故障时可能丢失，快照间隔越长，丢失窗口越大。
    • AOF 是追加命令日志，记录会修改数据的写命令，重启时重放日志恢复数据；它可以配置 appendfsync always、everysec 或 no，分别在可靠性和性能之间取舍，常见 everysec 仍可能丢约一秒内的数据，并且还受操作系统、磁盘和虚拟化环境影响。
    • AOF 文件会增长，需要 rewrite 把历史命令压缩为等价的当前状态；rewrite 也有后台进程、缓冲增量和磁盘写入成本。
    • Redis 4 以后支持混合持久化，AOF 重写文件前半部分可使用 RDB 格式作为基线，后面追加增量 AOF，兼顾加载速度和较小丢失窗口。
    • RDB 和 AOF 都不能简单等同关系数据库事务日志：Redis 默认异步复制，持久化刷盘也依赖配置，进程宕机、机器断电、磁盘损坏和主从切换都可能丢数据。
    • 只做缓存时可以弱化持久化，甚至关闭以降低延迟和磁盘成本；承载会话、限流状态、库存预扣等重要数据时，必须明确可接受丢失窗口，配置备份、监控 AOF rewrite、校验恢复流程，并把最终正确性放在数据库、幂等和补偿机制上。

  • 原理解析：

    • RDB 的抽象是“某一时刻的全量快照”，AOF 的抽象是“写命令追加日志”。前者适合备份、复制基线和快速装载，后者更关注缩短故障丢失窗口；两者都服务于 Redis 自身恢复，不等价于关系库强事务日志，也不能替代业务层幂等和补偿设计。
    • RDB 通常 fork 子进程遍历内存写文件，主进程继续服务。因果链是低侵入生成快照，但 fork、写时复制和磁盘 I/O 会造成内存峰值与延迟抖动，且两次快照之间的数据可能丢失。数据集越大、写入越活跃，写时复制放大的内存压力越明显。
    • AOF 通过 appendfsync always/everysec/no 在可靠性与性能间取舍，文件增长后靠 rewrite 压缩历史命令。Redis 4 以后常见混合持久化，用 RDB 做重写基线再追加 AOF 增量，兼顾加载速度和较小恢复窗口。
    • 失败边界包括断电、磁盘损坏、虚拟化刷盘语义、AOF rewrite 异常和主从切换数据丢失。只做缓存时可弱化持久化；承载重要状态时要先定义可丢窗口，并通过备份、恢复演练、监控 rewrite 与磁盘延迟来闭环。记忆抓手：RDB 像照片，AOF 像流水账，混合模式是照片加后续流水。

  • [ ] ★★★ Redis 主从复制、哨兵和 Cluster 分别解决什么问题？

  • 完整回答：
    • 主从复制解决的是副本和读扩展问题：一个主节点接收写入，从节点异步复制主节点数据，可用于读分担、备份、故障恢复基础和全量同步来源。
    • 它的边界是复制通常异步，主节点返回写成功时从节点未必已经收到，主从延迟会导致读从库读到旧数据，主节点宕机后最近写入也可能在切换中丢失。
    • 哨兵建立在主从复制之上，负责监控主从状态、主观和客观下线判断、选举哨兵 leader、提升某个从节点为新主，并通知客户端新的主节点地址。
    • 哨兵解决的是高可用和主节点发现，不解决单主写入容量和单实例内存上限；故障转移期间可能短暂不可写，客户端也要正确处理重连、旧主降级和配置刷新。
    • Cluster 解决的是水平分片和一定的高可用，把 16384 个哈希槽分布到多个主节点，每个主节点可以带从节点，客户端根据槽位路由请求，并处理 MOVED、ASK 等重定向。
    • Cluster 能扩展总内存和写入吞吐，但不是强一致分布式数据库：跨槽多 Key 操作受限制，事务、Lua、批量命令通常要求 Key 在同一槽，网络分区、复制延迟和故障转移仍可能带来短暂不可用或数据丢失。
    • 选择方案要先区分目标：单机加副本适合读扩展和备份，哨兵适合单主高可用，Cluster 适合容量和写压力已经超过单主边界的场景。
    • 实际部署还要关注客户端拓扑感知、复制 backlog、哨兵数量、故障转移参数、槽位迁移、热点 Key、读写分离规则和持久化配置，否则“有副本”并不等于业务连续。

  • 原理解析：

    • 三者分别对应三个层级：主从复制解决副本与读扩展，哨兵解决单主架构的自动故障转移和主节点发现，Cluster 解决容量与写入吞吐的水平分片。先分清目标，才能选部署模式；把它们混说成“高可用”会忽略容量、路由和一致性边界，面试和设计评审都容易误判风险。
    • 复制链路包含全量同步、增量同步、复制 backlog、复制偏移量等机制。主节点写成功不等于从节点已持久收到，读从库会遇到延迟，故障切换也可能丢最后一段异步复制数据。复制 backlog 太小或断线太久会退化为全量同步，进一步放大网络和磁盘压力。
    • 哨兵通过主观下线、客观下线、leader 选举和从节点晋升完成高可用。因果链是监控发现故障、达成多数判断、挑选新主、通知客户端；边界是切换期间短暂不可写、旧主回归后的角色修正和客户端拓扑刷新，业务侧还要处理重连和重试的幂等。
    • Cluster 用 16384 个哈希槽路由 Key，节点迁移时客户端要处理 MOVED/ASK。它扩容的是总内存和多主写入，不提供跨槽强事务；多 Key、Lua、事务通常要同槽，热点 Key 也不会因为槽多而自动拆散。记忆抓手：复制保副本，哨兵保主从可用，Cluster 保分片容量。

  • [ ] ★★★ 如何使用 Redis 实现分布式锁？

  • 完整回答：
    • Redis 分布式锁的基本做法是用一条原子命令完成加锁和设置租约，例如 SET lock:key token NX PX ttl：只有 Key 不存在时写入成功，token 是客户端生成的唯一随机值或请求 ID，ttl 防止持锁方崩溃后锁永久不释放。
    • 解锁不能直接 DEL，必须用 Lua 脚本先比较当前值是否等于自己的 token，再删除 Key，避免线程 A 的锁过期后线程 B 已重新加锁，线程 A 结束时误删线程 B 的锁。
    • 业务执行时间可能超过 TTL 时，需要续期机制，续期同样要校验 token，并设置最大续期次数或总租约边界，防止进程卡住后长期占锁。
    • 加锁失败时要采用有限重试、退避和超时返回，不能让请求无限等待；锁粒度也要足够细，避免把无关资源串行化。
    • 这个方案适合防重复提交、任务调度去重、弱互斥资源保护等工程场景，但不能承诺绝对互斥：Redis 主从复制是异步的，主节点刚写入锁后宕机，提升的从节点可能没有这把锁；客户端 GC 暂停、网络分区、时钟和调度抖动可能导致锁已经过期但业务仍在执行；持久化配置也不能保证锁状态零丢失。
    • Redlock 通过多个独立 Redis 节点投票降低单点风险，但其正确性依赖租约时间、时钟漂移和故障模型，业界也有争议，不能替代严格一致系统。
    • 强一致资源保护应考虑数据库条件更新、唯一约束、状态机、ZooKeeper/etcd 租约或业务幂等补偿。
    • 实践中应把 Redis 锁视为降低并发冲突的协调手段，而不是最终正确性的唯一边界。

  • 原理解析：

    • Redis 锁的核心抽象是“带租约的互斥标记”，不是永久所有权。SET key token NX PX ttl 把不存在才写入、唯一持有者标识、自动过期合成一条原子命令，避免加锁和设置过期分两步时留下死锁。这里的 ttl 是安全边界，也是并发窗口的来源。
    • 解锁必须比较 token 再删除，通常用 Lua 保证读值和删除在 Redis 内部原子执行。因果链是锁过期后别人可能重新获得锁，旧持有者若直接 DEL 会删掉别人的锁，因此 token 是所有权证明。
    • TTL 要覆盖业务执行时间，但不能无限大；续期也要校验 token，并设置总租约边界。客户端需要有限重试、退避、超时失败和合适锁粒度，否则锁会从保护资源变成热点 Key 或长队列。
    • 失败边界是 Redis 的单实例或异步复制故障模型：主从切换可能丢锁，网络分区、GC 暂停、调度抖动可能让业务在租约过期后继续执行。Redlock 降低单点风险但依赖时间假设、独立节点和多数成功窗口，不能替代强一致协调。
    • 记忆抓手：加锁看 NX+PX，解锁看 token+Lua，正确性看业务幂等和最终约束。强互斥资源应优先考虑数据库条件更新、唯一约束、etcd/ZooKeeper 租约或状态机。

  • [ ] ★★ Redis 大 Key 和热 Key 有什么危害？如何发现和处理？

  • 完整回答：
    • 大 Key 指单个 Key 的 value 或集合元素规模过大，例如几十 MB 的 String、包含几十万成员的 Hash、Set 或 Sorted Set；热 Key 指访问流量高度集中到少数 Key。
    • 大 Key 的危害是单次读取会占用大量网络带宽和客户端内存，序列化、复制、AOF/RDB、迁移和删除成本高，还可能长时间占用 Redis 事件循环，造成其他请求排队。
    • 热 Key 的危害是 CPU、网卡、连接和 Cluster 单槽位压力集中，分片数量再多也无法自动拆散同一个 Key 的访问。
    • 发现大 Key 可使用 redis-cli --bigkeys、--memkeys、MEMORY USAGE、慢日志、延迟监控、离线 RDB 分析和业务埋点，生产环境扫描要控制速率，避免 SCAN 过密影响实例。
    • 热 Key 可通过访问日志、代理层统计、客户端埋点、Redis hotkeys 采样、节点 CPU/带宽倾斜和慢查询定位。
    • 处理大 Key 通常要拆分数据模型，如按用户、日期、分页、分桶拆成多个 Key；读取时分页或增量拉取；删除时用 UNLINK、分批 HSCAN/SSCAN/ZSCAN 清理，避免 DEL 阻塞。
    • 处理热 Key 可用本地缓存、请求合并、短 TTL 旧值兜底、读副本、热点多副本 Key、限流、预热和业务降级。
    • 误区是只调大内存或加 Cluster 节点：大 Key 和热 Key 本质是单对象、单槽位、单链路瓶颈，必须从数据粒度和访问模式上拆散压力。

  • 原理解析：

    • 大 Key 是单个对象过大，热 Key 是访问集中，二者都把 Redis 的优势压回单点瓶颈。大 Key 放大网络传输、序列化、复制、RDB/AOF 和删除成本；热 Key 则让 CPU、网卡、连接和 Cluster 槽位倾斜。
    • 发现大 Key 依赖 --bigkeys、--memkeys、MEMORY USAGE、慢日志、延迟监控和 RDB 离线分析；发现热 Key 依赖代理层、客户端埋点、访问日志、hotkeys 采样和节点指标倾斜。生产扫描要限速，避免排查动作制造抖动。
    • 处理大 Key 的因果修复是拆数据粒度：分桶、分页、按日期或用户拆 Key，读取改为范围或增量，删除用 UNLINK 或 scan 分批。处理热 Key 则要拆访问压力：本地缓存、请求合并、热点副本、读副本、限流和旧值兜底。
    • 记忆抓手：大 Key 是“东西太大”，热 Key 是“人都挤到一个点”。加机器只能扩总量，不能自动拆开单对象、单槽位、单链路瓶颈。

  • [ ] ★★ 布隆过滤器的原理是什么？有什么局限？

  • 完整回答：
    • 布隆过滤器是一种空间效率很高的概率型集合结构，由一个位数组和多个哈希函数组成。
    • 插入元素时，对元素计算多个哈希位置，并把对应位都置为 1；查询元素时，再计算同样的位置，只要有任意一位为 0，就能确定元素一定不存在；如果所有位置都是 1，只能说明元素可能存在，因为这些位可能由多个其他元素共同置位。
    • 它的核心价值是在不保存完整元素集合的情况下快速判断“不存在”，常用于缓存穿透防护、黑名单初筛、URL 去重、爬虫去重和推荐曝光去重。
    • 局限首先是假阳性，即返回“可能存在”但实际不存在；在没有错误删除、哈希实现缺陷或数据损坏的前提下，普通布隆过滤器不会把已插入元素判断为不存在。
    • 误判率取决于预估容量、位数组长度、哈希函数数量和实际插入规模，超过设计容量后误判会明显上升，所以需要容量规划和重建策略。
    • 其次，普通布隆过滤器不能精确删除，因为一个位置可能被多个元素共享，直接清零会影响其他元素；计数布隆过滤器可以支持删除，但需要更多空间，并可能受计数溢出和并发更新影响。
    • 它也不能列出成员、不能提供精确数量，适合前置过滤而不是最终判断。
    • 用于 Redis 缓存穿透时，过滤器本身还要和数据库新增、删除、批量导入保持一致，否则可能把合法新数据挡在缓存和数据库之前，或因初始化不完整导致保护效果不足。

  • 原理解析：

    • 布隆过滤器的抽象是“用位数组近似表示集合成员关系”。元素写入时经过多个哈希函数，把多个位置置 1；查询时只要有一位是 0，就能确定没插入过，所有位都是 1 则只能判断可能存在。
    • 它适合缓存穿透，是因为能廉价回答“大概率不需要查库”。因果链是非法 ID 被过滤器提前拒绝，数据库回源量下降；合法 ID 仍进入缓存和数据库路径，由后端给出最终判断。
    • 局限来自位共享：多个元素可能命中同一批位，所以会有假阳性；普通布隆过滤器不能精确删除，清零可能误伤其他元素。计数布隆能删但消耗更多空间，还要处理计数溢出和并发更新。
    • 记忆抓手：布隆过滤器只可靠地说“一定不存在”，不能可靠地说“一定存在”。容量、误判率、哈希数和数据库新增同步，是落地时必须一起设计的四个参数；超过预估容量后误判率会上升，缓存穿透防护会逐步退化。

  • [ ] ★★ 为什么 Redis 事务不等同于关系数据库事务？

  • 完整回答：
    • Redis 事务主要由 MULTI、命令入队和 EXEC 组成，EXEC 执行时会把队列中的命令按顺序串行执行，中间不会插入其他客户端命令，因此它提供的是一段命令序列的原子执行窗口。
    • 它不等同于关系数据库事务，因为 Redis 没有传统数据库那套完整 ACID 机制：没有基于 undo/redo 日志的自动回滚，没有多隔离级别，没有跨表约束检查，也不会在执行阶段某条命令失败时自动撤销已经执行的其他命令。
    • 入队阶段如果命令语法或参数数量明显错误，事务可能整体失败；但执行阶段例如对错误类型执行操作，通常只是该命令返回错误，其他命令仍继续执行。
    • WATCH 可以在事务前监控 Key，若被其他客户端修改，EXEC 返回失败，由客户端重试，相当于乐观锁式条件更新，但它不能解决复杂业务跨系统一致性。
    • Lua 脚本可以把“读、判断、写”封装为单个原子脚本，适合库存扣减、限流和锁释放，但脚本执行期间会阻塞事件循环，脚本过长或访问大 Key 会放大延迟，并且脚本内原子性仍只覆盖 Redis 自身。
    • 关系数据库事务通常还承担持久化、回滚、隔离和约束语义，而 Redis 的事务更像命令批量串行执行机制。
    • 涉及数据库、消息队列、外部接口时，Redis 事务不能提供分布式事务保证，仍需要幂等、补偿、唯一约束和状态机校验。
  • 原理解析：
    • Redis 事务的抽象是“排队后串行执行的一组命令”，核心能力是 EXEC 期间不插入其他客户端命令。它提供命令序列的原子执行窗口，但不提供关系数据库意义上的完整 ACID。
    • 差异的因果链在错误处理和隔离语义：入队阶段语法错误可能让事务整体失败，执行阶段类型错误通常只让该命令报错，前后命令继续执行；Redis 不会像关系库那样自动回滚已经执行的修改。
    • WATCH 是乐观锁，监控 Key 被改动则让 EXEC 失败，由客户端重试；Lua 脚本能把读判写封成单个原子片段，但脚本太长会阻塞事件循环，且原子性只覆盖 Redis 内部状态。
    • 记忆抓手：Redis 事务重“串行批处理”，关系库事务重“提交、回滚、隔离、约束、持久化”。跨数据库、消息队列和外部接口时，仍要靠幂等、补偿、唯一约束和状态机守住最终正确性。
