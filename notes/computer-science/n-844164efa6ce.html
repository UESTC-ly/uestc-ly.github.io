学习目标

学完本篇，你应该能够：

  • 设计一个相对稳健的 Redis 生产使用方案，包括部署、配置、权限、备份、容量和监控。
  • 按现象快速判断 Redis 常见故障方向：连接失败、延迟升高、内存异常、数据丢失、主从复制异常、Cluster 问题等。
  • 掌握 Redis 故障排查的通用流程和关键命令。
  • 建立从入门到进阶的 Redis 学习路线，知道下一步该补哪些能力。

核心概念

1. 生产使用 Redis 的基本原则

Redis 在生产环境中常见角色：

场景 典型用途 关注点
缓存 缓存数据库查询、接口结果 命中率、穿透、击穿、雪崩、淘汰策略
分布式锁 控制并发互斥 锁超时、续期、误删、可重入需求
计数器 浏览量、限流计数 原子性、过期时间、热点 Key
排行榜 ZSet 排名 数据量、分页、更新频率
消息流 Stream 消费组 消费确认、Pending、重试、堆积
会话存储 登录态、临时状态 TTL、容量、权限、安全

生产原则：

  1. 明确 Redis 是缓存还是数据源：缓存可丢，数据源要考虑持久化、备份和恢复。
  2. 所有 Key 要有命名规范：方便排查、统计、清理和权限控制。
  3. 容量先行：预估 Key 数量、Value 大小、TTL、增长速度。
  4. 监控先于优化：没有指标就无法判断优化是否有效。
  5. 变更可回滚：配置、脚本、数据迁移都要准备回退方案。

2. 故障排查方法论

推荐按“现象 -> 范围 -> 指标 -> 证据 -> 修复 -> 复盘”进行：

1. 明确现象：慢、错、连不上、数据不一致、内存满？
2. 缩小范围：单业务、单实例、单节点、全局？
3. 采集证据：日志、INFO、SLOWLOG、LATENCY、客户端错误。
4. 临时止血：限流、降级、扩容、切主、清理异常流量。
5. 根因修复：代码、配置、容量、架构或运维流程。
6. 复盘沉淀：监控、告警、演练、文档、自动化。

3. 生产配置的三条底线

  • 安全底线：不要裸奔暴露公网；设置 ACL / 密码；限制危险命令；最小权限访问。
  • 容量底线：设置 maxmemory；明确淘汰策略；预留系统内存和 fork 内存空间。
  • 可恢复底线：如果 Redis 承载不可丢数据，要有持久化、备份、恢复演练。

4. 版本差异提示

  • Redis 6 引入 ACL、I/O threads、RESP3 等能力，Redis 7.x 在此基础上持续增强。
  • Redis 7.x 常见运维命令和配置与 Redis 6 大体一致，但具体字段、默认配置、子命令可能随小版本变化。
  • 学习和生产排查时，优先查看当前实例版本：
redis-cli INFO server | grep redis_version

关键命令/配置

1. 基础健康检查

redis-cli PING
redis-cli INFO server
redis-cli INFO clients
redis-cli INFO memory
redis-cli INFO stats
redis-cli INFO persistence
redis-cli INFO replication
redis-cli INFO keyspace

常见判断：

现象 优先查看
连不上 网络、防火墙、bind、protected-mode、密码/ACL、maxclients
变慢 SLOWLOG、LATENCY、CPU、命令复杂度、大 Key、持久化
内存满 INFO memory、MEMORY STATS、maxmemory-policy、大 Key
数据丢失 TTL、淘汰、误删、持久化策略、主从切换窗口
主从异常 INFO replication、网络、复制积压缓冲区、磁盘/CPU
Cluster 异常 CLUSTER INFO、CLUSTER NODES、slot 分配、节点状态

2. 安全相关配置

# 只监听内网地址示例，按实际机器地址调整
bind 127.0.0.1 10.0.0.10

# 开启保护模式，默认通常为 yes
protected-mode yes

# Redis 6+ ACL 推荐使用用户权限，而不是只依赖 requirepass
# 示例：创建应用用户，只允许访问 app:* key，允许常见读写命令
user app on >strong_password ~app:* +get +set +del +expire +ttl +hget +hset +hmget +incr +decr

查看 ACL：

redis-cli ACL LIST
redis-cli ACL WHOAMI
redis-cli ACL CAT

危险命令治理示例：

# Redis 7.x 仍支持 rename-command，但更推荐结合 ACL 做权限控制
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command CONFIG ""

rename-command 改动会影响运维工具兼容性。生产中优先用网络隔离、ACL、审计和最小权限。

3. 内存与淘汰配置

# 生产建议设置明确上限
maxmemory 4gb

# 缓存场景常用策略之一
maxmemory-policy allkeys-lru

# 其他常见策略：
# noeviction        达到上限后写入报错，适合不能随意丢数据的场景
# volatile-lru      只淘汰设置了过期时间的 Key
# allkeys-lfu       Redis 4+ 支持，按访问频率淘汰，适合热点明显场景
# volatile-ttl      优先淘汰剩余 TTL 短的 Key

查看内存：

redis-cli INFO memory
redis-cli MEMORY STATS
redis-cli MEMORY DOCTOR
redis-cli --bigkeys
redis-cli --memkeys

4. 持久化与备份

RDB 示例：

save 900 1
save 300 10
save 60 10000

dbfilename dump.rdb
dir /var/lib/redis

AOF 示例：

appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec

Redis 7.x AOF 相关说明：

  • Redis 7 使用 multi-part AOF 机制：基础文件 + 增量文件 + manifest 管理。
  • 对使用者而言，仍重点关注 appendonly、appendfsync、AOF 重写状态和备份恢复流程。

检查持久化状态：

redis-cli INFO persistence
redis-cli LASTSAVE
redis-cli BGSAVE
redis-cli BGREWRITEAOF

BGSAVE 和 BGREWRITEAOF 会 fork 子进程，数据量大时可能带来延迟和内存压力，应在低峰期或受控环境执行。

5. 复制、哨兵与 Cluster

主从复制：

redis-cli INFO replication
redis-cli ROLE

哨兵：

redis-cli -p 26379 SENTINEL masters
redis-cli -p 26379 SENTINEL slaves mymaster
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

Cluster：

redis-cli -c -p 7000 CLUSTER INFO
redis-cli -c -p 7000 CLUSTER NODES
redis-cli -c -p 7000 CLUSTER SLOTS
redis-cli -c -p 7000 CLUSTER KEYSLOT app:user:1001

6. 客户端连接与超时

# 最大客户端连接数
maxclients 10000

# 空闲连接超时，0 表示不主动断开
timeout 0

# TCP keepalive
tcp-keepalive 300

客户端建议：

  • 设置连接超时、读写超时，不要无限等待。
  • 使用连接池，但不要设置过大导致 Redis 连接数耗尽。
  • 对重试设置退避和上限，避免 Redis 抖动时形成重试风暴。
  • 区分读写命令的超时与业务接口超时。

示例

示例 1：Redis 突然连接不上

排查顺序：

# 1. 机器是否能连通端口
nc -vz 127.0.0.1 6379

# 2. Redis 是否响应
redis-cli -h 127.0.0.1 -p 6379 PING

# 3. 是否需要认证
redis-cli -h 127.0.0.1 -p 6379 -a 'password' PING

# 4. 查看连接数和拒绝连接
redis-cli INFO clients
redis-cli INFO stats | grep rejected_connections

常见原因：

  • Redis 进程未启动或端口不对。
  • bind 只绑定了本地地址，远程无法连接。
  • protected-mode yes 且未正确配置访问方式。
  • 密码或 ACL 用户权限错误。
  • maxclients 达到上限。
  • 网络策略、防火墙、安全组拦截。

临时止血：

  • 先恢复业务读路径，例如切换到备用 Redis、降级到数据库或本地缓存。
  • 如果连接数爆满，定位异常客户端，必要时限制流量或重启异常应用实例。

示例 2：Redis 延迟突然升高

redis-cli --latency-history
redis-cli LATENCY LATEST
redis-cli LATENCY DOCTOR
redis-cli SLOWLOG GET 20
redis-cli INFO commandstats
redis-cli INFO persistence
redis-cli INFO memory

排查方向：

  1. SLOWLOG 是否出现 HGETALL、SMEMBERS、ZRANGE 0 -1、复杂 Lua？
  2. LATENCY 是否出现 fork、aof-fsync、expire-cycle？
  3. INFO persistence 是否显示正在 RDB/AOF 重写？
  4. INFO memory 是否接近 maxmemory，并频繁淘汰？
  5. 操作系统 CPU、磁盘 I/O、网络是否异常？

止血动作：

  • 暂停或限流高成本接口。
  • 将全量读取改为分页/游标扫描。
  • 在低峰期处理大 Key 拆分和 AOF/RDB 重写。
  • 如果是热 Key，加入本地缓存、Key 副本或限流。

示例 3：缓存雪崩、击穿、穿透

缓存雪崩

大量 Key 同时过期，数据库被打爆。

治理：

TTL = 基础过期时间 + 随机抖动
例如：3600s + random(0, 300s)

缓存击穿

一个热点 Key 过期，大量请求同时回源。

治理：

  • 互斥锁保护回源。
  • 后台异步刷新热点 Key。
  • 热点 Key 设置较长 TTL 或逻辑过期。

伪代码：

value = redis.get(key)
if value exists:
    return value

if redis.set(lockKey, "1", nx=True, ex=5):
    value = db.query()
    redis.set(key, value, ex=ttl_with_jitter)
    redis.del(lockKey)
else:
    sleep(short_time)
    retry_read_cache()

缓存穿透

请求大量不存在的数据，缓存和数据库都没有。

治理：

  • 缓存空值，设置较短 TTL。
  • 使用布隆过滤器拦截明显不存在的 ID。
  • 对异常参数和恶意请求限流。

示例 4：怀疑数据丢失

先区分“真的丢失”还是“读错地方”：

# 1. 确认连接的库、节点、用户和 key
redis-cli INFO server | grep redis_version
redis-cli DBSIZE
redis-cli EXISTS app:user:1001
redis-cli TTL app:user:1001
redis-cli TYPE app:user:1001

# 2. 看是否被过期或淘汰
redis-cli INFO stats | grep -E 'expired_keys|evicted_keys'
redis-cli INFO memory | grep -E 'used_memory_human|maxmemory_human|maxmemory_policy'

# 3. 看持久化是否成功
redis-cli INFO persistence

常见原因：

  • Key 设置了 TTL，业务未意识到。
  • 内存达到上限，被淘汰策略删除。
  • 应用写入了不同环境、不同 DB、不同前缀。
  • 主从切换时存在复制延迟，少量最近写入未同步。
  • 持久化配置不满足“不可丢数据”要求。

示例 5：Stream 消息堆积

# 查看 Stream 长度
redis-cli XLEN mystream

# 查看消费组信息
redis-cli XINFO GROUPS mystream

# 查看消费者信息
redis-cli XINFO CONSUMERS mystream mygroup

# 查看 pending 消息
redis-cli XPENDING mystream mygroup
redis-cli XPENDING mystream mygroup - + 10

排查方向：

  • 消费者是否宕机或处理变慢。
  • 是否忘记 XACK。
  • Pending 消息是否长期无人认领。
  • Stream 是否没有裁剪导致内存增长。

处理示例：

# 认领空闲超过 60 秒的 pending 消息
redis-cli XAUTOCLAIM mystream mygroup consumer-2 60000 0 COUNT 10

# 近似裁剪，保留约 10000 条
redis-cli XTRIM mystream MAXLEN '~' 10000

常见误区

误区 1：Redis 做缓存就不需要备份

如果 Redis 只是纯缓存，确实可以接受丢失；但很多系统会把会话、队列、计数、锁状态、业务中间态放进 Redis。只要数据不可随意丢，就要设计持久化和恢复策略。

误区 2：分布式锁只要 SETNX 就够了

更推荐使用带过期时间的原子写法：

SET lock:order:1001 request-id NX EX 10

释放锁时要校验 value，避免误删别人的锁。复杂场景还要考虑续期、时钟、超时、幂等和业务补偿。

误区 3：所有 Key 都设置相同 TTL

相同 TTL 容易导致雪崩。建议加随机抖动，并按业务热度区分 TTL。

误区 4：maxmemory-policy noeviction 总是最安全

noeviction 可以避免静默淘汰，但内存满后写命令会报错。缓存场景通常更适合 LRU/LFU；不可丢数据场景则要保证容量和告警。

误区 5：主从复制等于强一致

Redis 复制通常是异步的。主节点写入成功后，从节点可能尚未同步；故障切换时存在丢失最近写入的风险。强一致需求不能简单依赖 Redis 异步复制。

误区 6：排障时先重启

重启可能短期恢复，但会丢失现场证据。除非已经影响严重且有止血预案，否则应先采集 INFO、SLOWLOG、LATENCY、日志和系统指标。

实践检查清单

上线前检查

  • [ ] 明确 Redis 用途：缓存、锁、队列、计数器、会话或数据源。
  • [ ] Key 命名规范已定义，例如 业务:模块:对象:id。
  • [ ] TTL 策略已定义，热点 Key 和普通 Key 区分处理。
  • [ ] 已设置 maxmemory 和匹配的 maxmemory-policy。
  • [ ] 已设置认证、ACL、网络隔离，未暴露公网。
  • [ ] 已评估 RDB/AOF/备份策略是否满足恢复目标。
  • [ ] 客户端配置了连接池、超时、重试上限和熔断降级。
  • [ ] 监控和告警已覆盖延迟、内存、连接数、慢日志、持久化、复制状态。

故障排查检查

  • [ ] 先记录故障开始时间、影响范围、错误信息和业务现象。
  • [ ] 采集 INFO、SLOWLOG GET、LATENCY LATEST、Redis 日志和系统指标。
  • [ ] 判断是否为客户端连接问题、慢命令、大 Key、热 Key、内存、持久化、复制或网络问题。
  • [ ] 止血动作优先保护核心业务：限流、降级、切换、扩容、暂停高成本任务。
  • [ ] 修复后对比故障前后指标，确认问题没有继续扩大。
  • [ ] 完成复盘：根因、时间线、监控缺口、预防动作、负责人。

运维演练

  • [ ] 演练从 RDB/AOF 备份恢复数据。
  • [ ] 演练主从切换或哨兵故障转移。
  • [ ] 演练 Redis Cluster 节点故障和 slot 迁移。
  • [ ] 演练大 Key 扫描和拆分流程。
  • [ ] 演练缓存雪崩/击穿/穿透的降级策略。

学习路线

第一阶段：入门基础

目标：能独立使用 Redis 做基础缓存。

建议学习：

  1. Redis 是什么、适合什么场景、不适合什么场景。
  2. String、Hash、List、Set、ZSet 基础命令。
  3. Key 命名、TTL、过期机制。
  4. redis-cli 基本使用。
  5. 用一门语言的客户端完成 GET、SET、HGET、EXPIRE。

练习：

  • 为用户信息接口增加缓存。
  • 为验证码或登录态设置 TTL。
  • 用 INCR 实现简单计数器。

第二阶段：进阶应用

目标：理解 Redis 的数据结构和常见业务模式。

建议学习：

  1. 位图 Bitmap、HyperLogLog、GEO、Stream。
  2. 事务、Lua、Pipeline。
  3. 缓存穿透、击穿、雪崩治理。
  4. 分布式锁的正确写法和边界。
  5. Big Key、Hot Key 识别与治理。

练习：

  • 用 ZSet 实现排行榜。
  • 用 Stream 实现消费组消息处理。
  • 写一个带随机 TTL 的缓存封装。
  • 用 Lua 实现“检查库存并扣减”的原子操作。

第三阶段：高可用与扩展

目标：能理解并参与 Redis 生产部署设计。

建议学习：

  1. RDB、AOF、混合持久化、AOF 重写。
  2. 主从复制、复制延迟、部分重同步。
  3. Sentinel 故障转移原理。
  4. Redis Cluster slot、重定向、reshard。
  5. 容量规划、内存淘汰、监控告警。

练习：

  • 本地启动一主两从并观察复制状态。
  • 搭建 Sentinel 并模拟主节点宕机。
  • 搭建 3 主 3 从 Cluster 并迁移 slot。
  • 比较 RDB、AOF、appendfsync 不同配置对延迟的影响。

第四阶段：生产专家方向

目标：能独立排查复杂 Redis 问题并制定治理方案。

建议学习：

  1. Redis 源码中的事件循环、对象编码、过期删除、淘汰策略。
  2. 操作系统层面的内存、fork、透明大页、TCP backlog、文件描述符。
  3. 客户端连接池、重试风暴、超时传播。
  4. 多级缓存、本地缓存一致性、热点保护。
  5. Redis 与数据库、消息队列、搜索系统的边界设计。

练习：

  • 基于真实业务流量做容量预估。
  • 建立 Redis Grafana 监控面板。
  • 制作 Redis 故障应急手册。
  • 对一次慢查询或大 Key 事故做复盘报告。
