学习目标

  • 理解索引、事务、隔离级别、锁、日志和复制的基本作用。
  • 能用执行计划分析查询，而不是凭感觉加索引。
  • 正确配置客户端超时、连接池和事务边界。

本篇讲通用原理，实验可选 MySQL 或 PostgreSQL。具体语法、默认隔离级别、锁行为和复制能力以所用数据库官方文档为准。

核心原理

关系数据库用约束表达不变量，用索引降低读取成本，用事务和隔离控制并发可见性，用 WAL 支持恢复，用复制换取可用性和读扩展。C++ 服务接入数据库时，还必须把连接池、deadline、取消和错误不确定性纳入调用链。

1. 数据模型和约束

关系数据库的价值不仅是保存行，还包括用主键、唯一约束、外键、检查约束和事务维护不变量。

  • 主键应稳定、紧凑；业务可读编号和内部主键可分离。
  • NULL 表示未知/缺失，不等于空字符串或零。
  • 金额避免二进制浮点，使用定点小数或最小货币单位整数。
  • 时间要明确时区、精度和语义；存储时间点与展示时区分离。
  • 不要仅靠应用检查唯一性；并发下最终由数据库唯一约束裁决。

2. 索引

B+Tree 索引适合等值、范围和排序；复合索引遵循其有序键结构。判断索引要结合查询模式、选择性、回表成本、写放大和缓存。

B+Tree 内部机制

B+Tree/B+Tree 变体把键按顺序保存在多级页结构中。根页定位范围，中间页缩小搜索区间，叶子页保存键和行定位信息；多数关系数据库的常规索引实现接近 B+Tree 或 B+Tree 变体。叶子页有序意味着它不仅能做等值查找，也能做范围扫描和按索引顺序返回结果。

一次索引查询大致是：

root page -> branch page -> leaf page range -> row lookup/filter -> return

如果索引覆盖了查询需要的列，数据库可能不必回表；如果只用索引找到大量行再回表，随机 I/O 和缓存 miss 可能让它比顺序扫描更慢。写入时还要维护索引页，页分裂和 WAL 记录都会增加写放大。

复合索引 (tenant_id, status, created_at) 能否有效使用，取决于查询的等值前缀、范围条件与排序。不要机械背“最左匹配”，应读取执行计划观察扫描行数、过滤、排序和回表。

索引代价：

  • 占用内存与磁盘；
  • 插入、更新、删除需要维护；
  • 低选择性条件可能全表扫描更便宜；
  • 过多相似索引增加优化器选择和运维成本。

3. 事务与 ACID

  • 原子性：事务要么整体提交，要么回滚。
  • 一致性：应用不变量在正确事务和约束下从一个有效状态转到另一个；不是数据库自动理解业务。
  • 隔离性：并发事务的可见行为受隔离级别与实现影响。
  • 持久性：提交后的数据在声明的故障模型下可恢复，取决于日志、刷盘和复制配置。

常见异常：脏读、不可重复读、幻读、丢失更新、写偏差。SQL 标准隔离级别只是起点，不同数据库用锁、MVCC 或 SSI 实现，具体保证要查官方文档并做并发实验。

MVCC 与隔离异常

MVCC 通过保存多个版本，让读请求在某个快照上读取数据，减少读写互相阻塞。写事务通常创建新版本并记录提交信息；旧版本要等不再被任何活跃快照需要后才能清理。长事务会拖住版本回收，使表膨胀、undo/垃圾版本增长，并影响查询性能。

典型隔离异常：

  • 丢失更新：两个事务都读到旧值，再分别写回，后写覆盖先写；
  • 不可重复读：同一事务两次读同一行，看到不同已提交版本；
  • 幻读：同一条件范围两次查询，第二次出现新行；
  • 写偏差：两个事务各自读到约束满足，分别更新不同记录，提交后整体约束被破坏。

修复方式可能是唯一约束、条件更新、显式锁、提高隔离级别或重构不变量。不能只说“开事务”。

事务越长，持锁/MVCC 版本保留越久，冲突和资源占用越大。不要在事务内做远程 HTTP 调用或等待用户输入。

事务代码边界

事务边界应围绕一个短小的不变量变更，不应覆盖模板渲染、RPC 调用或用户交互。C++ 服务里常见写法是用 RAII 包装事务，但析构自动回滚只能作为兜底，业务代码仍应显式 commit() 并处理失败。

Transaction tx = db.begin(deadline.remaining());
auto row = tx.queryOne("select stock from item where id=? for update", id);
if (row.stock < n) return Error::InsufficientStock;
tx.exec("update item set stock=stock-? where id=?", n, id);
tx.commit();      // commit 失败时调用者必须知道写入结果不确定或已回滚

这段示例省略了具体数据库 API。关键是 commit 的错误路径不能被当作普通网络错误随意重试；在连接断开时，客户端可能不知道事务是否已经提交，需要幂等键或业务查询确认。

4. 日志、恢复与复制

预写日志（WAL）的核心直觉：先持久化描述修改的日志，再让数据页异步落盘，以支持崩溃恢复。数据库日志、二进制日志/逻辑日志、慢查询日志用途不同。

主从复制可能同步、半同步或异步；“提交成功”是否意味着副本已有数据取决于配置。读副本可能滞后，读写分离会出现刚写后读不到。需要读己之写时，可访问主库、携带位置等待副本追上，或采用业务可接受的会话策略。

WAL、恢复和复制延迟

WAL 把随机数据页修改转成顺序日志追加，崩溃后通过 redo/undo 或类似机制恢复到一致状态。刷盘参数决定提交延迟和故障丢失窗口，不同数据库、存储和配置的保证不同。

复制不是单一概念：物理复制传输页或 WAL 级别变化，逻辑复制传输行级或语句级变化；同步复制降低丢数据风险但增加提交延迟，异步复制延迟低但可能在主库故障时丢失已确认给客户端但未到副本的数据。工程上要把 RPO/RTO、读己之写和跨机房延迟写成明确取舍。

5. 查询与执行计划

分析查询时记录：

  1. 输入参数分布，而不是只测一个值；
  2. 估算行数与实际行数差异；
  3. 索引/全表扫描、连接顺序与算法；
  4. 排序、临时表、聚合、回表；
  5. buffer/cache 命中、I/O 与锁等待；
  6. P95/P99 延迟和并发下吞吐。

大分页的 OFFSET 往往需要扫描并丢弃大量行。稳定排序下可使用 keyset/seek pagination，例如用 (created_at, id) 作为游标；它不支持随意跳页，但性能更稳定。

执行计划不是静态真理

优化器根据统计信息估算行数和成本。数据分布倾斜、统计信息过期、参数值不同，都会让计划变化。看执行计划时不要只看是否“用了索引”，还要看实际扫描行数、过滤比例、排序方式、内存/磁盘临时结构和锁等待。

对于 C++ 后端，SQL 性能问题常被连接池掩盖：请求卡在 acquire 阶段时，慢 SQL 可能已经把池耗尽。日志应区分 acquire 耗时、执行耗时、返回行数和事务总耗时。

6. 连接池与超时

连接池是容量控制器，不是越大越好。池大小必须服从数据库能承受的并发，以及服务实例总数：

总连接数 ≈ 单实例池上限 × 实例数 + 运维/迁移连接

应区分：

  • 获取连接超时；
  • 建连/握手超时；
  • 查询/statement 超时；
  • 事务超时；
  • Socket 读写超时；
  • 请求总体截止时间。

从池中归还连接前要清理事务、会话变量和临时状态；坏连接应丢弃。请求取消后，还要确认数据库查询是否被取消，否则后台工作仍占容量。

故障排查/观测

慢查询与锁等待

排查数据库问题时按调用链拆开：应用是否拿到连接，SQL 是否发出，数据库是在执行、等待锁、等待 I/O，还是结果集太大导致网络传输慢。应用日志至少包含 trace id、SQL 模板名、参数规模、连接池等待时间、执行时间、影响行数和错误码。

数据库侧常用：

EXPLAIN ANALYZE ...
-- MySQL/PostgreSQL 的慢查询日志、锁等待视图和活动会话视图名称不同，以官方文档为准。

连接池故障信号

连接池耗尽不一定说明池太小。它可能来自慢查询、长事务、连接泄漏、下游数据库停顿或请求取消未传播。先看 busy/idle/waiter 数、最长持有时间和每个连接当前 SQL，再决定是优化 SQL、缩短事务、修复泄漏，还是调整池大小。

面试与工程复盘

如何讲一个慢 SQL

按“查询目标 -> 参数分布 -> 执行计划 -> 实际行数 -> 锁/I/O/排序 -> 索引取舍 -> 回归验证”讲。不要只说“加索引”，还要说明写入代价、是否覆盖查询、是否影响其他查询和统计信息是否可靠。

如何讲事务安全

先给出业务不变量，再说明使用的隔离级别和数据库实现，最后说明还可能存在什么异常以及如何用约束、锁、条件更新或重试处理。事务安全不是一句“ACID 保证”。

最小验收清单

  • 每个索引都能对应查询模式。
  • 每个事务都能对应业务不变量。
  • 每个连接池超时都能映射到调用链 deadline。
  • 每个复制读策略都说明读己之写边界。

7. 数据库与缓存

缓存不是数据库事务的一部分。常用 cache-aside：读缓存未命中再查库并填充；写库后删除缓存。它仍有并发窗口、删除失败和延迟问题，应结合 TTL、消息/outbox、版本号或对账修复，并按业务容忍度选择。

不要无条件使用“双写数据库和缓存”并宣称强一致；跨两个独立系统缺少统一事务时必须说明失败窗口和补偿方式。

常见误区

  • 有索引就一定走索引、走索引就一定更快。
  • 开启事务就自动避免所有并发异常。
  • 读副本与主库实时一致。
  • 连接池越大吞吐越高。
  • ORM 免除了理解 SQL、事务和执行计划的需要。

自测题

  1. 唯一约束为什么比“先查后插”更能处理并发？
  2. 长事务会带来哪些资源和一致性影响？
  3. 读写分离为何可能违背 read-your-writes？
  4. keyset pagination 与 offset pagination 有何取舍？
  5. 如何给连接池设置上限并避免多实例放大？

实践任务

  1. 创建百万行带倾斜分布的数据，对三个查询读取执行计划并设计复合索引。
  2. 开两个会话复现丢失更新或写偏差，再用约束、锁或条件更新修复。
  3. 实现带获取超时的连接池，测试连接泄漏、事务未回滚和数据库重启。
  4. 为 cache-aside 写并发测试，观察读写交错导致的旧值窗口。
