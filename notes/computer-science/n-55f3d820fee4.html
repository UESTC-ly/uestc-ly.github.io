目标：理解 Redis 如何通过复制（Replication）扩展读能力、通过 Sentinel（哨兵）发现故障并完成主从切换；知道它能解决什么，不能解决什么。

学习目标

学完本章，你应该能够：

  • 解释 Redis 主从复制的基本流程：连接、全量同步、增量同步、命令传播。
  • 区分复制、持久化、备份、高可用之间的关系。
  • 使用 replicaof / REPLICAOF 搭建一主多从结构。
  • 理解 Sentinel 的监控、主观下线、客观下线、故障转移与配置改写。
  • 读懂常见复制与哨兵配置，并能做基础排障。
  • 识别 Redis 高可用方案中的常见误区：异步复制丢数据、脑裂、只读从库延迟等。

核心概念

1. 主从复制（Replication）

Redis 复制是 一个主节点（master）把数据变化异步传播到一个或多个从节点（replica） 的机制。

常见用途：

  • 读写分离：主库处理写请求，从库承担读请求。
  • 故障恢复基础：主库故障时，从库可被提升为新主库。
  • 数据冗余：多个副本降低单点数据不可用风险。
  • 备份辅助：可在从库上执行备份，减少主库压力。

注意：Redis 5.0 以后官方文档逐步使用 replica 替代 slave，但旧命令和配置中仍可能看到 slave 字样，例如 INFO replication 输出里的历史字段。

2. 全量同步与增量同步

当一个 replica 第一次连接 master，或复制积压缓冲区无法覆盖断线期间的数据时，会发生 全量同步：

  1. replica 向 master 发起同步请求。
  2. master 生成 RDB 快照，并继续记录后续写命令。
  3. master 把 RDB 发送给 replica。
  4. replica 加载 RDB。
  5. master 将快照期间积累的写命令继续发送给 replica。

如果 replica 短暂断线后重连，并且 master 的复制积压缓冲区仍保留断线期间的写命令，则可进行 增量同步（PSYNC 部分重同步），避免重新传输完整数据集。

3. 复制偏移量与复制积压缓冲区

Redis 通过复制偏移量追踪主从同步位置：

  • master 维护写命令流的偏移量。
  • replica 记录自己同步到的位置。
  • repl-backlog-size 决定 master 保存最近写命令的缓冲区大小。

如果断线时间较长、写入量较大，缓冲区被覆盖，replica 重连时就无法增量同步，只能全量同步。

4. 异步复制与数据安全边界

Redis 复制默认是 异步 的：master 写成功后通常不会等待所有 replica 确认。

这意味着：

  • 性能高，写入延迟低。
  • master 宕机时，尚未复制到 replica 的写入可能丢失。
  • Sentinel 或 Cluster 的自动故障转移不能保证零数据丢失。

可以用 WAIT 命令或 min-replicas-to-write 配置增强写入安全，但这会增加延迟，并且仍不等价于传统强一致事务。

5. Sentinel（哨兵）

Sentinel 是 Redis 的高可用组件，主要职责：

  • 监控（Monitoring）：定期检查 master、replica、其他 sentinel 是否存活。
  • 通知（Notification）：发现故障后可通过脚本或日志通知外部系统。
  • 自动故障转移（Automatic failover）：master 不可用时，选举一个 replica 为新 master。
  • 配置提供者（Configuration provider）：客户端可向 Sentinel 查询当前 master 地址。

Sentinel 本身通常也要部署多个实例，常见为 3 个或 5 个，以避免单个哨兵误判。

6. 主观下线与客观下线

Sentinel 判断故障分两层：

  • 主观下线（SDOWN）：某个 Sentinel 自己认为 master 不可达。
  • 客观下线（ODOWN）：足够数量的 Sentinel 都认为 master 不可达，达到 quorum 后才认为 master 客观下线。

quorum 不是“同意故障转移所需的全部票数”，而是“确认 master 故障所需的 Sentinel 数量”。真正执行故障转移还需要 Sentinel 之间进行 leader 选举。

7. Sentinel 故障转移流程

简化流程：

  1. 多个 Sentinel 监控同一个 master。
  2. master 超过 down-after-milliseconds 未响应。
  3. Sentinel 进入主观下线判断。
  4. 达到 quorum 后进入客观下线。
  5. Sentinel 选举故障转移 leader。
  6. leader 从 replicas 中选择一个提升为新 master。
  7. 其他 replicas 改为复制新 master。
  8. Sentinel 改写本地配置，客户端通过 Sentinel 发现新 master。

关键命令 / 配置

复制相关命令

# 查看复制状态
redis-cli INFO replication

# 将当前实例设置为某个 master 的 replica
redis-cli REPLICAOF 127.0.0.1 6379

# 取消复制，提升为独立 master
redis-cli REPLICAOF NO ONE

# 旧版本命令，Redis 5.0 前更常见；Redis 7.x 仍兼容
redis-cli SLAVEOF 127.0.0.1 6379
redis-cli SLAVEOF NO ONE

# 写入后等待至少 1 个副本确认，最多等待 1000 ms
redis-cli WAIT 1 1000

复制相关配置

# redis.conf

# 启动时直接成为某个 master 的 replica
replicaof 127.0.0.1 6379

# master 设置密码时，replica 用它认证 master
masterauth your_password

# replica 默认只读，避免误写
replica-read-only yes

# 复制积压缓冲区大小，影响断线后能否增量同步
repl-backlog-size 64mb

# 至少有 1 个延迟不超过 10 秒的 replica，master 才接受写入
min-replicas-to-write 1
min-replicas-max-lag 10

Sentinel 常用配置

# sentinel.conf

# 监控名为 mymaster 的 master，地址 127.0.0.1:6379，至少 2 个 Sentinel 同意才客观下线
sentinel monitor mymaster 127.0.0.1 6379 2

# master 多久无响应后，被单个 Sentinel 判断为主观下线
sentinel down-after-milliseconds mymaster 5000

# 故障转移时，同时允许几个 replica 重新复制新 master
sentinel parallel-syncs mymaster 1

# 故障转移超时时间
sentinel failover-timeout mymaster 60000

# master 需要认证时，Sentinel 使用此密码连接
sentinel auth-pass mymaster your_password

启动 Sentinel：

redis-sentinel sentinel.conf
# 或
redis-server sentinel.conf --sentinel

Sentinel 查询命令

# 查看当前 master 地址
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

# 查看 Sentinel 认识的 replicas
redis-cli -p 26379 SENTINEL replicas mymaster

# 查看 Sentinel 认识的其他 sentinels
redis-cli -p 26379 SENTINEL sentinels mymaster

# 手动触发故障转移，常用于演练
redis-cli -p 26379 SENTINEL failover mymaster

示例：本机搭建一主两从三哨兵

仅用于学习环境。生产环境应分布在不同主机或可用区，并结合认证、网络隔离、监控与备份。

1. 准备三个 Redis 实例

目录示例：

redis-lab/
  6379/redis.conf
  6380/redis.conf
  6381/redis.conf

6379/redis.conf：

port 6379
dir ./6379
dbfilename dump.rdb
appendonly yes

6380/redis.conf：

port 6380
dir ./6380
dbfilename dump.rdb
appendonly yes
replicaof 127.0.0.1 6379

6381/redis.conf：

port 6381
dir ./6381
dbfilename dump.rdb

replicaof 127.0.0.1 6379

启动：

redis-server 6379/redis.conf
redis-server 6380/redis.conf
redis-server 6381/redis.conf

验证：

redis-cli -p 6379 SET course redis-ha
redis-cli -p 6380 GET course
redis-cli -p 6381 GET course

2. 准备三个 Sentinel 实例

26379/sentinel.conf：

port 26379
dir ./26379
sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1

启动：

redis-server 26379/sentinel.conf --sentinel
redis-server 26380/sentinel.conf --sentinel

3. 演练故障转移

# 停掉 master
redis-cli -p 6379 SHUTDOWN NOSAVE

# 等待几秒后查询新 master
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

# 查看 6380 / 6381 谁被提升
redis-cli -p 6380 INFO replication
redis-cli -p 6381 INFO replication

如果原 master 恢复，Sentinel 通常会把它重新配置为新 master 的 replica，而不是让它自动抢回主库身份。

常见误区

误区 1：有复制就不会丢数据

复制不是强同步。master 写入成功但尚未传到 replica 时，master 宕机并发生故障转移，这部分数据可能丢失。

误区 2：Sentinel 等于数据备份

Sentinel 解决的是“服务可用性”和“自动主从切换”，不是备份。误删除、逻辑错误、过期策略导致的数据消失，会很快复制到 replica。

误区 3：从库读一定是最新数据

Replica 可能落后于 master。对强读一致性敏感的场景，应读 master，或设计业务校验、版本号、延迟容忍策略。

误区 4：部署两个 Sentinel 就足够可靠

两个 Sentinel 容易出现多数派不足或误判问题。学习环境可以简化，生产环境通常至少 3 个 Sentinel。

误区 5：只要自动切换就没有脑裂

网络分区时，旧 master 可能仍接收部分客户端写入，而 Sentinel 在另一侧提升新 master。需要通过客户端发现机制、min-replicas-to-write、网络隔离和监控降低风险。

误区 6：Replica 可以随便写

默认 replica-read-only yes。即使改成可写，从库本地写入也不会同步回 master，且可能在重新同步时被覆盖。

实践检查清单

复制检查

  • [ ] INFO replication 中 master / replica 角色符合预期。
  • [ ] Replica 的 master_link_status 为 up。
  • [ ] 主从复制延迟在业务可接受范围内。
  • [ ] repl-backlog-size 足够覆盖短暂网络抖动期间的写入量。
  • [ ] 已理解全量同步对 CPU、磁盘、网络的影响。
  • [ ] 从库读请求可以接受延迟或已设计一致性补偿。

Sentinel 检查

  • [ ] Sentinel 至少 3 个，分布在不同故障域。
  • [ ] quorum 设置合理，不会因为单个 Sentinel 误判就切换。
  • [ ] 客户端通过 Sentinel 或支持 Sentinel 的连接池发现 master。
  • [ ] 已演练 SENTINEL failover 和真实 master 宕机场景。
  • [ ] 监控了 +sdown、+odown、+failover-end 等 Sentinel 事件。
  • [ ] 配置了认证、网络访问控制和日志采集。

数据安全检查

  • [ ] 关键写入是否需要 WAIT 或 min-replicas-to-write 已评估。
  • [ ] 已配置 RDB / AOF / 外部备份，不把 replica 当作备份唯一来源。
  • [ ] 明确故障切换时可接受的数据丢失窗口（RPO）。
  • [ ] 明确故障恢复时间目标（RTO）。

  • Redis high availability RPO RTO

小结

复制提供副本和读扩展，Sentinel 在复制基础上提供自动故障发现与主从切换。它们能显著提升可用性，但不等于强一致、不等于备份，也不能单独消除脑裂和数据丢失风险。学习 Redis 高可用时，必须同时理解复制延迟、故障检测、客户端发现和数据安全边界。
