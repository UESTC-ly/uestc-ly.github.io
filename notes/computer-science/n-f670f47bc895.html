记住六步：认人 → 发卡 → 验卡 → 查权限 → 查归属 → 能撤销。

1. 先理解：鉴权到底在做什么

把系统想成办公楼：

环节 要回答的问题 类比
认证 你是谁？ 前台核对身份
会话管理 怎么知道你已经登录？ 发放、核验门禁卡
功能权限 你能做什么？ 能不能进入档案室
数据权限 你能操作哪些数据？ 能不能查看某份档案

例子：张三登录后可以查看订单，但只能查看自己的订单。

登录成功、可以查订单、可以查这笔订单，是三个不同的判断。

2. 常见方案：MySQL + Redis + Cookie + RBAC

普通网站、管理后台可以从这套方案开始：

技术 存什么、做什么
MySQL 保存用户、密码哈希、角色和权限
Redis 保存登录会话，支持过期和撤销
Cookie 浏览器保存并自动携带 Session ID
RBAC 通过“用户 → 角色 → 权限”分配能力

几个名词不要混淆：

  • Session：服务端的登录记录。
  • Session ID：找到这条记录的随机凭据，像门禁卡号。
  • Token：凭据的统称，Session ID 也是一种 Token。
  • JWT：一种 Token 格式，常用签名验证真实性。

Cookie 是携带凭据的方式，JWT 是凭据格式，两者可以一起使用。

3. 核心流程：登录一次，每次请求都检查

登录：

账号密码 → 检查密码与账号状态 → 创建会话存入 Redis → 通过 Cookie 返回随机 Session ID。

密码使用成熟库做专门的密码哈希，新系统可优先选 Argon2id，已有项目常见 BCrypt。不要存明文，也不要用单次 MD5、SHA-256 存密码。

后续请求：

携带 Session ID → 查询 Redis、检查会话有效性 → 恢复用户身份 → 检查权限和数据归属 → 执行业务。

用户身份必须来自服务端验证结果，不能相信客户端自己传来的“我是管理员”。

在 C++ 后端中，可由认证中间件统一验身份，业务服务检查权限和归属，把当前用户信息放在请求上下文里。

4. 权限设计：角色管分配，权限管判断

RBAC 的关系很简单：

张三 → 普通用户角色 → 查看自己的订单

常见建表方式是五张表：用户、角色、权限，以及用户角色关联、角色权限关联。

一个用户可以有多个角色，一个角色可以有多个权限。接口通常检查具体权限，而不是写死角色名，这样新增角色时更容易复用已有能力。

但 RBAC 不能代替数据归属检查：

  • 功能权限：有没有“查看订单”的能力？
  • 数据权限：这笔订单是不是他的？

查询、修改、删除都要限制数据范围；多租户系统还要检查所属租户。前端隐藏按钮只是界面控制，后端仍必须鉴权。

5. 会话管理：既要能登录，也要能失效

场景 处理方式
长时间未操作 空闲过期
持续使用很久 绝对过期，避免无限续期
退出登录 删除服务端会话，同时清除 Cookie
退出所有设备、踢下线 撤销该用户的相关会话
修改权限 更新或失效权限缓存、会话中的旧权限

只清除浏览器 Cookie，不能让已泄露的凭据失效；只修改数据库，也不能保证缓存里的旧权限立即消失。

设计时说清楚：禁用、撤权要求立即生效，还是允许短暂延迟，并选择对应的检查与失效机制。

6. Session 和 JWT 怎么选

对比 Redis Session JWT 本地验证
验证方式 查服务端登录记录 验证签名和有效期等声明
退出、踢人 撤销服务端会话 单靠本地验证不能立即撤销
常见用途 普通网站、管理后台 多服务 API、身份平台对接

先按需求选，普通项目不必强行使用 JWT。 多个后端实例也可以共享 Redis Session。

JWT 记住三点：

  • 签名不等于加密，普通签名 JWT 的内容可以被读取。
  • 验证不仅是解析，还要检查签名、允许的算法、有效期、签发方和接收方。
  • 要求即时退出或撤权时，通常仍需要额外的服务端状态或撤销检查。

双 Token 方案中，Access Token 用于访问接口，Refresh Token 用于续期。撤销 Refresh Token 不会自动让已发出的 Access Token 立即失效。

7. 最容易漏掉的安全点

  • 防猜密码：登录限流，失败统一提示“用户名或密码错误”。
  • 防凭据泄露：使用 HTTPS、安全随机 Session ID；登录成功时更新会话标识；日志不记录密码和完整凭据。
  • 保护 Cookie：设置 HttpOnly、Secure 和合适的 SameSite；它们各有作用，不能包办所有防护。
  • 防 CSRF：浏览器自动携带认证 Cookie 时，修改数据的请求应有 CSRF 防护，不能只靠 SameSite；GET 不修改数据。
  • 防越权：每次请求检查权限和资源归属；Redis 故障时不能直接放行。

常见状态码：401 表示缺少有效身份，403 表示身份有效但权限不足。

8. 复习时这样讲

我会用 MySQL 保存用户和角色权限，用 Redis 保存登录会话，浏览器通过 Cookie 携带 Session ID。登录时校验密码，请求时由中间件恢复身份，再检查功能权限和数据归属。权限采用 RBAC，同时补齐会话过期、退出、踢下线、权限缓存失效，以及限流和 CSRF 防护。如果使用 JWT，则重点处理验证规则和撤销问题。

记忆口诀：认人、发卡、验卡、查权限、查归属、能撤销。
