3. 计算机网络

  • [ ] ★★★ 从浏览器输入一个 URL 到页面返回，中间发生了什么？
  • 完整回答：
    • 解析 URL 与本地命中： 浏览器先解析协议、主机名、端口、路径、查询参数和片段，并判断浏览器缓存、Service Worker 或 HSTS 规则是否能直接影响后续访问；如果缓存可用，可能不真正访问源站。
    • DNS 与目标地址： 需要出网时会进行域名解析，浏览器、操作系统、hosts、本地 DNS 缓存和递归解析器都可能参与；递归解析器缓存未命中时，再向根、顶级域和权威 DNS 服务器迭代查询，最终得到 A/AAAA 等记录。
    • 路由与下一跳： 拿到目标 IP 后，主机根据路由表确定下一跳；同一链路通过 ARP 或 IPv6 NDP 找到下一跳 MAC，跨网段则把帧交给网关，由路由器逐跳转发。
    • 传输连接与加密： HTTP/1.1、HTTP/2 常运行在 TCP 上，需要先完成三次握手；HTTPS 还要经过 TLS 握手来验证证书、协商密钥和加密参数；HTTP/3 基于 QUIC/UDP，将传输握手与 TLS 1.3 集成，并支持连接迁移。
    • 中间层转发： 请求在到达应用服务前，可能先经过 CDN、WAF、四层或七层负载均衡、API 网关等组件，这些组件可能缓存、终止 TLS、改写头部或按规则路由。
    • 服务端处理： 应用侧收到请求后，可能读取缓存、数据库、对象存储、消息队列或调用下游服务，生成响应后再沿网络链路返回给浏览器。
    • 浏览器处理与渲染： 浏览器根据状态码、缓存头和内容类型处理响应；HTML 解析为 DOM，CSS 生成 CSSOM，二者合成渲染树，再进行布局、绘制和合成。JS 可能阻塞解析或触发新请求，图片、字体、脚本和样式也会影响首屏。
    • 常见边界： 不能把全过程简化成 DNS、TCP、HTTP 三步，还要考虑缓存、代理、TLS、连接复用、HTTP 版本、CDN 和浏览器渲染阶段的差异。

  • 原理解析：

    • 这道题考的是一次 Web 访问的端到端链路，不是单个 HTTP 请求。URL 先决定应用层语义和默认端口，缓存或 Service Worker 可能直接返回响应，也可能触发缓存校验；HSTS 则是在真正出网前把 HTTP 升级为 HTTPS，随后仍会继续 DNS、路由、传输连接和服务器处理。
    • 时序上可以记成“解析目标、找到地址、找到下一跳、建立安全传输、发送请求、生成响应、浏览器渲染”。DNS 负责名字到记录，ARP/NDP 负责同链路下一跳 MAC，IP 负责跨网段转发，TCP/QUIC 负责端到端传输，TLS 负责身份与加密，HTTP 承载资源语义。
    • 版本边界很关键：HTTP/1.1 和 HTTP/2 常见部署在 TCP 上，HTTP/2 解决的是 HTTP 层多路复用但仍受 TCP 丢包队头阻塞影响；HTTP/3 基于 QUIC/UDP，把 TLS 1.3 和传输握手整合，并用 stream 降低跨请求阻塞。
    • 工程链路经常经过 CDN、WAF、负载均衡和网关，这些是部署选择，不是 HTTP 规范本身；它们可能终止 TLS、改写头部、缓存静态资源或按七层规则路由，所以排障要区分浏览器、网络、中间层和源站。
    • 记忆抓手是“URL 不是直接到服务器，页面返回也不是结束”。响应回来后还有状态码、缓存策略、HTML/CSS/JS 解析、布局绘制和资源瀑布；只说 DNS、TCP、HTTP 会漏掉缓存、安全、版本和渲染四个高频考点。

  • [ ] ★★★ OSI 七层模型和 TCP/IP 模型分别是什么？

  • 完整回答：
    • OSI 七层定位： OSI 七层模型是一种教学和分析用的分层参考模型，从下到上依次是物理层、数据链路层、网络层、传输层、会话层、表示层和应用层。
    • 低层职责： 物理层关心电信号、光信号、无线信号和比特传输；数据链路层关心帧、MAC 地址、同一链路内寻址、差错检测和介质访问，典型例子有以太网、Wi-Fi。
    • 网络与传输层： 网络层负责跨网络寻址和路由，核心协议是 IP，ICMP 也常在这一层讨论；传输层提供端到端进程通信，典型协议有 TCP、UDP，QUIC 虽基于 UDP 实现，但功能上承担连接、可靠性、拥塞控制和多路复用。
    • 高层职责： 会话层和表示层分别抽象会话管理、数据表示、编码和加密等能力；应用层承载 HTTP、DNS、SMTP、SSH、RPC 等面向应用语义的协议。
    • TCP/IP 模型： TCP/IP 模型更贴近互联网实际实现，常见划分为链路层、网络层、传输层、应用层，也有人把链路层进一步拆成网络接口层和物理层。
    • 真实协议边界： 实际协议栈并不严格一一对应 OSI。例如 TLS 通常位于应用协议和 TCP 之间，既做加密表示，也参与身份认证；DNS 是应用层协议，但可以运行在 UDP、TCP、DoT、DoH 等不同承载上。
    • 分层价值： 分层帮助明确职责和排障边界：发送时上层数据逐层封装为段、包、帧和比特，接收时逐层解封装；排障时可区分链路不通、IP 路由异常、端口不可达、TLS 证书失败，还是应用返回错误。
    • 工程理解： 工程中使用分层模型是为了沟通和定位，不是要求每个真实协议都机械塞进某一层；跨层优化很常见，但不能混淆各层对外提供的基本语义和排错入口。

  • 原理解析：

    • 分层模型的核心不是背名字，而是把“谁负责什么”拆清楚。低层提供传输介质和相邻节点交付，中间层提供跨网络寻址与端到端进程通信，高层定义应用语义、编码、安全和会话组织；每层只依赖下层能力，对上层暴露相对稳定的接口。
    • 封装时应用数据向下依次加头：传输层形成段或数据报，网络层形成 IP 包，链路层形成帧，物理层变成比特信号；接收端反向解封装。抓住“数据单位变化”和“地址变化”：MAC 管一跳，IP 管跨网路径，端口管进程。
    • OSI 是参考模型，TCP/IP 是互联网实际协议族的常用抽象，两者不是严格映射表。会话层、表示层在真实栈中常被应用库、TLS、序列化格式承担；QUIC 虽跑在 UDP 之上，但功能上又实现可靠传输和拥塞控制。
    • 常见误区是把某协议机械塞进一层后停止思考。DNS 是应用层协议，但可走 UDP、TCP、HTTPS；TLS 位于 HTTP 与 TCP 之间，兼具加密、认证和协商；ICMP 服务于网络层控制和诊断，但也会被应用工具间接使用。
    • 记忆抓手是排障路径：先看物理和链路是否通，再看 IP 路由和 DNS，再看端口、握手、TLS，最后看 HTTP 状态和业务响应。分层是定位边界的工具，不是现实协议栈的硬隔板。

  • [ ] ★★★ TCP 和 UDP 有什么区别？分别适用于哪些场景？

  • 完整回答：
    • TCP 的核心语义： TCP 是面向连接的可靠字节流协议，通信前要建立连接，通信中通过序列号、确认应答、重传、滑动窗口、流量控制和拥塞控制，尽量保证数据按序、不丢、不重地交付给应用。
    • TCP 的消息边界： TCP 提供连续字节流，不保留应用每次 write/send 的消息边界，因此上层协议必须自行定义长度、分隔符或帧格式。
    • UDP 的核心语义： UDP 是无连接的数据报协议，发送前不需要建立连接，头部较小，保留一次发送对应一个数据报的边界；但协议本身不保证可达、顺序、不重复，也不提供 TCP 那样的内建流量控制和拥塞控制。
    • 性能与控制权： UDP 的优势不是“绝对更快”，而是机制简单、延迟低，应用可以自行选择可靠性、重传和拥塞策略；在丢包可容忍或时效性高于完整性的场景更合适。
    • 典型场景： TCP 常用于 Web、文件传输、邮件、数据库连接、常规 RPC 等要求可靠有序的业务；UDP 常用于 DNS 查询、实时音视频、在线游戏、监控上报、广播/组播和部分隧道协议。
    • QUIC 边界： 现代 QUIC 基于 UDP 构建可靠传输、多路复用、拥塞控制和 TLS 1.3 加密，所以不能把“UDP 应用”简单等同于“不可靠”。
    • 工程风险： UDP 数据报过大可能触发 IP 分片，任一分片丢失会导致整个报文不可用；TCP 在高丢包链路上可能受队头阻塞、连接状态和拥塞控制影响。糟糕的应用层重传策略也可能让 UDP 服务比 TCP 更不稳定。
    • 选型维度： 选择协议时应看可靠性、时延、消息边界、网络穿透、中间设备兼容性，以及应用是否愿意承担传输控制复杂度；防火墙和 NAT 对两者的处理习惯也会影响可达性。

  • 原理解析：

    • TCP 的抽象是“连接上的可靠有序字节流”，UDP 的抽象是“尽力而为的数据报”。前者用连接状态、序列号、ACK、重传、窗口和拥塞控制把复杂性放进内核协议栈；后者只提供端口复用、长度、校验和和一次数据报边界，把可靠性选择留给应用。
    • 报文语义不同会直接影响编程模型。TCP 中多次 write 可能被对端一次 read 读到，也可能一次大消息被多次 read 读完；UDP 一次 sendto 对应一个 datagram，接收缓冲区不够时还可能截断或丢弃，所以 UDP 保边界不等于保完整可达。
    • 因果链上，TCP 可靠性带来握手、状态、重传等待和队头阻塞，适合文件、网页、数据库和常规 RPC；UDP 少握手、少状态、低延迟，但丢包乱序要应用承受，适合 DNS、音视频、游戏、广播组播或自定义传输。
    • 版本与部署边界要分清：QUIC 使用 UDP 只是为了穿透现有网络和用户态演进，它本身提供可靠 stream、拥塞控制和 TLS 1.3；因此“UDP 不可靠”说的是 UDP 协议本身，不是所有基于 UDP 的应用协议。
    • 常见误区是把 UDP 简化成“一定快”。小请求、拥塞网络、NAT 超时、防火墙策略、应用重传算法都会改变结果；选型记“可靠顺序选 TCP，可控时效选 UDP，浏览器现代低延迟 Web 传输关注 QUIC”。

  • [ ] ★★★ TCP 为什么需要三次握手？两次可以吗？

  • 完整回答：
    • 核心目标： TCP 建立连接的目标是让双方确认彼此的收发能力，并同步双方的初始序列号，而不只是笼统地“保证可靠”。
    • 第一次握手： 客户端发送 SYN，携带自己的初始序列号，状态从 CLOSED 进入 SYN-SENT；服务端收到后知道客户端具备发送能力、自己具备接收能力。
    • 第二次握手： 服务端返回 SYN+ACK，既确认客户端的 SYN，也发送自己的初始序列号，并进入 SYN-RECEIVED；客户端收到后知道服务端具备接收和发送能力，也知道自己的报文确实到达。
    • 第三次握手： 客户端发送 ACK 确认服务端的 SYN；服务端收到后才能确认客户端也具备接收服务端报文的能力，双方进入 ESTABLISHED。
    • 两次握手的问题： 两次握手不能完整确认服务端到客户端方向的可达性。服务端如果发出 SYN+ACK 后就认为连接成立，可能为一个从未最终确认的连接分配资源。
    • 历史报文防护： 三次握手还能防止历史重复 SYN 造成错误连接。网络中延迟的旧 SYN 到达服务端后，若客户端已不需要该连接，会返回 RST 或不完成最终 ACK，服务端就不会把旧请求当成真正连接。
    • 序列号意义： 初始序列号用于标识连接生命周期中的字节位置，降低旧报文混入新连接的风险；SYN backlog、SYN cookie、超时重传和半连接队列等机制则用于应对丢包和 SYN flood。
    • 实现边界： 第三次 ACK 可以携带数据，但是否使用取决于协议栈和应用；准确回答应落到双向能力确认、序列号同步和旧报文/半连接资源问题。

  • 原理解析：

    • 三次握手要同时完成两件事：确认双向通信能力和同步双方初始序列号。第一次 SYN 证明客户端到服务端方向可达，第二次 SYN+ACK 证明服务端能收也能发，第三次 ACK 证明客户端能收到服务端报文，服务端此时才有足够证据进入已建立连接。
    • 两次握手的问题不只是“少一次不可靠”，而是服务端无法确认自己的 SYN+ACK 是否到达客户端。若服务端第二次后就分配已建立连接资源，丢失的 SYN+ACK、伪造源地址或历史 SYN 都可能形成无用状态，增加半连接和资源耗尽风险。
    • 序列号是字节流可靠传输的坐标系，SYN 会消耗一个序号。双方交换 ISN 后，后续 ACK 才能表达“我期望收到哪个字节”；这也帮助识别旧连接生命周期中延迟到达的历史报文，降低混入新连接的概率。
    • 实现选择包括 SYN backlog、重传次数、SYN cookie、TCP Fast Open 等，它们不改变三次握手的基本语义。TFO 允许在握手阶段携带数据，但依赖 cookie 和实现支持，不能理解为取消了连接确认。
    • 记忆抓手是“问、答加反问、确认答复”：客户端问能连吗，服务端回答并问回去，客户端确认服务端的问题。只说“为了可靠”太粗，完整答案要落到双向可达、序列号和旧报文/资源问题。

  • [ ] ★★★ TCP 为什么通常需要四次挥手？

  • 完整回答：
    • 全双工前提： TCP 是全双工协议，一个连接包含客户端到服务端、服务端到客户端两个独立的数据发送方向；关闭一个方向只表示该端不再发送数据，并不表示它不能继续接收数据。
    • 主动方 FIN： 主动关闭方调用关闭后发送 FIN，含义是“我这一侧的数据已经发送完毕”。被动关闭方收到 FIN 后返回 ACK，确认这个方向关闭。
    • 半关闭状态： 被动关闭方确认对方 FIN 后，自己的应用可能还有剩余数据要写，所以连接通常进入半关闭状态；等它也发送完数据并决定关闭自己的发送方向时，才再发送 FIN。
    • 典型四个报文： 主动关闭方收到被动方 FIN 后返回最后一个 ACK，然后进入 TIME_WAIT；被动关闭方收到 ACK 后进入 CLOSED。这个过程常表现为 FIN、ACK、FIN、ACK 四个报文，所以称为四次挥手。
    • 报文数不是绝对： 四次挥手不是协议强制每次都拆成四个独立包；如果被动关闭方收到 FIN 时已经没有数据要发送，协议栈可能把 ACK 和自己的 FIN 合并，看起来像三次交互。
    • 状态与排障： 主动方可能经历 FIN_WAIT_1、FIN_WAIT_2、TIME_WAIT，被动方可能经历 CLOSE_WAIT、LAST_ACK；如果应用收到对方 FIN 后迟迟不关闭本端 socket，就可能积累 CLOSE_WAIT，通常说明应用没有正确释放连接。
    • FIN 与 RST： FIN 关闭的是有序字节流，RST 是异常复位，会丢弃未读数据并立即拆除连接。
    • 常见误区： 四次挥手的原因不是“双方各发两次固定报文”，而是全双工方向独立关闭，报文数量还会受应用状态和协议栈合包影响。

  • 原理解析：

    • TCP 是全双工字节流，两个发送方向可以独立结束。FIN 的精确语义是“我不再发送新数据”，不是“整个连接马上消失”；收到 FIN 的一方仍然可以把已缓冲或应用稍后写出的数据发完，所以关闭天然可能分成两个方向。
    • 典型时序是主动方 FIN 后进入 FIN_WAIT_1，被动方 ACK 后进入 CLOSE_WAIT；当被动方应用也 close 时发送 FIN，主动方 ACK 后进入 TIME_WAIT，被动方进入 CLOSED。这里 ACK 与 FIN 分离，是因为“确认对方结束”和“自己也结束”不是同一个事件。
    • 报文数量是常见表现，不是绝对规范要求。若被动方收到 FIN 时正好也无数据要发，协议栈可能把 ACK 和 FIN 合并；若异常关闭则可能发 RST，直接复位并丢弃未交付数据，语义不同于有序的 FIN 关闭。
    • CLOSE_WAIT 积累通常不是网络问题，而是应用收到对端关闭后没有及时关闭本端 socket；TIME_WAIT 出现在主动关闭方，用来兜底最后 ACK 丢失和旧包过期。状态名能帮助把责任定位到应用、协议栈还是对端。
    • 记忆抓手是“两个方向各关一次”。建立连接需要同步双方起点，关闭连接要分别结束两个方向；不要把四次挥手背成固定四包，而要解释为什么被动方可以先 ACK、稍后 FIN。

  • [ ] ★★★ TIME_WAIT 状态有什么作用？过多时如何分析？

  • 完整回答：
    • 出现位置： TIME_WAIT 通常出现在主动关闭 TCP 连接的一方，它不是异常状态，而是正常关闭流程的一部分。
    • 保证最后 ACK： 主动关闭方发出最后一个 ACK 后，如果该 ACK 丢失，被动关闭方会重发 FIN；主动方停留在 TIME_WAIT，才能再次回复 ACK，避免对方一直重传或收到异常复位。
    • 隔离旧报文： TIME_WAIT 还用于让旧连接中的迟到报文在网络中自然过期，避免相同四元组的新连接复用后被旧报 文污染。
    • 2MSL 设计： TIME_WAIT 持续时间通常按 2MSL 设计，MSL 是报文在网络中的最大生存时间；不同操作系统和内核版本的默认值、参数名和语义可能不同。
    • 是否故障： TIME_WAIT 过多本身不一定是故障，高并发短连接客户端、代理、网关或主动关闭连接的一侧都可能自然积累。
    • 分析路径： 先确认本机是客户端还是服务端、谁主动关闭、四元组分布、连接创建速率、端口耗尽情况、文件描述符和内存占用，再结合 HTTP keep-alive、连接池、上游超时、负载均衡 idle timeout、发布重启和异常报错判断原因。
    • 治理优先级： 优先减少短连接和不必要主动关闭，例如启用连接复用、合理配置连接池、匹配服务端与客户端超时策略、扩大可用本地端口范围、分散源地址或实例。
    • 调参边界： 直接调低 TIME_WAIT 时间或开启复用类内核参数，需要理解版本差异以及 NAT、中间设备、时间戳选项带来的风险；只有同时出现端口耗尽或连接失败时，才应把它作为容量问题优先处理。

  • 原理解析：

    • TIME_WAIT 服务于 TCP 关闭的最后可靠性。主动关闭方发出最后 ACK 后，如果立即删除连接状态，而这个 ACK 又丢了，被动方重发 FIN 时本机无法按原连接语义补 ACK，可能导致对端长时间重传或收到复位。
    • 另一个作用是隔离旧报文。TCP 连接由源 IP、源端口、目的 IP、目的端口标识；若四元组很快复用，网络中迟到的旧段可能被误认为新连接数据。等待 2MSL 的设计，就是让旧包有时间自然消亡。
    • “过多”要先转成容量问题看：谁主动关闭、是否高频短连接、源端口是否耗尽、是否集中访问少量四元组、连接池和 keep-alive 是否失效、上游或负载均衡 idle timeout 是否先断。没有错误和资源压力时，TIME_WAIT 多只是连接行为的结果。
    • 内核参数属于实现与版本选择，不是协议万能开关。不同 Linux 版本对 reuse、timestamps、端口范围和 TIME_WAIT 回收语义差异很大，NAT 或负载均衡场景下激进复用可能放大旧包和身份混淆风险。
    • 记忆抓手是“最后 ACK 的保险箱、旧连接的隔离带”。治理优先减少短连接和不必要主动关闭，再扩端口、调连接池和超时；不要一看到 TIME_WAIT 就先改内核。

  • [ ] ★★★ TCP 如何保证可靠传输？

  • 完整回答：
    • 整体机制： TCP 的可靠传输由多种机制共同完成，不是依赖单一确认；它面向字节流，在连接正常维持期间尽力向应用提供可靠有序的数据。
    • 序列号与重组： TCP 给字节流中的每个字节编号，报文段携带序列号；接收方据此按序重组，发现重复数据并丢弃重复片段。
    • ACK 与 SACK： 接收方通过 ACK 告诉发送方已经连续收到哪些数据。传统 ACK 是累积确认，表示某个序号之前的数据都已收到；SACK 选项还能报告已收到的非连续区间，帮助发送方只重传真正缺失的片段。
    • 超时与快速重传： 发送方维护重传计时器，超时未收到确认会重传；如果收到多个重复 ACK，通常可以触发快速重传，在超时前补发可能丢失的报文。
    • 校验和边界： TCP 头部校验和能发现传输中的部分比特错误，但它不是密码学完整性保护，不能替代 TLS 的认证加密。
    • 滑动窗口： 滑动窗口允许发送方在未收到每个 ACK 前连续发送一定数量的数据，提高吞吐，同时限制在途数据规模。
    • 流控与拥塞控制： 接收窗口 rwnd 反映接收方缓冲区能力，避免发送方压垮接收方；拥塞窗口 cwnd 由发送方根据 ACK、丢包、延迟等反馈估计网络承载能力，避免把网络打爆。
    • 可靠性的边界： TCP 不能保证应用一定处理成功，也不能保证业务幂等；连接断开、超时、RST 或应用崩溃时，上层仍需要超时、重试、去重和事务语义。可靠传输也有额外头部、状态维护、重传延迟和队头阻塞等代价。

  • 原理解析：

    • TCP 可靠性的基础是“给字节编号”。序列号标识本段第一个字节的位置，ACK 表示接收方已经连续收到的下一个期望序号；接收方可按序重组、缓存乱序段、丢弃重复段，发送方则据此知道哪些数据仍在路上或已丢失。
    • 丢包恢复靠超时重传和快速重传配合。RTO 适合没有足够反馈的场景，但等待较长；多个重复 ACK 暗示中间某段缺失，能提前触发快速重传。SACK 是选项，不改变基本 ACK 语义，但能减少不必要重传。
    • 滑动窗口把可靠性和效率连接起来：发送方不必等每段确认后再发下一段，而是在窗口内连续发送。实际可发数据受接收窗口、拥塞窗口、发送缓冲和应用写入速度共同限制，所以可靠传输不是无限制猛发。
    • TCP 校验和只能发现常见传输差错，不提供抗篡改身份认证；TLS 才提供密码学完整性和机密性。TCP 保证的是到本机应用读取接口前的有序字节流，不能保证服务端业务提交成功、消息只处理一次或事务回滚。
    • 记忆抓手是“编号、确认、重传、排序、窗口”。常见误区是说 TCP 永不丢数据；更准确是连接正常时尽力恢复，无法恢复时通过超时、RST 或错误把失败交给应用处理。ACK 丢失不等于数据丢失，接收端仍要靠序号去重，发送端也会再确认。

  • [ ] ★★★ TCP 流量控制和拥塞控制有什么区别？

  • 完整回答：
    • 区别概括： 流量控制和拥塞控制都会限制发送速度，但流量控制解决“接收方收不收得下”，拥塞控制解决“网络路径扛不扛得住”。
    • 流量控制变量： 流量控制的核心变量是接收窗口 rwnd。接收方根据接收缓冲区剩余空间在 ACK 中通告窗口大小，发送方不能让未确认数据超过这个窗口。
    • 零窗口场景： 如果接收端应用读取很慢，rwnd 会变小，甚至进入零窗口状态；发送方只能通过零窗口探测等待接收方恢复。
    • 拥塞控制变量： 拥塞控制关注网络路径承载能力，核心变量是拥塞窗口 cwnd，由发送方根据 ACK、丢包、延迟等网络反馈动态调整。
    • 实际发送窗口： 实际发送窗口通常受 min(rwnd, cwnd) 约束，还会受到发送缓冲区、应用写入速度、接收端延迟 ACK 等因素影响；两者叠加时只能按更小约束发送。
    • 传统拥塞算法： 传统拥塞控制以丢包作为拥塞信号，慢启动阶段指数增长 cwnd 来探测容量；达到阈值后进入拥塞避免，增长更保守；检测到丢包后通过快速重传、快速恢复或超时回退降低速率。
    • 算法差异： Reno/CUBIC 更多围绕丢包和窗口增长，BBR 更关注带宽和往返时延估计；窗口扩大选项、缓冲区配置和内核算法版本也会改变实际吞吐上限和调优空间。
    • 排查方法： 流量控制问题常见于接收端应用慢、缓冲区不足，表现为 rwnd 很小；拥塞控制问题常见于链路排队、丢包、RTT 上升，表现为吞吐下降和重传增加。排查时应分别观察 rwnd、cwnd、RTT、重传率、丢包和应用读取速度。

  • 原理解析：

    • 流量控制保护接收端，拥塞控制保护网络路径。前者的问题是“对方应用或缓冲区接不住”，由接收方在 ACK 中通告 rwnd；后者的问题是“中间链路承载不了”，由发送方根据丢包、ACK 节奏、RTT 或带宽估计维护 cwnd。
    • 发送窗口可粗略记为 min(rwnd, cwnd)。rwnd 小时，即使网络很空也不能多发，否则压垮接收缓冲；cwnd 小时，即使接收端很快也要收敛，否则造成排队、丢包和全网拥塞。两者都是限速，但因果对象不同。
    • 典型时序上，接收端应用读取慢会让可用缓冲减少，窗口通告下降，甚至零窗口，发送端做窗口探测等待恢复；网络拥塞则表现为 ACK 变慢、RTT 上升、重复 ACK 或超时，拥塞算法降低 cwnd 后再探测。
    • 算法是实现选择和版本边界。Reno、CUBIC、BBR 的增长和回退逻辑不同，窗口扩大、自动调缓冲、延迟 ACK 也会影响观测；不能只凭“吞吐低”判断是哪一类控制在起作用。
    • 记忆抓手是“rwnd 看接收方，cwnd 看网络”。排障要同时看窗口、RTT、重传、丢包、应用消费速率和系统缓冲；把接收端慢误判成网络拥塞，会导致调错方向。rwnd 低时扩带宽无效，cwnd 受限时加接收缓冲也无效。

  • [ ] ★★★ TCP 为什么会发生粘包和拆包？如何解决？

  • 完整回答：
    • 问题本质： 粘包和拆包不是 TCP 协议错误，而是应用层把 TCP 的有序字节流误当成一条条消息造成的现象。
    • 粘包原因： TCP 不记录应用调用 write/send 的边界。发送方多次小写入可能被协议栈、Nagle 算法、缓冲区或网卡合并成较少报文，接收方一次 read 也可能读到多个应用消息。
    • 拆包原因： 一个很大的应用消息可能因 MSS、发送窗口、拥塞窗口、接收缓冲区或应用读取长度限制，被拆成多个 TCP 段，接收方一次 read 只能拿到部分内容。
    • 解决原则： 解决方式必须在应用层协议中定义明确 framing，也就是消息边界；不能依赖一次 read 得到完整请求，也不能假设一次 write 会被对端按同样粒度读取。
    • 常见分帧方式： 固定长度协议解析简单，但浪费空间且扩展不灵活；分隔符协议适合文本场景，例如按换行分隔，但要处理转义、内容中出现分隔符和超长行；长度字段最常见，先读固定头部获得 body 长度，再循环读取完整 body，并校验长度上限以避免内存攻击。
    • 协议例子： JSON、Protobuf 这类自描述格式外层通常仍需要长度或流式解析规则；HTTP/1.1 通过 Content-Length、Transfer-Encoding: chunked 或连接关闭确定消息边界，HTTP/2/gRPC 使用二进制帧，Redis RESP 使用前缀长度和分隔符组合。
    • 工程实现： 应使用缓冲区、状态机和循环解析，处理半包、多个完整包、非法长度、连接关闭和超时。
    • Nagle 边界： 关闭 Nagle 只能影响小包发送时机，不能替代协议分帧。

  • 原理解析：

    • TCP 的协议对象是字节流，不是应用消息。内核只负责把一串有序字节交给对端，write/send 的次数不会写进 TCP 头；接收端 read 到多少，取决于缓冲区、应用读取长度、调度时机和已到达字节数。
    • “粘包”来自多个应用消息在流中相邻，被一次读取或一次解析看到；“拆包”来自一个应用消息跨多个 TCP 段或多次 read 才凑齐。MSS、窗口、Nagle、延迟 ACK、网卡分段卸载和应用缓冲都会改变传输粒度，但都不提供消息边界。
    • 正确解法是应用层 framing：固定长度、分隔符、长度字段、TLV、HTTP chunk、HTTP/2 frame、Redis RESP 等。本质都是让接收方能判断“一个完整消息从哪里开始、在哪里结束”，并能在半包和多包场景下持续解析。
    • 工程实现应使用缓冲区和状态机：先读头，再按长度读体；检查最大长度、非法格式、超时和连接关闭；一次 read 后循环取出所有完整消息，剩余不完整部分留到下次。这样才能同时处理粘连、半包和恶意输入。
    • 记忆抓手是“TCP 保顺序，不保边界”。关闭 Nagle 只影响小数据发送等待，不能解决协议分帧；UDP 保数据报边界，但又不保证可靠、顺序和不重复。

  • [ ] ★★★ HTTP/1.1、HTTP/2 和 HTTP/3 的主要区别是什么？

  • 完整回答：
    • HTTP/1.1 特点： HTTP/1.1 是文本协议，引入并普及了持久连接、Host 头、缓存控制、分块传输等能力；持久连接允许一个 TCP 连接复用多个请求，减少握手成本。
    • HTTP/1.1 队头阻塞： 管线化理论上允许连续发送多个请求，但响应必须按请求顺序返回，容易出现应用层队头阻塞，现实部署中使用不广泛；浏览器通常通过多个并发 TCP 连接提升并行度。
    • HTTP/2 分帧与多路复用： HTTP/2 改为二进制分帧，把一个连接拆成多个 stream，请求和响应被切成 frame 后可交错传输，从而解决 HTTP 层的请求排队问题。
    • HTTP/2 其他能力： HTTP/2 提供 HPACK 头部压缩、流优先级和服务端推送等机制；其中服务端推送在现代浏览器中支持和使用都很有限。
    • HTTP/2 的 TCP 边界： HTTP/2 多路复用仍运行在一个 TCP 字节流之上，如果底层 TCP 某个包丢失，后续字节即使属于其他 stream，也必须等重传后才能交付给应用，这就是 TCP 层队头阻塞。
    • HTTP/3 与 QUIC： HTTP/3 基于 QUIC/UDP。QUIC 在用户态实现连接、可靠传输、多路复用、拥塞控制和 TLS 1.3 加密，不同 stream 的丢包通常不会阻塞其他 stream 的应用数据交付；它还通过 Connection ID 支持网络切换后的连接迁移。
    • 压缩与部署： HTTP/3 使用 QPACK 头部压缩，以适配 QUIC 多流传输。版本选择受客户端、服务端、中间设备、TLS、CDN 和 UDP 可达性影响。
    • 性能边界： HTTP/2/3 不必然总比 HTTP/1.1 快，小请求、弱网、代理链路、服务器实现和优先级调度都会影响结果；HTTP 语义基本延续，差异主要在连接和传输层表达方式。

  • 原理解析：

    • 三个版本的 HTTP 语义大体延续，请求方法、状态码、头字段和资源语义不是每代重造；主要变化在“如何在连接上传输这些语义”。HTTP/1.1 是文本报文，HTTP/2 是二进制帧和 stream，HTTP/3 把 HTTP 映射到 QUIC stream。
    • HTTP/1.1 keep-alive 降低建连成本，但一个连接内响应按序返回，管线化容易被前一个慢响应阻塞，所以浏览器长期用多条 TCP 连接绕开。HTTP/2 在单连接中交错传 frame，解决 HTTP 层请求排队，还用 HPACK 压缩头部。
    • HTTP/2 的边界在 TCP：所有 stream 最终仍是同一可靠字节流，某个 TCP 段丢失会阻塞后续字节交付，即使那些字节属于别的 stream。HTTP/3 的 QUIC 在 UDP 上实现多 stream 可靠传输，单个 stream 丢包通常不阻塞其他 stream 的应用数据。
    • 部署边界同样重要。HTTP/2 在浏览器里通常要求 TLS 并通过 ALPN 协商；HTTP/3 依赖 UDP 可达、QUIC 支持和 Alt-Svc 或 HTTPS 记录等发现机制。CDN、代理、防火墙和服务器优先级调度都会影响真实效果。
    • 记忆抓手是“1.1 文本复用连接，2 分帧复用请求，3 换 QUIC 复用传输”。不要说新版本一定更快；小页面、弱 UDP、错误优先级或中间代理都可能让收益变小。

  • [ ] ★★★ HTTPS 的 TLS 握手过程是什么？

  • 完整回答：
    • HTTPS 与 TLS 目标： HTTPS 是 HTTP 运行在 TLS 之上。TLS 握手用于认证服务端身份、协商协议参数、生成共享密钥，并为后续 HTTP 数据提供机密性、完整性和身份保护。
    • ClientHello： 以常见 TLS 1.3 为例，客户端先发送 ClientHello，包含支持的 TLS 版本、密码套件、扩展、SNI、ALPN、随机数，以及用于密钥交换的 key share。
    • ServerHello 与服务端证明： 服务端返回 ServerHello，选择版本和密码套件，提供自己的 key share，随后发送加密的扩展、证书、证书验证和 Finished。
    • 客户端验证与密钥派生： 客户端验证证书链、域名、有效期、用途、签名算法和吊销状态等，再发送 Finished；双方基于 ECDHE 等临时密钥交换材料和随机数派生会话密钥。
    • 应用数据保护： 握手完成后，HTTP 应用数据使用对称加密和 AEAD 完整性保护传输；非对称密码主要用于身份认证和密钥协商，不用于大量业务数据加密。
    • TLS 版本差异： TLS 1.2 的典型 ECDHE 握手往返更多，消息结构也不同；旧式 RSA 密钥交换不具备前向安全，现代部署通常不推荐。TLS 1.3 默认使用具备前向安全的密钥交换，移除了许多旧算法。
    • 恢复与 0-RTT： TLS 1.3 支持会话恢复和 0-RTT；0-RTT 可以减少延迟，但早期数据可能被重放，因此只适合幂等或可防重放的请求。
    • 部署与失败原因： 证书只能证明公钥和域名身份关系，不能证明业务本身可信。实际部署还涉及 ALPN 协商 HTTP/2 或 HTTP/1.1、SNI 选择虚拟主机、OCSP Stapling、证书轮换和中间证书配置；握手失败可能来自证书链、时间、域名、算法兼容或中间设备拦截。

  • 原理解析：

    • TLS 握手的核心是“先确认你是谁，再商量怎么安全通信”。ClientHello 暴露客户端能力和随机数，ServerHello 选择具体参数；证书链把域名和服务端公钥绑定，CertificateVerify 证明服务端持有私钥，Finished 校验此前握手未被篡改。
    • 密钥机制要区分用途：非对称签名用于身份认证，ECDHE 等密钥交换用于生成共享秘密，对称 AEAD 用于大量应用数据加密和完整性保护。大量业务数据不用 RSA 直接加密，是因为性能、前向安全和协议设计都不适合。
    • TLS 1.3 和 TLS 1.2 的边界很重要。TLS 1.3 精简握手、默认前向安全、移除旧算法，并把多数握手后消息加密；TLS 1.2 的消息和往返更多，旧 RSA 密钥交换即使证书可信，也没有前向安全。
    • 部署细节不是装饰：SNI 决定同一 IP 上选哪个证书，ALPN 决定后续用 HTTP/2 还是 HTTP/1.1，OCSP Stapling 改善吊销状态获取，中间证书缺失、系统时间错误、域名不匹配或公司代理插证书都会导致失败。
    • 0-RTT 是性能优化而非免费加速。会话恢复可减少握手成本，但 0-RTT 早期数据存在重放风险，只适合幂等请求或业务层能去重的动作。记忆抓手是“身份、参数、密钥、校验、加密数据”。

  • [ ] ★★★ DNS 解析的完整过程是什么？

  • 完整回答：
    • DNS 作用： DNS 解析是把域名转换为 IP 地址或其他记录的分布式查询过程，结果不只可能是 A/AAAA，也可能涉及 CNAME、MX、TXT、NS 等记录。
    • 本地查询顺序： 客户端通常先查浏览器缓存、操作系统缓存、hosts 文件，以及本机或局域网 DNS 缓存；未命中时才把查询发给配置的递归解析器。
    • 递归解析器来源： 递归解析器可能由运营商、企业网关、公共 DNS 或本地代理提供；普通客户端多数只和递归解析器交互。
    • 迭代查询过程： 如果递归解析器也没有可用缓存，它会代表客户端迭代查询：先问根服务器，根服务器返回对应顶级域服务器信息；再问 .com、.cn 等 TLD 服务器，得到目标域名的权威 DNS 服务器地址；最后问权威服务器获取目标记录。
    • CNAME 与 TTL： 如果返回 CNAME，还要继续解析 CNAME 指向的规范域名，直到得到最终需要的记录。解析结果会按 TTL 缓存在各级解析器中，TTL 影响变更生效速度和缓存命中率，但不同客户端、递归解析器和中间 DNS 代理可能有最小/最大缓存策略。
    • 承载协议： DNS 默认常用 UDP 53；报文过大、区域传送或部分场景会使用 TCP；现代安全和隐私场景还可能使用 DoT、DoH 或 DoQ。
    • 权威侧调度： 权威 DNS 可结合地理位置、运营商、EDNS Client Subnet、负载均衡和健康检查返回不同结果，因此同一域名在不同网络下可能解析到不同地址。
    • 排障边界： 常见误区是认为客户端亲自查询根到权威全过程，或认为 DNS 只返回一个 IP。真实部署中可能有多个记录、CNAME 链、IPv4/IPv6 双栈和 CDN 调度，排障时要同时检查本地缓存、递归解析器缓存和权威记录是否一致。

  • 原理解析：

    • DNS 是分布式命名系统，目标不是只返回 IP，而是按记录类型回答问题。A/AAAA 给 IPv4/IPv6 地址，CNAME 给规范名，MX 指邮件交换，NS 指权威服务器，TXT 常用于验证和策略；查询时必须带着期望记录类型理解结果。
    • 普通客户端多数只做 stub resolver：查本地缓存和 hosts 后，把问题交给递归解析器。递归解析器才代表它从根、TLD 到权威服务器迭代追问；根和 TLD 通常返回“去问谁”，权威服务器才对目标域名数据负责。
    • 时序里 CNAME 会产生继续解析的因果链，TTL 决定缓存可用时间。TTL 低可让变更更快扩散但增加查询量，TTL 高命中率好但切流慢；实际还受浏览器、系统、递归解析器和 DNS 代理的最小/最大缓存策略影响。
    • 协议边界要分清：传统 DNS 常用 UDP 53，响应过大、截断、区域传送等场景会用 TCP；DoT、DoH、DoQ 是安全或隐私承载选择，不改变 DNS 记录语义。CDN 基于地理、运营商、ECS、健康状态返回不同答案属于权威侧调度策略。
    • 记忆抓手是“本地先找，递归代问，根指路，权威作答，TTL 缓存”。排障不要只 dig 一个公共 DNS，要比较本机、递归解析器和权威结果，并注意 IPv4/IPv6 和 CNAME 链。

  • [ ] ★★ GET 和 POST 的区别是什么？

  • 完整回答：
    • 本质区别： GET 和 POST 的核心区别来自 HTTP 方法语义，而不是“参数放 URL 还是请求体”。
    • GET 语义： GET 用于获取目标资源的当前表示，按规范语义应是安全的，即不应产生用户可感知的服务端状态改变；它也应是幂等的，即同一请求执行一次和多次的预期效果相同。
    • POST 语义： POST 表示把请求体提交给目标资源处理，常用于创建子资源、提交表单、触发计算或执行非幂等动作，因此重复提交可能产生多条订单、多次扣款或多次任务。
    • 参数位置： GET 参数通常放在查询串中，便于链接分享、缓存和书签；POST 数据通常放在 body 中，适合较复杂或较大的提交内容。但 HTTP 并不把“GET 绝不能有 body”或“POST 参数只能在 body”作为语义核心。
    • 兼容性边界： 不同服务器、代理和客户端对 GET body 支持不一致，实践中应避免依赖它；URL 长度限制主要来自浏览器、服务器、网关和代理实现，不是 HTTP 统一规定的固定值。
    • 缓存与自动行为： GET 更容易被浏览器、代理和 CDN 按缓存头缓存，也可能被预加载、重试或记录在历史、日志和 Referer 中；POST 默认通常不被缓存，但带明确缓存控制时也可能被缓存。
    • 安全边界： 敏感信息不应放在 URL 中，因为会进入日志和历史；但放在 POST body 也不是安全边界，防窃听和防篡改仍依赖 HTTPS、认证、授权和签名等机制。

  • 原理解析：

    • GET 与 POST 的核心差异是方法语义。GET 表示取资源表示，规范语义安全且幂等；POST 表示把请求内容交给目标资源处理，常见结果是创建、提交、触发计算或产生副作用，所以重复请求可能改变业务状态。
    • URL 参数和 body 是常见实践，不是本质定义。GET 常把查询条件放在 query，利于缓存、分享、书签和日志追踪；POST 常把表单或 JSON 放 body，利于表达复杂提交。GET body 在协议层不是核心语义，生态兼容差，工程上不应依赖。
    • 因果链上，安全和幂等会影响缓存、预取、重试和爬虫行为。GET 可能被浏览器、代理或 CDN 根据缓存头复用，POST 默认通常不缓存；如果服务端用 GET 做扣款删除，就会被自动重试或预加载放大风险。
    • 常见误区是“POST 更安全”。URL 会进入历史、日志和 Referer，确实不适合敏感信息；但 body 也会被服务端日志、代理或抓包看到，真正的传输安全依赖 HTTPS，业务安全还依赖认证、授权、CSRF 防护和签名。
    • 记忆抓手是“GET 取表示，POST 交处理”。回答时先讲语义，再讲参数位置、缓存、长度限制和安全；不要把浏览器或网关的 URL 长度限制说成 HTTP 标准固定值。

  • [ ] ★★ HTTP 常见状态码有哪些？

  • 完整回答：
    • 状态码作用： HTTP 状态码用于表达服务器对请求的处理结果，客户端、代理、网关、缓存和监控系统都会依赖它做判断。
    • 1xx 信息响应： 1xx 表示过程性信息，例如 100 Continue 表示客户端可以继续发送请求体，101 Switching Protocols 常用于协议升级。
    • 2xx 成功： 200 OK 是通用成功；201 Created 表示资源已创建，通常配合 Location 头；202 Accepted 表示请求已接受但尚未处理完成，适合异步任务；204 No Content 表示成功但没有响应体。
    • 3xx 重定向与缓存： 301 Moved Permanently 表示永久迁移，客户端和搜索引擎可能缓存；302 Found 是临时重定向，历史实现中方法处理存在差异；303 See Other 常用于 POST 后跳转到查询页；307/308 更明确要求保留原方法；304 Not Modified 表示缓存仍有效，不返回主体。
    • 4xx 客户端问题： 400 Bad Request 是请求格式或参数错误；401 Unauthorized 表示未认证或认证无效；403 Forbidden 表示已识别身份但无权限；404 Not Found 表示资源不存在；405 Method Not Allowed 表示方法不支持；409 Conflict 表示资源状态冲突；415 Unsupported Media Type 表示内容类型不支持；422 常用于语义校验失败；429 Too Many Requests 表示限流。
    • 5xx 服务端或上游问题： 500 是内部错误；502 是网关收到无效上游响应；503 表示服务暂不可用，可配 Retry-After；504 表示网关等待上游超时。
    • 业务错误边界： 业务错误不应一律塞进 200，否则会削弱缓存、重试、告警和客户端通用处理能力；但具体 API 也要保持一致的错误结构。

  • 原理解析：

    • 状态码是 HTTP 层给通用组件看的结果分类，不只是给前端展示文案。浏览器、代理、CDN、网关、SDK、重试器、监控告警和缓存都会依据状态码判断是否成功、是否重定向、是否可缓存、是否该重试。
    • 分类先记百位：1xx 过程提示，2xx 成功，3xx 重定向或缓存协商，4xx 请求侧问题，5xx 服务端或上游问题。具体码再记高频语义，例如 201 创建、202 异步受理、204 无主体、304 缓存有效、429 限流。
    • 重定向里方法语义有坑：301/302 历史实现常把 POST 改成 GET，303 明确让客户端去 GET 另一个资源，307/308 要求保留原方法和 body。缓存协商中的 304 不是错误，也不应带完整响应体。
    • 4xx 与 5xx 的因果边界影响告警和责任定位。401 是未认证，403 是已识别但无权限，404 是资源不存在或隐藏，409 是状态冲突，422 是语义校验失败；502/504 多指网关与上游链路，503 表示暂不可用并可配 Retry-After。
    • 常见误区是业务失败都返回 200 再在 JSON 里塞错误码。这样会破坏缓存、重试、监控和客户端通用处理；合理做法是 HTTP 状态表达协议层结果，响应体承载业务错误细节并保持结构一致。

  • [ ] ★★ Cookie、Session、Token 和 JWT 有什么区别？

  • 完整回答：
    • 概念层级： Cookie 是浏览器提供的客户端存储和自动携带机制，Session 通常是服务端保存会话状态的模式，Token 是访问凭证的泛称，JWT 是一种具体的自包含 Token 格式。
    • Cookie 机制： 服务端通过 Set-Cookie 写入 Cookie，浏览器之后按域名、路径、Secure、SameSite、过期时间等规则随请求发送。Cookie 本身不等于登录态，只是承载数据或凭证的容器。
    • Cookie 安全属性： HttpOnly 可降低被 JS 读取的风险，Secure 限制只在 HTTPS 中发送，SameSite 能降低部分 CSRF 风险。
    • Session 模式： Session 通常由服务端保存会话状态，客户端只持有 session id，服务端根据 id 查询 Redis、数据库或内存中的会话数据。
    • Session 优缺点： Session 容易集中撤销、续期和管理；缺点是依赖服务端存储，分布式部署需要共享会话、粘性会话或统一认证中心。
    • Token 与 JWT： Token 可以是不透明随机串，也可以是结构化令牌，可放在 Authorization Header、Cookie 或其他位置。JWT 由 header、payload、signature 三部分组成，payload 存声明，签名用于防篡改。
    • JWT 安全边界： JWT 默认只是 Base64URL 编码，不是加密，任何拿到令牌的人都能解码载荷，所以不能放密码、身份证号等敏感明文；若需要加密应使用 JWE 或把敏感数据放服务端。
    • 选型与防护： JWT 可无状态校验，适合跨服务传递身份声明，但过期前难以即时撤销，通常需要短有效期、刷新令牌、黑名单、用户版本号或密钥轮换配合。无论 Cookie、Session 还是 Token，泄露后都可能被冒用，必须结合 HTTPS、CSRF/XSS 防护、过期策略、设备管理和权限校验。

  • 原理解析：

    • Cookie 是浏览器机制，Session 是服务端会话模式，Token 是凭证概念，JWT 是一种具体 token 格式。四者不在同一分类层级：Cookie 可以装 session id 或 JWT，Token 可以放 Header 或 Cookie，Session 也可以用 Redis、数据库或内存实现。
    • Cookie 的关键在自动携带和作用域规则。Domain、Path 决定发送范围，Expires/Max-Age 决定生命周期，Secure、HttpOnly、SameSite 分别约束 HTTPS、JS 读取和跨站发送；这些是浏览器行为，不等同于服务端登录逻辑。
    • Session 的因果链是“客户端交 id，服务端查状态”。好处是可集中撤销、改权限、续期和踢下线；代价是服务端存储和分布式一致性，需要共享存储、粘性会话或统一认证。JWT 的链路是“服务端签发，资源方验签读声明”，减少查询但撤销较难。
    • 安全边界要分清：JWT 签名防篡改，不默认加密；Base64URL 可直接解码，不能放敏感明文。Cookie 的 HttpOnly 防读取但不防自动携带，仍要考虑 CSRF；Header Token 较少受 CSRF 影响，但更怕 XSS 窃取。
    • 记忆抓手是“Cookie 管携带，Session 管状态，Token 管凭证，JWT 管格式”。选型看撤销需求、跨服务传播、浏览器安全模型、过期刷新和权限变更频率。

  • [ ] ★★ 长连接、短连接、WebSocket 和 SSE 分别适用于什么场景？

  • 完整回答：
    • 短连接场景： 短连接是每次请求建立连接、完成响应后关闭连接，模型简单、资源释放明确，但每次都要付出 TCP 握手、TLS 握手、慢启动和认证等成本，适合低频、简单或资源受限场景。
    • 长连接场景： 长连接是在同一连接上连续处理多个请求或持续传输数据，HTTP/1.1 keep-alive、HTTP/2 多路复用和数据库连接池都属于连接复用思路。
    • 长连接代价： 长连接能显著减少握手和建连开销，但会占用文件描述符、内存、连接池、负载均衡连接表和服务端状态，需要合理的 idle timeout、心跳、限流和关闭策略。
    • WebSocket 能力： WebSocket 通过 HTTP/1.1 Upgrade 建立后切换为持久的全双工消息通道，客户端和服务端都可以主动发送数据，适合聊天、协同编辑、实时游戏、交易行情、在线客服等双向实时场景。
    • WebSocket 工程点： WebSocket 绕过普通 HTTP 请求响应模型，工程上要额外处理连接认证、心跳保活、断线重连、消息顺序、背压、水平扩展和网关支持。
    • SSE 能力： SSE 即 Server-Sent Events，基于普通 HTTP 响应持续推送 text/event-stream，浏览器 EventSource 原生支持自动重连和事件 ID。
    • SSE 场景与限制： SSE 适合服务端到客户端单向推送，例如通知、任务进度、日志流、价格更新和模型流式输出；它通常比 WebSocket 更容易穿过代理和 HTTP 基础设施，但只支持服务端向浏览器推送文本事件，客户端要发送数据仍需另发 HTTP 请求。
    • 选择标准： 选择时看通信方向、频率、实时性、代理兼容性、浏览器支持、服务端连接规模和消息可靠性要求，而不是简单认为长连接一定优于短连接。
  • 原理解析：
    • 短连接和长连接描述的是连接生命周期，不是某个单独协议。短连接每次请求付出建连、TLS 和慢启动成本，但释放明确；长连接复用连接降低延迟和 CPU 成本，却长期占用 fd、内存、连接表和负载均衡状态。
    • WebSocket 是从 HTTP/1.1 Upgrade 切换出的全双工消息通道，之后不再是普通请求响应语义。它适合双向实时和高频小消息，但要自己处理认证续期、心跳、断线重连、背压、消息确认、水平扩展和网关超时。
    • SSE 是基于 HTTP 响应流的服务端单向推送，Content-Type 为 text/event-stream。浏览器 EventSource 支持自动重连和 Last-Event-ID，适合通知、进度、日志、行情和模型流式输出；客户端上行仍需普通 HTTP 请求。
    • 部署习惯会影响选型。SSE 更容易复用 HTTP 代理、鉴权和缓存基础设施，但浏览器连接数、代理缓冲和超时要配置；WebSocket 对网关支持、负载均衡粘性和连接规模更敏感，但双向交互能力更强。
    • 记忆抓手是“低频短连，复用长连，双向 WebSocket，单向 SSE”。不要默认长连接更好；当请求很少、服务资源紧张或中间设备不友好时，短连接反而更简单可靠。
