4. 并发编程

  • [ ] ★★★ 并发和并行有什么区别？
  • 完整回答：
    • 并发和并行描述的是两个不同层面的能力。
    • 并发强调在同一段时间内多个任务都能推进，重点是程序结构、调度和资源复用；并行强调在同一时刻多个任务真正同时执行，重点是硬件执行单元和任务是否能被拆分。
    • 单核 CPU 上可以通过时间片轮转、事件循环或协程调度让多个请求交替推进，这属于并发，但任意时刻只有一个指令流在核心上运行。
    • 多核 CPU、多个硬件线程、GPU 或多台机器可以让多个计算任务同时运行，这才是并行。
    • 语言无关地看，并发解决“如何同时管理很多进行中的事情”，例如一个网关同时维护大量连接；并行解决“如何更快完成可拆分的工作”，例如把图片处理切成多块在多个核心上计算。
    • Java 线程、C++ std::thread、Go goroutine、Rust async task 都可以表达并发，但能否并行取决于运行时是否把任务调度到多个内核线程、是否受全局解释器锁等机制限制，以及任务本身是否被锁、I/O、依赖关系串行化。
    • 并发程序不必然更快，线程切换、锁竞争、缓存失效、队列排队和上下文传播都会消耗资源；并行程序也不必然线性加速，因为任务拆分、合并结果和共享数据同步会受到 Amdahl 定律限制。
    • 常见误区是把“多个线程”直接等同于“并行”。
    • 在单核机器上多个线程只是并发；在多核机器上，如果线程都在等待同一把锁或同一个下游服务，实际执行也可能高度串行。
    • 设计时应先判断瓶颈是 I/O 等待、CPU 计算、锁竞争还是下游容量，再决定用异步并发、线程池、并行计算、分片还是队列削峰。

  • 原理解析：

    • 概念边界：并发是“任务生命周期重叠”，关注调度、等待与资源复用；并行是“执行时刻重叠”，依赖多个执行单元。单核时间片切换能制造多个任务都在推进的效果，但同一时刻只有一个任务占用核心，所以是并发不是并行。
    • 因果链：当任务主要等待 I/O 时，并发能把等待时间让给其他任务，提高资源利用率；当任务主要消耗 CPU 且可拆分时，并行才可能缩短总计算时间。若任务间共享状态多、锁竞争重或合并结果成本高，并行收益会被同步和通信抵消。
    • 内存与同步：并发程序一旦共享可变状态，就要处理互斥、可见性和执行顺序；并行程序还会放大缓存一致性、伪共享和内存带宽瓶颈。语言无关原理是“先定义共享和依赖”，具体实现才落到线程、协程、事件循环或任务调度器。
    • 实现差异：Java、C++、Go 都能创建并发任务，但是否真正并行取决于运行时、操作系统线程映射、CPU 核数和语言限制。记忆抓手是：并发解决“多件事怎么都照顾到”，并行解决“一件大事怎么拆开同时做”。
    • 设计误区：看到响应慢就加线程，可能只是让更多任务一起排队或一起争锁；看到多核就拆任务，也可能被串行依赖和结果合并限制。先用瓶颈类型决定模型，再用监控确认 CPU 利用、等待时间和锁竞争。

  • [ ] ★★★ 线程安全是什么意思？常见的线程安全问题有哪些？

  • 完整回答：
    • 线程安全是指多个线程并发访问同一段代码或共享状态时，无论调度顺序如何交错，只要调用方式满足接口约定，程序结果都保持正确，不依赖偶然的时序。
    • 它不是“代码里用了锁”这么简单，而是共享状态在并发下满足业务不变量，例如库存不能扣成负数、集合内部结构不能损坏、状态机不能跳过非法状态。
    • 通用地看，线程安全问题主要来自原子性、可见性和有序性。
    • 原子性问题是一个逻辑操作由多个读写步骤组成，中途被其他线程插入，例如 i++ 包含读、加一、写回，两个线程可能丢失更新。
    • 可见性问题是一个线程写入的值没有按预期被另一个线程看到，原因可能是寄存器缓存、CPU 缓存、编译器优化或语言内存模型没有建立同步关系。
    • 有序性问题是编译器、CPU 或运行时在不破坏单线程结果的前提下重排指令，但并发观察者可能看到中间状态。
    • Java 通过 volatile、锁、原子类和 happens-before 规则定义可见性与重排序边界；C++ 通过 std::atomic 的 memory order、mutex 和数据竞争规则定义行为，普通数据竞争甚至可能导致未定义行为；Go 通过 channel、mutex、atomic 和内存模型规定同步前后关系，不能把某一种语言的规则泛化到所有语言。
    • 常见线程安全问题包括竞态条件、丢失更新、发布未完全初始化对象、迭代时并发修改容器、死锁、活锁、饥饿、优先级反转和锁外读写破坏不变量。
    • 解决手段包括不可变对象、线程封闭、减少共享状态、互斥锁、读写锁、原子变量、线程安全容器、消息传递、单线程事件循环和事务化更新。
    • 性能代价也要明确：锁会阻塞和切换，原子操作会引发缓存一致性流量，线程安全容器可能扩大临界区，过度同步会降低并发度。
    • 常见误区是认为单个方法加锁就一定安全；如果多个方法组合起来才构成业务操作，调用者仍可能在方法之间看到被其他线程修改后的状态。

  • 原理解析：

    • 核心概念：线程安全不是“不会崩溃”，而是在所有允许的线程交错下都保持不变量。判断对象是一个操作、一个类、还是一组业务步骤；如果库存扣减由读库存、判断、写回组成，单步安全并不代表组合安全。
    • 三类根因：原子性缺失导致多个线程把一个逻辑操作拆开交错执行；可见性缺失导致写入没有被其他线程及时、按规则观察到；有序性问题来自编译器、CPU 或运行时重排，使并发观察者看到单线程中不会暴露的中间状态。
    • 同步机制：互斥锁通过排他进入临界区同时建立释放与获取之间的同步关系；原子变量适合单变量或简单状态转移；消息传递、不可变对象和线程封闭则通过减少共享来降低证明难度。正确性先于性能，临界区要覆盖完整不变量。
    • 语言边界：Java 用 happens-before、volatile、锁和原子类约束行为；C++ 对普通数据竞争可给出未定义行为，memory order 更细；Go 依赖 channel、mutex、atomic 等建立同步。记忆抓手是：共享可变状态同时需要“不能插队、能看见、别乱序”。
    • 边界误区：线程安全通常是有范围的，单个容器安全不等于容器中多步业务操作安全，单个字段原子也不等于对象整体状态安全。分析时要写出被保护的不变量，以及哪些读写必须处在同一同步协议下。

  • [ ] ★★★ 互斥锁、读写锁、自旋锁和信号量有什么区别？

  • 完整回答：
    • 互斥锁、读写锁、自旋锁和信号量都用于协调并发访问，但抽象语义和适用边界不同。
    • 互斥锁保护临界区，同一时刻最多一个线程持有锁，适合维护普通共享数据结构或跨多个字段的不变量。
    • 竞争失败时，用户态锁通常先短暂尝试，失败后让线程阻塞，由内核或运行时在锁释放后唤醒；成本包括原子指令、内存屏障、上下文切换和锁队列管理。
    • 读写锁把访问分成共享读和独占写，允许多个读者同时进入，但写者必须独占，适合读操作远多于写操作、读临界区较短且读写语义清晰的场景。
    • 读写锁不是免费优化：写多、读持锁时间长、读写切换频繁或公平策略不合适时，它可能比互斥锁更慢，还可能出现写饥饿或读者排队。
    • 自旋锁在获取失败时不立即睡眠，而是在 CPU 上循环检查锁状态，避免睡眠和唤醒开销，适合临界区极短、线程不能睡眠或内核中断上下文等场景；如果持锁时间长、线程数超过核心数或锁竞争激烈，自旋会浪费 CPU 并加剧缓存行争用。
    • 信号量维护一个许可计数，获取许可后进入，释放时归还，适合限制最多 N 个并发访问者，例如连接池、下载并发、限流窗口；当许可数为 1 时可模拟互斥，但信号量通常不表达“谁拥有锁”的所有权语义，错误释放更难被发现。
    • 不同语言实现差异很大：Java 的 synchronized、ReentrantLock、ReadWriteLock、Semaphore 由 JVM 和 java.util.concurrent 提供；C++ 标准库提供 mutex、shared_mutex、counting_semaphore 等；Go 常用 sync.Mutex、sync.RWMutex 和 channel 模拟许可。
    • 选择时先缩小共享状态和临界区，再选最简单能表达约束的原语。
    • 常见误区是看到“读多写少”就一定用读写锁，或把自旋锁用于普通业务长临界区；正确性优先于吞吐，锁粒度、持锁时间和失败路径比锁名称更重要。

  • 原理解析：

    • 抽象差异：互斥锁表达“同一时刻只能一个执行者修改或观察受保护不变量”；读写锁表达“读读可共享、读写和写写互斥”；自旋锁表达“暂不让出 CPU，反复检查”；信号量表达“许可数量有限”，不天然表达所有权。
    • 同步因果：锁获取失败后的阻塞会让线程进入等待队列，减少 CPU 空转但付出上下文切换；自旋避免睡眠唤醒，却会持续消耗核心并推动缓存行在核心间迁移。读写锁只有在读多、写少、临界区短且公平策略合适时才可能胜过互斥锁。
    • 适用边界：保护复杂共享对象优先用互斥锁；读多写少且读操作不会修改隐藏状态时考虑读写锁；极短临界区、内核或不能睡眠场景才适合自旋；连接池、限流和最多 N 个并发者更适合信号量。
    • 实现差异：Java、C++、Go 的锁是否可重入、是否公平、是否支持升级降级、等待是否可中断都不同，不能按名字推断行为。记忆抓手是：锁管临界区，读写锁拆读写，自旋用 CPU 换延迟，信号量管名额。
    • 常见陷阱：锁粒度过大降低并发度，锁粒度过小又可能保护不住跨字段不变量；读锁里做慢 I/O 会拖住写者；信号量许可泄漏会让系统永久降容。选择原语前先明确“保护数据”还是“限制数量”，再检查持有期间是否可能阻塞、递归或跨层回调。

  • [ ] ★★★ 什么是 CAS？它有什么问题？

  • 完整回答：
    • CAS 是 Compare-And-Swap 或 Compare-And-Set 的缩写，语义是读取某个内存位置的当前值，与调用方给出的期望值比较；如果相等，就以一个不可分割的原子步骤写入新值，否则不写入并返回失败。
    • CAS 的底层通常由 CPU 原子指令支持，例如 x86 的 cmpxchg 或 ARM 的 load-linked/store-conditional 族机制；语言运行时再把它封装成原子变量、无锁队列、引用更新或乐观状态转移。
    • 典型执行过程是：线程先读取旧值，基于旧值计算新值，然后调用 CAS；若期间没有其他线程把值改成不同内容，更新成功；否则重新读取并重试或走失败分支。
    • CAS 的好处是不必在失败线程上进行传统阻塞等待，在低冲突、操作短小、单变量状态更新时可以减少锁竞争，例如计数器、状态位、对象引用发布。
    • 它的第一个问题是 ABA：一个值从 A 改成 B 又改回 A，CAS 只看到当前仍等于 A，无法知道中间变化，可能破坏栈、队列等依赖节点生命周期的无锁结构。
    • 缓解办法包括版本号、时间戳、带标记指针、hazard pointer、epoch 回收或 Java 中的 AtomicStampedReference，但这些都有额外复杂度。
    • 第二个问题是高竞争下自旋重试会消耗 CPU，并让同一个缓存行在核心间频繁迁移，吞吐可能不如阻塞锁或分段计数。
    • 第三个问题是单个 CAS 难以维护多个变量或多个对象之间的一致性，复杂无锁算法需要精确的内存序、回收策略和线性化点，验证难度高。
    • Java 原子类通常提供 volatile 级别的可见性语义；C++ compare_exchange 需要显式选择成功和失败 memory order；Go 的 sync/atomic 也有自己的内存模型约束。
    • 常见误区是把 CAS 称为“无锁所以没有锁开销”。
    • CAS 仍然需要原子指令和内存屏障，仍然会产生缓存一致性成本，也不能自动解决业务层的重试、幂等和公平性问题。

  • 原理解析：

    • 核心语义：CAS 把“比较当前值”和“写入新值”合成一个不可分割的硬件级原子步骤，线性化点就是成功写入的那一刻。它适合把状态转移表示成“只有当前仍是我看到的旧值，才允许改成新值”。
    • 内存模型：CAS 不只是比较数值，还通常伴随内存序约束，保证前后读写在并发观察者眼中的顺序。Java 原子类、C++ compare_exchange、Go sync/atomic 暴露的内存语义不同，尤其 C++ 需要显式考虑成功和失败路径 memory order。
    • 问题链条：高冲突时多个线程反复读旧值、计算、CAS 失败、重试，会消耗 CPU 并制造缓存一致性流量；ABA 则是值看似没变但历史已经变化，依赖节点身份或生命周期的无锁结构会因此误判。
    • 边界误区：CAS 能降低阻塞锁成本，但不能自动维护多字段不变量，也不保证公平；复杂无锁算法还要解决内存回收、重试退避和失败处理。记忆抓手是：CAS 乐观地赌“没人改过”，赌错就重来，赌对也只保证这个原子点。
    • 实践判断：计数器、状态位、引用替换适合 CAS；账户转账、双队列迁移、多个字段一致更新通常更适合锁或事务。若重试循环中包含昂贵计算、外部调用或不可幂等副作用，CAS 失败路径会变得危险。

  • [ ] ★★★ 什么是乐观并发控制和悲观并发控制？

  • 完整回答：
    • 悲观并发控制和乐观并发控制是处理共享资源冲突的两种策略，而不是某个具体语言或数据库独有的机制。
    • 悲观控制假设冲突经常发生，因此在执行关键操作前先取得排他权，其他执行者必须等待、失败或绕行。
    • 互斥锁、数据库行锁、SELECT ... FOR UPDATE、分布式锁都体现了悲观思想。
    • 它的优点是语义直接，适合冲突概率高、失败代价大、必须串行维护不变量的场景，例如抢占任务、账户余额转账、关键库存行扣减。
    • 代价是锁等待、死锁、连接占用、上下文切换和吞吐下降；持锁期间如果包含网络 I/O、慢查询或外部回调，风险会显著放大。
    • 乐观控制假设冲突较少，读或计算阶段不先排他锁定资源，而是在提交时检查资源是否仍符合预期，例如版本号、时间戳、状态条件、ETag、CAS 期望值或数据库条件更新。
    • 典型 SQL 是 UPDATE item SET value=?, version=version+1 WHERE id=? AND version=?，影响行数为 0 表示并发冲突，需要重试、提示用户或放弃。
    • 乐观控制适合读多写少、操作可重试、冲突提示可接受的场景，例如资料编辑、配置发布、低冲突状态流转。
    • 它的代价集中在冲突时：计算结果可能作废，重试会增加尾延迟和系统负载，重试风暴可能把热点资源压垮，因此必须有次数上限、退避、幂等和失败处理。
    • 语言内存里的 CAS 是乐观并发的一种底层形式，数据库版本号也是乐观控制的一种业务实现，但两者的隔离、持久性和可见性规则不同，不能混为一谈。
    • 常见误区是认为乐观锁完全不加锁；数据库执行最终 UPDATE 时仍会加行锁，只是冲突检测推迟到写入阶段。
    • 另一个误区是认为悲观锁一定更安全；如果锁范围不准、租约过期、锁顺序不一致或事务过长，仍会出现并发错误、死锁或可用性问题。

  • 原理解析：

    • 策略本质：悲观控制先假设会冲突，所以先拿排他权再操作；乐观控制先假设少冲突，所以先读和计算，提交时再验证条件。二者都在维护同一件事：共享资源的不变量不能被并发交错破坏。
    • 因果链：悲观方式把冲突转化为等待或失败，降低回滚成本，但会带来锁等待、死锁和持锁资源占用；乐观方式把等待推迟为提交校验，低冲突时吞吐更好，高冲突时则变成大量重试、尾延迟和废弃计算。
    • 同步机制：互斥锁、行锁、分布式锁偏悲观；版本号、条件更新、ETag、CAS 偏乐观。数据库乐观更新最终仍可能短暂加行锁，内存 CAS 也只保护一个原子位置，它们体现同一思想但不共享事务隔离和持久化语义。
    • 边界误区：乐观不是“不加锁”，悲观也不是“一定安全”。锁范围、锁顺序、事务长度、租约过期、重试上限、幂等设计都会影响正确性。记忆抓手是：悲观先占座，乐观先办事、结账时验票。
    • 选择依据：冲突率高、失败代价大、必须串行维护强不变量时偏悲观；冲突率低、操作可重试、用户可接受冲突提示时偏乐观。热点资源上盲目乐观会形成重试风暴，长事务里盲目悲观会拖垮吞吐。工程上还要记录冲突率、重试次数和锁等待时间，用数据判断策略是否失配，并配套告警阈值、退避策略和降级路径。

  • [ ] ★★★ 线程池的核心参数有哪些？应该如何设置？

  • 完整回答：
    • 线程池把线程创建、复用、排队和拒绝策略集中管理，用来避免每个任务都新建线程，也用来给下游资源建立并发上限。
    • 核心参数通常包括核心线程数、最大线程数、任务队列类型与容量、空闲线程存活时间、线程工厂、拒绝策略，以及在某些框架中的预启动、钩子函数、任务超时和上下文传播配置。
    • Java ThreadPoolExecutor 的执行过程很典型：任务到来后，如果运行线程数小于核心线程数，优先创建核心线程；否则尝试入队；队列满且线程数小于最大线程数时再创建非核心线程；仍无法处理则触发拒绝策略。
    • 这个过程与 Go goroutine 调度、C++ 自建线程池、Rust async executor 不完全相同，但共同目标都是控制并发、排队和失败边界。
    • 参数设置应从任务性质和容量约束反推。
    • CPU 密集型任务主要消耗核心，线程数通常接近可用 CPU 核数或略高，过多线程只会增加上下文切换和缓存失效。
    • I/O 密集型任务有大量等待网络、磁盘或数据库的时间，线程数可以高于核心数，但上限不能超过数据库连接池、远程接口限流、文件描述符、内存和延迟目标。
    • 队列容量不是越大越好；长队列能削峰，但会增加排队时间，让请求在执行前已经超时，并掩盖过载。
    • 拒绝策略是背压的一部分，可以抛异常、调用者执行、丢弃、丢弃最旧任务或自定义降级告警，选择取决于任务是否可丢、是否同步请求、是否需要保护下游。
    • 线程工厂应设置可识别线程名、异常处理器和必要的优先级配置，便于日志和 dump 定位。
    • 生产中不能只套公式，应基于平均耗时、P95/P99、阻塞比例、峰值 QPS、下游容量和压测结果调参，并持续监控活跃线程、队列长度、拒绝次数、任务耗时、错误率、CPU、GC 和上下文切换。
    • 常见误区是把最大线程数设得很大来“提高吞吐”，实际可能只是把压力转移到数据库或外部服务，导致整体延迟和失败率上升。

  • 原理解析：

    • 抽象目标：线程池不是单纯复用线程，而是给任务执行建立“并发上限、排队边界和失败策略”。它把系统容量显式化：能同时跑多少、能等多少、超出后怎么办，避免把压力无限转移到内存和下游。
    • 设置逻辑：CPU 密集型受核心数限制，线程过多只会增加调度和缓存成本；I/O 密集型可高于核心数，因为等待期间线程不占用 CPU，但上限仍受数据库连接池、远程限流、文件描述符、内存和延迟目标约束。
    • 因果链：任务到达速率大于处理速率时，要么排队、要么扩线程、要么拒绝。队列过长会把延迟藏起来，最大线程数过大可能压垮下游，拒绝策略则是背压和降级的一部分，不是异常情况的装饰。
    • 实现边界：Java ThreadPoolExecutor 的“核心线程、队列、最大线程、拒绝”顺序很具体；Go、C++、Rust 执行器可能没有同一组参数，但容量规划原则相同。记忆抓手是：先看任务吃 CPU 还是等 I/O，再看下游能扛多少，最后用压测校准。
    • 运行校准：参数不是一次性公式，而要结合 P95/P99 耗时、峰值 QPS、阻塞比例、队列等待、拒绝次数、CPU、GC 和下游错误率持续调整。线程名、异常处理和监控指标也是线程池可运维性的组成部分。

  • [ ] ★★★ 为什么不建议无界队列或无限创建线程？

  • 完整回答：
    • 无界队列和无限创建线程的问题在于它们把系统过载隐藏起来，让失败从可控的拒绝、降级或限流，变成不可控的内存耗尽、调度崩溃和长尾延迟失控。
    • 无界队列表面上能接收所有任务，但当生产速度长期大于消费速度时，队列长度会持续增长，占用堆内存或进程内存；排队时间也会越来越长，很多任务被执行时请求方已经超时或业务价值已经消失。
    • 队列越长，故障恢复也越慢，因为系统即使下游恢复，也要先消化历史积压。
    • 无限创建线程同样危险。
    • 每个线程需要栈空间、线程控制块、调度状态和语言运行时元数据，还会竞争文件描述符、连接池、锁和 CPU 时间片。
    • 线程数远超核心数后，操作系统频繁调度，CPU 缓存局部性下降，上下文切换增加，真正执行业务代码的时间反而减少；在线程执行阻塞 I/O 时，还可能把过量并发继续打到数据库、缓存、消息队列和第三方接口，引发级联故障。
    • 通用原则是并发必须有边界：入口限流、线程数上限、有界队列、超时、取消、拒绝策略、熔断、降级和监控告警共同构成背压。
    • Java 固定线程池如果配无界 LinkedBlockingQueue，最大线程数可能形同虚设；Go goroutine 创建很便宜，但无界 goroutine 仍会消耗栈、调度器和下游资源；异步运行时中的无界任务队列也会制造同类问题。
    • 更合理的做法是按服务目标和下游极限设置容量，例如请求线程池队列只容纳短时间峰值，后台任务队列设定过期和失败处理，关键任务和可丢弃任务分池隔离。
    • 常见误区是认为“不拒绝请求”就是稳定，实际上稳定系统必须在超出能力时尽早、明确、可观测地施加背压，否则最终会在内存、连接数或延迟上以更差方式失败。

  • 原理解析：

    • 核心原则：任何系统都有容量上限，无界队列和无限线程只是把上限从业务层隐藏到内存、调度器、连接池或下游服务。稳定性设计要让过载尽早、明确、可观测地表现出来，而不是等资源耗尽后整体崩溃。
    • 因果链：生产速度长期大于消费速度时，无界队列会持续积压，内存和排队延迟同步增长；无限线程会消耗栈和调度元数据，线程数远超核心后上下文切换和缓存失效上升，真正业务执行时间下降。
    • 背压机制：有界队列、线程数上限、超时、取消、限流、熔断、拒绝和降级共同构成闭环。队列容量用于吸收短峰，不用于掩盖长期过载；拒绝策略用于保护系统整体，不等于“不服务用户”。
    • 语言边界：Java 无界队列可能让最大线程数失效；Go goroutine 虽轻量但不是零成本；异步任务队列也会占内存和下游并发。记忆抓手是：无限接单不是高可用，而是把失败延期并放大。
    • 边界设计：容量要按服务目标和下游极限反推，关键任务与可丢弃任务最好隔离，历史积压还要考虑过期和清理。一个健康系统在超载时应快速失败、降级或排队在可接受范围内，而不是无限等待。监控上至少能看到队列长度、创建速率、拒绝数和任务年龄，并能定位是哪类任务占满容量，便于及时隔离、扩容评估和故障复盘。

  • [ ] ★★ 如何实现一个生产者—消费者模型？

  • 完整回答：
    • 生产者—消费者模型用一个缓冲区把生产速度和消费速度解耦：生产者把任务、消息或数据块放入缓冲区，消费者从缓冲区取出处理。
    • 生产者和消费者可以有多个，但共享缓冲区必须满足互斥访问、空满等待、关闭退出和失败处理等语义。
    • 最常见实现是有界阻塞队列。
    • 队列未满时生产者入队；队列满时生产者阻塞、超时失败或触发拒绝策略，从而形成背压；队列非空时消费者出队；队列为空时消费者等待，直到有新任务或收到关闭信号。
    • 手写时通常需要一个互斥锁保护队列内部结构，再用两个条件变量表示“非空”和“未满”，等待条件必须放在循环中检查，避免虚假唤醒或被其他线程抢先消费。
    • 信号量也可以表达空槽数量和已用槽数量，环形缓冲区常用这种方式。
    • 不同语言应优先使用成熟库：Java 可用 BlockingQueue 和线程池，Go 可用有缓冲 channel 配合 context 取消，C++ 可用 mutex、condition_variable 或并发队列库。
    • 关闭语义必须提前定义：是停止接收新任务后消费完剩余任务，还是立即取消；是用关闭标记、特殊结束消息、关闭 channel，还是通过上下文传播取消。
    • 消费失败也要明确策略，例如有限重试、延迟重试、失败队列、丢弃、告警或幂等补偿。
    • 性能上，有界队列会增加入队出队和同步成本，但能限制内存并保护下游；队列过大增加延迟，过小降低削峰能力。
    • 常见误区是用普通列表加忙等循环实现，既不保证可见性和互斥，也浪费 CPU；另一个误区是只考虑正常生产消费，不处理关闭时消费者永久阻塞、生产者无法退出或失败任务无限重试的问题。

  • 原理解析：

    • 模型本质：生产者和消费者通过缓冲区解耦速率，缓冲区既是数据通道也是背压边界。正确实现必须同时回答四件事：谁能改队列、满了怎么办、空了怎么办、系统关闭或失败时怎么退出。
    • 同步机制：互斥锁保护队列结构和计数不变量；条件变量或信号量负责在“非空”和“未满”之间传递状态变化。等待条件要放在循环里复查，因为唤醒不等于条件仍成立，也可能出现虚假唤醒或被其他消费者抢先取走。
    • 边界处理：有界队列限制内存并保护下游，但容量过大会增加延迟，过小会削峰不足。关闭语义要提前定义，是消费完剩余任务再停，还是立即取消；失败任务也要有重试、丢弃、失败队列或告警策略。
    • 实现差异：Java BlockingQueue、Go buffered channel、C++ mutex/condition_variable 都能表达该模型，但取消、关闭和异常传播规则不同。记忆抓手是：一把锁保队列，两个条件管空满，一个关闭信号管收尾。

  • [ ] ★★ 如何保证多个线程按指定顺序执行？

  • 完整回答：
    • 保证多个线程按指定顺序执行，本质是把“顺序”建模为明确的依赖状态，而不是依赖操作系统调度的偶然先后。
    • 最简单的固定顺序可以用信号量、条件变量、锁加状态变量、事件对象或 channel。
    • 比如线程 A 完成后释放一个许可，线程 B 在该许可上等待；B 完成后再释放另一个许可给 C。
    • 条件变量实现时，需要在同一把锁保护下检查阶段变量，未到目标阶段就等待，被唤醒后重新检查条件，避免虚假唤醒和丢失通知。
    • 多任务依赖更复杂时，可以使用 Future/Promise、CompletableFuture、任务 DAG、倒计时器或屏障。
    • 倒计时器适合多个前置任务都完成后再启动后续任务；屏障适合同一批线程分阶段并行，每一阶段所有线程到达后再进入下一阶段；单线程执行器或队列适合必须严格串行处理的一组任务，往往比多个线程互相等待更简单。
    • 语言实现不同：Java 有 CountDownLatch、CyclicBarrier、Phaser、Semaphore、CompletableFuture；Go 常用 channel、sync.WaitGroup、mutex/cond；C++ 可用 std::condition_variable、std::latch、std::barrier、future。
    • 无论使用哪种工具，都要确保状态变更和通知之间有同步关系，否则其他线程可能看不到阶段更新。
    • 性能代价包括线程阻塞唤醒、上下文切换、调度延迟和过度串行化；如果业务实际没有并行收益，直接单线程顺序执行可能更可靠。
    • 常见误区是使用 sleep 猜测先后顺序，或用空循环读取普通变量等待状态变化。
    • 前者在不同机器负载下不可靠，后者可能因为可见性缺失永远看不到变化，还会浪费 CPU。

  • 原理解析：

    • 核心概念：指定顺序不是靠“哪个线程先被调度”，而是靠显式依赖状态。A 完成后发布信号，B 等到该信号再执行，B 完成后再唤醒 C，这样顺序由同步关系决定，而不是由时间片碰运气。
    • 同步机制：信号量、条件变量、事件、channel、Future、latch、barrier 都是在表达“前置条件满足”。条件变量要把阶段变量的检查、修改和通知放进同一同步协议里，被唤醒后必须重新检查条件，避免丢通知和虚假唤醒。
    • 适用边界：固定 A-B-C 顺序用链式信号最简单；多个前置任务全部完成后再继续，用倒计时器；多线程分阶段一起推进，用屏障；任务本来必须全串行时，单线程执行器或队列比线程互等更清晰。
    • 误区抓手：sleep 只能制造延迟，不能证明顺序；忙等普通变量既浪费 CPU，又可能因为可见性缺失永远看不到变化。记忆抓手是：顺序必须变成状态，状态必须被同步发布。

  • [ ] ★★ 什么是伪共享？如何避免？

  • 完整回答：
    • 伪共享是一种硬件缓存层面的性能问题：多个线程修改的是不同变量，逻辑上没有共享同一个字段，但这些变量恰好位于同一个 CPU 缓存行中，导致缓存一致性协议把它们当成同一粒度的数据来同步。
    • 现代 CPU 缓存通常以缓存行为单位加载和维护一致性，常见缓存行大小是 64 字节，但具体架构可能不同。
    • 当核心 1 修改缓存行中的变量 A，核心 2 修改同一缓存行中的变量 B 时，即使 A 和 B 没有业务关系，该缓存行的所有权也会在核心之间反复迁移，其他核心上的副本被置为无效，产生大量缓存一致性流量。
    • 结果是线程看起来没有锁竞争，却出现吞吐下降、CPU 利用率高但有效工作少、性能随线程数增加反而变差。
    • 伪共享常见于高频写计数器、数组中相邻槽位、环形队列的 head/tail、工作窃取队列、统计指标和并发框架底层结构。
    • 避免方式包括让高频写变量分散到不同缓存行、为结构体或对象字段添加填充、按线程分片计数后汇总、使用运行时提供的防伪共享注解或类型，以及调整数组步长或对象布局。
    • Java 曾有 @Contended 等机制，但使用受 JVM 参数和模块限制；C++ 可参考 std::hardware_destructive_interference_size 或手动 alignas；Go 需要通过结构体填充或库中已有的 cache line padding 类型处理。
    • 代价是占用更多内存，可能降低缓存容量利用率，并增加代码可读性负担。
    • 因此普通业务代码不应预先到处填充，应该先通过性能分析、硬件计数器、压测对比或并发热点定位确认问题。
    • 常见误区是把所有共享变量慢都归因于伪共享；真实共享写、锁竞争、内存分配、GC、系统调用和下游 I/O 也会造成类似现象，需要用证据区分。
  • 原理解析：
    • 硬件原理：CPU 缓存按缓存行维护一致性，不按变量维护。两个线程写不同变量时，如果变量落在同一缓存行，硬件仍要在核心之间转移该缓存行所有权，于是逻辑上不共享，物理上却发生了共享。
    • 性能因果：频繁写同一缓存行会让其他核心副本失效，缓存行反复迁移，表现为没有明显锁竞争却吞吐下降、核心很忙但有效工作少。高频计数器、相邻数组槽、队列 head/tail 是常见热点。
    • 避免方式：把高频写字段按缓存行隔开，使用填充、对齐、分片计数后汇总，或采用运行时提供的防伪共享类型。Java、C++、Go 的对象布局、对齐工具和注解支持不同，不能把某个注解当成通用方案。
    • 边界误区：填充会浪费内存并降低缓存容量利用率，不应无证据滥用；锁竞争、真实共享写、GC、系统调用和 I/O 也会导致类似慢。记忆抓手是：变量不同不代表缓存行不同。
