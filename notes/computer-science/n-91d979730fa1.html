学习目标

  • 理解配置阶段、生成阶段、构建阶段的区别。
  • 能写出现代 CMake 的目标式配置。
  • 能管理 include 路径、编译选项、链接库、测试和安装规则。
  • 能排查构建目录、缓存、编译器、生成器和依赖发现问题。

核心概念

  • 源码目录：包含 CMakeLists.txt 的项目目录。
  • 构建目录：CMake 生成工程文件和编译产物的位置，推荐与源码目录分离。
  • 生成器：决定生成 Ninja、Makefile、Xcode 或 Visual Studio 工程。
  • 目标：可执行程序、库或自定义构建对象。
  • 属性传播：PUBLIC、PRIVATE、INTERFACE 控制 include、编译定义和链接依赖如何传递。
  • 缓存：CMakeCache.txt 记录配置结果；编译器、依赖路径等变更后可能需要重新配置或清理构建目录。
  • 构建类型：单配置生成器常用 CMAKE_BUILD_TYPE=Debug 或 Release；多配置生成器在构建时选择配置。

最小项目示例

cmake_minimum_required(VERSION 3.20)
project(demo LANGUAGES CXX)

add_library(core src/core.cpp)
target_compile_features(core PUBLIC cxx_std_20)
target_include_directories(core PUBLIC include)

add_executable(demo_app src/main.cpp)
target_link_libraries(demo_app PRIVATE core)

说明：core 对外暴露头文件目录和 C++ 标准要求；demo_app 只是使用 core，所以链接关系是 PRIVATE。

常用命令

配置项目。会写入构建目录；不要把构建目录放进源码目录内的版本控制范围。

cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug

构建项目。会生成目标文件、库和可执行文件。

cmake --build build

并行构建。会增加 CPU 和内存压力；大型项目上可能让机器负载很高。

cmake --build build --parallel 8

运行测试。风险低，通常只读源码和运行测试产物；部分测试可能写临时文件或访问网络，取决于项目实现。

ctest --test-dir build --output-on-failure

安装到指定前缀。会写入安装目录；确认 --prefix 不指向系统路径，除非你确实需要系统级安装。

cmake --install build --prefix install

清理构建产物。会删除构建系统知道的产物；不会等同于删除整个 build 目录。

cmake --build build --target clean

常用配置片段

添加测试。

include(CTest)

if(BUILD_TESTING)
  add_executable(core_tests tests/core_tests.cpp)
  target_link_libraries(core_tests PRIVATE core)
  add_test(NAME core_tests COMMAND core_tests)
endif()

添加编译告警。

target_compile_options(core PRIVATE
  $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall -Wextra -Wpedantic>
  $<$<CXX_COMPILER_ID:MSVC>:/W4>
)

查找并链接外部包。

find_package(fmt CONFIG REQUIRED)
target_link_libraries(core PRIVATE fmt::fmt)

风险说明：find_package 的结果取决于包是否安装、安装方式、CMAKE_PREFIX_PATH 和工具链文件。不要假设所有机器都有同样的全局依赖。

典型工作流

  1. 新项目先建立 out-of-source 构建。
cmake -S . -B build/debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug
ctest --test-dir build/debug --output-on-failure
  1. 切换 Release 构建时使用独立目录。
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release --parallel 8
  1. 编译器或工具链变更时重新配置。
cmake -S . -B build/clang -DCMAKE_CXX_COMPILER=clang++

风险说明：不要在同一个 build 目录里反复切换编译器。缓存可能保留旧探测结果，导致问题难以解释。

常见坑

  • 在源码目录内构建，污染仓库并容易误提交生成文件。
  • 全局使用 include_directories()、link_libraries()，依赖边界不清晰。
  • 滥用变量拼接编译命令，没有利用 target 属性传播。
  • PUBLIC、PRIVATE、INTERFACE 随便写，导致依赖泄漏或下游缺少头文件。
  • 修改编译器、工具链或依赖路径后没有清理缓存。
  • 单配置和多配置生成器混用时误解 CMAKE_BUILD_TYPE。

排障步骤

  1. 看配置命令、生成器和编译器。
cmake -S . -B build --log-level=STATUS
cmake -LAH build
  1. 查看缓存中的关键变量。
rg "CMAKE_CXX_COMPILER|CMAKE_BUILD_TYPE|CMAKE_PREFIX_PATH" build/CMakeCache.txt
  1. 打开详细构建输出。
cmake --build build --verbose
  1. 依赖找不到时，显式提供前缀。
cmake -S . -B build -DCMAKE_PREFIX_PATH=/path/to/deps
  1. 无法解释的缓存问题，换一个新的构建目录验证。
cmake -S . -B build/fresh-debug -DCMAKE_BUILD_TYPE=Debug

风险说明：删除整个构建目录通常可恢复，但会丢失本地构建产物和缓存配置。删除前确认目录确实是构建目录，不是源码或安装目录。

练习

  • 写一个包含静态库和可执行程序的最小 CMake 项目。
  • 给库添加 PUBLIC 头文件目录，并解释为什么应用目标能找到头文件。
  • 添加一个测试目标并用 ctest 运行。
  • 分别创建 Debug 和 Release 构建目录，比较编译命令差异。

检查清单

  • 我能区分配置、生成、构建和测试阶段。
  • 我习惯使用 cmake -S . -B build 的 out-of-source 构建。
  • 我能解释 PUBLIC、PRIVATE、INTERFACE 的影响。
  • 我知道修改编译器或工具链后要避免复用旧缓存。
  • 我能用 verbose 构建和 CMakeCache.txt 排查问题。

  • 版本协作见：Git 和分支协作。
  • Python 辅助工具和脚本环境见：Python 环境和依赖管理。

深化学习说明

前半部分用于快速建立 CMake 命令、目标和常见片段的操作感。下面的内容进一步解释目标属性、配置/构建阶段证据和排障路径，帮助你从“能构建”推进到“能定位构建为什么失败”。

前置知识和完成标准

学习本章前，应理解编译、链接、头文件搜索路径、库文件和可执行文件的区别。CMake 不是编译器，而是生成构建系统的元构建工具；真正编译代码的是 GCC、Clang、MSVC 等工具链。

完成本章后，应能做到：

  • 区分配置、生成、构建、测试、安装五个阶段的输入和输出。
  • 能写出一个库、一个可执行程序、一个测试目标，并使用目标式命令传播依赖。
  • 能解释 PUBLIC、PRIVATE、INTERFACE 对当前目标和下游目标的影响。
  • 遇到“找不到头文件/库/包”时，能从 target 属性、缓存、编译命令和依赖安装位置逐层排查。

核心概念分层

第一层是目录分离：源码目录保存人写的文件，构建目录保存 CMake 生成物和编译产物。构建目录可删除重建，源码目录不应被生成物污染。

第二层是阶段分离：cmake -S -B 完成配置和生成，cmake --build 调用底层构建工具，ctest 执行已注册测试，cmake --install 执行安装规则。阶段不同，失败证据也不同。

第三层是目标模型：现代 CMake 以目标为中心。include 路径、编译选项、编译定义、链接库都挂在目标上，而不是通过全局变量散落到目录。

第四层是使用要求：库的头文件目录、C++ 标准、必要编译定义可能是消费者必须知道的要求，应通过 PUBLIC 或 INTERFACE 暴露；仅当前库内部需要的选项应保持 PRIVATE。

从零开始实验：库、应用、测试

教学边界：实验在系统临时目录下创建唯一目录。生产项目中不要直接复制版本号和目录结构，应遵循项目已有 CMake 最低版本和工具链约定。

lab_dir="$(mktemp -d "${TMPDIR:-/tmp}/cmake-lab.XXXXXX")"
mkdir -p "$lab_dir/include" "$lab_dir/src" "$lab_dir/tests"
cd "$lab_dir"
cat > include/mathlib.hpp <<'EOF'
#pragma once
int add(int a, int b);
EOF
cat > src/mathlib.cpp <<'EOF'
#include "mathlib.hpp"
int add(int a, int b) { return a + b; }
EOF
cat > src/main.cpp <<'EOF'
#include "mathlib.hpp"
#include <iostream>
int main() { std::cout << add(2, 3) << "\n"; }
EOF
cat > tests/mathlib_test.cpp <<'EOF'
#include "mathlib.hpp"
int main() { return add(2, 3) == 5 ? 0 : 1; }
EOF
cat > CMakeLists.txt <<'EOF'
cmake_minimum_required(VERSION 3.20)
project(cmake_lab LANGUAGES CXX)

add_library(mathlib src/mathlib.cpp)
target_compile_features(mathlib PUBLIC cxx_std_17)
target_include_directories(mathlib PUBLIC include)

add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE mathlib)

include(CTest)
if(BUILD_TESTING)
  add_executable(mathlib_test tests/mathlib_test.cpp)
  target_link_libraries(mathlib_test PRIVATE mathlib)
  add_test(NAME mathlib_test COMMAND mathlib_test)
endif()
EOF

cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure

预期结果：配置阶段识别 C++ 编译器，构建阶段生成 app 和 mathlib_test，测试阶段显示 100% tests passed。若缺少编译器，配置阶段就会失败；若 include 传播错误，构建测试目标时会报 mathlib.hpp 找不到。

验证方式：运行 ./build/app 应输出 5；cmake --build build --verbose 能看到编译命令中包含 -I.../include。

命令和配置逐段解释

target_include_directories(mathlib PUBLIC include)

mathlib 自己编译 src/mathlib.cpp 时需要 include，链接 mathlib 的 app 和 mathlib_test 也需要这个目录才能包含公开头文件，所以使用 PUBLIC。如果头文件只给库内部 .cpp 使用，应改为 PRIVATE。

target_link_libraries(app PRIVATE mathlib)

app 使用 mathlib，但 app 不是库，不需要继续把该依赖传播给下游，所以用 PRIVATE。如果某个库 api 的公开头文件中包含了 mathlib 的头文件，api 链接 mathlib 往往应使用 PUBLIC。

cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug

-S . 指源码目录，-B build 指构建目录，-D 设置缓存变量。单配置生成器会使用 CMAKE_BUILD_TYPE；Visual Studio、Xcode 等多配置生成器通常在构建时用 --config Debug 选择配置。

常见坑的机制和排障决策路径

遇到构建失败，先判断失败阶段：

  1. 配置阶段失败：先看终端错误和编译器探测。较新的 CMake 会把详细配置事件写入 build/CMakeFiles/CMakeConfigureLog.yaml；较旧版本常见证据在 build/CMakeFiles/CMakeOutput.log 和 build/CMakeFiles/CMakeError.log。排查 find_package 时还要保留完整配置命令和 CMAKE_PREFIX_PATH。
  2. 生成阶段失败：通常是目标名重复、生成表达式错误、属性冲突。
  3. 编译阶段失败：用 cmake --build build --verbose 看真实编译命令，确认 -I、-D、标准版本。
  4. 链接阶段失败：确认库是否被编译、链接顺序、符号是否定义、Debug/Release ABI 是否混用。
  5. 测试阶段失败：ctest --output-on-failure 查看测试 stdout/stderr，再进入单测二进制复现。

失败现象和含义：

  • Could NOT find fmt：CMake 没找到 fmt 的包配置或查找模块；检查包是否安装、CMAKE_PREFIX_PATH、工具链文件。
  • undefined reference 或 unresolved external symbol：头文件编译通过，但链接时找不到实现或链接了不匹配的库。
  • 修改 CMakeLists 后构建没变化：可能没有重新配置，或改的是未被包含的子目录。
  • 换编译器后错误异常：旧 CMakeCache.txt 保留了上一套工具链探测结果，应使用新构建目录验证。

练习答案要点

基础练习：最小项目必须包含 cmake_minimum_required、project、add_executable，并能完成 cmake -S . -B build && cmake --build build。

进阶练习：库的公开头文件目录用 PUBLIC，因为消费者编译自己的源码时也要找到这些头文件。若把它误写成 PRIVATE，库本身能编译，应用目标会失败。

综合练习：Debug/Release 对比应从独立构建目录产生，不能在同一个缓存里来回切。答案应说明 Debug 通常包含调试信息且优化较低，Release 通常优化更高，但具体编译参数由工具链和项目配置决定。

章节小结

现代 CMake 的主线是“目标及其使用要求”。少用全局命令，多让依赖关系跟着目标传播，构建问题就能从目标、属性、缓存和真实命令四个位置逐层定位。
