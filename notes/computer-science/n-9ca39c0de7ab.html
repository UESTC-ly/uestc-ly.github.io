分章节讲解

1. 超时

核心定义： 超时为远程调用设置等待上限，使调用方在依赖异常时释放资源并进入失败处理路径。

底层原理 / 机制拆解： - 超时包括连接超时、请求超时、读写超时、整体 deadline，每层含义不同。 - 合理超时应基于延迟分布、调用链预算和业务容忍度，而不是随意固定值。 - 超时发生时下游操作可能仍在执行，所以必须配合取消、幂等和结果查询。

适用场景： 适用于所有跨网络调用、数据库访问、缓存访问、外部 API、消息处理和批任务。

不适用场景 / 失败边界： 不适合无限等待，也不适合过短导致正常 P99 请求被大量误杀。

工程实践或做题/面试理解： 工程上用端到端 deadline 逐层递减，监控超时率和下游实际完成情况；面试中强调“超时是资源边界”。

常见误区与纠正方式： 认为超时代表操作失败且没有副作用；纠正方式是为超时后的重试设计幂等键和查询确认。

速记： 超时定边界，但结果可能未知。

2. 重试

核心定义： 重试是在瞬时故障后再次尝试操作，以提高成功率，但会引入重复副作用和流量放大。

底层原理 / 机制拆解： - 有效重试需要限制次数、指数退避、随机抖动、错误分类和整体 deadline。 - 只对可恢复错误重试，例如超时、限流、临时 5xx；对参数错误、权限错误不应重试。 - 重试会把上游压力乘法放大，多个层级同时重试会形成重试风暴。

适用场景： 适用于幂等读、幂等写、临时网络抖动、主从切换、限流后延迟重试和异步任务。

不适用场景 / 失败边界： 不适合非幂等支付扣款、创建订单等无幂等键操作，也不适合在下游持续过载时猛重试。

工程实践或做题/面试理解： 工程上统一重试库，配置退避和 jitter，记录 attempt；面试中说“重试前先问是否幂等”。

常见误区与纠正方式： 无脑重试提高可用性；纠正方式是重试预算、熔断、限流和幂等一起使用。

速记： 重试救瞬断，幂等防副作用。

3. 熔断与降级

核心定义： 熔断在下游持续异常时快速失败，降级提供缓存、默认值或弱功能，防止故障扩散成雪崩。

底层原理 / 机制拆解： - 熔断器通常有关闭、打开、半开状态；错误率或慢调用超过阈值后打开，半开用少量探测判断恢复。 - 降级要预先定义用户可接受的替代结果，例如只读缓存、排队、隐藏非核心模块。 - 熔断保护调用方资源，但不会修复下游根因，恢复需要探测和监控闭环。

适用场景： 适用于依赖强、调用量大、下游不稳定或核心链路需要隔离的服务。

不适用场景 / 失败边界： 不适合对必须强一致成功的关键写操作返回虚假成功，也不适合没有监控的静态开关长期打开。

工程实践或做题/面试理解： 工程上为非核心依赖设置熔断和 fallback，核心写路径宁可失败也不伪成功；面试中说明三态机。

常见误区与纠正方式： 熔断等于修复下游；纠正方式是区分保护调用方、降级体验和修复根因。

速记： 熔断止血，降级保命，恢复靠探测。

4. 分布式追踪

核心定义： 分布式追踪用 Trace、Span 和上下文传播还原一次请求跨服务的调用路径、耗时和错误位置。

底层原理 / 机制拆解： - Trace 表示完整请求，Span 表示一次操作，父子关系描述调用树。 - 上下文通过 HTTP Header、消息属性或 RPC metadata 传播，日志和指标用 trace_id 关联。 - 采样、异步边界、批处理和隐私脱敏会影响追踪完整性。

适用场景： 适用于微服务排障、性能瓶颈定位、错误归因、SLO 分析和依赖拓扑治理。

不适用场景 / 失败边界： 不适合把追踪当唯一监控；指标用于发现异常，日志用于细节，追踪用于路径关联。

工程实践或做题/面试理解： 工程上统一 OpenTelemetry 规范，关键入口生成 trace_id，异步消息携带上下文；面试中讲“三件套：指标、日志、追踪”。

常见误区与纠正方式： 只有日志没有关联 ID；纠正方式是所有服务统一 trace_id/span_id 并在日志中结构化输出。

速记： 指标报异常，日志给细节，追踪串路径。

深度扩展：底层原理与应用边界

1. 本章在「分布式系统」中的位置

  • 核心定位： 在网络不可靠、节点会失败、时钟不一致的条件下组织多节点协同。
  • 本章作用： 「分布式系统：可观测性与容错工程」负责把总纲落到可操作的判断框架：先确认问题边界，再拆解机制，最后根据代价和风险选择方法。
  • 主要风险： 最大风险是把远程调用当本地调用，忽视超时、重试、幂等、分区和一致性语义。
  • 实践抓手： 设计时先声明系统模型和一致性要求，再选择复制、分片、共识或异步补偿方案。

5. 验证与复盘

  • 验证方式： 用故障注入、超时重试测试、乱序重复消息测试和一致性检查验证。
  • 复盘方式： 每次做题或设计后，记录“我使用了哪个前提、哪个前提最容易被破坏、如果破坏如何调整”。
  • 记忆方式： 不背孤立结论，只背“问题 → 机制 → 边界 → 验证”的链路。

本轮扩写：分布式容错的预算、传播与雪崩控制

1. 超时预算要从入口向下分配

分布式调用链不能让每层都设置一个“看起来合理”的超时，否则总延迟会失控。

flowchart LR
  A["入口 800ms"] --> B["服务A 300ms"]
  A --> C["服务B 300ms"]
  B --> D["DB 120ms"]
  B --> E["Cache 50ms"]
  • 入口 SLO 决定总预算；下游预算之和要留出网络、排队和重试空间。
  • 重试必须消耗剩余预算，不能重新获得完整超时。
  • 超时要小于调用方等待时间，否则下游还在工作，上游已经放弃，容易制造幽灵流量。

2. 重试风暴的形成机制

阶段 表现 根因 控制手段
轻微抖动 P99 上升 下游排队增长 指数退避、抖动 jitter
集体重试 QPS 放大 客户端同时重试 限制重试次数、预算内重试
资源耗尽 线程池/连接池打满 排队请求占住资源 舱壁隔离、快速失败
雪崩传播 多个服务同时告警 上游继续放大流量 熔断、限流、降级

3. Trace Context 的工程边界

  • Trace ID 用于串起链路，不等于业务幂等键。
  • Span 要记录关键依赖和错误标签，但不要把敏感数据写进 span attribute。
  • 采样率要区分普通流量和错误流量；错误链路应提高采样。
  • 异步消息要把 trace context 放进消息 header，否则链路会断在队列边界。

4. 容错策略适用/不适用

策略 适用 不适用 验证方式
超时 所有远程调用 用无限等待掩盖慢依赖 注入延迟，检查调用方释放资源
重试 瞬时失败、幂等操作 非幂等写、确定性失败 重复请求测试和幂等键检查
熔断 下游持续异常 业务必须同步强依赖且无降级 压测异常比例和恢复窗口
舱壁隔离 多租户、多依赖共享资源 资源极少且隔离成本过高 单依赖打满不影响其他依赖

5. 面试追问路径

  • “为什么重试会让系统更差？”——解释放大系数、排队、连接池占用和同步退避缺失。
  • “熔断后如何恢复？”——回答半开探测、小流量试探、成功阈值、失败回退。
  • “如何判断是下游慢还是网络慢？”——回答 span 分解、客户端计时、服务端计时、网络错误码和队列等待。
