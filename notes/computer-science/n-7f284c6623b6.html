Python 环境和依赖管理

学习目标

  • 理解解释器、虚拟环境、包、依赖解析和锁定文件的关系。
  • 能为项目创建隔离环境并安装、升级、导出依赖。
  • 能区分运行依赖、开发依赖、工具依赖和系统依赖。
  • 能排查版本冲突、解释器不一致、路径污染和可复现性问题。

核心概念

  • Python 解释器：实际执行代码的程序，例如 python3.11。
  • 虚拟环境：项目级隔离目录，保存独立的 Python 可执行文件入口和 site-packages。
  • 包管理器：安装和解析 Python 包，常见工具包括 pip、uv、poetry、pdm。
  • 依赖声明：描述项目需要什么包，常见文件包括 pyproject.toml、requirements.txt。
  • 锁定文件：记录解析后的精确版本和来源，用于可复现安装。
  • 系统依赖：不由 Python 包管理器完全负责的依赖，例如 C 编译器、OpenSSL、数据库客户端库。
  • 工具隔离：格式化、lint、测试、代码生成工具应尽量固定版本，避免“我机器上刚好可用”。

常用命令

查看解释器。风险低，只读。

python3 --version
python3 -c "import sys; print(sys.executable)"

创建标准库虚拟环境。会写入 .venv 目录；不要把虚拟环境提交到 Git。

python3 -m venv .venv

激活虚拟环境。会改变当前 Shell 的 PATH，只影响当前终端会话。

source .venv/bin/activate

确认正在使用的 Python 和 pip。风险低，只读。

python -c "import sys; print(sys.executable)"
python -m pip --version

安装依赖。会修改虚拟环境中的包；如果没有激活环境，可能写到用户或系统环境。

python -m pip install requests

从 requirements 安装。会安装文件中声明的包；如果没有固定版本，解析结果可能随时间变化。

python -m pip install -r requirements.txt

导出当前环境。会把当前安装结果写入文件；注意它可能包含间接依赖和本机特定包。

python -m pip freeze > requirements.lock.txt

使用 uv 创建和同步环境。会写入虚拟环境和锁定文件，具体行为取决于项目配置。

uv venv
uv sync

配置示例

一个简化的 pyproject.toml：

[project]
name = "demo-tools"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
  "requests>=2.32,<3",
]

[project.optional-dependencies]
dev = [
  "pytest>=8,<9",
  "ruff>=0.6,<1",
]

说明：requires-python 限制解释器版本；依赖范围既不应过宽到无法预测，也不应无理由锁死到妨碍安全更新。最终可复现安装通常还需要锁定文件。

典型工作流

  1. 进入项目后先确认解释器。
pwd
python3 --version
  1. 创建并激活虚拟环境。
python3 -m venv .venv
source .venv/bin/activate
  1. 升级基础安装工具。会修改虚拟环境；不建议在系统 Python 上直接执行。
python -m pip install --upgrade pip setuptools wheel
  1. 安装项目依赖和开发工具。
python -m pip install -r requirements.txt
python -m pip install -r requirements-dev.txt
  1. 运行验证。
python -m pytest
python -m ruff check .
  1. 新增依赖后记录来源和原因。
python -m pip install httpx
python -m pip freeze > requirements.lock.txt

风险说明：pip freeze 记录的是当前环境完整状态，不等于精心维护的直接依赖清单。团队项目应明确直接依赖和锁定依赖的职责。

常见坑

  • 使用了错误解释器：命令行是系统 Python，IDE 用的是虚拟环境，CI 又是另一个版本。
  • 直接运行 pip install，但 pip 不属于当前 python。
  • 没有锁定依赖，过几周重新安装得到不同版本。
  • 把 .venv、缓存目录或本地凭据提交进仓库。
  • Python 包需要编译扩展，但机器缺少编译器或系统头文件。
  • 在全局环境安装工具，多个项目之间版本互相污染。
  • 忽略 requires-python，导致依赖解析成功但运行时语法或 ABI 不兼容。

排障步骤

  1. 确认解释器和包安装位置。
python -c "import sys, site; print(sys.executable); print(site.getsitepackages())"
python -m pip --version
  1. 查看包版本和依赖关系。
python -m pip show requests
python -m pip check
  1. 确认导入的是哪个文件。
python -c "import requests; print(requests.__file__)"
  1. 清理后重建环境。不要直接递归删除 .venv；先确认它确实是虚拟环境，再移动到带时间戳的备份目录。这样如果判断失误，还有恢复空间。
if [ -d .venv ] && [ -f .venv/pyvenv.cfg ]; then
  backup_dir=".venv.backup.$(date +%Y%m%d%H%M%S)"
  mv .venv "$backup_dir"
  printf "moved old venv to %s\n" "$backup_dir"
else
  printf "refuse to move: .venv is missing or is not a Python virtual environment\n" >&2
  exit 1
fi
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
  1. 安装编译失败时，先看缺少的是 Python 包还是系统库。
python -m pip install -v package-name

风险说明：详细安装日志可能包含本机路径、内部镜像地址或 token，分享前需要脱敏。

练习

  • 创建一个虚拟环境，安装 requests，写脚本请求一个公开 HTTP 地址。
  • 故意在未激活和已激活环境中分别查看 python -m pip --version，比较路径。
  • 写一个 requirements.txt，固定一个直接依赖版本，再重建环境验证。
  • 用 pip check 制造并观察一次依赖冲突提示。

检查清单

  • 我能确认当前 python 和 pip 是否属于同一个虚拟环境。
  • 我知道虚拟环境目录不应该提交。
  • 我能解释直接依赖、间接依赖和锁定文件的区别。
  • 我会用 python -m pip 降低 pip 指向错误的风险。
  • 我能根据错误日志判断是 Python 版本、包版本还是系统依赖问题。

深化学习说明

前半部分是虚拟环境、pip 和依赖文件的日常速查。下面的内容深入解释解释器归属、依赖声明、锁定和可复现重建，重点训练你在“装了但导不进来”这类问题中找到真实环境。

前置知识和完成标准

学习本章前，应能使用 Shell 进入项目目录、运行命令、查看环境变量，并知道 Python 模块导入和包安装不是同一件事。import requests 成功，说明当前解释器能在自己的搜索路径中找到模块；不说明其他解释器也能找到。

完成本章后，应能做到：

  • 使用 python -c "import sys; print(sys.executable)" 确认当前解释器。
  • 解释虚拟环境如何通过 PATH、pyvenv.cfg、site-packages 隔离依赖。
  • 区分 pyproject.toml、requirements.txt、锁定文件、构建后端的职责。
  • 遇到依赖冲突、导入错误、编译失败时，能判断是解释器、Python 包、系统库还是网络/索引问题。

核心概念分层

第一层是解释器：不同 Python 版本有不同语法、标准库行为和 ABI。项目应明确 requires-python，CI 应覆盖支持范围。

第二层是环境：虚拟环境保存项目依赖和命令入口。激活环境只是修改当前 Shell 的 PATH；脚本和 CI 更可靠的写法是使用 .venv/bin/python -m ... 或工具管理器提供的运行命令。

第三层是依赖声明：直接依赖是项目主动使用的包，间接依赖是解析器为满足直接依赖拉入的包。把两者混在一个无注释文件里，会让升级和安全修复困难。

第四层是可复现性：版本范围描述允许什么，锁定文件记录实际选了什么。应用服务通常更需要锁定；库项目通常声明兼容范围，并通过测试验证范围内版本。

从零开始实验：创建可重建环境

教学边界：实验在系统临时目录下创建唯一目录并安装公开包。生产环境应使用团队认可的索引、锁定策略和凭据管理，不要把 token 写入 requirements 或日志。

lab_dir="$(mktemp -d "${TMPDIR:-/tmp}/python-env-lab.XXXXXX")"
cd "$lab_dir"
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install "requests>=2.32,<3"
.venv/bin/python - <<'PY'
import sys
import requests
print(sys.executable)
print(requests.__version__)
print(requests.__file__)
PY
.venv/bin/python -m pip freeze > requirements.lock.txt
.venv/bin/python -m pip check

预期结果：输出的解释器路径包含本次 mktemp 创建目录下的 .venv，requests.__file__ 位于该虚拟环境的 site-packages 下，pip check 报告无冲突。

失败现象：

  • No module named requests：安装发生在另一个解释器，或当前命令没使用虚拟环境。
  • externally-managed-environment：系统 Python 被发行版保护，不应直接全局安装；创建虚拟环境后再装。
  • 编译扩展失败：可能缺少编译器、Python 头文件、OpenSSL/libpq/mysqlclient 等系统依赖。

验证方式：按上面的校验和备份步骤移动旧 .venv，再用同一依赖文件重建，并确认脚本输出一致。确认新环境可用后，再按团队清理策略处理备份目录。

命令和配置逐段解释

python3 -m venv .venv

python3 是基础解释器，-m venv 运行标准库模块，.venv 是目标目录。虚拟环境可重建，不应保存业务代码或手工唯一文件。

python -m pip install -r requirements.txt

python -m pip 强制使用当前解释器对应的 pip，降低 pip 命令指向另一个环境的风险。-r requirements.txt 读取依赖文件；pip 不保证按文件顺序安装，所以不能依赖顺序解决构建副作用。

[project]
requires-python = ">=3.11"
dependencies = [
  "requests>=2.32,<3",
]

requires-python 用于阻止不支持的解释器安装项目。依赖范围给解析器选择空间；锁定文件才负责把某次部署固定到具体版本。生产镜像构建应记录锁定文件、包索引和基础镜像摘要。

常见坑的机制和排障决策路径

遇到 Python 环境问题，按下面顺序查：

  1. 解释器：python -c "import sys; print(sys.version); print(sys.executable)"。
  2. 环境：python -c "import sys; print(sys.prefix); print(sys.base_prefix)"，两者不同通常表示在虚拟环境中。
  3. pip 归属：python -m pip --version，看路径是否在目标虚拟环境。
  4. 包位置：python -c "import pkg; print(pkg.__file__)"，确认导入来源。
  5. 依赖一致性：python -m pip check，找已安装包之间的不兼容。
  6. 解析输入：检查 requirements.txt、约束文件、锁定文件、私有索引配置是否一致。
  7. 系统依赖：编译失败时看第一条真正的编译器或链接器错误，不要只看最后的 pip 总结。

边界说明：

  • 库项目不应无理由锁死所有间接依赖，否则下游难以组合。
  • 应用项目不应只写宽泛范围就部署，否则重复构建可能拿到不同版本。
  • .venv 不可移动；路径写入脚本 shebang 后，移动目录可能导致命令入口失效。

练习答案要点

基础练习：答案应显示虚拟环境路径，并证明包安装在该环境内。

.venv/bin/python -c "import sys, requests; print(sys.executable); print(requests.__file__)"

进阶练习：比较未激活和已激活环境时，关键不是提示符变化，而是 python -m pip --version 指向的 site-packages 路径不同。

综合练习：制造冲突后应使用 pip check 或解析器错误说明“哪个包要求哪个版本范围”。修复思路包括升级上游包、收窄或放宽版本范围、替换依赖，不能只反复清缓存。

章节小结

Python 依赖管理的核心是让“哪个解释器、哪个环境、哪些直接依赖、解析出了哪些精确版本”都可见、可重建。稳定团队流程通常把本地开发便利和生产可复现性分开设计。
