学习目标

  • 区分并发安全、线程安全、无数据竞争和业务原子性。
  • 正确使用互斥量、条件变量、原子变量和停止机制。
  • 能为线程池、队列和异步任务定义清晰的关闭语义。

核心原理

并发正确性来自共享状态不变量，而不是来自“多加几把锁”。本篇先定义数据竞争和业务竞态，再展开互斥量、条件变量、原子内存序、线程生命周期、线程池关闭和常见并发架构。

1. 先定义不变量

并发设计不是“哪里冲突就加锁”。先写出共享状态的不变量，例如：

队列元素数始终在 [0, capacity]；关闭后不再接受新任务；已接受任务要么执行完，要么以取消结果结束。

然后决定由哪把锁保护哪些字段、条件变量等待哪个谓词、状态在哪些操作中必须一起改变。

数据竞争与竞态条件

  • 数据竞争：多个线程并发访问同一内存位置，至少一个写，且缺少规定的同步；C++ 中通常导致未定义行为。
  • 竞态条件：结果取决于时序，可能有同步但业务仍错误。例如“先查询余额再扣款”分两步加锁，整体仍非原子。

状态变化要成组发生

并发队列里 closed_、queue_ 和等待者通知是同一组状态。push() 不能只检查队列未满，还要检查关闭状态；close() 不能只改标志，还要唤醒所有可能卡在 not_empty_ 或 not_full_ 上的线程。

producer: lock -> check !closed && !full -> push -> unlock -> notify not_empty
consumer: lock -> wait closed || !empty -> pop/drain -> unlock -> notify not_full
shutdown: lock -> closed = true -> unlock -> notify_all both sides

如果这些状态分散在多把锁或多个原子里，必须证明观察顺序不会让线程永久睡眠、关闭后继续提交，或任务既被取消又被执行。

2. 互斥量和条件变量

条件变量总要配合谓词循环，以处理虚假唤醒和状态已变化：

std::unique_lock lock(mu_);
not_empty_.wait(lock, [&] { return closed_ || !queue_.empty(); });
if (queue_.empty()) return std::nullopt;  // closed and drained
auto item = std::move(queue_.front());
queue_.pop();
lock.unlock();
not_full_.notify_one();
return item;

关键规则：

  • 等待的是状态谓词，不是某次通知。
  • 不要持锁执行未知回调、网络 I/O 或长时间计算。
  • 多字段共同构成不变量时，通常由同一同步策略保护。
  • 建立固定锁顺序，或使用 std::scoped_lock 一次获取多把锁，避免死锁。

条件变量错误路径

wait 返回不代表一定收到了想要的业务事件；可能是虚假唤醒，也可能是其他线程先消费了状态。因此等待代码必须用谓词重新读取共享状态。通知通常放在释放锁之后，减少被唤醒线程马上阻塞在同一把锁上的概率；但状态修改本身必须在锁内完成。

关闭队列时用 notify_all() 而不是只通知一个线程，因为生产者和消费者都可能在不同条件上等待。若只唤醒一个消费者，其他生产者可能永远卡在满队列等待中。

3. 原子与内存顺序

原子变量适合简单计数、标志或经过证明的数据结构。它解决单个原子对象的竞争，不自动让多个操作组成业务事务。

  • memory_order_seq_cst 提供最直观的全序语义，先保证正确再考虑放宽。
  • release/acquire 常用于“发布数据—观察标志”：写方先写数据再 release 存储标志，读方 acquire 读到标志后可见此前写入。
  • relaxed 只保证该原子操作不可分割，通常用于不承担同步职责的统计计数。

无锁代码还需面对 ABA、内存回收和硬件内存模型。除非性能证据证明锁是瓶颈，并且团队能验证算法，否则优先使用锁和清晰分区。

memory order 的最小推导

release/acquire 的典型意图是发布一段普通内存状态：

Payload payload;
std::atomic<bool> ready{false};

void writer() {
    payload.value = 42;
    ready.store(true, std::memory_order_release);
}

void reader() {
    if (ready.load(std::memory_order_acquire)) {
        use(payload.value);
    }
}

如果读线程 acquire 读到了 true，它能看到写线程在 release 之前对 payload 的写入。这个例子只适合单写、对象生命周期已被外部保证的教学场景；如果 payload 可能被多个线程修改，或者 ready 从 true 再变 false，还需要额外协议。relaxed 计数适合“最后打印统计值”这类不承担发布数据职责的场景，不适合用作任务队列的可见性开关。

4. 线程生命周期与停止

线程对象析构时仍 joinable 会导致进程终止。后台线程应有明确协议：

  1. 发布停止请求；
  2. 唤醒等待者；
  3. 停止接受新任务；
  4. 排空或取消已接受任务；
  5. join 所有线程；
  6. 再销毁队列、连接和日志等依赖。

C++20 的 std::jthread 与 stop_token 能表达协作式停止，但阻塞系统调用或不支持取消的第三方调用仍需超时、关闭 fd 等额外手段。

5. 线程池的工程边界

线程池至少要定义：

  • 队列是否有界，满时阻塞、拒绝、降级还是调用方执行；
  • 任务是否允许抛异常，结果如何回传；
  • 不同优先级是否会饥饿；
  • 关闭时排空还是取消，最大等待时间是多少；
  • 任务内部阻塞下游时，是否耗尽全部工作线程。

CPU 密集任务通常按可用核数附近配置；阻塞 I/O 任务需要结合等待比例和下游容量，但增加线程不能扩大数据库或外部服务的真实容量。

shutdown 语义

线程池关闭必须先写成产品语义，再写代码。常见两种模式：

  • drain：停止接收新任务，已入队任务继续执行，适合日志 flush、已承诺处理的请求；
  • cancel：停止接收新任务，未开始任务返回取消，适合后台预取、可丢弃计算。

任务函数抛异常时，工作线程不能直接退出导致池容量下降；应捕获异常并写入 future、回调错误或统一日志。析构线程池时如果仍有任务持有外部对象引用，必须保证外部对象晚于线程池销毁，或先取消任务并等待工作线程退出。

6. 常见并发架构

架构 优点 风险
每连接一线程 直观 大量线程、栈内存和调度开销
I/O 线程 + 工作池 网络与业务分离 跨线程队列、响应顺序和背压
one loop per thread 连接状态局部化 连接分配、跨 loop 协调
actor/消息传递 所有权清晰 邮箱积压、消息语义和调试复杂

工程实践/示例

本篇示例重点放在有界队列、release/acquire 发布、线程池 shutdown 和诊断命令。真正落地时建议先把队列和线程池写成独立库，用单元测试覆盖关闭、满队列、虚假唤醒和异常任务，再接入网络服务，避免在连接回调里同时调试协议和并发问题。

故障排查/观测

死锁、活锁和饥饿

死锁通常表现为线程都在等待锁或条件变量；活锁表现为 CPU 活跃但业务不前进；饥饿表现为部分任务长期得不到执行。定位时记录锁保护的字段、等待谓词、通知位置和队列长度变化，比只看某个线程栈更有效。

常用命令：

top -H -p <pid>
pstack <pid>              # 部分发行版提供
gdb -p <pid>              # thread apply all bt
perf sched record ./server

如果不能在线附加调试器，至少在日志中打出队列深度、提交成功/拒绝次数、工作线程 busy/idle 数、关闭状态和最长任务耗时。

数据竞争验证

ThreadSanitizer 能发现很多未同步读写，但不能证明业务原子性正确。建议把纯状态机拆出来做确定性单元测试，再用压力测试覆盖多生产者、多消费者、关闭同时提交、任务抛异常、队列满和超时等待。

面试与工程复盘

如何解释一把锁

回答“为什么这里加锁”时，应说明这把锁保护哪些字段、维护什么不变量、在哪些函数里获取、是否允许回调持锁执行、和其他锁的顺序是什么。只说“防止并发问题”没有工程信息。

如何解释一个原子

说明原子变量时要讲它承担的是计数、标志还是同步发布。如果使用非 seq_cst 内存序，要能画出写线程和读线程的 happens-before 关系；如果画不出，先用更保守的同步方式。

最小验收清单

  • 每个共享字段能说出保护者。
  • 条件变量等待都有谓词。
  • 线程池关闭后不能继续提交。
  • 压测覆盖关闭、队列满和任务异常。

常见误区

  • volatile 能做线程同步：C++ volatile 主要不是并发同步工具。
  • 原子计数器让整个对象线程安全：复合不变量仍可能破坏。
  • 队列无限大更不容易丢任务：它会把过载变成延迟和内存崩溃。
  • 线程越多吞吐越高：可能增加上下文切换、缓存失效和下游竞争。

  2. 实现固定线程池，禁止关闭后提交，并让任务异常可通过 future 获取。
