复习定位：本笔记覆盖 MySQL 生产运维、高可用、安全治理、容量规划与面试高频问题。建议结合 01-MySQL基础与体系结构、03-MySQL索引与查询优化、04-InnoDB事务锁与日志，并结合 Redis、Linux、分布式系统 复习。

说明：文中的 Shell/SQL 片段主要是生产演练模板。真实执行前必须在测试环境替换主机、端口、账号、库名、备份路径并做恢复演练。

1. 运维目标与核心原则

MySQL 运维的目标不是“数据库不报错”，而是让业务在可接受成本下持续满足 RPO、RTO、吞吐、延迟、安全与可审计 要求。

目标 含义 常见指标
RPO 可接受的数据丢失窗口 0、秒级、分钟级
RTO 故障后恢复服务的时间 秒级切换、分钟级恢复
可用性 服务可访问比例 99.9%、99.99%
一致性 主从、备份、应用读写看到的数据是否符合预期 复制延迟、GTID 位点、事务一致性
可观测性 能否发现、定位、复盘问题 指标、日志、审计、告警
安全性 权限、加密、审计、漏洞修复 最小权限、TLS、脱敏、补丁

生产原则：

  1. 先备份，再变更：DDL、升级、迁移、参数变更前确认可恢复。
  2. 备份必须可恢复：只“备份成功”没有意义，必须定期恢复演练。
  3. 高可用不等于零风险：HA 只能降低故障影响，不能替代备份、监控和变更治理。
  4. 读写分离必须理解一致性代价：从库延迟会导致读到旧数据。
  5. 参数调优先基线后改动：没有基线的调参容易把偶发问题固化成长期风险。
  6. 权限默认拒绝：按应用、环境、用途拆分账号，禁止共享高权账号。

2. 备份与恢复

2.1 备份类型

类型 代表工具 优点 缺点 适用场景
逻辑备份 mysqldump、mysqlpump、mysqlsh util.dumpInstance() 可读、跨版本/跨平台较友好、可按库表恢复 大库慢、恢复慢、占用 SQL 执行资源 小中型库、迁移、对象级恢复
物理备份 MySQL Enterprise Backup、Percona XtraBackup、存储快照 速度快、适合大库、恢复快 依赖版本/文件格式，操作复杂 大库、低 RTO、全实例恢复
增量备份 binlog、物理增量 节省空间，可做时间点恢复 恢复链复杂 任意需要 PITR 的生产系统
快照备份 云盘/存储快照 快速、低侵入 需要一致性点，跨地域恢复需验证 云数据库、虚拟化环境

2.2 mysqldump 逻辑备份

常用模板：

mysqldump \
  --host=127.0.0.1 \
  --port=3306 \
  --user=backup_user \
  --password \
  --single-transaction \
  --routines \
  --triggers \
  --events \
  --set-gtid-purged=OFF \
  --databases app_db \
  > app_db_$(date +%F).sql

关键选项：

  • --single-transaction：对 InnoDB 表创建一致性快照，避免长时间锁表。依赖事务隔离与 MVCC，参考 04-InnoDB事务锁与日志。
  • --routines --triggers --events：导出存储过程、触发器、事件。
  • --master-data：在备份文件中记录二进制日志位点，便于搭建复制或 PITR。
  • --set-gtid-purged：GTID 环境必须谨慎设置，迁移到已有 GTID 集合的实例时尤其要确认。

注意事项：

  1. MyISAM 表无法通过 --single-transaction 保证一致性，需锁表或停写。
  2. 大表导出会产生长事务，可能拖住 undo purge，影响历史版本清理。
  3. 逻辑恢复会重放 SQL，恢复速度通常慢于物理备份。

2.3 mysqlpump

mysqlpump 是 MySQL 提供的并行逻辑备份工具，支持库表级并行导出，适合比 mysqldump 更快的逻辑备份场景。

mysqlpump \
  --host=127.0.0.1 \
  --user=backup_user \
  --password \
  --default-parallelism=4 \
  --routines \
  --triggers \
  --events \
  app_db > app_db_pump.sql

使用建议：

  • 并行度不要超过数据库和磁盘可承受范围。
  • 仍需评估长事务和导出期间的 IO 压力。
  • 在复杂对象、权限和 GTID 场景下要做恢复验证。

2.4 MySQL Shell 逻辑备份：mysqlsh

MySQL Shell 的 Dump & Load Utilities 适合 MySQL 8.0+ 迁移、并行导入导出和云迁移。

// mysqlsh JavaScript 模式模板
util.dumpInstance('/backup/mysql-dump', {
  threads: 8,
  consistent: true,
  ocimds: false
})

util.loadDump('/backup/mysql-dump', {
  threads: 8,
  deferTableIndexes: 'all'
})

适用场景：

  • 需要并行逻辑导入导出。
  • 迁移到 MySQL 8.0 或云数据库。
  • 需要对象兼容性检查与可控加载。

2.5 物理备份概念

物理备份复制的是数据文件、redo、undo、系统表空间等物理文件。它通常分为：

  1. 全量备份：复制完整数据目录或物理页。
  2. 增量备份：只复制自上次备份后变化的数据页或日志。
  3. Prepare 阶段：应用 redo、回滚未提交事务，让备份达到一致状态。
  4. Restore 阶段：停止实例、替换数据目录、修复权限、启动验证。

物理备份关注点：

  • MySQL 主版本、存储引擎和页格式兼容性。
  • innodb_page_size、加密、压缩、redo 格式。
  • 备份期间的 IO 限速与业务低峰调度。
  • 备份文件校验、异地存储、保留周期。

2.6 时间点恢复（PITR）

PITR = 全量备份 + 增量 binlog 重放。

流程：

  1. 找到故障前最近一次可用全量备份。
  2. 在隔离环境恢复全量备份。
  3. 根据 GTID、binlog 文件位置或时间点重放 binlog。
  4. 跳过误操作事务或恢复到误操作前一刻。
  5. 校验数据后再回切业务。

模板：

mysqlbinlog \
  --start-datetime='2026-06-08 10:00:00' \
  --stop-datetime='2026-06-08 10:29:59' \
  mysql-bin.000123 | mysql --host=restore-host --user=root --password

PITR 风险：

  • 使用 stop-datetime 时要确认数据库服务器时区。
  • 大事务和跨库事务可能让按时间截断变得危险。
  • GTID 环境中跳过事务必须记录并复盘。

2.7 备份策略模板

数据规模 推荐策略 恢复目标
< 50 GB 每日逻辑全量 + binlog 小时级 RTO，分钟级 RPO
50 GB - 1 TB 每日物理全量/增量 + binlog + 每周逻辑抽样 分钟到小时级 RTO
> 1 TB 物理备份 + 存储快照 + 分库分表级演练 依赖架构分层恢复
核心交易库 多副本 + 物理备份 + 实时 binlog 归档 + 异地灾备 秒/分钟级 RPO，分钟级 RTO

备份检查清单：

  • [ ] 备份账号最小权限。
  • [ ] 全量备份、binlog、配置文件、用户权限一起纳入恢复方案。
  • [ ] 备份文件加密存储。
  • [ ] 本地、异地、离线至少两类副本。
  • [ ] 每月至少一次恢复演练。
  • [ ] 恢复演练记录耗时、缺陷和改进项。

3. 复制体系

3.1 MySQL 复制基本模型

经典异步复制链路：

  1. 主库提交事务并写 binlog。
  2. 从库 I/O 线程拉取 binlog，写入 relay log。
  3. 从库 SQL 线程或多线程 applier 重放 relay log。
  4. 从库数据逐步追上主库。

复制格式：

格式 特点 风险
STATEMENT 记录 SQL 非确定函数、环境差异可能导致主从不一致
ROW 记录行变更 binlog 体积较大，最安全常用
MIXED 自动切换 可读性和确定性介于两者之间

生产常用：binlog_format=ROW。

3.2 复制延迟来源

常见原因：

  • 主库写入并发高，从库单线程或并行度不足。
  • 大事务导致从库长时间应用。
  • 从库硬件、IO、CPU 弱于主库。
  • 从库执行查询占用资源，影响回放。
  • 网络抖动或跨地域链路延迟。
  • 表无主键导致 ROW 回放定位慢。

排查入口：

SHOW REPLICA STATUS\G
-- 旧版本也可能使用 SHOW SLAVE STATUS\G

重点字段：

  • Replica_IO_Running / Slave_IO_Running
  • Replica_SQL_Running / Slave_SQL_Running
  • Seconds_Behind_Source / Seconds_Behind_Master
  • Last_IO_Error
  • Last_SQL_Error
  • Retrieved_Gtid_Set
  • Executed_Gtid_Set

3.3 多线程复制

多线程复制提升从库 apply 能力。常见参数：

replica_parallel_workers = 8
replica_parallel_type = LOGICAL_CLOCK
replica_preserve_commit_order = ON

旧版本参数名可能是 slave_parallel_workers、slave_parallel_type、slave_preserve_commit_order。

建议：

  • 并行度根据 CPU、IO 和业务库表冲突程度逐步调大。
  • 对延迟敏感的读库，避免同时承载重分析查询。
  • 大事务拆小比盲目加并行度更有效。

4. GTID

GTID（Global Transaction Identifier）为每个已提交事务提供全局唯一编号，简化复制切换和故障恢复。

4.1 GTID 优点

  • 自动定位复制位点，减少手工找 binlog 文件与 offset。
  • 主从切换、级联复制、故障恢复更安全。
  • 便于比较实例已执行事务集合。

4.2 核心参数

gtid_mode = ON
enforce_gtid_consistency = ON
log_bin = ON
log_replica_updates = ON

旧版本可能使用 log_slave_updates。

4.3 GTID 运维要点

  1. 开启前检查不兼容语句，例如某些非事务表与事务混用场景。
  2. 复制切换时比较 Executed_Gtid_Set，确认候选新主包含原主已提交事务。
  3. 严禁随意修改 gtid_purged。
  4. 清理 binlog 前确认备份、从库和灾备不再需要对应 GTID 范围。
  5. 跳过事务要记录 GTID、原因、影响和修复动作。

4.4 GTID 面试重点

  • GTID 解决的是“事务定位”和“复制拓扑切换”问题，不自动解决数据一致性。
  • GTID 集合能判断包含关系，但不能证明业务语义正确。
  • GTID 与半同步、组复制可以组合使用，但各自解决的问题不同。

5. 半同步复制

半同步复制介于异步复制和强同步复制之间。主库提交事务时，至少等待一个从库确认收到 binlog 后再向客户端返回成功。

5.1 工作机制

  1. 主库写 binlog。
  2. 主库等待半同步从库 ACK。
  3. 达到 ACK 或超时。
  4. 成功返回，或超时退化为异步复制。

5.2 优点与限制

优点：

  • 降低主库宕机后已提交事务丢失概率。
  • 对应用透明。

限制：

  • 从库 ACK 通常表示收到日志，不代表已应用完成。
  • 网络抖动会增加提交延迟。
  • 超时后可能退化为异步复制。
  • 至少一个从库确认不等于多数派一致。

5.3 适用场景

  • 单主多从架构中需要降低数据丢失概率。
  • 能接受提交延迟小幅上升。
  • 不想引入组复制复杂度。

6. 组复制与 InnoDB Cluster

6.1 组复制（Group Replication）

组复制基于分布式一致性协议，在多个 MySQL 节点之间复制事务并做冲突检测。

模式：

模式 说明 适用场景
Single-Primary 单主写，多节点读 最常见，降低写冲突复杂度
Multi-Primary 多主可写 写冲突和应用约束复杂，谨慎使用

要求与约束：

  • InnoDB 表必须有主键或等价唯一键。
  • 推荐开启 GTID。
  • 网络质量和节点时钟稳定性重要。
  • 多数派存活才能保证集群可用。
  • DDL、长事务、大事务会影响集群稳定性。

6.2 InnoDB Cluster

InnoDB Cluster 通常由三部分组成：

  1. MySQL Group Replication：数据复制与成员管理。
  2. MySQL Shell：集群创建、管理、检查。
  3. MySQL Router：应用连接路由。

典型能力：

  • 自动主节点选举。
  • 读写端口分离。
  • 节点状态检测。
  • 集群配置检查。

6.3 组复制运维关注点

  • group_replication_member_expel_timeout：成员驱逐时间。
  • 流控状态：防止慢节点拖垮集群。
  • 事务大小：大事务会放大复制和认证成本。
  • 网络分区：确认多数派和故障域设计。
  • Router 配置：避免应用绕过路由直连错误节点。

7. 读写分离

读写分离通过主库承接写入、从库承接读取来分摊压力。常见实现：

  • 应用层路由：代码按读写选择数据源。
  • 中间件路由：ProxySQL、MySQL Router、ShardingSphere 等。
  • 云数据库代理：云厂商读写分离代理。

7.1 一致性问题

读写分离最大的坑是 复制延迟。

典型问题：

  1. 用户写入成功后立刻读从库，读不到新数据。
  2. 下单后查询订单列表为空。
  3. 权限变更后从库未同步，鉴权结果错误。

解决方法：

  • 写后读主库。
  • 按会话粘主一段时间。
  • 读取前检查 GTID 已追上。
  • 强一致业务不读从库。
  • 从库仅用于报表、搜索索引构建、低一致性查询。

7.2 读写分离清单

  • [ ] 明确哪些接口允许读从库。
  • [ ] 明确写后读一致性策略。
  • [ ] 监控每个从库复制延迟。
  • [ ] 从库故障自动摘除。
  • [ ] 慢查询和报表查询不能拖慢复制。
  • [ ] 应用连接池、代理和 DNS 切换策略经过演练。

8. 分库分表

分库分表是容量和吞吐的架构手段，不是优先级最高的优化手段。优先顺序通常是：索引与 SQL 优化 → 缓存 → 读写分离 → 垂直拆分 → 水平分片。

8.1 垂直拆分

按业务边界拆库：

  • 用户库
  • 订单库
  • 支付库
  • 库存库

优点：边界清晰、降低单库耦合。
缺点：跨库事务、跨库查询、数据一致性复杂。

8.2 水平分片

按分片键把同一张逻辑表拆到多个物理库/表。

常见分片键：

  • user_id
  • tenant_id
  • order_id
  • 时间 + 业务 ID

分片键选择原则：

  1. 查询高频条件中必须出现。
  2. 分布足够均匀。
  3. 不轻易变更。
  4. 能支撑扩容迁移。
  5. 避免热点租户或热点用户压垮单分片。

8.3 分库分表带来的复杂度

  • 跨分片查询、排序、分页成本高。
  • 分布式事务复杂，常用最终一致性、消息表、TCC/Saga，参考分布式事务相关资料。
  • 全局唯一 ID 需要独立方案。
  • 扩容迁移需要双写、校验、回放和切流。
  • 运维、备份、监控、权限都会成倍增加。

8.4 面试回答模板

如果被问“什么时候分库分表”：

当单机优化、索引优化、缓存、读写分离已经不能满足容量或吞吐目标，并且业务可以接受分片带来的查询、事务和运维复杂度时，才考虑分库分表。决策前要有容量预测、热点分析、分片键设计、扩容方案、数据迁移方案和回滚方案。

9. 分区表

分区表是在同一个逻辑表下按规则拆分为多个物理分区。

9.1 常见分区类型

类型 说明 场景
RANGE 按范围分区 按日期归档、日志表
LIST 按枚举值分区 地区、类型
HASH 哈希分区 均匀分散写入
KEY MySQL 内部哈希 简化哈希分区

9.2 分区表适合什么

  • 按时间清理历史数据。
  • 查询条件经常包含分区键。
  • 大表归档、冷热数据管理。

9.3 分区表不适合什么

  • 期望自动提升所有查询性能。
  • 查询条件不带分区键。
  • 需要大量全局唯一约束的复杂表。
  • 高频跨分区扫描。

9.4 分区表运维要点

  • 提前创建未来分区。
  • 定期删除过期分区，避免 DELETE 大量历史数据。
  • 所有唯一键必须包含分区键这一约束要提前设计。
  • 分区数量过多会增加优化器和元数据开销。

10. 容量规划

10.1 需要收集的数据

类别 指标
数据量 表行数、数据大小、索引大小、增长率
写入 TPS、QPS、binlog 生成速度、redo 写入量
读取 QPS、慢查询、热点 SQL、缓存命中率
资源 CPU、内存、磁盘空间、IOPS、吞吐、网络
高可用 从库延迟、备份耗时、恢复耗时、切换耗时
成本 实例规格、存储、备份、跨地域流量

10.2 粗略估算公式

数据容量：

未来数据量 = 当前数据量 × (1 + 月增长率) ^ 月数
存储需求 = 数据量 + 索引量 + undo/redo/binlog + 临时空间 + 备份空间 + 安全水位

经验安全水位：

  • 磁盘使用率超过 70% 开始扩容评估。
  • 超过 80% 进入风险状态。
  • 超过 90% 需要立即处理，避免 binlog、临时表或 undo 撑满磁盘。

10.3 容量规划输出物

  • 当前容量快照。
  • 近 7/30/90 天增长趋势。
  • 未来 3/6/12 个月预测。
  • 单表 Top N 数据和索引占用。
  • 备份窗口和恢复窗口。
  • 扩容阈值和负责人。

12. 性能基线

性能基线是调优和故障判断的参照物。

12.1 基线内容

  • 核心接口 QPS、TPS、P95、P99。
  • Top SQL 延迟、扫描行数、返回行数。
  • CPU、内存、IOPS、磁盘吞吐。
  • Buffer Pool 命中率和脏页比例。
  • binlog 生成速度和复制延迟。
  • 备份耗时、恢复耗时。
  • 正常业务峰谷曲线。

12.2 建立方法

  1. 选择业务低峰、普通峰值、大促峰值三个时间段。
  2. 固定采样窗口，例如 1 分钟、5 分钟、1 小时。
  3. 记录 MySQL、OS、应用连接池、代理层指标。
  4. 标记变更事件：发布、DDL、参数调整、扩容。
  5. 每次重大变更后刷新基线。

12.3 基线用途

  • 判断“慢”是绝对慢还是相对基线变慢。
  • 识别容量拐点。
  • 评估参数调整是否有效。
  • 支撑压测目标和容量预算。

13. 参数调优

参数调优必须基于业务负载、硬件资源和基线，不要照抄模板。

13.1 内存相关

参数 作用 建议
innodb_buffer_pool_size InnoDB 数据和索引缓存 专用数据库常见为物理内存 50%-75%，需结合连接和 OS 缓存
innodb_buffer_pool_instances Buffer Pool 分片 大内存实例可减少竞争
tmp_table_size / max_heap_table_size 内存临时表上限 防止过多磁盘临时表，但不能盲目调大
sort_buffer_size / join_buffer_size 每连接分配 过大可能导致连接多时内存爆炸

13.2 日志与刷盘

参数 作用 取舍
innodb_flush_log_at_trx_commit=1 每次提交刷 redo 最安全，性能成本高
sync_binlog=1 每次事务同步 binlog 最安全，降低丢事务风险
innodb_log_file_size / redo 容量 影响 checkpoint 和写入平滑性 过小会频繁 checkpoint，过大恢复时间增加
binlog_expire_logs_seconds binlog 保留时间 必须覆盖备份、从库、PITR 需要

核心库建议优先保证安全：

innodb_flush_log_at_trx_commit = 1
sync_binlog = 1
binlog_format = ROW

13.3 连接相关

参数 风险
max_connections 调太大可能让数据库在连接风暴中耗尽内存
wait_timeout 太长占用连接，太短影响长连接
thread_cache_size 可降低线程创建销毁成本

建议从应用连接池治理入手，而不是单纯调大 max_connections。

13.4 优化器与 SQL

  • 使用 EXPLAIN 和 EXPLAIN ANALYZE 验证执行计划，参考 03-MySQL索引与查询优化。
  • 更新统计信息，避免优化器因统计过期选错索引。
  • 控制大分页、隐式类型转换、函数包裹索引列。
  • 避免无界查询和返回过多字段。

14. 安全加固

14.1 账号与权限

原则：最小权限、按环境隔离、按应用隔离、按用途隔离。

常见账号：

账号 权限
应用读写账号 仅业务库必要 DML
只读账号 仅 SELECT
备份账号 SELECT、SHOW VIEW、TRIGGER、LOCK TABLES、RELOAD 等按工具需要授予
复制账号 REPLICATION SLAVE/REPLICA CLIENT 相关权限
运维账号 按工单临时授权

禁止：

  • 应用使用 root。
  • 多个系统共享同一账号。
  • 生产账号和测试账号密码一致。
  • 长期保留离职人员账号。

14.2 密码与认证

  • 使用强密码和定期轮换。
  • 启用密码复杂度组件或插件。
  • 限制失败登录次数。
  • 禁止空密码和匿名用户。
  • 优先使用更安全的认证插件与 TLS。

14.3 网络与传输

  • 数据库不暴露公网。
  • 安全组只允许应用、堡垒机、备份机访问。
  • 跨机房、跨云、跨公网链路启用 TLS。
  • 管理端口与业务访问隔离。

14.4 数据加密

层级 方案
传输加密 TLS
静态加密 表空间加密、磁盘加密、云 KMS
字段加密 应用层加密、密钥管理系统
备份加密 备份文件加密、密钥分权

14.5 敏感数据治理

  • 身份证、手机号、邮箱、银行卡等字段分类分级。
  • 非生产环境使用脱敏数据。
  • 日志禁止打印明文敏感信息。
  • 查询导出必须走审批和审计。

15. 审计

审计关注“谁在什么时间从哪里对哪些数据做了什么”。

15.1 审计对象

  • 登录成功和失败。
  • 权限变更。
  • DDL 操作。
  • 高危 DML：无 WHERE 的 UPDATE/DELETE、大范围变更。
  • 敏感表 SELECT。
  • 备份、导出、复制账号访问。
  • root 或高权账号行为。

15.2 审计实现

  • MySQL Enterprise Audit。
  • 云数据库审计。
  • ProxySQL/网关审计。
  • binlog 归档与解析。
  • 应用层操作日志。

15.3 审计落地要求

  • 审计日志独立存储，防止数据库管理员直接篡改。
  • 保留周期满足合规要求。
  • 对高危事件设置实时告警。
  • 审计日志要能关联工单、发布单和人员身份。

16. 升级与迁移

16.1 升级前检查

  • 版本差异和废弃特性。
  • SQL 语法兼容性。
  • 字符集与排序规则变化。
  • 认证插件变化。
  • 保留字变化。
  • 执行计划变化。
  • 备份与回滚方案。
  • 驱动版本兼容性。

16.2 升级路径

常见策略：

  1. 原地升级：停机窗口内升级实例。
  2. 主从滚动升级：先升级从库，切主后升级旧主。
  3. 逻辑迁移：导出导入到新版本。
  4. 双写迁移：应用同时写新旧库，校验后切流。
  5. CDC 迁移：通过 binlog 同步工具持续追平。

16.3 迁移步骤模板

  1. 明确迁移目标、窗口、RPO、RTO。
  2. 建立目标库并完成参数、账号、网络、安全配置。
  3. 全量迁移。
  4. 增量同步。
  5. 数据校验：行数、校验和、抽样业务校验。
  6. 灰度读流量。
  7. 停写或短暂停写切换。
  8. 切应用连接。
  9. 观察核心指标。
  10. 保留旧库只读回滚窗口。

16.4 回滚设计

没有回滚方案的迁移不是完整方案。

回滚要回答：

  • 切换后新库产生的数据如何回放旧库？
  • 是否允许业务短暂停写？
  • 回滚窗口多长？
  • 回滚触发条件是什么？
  • 谁有决策权？

17. 故障排查 Runbook

17.1 实例不可连接

症状：应用大量连接失败、健康检查失败。

排查：

  1. 确认实例进程、端口、主机状态。
  2. 检查 error log。
  3. 检查磁盘是否写满。
  4. 检查连接数是否达到 max_connections。
  5. 检查网络、安全组、DNS、代理。
  6. 如果主库不可恢复，按 HA 预案切换。

快速 SQL：

SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';
SHOW PROCESSLIST;

17.2 数据库变慢

排查顺序：

  1. 是否有发布、DDL、批任务、流量突增。
  2. 看 CPU、IO、内存、网络是否异常。
  3. 查慢查询和 Top SQL。
  4. 查锁等待、死锁、metadata lock。
  5. 查执行计划是否变化。
  6. 查 Buffer Pool 命中率和磁盘临时表。
  7. 必要时限流、kill 问题会话、回滚发布。

常用入口：

SHOW FULL PROCESSLIST;
SHOW ENGINE INNODB STATUS\G
SELECT * FROM information_schema.innodb_trx\G

17.3 复制中断

排查：

  1. 查看复制状态和错误信息。
  2. 判断 IO 线程还是 SQL 线程失败。
  3. 检查网络、权限、binlog 是否被清理。
  4. 如果 SQL 线程报主键冲突或缺行，先判断数据不一致原因，不能盲目跳过。
  5. 修复后启动复制并观察延迟。
SHOW REPLICA STATUS\G
START REPLICA;
STOP REPLICA;

17.4 复制延迟

处理：

  1. 找出是否存在大事务。
  2. 检查从库 SQL 线程应用速率。
  3. 增加合理并行复制 workers。
  4. 暂停从库上的重查询。
  5. 核心读流量临时切主或切到延迟小的从库。
  6. 长期优化：拆小事务、补主键、提升从库规格。

17.5 磁盘写满

优先级：保护数据一致性，避免误删数据文件。

处理：

  1. 确认占用来源：binlog、relay log、general log、slow log、临时文件、备份文件。
  2. 不要直接删除 MySQL 正在管理的日志文件。
  3. 用 MySQL 命令清理已确认可删除的 binlog。
  4. 扩容磁盘或迁移备份文件。
  5. 检查为什么容量告警没有提前触发。

模板：

SHOW BINARY LOGS;
PURGE BINARY LOGS BEFORE '2026-06-01 00:00:00';

17.6 误删数据

处理原则：先止血、再恢复、后复盘。

  1. 立即停止相关应用写入或隔离问题账号。
  2. 确认误操作时间、SQL、影响表和范围。
  3. 禁止在原库上直接尝试不确定修复。
  4. 从备份 + binlog 恢复到临时库。
  5. 校验并回灌受影响数据。
  6. 补充权限、审计、SQL 审批和备份演练。

17.7 死锁频发

排查：

  • 查看 SHOW ENGINE INNODB STATUS\G 最新死锁信息。
  • 找到事务访问表和索引顺序。
  • 检查是否缺索引导致范围锁扩大。
  • 统一业务更新顺序。
  • 缩短事务，减少交互式事务。

参考 04-InnoDB事务锁与日志。

17.8 Metadata Lock 阻塞

常见场景：长事务未提交，DDL 等待 MDL，后续查询又排队。

处理：

  1. 找到持有 MDL 的长事务。
  2. 评估能否 kill。
  3. DDL 使用在线变更工具或低峰执行。
  4. DDL 前检查长事务。

18. 常见面试题与答案

18.1 mysqldump --single-transaction 为什么适合 InnoDB？

因为 InnoDB 支持事务和 MVCC。--single-transaction 会在导出开始时开启一致性快照，导出期间不需要锁住 InnoDB 表，也能看到同一时间点的数据视图。但它不适合 MyISAM 等非事务表，也会产生长事务风险。

18.2 逻辑备份和物理备份怎么选？

小库、跨版本迁移、对象级恢复优先逻辑备份；大库、低 RTO、全实例恢复优先物理备份。生产通常组合使用：物理备份保证恢复速度，逻辑备份用于抽样校验、对象恢复和迁移。

18.3 binlog 有什么作用？

binlog 记录数据库变更，用于复制、时间点恢复、审计和数据同步。生产中要设置合理保留周期，确保覆盖从库延迟、备份恢复和审计需要。

18.4 GTID 解决什么问题？

GTID 给每个事务一个全局唯一编号，让复制切换和故障恢复不再依赖手工匹配 binlog 文件和 offset。它简化拓扑切换，但不自动保证业务数据一致。

18.5 异步复制、半同步复制、组复制有什么区别？

  • 异步复制：主库提交不等从库，性能好但可能丢最近事务。
  • 半同步复制：主库至少等一个从库收到日志再返回，降低丢失概率但增加延迟，超时可能退化。
  • 组复制：多个节点通过组通信和冲突检测维护一致复制，支持自动选主，但复杂度和网络要求更高。

18.6 主从延迟怎么排查？

先看 SHOW REPLICA STATUS\G 判断 IO 线程还是 SQL 线程问题，再查大事务、从库资源、并行复制配置、无主键表、重查询、网络延迟。短期可切读流量或暂停报表，长期要拆小事务、补索引/主键、提升规格或优化架构。

18.7 读写分离有什么坑？

最大的问题是复制延迟导致写后读不一致。解决方式包括写后读主库、会话粘主、GTID 等待、强一致接口禁读从库，以及从库故障摘除。

18.8 分库分表解决什么问题？代价是什么？

解决单库容量、写入吞吐、热点隔离问题。代价是跨分片查询、分页、排序、事务、全局 ID、扩容迁移、监控备份都更复杂。不能把分库分表当作普通 SQL 优化的替代品。

18.9 分区表和分表有什么区别？

分区表仍是一个逻辑表，由 MySQL 管理多个分区，适合按时间归档和分区裁剪。分表是多个独立物理表或库表，通常由应用或中间件路由。分区表降低部分运维成本，但不能解决所有大表性能问题。

18.10 MySQL 磁盘满了怎么办？

先确认占用来源，不要直接删除 MySQL 管理的日志文件。可清理确认不再需要的 binlog、迁走备份、扩容磁盘、关闭异常 general log。处理后复盘容量告警和 binlog 保留策略。

18.11 innodb_flush_log_at_trx_commit 和 sync_binlog 怎么设置？

核心交易库通常设置为 1 和 1，保证事务提交时 redo 和 binlog 都尽量落盘，降低宕机丢数据风险。非核心或可容忍丢失的场景可以在明确 RPO 后放宽以换取性能。

18.12 如何做 MySQL 升级？

先做兼容性检查、驱动检查、备份和回滚方案；在测试环境用真实流量或回放验证；生产优先滚动升级或新集群迁移；切换前做数据校验；切换后保留旧库只读回滚窗口。

18.13 如何防止误删数据？

  • 最小权限，应用账号禁止 DDL 和高危权限。
  • SQL 审批和变更窗口。
  • 生产默认禁用无 WHERE 的 UPDATE/DELETE 或通过网关拦截。
  • 开启 binlog、审计和备份演练。
  • 高危操作前强制备份和二次确认。

18.14 如何判断数据库瓶颈在 CPU、IO 还是锁？

CPU 高通常伴随计算型 SQL、执行计划错误或并发过高；IO 高常见于 Buffer Pool 命中率下降、临时表、全表扫描、刷脏压力；锁瓶颈表现为 Threads_running 高但 CPU 不一定高，并伴随 row lock、metadata lock 或死锁信息。要结合 OS 指标、Performance Schema、慢日志和 InnoDB 状态判断。

19. 生产最佳实践清单

19.1 架构与高可用

  • [ ] 核心库至少一主两从或托管高可用实例。
  • [ ] 跨可用区部署，故障域隔离。
  • [ ] 开启 GTID，切换流程经过演练。
  • [ ] 关键链路评估半同步或组复制。
  • [ ] 读写分离有一致性策略。
  • [ ] 故障切换后有旧主隔离机制，防止双写。

19.2 备份恢复

  • [ ] 全量备份 + binlog 归档。
  • [ ] 备份加密和异地保存。
  • [ ] 备份保留周期覆盖合规和恢复要求。
  • [ ] 定期恢复演练并记录 RTO。
  • [ ] 误删恢复 runbook 可执行。
  • [ ] 升级、DDL、迁移前有专项备份。

19.3 性能与容量

  • [ ] 核心 SQL 有索引评审和执行计划记录。
  • [ ] 慢查询日志开启并定期治理。
  • [ ] 建立性能基线。
  • [ ] 容量增长有 3/6/12 个月预测。
  • [ ] 磁盘、连接、复制延迟、锁等待有告警。
  • [ ] 大表有归档、分区或拆分策略。

19.4 参数与变更

  • [ ] 参数变更有变更单、回滚方案和观察窗口。
  • [ ] 核心库优先保证 innodb_flush_log_at_trx_commit=1、sync_binlog=1。
  • [ ] 不盲目调大连接数和 per-connection buffer。
  • [ ] DDL 使用在线方案并避开业务高峰。
  • [ ] 变更前检查长事务、复制延迟和备份状态。

19.5 安全与审计

  • [ ] 应用账号最小权限。
  • [ ] root 不给应用使用，不允许远程通用 root。
  • [ ] 密码定期轮换，离职人员权限及时回收。
  • [ ] 数据库不暴露公网。
  • [ ] 传输链路启用 TLS。
  • [ ] 敏感数据脱敏、加密、分类分级。
  • [ ] 高危操作、敏感查询和权限变更有审计。

19.6 应急与复盘

  • [ ] 有主库故障、复制中断、磁盘满、误删数据、慢查询风暴 runbook。
  • [ ] 每次故障记录时间线、影响范围、根因、恢复动作。
  • [ ] 复盘输出改进项并跟踪关闭。
  • [ ] 告警必须有负责人、阈值解释和处理手册。
