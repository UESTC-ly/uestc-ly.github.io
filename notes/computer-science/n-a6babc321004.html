学习目标

  • 掌握 String、Hash、List、Set、ZSet 的内部直觉、典型命令、复杂度和适用场景。
  • 能根据访问模式选择数据类型，避免慢命令、大对象、跨 slot 多键操作和不可控扫描。
  • 理解 Redis 单命令原子性、数据结构编码优化与业务一致性之间的边界。

核心原理

Redis 不是只保存字符串的 KV，它把常见内存数据结构封装成命令接口。命令在单个 Redis 实例事件循环中顺序执行，所以单条命令不会被其他客户端命令插入打断；但多个命令之间仍可能被其他请求穿插，业务流程需要事务、Lua 或外部幂等来补齐。

类型选择先看访问路径

选择 Redis 类型时不要先问“哪个省内存”，而要先画访问路径：是否按字段读写、是否需要排名、是否只判断存在、是否需要两端队列、是否会按范围读取。结构选错后，后续通常只能靠大 Key 拆分和批处理补救。

类型 内部直觉 常用命令 常见复杂度 典型场景 风险点
String 字节数组，可表达文本、数字、bitmap、小 JSON GET、SET、INCR、MGET、SETBIT 多数 O(1)，MGET O(N) 缓存值、计数器、令牌、位图 大 value、热点计数、非幂等重试
Hash key 下的 field-value 字典，小对象有紧凑编码，大对象按哈希表直觉理解 HGET、HSET、HMGET、HSCAN、HINCRBY 单字段平均 O(1)，扫描 O(N) 对象字段缓存、配置、轻量状态 字段过多形成大 Key；字段过期依赖 Redis 版本
List 双端链表/紧凑列表直觉，适合两端操作 LPUSH、RPOP、BLPOP、LRANGE 两端 O(1)，范围 O(S+N) 简单队列、最新列表 中间访问慢，可靠消费能力弱
Set 不重复成员集合，支持存在判断和集合运算 SADD、SISMEMBER、SREM、SINTER 单元素平均 O(1)；集合运算取决于集合数与成员数，如 SINTER 最坏 O(N×M) 去重、标签、关系判断 大集合交并差阻塞实例
ZSet 成员唯一，按 score 排序，通常可按 skiplist + dict 理解 ZADD、ZRANGE、ZRANK、ZREM 写/排名 O(log N)，范围 O(log N+M) 排行榜、延迟队列、优先级 高写排行、超大范围读取

String：缓存、计数和位图

String 的 value 是二进制安全字节序列，数字自增只是 Redis 对字符串内容执行整数解析后的原子更新。它适合“整值读写”的对象，不适合频繁修改大 JSON 的局部字段；每次 SET 都会替换整个 value。

SET user:42:profile '{"name":"Li","level":"gold"}' EX 600
INCR article:1001:view_count
SETBIT user:active:2026-08-31 42 1
BITCOUNT user:active:2026-08-31

工程判断：

  • 高频计数用 INCRBY 比“GET 后在应用层加一再 SET”可靠，因为单命令原子。
  • 需要读取对象中少数字段时，Hash 往往比大 JSON String 更合适。
  • bitmap 节省空间但要求 ID 可映射到偏移，稀疏大 ID 会浪费巨大空间。

Hash：字段级更新与版本化字段过期

Hash 适合“一个业务对象、多字段、小字段值、字段级读写”。它能避免每次更新都序列化整个对象。传统 Redis 版本的 TTL 只作用于整个 key；Redis 7.4 起提供 HEXPIRE/HPEXPIRE 等 hash field expiration 命令，可以为指定字段设置 TTL。部署在旧版本、客户端尚未支持这些命令，或字段生命周期涉及独立容量/迁移边界时，仍应拆分 key，而不是假设字段过期始终可用。

HSET user:42 name "Li" level "gold" updated_at "2026-08-31T10:00:00Z"
HMGET user:42 name level
HINCRBY user:42 login_count 1

边界：

  • 用户基础信息、统计字段、权限标记的生命周期不同，应拆成多个 Hash 或 String。
  • 单个 Hash 包含几十万字段时，本质已经是大 Key；HGET 仍快，但迁移、删除、扫描、持久化都会变重。
  • 需要遍历时使用 HSCAN 分批，不要在请求路径一次性 HGETALL 大 Hash。

List：简单队列和时间线片段

List 的优势在两端插入/弹出。它可以做轻量任务队列，但缺少成熟消息队列的消费组、重放位点、死信、延迟重试、长期保留能力。Redis Streams 比 List 更接近队列模型，但和 Kafka/RocketMQ 的定位仍不同。

LPUSH jobs:resize payload-1
BRPOP jobs:resize 5
LRANGE feed:user:42 0 49
LTRIM feed:user:42 0 999

故障窗口：消费者 BRPOP 成功后进程崩溃，消息已经从 List 移除但业务未完成。可以用“取出后写处理中列表 + ack 后删除”缓解，但复杂度会接近重新实现消息队列。

Set：去重和关系判断

Set 适合成员唯一、无需顺序的场景，例如点赞用户集合、标签集合、抽奖去重。SISMEMBER 是典型 O(1) 关系判断；集合交并差在成员很多时会把 CPU 时间集中到单实例。

SADD post:1001:liked_users user:42
SISMEMBER post:1001:liked_users user:42
SINTER user:42:followees user:99:followers

工程取舍：

  • 只需要计数时优先用 String 计数器，不必保存完整 Set。
  • 大集合求交集适合离线预计算、分桶或数据库查询，不适合请求路径临时 SINTER。
  • 需要按时间或分数取 TopN 时不要用 Set，改用 ZSet。

ZSet：排行榜、时间轮和延迟队列

ZSet 维护 member 到 score 的映射并按 score 排序。它适合按照积分、时间戳、优先级取范围。范围查询复杂度不仅看定位的 log N，还看返回元素个数 M；返回 10 万个成员会造成网络和序列化压力。

ZADD rank:daily 9527 user:42
ZREVRANGE rank:daily 0 99 WITHSCORES
ZRANGEBYSCORE delay:jobs -inf 1788170400000 LIMIT 0 100

延迟队列伪代码：

while true:
    jobs = ZRANGEBYSCORE(delay_key, -inf, now_ms, LIMIT 0 100)
    for job in jobs:
        if ZREM(delay_key, job) == 1:
            handle(job)

这个模型只保证“抢到再处理”，不保证处理成功后自动 ack；进程崩溃需要业务幂等和重新入队补偿。

复杂度要叠加网络成本

Redis 命令复杂度只描述服务端数据结构操作，不包含网络传输、序列化、客户端排队和反序列化。MGET 1000 复杂度是 O(N)，但可能比 1000 次 GET 更快，因为减少 RTT；ZRANGE 0 99999 即使服务端能完成，也可能拖慢网络和客户端内存。

flowchart LR
  Model["访问模式"] --> Type["选择类型"]
  Type --> Command["选择命令"]
  Command --> Cost["复杂度 + 返回体大小 + RTT"]
  Cost --> Limit["限流/分页/拆分/异步化"]

工程实践/示例

四类业务建模案例

场景 推荐类型 核心命令 说明
文章浏览计数 String INCRBY article:{id}:views 1 单值原子累加，周期落库
用户资料缓存 Hash 或 String HMGET user:{id} name level 字段常单独更新用 Hash；整对象读写用 String
关注关系判断 Set SISMEMBER user:{uid}:followees {target} 大 V 关注/粉丝集合要分桶或落库
积分排行榜 ZSet ZINCRBY rank:daily 10 user:42 排名与 TopN 读取自然匹配

线上排查命令

TYPE user:42
MEMORY USAGE user:42
OBJECT ENCODING user:42
SLOWLOG GET 10
SCAN 0 MATCH 'user:*' COUNT 1000

OBJECT ENCODING 可辅助理解内部编码，但不要把编码阈值写入业务假设；它们受 Redis 版本和配置影响。业务文档应描述访问模式和数据规模上限，而不是依赖某个内部编码永远不变。

容量估算

key_count = 日活用户数 * 每用户 key 数
memory ~= key 元数据 + value 字节 + 数据结构额外索引 + allocator 碎片
network_out ~= QPS * 平均返回字节

容量评估要给每类 key 设上限：value 最大字节数、集合最大成员数、单次范围最大返回条数、过期时间、是否可重建。没有上限的结构会在业务增长后变成大 Key。

常见误区

误区 说明
KEYS * 可用于线上排查 KEYS 是 O(N)，线上应优先使用 SCAN 分批遍历
Hash 一定比 String 省内存 小对象可能省，字段过多或结构膨胀后仍会造成大 Key
Redis 原子命令能保证完整业务原子 只保证单条命令执行不被打断，多步骤业务仍会发生竞态
List 可以替代 Kafka Redis List 缺少成熟的消费组、重放、位点和长期存储能力
SCAN 不影响线上 SCAN 分批降低阻塞，但仍消耗 CPU，批量和频率要受控

自测题

  1. ZRANGE key 0 9999 WITHSCORES 的复杂度风险在哪里？
  2. 为什么 SINTER 在大集合上可能成为慢命令？
  3. 用 Hash 缓存用户对象时，哪些字段不适合放在同一个 Key？
  4. 只需要判断“用户今天是否活跃”时，Set 和 bitmap 的取舍是什么？
  5. 为什么 MGET 可以降低 RTT，但仍需要限制 key 数和返回体大小？

实践任务

  • 为“关注关系”“视频点赞”“文章浏览计数”“积分排行榜”分别选择 Redis 类型并写出核心命令。
  • 使用 SCAN 设计一个按前缀统计 Key 数量的脚本，要求每批限制数量并可中断恢复。
  • 给一个商品详情缓存设计数据规模契约：最大 value、最大字段数、TTL、是否允许空值缓存。
