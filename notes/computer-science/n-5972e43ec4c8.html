分章节讲解

1. 配置管理

核心定义： 配置应与代码分离，区分环境、密钥和运行参数，并支持审计。

底层原理： - 配置是把“会变的内容”从代码中剥离出来。 - 环境变量、配置中心、密钥系统分别承担不同职责。 - 配置的目标是让环境差异可控、变更可追踪、回滚可恢复。

工程理解： - 密钥不能写进代码、仓库或镜像。 - 配置最好有版本、灰度、审计和回滚能力。 - 配置的粒度要适中，太碎会难管，太粗会难改。

适用场景： - 多环境部署。 - 不同租户/集群/地域的差异化运行。 - 需要频繁调整而不想频繁发版的参数。

常见误区： 把密钥写进代码或镜像会形成长期泄露风险。

2. 日志

核心定义： 日志记录关键业务事件、错误上下文和关联 ID，便于排障和审计。

底层原理： - 日志是一条时间序列化的事实记录。 - 结构化日志比纯文本更容易检索、聚合和关联。 - Trace ID / Request ID 是跨服务排障的重要线索。

工程理解： - 日志要“可读、可查、可关联、可脱敏”。 - 关键路径要记录业务语义，不只是技术异常。 - 过量日志会让存储、检索和噪音成本一起上升。

适用场景： - 错误排查、审计、用户行为追踪、异常复现。

常见误区： 日志过多会增加成本；日志过少会无法定位问题。

3. 指标

核心定义： 指标反映系统健康，如延迟、吞吐、错误率和资源使用率。

底层原理： - 指标是“可聚合的数值事实”。 - 监控关注趋势、阈值和异常变化，不只是单点数值。 - 平均值常常会掩盖长尾，分位数更有参考价值。

工程理解： - 指标要和告警方案绑定，否则只是展示。 - 业务指标比纯技术指标更能反映真实体验。 - 指标设计要考虑可行动性：看到异常后能否立即采取动作。

适用场景： - SLA/SLO 监控、容量评估、发布观察、故障判断。

常见误区： 只看平均值会掩盖长尾问题；P95/P99 更适合观察体验。

4. 发布方案

核心定义： 蓝绿、金丝雀、灰度和特性开关用于降低发布风险。

底层原理： - 蓝绿解决“快速切换”；金丝雀解决“小流量试探”；特性开关解决“功能开关控制”。 - 发布不是单次动作，而是“验证、扩量、观察、回滚”的过程。 - 没有监控的发布只是把未知风险扩大。

工程理解： - 新版本要带观察指标和回滚路径。 - 复杂功能最好配合特性开关，方便按用户、租户、环境控制。 - 发布节奏要与告警、回滚、值班机制联动。

适用场景： - 大版本上线、风险较高的改动、逐步验证新功能。

常见误区： 没有监控和回滚的灰度只是在慢慢扩大事故范围。

  B --> C["看指标趋势"]

实战深化：部署流水线、观测信号与回滚决策

1. 部署流水线不是“把代码放上去”

一条可靠的后端部署流水线至少要回答四个问题：

  1. 构建物是否可信： 代码、依赖、镜像、配置和数据库变更是否可追溯。
  2. 环境是否一致： 开发、测试、预发、生产是否使用同一套构建物，只通过配置区分环境。
  3. 上线是否可控： 能否按实例、流量、租户、地域或功能开关逐步放量。
  4. 失败是否可退： 发现异常后能否快速停止、降级、回滚或切流。
flowchart LR
  A["提交代码"] --> B["CI 构建"]
  B --> C["自动测试"]
  C --> D["制品入库"]
  D --> E["预发验证"]
  E --> F["灰度发布"]
  F --> G["指标观察"]
  G --> H{是否异常}
  H -- 否 --> I["继续放量"]
  H -- 是 --> J["回滚/降级"]

关键理解： - CI 主要证明“代码和构建物基本可信”，CD 主要证明“变更可以安全进入目标环境”。 - 同一份构建物在不同环境运行，能减少“测试环境通过、生产环境失败”的偶然性。 - 数据库迁移、消息队列 schema、缓存 key、配置开关都属于发布内容，不能只盯应用镜像。

2. 日志、指标、追踪分别回答不同问题

观测信号 主要回答 典型内容 适合定位 不适合替代
日志 发生了什么 错误栈、业务事件、请求参数摘要、Trace ID 单次请求、异常上下文、审计 系统整体趋势
指标 变化是否异常 QPS、错误率、P95/P99、CPU、队列长度 趋势、容量、告警、SLO 具体调用细节
追踪 慢在哪里 跨服务 span、依赖调用、耗时拆分 链路瓶颈、下游依赖、扇出调用 业务审计

排障顺序建议： 1. 先看指标确认影响面：是全局异常、单接口异常，还是单租户/单地域异常。 2. 再看追踪定位慢点或错误传播路径：入口、网关、应用、数据库、缓存、第三方接口分别耗时多少。 3. 最后看日志补上下文：具体请求、异常栈、业务状态、配置版本和发布版本。

3. 回滚不是唯一解：先判断变更类型

变更类型 首选止血动作 为什么 风险
纯应用代码 回滚版本或切回旧实例 构建物边界清楚，回滚成本低 旧版本是否兼容新数据
配置错误 回滚配置或关闭开关 生效快、影响面可控 配置传播延迟和缓存
数据库 schema 向前修复或兼容回滚 DDL 可能不可逆或耗时长 新旧代码同时访问
缓存污染 清理 key、旁路缓存、降级读库 根因可能不在代码版本 读库压力上升
下游依赖异常 熔断、限流、降级、切备用 回滚本服务不一定有效 降级体验和数据补偿

面试表达： 不要直接说“出问题就回滚”。更好的回答是：先判断变更是否可逆、数据是否兼容、影响面是否仍在扩大，再选择回滚、降级、切流、关闭开关或向前修复。

4. 一个线上排障案例：订单接口延迟突然升高

现象： 发布后 10 分钟，订单创建接口 P99 从 300ms 升到 3s，错误率没有明显上升。

定位路径： 1. 指标： 发现只有 POST /orders 的 P99 异常，QPS 没有突增，CPU 正常，数据库连接池等待时间升高。 2. 追踪： 链路显示库存校验和优惠券校验耗时正常，订单写库阶段 span 拉长。 3. 日志： 慢请求日志带出新版本号和 SQL 摘要，发现新增查询没有命中索引。 4. 决策： 如果新字段不是核心路径，先关闭特性开关；如果无法关闭，回滚应用并保留向后兼容 schema。 5. 复盘： 为慢 SQL 增加索引评审、预发压测和发布后 P99 自动看板。

  B --> C["查链路耗时"]
  C --> D["定位数据库等待"]
  D --> E["查慢 SQL 日志"]
  E --> F["关闭开关/回滚"]
  F --> G["补索引与压测"]

5. 发布前检查清单

  • 代码： 核心路径有自动化测试；异常分支和幂等逻辑已覆盖。
  • 数据： schema 变更可兼容新旧版本；迁移脚本可重复执行或可检测执行状态。
  • 配置： 新配置有默认值、范围校验、审计记录和回滚方式。
  • 观测： 新接口或新依赖有日志、指标、追踪和告警阈值。
  • 回滚： 明确回滚触发条件、负责人、命令或操作入口。
  • 沟通： 值班、客服、业务方知道可能影响和降级口径。

6. 发布后观察窗口

时间窗口 重点观察 常见动作
0-5 分钟 实例启动、健康检查、错误率 发现启动失败立即停止扩量
5-30 分钟 P95/P99、核心接口、下游依赖 小流量灰度，必要时关闭开关
30-120 分钟 业务转化、队列积压、资源趋势 逐步扩量，确认无慢性退化
24 小时内 定时任务、峰谷流量、长尾用户 复盘告警噪音和遗漏指标

边界条件： 有些问题不会在短观察窗口出现，例如定时任务、月末账单、低频租户、冷缓存、跨时区请求。因此高风险发布要结合业务周期设定观察窗口。

7. 常见误区与反例

  • 误区 1：有日志就等于可观测。 反例：日志没有 Trace ID，跨服务调用无法串起来，只能靠猜。
  • 误区 2：灰度一定安全。 反例：灰度用户触发了不可逆数据库写入，回滚应用也无法恢复旧数据语义。
  • 误区 3：告警越多越安全。 反例：噪音告警太多导致值班忽略真正的核心链路异常。
  • 误区 4：平均延迟正常就没问题。 反例：P99 变差只影响少量高价值用户，但业务损失很大。
  • 误区 5：回滚能解决所有发布问题。 反例：消息格式已经被新版本消费者写入队列，旧版本无法解析。

8. 面试追问路径：从“会背概念”到“能处理事故”

  1. 面试官问：如何设计发布流程？ - 先答：CI 构建、测试、制品、预发、灰度、监控、回滚。 - 追问准备：数据库变更如何兼容？配置如何回滚？特性开关如何分组？
  2. 面试官问：线上延迟升高怎么办？ - 先答：看指标定范围，看追踪定路径，看日志定上下文。 - 追问准备：如果是下游慢怎么办？如果是缓存击穿怎么办？如果错误率不高但用户投诉怎么办？
  3. 面试官问：如何设置告警？ - 先答：围绕 SLO、错误率、延迟、饱和度和业务指标设置。 - 追问准备：如何降低噪音？如何避免只监控机器不监控业务？

知识点 正确理解 常见误区
