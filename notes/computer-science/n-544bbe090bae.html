Nginx：反向代理、负载均衡与入口层

学习目标

  • 理解 Nginx 作为 Web Server、反向代理、负载均衡器和 TLS 终止点的常见角色。
  • 能配置静态文件服务、反向代理、Header 透传、超时和基础限流。
  • 能排查 404、502、504、跨域、上传大小和 WebSocket 代理问题。
  • 能识别生产入口层的安全和可观测性要求。

核心概念

Nginx 使用 master/worker 进程模型，擅长处理大量连接。常见配置层级是 http、server、location。server 通常对应一个域名或端口，location 根据路径匹配请求。

反向代理把客户端请求转发给后端服务，并可处理 TLS、压缩、缓存、连接复用、限流和访问日志。负载均衡通过 upstream 把请求分发给多个后端实例。

Nginx 不应替代应用层鉴权和业务校验，但适合做入口层通用策略，例如请求体大小限制、基础速率限制、安全 Header、静态资源缓存和错误页。

示例

反向代理

下面的 listen 80 示例适用于本地实验、容器内网或受控内网入口。公网入口不应只暴露明文 HTTP，通常应在 Nginx 或上游负载均衡层终止 TLS，并配置证书续期、HSTS 策略和安全 Header。

upstream user_api {
    server user-api-1:8080;
    server user-api-2:8080;
}

server {
    listen 80;
    server_name api.example.com;

    access_log /var/log/nginx/access.log;
    error_log /var/log/nginx/error.log warn;

    location / {
        proxy_pass http://user_api;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
        proxy_send_timeout 30s;
    }
}

静态文件缓存

下面的 listen 80 同样按本地或内网示例理解；面向公网的静态站点也应通过 HTTPS 对外服务。

server {
    listen 80;
    server_name static.example.com;

    root /usr/share/nginx/html;

    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }
}

生产注意事项：公网入口应启用 HTTPS、现代 TLS 配置、访问日志采集、错误日志告警、请求 ID 透传、合理超时、上传大小限制和限流。若在 Kubernetes 中使用 Nginx Ingress，还要确认注解是否被集群策略允许。

典型工作流

  1. 明确 Nginx 负责的边界：静态文件、反向代理、TLS、限流或 Ingress。
  2. 写 server 和 location，配置 proxy_pass、Header 和超时。
  3. 使用 nginx -t 检查配置语法。
  4. reload 配置而不是直接杀进程，例如 nginx -s reload。
  5. 用 curl 验证状态码、Header、重定向、压缩和超时行为。
  6. 接入访问日志和错误日志，按域名、路径、状态码和 upstream 状态观察。

常见坑

  • proxy_pass 末尾斜杠处理不清楚，导致转发路径变化。
  • 忘记传 Host、X-Forwarded-For、X-Forwarded-Proto，后端无法生成正确链接或审计来源。
  • 默认上传大小太小，出现 413 Request Entity Too Large。
  • 超时太短导致慢接口 504，太长又会占用连接资源。
  • WebSocket 未设置 HTTP/1.1 和 Upgrade Header。
  • 静态资源缓存设置过长但文件名没有内容哈希，导致用户拿到旧文件。

排障步骤

  1. nginx -t 检查配置语法和 include 路径。
  2. 查看 access log 中的状态码、upstream 地址、响应时间和请求路径。
  3. 查看 error log 是否有连接拒绝、超时、权限或文件不存在。
  4. 对 502 检查后端是否启动、端口是否正确、DNS 是否解析。
  5. 对 504 检查后端耗时、proxy_read_timeout 和上游负载。
  6. 对路径异常，明确 location 匹配结果和 proxy_pass 是否改写 URI。

练习

  1. 配置 Nginx 把 /api/ 转发到本地 8080 服务，把 /assets/ 指向静态目录。
  2. 修改 proxy_pass 是否带末尾斜杠，观察后端收到的路径差异。
  3. 配置 client_max_body_size，验证大文件上传行为。
  4. 为 WebSocket 服务增加 Upgrade Header 并用客户端验证连接。

检查清单

  • 每个 server 的域名、端口、日志和默认行为明确。
  • 反向代理传递必要 Header，并设置连接、读取和发送超时。
  • 静态资源缓存策略与文件名版本化策略匹配。
  • 生产入口启用 HTTPS、限流、日志和必要安全 Header。
  • 排障时能区分 Nginx 配置问题、上游服务问题和网络问题。

前置知识与完成标准

前置知识：理解 HTTP 方法、状态码、Header、Host、URI、TLS 证书和后端服务端口；能读 Nginx 配置块和基础 shell 命令。

完成标准：

  • 能说明请求进入 Nginx 后如何选择 server 和 location。
  • 能解释 proxy_pass、Header 透传、upstream 负载均衡、超时、缓冲、限流和 TLS 终止的作用。
  • 能从零启动一个后端服务和一个 Nginx 反向代理，并用 curl 验证路径、Header 和状态码。
  • 能根据 404、413、499、502、504、WebSocket 失败等现象定位到配置、上游或客户端问题。

请求阶段与入口层数据流

Nginx 处理请求时先根据监听地址和端口找到候选 server，再用 Host 匹配 server_name，没有匹配时进入该监听端口的默认 server。进入 server 后再根据 URI 选择 location：精确匹配优先，其次是最长前缀和正则匹配规则。查询字符串通常不参与 location 路径匹配。

反向代理数据流是：客户端 TCP/TLS 连接 -> Nginx 读取请求行和 Header -> 匹配 server/location -> 应用 rewrite、限流、访问控制、请求体大小等策略 -> 转发到 upstream -> 读取响应头和响应体 -> 按缓冲、压缩、缓存和日志策略返回客户端。

upstream 默认轮询，也可配置 least_conn 或 ip_hash。轮询适合实例能力接近且请求耗时接近的场景；least_conn 适合慢请求较多的服务；ip_hash 可保持简单会话亲和，但会受 NAT 和实例变更影响。生产中更推荐应用无状态化，把会话放到共享存储或 token。

缓冲的边界很重要：响应缓冲开启时，Nginx 会尽快读取上游响应并缓存到内存或临时文件，再向慢客户端发送，保护上游连接；关闭缓冲适合 SSE、流式下载等需要边产生边传输的场景。请求缓冲类似，上传大文件时可能先落到临时文件，再转发给上游。

从零可复现实验

目标：用 Docker 同时启动后端和 Nginx，验证反向代理、Header 和 502。

  1. 创建 nginx.conf：
events {}

http {
    upstream app {
        server app:8080;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://app;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_connect_timeout 2s;
            proxy_read_timeout 10s;
        }
    }
}
  1. 创建 compose.yaml：
services:
  app:
    image: hashicorp/http-echo:1.0
    command: ["-listen=:8080", "-text=hello through nginx"]
  nginx:
    image: nginx:1.27
    ports:
      - "8080:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - app
  1. 验证：
docker compose up
curl -i http://127.0.0.1:8080/
docker compose stop app
curl -i http://127.0.0.1:8080/

预期结果：第一次返回 200 和 hello through nginx；停止后端后返回 502。验证方法：查看 Nginx access log 和 error log，确认 upstream 连接拒绝或超时。

配置与命令逐段讲解

location /api/ {
    proxy_pass http://backend/;
}

当 proxy_pass 带 URI 部分并以 / 结尾时，匹配到的 /api/ 前缀会被替换为 /，后端收到的路径会变化。若写成 proxy_pass http://backend;，通常会把原始 URI 传给后端。路径异常时首先比较这两种写法。

proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

这些 Header 让后端知道原始 Host、客户端 IP 链和协议。缺少 X-Forwarded-Proto 时，后端可能生成 http 链接或错误重定向；缺少 IP 透传时，审计、限流和风控会看到 Nginx 的地址。

client_max_body_size 20m;
proxy_connect_timeout 3s;
proxy_send_timeout 30s;
proxy_read_timeout 30s;
proxy_buffering on;
limit_req_zone $binary_remote_addr zone=api_rate:10m rate=10r/s;
  • client_max_body_size 限制请求体大小，过小会出现 413。
  • proxy_connect_timeout 是连接上游的时间。
  • proxy_send_timeout 是向上游发送请求的等待时间。
  • proxy_read_timeout 是等待上游响应数据的时间，慢接口常触发 504。
  • proxy_buffering 控制响应缓冲，流式接口常需要关闭。
  • limit_req_zone 定义限流共享区，实际生效还要在 server 或 location 使用 limit_req。

教学配置与生产配置边界

教学配置可用 HTTP、单个 server、容器内 upstream、宽松日志格式。生产公网入口应启用 HTTPS、自动证书续期、HSTS、安全 Header、访问日志结构化、错误日志告警、请求 ID、合理超时、连接和请求限流、上传大小限制，以及对管理路径的访问控制。

教学中可以用 Nginx 直接做简单负载均衡；生产中要明确它和云负载均衡、Ingress Controller、服务网格、应用鉴权的边界。Nginx 可以挡住通用流量风险，但不能替代业务权限判断、数据校验和审计。

排障决策树

入口访问异常
├─ nginx -t 失败？
│  ├─ 是：修语法、include 路径、证书文件权限
│  └─ 否：继续
├─ 404？
│  ├─ 静态文件：检查 root/alias、try_files、文件权限
│  └─ 代理路径：检查 location 与 proxy_pass URI 改写
├─ 413？
│  └─ 调整 client_max_body_size，并确认上游也允许该大小
├─ 502？
│  └─ 检查 upstream DNS、端口、后端进程、连接拒绝、TLS 到上游
├─ 504？
│  └─ 检查上游耗时、proxy_read_timeout、队列积压、数据库慢查询
└─ WebSocket/SSE 失败？
   └─ 检查 HTTP/1.1、Upgrade/Connection Header、proxy_buffering

练习与答案要点

基础练习：写两个 server，一个默认返回 444 或 404，一个匹配 api.local 转发到后端。答案要点：Host 不匹配时不会误进业务后端；curl -H 'Host: api.local' 可验证 server 选择。

进阶练习：分别配置 proxy_pass http://backend; 和 proxy_pass http://backend/;，请求 /api/users 并记录后端路径。答案要点：能说明 URI 替换差异；路径问题先看 location 和 proxy_pass。

综合练习：为 /api/ 配置限流、20m 上传限制、30s 读取超时、WebSocket Header 和结构化 access log。答案要点：每个策略有验证命令；生产说明 TLS、证书续期和告警。

小结与官方延伸阅读

Nginx 是入口层的流量治理工具：它负责连接、路由、代理、TLS、缓冲、限流和日志，但业务正确性仍由后端服务负责。学会从请求处理阶段拆问题，能显著缩短 502、504 和路径改写类故障的定位时间。
