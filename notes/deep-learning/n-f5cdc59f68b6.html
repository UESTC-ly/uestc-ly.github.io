本章把 OpenCV 从“能跑”推进到“跑得稳、跑得快、可复现”。性能问题不要先问“能不能上 GPU”，而要先定位瓶颈来自计算、内存带宽、复制、同步还是 I/O：计算瓶颈随图像尺寸、卷积核或模型复杂度增长；内存带宽瓶颈表现为简单逐像素操作也慢，连续内存和 ROI 步长影响明显；复制瓶颈来自 copy、clone、astype、cvtColor、CPU/GPU 往返；同步瓶颈常见于锁、GPU 下载、显示窗口和日志刷盘；I/O 瓶颈来自磁盘、网络、解码器、摄像头 backend、编码和 GUI 刷新。可靠优化顺序是：测量、归因、改算法或数据流、减少搬运、打开已编译加速能力，最后才手写并行或 SIMD。

8.1 先建立可复现基准

基准测试要固定输入、预热、重复多次、分离 I/O 与计算，并记录 OpenCV 构建信息。首次调用可能触发动态初始化、OpenCL kernel 编译、页面调入或缓存填充，因此单次耗时没有解释力。Python 中可以用 cv.getTickCount()/cv.getTickFrequency()，也可以用 time.perf_counter()；C++ 中优先用 cv::TickMeter，它与 OpenCV 的计时体系一致，便于在示例和库代码中对照。

import cv2 as cv
import numpy as np

img = cv.imread("input.jpg", cv.IMREAD_COLOR)
assert img is not None
kernel = np.ones((5, 5), np.float32) / 25

def bench(name, fn, warmup=5, repeat=50):
    for _ in range(warmup):
        fn()
    t0 = cv.getTickCount()
    for _ in range(repeat):
        out = fn()
    dt = (cv.getTickCount() - t0) / cv.getTickFrequency()
    print(f"{name}: {dt * 1000 / repeat:.3f} ms/frame, shape={out.shape}")

bench("blur", lambda: cv.blur(img, (5, 5)))
bench("filter2D", lambda: cv.filter2D(img, -1, kernel))

print("OpenCL:", cv.ocl.haveOpenCL(), cv.ocl.useOpenCL())
print(cv.getBuildInformation())

这段代码的关键是固定同一输入、循环次数和输出形状。正式报告应记录 CPU/GPU、OpenCV 版本、Python/编译器、系统、Debug/Release、OpenCL/CUDA、线程数和图像尺寸。Debug 构建、省电模式、后台任务和热降频都会污染结果。

C++ 侧的最小对照如下：

#include <opencv2/opencv.hpp>
#include <iostream>

int main() {
    cv::Mat img = cv::imread("input.jpg", cv::IMREAD_COLOR);
    CV_Assert(!img.empty());

    cv::TickMeter tm;
    cv::Mat out;
    for (int i = 0; i < 5; ++i) cv::blur(img, out, cv::Size(5, 5));

    tm.start();
    for (int i = 0; i < 100; ++i) cv::blur(img, out, cv::Size(5, 5));
    tm.stop();

    std::cout << "avg ms/frame: " << tm.getTimeMilli() / 100 << std::endl;
    std::cout << cv::getBuildInformation() << std::endl;
}

对应 CMake：

cmake_minimum_required(VERSION 3.16)
project(opencv_perf_demo CXX)
set(CMAKE_CXX_STANDARD 17)
find_package(OpenCV REQUIRED)
add_executable(opencv_perf_demo main.cpp)
target_link_libraries(opencv_perf_demo PRIVATE ${OpenCV_LIBS})

OpenCV 5 主线推荐 C++17；OpenCV 4.x 中 C++11 是基本要求，工程中也常统一到 C++17。对比 4.12 与 5 主线时，应分别记录 getBuildInformation()，不能只写“OpenCV 已安装”。

8.2 Python：少写逐像素循环，少做隐式复制

Python 循环通常输在解释器开销，而不是算法本身。下面的阈值化例子可以用于课堂演示：

import cv2 as cv
import numpy as np

gray = cv.imread("input.jpg", cv.IMREAD_GRAYSCALE)
assert gray is not None

def slow_loop(x):
    out = np.empty_like(x)
    h, w = x.shape
    for y in range(h):
        for col in range(w):
            out[y, col] = 255 if x[y, col] > 127 else 0
    return out

def numpy_where(x):
    return np.where(x > 127, 255, 0).astype(np.uint8)

def opencv_threshold(x):
    return cv.threshold(x, 127, 255, cv.THRESH_BINARY)[1]

for name, fn in [("loop", slow_loop), ("numpy", numpy_where), ("opencv", opencv_threshold)]:
    t0 = cv.getTickCount()
    out = fn(gray)
    ms = (cv.getTickCount() - t0) * 1000 / cv.getTickFrequency()
    print(name, ms, out.dtype)

逐像素 Python 写法把每个像素都变成一次解释器访问；NumPy 把循环交给 C；OpenCV 函数通常还能利用内部并行、向量化和类型优化。优化 Python 代码时优先检查：

  1. 是否可以用 OpenCV/NumPy 一次处理整张图，而不是双层 for。
  2. 是否反复 astype()、copy()、np.array()、clone()，导致每帧全量复制。
  3. ROI 是否只是视图。NumPy 切片和 cv::Mat ROI 多数情况下共享底层数据，但某些函数需要连续内存，可能触发内部复制。
  4. 数据类型是否匹配。uint8、float32、float64 混用会造成额外转换，也可能让算法走慢路径。
  5. 通道顺序是否反复 BGR/RGB 转换。把转换放在边界，不要在每个算子前后转换。

NumPy 表达式也可能创建临时数组。例如 ((img - mean) / std).astype(np.float32) 涉及类型转换和中间结果；热路径中可考虑 cv.subtract、cv.multiply、预分配输出或一次性归一化。

8.3 ROI、连续内存与预分配

cv::Mat 头部很轻，复制 Mat 变量通常只是共享引用计数；clone() 和 copyTo() 才复制像素。ROI 也是一个带偏移和步长的视图：

cv::Mat img = cv::imread("input.jpg");
cv::Rect box(100, 100, 320, 240);
cv::Mat roi = img(box);        // 共享数据，不复制
cv::Mat owned = roi.clone();   // 深拷贝，数据连续

ROI 的问题在于 roi.isContinuous() 可能为假。OpenCV 内置函数通常能处理步长；手写循环、SIMD、外部库和硬件接口则容易出错或变慢。手写遍历要用 ptr<uchar>(y) 按行访问，只有 isContinuous() 为真时才能把图像当作线性内存。

预分配能减少堆分配和引用计数抖动。C++ 中很多函数支持输出参数：

cv::Mat gray, blur8u, edges;
gray.create(src.rows, src.cols, CV_8UC1);
blur8u.create(src.rows, src.cols, CV_8UC1);
edges.create(src.rows, src.cols, CV_8UC1);

cv::cvtColor(src, gray, cv::COLOR_BGR2GRAY);
cv::GaussianBlur(gray, blur8u, cv::Size(5, 5), 1.2);
cv::Canny(blur8u, edges, 80, 160);

Python 中不是所有函数都暴露 dst，但很多基础算子支持 dst=；视频处理也可复用中间变量并避免不必要的 copy()。图像尺寸固定时，预分配收益更稳定。

8.4 线程、parallel_for_ 与 SIMD

OpenCV 内部大量函数已经并行化。cv::setNumThreads() 影响后续并行区域，cv::getNumThreads() 可记录配置。不要在外层开很多线程后，每个线程里再调用内部多线程 OpenCV 函数，否则容易过度订阅。常见策略是二选一：让 OpenCV 管内部并行，外层只拆 I/O、计算、编码；或外层并行处理多路流，并限制 OpenCV 线程数。

当需要并行自己的 C++ 热循环时，用 cv::parallel_for_ 比直接绑死某个线程库更贴近 OpenCV 的构建方式。它依赖 OpenCV 编译时可用的并行后端，例如 TBB、OpenMP、平台线程或其他后端；是否可用要看构建信息。

cv::parallel_for_(cv::Range(0, src.rows), [&](const cv::Range& range) {
    for (int y = range.start; y < range.end; ++y) {
        const uchar* s = src.ptr<uchar>(y);
        uchar* d = dst.ptr<uchar>(y);
        for (int x = 0; x < src.cols; ++x) {
            d[x] = 255 - s[x];
        }
    }
});

并行循环的边界是数据竞争。每个线程应写不同的行、块或输出缓冲；共享统计量用规约或线程局部变量，避免在像素循环里加锁。粒度太小会被调度开销淹没，粒度太大又会负载不均。卷积和形态学等有 halo 区域，边界依赖要单独处理。

SIMD 层面，OpenCV 使用 HAL 和 Universal Intrinsics 为 SSE/AVX/NEON/RVV 等指令集提供统一封装。普通用户通常不需要直接写 Universal Intrinsics；先确认 cv::useOptimized() 为真、构建启用了 CPU dispatch，并使用内置函数。只有自定义算子成为明确热点且无法由已有函数表达时，才考虑手写 SIMD，并用标量实现校验对齐、尾部元素、ROI 步长和不同指令集。

8.5 OpenCL UMat、CUDA GpuMat 与 Vulkan 边界

OpenCV 的透明 API（T-API）通过 cv::UMat 使用 OpenCL。收益取决于 OpenCV 是否以 WITH_OPENCL 构建、机器是否有 OpenCL 设备、函数是否有 OpenCL 实现、数据是否能留在设备上。每帧 Mat -> UMat -> Mat 往返通常会抵消加速。适合 UMat 的场景是多个支持 OpenCL 的算子串联，且中间结果不下载回 CPU。

cv::UMat u, gray, edges;
src.copyTo(u);
cv::cvtColor(u, gray, cv::COLOR_BGR2GRAY);
cv::GaussianBlur(gray, gray, cv::Size(5, 5), 1.2);
cv::Canny(gray, edges, 80, 160);
cv::Mat result = edges.getMat(cv::ACCESS_READ); // 只在最终边界下载

CUDA 使用 cv::cuda::GpuMat，但从 OpenCV 4.0 起，很多 CUDA 加速算法位于 opencv_contrib 的 CUDA 模块中。构建需 NVIDIA CUDA Toolkit、匹配编译器、WITH_CUDA=ON，并通过 OPENCV_EXTRA_MODULES_PATH 同时构建 contrib。DNN CUDA 还涉及 OPENCV_DNN_CUDA、cuDNN、cuBLAS。GpuMat.upload() 和 download() 是明确搬运边界；每个小算子都上传下载通常更慢。

Vulkan 在 OpenCV 构建选项中属于可选且实验性的异构后端能力，需 WITH_VULKAN，并依赖平台驱动、Vulkan headers/loader 和具体模块支持。不能把“打开 Vulkan”理解成“所有 imgproc 自动走 Vulkan”。OpenCV 5 主线以当前源码和官方构建说明为准；4.12 以 getBuildInformation() 实际启用项为准。

加速后端的判断原则：计算量大、数据能常驻设备、批量足够、同步少，才值得上设备；小图、小核、频繁 CPU 访问、复杂分支和大量 codec/GUI 边界，往往 CPU 更稳。

8.6 图像与视频流水线并行

视频系统常见瓶颈不是某个算子，而是流水线：采集或解码、预处理、推理或分析、绘制、编码、显示、写盘。把每帧串行处理会让最慢阶段决定吞吐。工程中可用有界队列拆成多阶段：

capture/decode -> preprocess -> analyze -> render/encode -> sink

队列必须有界，否则短时阻塞会积压内存并增加延迟。实时摄像头通常丢旧帧，离线转码通常阻塞等待。多线程版本要记录端到端延迟、每阶段耗时、队列长度和丢帧数；只看 FPS 会掩盖延迟爆炸。服务端部署通常不要依赖 HighGUI。

视频 I/O 要分清 OpenCV API 与实际 backend。VideoCapture/VideoWriter 可能走 FFmpeg、GStreamer、MSMF、AVFoundation、V4L2 等。同一 FourCC 在不同平台不一定可用；编码参数可能被 backend 忽略。排查时先打印 backend、帧宽高、FPS、FourCC 和第一帧形状。

8.7 Build Information、CMake、contrib 与部署

cv::getBuildInformation() 是排障入口。它能回答 OpenCV 版本、编译器、C++ 标准、构建类型、CPU dispatch、并行框架、OpenCL、CUDA、Vulkan、JPEG/PNG/TIFF/WebP/OpenEXR、FFmpeg/GStreamer、GUI backend、Python 绑定、安装路径和模块列表。生产程序启动时建议保存精简构建信息。

常用 CMake 构建思路：

cmake -S ../opencv -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CXX_STANDARD=17 \
  -DBUILD_TESTS=OFF \
  -DBUILD_PERF_TESTS=OFF \
  -DBUILD_EXAMPLES=OFF \
  -DWITH_OPENCL=ON \
  -DWITH_VULKAN=ON \
  -DOPENCV_EXTRA_MODULES_PATH=../opencv_contrib/modules
cmake --build build --config Release --parallel
cmake --install build

CUDA 构建需额外明确 WITH_CUDA=ON，并按显卡设置架构参数。包装发行时建议启用 ENABLE_CONFIG_VERIFICATION=ON，避免 CMake 静默找不到依赖后关掉功能。contrib 必须与 OpenCV 主仓库版本匹配；OpenCV 5 主线变化更快，最终以源码分支、构建日志和 build information 为准。

部署时要控制 ABI。C++ 要确认编译器、标准库、运行时库、Debug/Release、OpenCV 动态库路径一致；Python 要确认 cv2.__file__ 指向预期环境，避免系统包、conda、pip wheel 和自编译版本混用。容器要纳入 codec、GPU runtime、OpenCL ICD、Vulkan loader、字体、设备权限和动态库路径。日志至少保留输入、参数、随机种子、OpenCV 版本、构建摘要和异常栈。

8.8 优化决策树

问题：程序慢
|
+-- 无可重复基准：固定输入、预热、多次重复、记录 build information
|
+-- 慢在 I/O 吗？
|   +-- imread/video/decode/write/display 占主导：换 codec/backend、缓存、异步 I/O、减少显示和写盘
|
+-- 慢在 Python 循环吗？
|   +-- 是：改 OpenCV/NumPy 向量化，或移到 C++/Cython/Numba
|
+-- 慢在复制/转换吗？
|   +-- 是：减少 copy/clone/astype/cvtColor，复用 ROI，预分配 dst，把格式转换放到边界
|
+-- 慢在内存带宽吗？
|   +-- 是：检查连续内存、步长、缓存局部性、数据类型、融合简单 pass
|
+-- 慢在计算吗？
|   +-- 是：换算法、降分辨率/频率、用 separable/filter pyramid、启用线程/SIMD
|
+-- 慢在同步吗？
    +-- 是：减少锁、日志、GPU download、跨线程等待；重构流水线和队列

GPU/OpenCL/CUDA 子决策：轻量算子且立即回 CPU，优先 CPU；多个重计算算子、数据能留在设备、硬件和构建满足，再测 UMat 或 GpuMat。后端切换必须用端到端指标证明。

8.10 生产检查表

发布前确认：版本和 getBuildInformation() 摘要已记录；Release 构建、CPU dispatch、并行框架、OpenCL/CUDA/Vulkan、codec、GUI/backend 与需求一致；输入路径、权限、格式、尺寸、通道、dtype、颜色空间都有断言；固定样本能区分 I/O、计算、复制、同步，并记录平均值、P95/P99 和端到端延迟；无无界队列，热路径不反复分配大缓冲；线程数可配置，退出能释放相机、窗口和编码器；加速能力都有编译条件、硬件条件和回退路径；动态库路径、Python 环境、容器权限、GPU runtime、OpenCL ICD、Vulkan loader、字体和 locale 可复现；异常日志包含输入、阶段、尺寸、dtype、backend、版本和参数；升级后能跑 smoke test。

8.11 系统化排障流程

排障按“最小复现、分层隔离、替换变量”推进。第一步写 20 行以内脚本，只保留失败 API 和一张输入图；第二步打印版本、构建信息、路径、shape、dtype、min/max；第三步替换输入、换绝对路径、换 backend、关 GPU 或关多线程；第四步在干净环境中重装或自编译；第五步才怀疑 OpenCV bug，并准备源码版本、构建参数、最小输入和完整日志。

性能排障也一样：先把读帧、算法、显示、写盘拆开计时；再把复制、转换、上传下载单独计时；最后再优化。不要在一个大循环里同时改算法、线程、GPU 和 codec，否则无法解释收益。优化要保留回退开关，例如 --threads 1、--disable-opencl、--backend cpu、--no-display。

8.12 练习

  1. 用 Python 实现逐像素阈值、NumPy 阈值和 cv.threshold，在 640x480、1080p、4K 上记录耗时并解释瓶颈。
  2. 用 TickMeter 比较 GaussianBlur、medianBlur、bilateralFilter 在不同核大小下的曲线。
  3. 对视频建立读取、预处理、分析、显示/写盘四阶段计时；加入有界队列后比较吞吐、延迟和队列长度。
  4. 构造 ROI 非连续内存示例，对比错误线性遍历和按行 ptr 遍历。
  5. 在支持 OpenCL 的机器上比较 Mat 与 UMat：每步下载、最后下载、全 CPU。
  6. 自编译 OpenCV 4.12 或 5 主线，开启 OPENCV_EXTRA_MODULES_PATH，保存 CMake、build information 和最小程序日志。
  7. 制造 BGR/RGB 错误、uint8 溢出、VideoWriter 尺寸不一致，并写检测断言和修复代码。
