# 工具权限控制与可靠性

## 1. 权限控制的基本边界

工具调用链建议分成四层：

```text
模型提出调用
  ↓
Schema 校验：参数形状是否正确
  ↓
策略校验：用户、租户、资源、风险和额度是否允许
  ↓
执行器：以受限身份调用真实系统
```

模型不能决定自己的权限，也不能通过参数传入 `user_id`、数据库连接或内部路径来扩大权限。调用上下文中的身份应由服务端会话、认证令牌和租户信息注入。

## 2. 最小权限设计

- 工具注册表使用显式白名单，不根据字符串动态导入函数；
- 区分只读工具和有副作用工具；
- 为不同 Agent、用户、租户配置不同能力集合；
- 工具本身再次做资源级鉴权，不能只依赖上游；
- 限制网络出口、文件系统目录、数据库操作和返回字段；
- 密钥放在密钥管理系统或服务端配置中，不放入 Prompt、日志和模型可见结果；
- 高风险工具默认关闭，必须有审批或明确授权。

## 3. 参数验证不只是 JSON Schema

建议采用分层校验：

1. JSON 解析：确认参数是合法 JSON；
2. Schema：类型、必填字段、枚举、长度和额外字段；
3. 业务规则：订单属于当前用户、金额不超过可退款金额、日期范围合法；
4. 权限规则：当前身份能否对这个资源执行该动作；
5. 风险规则：是否需要二次确认、频率限制或人工审批。

例如，`order_id` 是合法字符串，并不代表它属于当前用户；`amount` 是合法数字，也不代表允许扣款。

## 4. 通过策略对象集中控制

```python
class Policy:
    def authorize(self, *, principal, tool_name, args, state):
        if tool_name not in principal.allowed_tools:
            raise PermissionError("tool_not_allowed")
        if tool_name == "create_refund":
            if not state.get("approval", {}).get("approved"):
                raise PermissionError("approval_required")
            if args["amount"] > state["order"]["refundable_amount"]:
                raise PermissionError("amount_exceeds_limit")
        return True
```

错误消息对用户可以友好，但内部日志仍应包含可关联的错误类型和请求 ID。不要返回 SQL、内部路径、令牌或供应商密钥。

## 5. 超时预算

超时至少分为：

- 连接超时：建立连接的最长时间；
- 读取超时：等待上游数据的最长时间；
- 工具超时：单个工具允许执行多久；
- 节点超时：一个 Agent 节点允许多久；
- 任务超时：整个任务的截止时间。

应把截止时间放入任务上下文，子调用不能自行把总预算延长：

```python
def remaining_seconds(deadline):
    return max(0, deadline - monotonic())

result = invoke_tool(
    name,
    args,
    timeout=min(TOOL_LIMIT, remaining_seconds(task_deadline)),
)
```

超时后要取消上游请求、释放连接和清理临时资源；对于无法确认是否成功的副作用操作，应先查询状态，再决定是否重试。

## 6. 重试策略

重试前先回答三个问题：

1. 这是临时错误还是确定性错误？
2. 操作是否幂等？
3. 即使重复执行，业务结果和用户体验是否可接受？

通常：

- 参数错误、权限拒绝、业务规则拒绝：不应盲目重试；
- 网络抖动、服务暂时不可用、限流：可有限次数重试；
- 创建订单、扣款、发货：必须使用幂等键，并最好查询最终状态；
- 重试应有指数退避、随机抖动、最大次数和总截止时间。

```python
for attempt in range(max_attempts):
    try:
        return call(idempotency_key=task_id, timeout=remaining())
    except TemporaryError:
        if attempt == max_attempts - 1:
            raise
        sleep(backoff_with_jitter(attempt))
```

## 7. 补偿与 Saga

分布式任务往往无法真正回滚。可以为每个已完成的副作用定义补偿动作：

```text
预留库存 → 创建支付 → 创建发货
    ↑          ↑           ↑
释放库存 ← 退款/撤销 ← 取消发货
```

补偿不是一定成功，因此也需要权限、幂等、重试和人工兜底。补偿操作不能被模型随意选择，应由业务代码根据状态决定。

## 8. 日志、Trace 与审计

建议每次任务生成：`trace_id`、`task_id`、`run_id`、`step_id`、`tool_call_id` 和 `attempt`。结构化事件至少记录：

```json
{
  "event": "tool_finished",
  "trace_id": "tr_001",
  "task_id": "task_001",
  "step_id": "check_order",
  "tool_name": "get_order_status",
  "duration_ms": 184,
  "result": "success",
  "attempt": 1
}
```

应分别区分：

- 普通运行日志：用于诊断；
- 安全审计日志：谁在何时批准或执行了什么；
- 指标：成功率、延迟、重试率、工具错误率、Token 和费用；
- 模型追踪：模型、版本、提示模板版本和响应元数据。

日志要脱敏、限制访问并设置保留期限。不要默认记录完整 Prompt、完整工具参数或完整用户资料。

## 9. 安全检查清单

- [ ] 工具名称来自白名单。
- [ ] 参数经过解析、Schema 和业务校验。
- [ ] 用户、租户和资源权限由应用验证。
- [ ] 高风险动作有审批、额度和幂等键。
- [ ] 工具结果被当作不可信数据处理。
- [ ] 每轮有步数、Token、费用和耗时预算。
- [ ] 超时会取消上游并释放资源。
- [ ] 重试只作用于允许重试的错误。
- [ ] 状态和审计记录可关联、可恢复、可脱敏。
