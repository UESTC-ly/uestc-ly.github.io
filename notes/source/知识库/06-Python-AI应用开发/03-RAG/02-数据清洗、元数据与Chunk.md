# 数据清洗、元数据与 Chunk

> 上一节：[[01-数据接入与文档解析]]｜导航：[[00-RAG学习路线]]｜下一节：[[03-Embedding与向量检索]]

## 1. 本节目标

完成文档进入 RAG 检索链路前的准备工作：

- 建立可重复、可回溯的数据清洗流水线；
- 在不破坏语义的前提下去除格式噪声；
- 设计支持过滤、权限、溯源、更新和调试的元数据；
- 理解固定长度、递归、语义和父子块等 Chunk 策略；
- 通过离线评测选择 Chunk 参数，而不是只凭经验；
- 能够区分解析、清洗、分块、Embedding 和检索环节造成的失败。

---

## 2. 从原始文档到可检索 Chunk

数据清洗、元数据补充和切分不应当是互相独立的一组脚本，而应当组成一个有版本、有日志、可重复执行的流水线：

```text
原始文档
  ↓
格式统一与文本清洗
  ↓
结构识别（标题、段落、表格、代码块、列表）
  ↓
元数据补充与权限继承
  ↓
按结构切分 Chunk
  ↓
Chunk 质量校验
  ↓
Embedding / 全文索引
  ↓
向量库与原始文档版本记录
```

每个阶段都应尽量满足以下要求：

1. **确定性**：相同输入、规则和版本应产生相同结果；
2. **可追溯**：Chunk 能够定位到原始文档、页码、章节和原文位置；
3. **可观测**：记录文档数、Chunk 数、平均长度、异常数和失败原因；
4. **可增量更新**：文档变化时只重处理受影响的文档或章节；
5. **可回滚**：保留原始文件、清洗规则版本和索引版本，避免错误清洗后无法恢复。

### 2.1 原始文档与检索块分离

建议在流水线内部明确区分原始文档和检索块：

- **Document**：代表一份完整来源，保存原始内容、来源地址、版本和整体元数据；
- **Chunk**：代表实际参与 Embedding、召回和重排的最小检索单元。

```python
from dataclasses import dataclass, field
from typing import Any


@dataclass
class Document:
    doc_id: str
    text: str
    metadata: dict[str, Any] = field(default_factory=dict)


@dataclass
class Chunk:
    chunk_id: str
    text: str
    metadata: dict[str, Any] = field(default_factory=dict)
```

一个 Chunk 至少要能够回答这些问题：

- 来自哪一份原始文档？
- 位于哪个章节、页码或段落？
- 在原文中的顺序是什么？
- 使用了哪一种切分策略和参数？
- 由哪一个清洗规则、Pipeline 版本生成？
- 是否继承了文档级权限和租户信息？

## 3. 数据清洗

### 3.1 清洗的基本原则

清洗的目标不是把文本变得“越干净越好”，而是在**保留语义和结构**的前提下，去除会干扰检索的噪声。

应重点遵循以下原则：

- 保留标题、列表编号、字段名、单位、否定词、错误码和版本号；
- 保留段落边界、表格关系、代码块边界以及问答顺序；
- 对明显的 OCR 错误进行修复，但必须保留原文备份；
- 清洗规则应当显式、可测试，避免在一个函数中混入大量不可解释的替换；
- 清洗前后都记录内容哈希，便于判断变化范围和排查误删；
- 对 HTML、Markdown、PDF、表格、代码和对话记录使用不同的处理策略。

### 3.2 常见清洗任务

| 清洗任务 | 处理建议 | 主要风险 |
|---|---|---|
| 换行与空白 | 统一换行符，去除行尾空格，合并过多空行 | 误删段落边界 |
| 特殊字符 | 处理不间断空格、不可见字符和异常控制字符 | 破坏代码或公式 |
| 页眉页脚 | 统计跨页重复行，并结合位置判断是否为模板噪声 | 删除正文中同名内容 |
| OCR 错误 | 仅修复高置信度错误，保留原文和修复记录 | 改变专有名词、数字 |
| 重复内容 | 使用文档哈希和段落指纹检测完全重复、近重复内容 | 删除有意重复的定义 |
| 敏感信息 | 按业务要求脱敏或隔离，并记录处理策略 | 影响审计与权限控制 |
| HTML/Markdown | 去除展示性标签，保留标题、链接、列表和代码语义 | 丢失结构信息 |
| 表格 | 保留表头与行列关系，必要时转换为结构化文本 | 表格线性化后歧义 |

### 3.3 低风险文本规范化

下面的函数只做低风险规范化，不负责 OCR 纠错、页眉页脚识别或敏感信息脱敏：

```python
import re


def normalize_text(text: str) -> str:
    """进行低风险文本规范化，不改变主要语义。"""
    text = text.replace("\r\n", "\n").replace("\r", "\n")
    text = text.replace("\u00a0", " ")  # 不间断空格
    text = text.replace("\u200b", "")   # 零宽空格
    text = re.sub(r"[ \t]+\n", "\n", text)
    text = re.sub(r"\n{3,}", "\n\n", text)
    return text.strip()
```

这类函数应配合单元测试使用。测试样例至少包括：空字符串、中文文本、英文文本、混合换行、代码块、表格和包含连续空格的内容。

### 3.4 页眉、页脚与重复内容

不能简单地删除所有重复行，因为正文中的警告、章节名和表格表头也可能在多页重复。更稳妥的流程是：

1. 按页或文本块收集行及其出现位置；
2. 统计每一行的跨页频率、垂直位置和字体/样式信息；
3. 将高频且总位于页首或页尾的内容标记为候选噪声；
4. 在少量样本上人工核验后再应用删除规则；
5. 保存删除行、所在页码和规则版本，支持回溯。

对于重复文档，可以先计算规范化后的 `content_hash`；对于只修改少量内容的文档，可以进一步使用段落级指纹或 MinHash 检测近重复段落。删除重复内容前，应确认重复是否会影响权限、版本或上下文。

### 3.5 敏感信息与权限

脱敏不能替代权限控制。两者应分别处理：

- **权限控制**决定用户是否可以检索到某个文档或 Chunk；
- **脱敏处理**决定文本中是否保留手机号、邮箱、身份证号、密钥等敏感内容。

实际项目中应记录：脱敏规则版本、命中的类型、处理数量以及是否保留可审计的原文引用。API Key、密码和令牌不应写入 Chunk、日志或项目笔记。

## 4. 结构识别：先识别结构，再进行切分

直接按字符数切分容易破坏标题与正文、问题与答案、代码与解释之间的关系。更可靠的顺序是：

```text
识别文档结构 → 形成语义单元 → 在语义单元内部控制长度
```

常见结构单元包括：

- 标题及其层级路径；
- 段落、列表和引用；
- 表格及其表头；
- 代码块及编程语言；
- FAQ 的问题—答案对；
- 对话记录中的角色、时间和消息顺序。

以 Markdown 为例：

```markdown
# 产品文档
## 安装
### Linux
安装命令……
### Windows
安装步骤……
## 配置
配置参数……
```

切分后应将标题路径写入元数据，或者拼接到 Chunk 文本前面：

```text
文档标题：产品文档
章节路径：安装 > Linux

安装命令……
```

标题路径能够弥补正文片段脱离上下文的问题，尤其适合“如何配置某个参数”“某个错误码是什么意思”等问题。

## 5. 元数据设计

### 5.1 推荐字段

| 类别 | 推荐字段 | 作用 |
|---|---|---|
| 唯一标识 | `document_id`、`chunk_id` | 稳定定位和增量更新 |
| 来源 | `source_type`、`source_uri`、`source_name` | 展示引用和回溯来源 |
| 内容版本 | `version`、`content_hash` | 判断内容是否变化 |
| 结构 | `title`、`section_path`、`heading_level` | 过滤、展示和补充上下文 |
| 位置 | `page_number`、`start_offset`、`end_offset` | 定位原文和生成引用 |
| 顺序 | `chunk_index`、`previous_chunk_id`、`next_chunk_id` | 恢复相邻上下文 |
| 切分 | `chunk_strategy`、`chunk_size`、`overlap` | 实验对比和问题排查 |
| 时间 | `created_at`、`updated_at`、`indexed_at` | 增量同步和时效过滤 |
| 权限 | `tenant_id`、`owner_id`、`acl` | 租户隔离和访问控制 |
| 流水线 | `cleaning_version`、`pipeline_version` | 复现处理结果 |
| 关联 | `parent_chunk_id`、`document_id` | 父子块扩展和文档聚合 |

示例：

```python
metadata = {
    "document_id": "manual-001",
    "source_type": "markdown",
    "source_uri": "docs/manual.md",
    "title": "产品使用手册",
    "section_path": ["安装与配置", "Linux"],
    "page_number": 3,
    "start_offset": 1200,
    "end_offset": 1850,
    "chunk_index": 5,
    "chunk_strategy": "recursive",
    "chunk_size": 800,
    "overlap": 120,
    "content_hash": "sha256:...",
    "pipeline_version": "2025-01",
    "tenant_id": "tenant-a",
}
```

### 5.2 ID、版本和增量更新

`document_id` 应保持稳定。同一份文档重新处理时，不要因为重新运行程序就随机生成新的文档 ID。`chunk_id` 可以由以下信息组合生成：

```text
document_id + 内容版本 + 结构路径 + 块序号 + 切分策略版本
```

需要注意：如果 Chunk ID 完全依赖块序号，前文插入一段文字可能导致后续所有块的 ID 改变。对更新频繁的文档，可以结合稳定的章节 ID、内容哈希或段落标识，减少无意义的索引重建。

增量处理通常可按以下顺序执行：

1. 读取来源的最新版本和更新时间；
2. 比较文档级 `content_hash`；
3. 未变化的文档直接复用已有索引；
4. 发生变化的文档重新解析、清洗和切分；
5. 删除旧版本失效的 Chunk，写入新版本 Chunk；
6. 更新索引记录，并保留处理日志。

## 6. Chunk 策略

Chunk 没有适用于所有数据集的固定最佳大小。它需要在以下因素之间平衡：

- 内容是否自洽；
- 问题中的关键词是否能与 Chunk 同时出现；
- 召回后是否包含足够上下文；
- Chunk 数量、Embedding 成本和索引大小；
- 上下文窗口、重排模型和生成模型的限制。

### 6.1 固定长度 Chunk

按字符数、Token 数或其他长度单位直接切分，通常还会设置重叠区间。

**优点**：实现简单、速度快、长度容易控制。  
**缺点**：可能截断句子、标题、表格、代码和问答关系。  
**适用场景**：结构较弱、文本格式统一、需要快速建立基线的语料。

实验时应明确记录：

- 长度单位是字符、词还是 Token；
- Chunk 大小；
- Overlap 长度或比例；
- 是否在句子边界处优先截断；
- 超长表格、代码块和链接的处理方式。

### 6.2 递归 Chunk

准备一组从强到弱的分隔符，先按章节或段落切分；如果片段仍然过长，再退化到句子、空格或字符级别。

```python
from collections.abc import Sequence


def split_by_separators(
    text: str,
    max_chars: int = 800,
    separators: Sequence[str] = ("\n\n", "\n", "。", "！", "？", "；", " "),
) -> list[str]:
    text = text.strip()
    if not text:
        return []
    if len(text) <= max_chars:
        return [text]

    for separator in separators:
        parts = [part.strip() for part in text.split(separator) if part.strip()]
        if len(parts) <= 1:
            continue

        result: list[str] = []
        current = ""
        for part in parts:
            candidate = f"{current}{separator}{part}" if current else part
            if len(candidate) <= max_chars:
                current = candidate
            else:
                if current:
                    result.append(current)
                current = part

        if current:
            result.append(current)

        # 某个分隔符已经能够形成多个片段；超长片段继续递归处理。
        expanded: list[str] = []
        for part in result:
            expanded.extend(split_by_separators(part, max_chars, separators[1:]))
        return expanded

    # 没有可用分隔符时才进行最后的硬截断。
    return [text[i : i + max_chars] for i in range(0, len(text), max_chars)]
```

递归切分通常比纯固定长度更能保留结构，但仍需处理：

- 标题是否附加到每个子块；
- 单个段落超过上限时如何继续切分；
- 中英文标点和代码语言的分隔符；
- 是否需要在段落之间增加 Overlap。

### 6.3 语义 Chunk

语义切分尝试在主题发生明显变化的位置切开。常见做法是：

1. 先按段落或句子拆分；
2. 为相邻句子或段落计算 Embedding；
3. 比较相邻单元的相似度或距离；
4. 在距离突增处设置边界；
5. 再用最小、最大长度约束修正结果。

**优点**：更可能形成主题完整的块。  
**缺点**：需要额外计算 Embedding，阈值对数据集敏感，结果可能不够稳定。  
**适用场景**：段落结构不可靠、主题切换明显、对语义完整性要求较高的资料。

语义边界不应完全取代长度约束。过大的“语义完整块”仍可能导致召回噪声、重排困难或超出上下文预算。

### 6.4 父子块 Chunk

父子块策略将“召回”和“提供上下文”分开：

- **子块**较小，适合精确匹配和向量召回；
- **父块**较大，包含更完整的章节或段落；
- 召回子块后，通过 `parent_chunk_id` 找回父块，再将父块或其摘要交给生成模型。

这种方法需要明确：

- 一个父块包含哪些子块；
- 多个子块命中同一个父块时如何去重；
- 父块过大时是否再次裁剪或压缩；
- 引用应指向子块、父块还是原文页码；
- 父块扩展是否会引入其他权限范围的内容。

父子块不是“无限扩大上下文”。如果父块包含多个无关主题，召回精度仍可能下降。

### 6.5 特殊内容的切分

| 内容类型 | 建议 |
|---|---|
| 表格 | 保留表头；将每行转换为带字段名的文本，或单独建立结构化检索字段 |
| 代码 | 尽量按函数、类、配置块或完整示例切分，保存语言和文件路径 |
| 对话 | 保留角色、时间和消息顺序，避免把问题与答案拆开 |
| FAQ | 优先将问题与答案作为一个语义单元，并将问题改写或扩展为检索文本 |
| 法律/制度文本 | 保留条款编号、章节路径、适用范围和例外条件 |
| 日志 | 保留时间、服务、级别、请求 ID 等字段，必要时按事件聚合 |

## 7. Overlap 如何影响系统

Overlap 用于缓解边界截断：前一个 Chunk 的末尾内容会重复出现在后一个 Chunk 的开头。

**可能的收益**：

- 提高跨边界事实被完整召回的概率；
- 让句子或定义在切分边界附近不至于完全断开。

**可能的代价**：

- Chunk 数量和 Embedding 成本上升；
- 相邻块内容重复，增加检索结果冗余；
- 生成上下文中出现重复内容；
- 在固定长度切分中，Overlap 过大可能掩盖糟糕的边界策略。

因此，Overlap 不应孤立调参。应同时观察：召回率、重复率、索引规模、平均上下文长度和最终回答质量。结构化递归切分通常可以使用较小的 Overlap；边界不稳定或句子较长的语料才需要更大重叠。

## 8. Chunk 质量校验

写入向量库前，至少执行以下检查：

- 文本是否为空或只包含标点、页码和导航词；
- 是否存在异常短块、异常长块和超出 Token 上限的块；
- 标题路径、来源 URI、文档 ID 和版本是否完整；
- `chunk_index` 是否连续，前后块关系是否一致；
- 权限字段是否继承正确，是否出现跨租户内容；
- 表格、代码块和 Markdown 标记是否被意外截断；
- 同一文档内是否存在高度重复的 Chunk；
- 清洗后的文本是否还能定位回原始文档。

可以把质量检查结果作为独立报告保存，而不是只在控制台打印。例如：

```python
def validate_chunk(chunk: Chunk, max_chars: int = 2_000) -> list[str]:
    errors: list[str] = []

    if not chunk.text.strip():
        errors.append("empty_text")
    if len(chunk.text) > max_chars:
        errors.append("too_long")
    if not chunk.metadata.get("document_id"):
        errors.append("missing_document_id")
    if not chunk.metadata.get("source_uri"):
        errors.append("missing_source_uri")
    if "chunk_index" not in chunk.metadata:
        errors.append("missing_chunk_index")

    return errors
```

校验函数不应只检查字段是否存在，还应在业务层检查字段的值是否相互一致。例如 `parent_chunk_id` 是否确实属于同一文档，`page_number` 是否在有效范围内，`tenant_id` 是否与权限记录匹配。

## 9. 评测与失败定位

### 9.1 离线评测集

准备一组带有标准答案或标准来源的查询，至少包含：

- 直接事实查询；
- 需要章节上下文的查询；
- 同义改写和口语化查询；
- 表格、代码和错误码查询；
- 权限边界查询；
- 文档不存在或资料不足的查询。

对每个问题记录期望命中的文档或 Chunk，并观察：

- **Recall@K**：前 K 个结果是否包含正确来源；
- **MRR**：正确结果是否排在靠前位置；
- **上下文精确度**：召回内容中无关文本的比例；
- **回答正确性**：生成答案是否得到问题要求的事实；
- **引用准确性**：答案是否引用了真正支持结论的来源。

### 9.2 失败定位表

| 现象 | 优先排查 |
|---|---|
| 原文中有内容，但索引中找不到 | 解析、清洗、过滤、权限和索引写入 |
| 能找到文档，但找不到关键段落 | Chunk 边界、标题路径、Overlap 和元数据 |
| 命中结果相关，但答案缺少条件 | 父子上下文、上下文排序和重排 |
| 召回很多重复内容 | Overlap、重复文档、去重和相邻块合并 |
| 只对精确关键词有效 | Embedding、查询改写、同义表达和全文检索融合 |
| 结果跨租户或超出权限 | 元数据继承、过滤时机和权限校验 |
| 旧内容仍被回答 | 版本、删除标记、索引刷新和缓存 |
| 表格或代码回答错误 | 专用解析、结构化字段和内容切分 |

排查时应保存一条完整链路：用户问题 → 查询改写 → 检索条件 → 命中的 Chunk ID → 重排结果 → 最终上下文 → 生成答案。只看最终回答，通常无法判断问题到底来自哪一层。

## 11. 常见误区

### 11.1 Chunk 越大越好

不是。Chunk 过小会丢失上下文，过大会引入无关内容并降低检索精度。应根据问题类型、文档结构、重排能力和上下文预算共同评估。

### 11.2 只调整 Chunk 大小，不检查解析质量

如果 PDF 表格已经错位、标题已经丢失、页眉仍大量混入正文，调节 Chunk 大小通常不能解决根本问题。

### 11.3 把所有格式都当作普通文本

代码、表格、对话和制度条款有不同的语义结构。统一按字符切分虽然方便，但经常会破坏最重要的关联关系。

### 11.4 只保存向量，不保存来源和版本

没有来源 URI、页码、章节和版本，就难以生成可信引用，也难以处理文档更新、删除和用户投诉。

### 11.5 用脱敏代替权限过滤

脱敏只能减少文本中的敏感信息，不能防止用户检索到其无权访问的普通内容。权限过滤应在召回前或检索过程中强制执行，并在返回前再次校验。

## 13. 本节小结

数据清洗的核心不是简单删除字符，而是让文本在保持语义和结构的同时变得更适合检索。元数据决定了系统能否过滤、引用、更新和排查问题；Chunk 策略决定了信息以什么粒度进入召回链路。

一条稳妥的实践路径是：先以递归切分建立保留结构的基线，再根据评测结果比较固定长度、语义切分和父子块；同时持续记录来源、版本、权限和处理日志。这样才能把“检索效果不好”从模糊问题拆解为可验证的工程问题。
