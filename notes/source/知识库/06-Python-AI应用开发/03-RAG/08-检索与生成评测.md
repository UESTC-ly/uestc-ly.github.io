# 检索与生成评测

> 上一节：[文档权限与多租户隔离](./07-文档权限与多租户隔离.md)｜导航：[RAG 学习路线](./00-RAG学习路线.md)｜下一节：[增量更新、删除与索引一致性](./09-增量更新、删除与索引一致性.md)

## 1. 本节定位

RAG 系统的评测不能只看“最终答案像不像正确答案”。一次问答通常要经过查询理解、召回、重排、上下文压缩、提示词组装和答案生成多个环节；最终答案出错时，原因可能是：

- 相关文档根本没有被召回；
- 召回结果中有证据，但排序太靠后或被截断；
- 上下文包含互相冲突、重复或无关的片段；
- 模型看到了证据，却没有正确使用证据；
- 答案引用了不存在于上下文中的内容；
- 权限、版本或索引状态导致系统使用了不应使用的证据。

因此，评测的基本原则是：**拆开链路分别测，再用端到端指标验证整体效果；同时记录质量、延迟、成本和安全性。**

---

## 2. 评测目标与问题分解

建议先明确本次评测要回答的问题，而不是直接选择一个指标：

| 评测问题 | 主要对象 | 典型指标或方法 |
| --- | --- | --- |
| 相关证据能否被找到？ | 检索器 | Recall@K、Precision@K、Hit@K、MRR、nDCG |
| 排名靠前的内容是否最有用？ | 重排器与结果融合 | Precision@K、MRR、nDCG、位置敏感人工检查 |
| 提供给模型的上下文是否足够且干净？ | 上下文构造 | 证据覆盖率、冗余率、上下文有效率、冲突率 |
| 答案是否回答了问题？ | 生成器 | Answer Relevance、完整性、任务指标、人工评分 |
| 答案是否有证据支持？ | 生成器与引用 | Faithfulness、Citation Precision、Citation Recall |
| 系统是否稳定、经济、安全？ | 端到端系统 | 延迟、Token、费用、失败率、越权率、拒答正确率 |

同一指标也要明确统计范围。例如，Recall@5 可以按问题平均，也可以按文档类型、租户、难度、语言或权限场景分组统计；只看一个总体平均值，容易掩盖某类用户或某类文档的严重退化。

## 3. 构造评测集

### 3.1 推荐字段

一个可复现的 RAG 评测集，至少应保存问题、标准证据和参考答案，而不是只保存问题与答案：

```text
case_id                 用例唯一标识
question                用户问题
question_type           事实查询、比较、总结、流程、计算、拒答等
expected_answer         参考答案或关键事实
relevant_doc_ids        相关文档标识
relevant_chunk_ids      相关片段标识
required_facts          答案必须包含的事实
forbidden_facts         不应出现的事实或越权信息
citation_requirements   是否必须引用，以及引用粒度
allowed_scope           用户、租户、角色和时间范围
corpus_version          文档库或索引版本
metadata                难度、语言、领域、来源等标签
```

其中 `relevant_chunk_ids` 和 `required_facts` 尤其重要。只保存参考答案，无法判断检索阶段是否找到正确证据；只保存相关文档，又无法判断答案是否遗漏了关键事实。

### 3.2 用例来源

评测集可以组合以下几类样本：

1. **真实日志脱敏样本**：最能反映真实分布，但要先移除个人信息、密钥和业务机密。
2. **专家编写样本**：覆盖高价值、低频和容易出错的问题。
3. **模板生成样本**：适合批量覆盖实体、日期、版本和过滤条件，但必须人工抽检。
4. **对抗样本**：包括相似文档、旧版本文档、冲突信息、跨租户请求和无答案问题。
5. **回归样本**：过去发生过的线上错误，每次索引、模型或提示词变更后都应重复测试。

评测集应划分为开发集、验证集和最终测试集。最终测试集不应被反复用于调参，否则分数会逐渐反映“对测试题的适应”，而不是系统的泛化能力。

### 3.3 问题类型覆盖

至少应覆盖：

- 单跳事实查询：答案集中在一个片段中；
- 多跳问题：需要连接多个文档或多个片段；
- 条件过滤：带有时间、组织、版本、地域等约束；
- 比较与总结：需要综合多个来源，并处理差异；
- 无答案问题：知识库没有足够证据时应正确说明不知道；
- 冲突问题：新旧版本或不同来源给出不一致信息；
- 权限问题：相关内容存在，但当前用户无权访问；
- 长上下文问题：证据位于较长上下文的中间或末尾；
- 多语言、表格和代码问题：检验解析与分块质量。

## 4. 检索阶段评测

### 4.1 基本指标

设问题 $q$ 的标注相关片段集合为 $G_q$，系统返回前 $k$ 个片段的集合为 $R_{q,k}$。

**召回率**衡量相关证据有多少被找回：

$$
Recall@k = \frac{|G_q \cap R_{q,k}|}{|G_q|}
$$

**准确率**衡量返回结果中有多少相关内容：

$$
Precision@k = \frac{|G_q \cap R_{q,k}|}{|R_{q,k}|}
$$

当只关心“前 $k$ 个结果中是否至少出现一个相关片段”时，可以使用 Hit@k：

$$
Hit@k = \mathbb{1}(|G_q \cap R_{q,k}| > 0)
$$

对于排序质量，MRR 关注第一个相关结果出现的位置：

$$
MRR = \frac{1}{N}\sum_{i=1}^{N}\frac{1}{rank_i}
$$

其中 $rank_i$ 是第 $i$ 个问题的第一个相关结果排名；没有相关结果时，该项记为 $0$。

nDCG 会根据相关性等级和位置进行折损，适合“高度相关、部分相关、不相关”这种多级标注场景。工程上不要只追求 Recall@k：盲目提高召回量可能把大量噪声带入上下文，反而降低答案质量和增加成本。

### 4.2 按链路拆分检索评测

应分别比较：

- 关键词检索的结果；
- 向量检索的结果；
- 混合召回的结果；
- Rerank 前的候选集；
- Rerank 后最终交给生成模型的结果。

例如，混合召回的 Recall@20 提升，但最终上下文的 Recall@5 没有提升，可能说明候选集虽然扩大了，重排器没有把正确证据推到前面。此时应该检查融合算法、重排模型、元数据过滤和截断策略，而不是继续增大上下文窗口。

### 4.3 评测过滤条件与权限

检索指标必须在真实过滤条件下测量。对某个用户来说，“全库相关文档”不一定是合法候选；正确的评测基准应先应用租户、用户、角色、文档状态和版本约束，再判断相关证据是否可被召回。

对于无权限问题，还要单独统计：

- 越权文档是否出现在候选结果、上下文、缓存或引用中；
- 系统是否正确拒答，而不是泄露文档存在性；
- 权限变更或文档删除后，旧索引是否仍可召回内容。

安全指标不能用平均问答质量替代。一次越权泄露应作为高严重度错误单独阻断发布。

## 5. 上下文构造评测

检索结果正确，不代表最终上下文正确。需要检查从候选结果到提示词之间发生了什么。

### 5.1 证据覆盖率

可以统计答案所需事实中，有多少能够在最终上下文中找到：

$$
EvidenceCoverage = \frac{|F_{required} \cap F_{context}|}{|F_{required}|}
$$

该指标帮助区分两类错误：上下文缺少关键事实，或上下文已有事实但模型没有使用。

### 5.2 噪声与冗余

常见辅助指标包括：

- **上下文有效率**：最终上下文中与问题或答案直接相关的片段比例；
- **重复率**：相同内容、重叠 Chunk 或同一事实重复出现的比例；
- **冲突率**：上下文中互相矛盾且未标明版本、时间或来源的事实比例；
- **截断损失**：候选证据在压缩、排序或 Token 截断后被丢弃的比例；
- **来源多样性**：答案是否过度依赖单一来源，以及多来源内容是否发生不可解释的冲突。

这些指标未必都有统一公式，可以先定义稳定的标注规则。例如，将每个上下文片段标记为“支持、部分支持、无关、冲突”，再计算片段级占比和问题级通过率。

### 5.3 消融实验

为了判断上下文各环节的贡献，可进行消融：

- 仅使用向量召回；
- 加入关键词召回；
- 加入 Rerank；
- 去重前后对比；
- 压缩前后对比；
- 改变 `top_k`、上下文长度和片段顺序；
- 保留标题、来源、时间和权限元数据与否的对比。

消融实验应固定模型版本、数据版本和随机性设置，并记录每次改变的参数。否则“改了很多东西后分数变好”无法说明究竟是哪一个环节有效。

## 6. 生成与引用评测

### 6.1 答案相关性与完整性

答案评测至少包含两个不同问题：

- **相关性**：答案是否直接回应了用户的问题，而不是泛泛介绍主题；
- **完整性**：答案是否覆盖问题要求的全部条件和关键事实。

对于分类、抽取、数值计算等任务，可以使用准确率、F1、Exact Match 或领域专用校验器。对于开放式总结，通常需要结合规则、模型评审和人工抽样，不能把词面相似度当作事实正确性。

### 6.2 忠实性与幻觉

忠实性关注答案中的陈述能否由给定上下文支持。可先把答案拆成若干原子陈述，再为每个陈述标记：

- `entailed`：上下文明确支持；
- `partially_supported`：只有部分内容有依据；
- `unsupported`：上下文没有依据；
- `contradicted`：与上下文冲突。

一个简单的支持率可以写成：

$$
Faithfulness = \frac{N_{entailed}}{N_{all\ claims}}
$$

实际评测还应单独报告“冲突”和“无依据”，因为二者的处理方式不同：前者需要优先解决版本或来源冲突，后者通常意味着模型产生了上下文外的信息。

### 6.3 引用正确性

如果系统要求引用，应同时评估：

- **Citation Precision**：答案给出的引用是否真的支持对应陈述；
- **Citation Recall**：需要引用的关键陈述是否都给出了引用；
- **引用定位准确性**：引用是否指向具体文档、页码、段落或 Chunk，而不是只给一个无法核查的来源名称；
- **引用完整性**：答案中的数字、条件、例外和结论是否都有相应依据。

“答案末尾放了一个相关链接”不等于引用正确。引用应尽量与被支持的陈述建立明确对应关系；如果证据不足，系统应允许回答“当前资料无法确认”。

### 6.4 模型评审与人工评审

LLM-as-a-Judge 可以用于批量初筛，但不应作为唯一真值来源。评审提示词应明确评分标准、输入上下文、问题和引用，并尽量采用结构化输出。推荐做法是：

1. 用自动规则筛查格式、引用存在性、敏感信息和明显事实错误；
2. 用模型评审进行大规模排序和错误聚类；
3. 对高风险、争议样本和指标变化样本进行人工复核；
4. 定期抽样比较模型评审与人工标注的一致性。

人工标注指南应定义“正确、部分正确、无关、无依据、冲突、越权”等类别，并给出正例和反例。没有统一标注标准时，评测分数的变化可能只是标注者判断不同。

## 7. 端到端评测设计

### 7.1 固定实验条件

每次实验至少记录：

```text
code_version
model_version
embedding_model
rerank_model
corpus_version
index_version
chunking_config
retrieval_config
prompt_version
temperature / seed
permission_context
evaluation_set_version
```

如果不记录这些信息，即使分数变化，也无法判断是模型、索引、数据、提示词还是权限过滤导致的。

### 7.2 错误归因矩阵

可为每个失败样本记录主因和次因：

| 错误类别 | 典型现象 | 优先检查 |
| --- | --- | --- |
| 查询理解错误 | 问题改写改变了原意 | Query Rewrite、意图和约束提取 |
| 召回遗漏 | 相关片段未进入候选集 | Chunk、Embedding、关键词和过滤 |
| 排名错误 | 相关片段存在但位置靠后 | Rerank、融合和排序特征 |
| 上下文污染 | 重复、冲突或无关内容过多 | 去重、压缩、版本和截断 |
| 生成错误 | 证据正确但答案错误 | 提示词、模型能力、输出校验 |
| 引用错误 | 引用与陈述不匹配 | 引用绑定、定位和后处理 |
| 权限错误 | 返回无权内容或错误拒答 | 检索前过滤、缓存和索引隔离 |
| 数据新鲜度错误 | 使用旧版本或已删除内容 | 增量更新、删除和一致性 |

这种归因比单纯报告“准确率下降 3%”更有行动价值，因为不同错误类别对应不同的修复路径。

### 7.3 分层报告

总体分数之外，至少按以下维度分组：

- 问题类型和难度；
- 单跳、多跳和跨文档；
- 文档类型、长度和语言；
- 新文档、旧文档和版本冲突；
- 用户权限、租户和过滤条件；
- 有答案与无答案；
- 短上下文与长上下文；
- 低频实体、数字、日期和专有名词。

同时报告均值、分位数和置信区间。平均延迟不能替代 P95/P99 延迟；平均质量也不能掩盖少数高风险错误。

## 8. 质量、延迟、成本与安全的联合权衡

RAG 评测不是单目标优化。增大 `top_k` 可能提高召回率，却增加重排耗时、输入 Token 和生成成本；加入更多上下文可能改善完整性，却增加冲突和“迷失在上下文中”的风险。

建议建立发布门槛，例如：

- Recall@K 不低于基线；
- 忠实性和引用正确性不低于目标值；
- 无答案问题的拒答正确率达到要求；
- 越权样本为零；
- P95 延迟、Token 消耗和单次成本不超过预算；
- 关键回归样本不能退化。

在无法同时满足所有指标时，应按业务风险排序：安全与权限问题通常优先于一般质量提升；高风险领域的事实支持和引用可靠性通常优先于回答风格。

## 9. 线上监控与持续评测

离线评测不能覆盖真实流量中的所有问题。上线后应持续记录经过脱敏和访问控制的运行指标：

- 请求量、成功率、超时率和异常率；
- 检索命中、空结果和候选数量分布；
- 端到端延迟及各阶段耗时；
- 输入输出 Token、缓存命中率和成本；
- 用户反馈、人工纠错和追问率；
- 引用点击、引用打开失败和答案复制等行为信号；
- 权限拒绝、敏感信息拦截和审计告警。

线上信号只能作为辅助证据。例如，用户没有追问不一定代表答案正确；引用被点击也不一定代表引用支持答案。对线上样本进行抽样复核，并将确认过的错误加入回归集，才能形成持续改进闭环：

```text
线上采样 → 脱敏与标注 → 错误归因 → 修复链路 → 离线回归 → 灰度发布 → 线上观察
```

## 10. 一个最小可行评测流程

可以先实现一个小而完整的评测闭环：

1. 选取一批覆盖主要问题类型的人工标注样本；
2. 固定语料、索引、模型、提示词和权限上下文版本；
3. 记录 Top-K 检索结果及其文档、Chunk、分数和元数据；
4. 计算 Recall@K、MRR 或 nDCG；
5. 保存最终上下文，检查证据覆盖、重复和冲突；
6. 生成答案并记录引用；
7. 评估答案相关性、完整性、忠实性和引用正确性；
8. 统计延迟、Token、费用和失败率；
9. 对错误样本进行归因，并把高价值错误加入回归集；
10. 只有在关键安全门槛通过后，才比较整体质量变化。

伪代码示意：

```python
for case in evaluation_set:
    candidates = retrieve(
        query=case.question,
        allowed_scope=case.allowed_scope,
    )
    ranked = rerank(case.question, candidates)
    context = build_context(ranked)
    answer = generate(case.question, context)

    log_result(
        case_id=case.case_id,
        candidates=candidates,
        context=context,
        answer=answer,
    )

report = evaluate(
    retrieval=logged_candidates,
    context=logged_context,
    answers=logged_answers,
    references=evaluation_set,
)
```

这段流程的重点不是代码形式，而是**保留中间产物**。如果只保存最终答案，就无法定位问题发生在召回、上下文构造还是生成阶段。

## 11. 常见误区

### 误区一：只用最终答案准确率

最终答案正确可能是模型凭常识猜对，最终答案错误也可能只是引用格式不符合规则。必须保留检索和上下文级别的指标。

### 误区二：只追求更高 Recall

召回更多内容不一定提升生成质量。应同时观察 Precision、冗余、冲突、Token 和忠实性。

### 误区三：用合成问题代替真实分布

合成数据适合补齐覆盖范围，但容易过于规整。应与真实问题、长尾问题和历史失败案例结合。

### 误区四：让同一个模型生成问题、答案和评判

这会放大模型自身偏差。关键样本应引入原始文档、规则校验和人工复核，并尽量使用不同的评审路径。

### 误区五：忽略无答案和拒答能力

一个只会“尽量回答”的系统，可能在知识不足时制造幻觉。评测集必须包含明确无答案、权限不足和信息冲突的场景。

### 误区六：忽略数据与索引版本

相同问题在文档更新前后可能有不同答案。评测结果必须绑定语料版本和索引版本，否则无法解释新鲜度问题。

---

## 12. 学习检查清单

完成本节后，应能够回答：

- 为什么要把 RAG 评测拆成检索、上下文和生成三层？
- Recall@K、Precision@K、MRR 和 nDCG 分别适合观察什么？
- 如何证明答案中的关键事实确实出现在最终上下文中？
- 如何区分“没有召回证据”和“有证据但模型没有使用”？
- 引用正确性与答案相关性有什么区别？
- 为什么无答案、权限不足和版本冲突必须进入评测集？
- 如何记录实验条件，使一次评测可以复现？
- 为什么线上用户反馈不能直接等同于答案正确率？
