# 向量存储选型

> 上一节：[增量更新、删除与索引一致性](./09-增量更新、删除与索引一致性.md)｜导航：[RAG 学习路线](./00-RAG学习路线.md)｜下一节：[RAG 端到端实践](./11-RAG端到端实践.md)

## 1. 本节定位

向量存储选型不是简单地比较“谁的向量检索速度更快”。一个可用的 RAG 系统还需要同时处理：

- 向量保存与近似最近邻检索；
- 文档、Chunk、版本和来源元数据；
- 租户、权限、时间范围和业务标签过滤；
- 关键词检索与向量检索的混合；
- 新增、修改、删除和索引重建；
- 查询延迟、并发、可用性、备份与恢复；
- 成本、团队熟悉度和长期迁移风险。

因此，本节关注的是“怎样根据业务约束选择存储和检索方案”，而不是罗列产品特性。

## 2. 学习目标

完成本节后，应能够：

1. 区分向量数据库、关系数据库扩展、搜索引擎和本地向量索引；
2. 根据数据规模、过滤复杂度、更新频率和运维能力缩小候选范围；
3. 理解 HNSW、IVF 等索引结构对召回率、延迟和资源消耗的影响；
4. 设计向量、Chunk、版本和权限元数据的存储边界；
5. 用统一数据集和统一指标完成可重复的选型实验；
6. 认识到选型结果必须与 RAG 的增量更新、权限隔离和评测方案一起验证。

## 3. 先明确：向量存储在 RAG 中负责什么

一个 RAG 系统通常包含以下几类数据：

| 数据 | 典型内容 | 主要访问方式 | 是否适合只放在向量索引中 |
| --- | --- | --- | --- |
| 原始文档 | PDF、网页、Office 文件、业务记录 | 按文档 ID、版本和权限读取 | 不适合 |
| 解析结果 | 清洗后的正文、标题层级、页码 | 按文档版本读取 | 通常不适合 |
| Chunk | 可检索的文本片段及其来源 | 按 Chunk ID、文档 ID、过滤条件读取 | 可与向量索引关联 |
| Embedding | 每个 Chunk 的向量 | Top-k 相似度检索 | 适合 |
| 关键词索引 | 词项、倒排信息、BM25 字段 | 关键词检索 | 由搜索引擎负责 |
| 权限元数据 | tenant、用户组、资源范围、可见状态 | 检索前过滤 | 必须由可信服务控制 |
| 处理状态 | 解析、Embedding、索引发布状态 | 任务查询和重试 | 不应只依赖向量库 |

推荐把“事实来源”和“派生索引”分开考虑：

```text
原始文档 / 业务数据库
        │
        ├── 解析、清洗、切分
        │
        ├── Chunk 与元数据事实表
        │       ├── 关键词索引
        │       └── 向量索引
        │
        └── 发布状态、版本指针、审计记录
```

向量存储通常是检索链路中的派生系统。它可以保存检索所需的文本和元数据副本，但不应成为唯一的事实来源。这样做有几个好处：

- 索引损坏或重建时，能够从事实来源恢复；
- 修改 Embedding 模型时，可以重新生成向量；
- 权限和版本发生变化时，可以重新发布索引；
- 不把业务事务、审计和复杂数据关系强行塞入向量数据库。

## 4. 选型前先写清楚约束

### 4.1 数据规模

至少记录以下数量，而不是只估计“文档数”：

- 文档数量；
- 平均和最大 Chunk 数；
- Chunk 总数；
- 向量维度；
- 向量数据类型，例如 `float32`、`float16` 或量化格式；
- 元数据大小和全文字段大小；
- 每日新增、修改和删除量；
- 预计一到三年后的增长量。

向量本体的粗略空间可以按下面的方式估算：

$$
S_{vector} \approx N \times d \times b \times (1 + r)
$$

其中：

- $N$ 是向量数量；
- $d$ 是向量维度；
- $b$ 是每个分量占用的字节数，`float32` 通常为 4；
- $r$ 是索引结构、对齐和副本带来的额外开销。

实际容量还要加上文本、元数据、倒排索引、日志、备份和副本。不能只用“向量数量 × 维度 × 4”作为机器规格。

### 4.2 查询模式

需要明确查询是以下哪一种，或哪几种的组合：

- 纯语义相似度检索；
- 带 `tenant_id`、部门、产品、语言、时间范围等过滤；
- 关键词检索；
- 向量与 BM25 的混合检索；
- 按文档、章节、版本聚合或去重；
- 相似度检索后还要排序、聚合或高亮；
- 多路召回后统一合并和重排。

如果业务问题包含大量精确条件，例如订单号、版本号、权限范围和时间窗口，单纯依赖向量相似度通常不是好方案。存储系统必须能够在召回阶段高效执行结构化过滤，或与关系数据库、搜索引擎协作完成过滤。

### 4.3 性能目标

不要只写“要快”，应明确：

- 目标并发和峰值并发；
- `top_k` 的范围；
- p50、p95、p99 延迟目标；
- 是否允许异步查询；
- 写入延迟和可见性延迟；
- 索引构建、扩容和恢复期间是否需要继续服务；
- 单租户大查询是否会影响其他租户。

RAG 的端到端延迟还包括 Query Rewrite、Embedding、检索、Rerank、Prompt 组装和大模型生成。向量检索从 30 毫秒降到 10 毫秒，并不一定能改善整体体验；反之，过滤错误造成的低召回也不能用更快的延迟弥补。

### 4.4 一致性与更新模式

确认以下问题：

- 新写入的 Chunk 多久后必须可检索；
- 文档修改是否要求旧版本立即不可见；
- 删除是否必须立即生效；
- 是否允许短时间读到旧版本；
- 索引更新失败后如何重试；
- 如何发现事实来源和索引之间的不一致；
- 是否需要双写、消息队列或批量发布。

这些问题与上一节的增量更新设计直接相关。存储产品的写入 API 并不能自动解决业务上的版本发布和删除语义。

## 5. 主要方案类别

### 5.1 关系数据库 + 向量扩展

典型思路是在已有关系数据库中保存 Chunk、元数据和向量，并使用向量扩展完成相似度检索。

**适合：**

- 数据规模中小到中等；
- 已经使用关系数据库，团队熟悉 SQL；
- 过滤条件和事务关系比较重要；
- 希望减少基础设施数量；
- 向量检索不是唯一或最大的业务负载。

**优点：**

- 文档、Chunk、权限和版本可以放在同一套数据模型中；
- SQL 过滤、连接和事务能力成熟；
- 备份、权限、迁移和监控可以复用现有体系；
- 对原型和业务系统集成比较直接。

**风险与边界：**

- 大规模高并发向量检索可能与在线事务互相影响；
- 向量索引构建、更新和 vacuum 等维护会消耗资源；
- 复杂混合检索和全文搜索能力可能不如专用搜索引擎；
- 扩展到多节点时，需要确认分片、路由和高可用方案。

这类方案的关键不是“数据库能不能存向量”，而是验证在真实过滤条件和真实并发下，在线事务与向量查询是否能够稳定共存。

### 5.2 搜索引擎 + 向量检索

搜索引擎通常同时提供倒排索引、BM25、结构化过滤、聚合和向量检索，适合搜索体验较强的应用。

**适合：**

- 关键词和语义检索都很重要；
- 需要高亮、聚合、字段过滤或复杂查询；
- 用户经常输入专有名词、编号、版本和短关键词；
- 已有搜索引擎集群和运维经验。

**优点：**

- 关键词、过滤和向量检索可以在一套查询体系中组合；
- 适合实现混合检索、字段权重和搜索分析；
- 搜索结果的解释和调试工具通常较丰富。

**风险与边界：**

- 向量字段、索引和副本可能显著增加内存与存储成本；
- 混合检索的分数融合需要实验，不能直接把不同分数相加；
- 分片、刷新和段合并会影响写入可见性与查询延迟；
- 对强事务和复杂业务关系的支持通常不如关系数据库。

### 5.3 专用向量数据库

专用向量数据库将近似最近邻索引、向量存储、过滤、分片和副本作为核心能力，常见于大规模语义检索服务。

**适合：**

- 向量检索是系统的主要负载；
- 向量数量较大，未来还会持续增长；
- 需要独立扩展查询和写入资源；
- 团队能够接受新的运维模型或使用托管服务。

**优点：**

- 向量索引和检索能力通常比较完整；
- 可以围绕检索负载进行容量规划和水平扩展；
- 常提供 payload 过滤、分区、批量写入和索引参数调节。

**风险与边界：**

- 文档事实、复杂事务和审计通常仍需外部系统保存；
- 产品之间的过滤语义、更新语义和一致性保证可能不同；
- 迁移成本取决于查询语法、索引参数和数据模型；
- “专用”不等于不需要调参、监控、备份和故障演练。

使用专用向量数据库时，建议把它当作“检索索引服务”，不要把所有业务状态都迁入其中。

### 5.4 本地索引库或内存索引

本地索引库适合在单机、离线任务、实验或小规模应用中使用。常见做法是生成索引文件，加载到进程内或独立服务中。

**适合：**

- 离线评测和算法实验；
- 数据量较小且更新不频繁；
- 对高可用、在线删除和多租户隔离没有严格要求；
- 需要快速验证 Embedding、召回和索引参数。

**不适合直接承担：**

- 多副本在线服务；
- 频繁增删改；
- 严格权限过滤；
- 跨节点故障恢复；
- 复杂的租户级资源隔离。

本地索引可以是很好的实验基线，但不要因为离线测试结果好，就直接推断它适合生产系统。

### 5.5 托管向量服务

托管服务可以减少集群运维、升级和扩容工作，适合希望快速上线、但不想自建检索基础设施的团队。

选择时重点确认：

- 计费单位是存储、向量数量、读写次数还是节点规格；
- 过滤、批量写入、删除和版本发布是否满足需求；
- 数据所在区域、备份、保留和合规能力；
- 是否支持导出全量数据与增量变更；
- 发生服务故障或供应商迁移时的退出方案；
- 端到端网络延迟以及跨区域访问成本。

托管服务降低的是基础设施运维成本，不会自动降低数据建模、权限设计和检索评测成本。

## 6. 索引结构：不要只比较产品默认参数

### 6.1 HNSW

HNSW 通过多层图结构在高维空间中快速寻找近邻，常用于需要较低查询延迟和较高召回率的在线检索。

通常需要关注：

- 构建阶段的连接参数；
- 查询阶段访问的候选数量；
- 索引构建时间和内存占用；
- 增量写入后索引质量是否稳定；
- 删除、更新和重建的具体语义。

增大查询候选数量通常可能提高召回率，但会增加延迟；增大图连接度可能改善检索质量，却会增加构建时间和内存。最终参数应由基准测试确定。

### 6.2 IVF 及其变体

IVF 先把向量划分到多个簇，查询时只搜索部分簇，以减少需要比较的候选数量。

需要关注：

- 簇数量是否与数据规模匹配；
- 查询时探测多少个簇；
- 索引训练是否使用了有代表性的样本；
- 数据分布变化后是否需要重新训练；
- 小数据集上是否反而增加了复杂度。

IVF 的效果与数据分布和参数关联较强。不能把某个数据集上的默认参数直接复制到另一种语言、领域或 Embedding 模型上。

### 6.3 精确检索与近似检索

精确最近邻检索可以作为质量基线，尤其适合小数据集和离线评测。生产环境通常使用近似索引换取延迟和吞吐，但必须用精确结果计算召回损失。

推荐保留一个小规模的精确检索基线：

1. 对同一批查询执行精确检索；
2. 对不同索引参数执行近似检索；
3. 计算 `Recall@k`、延迟和资源占用；
4. 找到满足质量门槛的最低资源配置。

## 7. 元数据与过滤设计

### 7.1 把高频过滤字段结构化

常见的结构化字段包括：

```json
{
  "tenant_id": "tenant-a",
  "document_id": "doc-123",
  "document_version": 7,
  "chunk_id": "doc-123-v7-c004",
  "visibility": "published",
  "source_type": "manual",
  "language": "zh-CN",
  "department_id": "dept-01",
  "updated_at": "2025-01-01T00:00:00Z",
  "page": 12,
  "embedding_model": "embedding-model-v1"
}
```

字段设计原则：

- 高频过滤字段使用明确的数据类型，不要全部编码成字符串；
- 时间、版本和状态字段要有稳定语义；
- `document_id`、`document_version`、`chunk_id` 之间保持可追溯关系；
- 过滤字段与展示字段分开，避免把无关大字段复制到每个 Chunk；
- 需要聚合、排序或范围过滤的字段，应确认底层存储是否对其建立了合适的索引。

### 7.2 过滤必须在可信边界执行

权限过滤不能由模型决定，也不能只在生成答案后再过滤。推荐流程是：

```text
认证用户
  → 授权服务计算可访问范围
  → 应用服务生成服务端过滤条件
  → 向量 / 关键词检索
  → 只把已授权结果交给 Rerank 和生成模型
```

用户输入中的 `tenant_id`、部门或权限条件不能直接作为可信过滤条件。检索服务应尽量只接受应用服务生成的过滤表达式，并记录实际使用的授权范围用于审计。

### 7.3 过滤与 ANN 的组合是重点测试项

同一个向量索引，在无过滤、低选择性过滤和高选择性过滤下，性能可能完全不同。至少测试：

- 不带过滤的查询；
- 过滤后仍有大量候选的查询；
- 过滤后只剩很少候选的查询；
- 多个字段组合过滤；
- 过滤字段分布严重倾斜的租户；
- 不存在匹配结果的查询。

有些系统先做 ANN 再过滤，可能导致过滤后结果不足；有些系统支持过滤感知的检索，但会有额外执行开销。必须根据实际执行计划和召回结果判断，不能只看接口文档中的“支持过滤”。

## 8. 数据模型建议

可以将逻辑模型拆成四层：

### 8.1 文档事实表

保存文档身份、来源、当前版本、业务状态和权限事实。它通常位于关系数据库或业务系统中。

### 8.2 文档版本表

保存每次发布的内容版本、内容哈希、解析器版本、切分策略和 Embedding 模型版本。例如：

```text
document_id
version
content_hash
parser_version
chunking_version
embedding_model
status
created_at
published_at
```

### 8.3 Chunk 记录

保存 Chunk 文本、标题路径、页码、字符区间、父文档和版本关系。向量库可以保存其中用于检索和展示的副本，但应保留通过 ID 回查事实来源的能力。

### 8.4 向量索引记录

至少能够定位：

```text
vector_id → chunk_id → document_id + version
```

同时记录索引批次、发布时间、可见状态和 Embedding 模型。这样才能回答“这个答案来自哪个文档版本、由哪个模型生成、何时发布”。

## 9. 选型决策矩阵

| 条件 | 优先考虑 | 需要重点验证 |
| --- | --- | --- |
| 已有关系数据库，规模适中 | 关系数据库 + 向量扩展 | ANN 与在线事务的资源隔离 |
| 关键词、过滤、聚合很重要 | 搜索引擎 + 向量检索 | 混合检索分数融合和刷新延迟 |
| 向量规模大、检索是核心负载 | 专用向量数据库 | 分片、扩容、备份、过滤和更新语义 |
| 快速原型或离线评测 | 本地索引库 | 与生产数据模型和权限能力的差距 |
| 团队希望少运维 | 托管服务 | 成本、数据导出和供应商退出方案 |
| 强事务、复杂业务关联为主 | 关系数据库保存事实，外接检索索引 | 双系统一致性与重建流程 |

这张表只能帮助缩小范围，不能替代基准测试。同一类别中的不同实现，也可能在过滤、写入可见性和故障恢复方面有明显差异。

## 10. 一个可重复的基准测试方案

### 10.1 准备固定数据集

数据集应包含生产中真实存在的差异：

- 长文档和短文档；
- 表格、代码、标题层级和多语言文本；
- 重复内容与近似内容；
- 不同租户和不同权限范围；
- 新版本与旧版本；
- 高热度文档和长尾文档。

不要只用随机向量测试。随机向量能测出接口吞吐，却不能验证 Embedding 分布、过滤选择性和实际召回质量。

### 10.2 准备查询集和相关性标注

查询集至少覆盖：

- 直接问法；
- 同义改写；
- 包含产品名、版本号和编号的问法；
- 需要时间或状态约束的问法；
- 无答案问题；
- 跨文档、多跳问题；
- 权限不同但文本相似的问题。

为每个查询准备人工标注的相关 Chunk 或相关文档，作为检索质量的参考答案。标注数据应区分“主题相关”和“足以支持回答”，后者更接近 RAG 的实际目标。

### 10.3 固定变量

比较候选方案时，尽量固定：

- 同一个 Embedding 模型和向量版本；
- 同一个 Chunk 数据集；
- 同一个查询集；
- 同一个 `top_k` 和过滤条件；
- 同一个硬件级别或成本预算；
- 相同的预热、并发和超时策略。

否则测到的可能是模型或硬件差异，而不是存储方案差异。

### 10.4 记录指标

**检索质量：**

- `Recall@k`：相关结果是否进入候选集合；
- `Precision@k`：返回结果中相关结果的比例；
- `MRR` 或 `nDCG`：相关结果的排序质量；
- 过滤正确率：是否返回了不应可见的数据；
- 版本正确率：是否混入已失效版本；
- 空结果和无答案问题的误召回率。

**性能与资源：**

- p50、p95、p99 查询延迟；
- 吞吐和并发下的错误率；
- 批量写入吞吐；
- 从写入到可检索的延迟；
- 删除或版本切换到生效的延迟；
- CPU、内存、磁盘、网络和副本开销；
- 重启、扩容、重建和恢复时间。

**运维与成本：**

- 日常操作复杂度；
- 监控指标和告警完整性；
- 备份恢复是否经过演练；
- 版本升级与回滚方式；
- 单位查询成本和单位向量存储成本；
- 数据导出和迁移所需时间。

### 10.5 用门槛而不是单一排名决策

可以先设定硬性门槛，再在满足门槛的方案中比较成本和便利性。例如：

```text
过滤正确率 = 100%
Recall@20 ≥ 目标值
p95 查询延迟 ≤ 目标值
删除生效延迟 ≤ 目标值
故障恢复时间 ≤ 目标值
月度成本 ≤ 预算
```

任何违反权限隔离或版本可见性要求的方案，都不应因为延迟更低而被选中。

## 11. 推荐的最小落地架构

对于多数中小规模 RAG 项目，可以先采用以下边界：

```text
关系数据库：
  文档事实、版本、权限事实、任务状态、审计记录

对象存储：
  原始文件、解析中间产物、索引构建快照

检索存储：
  Chunk 的检索文本、Embedding、必要的过滤元数据

应用检索服务：
  生成授权过滤条件、执行混合召回、记录引用和版本

评测系统：
  固定查询集、相关性标注、离线指标和线上监控
```

在数据规模尚未证明需要拆分时，可以先使用关系数据库的向量扩展或已有搜索引擎；当向量查询成为明显瓶颈，再独立部署专用向量存储。迁移前应确保 `chunk_id`、文档版本和元数据模型已经稳定。

## 12. 常见误区

### 误区一：只按向量数量选择产品

真实压力还取决于向量维度、过滤字段、查询并发、`top_k`、副本、更新频率和元数据大小。

### 误区二：只看官方无过滤吞吐

RAG 往往必须携带租户、权限、版本和业务条件。无过滤基准不能代表真实查询。

### 误区三：把相似度分数当成统一标准

不同模型、距离函数和归一化方式产生的分数不能直接横向比较。混合检索需要进行分数校准、排名融合或使用 Rerank。

### 误区四：把向量库当成唯一事实来源

索引重建、Embedding 迁移、权限修复和数据对账都会要求可恢复的事实数据。

### 误区五：忽略删除和旧版本残留

向量删除成功不代表缓存、关键词索引、引用记录和其他副本都已同步。必须定义可见性和对账机制。

### 误区六：只测试平均延迟

长尾延迟通常由高并发、分片倾斜、过滤选择性、缓存未命中和索引维护造成。至少观察 p95 和 p99。

### 误区七：把“支持多租户”理解成天然安全

多租户能力可能只是提供一个字段，并不等于自动完成权限过滤、资源隔离、配额限制和审计。授权逻辑必须由可信应用服务强制执行。

### 误区八：过早追求复杂架构

在没有数据规模和负载证据之前，拆分多个数据库会增加一致性、监控、备份和排障成本。先建立可重建的数据管道和评测基线，再根据瓶颈演进。

## 13. 选型检查清单

### 数据与模型

- [ ] 已统计 Chunk 总数、向量维度、元数据大小和增长量；
- [ ] 已固定 Embedding 模型、距离函数和向量版本；
- [ ] 已明确全文、Chunk 和原始文件的存放位置；
- [ ] 已设计 `document_id`、版本和 `chunk_id` 的关系。

### 检索与过滤

- [ ] 已列出真实查询模式和过滤条件；
- [ ] 已验证租户、权限、状态和版本过滤；
- [ ] 已测试无过滤、低选择性和高选择性过滤；
- [ ] 已确认是否需要 BM25、混合检索、聚合或高亮；
- [ ] 已保留精确检索或其他质量基线。

### 更新与可靠性

- [ ] 已定义新增、修改、删除和重试语义；
- [ ] 已定义“写入成功”和“可检索”的区别；
- [ ] 已验证旧版本不可见和删除生效时间；
- [ ] 已测试备份、恢复、重建和故障切换；
- [ ] 已有事实来源与索引之间的对账机制。

### 成本与运维

- [ ] 已测试 p50、p95、p99，而不只是平均延迟；
- [ ] 已测量不同索引参数下的召回率和资源占用；
- [ ] 已估算副本、备份、网络和扩容成本；
- [ ] 已确认监控、告警、升级和回滚方式；
- [ ] 已制定数据导出和迁移方案。

## 14. 核心结论

1. 向量存储选型是 RAG 整体架构决策，不是孤立的数据库采购。
2. 数据规模、过滤复杂度、更新语义和团队运维能力，通常比产品名称更重要。
3. 关系数据库适合以业务数据和事务为中心的中小规模场景；搜索引擎适合关键词、过滤和混合检索；专用向量数据库适合以大规模向量检索为核心的场景；本地索引适合实验和离线任务。
4. 必须使用真实数据、真实过滤条件和固定评测集，联合比较召回率、延迟、更新生效、恢复能力和成本。
5. 权限、版本和删除语义必须由可信服务和数据管道保证，不能交给模型或向量数据库的默认行为。
6. 无论采用哪种存储，都应保留可重建的事实来源、稳定的 Chunk 身份和明确的索引发布流程。
