# 第 12 课：响应缓存

> 本页依据通用的大模型应用工程实践整理。项目当前可见资料没有指定缓存介质、模型服务商或 SDK，因此示例使用与具体厂商无关的 Python 伪代码；接入 Redis、数据库、本地 LRU 或供应商提供的 Prompt Cache 时，需要根据实际接口补充序列化、并发控制、监控和安全配置。

## 1. 响应缓存解决什么问题

响应缓存（response cache）是将一次已经完成并通过校验的模型请求结果，按照一组确定的规则保存起来。当后续请求与原请求**足够等价**时，应用可以直接返回缓存结果，而不必再次调用模型。

一次模型请求的成本通常不仅是模型调用费用，还包括网络等待、排队、重试、输入与输出 token、检索和工具调用等成本。合理使用缓存可以降低：

- **重复请求的延迟**：命中缓存时通常只需要访问缓存服务，不需要等待模型排队和生成；
- **模型调用成本**：减少重复消耗的输入、输出 token；
- **供应商压力**：降低 QPS、并发数和限流概率；
- **高峰期风险**：在模型服务变慢或配额紧张时，用缓存承担一部分流量；
- **输出波动**：对确定性较强的任务，减少同一输入因为采样而得到不同结果的情况；
- **系统可用性压力**：在业务允许返回最近结果时，缓存可以作为短时的后端减压层。

但缓存首先是**性能和成本优化机制**，不是正确性机制，也不是权限校验机制。缓存中的结果可能过时、属于其他用户，或者是由旧版本 prompt 生成的。缓存命中后仍然必须满足当前请求的安全边界；不能因为命中了缓存，就跳过鉴权、租户隔离或必要的业务校验。

### 1.1 适合缓存的任务

通常适合从精确响应缓存开始的任务包括：

- 固定 FAQ 或产品说明问答；
- 结构化抽取、分类、标签生成等相对确定的任务；
- 文本翻译、格式转换、摘要（前提是输入内容本身可复用）；
- 对同一份文档、同一组参数进行重复分析；
- 测试、评估和离线批处理中的重复请求；
- 允许在一定时间内返回略旧结果的非实时场景。

### 1.2 不适合直接缓存的任务

下面这些请求默认应谨慎缓存，很多情况下应直接不进入共享响应缓存：

- 依赖实时价格、库存、天气、新闻、政策或账户余额的内容；
- 结果高度个性化，且包含用户隐私、权限范围或业务机密；
- 会触发支付、发货、写库、发邮件、创建工单等副作用的工具调用；
- 包含一次性验证码、访问令牌、临时签名或其他短期凭证；
- 医疗、法律、财务等对新鲜度和上下文准确性要求很高的建议；
- 输出应当具有随机性，且随机性本身是业务要求的场景。

如果请求中包含工具调用，通常更适合缓存**工具调用前的纯推理结果**或安全的中间产物，而不是直接复用已经执行过的副作用。对工具调用结果进行缓存时，还要明确工具是否幂等、数据是否仍然有效，以及再次使用结果是否会绕过当前权限检查。

## 2. 先区分缓存的对象

“大模型缓存”并不只指一种缓存。设计前应先确定要缓存的是完整响应、提示词前缀、会话状态，还是检索结果。不同对象的命中条件、失效方式和风险不同。

| 类型 | 缓存对象 | 典型命中条件 | 适用场景 | 主要风险 |
| --- | --- | --- | --- | --- |
| 精确响应缓存 | 完整的模型响应和必要元数据 | 请求语义及所有决定性参数完全一致 | FAQ、抽取、翻译、固定格式生成 | key 漏字段导致串结果 |
| 语义缓存 | 问题与历史问题的相似匹配 | 相似度超过阈值，且业务条件满足 | 知识问答、客服、相似问题复用 | 相似不等于等价，可能答非所问 |
| 前缀/提示词缓存 | 长 system prompt 或共享前缀的中间计算 | 请求共享相同前缀 | 长规则、长文档、固定系统提示词 | 通常由模型服务侧管理，不能替代应用响应缓存 |
| 检索结果缓存 | 查询对应的文档 ID、片段或排序结果 | 查询、索引和过滤条件一致 | RAG 应用、重复检索 | 索引更新后仍返回旧文档 |
| 会话状态缓存 | 摘要、用户上下文、派生状态 | 会话 ID 和状态版本一致 | 多轮对话 | 旧状态污染新上下文 |
| 负缓存 | 已确认的稳定失败结果 | 相同输入在短窗口内重复失败 | 明确无效的参数、已知不存在的资源 | 把临时故障缓存成持续失败 |

应用层通常应从**精确响应缓存**开始，因为它的命中条件容易解释、验证和回滚。语义缓存需要额外的相似度阈值、领域限制、敏感主题排除规则和离线质量评测，不能仅凭向量距离判断两个问题可以复用同一答案。

## 3. 缓存键：必须表达结果的决定因素

缓存键（cache key）决定了两个请求是否被视为“等价”。最危险的错误不是缓存没有命中，而是**错误命中**：请求命中了一个不属于它的结果，且系统没有明显报错。

缓存键不应只包含用户最后一句话。凡是可能改变输出、权限范围或数据新鲜度的输入，都应纳入键，或者纳入具有明确版本语义的命名空间。

### 3.1 通常需要纳入的字段

至少应考虑以下维度：

- **模型信息**：模型 ID、模型版本、服务商、区域和路由配置；
- **完整消息**：system、developer、user、assistant 消息及其顺序、角色和内容；
- **Prompt 版本**：模板版本、few-shot 示例版本、系统规则版本；
- **上下文数据**：检索文档 ID、文档版本、排序结果、知识库或索引版本；
- **工具定义**：工具名称、描述、参数 Schema、工具版本和是否允许调用；
- **生成参数**：温度、`top_p`、最大输出 token、停止序列、随机种子（若使用）；
- **输出约束**：响应格式、JSON Schema、字段版本、语言、风格和业务策略；
- **隔离维度**：租户、用户、组织、权限范围、数据区域和环境；
- **请求模式**：同步/流式、是否要求引用、是否允许使用实时数据等；
- **安全与策略版本**：内容安全策略、脱敏规则、后处理器和审核器版本。

并不是所有字段都必须原样拼进 key。常见做法是先构造一个完整的规范化请求对象，再对该对象做摘要。这样既能表达完整依赖，又能避免把完整 prompt 或个人信息直接暴露在缓存 key 和日志中。

### 3.2 不要遗漏隐含输入

有些输入不会出现在用户请求体中，却可能改变结果。例如：

- 应用根据当前用户身份注入的系统提示词；
- 当前租户启用的产品功能开关；
- 检索器使用的索引版本和过滤条件；
- 服务端根据区域选择的模型路由；
- 业务代码读取的当前日期、币种或语言；
- 预处理和后处理代码的版本；
- 允许模型使用的工具清单。

如果这些隐含输入没有进入 key，应用升级配置后可能继续返回旧结果。一个实用原则是：**凡是改变“模型实际看到的输入”或“结果如何被解释”的因素，都应有明确的版本或隔离表示。**

### 3.3 稳定序列化

对于 JSON 请求，应采用稳定的序列化方式，不要依赖字典插入顺序，也不要使用可能变化的对象默认字符串表示。需要提前约定：

- 对象键是否按字典序排序；
- Unicode 是否保持原样；
- 数字 `1`、`1.0` 和字符串 `"1"` 是否被视为不同值；
- 空字段、默认字段和缺省字段是否等价；
- 列表顺序是否有语义；
- 浮点数如何规范化；
- 二进制内容或大文件是否使用内容摘要；
- 日期、时区和换行符如何表示。

下面的示例使用稳定 JSON 序列化，并使用带服务端密钥的 HMAC 生成摘要。HMAC 主要用于避免直接暴露原始请求内容，并不替代访问控制和加密。

```python
import hashlib
import hmac
import json
from typing import Any


def canonical_json(value: Any) -> bytes:
    """将请求对象序列化为跨进程尽量稳定的字节串。"""
    return json.dumps(
        value,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    ).encode("utf-8")


def make_cache_key(namespace: str, request: dict, secret: bytes) -> str:
    payload = canonical_json(request)
    digest = hmac.new(secret, payload, hashlib.sha256).hexdigest()
    return f"{namespace}:{digest}"
```

实际项目中还应对规范化函数做测试，特别是确认“仅改变无关字段时是否应该命中”和“改变任一决定性字段时是否必须不命中”。密钥应由受控配置系统或密钥管理服务提供，不能写入代码、提交到版本库或输出到日志。

### 3.4 命名空间与版本

不要把所有版本信息都隐含在一段不可读的摘要中。通常可以将容易排查的问题放在可观察的命名空间中，例如：

```text
response:v3:tenant-a:chat:<hmac>
```

其中 `v3` 可以代表 key 结构或业务协议版本。模型版本、Prompt 版本、Schema 版本也可以作为规范化请求的一部分，或者作为更细粒度的命名空间。这样做的好处是：

- 变更时可以切换新空间，避免逐条查找并删除旧 key；
- 可以统计不同版本的命中率和错误率；
- 出现问题时能够快速停止使用某个版本；
- 避免将旧模型输出误认为新模型输出。

切换命名空间会暂时降低命中率，这是可接受的发布成本；不要为了追求短期命中率而跨版本复用无法证明等价的结果。

## 4. 缓存值应保存什么

缓存值不一定只保存模型返回的纯文本。为了便于校验、调试和后续兼容，建议保存一个带版本的记录，例如：

```json
{
  "schema_version": 2,
  "value": {
    "answer": "...",
    "citations": ["doc-123"]
  },
  "model": "model-id",
  "prompt_version": "prompt-v7",
  "created_at": "2025-01-01T00:00:00Z",
  "expires_at": "2025-01-01T01:00:00Z",
  "validation": {
    "syntax": "passed",
    "schema": "passed",
    "business": "passed"
  }
}
```

具体字段应按业务需要取舍。通常值得保留：

- 可供业务直接返回的最终结果；
- 结果格式版本；
- 生成模型和 prompt 版本；
- 生成时间、过期时间和必要的来源版本；
- 校验状态或结果摘要；
- 可观测性所需的非敏感元数据。

不要把完整 prompt、完整响应、用户隐私和敏感工具参数无条件写入普通日志。缓存值本身也可能包含个人信息或业务机密，仍需访问控制、加密、最小化保留和删除机制。即使 key 只有摘要，也不能因此认为缓存内容天然安全。

## 5. 读写模式：Cache-aside

### 5.1 基本流程

最常用的模式是 Cache-aside（旁路缓存）：应用自己负责读取和写入缓存。

```text
请求
  ↓
完成鉴权与请求规范化
  ↓
计算 cache key
  ↓
读取缓存
  ├─ 命中：检查版本、TTL、权限边界和必要的业务条件 → 返回
  └─ 未命中：调用模型 → 解析输出 → 通过校验 → 写入缓存（带 TTL）→ 返回
```

典型伪代码如下：

```python
async def answer(request, user_context):
    # 1. 先做鉴权；缓存不能替代鉴权
    authorize(user_context, request)

    cache_request = build_cache_request(
        request=request,
        user_context=user_context,
        model_version="model-v3",
        prompt_version="prompt-v7",
        schema_version="answer-v2",
    )
    key = make_cache_key("response:v3", cache_request, cache_secret)

    cached = await cache.get(key)
    if cached is not None and is_usable(cached, user_context):
        metrics.increment("response_cache.hit")
        return cached["value"]

    metrics.increment("response_cache.miss")
    raw = await call_model(request, user_context)
    result = parse_and_validate(raw)

    # 解析失败或业务校验失败时，不应写入正常响应缓存
    if result.ok:
        await cache.set(
            key,
            make_cache_record(result.value, cache_request),
            ttl=choose_ttl(request, result.value),
        )

    return result.value
```

缓存读取失败时，通常应将其视为一次 miss 或旁路请求，而不是直接让整个业务失败；但应监控缓存服务故障，避免缓存故障被静默掩盖。缓存写入失败一般不应覆盖已经成功生成的模型结果，除非业务明确要求“必须缓存才算成功”。

### 5.2 先校验输出，再写缓存

不能将以下结果当作正常值长期缓存：

- JSON 解析失败；
- 输出被截断，缺少必需字段；
- 不符合 JSON Schema 或类型约束；
- 引用的文档不存在或引用与答案不一致；
- 触发业务规则、内容安全规则或敏感信息规则；
- 模型返回了供应商错误包装，但 HTTP 请求本身成功；
- 工具调用状态不完整，或副作用是否执行不明确。

如果要缓存失败结果，必须使用单独的负缓存类型，并设置很短的 TTL，同时区分稳定的客户端错误和临时的后端错误。

### 5.3 缓存命中后的再校验

即使缓存记录曾经通过校验，命中时仍可以做轻量检查：

- 记录格式版本是否仍被当前代码支持；
- 当前用户是否仍然有权访问该结果涉及的数据；
- 结果引用的文档或资源是否已经被删除；
- 结果是否已超过业务允许的新鲜度；
- 当前策略版本是否要求重新审核。

对于高风险结果，应在缓存命中路径重新执行权限检查和必要的业务校验，而不是直接返回。

## 6. TTL、失效与新鲜度

### 6.1 TTL 的选择

TTL（Time To Live，生存时间）应由内容的时效性和错误代价决定，而不是只追求高命中率：

| 内容类型 | 典型策略 | 说明 |
| --- | --- | --- |
| 固定格式转换、确定性抽取 | 较长 TTL | 输入和处理版本不变时可长期复用 |
| 产品说明、内部知识问答 | 中等 TTL | 需要配合文档版本或索引版本失效 |
| 含天气、价格、库存等实时数据 | 很短 TTL 或不缓存 | 过期结果可能直接误导用户 |
| 个性化账户或权限相关数据 | 默认不做共享缓存 | 如确需缓存，应严格按用户和权限隔离 |
| 失败结果 | 很短 TTL | 仅适合稳定、可重复的客户端错误 |

TTL 不是“数据永远有效”的证明，只是系统允许缓存条目存活多长时间的上限。对于有明确业务截止时间的内容，应同时保存绝对过期时间，并在命中时检查业务新鲜度。

### 6.2 失效方式

常见失效方式包括：

1. **自然过期**：达到 TTL 后由缓存系统删除或标记不可用；实现简单，但旧值可能存活到 TTL 结束；
2. **版本命名空间切换**：修改模型、prompt、Schema、工具或索引时改用新版本；适合大范围变更；
3. **主动删除**：已知文档、产品配置或账户数据变化时，根据关联索引删除相关 key；实时性较好，但实现复杂；
4. **标签或依赖失效**：缓存记录关联文档 ID、租户 ID 或配置 ID，依赖对象变化时批量失效；需要维护反向索引；
5. **分层 TTL**：缓存值有技术 TTL，同时业务层还有更短的新鲜度窗口。

变更 prompt、模型、检索索引、工具定义或输出 Schema 后，不应默认继续复用旧条目。最安全的方式通常是切换 `v2` 等命名空间，待新版本稳定后再清理旧空间。

### 6.3 Stale-While-Revalidate

对于允许轻微陈旧的内容，可以采用 **stale-while-revalidate（过期可用、后台刷新）**：

1. 在“新鲜窗口”内直接返回缓存；
2. 在“可容忍陈旧窗口”内先返回旧值，同时异步触发一次刷新；
3. 超过陈旧窗口后才强制回源；
4. 刷新任务应使用 single-flight，避免多个请求重复刷新同一 key。

这种方式适合一般知识问答或非关键推荐，不适合权限、交易、库存、医疗建议等需要强新鲜度的场景。返回陈旧值时应记录其年龄，必要时向业务层暴露 `stale=true`，让产品决定是否提示用户。

## 7. 并发击穿、穿透与雪崩

### 7.1 缓存击穿：热点 key 同时回源

同一个热点 key 失效时，大量并发请求可能同时发现 miss，然后一起调用模型。这称为缓存击穿或 stampede。后果包括模型 QPS 突增、费用增加、触发限流，甚至让所有请求都超时。

常用措施：

- **single-flight / 请求合并**：同一 key 同时只允许一个请求回源，其他请求等待相同结果；
- **短期分布式锁**：锁必须有过期时间，并处理持锁请求异常退出的情况；
- **TTL 加随机抖动**：避免大量 key 在同一时刻过期；
- **提前刷新**：热点 key 接近过期时由后台任务刷新；
- **旧值兜底**：业务允许时，在短暂陈旧窗口内先返回旧值；
- **回源限流**：限制每个 key、租户和全局的并发回源数量。

single-flight 等待必须有超时。不能让等待缓存刷新的请求无限阻塞；当领头请求失败时，应明确由一个等待者接管、直接返回错误，还是短暂使用旧值。

### 7.2 缓存穿透：请求反复查不到可缓存结果

缓存穿透是指大量请求访问本来就不存在、无效或不应缓存的内容，每次都绕过缓存访问模型或后端。例如，用户不断提交格式无效的问题，而系统从不保存任何结果。

可以考虑：

- 在调用模型前进行参数格式校验；
- 对明确稳定的无效请求使用短 TTL 负缓存；
- 对高频异常请求进行限流和惩罚；
- 对不存在的资源使用带版本的否定结果；
- 不要对鉴权失败、临时 5xx、超时等错误做普通负缓存。

负缓存必须区分错误类别。临时服务故障不应被缓存成“该请求永远失败”，否则短暂故障会被放大为持续失败。

### 7.3 缓存雪崩：大量 key 同时失效

如果大量条目使用同一个 TTL 或在发布时同时写入，它们可能同时过期，造成集中回源。除了 TTL 随机抖动，还可以：

- 将过期时间分散到一个时间区间；
- 使用分批预热和后台刷新；
- 对模型回源设置全局和分租户并发上限；
- 准备降级策略，如返回经过审核的静态答案；
- 在发布新版本时逐步放量，而不是一次性切换全部流量。

## 8. 语义缓存的额外问题

精确缓存要求请求完全等价；语义缓存则尝试判断“两个不同表述的问题是否可以复用同一结果”。它可能提高命中率，但也会引入新的错误类型：相似问题在时间范围、用户身份、数字、否定词或业务条件上并不等价。

启用语义缓存前应明确：

- 只在哪些业务领域启用，哪些领域强制禁用；
- 使用什么相似度模型和距离阈值；
- 是否对数字、日期、实体、否定词和权限词做精确约束；
- 候选答案的文档版本、租户和语言是否一致；
- 低置信度时是否回源，而不是勉强命中；
- 如何离线评测“语义命中后答案仍然正确”的比例。

一个更安全的判定流程可以是：

```text
向量检索候选缓存
  ↓
检查相似度是否超过阈值
  ↓
检查租户、权限、语言、模型和版本是否一致
  ↓
检查日期、数字、实体和实时性约束
  ↓
通过业务等价性判断 → 命中
否则 → 当作 miss 回源
```

相似度阈值不是通用常数。应按任务类型、错误代价和评测集调整，并持续监控语义缓存的错误复用率。

## 9. 多租户、权限与隐私安全

缓存最危险的错误是跨用户或跨租户复用结果。设计时应明确：

1. key 中包含租户、用户、组织、权限范围或经过验证的权限版本；
2. 如果结果确实是公共内容，使用明确的公共命名空间，不要通过“猜测用户相同”来共享；
3. 缓存服务按环境和租户进行网络、凭据和访问隔离；
4. 缓存值采用最小必要 TTL，敏感内容按要求加密并支持删除；
5. 日志只记录 key 前缀、版本、命中状态、大小和指标，不输出完整 prompt 或响应；
6. 包含一次性令牌、工具参数、个性化隐私数据的结果默认不进入共享缓存；
7. 删除用户数据时，同时考虑缓存、备份、派生摘要和语义索引中的残留；
8. 缓存命中后仍执行当前请求的鉴权，不能把“曾经有权限”当作“现在有权限”。

HMAC key 只解决摘要不可直接反推等部分问题，不解决缓存值泄露、越权读取、重放和错误配置。缓存系统本身仍需使用安全凭据、网络隔离、访问审计和必要的加密措施。

## 10. 流式响应、工具调用与缓存边界

### 10.1 流式响应

流式响应不能简单地在收到第一个 token 时写缓存，因为后续内容可能被截断、连接可能中断，或者最终结果不满足校验要求。更稳妥的流程是：

1. 将流式片段发送给前端，同时在服务端暂存必要内容；
2. 等待流正常结束；
3. 合并完整响应并执行解析、Schema 和业务校验；
4. 只有全部通过后才写入正常响应缓存；
5. 若中途断流或校验失败，不写入正常缓存，必要时记录单独的失败指标。

如果产品必须支持断流恢复，应设计独立的流式游标或会话状态协议，不能把一个未完成的响应当作完整响应缓存。

### 10.2 工具调用

工具调用至少要区分三种对象：

- 模型决定调用哪个工具以及参数的推理结果；
- 工具实际执行后返回的数据；
- 最终展示给用户的答案。

纯函数、只读且具有明确版本的数据查询在满足权限和新鲜度条件时可以缓存。带副作用的工具执行通常不应因为命中了响应缓存而再次执行，也不应把“工具已执行”这一事实无限期当作可复用结果。对于支付、写入、发信等操作，应使用幂等键、业务状态查询和明确的执行记录，而不是依赖普通响应缓存。

## 11. 关键指标与日志

建议至少观察以下指标，并按租户、任务类型、模型版本、prompt 版本和响应状态分组：

### 11.1 命中与成本指标

- 命中率：

  $$
  \text{hit\_rate}=\frac{\text{hits}}{\text{hits}+\text{misses}}
  $$

- 命中次数、未命中次数和跳过缓存次数；
- 缓存节省的模型调用数、输入 token、输出 token 和估算成本；
- 热点 key 的访问集中度和缓存容量使用率。

### 11.2 延迟与可靠性指标

- 命中与未命中的端到端延迟；
- 缓存读取、写入和序列化延迟；
- 缓存服务错误率、超时率和连接池耗尽次数；
- 回源请求并发数、single-flight 等待数和等待时间；
- TTL 到期后的回源峰值。

### 11.3 正确性与安全指标

- 陈旧结果率和平均结果年龄；
- 错误复用率、Schema 校验失败率和业务校验失败率；
- 跨租户、跨用户或权限边界命中事件；
- 负缓存命中率和负缓存导致的错误持续时间；
- 不同版本之间的缓存命中、错误和回源比例。

高命中率不必然是好事。如果 key 漏掉用户权限、模型版本或文档版本，命中率可能“很好”，但结果是错误的、过时的，甚至造成越权。监控时应把命中率与正确性、隔离性和新鲜度一起看。

日志中可以记录：缓存版本、命中/未命中、是否陈旧、TTL 剩余时间、响应大小、耗时和非敏感的任务类型。不要直接记录完整 key 对应的原始 prompt，也不要为了调试而在生产日志中输出完整响应。

## 12. 测试与验证

响应缓存需要验证的不只是“第二次请求变快了”，还包括“任何决定性输入改变后不会错误命中”。建议覆盖以下测试：

### 12.1 key 完整性测试

逐项改变模型版本、prompt 版本、消息顺序、Schema、工具定义、租户、权限和检索版本，确认 key 发生变化；只改变约定为无关的字段时，确认是否按设计保持一致。

### 12.2 读写流程测试

- 第一次请求 miss 并回源；
- 成功结果写入后，第二次请求 hit；
- 解析失败、Schema 失败和业务校验失败不会写入正常缓存；
- 缓存读取失败时可以安全回源；
- 缓存写入失败不会丢失已经成功生成的响应；
- 过期后按照预期回源或使用 stale-while-revalidate。

### 12.3 并发测试

同时发送多个相同请求，确认不会产生不受控的重复回源；模拟领头请求超时、崩溃和返回失败，确认锁、等待者和重试行为最终能够释放并恢复。

### 12.4 安全测试

- 用户 A 写入的结果不能被用户 B 命中；
- 权限撤销后，旧缓存不能绕过鉴权；
- 不同租户、区域和环境之间不能意外共享；
- 日志、指标和错误信息不会泄露原始 prompt 或敏感响应；
- 删除数据后，缓存记录及相关索引能够按要求清除。

### 12.5 变更与回滚测试

模拟模型、prompt、Schema、工具和检索索引升级，确认旧版本不会错误复用；模拟回滚时确认是否需要恢复旧命名空间，以及旧缓存是否仍符合当前业务规则。

## 13. 一个可落地的设计步骤

可以按以下顺序引入响应缓存：

1. **定义缓存边界**：列出哪些任务允许缓存、哪些任务强制绕过；
2. **确定等价条件**：整理所有会影响结果、权限和新鲜度的输入；
3. **建立规范化请求对象**：统一默认值、字段顺序、数字、日期和列表语义；
4. **加入版本和隔离维度**：至少覆盖模型、prompt、Schema、工具、索引、租户和环境；
5. **选择存储与容量策略**：确定 TTL、大小上限、淘汰方式、加密和访问控制；
6. **实现 Cache-aside**：先鉴权，再读缓存；miss 时回源，校验成功后写入；
7. **处理并发**：为热点 key 加 single-flight、锁、TTL 抖动或后台刷新；
8. **建立失效流程**：版本切换优先，必要时补充主动失效和依赖索引；
9. **接入监控**：同时观察命中率、延迟、成本、陈旧度、正确性和隔离性；
10. **灰度发布**：先只读观测或小流量写入，确认没有错误复用后再扩大范围；
11. **准备旁路开关**：缓存出现异常时可以按任务、租户或版本快速关闭；
12. **定期复盘**：根据缓存命中质量、成本节省和数据合规要求调整策略。

## 14. 常见反模式

### 反模式一：只用用户问题作为 key

问题：忽略模型、prompt、权限、检索结果和 Schema，导致旧答案复用、跨用户泄露或格式不匹配。

改进：构造完整规范化请求对象，并把隐含输入纳入 key 或版本命名空间。

### 反模式二：缓存所有模型返回值

问题：将截断、解析失败、临时错误和不符合业务规则的结果长期传播。

改进：模型调用成功不等于业务结果成功；先做语法、Schema、安全和业务校验，再写正常缓存。

### 反模式三：把 TTL 设得极长来追求命中率

问题：文档、价格、政策或模型版本变化后仍然返回旧内容。

改进：根据错误代价设置 TTL，并通过版本命名空间或主动失效处理变更。

### 反模式四：命中缓存后跳过鉴权

问题：缓存被错误地当作权限判断，形成越权漏洞。

改进：鉴权始终在缓存读取前执行；命中后按风险等级再次检查数据权限和新鲜度。

### 反模式五：缓存带副作用的工具结果

问题：重放或误认为操作已经执行，造成重复扣款、重复发信或状态不一致。

改进：将普通响应缓存与业务幂等、执行记录和状态查询分开设计。

### 反模式六：只监控命中率

问题：命中率上升可能只是 key 过于粗糙，错误复用和数据泄露反而增加。

改进：同时监控错误复用、陈旧结果、跨租户命中、成本、延迟和回源峰值。

## 15. 实施清单

- [ ] 明确哪些任务可以缓存，哪些任务必须绕过共享缓存。
- [ ] 从精确响应缓存开始，为请求定义完整、稳定、可测试的 key。
- [ ] 将模型、prompt、消息、Schema、工具、检索版本和业务策略纳入 key 或命名空间。
- [ ] 将租户、用户、权限、区域和环境作为明确的隔离维度。
- [ ] 使用规范化序列化，不能依赖字典插入顺序或对象默认字符串。
- [ ] 先完成鉴权，再读取缓存；命中后仍按需要做权限和新鲜度检查。
- [ ] 只缓存通过语法、Schema、安全与业务校验的成功结果。
- [ ] 对流式响应等待正常结束后再缓存完整结果。
- [ ] 对工具调用区分纯推理、只读查询和带副作用的执行结果。
- [ ] 根据内容新鲜度和错误代价设置 TTL，而不是只追求高命中率。
- [ ] 通过版本化、主动失效、标签依赖或后台刷新处理数据和配置变更。
- [ ] 防止热点 key 击穿，并给锁、等待和回源设置超时。
- [ ] 对无效请求谨慎使用短 TTL 负缓存，不缓存临时 5xx、超时和鉴权失败。
- [ ] 监控命中率之外的延迟、成本、陈旧度、错误复用和隔离指标。
- [ ] 准备缓存旁路开关、灰度发布和回滚方案。
- [ ] 定期测试 key 完整性、并发行为、权限隔离和数据删除流程。

## 16. 核心结论

响应缓存的核心不是“把模型结果存起来”，而是可靠地回答三个问题：

1. **什么请求才算等价？**——缓存键必须包含所有决定结果、权限和新鲜度的因素；
2. **什么结果才允许复用？**——只有通过完整校验、没有副作用风险且仍在有效期内的结果才应进入正常缓存；
3. **结果什么时候不再可信？**——TTL、版本、依赖失效和权限变化都必须能够阻止旧结果继续传播。

在实践中，精确响应缓存、完整 key、版本化失效、严格校验和租户隔离通常比单纯提高命中率更重要。先从范围明确、容易回滚的场景开始，再根据指标和评测结果逐步引入语义缓存、后台刷新和更复杂的缓存层次。
