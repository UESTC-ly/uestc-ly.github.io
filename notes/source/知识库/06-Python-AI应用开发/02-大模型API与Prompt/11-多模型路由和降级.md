# 第 11 课：多模型路由和降级

> 本页依据通用的大模型应用工程实践整理；项目当前可见资料未提供特定厂商、模型名称或既有路由实现，因此示例使用抽象接口。

## 1. 为什么需要多模型路由

单一模型通常无法同时在质量、延迟、价格、上下文长度、工具调用、结构化输出和可用性上达到最优。**多模型路由（routing）**是在发起请求前，为任务选择合适模型或服务商的决策过程；**降级（fallback）**则是在首选路径不可用或不满足约束时，按预设策略切换到可兼容的后备路径。

目标不是“永远使用最强的模型”，而是在明确的质量下限内优化：

- 任务成功率和用户体验；
- P95/P99 延迟与可用性；
- 单请求与整体成本；
- 数据合规、地域和供应商风险；
- 输出契约的一致性。

## 2. 路由前先定义任务与约束

每个请求先被描述为一个任务配置，而不只是“一段 prompt”。常见字段如下：

| 维度 | 示例 | 作用 |
| --- | --- | --- |
| 任务类型 | 问答、摘要、代码、分类、视觉理解 | 筛选能力匹配的候选模型 |
| 质量等级 | `basic`、`standard`、`premium` | 决定评测阈值或预算 |
| 输出契约 | 纯文本、JSON Schema、工具调用 | 排除不兼容模型 |
| 上下文与模态 | token 数、图片、音频 | 检查窗口和输入能力 |
| 性能约束 | 最大延迟、最大单次成本 | 参与排序或直接拒绝 |
| 数据约束 | 租户、地区、敏感等级 | 限制可使用的服务与缓存 |

其中，**能力与合规约束应当先于价格排序**。例如，要求严格 JSON Schema 的任务不能仅因价格低而被路由到不支持该能力的模型。

## 3. 常见路由策略

### 3.1 静态规则路由

依据显式条件选择模型，例如“含图片使用多模态模型”“超过 32k token 使用长上下文模型”。它可解释、易审计，适合作为第一版和关键约束层，但规则过多会难维护。

### 3.2 评分/加权路由

对通过硬约束的候选模型计算分数：

$$
score(m)=w_qQ(m)-w_lL(m)-w_cC(m)+w_aA(m)
$$

其中 $Q$ 为离线评测质量，$L$ 为近期延迟，$C$ 为预估成本，$A$ 为近期可用性。质量、延迟等指标必须按任务类别和时间窗口更新，不能将不同类型任务的平均分混用。

### 3.3 级联路由

先尝试低成本模型；仅在结果置信度不足、校验失败或用户任务较难时升级到强模型。级联能降低成本，但要定义“升级信号”：分类置信度、规则检查、评审模型分数或用户显式重试等。不要把“模型自称有把握”作为唯一依据。

### 3.4 混合策略

生产中常见流程是：

1. 用硬规则过滤不兼容候选；
2. 按任务等级、预算和实时健康度排序；
3. 先调用首选模型；
4. 按失败类型决定重试、切换模型或直接返回可解释错误。

## 4. 降级不是简单地“换一个模型”

后备模型必须满足与首选路径相同的最小契约。应为每条任务链维护兼容性矩阵：

| 能力 | 降级时的要求 |
| --- | --- |
| JSON 输出 | 后备模型也支持结构化输出，或接入本地解析与校验流程 |
| 工具调用 | 工具参数 schema、调用语义和并行能力兼容 |
| 上下文 | 能容纳裁剪后的消息；必要时先摘要再调用 |
| 多模态 | 无多模态后备时，明确拒绝或先完成受控的文本化转换 |
| 安全策略 | 不因换模型而绕过内容审核、权限或数据隔离 |

还要区分不同故障：

- **超时、连接错误、5xx、限流**：通常先按第 10 课的退避策略重试；超过预算后可切换提供商或模型。
- **4xx 参数错误、鉴权错误、schema 不兼容**：重试通常无效，应修复调用配置或停止请求。
- **内容被安全策略拒绝**：不可通过换模型来绕过策略，应返回合规的提示。
- **输出质量不足或业务校验失败**：可按级联策略升级模型，但应限制次数并记录原因。

## 5. 一个抽象的实现骨架

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ModelProfile:
    name: str
    supports_json_schema: bool
    supports_tools: bool
    max_context_tokens: int
    estimated_cost: float


def select_candidates(task, profiles: list[ModelProfile]) -> list[ModelProfile]:
    compatible = [
        p for p in profiles
        if (not task.requires_json_schema or p.supports_json_schema)
        and (not task.requires_tools or p.supports_tools)
        and p.max_context_tokens >= task.input_tokens
    ]
    # 实际排序还应纳入近期健康度、延迟、任务评测分和租户策略。
    return sorted(compatible, key=lambda p: p.estimated_cost)


async def invoke_with_fallback(task, invoke, profiles):
    failures = []
    for profile in select_candidates(task, profiles):
        try:
            return await invoke(profile, task)
        except TransientProviderError as exc:
            failures.append({"model": profile.name, "reason": str(exc)})
            continue
    raise ServiceUnavailableError("所有兼容模型均暂不可用", failures)
```

这里的 `TransientProviderError`、`ServiceUnavailableError` 和 `invoke` 是应用自行定义的抽象。真实实现还应在单个模型内部设置超时、有限重试和总请求时间预算，避免后备链无限拉长用户等待时间。

## 6. Prompt、参数与模型版本管理

同一份 prompt 在不同模型上的表现可能不同。应把以下配置版本化并随调用记录：

- 模型 ID/快照、服务商与区域；
- system prompt、模板版本和 few-shot 样例版本；
- 温度、最大输出 token、工具定义与响应格式；
- 路由规则版本和最终选择理由。

建议将“业务意图”与“供应商请求格式”分层：上层产出统一的 `TaskRequest`，适配器再转换为具体 API 请求。这样替换服务商时不会将业务逻辑散落在各处。

## 7. 观测、评测与测试

每次调用至少记录结构化元数据，而不记录不必要的敏感原文：

- `request_id`、租户/环境、任务类别；
- 路由候选、最终模型、切换次数和切换原因；
- 延迟、输入/输出 token、成本估算、缓存命中情况；
- API 失败码、输出校验结果和用户反馈。

用固定评测集比较不同路由策略的任务成功率、平均成本和 P95 延迟；灰度发布新规则，并为关键任务保留人工审核或可回滚开关。测试至少覆盖：候选过滤、后备顺序、不可重试错误不切换、输出契约在降级后仍成立，以及全链路时间预算。
