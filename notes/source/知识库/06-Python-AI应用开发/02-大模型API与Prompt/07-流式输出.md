## 二、为什么需要流式输出

### 2.1 非流式调用

非流式调用会等待模型生成完整回答后，一次性返回结果：

```python
response = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "解释什么是 RAG"}],
)

print(response.choices[0].message.content)
```

它的优点是代码简单，拿到响应时内容通常已经完整，适合：

- 短文本生成；
- 后台批处理；
- 只关心最终结果的任务；
- 需要在返回前完成整体 JSON 校验的接口。

缺点是首字等待时间较长。即使模型已经生成了一部分内容，用户仍然看不到。

### 2.2 流式调用

流式调用会在生成过程中分批返回增量内容：

```text
请求发出
   ↓
等待首个数据块
   ↓
Chunk 1 → Chunk 2 → Chunk 3 → ... → 完成
```

它的主要价值是改善用户感知延迟。用户不必等整段回答生成完毕，就能开始阅读。

典型场景包括：

- 聊天机器人逐字展示回答；
- 长文章、代码或报告生成；
- Agent 执行过程的状态反馈；
- 服务端把模型结果实时转发给浏览器。

> 流式输出通常不能显著缩短“完整答案生成时间”，主要优化的是首个可见内容的等待时间和交互体验。

## 三、核心概念

### 3.1 Streaming

Streaming 表示服务端不等待整个响应完成，而是在同一个连接上持续发送数据块。

模型生成过程可以抽象为：

```text
完整答案 = delta_1 + delta_2 + delta_3 + ... + delta_n
```

其中每个 `delta` 都是相对于已接收内容的新增部分。

### 3.2 Chunk

Chunk 是 SDK 每次迭代得到的响应对象。一个 Chunk 不一定对应一个完整单词，也不保证只含一个 Token。

Chunk 可能包含：

- 角色信息；
- 文本增量；
- Tool Call 增量；
- 结束原因；
- 用量统计；
- 空内容或提供商扩展字段。

因此，不应假设每个 Chunk 都有可打印的文本。

### 3.3 Delta

在 Chat Completions 接口中，增量内容通常位于：

```python
chunk.choices[0].delta
```

普通文本一般位于：

```python
chunk.choices[0].delta.content
```

`delta` 表示“这次新增了什么”，不是到当前为止的完整答案。应用需要自行拼接。

### 3.4 SSE

许多 OpenAI 兼容接口底层使用 Server-Sent Events（SSE）传输流式结果。其 HTTP 响应常见类型为：

```text
Content-Type: text/event-stream
```

原始事件可能形如：

```text
data: {"choices":[{"delta":{"content":"你"}}]}

data: {"choices":[{"delta":{"content":"好"}}]}

data: [DONE]
```

使用官方或兼容 SDK 时，SDK 通常已经完成 SSE 解析，业务代码只需遍历 Chunk。

> SSE 是单向的服务端到客户端数据流。若业务需要真正的双向实时通信，可以考虑 WebSocket，但不要因为模型输出是流式的就默认必须使用 WebSocket。

## 五、同步流式输出

### 5.1 最小示例

同步客户端使用普通 `for` 循环读取流：

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["LLM_API_KEY"],
    base_url=os.environ["LLM_BASE_URL"],
)

stream = client.chat.completions.create(
    model=os.environ["LLM_MODEL"],
    messages=[
        {"role": "user", "content": "用三句话解释向量数据库。"}
    ],
    stream=True,
)

for chunk in stream:
    if not chunk.choices:
        continue

    content = chunk.choices[0].delta.content
    if content is not None:
        print(content, end="", flush=True)

print()
```

关键点：

1. 请求参数必须包含 `stream=True`；
2. 返回值不再是普通完整响应，而是可迭代的流；
3. `chunk.choices` 可能为空；
4. `delta.content` 可能是 `None`；
5. `flush=True` 可以避免终端缓冲导致内容不能及时显示。

### 5.2 一边展示，一边收集完整答案

真实应用通常既要实时展示，也要保留完整结果：

```python
parts: list[str] = []
finish_reason = None

stream = client.chat.completions.create(
    model=os.environ["LLM_MODEL"],
    messages=[{"role": "user", "content": "介绍 Python 生成器。"}],
    stream=True,
)

for chunk in stream:
    if not chunk.choices:
        continue

    choice = chunk.choices[0]
    content = choice.delta.content

    if content:
        parts.append(content)
        print(content, end="", flush=True)

    if choice.finish_reason is not None:
        finish_reason = choice.finish_reason

full_text = "".join(parts)

print("\n\n---")
print("结束原因：", finish_reason)
print("完整字符数：", len(full_text))
```

不要在循环中不断执行：

```python
full_text += content
```

少量文本问题不大，但对于长文本，先放入列表、最后 `"".join(parts)` 通常更清晰，也能避免大量重复字符串复制。

## 六、异步流式输出

Web 服务需要同时处理多个请求时，通常使用异步客户端：

```python
import asyncio
import os
from openai import AsyncOpenAI

client = AsyncOpenAI(
    api_key=os.environ["LLM_API_KEY"],
    base_url=os.environ["LLM_BASE_URL"],
)


async def main() -> None:
    stream = await client.chat.completions.create(
        model=os.environ["LLM_MODEL"],
        messages=[
            {"role": "user", "content": "解释 async for 的作用。"}
        ],
        stream=True,
    )

    parts: list[str] = []

    async for chunk in stream:
        if not chunk.choices:
            continue

        content = chunk.choices[0].delta.content
        if content:
            parts.append(content)
            print(content, end="", flush=True)

    print("\n完整结果：", "".join(parts))


if __name__ == "__main__":
    asyncio.run(main())
```

同步与异步的主要差异：

| 场景 | 客户端 | 读取方式 |
|---|---|---|
| 命令行脚本、简单任务 | `OpenAI` | `for chunk in stream` |
| FastAPI、高并发服务 | `AsyncOpenAI` | `async for chunk in stream` |

异步流式调用不会让单次模型生成变快，但能减少等待网络数据时对线程的占用，更适合 I/O 密集型并发服务。

## 七、结束原因与用量统计

### 7.1 `finish_reason`

流式传输接近结束时，Choice 中可能出现 `finish_reason`。常见值包括：

| 值 | 含义 |
|---|---|
| `stop` | 正常停止或命中停止序列 |
| `length` | 达到最大输出长度 |
| `tool_calls` | 模型决定调用工具 |
| `content_filter` | 内容受到安全策略限制，具体支持取决于提供商 |

处理结束原因非常重要。例如，`length` 表示回答可能被截断，不能把它当作完整结果直接入库。

### 7.2 Usage

某些 OpenAI 兼容服务支持在最后的 Chunk 中返回 Token 用量：

```python
stream = client.chat.completions.create(
    model=os.environ["LLM_MODEL"],
    messages=[{"role": "user", "content": "解释流式输出。"}],
    stream=True,
    stream_options={"include_usage": True},
)

usage = None

for chunk in stream:
    if chunk.usage is not None:
        usage = chunk.usage

    if not chunk.choices:
        continue

    content = chunk.choices[0].delta.content
    if content:
        print(content, end="", flush=True)

print("\nUsage:", usage)
```

注意：

- Usage 可能只在最后一个 Chunk 中出现；
- 带 Usage 的 Chunk 可能没有 `choices`；
- 部分兼容服务不支持 `stream_options`；
- 客户端提前断开时，应用可能拿不到最终 Usage；
- 计费应优先使用服务端账单或供应商返回的权威统计。

## 八、流式 Tool Calling

流式场景下，工具名称和参数也可能被拆成多个增量。例如，参数字符串可能依次到达：

```text
{"city"
:"北
京"}
```

因此，单个 Chunk 中的 `arguments` 往往不是合法完整 JSON。

### 8.1 正确处理原则

1. 按 Tool Call 的索引或 ID 聚合增量；
2. 拼接工具名称和参数字符串；
3. 等流结束或收到 `finish_reason="tool_calls"`；
4. 再执行 JSON 解析和 Schema 校验；
5. 校验通过后才能调用真实工具。

简化示例：

```python
import json

pending_calls: dict[int, dict[str, str | None]] = {}

for chunk in stream:
    if not chunk.choices:
        continue

    choice = chunk.choices[0]
    tool_call_deltas = choice.delta.tool_calls or []

    for call_delta in tool_call_deltas:
        item = pending_calls.setdefault(
            call_delta.index,
            {"id": None, "name": "", "arguments": ""},
        )

        if call_delta.id:
            item["id"] = call_delta.id

        if call_delta.function:
            if call_delta.function.name:
                item["name"] += call_delta.function.name
            if call_delta.function.arguments:
                item["arguments"] += call_delta.function.arguments

# 流结束后再解析，不能对半截 JSON 执行工具
for item in pending_calls.values():
    arguments = json.loads(item["arguments"] or "{}")
    print(item["name"], arguments)
```

> 绝不能在参数尚未接收完整时执行工具。JSON Schema 只能验证参数结构，业务代码仍需执行鉴权、权限控制、取值范围检查和审计。

## 九、流式 Structured Output

如果要求模型输出 JSON，流式过程中常会依次收到：

```text
{
  "name":
  "Alice",
  "age": 20
}
```

中间状态不是完整 JSON，所以以下做法通常不可靠：

```python
# 错误示意：每个增量到达后立刻解析
json.loads(current_partial_text)
```

更稳妥的策略是：

1. 前端可以实时展示普通文本或“正在生成”的状态；
2. 服务端持续拼接完整字符串；
3. 流正常结束后再解析 JSON；
4. 使用 JSON Schema 或数据模型执行整体校验；
5. 只有校验通过后，才把结果用于后续业务逻辑。

如果业务要求“页面边生成边得到结构化字段”，应设计专门的增量协议或使用支持增量 JSON 解析的组件，但仍需在最终阶段进行完整校验。

## 十、在 FastAPI 中转发模型流

下面使用 `StreamingResponse` 把模型增量以 SSE 形式发送给浏览器：

```python
import json
import os
from collections.abc import AsyncIterator

from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from openai import AsyncOpenAI

app = FastAPI()

client = AsyncOpenAI(
    api_key=os.environ["LLM_API_KEY"],
    base_url=os.environ["LLM_BASE_URL"],
)


def encode_sse(event: str, data: dict) -> str:
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event}\ndata: {payload}\n\n"


async def generate_answer(
    request: Request,
    prompt: str,
) -> AsyncIterator[str]:
    try:
        stream = await client.chat.completions.create(
            model=os.environ["LLM_MODEL"],
            messages=[{"role": "user", "content": prompt}],
            stream=True,
        )

        async for chunk in stream:
            if await request.is_disconnected():
                break

            if not chunk.choices:
                continue

            choice = chunk.choices[0]
            content = choice.delta.content

            if content:
                yield encode_sse("delta", {"content": content})

            if choice.finish_reason:
                yield encode_sse(
                    "finish",
                    {"reason": choice.finish_reason},
                )

    except Exception:
        # 对外返回稳定错误格式；详细异常写入服务端日志。
        yield encode_sse(
            "error",
            {"message": "模型生成失败，请稍后重试"},
        )


@app.get("/chat/stream")
async def chat_stream(request: Request, prompt: str):
    return StreamingResponse(
        generate_answer(request, prompt),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        },
    )
```

前端接收示意：

```javascript
const source = new EventSource(
  `/chat/stream?prompt=${encodeURIComponent("解释 RAG")}`
);

source.addEventListener("delta", (event) => {
  const data = JSON.parse(event.data);
  document.querySelector("#answer").textContent += data.content;
});

source.addEventListener("finish", (event) => {
  console.log("生成结束", JSON.parse(event.data));
  source.close();
});

source.addEventListener("error", () => {
  source.close();
});
```

生产环境还需要考虑：

- 身份认证与授权；
- 不要通过 GET 查询参数传递敏感内容；
- 请求体较复杂时，可以用 `fetch` 读取流，或先 POST 创建任务再订阅 SSE；
- 反向代理缓冲设置；
- 心跳与空闲连接超时；
- 客户端断开后的上游取消；
- 并发数限制和资源回收；
- 错误日志、Trace ID 与敏感字段脱敏。

## 十一、超时、取消与重试

### 11.1 流式请求有多个时间维度

流式调用不能只关注一个总超时，至少应区分：

1. **连接超时**：与服务端建立连接的最大等待时间；
2. **首块超时**：请求发出后，等待第一个有效 Chunk 的时间；
3. **块间空闲超时**：两个 Chunk 之间允许的最大间隔；
4. **业务总超时**：整个生成过程允许持续的最长时间。

不同 SDK 和 HTTP 客户端对这些超时的配置方式不同，需要结合所用版本验证。

### 11.2 客户端取消

当用户点击“停止生成”或关闭页面时，应尽快：

1. 停止前端读取；
2. 通知应用服务取消任务；
3. 关闭或退出上游流；
4. 记录该响应是用户取消，而不是正常完成；
5. 决定是否保留已经生成的部分内容。

如果下游已经断开，但服务端仍持续读取模型流，会浪费连接、Token 和费用。

### 11.3 重试边界

流式重试比非流式更复杂：

- **收到首个 Chunk 之前失败**：通常可以按网络错误、限流和临时服务错误进行有限重试；
- **已经向用户发送部分内容后失败**：不能直接无提示重试，否则可能产生重复或前后不一致的文本；
- **工具或写操作已经执行后失败**：必须结合幂等键、执行记录和业务状态判断，不能盲目重放。

大多数模型接口不保证从中断位置无缝续传。常见产品策略是：

- 明确提示“生成已中断”；
- 保留已生成内容；
- 允许用户重新生成；
- 或把已有内容作为上下文，请模型继续，但要接受衔接并不完全可靠。

## 十二、背压与并发控制

### 12.1 什么是背压

如果模型产生数据的速度高于下游消费速度，就会出现背压。例如：

- 浏览器网络很慢；
- 前端渲染频率过高；
- 服务端对每个字符都执行数据库写入；
- 日志系统同步阻塞。

应避免无界缓存。可采用：

- 有界队列；
- 按时间或字符数合并小 Chunk；
- 限制单用户并发流数量；
- 客户端断开后立即停止上游读取；
- 将持久化与展示路径合理解耦。

### 12.2 并发控制

异步不等于无限并发。每个活跃流都会占用：

- 上游 API 连接；
- 服务端文件描述符和内存；
- 模型服务并发额度；
- Token 与费用预算。

可以用信号量限制并发：

```python
import asyncio

stream_semaphore = asyncio.Semaphore(20)


async def limited_stream_call():
    async with stream_semaphore:
        # 在这里创建并消费模型流
        ...
```

信号量应覆盖真正占用稀缺资源的阶段。对流式请求而言，通常需要覆盖从建立上游流到流消费完成或取消的整个过程。

## 十三、流式输出的可观测性

流式接口只记录“总耗时”是不够的。建议至少采集：

| 指标 | 含义 |
|---|---|
| TTFT | Time To First Token/Chunk，从请求开始到首个有效内容的时间 |
| 总时长 | 从请求开始到正常结束或失败的时间 |
| 输出 Token 数 | 衡量输出规模与成本 |
| 生成速率 | 每秒输出 Token 数或字符数，仅作近似体验指标 |
| 中断率 | 因网络、服务错误、超时或用户取消而中断的比例 |
| 首块前失败率 | 尚未输出内容就失败的比例 |
| 首块后失败率 | 已输出部分内容后失败的比例 |
| 活跃流数量 | 当前正在占用资源的流式请求数 |

日志建议记录：

- 请求 ID 和 Trace ID；
- 模型与供应商；
- 开始、首块、结束时间；
- `finish_reason`；
- Usage（如果可用）；
- 错误类别和重试次数；
- 是否由用户主动取消。

不要默认记录完整 Prompt、完整回答、工具参数或敏感个人信息。应根据业务要求进行脱敏、采样和访问控制。

## 十四、常见误区

### 误区 1：一个 Chunk 就是一个 Token

错误。Chunk 是传输和 SDK 封装的数据单元，可能含零个、一个或多个 Token 对应的文本。

### 误区 2：每个 Chunk 都能读取到文本

错误。它可能只包含角色、结束原因、Usage、Tool Call 增量或空 Choice。

### 误区 3：流式输出能降低模型费用

通常不能。费用主要取决于输入和输出 Token。流式输出主要改善交互体验，还可能因为连接管理和代理转发增加工程复杂度。

### 误区 4：收到部分 JSON 就可以执行

错误。Structured Output 和工具参数在流式过程中可能不是合法完整 JSON，必须先聚合，再解析和校验。

### 误区 5：连接中断后直接自动重试即可

错误。如果已经展示部分内容或执行过工具，直接重试可能导致文本重复、重复扣费或业务操作重复。

### 误区 6：使用异步客户端就可以无限并发

错误。异步只能提高等待 I/O 时的资源利用率，仍需考虑连接数、限流、模型配额和内存。

### 误区 7：前端关闭后，服务端会自动停止所有工作

不一定。应用需要检测断连并主动结束上游读取，否则模型可能继续生成。

### 误区 8：SSE 和 WebSocket 是同一个东西

错误。SSE 主要是服务端到客户端的单向事件流；WebSocket 是全双工通信协议。

## 十六、自测题

1. 非流式输出和流式输出最主要的体验差异是什么？
2. 为什么不能假设一个 Chunk 对应一个 Token？
3. 为什么读取 `delta.content` 前需要判空？
4. 为什么 Tool Calling 的参数不能在每个 Chunk 到达时立即解析并执行？
5. `finish_reason="length"` 说明了什么？
6. 为什么有些携带 Usage 的 Chunk 可能没有 `choices`？
7. 流已经向用户输出一半后发生网络错误，为什么不能盲目自动重试？
8. TTFT 与总生成时长分别衡量什么？
9. 浏览器关闭页面后，服务端为什么还要主动取消上游流？
10. 异步流式调用为什么仍然需要并发限制？

### 参考答案

1. 流式输出能更早展示增量内容，降低用户感知的首字等待时间。
2. Chunk 是传输数据块，SDK 或服务端可能合并、拆分 Token，也可能发送不含文本的控制信息。
3. Chunk 可能只携带角色、工具调用、结束原因或 Usage，`content` 可能为 `None`。
4. 参数可能只是半截 JSON；应先完整聚合，再解析、校验和执行。
5. 输出达到长度上限，回答可能被截断。
6. 服务可能使用单独的最终 Chunk 返回 Usage，而该 Chunk 不包含普通候选内容。
7. 重试可能产生重复文本、不一致回答、重复费用，甚至重复执行有副作用的操作。
8. TTFT 衡量首个有效内容出现前的等待时间；总时长衡量整个请求从开始到结束的时间。
9. 下游断开不一定自动终止上游生成，不主动取消会继续占用连接和费用。
10. 每条流仍会占用连接、内存、模型并发额度和 Token 预算。

## 十七、本课小结

流式输出的核心并不是“逐字打印”，而是正确处理一个长期存在、持续产生增量的请求生命周期：

```text
创建请求
  → 等待首块
  → 持续读取 Delta
  → 展示并聚合内容
  → 处理结束原因与 Usage
  → 正常完成、失败或取消
  → 释放资源并记录指标
```

开发时应重点记住：

- `stream=True` 开启流式响应；
- 同步代码使用 `for`，异步代码使用 `async for`；
- Chunk 不等于 Token，也不一定包含文本；
- 完整文本需要应用自行聚合；
- Tool Call 和 JSON 必须等增量完整后再解析、校验和执行；
- 首块前失败与首块后失败应采用不同重试策略；
- 客户端取消、背压、并发控制和可观测性是生产环境的必修内容。
