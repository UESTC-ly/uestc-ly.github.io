# 第一章：Lambda 表达式

## 1. 为什么一定要学 Lambda

如果你学到 C++ 后面，会发现很多代码越来越像这样：

```cpp
sort(v.begin(), v.end(), [](int a, int b) {
    return a > b;
});
```

第一次看到时，很多人会懵：
- `[]` 是什么？
- 这个像函数，又不像普通函数的东西是什么？
- 为什么它能直接写在参数里？

这就是 **Lambda 表达式**。

它是现代 C++ 里非常重要的一部分，因为它解决了一个核心问题：

> **“我只想临时写一个很短的小函数，不想专门再定义一个普通函数或函数对象类。”**

所以，Lambda 的本质可以先记成一句话：

> **Lambda = 可以写在代码里的匿名小函数对象。**

---

## 2. 一句话抓本质

### 2.1 最短定义
**Lambda 表达式本质上是“匿名函数对象”。**

注意这句话里有两个关键词：

1. **匿名**：没有名字
2. **函数对象**：本质上更接近“对象”，不是普通函数

也就是说：
- 它看起来像函数
- 用起来像函数
- 但底层更像一个“重载了 `operator()` 的对象”

---

## 3. 为什么会有 Lambda

在 Lambda 出现之前，如果你想把“一个小逻辑”传给算法，比如排序规则、筛选条件、回调逻辑，通常有三种做法：

### 3.1 写普通函数

```cpp
bool cmp(int a, int b) {
    return a > b;
}

sort(v.begin(), v.end(), cmp);
```

问题：
- 如果这个比较逻辑只用一次，专门写个函数很啰嗦
- 逻辑离使用位置太远，不直观

---

### 3.2 写函数对象（仿函数）

```cpp
struct Cmp {
    bool operator()(int a, int b) const {
        return a > b;
    }
};

sort(v.begin(), v.end(), Cmp());
```

问题：
- 功能是有了，但太重了
- 只为了写一个小规则，结果要写一个类

---

### 3.3 Lambda 的优势

```cpp
sort(v.begin(), v.end(), [](int a, int b) {
    return a > b;
});
```

优点：
- 逻辑就写在使用处
- 短小
- 易读
- 很适合“只用一次的小函数逻辑”

所以你要记住：

> **Lambda 的出现，本质上是为了让“临时函数逻辑”写起来更自然。**

---

## 4. Lambda 的基本语法

先看最常见的结构：

```cpp
[capture](params) -> return_type {
    body;
}
```

它由 4 部分组成：

1. `capture`：捕获列表
2. `params`：参数列表
3. `return_type`：返回类型（很多时候可省略）
4. `body`：函数体

---

## 5. 先从最简单的 Lambda 开始

### 5.1 不带参数

```cpp
[] {
    cout << "hello lambda" << endl;
};
```

这只是定义了一个 Lambda，但**还没有调用**。

调用方式：

```cpp
auto f = [] {
    cout << "hello lambda" << endl;
};

f();
```

输出：

```cpp
hello lambda
```

---

### 5.2 带参数

```cpp
auto add = [](int a, int b) {
    return a + b;
};

cout << add(3, 5) << endl;
```

输出：

```cpp
8
```

这时你可以把它理解成：

```cpp
int add(int a, int b) {
    return a + b;
}
```

只不过 Lambda 没有函数名，所以通常用 `auto` 接住。

---

## 6. Lambda 为什么通常要用 `auto` 接收

因为 Lambda 的类型是编译器生成的、匿名的、很长的、你通常写不出来。

比如：

```cpp
auto f = [](int x) { return x * 2; };
```

这里的 `f` 不是“函数指针”，而是一个**闭包对象**。

所以一般写法都是：

```cpp
auto func = [](...) { ... };
```

记忆：

> **Lambda 没名字，所以通常交给 `auto`。**

---

## 7. 最核心部分：捕获列表 `[]`

这是 Lambda 最重要、也是最容易考的部分。

因为 Lambda 经常要使用外部变量。

例如：

```cpp
int x = 10;
auto f = [x]() {
    cout << x << endl;
};
```

这里 `[x]` 的意思是：

> **把外部变量 `x` 捕获进 Lambda 里。**

如果你不捕获，Lambda 默认不能直接用外部局部变量。

---

## 8. 为什么要“捕获”

Lambda 本质上是一个独立对象。

而函数体里如果想访问外部局部变量，比如：

```cpp
int x = 10;
```

那它必须先“拿到 x”。这个“拿到”的过程，就叫 **捕获**。

你可以把它理解成：

> **Lambda 想用外部变量，得先声明“我要带哪些东西进去”。**

---

## 9. 捕获的几种基本方式

---

### 9.1 值捕获 `[x]`

```cpp
int x = 10;
auto f = [x]() {
    cout << x << endl;
};

f();
```

输出：

```cpp
10
```

#### 本质
值捕获是：

> **把外部变量的一个副本拷贝进 Lambda 对象里。**

所以后面即使外部 `x` 变了，Lambda 里的那个 `x` 不一定变。

例如：

```cpp
int x = 10;
auto f = [x]() {
    cout << x << endl;
};

x = 100;
f();
```

输出仍然是：

```cpp
10
```

因为 Lambda 捕获的是当时那个值的副本。

#### 记忆
> **值捕获：拷贝一份，外面再变，里面不跟着变。**

---

### 9.2 引用捕获 `[&x]`

```cpp
int x = 10;
auto f = [&x]() {
    cout << x << endl;
};

x = 100;
f();
```

输出：

```cpp
100
```

#### 本质
引用捕获是：

> **Lambda 里不存副本，而是直接引用外部那个变量本身。**

所以外部变了，里面看到的也是新的值。

#### 记忆
> **引用捕获：共用同一个变量。**

---

### 9.3 全部按值捕获 `[=]`

```cpp
int a = 1, b = 2;
auto f = [=]() {
    cout << a + b << endl;
};
```

含义：

> 用到的外部变量，默认都按值捕获。

---

### 9.4 全部按引用捕获 `[&]`

```cpp
int a = 1, b = 2;
auto f = [&]() {
    a++;
    b++;
};
```

含义：

> 用到的外部变量，默认都按引用捕获。

---

### 9.5 混合捕获 `[=, &x]`

```cpp
int x = 10, y = 20;
auto f = [=, &x]() {
    x++;
    cout << x << " " << y << endl;
};
```

含义：
- 默认按值捕获
- 但 `x` 特别指定按引用捕获

这个语法很常见。

---

## 10. 值捕获和引用捕获的真正区别

这是面试和选择题高频点。

| 方式     | 本质    | 外部变量变化是否影响 Lambda 内部 | 是否能改外部变量  |
| ------ | ----- | -------------------- | --------- |
| `[x]`  | 拷贝副本  | 不影响                  | 不能直接改外部变量 |
| `[&x]` | 引用原变量 | 会影响                  | 可以改外部变量   |

你一定要会下面这个判断：

### 题型 1

```cpp
int x = 10;
auto f = [x]() {
    cout << x << endl;
};
x = 20;
f();
```

输出：`10`

---

### 题型 2

```cpp
int x = 10;
auto f = [&x]() {
    cout << x << endl;
};
x = 20;
f();
```

输出：`20`

---

## 11. 为什么值捕获默认不能修改捕获变量

看这个：

```cpp
int x = 10;
auto f = [x]() {
    x++; // 报错
};
```

为什么？

因为默认情况下，Lambda 的 `operator()` 是 `const` 的。

也就是说，值捕获进来的成员，默认在这个调用过程中当成“不能改”。

---

## 12. `mutable` 的作用

如果你想修改**值捕获进来的副本**，要加 `mutable`。

```cpp
int x = 10;
auto f = [x]() mutable {
    x++;
    cout << x << endl;
};

f();
cout << x << endl;
```

输出：

```cpp
11
10
```

注意：
- 改的是 Lambda 内部那份副本
- 外部原变量 `x` 没变

#### 记忆
> **`mutable` 只能让你改“值捕获的副本”，改不了外面的原变量。**

---

## 13. Lambda 返回类型

很多时候返回类型可以自动推导：

```cpp
auto add = [](int a, int b) {
    return a + b;
};
```

但有时也可以显式写：

```cpp
auto f = [](int x) -> double {
    return x / 2.0;
};
```

### 什么时候显式写更好
1. 返回逻辑复杂
2. 多个 `return` 分支类型不够直观
3. 想强调结果类型

---

## 14. Lambda 最常见的使用场景

---

### 14.1 配合 `sort`

```cpp
vector<int> v = {3, 1, 5, 2};
sort(v.begin(), v.end(), [](int a, int b) {
    return a > b;
});
```

这是降序排序。

#### 本质
`sort` 第三个参数需要一个“比较规则”。
Lambda 就非常适合临时写这种小规则。

---

### 14.2 配合 `for_each`

```cpp
vector<int> v = {1, 2, 3};
for_each(v.begin(), v.end(), [](int x) {
    cout << x << " ";
});
```

输出：

```cpp
1 2 3
```

---

### 14.3 配合 `find_if`

```cpp
vector<int> v = {1, 3, 5, 8, 9};
auto it = find_if(v.begin(), v.end(), [](int x) {
    return x % 2 == 0;
});
```

意思：找到第一个偶数。

---

### 14.4 作为回调函数

比如以后学线程、异步、GUI、事件处理时，经常要传一个“执行逻辑”。
这时 Lambda 很方便。

```cpp
auto callback = []() {
    cout << "button clicked" << endl;
};
```

---

## 15. Lambda 和普通函数的区别

| 项目 | Lambda | 普通函数 |
|---|---|---|
| 是否有名字 | 通常没有 | 有 |
| 能否写在局部 | 可以 | 一般不能在函数内部定义普通函数 |
| 能否捕获外部局部变量 | 可以 | 不可以 |
| 是否适合一次性小逻辑 | 非常适合 | 不够方便 |

### 最关键区别
> **普通函数不能直接“带走”外部局部变量，Lambda 可以通过捕获做到。**

这就是 Lambda 最大的价值之一。

---

## 16. Lambda 和函数指针的区别

很多人会混。

### 16.1 无捕获 Lambda 可以转函数指针

```cpp
auto f = [](int x) {
    return x * 2;
};
```

因为它没有捕获外部变量，所以它可以转换成函数指针使用。

但如果有捕获：

```cpp
int a = 10;
auto f = [a](int x) {
    return x + a;
};
```

这种一般**不能直接当普通函数指针**，因为它内部带状态。

#### 记忆
> **无捕获 Lambda 更像函数；有捕获 Lambda 更像对象。**

---

## 17. Lambda 的本质：闭包对象

这是进阶理解，但非常重要。

比如：

```cpp
int x = 10;
auto f = [x]() {
    return x + 1;
};
```

编译器大致会把它理解成类似这样：

```cpp
class __Lambda {
private:
    int x;
public:
    __Lambda(int val) : x(val) {}

    int operator()() const {
        return x + 1;
    }
};
```

然后：

```cpp
auto f = __Lambda(x);
```

所以你要真正记住：

> **Lambda 本质不是普通函数，而是“带 `operator()` 的匿名类对象”。**

这也是为什么：
- 它能保存捕获变量
- 它能像函数一样调用
- 它又有对象语义

---

## 18. `[this]` 捕获

在类的成员函数里，经常会用到这个。

```cpp
class Test {
public:
    int x = 10;

    void func() {
        auto f = [this]() {
            cout << x << endl;
        };
        f();
    }
};
```

这里 `[this]` 的意思是：

> **捕获当前对象的 `this` 指针。**

这样 Lambda 里就能访问成员变量和成员函数。

### 易混点
`[this]` 捕获的不是“成员变量副本”，而是当前对象指针。
所以如果对象 later 已销毁，而 Lambda 还被拿去调用，就有风险。

---

## 19. `[=]`、`[&]` 在类里要更小心

在成员函数里写：

```cpp
[=]
```

很多人以为是“把所有成员变量都按值捕获”。

其实更准确地说：
- 它会让你可以访问当前对象相关内容
- 但本质上经常绕不过 `this`

所以在类成员函数中，涉及异步、回调、延迟执行时，`this` 生命周期问题要特别小心。

#### 记忆
> **类里写 Lambda，真正危险的常常不是语法，而是对象生命周期。**

---

## 20. Lambda 高危坑点

---

### 20.1 引用捕获悬空

```cpp
auto makeFunc() {
    int x = 10;
    return [&]() {
        cout << x << endl;
    };
}
```

这是危险的。

因为函数返回后，`x` 已经销毁了。
Lambda 里引用的是悬空引用。

#### 记忆
> **引用捕获最怕变量先死，Lambda 后用。**

---

### 20.2 `[&]` 虽方便，但容易误伤

```cpp
int a = 1, b = 2, c = 3;
auto f = [&]() {
    a++;
    b++;
    c++;
};
```

问题：
- 看起来简洁
- 但你可能不清楚到底捕获了哪些变量
- 代码变大后容易引发隐式副作用

所以工程里通常更鼓励：

```cpp
[&a, &b]
```

明确写出真正需要的变量。

---

### 20.3 值捕获不是“绑定”，是“拷贝当时的值”

```cpp
int x = 10;
auto f = [x]() {
    cout << x << endl;
};
x = 20;
f();
```

输出仍是 `10`。

这个坑非常常见。

---

### 20.4 `mutable` 改不到外部变量

很多人以为：

```cpp
[x]() mutable { x++; }
```

会把外面也改掉。
其实不会。

改的是内部副本。

---

## 21. Lambda 常见题型总结

---

### 题型1：判断输出

```cpp
int x = 5;
auto f = [x]() mutable {
    x++;
    cout << x << endl;
};

f();
cout << x << endl;
```

输出：

```cpp
6
5
```

原因：
- Lambda 内部改的是副本
- 外部 `x` 没变

---

### 题型2：判断是否能编译

```cpp
int x = 5;
auto f = [x]() {
    x++;
};
```

不能编译。因为默认值捕获是只读副本，要改得加 `mutable`。

---

### 题型3：判断引用捕获风险

```cpp
auto f = []() {
    int x = 10;
    return [&]() { cout << x << endl; };
};
```

返回的 Lambda 存在悬空引用风险。

---

## 22. Lambda 怎么记最省力

你可以把 Lambda 分成 4 个层次记忆：

### 第一层：它是什么
> **匿名函数对象**

### 第二层：最常见用途
> **给算法、回调、临时逻辑传一个小函数**

### 第三层：最关键语法
> **`[]` 是捕获列表，决定能不能用外部变量，以及怎么用**

### 第四层：最高频坑
> **值捕获是副本；引用捕获会受生命周期影响；有名字的右值引用是左值；Lambda 本质是对象**

---

# 第二章：回调函数

## 1. 什么是回调函数

先直接给定义：

> **回调函数，就是“把一个函数交给别人，在合适的时候再调用”。**

这句话非常重要。

回调里有两个角色：

1. **提供函数的人**
2. **调用函数的人**

也就是说：
- 你先把一个函数传出去
- 对方先收下
- 等到某个时机成熟，再调用它

所以回调的本质不是“函数”，而是：

> **一种“先注册，后调用”的机制。**

---

## 2. 为什么会有回调函数

如果没有回调，很多逻辑会写死。

例如：

```cpp
void doTask() {
    cout << "任务完成后固定打印一句话" << endl;
}
```

问题是：
- 如果这次任务完成后你想打印日志
- 下次你想发通知
- 再下次你想更新界面

那 `doTask()` 内部逻辑就得不断改。

这很不灵活。

更好的方式是：

> **“任务怎么做” 和 “做完之后干什么” 分开。**

于是就有了回调：

```cpp
void doTask(void (*callback)()) {
    cout << "正在执行任务..." << endl;
    callback();
}
```

这样：
- `doTask` 负责做任务
- `callback` 负责任务结束后的动作

这就是回调的价值：

> **把变化的部分交给外部。**

---

## 3. 一句话抓本质

### 3.1 最短理解
**回调函数 = 传进去的函数 + 将来某时被调用。**

### 3.2 再换一种说法
**回调不是某种特殊函数类型，而是一种使用方式。**

也就是说：
- 普通函数可以作为回调
- Lambda 可以作为回调
- 函数对象可以作为回调
- `std::function` 可以包装回调

所以你一定要分清：

| 概念 | 含义 |
|---|---|
| 函数 | 一段可执行逻辑 |
| 回调函数 | 被传给别人、由别人之后再调用的函数 |

记忆：

> **回调的重点不在“它长什么样”，而在“它什么时候、被谁调用”。**

---

## 4. 最基础例子：普通函数做回调

### 4.1 代码

```cpp
#include <iostream>
using namespace std;

void onFinish() {
    cout << "任务完成，执行回调" << endl;
}

void doTask(void (*callback)()) {
    cout << "正在执行任务..." << endl;
    callback();
}

int main() {
    doTask(onFinish);
    return 0;
}
```

### 4.2 输出

```cpp
正在执行任务...
任务完成，执行回调
```

### 4.3 怎么理解

流程是：
1. `main` 调用 `doTask(onFinish)`
2. `onFinish` 被作为参数传进 `doTask`
3. `doTask` 先完成自己的逻辑
4. 然后调用 `callback()`
5. 也就是调用 `onFinish()`

这就是最标准的回调流程。

---

## 5. 回调最关键的特征

你要抓住这 3 点：

### 5.1 函数先作为参数传进去
比如：

```cpp
doTask(onFinish);
```

### 5.2 真正调用发生在别的函数内部
比如：

```cpp
callback();
```

### 5.3 调用时机由“接收方”决定
比如：
- 任务完成后调用
- 按钮点击后调用
- 数据到达后调用
- 排序比较时调用

所以回调最本质的地方是：

> **调用权交给了别人。**

---

## 6. 回调为什么容易和普通“函数调用”混淆

很多人会觉得：

```cpp
foo();
```

和

```cpp
callback();
```

不都是调函数吗？

区别在于：

### 普通函数调用
你自己直接决定现在就调。

### 回调函数
你先把函数交出去，之后什么时候调、在哪里调，是由对方决定的。

#### 对比

```cpp
onFinish();   // 自己立即调用
```

```cpp
doTask(onFinish);  // 传给别人，让别人以后再调
```

记忆：

> **直接调用 = 自己掌控时机；回调 = 把时机交给别人。**

---

## 7. 带参数的回调函数

很多时候，回调不是简单“通知你一下”，而是还要把信息传回来。

### 7.1 代码

```cpp
#include <iostream>
using namespace std;

void showResult(int result) {
    cout << "结果是：" << result << endl;
}

void calculate(int a, int b, void (*callback)(int)) {
    int sum = a + b;
    callback(sum);
}

int main() {
    calculate(3, 5, showResult);
    return 0;
}
```

### 7.2 输出

```cpp
结果是：8
```

### 7.3 本质
这里回调的作用是：

> **主逻辑做完后，把结果交给外部处理。**

所以你可以把回调理解成：
- 有时候是“通知”
- 有时候是“通知 + 带数据返回”

---

## 8. 函数指针和回调的关系

传统 C/C++ 里，最经典的回调实现方式就是：

> **函数指针**

比如：

```cpp
void (*callback)()
```

它表示：
- `callback` 是一个指针
- 指向“无参数、无返回值”的函数

### 8.1 为什么函数指针常用于回调
因为函数要想“被传来传去”，就得有一种方式表示它。
在传统写法里，这种方式就是函数指针。

### 8.2 经典格式

```cpp
返回值类型 (*指针名)(参数类型列表)
```

例如：

```cpp
int (*f)(int, int);
```

意思：
- `f` 是函数指针
- 指向一个参数为 `(int, int)`
- 返回值为 `int` 的函数

---

## 9. 函数指针为什么看着难
因为语法太绕。

例如：

```cpp
void doTask(void (*callback)())
```

很多人读不懂。

你可以拆开看：

### 第一步：看名字
`callback`

### 第二步：看 `(*callback)`
说明它是指针

### 第三步：看后面的 `()`
说明这个指针指向的是函数

### 第四步：看前面的 `void`
说明这个函数返回 `void`

所以它表示：

> `callback` 是一个指向“无参、返回 `void` 的函数”的指针。

---

## 10. 用 `typedef` / `using` 简化回调类型

为了不让函数指针太难看，通常会起别名。

### 10.1 `typedef` 写法

```cpp
typedef void (*Callback)();
```

然后：

```cpp
void doTask(Callback cb) {
    cb();
}
```

---

### 10.2 `using` 写法（现代 C++ 更推荐）

```cpp
using Callback = void (*)();
```

这样代码更清晰。

记忆：

> **回调本身不复杂，复杂的是函数指针语法；能起别名就起别名。**

---

## 11. Lambda 作为回调

现代 C++ 里，更常用的是：

> **用 Lambda 当回调。**

因为它更短、更自然。

### 11.1 例子

```cpp
#include <iostream>
using namespace std;

void doTask(void (*callback)()) {
    cout << "任务处理中..." << endl;
    callback();
}

int main() {
    doTask([]() {
        cout << "Lambda 回调执行了" << endl;
    });
    return 0;
}
```

### 11.2 优势
- 不用专门写一个额外函数
- 临时逻辑可以直接写在调用处
- 更适合“只用一次”的回调

---

## 12. 为什么有的 Lambda 能做回调，有的不能

这是高频易错点。

### 12.1 无捕获 Lambda
可以转换成普通函数指针。

```cpp
[]() {
    cout << "hello" << endl;
}
```

因为它不依赖外部状态。

---

### 12.2 有捕获 Lambda
通常**不能直接转函数指针**。

```cpp
int x = 10;
auto f = [x]() {
    cout << x << endl;
};
```

为什么？

因为它内部带状态，本质是对象，不是纯函数地址。

#### 记忆
> **无捕获 Lambda 像函数；有捕获 Lambda 像对象。**

---

## 13. 更通用的回调：`std::function`

### 13.1 先说结论
如果你想把“任何像函数一样能被调用的东西”统一装进一个变量里，然后当回调传来传去，最常见的标准方案就是：

> **`std::function`**

它解决的问题很简单：

> **我不想只接收“纯函数指针”，我希望普通函数、Lambda、仿函数、`bind` 结果都能作为回调传进来。**

---

### 13.2 先理解它到底是干什么的

你可以把 `std::function` 理解成一个“**可调用对象的通用盒子**”。

这个盒子里可以装：
- 普通函数
- 无捕获 Lambda
- 有捕获 Lambda
- 仿函数（重载了 `operator()` 的对象）
- `std::bind` 绑定后的结果

换句话说：

> **函数指针像“只会装纯函数的窄盒子”，`std::function` 像“能装很多种可调用对象的通用盒子”。**

---

### 13.3 为什么函数指针不够用

先看函数指针：

```cpp
void doTask(void (*callback)()) {
    callback();
}
```

它的问题是：

1. **太窄**：只能接普通函数、无捕获 Lambda
2. **表达力弱**：不能直接接有状态的回调
3. **不够现代**：很多 C++ 风格的可调用对象装不进去

例如：

```cpp
int x = 10;
auto f = [x]() {
    cout << x << endl;
};
```

这是**有捕获 Lambda**，它不是普通函数指针能直接表达的。

所以就需要 `std::function`。

---

### 13.4 `std::function` 的基本写法

```cpp
#include <iostream>
#include <functional>
using namespace std;

void doTask(function<void()> callback) {
    cout << "任务处理中..." << endl;
    callback();
}

int main() {
    int x = 10;
    doTask([x]() {
        cout << "x = " << x << endl;
    });
    return 0;
}
```

### 13.5 这段代码为什么能工作

因为 `std::function<void()>` 表示：
- 它要接收一个**没有参数、返回值是 void** 的可调用对象
- 不管这个可调用对象是普通函数、Lambda 还是仿函数，只要“能像函数一样被调用”，都可以装进去

所以：

```cpp
doTask([x]() { ... });
```

之所以可以，是因为 Lambda 被 `std::function` 包装接住了。

---

### 13.6 你一定要会读这个模板

```cpp
function<void()>
```

它的意思是：

> **一个“返回值为 void、参数列表为空”的通用可调用对象。**

如果换成：

```cpp
function<int(int, int)>
```

那它表示：

> **一个“接收两个 int，返回 int”的可调用对象。**

比如：

```cpp
function<int(int, int)> add = [](int a, int b) {
    return a + b;
};
```

你可以把它当成一种“**统一接口类型**”。

---

### 13.7 `std::function` 和普通函数指针的核心区别

| 项目            | 函数指针 | `std::function` |
| ------------- | ---- | --------------- |
| 能否接普通函数       | 可以   | 可以              |
| 能否接无捕获 Lambda | 可以   | 可以              |
| 能否接有捕获 Lambda | 通常不行 | 可以              |
| 能否接仿函数        | 不方便  | 可以              |
| 是否更通用         | 否    | 是               |

一句话记忆：

> **函数指针只能接“纯函数”，`std::function` 能接“更广义的可调用对象”。**

---

### 13.8 什么叫“可调用对象”

这是理解 `std::function` 的关键。

所谓可调用对象，就是**你能像函数一样写 `obj()` 去调用它**的东西。

常见可调用对象有：
1. 普通函数
2. 函数指针
3. Lambda
4. 仿函数对象
5. `std::bind` 返回的对象

例如：

```cpp
struct Foo {
    void operator()() const {
        cout << "hello" << endl;
    }
};

Foo f;
f(); // 可以像函数一样调用
```

这种对象就叫可调用对象。

所以 `std::function` 的本质就是：

> **把“可调用对象”统一包装成一种标准接口。**

---

### 13.9 为什么 `std::function` 叫“包装器”

因为它不是把函数“复制成另一个函数”，而是把不同类型的可调用对象“装进统一容器里”。

你可以把它想成：
- 外面是一层统一接口
- 里面可以放不同类型的调用实体
- 你只管 `callback()`，不管里面到底是啥

这就是“类型擦除”的思想。

---

### 13.10 类型擦除先有个直观理解

你可以先不背术语，只记住感觉：

> **`std::function` 会把“具体类型是谁”这件事隐藏起来，只保留“我能被调用”这个能力。**

比如：
- 里面到底装的是普通函数？Lambda？仿函数？
- 外面一般不关心
- 外面只关心它能不能调用

这就是它特别适合做回调的原因。

---

### 13.11 为什么 `std::function` 更适合回调

因为回调场景里，你通常关心的是：
- 这个东西能不能被调用
- 它的参数和返回值是什么
- 它的具体来源是什么，往往不重要

例如：

```cpp
void doTask(function<void(int)> callback) {
    callback(42);
}
```

这时调用方可以传：

```cpp
doTask([](int x) {
    cout << x << endl;
});
```

也可以传：

```cpp
void print(int x) {
    cout << x << endl;
}
doTask(print);
```

也可以传带捕获的 Lambda：

```cpp
int base = 100;
doTask([base](int x) {
    cout << base + x << endl;
});
```

这就是它强大的地方。

---

### 13.12 `std::function` 的优点

1. **通用**：能接很多种可调用对象
2. **统一**：调用方接口简单
3. **好用**：回调、事件、任务队列里很方便
4. **现代**：比裸函数指针更灵活

你可以把它理解成：

> **“回调接口的通用标准件”。**

---

### 13.13 `std::function` 的代价

它虽然好用，但不是没有成本。

常见代价：
1. 可能有额外间接调用
2. 可能有类型擦除开销
3. 某些情况下可能触发堆分配
4. 频繁调用时不如模板直接内联高效

所以它不是“哪里都最优”，而是“**够通用、够好用**”。

#### 记忆
> **`std::function` 解决通用性，模板解决性能极致。**

---

### 13.14 什么时候用 `std::function`

适合：
- 做回调接口
- 做事件系统
- 做任务调度
- 做需要统一保存不同可调用对象的场景
- 你想“把调用逻辑当数据传递”

不太适合：
- 特别热的内层循环
- 对性能极度敏感且调用目标固定
- 可以用模板直接把逻辑编译期确定的场景

---

### 13.15 一个更完整的例子

```cpp
#include <iostream>
#include <functional>
using namespace std;

void process(int x, function<void(int)> cb) {
    cout << "处理数据：" << x << endl;
    cb(x);
}

int main() {
    int offset = 100;

    process(5, [offset](int v) {
        cout << "回调结果：" << offset + v << endl;
    });

    return 0;
}
```

输出：

```cpp
处理数据：5
回调结果：105
```

### 这段代码的理解顺序

1. `process` 接收一个 `function<void(int)>`
2. 调用者传入一个带捕获的 Lambda
3. `process` 处理完自己的事情后，调用 `cb(x)`
4. Lambda 接收到参数并执行自己的逻辑

这就是非常标准的“回调 + `std::function`”组合。

---

### 13.16 `std::function` 最适合怎么记

你可以把它记成三句话：

> 1. 函数指针太窄。  
> 2. Lambda 太灵活。  
> 3. `std::function` 把各种可调用对象统一起来。

再进一步记：

> **`std::function` = 能装函数、Lambda、仿函数的通用回调盒子。**

---

### 13.17 这章最容易考的点

1. `std::function` 是什么？
   - 答：通用可调用对象包装器。
2. 它能装什么？
   - 答：普通函数、Lambda、仿函数、`bind` 结果等。
3. 它和函数指针区别？
   - 答：更通用，但可能有额外开销。
4. 什么时候用？
   - 答：回调、事件、任务、统一接口场景。
5. 什么时候别乱用？
   - 答：性能敏感热点路径。

---

### 13.18 记忆口诀

> **函数指针接纯函数，Lambda 负责写得短，`std::function` 统统装，回调接口最常见。**

---

## 14. 回调函数最经典的使用场景

---

### 14.1 排序比较规则

```cpp
sort(v.begin(), v.end(), [](int a, int b) {
    return a > b;
});
```

虽然大家平时不一定把它叫“回调”，但本质上它就是：
- 把比较逻辑传给 `sort`
- `sort` 在排序过程中反复调用它

这就是回调。

---

### 14.2 遍历处理逻辑

```cpp
for_each(v.begin(), v.end(), [](int x) {
    cout << x << endl;
});
```

`for_each` 并不知道你想对每个元素做什么。
你把处理逻辑作为回调传进去，它来负责调用。

---

### 14.3 条件筛选

```cpp
auto it = find_if(v.begin(), v.end(), [](int x) {
    return x > 5;
});
```

`find_if` 不知道你想找什么。
你把“判定条件”作为回调传给它。

---

### 14.4 事件处理

比如：
- 按钮点击后执行什么
- 收到消息后怎么处理
- 网络请求完成后如何响应

这类几乎都是回调思想。

---

### 14.5 异步编程

例如：
- 下载完成后调用某函数
- 数据库查询结束后通知结果
- 定时器到时间后执行动作

这种“现在不执行，未来某个时刻再执行”的逻辑，本质上都离不开回调。

---

## 15. 回调的核心思想：控制反转

这是一个很重要的概念。

平时写代码往往是：

> 我调用别人。

而回调是：

> 我先把函数交给别人，以后由别人来调用我。

这叫：

> **控制反转（Inversion of Control）**

也就是“调用权转移了”。

比如：
- 你不再决定“何时执行这个函数”
- 框架/库来决定何时执行

这就是为什么 GUI、网络框架、异步框架中回调极多。

---

## 16. 回调和“返回值”的区别

很多初学者会问：

> 既然函数做完了要告诉我结果，为什么不用返回值？

这个问题非常好。

### 用返回值的情况
适合：
- 调用马上结束
- 结果立刻拿到

例如：

```cpp
int add(int a, int b) {
    return a + b;
}
```

---

### 用回调的情况
适合：
- 不一定马上结束
- 结果将来才出来
- 处理逻辑希望交给调用者自定义

例如：
- 网络请求完成后返回
- 用户点击按钮后触发
- 排序过程反复调用比较规则

#### 记忆
> **返回值是“立刻给结果”，回调是“将来通知结果”。**

---

## 17. 回调和多态的关系

回调和多态都能实现“把变化部分交给外部”，但方式不同。

### 17.1 回调
把“函数逻辑”传进去。

### 17.2 多态
把“对象行为”交给子类去重写。

例如：
- 回调用于“小逻辑临时定制”
- 多态用于“整体行为结构化扩展”

记忆：

> **回调更轻，适合临时动作；多态更重，适合长期结构设计。**

---

## 18. 回调最常见的坑

---

### 18.1 函数签名不匹配

比如：

```cpp
void doTask(void (*cb)(int));
```

那你传进去的回调就必须是：
- 参数是 `int`
- 返回值是 `void`

如果签名不一致，就不能直接传。

#### 记忆
> **回调能不能传，先看签名。**

---

### 18.2 有捕获 Lambda 不能直接传给函数指针

```cpp
void doTask(void (*cb)());

int x = 10;
doTask([x]() {   // 通常不行
    cout << x << endl;
});
```

原因：
- `doTask` 要的是函数指针
- `[x]` 是有状态闭包对象
- 类型不匹配

解决方法：
- 改成 `std::function`

---

### 18.3 引用捕获生命周期问题

```cpp
function<void()> makeCallback() {
    int x = 10;
    return [&]() {
        cout << x << endl;
    };
}
```

这是危险的。

因为 `x` 在函数结束后已经销毁。
回调里引用的是悬空引用。

#### 记忆
> **回调最怕“回头再调时，人已经没了”。**

---

### 18.4 `this` 指针失效

```cpp
class A {
public:
    void func() {
        auto cb = [this]() {
            cout << "callback" << endl;
        };
    }
};
```

如果这个回调被异步保存，而对象已经析构，再调就危险。

#### 记忆
> **涉及 `[this]` 的回调，一定要先想对象还能活多久。**

---

## 19. 回调函数题目怎么做

做题时，建议按这 4 步看：

### 第一步：谁是回调
先找出“被当参数传进去的函数/可调用对象”。

### 第二步：签名是否匹配
看参数和返回值是否一致。

### 第三步：谁来调用它
看是哪个函数、算法、框架在调。

### 第四步：调用时机是什么
是立刻调？循环里调？事件发生后调？异步完成后调？

如果涉及 Lambda，再补两步：

### 第五步：捕获方式
- 值捕获？
- 引用捕获？
- `[this]`？

### 第六步：生命周期风险
- 引用还活着吗？
- 对象还活着吗？

---

## 20. 高频题型总结

---

### 题型1：判断这是不是回调

```cpp
void run(void (*cb)()) {
    cb();
}
```

是。
因为：
- 函数被当参数传入
- 再由 `run` 内部调用

---

### 题型2：能否传有捕获 Lambda

```cpp
void run(void (*cb)());
int x = 10;
run([x]() { cout << x; });
```

通常不行。

原因：
- `run` 需要函数指针
- 有捕获 Lambda 不是普通函数指针

---

### 题型3：为什么推荐 `std::function`

答：
因为它更通用，可以统一接收多种可调用对象。

---

### 题型4：为什么异步场景常用回调

答：
因为结果不是马上就有，适合“先注册逻辑，未来再通知”。

---

## 21. 回调、函数指针、Lambda、`std::function` 的关系图

你可以这样理解：

### 第一层：回调是一种思想
“把函数交给别人，之后再调”

### 第二层：要实现回调，需要一个载体
常见载体有：
- 普通函数
- 函数指针
- Lambda
- 函数对象
- `std::function`

### 第三层：现代 C++ 最常见写法
- 简单场景：Lambda
- 需要通用接收：`std::function`

## 22. 实战对比：三种写法

---

### 22.1 普通函数 + 函数指针

```cpp
void finish() {
    cout << "finish" << endl;
}

void work(void (*cb)()) {
    cb();
}
```

优点：
- 简单
- 开销小

缺点：
- 只能接函数指针类目标

---

### 22.2 Lambda + 函数指针

```cpp
void work(void (*cb)()) {
    cb();
}

work([]() {
    cout << "finish" << endl;
});
```

优点：
- 写法短

缺点：
- 只能是**无捕获 Lambda**

---

### 22.3 `std::function` + Lambda

```cpp
void work(function<void()> cb) {
    cb();
}

int x = 10;
work([x]() {
    cout << x << endl;
});
```

优点：
- 最灵活
- 最现代

缺点：
- 比原始函数指针有额外包装成本

---

# 第三章：C++中的锁

## 1. 为什么要学“锁”

当你开始写多线程程序，最先撞上的问题通常不是“怎么开线程”，而是：

> **多个线程同时改同一份数据，会不会乱？**

答案是：**会。**

如果没有同步机制，线程之间会出现：
- 数据竞争
- 结果不稳定
- 偶发崩溃
- 很难复现的 bug

这时就需要“锁”。

你可以把锁先理解成：

> **把一段共享资源保护起来，保证同一时间只有满足条件的线程能进去。**

锁的核心目标就两个字：

1. **互斥**
2. **安全**

---

## 2. 一句话抓本质

### 2.1 最短定义
**锁就是用来保护共享资源，避免多个线程同时修改导致数据错乱的同步工具。**

### 2.2 再换一种说法
锁不是“让线程更快”的工具，它的作用是：

> **让并发访问从“乱序竞争”变成“有规则排队”。**

所以你要记住：
- 锁解决的是**正确性**
- 不是优先解决**性能**

---

## 3. 为什么会有锁

假设有一个共享变量：

```cpp
int cnt = 0;
```

两个线程同时执行：

```cpp
cnt++;
```

你以为是“+1 +1 = +2”，但真实情况并不一定。

因为 `cnt++` 不是一个原子动作，它通常可以拆成三步：
1. 读出 `cnt`
2. 加 1
3. 写回去

两个线程如果交错执行，就可能发生：
- 线程 A 读到 0
- 线程 B 也读到 0
- 两边都加 1
- 最后都写回 1

本来应该变成 2，结果只变成 1。

这就是经典的并发错误。

所以锁的意义就是：

> **把“可能冲突的读写区间”圈起来，确保一次只让一个线程处理。**

---

## 4. C++ 中最常见的锁是什么

C++ 标准库里最常见的是这些：

1. `std::mutex`
2. `std::recursive_mutex`
3. `std::timed_mutex`
4. `std::shared_mutex`
5. `std::lock_guard`
6. `std::unique_lock`
7. `std::scoped_lock`

初学阶段你先抓住最重要的四个：

- `mutex`
- `lock_guard`
- `unique_lock`
- `scoped_lock`

---

## 5. `std::mutex` 是什么

`std::mutex` 是最基础的互斥锁。

它的作用很直接：

> **同一时刻只允许一个线程持有它。**

### 5.1 最简单写法

```cpp
#include <mutex>

std::mutex mtx;

void add() {
    mtx.lock();
    // 访问共享资源
    mtx.unlock();
}
```

### 5.2 它的含义
- `lock()`：上锁
- `unlock()`：解锁

如果另一个线程已经持有这把锁，当前线程就会阻塞等待。

### 5.3 记忆
> **mutex = 互斥锁 = 同一时间只进一个人。**

---

## 6. 为什么不建议手写 `lock()` / `unlock()`

看起来这样写很直接：

```cpp
mtx.lock();
// do something
mtx.unlock();
```

但问题是：
- 中间如果抛异常
- 中间如果 `return`
- 中间如果 `break`
- 中间如果程序提前退出

你可能忘记 `unlock()`。

一旦忘了：
- 锁就一直被占着
- 其他线程永远进不来
- 轻则卡住，重则死锁

所以现代 C++ 更推荐：

> **用 RAII 的锁包装器。**

---

## 7. `lock_guard`：最简单的自动加锁

`std::lock_guard` 是最轻量、最常用的 RAII 锁包装器。

### 7.1 写法

```cpp
#include <mutex>
using namespace std;

mutex mtx;

void add() {
    lock_guard<mutex> lock(mtx);
    // 这里自动加锁
    // 函数结束时自动解锁
}
```

### 7.2 本质
`lock_guard` 的特点非常简单：

1. 构造时上锁
2. 析构时解锁

这就完美符合 RAII 思想。

### 7.3 为什么它好
因为你不用自己记着 `unlock()`。

只要对象活着，锁就在；对象一销毁，锁就释放。

### 7.4 记忆
> **lock_guard = 最简单的自动锁，生时加锁，死时解锁。**

---

## 8. `unique_lock`：更灵活的锁

`std::unique_lock` 比 `lock_guard` 更灵活。

它也能管理 `mutex`，但功能更多，比如：
- 可以延迟加锁
- 可以手动解锁
- 可以重新加锁
- 可以和条件变量配合使用

### 8.1 写法

```cpp
#include <mutex>
using namespace std;

mutex mtx;

void add() {
    unique_lock<mutex> lock(mtx);
    // 自动加锁
    lock.unlock();   // 手动解锁
    lock.lock();     // 再次加锁
}
```

### 8.2 和 lock_guard 的区别

| 项目 | lock_guard | unique_lock |
|---|---|---|
| 是否自动加锁 | 是 | 可以是 |
| 是否自动解锁 | 是 | 是 |
| 是否可手动解锁 | 否 | 可以 |
| 是否更轻量 | 是 | 否 |
| 是否更灵活 | 否 | 是 |

### 8.3 什么时候用
- 简单保护临界区：`lock_guard`
- 需要条件变量或更复杂的锁控制：`unique_lock`

### 8.4 记忆
> **lock_guard 简单，unique_lock 灵活。**

---

## 9. `scoped_lock`：一次锁多个锁

如果你要同时锁多个互斥量，`std::scoped_lock` 很好用。

### 9.1 例子

```cpp
#include <mutex>
using namespace std;

mutex m1, m2;

void f() {
    scoped_lock lock(m1, m2);
    // 同时锁住两个 mutex
}
```

### 9.2 它的价值
多个锁一起加时，最怕死锁。
`scoped_lock` 会帮你用更安全的方式同时锁住多个 mutex。

### 9.3 记忆
> **scoped_lock = 一次锁多个，省心防死锁。**

---

## 10. 死锁是什么

死锁是并发里最经典的锁问题之一。

### 10.1 定义
多个线程互相等待对方释放资源，导致大家都卡住，这就叫死锁。

### 10.2 经典场景

线程 A：
1. 先锁 `m1`
2. 再等 `m2`

线程 B：
1. 先锁 `m2`
2. 再等 `m1`

如果时机刚好错开，就可能：
- A 等 B
- B 等 A
- 谁都不动

### 10.3 记忆
> **死锁就是“我等你，你等我，大家一起卡住”。**

---

## 11. 为什么会死锁

死锁通常和这几件事有关：

1. 资源互斥
2. 线程占着不放
3. 又去申请别的资源
4. 申请顺序混乱

最常见根源其实就一句话：

> **锁的顺序不统一。**

---

## 12. 如何避免死锁

### 12.1 最核心办法：统一加锁顺序

比如所有线程都先锁 `m1`，再锁 `m2`。

只要顺序统一，很多死锁就不会发生。

### 12.2 尽量缩小锁作用域

能少锁就少锁，能短就短。

```cpp
{
    lock_guard<mutex> lock(mtx);
    // 只保护真正需要保护的代码
}
```

### 12.3 不要在拿着锁的时候做耗时操作

例如：
- 睡眠
- I/O
- 网络请求
- 大循环

都尽量别放在锁里。

### 12.4 用 RAII 封装锁

这样不会因为异常或提前返回忘记解锁。

### 12.5 记忆
> **防死锁三件事：顺序统一、范围缩小、时间别长。**

---

## 13. 共享资源为什么一定要锁

当多个线程同时访问同一份数据时，必须先想清楚：

1. 这份数据能不能被并发改？
2. 如果不能，就必须加锁
3. 锁住的是“临界区”，不是整个程序

### 临界区是什么
临界区就是：

> **访问共享资源的那一小段代码。**

你不是把整个线程锁住，而是只保护共享数据。

---

## 14. 锁的本质：保护临界区

这句话很重要：

> **锁不是保护线程，锁是保护共享数据。**

你加锁的目的不是“让线程不能动”，而是：
- 让访问共享资源的顺序可控
- 让数据不被并发破坏

所以做题时要记住：
- 锁是为了**正确性**
- 不加锁可能更快，但不一定对

---

## 15. `mutex` 的常见使用模板

这是最常见的写法：

```cpp
#include <mutex>
using namespace std;

mutex mtx;
int cnt = 0;

void add() {
    lock_guard<mutex> lock(mtx);
    ++cnt;
}
```

### 为什么这样写
- `cnt` 是共享变量
- `lock_guard` 保证进入临界区前已加锁
- 函数结束自动释放

这就是最标准的“安全写法”。

---

## 16. `lock_guard` 和 `unique_lock` 怎么选

### 16.1 默认优先 `lock_guard`
因为它简单、轻量、不容易误用。

### 16.2 需要灵活控制时用 `unique_lock`
比如：
- 条件变量要配合等待
- 需要临时解锁
- 需要延迟加锁

### 16.3 记忆
> **简单场景用 lock_guard，复杂控制用 unique_lock。**

---

## 17. 条件变量和锁的关系

虽然严格说条件变量不是“锁”，但它和锁几乎总是一起出现。\n\n
### 为什么一起出现
因为线程等待条件时，必须在等待前释放锁，唤醒后再重新拿锁，才能避免资源竞争。

### 常见搭配

```cpp
unique_lock<mutex> lock(mtx);
cv.wait(lock, [] { return condition; });
```

### 记忆
> **条件变量负责“等”，锁负责“保护等的条件”。**

---

## 18. 锁相关面试高频点

### 高频 1：`mutex` 和 `lock_guard` 区别？
答：`mutex` 是锁本体，`lock_guard` 是 RAII 包装器。

### 高频 2：`lock_guard` 和 `unique_lock` 区别？
答：`lock_guard` 简单轻量，`unique_lock` 更灵活。

### 高频 3：什么是死锁？
答：多个线程互相等待对方释放资源。

### 高频 4：如何防死锁？
答：统一顺序、缩短锁时间、减少嵌套、用 RAII。

### 高频 5：锁的作用是什么？
答：保护共享资源，避免并发写乱数据。

---

## 19. 记忆总表

| 名称 | 作用 | 特点 |
|---|---|---|
| `mutex` | 互斥 | 最基础的锁 |
| `lock_guard` | 自动加解锁 | 简单、轻量 |
| `unique_lock` | 灵活锁管理 | 可手动解锁/延迟加锁 |
| `scoped_lock` | 一次锁多个 | 更适合多锁场景 |
| 死锁 | 锁互相等待 | 要尽量避免 |
| 临界区 | 共享资源代码段 | 要受保护 |

---

## 20. 一句话总结本章

> **C++ 中的锁，本质就是用 RAII 思想保护临界区，保证多线程访问共享资源时不出错。**

---

## 21. 记忆口诀

### 口诀 1
**锁不是管线程，是管共享数据。**

### 口诀 2
**简单用 lock_guard，复杂用 unique_lock。**

### 口诀 3
**顺序统一防死锁，临界区短更安全。**

### 口诀 4
**mutex 是锁本体，RAII 才是现代写法。**

# 第四章：C++与内存

## 1. 为什么 C++ 学到后面一定会碰内存

如果你把 C++ 学深一点，会发现它和很多语言最大的区别之一就是：

> **C++ 允许你更直接地接触内存，也要求你更负责地管理内存。**

这件事有好处，也有代价。

### 好处
- 性能高
- 控制力强
- 能写出很底层、很高效的代码

### 代价
- 容易泄漏
- 容易悬空
- 容易越界
- 容易把对象生命周期搞乱

所以“C++ 与内存”不是一个小知识点，而是整个 C++ 的核心之一。

你可以先记住一句话：

> **C++ 的很多问题，本质上都和“谁拥有内存、谁负责释放、什么时候释放”有关。**

---

## 2. 一句话抓本质

### 2.1 最短定义
**C++ 与内存，核心是“对象的存储、生命周期、所有权、访问方式”四件事。**

### 2.2 再展开一点
你在 C++ 里写的很多东西，最后都会落到内存上：
- 局部变量放哪
- 对象什么时候创建
- 对象什么时候销毁
- 指针指向谁
- 引用是不是还活着
- 堆上的对象谁来删

所以，内存不是“高级专题”，而是基础中的基础。

---

## 3. C++ 程序里的几块常见内存区域

初学时你可以先把内存想成几个“区域”。

### 3.1 栈区（stack）
通常存放：
- 局部变量
- 函数调用相关信息
- 返回地址

特点：
- 自动分配
- 自动释放
- 速度快
- 生命周期短

### 3.2 堆区（heap）
通常存放：
- `new` 出来的对象
- 动态分配的内存

特点：
- 手动或间接管理
- 生命周期可更长
- 灵活
- 但容易泄漏

### 3.3 静态存储区
通常存放：
- 全局变量
- 静态变量

特点：
- 程序开始就存在
- 程序结束才释放

### 3.4 常量区 / 只读区
通常存放：
- 字符串字面量
- 只读常量数据

比如：

```cpp
const char* s = "hello";
```

这里的 `"hello"` 通常就不在普通栈上。

---

## 4. 栈和堆到底怎么理解

这是 C++ 内存最经典的一组概念。

### 4.1 栈：自动化管理

```cpp
void f() {
    int x = 10;
}
```

这里的 `x` 一般放在栈上。

函数调用结束后，`x` 自动消失，不需要你手动释放。

### 4.2 堆：手动控制

```cpp
int* p = new int(10);
delete p;
```

这里的整数对象通常在堆上。

你必须自己负责 `delete`，否则就会泄漏。

### 4.3 栈和堆的核心差异

| 项目 | 栈 | 堆 |
|---|---|---|
| 分配方式 | 自动 | 手动/间接 |
| 释放方式 | 自动 | 需要管理 |
| 速度 | 快 | 相对慢 |
| 生命周期 | 函数级别常见 | 可灵活控制 |
| 风险 | 较小 | 容易泄漏/悬空 |

### 4.4 记忆
> **栈像自动柜，堆像自己租仓库。**

---

## 5. 局部变量为什么通常很安全

```cpp
void f() {
    int x = 10;
}
```

这个 `x` 的生命周期通常和函数绑定：
- 函数进来，`x` 出生
- 函数出去，`x` 结束

所以它不需要你手动释放。

这就是为什么：
- 局部对象特别适合 RAII
- 现代 C++ 喜欢让对象“按生命周期自动管理资源”

---

## 6. `new/delete` 和对象生命周期

### 6.1 `new` 做了什么

```cpp
int* p = new int(10);
```

`new` 不是只做一件事，它通常包含两步：
1. 申请内存
2. 在这块内存上构造对象

### 6.2 `delete` 做了什么

```cpp
delete p;
```

`delete` 通常也包含两步：
1. 调用析构函数
2. 释放内存

### 6.3 记忆
> **new = 分配 + 构造，delete = 析构 + 释放。**

---

## 7. 为什么不能把 `malloc/free` 和 `new/delete` 混着用

这个问题特别常考。

### 7.1 原因
- `malloc/free` 只管原始内存
- `new/delete` 还管对象构造/析构

如果混用，就会破坏生命周期规则。

### 7.2 典型错误

```cpp
int* p = (int*)malloc(sizeof(int));
delete p;   // 错
```

或者：

```cpp
int* p = new int(10);
free(p);    // 错
```

### 7.3 记忆
> **C 的那套只管“地皮”，C++ 的那套还管“房子怎么建、怎么拆”。**

---

## 8. 指针是什么

指针可以先理解成：

> **存放地址的变量。**

它不直接存数据本身，而是存“数据在哪里”。

### 8.1 例子

```cpp
int x = 10;
int* p = &x;
```

这里：
- `x` 是数据
- `p` 存的是 `x` 的地址

### 8.2 为什么指针重要
因为只要你掌握了地址，就能：
- 访问对象
- 传递大对象更高效
- 操作动态内存
- 构建复杂数据结构

### 8.3 记忆
> **指针不是数据，指针是“数据位置”的说明书。**

---

## 9. 引用是什么

引用可以先理解成：

> **某个对象的别名。**

```cpp
int x = 10;
int& r = x;
```

这里 `r` 就是 `x` 的别名。

### 9.1 和指针对比

| 项目 | 指针 | 引用 |
|---|---|---|
| 是否可以为空 | 可以 | 通常不可以 |
| 是否需要解引用 | 需要 | 不需要 |
| 是否容易改指向 | 可以 | 绑定后不能改成别的对象 |
| 语法复杂度 | 高一些 | 更像普通变量 |

### 9.2 记忆
> **指针像地址卡，引用像别名。**

---

## 10. 指针和引用为什么都要学

因为它们在 C++ 里承担的角色不一样：

### 指针适合
- 表达“可空”
- 表达“动态分配”
- 表达“需要重新指向”
- 表达底层控制

### 引用适合
- 表达“明确借用”
- 表达“不会为空”
- 表达“函数参数更清晰”

所以不要问“谁更高级”，而要问：

> **这个场景需要表达什么语义？**

---

## 11. 内存泄漏是什么

内存泄漏指的是：

> **你申请了内存，但后面再也没把它释放掉。**

### 11.1 例子

```cpp
void f() {
    int* p = new int(10);
    // 忘记 delete
}
```

### 11.2 后果
- 程序长期运行时占用越来越多内存
- 可能最终导致性能下降或崩溃

### 11.3 记忆
> **泄漏不是“立刻炸”，而是“慢慢把内存吃光”。**

---

## 12. 悬空指针是什么

悬空指针指的是：

> **指针还在，但它指向的对象已经没了。**

### 12.1 例子

```cpp
int* p = new int(10);
delete p;
// p 还在，但已经悬空
```

### 12.2 为什么危险
因为你后面再用它，就像拿着一张已经作废的地址卡去找房子。

### 12.3 记忆
> **悬空指针 = 指针还活着，目标对象死了。**

---

## 13. 野指针是什么

野指针通常指：

> **没有被正确初始化，或者指向未知区域的指针。**

### 13.1 例子

```cpp
int* p;   // 未初始化
```

这个 `p` 很危险，因为它里面可能是随机值。

### 13.2 和悬空指针区别
- 悬空指针：曾经指向过合法对象，后来失效
- 野指针：一开始就不可靠

### 13.3 记忆
> **野指针 = 从出生起就不靠谱。**

---

## 14. 为什么 C++ 特别强调 RAII

因为 C++ 里很多资源不是“自动就没了”的。

例如：
- 动态内存
- 文件
- 锁
- socket
- 数据库连接

如果你全靠手写 `delete`、`close`、`unlock`，就很容易漏。

所以现代 C++ 强调：

> **用对象管资源，用析构自动收尾。**

这就是 RAII 的威力。

---

## 15. 智能指针和内存

智能指针本质上也是在帮你管理内存。

### 15.1 `unique_ptr`
独占资源，最适合明确所有权。

### 15.2 `shared_ptr`
共享所有权，多个对象一起管生命周期。

### 15.3 `weak_ptr`
弱观察，不参与所有权，主要用来打破环。

### 15.4 记忆
> **智能指针的本质：让“谁负责释放”这件事写进类型里。**

---

## 16. 对齐和 padding 是什么

### 16.1 对齐
对象通常要放在某种地址边界上，方便 CPU 高效访问。

### 16.2 padding
为了满足对齐，编译器可能会在成员之间或结构体末尾插入一些“空字节”。

### 16.3 为什么会有这些空字节
因为：
- 让访问更快
- 符合硬件要求

### 16.4 记忆
> **对齐是规则，padding 是为了满足规则插进去的空位。**

---

## 17. 为什么结构体大小可能比成员之和大

因为：

1. 成员之间可能有 padding
2. 整体结构体末尾也可能补齐

例如：

```cpp
struct A {
    char c;
    int i;
};
```

`sizeof(A)` 往往大于 `1 + 4` 的直觉之和。

### 记忆
> **结构体大小不只看成员数量，还看对齐规则。**

---

## 18. 什么时候容易出内存问题

下面这些场景最危险：

1. 手写 `new/delete`
2. 手写 `malloc/free`
3. 拷贝资源对象却没定义拷贝语义
4. 引用捕获或裸指针跨越生命周期
5. 多线程里共享数据但没同步

你会发现，很多问题本质都和：

> **对象什么时候活、谁来释放、是否还能访问**

有关。

---

## 19. 内存相关题怎么做

做题时你可以按这 5 步看：

### 第一步：对象放哪
- 栈上？
- 堆上？
- 静态区？

### 第二步：谁创建
- 自动创建？
- `new` 创建？
- 还是容器内部创建？

### 第三步：谁释放
- 自动释放？
- `delete`？
- 容器析构？

### 第四步：是否有拷贝
- 是浅拷贝还是深拷贝？
- 是否共享资源？

### 第五步：有没有生命周期风险
- 指针悬空？
- 引用失效？
- 多线程并发访问？

只要你能按这五步拆，很多内存题就不慌了。

---

## 20. 一句话总结本章

> **C++ 与内存的核心，不是“记住几个名词”，而是理解对象生命周期、所有权、访问方式和释放时机。**

---

## 21. 记忆口诀

### 口诀 1
**栈自动，堆手动。**

### 口诀 2
**new 负责构造，delete 负责析构。**

### 口诀 3
**指针是地址，引用是别名。**

### 口诀 4
**谁拥有资源，谁负责释放。**

### 口诀 5
**内存问题大多数都离不开生命周期。**

# 第五章：线程池

## 1. 为什么要学线程池

如果你已经知道线程能并发执行任务，就很容易想到：

> **那我每来一个任务，就开一个线程，不就行了吗？**

听起来合理，但实际工程里这样通常不行。

原因是：
- 创建线程有开销
- 销毁线程也有开销
- 线程太多会频繁切换
- 线程数失控会拖垮系统

所以工程里不会无限制地“来一个任务开一个线程”，而是更常用：

> **先准备一批线程，任务来了就交给这批线程反复处理。**

这就是线程池。

---

## 2. 一句话抓本质

### 2.1 最短定义
**线程池就是“预先创建并复用一组工作线程”的机制。**

### 2.2 再说直白一点
线程池不是“新的线程类型”，而是一种组织线程的方法：

- 线程不是临时创建
- 线程先准备好
- 任务不断塞进去
- 线程不断拿任务执行

所以本质上：

> **线程池 = 线程复用 + 任务排队 + 统一调度。**

---

## 3. 为什么不直接频繁创建线程

### 3.1 创建线程并不便宜
线程创建时通常要做很多事：
- 向系统申请线程资源
- 分配线程栈
- 注册调度信息
- 让操作系统参与调度

这些都不是“零成本”。

### 3.2 线程销毁也有成本
线程执行完也不是立刻无代价消失：
- 要回收资源
- 要清理上下文
- 要退出调度

### 3.3 线程太多还会抢 CPU
如果线程数量远大于 CPU 核心数，问题会变成：
- 不是任务更快
- 而是线程之间来回切换更多

这会带来：
- 调度开销增加
- 缓存命中率下降
- 性能反而更差

### 3.4 记忆
> **线程不是越多越快，线程多了会互相抢时间片。**

---

## 4. 线程池解决的核心问题

线程池主要解决 3 件事：

### 4.1 线程复用
线程创建一次，多次使用。

### 4.2 任务排队
任务不是直接和线程绑定，而是先放进队列。

### 4.3 调度控制
由线程池来控制：
- 开几个线程
- 什么时候取任务
- 什么时候退出

所以你可以把线程池想成一个“工厂”：

- **线程** 是工人
- **任务队列** 是待加工订单
- **线程池** 是车间管理系统

---

## 5. 线程池的工作流程

线程池最经典的流程如下：

### 第一步：先创建若干工作线程
比如 4 个线程。

### 第二步：线程进入等待状态
它们不会一直忙跑，而是等任务。

### 第三步：新任务到来
任务被放进任务队列。

### 第四步：空闲线程取任务
哪个线程空出来，就去队列里拿一个任务执行。

### 第五步：执行完成后继续等下一个任务
线程不退出，而是继续复用。

这就是线程池最核心的工作方式。

### 一句话版
> **线程池不是“给任务造线程”，而是“给线程喂任务”。**

---

## 6. 线程池和“直接开线程”的区别

| 项目 | 直接开线程 | 线程池 |
|---|---|---|
| 每个任务都建线程 | 是 | 否 |
| 线程是否复用 | 否 | 是 |
| 创建销毁开销 | 高 | 低 |
| 并发数量是否容易失控 | 容易 | 可控 |
| 工程可维护性 | 一般 | 更强 |

### 记忆
> **直接开线程是“任务来了再招人”，线程池是“先养一批工人再分活”。**

---

## 7. 线程池里最重要的几个组成部分

一个最基础的线程池，通常有下面这些部分：

### 7.1 工作线程集合
比如：

```cpp
vector<thread> workers;
```

用来保存一组线程对象。

### 7.2 任务队列
比如：

```cpp
queue<function<void()>> tasks;
```

这里每个任务都被包装成“无参、无返回值”的统一可调用对象。

### 7.3 互斥锁
因为多个线程会同时访问任务队列，所以必须保护队列。

### 7.4 条件变量
如果队列为空，线程不能空转狂跑，要等任务到来时被唤醒。

### 7.5 停止标记
线程池销毁时，要告诉工作线程可以退出了。

---

## 8. 为什么线程池几乎总和这些工具一起出现

你会发现线程池特别常和下面这些一起出现：
- `mutex`
- `unique_lock`
- `condition_variable`
- `queue`
- `function`

原因很简单：

### 任务队列是共享资源
多个线程都要访问，所以要锁。

### 线程需要“没任务时休眠”
所以要条件变量。

### 任务类型要统一
所以常用 `function<void()>` 包装。

### 记忆
> **线程池不是单独一个知识点，而是“线程 + 锁 + 条件变量 + 回调”的组合应用。**

---

## 9. 一个最小线程池模型怎么理解

即使你暂时不自己手写完整线程池，也要先理解它的思路。

可以先把它简化成这样：

### 9.1 有一个任务队列

```cpp
queue<function<void()>> tasks;
```

### 9.2 有几个线程一直循环

```cpp
while (true) {
    // 取任务
    // 执行任务
}
```

### 9.3 如果没任务就等
线程不忙等，而是睡眠等待。

### 9.4 如果有任务就拿出来执行
执行完再回去继续等。

这就是线程池最小模型。

---

## 10. 为什么任务队列常写成 `function<void()>`

这是线程池里特别常见的一行：

```cpp
queue<function<void()>> tasks;
```

为什么是 `function<void()>`？

因为线程池想把不同任务统一存起来。

例如：
- 打印日志
- 处理网络包
- 更新缓存
- 计算结果

这些函数逻辑各不相同，但只要包装成：

> **“能直接调用的无参任务”**

就能统一塞进队列。

这就是 `function<void()>` 在这里的意义：

> **把各种任务统一成同一种可执行接口。**

---

## 11. 为什么任务常被包装成“无参函数”

有些人会问：

> 任务明明可能有参数，为什么线程池里还总写成 `void()`？

因为任务进入线程池之前，通常已经把参数绑定好了。

例如：

```cpp
int x = 10;
tasks.push([x]() {
    cout << x << endl;
});
```

这里：
- 原始任务逻辑可能依赖参数
- 但放进线程池时，已经封成一个可直接执行的小闭包了

所以线程池工作线程只需要：

```cpp
task();
```

不需要知道参数细节。

---

## 12. 条件变量在线程池中为什么特别重要

如果没有条件变量，工作线程可能会这样：

```cpp
while (true) {
    if (!tasks.empty()) {
        // 取任务
    }
}
```

这叫**忙等**。

问题：
- CPU 会被白白浪费
- 没任务时线程还一直转

所以正确做法是：

> **没任务就睡眠，有任务再唤醒。**

这就需要 `condition_variable`。

### 记忆
> **条件变量解决的不是“锁”，而是“怎么优雅地等任务”。**

---

## 13. 线程池中锁的作用是什么

线程池里锁最主要保护的是：

> **任务队列**

因为：
- 多个线程会抢着取任务
- 主线程还可能不断往里放任务

如果不加锁：
- 队列状态会乱
- 可能重复取
- 可能越界
- 可能直接崩溃

所以要记住：

> **线程池里，锁主要不是锁线程，而是保护任务队列这个共享资源。**

---

## 14. 线程池销毁时为什么要特别小心

线程池不是普通对象，销毁时如果处理不好，会出大问题。

### 14.1 为什么危险
因为这时候可能还存在：
- 线程还在跑
- 线程还在等任务
- 队列里还有任务没做完

### 14.2 销毁时通常要做什么
1. 设置停止标记
2. 唤醒所有等待线程
3. 让线程跳出循环
4. `join()` 所有线程

### 14.3 为什么一定要 `join`
因为线程对象如果还 joinable 就析构，程序可能直接终止。

### 14.4 记忆
> **线程池销毁不是“对象没了”就完了，而是要把所有工人安全收队。**

---

## 15. `join` 和线程池的关系

线程池中的工作线程一般不是“任务完成就销毁”，而是长期活着。

所以通常：
- 线程池创建时开线程
- 线程池销毁时统一 `join`

这和临时线程很不一样。

### 记忆
> **线程池里的线程是“常驻工人”，统一下班时再 join。**

---

## 16. 线程池最大的优点

### 16.1 减少线程创建销毁开销
这是最直接的收益。

### 16.2 控制并发度
不会让线程数量无限膨胀。

### 16.3 更适合大量短任务
如果任务很多，但每个都不重，线程池特别有价值。

### 16.4 统一调度
所有任务入口统一，便于管理、监控、扩展。

---

## 17. 线程池最大的缺点或难点

线程池也不是没有代价。

### 17.1 实现复杂
它同时涉及：
- 线程
- 锁
- 条件变量
- 生命周期
- 任务封装

### 17.2 容易出并发 bug
比如：
- 队列没锁好
- 停止逻辑有问题
- 销毁时还有线程没退出

### 17.3 任务阻塞会拖累线程池
如果某个任务长期卡住，会占住工作线程，影响整体吞吐。

### 17.4 线程数不是越多越好
线程太多会导致调度成本上升。

## 18. 线程池适合什么场景

典型适合：
- Web 服务器处理请求
- 后台任务系统
- 日志异步写入
- 图片处理 / 文件处理
- 一大批小任务并发执行

### 不太适合的情况
- 任务量极少
- 每个任务都极重且强依赖专属线程
- 实时性要求特别特殊、需要更专门调度策略

## 19. 线程池和异步的关系

很多人会把“异步”和“线程池”混成一回事。

其实它们不是同一个概念。

### 异步
强调的是：

> **调用后不马上等结果，结果以后再处理。**

### 线程池
强调的是：

> **一批线程怎么高效复用来执行任务。**

所以：
- 异步是编程方式
- 线程池是执行机制

它们经常一起出现，但不是同一个东西。

## 20. 线程池和回调函数的关系

你会发现线程池特别爱和回调一起出现。

因为线程池里的任务，很多时候本质就是：

> **把一个可执行逻辑（回调 / Lambda / function）塞进队列，等线程以后来执行。**

比如：

```cpp
pool.submit([]() {
    cout << "do work" << endl;
});
```

这里这个 Lambda，本质上就是交给线程池的回调任务。

所以你要把前一章和这一章连起来理解：

> **回调解决“任务怎么表达”，线程池解决“任务由谁执行”。**

## 26. 手写线程池：把锁、Lambda、条件变量串起来

这一节非常重要，因为它把前面学过的几个高频概念全都串起来了：

- **Lambda**：用来定义工作线程执行的逻辑、以及封装任务
- **mutex / lock_guard / unique_lock**：保护任务队列
- **condition_variable**：让线程“没任务就睡，有任务再醒”
- **function / packaged_task / future**：统一包装任意任务，并支持返回值

所以线程池不是单独的一章，它是很多知识点的“综合题”。

---

### 26.1 一句话抓本质

> **线程池 = 一组长期存活的工作线程 + 一个任务队列 + 一把锁 + 一个条件变量。**

它的工作方式就是：

1. 外部把任务提交到队列里
2. 工作线程在后台不断取任务
3. 没任务时睡觉
4. 有任务时被唤醒继续执行
5. 程序结束时安全退出并 `join`

---

### 26.2 为什么线程池一定会和 Lambda 一起出现

因为线程池里最核心的两件事，本质上都是“把一段代码交给别的地方执行”：

#### 1）工作线程执行逻辑，通常写成 Lambda

```cpp
workers.emplace_back([this] {
    // 工作线程循环执行任务
});
```

这里的 `[this]` 就是 Lambda 捕获。

#### 2）提交任务时，常常把任务再包一层 Lambda

```cpp
tasks.emplace([task]() {
    (*task)();
});
```

这里的 `[task]` 也是捕获。

所以你会发现：

> **线程池特别爱和 Lambda 搭配，是因为 Lambda 最适合“临时封装一段可执行逻辑”。**

---

### 26.3 线程池要解决的 4 个核心问题

#### 问题 1：任务放哪？
放到**任务队列**里。

#### 问题 2：谁来取任务？
由一批**工作线程**来取。

#### 问题 3：怎么保证线程安全？
用 **mutex** 保护任务队列。

#### 问题 4：没任务时怎么办？
用 **condition_variable** 让线程睡眠等待。

---

### 26.4 最常见的手写线程池代码

下面这份代码是一个比较标准、适合面试讲解的版本：

```cpp
#include <iostream>
#include <vector>
#include <queue>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <future>
#include <functional>
#include <stdexcept>
#include <type_traits>

class ThreadPool {
public:
    // 构造函数：创建线程池，启动固定数量的工作线程
    explicit ThreadPool(size_t threadCount)
        : stop(false) {

        if (threadCount == 0) {
            threadCount = 1;
        }

        // 创建 threadCount 个工作线程
        for (size_t i = 0; i < threadCount; ++i) {
            workers.emplace_back([this] {
                // 每个工作线程都会不断循环：
                // 1. 等待任务
                // 2. 取出任务
                // 3. 执行任务
                while (true) {
                    std::function<void()> task;

                    {
                        // 先加锁，再访问任务队列
                        std::unique_lock<std::mutex> lock(mtx);

                        // 没任务就睡，直到：
                        // 1. 有任务来了
                        // 2. 线程池要停止了
                        cv.wait(lock, [this] {
                            return stop || !tasks.empty();
                        });

                        // 如果线程池已经停止，并且任务队列也空了，就退出线程
                        if (stop && tasks.empty()) {
                            return;
                        }

                        // 从队列头取出一个任务
                        task = std::move(tasks.front());
                        tasks.pop();
                    }

                    // 注意：真正执行任务时，已经把锁释放了
                    // 这样可以减少锁的持有时间，提高并发效率
                    task();
                }
            });
        }
    }

    // 提交任务：支持任意可调用对象，并返回 future
    template <class F, class... Args>
    auto submit(F&& f, Args&&... args)
        -> std::future<std::invoke_result_t<F, Args...>> {

        using RetType = std::invoke_result_t<F, Args...>;

        // 把函数和参数包装成一个 packaged_task
        // 这样既能执行任务，又能通过 future 拿到返回值
        auto task = std::make_shared<std::packaged_task<RetType()>>(
            std::bind(std::forward<F>(f), std::forward<Args>(args)...)
        );

        std::future<RetType> result = task->get_future();

        {
            // 保护任务队列
            std::lock_guard<std::mutex> lock(mtx);

            if (stop) {
                throw std::runtime_error("ThreadPool has been stopped");
            }

            // 真正进入队列的任务类型是 void()
            // 这里再包一层 Lambda，把 packaged_task 调起来
            tasks.emplace([task]() {
                (*task)();
            });
        }

        // 有新任务到来，通知一个工作线程来取
        cv.notify_one();

        return result;
    }

    // 析构函数：安全关闭线程池
    ~ThreadPool() {
        {
            // 先设置停止标记
            std::lock_guard<std::mutex> lock(mtx);
            stop = true;
        }

        // 唤醒所有工作线程
        cv.notify_all();

        // 等待所有线程退出
        for (auto& worker : workers) {
            if (worker.joinable()) {
                worker.join();
            }
        }
    }

private:
    std::vector<std::thread> workers;              // 工作线程数组
    std::queue<std::function<void()>> tasks;        // 任务队列
    std::mutex mtx;                                 // 保护任务队列
    std::condition_variable cv;                     // 控制线程睡眠和唤醒
    bool stop;                                      // 停止标记
};

int main() {
    ThreadPool pool(4);

    // 任务 1：普通 Lambda，带参数，返回 int
    auto f1 = pool.submit([](int a, int b) {
        return a + b;
    }, 3, 5);

    // 任务 2：打印字符串，没有返回值
    auto f2 = pool.submit([](const std::string& msg) {
        std::cout << "task: " << msg << std::endl;
    }, "hello thread pool");

    // 任务 3：捕获外部变量
    int base = 100;
    auto f3 = pool.submit([base](int x) {
        return base + x;
    }, 23);

    std::cout << "f1 result = " << f1.get() << std::endl;
    f2.get();
    std::cout << "f3 result = " << f3.get() << std::endl;

    return 0;
}
```

### 26.5 代码逐段拆解

#### 1）为什么要有 `std::vector<std::thread> workers`

因为线程池不是一个线程，而是一组线程。

```cpp
std::vector<std::thread> workers;
```

你可以把它理解成：

> **线程池的“池”，指的就是这批工作线程。**

---

#### 2）为什么要有 `std::queue<std::function<void()>> tasks`

```cpp
std::queue<std::function<void()>> tasks;
```

这里是线程池最核心的共享资源。

为什么用 `std::function<void()>`？

因为线程池不关心任务细节，只关心：

> **这个任务能不能被调用。**

也就是说：

- 任务可以是普通函数
- 任务可以是 Lambda
- 任务可以是函数对象
- 任务可以是绑定参数后的可执行对象

统一放进 `function<void()>` 里，就很方便。

---

#### 3）为什么要有 `std::mutex mtx`

因为多个线程会同时访问任务队列。

如果没有锁，就可能发生：

- 一个线程正在 `pop`
- 另一个线程同时 `push`
- 队列状态被破坏

所以：

> **锁保护共享资源，队列就是共享资源。**

---

#### 4）为什么要有 `std::condition_variable cv`

因为工作线程不能一直空转。

如果没有条件变量，线程就会一直循环检查：

```cpp
while (tasks.empty()) { }
```

这叫**忙等**，会白白浪费 CPU。

所以正确做法是：

> **没任务时把线程挂起，有任务时再唤醒。**

---

#### 5）为什么 `cv.wait(lock, predicate)` 很重要

这一句是线程池面试高频：

```cpp
cv.wait(lock, [this] {
    return stop || !tasks.empty();
});
```

它的意思是：

- 如果条件不满足，就睡
- 条件满足了才继续往下执行

条件是：

- 线程池停止了
- 或者任务队列里有任务了

这个写法比单纯 `wait(lock)` 更安全，因为它能防止**虚假唤醒**。

---

#### 6）为什么取任务时先加锁，执行任务时却要先解锁

这段很关键：

```cpp
{
    std::unique_lock<std::mutex> lock(mtx);
    ...
    task = std::move(tasks.front());
    tasks.pop();
}

task();
```

原因是：

- `pop` 任务时需要保护队列，所以要锁
- 真正执行任务时，不需要再访问队列，所以可以解锁

好处：

1. 缩短锁持有时间
2. 降低线程竞争
3. 提高并发性能

记住一句话：

> **锁只保护共享数据，不保护任务执行本身。**

---

### 26.6 Lambda 在线程池里到底干了什么

这一段是重点中的重点。

#### 场景 1：工作线程启动时的 Lambda

```cpp
workers.emplace_back([this] {
    ...
});
```

这里 `[this]` 把当前对象捕获进去。

因为 Lambda 里面要访问：

- `tasks`
- `mtx`
- `cv`
- `stop`

这些都是类成员。

所以它需要 `this`。

---

#### 场景 2：把任务塞进队列时的 Lambda

```cpp
tasks.emplace([task]() {
    (*task)();
});
```

这里的 Lambda 作用是：

> **把一个 `packaged_task` 变成队列里统一可执行的 `void()` 任务。**

因为任务队列的类型是：

```cpp
std::queue<std::function<void()>> tasks;
```

所以不管原任务是什么，最后都要包装成 `void()`。

---

### 26.7 为什么 `submit` 要返回 `future`

因为很多时候，线程池提交的任务不是只执行一下，还想拿返回值。

比如：

```cpp
auto f = pool.submit([](int a, int b) {
    return a + b;
}, 3, 5);
```

主线程之后可以：

```cpp
cout << f.get() << endl;
```

这就是 `future` 的意义：

> **把异步任务的结果，变成以后可以取回来的值。**

---

### 26.8 这段代码最容易混淆的点

#### 1）`lock_guard` 和 `unique_lock` 的区别

##### `lock_guard`
- 简单
- 一进作用域就加锁，出作用域自动解锁
- 不能手动解锁

##### `unique_lock`
- 更灵活
- 可以配合 `condition_variable`
- 可以手动解锁/重新加锁

所以线程池里等待条件变量时，通常用：

```cpp
std::unique_lock<std::mutex> lock(mtx);
```

---

#### 2）为什么 `stop && tasks.empty()` 才退出

```cpp
if (stop && tasks.empty()) {
    return;
}
```

因为线程池关闭时，可能已经有任务排队了。

所以退出条件不能只看 `stop`，还要看队列是否清空。

正确逻辑是：

> **既要停止接新任务，也要把已有任务处理完。**

---

#### 3）为什么 `notify_one()` 而不是 `notify_all()`

大多数提交任务时，只需要唤醒一个线程就够了。

因为：

- 一个任务通常只需要一个线程执行
- `notify_all()` 会唤醒所有线程，容易造成惊群效应

所以通常：

```cpp
cv.notify_one();
```

而在析构关闭时，要唤醒所有线程：

```cpp
cv.notify_all();
```

如果面试官让你写线程池，你可以按这个思路回答：

### 26.13 `stop(false)` 是什么

`stop(false)` 出现在构造函数的**初始化列表**里：

```cpp
ThreadPool(size_t threadCount)
    : stop(false) {
```

它的意思是：

> **把成员变量 `stop` 初始化为 `false`。**

在这个线程池里，`stop` 通常是一个 `bool` 标志位，用来表示：

- `false`：线程池正常运行，还可以接收任务
- `true`：线程池准备关闭，不再接新任务，工作线程该退出了

---

#### 1）为什么不是在函数体里写 `stop = false;`

可以写，但**初始化列表更标准、更推荐**。

例如：

```cpp
ThreadPool(size_t threadCount) {
    stop = false;
}
```

和

```cpp
ThreadPool(size_t threadCount)
    : stop(false) {
}
```

相比之下，后者是**直接初始化**，更符合 C++ 的习惯。

---

#### 2）为什么 `stop` 要初始化为 `false`

因为线程池一开始应该是**正常工作状态**。

如果一上来就是 `true`，那工作线程可能会立即退出，线程池就没法用了。

所以这个标志位通常要这样理解：

```cpp
false = 正常运行
true  = 准备停止
```

---

#### 3）它在线程池里怎么起作用

比如工作线程里常有这样的判断：

```cpp
cv.wait(lock, [this] {
    return stop || !tasks.empty();
});
```

意思是：

- 如果 `stop == false` 且没任务，就继续睡
- 如果来了任务，或者线程池要停了，就醒来

析构时会把它改成 `true`：

```cpp
stop = true;
cv.notify_all();
```

这样所有工作线程都会被唤醒，然后在任务处理完后退出。

#### 4）一句话记忆

> **`stop(false)` 就是“线程池刚启动，先别停，正常干活”。**
