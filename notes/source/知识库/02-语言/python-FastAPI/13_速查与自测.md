# 13 速查与自测

> 复习目标：看到一个需求，能选对机制，并说出理由。

## 1. 先判断你正在解决哪类问题

学习 FastAPI 时，容易把所有问题都看成“该写哪个参数”。更有效的顺序是先问职责：我是在描述输入、控制输出、准备资源，还是安排工作的执行时机？职责想清楚后，具体写法通常就有了范围。

例如“分页”是输入问题，“不返回内部备注”是输出问题，“多个接口都需要当前用户”是公共准备问题，“启动时创建连接池”是资源生命周期问题。它们可能出现在同一个接口里，但不应该混成同一件事。

| 需求 | 首先想到 | 回看章节 |
| --- | --- | --- |
| 根据 ID 找一条记录 | 路径参数 | 02 |
| 筛选、排序、分页 | 查询参数 | 02 |
| 提交有多个字段的数据 | 请求体模型 | 03 |
| 限制标题长度、数值范围 | 数据校验 | 03 |
| 限制对外返回的字段 | 响应模型 | 04 |
| 告诉客户端资源不存在 | HTTPException 与状态码 | 04 |
| 复用当前用户、数据库会话等准备逻辑 | Depends | 05 |
| 网络等待时处理其他请求 | 合适的异步 I/O | 06 |
| 按业务组织一组接口 | APIRouter | 07 |
| 重启后还保留数据 | 数据库 | 08 |
| 验证身份并限制可访问资源 | 认证与授权 | 09 |
| 接收文件、表单或请求元数据 | File、Form、Header | 10 |

## 2. 用两两对照消除混淆

### 2.1 路径与查询：身份和条件

路径通常定位资源，查询参数通常描述如何读取资源。“查第 3 本书”中的 3 很适合放在路径里；“只看未读书，最多返回 10 本”则适合查询参数。这是接口设计习惯，不是框架强制规定。重点是让调用者容易理解资源和操作条件。

### 2.2 允许为空与允许省略：值和字段是否出现

允许为空是在说“这个位置可以填空值”，允许省略是在说“这个位置可以不提交”。两者独立。可以要求调用者必须提交一个字段，但允许它的值为 null；也可以允许省略字段，在省略时使用一个非空默认值。遇到必填问题时，分别检查类型允许什么值，以及有没有默认值。

### 2.3 输入模型与输出模型：接收承诺和返回承诺

输入模型告诉客户端需要提交什么；输出模型告诉客户端能得到什么。服务端内部拿到的数据可能比公开响应多得多，因此不应该把“数据库里有的字段”直接等同于“客户端应该收到的字段”。两套模型分开后，双方的边界更清楚。

### 2.4 同步与异步：谁在等待，等待时能否让路

异步的优势主要来自等待期间让出执行机会。它不会缩短外部服务本身的响应时间，也不会让一段密集计算自动加速。选择写法前先看所用库是否支持异步，再看工作主要是等待还是计算，不要仅凭“async 看起来更快”决定。

### 2.5 依赖与中间件：接口需要什么和统一包住什么

依赖适合表达某个接口需要的对象或检查，例如当前用户、分页信息、数据库会话。中间件适合围绕请求处理做统一工作，例如记录耗时。两者都可能执行公共逻辑，但依赖和接口参数、业务需求联系更紧，中间件关注的通常是请求整体。

### 2.6 认证与授权：身份有效不代表权限足够

认证判断来访者是谁；授权判断这个人是否可以进行当前操作。一个有效用户请求另一名用户的私有记录时，认证可以成功，授权仍应失败。登录成功只能解决前一个问题。

### 2.7 请求资源与应用资源：寿命不同，管理位置不同

一次请求使用的数据库会话，通常在依赖中申请并释放；应用长期复用的连接池或客户端，通常在 lifespan 中创建和关闭。不要因为“都是初始化”就把它们放在同一层，否则容易出现请求之间共享不该共享的状态，或每次请求都重复创建昂贵资源。

## 3. 一次请求，按故事复述

假设用户提交一个新任务。服务器先接收请求，框架匹配到对应路由，并解析请求参数、校验数据、求解依赖。若输入不符合要求，请求通常在进入业务函数前就会失败；若输入合格，业务函数使用准备好的资源完成操作。

函数返回后，框架通常还要按照响应约定进行校验和序列化，再把结果发给客户端。中间件可以围绕这段过程执行公共处理。流式响应会继续逐步产出内容，因此“函数返回了响应对象”不一定意味着“全部内容已经发完”。

这段故事帮助记住职责，不是所有内部步骤的严格时序表。依赖自身也会解析和校验参数；依赖清理、后台任务和流式发送的时机，需要结合具体机制理解。

## 4. 排错先找出错的边界

| 现象 | 应先检查的边界 |
| --- | --- |
| 服务器无法导入应用 | 当前目录、虚拟环境、模块名与 app 对象 |
| 404 | 请求是否匹配到正确路径，router 是否注册 |
| 405 | 路径存在，但 HTTP 方法是否匹配 |
| 422 | 参数来源、必填条件、字段类型与约束 |
| 500 | 服务端日志、业务异常、返回值是否满足输出约定 |
| 浏览器失败而其他客户端成功 | 浏览器控制台、Origin 与 CORS 预检 |
| 异步接口影响其他请求响应 | 是否直接执行了阻塞 I/O 或大量计算 |
| 重启后数据消失 | 数据是否只保存在进程内存 |
| 返回结果缺少内部字段 | 响应模型是否有意过滤了这些字段 |

排错时先看状态码，再看响应中的错误位置和服务端日志。一次只验证一个猜测。例如遇到 422，先确认报错位置是路径、查询还是请求体，不要立即修改数据库逻辑。

## 5. 场景自测：先说理由，再看答案

**问题一：用户没有填写“每页条数”，希望默认返回 10 条。应该把它设为必填吗？**

不用。为查询参数提供默认值，同时给出合理上下界即可。这里涉及的是省略后的行为，与是否允许 null 是两个问题。

**问题二：任务不存在时，返回一个包含 error 字段的 JSON 就够了吗？**

不够。客户端还需要从状态码判断请求结果。资源不存在通常应返回 404，并附上清楚的错误信息；只返回 error 字段可能仍保留 200 状态码。

**问题三：五个接口都要检查当前用户，应该把同一段逻辑复制五次吗？**

可以抽成依赖，由需要它的路由声明使用。这样公共检查和用户获取流程集中在一个地方，接口仍然能清楚表达“我需要当前用户”。

**问题四：把一个同步 HTTP 请求放进 async 函数，它就不会阻塞了吗？**

仍可能阻塞。调用本身必须支持异步并在等待时让出执行机会，或者通过适当的线程调度处理同步 I/O。仅改变外层函数声明不会改变库的执行方式。

**问题五：前端跨域访问失败，放开 CORS 能否同时解决没有登录的问题？**

不能。CORS 管浏览器是否允许跨域访问，认证管身份是否有效，它们是不同的边界。允许一个来源不意味着信任该来源发来的每一次业务请求。

**问题六：一项任务不能因服务器重启而丢失，直接放进 BackgroundTasks 是否足够？**

不够。当前进程的后台执行不提供持久化和崩溃恢复保证，需要可靠的任务保存与调度机制。

## 6. 最后做一个小练习

用自然语言设计一个“图书查询接口”，先不写代码。说明路径怎样定位图书、查询参数有哪些默认值、输入错误返回什么、公开响应包含哪些字段，以及访问私有书单时如何检查权限。

能把这几个选择解释清楚之后，再写一个只返回固定数据的最小接口验证设计。数据库、完整 CRUD 和部署可以在后续练习中逐步添加，不需要在第一步一起完成。
