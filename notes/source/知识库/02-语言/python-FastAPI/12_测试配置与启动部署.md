# 12 测试配置与启动部署

> 记忆句：**测试守住行为，配置适应环境，部署维持运行。**

## 1. 能在浏览器打开，不代表已经验证完接口

在 `/docs` 点一次成功请求，只能说明这一组输入得到了你刚才看到的结果。如果明天调整参数模型，忘了保留一个字段，人工操作未必能及时发现。自动化测试把期望写成可重复执行的判断，帮助你确认修改后旧的约定是否仍然成立。

接口的约定不只是“返回了什么 JSON”，还包括状态码、输入校验和访问条件。例如“编号必须是整数”不仅应该让合法请求成功，也应该让非法输入明确失败。好的最小测试通常同时包含一条正常路径和一条重要失败路径。

测试可以想成给接口留下一份可执行的验收说明。它保证的是被检查过的行为，并不会因为全部通过就证明系统没有任何问题；测试覆盖不到的场景仍需按业务风险补充。

## 2. TestClient 为什么不需要启动服务器？

`TestClient` 在当前进程内调用 ASGI 应用，模拟发出请求并接收响应。因此它能走过路由匹配、参数校验和业务处理这些应用层流程，却不需要监听 8000 端口，也不要求先运行 Uvicorn。

这带来两个好处：运行快，且测试时不容易把请求发到错误的本地服务。对应的边界也很清楚：它没有检验真实网络、代理、HTTPS 证书或部署环境。应用层测试通过之后，仍需针对部署检查对外访问是否正常。

## 3. 最小 demo：成功与非法输入各测一次

按照学习地图安装依赖，确保包含 `httpx` 和 `pytest`。下面是完整且自包含的示例，保存为 `main.py`，执行 `python -m pytest -q main.py`；不需要先启动服务器。文件名没有采用默认的 `test_` 前缀，所以命令中明确指定文件。

```python
from fastapi import FastAPI
from fastapi.testclient import TestClient

app = FastAPI()

@app.get("/items/{item_id}")
def read_item(item_id: int):
    return {"id": item_id}

def test_read_item():
    with TestClient(app) as client:
        response = client.get("/items/3")
        assert response.status_code == 200
        assert response.json() == {"id": 3}
        assert client.get("/items/abc").status_code == 422
```

预期看到 `1 passed`：这里有一个测试函数，函数内包含多个断言，所以不是每个断言都计为一个测试。第一组断言验证成功请求的状态和内容，最后一条验证 FastAPI 拒绝不合法的整数输入。

使用 `with TestClient(app)` 还能在进入和退出测试时执行应用的 lifespan，适合以后加入启动资源的场景。若想在浏览器体验同一个接口，仍可运行 `python -m uvicorn main:app --reload`；这是另一种运行方式，与上面的测试命令分开使用。

可选配套文件：[demos/ch12.py](demos/ch12.py) 展示环境配置和健康检查，与正文测试例不完全相同；[demos/test_demos.py](demos/test_demos.py) 则验证原配套 demo。后者可用 `python -m pytest -q demos/test_demos.py` 执行，但不等于验证所有正文示例。

## 4. 测试最值得补哪些场景？

先从接口契约找分支。输入符合规则时应该成功，输入违反规则时应该返回明确错误；查询不存在的资源时应该得到 404；凭证无效或权限不足时应该按约定拒绝。比起机械地给每一行代码配一个测试，这些场景更容易抓住真实回归。

涉及数据库或外部服务时，还要控制测试环境。测试不能随意写入真实业务数据，也不应因为一个第三方服务暂时不可用就全部失败。FastAPI 可以用 `app.dependency_overrides` 将原依赖替换成测试依赖，例如提供测试数据库会话；测试结束后要恢复，避免影响后续测试。

替换依赖的代价是：被替换部分没有在这次测试中受到检验。所以需要区分“路由在给定依赖结果下行为正确”和“真实数据库连接也正常”。这是不同层次的问题，没有必要强塞进同一个最小示例。

## 5. 配置为什么应该离开业务代码？

同一份程序在开发、测试和线上可能使用不同数据库地址、服务名称和密钥。如果把这些值直接写进代码，每换环境就要修改程序，很容易误连数据源或把敏感配置提交进仓库。

环境变量负责把外部配置交给进程；`pydantic-settings` 负责把这些通常以字符串形式传入的值转换成指定类型，并验证是否有效。例如把端口声明为整数，就能在配置装载阶段发现无效值。业务代码因此使用已经整理好的配置对象，而不必到处手动转换字符串。

`.env` 是便于本地开发的配置文件，但不会凭空自动生效，需要显式设置 `env_file` 等读取规则。已经创建的 Settings 对象通常也不会随着环境变量改变而自动刷新；更改后需重新创建对象或重启进程。配置检查接口只应暴露必要的非敏感信息，不要返回整个配置对象。

可选配套例使用 `DEMO_` 前缀，因此 `DEMO_APP_NAME` 对应其中的 `app_name` 字段。若想实践这部分，阅读配套文件即可，不必同时记住更多代码模板。

## 6. 启动命令里的每一部分在做什么？

以 `python -m uvicorn main:app --reload` 为例：Uvicorn 是实际运行 ASGI 应用的服务器，`main` 是模块名，冒号后的 `app` 是模块中的应用对象；`--reload` 让开发时修改代码后自动重启。FastAPI 定义应用行为，Uvicorn 接收网络请求并驱动应用执行。

| 参数或概念 | 作用 | 最容易误解的地方 |
| --- | --- | --- |
| `--reload` | 开发时自动重启 | 不应当作生产进程管理方案 |
| `--host 0.0.0.0` | 监听所有网卡 | 这是监听地址，不是用户访问目标地址 |
| `--port 8000` | 选择监听端口 | 同一地址端口不能被多个独立服务随意占用 |
| `--workers 2` | 启动多个工作进程 | 进程之间不共享普通 Python 字典和列表 |

`--reload` 与多 worker 模式不要一起使用。增加 worker 也不代表所有资源免费增加：内存中的模型、连接池等可能各有一份。需要跨 worker 一致保存的业务状态，应放进数据库或其他外部存储。

## 7. “进程跑起来”与“服务部署好”之间还差什么？

一个启动命令只解决“现在启动这个进程”。部署还要回答：进程异常退出谁负责重启？HTTPS 在哪里处理？日志在哪里查看？配置如何注入？数据库是否可达？这些属于运行环境的职责，需要与应用本身配合。

健康检查也要先明确含义。一个直接返回 `{"status":"ok"}` 的接口只能证明相应处理逻辑还能运行，并不能证明数据库和外部服务可用。是否需要检查这些依赖，应取决于你想判断“进程活着”还是“已经准备好接业务请求”。

学习阶段先理解这条链即可：**代码通过应用层测试 → 在目标环境加载正确配置 → 启动并检查服务 → 持续监控运行情况。** 每一步解决不同的问题，不能由一次浏览器访问替代全部验证。

## 8. 合上笔记再回答

1. **TestClient 通过了，是否说明 HTTPS 配置正确？** 不说明，它没有经过真实网络和 TLS 部署。
2. **为什么测试函数中有三个断言，却显示一个测试通过？** pytest 按收集到的测试用例计数，不按断言数量计数。
3. **两个 worker 的全局列表相同吗？** 不同，每个进程有自己的内存。
4. **修改环境变量后，现有配置对象会自动改变吗？** 通常不会，需要重新装载或重启。
