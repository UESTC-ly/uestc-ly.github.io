# 07 APIRouter 与项目拆分

> 记忆句：**按业务收拢路由，在入口统一组装；先分清职责，再增加文件。**

## 1. 为什么需要 APIRouter

只有两三个接口时，把所有代码放在一个文件中很直观。但当用户、任务、订单都写进同一个文件，查找一个接口要来回翻页，修改权限规则也容易漏掉某个入口。问题不只是文件变长，而是不同业务混在一起，读者无法快速确定某段代码属于谁。

`APIRouter` 用来集中声明一组相关接口。例如任务模块有自己的 router，用户模块有自己的 router，主应用通过 `include_router` 把它们纳入同一个应用。这样每组接口可以拥有统一的路径前缀、文档标签和公共依赖。[官方多文件应用教程](https://fastapi.tiangolo.com/tutorial/bigger-applications/)

可以把 router 看作商场里某一层的商铺名录，主应用负责把各层名录汇总到总导览。这个类比说明的是“收集和注册”，不表示每个 router 都是一个独立服务器。它们通常仍在同一个应用里处理请求，共享应用级配置。

## 2. 注册时发生什么，请求时又发生什么

定义 `@router.get(...)` 时，接口先登记在 router 上。仅创建 router 并不会让外部用户访问到它；主应用调用 `include_router` 后，这些路由才被注册到应用中，并出现在该应用的接口文档里。

因此，`include_router` 是应用组装阶段的工作，不需要在每次请求里调用。实际请求到来时，应用根据 HTTP 方法和完整路径匹配接口，再执行依赖解析和路由函数。

路径可以由多层前缀拼起来，但前缀越多越需要明确每层负责什么。例如 `/api/v1` 表示 API 版本，`/tasks` 表示业务资源，`/{task_id}` 表示具体对象。前缀是 URL 的一部分；`tags` 只是接口文档中的分类标签，更改标签不会改变访问地址。

## 3. 最小 demo：先在一个文件里看清组装

将下面代码复制到 `main.py`，运行 `python -m uvicorn main:app --reload`。依赖安装见[学习地图](00_学习地图.md)；切换前先停止上一章服务。

```python
from fastapi import APIRouter, FastAPI

router = APIRouter(prefix="/tasks", tags=["任务"])

@router.get("")
def list_tasks():
    return [{"id": 1, "title": "理解路由组装"}]

app = FastAPI()
app.include_router(router, prefix="/api/v1")
```

打开 `http://127.0.0.1:8000/docs`，在“任务”分类下找到 `GET /api/v1/tasks`，点击 **Try it out** 后执行，会得到一个任务列表。

先口算完整路径：注册前缀 `/api/v1`，加上 router 前缀 `/tasks`，再加接口路径的空字符串，结果就是 `/api/v1/tasks`。如果只访问 `/tasks`，本例没有这个路径，因此返回 404；这与文档标签叫什么无关。

为了看清“定义”和“注册”的区别，可以临时注释最后一行，再刷新 `/docs`：接口会消失。恢复该行后再继续学习即可。这个小实验比先搭一整套目录更容易理解 router 的职责。

## 4. 真正拆成多个文件时，只搬职责

理解组装以后，再把 router 和相关路由函数移到业务模块，例如 `routers/tasks.py`。该模块负责定义自己的 router；入口 `main.py` 负责导入它、创建应用并调用 `include_router`。这是最初足够用的拆分，不需要立刻引入很多层。

关键是导入方向：**入口导入业务路由，业务路由不要反过来导入入口里的 app。** 否则入口还没初始化完，业务模块又试图从入口取对象，容易形成循环导入。业务模块用自己的 router 装饰器注册接口即可，无需知道最终是哪一个 app 使用它。

如果统一前缀或依赖写在 router 定义处，它通常属于该业务模块的默认规则；写在 `include_router` 处，则便于入口根据组装场景增加规则。例如入口统一加 `/api/v1`，模块专注自己的 `/tasks`。两处都配置前缀时会叠加，不会互相覆盖。

## 5. 路由、业务、数据访问到底怎么分

可以从一个“完成任务”的需求理解职责。HTTP 层先接收任务 ID 和当前用户；业务层判断任务能否被此人完成、是否已经完成；数据访问层读取和保存数据库记录。拆分的目的，是让规则与存储细节各有归属，而不是机械规定每个函数都必须经过三层。

| 职责 | 主要回答的问题 | 常见内容 |
| --- | --- | --- |
| 路由层 | 这个 HTTP 请求如何进入系统 | 参数、状态码、依赖、响应模型 |
| 业务层 | 这件事按业务规则能否发生 | 权限规则、状态变化、多步骤业务 |
| 数据访问层 | 数据从哪里读、怎样写 | 查询、持久化、数据库细节 |

只有一个简单查询时，直接在路由中调用数据库也能清楚表达意图。等同一套业务被多个接口复用，或一个路由开始同时做很多决定时，再拆出业务函数。**出现清晰的职责边界才拆，比追求固定目录数量更容易维护。**

请求模型与表模型也是两个职责：前者约定客户端能传什么、必须满足什么条件；后者描述数据库怎样保存数据。字段看起来相同，不意味着永远应该共用。例如数据库有内部审核标记，客户端就不应因此获得修改它的入口。

## 6. 常见误区与排查顺序

接口访问不到时，先看 `/docs` 是否出现该接口。没有出现，优先检查是否导入并注册了 router；出现了，检查完整路径和 HTTP 方法。这样能区分“未组装进应用”和“请求地址写错”，比先怀疑服务器更有效。

路由组的公共依赖适合统一身份检查，但不能仅凭 `tags=["管理员"]` 认为接口已经受保护。文档标签只有展示作用，真正的限制必须由依赖或业务检查执行。

`APIRouter` 也不是应用隔离机制。它帮助组织同一应用的接口，不能靠拆成不同 router 就获得独立进程、独立资源限制或独立部署。是否需要子应用或不同服务，是另一个层面的问题。

## 7. 合上笔记再回答

1. router 已定义却没有出现在文档里，先检查什么？是否执行了 `app.include_router(router)`。
2. 把标签“任务”改成“待办”，请求路径会改变吗？不会。
3. 为什么业务路由尽量不导入 `main.py` 中的 app？减少耦合，并避免循环导入。
4. 小项目是否必须立刻分三层？不必，先让职责清楚，再根据复用和复杂度拆分。
