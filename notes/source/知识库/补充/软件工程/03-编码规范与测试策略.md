## 分章节讲解
### 1. 可读性
**核心定义：** 可读代码使用清晰命名、短函数、明确控制流和局部化副作用。

**理解路径：**
- 先明确它解决的具体问题，再判断它依赖的前提条件。
- 把它放回“测试不是证明没有错误，而是锁定关键行为和降低修改风险。”这条主线中理解，不要孤立记忆。
- 学习时至少能说出：输入是什么、输出是什么、代价是什么、失败边界是什么。

**常见误区：** 聪明的一行代码往往不如可维护的多行代码。

### 2. 单元测试
**核心定义：** 单元测试隔离验证小范围逻辑，适合快速反馈和边界条件验证。

**理解路径：**
- 先明确它解决的具体问题，再判断它依赖的前提条件。
- 把它放回“测试不是证明没有错误，而是锁定关键行为和降低修改风险。”这条主线中理解，不要孤立记忆。
- 学习时至少能说出：输入是什么、输出是什么、代价是什么、失败边界是什么。

**常见误区：** 只测实现细节会导致重构时大量脆弱测试失败。

### 3. 集成测试
**核心定义：** 集成测试验证模块协作、数据库、消息队列或外部接口的真实交互。

**理解路径：**
- 先明确它解决的具体问题，再判断它依赖的前提条件。
- 把它放回“测试不是证明没有错误，而是锁定关键行为和降低修改风险。”这条主线中理解，不要孤立记忆。
- 学习时至少能说出：输入是什么、输出是什么、代价是什么、失败边界是什么。

**常见误区：** 集成测试不是越多越好；慢而不稳定的测试会拖垮交付。

### 4. 测试金字塔
**核心定义：** 测试金字塔强调大量快速单元测试、适量集成测试、少量端到端测试。

**理解路径：**
- 先明确它解决的具体问题，再判断它依赖的前提条件。
- 把它放回“测试不是证明没有错误，而是锁定关键行为和降低修改风险。”这条主线中理解，不要孤立记忆。
- 学习时至少能说出：输入是什么、输出是什么、代价是什么、失败边界是什么。

**常见误区：** 只依赖 E2E 会反馈慢且定位困难；只依赖单测又覆盖不了协作问题。

## 实战深化：可读性、可测性与回归保护

### 1. 底层机制拆解
编码规范降低理解成本，测试策略把隐含契约变成可重复验证的证据。

```mermaid
flowchart LR
  A[输入/前提] --> B[核心结构]
  B --> C[处理规则]
  C --> D[输出结论]
  D --> E[验证边界]
```

### 2. 适用与不适用
| 判断点 | 适用信号 | 不适用/风险信号 |
|---|---|---|
| 前提 | 对象、约束和目标清晰 | 概念边界含糊或约束缺失 |
| 机制 | 能说明中间状态如何变化 | 只能背结论，无法解释过程 |
| 成本 | 复杂度、维护成本或风险可接受 | 资源、复杂度或安全边界失控 |
| 验证 | 有样例、测试、证明或观测证据 | 无法复现、无法审计、无法回滚 |

### 3. 案例理解
重构前先补 Characterization Test，锁住现有行为，再逐步改善命名、边界和重复逻辑。

### 4. 常见误区与纠正
- **误区：** 只记概念定义，不问前提。**纠正：** 每次回答都先说适用条件。
- **误区：** 用单个样例证明普遍正确。**纠正：** 补充边界样例、反例或不变量。
- **误区：** 忽略工程成本。**纠正：** 同时说明性能、可靠性、安全性和维护代价。

- 如果输入规模、业务约束或安全边界变化，结论是否还成立？

## 继续扩写：机制、边界与面试追问

### 机制拆解补充
- 编码规范的价值在于降低阅读和修改成本，优先统一命名、错误处理、边界检查和依赖方向。
- 测试策略应覆盖单元、集成、契约、端到端和回归；每层测试解决不同置信度问题。
- 高覆盖率不等于高质量，关键是覆盖风险路径、失败模式和历史缺陷。

```mermaid
flowchart LR
  A[前提] --> B[机制]
  B --> C[适用]
  C --> D[不适用]
  D --> E[验证]
```

### 适用 / 不适用场景
| 维度 | 适用信号 | 不适用信号 | 纠偏动作 |
|---|---|---|---|
| 前提 | 关键假设可明确写出 | 只能靠经验套模板 | 先补定义、约束和反例 |
| 代价 | 时间、空间、人力成本可接受 | 复杂度或维护成本不可控 | 降维、分层或换方案 |
| 验证 | 能用样例、测试或演练证明 | 只能口头保证 | 增加边界用例和观测点 |
| 演进 | 变化范围局部可控 | 一处变化牵动多处 | 重画边界和依赖关系 |
