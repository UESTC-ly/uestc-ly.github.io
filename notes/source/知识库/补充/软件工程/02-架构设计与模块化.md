## 分章节讲解
### 1. 高内聚低耦合
**核心定义：** 高内聚让模块内部围绕单一职责，低耦合减少模块间变化传染。

**理解路径：**
- 先明确它解决的具体问题，再判断它依赖的前提条件。
- 把它放回“好架构让变化被限制在明确边界内。”这条主线中理解，不要孤立记忆。
- 学习时至少能说出：输入是什么、输出是什么、代价是什么、失败边界是什么。

**常见误区：** 把代码拆成很多文件不等于低耦合；共享全局状态会制造隐性耦合。

### 2. 分层架构
**核心定义：** 分层架构按表现、应用、领域、基础设施组织依赖，便于替换和测试。

**理解路径：**
- 先明确它解决的具体问题，再判断它依赖的前提条件。
- 把它放回“好架构让变化被限制在明确边界内。”这条主线中理解，不要孤立记忆。
- 学习时至少能说出：输入是什么、输出是什么、代价是什么、失败边界是什么。

**常见误区：** 层间不能随意跨越；否则分层只剩目录结构。

### 3. 接口与抽象
**核心定义：** 接口定义模块协作契约，抽象应来自稳定变化点而不是凭空设计。

**理解路径：**
- 先明确它解决的具体问题，再判断它依赖的前提条件。
- 把它放回“好架构让变化被限制在明确边界内。”这条主线中理解，不要孤立记忆。
- 学习时至少能说出：输入是什么、输出是什么、代价是什么、失败边界是什么。

**常见误区：** 过度抽象会增加理解成本；没有多个实现或变化压力时要谨慎。

### 4. 架构决策记录
**核心定义：** ADR 记录背景、决策、备选方案和后果，帮助团队理解为什么这样设计。

**理解路径：**
- 先明确它解决的具体问题，再判断它依赖的前提条件。
- 把它放回“好架构让变化被限制在明确边界内。”这条主线中理解，不要孤立记忆。
- 学习时至少能说出：输入是什么、输出是什么、代价是什么、失败边界是什么。

**常见误区：** 只记录结论不记录约束，未来维护者会重复争论。

## 实战深化：边界、依赖与演进成本

### 1. 底层机制拆解
架构设计不是画层次图，而是决定职责边界、依赖方向、数据所有权和变化隔离。

```mermaid
flowchart LR
  A[输入/前提] --> B[核心结构]
  B --> C[处理规则]
  C --> D[输出结论]
  D --> E[验证边界]
```

### 2. 适用与不适用
| 判断点 | 适用信号 | 不适用/风险信号 |
|---|---|---|
| 前提 | 对象、约束和目标清晰 | 概念边界含糊或约束缺失 |
| 机制 | 能说明中间状态如何变化 | 只能背结论，无法解释过程 |
| 成本 | 复杂度、维护成本或风险可接受 | 资源、复杂度或安全边界失控 |
| 验证 | 有样例、测试、证明或观测证据 | 无法复现、无法审计、无法回滚 |

### 3. 案例理解
订单、库存、支付拆分服务后，要明确一致性、幂等、重试和补偿，否则拆分只会增加故障面。

### 4. 常见误区与纠正
- **误区：** 只记概念定义，不问前提。**纠正：** 每次回答都先说适用条件。
- **误区：** 用单个样例证明普遍正确。**纠正：** 补充边界样例、反例或不变量。
- **误区：** 忽略工程成本。**纠正：** 同时说明性能、可靠性、安全性和维护代价。

### 5. 面试追问路径
- 如果输入规模、业务约束或安全边界变化，结论是否还成立？
- 这个概念和相邻概念的区别是什么？
- 如何设计一个测试、证明或观测指标来验证你的判断？

## 继续扩写：机制、边界与面试追问

### 机制拆解补充
- 架构设计的核心是控制变化传播：高内聚、低耦合只是结果，不是可直接套用的口号。
- 模块边界要围绕数据所有权、事务边界、团队认知和部署风险共同确定。
- 分层、六边形、事件驱动和微服务都有适用边界，不能用架构名词替代约束分析。

```mermaid
flowchart LR
  A[前提] --> B[机制]
  B --> C[适用]
  C --> D[不适用]
  D --> E[验证]
```

### 适用 / 不适用场景
| 维度 | 适用信号 | 不适用信号 | 纠偏动作 |
|---|---|---|---|
| 前提 | 关键假设可明确写出 | 只能靠经验套模板 | 先补定义、约束和反例 |
| 代价 | 时间、空间、人力成本可接受 | 复杂度或维护成本不可控 | 降维、分层或换方案 |
| 验证 | 能用样例、测试或演练证明 | 只能口头保证 | 增加边界用例和观测点 |
| 演进 | 变化范围局部可控 | 一处变化牵动多处 | 重画边界和依赖关系 |
