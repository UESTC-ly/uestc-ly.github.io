## 如何从枚举前缀和优化到哈希表

**回答：**

从左到右扫描右边界，用哈希表 `freq` 记录此前每个前缀和出现的次数。当前前缀和为 `prefix` 时，所有值为 `prefix-K` 的旧前缀都能与它组成合法非空区间，因此将 `freq[prefix-K]` 加入答案。

必须先查询再登记当前前缀，否则当 `K=0` 时，会错误地把当前前缀与自己配对，计入空区间。初始 `freq[0]=1` 表示数组之前的空前缀，使从下标零开始的合法区间也能被计数。

```python
def count_subarrays_sum_k(nums, k):
    freq = {0: 1}
    prefix = 0
    count = 0
    for x in nums:
        prefix += x
        count += freq.get(prefix - k, 0)
        freq[prefix] = freq.get(prefix, 0) + 1
    return count
```

哈希表保存的是出现次数，不能只用集合判断存在性。例如 `[0,0,0]`、`K=0`，每一步新增的合法区间分别为 1、2、3，总数为 6。

在哈希操作均摊常数时间、整数运算固定成本的假设下，时间复杂度为期望 $O(n)$，额外空间为 $O(n)$。Java 或 Go 实现需要依据范围选择前缀和与计数类型；计数最多达到 $n(n+1)/2$，可能超过 32 位整数。

## 如何从理论浮点数计算次数（FLOPs）估算训练时间和项目成本？

**难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐ (4/5)**

### 1. 从理论算力到实际训练时间

理论 FLOPs 不是训练耗时。训练时间常用近似：

```math
T \approx \frac{\text{FLOPs}_{\text{train}}}{G \times \text{FLOPs}_{\text{GPU-peak}} \times \text{MFU}}
```

其中 $G$ 是 GPU 数量，MFU 是模型浮点运算利用率。MFU 受并行策略、批量规模（batch size）、序列长度、通信重叠、算子融合、显存带宽和数据管线影响。快速注意力（Flash Attention）通常不是减少理论 FLOPs，而是减少 HBM 读写、提升实际吞吐；FP8/BF16 主要提升硬件有效吞吐和降低显存；激活检查点会省显存但增加重算开销。

训练成本可进一步估算为：

```math
\text{Cost}_{\text{GPU}} \approx T_{\text{hours}} \times G \times \text{Price}_{\text{GPU-hour}}
```

真实成本还要加上存储、网络、数据处理、评估、集群运维、人力和失败重训成本。

**不同数据集承担不同职责。** 固定回归集用于长期比较，版本应尽量稳定；挑战集收集已知短板，随失败模式扩充；线上代表集按真实流量定期刷新，并完成隐私和安全处理。线上失败样本若进入训练或开发调参，就不能继续充当独立留出证据；需要把它及近重复样本移出冻结测试集，另保留未参与训练的独立留出集（holdout）。

**评估强度随发布阶段提高。** checkpoint 阶段运行便宜、稳定的自动回归；候选版本增加完整分维评测、人评和经过校准的 MLLM judge；发布前再检查安全、延迟、失败率和成本；灰度阶段监控线上分桶与关键护栏指标，并保留快速回滚能力。

**失败结果要能指向动作。** 每条严重失败至少包含任务类型、能力维度、输入规格、模型与推理版本、失败标签和复现信息，再归因到数据、条件解析、时空建模、采样解码或服务配置。修复后先回到对应挑战集验证，再检查固定回归集，防止局部问题改善后引入新的能力退化。

**发布门槛要区分硬约束与权衡指标。** 安全、核心场景和严重一致性问题适合硬门禁；一般画质、吞吐和成本可以按业务权重比较，但必须保留分项结果，不能只留一个总分。

## 如何根据profile结果做算子优化

**回答：**

从 profile 中建立假设，再做最小改动验证。不要一看到带宽低就机械提高 block size；带宽低也可能是并行不足、依赖链或访问不合并。

| 证据组合 | 待验证原因 | 可能的改动 |
| --- | --- | --- |
| 大量中间读写，HBM 接近可达上限 | 内存流量主导 | 融合、分块复用、降低中间存储精度 |
| Tensor Core 利用差且矩阵工作占主导 | 形状、布局或分派不适配 | 调整 tile、数据布局和库/内核选择 |
| 寄存器多、local memory 流量增大 | spill 或驻留受限 | 减少 live state、调整展开与 tile |
| 大量短 kernel 之间出现空隙 | launch、CPU 调度或同步 | 融合、CUDA Graph、减少不必要同步 |
| 有效访存字节少、事务多 | 非合并或重复访问 | 改数据布局与索引，复用已加载块 |

stall 指标用于提供线索，不能把某个 stall 百分比高直接当作唯一根因；计数器语义和瓶颈之间需要结合指令与访存行为解释。通信瓶颈还要另看 NCCL、拓扑与并行划分。

每次改动运行同一正确性集与代表形状集，记录速度回退和新增开销。若原热点只占总时长的比例 $`f`$，将其加速 $`s`$ 倍后的理想整体加速上界为 $`1/((1-f)+f/s)`$；还需考虑并发和关键路径变化，不能直接把单算子倍数当成服务倍数。

可建立一个最小实验记录表：输入 shape/dtype/stride、GPU 与软件版本、算法分派、实测字节量、指令/计算量、耗时及误差。一次仅改变一个主要因素，再覆盖代表形状；一个长序列形状的最优 tile 可能让短序列明显退化。

例如 Amdahl 公式中取 $`f=0.3,s=2`$，理想整体加速只有约 $`1.176`$ 倍，端到端时长降低 15%。它们是同一结果的两种口径，不能把“算子提速 2 倍”写成“请求时延降低一半”。若算子与其他工作有重叠，还要重新确认被缩短的部分是否位于关键路径。

## 如何用 Roofline 模型结合硬件理论算力与带宽上限，设定合理的优化目标？

**难度评分：⭐⭐⭐⭐⭐ (5/5)  |  考察频率：⭐⭐⭐ (3/5)**

### 一、Roofline 模型的三个关键值

以 NVIDIA A100（80GB）为例：

| 硬件上限 | 理论峰值 | 说明 |
|---------|---------|------|
| FP16 Tensor Core 算力（无稀疏） | 312 TFLOPS | 需要 Tensor Core + FP16 |
| FP32 算力 | 19.5 TFLOPS | 非 Tensor Core 路径 |
| HBM2e 带宽 | 2039 GB/s (≈ 2 TB/s) | HBM2e @ 80GB |

这三个值定义了 Roofline 图的"屋顶线"——斜线部分由带宽决定，水平线部分由算力决定。

### 二、设定优化目标的步骤

**步骤 1：确定 Kernel 的计算强度**
```
计算强度 = 总 FLOP / 总 Bytes
```

以标准 GEMM（M=N=K=4096, FP16）为例：
```
FLOP ≈ 2 × M × N × K = 2 × 4096³ ≈ 137B FLOP
Bytes ≈ (M×K + K×N + M×N) × 2 bytes ≈ 0.1 GB
计算强度 ≈ 137B / 0.1GB ≈ 1370 FLOP/Byte
```

1370 FLOP/Byte 远大于 A100 的 156 FLOP/Byte → Compute-Bound → 优化目标应围绕提升算力利用率。

**步骤 2：计算理论延迟下限**

对于 Compute-Bound Kernel：
```
理论最短延迟 = 总 FLOP / 理论峰值算力
GEMM 理论最短延迟 ≈ 137B / 312T ≈ 0.44 ms
```

对于 Memory-Bound Kernel：
```
理论最短延迟 = 总 Bytes / 理论峰值带宽
```

**步骤 3：设定合理优化目标**

```
实际延迟 / 理论最短延迟 = 效率

优化目标示例：
- 当前效率 30% → 目标 50%（可行性高）
- 当前效率 50% → 目标 70%（需要 Kernel 级优化）
- 当前效率 70% → 目标 80%（难度高，可能需要重写 Kernel）
```

**步骤 4：量化优化空间**

```
Memory-Bound Kernel：
  优化上限 = (实际带宽 / 理论带宽) 的倒数 × 当前延迟
  例如：200 GB/s 有效带宽 / 2000 GB/s 理论 = 10% 带宽利用率
  理论上限加速 = 10×（如果能达到 100% 带宽利用率）
  实际可达加速 ≈ 2-3×（考虑实际局限性）
```

### 三、实操案例：Decode 阶段 GEMM 分析

```
某个 Decode 阶段的 GEMM (M=1, K=4096, N=4096)：

FLOP = 2 × 1 × 4096 × 4096 ≈ 33.6M FLOP
Bytes ≈ (1×4096 + 4096×4096 + 1×4096) × 2B ≈ 33.6MB
计算强度 ≈ 33.6M / 33.6MB ≈ 1 FLOP/Byte

A100 硬件比 ≈ 156 FLOP/Byte
1 << 156 → 严重 Memory-Bound

理论延迟下限 = 33.6MB / 2000GB/s ≈ 16.8 μs
实际延迟 ≈ 250 μs（有效带宽约 134 GB/s，利用率仅约 7%）

优化方向：
  1. 不是降低 FLOP（才 33.6M）——计算不是瓶颈
  2. 是减少访存——GQA（减少 K/V 头数）、KV Cache 量化（降低每个 Byte 的精度）
  3. 或设法增大 M（增大 batch size 提升计算强度）
```

可以总结为：**Roofline 模型不仅能定性判断 bottleneck，还能定量计算优化上限。先根据 Kernel 的计算强度判断 Memory-Bound 还是 Compute-Bound，再基于理论峰值算力/带宽计算最短延迟，最终结合当前效率设定可实现的优化目标。对于大模型 Decode 阶段的大量小 M GEMM，计算强度极低，优化应聚焦于减少访存量。**

## 如何监控与缓解？

工程上通常会持续监控训练损失、验证损失、梯度范数、参数范数、激活范数、学习率、NaN/Inf、tokens/sec、MFU、显存占用、通信耗时和数据加载耗时。对于多源数据训练，还可以按数据来源或数据类型监控 loss，帮助定位某一类数据是否导致异常。

一旦出现异常，需要**先判断是优化、数值、数据问题还是分布式系统问题**。

- 优化问题通常通过降低学习率、增加 warmup、梯度裁剪或调整 batch size 缓解；
- 数值问题通常通过 BF16、稳定 softmax、检查归一化层和 loss scaling 处理；
- 数据问题需要定位异常 batch、回溯样本来源并修复清洗规则；
- 系统问题则需要检查通信、节点状态和 checkpoint 一致性。

大规模大语言模型训练通常还会建立自动恢复机制，例如定期保存 checkpoint、异常时回滚到最近稳定版本、自动跳过坏 batch、记录异常样本 ID、保存训练日志和数据 shard 元信息。稳定性治理的重点不是等训练崩溃后再排查，而是通过监控、告警、回滚和数据追踪，把 loss spike、NaN 和梯度异常控制在可定位、可恢复的范围内。

## 如何缓解灾难性遗忘？

- **使用 LoRA/QLoRA**：限制可训练参数规模，减少对底座能力的破坏。

- **降低学习率和训练轮次**：避免模型参数或 adapter 过度偏向窄领域数据。

- **混合通用数据**：在领域数据中加入少量通用指令、对话、格式和安全数据。

- **Replay 数据**：保留部分旧任务或通用能力样本，用于维持原有能力。

- **正则约束**：限制新模型参数或输出分布偏离原模型过远。

- **分阶段训练**：领域差异较大时，可以先做领域继续预训练，再做 SFT，减少直接迁移冲击。

- **保留安全数据**：在微调集中混入安全拒答、合规边界和风险场景样本，避免安全能力退化。

- **保留 checkpoint 和回滚机制**：对比不同训练步数和超参数下的模型效果，选择综合表现最优的版本。

## 如何解释RL训练初期Reward数值先降后升的现象？

**回答：**

RL 初期 reward 先降后升是常见现象，不一定代表训练失败。原因通常是策略从 SFT 初始分布开始探索，新策略会尝试不同回答长度、推理路径和格式，短期内偏离原来稳定但保守的输出，导致 reward 下降；当模型逐渐学到 reward 偏好的行为后，reward 再回升。

具体可以从四个角度解释。第一，探索成本。RL 需要采样多种动作，早期会产生更多低质量输出。第二，KL 约束调整。如果 KL penalty 太弱，策略偏离 SFT 过快，reward 可能先掉；如果太强，模型学不动。第三，reward 归一化和 advantage 估计在早期不稳定，尤其 group size 小、样本方差大时，GRPO 的相对优势会有噪声。第四，任务难度课程变化。如果训练逐步加入困难样本，平均 reward 也可能阶段性下降。

判断是否健康，要同时看 reward、KL、entropy、格式合法率、长度、验证集指标和人工样本。如果 reward 先降后升，同时 KL 可控、entropy 没塌、验证集后续提升，这是正常探索。如果 reward 下降后不回升、输出格式崩坏、长度异常、KL 爆炸，就要降低学习率、加强 KL、缩短生成长度、调 reward 权重或回滚 checkpoint。

一句话：reward 曲线不能孤立解读，要和策略漂移、输出分布和验证集效果一起看。

## 如何降低大模型输出幻觉？除了Prompt约束之外，还有哪些工程优化方案？

**回答：**

幻觉包括事实不存在、证据不支持、引用错配、工具结果误读和业务状态误判，不能只靠一句“不要编造”。工程上要把生成任务变成有证据、有边界、有验收的流程：

1. **Grounding：** 对时效性或领域事实使用 RAG、数据库、搜索或业务 API；要求答案绑定证据片段、页码或结构化字段，证据不足就澄清或拒答。
2. **工具化计算：** 金额、日期、统计、权限和状态查询由确定性程序完成；模型只负责理解意图和组织结果。
3. **结构化输出与校验：** 使用 JSON Schema、枚举、类型和范围检查；对引用存在性、字段一致性和业务不变量做服务端验证。
4. **拆分与验证：** 将抽取、检索、推理、生成和审查分段，使用规则、单元测试、数据库状态或独立评估器验收；不要让模型自称完成作为唯一标准。
5. **模型和解码控制：** 选择与任务匹配的模型，合理设置温度和输出长度；高风险场景宁可走人工或模板路径，也不要用更高随机性换“自然”。
6. **数据与评测治理：** 修复训练/知识库中的冲突和过期文档，维护真实分布的回归集，分层统计事实错误、拒答错误、引用错误、工具误用和严重业务损失。
7. **运行时安全：** 对外部文档和工具返回标记为不可信数据，防止 Prompt Injection；隔离权限、预算和副作用，记录完整 Trace 便于回放。

最终指标不能只看“看起来流畅”。应同时测答案正确率、证据忠实度、引用精确率、拒答准确率、工具状态一致性、敏感信息泄漏率、成本和延迟。幻觉治理的本质是缩小模型可以无依据自由发挥的空间，并把关键结论交给外部证据和确定性系统确认。

## 如果Token消耗突然增加，你会如何定位原因并进行优化？

**回答：**

先把 Token 当作可观测资源，而不是凭感觉“缩短 Prompt”。我会按 `trace_id / user / task / model / prompt_version / tool / step` 记录输入、缓存命中、推理、输出和工具相关 Token，并与请求量、任务成功率、延迟和费用一起看。

定位顺序如下：

1. **确认增长构成。** 是单请求 Token 增加、请求量增加、Agent 步数增加，还是模型价格/计费口径变化；区分 input、cached input、reasoning 和 output。
2. **比较版本差异。** 检查最近的 Prompt、工具 schema、RAG Top-K、记忆注入、摘要策略、模型路由和重试配置。
3. **查看轨迹分布。** 统计消息类别占比、工具定义长度、检索片段长度、工具返回体、无效步骤数、循环率、重试率和上下文压缩触发率。
4. **定位异常样本。** 对 P95/P99 Token 的任务回放，常见根因是全量工具 schema、重复历史、检索重复、大日志未裁剪、模型陷入循环、失败重试重新携带全部上下文或摘要失效。

优化时先减少无效信息：工具渐进披露、按意图加载 schema；RAG 去重并按 token budget 截断；大文件和日志外置，只传摘要与句柄；长期记忆按需召回；长任务按阶段 checkpoint；设置最大步骤、总 Token 和重试预算。稳定前缀可使用 Prompt caching，简单路由/抽取可切换小模型。

但不能只追求 Token 下降。每项优化都要比较任务成功率、关键信息保留率、P95 延迟和单位成功任务成本：

$$
\text{Cost per Success}=\frac{\text{Total Model Cost}}{\text{Successful Tasks}}
$$

如果 Token 降低 30% 却让重试和人工接管翻倍，它不是有效优化。

## 如果对话轮次过多，你怎么去做优化？

**回答：**

对话过长时，我不会只做一次粗暴截断，而是按“保真优先级 + 按需取回”管理上下文。

第一，永远保护系统约束、权限、当前目标和输出契约；这些内容一旦被摘要掉，Agent 可能改变行为边界。第二，保留最近的完整交互和当前未完成步骤，它们构成工作集。第三，把已完成阶段压缩成结构化状态，而不是自然语言流水账。第四，将原始对话、工具日志和大文件放在外部存储中，通过事件 ID、文件句柄或检索接口按需取回。

上下文组装时再做相关性选择：与当前子任务直接相关的历史优先；已经完成且没有后续依赖的细节只保留结论；失败轨迹只保留失败原因和不可重复的动作，避免模型再次踩坑；高风险决策要保留证据和审批记录，不能只剩一句摘要。

还可以把长任务切成多个有边界的阶段，每个阶段结束生成 checkpoint。子任务之间通过结构化产物传递，而不是把全部对话继续往后拖。对代码 Agent 来说，这种产物可以是修改文件列表、测试结果、剩余 TODO 和当前 Git diff；对业务 Agent，可以是订单 ID、审批状态和待补字段。

Rocky认为，长上下文优化的本质不是“把 Prompt 压短”，而是把对话历史升级为可管理的任务状态。只有状态可恢复、原文可回溯、信息可按需展开，压缩才不会变成不可逆的信息丢失。

## 字符择优连续区间问题，如何转化为最大子数组和问题，Kadane算法复杂度优化逻辑是什么？

**回答：**

先把字符偏好转成数值权重。假设希望找到一段连续区间，使“优选字符”尽量多、“非优选字符”尽量少，可以把优选字符映射为 $+1$，非优选字符映射为 $-1$；若不同字符价值不同，则映射为对应收益或代价。这样问题就转化为：在数值数组中寻找和最大的连续子数组。

Kadane 算法的状态定义是：`current` 表示“必须以当前位置结尾”的最大子数组和，`best` 表示遍历到当前位置时的全局最大和。转移只有两个选择：把当前元素接到前一段后面，或者从当前元素重新开始。

$$
current_i=\max(a_i,\ current_{i-1}+a_i)
$$

$$
best_i=\max(best_{i-1},\ current_i)
$$

Python 实现如下，同时返回最优区间：

```python
def best_interval(text: str, preferred: set[str]) -> tuple[int, int, int]:
    if not text:
        return 0, -1, 0

    scores = [1 if ch in preferred else -1 for ch in text]
    current = best = scores[0]
    current_left = best_left = best_right = 0

    for right in range(1, len(scores)):
        if current + scores[right] < scores[right]:
            current = scores[right]
            current_left = right
        else:
            current += scores[right]

        if current > best:
            best = current
            best_left = current_left
            best_right = right

    return best_left, best_right, best
```

暴力枚举所有区间需要 $O(n^2)$ 个区间；使用前缀和只能把单个区间求和降到 $O(1)$，总枚举量仍是 $O(n^2)$。Kadane 的优化来自最优子结构：如果前缀累计和已经小于零，它只会拖累后续任何区间，因此可以直接丢弃。每个位置只更新常数个状态，时间复杂度降为 $O(n)$，空间复杂度为 $O(1)$。

边界条件要说明：数组全为负数时，上述实现返回最大的单个元素；若业务允许选择空区间，则可把最优值初始化为零，并在所有分数为负时返回空区间。

## 对比学习相比分类式/生成式目标，为什么更适合 CLIP 的大规模预训练？

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

在 CLIP 之前，从图文数据里学视觉表示主要有两种思路。分类式把 caption 映射成固定标签做分类，生成式让模型逐词生成图像的 caption。CLIP 论文做了对比实验，最后选了对比学习，主要因为训练效率高得多。对比学习更适合大规模预训练，原因有三点：

1. **生成式目标太难，收敛慢。** 同一张图可以有很多种合理描述，逐词预测 caption 等于要模型拟合语言的全部细节。CLIP 论文的实验里，一个 63M 参数的 Transformer 语言模型逐词预测 caption，学会识别 ImageNet 类别的速度比预测词袋（bag-of-words）的简单基线慢 3 倍；把词袋预测换成对比目标，效率又提高 4 倍[1]。对比学习只要求匹配图文的相似度高于不匹配的，是宽松得多的代理任务。

2. **分类式目标受限于固定标签空间。** 把 caption 转成 one-hot 标签（如 ImageNet 的 1000 类）会丢掉文本的开放语义，"一只橘色的小猫趴在沙发上"被压成"猫"一个标签，"橘色""沙发""趴"这些概念都学不到。对比学习直接用整句自然语言做监督，标签空间是开放的，CLIP 能做开放词表的零样本分类，前提在这里。

3. **和大 batch、海量噪声数据契合。** InfoNCE 在大 batch 下负样本多，监督信号丰富。4 亿网络图文对里有一部分错配，对比目标拉近正例、推远负例，是在整批样本上做统计平均，受单条噪声 caption 的影响一般比逐词生成小。

形式化地看，CLIP 要让匹配图文对的相似度高于同一 batch 里所有不匹配的对，即满足 $`\text{sim}(f_v(v_i), f_t(t_i)) > \text{sim}(f_v(v_i), f_t(t_j)),\ j \neq i`$。实现这一目标的是对称 InfoNCE 损失，它把图到文、文到图两个方向的损失相加。符号与 [5.1.2.2](https://github.com/WeThinkIn/AIGC-Interview-Book/blob/34e9ee6aa6d35d1e213099a7ae9f433b7b9e6fe6/AI%E5%A4%9A%E6%A8%A1%E6%80%81%E5%9F%BA%E7%A1%80%EF%BC%88%E7%B2%BE%E5%8D%8E%E7%89%88%EF%BC%89/1_AI多模态理论基础高频考点.md#q5122) 一致，损失写作：

其中 $`N`$ 是批内的图文对数，$`t_i`$、$`v_i`$ 是第 $`i`$ 对图文的文本和图像表示，$`\text{sim}(\cdot,\cdot)`$ 是 L2 归一化后的余弦相似度，$`\tau`$ 是温度系数。第一项固定文本 $`t_i`$，在批内全部图像中检索匹配项；第二项固定图像 $`v_i`$，在批内全部文本中检索匹配项。$`\tau`$ 越小，softmax 分布越尖锐。CLIP 把 $`\tau`$ 设为可学习参数，初始值对应 0.07，并限制 logit 的缩放倍数不超过 100[1]。

> **面试速答**：CLIP 论文的实验里，逐词预测 caption 的 Transformer 学 ImageNet 类别比预测词袋慢 3 倍，换成对比目标效率再提高 4 倍。分类式目标把文本压成固定标签，丢掉开放语义；对比学习用整句文本监督，只要求匹配对相似度更高，适合大 batch 和含噪的网络数据。

## 已经构建推理类Reasoning训练数据，为什么还需要接入RL训练？仅依靠SFT能否满足业务需求？

**回答：**

SFT 能教会模型“模仿高质量推理轨迹”，但它本质仍是最大似然学习：给定 prompt 和标准答案，让模型提高参考回答中每个 token 的概率。它解决的是“像不像标注答案”的问题，不天然解决“在多条可能推理路径中哪条更有效、最终结果是否更优、遇到新题能否探索”的问题。

Reasoning 类任务的难点在于：正确性往往依赖长链路、多步搜索、自我校验和中间纠错。SFT 数据即使质量高，也只是覆盖了有限路径，模型容易学到表面格式，比如先写“我们一步步分析”，但真正遇到分布外问题时未必会探索正确路径。RL 的价值在于把优化目标从“模仿轨迹”进一步推进到“最大化结果或过程 reward”。例如数学、代码、字段抽取、结构化推理任务可以设计可验证 reward，让模型通过采样、比较、更新，学会更有收益的推理策略。

仅靠 SFT 在简单、分布稳定、答案形式固定的业务里可以满足初版需求，例如格式化抽取、标准客服话术、模板化摘要。但如果业务要求复杂推理、强泛化、低错误率，或者希望模型学会自检、反思、工具使用、拒答和多轮纠错，SFT 通常不够。更成熟的链路是：先用 SFT 建立基本指令遵循和输出格式，再用 DPO/RLHF/GRPO/RLVR 等后训练方法优化偏好、正确性和推理策略，最后用评测和线上反馈闭环。

## 强化学习课程采样（RLCS）如何解决多领域训练中的样本效率问题？

RLCS的核心思想是将课程学习与在线采样结合，动态匹配模型能力与样本难度。具体流程分为三步：  
1. **离线难度标注**：在训练前，使用多个已有模型对全量数据运行Pass@k评估，结合人工标注将样本划分为“极易”“中等”“极难”等多个等级；  
2. **在线表现追踪**：在RL训练中，实时记录每个样本的推理结果（正确/错误），并与离线难度标签融合，生成动态难度分布；  
3. **比例EMA调整**：通过指数移动平均计算无效样本（全对/全错批次）比例，动态扩展采样规模（如扩展比为1/(1-无效样本率)），确保每批次包含足够多的有效梯度信号。  

该方法显著提升训练稳定性。例如，在混合STEM、OCR、GUI代理的多领域训练中，RLCS通过抑制“极难样本”（避免梯度爆炸）和“极易样本”（避免梯度消失），使模型在数学推理、视觉定位等任务上同步提升。实验显示，其训练效率比均匀采样高30%，且在跨领域泛化中呈现正向迁移（如GUI代理训练反而提升视觉定位能力）。

## 当针对特定领域（如体育视频）微调生成模型时，应该采用哪些特殊策略？

1. 数据层面：
   - 运动轨迹强化（增加球类/运动员跟踪标注）
   - 关键帧提取（得分时刻优先采样）
   - 多机位数据对齐
2. 架构调整：
   - 运动注意力机制（增加轨迹预测头）
   - 物理约束模块（抛物线运动先验）
   - 高速运动专用编码器（处理运动模糊）
3. 训练技巧：
```python
# 典型体育视频训练代码片段
def sports_loss(video_pred, video_gt):
    optical_flow_loss = RAFT_loss(pred_flow, gt_flow)
    trajectory_loss = L1(track_pred, track_gt)
    temporal_consistency = 1 - SSIM(consecutive_frames)
    return 0.6*optical_flow_loss + 0.3*trajectory_loss + 0.1*temporal_consistency
```
4. 评估侧重：
   - 运动轨迹准确性（TO指标）
   - 高速动作清晰度（BSI评分）
   - 规则符合度（如篮球走步检测）

## 微调分别和预训练、后训练、提示工程有什么关系？

| 方法 | 是否更新参数 | 数据类型 | 主要目标 | 典型作用 |
| --- | --- | --- | --- | --- |
| 预训练（Pre-training） | 更新参数 | 海量无标注文本、代码、数学、多语种数据 | 学习通用语言规律、知识表示和基础推理能力 | 构建基座模型能力 |
| 微调（Fine-tuning） | 更新全部或部分参数 | 标注数据、指令数据、领域数据、对话数据、工具调用数据 | 让模型适配特定任务、领域表达、格式或行为模式 | 任务适配、领域适配、格式适配、工具调用适配 |
| 提示工程（Prompt Engineering） | 不更新参数 | Prompt、示例、上下文、系统指令 | 通过输入引导模型临时改变行为 | 快速适配任务、降低开发成本 |

微调和后训练不是完全割裂的概念。微调更像是一类“继续训练模型参数”的技术动作；后训练更像是预训练之后的一整套训练阶段或流程。SFT 既可以被称为微调，也经常被视为后训练的第一阶段。

> **注**：预训练学习通用能力，微调学习任务行为和输出模式，提示工程通过上下文临时引导模型。

## 微调过模型吗；LoRA 听过吗

**回答：**

先如实说明是否做过微调、使用的底座与规模、数据任务、训练方法和自己负责的环节。没有完成过微调实验，可以说明理解原理并给出实验设计，不能把看过教程或调用模型 API 表述成真实训练经验。

LoRA 是一种参数高效微调方法：冻结预训练权重 W，只训练低秩增量。对于线性层，可以写成：

```math
W'=W+\frac{\alpha}{r}BA,\qquad
W\in\mathbb{R}^{d_{\mathrm{out}}\times d_{\mathrm{in}}},\quad
B\in\mathbb{R}^{d_{\mathrm{out}}\times r},\quad
A\in\mathbb{R}^{r\times d_{\mathrm{in}}}.
```

r 是秩，通常远小于输入和输出维度；标准缩放为 α/r，部分变体采用其他缩放规则。可训练参数从 d_out×d_in 降至 r×(d_in+d_out)。常见初始化让一个矩阵为零、另一个为随机值，使初始增量为零，同时允许梯度开始更新。目标模块可选注意力投影或其他线性层，具体配置应与任务和预算共同评估。

LoRA 显著减少可训练参数、梯度和优化器状态，但仍需加载底座并进行前向与必要的反向传播，激活显存并不会等比例消失。QLoRA 进一步结合量化底座和低秩适配，两者不能简单画等号。支持权重合并的部署可以将增量并入兼容精度的底座；量化、多个适配器和动态切换场景还需考虑额外转换或运行开销。

介绍实验时应说明数据清洗、训练测试隔离、学习率、rank、训练步数及验证集选择，而不是只报用了哪张显卡。比较基座、提示词优化、RAG 与微调的效果：经常更新的业务知识通常更适合外部检索，稳定的任务格式和行为模式可以考虑微调。验收包括目标任务收益、通用能力退化、过拟合、成本和推理延迟。

## 怎么做数据混合配比？

- 经验划分；
- DoReMi：先训练小型参考/代理模型，以跨数据域的最坏**超额损失**为信号，用 Group DRO 更新域权重，再用所得权重训练大模型（在没有指定下游任务时，如何减少最差数据域的相对损失）。
- RegMix 则在多种配比上训练许多小模型，将“配比 $\rightarrow$ 验证表现”拟合为回归问题，预测未试配比，再把候选最优配方放大验证。

配比没有固定公式，通常通过实验迭代确定：

```text
设定目标能力 → 数据分桶与质量打分 → 设置初始采样权重 → 小规模训练 → 验证集和 benchmark 评估 → 消融分析 → 调整配比并扩大训练
```

判断依据包括**验证集 loss、下游任务表现、质量分数、重复率、污染风险、目标能力缺口和通用能力回归**。

很多训练还会采用**阶段式配比**：早期使用覆盖广的通用数据建立基础语言和世界知识，中期提高书籍、论文、代码、数学等高质量数据比例，后期加入更多指令、领域或能力增强数据，使模型向目标能力收敛。

**回答：**

## 手撕：DSPO算法侧重序列级优化的设计逻辑与优势

**回答：**

DSPO 这类序列级优化方法的核心思想，是减少把同一个序列级结果机械复制到所有 Token 所造成的信用分配噪声，直接围绕完整序列的概率、回报或偏好进行更新。典型序列目标会使用整段响应的 log-probability：

$$
\log \pi_\theta(y|x)=\sum_t \log \pi_\theta(y_t|x,y_{<t}),
$$

再结合序列级优势、参考策略约束或重要性比率进行优化。它更贴近“任务是否完成”的目标，也不容易因为某个局部 Token 概率变化而过度放大长度效应；代价是序列级信号更稀疏、长序列方差更高，对采样质量、长度归一化和 KL 控制更敏感。

回答时应说明 DSPO 的具体论文/代码版本，因为不同实现对截断、归一化、采样和参考策略的定义可能不同。不要把所有序列级损失都统称成同一个标准算法。

## 推理框架在性能优化上通常做哪些工作？

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

![推理性能优化路径](https://raw.githubusercontent.com/WeThinkIn/AIGC-Interview-Book/34e9ee6aa6d35d1e213099a7ae9f433b7b9e6fe6/%E6%A8%A1%E5%9E%8B%E9%83%A8%E7%BD%B2%E5%9F%BA%E7%A1%80%EF%BC%88%E7%B2%BE%E5%8D%8E%E7%89%88%EF%BC%89/imgs/performance-optimization.png)

推理框架的性能优化可以从”少算、快算、省内存、批量跑”四个角度理解。

### 一、少算：减少不必要的计算

常见方式包括：
- **常量折叠**：把编译期就能算出来的结果提前算好
- **死代码消除**：删除不会影响输出的节点或分支
- **公共子表达式消除**：相同计算只保留一份结果
- **算子融合**：把多个连续小算子合并成一个大算子，例如 Conv + BN + ReLU、MatMul + Bias + Activation
- **低精度推理**：从FP32改为FP16、BF16、INT8、INT4或FP8，在硬件和kernel支持时减少计算开销

### 二、快算：让硬件更高效地执行

推理框架会根据不同硬件选择或生成更快的算子实现：
- CPU上使用SIMD指令、多线程、NUMA亲和性和缓存友好的数据布局
- GPU上使用Tensor Core、shared memory、访存合并、tiling、kernel fusion和CUDA Graph
- NPU/TPU上使用芯片厂商提供的编译器、算子库和专用数据布局

这类优化的目标是提高计算单元利用率，减少访存等待和kernel launch等调度开销。

### 三、省内存：减少内存和显存占用

常见方式包括：
- **内存池 / 显存池**：避免频繁申请和释放内存
- **张量复用**：生命周期不重叠的中间张量共用同一块内存
- **静态内存规划**：提前规划中间张量和workspace，降低峰值占用
- **权重和激活量化**：降低模型参数和中间张量占用
- **KV Cache管理**：大模型推理中通过PagedAttention、Prefix Cache、KV Cache量化等技术减少KV缓存浪费

省内存不仅能降低资源成本，也能让同一张GPU承载更大batch、更长上下文或更多并发会话。

### 四、批量跑：提升吞吐和硬件利用率

单个请求往往无法充分利用GPU或加速器。推理框架通常会把多个请求合并成一个batch执行，从而提高吞吐量。

常见方式包括：
- **静态批处理**：固定batch大小，适合离线或输入形状稳定的场景
- **动态批处理**：在线服务中短时间窗口聚合请求，在延迟和吞吐之间做权衡
- **连续批处理**：大模型推理中每个decode step动态加入新请求、移除已完成请求，避免短请求完成后槽位空闲

可以总结为：**推理框架性能优化的核心是减少无效计算、提升单算子执行效率、降低内存和显存开销，并通过batching和调度提高硬件利用率。实际收益必须结合模型结构、输入shape、硬件后端、精度方案和压测负载验证。**

## 改用BCE+InfoNCE联合损失的原因，两项损失各自带来的效果增益

**回答：**

BCE 和 InfoNCE 解决两个层面的问题。BCE 是点式目标，判断一个 Query-Item 对本身的相关概率；InfoNCE 是对比目标，让正样本在候选集合中排到负样本前面。

$$
\mathcal{L}_{BCE}
=-\left[y\log\sigma(z)+(1-y)\log(1-\sigma(z))\right]
$$

$$
\mathcal{L}_{InfoNCE}
=-\log
\frac{\exp(\operatorname{sim}(q,i^+)/\tau)}
{\sum_{j=1}^{K}\exp(\operatorname{sim}(q,i_j)/\tau)}
$$

联合目标通常为：

$$
\mathcal{L}
=\lambda\mathcal{L}_{BCE}
+(1-\lambda)\mathcal{L}_{InfoNCE}
$$

BCE 的增益通常体现在分数校准、绝对相关性判断和业务标签拟合；InfoNCE 通常改善 Embedding 空间分离、召回排序和长尾语义匹配。但没有消融实验不能声称某一项带来固定增益。应设置 BCE-only、InfoNCE-only、联合损失和不同 $\lambda$ 的实验，比较 AUC、Recall@K、nDCG、分桶和线上指标。

联合训练还要处理 loss 尺度不同、温度 $\tau$、批内假负样本和点击偏差。真正的理由不是“多加一个 loss 更强”，而是两种监督是否提供互补信号，并且稳定性和成本是否可接受。

## 数据加载、预处理、模型推理、后处理各阶段的典型耗时分布与优化思路是什么？

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

### 一、推理全链路的五阶段模型

```
请求到达 → [网络接收] → [队列等待] → [预处理] → [推理 (H2D+计算+D2H)] → [后处理] → [网络返回] → 响应
```

| 阶段 | 典型耗时占比 | 主要瓶颈 | 是否可流水线化 |
|------|------------|---------|-------------|
| 网络接收/返回 | < 5% | 网络带宽、序列化开销 | 是 |
| 队列等待 | 0-50%+ | 并发、批策略、负载 | 部分 |
| 预处理 | 5-30% | CPU 算力、图像解码、Tokenization | 是 |
| 模型推理 | 40-90% | GPU 算力/带宽、模型结构 | 部分（H2D/D2H） |
| 后处理 | 5-20% | CPU 算力、NMS、解码 | 是 |

### 二、各阶段的优化思路

1. 数据加载（Data Loading）
**瓶颈特征**：GPU 空闲等待，Timeline 上推理 Kernel 之前有大段空白。

**优化手段**：
- **预取（Prefetch）**：`DataLoader(num_workers>0, prefetch_factor=2)`，让数据加载与 GPU 计算重叠
- **固定内存（Pinned Memory）**：使用 `pin_memory=True` 加速 H2D 传输
- **预处理前置**：将耗时预处理（如 JPEG 解码、Tokenization）放到独立线程池或单独的预处理服务

2. 预处理（Preprocessing）
**瓶颈特征**：CPU 占用高，H2D 之前时间明显长。

**优化手段**：
- **GPU 上做预处理**：图像 resize/normalize 可以用 PyTorch CUDA 算子或 nvJPEG 硬解码
- **批量化预处理**：多个请求的预处理合并执行，利用 SIMD
- **预计算和缓存**：归一化参数预存为张量，避免每次计算

3. 模型推理（Model Inference）
**瓶颈特征**：GPU 活跃时间长，但延迟仍不满足要求。

**优化手段**：
- 模型压缩（量化、剪枝、蒸馏）
- 图优化（算子融合、常量折叠）
- 精度降级（FP32 → FP16 → INT8）
- Kernel 级优化（Tensor Core 启用、内存访问优化）

4. 后处理（Postprocessing）
**瓶颈特征**：推理完成后 CPU 处理时间长，且与下一请求的推理串行。

**优化手段**：
- **GPU 化**：NMS（非极大值抑制）、CTC 解码等可用 CUDA 实现
- **异步化**：后处理与下一请求的预处理/推理并行
- **算法优化**：如 soft-NMS 替换标准 NMS、Top-K 采样优化

### 三、时序拆解的实操方法

**方法 1：代码打点**
```python
import time
t0 = time.time()
input_tensor = preprocess(data)  # t1
output = model(input_tensor)     # t2
result = postprocess(output)     # t3
print(f"pre: {t1-t0:.2f}ms, infer: {t2-t1:.2f}ms, post: {t3-t2:.2f}ms")
```

**方法 2：Triton Inference Server 自动拆解**
Triton 自动记录每个请求的 Queue、ComputeInput、ComputeOutput、ComputeInfer 等阶段的耗时，通过 `--metrics` 暴露。

**方法 3：Nsight Systems + NVTX 标记**
分别在预处理/推理/后处理代码段插入 NVTX 标记，在 Timeline 上直接看到各段精确耗时。

可以总结为：**推理全链路的时耗拆解是性能优化的第一步——不知道"时间花在哪"就不知道该优化什么。典型优化策略是"让预处理和推理重叠、让后处理异步化、让推理本身加速"。**

## 数据课程学习、退火与合成数据应如何进入预训练配方？

**难度评分：⭐⭐⭐⭐⭐ (5/5) | 考察频率：⭐⭐⭐⭐ (4/5)**

数据课程不是简单的“先易后难”，而是让混合分布随已训练 token $t$ 变化：

```math
p_t(x)=\sum_i\alpha_i(t)p_i(x)
```

常见策略是早期用覆盖广、低重复的通用语料建立语言统计，中期提高代码、数学、书籍和论文比例，末期数据退火到高质量、长文本和目标域样本，同时配合学习率衰减。末期高质量数据的价值在于把有限的小步长更新投入更可信的 token；风险是配方过窄会造成通用能力回退，因此必须用多桶验证集做回归。

合成数据应当被当作一个独立的、经验可控的数据领域来对待，而不是简单地把生成内容倒进原始语料就当作扩容。可写为：

```math
q(x)=\lambda p_{\text{real}}(x)+(1-\lambda)p_{\text{synthetic}}(x)
```

> **注 **：**多桶验证集**是把验证数据按领域/难度等切成多个子集，分别评估模型在每个子集上的表现。它能体现“不同配比对不同能力的影响”，避免用单一总分掩盖偏科，从而找到更均衡、更可靠的数据配比。

## 无约束优化、有约束优化、拉格朗日乘子和 KKT 条件如何理解？

无约束优化形式：

$$
\min_x f(x)
$$

常见方法包括梯度下降、Momentum、Adam、Newton 法、拟 Newton 法等。深度学习训练大多数时候可看作大规模随机无约束优化。

等式约束优化形式：

$$
\min_x f(x),\quad \text{s.t. } h_i(x)=0
$$

拉格朗日函数：

$$
\mathcal{L}(x,\lambda)=f(x)+\sum_i\lambda_i h_i(x)
$$

最优点需要满足驻点条件：

$$
\nabla_x\mathcal{L}(x,\lambda)=0
$$

不等式约束优化形式：

$$
\min_x f(x),\quad \text{s.t. } g_i(x)\le 0,\ h_j(x)=0
$$

KKT 条件包括：

- 原始可行性：$g_i(x)\le 0,\ h_j(x)=0$
- 对偶可行性：$\lambda_i\ge 0$
- 互补松弛：$\lambda_i g_i(x)=0$
- 驻点条件：$\nabla_x \mathcal{L}(x,\lambda,\nu)=0$

**AI 中的典型联系：**

- SVM 的最大间隔推导依赖拉格朗日对偶和 KKT。
- PPO、DPO、RLHF 中的 KL 约束可以看作约束优化或正则化优化。
- 权重范数约束、谱范数约束、正交约束都属于约束优化思想。
- 实践中常把硬约束转成软惩罚，例如 $L+\lambda R(\theta)$。

## 是否有推荐的调参顺序？

实际微调中，通常不建议一开始同时调所有参数，可以按优先级逐步调整：

1. 数据和目标：确认数据质量、聊天模板、损失掩码和验证集。
2. 确定最大长度：保证关键指令、上下文和答案不被截断。
3. 根据显存确定微批大小：尽量避免显存溢出。
4. 用梯度累积设置全局批大小：兼顾稳定性和显存。
5. 优先调学习率和轮数：这是影响效果和遗忘风险最大的组合。
6. 再调预热、调度器、权重衰减和梯度裁剪：提升稳定性。
6. 最后微调结构参数：调 LoRA秩（LoRA rank）、缩放因子（alpha）、随机失活（dropout）和目标模块（target modules）等参数，在效果和成本之间做权衡。

## 最常用的粗估公式是什么？

稠密仅解码器变换器（Decoder-only Transformer）的预训练算力常用近似为：

```math
\text{FLOPs}_{\text{train}} \approx 6 \times N \times D
```

其中， $N$ 是每个词元（token）训练时参与计算的有效参数量，稠密模型中可近似为总参数量； $D$ 是训练 token 总数。系数 6 来自经验分解：前向约 $2ND$，反向和参数梯度约 $4ND$。这是面试中最常用的一级估算，但它是粗估，不精确包含通信、数据加载、填充、激活检查点、软最大值、层归一化和失败重训等开销。

## 模型开启/关闭Thinking推理机制，对微调训练效果的影响

**回答：**

Thinking 开关本质上是在控制模型是否显式生成中间推理过程。开启 Thinking 时，模型会分配更多 token 给问题分析、步骤拆解、自检和反思；关闭 Thinking 时，模型更倾向于直接给出结果或短解释。

对 SFT 的影响主要有三点。第一，训练目标不同。开启 Thinking 的样本如果包含高质量推理链，模型能学到中间策略，对数学、代码、复杂字段推断、长链路决策有帮助；但如果推理链质量差，模型会学习冗长、绕路甚至错误的思考模式。第二，成本和延迟不同。Thinking 会增加输出长度，训练和推理成本都上升。第三，评测口径不同。有些业务只需要最终结构化字段，显式思考反而可能泄露内部逻辑或影响格式稳定。

实操上要按任务分流。复杂推理、规则验证、疑难样本可以开启 Thinking 或训练 hidden reasoning；简单抽取、固定格式生成、低延迟线上接口更适合关闭 Thinking。训练数据也要区分：有 thinking 标签的样本、无 thinking 的直接答案样本、只对 final answer 计 loss 的样本不要混在一起乱训。

成熟方案不是永远开或永远关，而是让模型学会按任务选择推理预算：简单任务短答，复杂任务展开推理，高风险任务自检，最终对用户输出可控、简洁、可验证的结果。

## 模型微调用的是全参微调还是lora微调，为什么这么选

**回答：**

先报告真实选择，再讲依据。LoRA 只学习选定层的低秩增量，优化器与梯度开销小，适合资源有限、多任务适配和快速迭代；全参微调允许更广泛地改变表示，但需要更多显存、计算和足量高质量数据，也更容易改变原能力。

多模态模型还要区分视觉编码器、连接器与语言主干。可先训练连接器或语言侧 LoRA，再根据失败类型决定是否扩大适配层或解冻视觉部分，不必只有全参和全部冻结两个极端。

在相同测试集比较质量、成本、遗忘和部署方式。低秩适配没有解决的错误可能来自数据或视觉分辨率，不能直接把它归结为 rank 不够。

## 模型训练加速有什么方法

**回答：**

训练加速可以按“减少计算量、减少显存、减少通信、提高流水线利用率、减少无效数据”五个方向组织。

1. **精度与算子。** 使用 BF16/FP16 混合精度、TF32 的适用路径、FlashAttention、fused activation、fused optimizer、CUDA Graph 和 kernel fusion。混合精度要配合 loss scaling 或框架的数值稳定策略，并监控溢出、梯度范数和 loss 是否异常。
2. **显存优化。** Gradient Checkpointing、Activation Offload、参数/梯度/优化器分片、KV 或中间激活重用。Checkpointing 不是无成本加速，它通过重算降低显存，通常是用显存换算力。
3. **并行训练。** Data Parallel 复制模型处理不同 batch；Tensor Parallel 切分层内矩阵；Pipeline Parallel 按层切分并用 micro-batch 填充流水线；Sequence Parallel 减少长序列激活压力；MoE 还需要 Expert Parallel 和 All-to-All。混合并行要结合模型尺寸、序列长度、GPU 互联和 batch 形态选择。
4. **通信优化。** 梯度桶化、通信计算重叠、梯度累积减少同步频率、合理设置 NCCL、拓扑感知的设备映射和分层通信。多卡加速不等于线性加速，通信时间、负载不均衡和 pipeline bubble 都要纳入分析。
5. **数据与序列。** 清洗重复和无效样本、packing、长度分桶、动态 batch、异步预取、缓存 tokenizer/视觉特征、减少 padding。数据读取和 CPU 预处理跟不上时，GPU 再快也会空转。
6. **训练策略。** 选择合适的 global batch、学习率调度、梯度累积、参数高效微调、冻结部分模块和 curriculum。若只需领域适配，LoRA/QLoRA 可能比全量训练更经济；但它不是普适的速度提升，目标模块、量化反量化和小 batch kernel 效率都要实测。
7. **系统与工程。** 使用高效 checkpoint、断点续训、异步日志、持久化进程、预分配内存和 profiler；通过 Nsight Systems、PyTorch Profiler、训练框架 trace 分辨计算、内存、通信、I/O 和同步瓶颈。

一个有说服力的优化闭环是：先建立固定 batch 和数据版本的基线，记录 step time 分解；每次只改一个变量；同时报告吞吐、峰值显存、数值稳定性和验证集效果；最后在目标硬件和真实数据分布上复测。不能只报单卡 FLOPS 或 GPU 利用率，因为无效 token 增多时 GPU 利用率可能上升，任务质量却下降。

## 比较提示学习和微调两种方法，并分析它们在下游任务中的适用场景

提示学习通过设计特定的输入提示来引导模型生成所需的输出，它适用于模型已经具备一定泛化能力且需要生成特定类型输出的任务。

提示方法试图通过学习一个语言模型来模拟文本 x自身的概率 P(x; θ)，并使用这个概率预测 y，从而减少对大量标记数据集的需求。提示方法最基本的数学描述包含许多关于提示的研究，并且可以扩展到其他方法。

微调则是通过在下游任务的数据集上调整模型的参数来优化模型在特定任务上的性能，适用于模型在特定任务上需要显著提升性能的情况。

![](https://raw.githubusercontent.com/WeThinkIn/AIGC-Interview-Book/34e9ee6aa6d35d1e213099a7ae9f433b7b9e6fe6/AI%E5%A4%9A%E6%A8%A1%E6%80%81%E5%9F%BA%E7%A1%80/imgs/微调.png)

（ 1) 适配器微调：这种方法使用神经适配器或模块化组件，以增强LLM 在特定领域任务上的性能，而不对 LLM 的内部参数进行大幅修改。这些适配器通常集成到现有的 LLM 结构中，允许进行特定任务的学习，同时保持原始模型基本完整。
（ 2) 任务导向微调：这种方法侧重于修改 LLM 的内部参数，以与特定任务对齐。然而，由于硬件限制和潜在的性能下降，完全更新 LLM 的所有参数是不现实的。因此，研究人员面临的挑战在于在广泛的参数空间内确定哪些参数需要被修改，或者如何高效地更新这些参数的子集。

## 泰勒展开和极限思想在优化与大模型训练中有什么作用？

泰勒展开用函数在某点的导数信息近似局部函数形状。一阶泰勒展开：

$$
f(x+\Delta x)\approx f(x)+\nabla f(x)^T\Delta x
$$

二阶泰勒展开：

$$
f(x+\Delta x)\approx f(x)+\nabla f(x)^T\Delta x+\frac{1}{2}\Delta x^TH\Delta x
$$

其中 $H$ 是 Hessian。

**在优化中的意义：**

- 梯度下降来自一阶近似：沿负梯度方向能最快降低局部线性近似。
- Newton 法来自二阶近似：利用 Hessian 曲率信息选择更新方向。
- 学习率过大时，局部近似失效，训练可能震荡或发散。
- Sharpness、平坦极小值、Hessian 特征值分析都依赖二阶局部近似。

极限思想贯穿深度学习数学：

- 导数是变化率在步长趋于 0 时的极限。
- 梯度下降可看作连续梯度流的离散近似。
- SDE/ODE 扩散模型把离散去噪过程推广到连续时间极限。
- 大 batch 梯度趋近全量梯度，小学习率更新趋近连续优化轨迹。

**面试回答模板：**

泰勒展开告诉我们“局部怎么变”，梯度给出一阶方向，Hessian 给出二阶曲率；现代深度学习主要用一阶方法，是因为参数规模太大，完整二阶矩阵难以存储和求逆。

## 用过哪些大模型微调方式，LoRA微调原理

**回答：**

可先区分全参微调、参数高效微调与训练目标。全参微调更新模型全部选定参数；LoRA、Adapter、Prefix/Prompt Tuning 限制可训练部分；SFT、DPO 等描述目标与数据组织，可以与部分参数高效方法组合。

LoRA 对线性权重采用：

```math
W'=W+\frac{\alpha}{r}BA,\quad B\in\mathbb R^{d_{out}\times r},\quad A\in\mathbb R^{r\times d_{in}}
```

冻结 $`W`$ 后，仅训练 $`r(d_{in}+d_{out})`$ 个增量参数，减少梯度与优化器状态开销。它仍需要主模型前向和部分反向激活，不能认为显存按可训练参数比例等比下降。部署时可在适用条件下把增量合并进权重，或保留多个适配器动态切换。

回答使用经验时，只列实际做过的方式，进一步说明 target modules、rank、学习率、数据量和验证集收益；没做过的方式应作为原理理解。

## 相比 CLIP/BLIP 的对比学习，LLaVA 的生成式训练带来了哪些能力差异？

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

LLaVA 全程用自回归语言建模损失，CLIP 用纯对比损失，BLIP 用对比、匹配加生成的混合损失。训练目标不同，能力边界也不同，差异主要体现在四个方面：

1. **从判别、检索到开放式对话。** CLIP 的对比学习学到的是图文是否匹配，属于判别能力；LLaVA 的生成式训练让模型能针对任意指令生成自由文本，可以多轮对话、解释和推理。CLIP 答不了"请详细描述这张图并推测拍摄者的意图"，LLaVA 可以。

2. **直接调用 LLM 的推理能力。** 生成式训练和 LLM 的预训练目标（next-token prediction）一致，能直接复用 LLM 的世界知识、逻辑推理和常识。对比学习的输出只是一个相似度，调动不了这些能力。

3. **指令跟随。** 这是 LLaVA 和 BLIP 系的主要区别。BLIP、BLIP-2 也能生成，但主要面向 captioning、VQA 等固定任务；LLaVA 经过指令微调，能理解多样、开放的人类指令，更接近通用视觉助手。

4. **代价是让出检索效率和判别精度。** LLaVA 不产出可索引的对齐向量，不适合做大规模跨模态检索，那仍是 CLIP 双塔的场景。在图文是否匹配这种纯判别任务上，生成式模型也未必比专门的 ITC、ITM 更准、更快。

三者的定位可以这样区分，CLIP 是对齐器和检索器，BLIP 是理解与生成统一的模型，LLaVA 是以 LLM 为中心的视觉对话助手。从 CLIP 到 LLaVA，训练目标从对比走向生成，能力重心也从检索匹配移到理解、推理和对话。

> **面试速答**：LLaVA 全程用语言建模损失，和 LLM 的预训练目标一致，能直接调用 LLM 的知识和推理，做开放式多轮对话；指令微调又让它能理解多样的人类指令，BLIP 系主要面向固定任务。代价是不产出可索引的对齐向量，不适合大规模检索，纯判别任务也未必比 ITC、ITM 准。

## 知识蒸馏、温度系数和 KL 损失如何理解？

知识蒸馏让学生模型学习教师模型输出分布，而不只是学习 hard label。

带温度的 Softmax：

$$
p_i^{(T)}=\frac{\exp(z_i/T)}{\sum_j\exp(z_j/T)}
$$

蒸馏损失常用 KL：

$$
L_{\text{KD}}=T^2D_{KL}(p_T^{\text{teacher}}\|p_T^{\text{student}})
$$

温度 $T$ 越大，分布越平滑，学生能学习到类别之间的“暗知识”。在 LLM 中，蒸馏还可以表现为：

- logits 蒸馏
- chain-of-thought 蒸馏
- preference distillation
- step-by-step reasoning distillation

## 离线训练和在线服务特征不一致，怎么对齐？

**回答：**

先把“不一致”拆成定义不同、时间不同、版本不同和数据缺失。比如离线按天统计、线上按滑动 24 小时统计；离线缺失填 0、线上填 -1；离线 tokenizer 和线上不是同一版本。这些都会让同一模型面对不同输入分布。

为每个特征建立契约：实体键、dtype、单位、时间窗口、时区、可用时间、空值规则、枚举版本和过期策略。尽量共享转换实现，或者从同一声明式定义生成批处理与流处理；使用同一个特征平台有帮助，但不能自动消除不同执行引擎的语义差异。

上线请求抽样记录实际输入值及版本，离线按相同请求时刻重算，逐字段比较缺失率、误差、分布和延迟。离散特征通常要求严格一致，浮点聚合使用可解释容差；已知迟到数据应作为时间一致性问题单独统计，不能简单忽略。

模型、特征 schema、embedding 模型、词表、预处理和服务镜像应组成可回滚的版本包。新版本先影子运行，兼容期间双写双读或适当回填；发布时避免先上新模型却仍喂旧特征。监控在线新鲜度、默认值占比、缓存命中与缺失特征告警，确保对齐持续发生。

验收不仅看字段是否相同，还要比较模型中间输出与最终分数。如果同输入仍不同，继续排查量化、算子、数值精度和导出图。这样才能把训练到服务的一致性检查覆盖到最后一层。

## 笔试题：找出文件中top k的字串，简单说了下用哈希以及用哈希的缺点和优化点

**回答：**

这题要先澄清“字串”含义：如果指按分隔符切出来的词/字符串，问题是大文件 Top K 频次；如果指所有连续子串，复杂度会爆炸，需要限制长度或使用后缀结构。面试里通常考的是大文件 Top K 高频字符串。

基础做法是哈希计数 + 小根堆。逐行读取文件，分词后用哈希表统计频次；统计完成后维护大小为 K 的小根堆，堆顶是当前 Top K 中频次最小的字符串。时间复杂度约为 $O(n + m\log k)$，其中 n 是总 token 数，m 是不同字符串数；空间复杂度是 $O(m)$。

哈希的缺点也要讲清楚。第一，大文件下不同字符串太多，哈希表可能放不进内存。第二，哈希冲突虽然平均可控，但极端情况下会退化。第三，分布倾斜时，热点 key 更新频繁。第四，如果文件远大于内存，单机一次性哈希不现实。

优化思路有几种：内存够时用哈希 + 小根堆；内存不够时按 hash 分桶，把字符串写入多个临时文件，每个桶内统计局部 Top K，再合并全局 Top K；近似统计可以用 Count-Min Sketch + heap；分布式场景可以用 MapReduce/Spark，map 做局部计数，reduce 汇总。回答时要体现：简单数据用哈希，海量数据要外部排序/分桶/分布式，精度可放松时才用近似算法。
