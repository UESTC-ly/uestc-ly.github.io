# 移动端

Android 与 iOS 具有不同的组件、调度与内存模型。Android 的 Handler、Service 与 iOS 的 RunLoop、GCD 需要分别理解。

<a id="m4938fa865ed6"></a>

## Android Activity 生命周期与界面状态

Activity 的创建、启动、恢复、暂停、停止等回调反映界面与用户交互状态的变化。进入后台不等于立刻销毁，配置变化或系统回收又可能使实例重新创建。应根据回调安排可见资源和交互资源，而不是把所有资源都留到 `onDestroy` 才释放。

状态也要按寿命分层：暂时的视图状态、跨配置变化的屏幕状态、需要进程重建后恢复的数据并不相同。系统不保证进程被终止前总有机会调用所有清理回调，持久数据不能依赖最终销毁通知才保存。测试旋转屏幕、切后台和进程重建，才能检验恢复逻辑是否完整。

来源：[amitshekhariitbhu/android-interview-questions](https://github.com/amitshekhariitbhu/android-interview-questions/blob/a8f95e444cd9a52a244929c55dd9fdc9ffe336d0/README.md#L346)；[Android Activity 生命周期](https://developer.android.com/guide/components/activities/activity-lifecycle)。

<a id="ma345733ccc93"></a>

## Android Fragment 与视图生命周期

Fragment 作为可复用的界面单元，有自己的生命周期，也有它所创建视图的生命周期。Fragment 对象仍被保留时，旧视图可能已经销毁；继续持有视图绑定、监听或回调，就可能操作已失效界面或让旧视图无法回收。

因此与视图相关的订阅和引用应绑定到视图生命周期，业务或屏幕状态则放在适当的状态持有者。它与 Activity 不是单纯“大页面和小页面”的区别，还涉及宿主、导航和恢复关系。异步结果返回时，应确认目标界面仍有资格接收，而不是只判断 Fragment 对象还存在。

来源：[amitshekhariitbhu/android-interview-questions](https://github.com/amitshekhariitbhu/android-interview-questions/blob/a8f95e444cd9a52a244929c55dd9fdc9ffe336d0/README.md#L342)。

<a id="m87283ac90e6d"></a>

## Android ViewModel 与状态持久化

ViewModel 为屏幕保存和组织状态，能跨常见配置变化继续存活，避免界面重建时重复发起同一工作。它的寿命由对应作用域决定，不意味着能跨任意进程终止永远保存数据，也不应持有比它更短命的 Activity 或视图引用。

需要进程重建后恢复的小状态可使用合适的保存状态机制，长期业务数据应进入持久存储。界面订阅状态时仍要遵循生命周期，避免不可见界面继续重复收集。回答“MVVM 有什么用”时，核心是状态归属和依赖方向，而不是为每张页面机械创建一组类。

来源：[Android ViewModel](https://developer.android.com/topic/libraries/architecture/viewmodel)。

<a id="m64d80d619118"></a>

## Android Handler、Looper 与消息队列

Handler 把消息或任务提交给关联 Looper 的队列，由该 Looper 所在线程调度处理。它不会因为调用 `post` 就新建一条执行线程；任务最后在哪运行，取决于 Handler 关联的 Looper。主线程上耗时任务仍会阻塞交互，改用 Handler 投递不能自动改变这一点。

延迟投递表达最早可处理的时间条件，不保证准确时刻执行。长寿命队列中的任务若捕获 Activity 等短寿命对象，还可能延长其存活。应在生命周期结束时取消不再需要的任务，并明确线程切换、取消与状态有效性，避免把内存问题仅归因于“Handler 必须静态”。

来源：[amitshekhariitbhu/android-interview-questions](https://github.com/amitshekhariitbhu/android-interview-questions/blob/a8f95e444cd9a52a244929c55dd9fdc9ffe336d0/README.md#L496)。

## Android Service、协程与持久后台任务

Service 是应用组件，不自动提供独立后台线程；协程或执行器组织进程内异步工作，也不保证进程被系统终止后任务仍继续。前台服务涉及用户可见通知与系统限制，适用性需要按平台版本和任务类型判断。

WorkManager 用于需要可靠调度、能够在应用离开前台或重启后重新安排的工作，可表达网络、电量等条件以及重试。它不是精确时钟，也不是所有立即执行工作的通用替代。选型时先问任务是否必须跨进程存活、能否推迟、是否用户可见，再选择对应组件，并使任务可重试且业务幂等。

来源：[amitshekhariitbhu/android-interview-questions](https://github.com/amitshekhariitbhu/android-interview-questions/blob/a8f95e444cd9a52a244929c55dd9fdc9ffe336d0/README.md#L458)；[Android 持久任务调度](https://developer.android.com/develop/background-work/background-tasks/persistent)。

<a id="ma3d4b73f9ec0"></a>

## Android IPC、Binder 与数据边界

不同进程拥有独立地址空间，跨进程调用必须经过明确的数据传递和权限边界。Binder 为 Android 组件间调用提供基础能力，AIDL 可描述接口并生成编解码与调用桥接；表面的方法调用仍可能阻塞、失败或因对方进程结束而中断。

接口设计要控制报文规模、调用频率和线程处理，并验证调用者权限。把大对象或高频细粒度交互放进同步 IPC，可能同时带来序列化成本和主线程等待。跨进程对象引用也不是普通内存指针，不能沿用进程内对象生命周期的直觉。

来源：[amitshekhariitbhu/android-interview-questions](https://github.com/amitshekhariitbhu/android-interview-questions/blob/a8f95e444cd9a52a244929c55dd9fdc9ffe336d0/README.md#L474)。

<a id="m88de5c219b28"></a>

## Android 列表复用、卡顿与 ANR

列表复用把视图创建与数据绑定分开，让可见项使用有限的视图对象；复用本身不保证绑定便宜，图片解码、复杂布局或重复网络请求仍可能造成卡顿。异步绑定结果还需核对视图当前对应的数据身份，避免旧图片显示到新条目。

ANR 关注系统要求及时响应的工作被长期阻塞，常见证据包括主线程栈、锁等待、同步 IPC 和 I/O。排查先看卡在哪条调用路径，再区别计算过重、等待资源或等待另一个进程；不能只看到主线程在等待就盲目增加线程，也不能用某个固定超时值解释所有 ANR 类型。

来源：[amitshekhariitbhu/android-interview-questions](https://github.com/amitshekhariitbhu/android-interview-questions/blob/a8f95e444cd9a52a244929c55dd9fdc9ffe336d0/README.md#L405)。

## iOS ARC、strong 与 weak

ARC 根据对象的引用所有权自动插入或管理保留与释放操作，不等同于定期扫描全部对象的追踪式垃圾回收。强引用维持对象存活，弱引用不拥有对象，并可在目标销毁后自动清空。两个长期互相强持有的对象可能形成引用环，使外部引用消失后仍无法释放。

解决问题应画出真正的持有关系，并选择哪条关系本来就不应拥有对方，而不是把所有属性都改成 weak。弱引用在读取时也可能已经为空，需要按生命周期处理。Objective-C 的 `assign` 与对象弱引用不能简单互换；值类型属性、对象生命周期和零值语义属于不同维度。

## iOS copy、可变对象与封装

声明为不可变接口的对象，实际传入值仍可能是可变子类；如果只保留同一个对象，外部修改就会改变内部看到的内容。需要保护这一值边界时，复制可以建立适当的独立或不可变表示。`copy` 表达的是复制协议语义，不应仅凭关键字断言必然产生新地址。

容器复制通常也不代表所有嵌套成员都深度独立。若声明类型需要可变接口，却用复制操作得到不可变对象，再调用修改方法就可能失败。面试中的 copy/strong、浅拷贝/深拷贝应统一回到“哪一层独立、对象是否可变、外界能否改变内部状态”来解释。

## iOS block、闭包捕获与引用环

对象保存一个回调，而回调又强持有该对象时，会形成持有环。是否泄漏取决于回调保存多久以及何时解除，不是出现 `self` 就必然泄漏。一次被执行后即释放的临时任务，与长期保存的属性回调、定时器或订阅具有不同生命周期。

弱捕获可以避免不必要的长期拥有，但执行期间又要明确对象是否必须存活。应把捕获列表、回调解除、订阅取消和线程语义一起说明；若业务需要的是结束后必定完成某项动作，单纯弱捕获后静默跳过也可能违背业务要求。

## iOS RunLoop、事件源与 Timer

RunLoop 组织线程上的事件处理，在有工作时分发事件，在合适时机等待新的输入；它不是一条新线程。主线程的事件处理循环由框架组织，其他线程是否配置并运行循环要看工作需求。Timer 是否被处理与当前运行模式、队列繁忙和线程调度都有关。

因此 Timer 不是精确实时保证。若滚动等交互切换了处理模式，某个模式中的计时器可能暂时不被处理；Common Modes 是一组模式关联的机制，不能当成另一条并行线程。管理计时器还要处理目标对象持有与失效清理，避免任务结束后继续保留资源。

来源：[iOSInterviewQuestions 固定版](https://github.com/ChenYilong/iOSInterviewQuestions/blob/b45dfde38042419c0084cf14a5e1596181daf4ec/01%E3%80%8A%E6%8B%9B%E8%81%98%E4%B8%80%E4%B8%AA%E9%9D%A0%E8%B0%B1%E7%9A%84iOS%E3%80%8B%E9%9D%A2%E8%AF%95%E9%A2%98%E5%8F%82%E8%80%83%E7%AD%94%E6%A1%88/%E3%80%8A%E6%8B%9B%E8%81%98%E4%B8%80%E4%B8%AA%E9%9D%A0%E8%B0%B1%E7%9A%84iOS%E3%80%8B%E9%9D%A2%E8%AF%95%E9%A2%98%E5%8F%82%E8%80%83%E7%AD%94%E6%A1%88%EF%BC%88%E4%B8%8B%EF%BC%89.md#L441)。

## iOS GCD 的同步、异步与串行

同步或异步描述提交方是否等待任务完成，串行或并发描述队列怎样调度多个任务，两组概念不能相互替代。主队列是关联主线程的串行队列；从主队列正在执行的任务中，再同步提交一个必须等主队列才能执行的任务，会形成相互等待。

后台队列适合承载可并发工作，UI 更新则要遵守界面的线程隔离要求。串行队列可组织某项状态的顺序访问，但多个独立串行队列之间仍可能并发。设计取消、错误与回调时应确认实际执行队列，不能把 `async` 直接当成“新建一个专用线程”。
