# 项目介绍与技术取舍

<a id="kaa23d1d3db1e"></a>

## 项目里LangChain做了哪些工具调用，有没有实现memory相关功能，还是只做prompt编排？

**回答：**

如果只说“用了 LangChain 写 prompt”，会显得项目停留在 demo。更好的回答要区分 prompt 编排、tool calling、memory 和 workflow orchestration。

在视频剪辑 Agent 里，LangChain 可以承担三类工作。第一是工具调用，把模型输出连接到确定性工具，例如素材检索工具、脚本结构化工具、字幕生成工具、TTS 工具、视频转码工具、时间轴校验工具、封面生成工具。模型负责判断下一步调用什么工具和传什么参数，工具负责真实执行。

第二是中间状态管理。比如把用户需求、脚本版本、素材候选、镜头列表、字幕片段、音频时长、渲染结果都作为结构化状态保存，而不是散落在 prompt 里。这部分如果链路复杂，用 LangGraph 的 StateGraph 会比单纯 LangChain chain 更清晰。

第三是 memory。这里要分短期 memory 和长期 memory。短期 memory 保存当前任务上下文，例如用户修改意见、已选素材、前一次生成失败原因；长期 memory 保存创作者偏好，例如常用风格、字幕样式、视频节奏、品牌词和禁用词。Memory 不能无脑把对话塞回 prompt，而要有写入策略、检索策略、过期策略和冲突处理。

所以我的回答是：项目不是只做 prompt 编排，而是把 LangChain/LangGraph 用作工具调用和状态编排层；memory 做了任务级短期记忆，长期偏好记忆可以按用户画像和风格模板继续扩展。

## 项目里封装了CLI工具，介绍下CLI的实际开发内容？

**回答：**

CLI 的开发内容应落到可调用契约，而不只是给脚本加命令名。可以介绍子命令划分、参数 schema、配置优先级、鉴权、服务调用、输出协议、退出码、错误处理和自动化测试。

例如一个测试 CLI 可以提供 `plan`、`run`、`status`、`cancel` 等子命令，输入支持结构化文件，输出用稳定 JSON，日志走 stderr，stdout 留给机器消费。长任务返回 run_id，由调用方查询状态；退出码区分参数错误、权限错误、执行失败和等待外部输入。

执行请求应携带环境、资源 ID、计划版本与幂等键。配置层明确命令行、环境变量、配置文件的优先级；凭据通过受控的凭据存储或环境注入，避免把密钥放进命令参数和日志。

CLI 调用外部程序时使用参数数组、固定可执行文件和允许的子命令，避免拼接不可信字符串交给 shell。提供超时、取消、输出大小限制和资源约束。

测试应覆盖帮助文本与 schema、错误退出码、无权限、网络超时、重复提交和版本兼容。若只完成了命令解析和 API 封装，就明确这一范围，不把整个后端执行系统算作 CLI 开发成果。

**把 CLI 当成机器接口设计。** 例如 `status` 命令成功查询到一个失败任务时，命令本身可以返回退出码 0，并在 JSON 中给出任务状态 FAILED；`run --wait` 则可以约定任务失败返回非零。两种约定都可以成立，但必须写清“命令调用成功”和“业务任务成功”的区别，否则上层 Agent 容易误判。

```json
{
  "schema_version": "1",
  "run_id": "example-run",
  "status": "WAIT_INPUT",
  "missing_fields": ["environment"],
  "retryable": false
}
```

这个示例强调结构化状态，不表示某个通用 CLI 标准。`retryable` 应结合错误类型和外部副作用判断，不能只因 HTTP 状态为 5xx 就自动重试。将工具输出当作数据读取，也比让模型继续猜测自由文本日志更容易验证。
