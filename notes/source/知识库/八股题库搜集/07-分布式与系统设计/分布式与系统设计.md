# 分布式与系统设计

分布式系统的难点不是把一个进程拆成多个服务，而是在独立失败、网络延迟和结果不确定时仍维持业务约束。本章沿着一致性、通信、事务、消息和流量治理组织常见提问；缓存数据结构详见 Redis 章，数据库内部事务详见数据库章。

<a id="m745c49d06b83"></a>

## CAP 中的一致性、可用性与网络分区

CAP 讨论网络发生分区时，系统能否同时提供线性一致的操作结果与对非故障节点请求的可用响应。这里的一致性不是数据库 ACID 中的合法状态约束，可用性也不等于业务仪表盘上的 SLA。分区不是开发者可以从真实网络中永久移除的一项功能。

当两边不能通信时，继续接受相冲突的写入就可能失去统一次序；拒绝某些操作以保持次序则会牺牲这些请求的可用性。实际方案应按操作与数据分类，例如关键写入要求多数派，部分查询允许旧值，而不是给整个产品贴一个永恒的 CP 或 AP 标签。网络恢复后的冲突解决与补偿同样需要设计。

## 一致性模型与读写保证

一致性模型说明客户端能观察到哪些读写顺序。线性一致要求每次操作看起来在调用与返回之间的某个时刻瞬间完成，并尊重真实时间先后；最终一致只承诺在没有新的更新且传播完成后副本趋于一致，不承诺每次立刻读到最新值。

业务常需要更具体的保证，例如自己写完能读到、同一会话不倒退或特定键的有序更新。选择读主、会话路由、版本位点和多数派读写前，应先明确需要的保证。增加副本数量只能提供更多冗余，不能自动推出所需的一致性或故障恢复语义。

来源：[Snailclimb/JavaGuide](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/distributed-system/distributed-system-interview-questions.md#L32)。

## Raft 的日志复制与多数派

Raft 通过领导者选举、日志复制和安全性约束组织复制状态机。领导者接收状态变更并复制日志，节点按相同已提交日志顺序执行确定性操作，使副本维持一致状态。任期用于识别新旧领导者，日志匹配与投票限制共同避免已提交历史被后续领导者随意改写。

多数派的交集使合法决策能够衔接，但“多数节点有一份内容”并不是独立于任期和日志规则的完整提交算法。常见崩溃故障模型下，少数派失联会影响其继续写入能力；Raft 并不自动处理任意恶意节点。成员变更、持久化、快照与读请求的一致性还要遵守对应协议，不能只实现心跳和选主就声称实现了共识。

来源：[Snailclimb/JavaGuide](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/distributed-system/distributed-system-interview-questions.md#L53)；[Raft 原论文](https://raft.github.io/raft.pdf)。

## RPC、序列化与远程调用边界

RPC 把接口调用映射成跨网络请求，通常涉及服务发现、连接、编码、请求标识、超时及响应匹配。序列化让双方能理解传输内容；协议与接口演进还必须处理字段变化、默认值和版本兼容。调用写得像本地方法，不代表具有本地调用的失败语义。

网络超时可能出现在请求未到达、执行中或服务端已成功但响应丢失之后，客户端不能仅凭超时判断业务未执行。设计 RPC 时要明确连接与总截止时间、取消传播、重试责任和幂等键。接口应避免过细的聊天式调用，并限制报文和并发，防止局部慢调用占满资源。

来源：[doocs/advanced-java](https://github.com/doocs/advanced-java/blob/80b89fb9496d7ea3213e402c8c3853399e00c363/docs/distributed-system/dubbo-rpc-design.md#L1)；[Snailclimb/JavaGuide](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/distributed-system/distributed-system-interview-questions.md#L59)。

## 服务发现、负载均衡与健康判断

服务发现回答可用实例在哪里，负载均衡决定一次请求发往哪里，健康检查判断实例是否应继续接收流量。轮询、随机、权重或按键路由各有分布与局部性取舍；按键路由能保持同键局部性，却也可能造成热点集中。

健康检查不是完美故障探测器。过敏的检查会在短暂抖动时频繁摘除节点，过慢的检查会继续把请求送向失效实例。上线和下线还需预热、连接排空及流量渐变。网关集中处理路由、认证和治理，但也增加一层资源与故障边界，不能因统一入口而忽视它自身的冗余和限额。

来源：[doocs/advanced-java](https://github.com/doocs/advanced-java/blob/80b89fb9496d7ea3213e402c8c3853399e00c363/docs/distributed-system/dubbo-load-balancing.md#L1)；[Snailclimb/JavaGuide](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/distributed-system/distributed-system-interview-questions.md#L59)。

## 超时、重试预算与幂等

超时限制调用方愿意等待的时间，不能证明被调用方已经停止。重试可以掩盖瞬态故障，也会复制流量与副作用；在多层同时重试时，请求量甚至可能逐层放大。因此应由明确的层负责，在总时间与重试预算内采用退避和随机抖动，避免同步重试再次冲击下游。

幂等要求同一业务操作重复执行仍得到允许的同一效果。稳定业务请求号、唯一约束和状态机可共同约束重复提交，处理并发重复、首次处理中以及结果已完成等状态。仅在入口先写一个“已处理”标记，再独立执行业务，会留下标记成功而业务失败的窗口；关键去重记录与业务更新应具有共同的原子边界或明确恢复协议。

## 分布式 ID 与排序需求

ID 设计要先区分唯一性、趋势递增、严格全局次序、不可预测性和生成可用性。这些目标并不等价。数据库号段减少逐次访问，时间加节点和序列的方案便于分散生成，随机标识降低协调需求；各自承担不同的存储、路由和排序代价。

时间型方案需要处理时钟回拨、同一时间粒度内的序列耗尽及节点编号冲突。严格全局有序通常要求更多协调，不能从“包含时间戳”推导出来。ID 还可能泄露业务数量或时间信息，面向外部的标识与内部主键可以按需求分开设计。

## 租约、旧持有者与 fencing

分布式锁的租约让失联持有者最终失去资格，但暂停或网络延迟可能让它在资格过期后仍继续执行。锁服务已经发出新租约，并不会使旧进程的 CPU 自动停止。因此重要写入的最终防线应放在被保护资源上。

fencing 为每次合法持有分配递增代号，资源拒绝代号落后于已接受代号的写入，从而挡住恢复后的旧持有者。前提是代号来源与资源校验具有所需的持久性和顺序保证。普通随机锁值用于安全释放，不能代替单调代号；锁本身用于减少并发工作还是维护正确性，也应先分清。

来源：[doocs/advanced-java](https://github.com/doocs/advanced-java/blob/80b89fb9496d7ea3213e402c8c3853399e00c363/docs/distributed-system/distributed-lock-redis-vs-zookeeper.md#L1)；[Kleppmann：分布式锁与 fencing](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)。

## 分布式事务的方案边界

本地事务无法直接原子提交多个独立服务的数据。两阶段提交让协调者先准备各参与方，再决定提交或回滚，但准备阶段的资源持有和故障恢复会影响可用性；TCC 把资源预留、确认和取消变成业务接口；Saga 以多个本地事务和补偿步骤完成长流程。

TCC 与 Saga 都需要处理幂等、重试、并发和异常恢复。补偿是新的业务操作，不保证能够抹去外界已经观察到的中间状态，也未必能精确反转所有现实副作用。选型要看业务是否允许中间状态、能否预留资源、流程长度及外部系统能力，不能把补偿方案笼统说成与单库事务相同的隔离与原子性。

来源：[doocs/advanced-java](https://github.com/doocs/advanced-java/blob/80b89fb9496d7ea3213e402c8c3853399e00c363/docs/distributed-system/distributed-transaction.md#L1)。

## Outbox 与事务消息

业务数据提交与消息发送分属两个系统，任何“先写库再发消息”或相反次序都可能在中途失败。Outbox 把业务变更和待发送事件写进同一数据库事务，再由可靠投递器发送并更新进度，从而把“是否需要发送”留在可恢复的本地状态中。

投递器发送成功但记录确认失败时仍会重发，消费者必须幂等。事务消息通过半消息和本地事务状态查询协调另一种发送协议，同样不能替消费者完成外部写入。两者都需要重试、过期处置、监控和对账；它们解决的是特定原子边界的衔接，不是消除所有分布式失败。

## 消息可靠性与消费语义

可靠性必须沿生产者、Broker、副本与持久化、消费者、业务落库逐段分析。生产者确认、消息落盘与副本策略降低不同环节的丢失风险；消费者在业务完成后确认可以避免过早推进进度，但响应或确认丢失会引起重复处理。

至多一次、至少一次与恰好一次需要声明观察范围。某个队列或流处理事务提供的恰好一次，不自动覆盖任意外部数据库或第三方接口。业务最终效果往往依赖稳定事件 ID、唯一约束、状态机和同一事务内的消费记录。不能用一项 `acks` 配置概括整条链路，更不能把成功写入消息队列当成下游业务已经成功。

来源：[Snailclimb/JavaGuide](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/high-performance/message-queue/message-queue-interview-questions.md#L60)；[doocs/advanced-java](https://github.com/doocs/advanced-java/blob/80b89fb9496d7ea3213e402c8c3853399e00c363/docs/high-concurrency/how-to-ensure-that-messages-are-not-repeatedly-consumed.md#L1)。

## 局部顺序、重试与状态推进

顺序通常是某个业务键范围内的顺序，而非整个系统所有消息的全局次序。将同一订单或账户的消息路由到同一队列或分区，再由有序处理链执行，可以避免不相关键互相阻塞，但同键并行度也受到限制。

只有存储有序还不够：消费者并发、失败重投、死信跳过和重放都可能改变完成顺序。需要说明失败消息是否阻塞后续消息，以及业务状态是否校验版本或前置条件。若业务只要求最终状态正确，带版本的幂等状态推进可能比全局串行更合适；但丢弃旧消息必须有充分的业务依据。

## 消息积压与消费能力

积压意味着一段时间内生产进入速度超过消费完成速度，原因可能是突发流量、处理变慢、下游限额、分区不均或故障重试。先观察最老消息年龄、生产与确认速率、每分区分布和下游延迟，再决定扩容、优化或限速。

增加消费者只有在可并行任务、分区和下游容量足够时才有效。为了追赶积压而放大下游故障，可能让整体恢复更慢。需要核查保留时间、过期消息的业务处置与重放幂等；不能把直接清空队列或跳过位点当作通用恢复方案。

## 限流、熔断、降级与资源隔离

限流控制进入的请求量或并发，避免超过容量；熔断在下游持续异常时暂时停止调用；降级按优先级减少能力或返回允许的替代结果；资源隔离避免一个依赖占满整个服务的线程、连接或额度。这些机制可以配合，但触发条件与恢复动作不同。

固定窗口实现简单，却有交界突刺；滑动窗口改善计量连续性；令牌桶允许受控突发；漏桶常用于平滑处理。阈值应来自容量和延迟目标，并同时说明拒绝、排队还是降级。熔断恢复需要受限探测流量，降级结果要保持可识别性，Fallback 本身也不应引入新的无界远程依赖。

## 容量估算与系统设计的表达顺序

系统设计先澄清功能、关键数据、用户规模、峰值访问、延迟、可靠性和一致性要求，再估算读写吞吐、数据量与带宽。平均值用于总体量级，峰值与尾延迟决定实际容量；还要给故障和流量不均留余量。

据此绘制最小可行的读写路径，逐步指出瓶颈、单点和故障恢复，再比较缓存、分片、副本或异步化能解决什么、付出什么代价。设计题的重点是需求到取舍的因果链，不是尽可能摆满组件。每引入一个组件，都应说明状态归属、失败窗口、扩容边界及如何验证效果。

## 高可用、RTO 与 RPO

高可用关注服务能否持续提供约定能力，冗余减少单节点故障影响，容灾还要求发现故障、接管流量并恢复正确数据。RTO 约束恢复时间，RPO 约束可接受的数据丢失范围；拥有备机或备份文件，并不证明达到了这些目标。

无状态服务扩容与数据库主切不是同一难度。自动故障转移需要处理误判、双主、复制延迟、客户端路由和回切。应按业务链路设置目标并定期演练恢复，关键写入和普通查询未必使用相同策略。跨地域增加副本也会引入延迟、成本和新的协调约束，不能直接推出“多活一定更可靠”。
