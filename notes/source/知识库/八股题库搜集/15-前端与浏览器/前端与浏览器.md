# 前端与浏览器

JavaScript 的语言语义、浏览器的执行与渲染、框架的组件更新属于不同层次。分析问题时先确定它发生在哪一层，再讨论各层之间的交互。

<a id="mefee6e3ee633"></a>

## 作用域、闭包与变量生命周期

词法作用域由代码定义位置决定，闭包让函数在离开定义处后仍能访问其捕获的词法环境。它保存的是对环境的访问关系，不是自动冻结某一时刻所有变量的副本。因此异步回调中读到什么，取决于捕获的是哪一个绑定、绑定后来是否被改变。

闭包常用于回调、封装私有状态和函数工厂，也会让被捕获对象活得更久。循环中的 `var` 常让多个回调共享同一绑定，而相应的 `let` 循环可为各轮建立独立绑定；结果差异来自绑定关系，不能只用“异步所以读错”解释。排查内存时要观察长期存活回调是否仍引用大对象；闭包本身不是内存泄漏，失去业务用途但仍被保留的引用才是问题。

来源：[h5bp/Front-end-Developer-Interview-Questions](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/33f5498b653e7ae061ee5a65a0b44e9ab860502c/src/translations/chinese/README.md#L118)；[MDN 闭包](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Closures)。

<a id="m7a2fda4bb218"></a>

## this、普通函数与箭头函数

普通函数的 `this` 通常取决于调用方式：作为对象方法、显式 `call/apply/bind`、构造调用或普通调用，会形成不同规则。把方法赋给变量再调用，可能失去原来的接收者。严格模式、模块和宿主环境还会影响普通调用时的值，不能统一回答成浏览器的 `window`。

箭头函数没有自己的 `this`，从外层词法环境取值，`bind` 也不能让它改成另一接收者。它适合需要继承外层接收者的回调，却不适合需要动态接收者或作为构造器的地方。判断题应先看函数种类和调用表达式，再讨论 `this` 指向。

来源：[sudheerj/javascript-interview-questions](https://github.com/sudheerj/javascript-interview-questions/blob/698de06ad5d9eb2eeb7dfff7f7c448d039a21998/README.md#L1042)；[sudheerj/javascript-interview-questions](https://github.com/sudheerj/javascript-interview-questions/blob/698de06ad5d9eb2eeb7dfff7f7c448d039a21998/README.md#L8974)。

## 原型链、属性查找与 class

访问对象属性时，运行时先检查对象自身，再沿其原型链查找，直到找到匹配属性或链结束。构造函数的 `prototype`、对象的内部原型和原型上的 `constructor` 是相关但不同的概念；不能把“对象有原型”简化成每个对象都公开一个可靠的 `__proto__` 用法。

`class` 为原型式对象模型提供更清晰的声明语法，同时也带来自己的语义约束。继承与组合应围绕对象之间的职责关系选择，而不是仅为了复用一段方法就制造很深的继承树。排查属性覆盖、方法共享和 `instanceof` 时，关键是对象与原型的实际连接关系。

来源：[h5bp/Front-end-Developer-Interview-Questions](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/33f5498b653e7ae061ee5a65a0b44e9ab860502c/src/translations/chinese/README.md#L112)。

## 值、对象引用与复制边界

基本值按其语义参与赋值和比较，对象赋值则让多个变量引用同一个对象。展开语法或常见浅拷贝只复制外层属性关系，内部对象仍可能共享；因此改动嵌套对象可能同时影响看似独立的两个结构。

深拷贝不是一个无条件复制“所有 JavaScript 值”的简单操作。JSON 往返会改变或丢失某些类型，也无法直接处理循环引用；其他克隆机制同样有可支持类型与不可复制资源的边界。先明确需要共享还是独立、哪些字段拥有外部资源，再选择复制方式，避免用深拷贝掩盖不清楚的状态所有权。

来源：[sudheerj/javascript-interview-questions](https://github.com/sudheerj/javascript-interview-questions/blob/698de06ad5d9eb2eeb7dfff7f7c448d039a21998/README.md#L6747)。

## 事件循环、任务与微任务

一段同步 JavaScript 在当前调用栈中执行，异步结果由宿主安排后续工作。浏览器在规定的检查点处理微任务，Promise 回调和 `queueMicrotask` 等常在其中执行；定时器回调要等到条件满足且事件循环能调度时运行，并非到指定毫秒就立即打断当前代码。

例如同步输出 A、安排一个 Promise 回调输出 B、安排计时器输出 C，再同步输出 D，通常先看到 A、D，再到 B，最后到 C。原因是同步代码先完成，随后处理相应微任务与后续任务，而不是 Promise 创建了一个专属线程。渲染是浏览器的另一个调度机会，不保证每个任务之后都立即绘制；递归产生微任务也可能拖延页面响应。

来源：[h5bp/Front-end-Developer-Interview-Questions](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/33f5498b653e7ae061ee5a65a0b44e9ab860502c/src/translations/chinese/README.md#L159)；[MDN 执行模型](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model)。

<a id="mc095fece74a0"></a>

## Promise、async 与错误传播

Promise 表达一个异步操作最终完成或失败的结果，创建 Promise 时传入的执行函数本身同步运行；后续反应回调按异步作业调度。`async` 函数返回 Promise，`await` 暂停该函数后续部分并等待结果，不把整个线程或浏览器停住。

串行 `await` 适合有依赖的步骤，互不依赖的任务可以先启动再汇合，但并发也需要容量上限。错误会沿 Promise 链传播，只有真正返回或等待的异步工作才能被上层链路观察。遗漏 `return`、没有等待的内部任务和吞掉异常都可能让失败脱离调用方；超时和取消也需由底层操作或协议明确支持。

来源：[sudheerj/javascript-interview-questions](https://github.com/sudheerj/javascript-interview-questions/blob/698de06ad5d9eb2eeb7dfff7f7c448d039a21998/README.md#L1783)。

## DOM 事件传播与事件委托

事件可以沿 DOM 关系经历捕获、目标与冒泡等阶段。事件委托在合适的祖先监听，让处理器根据事件目标判断具体操作，可减少重复监听并覆盖后来插入的子元素；它依赖事件本身的传播特性，不是所有事件都能无条件用同一种方式委托。

`preventDefault` 影响默认行为，`stopPropagation` 影响传播，两者不等价。组件边界、Shadow DOM、触摸与滚动相关监听还会影响目标和默认行为判断。实现时应选择清晰稳定的定位规则，并在不再需要时清理监听，避免将一次点击误处理成多个业务提交。

来源：[h5bp/Front-end-Developer-Interview-Questions](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/33f5498b653e7ae061ee5a65a0b44e9ab860502c/src/translations/chinese/README.md#L110)。

## 布局、绘制与页面性能

浏览器把文档与样式转换成可显示的结果，其中样式计算决定规则，布局确定几何位置，绘制生成视觉内容，合成再组织显示层。修改属性可能触发不同阶段，因此不能把所有 DOM 更新都等同于整页重绘。

反复交错写样式与读取布局结果，可能迫使浏览器提前完成布局计算。优化应先用性能记录定位长任务、布局、资源加载或图片解码，再减少无效工作和单次阻塞。动画使用哪些属性也要结合实际合成与页面结构验证，不能仅靠添加一个 CSS 属性保证完全不发生布局或绘制。

来源：[h5bp/Front-end-Developer-Interview-Questions](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/33f5498b653e7ae061ee5a65a0b44e9ab860502c/src/questions/performance-questions.md#L9)。

## CSS 盒模型与布局选择

盒模型区分内容、内边距、边框和外边距。通过 `box-sizing` 选择盒模型：`content-box` 下声明宽度主要约束内容区域，`border-box` 把内边距和边框纳入该宽度；外边距仍在盒外。只记“宽度是否包含 padding”而忽略边框和可用空间，容易在实际布局中算错。

Flexbox 便于沿主轴分配和对齐一组项目，Grid 便于显式组织行列关系，两者可以嵌套。选择时先确定内容如何换行、轨道如何伸缩和对齐，再设置尺寸与溢出规则。`z-index` 的比较受层叠上下文限制，数值更大也不保证跨不同上下文覆盖所有元素。

来源：[h5bp/Front-end-Developer-Interview-Questions](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/33f5498b653e7ae061ee5a65a0b44e9ab860502c/src/translations/chinese/README.md#L96)。

## 浏览器缓存、跨域与请求边界

缓存规则决定能否直接复用已有响应，或必须向服务端验证是否变化；浏览器的同源限制则控制某些跨源访问与读取。CORS 是服务端通过响应声明允许浏览器读取跨源结果的协议，不是阻止所有客户端向服务器发送请求的防火墙。

前端排查跨域时要区分请求未发送、预检失败、响应已到达但脚本无权读取，以及认证 Cookie 是否携带。不能用禁用浏览器安全策略作为产品修复。缓存与认证内容还要明确哪些响应可以共享，避免不同用户复用同一份敏感数据；协议基础可结合网络章阅读。

来源：[h5bp/Front-end-Developer-Interview-Questions](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/33f5498b653e7ae061ee5a65a0b44e9ab860502c/src/translations/chinese/README.md#L54)。

## React 的 props、state 与渲染快照

props 是外部传入当前组件的数据，state 是组件对应位置持有的状态。一次渲染读取的是该次状态快照，调用状态更新函数会请求后续渲染，不会把当前函数中的局部变量即时改写。因此同一事件处理器中的多次读取可能仍得到同一个旧值。

后续值依赖前一状态时，应使用函数式更新表达“如何从旧状态得到新状态”，而不是反复使用捕获的旧值。状态中的对象也应通过新引用表达更新，避免原地改动使不同渲染共享被修改的数据。不要把“state 可更新”误解成可随意直接修改当前 state 对象。

来源：[sudheerj/reactjs-interview-questions](https://github.com/sudheerj/reactjs-interview-questions/blob/55b7d491cd74c7b37f9352f3b2420d66e7187951/README.md#L997)；[React 状态快照](https://react.dev/learn/state-as-a-snapshot)。

## React 身份、key 与状态保留

React 按渲染树中的组件类型、位置及相应 key 等信息判断某个组件是否延续原身份。key 的作用是帮助相邻列表项稳定对应，而不只是消除控制台警告。动态插删或重排的列表使用下标，可能把旧组件状态接到另一条业务记录上。

合适的 key 来自稳定业务身份，不能每次渲染随机生成。组件重新渲染与卸载重建不同：前者通常保留状态，后者会重置状态并触发生命周期清理。分析表单错位、缓存失效或效果重复时，应先确认身份是否改变，再决定是否需要性能优化。

来源：[sudheerj/reactjs-interview-questions](https://github.com/sudheerj/reactjs-interview-questions/blob/55b7d491cd74c7b37f9352f3b2420d66e7187951/README.md#L1127)。

## Effect、依赖与外部资源清理

Effect 用于让组件与连接、订阅、计时器等外部系统保持同步。依赖变化后，React 按协议先清理旧的同步关系，再建立新的关系；组件移除时也需要清理。事件触发的业务动作和可由 props/state 直接计算的派生值，不必都塞进 Effect。

依赖列表描述 Effect 读取的响应式值，不是人为控制“希望执行几次”的开关。省略依赖可能让回调继续使用旧闭包，多余不稳定引用又可能导致反复同步。开发模式额外的建立与清理用于暴露不对称逻辑，不能据此推断生产环境的固定次数；正确清理比依赖“只挂载一次”更可靠。

来源：[React useEffect](https://react.dev/reference/react/useEffect)；[sudheerj/reactjs-interview-questions](https://github.com/sudheerj/reactjs-interview-questions/blob/55b7d491cd74c7b37f9352f3b2420d66e7187951/README.md#L5425)。

## 受控表单与单一状态来源

受控表单让输入值由组件状态决定，用户输入触发状态更新，下一次渲染再显示对应值。非受控表单主要把当前值交给 DOM 持有，通过引用或提交时读取。二者区别是状态由谁管理，不是哪个方案绝对更先进。

复杂联动校验和多字段业务常需要明确的统一状态，简单输入则可能不必每次按键都同步到整个组件树。需要保持输入模式稳定，并处理组合输入、校验时机、提交中重复操作和服务端错误回显，不能只验证“onChange 能触发”。

## memo、缓存与性能验证

记忆化用额外比较与存储换取跳过重复工作。`memo` 关注组件接收到的 props，`useMemo` 缓存计算结果，`useCallback` 保持函数引用；这些机制不能替代正确的状态归属，也不会保证组件在任何条件下都不再执行。

如果每次都创建新的对象或函数，浅比较可能无法命中；如果被缓存的工作本来很便宜，维护依赖与缓存反而没有收益。应先用分析工具确认哪次渲染或计算昂贵，再局部优化，并保证即使缓存失效语义仍正确。

来源：[sudheerj/reactjs-interview-questions](https://github.com/sudheerj/reactjs-interview-questions/blob/55b7d491cd74c7b37f9352f3b2420d66e7187951/README.md#L790)。

## Vue 3 的依赖追踪与响应式边界

Vue 3 的响应式系统在访问和修改响应式数据时追踪依赖、触发相关效果。对象代理能够拦截属性操作，`ref` 则通过 `.value` 等访问点承载值。组件渲染读取了哪些响应式数据，影响后续哪些更新需要重新求值。

把响应式对象的某个普通属性值直接解构到本地变量，可能失去后续属性访问的追踪关系；但解构得到的若仍是响应式对象，情况又不同。回答时应区分值与引用、代理与原对象，以及 Vue 2 和 Vue 3 的实现差异，不能把“所有变化都能被自动发现”当作统一规则。

来源：[Vue 3 响应式深入](https://vuejs.org/guide/extras/reactivity-in-depth.html)。

<a id="m66231693e72e"></a>

## computed、watch 与异步副作用

计算属性表达可由已有响应式状态推导的值，适合保持纯计算并利用依赖缓存；侦听器用于某些状态变化后执行副作用，例如发请求、记录或同步外部系统。二者应按“得到一个值”还是“触发一项操作”选择，而不是只比较写法长短。

异步侦听要处理旧请求晚返回的情况，否则旧结果可能覆盖新输入对应的结果。应通过清理、取消或版本校验使响应仍对应当前状态。组件销毁、侦听创建时机以及所用 API 的生命周期约束，也决定资源能否被正确释放。

来源：[Vue 3 响应式深入](https://vuejs.org/guide/extras/reactivity-in-depth.html)。

<a id="mc5abc9c65ec6"></a>

## 构建拆分、Tree Shaking 与加载成本

构建工具把模块依赖转换成浏览器可加载的产物；代码拆分把不必首屏执行的部分推迟加载，Tree Shaking 尝试移除可静态证明不需要的导出。它依赖模块结构与副作用信息，不是给库加一个标记就一定能删除所有未调用代码。

性能收益需要同时看首包大小、请求数、缓存复用和实际执行时间。拆得过细可能增加调度与网络成本，多个产物重复打包依赖也会抵消收益。优化应以用户场景和构建分析为依据，并确认动态导入失败、版本缓存与回滚时的兼容行为。
