## 网络分层与封装

常见问法：网络为什么分层；一次发送中各层分别处理什么。

分层把应用语义、端到端传输、跨网络寻址和局域网交付分开，使某一层的实现可以演进，而不要求上层同时修改。应用产生消息，传输层加端口等信息，网络层处理 IP 寻址与路由，链路层把数据交给下一跳；接收端逆向解封装。

端口用于区分主机内的通信端点，IP 地址用于网络寻址，MAC 地址用于相应链路的帧交付。不能把“经过路由器 MAC 会变化”说成“端到端 IP 一定不变”：NAT、隧道等机制会改变观察到的地址或封装。OSI 七层是分析模型，实际 TCP/IP 协议栈不必逐层对应。

## TCP与UDP的服务语义

常见问法：TCP和UDP有什么区别；什么场景适合TCP或UDP。

TCP 提供面向连接、可靠、有序的字节流，应用不需要自行处理常见的丢失、重复和乱序；UDP 提供数据报，保留报文边界，但本身不保证到达、顺序或拥塞控制。TCP 的可靠性也不等于“对方业务已经处理成功”，业务确认、幂等与持久化仍须应用设计。

选择应从时延、丢包容忍、广播/多播需求和上层协议出发。实时音视频常在 UDP 上实现自身的反馈与恢复；文件或一般请求响应可使用 TCP。UDP 上也能构建可靠协议，例如 QUIC，因此不能推出“HTTP 永远不能基于 UDP”。

| 维度 | TCP | UDP |
| --- | --- | --- |
| 应用看到的边界 | 字节流，需自行定义消息 | 数据报边界 |
| 协议内可靠有序交付 | 提供，仍可能以连接错误结束 | 不提供，由上层按需建立 |
| 通信状态与控制 | 有连接状态、流控与拥塞控制 | 基本数据报服务更简单 |
| 选择依据 | 需要有序字节流与成熟可靠传输 | 需要自定义时延、恢复或多播等策略 |

## TCP三次握手与初始序列号

常见问法：为什么TCP需要三次握手；两次握手有什么问题。

握手的核心是交换并确认双方的初始序列号，建立本次连接的状态。通常客户端发送 SYN，服务端发送 SYN+ACK，客户端再确认；SYN 本身占用一个序列号，确认号表示期待接收的下一字节位置。

第三次确认使服务端能够验证对方确实收到了自己的序列号，并帮助识别延迟到达的旧连接请求。只说“确认收发能力”不够，因为还须说明序列空间和历史报文。第三次 ACK 丢失时，服务端可能重传 SYN+ACK；若客户端随后发送带有效确认的数据，也可能完成状态推进。重传次数和超时是具体实现与配置，不能背成统一常数。

## TCP关闭、半关闭与CLOSE_WAIT

常见问法：为什么通常需要四次挥手；CLOSE_WAIT为什么可能很多。

TCP 两个方向独立关闭。主动方发送 FIN 表示自己没有更多字节要发送；对方确认后，仍可以继续发送尚未完成的数据，直到它也发送 FIN。若接收方已经准备好关闭，ACK 与 FIN 可以合并，所以“四次”是常见报文序列，不是每次都必须四个报文。

收到 FIN 后停在 CLOSE_WAIT，表示本端已经知道对方关闭发送方向，却尚未完成自己的关闭。大量长期 CLOSE_WAIT 通常要检查应用是否遗漏 close、是否卡在业务或资源释放，而不能只改内核 TIME_WAIT 参数。半关闭适用于一方发送完请求后仍等待另一方返回结果的协议。

## TIME_WAIT与连接复用边界

常见问法：TIME_WAIT为什么等待2MSL；TIME_WAIT过多怎样分析。

正常关闭中，发送最终确认的一方通常进入 TIME_WAIT。等待的目的包括：允许对方在 FIN 的确认丢失后重传，本端仍能再次确认；让旧连接中的延迟报文逐渐失效，避免干扰复用同一连接标识的新连接。MSL 是报文最大生存时间概念，具体超时实现不应与理论值混为一谈。

TIME_WAIT 多可能是短连接吞吐高的正常结果。需要结合主动关闭方、连接建立速率、可用端口和连接复用情况判断是否成为瓶颈。优先检查连接池与长连接策略；激进复用或缩短等待可能改变协议安全边界，不能把“减少状态数”当成唯一目标。

## TCP可靠传输与确认范围

常见问法：TCP如何保证可靠性；ACK能证明业务成功吗。

TCP 用序列号标识字节范围，接收端确认连续收到的位置，发送端保存未确认数据，并通过超时或丢失信号重传。接收端可以缓存乱序数据、丢弃重复数据，再向应用提供有序字节流；校验和用于发现部分传输错误。流量控制与拥塞控制则限制不合适的发送速度。

ACK 表示相应 TCP 接收端已经接收了数据，不意味着应用已读取、事务已提交或磁盘已落盘。网络中断后，客户端可能不知道请求到底有没有执行，此时应设计业务请求 ID、幂等处理和应用层确认。可靠传输还可能以超时或连接错误结束，不是无限等待直到成功。

## TCP流量控制与零窗口

常见问法：滑动窗口如何工作；接收窗口为零怎么办。

流量控制保护接收端：接收方通过通告窗口说明自己还能接收多少字节，发送方据此限制未确认数据。窗口可以随应用读取与缓冲区状态变化；发送约束还受拥塞窗口影响，不能只看接收窗口。

当通告窗口为零，发送方暂停普通数据发送，但仍需窗口探测机制，避免恢复窗口的通知丢失后双方永久等待。窗口扩大选项在建立连接时协商，用于表达更大的窗口；大带宽、高往返时延链路往往需要足够的在途数据，才能利用链路容量。

## TCP拥塞控制与丢失恢复

常见问法：流量控制和拥塞控制有什么区别；慢启动和快恢复如何配合。

拥塞控制保护网络路径，流量控制保护接收端。发送方通过确认、丢失和时延等信号调整拥塞窗口；经典算法以慢启动探测容量，再进入较平缓的拥塞避免。快重传利用重复确认等信号更早恢复丢失，而不必总等待重传超时。

“初始窗口固定为1 MSS”“任意丢包都回到同一状态”并不适用于所有实现。Reno、CUBIC、BBR 等算法的模型和状态推进不同。回答原理时先说明所讨论的算法，再说明超时与重复确认通常反映不同程度的网络不确定性，不要把教材的一张窗口变化图当成整个 TCP 标准。

## TCP字节流与应用消息边界

常见问法：为什么会粘包或拆包；如何设计TCP消息协议。

TCP 只传递有序字节，不保留一次 write 对应一次 read 的边界。应用一次发送可能被分成多次读取，多次发送也可能在一次读取中一起出现；这由缓冲、分段、网络和读取时机共同影响，属于字节流语义。

应用应自行定义帧边界：固定长度、分隔符、长度字段或成熟的自描述协议都可以。长度字段必须限制最大值并处理不完整头部、超长消息和异常断开；分隔符方案要规定转义。关闭 Nagle 或刻意延时读取都不能从根本上把字节流变成报文协议。

## 长连接、短连接与保活

常见问法：长连接有什么收益；TCP Keepalive和心跳有什么区别。

长连接复用已经建立的传输状态，减少握手、TLS 协商和资源反复创建的开销；短连接在一次或少量交互后关闭，实现简单但高频访问成本更高。连接复用需要处理空闲超时、服务端主动关闭、负载变化和连接池容量。

TCP Keepalive 检测连接对端是否仍有响应，应用心跳可以同时验证业务处理链路；二者的语义和时间尺度不同。HTTP 的持久连接或 Keep-Alive 说的是连接复用，也不等于 TCP Keepalive。任何一种检测都必须设置超时与失败处理，不能从“暂时没收到回应”推出对方一定已经故障。

## DNS解析、递归与迭代

常见问法：DNS解析过程是什么；递归查询与迭代查询有什么区别。

DNS 把域名映射到地址及其他记录。客户端通常把请求交给递归解析器；解析器先检查缓存，必要时依次询问根、顶级域和权威服务器，获得目标记录后返回并按 TTL 缓存。递归表示接收请求的一方负责拿到最终结果，迭代表示应答方可以告诉请求者下一步去问谁。

缓存降低时延和查询量，也意味着地址切换不会立即被所有客户端看到。CNAME 会引入别名链，负缓存会缓存部分不存在结果；解析出的地址也未必是最终处理业务的机器，后面可能还有 CDN 或反向代理。DNS 的多地址返回可分配访问流量，但不等于具备实时连接级负载感知。

## ARP与局域网下一跳

常见问法：ARP解决什么问题；访问外网时查询谁的MAC地址。

ARP 在 IPv4 链路上把下一跳 IP 地址解析为链路地址。主机先根据路由与子网判断下一跳：目标在直连网络时解析目标主机地址，否则通常解析网关地址，再把帧交给网关；并不是为互联网目的主机直接广播寻找 MAC。

ARP 请求通常广播，拥有该 IP 的节点回应，双方可以缓存映射。ARP 本身缺少强认证，因此伪造映射可能造成流量劫持。IPv6 的邻居发现使用不同机制，不能把 ARP 的流程直接套到 IPv6。

## NAT与端口映射

常见问法：NAT如何工作；内网主机怎样共享公网地址。

NAT 在转发路径上改写网络地址；常见的地址端口转换还会改写端口，用映射表把多个内网通信流区分开。返回报文到达后，设备查映射并恢复内网目标，因此外部看到的源地址可能与应用本机配置的地址不同。

这缓解了公网 IPv4 地址不足，也引入连接状态、映射超时、主动入站访问和端到端寻址的限制。需要外网访问内网服务时通常配置显式端口映射、代理或打洞方案。NAT 的地址隐藏不能代替防火墙策略，更不能代替身份认证和加密。

## HTTP方法、安全性与幂等性

常见问法：GET和POST有什么区别；幂等请求能否直接重试。

HTTP 方法表达操作语义：GET 用于获取表示，POST 让资源按其自身语义处理请求内容；PUT 常用于替换目标资源，DELETE 用于删除目标资源的关联。安全方法的预期语义不要求改变服务器状态；幂等表示重复相同请求的预期效果与一次相同，而不是响应内容必须完全一样。

GET 参数不天然比 POST 更不安全，两者都需 HTTPS 与正确的日志策略。HTTP 规范没有给 GET URL 规定一个统一的应用长度上限，实际受客户端、代理和服务器限制。即便协议方法幂等，超时重试仍需考虑鉴权、资源版本、限流和业务实现是否遵守语义。

参考资料：[wolverinn/Waking-Up：GET 和 POST 的区别](https://github.com/wolverinn/Waking-Up/blob/cf692b53e1b3d1b740a97dab0e4e71db801daf33/Computer%20Network.md#L321)；[Snailclimb/JavaGuide：GET 和 POST 的区别](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/cs-basics/network/other-network-questions.md#L371)；[规范或原始文档校核](https://www.rfc-editor.org/rfc/rfc9110.html#section-9)。

## HTTP状态码与重定向语义

常见问法：常见HTTP状态码有哪些；301和302以及307有什么区别。

状态码表达本次请求处理结果：2xx 表示成功，3xx 表示需要重定向或缓存相关处理，4xx 表示请求端相关错误，5xx 表示服务端无法完成请求。401 与认证挑战有关，403 表示拒绝访问；404 不等于一定没有该资源，也可能用于隐藏资源存在性。

301/308 表示永久重定向，302/307 表示临时重定向；307/308 保留原请求方法，301/302 在历史兼容行为下可能使 POST 被改为 GET。304 用于条件请求，告诉客户端可以复用已有表示，不能当成普通的重定向地址跳转。

参考资料：[wolverinn/Waking-Up：HTTP请求有哪些常见状态码？](https://github.com/wolverinn/Waking-Up/blob/cf692b53e1b3d1b740a97dab0e4e71db801daf33/Computer%20Network.md#L345)；[forthespada/InterviewGuide：常见的HTTP状态码有哪些？](https://github.com/forthespada/InterviewGuide/blob/25055ccfa146c11f2ccc986402ad36b34471e6c0/docs/notes/03-hunting_job/02-interview/03-06-net.md#L59)；[规范或原始文档校核](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)。

## HTTP各版本、多路复用与队头阻塞

常见问法：HTTP1和HTTP2有什么区别；HTTP3解决了什么问题。

HTTP/1.1 默认支持持久连接，但通常的请求处理方式容易产生应用层排队；HTTP/2 用二进制帧和多个流在同一连接上交错传输，并引入头部压缩等机制。多路复用减少了应用层串行等待，但 TCP 丢失字节仍会阻塞该连接后续字节交付，影响其中多个流。

HTTP/3 使用 QUIC，QUIC 在 UDP 上提供加密、可靠流和拥塞控制。不同流的传输恢复可以减少跨流的传输层队头阻塞，但单个流内部的有序数据仍会等待缺失部分，带宽竞争与连接级限制也不会凭空消失。HTTP 语义与承载协议应分开理解。

参考资料：[Snailclimb/JavaGuide：HTTP/1.1 和 HTTP/2.0 的队头阻塞有什么不同？](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/cs-basics/network/other-network-questions.md#L276)；[规范或原始文档校核](https://www.rfc-editor.org/rfc/rfc9113.html)。

## HTTPS、证书与TLS握手

常见问法：HTTPS如何保证安全；证书和对称加密各起什么作用。

HTTPS 是在安全传输保护下使用 HTTP。TLS 协商密码参数与密钥材料，借助证书验证所连接服务端的身份，再用派生出的对称密钥保护应用数据的机密性与完整性。客户端必须校验证书链、有效期和目标主机名，不能只因为“拿到公钥”就信任对方。

TLS 1.3 的常见握手采用临时密钥交换与签名认证，不能套用“客户端生成会话密钥，再用服务器 RSA 公钥直接加密发送”的旧流程。数据加密也不能防止服务器自身泄露明文、业务越权或用户主动连接错误站点；恢复会话和 0-RTT 还需要考虑重放约束。

## HTTP缓存与条件请求

常见问法：强缓存和协商缓存有什么区别；ETag与Last-Modified怎样配合。

缓存先判断已有响应是否仍然新鲜，新鲜时可以直接复用；过期后可用验证器发条件请求，让服务端判断表示是否变化。Cache-Control 控制缓存策略，ETag 标识表示版本，Last-Modified 表达修改时间；验证未变化时常返回 304，客户端继续使用原有响应体。

no-cache 表示复用前通常需要验证，并不等于完全不保存；no-store 才要求不存储相关消息。浏览器私有缓存与共享代理缓存的适用条件不同，身份相关内容应审慎设置 private、缓存键和 Vary，避免把某用户的表示发给其他用户。

参考资料：[forthespada/InterviewGuide：HTTP如何禁用缓存？如何确认缓存？](https://github.com/forthespada/InterviewGuide/blob/25055ccfa146c11f2ccc986402ad36b34471e6c0/docs/notes/03-hunting_job/02-interview/03-04-net.md#L272)；[规范或原始文档校核](https://www.rfc-editor.org/rfc/rfc9111.html)。

## Cookie、Session与Token

常见问法：Cookie和Session有什么区别；无状态HTTP怎样维持登录态。

Cookie 是浏览器保存并按域、路径及属性规则携带的数据机制；Session 是服务端维护会话状态的一种方案，浏览器通常只携带会话标识。Token 是携带授权或身份声明的凭证形式，既可能放在 Cookie 中，也可能由客户端在其他请求字段中提交，因此三者不处于同一抽象层。

服务端 Session 易于集中撤销，但需要共享或定位会话状态；自包含 Token 便于分布式验证，但撤销、泄露和过期策略仍需设计。Cookie 的 Secure、HttpOnly、SameSite 分别约束传输、脚本访问和跨站携带行为，不能用其中一个属性代替整套会话安全设计。

## 从URL到页面与请求耗时分解

常见问法：输入URL后发生了什么；怎样定位页面访问慢在哪一段。

浏览器解析 URL 并检查相关策略与缓存，解析域名，选择连接或复用已有连接，必要时建立传输连接与 TLS 会话，然后发送 HTTP 请求。响应可能经过缓存、CDN、反向代理和应用服务；浏览器再解析文档并获取依赖资源，逐步构建与更新页面。

排障应把 DNS、连接、TLS、首字节等待、内容下载和前端处理分开测量。缓存命中、连接复用、HTTP 版本和资源加载策略会省去或并行化部分步骤，因此不应把所有请求都描述成“固定串行执行完整握手”。这里的服务端请求路径与浏览器渲染机制应分开分析。

## WebSocket与轮询

常见问法：WebSocket和HTTP轮询有什么区别；WebSocket连接之后还需要心跳吗。

轮询由客户端周期性发请求；长轮询让请求保持到有数据或超时，再发起下一次请求。WebSocket 建立会话后提供双向消息通信，适合交互式通知与实时协作，并具有自己的消息和控制帧语义，而不是把 TCP 的字节边界直接暴露给业务。

持续连接仍可能被代理、网络设备或服务端超时关闭，需要心跳、重连和状态恢复。重连后是否补发消息、如何去重和确定顺序属于应用协议；仅换成 WebSocket 并不能保证离线期间的消息不丢。

## 代理、负载均衡与健康检查

常见问法：正向代理和反向代理有什么区别；负载均衡怎样选择后端。

正向代理代表客户端访问目标服务；反向代理作为服务入口，把请求转发给后端。负载均衡在多个可用目标之间分配流量，可以依据轮询、权重、连接数、请求负载或一致性哈希等策略；策略应与会话状态、后端容量和请求成本相匹配。

健康检查只覆盖它实际检测的路径：端口可连接不代表依赖数据库可用，某次探测成功也不保证后续请求成功。连接级均衡与请求级均衡的粒度不同，长连接可能放大分配不均。服务故障时还需要合理超时、重试预算与摘除恢复策略，避免重试把过载进一步放大。

参考资料：[规范或原始文档校核](https://www.rfc-editor.org/rfc/rfc9110.html)。
