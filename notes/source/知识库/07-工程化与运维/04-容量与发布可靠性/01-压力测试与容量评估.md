# 压力测试和容量评估

## 学习目标

- 把“并发很高”翻译成可执行的负载模型。
- 正确解释吞吐、延迟、并发、错误率、饱和度之间的关系。
- 设计可重复的基准测试，并识别客户端、网络和下游瓶颈。
- 用测试结果估算单实例能力、实例数、安全余量和扩容阈值。

## 1. 核心概念：先定义测试问题

| 类型 | 主要问题 | 典型做法 |
| --- | --- | --- |
| 基准测试 | 当前版本在固定环境下表现如何 | 稳定流量，多轮重复，保存基线 |
| 负载测试 | 预期业务负载下是否满足 SLO | 按真实请求比例和到达率施压 |
| 压力测试 | 极限在哪里，过载后如何退化 | 逐级升压直到 SLO 或资源越界 |
| 峰值测试 | 突发流量能否吸收 | 短时间快速升高再下降 |
| 浸泡测试 | 长时间运行是否泄漏或退化 | 中高负载持续数小时或更久 |
| 容量评估 | 目标业务量需要多少资源 | 结合压测、增长预测和冗余计算 |

一次实验只回答少数明确问题。例如：“在 4 vCPU、8 GiB、两个副本条件下，读写比 8:2、到达率 1000 RPS 时，服务端 p99 是否低于 200 ms，错误率是否低于 0.1%？”

## 2. 核心指标与关系

- **吞吐量**：单位时间完成的请求或任务数，常用 RPS/QPS/TPS。
- **延迟**：请求耗时分布。优先看 p50/p90/p95/p99，而不是只看平均值。
- **并发数**：同一时刻正在处理或等待的请求数。
- **错误率**：超时、协议错误、业务失败等失败请求占比。必须统一统计口径。
- **饱和度**：CPU、运行队列、内存、连接池、线程池、磁盘队列等接近上限的程度。

稳定系统近似满足 Little's Law：

```text
并发数 L = 到达率 λ × 平均停留时间 W
```

例如 500 RPS、平均响应时间 0.2 秒，对应约 100 个在途请求。它是校验量级的工具，不代表所有队列都稳定，也不能替代尾延迟分析。

## 3. 建立流量模型

至少明确以下维度：

1. 请求类型及比例，例如查询 80%、写入 15%、批处理 5%。
2. 到达模式：恒定、阶梯、脉冲、昼夜波动还是事件突发。
3. 数据分布：冷热数据、对象大小、缓存命中率、租户或用户倾斜。
4. 会话行为：登录、令牌刷新、思考时间、重试和幂等性。
5. 下游依赖：数据库、缓存、消息队列和第三方 API 的真实或替代行为。

开放模型按目标到达率发请求，更接近外部流量；封闭模型使用固定虚拟用户循环，更容易在服务变慢时自动降低实际到达率，从而掩盖过载。选型时要说清模型。

## 4. 典型工作流：一次可复现的测试流程

### 4.1 固定环境与版本

记录以下信息到测试报告：

```text
服务提交/镜像摘要：
编译类型与编译器：
实例规格、副本数、CPU/内存限制：
内核与容器运行时：
数据库/缓存版本与数据规模：
压测机规格、位置和工具版本：
场景脚本提交：
```

### 4.2 校验脚本正确性

- 用极低流量验证请求参数、断言和清理逻辑。
- 核对压测端“发送数”和服务端“接收数”。
- 确认压测机的 CPU、端口、连接和网络没有先饱和。
- 让脚本验证响应语义；仅收到 HTTP 200 不代表业务成功。

### 4.3 预热、升压、稳态和降压

```text
预热 5 min → 分级升压 10 min → 稳态 20 min → 降压/观察恢复 5 min
```

预热用于建立连接、填充缓存和触发 JIT（若有）。统计窗口应排除不需要的预热阶段，但不能隐藏真实的冷启动要求。

### 4.4 同步采集证据

客户端记录到达率、完成率、延迟分位数和错误；服务端记录 CPU、内存、GC（若有）、线程/连接池、队列、磁盘和网络；下游记录慢查询、锁、缓存命中率与限流。用统一时钟和测试标识关联日志、指标与 Trace。

## 5. 示例：容量估算

假设压测得到“满足 SLO 时单实例可持续 400 RPS”，目标峰值为 3000 RPS，希望平时最多使用 60% 的已验证能力：

```text
基础实例数 = ceil(3000 / (400 × 0.60)) = 13
```

还要验证：

- N+1 或单可用区故障时，剩余实例仍满足目标。
- 自动扩容在突发到来前是否来得及；冷启动期间由谁承载。
- 数据库、缓存、消息队列和外部配额是否随服务副本线性扩展。
- 单实例上限是否来自 CPU；若来自锁、共享存储或下游，简单加副本未必有效。

容量结论应给出适用范围，而不是一个永久数字：版本、数据规模、缓存命中率、资源限制或依赖变化后需要重测。

## 6. 常见坑与排障步骤：找到拐点而非只找最大值

典型排查顺序：

1. 观察目标到达率与实际完成吞吐是否分离。
2. 找到 p99、错误率开始恶化的流量级别。
3. 对齐同一时间窗的资源和队列指标。
4. 用 Trace、CPU 火焰图、慢查询或锁分析定位最主要等待点。
5. 降回低流量，确认系统能否恢复；不能恢复可能存在泄漏、重试风暴或队列积压。

常见误判：

- 客户端 CPU 满，被误判为服务端极限。
- 使用平均延迟掩盖少量严重超时。
- 压测数据过于单一，缓存命中率高得不真实。
- 无界重试放大流量，客户端统计一次请求而服务端处理多次。
- 测试环境和生产的 CPU 限额、网络、数据量或依赖不同，却直接外推。
- Coordinated Omission：生成器等待上一个响应后才发下一个请求，漏记本应在等待期间到达的请求。

## 深化学习说明

前半部分是压测和容量评估的速查框架，帮助你先定义问题、指标和报告口径。下面的内容进一步展开统计可信度、SLO/错误预算、可复现实验和全链路瓶颈定位，避免把工具输出误当成容量结论。

## 10. 前置知识和完成标准

学习本章前，应能读懂服务基础指标、HTTP 状态码、数据库连接池、线程池或异步队列的基本含义。压力测试不是“把工具开到最大”，而是用受控负载验证系统在目标条件下是否满足可靠性目标。

完成本章后，应能做到：

- 把业务目标转成负载模型：到达率、请求比例、数据分布、峰值持续时间和重试策略。
- 用 SLO/错误预算定义压测通过、降级、停止和回滚条件。
- 解释均值、分位数、置信区间、重复实验波动和样本量不足的风险。
- 从客户端、服务端、数据库、消息队列、缓存和平台资源中找出主要瓶颈证据。
- 写出容量结论的适用范围，而不是给出脱离版本和数据规模的永久数字。

## 11. 指标统计和流量建模补充

统计口径必须先于工具配置确定。一个请求是否算成功，通常需要同时满足协议成功、业务断言成功、延迟在可接受范围内。只把 HTTP 5xx 算失败，会漏掉业务错误码、空结果、幂等冲突、下游超时后的降级错误。

常用统计原则：

- 分位数需要足够样本。若某阶段只有 200 个请求，p99 只对应最慢的几个样本，结论很脆弱。
- 报告多轮重复结果时，至少给出中位结果、最差结果和波动范围，不只挑最好一次。
- 分开统计客户端观测延迟和服务端处理时间；排队、网络、TLS、连接复用都会造成差异。
- 对错误率很低的系统，用绝对失败数辅助判断。例如 0.01% 在 1000 请求里可能不到 1 个样本。
- 对长尾延迟，平均值只作为辅助。p95/p99 恶化通常更早暴露连接池、锁、GC 和下游抖动。

开放模型和封闭模型的选择会改变结论：

```text
开放模型：按外部到达率发请求，服务变慢时在途请求堆积，更容易暴露排队和过载。
封闭模型：固定虚拟用户循环，服务变慢时用户循环自然变慢，实际到达率下降，适合模拟有人类思考时间的会话。
```

生产容量评估一般优先用开放模型验证入口服务的峰值吸收能力，再用封闭模型验证会话型工作流体验。二者结论不能互相替代。

## 12. SLO、错误预算和停止条件

压测成功条件应对齐 SLO。例如：

```text
SLI：成功请求延迟、请求成功率、核心业务成功率
SLO：30 天内 99.9% 的 checkout 请求成功，且 99% 成功请求在 300 ms 内完成
可用性错误预算：30 天内最多允许 0.1% checkout 请求失败
延迟错误预算：30 天内最多允许 1% 成功 checkout 请求超过 300 ms
```

压测中可把错误预算转成操作规则：

- 晋级条件：目标 RPS 下连续 20 分钟，成功率预算消耗率在允许范围内，延迟超标比例 < 1%，p99 < 300 ms，错误率 < 0.1%，CPU < 70%，数据库连接池等待 p99 < 50 ms。
- 停止条件：关键业务错误率 > 0.5% 持续 3 分钟，或数据库锁等待/复制延迟越界，或压测端自身 CPU > 80% 导致工具不可信。
- 回滚条件：若压测在预生产或生产影子流量环境影响真实依赖，发现错误预算消耗异常、积压不可恢复、下游限流触发，应立即停止注入并恢复基线配置。

边界说明：压测阈值不是生产 SLO 本身。压测可用更严格的资源阈值保留余量，也可用更短窗口快速止损，但最终容量结论必须说明和正式 SLO 的对应关系。

## 13. 从零开始实验：用本地服务观察饱和

教学边界：以下实验只压测本机临时 HTTP 服务，不代表生产压测。不要把压测目标指向生产域名，除非已有变更审批、限流、停止条件、告警观察和责任人。

准备一个单线程慢接口：

```bash
lab_dir="$(mktemp -d "${TMPDIR:-/tmp}/load-lab.XXXXXX")"
cd "$lab_dir"
pwd
python3 -m venv .venv
.venv/bin/python -m pip install flask
cat > app.py <<'PY'
from flask import Flask
import time

app = Flask(__name__)

@app.get("/work")
def work():
    time.sleep(0.05)
    return {"ok": True}

if __name__ == "__main__":
    app.run(host="127.0.0.1", port=5005, threaded=False)
PY
.venv/bin/python app.py
```

另开终端用 Python 标准库发固定并发请求。将第一终端 `pwd` 输出的目录替换到下面的 `cd` 命令中：

```bash
cd /path/printed-by-first-terminal
.venv/bin/python - <<'PY'
from concurrent.futures import ThreadPoolExecutor, as_completed
from statistics import median, quantiles
from urllib.request import urlopen
import time

def one():
    start = time.perf_counter()
    with urlopen("http://127.0.0.1:5005/work", timeout=5) as r:
        r.read()
    return time.perf_counter() - start

for concurrency in [1, 5, 20, 50]:
    start = time.perf_counter()
    latencies = []
    errors = 0
    with ThreadPoolExecutor(max_workers=concurrency) as pool:
        futures = [pool.submit(one) for _ in range(100)]
        for f in as_completed(futures):
            try:
                latencies.append(f.result())
            except Exception:
                errors += 1
    elapsed = time.perf_counter() - start
    if not latencies:
        print(concurrency, "rps=0", "p50=n/a", "p95=n/a", "errors=", errors)
        continue
    p95 = quantiles(latencies, n=20)[18] if len(latencies) >= 20 else max(latencies)
    print(concurrency, "rps=", round(len(latencies)/elapsed, 1), "p50=", round(median(latencies), 3), "p95=", round(p95, 3), "errors=", errors)
PY
```

预期结果：并发升高后，RPS 不会无限增长，延迟会因单线程排队明显上升。失败现象可能包括超时或连接拒绝，说明客户端等待时间超过服务处理能力。

脚本说明：`ThreadPoolExecutor` 用固定并发模拟封闭模型；每个任务记录端到端客户端耗时；`errors` 统计超时、连接错误等异常；没有任何成功请求时输出 `n/a`，避免对空样本计算 `median` 或 `max`。这只是教学脚本，没有恒定到达率调度、预热窗口、直方图桶和服务端指标，不能替代生产压测工具。

验证重点：把输出中的并发、RPS、p50、p95 对照 Little's Law 粗算在途请求量；观察吞吐拐点，而不是只追求最大并发数字。

## 14. 数据库、缓存和消息队列容量边界

服务副本增加不代表全链路容量线性增加。常见非线性瓶颈包括：

- 数据库连接池：副本数增加会放大总连接数，可能超过数据库 `max_connections` 或让锁竞争变严重。
- 慢查询和锁：低并发下可接受的查询，在高并发下会形成队列并拖高尾延迟。
- 缓存热点：缓存命中率高时服务看起来很快，但热点 key 失效会把流量打到数据库。
- 消息队列：生产速率高于消费速率会形成积压；短时成功响应可能只是把问题推迟到异步链路。
- 第三方 API：外部配额、限流和重试退避通常不是你能通过加实例解决的。

容量报告应同时给出同步路径和异步路径结论。例如“入口服务在 2000 RPS 下成功响应，但订单事件积压增长 500 条/分钟”不能判定系统满足容量目标。

## 15. 排障决策路径

发现 p99 上升时：

1. 如果 RPS 未达到目标且客户端 CPU/网络已高，先扩压测端或降低客户端开销。
2. 如果服务 CPU 高且队列不长，优先看 CPU profile、序列化、加密、正则、日志同步写。
3. 如果 CPU 不高但延迟高，优先看锁、连接池等待、下游耗时、线程池排队。
4. 如果错误率伴随重试上升，先关闭或限制重试，避免放大下游故障。
5. 如果降压后不恢复，查内存泄漏、连接泄漏、队列积压、熔断半开策略和缓存击穿。

验证修复时必须回到同一负载模型、同一数据规模、同一统计窗口。只在低流量冒烟通过，不能证明容量问题修复。

## 16. 练习答案要点

基础练习：1000 RPS、读写比 9:1 的开放模型应拆成查询 900 RPS、下单 100 RPS，并说明数据分布、认证、购物车大小、库存冲突和幂等键。

进阶练习：连接池过小的预期现象是服务 CPU 不一定高，但连接等待时间、p95/p99 和超时上升；数据库 QPS 可能没有达到硬件极限。

综合练习：60 分钟浸泡测试答案要包含固定版本、预热窗口、RSS/堆/FD 趋势、错误率、p99、GC 或运行时指标。若 RSS 单调增长且降压后不回落，应优先怀疑泄漏或缓存无界增长。

## 17. 章节小结

压力测试的价值在于把“系统能扛多少”变成有边界、可复现、可解释的证据。可靠容量结论必须同时包含负载模型、SLO、统计可信度、瓶颈证据、冗余策略和失效场景。
