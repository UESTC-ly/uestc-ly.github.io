# CI/CD：从提交到可回滚发布

## 学习目标

- 理解 CI、CD、流水线、制品、环境、审批和回滚的职责。
- 能设计后端服务常见流水线：测试、构建、镜像、扫描、部署。
- 能把 Docker、Kubernetes、Nginx 和测试体系串成交付闭环。
- 能识别生产发布中的凭据、安全、并发和回滚风险。

## 核心概念

CI 是持续集成，核心是每次提交都尽快验证代码是否还能集成，包括格式、静态检查、单元测试、集成测试和构建。CD 可以指持续交付或持续部署：前者把制品准备到可发布状态，后者自动发布到目标环境。

制品是流水线产出的不可变结果，例如二进制包、Docker 镜像、SBOM、测试报告和部署清单。生产部署应使用已经验证过的制品，而不是在生产阶段重新构建。

环境通常分为开发、测试、预发和生产。越靠近生产，权限越严格，变更越需要审计、审批、告警和回滚策略。

## 示例

### GitHub Actions 示例

```yaml
name: service-ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: pytest -q

      - name: Build image
        run: docker build -t registry.example.com/user-api:${{ github.sha }} .
```

### 部署步骤示例

```bash
docker push registry.example.com/user-api:$GIT_SHA
kubectl set image deployment/user-api api=registry.example.com/user-api:$GIT_SHA
kubectl rollout status deployment/user-api
```

生产注意事项：CI/CD 凭据必须使用平台 Secret 或 OIDC 短期凭证，不要写入仓库。生产部署应限制触发分支和审批人，避免多个流水线同时部署同一环境。发布后必须观察错误率、延迟、重启次数和业务指标。

## 典型工作流

1. 开发者提交代码并创建 Pull Request。
2. CI 运行格式检查、静态分析、单元测试、集成测试和构建。
3. 合并后构建不可变镜像，生成 SBOM 和漏洞扫描结果。
4. 镜像推送到 Registry，部署清单引用该镜像 tag 或 digest。
5. 部署到测试或预发环境，运行接口测试和冒烟测试。
6. 生产发布执行滚动更新、金丝雀或蓝绿发布，并监控关键指标。
7. 若发布失败，使用上一版本镜像和部署记录回滚。

## 常见坑

- 测试和构建在 PR 阶段通过，但生产部署阶段重新构建了不同制品。
- 流水线使用长期云密钥，泄漏后影响面大。
- 缓存依赖没有锁版本，导致同一提交在不同时间构建结果不同。
- 集成测试依赖共享环境，多个流水线并发时互相污染。
- 部署成功即认为发布成功，没有冒烟测试和指标观察。
- 回滚步骤没有演练，真正故障时才发现数据库迁移不可逆。

## 排障步骤

1. 确认失败阶段：拉代码、装依赖、测试、构建、推送镜像、部署或验证。
2. 对测试失败，查看失败用例、随机种子、环境变量和依赖版本。
3. 对镜像构建失败，检查 Dockerfile 层、构建上下文、Registry 权限和磁盘空间。
4. 对部署失败，检查 kubeconfig、命名空间、镜像拉取权限、rollout 事件和 Pod 日志。
5. 对发布后异常，对比新旧版本差异、配置差异、错误率、延迟和资源使用。
6. 必要时停止继续发布，回滚到上一可用制品，并保留流水线日志用于复盘。

## 练习

2. 增加一个集成测试 job，使用服务容器启动 PostgreSQL。

## 检查清单

- PR 阶段有快速反馈，主干阶段生成不可变制品。
- 流水线依赖版本固定，缓存不会改变构建结果。
- 凭据使用 Secret 或 OIDC，不进入日志和制品。
- 部署引用已验证镜像，发布后有冒烟测试和指标观察。
- 回滚命令、上一版本和数据库兼容策略明确。

## 前置知识与完成标准

前置知识：理解 Git 分支、Pull Request、测试、Docker 镜像、Kubernetes Deployment 和环境变量；知道一次发布应能追溯到源码提交和制品。

完成标准：

- 能画出从提交到生产的流水线：检查、测试、构建、扫描、签名、部署、验证、回滚。
- 能区分 artifact、cache、release、镜像 tag 和 digest 的职责。
- 能写出最小 GitHub Actions 工作流，并解释触发器、权限、缓存、制品、环境审批和并发控制。
- 能说明环境提升策略：开发 -> 测试 -> 预发 -> 生产，且生产使用已验证制品。

## 流水线、制品与环境生命周期

CI/CD 的主线数据流是：源码提交 -> runner 拉取代码 -> 安装固定依赖 -> 运行测试和静态检查 -> 构建不可变制品 -> 上传测试报告/SBOM/镜像 -> 部署到目标环境 -> 冒烟测试和指标观察 -> 保留回滚记录。越靠后越接近生产，越不应重新构建。

制品与缓存不要混用。artifact 是本次流水线明确产出的结果，例如二进制包、测试报告、覆盖率、SBOM 和部署清单；cache 是可丢弃的加速材料，例如 pip/npm/maven 下载缓存。缓存命中不应改变构建结果，缓存丢失也不应导致构建失败。

环境提升强调同一制品逐级前进。PR 阶段验证代码可集成；主干阶段生成镜像并记录 digest；测试环境跑集成和接口测试；预发环境验证接近生产的配置；生产阶段只改变部署引用和配置开关。审批用于控制风险，不应变成人工手工改命令。

安全边界包括：默认最小 `GITHUB_TOKEN` 权限；部署 job 才能访问部署凭据；优先使用 OIDC 换取云厂商短期凭证；Secret 不进入缓存、日志和镜像层；来自 fork 的 PR 不应获得写权限或生产密钥。

## 从零可复现实验

目标：为 Python 项目建立最小 CI，保存测试报告，并为生产部署预留审批环境。

1. 创建 `.github/workflows/service-ci.yml`：

```yaml
name: service-ci

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: service-ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - run: pip install -r requirements.txt
      - run: pytest -q --junitxml=reports/junit.xml

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: test-report
          path: reports/junit.xml
```

2. 在仓库设置中创建 `production` environment，并配置 required reviewers。
3. 增加部署 job 时引用环境：

```yaml
  deploy-production:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      id-token: write
    steps:
      - run: echo "deploy verified artifact here"
```

预期结果：PR 和 main push 会运行测试；测试报告总是上传；生产 job 在环境规则处等待审批。失败现象：依赖安装失败多为锁文件或包源问题；测试报告缺失多为路径错误；部署 job 无法取 OIDC 多为 `id-token: write` 缺失。

## 配置与命令逐段讲解

```yaml
on:
  pull_request:
  push:
    branches: [main]
```

`pull_request` 给评审前反馈，`push main` 用于主干合并后的制品生成和环境提升。不要让任意分支自动部署生产。

```yaml
permissions:
  contents: read
```

显式设置最小权限，避免默认 token 权限过宽。需要推镜像、发 release、写部署状态或换取云凭证时，只在对应 job 增加最小写权限。

```yaml
concurrency:
  group: deploy-production
  cancel-in-progress: false
```

生产部署通常应避免并发。是否取消正在进行的部署取决于平台语义：测试流水线常取消旧提交，生产部署更常排队或人工判断，避免两个版本交叉修改同一环境。

```bash
docker build -t registry.example.com/user-api:$GIT_SHA .
docker push registry.example.com/user-api:$GIT_SHA
kubectl set image deployment/user-api api=registry.example.com/user-api:$GIT_SHA
kubectl rollout status deployment/user-api --timeout=5m
```

构建阶段产生镜像，推送阶段发布制品，部署阶段只更新 Kubernetes 引用，rollout 阶段验证控制器是否完成替换。生产更推荐记录镜像 digest，并把实际运行版本写入发布记录。

## 教学配置与生产配置边界

教学流水线可只包含 checkout、安装依赖、测试和构建镜像；生产流水线应补依赖锁、矩阵或目标平台构建、漏洞扫描、SBOM、镜像签名或 provenance、环境保护、审批、并发控制、部署后冒烟测试和监控门禁。

教学中可以使用仓库 Secret 模拟部署凭据；生产应优先使用环境 Secret 或 OIDC 短期凭据，并限制可访问分支和审批人。教学中回滚可用上一 tag；生产回滚还必须考虑数据库迁移、配置兼容、消息格式兼容和外部依赖状态。

## 排障决策树

```text
流水线失败
├─ checkout 或权限失败？
│  └─ 检查 token permissions、私有子模块、分支保护、fork PR 权限
├─ 依赖安装失败？
│  └─ 检查锁文件、缓存污染、包源、运行器系统版本
├─ 测试失败？
│  └─ 区分代码回归、flaky、时区、并发、共享服务污染
├─ 构建/推镜像失败？
│  └─ 检查 Dockerfile、构建上下文、Registry 登录、磁盘、tag
├─ 部署失败？
│  └─ 检查环境审批、OIDC/Secret、kubeconfig、命名空间、镜像拉取
└─ 部署后异常？
   └─ 看 rollout、Pod 日志、错误率、延迟、业务指标；满足回滚条件则回滚
```

## 练习与答案要点

基础练习：把 Python CI 拆成 lint 和 test 两个 job，test 依赖 lint。答案要点：`needs` 表达依赖；失败阶段清晰；两个 job 权限都最小。

进阶练习：加入 Docker build job，使用 Git SHA 标记镜像，并上传 SBOM 或镜像 digest 文件为 artifact。答案要点：制品可追溯；artifact 和 cache 职责不同；部署不重新构建。

综合练习：设计测试、预发、生产三环境提升流程，包含审批、并发控制、冒烟测试和回滚条件。答案要点：同一镜像 digest 逐级提升；生产 job 访问生产凭据；失败自动停止；回滚说明数据库兼容边界。

## 小结与官方延伸阅读

CI/CD 的目标不是把命令搬到服务器上自动执行，而是让每次变更都有可重复验证、可追溯制品、受控环境提升和可演练回滚。越接近生产，越要减少“现场构建”和“临时手工操作”。
