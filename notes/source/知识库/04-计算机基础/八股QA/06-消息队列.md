## 6. 消息队列（MQ）

- [ ] ★★★ 为什么使用消息队列？它会带来哪些问题？
  - **完整回答：**
    - 使用消息队列通常是为了把同步调用拆成可靠的异步事件流。
    - 一个业务动作发生后，生产者把消息发送到 Broker，Broker 按主题、队列、分区或路由规则保存并投递，消费者再按自己的能力拉取或接收消息并执行业务。
    - 这样订单创建可以先完成主链路，再让库存、积分、通知、风控等系统独立消费同一个事件，生产者不需要等待所有下游完成；突发流量也可以先进入队列，消费者按稳定速率处理，形成削峰填谷。
    - 但 MQ 不是单纯的性能开关，它把同步失败变成了异步不确定性。
    - 消息可能在生产确认前超时、Broker 落盘或副本复制前宕机、消费者处理成功但 ack 或 offset 提交失败，最终表现为丢失、重复、乱序、延迟和积压。
    - 异步化还会引入最终一致性，调用方不能立即知道下游结果，必须提供状态查询、回调、补偿、对账和告警。
    - 系统还要监控发送成功率、队列深度、消费 lag、死信量和端到端耗时，并在消费者追不上时限流或降级，否则队列只会把故障延后暴露。
    - 消息体、Schema 版本、重试策略和权限隔离也会成为新的治理成本，发布时要兼容新旧消费者。
    - Kafka 更像可回放的分布式日志，适合高吞吐事件流；RabbitMQ 更强调交换机、队列和路由；RocketMQ 在业务消息、事务消息、顺序和延迟能力上常见。
    - 选型和使用时要明确消息生命周期、确认机制、持久化、副本、消费语义、压测口径和失败恢复指标，否则只是把耦合从代码转移到队列和运维。
  - **原理解析：**
    - 消息队列的核心不是“加一个中间件”，而是把一次调用拆成生产、Broker 存储、消费者处理、确认推进四段生命周期。生产者只对 Broker 的接收负责，下游处理从同步等待变成异步订阅，所以主链路变短，系统边界也从方法调用变成了消息契约。
    - 削峰来自队列的缓冲能力：高峰期消息先落到队列、分区或日志里，消费者按稳定速率推进 ack 或 offset；解耦来自发布者只面向 topic、exchange 或 queue，不直接绑定每个下游实例。Kafka 偏日志和回放，RabbitMQ 偏路由和任务投递，RocketMQ 偏业务消息能力。
    - 代价的因果链是：异步后调用方不再即时知道结果，确认丢失、落盘失败、副本滞后、消费者宕机都会把失败推迟到消费阶段暴露，于是必须用监控、重试、死信、补偿、对账来收束不确定性。容量也要重新建模，因为队列能吸收短峰值，却不能消灭长期超载。
    - 记忆抓手：MQ 解决“等、抖、耦合”，但引入“丢、重、乱、慢、一致性”。回答时按生命周期说收益，再按生产确认、Broker 持久化/副本、消费确认说风险，最后补产品差异和治理成本，并强调消息契约、Schema 兼容和权限隔离也是长期成本。

- [ ] ★★★ 如何保证消息不丢失？
  - **完整回答：**
    - 消息不丢失要按生产端、Broker、消费端三段看，而不是只打开某个“可靠”配置。
    - 生产端创建消息后要带业务唯一键，发送时等待 Broker 的确认；同步发送要检查返回值，异步发送要处理回调，超时结果不能简单等同于失败，因为 Broker 可能已收到消息，所以重试必须允许重复。
    - Kafka 中常见配置是 `acks=all`、合理的 `min.insync.replicas`、重试和幂等生产者；幂等生产者主要避免生产者重试在 Kafka 日志中产生重复，Kafka 3.0+ 默认启用，但边界受 producer session、应用层重发、事务配置与外部副作用限制。
    - 跨 topic/partition 原子写及 offset 原子提交需要 Kafka 事务，外部 DB 仍要靠业务幂等、事务或对账。
    - RabbitMQ 需要 publisher confirm，队列和消息都持久化；classic mirrored queues 自 3.9/2021 起废弃、4.0 起移除，非镜像 classic queues 仍支持，需要复制时应优先评估 quorum queues 或 streams。
    - RocketMQ 可结合同步发送、刷盘策略、主从或 DLedger 类高可用部署、事务消息和发送重试。
    - Broker 侧要确保消息落盘和副本满足故障目标，异步刷盘和副本异步复制性能更好但故障窗口更大。
    - 消费端必须在业务落库、状态更新或外部副作用确认后再 ack 或提交 offset；如果先确认再处理，消费者宕机会直接丢业务。
    - 恢复验证要看发送失败率、未确认消息、ISR 或副本状态、消费 lag、死信数量，并通过补偿任务或对账表发现长期未完成的业务事件。
    - 工程上只能做到按故障模型的高可靠，不能承诺任意场景绝不丢。
  - **原理解析：**
    - “不丢”要按链路分段证明：生产端发出后必须拿到 Broker 确认，Broker 收到后要落盘并满足副本策略，消费端必须在业务真正成功后再确认。任一段把“已发送”“已写入”“已处理”混为一谈，都会留下消息静默丢失窗口。
    - Kafka 的关键是分区日志、Leader/Follower 副本、ISR、`acks=all` 和 `min.insync.replicas`：只有同步副本数量满足要求后才确认，可靠性更强但延迟更高；RabbitMQ 依赖 publisher confirm、持久化队列/消息以及 quorum queues 等复制队列；RocketMQ 关注刷盘、主从/高可用和发送重试。
    - 超时的边界最容易误判：生产者没收到确认，不代表 Broker 没收到；消费者处理成功但 ack 或 offset 提交失败，也会再次投递。因此可靠发送通常天然伴随重复风险，必须结合业务唯一键、幂等消费、补偿任务和对账。发送端重试要带同一业务键，不能把网络超时简单当成“消息一定失败”。
    - 记忆抓手：三段三件事，生产等确认，Broker 看落盘和副本，消费先处理后确认。只能按故障模型提升可靠性，不能承诺所有机器、磁盘、网络、代码和外部系统同时异常时仍绝不丢；真正上线还要用告警、演练和恢复指标验证配置有效。

- [ ] ★★★ 如何处理重复消息，保证消费幂等？
  - **完整回答：**
    - 重复消息是 MQ 使用中的正常路径，不是罕见异常。
    - 生产者发送超时后重试、Broker 主从切换、消费者处理成功但 ack 丢失、Kafka offset 提交晚于业务提交、RabbitMQ nack/requeue、RocketMQ 消费失败重试，都会让同一业务消息被再次投递。
    - 消费者因此要按至少一次投递来设计，使同一消息执行一次和多次的最终业务结果一致。
    - 最可靠的幂等依据应来自业务唯一键，例如订单号、支付流水号、退款单号、库存扣减流水或请求幂等键，而不是只依赖 MQ 自动生成的消息 ID，因为重发或跨系统转发可能改变消息 ID。
    - 常见做法是在数据库中建立唯一约束，先插入处理流水再执行业务，或者把业务状态流转写成带条件的更新，例如只允许订单从“待支付”变成“已支付”，重复支付回调只能读到已完成状态并返回首次结果。
    - 幂等表要处理并发插入、事务边界、过期清理和分库分表后的唯一性；Redis 去重只适合可接受过期窗口和偶发误差的场景，不能替代强一致落库。
    - 外部副作用更难，例如短信、发货、第三方支付，通常要使用对方支持的幂等键、查询确认和补偿撤销。
    - 幂等还要保留处理结果，客户端或补偿任务重复查询时应返回稳定状态，而不是把所有重复都当成错误，也不能在失败未定时错误地标记为已处理。
    - 验证方式不是只看消费者没有报错，而是压测重复投递、宕机重启、ack 失败和并发消费，确认余额、库存、订单、流水等核心数据不会多扣、多发或漏状态。
  - **原理解析：**
    - 重复的根因是 MQ 为了避免丢失，通常让“未确认”消息重新进入生命周期：生产端超时会重发，Broker 切换可能重放，消费者业务成功但 ack/offset 没提交也会重投。也就是说，不丢和不重天然存在张力，工程上常选择至少一次加幂等。
    - 幂等的核心是用业务事实定界，而不是信任消息投递次数。订单号、支付流水、库存扣减单这类业务唯一键要进入数据库唯一约束、处理流水或状态机条件更新中，使第二次消费只能读到已处理结果，不能再次扣钱、减库存或发货。
    - Kafka 的 offset 晚提交会重复，RabbitMQ 的 nack/requeue 会重复，RocketMQ 的消费失败重试也会重复；产品差异改变重投路径，不改变消费者必须幂等的结论。即使 Kafka 幂等生产者能减少日志中的重复写入，也不能消除应用层手工重发和外部副作用重复。Redis 去重只适合短窗口弱约束，强资金库存场景要落库和对账。
    - 失败边界在“处理结果未定”：插入幂等表成功但业务失败、外部接口成功但本地记录失败、并发重复同时到达，都要靠同一事务、状态查询、补偿撤销和稳定返回结果处理。
    - 记忆抓手：重复不是 bug，是可靠投递的副产品。答题顺序按来源、唯一键、落库幂等、外部副作用、验证场景展开，并明确“幂等”不是丢弃重复请求，而是让重复请求返回同一业务结果。

- [ ] ★★★ 如何保证消息顺序？
  - **完整回答：**
    - 消息顺序首先要明确是全局顺序还是按业务键的局部顺序。
    - 全局顺序要求所有消息进入同一个串行通道并由一个消费单元依次处理，吞吐、可用性和扩展性代价很高，实际业务更多只要求同一订单、同一用户、同一设备或同一库存维度内有序。
    - 实现方式是在生产端按同一业务键稳定路由到同一个 Kafka 分区、RabbitMQ 队列或 RocketMQ MessageQueue，Broker 在该通道内按追加顺序保存，消费者对这个通道串行处理，并在处理成功后再推进确认位置。
    - Kafka 只保证单分区内有序，跨分区没有全局顺序，同一 key 的分区路由要保持稳定，增加分区还可能影响后续 key 到分区的映射；RabbitMQ 用单队列单消费者可以维持投递顺序，但多消费者、prefetch、nack/requeue、死信回流都会改变观察到的顺序；RocketMQ 提供顺序消息消费模型，但也依赖发送端按选择器路由到同一队列和消费端串行消费。
    - 异常路径是顺序设计的难点：某条消息失败时，如果继续处理后续消息，就可能让“取消订单”早于“创建订单”；如果阻塞同 key 消息，则一个坏消息会造成局部积压。
    - 恢复策略通常是有限重试、进入人工处理或把同 key 后续消息暂停，并用状态机、版本号和幂等更新降低对严格顺序的依赖。
    - 验证时要构造乱序发送、消费失败、重平衡和重试回流场景，检查最终状态和中间状态都符合业务约束，尤其要确认扩容、重试和死信重放后不会绕过顺序通道。
  - **原理解析：**
    - 顺序的第一步是缩小范围：全局顺序意味着所有消息走一个串行日志或队列，吞吐和可用性都会被单点串行约束；多数业务只需要同一订单、用户、设备或库存维度内有序，因此按业务键做局部顺序更实际。
    - 生命周期上要保证同一 key 从生产路由到 Broker 存储再到消费确认都在同一有序通道内。Kafka 是同一 key 进入同一分区，分区 offset 按追加顺序增长；RabbitMQ 可用单队列单消费者维持投递顺序；RocketMQ 通过 MessageQueue 选择和顺序消费保持局部串行。
    - 顺序最怕异常路径：并发消费者、prefetch、重平衡、nack 回队、死信重放、扩分区改变路由，都可能让观察顺序偏离原追加顺序。某条消息失败时，继续消费会乱序，阻塞消费会积压，所以要在业务上决定阻塞、跳过、人工修复或用补偿事件推进。扩容前尤其要评估 key 到分区或队列的映射是否会变化。
    - 记忆抓手：同 key、同通道、单线程、后确认。再补一句“用状态机和版本号降低顺序依赖”，因为严格顺序是吞吐和恢复能力换来的，不适合作为所有业务的唯一正确性基础；能用单调版本拒绝旧事件时，就不要把所有正确性都压在 MQ 顺序上，尤其是跨服务流程。

- [ ] ★★★ 消息积压通常是什么原因？如何处理？
  - **完整回答：**
    - 消息积压的本质是生产速率在一段时间内持续高于有效消费速率，但原因可能在很多层。
    - 生产端可能遇到活动流量、批量导入或上游重试风暴；Broker 可能分区或队列热点、磁盘 IO 到顶、页缓存不足、副本同步变慢；消费者可能线程池耗尽、单条处理逻辑变慢、批量写库退化为逐条写、外部接口超时、数据库锁冲突，或者消费失败后不断重试同一批消息。
    - 处理时先看 Topic 或队列的生产速率、消费速率、lag、消费者错误率、P95/P99 处理耗时、下游容量和热点分布，不能一上来只扩消费者。
    - 如果瓶颈在 Kafka 同一消费组，消费者并行度通常受分区数限制，消费者数超过分区数不会继续提升并行度；如果瓶颈在数据库或第三方接口，盲目扩容消费者会把下游压垮。
    - 可行措施包括临时增加消费者实例、增加分区或队列并调整路由、批量拉取和批量写入、减少同步外部调用、隔离慢消息、对生产端限流或降级。
    - 对非核心消息可以按业务批准丢弃、转储到临时 Topic 后离线补偿；核心消息应保留可回放能力，不能为了清 lag 直接跳过。
    - 积压期间还要关注消息过期、磁盘水位、死信增长和消费者重启带来的重复处理风险，必要时暂停非关键生产者保护 Broker，并评估保留时间是否足够支撑恢复窗口、回放需求、业务恢复与补偿时限。
    - 恢复后要复盘容量模型、告警阈值、死信处理、消费者超时和压测结果，验证积压清空速度、下游错误率和数据对账结果，而不是只看队列深度归零。
  - **原理解析：**
    - 积压本质是生产速率大于有效消费速率，消息生命周期停在 Broker 存储或消费者未确认阶段。它可能不是 MQ 慢，而是上游突然放量、Broker 热点分区、磁盘/副本同步变慢、消费者业务逻辑或下游数据库变慢共同造成的结果。
    - 诊断要沿着指标链看：生产 TPS、消费 TPS、Kafka lag 或队列深度、未 ack 数、分区/队列热点、消费者错误率、P99 耗时、下游连接池和锁等待。Kafka 还要看分区数，因为同一消费组并行度受分区限制；RabbitMQ 要看队列堆积和 unacked；RocketMQ 要看消费进度、重试主题和队列分布。
    - 处理的因果链是先止血再恢复：限流或降级非关键生产者保护 Broker，隔离慢消息和失败重试风暴，增加消费者或分区/队列提升并行度，批量拉取写入减少单条开销；如果瓶颈在数据库或第三方，扩消费者只会把故障放大。
    - 失败边界包括消息过期、磁盘水位、保留时间不足、死信暴涨和恢复期重复消费。核心消息不能为清 lag 直接跳过，非核心消息也要有业务批准和转储补偿。
    - 记忆抓手：先定位“谁慢”，再决定“扩、批、隔、限、补”。队列深度归零不等于业务恢复，最后要看数据对账和端到端延迟。

- [ ] ★★★ 什么是消息确认、重试队列和死信队列？
  - **完整回答：**
    - 消息确认是消费者向 MQ 表达“这条消息对应的消费进度可以推进”的动作，但不同产品的模型不同。
    - Kafka 消费者读取分区日志后提交 offset，Broker 通常不因为某个消费者确认而删除消息，消息是否保留由保留时间或大小策略决定；RabbitMQ 使用 ack、nack、reject 管理队列中的投递，未确认消息在消费者连接断开后会重新入队；RocketMQ 消费者返回消费成功或失败状态，失败消息会按策略进入重试主题或稍后再次投递。
    - 正确确认时机一般是在业务处理成功之后，包括数据库事务提交、状态机更新或外部副作用可确认完成之后。
    - 重试队列用于处理网络抖动、短暂限流、数据库主从切换这类可恢复故障，应该有次数上限、退避间隔和错误分类；对参数非法、状态不允许、数据不存在等确定性业务错误，重复投递通常只会放大问题。
    - 死信队列用于隔离超过重试上限、过期、被拒绝或无法路由的消息，它不是垃圾桶，而是异常恢复入口，必须有告警、查询、修复、重放和审计流程。
    - 重放死信时要保留原始业务键和异常上下文，并经过幂等校验，避免修复动作造成二次破坏。
    - 重试和死信会改变消息生命周期，也可能破坏顺序，所以顺序敏感业务要决定是阻塞、跳过、人工修复还是用补偿事件推进。
    - 常见误区是把进入死信视为处理完成，实际它只是从自动流程转入异常治理流程。
    - 验证时应主动制造消费异常、消费者宕机、ack 丢失和死信重放，确认消息不会静默消失，重复投递也不会破坏业务数据。
  - **原理解析：**
    - 消息确认是消费生命周期的分界线：确认前，MQ 认为这条消息仍可能需要再次投递；确认后，消费进度推进。Kafka 表现为提交分区 offset，消息本身由日志保留策略决定是否删除；RabbitMQ 表现为 ack/nack/reject 管理队列投递；RocketMQ 表现为消费成功或失败状态驱动重试。
    - 确认必须放在业务成功之后，否则消费者宕机、事务回滚或外部调用失败时，MQ 已经认为进度完成，业务就会丢处理。反过来，如果业务成功但 ack 或 offset 提交失败，消息会重复出现，所以确认机制同时连接“不丢”和“会重”。
    - 重试队列处理可恢复故障，要有次数、退避和错误分类；死信队列承接超过重试上限、过期、被拒绝或无法路由的消息。它们不是结束状态，而是把消息从自动消费流程转入异常治理流程。
    - 失败边界是重试可能放大确定性错误，死信重放可能破坏顺序或造成二次副作用。重放时要带原始 key、异常上下文和幂等校验。
    - 记忆抓手：ack 管进度，retry 管暂时失败，DLQ 管异常闭环。回答时分别说 Kafka offset、RabbitMQ ack、RocketMQ 重试语义，避免把所有 MQ 说成一种模型。

- [ ] ★★★ 消息队列如何实现最终一致性？
  - **完整回答：**
    - MQ 实现最终一致性的关键，是把“本地业务状态变更”和“通知下游的消息”可靠地关联起来，再让下游通过可重试、可幂等的消费最终收敛到正确状态。
    - 典型消息生命周期是：上游在本地事务中创建订单并记录要发送的事件，消息被投递到 Broker，Broker 持久化并复制，消费者收到后更新库存、积分或账务，成功后确认消费；任何阶段失败，都要能通过重试、回查或对账继续推进。
    - 最常见方案是本地消息表，业务数据和待发送消息在同一个数据库事务中提交，后台任务扫描未发送记录并投递 MQ，收到发送确认后标记状态；发送确认丢失时可能重复发送，所以消费者必须幂等。
    - Outbox/CDC 是本地消息表的演进形式，业务事务写 outbox 表，由 CDC 捕获数据库变更并投递，减少业务代码直接操作 MQ 的不确定性。
    - RocketMQ 事务消息提供半消息和事务状态回查，适合某些本地事务与消息发送绑定的场景；Kafka 事务适合 Kafka 内 consume-transform-produce 的原子性，不能自动覆盖外部数据库。
    - 最终一致不是强一致，用户可能短时间看到“订单已创建但积分未到账”，系统要提供状态查询、处理中状态、超时补偿和人工处理，并定义超过多久仍未完成就进入告警或人工审核。
    - 验证要覆盖本地事务提交后发送失败、发送成功但标记失败、消费成功但 ack 失败、下游长期不可用等路径，并通过对账任务证明最终能收敛到一致状态。
  - **原理解析：**
    - 最终一致性的矛盾点是本地数据库事务和 MQ 发送不是天然同一个原子动作：订单提交成功但消息没发会漏通知，消息发成功但本地事务回滚会产生脏事件。设计目标不是让所有系统同时提交，而是让每个阶段失败后都有可重试、可回查、可补偿的推进路径。
    - 本地消息表和 Outbox 的原理是把业务状态与待发送事件写进同一个数据库事务，先保证“事实”和“待通知”同时落库，再由后台任务或 CDC 投递到 Broker。发送确认丢失时可能重复投递，所以消费者用业务 key 幂等；消费成功但确认失败时，也靠幂等抵消重复。
    - RocketMQ 事务消息通过半消息和事务回查绑定部分本地事务场景；Kafka 事务能覆盖 Kafka 内部读写和 offset 原子提交，更适合 consume-transform-produce 链路，但不能自动包住外部数据库、支付或短信。RabbitMQ 通常依赖 publisher confirm、本地表和消费幂等组合完成业务闭环。
    - 失败边界在“最终”二字：下游长期不可用、消息超保留时间、补偿任务停摆、人工修复错误，都会让收敛失败，所以要有状态查询、超时告警、对账和人工入口。
    - 记忆抓手：本地先留痕，消息可重发，消费要幂等，对账兜底。最终一致是可恢复流程，不是强一致的低配叫法；设计时要说清用户可见的中间状态、超时时限和人工介入条件。

- [ ] ★★ At-most-once、At-least-once 和 Exactly-once 分别是什么？
  - **完整回答：**
    - At-most-once、At-least-once 和 Exactly-once 描述的是消息投递或处理效果的语义，不等于所有业务副作用天然满足同样保证。
    - At-most-once 是最多一次，常见做法是先提交 offset 或 ack 再处理业务，这样不会重复处理同一投递，但消费者在真正执行业务前宕机就会丢消息，适合日志采样、监控指标这类可容忍丢失的场景。
    - At-least-once 是至少一次，通常业务处理成功后再确认，失败、超时或确认丢失会触发重投，因此更重视不丢，但必须接受重复，支付、库存、订单事件通常按这种模型配合幂等实现。
    - Exactly-once 在工程里要谨慎表述，它通常指在特定边界内达到“效果恰好一次”。
    - Kafka 的幂等生产者和事务可以在 Kafka 主题之间的读写链路中避免重复写入并原子提交相关 offset，但消费者写外部数据库、发短信、调用支付渠道时仍需要外部事务、幂等键或对账补偿。
    - RabbitMQ 和 RocketMQ 有确认、重试、事务消息等能力，但也不能把 MQ 产品特性扩展成任意端到端业务恰好一次。
    - 面试或设计中更稳妥的结论是：核心业务以 at-least-once 加幂等和对账实现业务效果收敛，只有在明确系统边界和存储事务能力时才谈 exactly-once。
  - **原理解析：**
    - 三种语义本质上由“处理业务”和“确认进度”的先后关系决定。先 ack 或提交 offset 再处理，就是 at-most-once，重复少但宕机可能丢；先处理成功再确认，就是 at-least-once，不易丢但确认失败会重投。
    - Exactly-once 要限定边界理解。Kafka EOS 需要稳定的 `transactional.id`，把 consume-process-produce 中的输出消息和消费 offset 放进同一个事务，并让下游消费者使用 `read_committed` 读取，才能在 Kafka 读写链路内做到效果恰好一次；但一旦消费者写外部 DB、发短信或调用支付接口，MQ 无法单独保证外部副作用也只发生一次。
    - RabbitMQ 的 ack/nack、RocketMQ 的消费重试和事务消息都能帮助控制投递与恢复，但不能被扩大成任意业务端到端 exactly-once。核心业务通常选择 at-least-once 加幂等、唯一约束、状态机和对账。
    - 记忆抓手：最多一次怕丢，至少一次怕重，恰好一次先问边界。不要背产品口号，要说清确认时机、重复来源和外部副作用。

- [ ] ★★ Kafka 为什么吞吐量高？
  - **完整回答：**
    - Kafka 吞吐量高来自它把消息系统设计成分布式追加日志，并尽量让 IO、网络和消费都批量化、顺序化。
    - 生产者把多条消息按 topic-partition 聚合成批次发送，Broker 追加写入分区日志文件，顺序写能充分利用磁盘和 SSD 的吞吐能力，避免频繁随机写。
    - Kafka 大量依赖操作系统页缓存，写入先进入页缓存，后台再刷盘；消费者读取热点数据时也可能直接从页缓存返回。
    - 发送日志文件给消费者时，Kafka 可利用零拷贝类机制减少用户态和内核态之间的数据复制，降低 CPU 开销。
    - 分区机制让一个 Topic 被拆成多个并行日志，分布在多个 Broker 上，生产、复制和消费都能横向扩展；消费者组内不同消费者处理不同分区，提高并行度。
    - 批处理和压缩减少请求次数、协议开销、磁盘占用和网络流量，但会带来 CPU 消耗和一定延迟，所以 `linger.ms`、batch size、压缩算法、分区数、副本数、`acks` 和消息大小都要按场景调优。
    - 高吞吐不是无条件成立，如果副本同步慢、消费者业务处理慢、分区热点明显、消息过大或确认级别过严，Kafka 仍会积压或延迟升高。
  - **原理解析：**
    - Kafka 把消息当成分区追加日志处理，生产者按 topic-partition 批量发送，Broker 顺序追加到日志文件并分配 offset。顺序写、批量网络请求和批量磁盘 IO 共同降低随机写、系统调用和协议开销。
    - 页缓存和零拷贝降低了数据搬运成本：写入先进入 OS page cache，热点读取可直接从缓存返回，文件发送给消费者时可减少用户态和内核态复制。分区再把一个 Topic 拆成多个并行日志，分布到多个 Broker 上扩展吞吐。
    - 高吞吐有边界：副本数、`acks=all`、ISR 同步、压缩算法、消息大小、分区热点、消费者处理耗时都会影响延迟和积压。Kafka 擅长日志流和回放，不代表每条业务命令都适合追求最大吞吐。
    - 记忆抓手：顺序写、页缓存、零拷贝、批处理、分区并行。回答时把这些机制串成“少随机 IO、少复制、少请求、多并行”的因果链。

- [ ] ★★ Kafka 的分区、副本、消费者组和 Offset 分别是什么？
  - **完整回答：**
    - Kafka Topic 是逻辑消息集合，分区是 Topic 的物理并行日志单元，每条消息写入某个分区并获得单调递增的 offset。
    - 分区带来两件事：一是同一分区内保持追加顺序，二是不同分区可以分布在多个 Broker 上并行读写；代价是跨分区没有全局顺序，同一业务键要用稳定 key 路由到同一分区。
    - 副本是分区的数据冗余，每个分区有 Leader 负责读写，Follower 从 Leader 复制，ISR 表示跟得上的同步副本集合；`acks`、`min.insync.replicas` 和副本数共同影响可靠性、可用性和延迟。
    - 消费者组是一组共享消费进度的消费者，同一组内一个分区同一时刻通常只分配给一个消费者，所以组内是负载均衡；不同消费者组拥有各自 offset，可以独立消费同一 Topic，实现多下游订阅。
    - Offset 是消费者在分区日志中的位置，提交 offset 代表消费进度推进。
    - 自动提交简单但可能在业务未完成时提交导致丢处理，手动提交能控制语义但要处理重复和重平衡。
    - 消费者加入、退出、宕机或分区变化会触发 rebalance，分区重新分配期间可能短暂停顿，处理中的消息如果没有妥善提交，就会重复消费。
    - 验证 Kafka 消费正确性要同时看 lag、提交位置、再均衡日志、重复处理率和业务幂等结果。
  - **原理解析：**
    - 分区是 Kafka 的基本日志单元：消息写入某个 partition 后得到递增 offset，同一分区内有序，跨分区只并行不保证全局顺序。业务要按 key 固定路由，才能让同一实体的事件落在同一条日志里。
    - 副本解决可靠性和高可用：每个分区有 Leader 处理读写，Follower 复制日志，ISR 代表跟得上的副本集合。`acks`、副本数和 `min.insync.replicas` 决定生产确认要等到什么复制程度，也决定故障时可能牺牲延迟还是可用性。
    - 消费者组让同一组内多个消费者分摊分区，不同组各自保存 offset 并可独立回放同一 Topic。提交 offset 只是推进这个组的消费进度，不会删除 Kafka 日志；提交太早会丢处理，提交太晚会重复。
    - 记忆抓手：partition 管并行和局部顺序，replica 管容灾，group 管负载均衡和多订阅，offset 管进度。重平衡时分区重新分配，最容易暴露重复消费和提交时机问题。

- [ ] ★★ RabbitMQ、Kafka 和 RocketMQ 如何选型？
  - **完整回答：**
    - 选型应从业务语义和运维现实出发，而不是只看性能排名。
    - RabbitMQ 是传统消息代理模型，Exchange、Queue、Binding 支持 direct、topic、fanout 等灵活路由，ack/nack、死信、TTL、优先级等机制成熟，适合任务队列、复杂路由、中等吞吐和需要较低使用门槛的业务系统；但长期海量堆积、高吞吐流式回放不是它的主要优势，新版本队列类型如 quorum queue 的可靠性和性能取舍也要评估。
    - Kafka 是高吞吐分布式日志，适合日志采集、行为事件、数据管道、流处理和多消费者组回放，保留策略使消息可重复消费，分区扩展能力强；它不擅长复杂 Broker 侧路由、任意延迟级别任务调度或传统命令式任务分发，单分区顺序和分区数也会限制并行度。
    - RocketMQ 常用于业务消息场景，顺序消息、延迟消息、事务消息和消费重试能力工程化较完整，在国内 Java 生态和阿里系云服务中常见；不同版本、部署形态和客户端语言能力要具体确认。
    - 若业务是订单、支付、库存等事件驱动，三者都能做，但关注点不同：RabbitMQ 看路由和确认，Kafka 看吞吐、回放和生态，RocketMQ 看业务消息能力和团队经验。
    - 已有稳定 MQ 基础设施时优先复用，只有当吞吐、回放、事务、顺序、延迟、成本或运维能力无法满足关键目标时再迁移。
  - **原理解析：**
    - 选型先看消息生命周期需要什么：如果需要复杂交换机路由、任务队列、ack/nack、TTL、死信和较低接入成本，RabbitMQ 更贴近传统 Broker；如果需要高吞吐日志、分区并行、多消费者组独立 offset 和历史回放，Kafka 更合适。
    - RocketMQ 更偏业务消息工程化，常见诉求是顺序消息、延迟消息、事务消息、消费重试和 Java 生态集成。它不是 Kafka 的简单替代，也不是 RabbitMQ 的性能版，重点在业务语义和部署经验。
    - 失败边界也不同：RabbitMQ 长期大堆积和流式回放不是强项；Kafka 复杂路由、任意延迟调度和单消息任务模型不占优；RocketMQ 要确认版本、客户端、云厂商形态和团队运维能力。
    - 记忆抓手：RabbitMQ 看路由，Kafka 看日志，RocketMQ 看业务消息。最终选择要落到吞吐、延迟、顺序、事务、回放、成本、团队经验和已有基础设施，而不是只报一个“性能最好”。
