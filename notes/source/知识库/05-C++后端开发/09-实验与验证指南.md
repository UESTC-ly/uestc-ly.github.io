# 实验与验证指南

学习后端开发的关键不是“看懂”，而是让概念在可控实验中产生可观察结果。本篇给出统一实验方法，适用于 C++ 并发、网络服务、Redis、消息队列、搜索与分布式系统。

## 1. 实验的四类问题

每次实验先声明要回答哪类问题：

1. **正确性**：输入、状态转换和输出是否符合协议或业务不变量？
2. **可靠性**：依赖失败、进程退出、重复或超时后，系统能否保持已声明的语义？
3. **性能**：在指定环境和负载下，吞吐、延迟和资源使用怎样变化？
4. **可运维性**：出现异常时，日志、指标和 trace 能否在目标时间内定位到组件和原因？

不要用一类证据替代另一类：压测不证明业务正确，单元测试不证明故障恢复，CPU 火焰图也不证明数据一致。

## 2. 可复现实验环境

### 环境清单

报告至少记录：

```text
OS / kernel:
CPU / NUMA / virtualization:
Memory / swap / cgroup limit:
Disk / filesystem:
Network topology and bandwidth:
Compiler and build type:
Service and client configuration:
Dataset generator and random seed:
Test command and duration:
```

网络、内核调度、文件系统和容器限制都会影响结果。macOS 上的功能实验不能直接代表 Linux epoll 行为；本地容器内的组件吞吐也不能外推生产集群。

### 构建矩阵

| 构建 | 目的 | 典型设置 |
| --- | --- | --- |
| Debug | 调试、断言、快速定位 | 符号完整、低优化、严格警告 |
| ASan/UBSan | 越界、UAF、部分未定义行为 | 独立构建，保留符号 |
| TSan | 数据竞争 | 单独运行，负载不必追求性能 |
| Release | 性能与部署候选 | 优化开启、保留可剖析符号 |

Sanitizer 会显著改变时间和内存行为，因此它的性能数字不能当作 Release 性能结论。反过来，Release 跑得快也不能替代 Sanitizer 检查。

## 3. 正确性实验

### 从不变量开始

例：有界队列的不变量可以写成：

- `0 <= size <= capacity`；
- 关闭后不再接受新元素；
- 已接受元素要么被消费，要么以规定方式取消；
- 消费者不会读到未构造对象；
- 所有等待线程最终被关闭操作唤醒。

测试应围绕不变量产生并发操作，而不是只检查某个固定执行顺序。

### 协议解析

长度字段协议至少覆盖：

- 完整帧、逐字节输入和随机分片；
- 多帧粘在一次输入；
- 头不完整、体不完整；
- 长度为零、刚好等于上限、超过上限；
- 加法溢出、未知版本/类型、随机字节；
- 合法帧之后跟非法帧；
- 解析错误后连接是关闭还是能够重新同步。

性质测试：同一字节序列无论如何分片，得到的完整消息序列必须相同。

### 状态机

把文档任务、订单、连接或熔断器的状态转换写成表：

| 当前状态 | 事件 | 新状态 | 副作用 | 重复事件结果 |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |

测试所有允许和禁止转换。并发状态更新使用条件写或版本号，断言只有一个竞争者成功。

## 4. 并发实验

### 常见注入方法

- 在读取共享状态和写入之间插入 barrier，放大竞态窗口。
- 随机让线程 yield 或短暂停顿，改变调度顺序。
- 在线程池关闭与提交任务同时发生时重复运行。
- 在定时器触发、取消和对象销毁之间建立竞争。
- 让 worker 在连接关闭后才返回结果，检查代数/状态校验。

仅靠 `sleep` 组织测试容易慢且不稳定；优先使用 latch/barrier/condition variable 明确控制到达点。

### 死锁排查

出现挂起时记录线程栈，检查：

- 多把锁的获取顺序是否一致；
- 条件变量谓词是否可能永远不成立；
- 持锁线程是否在做阻塞 I/O、等待 future 或 join；
- 线程池中的任务是否等待同一个已耗尽线程池执行子任务；
- 关闭路径是否先销毁了负责唤醒的对象。

### 竞态证据

TSan 报告提供冲突访问栈，但修复仍要回到不变量和所有权。单纯把字段改成 atomic 可能消除数据竞争，却保留“检查后执行”业务竞态。

## 5. 网络实验

### 流量形态

分别模拟：

- 短连接突发；
- 大量低活跃长连接；
- 小请求/小响应；
- 小请求/大响应并让客户端慢读；
- 连接建立后不发送完整请求；
- 同一连接 pipeline 多请求；
- 半关闭、RST、超时和客户端进程崩溃。

### 需要观察的层次

| 层次 | 信号 |
| --- | --- |
| 应用 | 当前连接、在途请求、buffer 字节、队列、错误码 |
| Runtime | 线程状态、锁等待、分配和回调延迟 |
| 系统调用 | accept/read/write/epoll_wait 的次数、错误和耗时 |
| TCP | listen 队列、重传、RTT、各连接状态 |
| 主机 | CPU、上下文切换、软中断、内存、带宽 |

一次请求慢可能来自入口排队、事件循环没被调度、输出缓冲、TCP 重传或客户端不读。只看业务函数耗时会漏掉这些时间。

## 6. Redis 和数据库实验

### 缓存故障

构造一个热点 key 同时过期，让大量请求回源。比较：无保护、互斥重建、逻辑过期、随机 TTL 和预热。记录缓存 QPS、回源并发、数据库延迟、等待请求数和失败率。

对大 key 测试时记录命令耗时、网络响应大小、事件循环阻塞和删除影响。不要只记录 key 占用字节。

### 一致性时间线

并发执行读缓存、查数据库、更新数据库和删除缓存，并在每个步骤前后注入暂停。记录哪些交错能把旧值重新写回缓存，再验证版本号、短 TTL、CDC 或对账怎样缩小/修复窗口。

### 数据库实验

- 用不同数据分布读取执行计划，比较估算行数与实际行数。
- 两个会话复现丢失更新、写偏差或锁等待。
- 故意持有长事务，观察 MVCC 版本、锁和清理影响。
- 缩小连接池，测池等待；扩大连接池，观察数据库是否因并发上升变慢。
- 模拟主从延迟，验证读己之写策略。

## 7. 消息队列实验

### 可靠性断点

在以下位置杀死消费者：

1. 收到消息后、业务前；
2. 数据库提交前；
3. 数据库提交后、offset/ack 前；
4. offset/ack 后、日志/指标/下游通知前。

同步请求还应单独测试“服务端业务提交后、客户端响应写回前崩溃”，它解释了为什么客户端超时后不能假定写入没有发生。

记录消息是否重投、业务是否重复、幂等记录与业务变更是否处于同一事务。第三个断点是检验“至少一次 + 幂等”的关键场景。

### 积压实验

逐步降低消费者处理率或让下游变慢，观察 backlog 条数和最老消息年龄。然后恢复容量并计算实际清空速度：

```text
net_drain_rate = consume_rate - produce_rate
estimated_drain_time = backlog / net_drain_rate
```

若净清空率小于等于零，系统不会自行恢复。扩消费者前检查分区数、热点分区、GPU/DB/搜索下游和重试流量。

### 毒消息

发送一个确定性失败输入，确认它不会无限占用同一分区：错误分类、有限重试、死信、告警、修复后重放和审计都要验证。

## 8. 搜索质量实验

### 离线集合

准备代表真实业务的查询和相关文档标注，包含短查询、长自然语言、专有名词、拼写变化、时间/租户过滤和“无正确答案”。训练/调参查询与最终评估查询分离，避免只对少数示例过拟合。

### 分层评估

- 召回：Recall@K，正确文档是否进入候选。
- 排序：MRR、NDCG 等，正确结果是否靠前。
- 系统：P50/P95/P99、超时和资源成本。
- 安全：租户/ACL 过滤是否始终成立。
- 新鲜度：更新后多长时间可搜索，旧版本何时消失。

比较 BM25、向量、RRF 融合和重排模型时使用同一集合与过滤条件。展示平均值之外，还要分析失败查询类型。

## 9. 分布式故障实验

### 超时不确定性

让服务端在提交业务后延迟响应，客户端先超时。验证客户端直接重试是否造成重复，幂等键或操作状态查询如何恢复确定性。

### 网络分区与慢节点

完全断网不是唯一故障；延迟、丢包、单向通信和慢磁盘更常造成超时与误判。观察健康检查、熔断、选举、重试和连接池如何相互作用，防止把慢依赖的工作转移成大量重试。

### 时间问题

模拟墙上时钟回拨/跳跃，检查 TTL、Snowflake ID、租约和日志排序。时长测量使用单调时钟；跨节点绝对时间只在同步误差假设内有意义。

## 10. 性能实验

### 延迟分布

平均延迟会隐藏少量极慢请求。至少报告 P50、P95、P99 和错误率，并说明样本量。协调遗漏（压测客户端因服务变慢而少发请求）会低估真实排队延迟，应使用能维持预定到达率或明确说明闭环模型的工具。

### 饱和点

阶梯增加负载，记录吞吐、延迟、错误、队列和资源：

```text
低负载：吞吐随负载增长，延迟稳定
接近饱和：某项利用率/队列增长，尾延迟上升
过载：吞吐不再增长甚至下降，超时和重试放大
```

系统安全容量应低于拐点，并为单实例故障、发布和流量突发留余量。

### 剖析闭环

1. 用指标定位 CPU、等待、内存、网络或下游方向；
2. 用 `perf`、火焰图、heap profile、锁/系统调用证据缩小范围；
3. 提出可证伪假设；
4. 做最小修改；
5. 在相同环境复测正确性与性能；
6. 检查是否把成本转移到尾延迟、内存或其他组件。

## 12. 常见无效结论

- “跑了一小时没崩，所以线程安全”：随机运行没有覆盖所有交错。
- “QPS 提高，所以优化成功”：可能牺牲了错误率、数据正确性、内存或 P99。
- “消息没丢”：如果没有在 ack/commit 边界注入崩溃，证据不足。
- “缓存一致”：没有枚举并发时间线和删除失败窗口。
- “支持优雅关闭”：只测试空载退出，没有测试长请求、长连接和截止时间。
- “高可用”：部署多副本但没验证共享依赖、容量、切换和恢复数据。

## 13. 最终检查

- [ ] 实验问题、假设和停止条件明确。
- [ ] 环境、配置、数据和命令可复现。
- [ ] 同时记录结果、错误和资源指标。
- [ ] 正常、边界、并发和故障路径均覆盖。
- [ ] 结论没有超出实验能够证明的范围。
- [ ] 失败实验也保留记录，并说明它推翻了什么假设。
- [ ] 修复后使用同一故障场景回归。
