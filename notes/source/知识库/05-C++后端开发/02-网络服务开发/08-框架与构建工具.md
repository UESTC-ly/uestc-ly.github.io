# 框架与构建工具

## 学习目标

- 理解 brpc、gRPC、Boost.Asio、Drogon/oatpp 的定位与选型。
- 知道框架学习应抓架构和边界，不背 API 细节。
- 理解 CMake、Conan、vcpkg 的职责。
- 能写出最小 CMake 示例，并知道何时查官方文档。

## 核心原理

### 框架定位

| 工具/框架 | 定位 | 适合场景 | 关注点 |
| --- | --- | --- | --- |
| brpc | C++ RPC 框架 | 高性能内部服务、百度系生态经验 | 协议支持、bthread、服务治理能力 |
| gRPC | 跨语言 RPC 框架 | 多语言微服务、IDL 优先、HTTP/2 | Protobuf、deadline、streaming、负载均衡 |
| Boost.Asio | 异步 IO 基础库 | 自定义协议、底层网络库、跨平台 IO | executor、异步模型、生命周期 |
| Drogon | C++ HTTP 应用框架 | Web API、HTTP 服务 | 路由、中间件、ORM、异步处理 |
| oatpp | C++ Web/API 框架 | REST API、DTO、OpenAPI 风格 | 组件体系、序列化、接口描述 |

选型时先问：

- 是内部 RPC 还是对外 HTTP API？
- 是否需要跨语言？
- 是否已有 IDL 和服务治理体系？
- 团队是否能维护异步生命周期复杂度？
- 性能瓶颈在框架层还是业务/存储/下游？

### 工作模型对比

brpc 的学习重点是 bthread、Controller、Channel、服务注册和内置治理能力；gRPC 的学习重点是 `.proto` 生成 stub、Channel、CompletionQueue/同步 API、deadline 和 status；Boost.Asio 的学习重点是 `io_context`、executor、异步操作回调和对象生命周期；Drogon/oatpp 更偏 HTTP 应用层，重点是路由、中间件、请求上下文和异步响应。

框架不是只替你调用 socket。它决定线程模型、回调在哪个线程执行、取消如何传播、连接何时关闭、错误如何映射到 status，以及指标和 tracing 如何接入。

### 不背 API 的学习方式

框架 API 会演进，面试和工程更看重：

- 事件循环或线程模型。
- 连接和请求生命周期。
- 超时、取消、重试和错误模型。
- 序列化和兼容策略。
- 观测性与调试手段。
- 与构建系统和部署环境的集成。

版本敏感内容以官方文档为准，不在笔记里写死未经核实的版本号。

### 选型边界

如果服务需要跨语言、强 IDL 和统一 deadline/status，gRPC 通常更容易标准化。如果团队主要做 C++ 内部服务，并且已有 brpc 运维经验，brpc 的生态能力可能更贴合。如果协议非常定制，Boost.Asio 或直接 epoll 更利于控制细节，但生命周期难度也更高。如果只是对外 REST API，Drogon/oatpp 能减少样板代码。

任何选择都要检查 TLS、流式传输、负载均衡、健康检查、观测、包管理、CI 构建时间和团队熟悉度。

### CMake 的职责

CMake 是构建系统生成器，用来描述 target、源码、依赖、编译选项和安装规则。现代 CMake 推荐围绕 target 建模，而不是全局堆变量。

最小示例：

```cmake
cmake_minimum_required(VERSION 3.20)
project(net_demo LANGUAGES CXX)

add_executable(net_demo main.cpp)
target_compile_features(net_demo PRIVATE cxx_std_17)
target_compile_options(net_demo PRIVATE -Wall -Wextra -Wpedantic)
```

引入依赖时优先使用 target：

```cmake
find_package(Protobuf CONFIG REQUIRED)
target_link_libraries(net_demo PRIVATE protobuf::libprotobuf)
```

具体 package 名称和 target 名称以依赖官方文档或包管理器生成结果为准。

### CMake target 传播规则

`PUBLIC` 表示当前 target 和依赖它的 target 都需要该属性；`PRIVATE` 只影响当前 target；`INTERFACE` 只影响使用者。头文件 include 目录、编译特性和链接库传播错误，会导致“本机能编、CI 不能编”或无关 target 被污染。

```cmake
target_include_directories(net_core PUBLIC include)
target_compile_features(net_core PUBLIC cxx_std_20)
target_link_libraries(server PRIVATE net_core)
```

这里 `server` 会继承 `net_core` 的 public include 目录和 C++ 标准要求，但不会继承 `net_core` 的 private 编译选项。

### Conan 与 vcpkg

| 工具 | 职责 | 典型价值 |
| --- | --- | --- |
| Conan | C/C++ 包管理，强调 profile、二进制包和私有仓库 | 企业内依赖治理、跨平台构建 |
| vcpkg | C/C++ 包管理，和 CMake 集成方便 | 快速获取开源依赖、manifest 模式 |

包管理器解决依赖获取、版本锁定、编译选项和传递依赖问题，但不能替代架构选型。

### Conan/vcpkg 的工程取舍

Conan 的 profile 能明确编译器、标准库、构建类型和选项，适合企业内二进制缓存和私有依赖治理。vcpkg manifest 模式上手快，和 CMake toolchain 集成直接，适合快速引入常见开源库。两者都需要锁定版本、固定 triplet/profile，并在 CI 中复现同样配置。

## 工程实践/示例

### 框架选型简表

| 需求 | 优先考虑 |
| --- | --- |
| 多语言服务调用，IDL 优先 | gRPC |
| C++ 内部高性能 RPC，已有 brpc 生态 | brpc |
| 自定义 TCP 协议或网络库练习 | Boost.Asio 或直接 epoll |
| 对外 REST API，想快速完成 Web 服务 | Drogon/oatpp |
| 学习 Linux 网络底层 | 先手写 socket/epoll，再看框架 |

### CMake 项目结构

```text
net-demo/
  CMakeLists.txt
  src/
    main.cpp
  include/
    net_demo/
      server.h
```

示例：

```cmake
cmake_minimum_required(VERSION 3.20)
project(net_demo LANGUAGES CXX)

add_library(net_core
    src/server.cpp
)
target_include_directories(net_core PUBLIC include)
target_compile_features(net_core PUBLIC cxx_std_17)

add_executable(net_demo src/main.cpp)
target_link_libraries(net_demo PRIVATE net_core)
```

### 使用框架前的检查清单

- 官方文档是否覆盖当前平台和编译器？
- 是否支持需要的协议、TLS、超时、取消和监控？
- 异步回调中的对象生命周期如何管理？
- 是否能和现有日志、配置、指标系统集成？
- 测试如何写：单元测试、集成测试、fake server、压测？

## 故障排查/观测

### 框架接入问题

框架接入最常见的问题不是 API 写错，而是线程模型误解：回调在哪个线程执行、是否允许阻塞、对象能否在回调返回前销毁、取消后是否还会回调。接入新框架时先写最小 echo/hello 服务，验证启动、关闭、超时、错误 status、日志 trace 和压测行为。

### 构建问题

CMake 找不到包时，先看 `CMAKE_PREFIX_PATH`、toolchain file、包管理器生成的 config 文件和 target 名称。链接错误要区分头文件可见但库未链接、ABI/编译选项不一致、Debug/Release 混用和传递依赖缺失。不要通过全局 `include_directories` 和 `link_directories` 临时修补，除非能解释影响范围。

## 推导示例

### 从 echo server 对比框架

同一个 echo 服务可以用不同框架验证工作模型：gRPC 关注 `.proto` 方法、deadline 和 status；Asio 关注 async read/write 和 handler 生命周期；Drogon/oatpp 关注 HTTP route、request object 和 response callback；brpc 关注 Controller、Channel 和 bthread 调度。比较时记录线程数、回调线程、关闭流程和错误映射，比单看 QPS 更有价值。

### CMake 依赖定位

当 `find_package(Protobuf CONFIG REQUIRED)` 失败时，不要马上改源码 include 路径。先确认包管理器是否安装了 Protobuf，toolchain file 是否传给 CMake，生成目录里是否存在 `ProtobufConfig.cmake`，以及官方导出的 target 名称是否真是 `protobuf::libprotobuf`。不同包和版本的 target 名称可能不同，以实际 config 和官方文档为准。

### 如何讲框架选型

选型回答应先给业务约束：内部 RPC 还是外部 HTTP，是否跨语言，是否需要流式传输、deadline、取消、观测和服务治理。然后再比较 brpc、gRPC、Asio、Drogon/oatpp 的工作模型和维护成本，不要只引用 benchmark。

### 最小验收清单

- 能画出框架线程和回调模型。
- 能说明超时、取消和错误映射。
- CMake 依赖使用 target-based 写法。
- 包管理器版本和 profile/triplet 在 CI 固定。

## 常见误区

- 为了简历引入重量级 RPC 框架，但业务只是简单 HTTP API。
- 只看框架 QPS benchmark，不看团队维护成本。
- 在 CMake 里用全局 include/link 变量污染所有 target。
- 包管理器版本未锁定，CI 和本机依赖不一致。
- 学框架只背接口，不理解线程模型和生命周期。
