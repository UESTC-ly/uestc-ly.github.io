# Linux 系统编程

## 学习目标

- 理解系统调用、文件描述符、进程、线程、信号和虚拟内存。
- 能用 Linux 工具观察程序真实行为。
- 为后续 Socket、epoll、零拷贝和性能分析建立模型。

## 核心原理

Linux 系统编程的关键是把 C++ 代码和内核对象对应起来：fd 是进程表项，线程共享地址空间和 fd 表，信号是受限异步通知，页缓存和虚拟内存会改变 I/O 与内存观测结果，调度决定代码何时真正运行。

## 1. 用户态、内核态与系统调用

应用通过系统调用请求内核执行文件、网络、进程和内存管理。系统调用有切换与检查成本，但性能问题通常来自更大的因素：阻塞等待、数据复制、上下文切换、缓存失效或过多小调用。优化前应测量。

Linux 将许多 I/O 对象暴露为 fd。fd 是进程文件描述符表中的整数索引，不是永久身份：关闭后数值可被快速复用。因此异步事件必须同时用连接对象生命周期、代数/序号或事件循环线程约束来防止“旧事件操作新连接”。

### 系统调用返回值的状态含义

系统调用返回值经常同时表达“完成了多少”和“下一步该怎么做”。`read` 返回正数是本次复制到用户缓冲区的字节数；返回 0 在 pipe/socket 上常表示 EOF 或对端关闭；返回 -1 时再看 `errno`。`write` 返回正数只代表内核接受了这部分数据，不代表文件已落盘或对端应用已处理。

对后端工程更重要的是把这些返回值接入状态机：`EINTR` 继续当前操作，`EAGAIN` 等待下一次就绪事件，`ENOMEM/EMFILE` 触发容量保护，其他永久错误关闭当前资源并保留诊断上下文。

常用观察工具：

```bash
strace -f -tt -T ./server       # 系统调用、耗时与子线程/进程
lsof -p <pid>                   # 进程打开的文件与 Socket
ls -l /proc/<pid>/fd            # fd 视图
cat /proc/<pid>/limits          # 资源限制
ss -lntp                        # 监听 TCP Socket
```

## 2. 进程与线程

进程拥有独立虚拟地址空间和资源视图；同一进程的线程共享地址空间、堆、全局对象和 fd 表，但有独立栈、寄存器和调度状态。

`fork()` 逻辑上复制进程，内存通常采用写时复制。多线程程序在 `fork` 后到 `exec` 前只能安全调用受限的 async-signal-safe 函数，否则可能继承“已加锁但持锁线程不存在”的状态。服务进程通常在启动线程前 fork，或 fork 后立即 exec。

守护进程/服务管理优先交给 systemd 或容器运行时，不必重复实现传统 double-fork。应正确处理标准输出、退出码、健康检查和终止信号。

### 进程、线程与 fd 表

线程共享 fd 表，所以一个线程 `close(fd)` 会影响同进程其他线程。若另一个线程还在 epoll 事件里保存这个整数，fd 被复用后可能误操作新连接。解决方法不是“close 前加一把全局锁”这么粗暴，而是让 fd 的所有操作归属到固定事件循环，跨线程只投递命令。

`fork()` 后子进程继承打开的 fd。忘记关闭无用 pipe 端会让读端永远等不到 EOF；忘记设置 `FD_CLOEXEC` 会让被 `exec` 的子进程意外继承监听 socket、日志文件或数据库连接。网络服务创建 fd 后通常立即设置 `O_CLOEXEC` 或 `FD_CLOEXEC`。

## 3. 信号

信号是异步通知，不适合在处理函数中执行复杂逻辑。常见做法：

- 处理函数只设置 `sig_atomic_t` 标志或写入 self-pipe/eventfd；
- 主事件循环收到可读事件后执行正常关闭流程；
- Linux 也可用 `signalfd` 把信号纳入事件循环；
- 忽略或处理 `SIGPIPE`，网络写入仍要检查 `EPIPE`。

信号处理函数中不要加普通互斥锁、分配内存、写复杂日志或调用非 async-signal-safe 函数。

### 信号与事件循环

self-pipe 和 `eventfd` 的目的都是把异步信号转换成普通 fd 可读事件。信号 handler 只写一个字节或设置标志，事件循环随后在正常线程上下文里执行停止 accept、连接排空和资源释放。这样可以避开 handler 中调用非 async-signal-safe 函数的风险。

`SIGPIPE` 是网络服务常见坑：忽略信号不等于写入成功，`send` 仍可能返回 `-1/EPIPE`。正确处理是忽略或屏蔽进程终止行为，同时在写路径把 `EPIPE/ECONNRESET` 转成连接关闭。

## 4. 文件 I/O 与缓存

`read`/`write` 可能短读短写，被信号中断返回 `EINTR`，或在非阻塞模式返回 `EAGAIN/EWOULDBLOCK`。调用方需要循环和状态机，不能假设一次完成。

页缓存使普通文件 I/O 看起来很快：写成功通常表示数据进入内核缓存，不必然已持久化到介质。需要持久性语义时研究 `fsync`/`fdatasync`、文件系统和存储设备的保证，以及“先写临时文件—同步—原子 rename—同步目录”的更新模式。

| 技术 | 减少的成本 | 边界 |
| --- | --- | --- |
| `mmap` | 显式 read/write 与部分复制 | 缺页、映射失效、错误处理复杂 |
| `sendfile` | 文件到 Socket 的用户态搬运 | 适用对象和平台有约束 |
| `splice` | 某些 fd 间数据搬运 | 组合复杂、需测量收益 |
| direct I/O | 绕过页缓存 | 对齐、设备特性和应用缓存复杂 |

“零拷贝”是减少某些数据复制/上下文切换，不代表完全没有复制，也不保证一定更快。

### mmap、页缓存和零拷贝边界

`mmap` 把文件页映射进进程地址空间，访问时可能触发缺页，由内核把文件内容调入页缓存并建立页表映射。它适合随机读、共享映射或减少一次用户态缓冲复制；但错误路径更复杂，例如文件被截断后访问映射区域可能触发 `SIGBUS`。

`sendfile` 常用于静态文件发送，减少“内核 -> 用户缓冲 -> 内核 socket 缓冲”的搬运。它的收益受文件类型、TLS、内核版本、网卡能力和缓存命中影响。开启 TLS 后，数据通常需要进入加密路径，具体能否减少复制取决于框架和内核能力，不能简单套用普通明文 TCP 结论。

## 5. 虚拟内存

进程地址空间通过页表映射到物理页或其他后备存储。常见概念：

- 栈适合自动生命周期的小型局部对象；大对象和深递归可能耗尽线程栈。
- 堆分配由分配器管理；释放给分配器不保证立即归还操作系统。
- 缺页分为可快速建立映射的 minor fault 与需存储 I/O 的 major fault。
- RSS 是驻留物理内存近似值；VIRT 大不等于真正占用同等物理内存。
- OOM、swap 和内存压力会造成显著尾延迟，应结合 cgroup/容器限制观察。

### 虚拟内存的状态变化

分配内存不一定立即得到物理页。进程可能先获得虚拟地址范围，真正读写时才触发缺页。写时复制也依赖这个机制：`fork()` 后父子进程共享只读物理页，直到某一方写入才复制页面。

工程上要区分：

- address space 增长：虚拟地址范围变大；
- RSS 增长：更多物理页驻留；
- page cache 增长：内核为文件缓存占用内存；
- allocator 保留：应用释放对象后分配器仍持有 arena。

因此“进程 VIRT 很大”不是单独结论；要结合 RSS、cgroup memory、page fault、swap 和分配器统计。

## 6. 调度、上下文切换和 CPU

线程在可运行、睡眠、不可中断等待等状态间切换。高 CPU 不一定是计算有效：自旋、锁竞争、频繁唤醒也会耗费 CPU。常用检查：

```bash
top -H -p <pid>
pidstat -p <pid> 1
perf stat -p <pid>
perf record -F 99 -g -p <pid>
```

CPU 亲和性和 NUMA 只应在测量证明跨核/跨节点访问是瓶颈后引入。绑定错误会造成负载不均或与容器 CPU 配额冲突。

## 7. 资源限制

后端常见资源上限：fd、进程/线程数、地址空间、锁定内存、cgroup CPU/内存限制、TCP 队列。提高上限不是完整修复：必须同时检查连接生命周期、泄漏、过载保护和监控。

服务要监控已用 fd、线程数、内存、连接状态、accept 错误和队列长度，并为 `EMFILE/ENFILE/ENOMEM` 设计受控失败行为。

## 故障排查/观测

### 从症状到工具

| 症状 | 优先观察 | 常见方向 |
| --- | --- | --- |
| fd 用尽 | `/proc/<pid>/fd`、`lsof`、accept 错误计数 | 连接泄漏、未关闭文件、TIME_WAIT 误判 |
| CPU 高 | `top -H`、`perf top/record` | 自旋、锁竞争、热函数、日志格式化 |
| 延迟长尾 | `pidstat`、`perf sched`、请求 trace | 阻塞 I/O、调度等待、major fault |
| 内存上涨 | RSS/cgroup、ASan/LSan、分配器统计 | 泄漏、缓存无界、连接积压 |
| 关闭卡住 | 线程栈、连接状态计数、fd 列表 | 有线程未唤醒、长事务、半关闭未处理 |

### 最小排查流程

先确认进程是否仍在接收流量，再看资源是否达到上限，最后定位代码路径。不要直接重启后宣称修复；重启只能释放现场。应保留当时的 fd 数、连接状态、线程栈、最近错误日志和关键指标，才能判断是泄漏、过载还是外部依赖阻塞。

## 推导示例

### 为什么 pipe EOF 依赖所有写端关闭

pipe 的读端只有在所有写端 fd 都关闭后才读到 EOF。父进程创建 pipe 后 fork，父子都会继承读写两端；如果子进程只负责读但忘记关闭自己的写端，即使父进程关闭写端，内核仍认为还有写者存在，子进程 `read` 就可能一直阻塞。

```text
pipe -> fork
parent: close read end -> write -> close write end
child: close write end -> read until 0
```

这个例子可以迁移到 socket 和日志文件：fork/exec 前没有清理 fd，会让资源生命周期跨进程延长，表现为端口占用、EOF 不出现或文件无法轮转。

### 为什么 mmap 访问可能在普通读写之外失败

`mmap` 成功只说明映射建立，不代表之后每次内存访问都不会失败。访问新页面时可能缺页；如果底层文件被截断，访问原映射范围可能触发 `SIGBUS`。因此 mmap 适合明确所有权和文件大小稳定的场景，不适合把错误处理简单包装成普通指针访问。

### 如何解释一次系统调用成本

系统调用成本不只是用户态/内核态切换。一次小 `write` 可能还包含参数检查、fd 查表、复制、锁、页缓存操作和调度影响。优化时先用 `strace -c` 看调用次数，再用 `perf` 看 CPU 栈，最后结合业务批量策略减少无意义小调用。

### 最小验收清单

- 能解释 fd 复用风险。
- 能说清 fork 后 fd 和锁的继承问题。
- 能区分 page cache、RSS 和虚拟地址。
- 能用工具证明瓶颈来自 CPU、I/O 还是调度。

## 常见误区

- fd 数字相同就代表同一连接：fd 可复用。
- `write` 返回成功就已落盘：通常只说明进入相应内核路径/缓存。
- 内存释放后 RSS 必然下降：分配器可能保留 arena 或碎片。
- 提高 fd 限制就解决连接问题：泄漏和过载仍存在。
- 信号处理函数就是普通回调：它有严格的异步安全限制。
