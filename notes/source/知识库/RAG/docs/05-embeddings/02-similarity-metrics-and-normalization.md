## “靠近”必须先定义尺子

上一章把嵌入描述为向量空间中的位置。但两个点是否接近，取决于使用哪把尺子。地图上
可以比较直线距离，也可以比较行进方向；向量检索同样可以比较方向、长度或两者的组合。

如果建立索引时按一种规则组织向量，查询时却按另一种规则理解分数，结果可能变化。度量
不是数据库旁边可随意切换的装饰选项，而是表示模型、归一化方法、索引结构和评估共同
组成的检索契约。

## 点积：方向与长度共同参与

两个同维向量的点积（dot product）是对应位置相乘后相加。对于二维向量：

`a = (a1, a2)`，`b = (b1, b2)`

点积为：

`a · b = a1 × b1 + a2 × b2`

例如 `a = (1, 0)`，`b = (0.8, 0.6)`，则点积为 `0.8`。若
`c = (2, 0)`，`a · c = 2`。

点积同时受到方向和向量长度影响。一个方向较接近但长度很大的向量，可能获得更大的点积。
这不一定是错误；某些模型就是按照这种比较方式训练和发布的。关键是遵循模型约定并用
自己的任务数据验证，而不是凭直觉认定某种度量永远更好。

## 余弦相似度：比较方向

余弦相似度（cosine similarity）把点积除以两个向量的长度：

`cos(a, b) = (a · b) / (||a|| × ||b||)`

其中 `||a||` 表示向量长度。对于非零向量，余弦相似度主要比较方向，减弱绝对长度的影响。

继续使用前面的向量：

- `a = (1, 0)` 的长度为 `1`；
- `b = (0.8, 0.6)` 的长度为 `1`；
- `c = (2, 0)` 的长度为 `2`。

于是 `cos(a, b) = 0.8`，而 `cos(a, c) = 1`。虽然 `c` 比 `a` 长一倍，它们方向完全
相同，因此余弦相似度为最高方向一致值。

余弦分数的数学范围和实际分布不是一回事。某个数据集的分数可能集中在很窄区间，不能
把别处使用的阈值直接搬过来。更不能把 `0.8` 解读成“答案有 80% 概率正确”。

## 欧氏距离：比较直线距离

欧氏距离（Euclidean distance，L2 distance）计算两个点之间的直线距离：

`distance(a, b) = sqrt((a1-b1)^2 + (a2-b2)^2)`

距离越小表示越接近，这与“相似度越大越接近”的排序方向相反。日志和接口必须标清字段
表示相似度还是距离，否则排查时很容易把最好结果当成最差结果。

对于 `a = (1, 0)` 和 `b = (0.8, 0.6)`，欧氏距离约为 `0.63`；对于 `a` 和
`c = (2, 0)`，距离为 `1`。在这个例子中，欧氏距离认为 b 更近，而余弦相似度认为 c
方向完全一致。两把尺子给出不同排序，正是因为它们回答的问题不同。

## L2 归一化：把向量缩放到单位长度

L2 归一化（L2 normalization）用向量除以自身长度，使非零向量的长度变为 `1`。

`normalize(a) = a / ||a||`

归一化后的 `(2, 0)` 变成 `(1, 0)`。当所有向量都做相同 L2 归一化后，点积与余弦
相似度的排序关系会变得紧密；欧氏距离也能与方向相似性建立对应关系。这种数学关系有助于
理解实现，但不代表可以忽略产品或模型的正式配置要求。

归一化需要注意四个边界：

1. **零向量不能直接除以长度。** 应明确拒绝、记录或采用有依据的处理策略。
2. **文档与查询要一致。** 只归一化一侧可能改变分数含义。
3. **索引与查询配置要一致。** 已建立的索引可能假定输入已归一化或由存储层处理。
4. **缓存键要包含配置。** 同一文本的原始向量与归一化向量不能共享模糊缓存条目。

## 一张比较表

| 度量 | 越大还是越小越接近 | 主要受什么影响 | 容易误解的地方 |
|---|---|---|---|
| 点积 | 通常越大越接近 | 方向和长度 | 长向量可能放大分数 |
| 余弦相似度 | 越大越接近 | 方向 | 分数不是正确概率 |
| 欧氏距离 | 越小越接近 | 位置差和长度 | 排序方向与相似度相反 |

表格只用于建立直觉。实际系统还可能使用由存储或模型定义的其他距离形式。采用前需要确认
模型建议、索引能力和评估结果三者是否一致。

## 一个排序例子：相似分数不是业务结论

用户查询“如何关闭账户”。候选包括：

- A：“关闭个人账户前请导出账单。”
- B：“暂时停用通知的方法。”
- C：“管理员可关闭企业子账户。”

向量分数可能把 A、C、B 依次排序。但如果当前用户是企业普通成员，A 可能属于错误产品，
C 可能描述管理员权限，B 虽然主题稍远却不回答问题。系统仍需用产品、角色和文档版本
过滤候选，并允许在证据不足时不回答。

阈值也不能解决全部问题。把最低相似度设得更高，可能减少弱相关候选，同时也可能丢掉
措辞不同但正确的资料。阈值需要在代表性查询集上观察召回、误召回和无答案行为。

## 怎样验证度量选择

一个轻量验证过程可以这样设计：

1. 收集一组真实或经过审查的查询；
2. 为每个查询标注允许作为证据的文本块，以及确实无答案的情况；
3. 固定嵌入版本，分别比较候选度量与归一化配置；
4. 记录正确证据是否出现在前 K 个候选中，也检查错误租户、旧版本和重复块；
5. 对差异案例逐条阅读，不只比较一个平均数；
6. 把最终配置和评估集版本写入表示契约。

这类评估只能支持“在当前数据和任务上表现如何”，不能证明对所有语言、领域和未来数据
都成立。

## 工程记录与排障

至少记录以下信息，才能解释一次检索：

- 嵌入模型与表示版本；
- 向量维度和是否归一化；
- 使用的度量及排序方向；
- Top-K、过滤条件和阈值；
- 候选分数、来源、版本和被过滤原因；
- 查询是否为空、被截断或使用了错误输入模式。

若分数突然整体漂移，先检查模型或预处理版本、归一化是否变化、索引是否混入不同版本，
再考虑修改阈值。直接调阈值可能暂时掩盖不兼容问题。

## 安全边界

高相似度不会自动绕过授权。权限过滤应与数据访问策略绑定，而不是通过一个相似度阈值
间接推断。恶意或被投毒的文本也可能与高价值查询高度相似，因此候选进入上下文前仍需
验证来源、适用范围和内容处理规则。

检索内容始终是数据，不是系统指令。分数再高，也不能让文本块获得修改系统规则、调用
工具或读取其他用户数据的权限。
