# 04 - 内存模型与淘汰策略

> 目标读者：想从“会用 Redis”进阶到“知道 Redis 为什么占内存、为什么会淘汰 key、怎么控制内存”的学习者。本文以 Redis 7.x 开源版为主；Redis 8.x 新增或云厂商特性会单独注明。

## 学习目标

学完本篇，你应该能够：

- 理解 Redis 内存主要花在哪里：数据、对象头、字典、编码结构、过期字典、客户端缓冲区、复制/AOF 缓冲区、内存碎片。
- 会使用 `INFO memory`、`MEMORY USAGE`、`OBJECT ENCODING` 等命令定位内存问题。
- 理解 `maxmemory` 与 `maxmemory-policy` 的作用边界。
- 能区分过期删除（expire）和内存淘汰（eviction）。
- 能为缓存、会话、排行榜、限流等场景选择合适淘汰策略。

---

## 核心概念

### 1. Redis 的内存不是只有 value

一个 key-value 在 Redis 中通常包含多层开销：

```text
数据库字典 dict
  └── key 对象（SDS 字符串）
      value 对象（redisObject）
        └── 具体编码结构（int / embstr / raw / listpack / quicklist / hashtable / skiplist ...）
```

因此，一个看起来很短的 key 和 value，也可能因为对象头、哈希表节点、内存分配器对齐等原因占用更多内存。

常见内存来源：

| 来源 | 说明 |
|---|---|
| 数据本身 | key、value、集合元素、列表元素等 |
| Redis 对象开销 | 类型、编码、LRU/LFU 信息、引用计数等元数据 |
| 字典开销 | Redis DB 主字典、哈希表 bucket、rehash 期间额外表 |
| 过期字典 | 设置 TTL 的 key 还会在 expires 字典中记录过期时间 |
| 客户端缓冲区 | 大查询、慢消费者、Pub/Sub、阻塞客户端可能占用大量内存 |
| 复制/AOF 缓冲区 | replication backlog、AOF buffer 等 |
| 内存碎片 | jemalloc / 系统分配器导致 `used_memory_rss` 高于逻辑数据内存 |

---

### 2. Redis 对象类型与底层编码

Redis 命令层看到的是 String、Hash、List、Set、ZSet、Stream 等类型；内部会根据数据大小和形态选择更省内存或更高性能的编码。

常见编码（Redis 7.x 视角）：

| 逻辑类型 | 常见编码 | 说明 |
|---|---|---|
| String | `int` / `embstr` / `raw` | 小整数可直接编码；短字符串常用 embstr；长字符串 raw |
| List | `quicklist` | 由多个紧凑节点组成，适合两端操作 |
| Hash | `listpack` / `hashtable` | 小 hash 用 listpack 省内存，大 hash 转 hashtable |
| Set | `intset` / `hashtable` | 全是整数且数量少时用 intset |
| ZSet | `listpack` / `skiplist` | 小 zset 用 listpack；大 zset 用 dict + skiplist |
| Stream | radix tree + listpack | 适合追加日志和消费组 |

查看编码：

```bash
OBJECT ENCODING mykey
MEMORY USAGE mykey
TYPE mykey
```

> 版本差异：Redis 早期文档常见 `ziplist`，Redis 7.x 中 Hash/ZSet 等小对象更多使用 `listpack`。阅读旧文章时要注意配置名和编码名变化。

---

### 3. 小对象聚合为什么省内存？

如果存 10 万个用户属性，有两种设计：

```text
方案 A：user:1:name, user:1:age, user:1:city ... 每个字段一个 key
方案 B：user:1 作为 hash，name/age/city 作为 field
```

方案 B 往往更省内存，因为：

- key 数量更少，主字典开销更低。
- 小 Hash 可能使用 `listpack` 紧凑编码。
- TTL 管理也更简单（但只能对整个 hash 设置 TTL，不能对单个 field 设置 TTL；Redis 7.x 开源版不支持 hash field 级 TTL）。

代价：

- 单个 field 不能独立过期。
- 大 hash 可能形成热点 key。
- 更新粒度和迁移策略要提前设计。

---

### 4. `maxmemory`：Redis 可用内存上限

`maxmemory` 用于限制 Redis 数据集使用的内存。当写入新数据导致内存超过限制时，Redis 根据 `maxmemory-policy` 决定淘汰 key 或返回错误。

```conf
maxmemory 4gb
maxmemory-policy allkeys-lru
```

运行时设置：

```bash
CONFIG SET maxmemory 4gb
CONFIG SET maxmemory-policy allkeys-lru
CONFIG GET maxmemory
CONFIG GET maxmemory-policy
```

注意：

- 64 位 Redis 默认 `maxmemory 0`，表示不主动限制数据集内存。
- `maxmemory` 不是进程 RSS 的绝对上限；客户端缓冲区、复制/AOF 缓冲区、碎片等会让进程实际占用更高。
- 开启复制或 AOF 时，应预留内存给 backlog / AOF buffer，避免到达上限后反复淘汰。

---

### 5. 过期删除 vs 内存淘汰

这两个概念经常混淆：

| 机制 | 触发条件 | 处理对象 | 目的 |
|---|---|---|---|
| 过期删除 expire | key 到达 TTL | 设置了过期时间的 key | 删除逻辑过期数据 |
| 内存淘汰 eviction | 内存超过 `maxmemory` | 取决于淘汰策略 | 释放内存给新写入 |

过期删除有两种主要方式：

- 惰性删除：访问 key 时发现过期再删除。
- 定期删除：Redis 后台周期性抽样检查过期 key。

内存淘汰则是在内存压力下，根据策略选择 key 删除。

## 淘汰策略（Redis 7.x）

配置项：

```conf
maxmemory-policy noeviction
```

Redis 7.x 开源版常用策略：

| 策略 | 候选 key | 淘汰规则 | 适合场景 |
|---|---|---|---|
| `noeviction` | 不淘汰 | 写入可能报 OOM 错误 | 数据不能被 Redis 自动丢弃 |
| `allkeys-lru` | 所有 key | 近似淘汰最近最少使用 | 通用缓存 |
| `volatile-lru` | 只有设置 TTL 的 key | 近似 LRU | 只允许淘汰缓存类 key |
| `allkeys-lfu` | 所有 key | 近似淘汰最低频使用 | 热点稳定的缓存 |
| `volatile-lfu` | 只有设置 TTL 的 key | 近似 LFU | 有 TTL 且热点稳定 |
| `allkeys-random` | 所有 key | 随机淘汰 | 访问分布接近均匀、低成本 |
| `volatile-random` | 只有设置 TTL 的 key | 随机淘汰 | 简单 TTL 缓存 |
| `volatile-ttl` | 只有设置 TTL 的 key | 优先淘汰 TTL 更短的 key | 希望快过期数据先走 |

> 版本差异：Redis 最新文档中可能出现 LRM（Least Recently Modified）策略，但它不属于 Redis 7.x 常规策略；写 Redis 7.x 配置时不要误用。

## 关键命令 / 配置

### 观察内存

```bash
# 内存总体情况
INFO memory

# 某个 key 的估算内存占用
MEMORY USAGE mykey
MEMORY USAGE myhash SAMPLES 0

# 内存统计细节
MEMORY STATS

# 内存诊断建议
MEMORY DOCTOR

# 查看对象编码和空闲时间 / 频率
OBJECT ENCODING mykey
OBJECT IDLETIME mykey       # LRU 策略下更有参考意义
OBJECT FREQ mykey           # LFU 策略下更有参考意义
```

常看指标：

| 指标 | 含义 |
|---|---|
| `used_memory` | Redis 分配器视角已用内存 |
| `used_memory_human` | 人类可读格式 |
| `used_memory_rss` | 操作系统看到的常驻内存 |
| `mem_fragmentation_ratio` | RSS / allocator used 的近似比值 |
| `mem_not_counted_for_evict` | 未计入淘汰判断的缓冲区内存 |
| `maxmemory` | 配置的数据集内存上限 |
| `evicted_keys` | 已淘汰 key 数量，来自 `INFO stats` |
| `expired_keys` | 已过期删除 key 数量，来自 `INFO stats` |

### 控制编码阈值

Redis 会根据阈值把小结构保持为紧凑编码，超过阈值后转为更适合大数据的结构。

```conf
hash-max-listpack-entries 512
hash-max-listpack-value 64

zset-max-listpack-entries 128
zset-max-listpack-value 64

set-max-intset-entries 512
```

实践建议：

- 不要为了省内存盲目调大阈值；紧凑编码在大对象上可能导致 CPU 开销增加。
- 调整前先构造真实数据压测 `MEMORY USAGE`、延迟和吞吐。

### 配置淘汰

```conf
maxmemory 4gb
maxmemory-policy allkeys-lru
maxmemory-samples 5

# LFU 相关
lfu-log-factor 10
lfu-decay-time 1

# 惰性释放，降低删除大 key 时的主线程阻塞风险
lazyfree-lazy-eviction no
lazyfree-lazy-expire no
lazyfree-lazy-server-del no
```

说明：

- `maxmemory-samples` 越大，LRU/LFU 近似越准确，但 CPU 成本更高。
- Redis 的 LRU/LFU 是近似算法，不是全局精确排序。
- `lazyfree-*` 能把部分释放工作放到后台线程，但也会改变内存回收的即时性，需要监控。

## 示例

### 示例 1：查看一个 key 的编码变化

```bash
HSET user:1 name alice age 18 city shanghai
OBJECT ENCODING user:1
MEMORY USAGE user:1

# 写入大量 field 后，可能从 listpack 转 hashtable
# 示例仅表达思路，不建议在生产直接压测大 key
```

观察点：小 Hash 通常更紧凑；变大后为了查询性能会转换编码。

---

### 示例 2：通用缓存配置

```conf
maxmemory 8gb
maxmemory-policy allkeys-lru
maxmemory-samples 5
```

适合：所有 key 都是缓存，丢了可以回源。

优点：简单，避免忘记设置 TTL 导致不可淘汰。  
风险：如果混入不能丢的数据，也会被淘汰。

---

### 示例 3：只淘汰带 TTL 的缓存 key

```conf
maxmemory 8gb
maxmemory-policy volatile-lru
```

适合：同一个 Redis 中混有“可淘汰缓存”和“不希望淘汰的数据”。

前提：所有可淘汰 key 必须设置 TTL。

风险：如果没有足够多 TTL key，Redis 可能无法释放内存，写入仍会报错。

---

### 示例 4：稳定热点读场景使用 LFU

```conf
maxmemory 8gb
maxmemory-policy allkeys-lfu
lfu-log-factor 10
lfu-decay-time 1
```

适合：热点相对稳定，例如热门商品、热门文章、公共配置。

不适合：热点快速变化且冷启动频繁的场景；LFU 计数有衰减，但仍需要观察命中率。

---

### 示例 5：区分过期和淘汰

```bash
INFO stats | grep -E 'expired_keys|evicted_keys'

SET cache:a 1 EX 10
# 10 秒后访问或后台任务清理，expired_keys 可能增加

# 当 used_memory 超过 maxmemory 且策略允许淘汰时，evicted_keys 增加
```

如果 `expired_keys` 很高，说明 TTL 数据自然过期多；如果 `evicted_keys` 持续增长，说明内存上限正在压迫数据集，需要评估容量、策略和命中率。

## 常见误区

### 误区 1：设置 TTL 就等于设置了内存上限

TTL 只说明 key 什么时候逻辑过期。过期前如果数据增长太快，仍可能打满内存。内存上限要靠 `maxmemory`。

### 误区 2：`maxmemory` 是 Redis 进程最大 RSS

`maxmemory` 主要用于数据集淘汰判断，不等于操作系统层面的进程内存硬限制。RSS 还受碎片、缓冲区、后台任务影响。

### 误区 3：LRU 是精确删除全局最久未访问 key

Redis 为了性能使用抽样近似 LRU。`maxmemory-samples` 会影响近似质量。

### 误区 4：`volatile-lru` 一定比 `allkeys-lru` 安全

如果缓存 key 忘记设置 TTL，`volatile-lru` 不会选择它，内存满时可能写入失败。安全的前提是 key 设计规范可靠。

### 误区 5：大 key 只是占内存多

大 key 还可能造成网络阻塞、删除阻塞、迁移阻塞、AOF/RDB 膨胀。应避免单个 Hash/List/Set/ZSet 过大。

### 误区 6：内存碎片高就一定是泄漏

碎片可能来自 jemalloc、数据频繁增删、fork Copy-on-Write、对象大小分布。先看趋势、RSS、allocator 指标和业务写入模式，再判断。

## 实践检查清单

### 建模阶段

- [ ] key 命名是否过长？是否包含重复冗余前缀？
- [ ] 是否可以把多个小 key 合并为 Hash，但不会形成难以维护的大 key？
- [ ] TTL 是按 key 维度还是 field 维度？Redis 7.x 是否满足需求？
- [ ] 数据是否可淘汰？如果不可淘汰，是否应该放在 Redis？
- [ ] 是否混用了缓存数据和关键状态数据？是否需要拆实例或拆 DB？

### 配置阶段

- [ ] 设置合理 `maxmemory`，为 OS、复制、AOF、客户端缓冲区预留空间。
- [ ] 选择明确的 `maxmemory-policy`，不要依赖默认值。
- [ ] 缓存实例优先考虑 `allkeys-lru` 或 `allkeys-lfu`。
- [ ] 混合实例如用 `volatile-*`，确保可淘汰 key 都有 TTL。
- [ ] 大 key 删除风险高时，评估 `lazyfree-*` 配置。

### 运行阶段

- [ ] 定期查看 `INFO memory`、`INFO stats`。
- [ ] 监控 `used_memory`、`used_memory_rss`、`mem_fragmentation_ratio`。
- [ ] 监控 `evicted_keys` 是否持续增长。
- [ ] 抽样检查大 key：`MEMORY USAGE`、`SCAN` + 类型命令。
- [ ] 观察命中率：`keyspace_hits` / (`keyspace_hits` + `keyspace_misses`)。
- [ ] 对重要业务做压测，验证淘汰后能否正确回源。

## 速记：策略怎么选？

```text
所有数据都可回源缓存     -> allkeys-lru
热点稳定、希望留住高频 key -> allkeys-lfu
只允许淘汰带 TTL 的 key   -> volatile-lru / volatile-lfu
希望快过期的先淘汰       -> volatile-ttl
数据绝不能被自动淘汰     -> noeviction，并做好容量保护
访问分布差不多且追求简单 -> allkeys-random
```
