Qwen2.5-VL 为什么要做 Window Attention 与 RMSNorm/SwiGLU 等高效化改造？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐ (3/5)

动态分辨率让模型看得清，代价是大图会产生大量 patch，ViT 全局注意力的计算量随 patch 数二次增长。Qwen2.5-VL（2025）从零训练了一个原生动态分辨率 ViT，在结构上做了两项改动[3]：

  1. 窗口注意力把大部分层的计算量降到线性。 32 层 ViT 里只有 4 层用全局自注意力，其余层都用窗口注意力，最大窗口 112×112，对应 8×8 个 patch，比这小的区域直接处理，不做填充[3]。大部分层只在局部窗口内算注意力，计算量随 patch 数线性增长，少数全局层保留全图视野。

  2. RMSNorm 和 SwiGLU 让 ViT 和 LLM 结构一致。 标准 ViT 用 LayerNorm 和 GELU，Qwen 系列 LLM 用 RMSNorm 和 SwiGLU，两边结构不统一。Qwen2.5-VL 的 ViT 也改用 RMSNorm 和 SwiGLU[3-5]，向 LLM 的结构靠拢，整体网络更简洁。

两项改动的目的相同，保住动态分辨率带来的细节，同时把大图的算力和工程开销压回可控范围。

面试速答：动态分辨率下大图的 patch 很多，全局注意力的开销随 patch 数二次增长。Qwen2.5-VL 的 ViT 只保留 4 层全局注意力，其余用最大 112×112 的窗口注意力，计算量近似线性；归一化和激活也换成 RMSNorm、SwiGLU，和 LLM 结构保持一致。

Qwen3 与 Qwen3.8 的公开架构分别有什么关键点？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐⭐ (5/5)

Qwen3 的稠密模型沿用 decoder-only Transformer：分组查询注意力（Grouped-Query Attention，GQA）、旋转位置编码（Rotary Position Embedding，RoPE）、预归一化（pre-norm）RMSNorm 和 SwiGLU 前馈层。相对 Qwen2，报告明确了去除 QKV bias 并引入 QK-Norm（将 \(q,k\) 归一化后再计算注意力，降低极端内积造成的训练不稳定）。

\[ \mathrm{Attn}(Q,K,V)=\mathrm{softmax}\left(\frac{\mathrm{Norm}(Q)\mathrm{Norm}(K)^\top}{\sqrt{d_h}}+M\right)V. \]

Qwen3 的 MoE 版本以更强的专家专业化与较低激活计算为目标，代价是专家并行（Expert Parallelism，EP）通信和负载均衡更关键：

  • 使用 128 个路由专家、每 token 选择 8 个专家，不使用 Qwen2.5 MoE 的共享专家，并使用全局批次的负载均衡损失。

Qwen3.8-2.4T-A95B 的当前配置为：

  • 2.4T 总参数、约 95B 激活参数、92 层、隐藏维 8192、512 个专家且每 token 路由 10 个再加 1 个共享专家；
  • 主干按三层 Gated DeltaNet 加一层 Gated Attention 的 3:1 节奏混合，含多 token prediction（MTP）模块。
  • 原生上下文是 262,144 token，可扩展到约 1M。

Qwen3-VL 将 T-RoPE 升级为文本时间戳对齐机制,这一改进如何实现？

文本时间戳对齐机制采用"时间戳-视频帧"交错的输入形式,实现帧级别的时间信息与视觉内容的细粒度对齐。

核心设计理念:

传统的 T-RoPE 使用绝对时间位置编码,而 Qwen3-VL 改用显式时间戳,将每一帧的时间信息以文本形式嵌入到输入序列中,格式如 <2.5 seconds><|vision_start|><frame><|vision_end|>。

时间戳计算实现:

在 Qwen3VLProcessor 中,通过 _calculate_timestamps 方法计算每帧的时间戳:

def _calculate_timestamps(self, indices: Union[list[int], np.ndarray], video_fps: float, merge_size: int = 2):
    if not isinstance(indices, list):
        indices = indices.tolist()

    # 确保帧数是 merge_size 的倍数,不足则填充
    if len(indices) % merge_size != 0:
        indices.extend(indices[-1] for _ in range(merge_size - len(indices) % merge_size))

    # 根据帧索引和 FPS 计算时间戳
    timestamps = [idx / video_fps for idx in indices]

    # 时间patch内取平均:因为帧会被 merge_size 合并
    # 所以取时间patch首尾帧的平均时间作为该patch的时间戳
    timestamps = [
        (timestamps[i] + timestamps[i + merge_size - 1]) / 2 
        for i in range(0, len(timestamps), merge_size)
    ]
    return timestamps

  1. 细粒度时间对齐: 每一帧都有明确的时间标记,模型能精确理解"在第5秒发生了什么"

  3. 时序推理增强: 显著提升事件定位、动作边界检测、跨模态时间问答等任务的性能
  4. 可解释性强: 时间信息以文本形式显式存在,便于调试和理解

Qwen3.5 的一个关键卖点是混合注意力：Gated DeltaNet + 全局注意力。请详细说说 Gated DeltaNet 属于哪类线性注意力，它是如何在保持表达能力的前提下降低复杂度的？3:1 的混合比例有什么技术考量？

Gated DeltaNet 可以理解为一种具备门控与增量状态更新的线性注意力 / SSM 变体，用于替代大部分标准自注意力层，核心目标是把计算和内存复杂度从 O(n²) 降到近似 O(n)。

  1. 基本思想：用“递归状态 + 门控”近似注意力 - 传统 Attention 要显式构造 n×n 的注意力矩阵，复杂度 O(n²)。 - Gated DeltaNet 将序列视为一个递归动态系统，每个 token 的表征依赖于前一时刻的“隐藏状态” hₜ₋₁ 和当前输入 xₜ：

    • hₜ = Gate(hₜ₋₁, xₜ) + Delta(xₜ)
      （这里 Gate 是门控函数，Delta 是增量更新）
    • 注意力“聚合历史信息”的效果被 状态 hₜ 的更新方程 近似实现，不再显式计算所有 token 两两之间的注意力得分。

  2. 门控机制的作用 - 引入类似 GRU/LSTM 的 update/reset gate，控制旧状态保留多少、新信息写入多少：

    • zₜ = σ(Wᶻ xₜ + Uᶻ hₜ₋₁)
    • hₜ = (1 − zₜ) ⊙ hₜ₋₁ + zₜ ⊙ ˜hₜ
    • 这样可以：
    • 减缓长序列中信息衰减问题；
    • 提升对“关键 token”长程依赖的建模能力，缓解纯线性注意力经常出现的“长程依赖缺失”问题。

Rectified Flow 如何定义直线路径

以噪声端点 \(z_n\) 和数据端点 \(z_d\) 为例，Rectified Flow 常用：

z_t=(1-t)z_n+t z_d, \qquad
\mathcal{L}_{\mathrm{RF}}
=\mathbb{E}\left[\left\lVert v_\theta(z_t,t,c)-(z_d-z_n)\right\rVert_2^2\right].

少步采样不能只看训练目标

RingAttention核心原理与作用

RingAttention 是一种面向超长序列处理的分布式注意力机制，通过环形分块计算和重叠通信，解决传统注意力机制因 \(O(n^2)\) 计算复杂度和显存占用而无法处理长序列（如100万token）的难题。其核心设计包括： - 环形分块：将输入序列切分为多个子块，分布在多个设备（GPU/TPU）上，形成环形拓扑。 - 块间通信：设备间按环形顺序传递键值（Key-Value）缓存，逐步累积全局注意力上下文。 - 重叠计算与通信：在计算当前块的同时，预取下一块的键值数据，隐藏通信延迟。

数学形式：
对第 \(i\) 个设备上的查询块 \(Q_i\) ，逐步接收并处理来自环上其他设备的键值块 \(\{K_j, V_j\}\) ，最终输出注意力结果：

\[\text{Output}_i = \sum_{j=0}^{P-1} \text{softmax}(Q_i K_j^T) V_j\]

其中 \(P\) 为设备数量。

RoPE Scaling、NTK-aware、YaRN 的长度外推直觉是什么？

RoPE 使用旋转频率注入位置信息。对位置 \(m\)，二维子空间旋转角为：

\[ m\theta_i \]

当推理长度远超训练长度时，高频维度的旋转角会进入训练未见区域，导致注意力相对位置泛化变差。

RoPE Scaling 的基本想法是把位置或频率重新缩放，让长序列下的旋转角变化更接近训练分布。

一种简单位置缩放：

\[ m'=\frac{m}{s} \]

即用较小有效位置替代真实位置。

NTK-aware scaling 的直觉是：不同频率维度对长度外推的敏感度不同，应更细致地调整 RoPE base 或频率分布，使注意力核在长上下文下更平滑。

YaRN 的思路可以理解为在插值和外推之间做折中：对不同频率区间采用不同缩放策略，并配合温度/幅度修正，让模型在长上下文下既保留局部分辨率，又扩展全局范围。

面试要点：

  • RoPE scaling 不是免费扩容，过度缩放可能损害短距离位置分辨率。
  • 插值式方法通常更稳，但可能压缩局部位置信息。
  • 外推式方法保留训练长度内行为，但超长位置可能不稳定。
  • 长上下文能力还依赖训练数据长度分布、attention pattern、检索能力和评测任务，不只是改 RoPE。

RoPE 为什么能表达相对位置信息？

RoPE 在二维子空间中对位置 \(m\) 的向量做旋转：

\[ R(m\theta)= \begin{bmatrix} \cos m\theta & -\sin m\theta \\ \sin m\theta & \cos m\theta \end{bmatrix} \]

对 query 和 key 分别注入位置：

\[ \tilde{q}_m=R(m\theta)q \]
\[ \tilde{k}_n=R(n\theta)k \]

注意力点积：

\[ \tilde{q}_m^T\tilde{k}_n =q^TR(m\theta)^TR(n\theta)k \]

旋转矩阵满足：

\[ R(a)^T=R(-a) \]

所以：

\[ R(m\theta)^TR(n\theta)=R((n-m)\theta) \]

因此：

\[ \tilde{q}_m^T\tilde{k}_n =q^TR((n-m)\theta)k \]

点积只依赖相对位置 \(n-m\)，而不是绝对位置 \(m,n\)。

结论：

RoPE 通过旋转矩阵的群结构，把绝对位置注入到 \(Q,K\) 中，但注意力分数天然包含相对位置信息。

RoPE和ALiBi两种相对位置编码的原理

回答：

RoPE 对 query 和 key 的二维通道对施加与位置相关的旋转。令 $R_p$ 为位置 $p$ 的旋转矩阵，则：

Scaled Dot-Product Attention 为什么要除以 \(\sqrt{d_k}\)？

注意力公式：

\[ \text{Attention}(Q,K,V)=\text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V \]

若 \(q\) 和 \(k\) 的每个分量均值为 0、方差为 1，则点积：

\[ q \cdot k = \sum_{i=1}^{d_k}q_ik_i \]

方差约为 \(d_k\)。当 \(d_k\) 很大时，logits 绝对值变大，Softmax 容易进入饱和区，梯度变小。

除以 \(\sqrt{d_k}\) 后，点积分数方差被缩放到稳定范围，有利于训练。

SGLang RadixAttention 缓存重用技术

RadixAttention，一种用于在运行时自动重用KV缓存的新技术。作者的方法不是在完成生成请求后丢弃KV缓存，而是将提示和生成结果的KV缓存保留在基数树中。这种结构可以实现高效的前缀搜索、重用、插入和淘汰。作者实现了最近最少使用（LRU）的淘汰策略，并辅以缓存感知的调度策略，以提高缓存命中率。此外，RadixAttention与现有的技术（如连续批处理和Paged Attention等）兼容。

基数树是一种数据结构，可替代前缀树。与典型的树不同，基数树的边不仅可以标记单个元素，而且还可以标记不同长度的元素序列。该特性显著提高了基数树的效率。在SGLang系统统中，作者使用基数树来管理一个映射。这个映射是在作为键的token序列和作为值的相应KV缓存张量之间的映射。这些KV缓存张量以非连续的分页布局进行存储，每个页的大小等于一个令牌的大小。

考虑到GPU内存的有限容量，因此无法重新训练无限的KV缓存张量，这就需要一个淘汰策略。为了解决这个问题，作者采用了递归淘汰叶节点的LRU淘汰策略。在连续批处理设置中，不能淘汰正在被当前运行的批处理使用的节点。因此，每个节点都维护一个引用计数器，显示有多少正在运行的请求正在使用该节点。如果一个节点的引用计数器为零，那么它就可以被淘汰。

前端始终将完整的提示发送到运行时，运行时将自动进行前缀匹配、重用和缓存。树结构存储在CPU上，维护开销很小。

树的结构维护历史的kv cache，从而减少prefix kv cache的计算，达到减少prefill计算的效果

SGLang的RadixAttention与vLLM的Prefix Caching有什么区别？

难度评分：⭐⭐⭐⭐⭐ (5/5) | 考察频率：⭐⭐⭐⭐⭐ (5/5)

一、先厘清比较对象

很多面试题会问"SGLang的RadixAttention与vLLM的PagedAttention有什么本质区别"，这个问题本身有一个陷阱：PagedAttention和RadixAttention不在同一层。

  • PagedAttention：KV Cache的内存管理机制，解决碎片化和按需分配
  • RadixAttention：KV Cache的前缀复用机制，用Radix Tree做前缀匹配和共享
  • vLLM Prefix Caching：vLLM中与RadixAttention同层的组件，基于Block哈希做前缀复用

所以正确的比较是 SGLang RadixAttention vs vLLM Prefix Caching；PagedAttention是vLLM Prefix Caching的底层内存管理基础。SGLang同样使用分页KV Cache和PagedAttention-style的注意力Kernel，RadixAttention是在其之上的前缀复用层，而不是对PagedAttention的替代。

面试时如果被问到原题，建议先指出这个层次差异，再展开对比，这比强行比较更加分。

二、Radix Tree管理KV Cache

Radix Tree（基数树/压缩前缀树）是一种高效的前缀匹配树结构。在SGLang中，Radix Tree用于管理所有请求的KV Cache：

树结构：

Root
├── "你是一个"
│   ├── "有帮助的AI助手\n"
│   │   ├── "用户：今天天气怎么样？"  ← 请求A的路径
│   │   └── "用户：帮我写首诗"        ← 请求B的路径
│   └── "知识渊博的专家\n"
│       └── "用户：解释相对论"         ← 请求C的路径

每个节点代表一段Token序列及其对应的KV Cache；节点可以按匹配结果拆分或合并，从Root到叶子的路径代表一个完整的Token序列。

三、前缀复用对比：vLLM Prefix Caching vs SGLang RadixAttention

这里比较的是两家的前缀复用机制。vLLM的Prefix Caching建立在PagedAttention的分页内存管理之上；SGLang的RadixAttention则用Radix Tree同时组织KV Cache和前缀匹配。

vLLM的Prefix Caching（基于哈希匹配）： - 以Block为单位计算哈希，仅在Block边界进行精确匹配 - 如果两个请求的前缀只在Block内部分相同（如15个Token相同但Block不全一致），则无法复用 - 单个Block的哈希查找为O(1)，但整条前缀需要逐Block匹配，整体复杂度与Block数相关；缓存Block数量巨大时需要维护大量哈希条目

SGLang的RadixAttention（基于Radix Tree）： - Token级别的匹配粒度，沿着Radix Tree向下匹配直到找到最长公共前缀 - 即使是部分匹配也能精确识别共享范围 - 树查找复杂度O(L)（L为前缀长度），但自动修剪和合并，管理更高效 - 请求完成时自动回收不再被引用的节点

四、RadixAttention的自动缓存管理

请求到达时的匹配流程：

  1. 将请求的Token序列从Radix Tree的Root节点开始匹配
  2. 沿着树向下遍历，找到最长匹配路径
  3. 已匹配的节点：直接复用KV Cache（引用计数+1）
  4. 未匹配的部分：创建新节点，分配新KV Cache Block
  5. 新生成的Token也动态追加到树中

请求完成时的回收流程： - 该请求路径上所有节点的引用计数-1 - 引用计数降为0的叶子节点：成为可驱逐候选；当缓存容量紧张时，按 LRU 策略从最久未访问的节点开始驱逐，整棵子树也会被递归回收 - 如果某个内部节点的子树全部被释放，该节点也被回收

五、RadixAttention的优势

  1. 更细粒度的前缀匹配：不像Block级别的哈希匹配，可以在任意Token位置匹配
  2. 自动前缀共享：无需显式配置，相同前缀自动复用
  3. 多轮对话场景收益明显：每一轮对话都是对历史路径的扩展，自然形成树结构
  4. 内存效率：LRU驱逐+引用计数+树修剪，自动控制缓存大小

六、对比总结

维度 vLLM Prefix Caching SGLang RadixAttention
索引结构 Block Hash映射 Radix Tree
前缀匹配粒度 完整Block（默认16 Token）为主 任意Token级别
查找方式 逐Block哈希查找，O(Block数) 树遍历，O(L)
内存管理 基于PagedAttention的Block Table 分页KV Cache（PagedAttention-style）+ Radix Tree节点
适用场景 固定System Prompt、RAG模板、多轮对话 大量共享前缀、多分支、Agent
缓存回收 BlockPool引用管理+缓存Block复用 引用计数+LRU+树修剪

可以总结为：SGLang RadixAttention与vLLM Prefix Caching都是前缀复用机制，但索引结构和匹配粒度不同：vLLM用Block Hash、以完整Block为主；SGLang用Radix Tree、支持Token级最长公共前缀。PagedAttention是vLLM Prefix Caching的底层内存管理基础，不应与RadixAttention直接对比。多轮对话、Agent调用等大量共享前缀的场景中，RadixAttention的匹配粒度更细。

Softmax 把 $V$ 个 Logit 归一化为和为 1 的条件分布。工程实现会使用减去最大 Logit 等数值稳定技巧。

Sparse Attention（稀疏注意力）

Transformer 模型的主要瓶颈之一是自注意力机制的计算复杂度，标准的全连接注意力（Full Attention）在序列长度为 \(N\) 的情况下，其计算复杂度为 \(O(N^2)\) 。这对于长序列任务，如机器翻译或长文本生成任务，代价非常高。

Xformers 提供了稀疏注意力机制，即通过减少不必要的查询-键值对（Query-Key pairs）的计算来降低复杂度，通常可以将计算复杂度降至 \(O(N \log N)\) 或 \(O(N)\) ：

  • 局部注意力（Local Attention）：仅计算局部范围内的注意力权重，而忽略远程依赖关系。
  • 因式分解注意力（Factorized Attention）：将注意力计算分解为更小的矩阵运算，降低计算需求。

Stable Diffusion 3/FLUX 类 Rectified Flow Transformer 的数学特点是什么？

这类模型常把扩散/flow 生成过程与 Transformer backbone 结合。核心不再只是 U-Net 去噪，而是用 Transformer 处理图像 latent token 与文本条件 token。

Rectified Flow 学习速度场：

\[ \frac{dx_t}{dt}=v_{\theta}(x_t,t,c) \]

其中 \(c\) 是文本或多模态条件。

常见线性插值路径：

\[ x_t=(1-t)x_0+tx_1 \]

目标速度：

\[ u_t=x_1-x_0 \]

训练目标：

\[ L=\mathbb{E}\left[\|v_{\theta}(x_t,t,c)-u_t\|_2^2\right] \]

T5对原始Transformer做了哪些简化修改（如层归一化位置、位置编码）？这些修改如何影响训练效率和稳定性？

T5的架构调整包括： 1. 层归一化（LayerNorm）位置： 原始Transformer：LayerNorm在残差连接和激活函数之后。 T5调整：LayerNorm置于残差连接之前（Pre-Norm），提升训练稳定性（梯度流动更顺畅）。 1. 位置编码： 使用相对位置编码（Relative Position Embeddings）而非绝对位置编码：每个注意力头学习一组标量，根据查询-键的相对位置偏移调整注意力logits。 优势：更好地处理长序列，泛化到训练未见长度。 1. 简化偏置项：移除LayerNorm中的偏置参数和部分线性层的偏置，减少冗余参数。

影响： - 训练效率：Pre-Norm允许使用更大学习率，加速收敛；相对位置编码减少外推偏差。 - 稳定性：简化设计降低过拟合风险，论文中T5-Base在GLUE上标准差仅0.235。

Token 压缩与稀疏注意力如何缓解长序列压力？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

前面几种策略在输入端控制计算量，token 压缩和稀疏注意力在编码过程中降低开销，前者减少 token 数，后者改变注意力的计算范围。后文与窗口注意力并列介绍的 FlashAttention 同属效率优化，但不改变注意力的数学定义，只是更高效的实现，并列是为了对照两类优化的边界。

Token 压缩：在编码之后减少 token 数量。

（1）池化与 Pixel Shuffle：把相邻的 patch token 合并。InternVL-1.5 在分块编码之后用 Pixel Shuffle 把每块的 token 数压到原来的四分之一[30]；Qwen2.5-VL、Qwen3-VL 用两层 MLP 把相邻 2×2 个特征合成一个 token[35,36]。

（2）可学习 query 聚合：用一组可学习的 query token，通过交叉注意力从视觉特征里提取信息。BLIP-2 的 Q-Former 采用这种做法，把 ViT 输出的 257 个视觉 token 压成 32 个 query token 再送进 LLM[10]。

窗口注意力与稀疏注意力：不减少 token 数。窗口注意力改变自注意力的计算范围，FlashAttention 只优化计算实现。

（1）窗口注意力：只在局部窗口内算自注意力。Swin Transformer 采用窗口注意力，把计算量从随图像尺寸二次增长降到线性增长，再用移位窗口（shifted window）让相邻窗口交换信息[37]。Qwen2.5-VL 的视觉编码器也在大部分层改用窗口注意力，32 层里只保留 4 层全局注意力[35]。

（2）FlashAttention：同属效率优化，但不改变注意力的数学定义，也不改变计算范围，只靠分块计算和减少显存读写来加速[38]，长序列场景基本都会开启。

Transformer 模型

Transformer 由多个自注意力机制（Multi-Head Attention） 和 前馈网络（Feedforward Layer） 组成。

  • 多头自注意力机制： 每个注意力头有 \( Q, K, V \) 三个矩阵，参数量为：

$$ \text{参数量} = 3 \times (\text{输入特征数} \times \text{注意力头的特征数}) \times \text{注意力头数} $$

  • 前馈网络： 包含两层全连接层，参数量为：

$$ \text{参数量} = 2 \times (\text{输入特征数} \times \text{隐藏特征数} + \text{隐藏特征数}) $$

Transformer、CLIP原理，图文对齐层工作机制

答：Transformer 的核心是用自注意力机制建模序列内部任意两个 token 之间的关系。输入 token 经过 Embedding 与位置编码后，被线性映射为 Query、Key、Value：

\[ Q=XW_Q,\quad K=XW_K,\quad V=XW_V \]

单头注意力计算为：

\[ \text{Attention}(Q,K,V)=\text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V \]

其中 \(QK^T\) 表示 token 两两之间的相关性，\(\sqrt{d_k}\) 用来防止点积数值过大导致 softmax 过饱和。多头注意力会把隐藏维度切成多个 head，每个 head 学习不同子空间下的依赖关系，最后拼接并经过输出投影。Transformer Block 通常由多头注意力、前馈网络、残差连接和 LayerNorm/RMSNorm 组成。Encoder 适合理解任务，Decoder 适合自回归生成任务，现在主流大语言模型多采用 Decoder-only 架构。

CLIP 的核心是“双塔编码器 + 对比学习”。图像经过视觉编码器，如 ResNet 或 ViT，得到图像向量 \(v_i\)；文本经过文本 Transformer 得到文本向量 \(t_i\)。二者再经过各自的投影层映射到同一维度的共享语义空间，并做 L2 normalization。一个 batch 内有 \(N\) 对图文样本，计算相似度矩阵：

\[ s_{ij}=\frac{v_i^Tt_j}{\tau} \]

其中 \(\tau\) 是可学习或固定的温度系数。训练目标是让匹配图文对的相似度最大，让非匹配图文对的相似度最小，常用图到文、文到图两个方向的对称交叉熵：

\[ \mathcal{L}_{i2t}=-\frac{1}{N}\sum_i \log \frac{\exp(s_{ii})}{\sum_j \exp(s_{ij})} \]
\[ \mathcal{L}_{t2i}=-\frac{1}{N}\sum_i \log \frac{\exp(s_{ii})}{\sum_j \exp(s_{ji})} \]
\[ \mathcal{L}=\frac{1}{2}(\mathcal{L}_{i2t}+\mathcal{L}_{t2i}) \]

所谓“图文对齐层”在 CLIP 类模型里通常就是图像塔和文本塔之后的 projection head。它的作用不是做复杂交互，而是把两个模态的特征投到同一个向量空间，使余弦相似度或点积相似度具备跨模态语义含义。在多模态大模型里，对齐层也可能指 vision projector、Q-Former、Perceiver Resampler 或 cross-attention bridge，它们负责把视觉 token 映射到语言模型可理解的 embedding 空间。面试时可以强调：CLIP 的对齐是“全局向量级对齐”，多模态大模型里的 projector 则更偏“token 级接入与语义适配”。

Transformer各类Decoder结构

答：Transformer Decoder 常见结构可以分为几类。

第一类是原始 Encoder-Decoder Transformer 里的 Decoder。它包含三部分：masked self-attention、cross-attention、FFN。masked self-attention 负责看已生成 token，cross-attention 负责看 Encoder 输出，适合机器翻译、摘要、语音识别等 seq2seq 任务。典型模型包括 T5、BART、原始 Transformer 翻译模型。

第二类是 Decoder-only 结构。它只有 causal self-attention 和 FFN，没有 Encoder，也没有标准 cross-attention。每个 token 只能看当前位置之前的 token，通过 next token prediction 训练。GPT、LLaMA、Qwen、Mistral、DeepSeek 等主流 LLM 大多采用这种结构。优点是预训练目标简单、扩展性强、生成能力好，适合统一建模文本、代码、多模态 token 等序列。

第三类是 Prefix-LM 或 UniLM 式 Decoder。它允许输入前缀部分双向可见，生成部分因果可见。这样可以兼顾理解和生成，例如给定一段上下文后生成答案。它介于 Encoder-Decoder 和纯 Decoder-only 之间。

第四类是带 Cross-Attention 的多模态 Decoder。语言模型仍然按自回归方式生成，但在部分层里通过 cross-attention 读取视觉、音频或检索特征。Flamingo 类模型就是典型代表。相比直接把视觉 token 拼进文本序列，cross-attention 可以更好地控制视觉信息注入位置和计算量。

第五类是 Query-based Decoder 或 Resampler。比如 BLIP-2 的 Q-Former 使用一组可学习 query 从视觉编码器中提取固定数量的视觉 token，再接入语言模型。它本质上不是传统语言 Decoder，但在多模态结构中承担了“从视觉特征中解码出语言模型可用表示”的作用。

面试回答时可以用一句话总结：Encoder-Decoder Decoder 擅长条件生成，Decoder-only 擅长通用自回归生成，Prefix/UniLM 兼顾理解与生成，多模态 Decoder 则重点解决视觉/音频信息如何接入语言生成的问题。

Transformer自回归解码中Prefill阶段与Decode阶段有什么不同？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐⭐ (5/5)

一、Prefill阶段

Prefill阶段处理输入的Prompt（提示词），一次性完成所有Prompt Token的编码：

计算特征： - 一次性将所有Prompt Token输入模型，计算所有层的K、V矩阵 - 首次生成Token时，需要计算Prompt中所有Token之间的Attention（因果掩码下仍为O(n²)复杂度） - K、V矩阵计算结果存入KV Cache供后续Decode复用 - 计算量大、并行度高，属于计算密集型（Compute-Bound）

计算流程：

给定 Prompt = [t1, t2, ..., tn]
→ 一次性前向计算所有n个Token的注意力
→ 生成第一个输出Token
→ 将n个Token的KV全部存入KV Cache

二、Decode阶段

Decode阶段是逐个Token生成的迭代过程：

计算特征： - 每次只处理一个新生成的Token - 该Token只需与所有历史Token（Prompt + 已生成的）计算注意力 - 历史Token的K、V直接从KV Cache读取，无需重计算 - 单Token的计算量很小，但需要访问大量KV Cache数据，属于访存密集型（Memory-Bound） - GPU计算单元大量时间在等待HBM数据读取

计算流程：

每步迭代：
→ 输入当前最新Token
→ 从KV Cache读取所有历史K、V
→ 计算该Token与历史的Attention
→ 生成下一个Token
→ 将新Token的KV追加到KV Cache

三、两阶段对比总结

维度 Prefill Decode
输入 Prompt全部Token（并行） 单个新Token（串行）
计算量 大（O(n²)注意力） 小（O(n)单Token注意力）
访存量 相对低（权重一次加载） 大（读取全部KV Cache）
瓶颈类型 计算密集型（Compute-Bound） 访存密集型（Memory-Bound）
并行度 高（所有Token并行计算） 低（只能逐个生成）
延迟贡献 TTFT的主要来源 TPOT的主要来源
KV Cache 写入阶段 读写阶段

四、两阶段差异的影响

理解Prefill和Decode的差异，才能理解大模型推理优化的侧重点：

  1. Prefill优化方向：利用并行计算能力，减少计算延迟。例如FlashAttention、算子融合、量化矩阵乘法
  2. Decode优化方向：减少KV Cache读取量，提高HBM带宽利用率。例如MQA/GQA减少KV头数、KV Cache量化、FlashDecoding
  3. 调度优化方向：将Prefill和Decode分开调度（PD分离），避免Decode的访存密集特征拖慢Prefill的计算效率

可以总结为：Prefill是一次性并行计算的"重"阶段，瓶颈在计算；Decode是逐个Token串行生成的"轻"阶段，瓶颈在访存。大模型推理优化的就是针对这两个截然不同的阶段采取不同的优化策略。

U-Net 为什么合适

  • 多尺度路径：编码器逐级降低分辨率并扩大感受野，解码器再恢复空间尺寸，使同一个网络能够处理从整体结构到局部细节的预测。
  • 跳跃连接（skip connection）：把当前噪声状态下的高分辨率中间特征送到对应解码层，保留位置和边界信息。这些特征仍然含有噪声，模型需要将其与低分辨率特征融合后预测训练目标。
  • 分层条件注入：时间步嵌入、文本条件和结构控制可以进入不同分辨率层，同时影响整体语义与局部细节。

卷积还提供了局部性和平移等变的归纳偏置。需要明确的是，U-Net 只是生成主干的一种选择，Diffusion 和 Flow Matching 都没有限定必须使用哪类网络。

扩展到视频时，需要补上跨帧信息流

仅把输入张量增加一个时间维还不够。如果每一帧仍由同一套空间网络独立处理，模型学到的依然主要是单帧去噪。常见改法有两条：

  • 复用图像 U-Net：保留预训练的 2D 空间层，在部分分辨率层插入时间卷积、时间注意力或 motion module。这种方式便于继承已有的空间表征，新增模块的作用范围取决于插入位置和时间感受野。
  • 构建时空 U-Net：将卷积、注意力或上下采样直接扩展到时间维，统一设计空间与时间运算。这通常会增加计算量，与图像预训练权重的兼容也更复杂。

具体选择 Temporal Conv 还是 Temporal Attention 属于 4.2.5。本题要抓住的是：视频化改造必须让中间特征跨帧交换信息。

Video VAE 的空间压缩、时间压缩和 latent 通道数应如何权衡？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

VAE 规格至少要看空间压缩率、时间压缩率和 latent 通道数。只报一个“总压缩倍数”，无法判断模型减少了多少时空位置，也看不出每个位置保留了多少特征。

先区分网格数、token 数和元素数量

设 RGB 视频尺寸为 \(T \times H \times W \times 3\) ，latent 尺寸为 \(T' \times H' \times W' \times C_z\) 。假设各维可整除；如果主干还把 latent 切成大小为 \(p_t \times p_h \times p_w\) 的 3D patch，则有：

\begin{aligned}
T' &= \frac{T}{r_t}, \qquad H' = \frac{H}{r_h}, \qquad W' = \frac{W}{r_w}, \\
N_{\mathrm{grid}} &= T'H'W' = \frac{T H W}{r_t r_h r_w}, \\
N_{\mathrm{token}} &= \frac{N_{\mathrm{grid}}}{p_t p_h p_w}.
\end{aligned}

其中， \(r_t\) 是时间压缩率， \(r_h\) 和 \(r_w\) 是空间压缩率， \(C_z\) 是 latent 通道数； \(p_t\)、 \(p_h\)、 \(p_w\) 分别是主干在时间、高度和宽度方向的 patch 大小。

当主干不再 patchify latent 时， \(p_t=p_h=p_w=1\) ，此时 latent 网格数才等于 token 数。VAE 压缩与主干 patch 化发生在不同位置，比较模型成本时不能混为一个指标。

如果把通道也算入，输入与 latent 的元素数量之比为：

R_{\mathrm{elem}}=\frac{3 T H W}{C_z T'H'W'}
=\frac{3 r_t r_h r_w}{C_z}

因此， \(r_t r_h r_w\) 表示 VAE 对时空网格的缩减倍数， \(R_{\mathrm{elem}}\) 才包含 latent 通道数。它仍然只是元素数量比，并未计入数值精度或熵编码，不能直接当成文件存储压缩率。增加 \(C_z\) 不会改变 latent 网格数，却会增加每个位置的表示容量、latent 激活量和输入输出投影成本。把网格缩减倍数、patch 大小和元素数量比混在一起，模型之间的效率比较很容易失真。

三个方向丢失的信息不同

  • 空间压缩首先影响小物体、文字、人脸和细纹理。空间压缩过强时，生成主干即使预测正确，解码后仍可能糊成相似纹理。
  • 时间压缩首先影响高速动作、瞬时表情、闪光和口型等高频变化。压缩过强时常见动作变钝、短事件消失或音画边界偏移。
  • Latent 通道数限制每个时空位置可携带的联合信息。通道过窄会同时影响颜色、纹理和运动表征；通道加宽又会提高 VAE 与主干投影层的成本。

效率与选型不能只看压缩倍数

token 减少通常会降低主干计算量，但“压缩两倍就快两倍”并不成立。全局注意力、局部窗口、稀疏注意力和卷积主干的复杂度不同，端到端延迟还包含 VAE 编解码、数据搬运和采样步数。

选型时先在真实视频上单独评估 VAE：按人脸、小字、高速运动、镜头切换和音画同步切片检查重建，再记录 latent token 数、通道数、显存和编解码延迟。VAE round-trip 合格后，才有必要比较下游扩散或 Flow Matching 的训练稳定性与生成质量。

面试速答：空间和时间压缩决定主干处理多少时空 token，通道数决定每个 token 能装多少信息。空间压缩主要损伤细节，时间压缩主要损伤快速运动，通道过窄会限制整体表示能力。比较模型时要区分 token 缩减倍数和包含通道数的元素数量比，并先做 VAE-only 重建测试。

时间耦合、时间压缩与因果性是三个属性

Video VAE 并不必然压缩时间。只要编码或解码过程显式混合跨帧信息，即使 \(r_t=1\) ，它仍属于视频自编码器。反过来，把相邻帧做简单时间降采样，也不等于学到了稳定的运动表示。

VLA 模型的架构谱系是怎样演进的？动作表示之争的本质是什么？

难度评分：⭐⭐⭐⭐⭐ (5/5) | 考察频率：⭐⭐⭐⭐ (4/5)

VLA（Vision-Language-Action，视觉-语言-动作）模型把看到的画面和语言指令映射为动作，其谱系可以分为离散动作、开源中等规模和连续动作三代，如图 6-10 所示。动作表示之争与 5.5.2.4 中离散 token 与连续表征的取舍属于同一类问题，离散动作复用语言模型的词表和训练目标，连续动作更适合高频控制。三代模型的代表工作分别是：

  1. 离散动作。 RT-2 以 PaLI-X（最大 55B）和 PaLM-E 为底座[40]，动作沿用 RT-1 的离散化方式[41]：末端执行器的 6 自由度位移和夹爪开合共 7 个连续维度，各自均匀量化为 256 个 bin，加上一个终止指令，一步动作表示为 8 个整数[40]。PaLI-X 的词表中 1000 以内的整数各有独立的 token，动作可以直接复用这些 token，从而放入自回归框架[40]。RT-2 要证明的是网页规模的图文知识可以迁移到机器人操作，操作对象可以不在机器人训练集中。论文也指出，模型的计算开销较高，用于更高频的控制时，实时推理可能成为主要瓶颈[40]。

  2. 开源中等规模。 OpenVLA 是 7B 模型，视觉侧融合 SigLIP 和 DINOv2 的特征，语言侧基于 Llama 2，训练数据是从 Open X-Embodiment 中整理出的约 97 万条真实机器人轨迹[42]。Open X-Embodiment 本身汇集了 60 个数据集、22 种机器人形态的超过 100 万条轨迹[43]，97 万条是 OpenVLA 的整理结果。论文报告，OpenVLA 在 29 个任务和多种机器人形态上的绝对成功率比 55B 的 RT-2-X 高 16.5 个百分点，参数量约为后者的七分之一[42]。这一数字是 29 个任务的平均差距，各项语义泛化能力需要分开看。这一代的动作仍是离散 token。

  3. 连续动作。 $\pi_0$ 以约 3B 参数的 PaliGemma 为底座，另加约 300M 参数、从零初始化的动作专家，合计约 3.3B[44]。它的动作块长度 $H=50$，用条件流匹配（Flow Matching）一次生成整段连续动作，论文写明控制频率最高约 50 Hz，示例任务包括叠衣服；推理时从噪声积分到动作块，实验中使用 10 步 Euler 积分[44]。直线路径与训练目标为：

\[ a_{\tau}=(1-\tau)\,a_0+\tau\,a_1,\qquad \mathcal{L}_{\mathrm{FM}}=\mathbb{E}\bigl\|v_{\theta}(a_{\tau},\tau\mid o)-(a_1-a_0)\bigr\|^{2} \]

这里 $a_0$ 是噪声，$a_1$ 是真实动作块，$o$ 为观测，$v_\theta$ 为待学习的速度场，速度目标是动作减去噪声，与 $\pi_0$ 论文中的 $A-\epsilon$ 一致[44]。

双系统架构的共性是把语义推理与高频控制解耦，各家的控制频率不同。Figure 的 Helix 中，System 2 是 7B 参数的开源 VLM，运行频率 7~9 Hz，输出一个连续潜变量；System 1 约 80M 参数，以 200 Hz 输出连续动作[45]。GR00T N1 论文给出的数字不同：System 2 是 VLM，在 NVIDIA L40 上约以 10 Hz 运行；System 1 是用流匹配训练的扩散 Transformer，以 120 Hz 生成动作[46]。NVIDIA 于 2026 年 4 月公开的 GR00T N1.7 约 3B 参数，仓库写明其视觉语言骨干是 Qwen3-VL 架构的 Cosmos-Reason2-2B，动作头仍是流匹配扩散 Transformer[47]；N1 的频率数字只适用于 N1 论文中的配置。

离散动作复用语言模型的词表、自回归和训练目标，控制频率和量化精度受到限制；连续动作平滑，适合高频控制，但脱离了语言词表；双系统把语义留在视觉语言模型中，把控制交给连续策略。

vLLM V1的EngineCore架构如何理解？Scheduler如何调度请求？

难度评分：⭐⭐⭐⭐⭐ (5/5) | 考察频率：⭐⭐⭐⭐ (4/5)

一、vLLM V1的架构层次

vLLM V1 以 EngineCore 为内层主循环，不能再简单套用早期”AsyncLLMEngine + BlockManager + swapped队列”的旧版表述。更准确的理解方式是：

1. API / Client层 - vllm serve提供OpenAI兼容接口 - 在线服务通常使用异步客户端形态，离线推理使用LLM接口 - 这一层负责请求解析、协议适配、流式返回和输入输出格式转换

2. LLMEngine / AsyncLLM兼容层 - LLMEngine保留为兼容入口，但内部已经转向V1实现 - AsyncLLM是异步在线服务的主要引擎客户端 - 这一层将外部请求转换为EngineCoreRequest，再把底层输出转换成用户可见的RequestOutput

3. EngineCore层 - EngineCore是V1的内层主循环 - 负责初始化Executor、Profile可用KV Cache显存、创建KV Cache配置、构造Scheduler - 每轮执行“调度→模型执行→采样→更新请求状态”的闭环

4. Scheduler + KV Cache管理层 - Scheduler决定每一步哪些请求、哪些Token进入本轮执行 - KV Cache由KVCacheManager、BlockPool和KV Cache Coordinator管理 - Prefix Caching、抢占、远端KV等待、Chunked Prefill等逻辑都在这一层协同

5. Executor / Worker / ModelRunner层 - Executor负责单机或分布式执行后端 - Worker负责设备初始化、权重加载、KV Cache分配、CUDA Graph捕获和模型前向 - ModelRunner真正组织GPU侧执行、Attention Backend和采样相关计算

二、Scheduler不再适合用“waiting/running/swapped三队列”概括

在vLLM V1 Scheduler中，状态更接近：

waiting队列：尚未进入执行，或被抢占后重新等待的请求
running列表：当前可被调度执行的请求
blocked waiting状态：等待远端KV、等待结构化输出grammar、等待流式输入等
finished集合：已完成、被中止或出错的请求

旧版资料里常说的swapped队列更像早期BlockManager/CPU swap语境下的解释。V1中更应强调preemption（抢占）：当KV Cache资源不足时，Scheduler可以抢占低优先级或靠后的running请求，释放其KV Cache，将请求状态标记为PREEMPTED并放回waiting队列，后续资源足够时再重新调度。

三、每轮调度在做什么

Scheduler每轮调度主要受两个预算约束：

  • Token预算：由max_num_batched_tokens等参数限制本轮最多处理多少Token
  • 请求预算：由max_num_seqs等参数限制同时运行多少请求

典型流程可以理解为：

  1. 先处理已在running中的请求，决定每个请求本轮继续Decode还是补充Prefill token
  2. 对长Prompt使用Chunked Prefill，把一次大Prefill拆成多个小块（chunk），每轮只做一部分Prefill计算，做完后立即"让步"给等待中的Decode请求——本质上是将大Prefill的计算量"分期付款"，避免某一轮因处理整个长Prompt而让所有Decode请求饥饿等待
  3. 检查KV Cache是否有足够Block；不足时触发抢占，被抢占请求回到waiting
  4. 从waiting中选择新请求加入running，受Token预算、请求预算、KV Cache容量和结构化输出状态约束
  5. 生成SchedulerOutput交给Executor执行，执行结果再反向更新请求状态、KV Cache状态和输出流

四、KV Cache管理的新口径

vLLM V1的组件是：

  • KVCacheManager：Scheduler和KV Cache内部结构之间的接口，负责查询命中、分配slot、释放请求占用的块
  • BlockPool：维护物理KV Cache Block、空闲Block队列、可被Prefix Caching命中的Block哈希表
  • KV Cache Coordinator：在不同KV Cache group、混合KV Cache结构、Prefix Caching等场景下协调Block分配与命中查询

可以总结为：vLLM V1架构应按”API/AsyncLLM或LLMEngine兼容层→EngineCore→Scheduler/KVCacheManager→Executor/Worker/ModelRunner”理解。Scheduler的重点是围绕Token预算、请求预算和KV Cache容量，在running/waiting请求之间做连续批处理、Chunked Prefill和抢占调度。KV Cache管理则为KVCacheManager、BlockPool和Coordinator体系。

一批文本进入变换器架构（Transformer）前，张量形状如何变化？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐ (4/5)

设批大小为 $B$，序列长度为 $L$，隐藏维度为 $d$，词表大小为 $V$：

  1. 原始文本经过 Tokenizer，得到 input_ids，形状为 $[B,L]$。
  2. 不同长度样本通常需要填充或打包，并生成有效位置掩码。
  3. Embedding 查表后得到 $X \in \mathbb{R}^{B\times L\times d}$。
  4. 位置机制向 $X$ 或后续的 Q、K 注入位置信息。
  5. 经过 $N$ 个 Transformer后，张量主体形状仍是 $[B,L,d]$。
  6. LM Head 映射到词表空间，得到 $[B,L,V]$ 的 Logits。推理时通常只需要最后一个有效位置的 $[B,V]$；训练时则会对多个位置计算下一 Token 损失。

如果多头数为 $H$，单头维度为 $d_h$，通常有 $d=H d_h$。Q 的常见形状可重排为 $[B,H,L,d_h]$。

注：填充掩码（padding mask）解决“哪些位置是填充”，因果掩码（causal mask）解决“哪些未来位置不可见”，二者目的不同，实际计算中可以合并应用。
