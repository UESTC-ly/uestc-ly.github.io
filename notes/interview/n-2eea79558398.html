容器、虚拟机与隔离边界

容器把进程及其文件系统、网络和资源环境组织起来，常与宿主共享内核；虚拟机通过虚拟化层运行独立客户操作系统。容器通常启动和分发更轻便，虚拟机提供不同的内核与隔离边界，二者也经常组合使用。

容器镜像不是完整虚拟机快照，容器内 root 也不自动等于安全隔离。选择时应考虑内核依赖、多租户威胁、设备访问、资源限制和运行维护成本；不能仅凭“部署了容器”就认为应用具备高可用或安全性。

参考资料：bregman-arie/devops-exercises 原文。

Namespaces、Cgroups 与容器资源

Linux namespaces 让进程看到隔离的系统资源视图，cgroups 对一组进程的资源使用进行统计和约束。前者侧重“看到什么”，后者侧重“能用多少”，两者结合构成容器机制的一部分，但并不覆盖全部安全控制。

CPU 限额可能引入节流，内存超限可能触发对应的 OOM 处理。排查性能时需区分应用自身负载、资源上限与节点竞争，并检查实际 cgroup 版本和运行时设置。容器里看到的内存、CPU 数量或负载指标也要结合宿主和配额解释。

参考资料：bregman-arie/devops-exercises 原文。

镜像层、构建缓存与持久化

镜像由可复用层和配置组成，容器在镜像基础上形成运行时可写层。把依赖变化较少的步骤与频繁变化的应用代码合理分开，有助于构建缓存复用；多阶段构建可将构建工具与最终运行内容分离。

容器重建不能依赖临时可写层保留业务数据。数据库文件、用户上传等状态需要明确持久化、备份和恢复策略。镜像标签可能变化，发布追踪应关联不可变摘要和构建记录；镜像越小也不自动意味着更安全，依赖与来源仍需管理。

参考资料：bregman-arie/devops-exercises 原文。

Kubernetes 声明式控制与控制器

Kubernetes 以期望状态为输入，控制器持续观察实际状态并推动二者收敛。API 请求被接受，只说明期望对象已记录，不等于容器已经运行或服务已可用；调度、拉取镜像、启动和就绪仍可能失败。

故障排查应沿对象状态、事件、调度条件、容器状态和日志逐层定位。控制器也不是无条件重试任何业务操作的替代品，外部副作用仍需幂等与身份约束。声明式配置有利于审计和重建，但必须与权限、版本管理和变更流程配合。

参考资料：bregman-arie/devops-exercises 原文。

Pod、Deployment 与状态管理

Pod 是 Kubernetes 中可调度的一组紧密协作容器，它们共享网络等环境；Deployment 通过控制器管理一类工作负载的副本和滚动更新。Pod 可被替换，业务不应依赖某个 Pod 的固定身份或临时本地状态。

需要稳定身份和持久卷关联的工作负载，应结合相应的有状态控制与存储设计；仅给容器挂载卷不代表备份、复制和数据一致性已经解决。解释高可用时需区分进程恢复、副本可达性和业务数据恢复。

参考资料：bregman-arie/devops-exercises 原文；Kubernetes 官方：Pod。

Service、Ingress 与服务流量

Pod 地址会随重建变化，Service 为符合选择规则的后端提供较稳定的访问入口；Ingress 描述一类面向 HTTP/HTTPS 的入口路由，实际处理依赖相应实现。二者作用层次不同，创建路由对象不保证外部网络、证书和控制器已经配置好。

流量不通时，应分别检查名称解析、入口、Service 选择条件、后端端点、就绪状态、网络策略和应用监听。把问题笼统归为“网关坏了”会跳过关键证据。具体数据转发方式与集群网络实现、版本有关，应避免将某一种实现当成协议规定。

参考资料：bregman-arie/devops-exercises 原文。

Liveness、Readiness 与 Startup Probe

存活探针用于判断容器是否需要重启，就绪探针用于判断它是否应接收流量，启动探针用于给慢启动程序保留初始化时间。探针检查的语义应不同：依赖服务暂时故障不一定意味着重启当前进程能修复问题。

检查过重或阈值过激可能让瞬时负载触发级联重启。探针成功也只验证所覆盖的条件，不代表全部业务操作正确。设计时应结合启动特征、超时、失败阈值和真实业务健康信号，并验证发布和故障时流量如何变化。

参考资料：bregman-arie/devops-exercises 原文；Kubernetes 官方：探针职责。

Requests、Limits 与容量规划

资源 requests 参与调度及相关资源分配判断，limits 则约束运行时可使用的资源范围。配置合理与否取决于实际峰值、稳定负载、启动特征和节点容量，不能把两个值机械设为相同后视作完成容量规划。

应观察 CPU 节流、内存峰值、OOM、排队与延迟分位数，区分资源不足、锁竞争、外部依赖和应用泄漏。扩容前还需确认瓶颈是否可被增加副本缓解，以及下游数据库、连接数和配额能否承受新增流量。

参考资料：bregman-arie/devops-exercises 原文。

CI、持续交付与安全发布

持续集成及时验证代码和依赖能否共同工作；持续交付使变更保持可发布状态；持续部署进一步自动把符合条件的变更上线。流水线应让构建产物、版本、测试结果和部署对象可追踪，而不是在不同环境临时重新拼装未知产物。

发布可采用滚动、蓝绿或金丝雀策略，核心是控制影响面、观测结果并具备回退路径。应用回滚不一定能回滚数据库结构和已经发生的副作用，因此需要兼容性设计和迁移顺序。测试全部通过也不能替代线上指标与业务验证。

参考资料：bregman-arie/devops-exercises 原文。

指标、日志、Trace 与可观测性

指标适合聚合趋势和告警，日志保留离散事件详情，Trace 连接一次请求跨组件的调用路径。三者互补：一个延迟尖峰需要指标发现，可能借助 Trace 定位慢调用，再用日志解释错误条件。

观测应关联服务、版本、请求身份和时间，并控制高基数标签、采样与敏感信息。仅接入很多工具不代表系统可观测，关键是能否回答“哪里变差、影响谁、从何时开始、与哪次变更相关”。告警应围绕可采取行动的症状，而非为每个波动都通知。

参考资料：bregman-arie/devops-exercises 原文。

SLI、SLO、SLA 与故障复盘

SLI 是对服务表现的测量，例如成功请求比例；SLO 为指定时间窗设定目标；SLA 是服务承诺及相关约定，可能涉及商业后果。可用性定义必须说明成功条件、统计窗口和分母，否则相同百分比可能含义完全不同。

错误预算表达允许消耗的失效空间，可帮助讨论发布速度与可靠性投入。故障处置先降低影响、恢复服务，再保留证据分析触发因素与系统性原因；复盘应落实可验证的改进，而非只归咎某个操作者或写“以后小心”。

参考资料：bregman-arie/devops-exercises 原文；bregman-arie/devops-exercises 原文。
