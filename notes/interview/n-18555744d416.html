以图搜图与拍照购物为什么采用检索式而非生成式方案？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐ (3/5)

以图搜图的主链路是双塔嵌入加近似最近邻检索。生成式模型无法建索引，无法对十亿级候选逐一打分，输出也不稳定，因此只适合放在链路两端。拍立淘是拍照购物的产品代表，公开资料没有披露其线上编码器的具体模型。下面依次说明主链路的构成、生成式模型不适合承担召回主链路的原因，以及生成式模型在链路两端的位置：

  1. 主链路。 商品库离线编码为向量，线上的 query 图像经过同一编码器，以余弦相似度 $s=\cos(\mathbf{v}_q,\mathbf{v}_d)$ 在近似最近邻索引中召回，其中 $\mathbf{v}_q$ 和 $\mathbf{v}_d$ 分别为 query 和商品的嵌入向量。CLIP 是这类双塔模型的代表[16]，索引常用 HNSW 和 IVF-PQ[17]。十亿级商品库能够在较短延迟内返回结果，依靠的是向量可以预先计算，具体延迟随库规模和硬件变化。

  2. 生成式模型不适合承担召回主链路，原因有三：

    （1）无法建索引。生成式模型的相似度判断发生在一次前向推理之中，无法转化为可离线存储的向量，每次查询都要对候选重新运行模型。

    （2）费用和延迟过高。候选规模一大，逐个生成的成本远高于一次近似最近邻查询，具体差距需要按库的规模计算。

    （3）结果不稳定。检索要求同一个 query 得到同一批结果，采样式生成无法保证这一点。

  3. 生成式模型的位置。 前端用它做 query 理解，区分用户拍的是鞋还是鞋上的标志，抽取颜色和款式并改写检索条件；后端对召回的一小批候选做属性比对，并生成推荐理由；入库时还可以用 MLLM 为商品图打结构化标签，提高召回质量。Qwen3-VL 这类模型可以承担上述理解任务，但不承担十亿级的在线打分。

面试速答：以图搜图的主链路是双塔嵌入加近似最近邻检索，CLIP 是代表，商品向量可以离线计算。生成式模型无法建索引，不能对十亿级商品逐个打分，采样结果也不稳定，因此适合放在两端：前端理解 query，后端解释一小批候选。

企业知识库问答为什么通常优先考虑 RAG？

企业知识库通常具有私有、动态、可追溯和权限敏感的特点。RAG 可以快速接入已有文档，更新成本低，并且能够输出引用来源。例：公司制度每周变化，用微调维护成本很高；用 RAG 只需更新文档索引。

优化切分后，召回率得到了提升。那你们最终是怎么判断整个客服系统的回答效果是真的变好了，而不只是召回指标好看。

回答：

召回只是中间指标，客服系统的目标是正确、完整、及时地解决用户问题。检索更高可能只是多塞了文档，生成阶段仍可能选错规则、混淆版本或忽略否定条件，因此要沿整条链路验收。

离线对固定、独立且覆盖业务分布的问题集，比较新旧系统的答案正确性、完整性、证据支持、引用可追溯、应拒答表现与高风险错误。人工盲评可减少对新方案的期待偏差；模型评审可以扩展覆盖，但需要人工校准和对争议样本仲裁。

同时固定或记录上下文 token、模型版本与成本，区分切分优化与“给模型更多材料”带来的影响。使用配对比较，重点复核从对变错的回归样本；按业务、问法、长尾、知识版本和权限场景分桶，不只报告一个平均值。

上线先影子流量或小流量灰度，再通过合适的随机实验观察问题解决率、重复咨询、人工转接、用户负反馈和延迟。转人工减少不一定是好事：如果系统错误地把问题标成已解决，表面指标会改善却损害用户。

将主目标与护栏预先写清楚：例如在高风险错误不增加、成本和延迟可接受的前提下，提高有效解决率。只有端到端质量与业务反馈共同支持，才有依据说客服系统真正变好了。

余弦相似度、欧几里得距离和曼哈顿距离有什么区别？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

余弦相似度衡量方向，欧几里得距离衡量直线距离，曼哈顿距离衡量各坐标绝对差之和。对向量 x、y，可写为：

\begin{aligned}
\mathrm{cos}(x,y)&=\frac{x^\top y}{\lVert x\rVert_2\lVert y\rVert_2},\\
d_2(x,y)&=\sqrt{\sum_i(x_i-y_i)^2},\\
d_1(x,y)&=\sum_i\lvert x_i-y_i\rvert.
\end{aligned}

余弦要求非零向量；若向量都已单位归一化，则平方 L2 距离等于 2 - 2 × 余弦相似度，两者排序等价。未归一化时，向量长度会改变 L2 和内积的排序，这个等价关系不再成立。L1 的几何性质也不能简单替代模型训练所用的度量。

检索时按模型推荐度量及验证结果选择，并区分相似度越大越好与距离越小越好。pgvector 的余弦距离 <=> 通常可由 1 - distance 转成余弦相似度；L2 使用 <->，L1 使用 <+>。索引是否支持所选类型和度量，应按实际扩展版本确认。

零向量与缺失向量应在入库时显式处理。 余弦分母为零时没有定义，不能悄悄返回“相似度为 1”。对空文本、编码失败、NaN 和无穷值，应保留失败原因并阻止无效向量进入检索。归一化也应只对范数满足要求的向量进行，且与模型使用契约一致。

单位化后的 L2 与余弦排序等价，是关于相同候选向量和精确数学距离的结论。两种 ANN 索引采用不同参数或近似搜索路径时，实际返回集合未必逐项一致；工程评估需要把度量关系与近似算法误差分开。

你做的知识库体系和Vicky这类工具本质区别是什么？

回答：

如果 Vicky 指通用知识库/AI 助手类工具，可以从定位、数据结构、验证能力和业务集成来区分。

通用知识库工具通常强调快速导入文档、检索问答和对话体验，适合个人或团队做知识查询。但项目里的知识库体系如果服务视频生成 Agent，本质上不是“问答工具”，而是 Agent 的可执行知识底座。

第四，系统集成不同。业务知识库要和工作流、工具链、评测系统、日志系统连接，成为生产链路的一部分。总结来说，通用工具是 knowledge assistant，项目知识库更像 workflow-grounded knowledge system。

你的 RAG 是用什么技术实现的？

回答：

按这个项目的真实口径，RAG 使用 BGE-large-zh-v1.5 做中文 Embedding，向量维度为 1024；数据写入 Milvus，并使用 IVF_FLAT 索引；查询阶段先召回 Top-20，再用 BGE reranker 精排，最终选取 Top-5 进入生成上下文。

完整链路应从数据治理讲起。文档解析后保留标题层级、段落、表格和来源 metadata；切片优先遵循语义边界，并使用父子块或邻接扩展保留上下文。需要注意，LangChain RecursiveCharacterTextSplitter 默认的 chunk_size=512 通常按字符长度函数计算，不天然等于 512 Token；如果要控制模型预算，应使用 tokenizer-aware splitter。

Milvus 的索引和查询参数需要一起调优。IVF_FLAT 的 nlist 决定聚类桶数量，查询 nprobe 决定探测多少桶；召回率、延迟和内存要通过数据集评测确定。向量写入前是否归一化、Milvus 使用 COSINE/IP/L2 哪种 metric，也必须与 Embedding 训练和检索配置一致。

你的知识库内容是不是基于spec文档做归纳总结生成的？

回答：

可以回答：一部分是，但不能只靠归纳总结。Spec 文档是知识库的重要来源，因为它包含业务规则、接口说明、产品约束和流程定义。但如果直接把 spec 丢进向量库，效果通常不稳定：文档长、结构复杂、版本变化快，模型容易断章取义。

更好的做法是分层处理。第一层保留原始 spec，作为可追溯证据。第二层抽取结构化规则，例如字段定义、接口约束、流程步骤、异常情况、示例。第三层生成面向 Agent 的操作手册，例如什么时候调用哪个工具、参数怎么填、失败怎么处理。第四层建立验证规则，例如 schema、正则、状态机或单元测试。

你设计的可验证知识库，打算通过什么方案完成验证？

回答：

可验证知识库的目标不是“看起来回答对”，而是能证明它的检索、引用和执行建议是可靠的。可以从离线验证、在线验证和人工闭环三层做。

离线层先构建 golden set。把真实问题、标准答案、证据文档位置、允许引用的段落标出来。评估检索时看 recall@k、MRR、nDCG、证据命中率；评估生成时看答案正确性、引用一致性、拒答准确率。

规则层做确定性校验。对结构化知识，例如接口参数、字幕规范、视频比例、工具调用 schema，可以用程序校验，而不是让模型自由判断。凡是能写成规则的，就不要交给模型猜。

在线层做 trace 和 badcase 回流。每次 Agent 使用知识库时记录 query、召回 chunk、rerank 分数、引用、最终动作和用户反馈。失败样本进入标注池，更新知识库、prompt、切分策略和评测集。

人工层处理争议和高风险内容。比如品牌规范、合规内容、商业素材使用等，需要人工审核或双人标注。

最终形成闭环：知识入库要有来源和版本，知识使用要有引用和 trace，知识效果要有评测，知识错误要能回滚和修复。这才叫可验证。

加入模态类型编码（Modality Type Embedding）的作用是什么？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐ (3/5)

模态类型编码（也叫 Segment Embedding、Modality Token）的作用是让模型知道序列里每个 token 来自哪种模态。

经过投影器对齐，视觉 token 和文本 token 在向量空间里已经比较接近，这本来就是对齐要达到的效果。可模型在一些环节仍要区分两者，主要体现在三个方面：

  1. 损失计算：文本 token 参与 LLM 的语言建模损失，视觉 token 一般不参与。

  2. 计算路径：不同模态可能走不同的计算路径，例如 Flamingo 在冻结的 LLM 层之间插入门控交叉注意力层，让文本 token 去查询视觉特征[40]。

  3. 内容边界：多模态指令微调中，模型要分清哪部分是用户问题、哪部分是图像内容。

实现方式有两种：

  1. 可学习的模态类型嵌入：给每种模态分配一个可学习向量，加到该模态所有 token 上。ViLT 就给文本 token 和图像 patch token 分别加了模态类型嵌入，做法来自 BERT 的 segment embedding[13,45]。

  2. 特殊标记包裹：用 <img>...</img>、<audio>...</audio> 这类特殊 token 包住对应模态的内容，让 LLM 自己学会模态边界。Qwen-VL 用 <img> 和 </img> 包住图像特征[43]，LLaVA 用 <image> 占位符标出图像插入的位置[8]，InternVL 也用 <img>、</img> 加图像上下文 token[46]。这种方式不额外加嵌入向量，模态信息体现在序列结构里。

位置编码回答 token 在哪，模态类型编码回答 token 属于哪种模态，两者互不干扰，常常一起用。当前主流的多模态大模型大多用特殊标记就够了；需要对不同模态做差异化处理时，才会显式加模态类型嵌入。

面试速答：模态类型编码让模型知道每个 token 来自哪种模态，用于区分哪些 token 算语言建模损失、走哪条计算路径、问题和图像的边界在哪。实现上可以像 ViLT 那样加可学习的模态嵌入，也可以像 Qwen-VL、LLaVA 那样用特殊标记包裹，目前主流用后者。

动态分块方案如何工作？有何优缺点？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐⭐ (5/5)

动态分块（Dynamic Tiling）是目前最常用的高分辨率方案。高分辨率图像被切成多个小块，每块单独过 ViT，最后把各块的输出拼成一条长 token 序列送进 LLM。

InternVL-1.5 采用了动态分块。它按原图长宽比把图像切成若干 448×448 的块，训练时 1 到 12 块，测试时最多放到 40 块，每块单独编码后拼接，另外保留一张缩略图提供全局信息[30]。到 InternVL3.5，这套做法仍在沿用[31]。

优势

  1. 复用预训练权重：编码器不用改，预训练好的 ViT 权重直接复用，迁移成本低。

  2. 方便并行：各块独立编码，可以并行处理。

  3. token 数可控：设定分块数上限，就能把单图的总 token 数控制住。

不足

  1. 块之间没有信息交互：每块只看到自己，一张跨两个块的长表格可能因为缺上下文被解析错。

  2. token 序列变长：分块多了，拼出来的序列可能有几千个 token，压力转到 LLM 端。ViT 端的二次方问题缓解了，LLM 端的 KV Cache 和推理延迟却上去了。

所以动态分块常和后面讲的 token 压缩、稀疏注意力一起用。

面试速答：动态分块按原图长宽比把高分辨率图像切成多个块，每块单独过 ViT 后拼接，再加一张缩略图补全局信息，InternVL-1.5 是代表。优点是复用 ViT 权重、易并行、token 数可控；缺点是块之间没有交互，拼接后序列变长，压力转到 LLM 端。

基于原生NTP任务Qwen模型，如何适配下游检索监督训练

回答：

原生 NTP 训练的是条件语言建模能力，不等于已经具备可直接用于向量检索的 Query-Item 表示。适配时可以复用 Qwen Transformer 主干，在 Query 和 Item 两侧共享或部分共享参数，取有效 token 的最后隐状态、特殊 pooling token 或 attention pooling，再经过投影头得到向量：

\[ e_q=f_\theta(q),\qquad e_i=g_\theta(i) \]

训练构造正样本 \((q,i^+)\) 和负样本 \(i^-\)，使用余弦/点积相似度配合 InfoNCE、Multiple Negatives Ranking Loss 或 pairwise loss。批内 Item 可作为负样本，同时加入经过曝光约束和语义过滤的 hard negative。训练后 Query 与 Item 必须使用一致的 tokenizer、池化、归一化和向量库 metric；Item 向量离线入库，Query 向量在线计算。

如果需要保留生成能力，可以采用多任务目标：

\[ \mathcal{L} =\lambda_{NTP}\mathcal{L}_{NTP} +\lambda_{retrieval}\mathcal{L}_{retrieval} \]

交叉编码精排则把 Query 和 Item 拼接输入模型，获得更充分的语义交互，但无法提前计算所有 Item 向量，在线成本更高。池化时不能取 padding 位置，也不能忽略 attention mask；不同长度要按有效 token 做 masked mean 或使用明确 EOS 表示。

本质上，这是把生成式语言表示迁移到可检索的度量空间，同时用检索监督塑造“相似样本靠近、难负样本分离”的几何结构。

多模态Embedding设计经验、图文对齐方案与主流对齐方式

答：多模态 Embedding 的目标是把文本、图像、视频、音频等不同模态映射到可比较、可检索、可聚类的统一语义空间。设计时要先明确业务目标：是做图搜文、文搜图、视频搜索、商品检索、推荐召回，还是给多模态大模型做特征接入。不同目标决定结构不同。

如果是大规模检索，常用双塔结构。文本塔编码 query、标题、描述、字幕，图像塔编码封面、关键帧或商品图，视频还可以加入抽帧、ASR、OCR、标签和剧情简介。各模态经过 projection head 映射到统一维度，并做 L2 normalization，最后用点积或余弦相似度检索。优点是可以离线建库、在线 ANN 召回，延迟低；缺点是 query 和 item 缺少细粒度交互。

如果是精排或复杂理解，可以使用 cross-encoder 或多模态 LLM。把 query 和候选图文一起输入模型，通过 cross-attention 或统一 token 序列建模细粒度关系，输出相关性分数。优点是精度高，缺点是成本高，不适合全库召回。

Embedding 设计经验包括：

  1. 共享空间维度要兼顾效果和索引成本。常见维度是 256、512、768、1024。维度越大表达力越强，但索引存储和检索成本越高。

  2. 向量归一化很重要。归一化后点积等价于余弦相似度，训练和检索更稳定。

  3. 多模态 item 最好保留多路向量。比如一个视频可以有封面向量、关键帧向量、字幕向量、标题向量、剧情简介向量，召回时做多路融合，而不是强行压成一个向量。

  4. 负样本质量决定上限。随机负样本容易，hard negative 才能让模型学会区分相似但不匹配的内容，例如同演员不同剧、同题材不同片段、相似封面不同语义。

  5. 业务行为要谨慎使用。点击、播放时长、完播率是弱监督信号，但有曝光偏差和位置偏差，需要采样校正。

主流图文对齐方式包括：

  1. CLIP 式对比学习：图像和文本分别编码，通过 InfoNCE 拉近匹配对、推远非匹配对，适合大规模检索和零样本迁移。

  2. Image-Text Matching：把图文对输入跨模态模型，判断是否匹配，适合精排和细粒度对齐。

  3. Caption/Language Modeling：给定图像生成文本，或给定图文上下文预测下一个 token，适合多模态生成和问答。

  4. Q-Former/Resampler 对齐：用少量 learnable query 从视觉特征中提取语言模型可用的视觉 token，典型如 BLIP-2。

  5. Projector 对齐：用线性层或 MLP 把视觉编码器输出映射到 LLM embedding 空间，典型如 LLaVA。实现简单，但依赖视觉编码器已有的语义质量。

  6. 蒸馏对齐：用强 MLLM、CLIP 或人工标注作为教师，训练轻量 embedding 模型或检索模型。

在爱奇艺这类视频场景，图文对齐不能只看封面和标题，还要利用视频帧、OCR、ASR、剧情简介、演员、标签和用户行为。一个好的多模态 Embedding 系统通常是“多模态内容理解 + 多路召回 + reranker 精排 + 业务反馈闭环”。

多轮 RAG 为什么比单轮问答复杂？

多轮对话中，用户可能使用省略、代词、追问和上下文依赖表达。例如“它支持退款吗？”中的“它”可能指上一轮提到的产品。若直接检索原始问题，检索系统无法理解真实意图。

如何优化 RAG 链路的性能

回答：

先测量再优化，把链路拆成检索前处理、Embedding、检索、重排、上下文组装、预填充和解码，记录各阶段耗时、P50/P95、吞吐、费用与质量指标。首 token 延迟和完整回答耗时要分别看，流式输出改善等待体验，并不必然减少后端总耗时。

检索侧可以复用已就绪索引、批量构建向量、优化权限与元数据过滤、调节近似检索的搜索预算，并在延迟允许时并行执行关键词和向量召回。不同引擎对过滤与近似检索的组合实现不同，不能假设扩大 Top-K 就一定解决过滤后候选不足。候选数、重排规模和最终上下文长度需要分别调优。

模型侧优先减少没有实际收益的改写与规划调用，选择足够胜任的模型，裁剪重复证据和冗长工具返回值，利用可用的批处理与前缀缓存。重排可以只用于困难问题或较大候选集，但路由策略应经过验证；简单问题不能为了固定流程无条件经过所有模型节点。

缓存提升重复请求效率，也可能返回过期或越权内容。缓存键应绑定 Workspace、访问范围、文档或索引版本和查询规范化方式；权限撤销与文档更新需要有失效机制。语义答案缓存尤其要防止相似问题实际包含不同日期、实体或限定条件。

最终用固定评测集做消融，观察 Recall@K、答案正确性、证据支持、失败率、延迟和成本的共同变化。把 K 从 50 降到 5 可能加快重排，却漏掉唯一证据；把上下文缩短可能降低预填充，却丢失例外条款。优化目标应是达到业务质量门槛下的资源效率，并通过并发与长尾样本验证。

延迟分析示例。 假设一个请求的两路检索分别耗时 40 ms 和 70 ms，融合与重排 90 ms，上下文组装 10 ms，模型从收到请求到首 token 需要 300 ms。忽略排队、网络传输及调度开销，两路检索串行时约为 510 ms，并行时约为 470 ms；并行阶段取较慢分支的耗时。即使检索完全免费，其余阶段仍需约 400 ms。这组假设数据说明，应沿关键路径定位瓶颈。各阶段的 P95 不能简单相加就当作端到端 P95，真实高分位延迟需要保留同一次请求的 trace，在目标并发下统计。

如何观察模型召回了哪些块？

回答：

需要给检索链路建立可回放的 trace。每次请求至少记录：原始 query、改写后的检索 query、过滤条件、Embedding/索引版本、初召 chunk ID 与分数、融合前后的排名、rerank 分数、最终进入 Prompt 的片段、Token 数和引用 ID。

如何设计一个记忆检索流程？历史信息应该如何筛选、存储和召回？

回答：

可以把流程设计成“写入门控 -> 多路存储 -> 查询召回 -> 重排注入 -> 反馈更新”。

  1. 写入门控： 从对话和工具事件中提取候选事实，判断是否稳定、可复用、由谁确认、是否敏感，过滤寒暄、一次性状态和未经证实的推断。对用户偏好最好让用户确认或保留低置信标记。
  2. 分型存储： 身份、权限和稳定偏好放结构化数据库；事件放带时间和版本的事件表；语义经验写入向量/全文索引；大对象只保存引用。不要把所有聊天原文无差别塞进一个向量库。
  3. 查询构建： 从当前目标、实体、时间约束和用户/项目作用域生成检索条件；必要时做查询改写，但保留原始查询，避免改写错误丢失关键条件。
  4. 多路召回： 结构化过滤、关键词、向量和时间/实体索引并行召回，去重并合并；先执行权限过滤，不能在召回后才把越权内容交给模型。
  5. 重排与注入： 按相关性、时效、置信度、来源可靠性、冲突状态和 Token 预算重排；注入时标记为记忆而非当前事实，并保留来源和更新时间。
  6. 反馈更新： 记录是否被引用、是否帮助任务成功、是否被用户纠正；纠正应产生新版本或失效旧版本，而不是静默覆盖审计记录。

评价要看记忆 Precision/Recall、错误记忆引用率、任务成功率、重复询问减少量、跨用户串线率、删除可达性和 Token 成本。长期记忆必须作用域隔离，且要支持用户查看、修改和删除，这是功能正确性和隐私合规的一部分。

如何设计知识库，包括知识的准确性和更新机制

回答：

知识库应同时管理内容、身份、版本、权限和质量。原始文件保存为可追溯快照，业务记录维护文档 ID、版本、生效时间、适用范围、负责人和状态；解析产物、chunk、向量与全文索引记录各自配置版本。内容哈希帮助检测变化，但不能代替文档业务身份和访问权限。

删除和撤权必须覆盖索引、原文件读取、证据扩展以及缓存，不只是删一条数据库记录。对于历史报告，需按保留政策处理快照和引用；不能为了历史可复现继续向已撤权用户暴露内容。模型或切分策略改变时也可能需要重建索引，并维持灰度与回滚能力。

如果RAG系统出现召回效果差的问题，你会如何定位？会优先检查Embedding、Chunk策略、Query Rewrite、Hybrid Search还是Rerank？

回答：

我会先把“召回差”拆成索引覆盖问题、候选召回问题和排序问题，而不是直接调 Rerank。用带有标准答案证据块的离线数据集做逐层回放，记录原始 Query、改写 Query、召回候选、分数、过滤条件、Rerank 结果和最终引用。

定位顺序通常是：

  1. 数据与权限： 文档是否被成功解析和入库，版本是否最新，权限过滤是否误删，元数据是否正确，目标证据是否存在。
  2. Chunk： 证据是否被切碎、标题是否丢失、块是否过长或过短、重叠是否合适，父子关系和去重是否正确。
  3. Embedding： 查询和文档是否使用同一模型与相同归一化方式，模型是否支持中文和领域术语，向量库距离度量和索引参数是否匹配。
  4. Query Rewrite： 改写是否改变了原意、丢失实体和否定条件；把原 Query 与改写 Query 都纳入召回，避免错误改写成为单点故障。
  5. 召回策略： 对术语、编号、产品名、精确短语和数值问题，BM25 往往补足向量召回；通过 RRF 或校准后的加权融合比较增益。
  6. Rerank： 只有候选集中已经包含正确证据时，Rerank 才能解决排序问题；如果 Top-N 候选里没有证据，换 Reranker 不能补回缺失文档。

所以我会先验证候选集 Recall，再判断是否是排序问题。最终用分层实验比较 Base Embedding、Chunk、Query Rewrite、Hybrid 和 Rerank 的增量，不用单个线上案例决定参数。

对比Memory机制与RAG检索增强的区别、优势和落地场景差异

回答：

Memory 和 RAG 都是在解决“模型上下文之外的信息如何进入推理”的问题，但信息来源和使用方式不同。

RAG 面向外部知识。它把文档、知识库、数据库、网页或业务资料切分、索引、召回、重排，再把相关证据放进上下文。优势是知识可更新、可引用、可审计，适合政策问答、企业知识库、商品知识、操作手册、字段定义等动态知识场景。它的核心指标是召回率、证据命中率、引用一致性、答案准确率和拒答能力。

Memory 面向用户、任务或系统的持续状态。短期记忆保存当前会话中的目标、约束、已完成步骤、工具返回和错误信息；长期记忆保存用户偏好、历史行为、常用模板、项目上下文和个性化信息。优势是能让系统跨轮次、跨任务保持连续性，适合 Agent、多轮协作、AI Coding、个人助手、商家运营助手等场景。

落地上，RAG 更像“查资料”，Memory 更像“记住我和任务”。两者都不能无脑塞 prompt。RAG 要做 chunk、embedding/BM25、rerank、引用和过期；Memory 要做写入策略、隐私权限、冲突消解、遗忘机制和重要性评分。一个成熟 Agent 通常同时需要 RAG 和 Memory：RAG 负责事实证据，Memory 负责任务连续性和个性化。

对话超过上下文限制后怎么处理？滑动窗口、摘要压缩和向量召回怎么选择？

回答：

三种方法解决的问题不同。滑动窗口保留最近若干轮，简单、低延迟，适合局部连续且旧信息价值快速衰减的闲聊或短任务；缺点是早期目标、承诺和约束可能被直接丢弃。因此系统规则、当前目标和结构化任务状态不应跟随窗口滑走。

向量召回适合跨很长历史按当前问题找相关片段，但相似度不等于重要性，也可能漏掉措辞不同的约束。应结合关键词、实体、时间、权限和 Rerank，并防止把旧版本或模型推测当成当前事实。

怎么保证检索召回的准确率？如何验证？

回答：

先把“准确率”拆成可测目标。检索阶段关注是否找齐所需证据和返回结果有多少相关内容；生成阶段关注回答是否正确、是否被证据支持以及有没有遗漏关键条件。只看最终回答是否流畅，无法判断召回质量。

投影器中加入位置编码（Position Embedding）的作用是什么？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐ (3/5)

ViT 和 LLM 各有自己的位置编码，但在投影器里或投影器之后补充位置信息，仍然有用。

问题出在跨模态拼接之后。原始 ViT 和 CLIP 的 ViT 给每个 patch 加的是可学习的一维绝对位置编码，按光栅顺序编号；ViT 论文附录 D.4 的消融显示，换成显式的二维位置编码没有明显收益，学到的一维编码本身已经反映出图像的行列结构[1,44]。从 Qwen2-VL 开始，Qwen 系列的视觉编码器去掉了绝对位置编码，改用 2D-RoPE 显式编码行列坐标[34]。LLM 用的是一维序列位置编码（如 RoPE），只区分先后顺序。视觉 token 经投影器投进 LLM 空间后，会和文本 token 拼成一条一维序列。LLM 的一维位置编码只能告诉模型“视觉 token A 排第 10 位、B 排第 11 位”，分不清 A 在 B 的左边还是上方。ViT 特征里虽然已经混入了位置信息，LLM 这一层却没有显式的二维坐标。

解决方法主要有两种：

  1. 在交叉注意力压缩时补二维位置信息：Qwen-VL 用一个单层交叉注意力模块和 256 个可学习 query 压缩视觉特征。论文在交叉注意力的 query-key 对中加入二维绝对位置编码，用来减少压缩过程中位置细节的损失[43]。

  2. 重新设计多模态位置编码：Qwen2-VL 提出的 M-RoPE（Multimodal RoPE）把旋转位置编码拆成时间、高度、宽度三个分量，视觉 token 用高、宽分量编码空间位置，视频再加上时间分量；文本 token 三个分量取相同的值，退化成普通的一维 RoPE[34]，如图 2-6 所示。这样 LLM 既知道时间顺序，也知道空间布局。

缺少空间位置信息时，“图中左上角的物体是什么”“红框在蓝框的哪一侧”等需要空间推理的问题更容易答错。

图 2-6 一维 RoPE 与 M-RoPE 对比示意图

面试速答：视觉 token 拼进 LLM 的一维序列后，一维位置编码只能表示先后，分不清左右上下。补位置编码就是把二维空间信息带进 LLM，做法有两种，一是像 Qwen-VL 那样在交叉注意力压缩时加入二维绝对位置编码，二是像 Qwen2-VL 的 M-RoPE 那样把位置拆成时间、高、宽三个分量。

拒绝采样、Best-of-N、Reward Reranking 与 RL 优化有什么关系？

拒绝采样从模型分布中采样候选，然后用规则或奖励阈值筛选：

\[ y\sim\pi_{\theta}(\cdot|x),\quad \text{accept if } r(x,y)>\tau \]

Best-of-N 采样多个候选，选择奖励最高者：

\[ y^*=\arg\max_{i=1,...,N}r(x,y_i) \]

Reward Reranking 对候选重新排序，本质上是推理时优化：

\[ \max_{y\in \mathcal{Y}_{sample}} r(x,y) \]

RL 优化则直接更新模型参数，使策略分布更偏向高奖励区域：

\[ \max_{\theta}\mathbb{E}_{y\sim\pi_{\theta}}[r(x,y)]-\beta D_{KL}(\pi_{\theta}\|\pi_{\text{ref}}) \]

关系：

  • 拒绝采样和 reranking 不改模型参数。
  • RL 会改变模型分布。
  • Best-of-N 可用于生成高质量 SFT/DPO 数据，也可作为推理增强。
  • 如果 reward model 有漏洞，Best-of-N 和 RL 都可能放大奖励黑客问题。

提示工程、RAG、SFT、RL、RLHF 应该分别在什么场景下应用？例如：快速迭代基本能力（提示工程）、用户个性化记忆（提示工程）、案例库和事实知识（RAG）、输出格式和语言风格 （SFT）、领域深度思考能力和工具调用能力（RL）、根据用户反馈持续优化（RLHF）

提示工程（Prompt Engineering）

  • 快速迭代和调试模型基本能力
  • 实现简单用户个性化和上下文记忆
  • 无需训练，低成本实验方案

RAG（Retrieval-Augmented Generation）

  • 利用外部案例库和事实知识补充模型知识盲点
  • 实时访问动态或专业知识库
  • 提高生成内容的准确性和时效性

SFT（Supervised Fine-Tuning）

  • 调整输出格式、语言风格和固定任务表现
  • 融合专业领域或企业特定风格
  • 提升模型对特定指令的响应能力

RL（Reinforcement Learning）

  • 培养模型的深度思考、策略选择和工具调用能力
  • 优化复杂任务的长期回报表现
  • 适合交互式和多步骤决策场景

RLHF（Reinforcement Learning from Human Feedback）

  • 根据用户或专家反馈持续优化模型输出质量
  • 处理主观偏好、多样性和安全性问题
  • 提升模型对人类意图的精准理解与执行

提示工程、多模态检索增强生成、微调和蒸馏分别对应四种缺口，即可行性、知识、行为和成本，如图 6-2 所示。数据量和迭代周期的经验对照如表 6-1 所示。各条路径弥补的缺口及其代价逐条说明如下：

  1. 提示工程。 提示工程是验证阶段的默认起点，不需要训练，几小时即可迭代一版，配合少量示例和输出模板就能检验可行性。它无法注入成规模的领域知识，提示越长每次调用越贵，对格式的约束也只是软约束。

  2. 多模态 RAG。 RAG（Retrieval-Augmented Generation，检索增强生成）弥补的是知识缺口。纯文本 RAG 处理图文文档时要先 OCR 再分块，版面和图表信息在转换中丢失。ColPali 改为按页做视觉检索：它在 PaliGemma-3B 之上加一层投影，把每个文本 token 和图像 patch 的输出映射为 128 维向量，检索时采用后期交互（late interaction）的 MaxSim 打分[1]，即 query 的每个向量在页面所有 patch 向量中取最大内积，再对 query 侧求和：

\[ s(q,d)=\sum_{i\in q}\max_{j\in d}\mathbf{E}_{q_i}^{\top}\mathbf{E}_{d_j} \]

其中 $\mathbf{E}_{q_i}$ 为 query 的第 $i$ 个向量，$\mathbf{E}_{d_j}$ 为页面的第 $j$ 个 patch 向量。图表、印章和手写批注保留在页面图像里，不需要先做 OCR；手册改版时只需替换索引中的页面，不必为新知识重新训练。提示工程同样不需要重新训练，但装不下整个文档库。

  1. 微调。 微调弥补的是行为缺口。模型不认识领域术语、输出必须严格符合下游的 JSON Schema、话术需要统一，这三种信号都指向微调。LoRA（Low-Rank Adaptation，低秩适配）冻结原权重 $W_0$，只训练低秩增量[2]：
\[ W' = W_0 + \Delta W = W_0 + BA,\qquad B\in\mathbb{R}^{d\times r},\ A\in\mathbb{R}^{r\times k},\ r\ll\min(d,k) \]

其中 $r$ 为秩，可训练参数因此从 $dk$ 降到 $r(d+k)$，LoRA 论文的实验显示很小的秩往往已经足够[2]。全参数微调需要更多数据和算力，业务侧更常用 LoRA。

  1. 蒸馏。 蒸馏弥补的是成本缺口。任务固定、流量增大之后，用大模型批量生成带推理链的标注，再训练一个专用小模型。Hinton 等人提出的蒸馏目标是硬标签交叉熵与教师软分布 KL 散度的加权[3]：
\[ \mathcal{L}_{\text{distill}} = \alpha\,\mathcal{L}_{\text{CE}}\bigl(y,\,p_s\bigr) + (1-\alpha)\,\tau^{2}\,\mathrm{KL}\bigl(p_t^{\tau}\,\Vert\,p_s^{\tau}\bigr) \]

其中温度 $\tau$ 使教师分布 $p_t$ 更平滑，学生 $p_s$ 因此能学到类别之间的相对关系，$\alpha$ 为两项损失的权重。蒸馏的代价是模型失去通用性，任务边界一旦变化就要重新蒸馏。

搜索中 RAG的向量检索会受到长尾商品影响，你会如何缓解?

回答：

用混合召回降低纯向量检索对长尾的偏置：BM25/关键词、类目与属性过滤、热门与长尾配额、语义向量和交叉编码器重排组合。对低频商品增强描述、属性和图谱特征，按类别和频次分层评测 Recall、曝光公平、转化与误召回。

既然输入对象已经明确，是否完全可以绕过知识库检索？

回答：

可以。输入已知、内容规模可控且任务不需要外部知识时，直接读取指定版本的完整内容即可。完整差异分析也可以走“解析—结构化切分—全量对齐—逐单元分析—汇总”的路径，整个过程不需要向量召回。

有哪些常见的Embedding方案？

方案 注入位置 核心思想 主要特点
绝对位置 Embedding 通常与 Token Embedding 相加 每个位置有一个向量或确定函数值 直观；学习式方案常受训练长度限制
RoPE 旋转 Q、K 的成对维度 用与位置相关的旋转使点积体现相对位移 兼顾绝对位置注入与相对关系，生成式 LLM 常用
ALiBi Attention Logits 按距离加入线性负偏置 不增加位置向量，偏好近邻，外推形式简单

绝对位置编码 可以是固定正弦函数，也可以是可学习位置向量。它直接表示“这是第几个位置”，但可学习表通常不能自然处理表外位置。

RoPE 不需要把位置向量直接加到输入上，而是对每个注意力头的 Q、K 做位置相关旋转。旋转后的点积会显式依赖相对位置差，因此适合自注意力。注意：采用 RoPE 时，“词嵌入加位置嵌入”并不是准确描述。

ALiBi 在注意力得分中加入与距离成比例的偏置。距离越远，惩罚通常越大。它参数少、实现直接，但归纳偏置与 RoPE 不同。

检索使用关键词、向量还是混合检索？

回答：

关键词检索适合条款编号、产品名称、金额和专有名词等精确匹配；向量检索适合语义相近但用词不同的问题。混合检索让两路分别返回候选，再融合和重排，适合同时存在精确字段与自然语言表述的资料。

例如用户询问“延误赔偿”，关键词可以定位包含明确词项的条款，向量检索可以补充“未按承诺时限送达”的相关描述。两路都必须先受授权范围和文档版本约束。融合可采用基于排名的 RRF，避免直接相加不同量纲的分数；之后在控制成本的前提下用重排模型重新判断相关性。

混合检索也不是必选项。小型结构化文档可能依靠章节编号和全文检索就足够，向量检索可能引入不相关候选。用相同标注集比较单路与混合方案，并报告各类问题上的收益和失败，才能说明选型合理。

检索召回之后，结果会直接交给模型吗？中间还有哪些处理环节？

回答：

召回结果通常还需要权限复核、去重、融合或重排、上下文补全和 token 预算控制。对比任务还要检查两侧版本是否都有证据，处理互相冲突或含有例外条件的片段，并保留标题、页码和版本标识。

随后把用户问题、任务规则和证据内容分开组织，明确文档内容是数据。给证据分配稳定引用标识，要求模型输出符合约定的结构。分数低或证据不足时，可以在授权范围内扩大检索、读取指定章节，或者明确无法确认，而不是强行生成肯定答案。

模型返回后验证结构、引用是否存在、引用是否来自本次允许的版本、关键数字是否一致，以及结论是否得到证据支持。引用格式正确只能证明能定位，不能证明语义蕴含关系成立；关键业务结论仍需要规则校验或人工抽检。证据校验失败应触发修复、降级或复核，不直接发布正式报告。

检索打分选用余弦相似度，不直接使用模型logits的理由

回答：

生成模型 logits 和检索相似度不在同一语义空间。Qwen logits 通常是词表大小的向量：

\[ \mathbf{z}_t=W_oh_t+b \]

它表示上下文 \(h_t\) 下下一个 token 的条件分布，受 prompt、位置、tokenizer、回答长度和词表影响。两个 Item 的词表 logits 不能天然作为稳定的 Query-Item 距离。

余弦相似度作用于经过同一表示学习目标训练的固定向量：

\[ \operatorname{cos}(q,i) =\frac{q^\mathsf{T}i}{\lVert q\rVert_2\lVert i\rVert_2} \]

它允许 Query 与 Item 独立编码，Item 向量离线建立 ANN 索引；归一化后尺度更稳定，固定维度也便于缓存、量化和分片。

如果用生成模型 logits 对每个候选 Item 判断相关性，本质上是 Cross-Encoder：需要把 Query 和 Item 一起送入模型，精度可能更高，但每个候选都要做昂贵前向，不能承担大规模初召。常见分层方案是双塔向量初召，Cross-Encoder 或 log-prob 精排。

余弦也不是天然正确，必须确认 Query/Item 向量由匹配目标训练，入库与查询使用一致的归一化和 metric，并用 Recall@K、nDCG、延迟和线上指标验证。

检索融合的具体流程是什么？召回后有没有做 Rerank？

回答：

一个比较完整的检索融合流程可以分成六步。

第一步是 query 预处理。包括去噪、分词、大小写归一、同义词扩展、实体识别、时间和权限条件解析。复杂问题还可以做 query rewrite 或 query decomposition，把一个大问题拆成多个子问题。

第二步是多路召回。一路走向量检索，用 embedding 从向量库召回 topK dense chunks；一路走 BM25 或倒排索引，召回 topK sparse chunks；必要时还可以加入标题召回、FAQ 精确匹配、知识图谱、数据库过滤、历史对话记忆等通道。

第三步是归一化与融合。如果用分数融合，需要把 cosine similarity、BM25 score 等不同分布的分数归一化后加权；如果用 RRF，就按各路排名进行融合。融合后做去重，尤其父子索引场景下要把同一 parent 下高度重复的 child 合并。

第四步是过滤。按权限、业务线、文档类型、时间有效性、语言、版本号等 metadata 过滤，避免召回到用户无权访问或已经过期的内容。

第五步是 Rerank。召回阶段追求高召回，排序往往不够精确，所以通常会加 reranker。Reranker 可以是 cross-encoder、bge-reranker 这类相关性模型，也可以是轻量 LLM rerank。它会把 query 和候选 chunk 成对输入，重新判断相关性。

第六步是上下文组装。根据 rerank 分数、token budget、parent 合并、去重、多样性和引用需求，选择最终进入 prompt 的 chunk。

所以召回后通常要做 Rerank，特别是在混合检索和父子索引场景中。原因是召回阶段更像粗筛，Rerank 能修正向量检索“语义相关但不回答问题”、BM25“词命中但语义不对”、多路融合分数不可比等问题。

滑动窗口注意力、稀疏注意力、分块注意力如何降低复杂度？

全量注意力复杂度：

\[ O(S^2D) \]

滑动窗口注意力让每个 token 只关注附近 \(w\) 个 token：

\[ O(SwD) \]

其中 \(w \ll S\)。它适合局部依赖强的任务，但远距离信息需要通过层数堆叠或全局 token 间接传递。

稀疏注意力只计算注意力矩阵中的部分位置。若每个 token 关注 \(k\) 个位置：

\[ O(SkD) \]

常见模式包括局部窗口、跨块全局 token、随机稀疏、块稀疏等。

分块注意力把序列分块后在块内做全注意力，块间通过摘要 token、递归状态或检索机制传递信息。

对比：

  • 滑动窗口：实现简单，适合长文本局部建模。
  • 稀疏注意力：更灵活，但 kernel 和路由复杂。
  • 分块/检索：适合超长文档，但容易丢失跨块细粒度依赖。
  • FlashAttention：降低显存 IO，但数学上仍是全量注意力，不改变 \(S^2\) 理论计算量。

用户身份、偏好这类明确字段，适合用向量检索吗？

难度评分：⭐⭐ (2/5) | 考察频率：⭐⭐⭐⭐ (4/5)

用户身份、租户、角色和明确偏好字段应先用结构化存储和精确查询。身份由认证链路建立，权限由服务端策略验证；相似用户、相似名字或相似偏好都不能作为身份匹配依据。

例如 user_id=U17 对应的语言偏好为 zh-CN，按主键读取比向量检索更明确、便于更新和删除。带范围与时效的偏好应同时记录版本、适用场景、更新时间和用户确认状态。

向量检索适合召回长文本经历、历史任务中的语义线索，但必须在已确定的用户或租户范围内进行。找到“喜欢周末上课”的相似记忆之后，也应检查它是否仍有效、是否只针对一次活动，以及是否与当前明确输入冲突。

知识图谱和 RAG 有什么关系？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐ (4/5)

知识图谱用实体和关系表示结构化知识。

RAG 用检索增强生成，让 LLM 在生成前获取外部知识。

两者关系：

  • 知识图谱可作为 RAG 的结构化知识源。
  • 图谱能提供实体关系、路径推理和约束。
  • RAG 能弥补纯知识图谱表达不自然、覆盖不足的问题。
  • Graph RAG 将文档 chunk、实体、关系、社区结构结合起来。

对比：

维度 知识图谱 RAG
知识形态 结构化实体关系 文档、向量、图、数据库
优势 可解释、关系清晰 覆盖广、生成自然
难点 构建和维护成本高 检索质量和幻觉控制
结合方式 实体链接、图检索、路径证据 LLM 生成答案

知识库在整个系统中起到什么作用？具体在哪个环节使用？

回答：

知识库是经过解析、组织和权限约束的文档集合及其检索能力。它在任务执行前负责准备可复用数据，在用户提出定向问题时提供相关证据，也可以存放需要额外查询的业务规则或术语解释。

在文档对比助手中，两份指定文档本身就是主要证据。完整对比可以直接读取其结构化内容，知识库中的向量检索不必成为必经步骤；如果问题需要定位某类条款，或解释涉及另外的业务制度，才按任务范围调用检索。

要区分文档存储、索引管理和检索增强生成三个概念。文件被保存进知识库，并不意味着每次任务都必须做相似度搜索。更好的架构是统一管理文档与证据，同时允许任务选择全量读取、结构化对齐或定向检索路径。

知识库是怎么搭建的？具体处理流程是什么？

回答：

知识库建设从数据契约开始：哪些文件允许进入、归属哪个 Workspace、版本如何标识、哪些主体可以访问。上传后校验实际文件类型、大小和内容完整性，保存原始文件及哈希，再由适配的解析器提取正文、结构、表格和位置。

之后进行有边界的清洗、结构化切分和元数据绑定。清洗可以去除重复页眉页脚，但必须防止误删正文和关键编号。按需要构建全文索引与向量索引，保存 Embedding 模型及切分配置；同时验证块数量、文档覆盖和证据定位是否合理。

构建采用可重试任务和明确状态，全部必要产物完成后才发布查询入口。更新时构建新快照，切换索引路由；删除和撤权同步处理查询权限、文件读取、索引及缓存。上线前用代表性文档与人工问题检查解析、检索和生成整条链路，不能只以“向量写入成功”作为验收标准。

知识库没有检索到可靠内容时，系统应该怎么处理？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐ (4/5)

先判断是问题缺条件、检索失败、权限不可见，还是知识库确实缺少答案。缺条件时澄清；检索不稳时可进行受预算约束的改写或词法补检；证据不足时明确说明不能根据现有资料确定，并给出可执行的下一步。

若业务允许，可以调用权威实时接口、查询经批准的外部渠道或转人工，但应标明证据适用范围。不能因为向量库总能返回“最近”的几段文本，就强制生成一个确定答案。最近邻只说明相对相似，不说明足以支持问题。

无答案阈值需要独立验证集，结合召回与重排分、证据覆盖和冲突检测，不能套用固定相似度常数。对预约、退款等业务，知识缺失时不执行未经验证的操作，也不泄露受限文档是否存在。
