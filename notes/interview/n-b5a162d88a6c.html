测试的作用是提供关于质量与风险的证据。需求、功能、接口、自动化、性能和稳定性测试各有目标；工具是执行手段，测试条件与正确结果仍需明确定义。

需求分析、测试目标与风险排序

测试从明确要验证什么开始：用户目标、业务规则、输入输出、状态变化、失败行为和非功能约束都应转成可观察条件。需求存在歧义时，先确定可接受结果，否则再多用例也只是重复执行不明确的步骤。

范围有限时可按影响、发生可能、变更范围和恢复成本排序，优先覆盖核心路径、边界和高风险失败。测试通过提供的是在给定条件下的证据，不是证明软件永远没有缺陷。测试计划应说明范围、环境、依赖、执行方式、准入退出条件和已知剩余风险，让时间不足时的取舍能够解释。

来源：GitDzreal93/tester-interview。

等价类与边界值设计

等价类把在同一规则下应具有相似处理方式的输入归组，用代表值降低穷举成本；边界值把注意力放在规则转换处，因为小于、等于、大于以及空值常触发不同路径。二者应从实际规则划分，不能机械地给每个字段写“正常、异常”两条。

例如允许长度区间的输入，除了区间内代表值，还需检查上下界、紧邻边界、空输入及编码长度等约束。多个字段组合后可能产生交互，单字段覆盖不能保证组合规则正确；这时需要补充决策表、组合策略或业务状态测试。

来源：GitDzreal93/tester-interview；GitDzreal93/tester-interview。

决策表、状态迁移与组合

当结果依赖多个条件时，决策表把条件组合与应执行动作显式对应，帮助发现缺失规则与冲突；当允许动作取决于历史状态时，状态迁移更合适，例如订单未支付、已支付、已取消之间的合法转换。

用例既要验证合法路径，也要验证非法转换、重复操作和在异常后恢复的路径。组合测试可以控制多维参数的规模，但它只覆盖所选择的交互阶数，不能替代关键业务组合的明确分析。先识别决定结果的条件，再选择降维策略，比盲目追求用例数量更有效。

来源：GitDzreal93/tester-interview。

单元、集成、端到端与测试替身

单元测试聚焦较小逻辑边界，集成测试验证组件协作，端到端测试从外部可见路径验证整体流程。边界由系统设计决定，不能仅按是否启动浏览器或数据库给所有测试贴标签。越接近完整环境，真实性通常越高，执行和定位成本也可能越高。

Mock、Stub 等替身适合控制依赖行为和触发罕见失败，但只能证明系统对这些模拟行为的处理。若替身与真实协议偏离，单元测试全绿仍可能集成失败。应让快速测试承担大量稳定逻辑检查，再用适当的集成与端到端测试覆盖关键协作和用户路径。

来源：GitDzreal93/tester-interview；h5bp/Front-end-Developer-Interview-Questions。

接口测试：契约、业务与持久结果

接口测试至少分清请求契约、返回契约和业务结果。方法、路径、认证、参数类型、缺失字段与边界决定是否接受请求；状态码与响应体需要符合约定；持久数据、事件和副作用则决定业务是否真正完成。仅断言 HTTP 200 会漏掉错误业务码或数据未落库。

还应验证权限边界、重复请求、超时、部分失败和版本兼容。接口链路要明确每步依赖的数据从哪里获得，而不是写死上一轮运行的 ID。测试读接口时也要区分“写后立即可见”是否属于承诺，避免把允许的异步状态与真实缺陷混为一谈。

来源：GitDzreal93/tester-interview。

幂等、并发与竞态测试

并发测试关注多个操作在时间上重叠时，业务不变量是否仍成立。重复提交、同一资源争抢、回调重放与读写交错都需要明确预期：最终应出现多少条记录、是否允许部分失败、库存或余额是否始终合法。

启动多个线程不代表已制造目标交错。可以通过同步点、受控延迟或故障注入让请求在关键步骤相遇，再核对数据库、消息和响应。测试需要稳定的业务请求号与可关联日志，尤其区分“服务端已完成但客户端超时”与完全未执行，避免把重试产生的重复副作用遗漏。

来源：GitDzreal93/tester-interview；Snailclimb/JavaGuide。

测试数据、环境与可重复性

可重复测试需要控制初始状态、环境配置、时间、随机性和外部依赖。用例应自己准备所需数据或声明稳定的前置条件，执行后清理或隔离，避免前一个用例的副作用决定下一个用例结果。

环境与真实部署不必完全一样，但关键差异必须明确，例如副本延迟、缓存、限流、队列和认证配置。遇到只在线上出现的问题，应比较差异而不是反复重跑相同输入。使用随机数据时保存种子和实际数据；使用时间相关规则时控制或记录时钟，才能把一次失败转成可复现证据。

来源：GitDzreal93/tester-interview。

Fixture、参数化与清理

Fixture 将测试所需资源的创建、依赖和销毁显式组织起来，使多个用例能复用准备逻辑。参数化让同一断言逻辑覆盖不同输入，减少复制代码，但每组参数仍需有清晰的预期结果和可辨识名称。

作用域越长并不越好：共享数据库连接或对象可降低成本，也可能带来状态污染。清理应覆盖执行失败的情况，不能假设测试一定走到末尾。使用 pytest 等框架时，应理解资源依赖顺序与 teardown 时机，再根据隔离成本选择作用域，而不是把所有准备操作放进一个全局大 Fixture。

来源：pytest Fixture 官方说明。

UI 自动化的定位、等待与断言

UI 自动化通过用户可见行为驱动界面，稳定性依赖可维护的元素定位和状态等待。等待条件应表达“元素可交互、数据已到位或结果已出现”，固定睡眠只是猜测时间，既可能太短失败，也可能太长浪费。

显式等待有明确超时与条件，定位应尽量依赖稳定语义或测试标识，避免过深且脆弱的 DOM 路径。页面对象等组织方式可集中界面细节，但不能把业务断言全部隐藏。自动化失败时保留截图、页面状态和日志；应先区分产品失败、等待错误、定位变化和环境故障。

来源：GitDzreal93/tester-interview；Selenium 等待策略。

Flaky 测试与失败分类

Flaky 测试在相同目标版本上时好时坏，往往涉及时间、状态共享、异步等待、资源竞争或外部依赖不稳定。盲目增加重跑次数只能隐藏症状，也可能把真正的竞态当成偶发环境问题。

先收集失败频率、日志和共同环境，按产品缺陷、测试缺陷与基础设施问题分类，再定位可控变量。必要时短期隔离以保护反馈通道，但要有负责人和恢复条件。修复应证明原失败机制已被处理，而不只是某次重跑变绿；失败诊断能力本身也是测试体系质量的一部分。

来源：GitDzreal93/tester-interview。

性能测试目标与负载模型

性能测试先定义要验证的场景、数据规模、吞吐、延迟与错误率目标，再建立接近实际访问比例的负载。基准测试观察固定条件下的表现，负载测试验证目标流量，压力测试寻找退化边界，持续测试检验资源随时间的变化。

还要说明流量如何产生：固定并发客户端会因服务变慢而自然降低请求速率，固定到达率则可能继续积压，两者会揭示不同问题。升压速度、预热、思考时间和测试持续时间都影响结果。压测机自身的 CPU、连接和网络若已饱和，测出的就不是目标系统的真实上限。

来源：GitDzreal93/tester-interview；JMeter 测试计划。

吞吐、并发、延迟与尾部指标

吞吐描述单位时间完成多少工作，并发描述同时在处理或等待的工作量，延迟描述单次工作耗时，三者不能直接画等号。在稳定系统且度量边界一致时，平均在途量约等于到达率乘平均停留时间；这能帮助估算规模，却不能用来忽略排队或瞬态过载。

平均延迟会掩盖少数很慢的请求，所以需要观察分位数、错误率与超时，并把服务端耗时和端到端耗时分开。报告“支持一万并发”时还应说明请求比例、数据规模、吞吐与延迟，否则无法判断实际能力。

来源：GitDzreal93/tester-interview；Snailclimb/JavaGuide。

瓶颈定位与性能验证

吞吐上不去时先确认负载确实送达，再沿调用链查看等待在哪里。CPU 饱和、锁竞争、连接池排队、磁盘、网络、数据库慢查询和下游限流会形成不同证据，单看应用 CPU 不高不能证明系统还有无限余量。

每次优化应形成假设、观测指标、修改与对照结果。保持测试条件可比，避免同时改变线程数、缓存和数据规模后无法解释收益。优化后还应确认错误率、尾延迟和资源是否转移到其他组件，不能只展示某一个吞吐数字变大。

来源：GitDzreal93/tester-interview；Snailclimb/JavaGuide。

稳定性、故障注入与恢复

稳定性测试关注持续运行中资源、延迟和错误是否随时间恶化；故障测试关注依赖变慢、节点退出、网络异常等情况下保护与恢复机制是否按设计工作。两者应验证业务效果，而不只看进程是否仍存活。

观察内存、句柄、连接、队列、重试和恢复时间，并检查恢复后是否遗漏、重复或损坏数据。注入故障前明确预期影响和恢复动作，结束后核对系统确实回到正常状态。容灾目标如 RTO、RPO 也需要恢复演练的证据，不能只依据架构图或配置项宣布达到。

来源：GitDzreal93/tester-interview；Snailclimb/JavaGuide。

缺陷报告、复现与开发协作

有用的缺陷报告需要说明版本、环境、前置状态、复现步骤、实际结果、预期依据与影响，并附可关联的请求、时间和日志。严重性描述影响，处理优先级还要结合暴露范围、绕过办法和交付安排，两者不一定相同。

无法稳定复现时，先保存现场并缩小变量，寻找用户、数据、时间、设备和并发条件的共同点。与开发讨论应围绕可观察证据和需求约定，不以“我这里能复现”代替共同环境。修复后既要验证原场景，也要按改动影响补回归，防止解决一个分支却破坏另一个分支。

来源：GitDzreal93/tester-interview。

CI、覆盖率与质量反馈

持续集成把构建、静态检查和自动化验证接入变更流程，目标是尽早给出可行动的反馈。快速检查适合每次提交，耗时或环境复杂的验证可分层安排。门禁应与风险相称，失败必须能定位，否则大量红灯会使团队逐渐忽视结果。

覆盖率说明哪些代码或条件被执行过，不直接证明断言正确、需求完整或异常被处理。测试报告应同时展示关键场景、失败、环境与剩余风险，避免把用例数或一个覆盖百分比当成全部质量。新增缺陷应转化为适当层次的回归检查，形成可持续反馈。

来源：GitDzreal93/tester-interview；GitDzreal93/tester-interview。

测试左移、TDD 与 BDD

测试左移把质量分析提前到需求、接口和设计阶段，及早澄清不明确规则并提高可测试性。TDD 以小步的失败测试、实现和重构推进代码设计；BDD 通过业务可理解的行为示例形成共同约定。它们都不能简化成“换个工具写更多用例”。

是否采用某种流程，要看团队如何维护例子、断言和反馈。提前参与设计可以降低后期返工，但仍需要集成、运行与真实用户路径的验证。行为示例应具体、可验证，并与实际系统规则保持同步，避免变成无人检查的文档副本。

来源：GitDzreal93/tester-interview。

移动端测试的场景组合

移动端除了业务输入输出，还受到设备、系统版本、权限、网络、电量和前后台生命周期影响。上传、支付、定位等流程需要验证中断、恢复和重复回调，而不只是正常网络下完成一次操作。

测试矩阵应从用户分布与能力差异选代表组合，再对高风险边界专项验证。弱网、切后台、进程重建、权限拒绝与升级后的数据兼容，都应有可解释的预期结果。自动化可以承担稳定回归，硬件和系统集成差异仍需要相应层次的真实环境验证。

来源：GitDzreal93/tester-interview；GitDzreal93/tester-interview。
