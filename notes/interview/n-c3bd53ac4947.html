你提到装饰器可以在不修改业务代码的前提下增强功能。那如果要给一个带位置参数、关键字参数，还有返回值的业务函数加统计执行耗时的装饰器，你会怎么处理被装饰函数的参数传递和返回值透传问题。

回答：

包装函数使用 *args 和 **kwargs 原样转发参数，保存并返回原函数结果；不要漏写 return，也不要擅自改写参数。用单调高分辨率时钟 time.perf_counter() 计算耗时，并把记录放在 finally 中，使成功与异常路径都有统计，同时让原异常继续向上传播。

同步函数与协程函数需要不同包装方式。同步包装器直接调用异步函数，只能测到创建协程对象的耗时，测不到真正执行时间。下面是可运行实现：

import functools
import inspect
import logging
import time

logger = logging.getLogger("function_timing")

def timed(func):
    if inspect.isgeneratorfunction(func) or inspect.isasyncgenfunction(func):
        raise TypeError("generator timing requires a separate contract")

    def record(start):
        elapsed = time.perf_counter() - start
        try:
            logger.info("%s elapsed=%.6fs", func.__qualname__, elapsed)
        except Exception:
            # 监控故障不覆盖业务返回值或业务异常。
            pass

    if inspect.iscoroutinefunction(func):
        @functools.wraps(func)
        async def async_wrapper(*args, **kwargs):
            start = time.perf_counter()
            try:
                return await func(*args, **kwargs)
            finally:
                record(start)
        return async_wrapper

    @functools.wraps(func)
    def sync_wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            record(start)
    return sync_wrapper

记录值覆盖原函数从开始到完成或抛错的时间，不包含后续日志写入耗时。生产环境还应采用低开销指标与受控采样，避免输出敏感参数，也不应让指标标签含无界用户 ID。同步日志处理器可能阻塞事件循环，应使用合适的异步或队列化监控通道。

该示例支持普通同步函数和常规 async def，显式拒绝生成器，因为“创建迭代器耗时”和“消费全部结果耗时”不同。同步函数返回 awaitable 的特殊情形也不在完整异步计时契约内。取消协程时 finally 仍会运行，取消异常不应被吞掉。

你的这个并发处理耗时请求是怎么设计的？

回答：

耗时任务应采用有界队列与受控 worker，而不是每个请求到来就无限创建协程。接入层先鉴权、校验并生成幂等任务 ID；短任务可等待结果，长任务通常返回任务 ID，后续查询或订阅进度。

将限流、排队、并发和超时分开控制：入口按租户与资源限速；队列容量限制待执行数量；信号量限制正在占用数据库连接、GPU 或外部 API 的任务；全链路 deadline 控制总等待时间。队列满时显式拒绝、降级或返回可重试状态，不能把内存当作无限缓冲。

任务状态持久化为 pending、running、succeeded、failed、cancelled 等，并记录租约、尝试次数和结果引用。worker 领取任务、续租、执行与提交需要处理宕机重试；外部写入使用幂等键，避免任务重放产生重复副作用。协程退出时释放资源，取消要传播到下游调用。

容量估算可以借助稳定系统中的 Little 定律：

N=\lambda T.

其中 \(N\) 是某个系统边界内的平均在途数量，\(\lambda\) 是稳定吞吐，\(T\) 是同一边界内平均逗留时长。它不是直接照搬的线程数公式；实际还要看尾延迟、资源瓶颈和余量。监控应分开记录排队与执行时间，并检查吞吐是否已经超过下游持续服务能力。

你说看过Claude源码，Claude Code学习经验总结？

回答：

这个问题回答时要谨慎。Claude Code 本体并不是完整开源、可随便阅读核心实现的项目，所以更准确的说法应是：学习过 Claude Code 的公开文档、CLI 行为、工具设计和可观察的 agent 工作流，并结合类似 coding agent 的开源实现做过复盘。如果直接说“看过 Claude Code 源码”，面试官追问细节时容易变成风险点。

学习总结可以分成几条。第一，Claude Code 的核心不是“会写代码”，而是把代码任务拆成一个 agent loop：理解任务、读取仓库上下文、定位相关文件、制定修改方案、编辑文件、运行命令或测试、根据结果修正、最后总结变更。模型能力只是其中一部分，真正重要的是上下文获取和工具闭环。

第二，它非常重视代码仓库的实时上下文。代码任务和普通知识问答不同，答案必须和当前仓库文件一致。所以它会使用文件读取、目录遍历、grep 检索、编辑工具、bash 命令等方式直接观察当前工作区，而不是只依赖模型记忆。

第三，工具权限和可控性很关键。一个 coding agent 能改文件、跑命令，就必须有权限边界、确认机制、可审计日志和失败恢复。否则模型一次误操作就可能破坏仓库。好的 agent harness 会把高风险工具和低风险工具区分开。

第四，上下文压缩和任务记忆很重要。真实代码库很大，不可能把所有文件都塞进上下文。Agent 需要先用检索定位，再选择性读文件，还要把已经确认的事实保留下来，避免反复搜索和遗忘。

第五，Claude Code 的工程价值在于“从自然语言任务到可验证 diff”。也就是说，它最后不是给一段建议，而是完成可运行、可检查、可回滚的代码变更。这个思路也可以迁移到业务 Agent：不要只输出文本，而要形成可执行动作、可验证结果和 trace。

使用 Bitmap 时，如果元素值范围非常大，会有什么问题？

回答：

普通 Bitmap 按取值域分配位置。若允许 \(U\) 个不同整数值，仅一个位图就约需：

M=\left\lceil\frac{U}{8}\right\rceil\ \text{bytes}.

因此空间主要由取值范围决定，而不是当前元素数。完整 64 位无符号整数域的单个位图需要 \(2^{61}\) 字节，即 2 EiB；两条流和输出去重状态还会进一步增加空间。稀疏而跨度大的 ID 直接映射普通 Bitmap 很不经济。

可选方案包括 Hash Set、磁盘 KV、按范围分区的稀疏结构，以及 Roaring 等压缩位图。Roaring 根据局部密度采用不同容器，收益依赖分布，也要区分 32 位实现与 64 位扩展，不能保证任何稀疏大域都很省空间。

坐标压缩要求维护原值到紧凑 ID 的映射；在无限新值流中，这个映射本身仍会增长。Bloom Filter 可以作为候选过滤器，但存在假阳性，单独使用无法输出精确交集；需要回查真实集合。清理过期过滤状态还必须与窗口语义一致。

修复实现中的状态转移问题

回答：

最常见错误是先覆盖最大状态，再用“新最大状态”计算最小状态，导致本轮元素被重复乘入。例如错误代码：

max_end = max(x, x * max_end, x * min_end)
min_end = min(x, x * max_end, x * min_end)  # 已混入新 max_end

在 [-2,3,-4] 上，最后一轮正确状态应为最大 24、最小 -12；上述写法却可能得到最小 -96。此时当前答案碰巧正确，但若再接一个 -1，错误状态就会把答案放大为 96，而正确答案仍为 24。

修复方法是先保存 old_max、old_min，让两个新状态都只读旧值；也可以先完整计算右侧候选，再统一赋值。定位时逐轮打印“当前元素、旧最大、旧最小、新最大、新最小、全局答案”，并用短数组暴力枚举所有连续子数组交叉验证，避免只看最终样例是否通过。

假设已进行 10 轮并做了总结，第 11 轮开始时，总结怎么处理？是重算前 11 轮还是叠加？

回答：

第 11 轮开始时，正常做法是使用已有摘要 \(S_{1:10}\) 加上尚未被摘要的近期消息，而不是立刻重算前 11 轮，也不是每出现一条新消息就再压缩一次。

当后续再次达到触发条件时，可以基于旧摘要和增量事件生成新版本：

\[ S_{1:11}=\operatorname{Summarize}(S_{1:10},D_{11}) \]

这种增量更新成本低，但它是有损链路。若长期只在旧摘要上继续摘要，早期错误和遗漏会被固化。因此工程上应采用“增量更新 + 周期性重建”：日常基于上一版本和新事件更新；到达重要阶段、摘要质量下降或发生冲突时，从原始事件/最近稳定 checkpoint 全量重建。

全量重算是否是 \(O(n^2)\) 取决于触发频率。若每一轮都重新处理从第 1 轮到当前轮，累计处理量确实呈二次增长；若只在少数阶段边界重建，则不能简单称为 \(O(n^2)\)。面试中应把复杂度前提讲清楚。

每个摘要版本要带 version、覆盖事件区间、生成模型/Prompt 版本和校验状态。这样第 11 轮到来时，系统能够准确判断它属于已压缩历史还是待合并增量，避免重复计算和事件丢失。

做内容理解时类别太多标注不够，你怎么办？

回答：

先治理标签体系，再增加模型复杂度。检查它是单标签还是多标签，类别是否互斥，层级关系是否合理，同义类是否重复，标注员能否依据一致规则区分相邻类别。类别定义混乱时，增加样本也会把冲突放大。

光栅化和 Z-buffer 为什么会带来不可微问题？

可微渲染的核心难点来自传统渲染中的离散决策。

光栅化 会判断一个像素是否被某个三角形覆盖。这个判断近似是二值函数：

\[ m(p, t) \in \{0,1\} \]

当像素 \(p\) 在三角形 \(t\) 内部时为 1，否则为 0。顶点轻微移动时，大多数像素的覆盖关系不变；但跨过边界时覆盖关系突然变化。因此该过程对顶点位置不是处处连续可导。

Z-buffer 会在多个三角形覆盖同一像素时选择深度最近的那个：

\[ t^* = \arg\min_t z_t \]

这个 argmin 也是离散选择。当两个三角形深度接近并发生前后切换时，像素颜色会突变。

所以，传统渲染中虽然模型变换、投影、光照计算大多可微，但光栅化的覆盖判断和 Z-buffer 的可见性选择会破坏端到端求导。

回答：

解决方案要对应根因，并先控制用户影响。第一步是设置总 Deadline 和阶段预算，把 5 分钟假设变成可观测、可执行的 SLA：例如为排队、模型、每类工具和重试分别分配预算，任一阶段超时就进入降级或转人工，而不是无限运行。

其他常见的分类标准有哪些？

除了开放程度和能力范围，还可以从模型结构和使用方式分类。这些维度彼此独立，同一个模型可以同时属于多个类别。

  • 按参数规模分类：可粗略区分小型、中型和大型模型，但没有统一阈值。

  • 按模型结构分类：可分为仅编码器（Encoder-only）、编码器—解码器（Encoder-Decoder）、仅解码器（Decoder-only），也可区分稠密模型和混合专家（Mixture of Experts，MoE）模型。主流生成式 LLM 多采用仅解码器架构。

写出伪代码用abc 预测第四个token 告诉了我特征维度头个数

回答：

先确认 a,b,c 指三个已分词 token。若每个字母未必对应一个 token，应先使用模型 tokenizer。设批大小 $B=1$、长度 $L=3$、隐藏维度 $d$、头数 $h$，要求 $d\bmod h=0$，每头维度 $d_h=d/h$。

以下是一层标准 MHA 的推理伪代码，省略 dropout，位置函数对 Q/K 施加 RoPE。输入可见三项，最后一个位置的 logits 预测第四个 token：

H = embed([id_a, id_b, id_c])             # [1, 3, d]
for block in blocks:
    X = norm1(H)
    Q, K, V = X @ Wq, X @ Wk, X @ Wv    # 各 [1, 3, d]
    Q = reshape(Q, [1,3,h,dh]).transpose(1,2)
    K = reshape(K, [1,3,h,dh]).transpose(1,2)
    V = reshape(V, [1,3,h,dh]).transpose(1,2)
    Q, K = apply_rope(Q, K, positions=[0,1,2])
    S = Q @ transpose_last_two(K) / sqrt(dh)
    S = mask_future_positions_with_minus_inf(S)
    C = softmax(S, axis=-1) @ V          # [1,h,3,dh]
    C = C.transpose(1,2).reshape([1,3,d])
    H = H + C @ Wo
    H = H + FFN(norm2(H))
logits = final_norm(H)[:, -1, :] @ W_vocab
next_id = argmax(logits, axis=-1)        # 或按解码策略采样

softmax 对 key 位置维归一化，不能沿头维归一化。训练时使用移位标签并对所有有效位置计算损失；这里推理只取最后位置。若继续生成，在下一步读入新 token 并复用各层 KV cache。

冷启动你有什么办法，新用户新内容都算。

回答：

新用户缺少行为历史，新内容缺少曝光反馈，这是两个不同的信息缺口。共同原则是利用已有内容信息建立先验，再通过受控探索获得新证据，避免把“没有观察到”理解为“不受欢迎”。

新用户可利用自愿选择的兴趣、当前搜索或会话行为、入口与语言等必要上下文，结合多样化优质候选快速学习偏好。不要把敏感属性或未经授权的跨域数据当默认特征。随着点击、停留、收藏和负反馈积累，应快速更新短期兴趣，并防止少量偶然点击把用户锁死在单一主题。

新内容依靠文本、图像、作者可信度与主题表征获得初始召回位置，先通过质量底线，再给出有预算的探索曝光。不同内容类型采用不同反馈成熟窗口；发布几分钟没有收藏，不能和曝光充分的老内容直接比较累计互动量。

可用上下文 bandit、UCB 或 Thompson sampling 在价值与不确定性之间分配探索，但奖励延迟、位置偏差和内容间竞争会影响估计。需要记录曝光概率，建立探索流量边界和反作弊检测。离线 IPS 等评估也要求行为策略有支持覆盖，极小 propensity 会带来高方差。

最终同时看新用户留存与负反馈、新内容获得有效曝光的时间、优质内容发现率、创作者覆盖和老用户体验。冷启动不是给所有新内容无限保量，而是在质量与生态约束下高效减少不确定性。

分头是怎么分的怎么拼接

回答：

标准 MHA 通常先把完整隐藏表示乘上 Q/K/V 投影矩阵，再把投影结果的最后一维拆成多个头。输入 $[B,L,d]$ 变为 $[B,L,h,d_h]$，转置得到 $[B,h,L,d_h]$；每个头在自己的特征子空间中计算 $L\times L$ 注意力。

得到每头输出后，先转回 $[B,L,h,d_h]$，再拼成 $[B,L,d]$，最后乘输出矩阵 $W_O$ 融合头间信息。不是把序列切成 h 段，也不是对各头直接求和。

例如 $d=768,h=12$，每头维度为 64，每个头都能看全部允许的上下文。GQA/MQA 的 key/value 头数可少于 query 头数，需要额外的分组共享关系，不能照搬相同头数的 reshape。

分步计算（以长度为n的数组为例）

  1. 外层循环：遍历无序区间（执行n-1次） 插入排序的外层循环从索引1开始（第1个元素是初始有序区间），到索引n-1结束，共执行 n-1次（对应n-1个无序元素，每个元素都要插入一次）。

  2. 内层循环：比较+移动元素（最坏情况执行次数累加） 内层循环的执行次数，取决于当前要插入的元素（key）在有序区间中的位置——最坏情况下（逆序数组），每次插入的key都是当前有序区间的最小值，需要从有序区间末尾遍历到最开头，执行次数等于当前有序区间的长度： - 第1次插入（i=1）：有序区间长度=1 → 内层循环执行1次 - 第2次插入（i=2）：有序区间长度=2 → 内层循环执行2次 - 第3次插入（i=3）：有序区间长度=3 → 内层循环执行3次 - ... - 第n-1次插入（i=n-1）：有序区间长度=n-1 → 内层循环执行n-1次

  3. 总执行次数（最坏情况） 内层循环的总执行次数是一个等差数列求和：
    1 + 2 + 3 + ... + (n-1) = n(n-1)/2

展开后为：(n² - n)/2，即 0.5n² - 0.5n。

  1. 简化为O(n²) 根据时间复杂度的「大O记法规则」： - 只保留最高次项（此处为0.5n²） - 忽略最高次项的系数（0.5可省略）

最终插入排序的最坏时间复杂度和平均时间复杂度均为O(n²) （平均情况是最坏情况的一半，仍为n²量级）。

分类能力和判别能力有什么区别？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐ (4/5)

分类能力关注决策边界能否把训练类别分开；判别能力还要求同一身份的样本在表示空间中足够近、不同身份的样本有足够大的安全间隔。只要样本落在正确边界一侧，普通分类损失就可能认为已经成功，但这并不保证边界附近的两张脸在开放集比较时可靠。

人脸度量学习更关心如下关系：类间最小距离应大于类内最大距离。姿态、年龄、光照、遮挡和摄像头差异会造成类内变化，因此训练目标必须显式压缩类内分布并扩大类间间隔。这个判断也解释了为什么人脸识别模型通常采用归一化特征、角度 margin 和严格的验证集阈值，而不是直接使用分类准确率。

切块时如何保证语义完整性？

回答：

语义完整性的关键是保留解释一个单元所必需的条件和关系。条款正文与其适用范围、例外条件、表格表头、单位和脚注应尽量一起处理；标题路径可以作为上下文补充，帮助模型理解段落属于哪个主题。

单目 RGB 重建 3D 人体/人脸时有哪些难点？

单目 RGB 缺少真实深度，因此是病态问题。

主要难点：

  • 深度歧义：同一 2D 投影可能对应多个 3D 姿态。
  • 遮挡：手、头发、衣服、物体会遮挡关键部位。
  • 光照和纹理混淆：阴影可能被误认为几何。
  • 表情和身份耦合：脸型、表情、姿态相互影响。
  • 宽松衣物：SMPL 类裸体/紧身模型难表示裙摆、袖子、布料褶皱。

改进方向：

  • 多帧时序约束。
  • 多模态输入，如 RGB-D、IMU、多视角。
  • 隐式场或神经表面表示。
  • SMPL/FLAME 先验 + diffusion/生成模型补细节。
  • 物理约束和布料模拟。

压缩或者摘要肯定会丢失信息，如何使得这个信息丢失最小化？

回答：

首先要区分“可丢失的表达”和“不可丢失的状态”。寒暄、重复日志、已经被确定性结果替代的探索过程可以压缩；用户目标、硬约束、授权、数字、时间、否定关系、实体、未完成事项、工具回执、关键决策依据和安全事件必须结构化保留。

推荐采用以下方法：

  1. 先结构化抽取，再生成摘要。 不让模型自由概括全部历史，而是按固定 Schema 抽取目标、事实、约束、状态、冲突、证据和待办事项。
  2. 分层压缩。 近期消息保留原文，中期内容做阶段摘要，长期内容进入带权限和版本的记忆；大型工具结果只保留摘要与可恢复引用。
  3. 保留证据指针。 摘要中的每个关键事实关联原消息、文档片段、工具调用或 Artifact ID，必要时可以回读原文。
  4. 冲突显式化。 新旧事实冲突时记录两个版本和判断依据，不能静默覆盖；当前明确指令优先于历史推断。
  5. 压缩后校验。 通过规则检查数字、日期、实体、否定词、权限条件和任务状态，再用独立模型或人工抽样复核高风险摘要。
  6. 按下游任务评估。 进行删除/压缩消融，测任务成功率、事实错误、约束漏检、引用丢失、恢复率和 Token 成本，而不是只看摘要是否流畅。

压缩模型的选择取决于错误成本：去重和格式归并可用规则或小模型，涉及复杂冲突和高风险事实时应使用更强模型或双重校验。系统不必保存模型私有 Chain-of-Thought，但必须保存可审计的决策摘要、行动结果和证据关系。最小信息损失不是字数最少，而是对未来决策的充分统计量尽可能完整。

参数化人体模型为什么难以表示宽松衣物？

SMPL/SMPL-X 的核心假设是：人体表面可以用统一拓扑的低维参数表示。这对身体几何非常有效，但对宽松衣物有天然限制。

主要瓶颈：

  1. 拓扑限制

宽松衣物可能与身体分离，例如裙摆、外套、袖口、披风；而 SMPL 是单层人体表面。

  1. 动态细节缺失

布料会产生褶皱、摆动、碰撞和惯性，低维 pose/shape 参数难以完整表示。

  1. 物理一致性不足

SMPL 的变形主要来自统计学习和骨骼蒙皮，不显式模拟重力、风、碰撞和摩擦。

  1. 轮廓与人体不一致

图像中的可见轮廓往往是衣服，不是人体。直接拟合 SMPL 容易把宽松衣服误解释为更胖的身体。

改进路线：

  • 分层表示：body mesh + garment mesh。
  • 衣物模板：针对 T-shirt、dress、coat 等建立可变形衣物模板。
  • 物理模拟：用布料仿真或物理约束网络提升动态合理性。
  • 隐式表示：用 SDF/Occupancy/Neural Field 表示拓扑更自由的衣物几何。
  • 生成式细节增强：用 diffusion/GAN/neural texture 生成褶皱和纹理细节。

可微渲染是什么？

可微渲染是指渲染结果可以对输入场景参数求导的渲染过程。它既要完成正向渲染：

\[ I = R(\theta) \]

也要支持反向传播：

\[ \frac{\partial I}{\partial \theta} \]

其中 \(\theta\) 可以是：

  • 顶点位置。
  • 相机参数。
  • 姿态参数。
  • 形状参数。
  • 表情参数。
  • 材质和纹理。
  • 光照参数。
  • 隐式场参数。

可微渲染的意义是：可以通过二维图像监督来优化三维参数。例如给定真实图像 \(I_{\text{gt}}\)，渲染预测图像 \(I_{\text{render}}\)，最小化：

\[ \mathcal{L} = \|I_{\text{render}} - I_{\text{gt}}\|_1 \]

就可以反向更新 3D 模型、相机、姿态和光照。

可微渲染有哪些主流实现思路？

主流思路可以分为三类：

  1. 近似梯度

正向渲染保持传统光栅化流程，但在反向传播时构造近似梯度。优点是正向结果真实、兼容传统管线；缺点是梯度设计复杂，可能依赖任务。

  1. 软光栅化

把三角形覆盖从硬 0/1 判断变成连续概率。例如像素离三角形越近，贡献越大；深度选择也从 hard argmin 改成 soft aggregation。优点是端到端可导；缺点是渲染结果可能变软或出现透明边界。

  1. 神经渲染/体渲染

使用 NeRF、SDF、3DGS 或神经纹理等连续表示，通过可微采样和合成得到图像。优点是适合高保真外观和隐式几何；缺点是训练、加速和编辑复杂。

常见工具和代表方向包括：

  • Neural Mesh Renderer。
  • Soft Rasterizer。
  • PyTorch3D differentiable renderer。
  • nvdiffrast。
  • NeRF/NeuS/VolSDF 类体渲染。
  • 3DGS 的可微 splatting。

面试回答时要注意：可微渲染不是一种固定算法，而是一类让图像损失能反向约束三维场景参数的方法。

同步与异步的区别总结

  1. 执行顺序： - 同步调用：任务按顺序执行，前一个任务完成后才会执行下一个任务。 - 异步调用：任务可以同时启动，程序可以在等待任务完成期间执行其他操作。

  2. 阻塞行为： - 同步调用：调用线程被阻塞，直到任务完成。 - 异步调用：调用线程不会被阻塞，可以继续执行其他任务。

  3. 效率和响应速度： - 同步调用：适用于简单、顺序的任务，易于理解和调试。 - 异步调用：适用于需要并发处理的任务，提高程序的效率和响应速度，但编程复杂度较高。

  4. 复杂度： - 同步调用：代码逻辑直观，容易调试和维护。 - 异步调用：需要处理回调、事件循环等机制，复杂度较高，但能显著提高性能。

向量范数、矩阵范数、核范数、Frobenius 范数分别有什么作用？

范数用于度量“大小”。常见向量范数：

\[ \|x\|_1 = \sum_i |x_i| \]
\[ \|x\|_2 = \sqrt{\sum_i x_i^2} \]
\[ \|x\|_{\infty} = \max_i |x_i| \]
\[ \|x\|_p = \left(\sum_i |x_i|^p \right)^{1/p} \]

常见矩阵范数：

\[ \|A\|_1 = \max_j \sum_i |a_{ij}| \]
\[ \|A\|_{\infty} = \max_i \sum_j |a_{ij}| \]
\[ \|A\|_F = \sqrt{\sum_i \sum_j a_{ij}^2} \]
\[ \|A\|_2 = \sigma_{\max}(A) = \sqrt{\lambda_{\max}(A^TA)} \]

核范数是奇异值之和：

\[ \|A\|_* = \sum_i \sigma_i \]

AI 中的典型用途：

  • \(L_1\) 范数：鼓励稀疏，可用于特征选择、稀疏正则。
  • \(L_2\) 范数：权重衰减、距离度量、Embedding 归一化。
  • Frobenius 范数：矩阵参数的整体大小，常用于权重正则、低秩近似误差。
  • 谱范数：约束 Lipschitz 常数，提升生成模型或判别器稳定性。
  • 核范数：秩函数的凸松弛，用于低秩约束和矩阵补全。
  • 梯度范数：判断梯度爆炸、裁剪梯度、监控训练稳定性。

听不懂，说人话？

回答：

可以把每段文本想象成高维空间里的一支箭。余弦相似度主要看两支箭指向是否一致，不太关心箭本身有多长：方向越接近，模型认为它们表达的语义越接近。

例如“怎么重置登录密码”和“忘记密码如何找回”用词不完全相同，但 Embedding 可能把它们放到接近的方向；“密码”和“天气”则会指向不同方向。RAG 就是用当前问题这支箭，去找知识库里方向最接近的几支箭。

四、大模型为什么PTQ占主导？

对于大模型（尤其是7B以上模型），PTQ在工程部署中更常见，原因包括： 1. 成本考量：对70B模型进行QAT需要相当于训练的成本，大多数团队无法承受 2. PTQ精度已较可用：INT8/FP8通常精度损失较小；INT4的AWQ/GPTQ在不少模型和任务上也能达到可接受效果 3. 大模型量化鲁棒性：大模型参数冗余度高，对量化噪声的容忍度比小模型强 4. 快速迭代：模型升级频繁，PTQ可以快速适配新版本

可以总结为：PTQ在模型训练后直接量化，通常无需重新训练；QAT在训练过程中模拟量化并通过微调补偿误差。大模型场景中PTQ更常用于部署落地，因为其成本低、速度快，更适合参数量大、迭代频繁的模型；但在强精度约束或特定低比特场景下，QAT仍有价值。

在不同的隔离级别下，一个事务分别会创造几个 ReadView？

回答：

读未提交一般不需要 ReadView，因为它允许读取未提交数据，不提供一致性快照语义。

读已提交下，一个事务内每次执行一致性读都会创建新的 ReadView。因此同一事务中多次 SELECT 可能创建多个 ReadView，每次都能看到语句开始前已经提交的数据。

可重复读下，一个事务通常只在第一次一致性读时创建一个 ReadView，后续一致性读复用它。因此同一事务内多次 SELECT 能看到相同快照，这也是可重复读的核心。

串行化下，InnoDB 通常通过加锁把并发事务串行化，普通 SELECT 也可能变成加锁读，因此重点不在 ReadView，而在锁控制。不过具体执行还和语句类型、引擎实现有关。

还要区分一致性读和当前读。即使在可重复读下，普通 SELECT 复用 ReadView；但 UPDATE、DELETE、SELECT FOR UPDATE 读取的是当前最新可见版本，并会加锁，不按普通快照读理解。

场景题：做一个意图识别的分类任务，类别特别多怎么做

回答：

基于质心和基于密度的文本聚类算法有什么优缺点？

基于质心的文本聚类（如 K-means）优缺点：

优点：

  • 算法简单、计算速度快，适合大规模数据；
  • 易于实现和理解；
  • 聚类结果通常是凸形，便于解释。

缺点：

  • 需要预先指定簇数；
  • 对初始质心敏感，容易陷入局部最优；
  • 不能很好处理非凸形簇或噪声数据。

基于密度的文本聚类（如 DBSCAN）优缺点：

  • 不需要预先指定簇数；
  • 能发现任意形状的簇；

  • 能有效识别噪声和离群点。

  • 对参数（邻域大小、最小点数）敏感，参数选择困难；

  • 计算复杂度较高，不太适合超大规模数据；
  • 在高维文本空间中，密度判断可能失效（“维度灾难”）。

基础算法题：两数之和

回答：

两数之和的本质是用空间换时间。暴力做法枚举两个数，时间复杂度 \(O(n^2)\)；更优做法是在遍历数组时维护哈希表，记录“值 -> 下标”。对每个元素 x，检查 target - x 是否已经出现，如果出现就返回两个下标；否则把当前值写入哈希表。

注意点有三个。第一，不能先把所有值放入哈希表后直接查，否则可能把同一个元素用两次。第二，如果有重复值，例如 [3,3] target=6，遍历时先查再写可以自然处理。第三，返回的是下标还是数值要看题目要求，LeetCode 原题返回下标。

from typing import List


def twoSum(nums: List[int], target: int) -> List[int]:
    seen: dict[int, int] = {}
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:
            return [seen[need], i]
        seen[x] = i
    return []

时间复杂度是 \(O(n)\)，空间复杂度是 \(O(n)\)。如果数组已排序，也可以用双指针做到 \(O(n)\) 时间和 \(O(1)\) 额外空间，但原题通常数组无序，所以哈希表是最直接的解法。

新增串行阶段本身不会让其余计算凭空变快；总时延降低必须来自其他环节节省。可把改动前后写为：

T_{new}=T_{extra}+T_{remaining,new},\quad
T_{new}<T_{old}\iff T_{extra}<T_{old}-T_{remaining,new}

例如先做轻量路由后，大量简单请求不再调用昂贵模型；先裁剪相关区域，后续视觉 token 变少；先做校验，减少无效调用与重试。新流程虽然阶段更多，执行的总工作可能更少。

要区分单请求延迟、平均延迟、吞吐和尾延迟。在同模型、硬件、并发、输入分布与缓存条件下打点，报告新增阶段耗时和被节省的部分。若只是测试负载变低或缓存更热，不能归因于新增串行流程。

复杂任务为什么要拆成多步提示？

因为大模型在单次长提示中容易同时承担读取、理解、推理、生成、格式化和自检，导致错误难以定位。

  • 任务更清晰，模型负担更小；
  • 中间结果可人工或程序校验；
  • 可以根据失败点局部重试；
  • 可按步骤选择不同模型，降低成本；
  • 更容易做日志、评估和回归测试。

外部环境、参数变化，会不会导致相同测试任务执行结果不一样？如何处理？

回答：

会。测试结果可以看成输入、构建版本、环境、数据、配置、外部依赖和随机性的共同函数。相同任务名称不等于相同执行条件。

运行清单应记录镜像/提交版本、配置和开关、资源 ID、数据快照、依赖版本、时间与时区、随机种子、并发条件，以及模型与检索策略版本。敏感配置记录安全引用或摘要，不写入明文密钥。

可控部分采用隔离环境、固定测试夹具、可重置数据、虚拟时钟和依赖 mock；真实集成测试另测外部依赖，并记录其可观测状态。mock 通过不代表真实集成一定通过，二者应分开报告。

把失败区分为确定性断言失败、环境阻塞、依赖失败和偶发不稳定。重跑可用于诊断，但不能一直重跑直到成功再覆盖原失败；保留首次结果、全部重试轨迹与不稳定率。

外部状态无法冻结时，要说明结果的有效时间和适用条件。高风险执行前重新读取状态与版本，若已发生变化则重算计划或请求确认。

多业务标准不统一，单模型如何承载多任务、规避任务冲突问题？

回答：

这个问题的本质不是“一个模型能不能做很多任务”，而是不同业务是否共享可迁移表示，以及它们的标签语义、数据分布和优化梯度是否互相冲突。

首先要把任务条件显式化。输入中应包含稳定的 task_id、业务规则、标签定义、输出 schema 和少量边界样例，避免模型靠数据表面特征猜当前任务。标签名相同但业务含义不同的场景，不能强行合并成一个全局标签；应建立上层统一语义体系，同时保留任务私有标签空间和映射层。

架构上可以采用“共享底座 + 任务私有能力”。共享 Transformer 学通用语言和领域表示；任务差异较小时使用独立分类头，差异较大时使用 Adapter、LoRA、软提示或 MoE 专家，由路由器选择对应能力。这样既复用底座，又避免所有业务把同一组参数往不同方向拉。

训练目标通常写成多任务加权和：

\[ \mathcal{L}=\sum_{t=1}^{T}\alpha_t\mathcal{L}_t \]

真正难点在权重 \(\alpha_t\) 和采样分布。大业务数据量大，若按自然分布采样，会淹没小业务；若简单均匀采样，又可能过拟合小任务。可采用温度采样、分阶段课程学习、基于不确定性的动态权重或 GradNorm。若两个任务梯度满足 \(g_i^\top g_j<0\)，说明更新方向冲突，可使用 PCGrad/CAGrad 等梯度手术，或直接增加任务私有参数，减少硬共享。

线上还需要做任务级评估和路由。不能只看一个总分，而要分别观察每个业务的 Accuracy/F1、校准误差、长尾召回和回归 case；同时监控加入新任务后旧任务是否退化。如果冲突持续存在，拆成多个专家模型通常比维持“一个万能模型”的形式更合理。

因此，单模型多任务的正确做法不是把数据混在一起训练，而是把“共享什么、隔离什么、如何路由、如何监控负迁移”设计清楚。

多人 ID 数据集如何构建？

  6. 做质量过滤：清晰度、美学、遮挡、ID 置信度、年龄跨度、重复图。

多条件控制发生冲突时，模型应如何处理？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

多条件联合失败不一定意味着输入互相矛盾。需要先区分三种情况：条件语义确实冲突，条件的坐标或时间没有对齐，以及各条件单独有效但模型缺少联合建模能力。

先定位冲突来自哪里

  • 语义冲突：文本要求红色外套，参考图却把黑色外套作为主体外观的一部分。系统需要明确身份属性与可编辑属性，而不是让两个条件隐式竞争。
  • 坐标和时间错位：相机、轨迹、姿态与掩码来自不同坐标系或帧率，即使每个输入单独正确，组合后也会产生错误约束。
  • 联合能力不足：各条件单独测试都能生效，成对或全部开启后却有一路被忽略，通常说明联合训练样本、条件容量或融合位置不足。

处理顺序比统一加权更重要

先做输入合法性和时空对齐，再根据任务定义硬约束、软约束和可编辑属性。不同条件可以走独立编码器或残差、注意力等注入路径，并使用 mask、时间窗口或门控限制作用范围。Guidance scale 只能调节部分条件的影响强度，不能替代坐标对齐，也不能保证解决语义矛盾；条件优先级同样没有通用答案，取决于当前任务允许修改什么。

图4-5 多条件控制应先校验语义与时空对齐，再检查作用域、融合竞争和组合训练

最小实验应从单条件开始，再做两两组合和全部条件联合。某一路单独就不生效，应先修条件表示或训练；单独有效、联合失效，才需要检查条件竞争、融合容量和组合数据覆盖。修复后还要回归单条件质量，避免为了联合遵循而削弱原有能力。

面试速答：多条件失败先分清是语义矛盾、时空坐标错位，还是模型缺少联合建模能力。处理时先校验输入并定义硬软约束，再用独立条件通路、空间作用域和时间调度控制融合；排查从单条件到两两组合，不能把所有问题都归结为 guidance 权重。
