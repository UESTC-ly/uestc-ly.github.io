LoRA底层原理、Rank选取依据、A/B矩阵初始化细节

回答：

LoRA 将权重更新约束在低秩子空间：

\[ \Delta W=\frac{\alpha}{r}BA \]

前向时可以把 \(W_0x\) 与 \(BAx\) 相加，训练时冻结 \(W_0\)，只更新 \(A\) 和 \(B\)。\(r\) 决定可表达的更新秩：增大 \(r\) 会提高适配容量，但增加参数量、显存、通信和过拟合风险；减小 \(r\) 成本低，但可能无法表达任务所需的变化。

Rank 不应凭经验固定。应在固定数据切分和训练预算下做小规模网格实验，并按模块、层深和任务类型观察验证集指标、长尾效果、稳定性与推理成本。可以先用较小 rank 快速筛选，再对敏感层增大 rank；不要只根据训练 loss 选择，因为更大的 rank 可能只是记住噪声。

常见初始化是 \(A\) 随机初始化、\(B\) 全零初始化，因此初始时：

\[ \Delta W_0=B_0A_0=0 \]

模型一开始等价于底座模型，训练过程再逐渐引入任务更新。不能让 \(A\)、\(B\) 同时为零，否则两者的梯度会同时失去有效更新信号。缩放因子 \(\alpha/r\) 用于控制增量幅度；LoRA dropout 可以降低过拟合，目标模块决定适配能力和成本，量化底座时要注意反量化计算、累加精度以及是否在合并权重时使用 FP32。

部署时可以保留 Adapter 动态加载，也可以把 \(BA\) 合并回权重以减少额外算子。合并应校验 dtype、量化误差和多 Adapter 兼容性；训练、导出和线上推理的 tokenizer、池化、归一化也必须保持一致。

LoRA微调方法为什么能加速训练？

1）只更新了部分参数：比如LoRA原论文就选择只更新Self Attention的参数，实际使用时我们还可以选择只更新部分层的参数；

2）减少了通信时间：由于更新的参数量变少了，所以（尤其是多卡训练时）要传输的数据量也变少了，从而减少了传输时间；

3）采用了各种低精度加速技术，如FP16、FP8或者INT8量化等。

这三部分原因确实能加快训练速度，然而它们并不是LoRA所独有的，事实上几乎都有参数高效方法都具有这些特点。LoRA的优点是它的低秩分解很直观，在不少场景下跟全量微调的效果一致，以及在预测阶段不增加推理成本。

Lora微调的阿尔法和rank是怎么选择的，对模型的影响分别是怎么样的

回答：

在常见 LoRA 参数化 $\Delta W=(\alpha/r)BA$ 中，rank $r$ 控制可表示增量的秩与参数量，alpha 控制显式缩放。增大 r 会增加表达容量、训练参数和计算，但也改变优化行为；增大 alpha 会放大当前低秩增量，可能加快适配也可能造成不稳定或遗忘。

不能认为‘固定 alpha/r 就完全等价’，因为矩阵尺寸、初始化、梯度与学习率仍不同。还需确认实现是否使用标准 alpha/r 或其他缩放变体，如基于平方根 rank 的规则。

选型先固定 target modules、数据、学习率与训练预算，再试少量 rank/scale 配置，检查验证任务、通用能力和显存；随后联合微调学习率。没有跨模型通用的最佳数值，实际回答应提供实验依据。

LoRA落地场景、常用超参配置

答：LoRA 的核心思想是在冻结原始权重 \(W_0\) 的基础上，增加一个低秩增量：

\[ W=W_0+\Delta W,\quad \Delta W=\frac{\alpha}{r}BA \]

其中 \(A\in \mathbb{R}^{r\times d_{in}}\)，\(B\in \mathbb{R}^{d_{out}\times r}\)，\(r\) 是 rank，\(\alpha\) 是缩放系数。训练时只更新 \(A\) 和 \(B\)，原模型参数不动。推理时可以把 \(\Delta W\) merge 回原权重，所以几乎不增加推理延迟。

LoRA 常见落地场景包括：

  1. 领域适配：客服、医疗、金融、电商、视频内容理解等垂直领域数据量不大，但希望模型学习领域术语和回答风格。

  2. 指令微调：用少量高质量指令数据提升模型在某类任务上的遵循能力。

  3. 多任务适配：同一个基座模型挂多个 LoRA adapter，不同业务按需加载不同 adapter。

  4. 多模态模型适配：对 LLM 的 attention/MLP、vision projector 或部分视觉编码器做 LoRA，提高图文问答、OCR、检索、视频理解能力。

  5. 低资源训练：显存有限时，用 QLoRA + 4bit 量化基座 + LoRA 训练，可以显著降低成本。

常用超参配置可以按任务规模选择：

参数 常见取值 经验说明
target_modules q_proj、k_proj、v_proj、o_proj，或再加 gate/up/down_proj 只调注意力更稳，调 MLP 表达力更强但更容易过拟合
r 4、8、16、32、64 小数据从 8/16 起，大任务可到 32/64
alpha 16、32、64、128 常用 alpha = 2r 或 4r
dropout 0、0.05、0.1 小数据建议 0.05 左右防过拟合
learning rate 1e-4 到 3e-4 LoRA 通常比全参微调学习率更大
batch size 视显存而定，配合梯度累积 保证有效 batch 稳定即可
epoch 1 到 3 指令数据质量高时不宜训练太久
precision BF16 优先 A100/H100/4090 等通常优先 BF16

面试时可以补一句：LoRA 不是 rank 越大越好。rank 过小表达力不足，rank 过大容易过拟合且训练成本上升。实际要通过验证集、业务指标和人工评测共同选择。

补充说明

回答： LoRA 冻结原模型权重，只训练低秩增量矩阵 ΔW=BA，从而降低显存和训练成本。适合数据量有限、需要快速适配垂直任务或多租户部署的场景。r 越大表达能力越强，但参数、显存和过拟合风险也越高；选择时要结合任务复杂度、数据量、target modules、alpha 和 dropout 一起调。

Loss mask 设置错误会有什么后果？

常见错误包括：

  • user 参与 loss：模型可能学习复述用户输入，而不是回答问题。

  • system 参与 loss：模型可能泄露或复述系统提示，影响安全性和对话格式。

  • assistant 没有完整参与 loss：模型回答能力学习不足，输出容易截断或格式不稳定。

  • EOS 被 mask 掉：模型可能学不会在合适位置停止，导致输出过长或停不下来。

  • 工具参数被 mask 掉：模型无法稳定生成函数名、参数 JSON 或工具调用格式。

  • tool response 参与 loss：模型可能学习伪造工具返回结果，而不是调用工具获取真实结果。

  • padding 参与 loss：模型会学习无意义 padding token，影响训练稳定性。

  • chat template 边界错误：模型可能混淆 user、assistant、tool 等角色。

  • packing 边界错误：不同样本之间可能串扰，导致模型学习到错误上下文关系。

MAE 的预训练策略与关键设计是什么？为什么遮蔽率高达 75%？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐⭐ (5/5)

MAE（Masked Autoencoder）用自监督的掩码重建预训练 ViT，不需要标注。做法是随机遮住 75% 的 patch，只把剩下 25% 的可见 patch 送进编码器，再用一个轻量解码器重建被遮住 patch 的像素[11]。它有两个关键设计：

  1. 遮蔽率 75%，远高于 BERT 的 15%。 图像的信息冗余比文本高得多，一张猫的照片遮掉四分之三，剩下的部分往往仍能看出是猫。只遮 15% 的话，模型靠相邻像素插值就能完成重建，学不到语义。遮蔽率拉高以后，模型必须理解整张图的内容才能补全[11,13]。

  2. 编码器只处理可见的 25% patch。 被遮住的 patch 到解码阶段才以 mask token 的形式加入。编码器的输入长度只有原来的四分之一，解码器又很轻（默认 8 层、512 维，每个 token 的计算量不到编码器的 10%），MAE 论文报告整体预训练提速 3 倍以上[11]。

面试速答：MAE 随机遮住 75% 的 patch，编码器只处理可见的 25%，再由轻量解码器补上 mask token 重建像素。遮蔽率这么高，是因为图像冗余大，遮得少靠邻近像素插值就能补全，学不到语义。编码器输入变短、解码器又轻，预训练能提速 3 倍以上。

MotionLoRA / MotionDirector 解决的本质问题是什么？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

两者都做运动定制，但解决的问题不同。

  • MotionLoRA 解决适配成本：在已有 Motion Module 上学习低秩增量，用少量参数适配新的运动模式，例如平移、缩放等镜头运动。交付物是可加载、替换或组合的轻量运动权重。
  • MotionDirector 缓解运动与外观耦合：直接用少量视频训练 LoRA 时，模型可能把“谁在动”和“怎么动”一起记住，使运动表征混入训练主体的外观信息。MotionDirector 用双路径 LoRA 分开承载外观与运动，并通过 appearance-debiased temporal loss 减少外观对时间学习目标的干扰。

从失败现象判断问题在哪一层

工程上不能只看训练参数量。若把“某只玩具熊举重”的运动迁移给汽车，结果仍带有玩具熊的颜色或形状，说明运动表征中混入了训练主体的外观信息；如果主体保持正常但动作幅度不足，则要继续检查训练片段是否对齐、目标运动是否稳定出现，以及镜头运动和物体运动是否被混在一起。

解耦仍有数据边界

MotionDirector 的解耦也不是严格的物理分解。训练样本过少、背景固定或主体与动作高度绑定时，模型仍可能借助外观线索拟合运动。

面试速答：MotionLoRA 用低秩更新降低运动定制成本；MotionDirector 进一步处理运动表征混入训练主体外观信息的问题。前者强调参数效率，后者强调运动跨主体迁移时的解耦质量。

ONNX Runtime如何通过图优化、算子库和内存管理提升推理性能？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

一、图优化：减少不必要计算和调度开销

ONNX Runtime加载模型后，会对ONNX计算图进行优化。常见优化包括：

  1. 常量折叠：把推理前就能确定的常量计算提前算好
  2. 无效节点消除：删除不影响输出的节点
  3. 算子融合：把连续算子合并成更高效的组合算子
  4. 布局优化：根据后端需要调整数据布局
  5. 子图划分：将不同子图分配给不同Execution Provider执行

例如，Conv + BatchNorm、MatMul + Add、Attention中的部分模式都有机会被融合，从而减少中间张量读写和kernel launch开销。

二、算子库：让单个算子执行更快

图优化解决“计算图怎么组织”，算子库解决“每个算子怎么执行”。ONNX Runtime会根据EP选择不同算子实现：

  • CPU EP使用CPU优化kernel、多线程和SIMD指令
  • CUDA EP使用CUDA kernel、cuDNN、cuBLAS等库
  • TensorRT EP调用TensorRT构建优化子图
  • OpenVINO EP调用OpenVINO后端优化Intel硬件执行

如果关键算子有高性能实现，推理速度会明显提升；如果关键算子只能走通用实现或回退CPU，性能可能不理想。

三、内存管理：减少分配开销和内存浪费

ONNX Runtime在运行时会做内存优化，常见包括：

  1. 内存复用：生命周期不重叠的中间张量复用同一块内存
  2. 内存池：减少频繁申请和释放内存的开销
  3. Arena Allocator：为CPU/GPU内存分配做缓存和复用
  4. 静态内存规划：对shape稳定的模型提前规划中间张量内存

这些优化可以降低峰值内存、减少分配释放开销，并提升推理稳定性。

四、Session配置也会影响性能

ONNX Runtime推理性能还和Session配置有关，例如：

  • graph_optimization_level：控制图优化级别
  • intra_op_num_threads：单个算子内部并行线程数
  • inter_op_num_threads：多个算子之间并行线程数
  • providers顺序：决定优先使用哪个EP
  • 是否开启TensorRT EP缓存、FP16、INT8等能力

示例：

import onnxruntime as ort

options = ort.SessionOptions()
options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
options.intra_op_num_threads = 8

session = ort.InferenceSession(
    "model.onnx",
    sess_options=options,
    providers=["CPUExecutionProvider"],
)

可以总结为：ONNX Runtime通过图优化减少冗余计算和调度开销，通过不同Execution Provider调用高性能算子库，通过内存池和张量复用降低内存分配开销。实际性能取决于模型结构、EP选择、算子覆盖、线程配置、输入shape和batch大小，需要通过压测验证。

ONNX模型推理结果与训练框架不一致时如何定位问题？

难度评分：⭐⭐⭐⭐⭐ (5/5) | 考察频率：⭐⭐⭐ (3/5)

一、先确认是不是输入和模式问题

很多ONNX输出不一致不是导出的问题，而是输入预处理或模型状态没对齐。

首先检查：

  1. 模型是否处于eval模式：Dropout、BatchNorm在训练和推理下行为不同
  2. 输入是否完全一致：shape、dtype、layout、归一化、RGB/BGR顺序是否一致
  3. 随机性是否关闭：推理过程中不应有随机增强、随机采样或未固定行为
  4. 输出是否取错：多输出模型中输出顺序、名称是否对应正确

这一步能解决大量看似“ONNX不准”的问题。

二、先用最保守后端对齐

建议排查顺序是：

PyTorch输出
  ↓ 对齐
ONNX Runtime CPU EP
  ↓ 对齐
ONNX Runtime CUDA EP
  ↓ 对齐
TensorRT / OpenVINO等优化后端

原因是CPU EP通常最接近ONNX标准语义，适合先验证导出是否正确。如果CPU EP和PyTorch都不一致，问题大概率在导出或输入对齐；如果CPU EP一致但TensorRT不一致，问题更可能在后端优化、精度或算子支持上。

三、比较数值误差要设置合理阈值

不同后端和精度下，数值完全一致不现实。通常要根据精度设置合理阈值：

  • FP32：误差应较小，可以使用较严格 rtol/atol
  • FP16/BF16：允许更大误差
  • INT8/INT4：必须结合校准数据和任务指标看精度损失
  • TensorRT融合后：可能因算子融合和计算顺序变化产生细微差异

因此，不要只看单个元素是否完全相同，而要看最大误差、平均误差、余弦相似度以及最终任务指标。

四、定位到具体层或算子

如果最终输出差异较大，需要缩小范围：

  1. 导出中间层输出：把关键中间节点临时作为模型输出
  2. 二分定位模块：逐段比较Backbone、Neck、Head等模块输出
  3. 使用Netron查看图结构：确认算子是否被错误转换或融合
  4. 检查高风险算子：Resize、Pad、Slice、Gather、NMS、TopK、LayerNorm等
  5. 关闭部分优化：降低图优化级别，判断是否由优化引入差异

对于TensorRT，还可以使用Polygraphy对比ONNX Runtime和TensorRT在各层输出上的差异。

五、常见问题来源

常见不一致来源包括：

  • BatchNorm未切eval
  • 输入预处理不一致
  • Resize/Interpolate的align_corners或坐标变换模式不同
  • trace导出固化了某个分支
  • 动态shape下Reshape/Slice行为异常
  • 后处理逻辑没有一起对齐
  • FP16/INT8量化带来的数值误差
  • TensorRT算子融合或Plugin实现不一致

可以总结为：ONNX输出不一致时，应先排查eval模式、输入预处理、输出名称和dtype等基础问题；再按PyTorch、ONNX Runtime CPU、CUDA、TensorRT/OpenVINO的顺序逐级对齐；如果仍不一致，就通过中间层输出、图可视化、关闭优化和工具对比定位到具体算子。最终还要结合任务指标判断误差是否可接受。

Open-Sora 如何把前沿视频模型拆成可复现、可优化的开放训练管线？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

Open-Sora 的价值在于把视频基础模型拆成可以单独训练、替换和评测的工程链路，而不是复刻一个未公开的 Sora 实现：

原始视频 -> 清洗与重标注 -> 视频压缩器 -> 时空 latent token
        -> 视频 DiT / STDiT -> 分阶段训练 -> 采样与系统优化

主导成本来自时空 token

主导矛盾是 token 成本。压缩器降低时空尺寸，时空去噪器学习 latent 上的运动与语义，数据和训练系统则决定有限算力被哪些样本消耗。若压缩并 patchify 后的 latent 网格为 \(T_z\times H_z\times W_z\) ，全时空注意力的计算量随 token 数近似二次增长：

\mathcal{O}(N^2), \quad N = T_z \times H_z \times W_z

因此，开放实现的价值不只在“有代码”，而在于能够回答四个工程问题：压缩损失有多大，时空交互花了多少算力，数据质量与训练阶段如何分配预算，最终吞吐和显存是否可复现。Open-Sora 2.0 进一步把数据整理、架构、训练策略和系统优化放进同一成本框架。

Open-Sora 与 Open-Sora Plan 是两套项目

前者使用 STDiT 等路线探索高效开放训练；后者是另一个项目，其 WF-VAE 用小波分解与 causal cache 降低长视频分块编解码的内存和边界问题，Skiparse/SUV 去噪器则用稀疏时空交互降低 DiT 成本。它们共享“开放复现前沿视频模型”的目标，但不是同一项目的前后版本。

P-Tuning v2 进一步增强了 P-Tuning。它不再只在输入层添加连续 Prompt，而是将软 Prompt 扩展到多层 Transformer 中，也就是常说的 Deep Prompt。

Policy Gradient 为什么能直接优化策略？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐ (3/5)

Policy Gradient 直接参数化策略：

\[ \pi_\theta(a|s) \]

目标是最大化期望回报：

\[ J(\theta)=\mathbb{E}_{\pi_\theta}[R] \]

策略梯度的基本形式：

\[ \nabla_\theta J(\theta)=\mathbb{E}[\nabla_\theta \log \pi_\theta(a|s) R] \]

优点：

  • 可处理连续动作。
  • 能学习随机策略。
  • 直接优化目标策略。

缺点：

  • 方差大。
  • 样本效率低。
  • 训练不稳定。

Actor-Critic 和 PPO 都是在这个方向上改进稳定性和样本效率。

Prefill和Decode阶段的瓶颈分别是什么？为什么需要分开优化？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

一、两阶段瓶颈的本质差异

Prefill阶段——计算密集型（Compute-Bound）

Prefill一次性处理所有Prompt Token： - 计算量：O(n²)注意力 + O(n) FFN（n = Prompt Token数） - 瓶颈：GPU的FLOPS（计算能力），而非HBM带宽 - 优化方向：让GPU的Tensor Core"吃饱"——大batch、大矩阵运算 - 对硬件的要求：高FLOPS的GPU

Decode阶段——访存密集型（Memory-Bound）

Decode逐个Token生成： - 计算量：O(n)注意力（单Token）+ O(1) FFN - 瓶颈：HBM带宽，GPU等待数据从显存搬运到计算单元 - 优化方向：减少每步Decode的访存量——MQA/GQA、KV Cache量化、减少KV Cache尺寸 - 对硬件的要求：高HBM带宽的GPU

二、分开优化的必要性

将Prefill和Decode放在同一GPU上处理，会产生干扰：

  1. Prefill的"计算轰炸"会抢占Decode的计算资源：当一个大Prompt的Prefill正在密集使用Tensor Core时，同时运行的Decode请求可能被"饿死"
  2. Decode的"带宽占用"会拖慢Prefill：Decode需要持续读取KV Cache（占用大量HBM带宽），影响Prefill阶段的权重加载速度
  3. 调度复杂度增加：在同一个Scheduler中同时管理两种不同瓶颈的请求，调度策略更难兼顾TTFT、TPOT和吞吐

瓶颈 优化策略

Decode（访存密集） 减少KV Cache大小（GQA/量化）、减少访问KV Cache的次数（多Token预测）、更高HBM带宽

Prefix Tuning 的基本原理是什么？

Prefix Tuning 是一种参数高效微调方法。它的基本思路是：冻结原模型参数，在每层 Transformer Attention 中加入一组可训练的 Key / Value 前缀向量，用这些前缀向量引导模型生成结果。

在标准 Transformer Attention 中，模型会根据输入计算 Query、Key、Value。Prefix Tuning 不直接修改原模型权重，而是在每一层 Attention 的 Key / Value 前面拼接一段可训练的前缀：

K' = [K_prefix; K]
V' = [V_prefix; V]

其中，K_prefix 和 V_prefix 是可训练参数，原模型参数保持冻结。

Prefix Tuning 的缺点是什么？

  • 会增加每层注意力前缀的计算与状态开销：每层都引入额外前缀。
  • 对前缀长度敏感：Prefix 太短表达能力不足，太长会增加开销。
  • 对初始化较敏感：初始化不好可能影响收敛和最终效果。
  • 表达能力通常不如 LoRA：尤其是在复杂业务微调或格式适配中。
  • 适配参数管理更复杂：多任务切换时需保证前缀版本与底座模型、Tokenizer 和模板一致。

Prompt优化除了添加规则约束之外，还有哪些常见的方法？你在实际使用中有哪些经验？

回答：

Prompt 优化不应等同于不断追加“必须、不要、严禁”。规则越多越可能互相冲突，也会抬高 Token 成本。更有效的方法包括：

  1. 重写任务定义。 明确目标、受众、输入边界、成功标准和非目标，减少模型猜测。
  2. 提供输出契约。 使用 JSON Schema、字段类型、枚举、单位和失败语义；机器消费场景优先约束解码与解析校验，而不是只靠自然语言格式要求。
  3. 选择高质量示例。 Few-shot 覆盖正常、边界、拒答和反例；示例应解释判定边界，不能只堆同质样本。
  4. 分解任务。 将抽取、检索、判断、生成和核验拆成可独立验证的阶段；稳定步骤用 Workflow，开放步骤再交给 Agent。
  5. 优化上下文。 去重、排序、标注来源与时间，检索真正相关的证据；很多所谓 Prompt 问题，本质是上下文缺失或污染。
  6. 加入工具和验证器。 对事实、计算、权限和业务状态调用真实工具；生成后用规则、单测、引用校验或独立评估器检查。
  7. 做模型和参数适配。 根据任务选择模型、温度、最大输出和推理预算；高随机性创作和低随机性结构化抽取不能使用同一配置。

我的实践是先建立 30～100 条代表性样本和错误分类，再做单变量迭代：记录 Prompt/模型/工具版本，比较任务成功率、结构化解析率、事实忠实度、Token 和延迟。线上 bad case 必须回流到回归集。没有固定评测集时，Prompt “变长了”通常只意味着更难维护，并不能证明更好。

Q-Former 的两阶段训练如何实现跨模态对齐？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐⭐ (5/5)

Q-Former 的训练分两个阶段，分别解决视觉特征怎样抽取、抽取出的特征怎样交给 LLM 两个问题，如图 3-4 所示。这里聚焦训练流程。

Q-Former 内部有 32 个可学习的 query 向量，每个 768 维。这些 query 通过 cross-attention 读取冻结视觉编码器输出的图像特征，把数量多、维度高的视觉特征压成 32 个固定的输出向量。输出是 32×768，而 ViT-L/14 输出的图像特征是 257×1024[14]。这 32 个向量作为视觉 token 交给 LLM。使它们完成跨模态对齐的两阶段训练如下：

  1. 第一阶段，视觉-语言表示学习。 Q-Former 接在冻结的视觉编码器后面，还不接 LLM，用 BLIP 同款的三个目标联合训练，即 ITC（图文对比）、ITM（图文匹配）和 ITG（Image-grounded Text Generation，图像引导的文本生成）。不同任务用不同的自注意力 mask，控制 query 和文本 token 能否互相看见，迫使 query 抽取和文本最相关的视觉信息，丢掉冗余的像素细节[14]。

  2. 第二阶段，视觉到语言的生成学习。 把第一阶段训好的 Q-Former 接到冻结的 LLM 前面，输出的 32 个向量经一层全连接投影到 LLM 的词嵌入维度，作为软视觉提示（soft visual prompt）拼在 LLM 输入文本的前面。这一阶段 LLM 冻结，只训练 Q-Former 和线性投影层，用语言建模损失让 LLM 根据这些视觉 token 生成正确的文本。接 decoder-only 的 OPT 时用普通的语言建模损失；接 encoder-decoder 的 FlanT5 时用前缀语言建模损失，把文本切成两段，前一段和视觉表示一起送进编码器，后一段作为解码器的生成目标[14]。

分两阶段的原因是，如果跳过第一阶段直接接 LLM，query 还不会抽取有意义的视觉信息，LLM 要自己承担视觉和语言对齐，负担重。论文的消融显示，去掉第一阶段后，两类 LLM 的零样本 VQA 效果都明显下降，用 OPT 时还出现了灾难性遗忘，训练越久性能越差[14]。

Q-Former 的 32 个 query 起到信息瓶颈的作用。一方面把视觉 token 数量压下来，减轻 LLM 的序列长度负担；另一方面经过两阶段训练，这 32 个向量落在 LLM 能理解的语义空间里，冻结两端之间的跨模态对齐靠它完成。

图 3-4 Q-Former 两阶段训练示意图

面试速答：Q-Former 用 32 个可学习 query 通过 cross-attention 把图像特征压成 32 个向量。第一阶段接冻结的视觉编码器，用 ITC、ITM、ITG 训练 query；第二阶段经全连接层接冻结的 LLM，用语言建模损失训练。跳过第一阶段会使零样本 VQA 明显下降。

QLoRA 是什么？

QLoRA（Quantized LoRA） 在 LoRA “冻结底座模型、只训练低秩适配器”的基础上，将冻结的底座模型权重量化到 4-bit 存储，从而进一步降低显存占用。

需要注意的是，QLoRA 通常不是把所有参数都用 4-bit 训练，而是：

  • 冻结的底座模型权重 以 4-bit 形式存储；
  • LoRA 参数 通常保持 FP16/BF16 等较高精度训练；
  • 前向和反向传播时，4-bit 权重会按需反量化到 FP16/BF16 等计算精度参与矩阵运算；
  • 反向传播会经过冻结的量化底座模型，但梯度和优化器状态主要只为 LoRA 参数保存；
  • 训练完成后通常只保存 LoRA Adapter 权重。

QLoRA 有什么优缺点？

优点：

  • 显存占用低：底座模型 4-bit 存储，明显降低权重显存；
  • 硬件门槛低：可以在较小显存 GPU 上微调更大的模型；
  • 训练成本低：相比全参微调和普通 LoRA，更适合个人、中小团队和低成本实验；
  • 效果较好：在很多指令微调、领域适配和业务任务上，可以接近普通 LoRA 或全量微调效果；
  • Adapter 管理灵活：可以为不同任务保存不同 LoRA Adapter，共享同一个量化底座模型。

缺点：

  • 训练速度可能变慢：量化和反量化会带来额外计算开销；
  • 存在量化误差：对高精度数学、代码、强推理或细粒度任务可能有影响；
  • 实现依赖较强：依赖 bitsandbytes（Python包）、Transformers（Python包）、PEFT（Python包）、CUDA 内核和硬件支持；
  • 权重格式管理更复杂：量化底座、适配器、量化配置与合并策略必须保持兼容；
  • 表达能力仍有限：本质上仍是 PEFT，如果任务和底座模型差异很大，可能不如继续预训练或全量微调。

QLoRA的核心技术和训练过程是什么？

QLoRA 的核心技术包括：

  • 4-bit 量化：将冻结底座模型权重从 FP16/BF16 压缩到 4-bit；
  • NF4（NormalFloat4）：适合神经网络权重近似正态分布的 4-bit 数据格式；
  • Double Quantization：对量化 scale / 常数再次量化，进一步节省量化元数据显存；
  • Paged Optimizer：利用分页机制缓解训练过程中的显存峰值，降低 OOM 风险。

QLoRA 训练可以概括为：

加载预训练模型 → 将底座模型权重量化为 4-bit → 冻结底座模型参数 → 插入 LoRA 低秩适配器 → 前向时按需反量化底座权重参与计算 → 反向时梯度传过底座模型，但只更新 LoRA 参数 → 保存 LoRA Adapter 权重

训练完成后，通常保存的是 LoRA Adapter，而不是完整模型权重。

注：QLoRA 比普通 LoRA 多了一层量化权重格式约束：固定量化类型、计算 dtype、适配器版本和合并策略。

Qwen-VL 三阶段训练范式及各阶段数据策略是怎样的？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐ (4/5)

作为对比，Qwen-VL 确立了更经典的预训练、多任务预训练、监督微调三阶段范式，三个阶段在训练哪些模块、用什么数据上逐步推进：

  1. 阶段一，预训练（Pretraining）。 冻结 LLM，只训练视觉编码器和投影器，建立基础的图文对齐，输入分辨率 224×224。数据是网络爬取的图文对，从 50 亿条清洗到约 14 亿条[1]，规模大、质量参差，目的是用规模换对齐。

  2. 阶段二，多任务预训练（Multi-task Pretraining）。 解冻全部参数训练整个模型，分辨率提到 448×448。数据覆盖图像描述、视觉问答、视觉定位、指代定位、带定位的描述、OCR 和纯文本自回归 7 类任务，同类任务的数据打包成长度 2048 的图文交错序列[1]，模型的能力广度主要来自这一阶段。

  3. 阶段三，监督微调（Supervised Fine-Tuning）。 冻结视觉编码器，训练 LLM 和投影器，用约 35 万条指令和多轮对话数据微调，得到 Qwen-VL-Chat[1]。

三个阶段先对齐、再扩展任务、最后对齐人类指令，数据从大而粗逐步走向小而精。和渐进式缩放放在一起看，渐进式缩放解决的是视觉编码器跨规模复用的成本，三阶段范式定下的是模块解冻顺序和数据由粗到精的节奏。

Qwen-VL系列模型的三阶段训练范式的具体运作机制与各阶段数据策略？

Qwen-VL的三阶段训练是一个“先预训练，再解锁（多任务预训练），后精修（指令微调（SFT））”的经典范式，后续迭代也基于此进行优化。

第一阶段：预训练

  • 目标：在海量图像-文本对上，让模型学习视觉表征与语言概念的最基本关联。此时，大型语言模型（LLM）的参数是被冻结的，只训练视觉编码器和视觉-语言适配器。这相当于先给模型“植入”视觉神经元。
  • 数据：规模巨大，约50亿对，但经过严格清洗后保留14亿高质量对（英语77.3%，中文22.7%），清洗保留率28%。数据来源多样，如LAION、Coyo等。

第二阶段：多任务预训练

  • 目标：引入高质量、细粒度的标注数据，解锁所有模型参数，激发模型的多任务能力（如VQA、定位、OCR等）。
  • 数据：约77M样本，任务类型多达7种，包括说明、VQA、对齐、引用对齐、接地说明、OCR、纯文本自回归。数据来源包括GRIT、RefCOCO等权威数据集和内部数据。
  • 在此阶段，图像分辨率会提升至448x448，并移除窗口注意力以捕捉更多细节。

第三阶段：指令微调（SFT）

  • 目标：让模型学会遵循人类指令进行对话和任务执行。此时，视觉编码器被冻结，只微调LLM和适配器，生成最终的Chat版本。
  • 数据：使用约350K指令数据，包含模型自生成的描述、人工标注的定位数据、以及多轮对话数据，旨在让模型变得“有用”和“易用”。

Qwen2.5-VL在此基础上进一步细化，将预训练拆分为视觉预训练、多模态预训练、长上下文预训练三个阶段，并引入了拒绝采样等高级技术来极致化数据质量，但其核心思想仍源于此范式。

Qwen2.5-VL后训练阶段如何结合监督微调（SFT）和直接偏好优化（DPO）？

Qwen2.5-VL的后训练采用了一种非常精细的双阶段优化范式，旨在先提升能力，再对齐偏好。整个后训练阶段，视觉编码器的参数都是被冻结的。

首先在监督微调（SFT）阶段，核心任务是使用约200万条高质量的指令数据来充分激发模型在预训练中获得的各种能力。这批数据是精心配比的，包含50%的纯文本数据和50%的多模态（图文和视频文本）数据。为了保证数据质量，引入了一个基于Qwen2-VL的分类模型（Qwen2-VL-Instag）对海量候选数据进行智能分类和过滤。

最关键的一步是采用了拒绝采样（Rejection Sampling） 技术。具体来说，使用一个中间版本的Qwen2.5-VL模型，对一批带有标准答案的数据集（有Ground Truth）进行推理，生成模型的响应。然后，将模型的输出与标准答案进行严格比对，只保留那些模型输出与正确答案匹配的样本，而自动丢弃那些生成错误、冗长、存在代码切换或重复模式的低质量样本。

这个过程就像一个极其严格的“考官”，只有交出满分答卷的样本才能进入最终的高质量SFT数据集。通过这种方式，确保了用于微调的数据都是最高效、最准确的“教学材料”，从而让模型的性能提升事半功倍。

在随后的直接偏好优化（DPO）阶段，目标从“提升能力”转向“修正行为”，即让模型的输出更符合人类的偏好和价值观。使用人工标注的偏好数据（例如，选择哪个回答更好），对模型进行训练。值得注意的是，此阶段主要使用图文和纯文本数据，暂不涉及更复杂的视频模态。通过DPO，模型学会了输出更受欢迎、更有帮助且更安全的回答，完成了从“能力强大”到“行为友善”的转变。

Qwen2.5-VL预训练数据构建的核心质量策略？

Qwen2.5-VL的性能飞跃，很大程度上源于在数据质量上进行的“精耕细作”。不再仅仅追求数据规模，而是通过一系列系统性的策略来构建一个“精英”数据集。

核心策略主要包括以下几个方面：

  1. 交错图文数据的精细化清洗：从海量原始数据中，通过基于CLIP模型的数据评分和一系列去重、去污的清洗流程，筛选出真正高质量、图文高度相关的样本。这确保了基础视觉-语言关联学习的可靠性。
  2. grounding数据的绝对坐标化：正如之前提到的，在检测和定位数据中摒弃了归一化坐标，采用基于图像真实尺寸的绝对坐标。这一改动虽然微小，但让模型学习到的空间关系是基于真实世界的尺度，极大提升了其在现实应用中的泛化能力。
  3. 文档数据的结构化合成：合成了大量包含表格、图表、公式、乐谱等复杂元素的文档数据，并统一用HTML格式来标注。这种结构化的表示方式让模型能无缝地理解和推理文档中的多模态元素之间的关系。
  4. 视频数据的时序精细化标注：对于视频数据，不仅动态采样帧，还构建了详细的长视频标题描述，并以“时分秒帧”（hmsf）的格式精确标注时间戳，让模型能够建立精确的时序理解。
  5. 智能体数据的多维构建：为了训练模型成为屏幕智能体，收集了移动端、Web和桌面的截图，并利用合成引擎生成了对UI元素的精准接地（grounding）注释。这使得模型能理解“可点击的按钮”在屏幕上的具体位置。

所有这些策略的共同点在于：不仅提供数据，更提供数据的精确上下文和结构化信息。是在为模型构建一个标注清晰、结构严谨的“教科书”，而不仅仅是提供一堆“阅读材料”。

Ref-SAV数据集是如何设计的？它在Sa2VA模型的训练中起到了什么作用？

Ref-SAV数据集是通过一个自动标注管道生成的，旨在解决现有指代视频分割数据集规模小、短片段和遮挡少的问题。具体来说，Ref-SAV数据集的生成过程包括三个阶段：

  • 对象/部分级别标注：从视频中选取包含最大对象面积的视频帧，并裁剪出非对象像素。然后将裁剪后的图像输入到InternVL2-76B模型中生成详细描述， 并通过Qwen2-72B模型进行一致性检查。
  • 场景级别标注：使用黄色轮廓在图像中突出显示对象，并将图像和对象/部分级别的描述输入到InternVL2-76B模型中，生成包含对象与场景和周围对象关系的详细描述。
  • 视频级别标注：从视频中均匀采样8帧，并使用黄色边框突出显示对象。将这些帧和场景级别的描述输入到InternVL2-76B模型中，生成捕捉对象运动和动作的视频级别描述。

Ref-SAV数据集在Sa2VA模型的训练中起到了重要作用，具体体现在：

  • 提升模型性能：通过使用Ref-SAV数据集进行训练，Sa2VA在复杂环境下的指代视频分割任务中表现出色，显著优于现有的基准模型。
  • 补充数据多样性：Ref-SAV数据集引入了更复杂的遮挡、长文本输入和运动模糊，增强了模型的鲁棒性和泛化能力。

RL全流程需要重点监控哪些核心训练指标，如何根据指标调优？

回答：

RL 训练要监控三类指标：优化指标、行为指标和业务指标。只看平均 reward 很危险，因为 reward 可能被 hacking，也可能掩盖不同场景的退化。

优化指标包括 reward mean/std、advantage 分布、policy loss、KL divergence、entropy、clip ratio、梯度范数、学习率、生成长度、拒答率。KL 太高说明策略偏离 reference 太快，要加大 KL penalty、降低学习率或缩短更新步数；KL 太低且 reward 不涨，说明模型学不动，可以降低 KL、提高采样多样性或增强 reward 区分度。Entropy 太低说明策略塌缩，可能需要提高探索、增加样本多样性；entropy 太高则说明输出不稳定。

行为指标包括格式合法率、字段准确率、证据命中率、多抽/漏抽率、幻觉率、长度分布、模板化比例和安全违规率。这些能发现 reward 没覆盖的问题。比如 reward 涨但格式合法率下降，说明 reward 权重不平衡；长度持续变长，可能是模型用冗长推理骗分；拒答率异常升高，可能是模型学会保守逃避。

业务指标包括线上 A/B、人工复核通过率、工单节省、人效提升、转化率、延迟和成本。调优时要按问题定位：数据问题补样本，reward 问题改规则，策略问题调 KL/学习率/group size，工程问题优化 rollout 和 batch。成熟 RL 不是一次跑完，而是“训练指标 - badcase - reward 修正 - 数据回流”的循环。

RL训练中如何兼顾难易样本，提升模型对高难度业务任务的探索能力？

回答：

兼顾难易样本，本质是控制训练课程和探索分布。简单样本保证基础能力和稳定 reward，高难样本提升上限和业务价值。只训练简单样本，模型会保守；只训练难样本，reward 稀疏、方差大、训练容易崩。

第一，建立难度分层。可以用人工标签、历史模型错误率、字段数量、文本长度、歧义程度、规则复杂度、reward 方差、是否长尾场景来定义 difficulty score。训练集按 easy、medium、hard、adversarial 分桶。

第二，做课程学习。早期 easy/medium 比例高，让模型学会格式和基础策略；中期提高 hard 样本比例；后期加入线上 badcase 和对抗样本。也可以用自适应采样：模型在哪类样本错得多，就提高该类样本采样权重。

第三，提升探索质量。GRPO 场景可以对高难 prompt 增加 group size 或采样温度，让模型产生更多候选路径；对可验证任务用 outcome reward + format reward；对长链路任务加入过程检查或中间 reward，降低稀疏奖励难度。

第四，防止困难样本破坏基础能力。保留一部分简单样本 replay，使用 KL 约束和验证集分层监控。如果 hard set 提升但 easy set 退化，说明训练过度偏向困难分布。

最终目标不是让所有样本平均出现，而是让采样概率与业务价值、模型薄弱点和训练阶段匹配。高难任务的探索能力来自更好的课程设计，而不是简单把难题堆进训练集。

RL训练数据集的构建思路，能否直接复用SFT阶段的训练数据？

回答：

RL 数据可以复用一部分 SFT prompt，但不能简单复用 SFT 的“输入-标准答案”格式。SFT 数据强调示范答案，RL 数据强调可采样、可比较、可打分。两者的数据对象不同。

构建 RL 数据集时，首先要选 prompt。prompt 应覆盖真实业务分布、困难样本、长尾样本、容易出错样本和高价值样本。其次要定义 reward 或偏好标准。字段抽取可以用规则和标准答案算 reward；开放问答可能需要人工偏好、reward model 或 LLM judge；推理任务最好有可验证最终答案。第三要准备评测集和隔离集，避免训练 reward 对评测泄漏。

SFT 数据可以复用的部分主要是 prompt、任务说明、部分高质量参考答案和冷启动样本。但 RL 阶段更需要同一 prompt 下的多候选答案、chosen/rejected 偏好、规则 reward、错误样本和边界样本。如果直接拿 SFT 标准答案做 RL，容易变成另一次监督学习，无法提供策略探索信号。

所以答案是：可以复用，但要重构。把 SFT 数据中的高质量 prompt 作为 RL 初始池，补充模型采样结果、reward 标注、困难样本和线上 badcase。SFT 教模型“怎么做”，RL 数据要让模型知道“做成什么样更值钱”。

SFT 加 DPO 两阶段组合与冻结 ViT 是出于什么考量？

后训练的第一类范式是监督微调提升能力、偏好优化调整对齐，Qwen2.5-VL 是标准样本，两个阶段都冻结 ViT，只更新语言侧[3]，其做法与考量依次为：

SFT 的数据集是越大越好吗？会存在 scaling law 吗？

回答：

不是越大越好。有效收益取决于质量、覆盖、重复率、任务混合、难度与模型当前能力。大量错误或同质样本可能把有限计算花在重复模式上，甚至造成格式偏置和通用能力退化。

Scaling law 是在特定模型、数据分布和训练配置下观察到的经验规律，不能直接把预训练的幂律套到 SFT 样本数。后训练更容易受标签质量、分布匹配和目标饱和限制，不保证存在跨任务通用的指数。

SFT的终止判定条件，满足哪些标准可切入RL训练？

回答：

SFT 终止不能只看训练 loss。训练 loss 下降说明模型更像训练答案，但不代表业务效果继续提升。合理的终止条件应该同时看验证指标、格式稳定性、泛化能力、badcase 类型和进入 RL 的前置条件。

第一，验证集核心指标进入平台期。例如字段抽取 F1、准确率、代码 pass rate、数学正确率、拒答准确率不再明显提升。第二，格式合法率达到线上底线，例如 JSON 可解析率、字段完整率、schema 合法率稳定。第三，训练集和验证集差距没有继续扩大，说明没有明显过拟合。第四，badcase 主要变成“偏好排序、复杂推理、边界策略”问题，而不是基础指令理解和格式错误。

切入 RL 还需要额外条件：reward 能可靠计算，且能区分候选答案好坏；同一 prompt 多次采样有足够多样性；评测集能覆盖简单、困难、长尾和安全样本；KL 约束、长度约束、格式约束和停止条件设计清楚。否则 RL 会把模型推向 reward 漏洞，而不是业务目标。

一句话总结：SFT 结束的信号是“模型已经会做事，但还需要学会做得更好”；如果模型还不会稳定做事，先继续修数据和 SFT，不要急着上 RL。

SFT训练达到怎样的效果指标后，才适合接入RL优化阶段？

回答：

判断能否进入 RL，不是看 SFT loss 降到多低，而是看模型是否已经具备稳定的基本能力。RL 会放大模型已有行为，如果 SFT 阶段连格式、任务理解和基础正确率都不稳定，直接接 RL 很容易把噪声也放大，出现 reward hacking 或训练震荡。

可以从五类指标判断。第一是基础任务成功率：在固定验证集上，答案正确率、字段抽取 F1、代码通过率、数学结果准确率等要达到可用底线。第二是格式稳定性：结构化输出 JSON 可解析率、字段完整率、schema 合法率要足够高，否则 reward 无法可靠计算。第三是分布泛化：不能只在训练同源样本上好，要在保留集、困难集、长尾集上保持稳定。第四是安全和拒答能力：不能为了答题强行编造，要有基本边界。第五是采样多样性：同一 prompt 下多次采样要能产生有差异的候选，否则 GRPO/PPO 这类策略优化很难获得有效学习信号。

工程上常见门槛可以设成：格式合法率接近线上要求，核心任务指标明显高于基座模型，badcase 主要集中在推理策略或偏好排序，而不是基础理解错误；reward 函数可以稳定区分好坏样本；训练样本和评测集已经去重并分层。达到这些条件后，RL 才像是在“精修策略”，而不是拿强化学习给脏数据和弱模型兜底。

SFT训练过程中，如何平衡简单任务与复杂任务的训练权重？

回答：

简单任务和复杂任务的矛盾在于：简单任务能稳定模型格式和基础能力，但占比过高会让模型变得模板化；复杂任务能提升推理和泛化，但太早或太多会造成训练不稳定。平衡策略应该是课程学习 + 动态采样 + 分层评测。

训练早期可以提高简单高质量样本比例，让模型先学会任务定义、输出格式、基本字段和安全边界。中期逐步增加复杂任务，例如多字段抽取、长文本推理、多约束生成、跨表推断、工具调用和拒答判断。后期重点加入真实 badcase、长尾场景和高难样本，修复线上薄弱点。

权重设计上，可以给不同样本打 difficulty score 和 business value score。高业务价值但困难的样本不一定一开始高权重，而是随训练阶段逐步提升。也可以对 loss 做样本级权重，对关键字段 token 做 loss mask 或加权，避免模型把大量无关解释学得很好、关键字段却不准。

评估时必须拆分简单集、困难集、长尾集和线上回放集。如果简单任务提升但复杂任务下降，说明模型可能过拟合模板；如果复杂任务提升但基础格式崩了，说明课程推进太快。真正的平衡不是平均混合，而是让模型先稳、再强、最后对业务高价值难点做定向优化。

SG-I2V方法如何在预训练的视频扩散模型中实现特征的对齐？

SG-I2V通过对自注意力层进行修改来实现特征的对齐。具体来说，原始的SVD模型在每个帧上独立应用空间自注意力，这导致跨帧的特征对应关系较弱。 为了解决这个问题，SG-I2V将每个帧的自注意力层的键和值替换为第一帧的键和值，从而使得所有帧的特征在语义上对齐。 这种修改后的自注意力层能够更好地捕捉跨帧的语义信息，使得优化过程能够更有效地控制视频元素的轨迹。

Sora 为什么保留原始宽高比和可变时空尺寸训练？工程上如何组织数据？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

把训练视频统一裁成固定正方形、固定帧数，批处理会更简单，但会丢掉两类信息：原始构图可能因裁剪而缺失，真实视频中的宽高比和时长分布也会被人为改写。Sora 技术报告指出，按原始尺寸训练不仅支持横屏、竖屏和不同长度的输出，还能改善取景与构图，减少主体被裁出画面的情况。

可变尺寸训练难在组批和负载均衡

样本的 \(T\times H\times W\) 不同，token 数和单样本显存也不同，不能继续按固定 batch size 粗放组批。常见处理思路包括：

  • 时空分桶：把帧数、分辨率和宽高比相近的样本放进同一批，减少 padding 和无效计算。
  • 按 token 预算组批：限制一个 batch 的总 token 数，而不是固定样本数。高分辨率或长视频每批更少，短视频每批更多。
  • 按计算量做负载均衡：多卡训练若只平均分配样本数，处理长视频的设备会成为拖尾；调度应尽量对齐每张卡的 token 量。
  • 校正采样与损失权重：短视频和低分辨率样本通常更容易装入 batch，若不控制采样比例或归一化方式，它们可能在优化中占据过大权重。

公开事实与通用工程方案要分开

Sora 报告明确披露了原始尺寸训练及其构图收益，但没有公布具体的 bucket、batch 调度和并行实现。上述方法是可变尺寸视频训练需要解决的通用工程问题，不应表述为 Sora 已公开的内部方案。

面试速答：保留原始宽高比和时长可以避免裁剪破坏构图，也让同一模型覆盖多种输出尺寸；训练时则要用时空分桶、token-budget batch 和负载均衡控制 padding、显存及多卡拖尾。

Triton如何支持多模型部署、并发调度和GPU资源利用优化？

难度评分：⭐⭐⭐⭐⭐ (5/5) | 考察频率：⭐⭐⭐ (3/5)

一、多模型部署能力

Triton可以在一个Server进程中同时加载多个模型，每个模型可以使用不同Backend、不同版本和不同实例配置。

例如一个完整视觉服务可能包含：

preprocess模型：Python Backend
  ↓
detection模型：TensorRT Backend
  ↓
postprocess模型：Python Backend

也可以同时部署多个独立模型：

resnet50
bert_classifier
yolo_detector
clip_encoder
ranker_model

这种能力适合模型平台、算法服务中台和多业务共享GPU资源的场景。

二、模型版本管理和热更新

Triton支持按版本目录管理模型。例如：

model_repository/
  ranker/
    config.pbtxt
    1/
      model.onnx
    2/
      model.onnx

可以通过配置决定加载哪个版本，也可以在模型仓库更新后让Triton重新加载模型。

这对灰度发布、模型回滚和A/B实验很重要。

不过，生产中模型热更新仍需谨慎：

  • 新版本输入输出必须兼容业务调用方
  • 需要验证显存是否足够
  • 需要关注加载新模型时的延迟抖动
  • 需要保留回滚方案

三、并发调度机制

Triton面对多个客户端请求时，会根据模型配置将请求放入对应模型队列，然后调度到可用模型实例执行。

影响并发能力的关键配置包括：

  1. Instance Group数量：同一模型启动几个实例
  2. Dynamic Batching配置：是否合并多个请求
  3. 模型Backend能力：底层运行时是否支持高并发执行
  4. GPU数量和实例分布：模型运行在哪些GPU上
  5. 请求输入shape和batch大小：是否容易合并和复用资源

如果一个模型只有一个实例，且单次推理耗时较长，其他请求可能会排队等待；增加实例或开启Dynamic Batching可以改善吞吐，但也会增加显存消耗。

四、GPU资源利用优化

Triton优化GPU资源利用通常从几个方向入手。

  1. 合理设置Instance Group

对于小模型，单个实例可能无法打满GPU，可以启动多个实例提高并发。

对于大模型，多个实例可能导致显存不足或竞争严重，此时应减少实例数量，重点优化batch和模型本身。

  1. 使用Dynamic Batching提高吞吐

当请求较碎、batch较小时，Dynamic Batching可以显著提升GPU利用率。

关键参数是：

  • preferred_batch_size
  • max_queue_delay_microseconds
  • max_batch_size

它们共同决定吞吐和延迟之间的平衡。

  1. 使用TensorRT Engine提升单模型执行效率

如果模型运行在NVIDIA GPU上，通常可以先用TensorRT构建Engine，再由Triton托管。

这样可以同时获得：

  • TensorRT的底层执行优化
  • Triton的服务化和调度能力
  1. 使用Ensemble串联多阶段流程

Triton Ensemble可以把多个模型或处理阶段串成一个逻辑模型，例如：

preprocess → inference → postprocess

这样客户端只需要请求一个服务，Triton内部完成多个阶段的调度。

但如果前后处理逻辑复杂或CPU耗时很高，仍需要单独压测端到端性能。

  1. 结合监控指标调优

Triton调优可以根据以下指标：

  • 请求队列时间是否过高
  • 模型推理时间是否过高
  • batch大小是否达到预期
  • GPU利用率是否偏低
  • 显存是否接近上限
  • P95/P99延迟是否满足SLA

如果GPU利用率低但队列时间高，可能是调度或CPU前后处理瓶颈；如果GPU利用率高且延迟高，可能需要扩容或优化模型。

五、常见调优思路

可以按下面顺序排查：

确认单模型单请求延迟
  ↓
开启TensorRT或更高效Backend
  ↓
调整max_batch_size和Dynamic Batching
  ↓
调整Instance Group数量
  ↓
观察队列时间、推理时间、GPU利用率
  ↓
优化前处理、后处理和数据拷贝
  ↓
根据SLA决定扩容或拆分服务

这个过程是区分瓶颈在模型执行、请求排队、CPU前后处理、数据拷贝还是GPU资源不足。

六、Triton部署的常见注意点

实际生产部署中还要注意：

  • config.pbtxt 中输入输出名称、dtype、shape必须和模型一致
  • max_batch_size 要和模型是否支持batch维度匹配
  • Dynamic Batching可能提升吞吐但增加尾延迟
  • 多实例会增加显存占用
  • TensorRT Engine可能与GPU架构、TensorRT版本和CUDA版本相关
  • Python Backend灵活但性能可能受GIL、CPU和数据拷贝影响
  • Ensemble简化客户端调用，但不一定自动提升性能

可以总结为：Triton通过模型仓库支持多模型多版本部署，通过Backend统一不同模型运行时，通过Instance Group和调度队列支持并发执行，通过Dynamic Batching把小请求合并成batch提高GPU吞吐，并通过监控指标指导资源调优。优化Triton服务时要同时关注模型执行时间、队列时间、batch大小、实例数量、GPU利用率和端到端SLA，而不是只看单次模型推理耗时。

VAPO 类方法主要改进什么？

价值增强的近端策略优化（VAPO）等新方法主要面向 长推理强化学习（Long-chain Reasoning RL / RLVR） 中的 value / advantage 估计、信用对齐、训练稳定性和样本效率问题。

  • 更稳定的 baseline：相比只用组内均值，改进后的 value / advantage 估计可以降低方差，让策略更新更稳定。

  • 更好的长序列优化信号：长推理回答包含大量 token 和中间步骤，改进后的训练目标可以减少长序列中的无效梯度和噪声更新。

  • 更高样本效率：通过筛选更有学习价值的样本、改进 advantage 估计或结合 verifier，减少无效 rollout 带来的训练浪费。

  • 更适合可验证任务：数学、代码、逻辑题可以用答案校验、单元测试、规则奖励或 verifier 判断结果质量，因此更适合这类 RLVR 方法。

  • 缓解 credit assignment 问题：结合过程奖励模型、step-level verifier 或更细粒度价值估计，可以更清楚地学习哪些推理步骤有价值。

Video VAE 的压缩率会如何影响训练和生成质量？

难度评分：⭐⭐⭐⭐⭐ (5/5) | 考察频率：⭐⭐⭐⭐ (4/5)

Video VAE 的压缩率决定生成主干在多小的时空网格上建模，也限定了可恢复视频信息的上限。压缩更强通常能减少后续 token 和 latent 存储，但是否损伤质量，不能只看一个压缩倍数。

先明确“压缩率”指什么。 工程文档常用 \(r_t \times r_h \times r_w\) 表示时间和空间下采样倍数，它描述的是 latent 网格缩小了多少。真正的 latent 数据量还与通道数、数值精度有关；DiT 的 token 数又要继续考虑 patch 大小。两个 VAE 即使网格压缩倍数相同，也可能具有不同的信息容量和计算开销。

空间压缩和时间压缩丢失的内容不同。 空间压缩过强，风险通常集中在小物体、文字、手部、细线条和身份细节；时间压缩过强，更容易削弱短促动作、快速位移和相邻帧变化。因果卷积、时间分组和边界填充还可能让首帧或分组边界的重建表现不同。因此，压缩倍数只能说明规模，不能单独推出重建质量。

VAE 需要通过三项检查。

  • 重建关：在固定输入上检查单帧细节、身份、快速运动、首尾帧和时间边界，既看重建指标，也看按内容类型拆分后的失败样本；
  • 生成关：固定生成主干、训练预算和数据，比较不同 VAE latent 下的收敛速度、生成质量与时序稳定性。重建更好不必然代表 latent 更容易被 Diffusion 或 Flow Matching 建模；
  • 系统关：记录编码与解码吞吐、峰值显存、latent 缓存体积以及生成主干节省的计算，避免只把成本从 DiT 转移到 VAE。

选型时应先确定产品不可接受的重建损失，再在满足质量底线的候选中比较端到端训练和推理成本。VAE 无法稳定重建的细节，即使生成主干能补出视觉上合理的内容，也不能保证与目标视频保持一致。

面试速答：Video VAE 的压缩率决定 latent 网格和生成主干的 token 规模，但网格压缩倍数不等于完整的数据压缩率，还要看 latent 通道和后续 patchify。空间压缩主要影响细节与身份，时间压缩主要影响快速动作和短时变化。选型必须同时比较重建质量、下游生成可学习性和端到端成本，不能只看 PSNR 或压缩倍数。

ViT 原始的有监督预训练方式有何局限？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐ (4/5)

ViT 原论文用有监督图像分类做预训练，沿用的是 CNN 时代的做法。放到 Transformer 上，问题在于它需要海量标注数据。

原论文在 JFT-300M（约 3 亿张带标签的图片）上预训练后，ViT 才超过同级别的 CNN；只用 ImageNet 这种规模的数据训练时，ViT 比同等规模的 ResNet 低几个百分点[1]。

原因在归纳偏置。卷积天然假设局部相关和平移不变，小数据上也能学到像样的视觉特征；ViT 没有这些先验，只能从数据里自己学，需要的样本量就大得多。

这个局限推动了后来的自监督预训练方法，如 MAE、DINO[11,12]。它们不依赖人工标注，可以用更便宜的无标注图片训练 ViT。

面试速答：ViT 原论文用有监督分类预训练，要在 JFT-300M 这种约 3 亿张标注图片的数据上训练才能超过 CNN，只用 ImageNet 时比同规模 ResNet 差。原因是它没有卷积的局部相关、平移不变先验，只能从大量数据里学。这推动了 MAE、DINO 等自监督方法。

Whisper 编码器的模型结构与训练目标是什么？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐⭐ (4/5)

Whisper 是 OpenAI 在 2022 年发布的语音识别模型[4]。它的编码器是语音多模态大模型常用的音频前端，Qwen-Audio 用 Whisper-large-v2 初始化音频编码器[18]，Qwen2-Audio 换成了 Whisper-large-v3[19]，SALMONN 把 Whisper 编码器和音频事件编码器 BEATs 一起用[20]。

下面分别说明 Whisper 编码器的模型结构和训练目标：

  1. 模型结构。 Whisper 是标准的 Encoder-Decoder Transformer，编码器负责把语音转成隐表示。音频先重采样到 16kHz，按 30 秒切窗，转成对数梅尔频谱图（Log-Mel Spectrogram），形状是 (80, 3000)[4]，large-v3 把梅尔频带数改成了 128[21]。接着两层一维卷积做下采样并升到模型隐藏维度，得到长度 1500 的序列，再送进 Transformer Encoder（large 系列 32 层），输出 1500 个语音表示向量[4]。

  2. 训练目标。 Whisper 用大规模弱监督的多任务学习训练。最初的版本用了 68 万小时从网上收集的带转写语音[4]，large-v3 扩展到 100 万小时弱标注数据加 400 万小时由 large-v2 生成的伪标注数据[21]。一个模型同时学多语种语音识别（ASR）、译成英文的语音翻译、语种识别、有无语音检测和时间戳预测，靠在解码器输入端放不同的任务 token 切换任务[4]。训练目标是把语音转成文字，所以编码器输出的表示偏语义，容易和文本对上，适合给 LLM 当输入前端。

多模态模型一般只取 Whisper 的编码器，丢掉原生解码器，再用投影器把编码器输出接到 LLM 的嵌入空间。

面试速答：Whisper 是 Encoder-Decoder Transformer，音频按 30 秒切窗转成对数梅尔频谱，经两层一维卷积下采样成 1500 帧再编码。它用大规模弱监督数据做识别、翻译等多任务训练，表示偏语义。多模态模型常只取编码器接投影器。

ZeRO 和 FSDP 有什么附加开销？

ZeRO/FSDP通过通信换显存，因此会带来额外通信开销，尤其是 ZeRO-3/FSDP 需要频繁 all-gather 参数和 reduce-scatter 梯度。如果网络带宽、拓扑或重叠度策略不好，训练吞吐可能明显下降。

另外，ZeRO/FSDP 会让工程复杂度上升：

  • checkpoint 保存和恢复更复杂，因为参数和优化器状态是分片的；
  • 调试更困难，因为每张卡只持有部分训练状态；
  • 对通信性能更敏感，需要高速互联；
  • 需要合理设置预取、重新分片、桶大小等参数；
  • 和 激活检查点、混合精度、张量并行、流水线并行等其他优化组合时要仔细验证。

ZeRO/FSDP 主要解决 参数、梯度和优化器状态的显存冗余，不直接消除所有显存压力。大语言模型训练中的激活显存、attention 显存和长上下文开销，还需要配合其他技术一起优化，比如activation checkpointing、FlashAttention、sequence parallel、张量并行和合理的 batch/sequence length设计。

一、为什么KV Cache需要优化？

大模型生成时，每生成一个token都要读取历史token的Key和Value。为了避免重复计算，推理系统会缓存这些KV，但这会带来很高的显存占用。

KV Cache占用和以下因素相关：

  • 层数
  • hidden size / head数 / head维度
  • batch大小
  • 上下文长度
  • 数据精度

可以用一个简化公式估算：

KV Cache显存 ≈ batch_size × seq_len × num_layers × 2 × hidden_size × bytes_per_element

其中 2 表示同时缓存Key和Value。实际工程中还会受到多查询注意力、分组查询注意力、block管理粒度和额外metadata影响。

上下文越长、并发越高，KV Cache越容易成为显存瓶颈。

三者分别解决什么问题？

  • 数据并行解决“数据太多、训练吞吐不够”的问题：不同 GPU 处理不同 batch，提高样本处理速度。
  • 张量并行解决“单层太宽”的问题：例如 attention 和 MLP 中的大矩阵乘法太大，需要拆到多卡上计算。
  • 流水线并行解决“模型太深”的问题：Transformer 层数很多时，可以把不同层分配到不同 GPU 上。

在实际大语言模型训练中，三者往往不是互斥关系，而是组合使用。例如一个训练集群可以在节点内使用张量并行，在节点间使用流水线并行和数据并行，从而同时解决显存、计算和吞吐问题。

上下文压缩为何必须进入训练，而不只是推理技巧？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

长任务超过窗口上限时，系统可把旧历史压成摘要，再继续执行。但摘要是有损状态：遗漏约束、文件路径或工具失败信息，会在后续步骤放大。只在推理时压缩、训练时始终给完整历史，会造成训练与执行分布不一致。

CompactionRL 把生成摘要和继续完成任务放进同一条训练轨迹，让最终任务奖励影响摘要策略；同时处理压缩造成的片段长度不均和跨片段信用分配。

不同任务的数据构造重点有哪些？

不同任务的共同要求是：训练样本必须体现推理时真实输入、真实约束和真实输出形态。例如：

  • 工具调用数据不能只包含自然语言回答，还应包含函数名、参数、调用时机和结果处理；
  • 法律辅助问答不能只给结论，还应包含依据、限制条件、审慎表达和风险提示。

实际工程中可以按以下流程构造：

明确目标能力 → 设计 chat template 和数据 schema → 收集真实任务样本 → 人工标注或模型辅助生成 → 质量审核与事实校验 → 去重清洗 → 安全与合规检查 → 格式校验 → 设置 loss mask → 划分训练集和验证集

不同场景下如何选择 PEFT 方法？

  • 默认业务微调：优先 LoRA；显存紧张时用 QLoRA。
  • 运行时额外计算预算紧：优先可合并的 LoRA，避免引入额外结构。
  • 多任务多版本管理：优先多个 LoRA adapter 或 Adapter，便于独立保存和切换。
  • 只做极轻量分类 / 抽取适配：可考虑 Prompt Tuning 或 P-Tuning，但要警惕表达能力不足。
  • 生成任务需要更强条件控制：可考虑 Prefix Tuning，但要评估前缀状态与上下文开销。

注：底座能力明显不足或领域差异很大，应考虑继续预训练、全量微调、采用检索增强或更换底座。 注：一般大多数 LLM 业务微调优先选择 LoRA / QLoRA，因为它们在效果、训练成本、生态支持和部署便利性之间最均衡。
