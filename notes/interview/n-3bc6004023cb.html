一个专业的提示词模板由哪几部分构成？为什么提示词中需要描述角色定义？

一个专业的提示词（Prompt）模板通常包含以下几部分：

  1. 角色定义（Role）→ 告诉模型“你是谁”（例如你是医生/律师/客服/算法工程师）。
  2. 任务目标（Task）→ 明确你要模型完成什么任务，比如“写摘要”、“做分类”、“写代码”。
  3. 上下文信息（Context）→ 提供必要背景，让模型理解问题场景。
  4. 输入数据（Input）→ 提供需要处理的具体内容，如文本、问题或数据片段。
  5. 输出格式要求（Output Format）→ 规定模型输出的格式或风格，比如表格、列表、JSON 或限制字数等。

因为大模型是通过模式学习的，角色定义能引导模型以更专业、更符合预期的语气和风格回答问题。

一个完整数字人产品链路通常包括哪些模块？

一个完整数字人链路可以分为离线生产和在线交互两类。

离线视频生产链路：

  1. 输入角色素材：参考图、人像视频、服装图、音频、脚本、目标动作。
  2. 预处理：人脸检测、裁剪、对齐、分割、姿态估计、音频降噪、说话人分离。
  3. 条件编码：ID embedding、pose map、DensePose、landmark、audio token、text embedding。
  4. 视频生成：U-Net/DiT/Video Diffusion/Flow 模型生成连续帧。
  5. 后处理：超分、脸部修复、插帧、色彩一致性、背景融合、音视频合成。
  6. 质检：唇形同步、身份一致性、闪烁、手部质量、内容安全。

实时交互链路：

  1. ASR 流式识别用户语音。
  2. LLM/Agent 生成响应。
  3. TTS 流式合成音频。
  4. 数字人 SDK 根据音频流驱动唇形、表情和动作。
  5. 前端渲染、播放和打断控制。

一个高质量提示通常包含哪些要素？

一个清晰提示通常包含六类要素：

  • 角色：模型应以什么身份回答，例如面试官、后端工程师、代码审查者、法律合规助理。
  • 任务：明确要完成什么动作，例如分类、抽取、总结、改写、推理、生成代码。
  • 背景：提供必要上下文，例如业务场景、输入字段含义、用户画像、文档来源。
  • 约束：说明不能做什么或必须满足什么，例如不得编造、只基于材料回答、不得输出敏感信息。
  • 输出格式：指定 JSON、表格、列表、步骤、固定字段或 Markdown 标题。
  • 评价标准：说明什么叫好答案，例如准确、完整、可引用、可执行、简洁、符合 schema。

例如：“你是企业知识库问答助手。请只基于给定上下文回答用户问题；如果上下文没有答案，回答不知道；输出包含 answer、citations、confidence 三个字段。”

上下文压缩保留什么信息？如何判断哪些内容可以丢弃？

面试官： 上下文压缩时保留什么信息？怎么判断哪些内容可以丢弃？

追问： 压缩任务交给小模型还是大模型？

回答：

上下文压缩应围绕“未来决策还依赖什么”来做，而不是围绕“哪些句子看起来重要”。建议保留以下几类信息：

  1. 当前目标与完成标准。 用户到底要什么，什么状态才算完成。
  2. 硬约束与授权。 时间、预算、格式、禁止项、权限范围、人工确认和安全规则。
  3. 任务状态。 已完成步骤、未完成步骤、阻塞原因、重试次数和下一步。
  4. 关键事实与实体。 明确确认的人、对象、数字、版本、路径、时间和业务状态。
  5. 决策及依据。 为什么选择某方案，哪些方案被排除，依据来自哪个证据或工具回执。
  6. 可恢复引用。 大型工具结果不必全文保留，但要保留 Artifact ID、查询条件、版本、摘要和关键片段。
  7. 用户稳定偏好。 只保留经用户确认、与后续任务相关且在隐私策略允许范围内的偏好。

通常可以压缩或丢弃的是：已被确定性结果取代的探索过程、重复日志、无新增信息的寒暄、已成功消费的大型中间输出，以及不影响后续行为的语言修辞。但不能简单删除所有“中间推理”。系统不需要保存模型私有 Chain-of-Thought，却需要保存可审计的决策摘要、证据和行动结果。

判断是否可丢弃，可以对每条信息做四个问题：后续步骤是否直接依赖它；删除后能否从外部 Artifact 可靠恢复；它是否属于安全或合规证据；它是否已被更新且旧值只需进入变更历史。压缩后应执行一致性校验，例如实体、数字、否定关系、未完成任务和权限条件是否仍然完整。

小模型还是大模型没有统一答案。结构化抽取、去重和日志归并可由规则或小模型完成；跨文档冲突、复杂计划和高风险事实压缩需要更强模型或双模型复核。选择标准应是压缩成本与下游错误成本，而不是模型价格本身。可以用事实保真率、约束召回率、未完成任务召回率、压缩率和最终任务成功率做评测。

优秀的上下文压缩不是写一段更短的摘要，而是构造一个可追溯、可更新、足以驱动下一步行动的最小任务状态。

上下文压缩（Context Compaction）操作后，模型信用分配难度加剧的原因

回答：

上下文压缩后信用分配更难，原因是原始轨迹中的 Token、动作、工具观察和奖励之间的时间对应关系被改变了。若把多轮历史压成一段摘要，策略梯度仍然需要知道哪些动作导致成功或失败，但摘要只保留语义结果，丢失了决策边界、错误尝试和工具返回的局部证据。

解决方法是把“模型可读上下文”和“训练用原始轨迹”分开：压缩后的摘要用于后续推理，原始消息、动作 Token、时间戳、工具观察和 mask 仍作为训练审计轨迹保存；在阶段边界写入 checkpoint 和阶段奖励；对摘要操作本身记录映射关系，必要时用层级 Credit Assignment 把终局奖励分配到阶段而不是伪造摘要 Token 的动作奖励。

压缩器还要经过实体、数字、否定、权限、未完成任务和证据引用保真评测。否则上下文变短了，训练的只是压缩错误。

上下文怎么做的？你是拆分的嘛？

回答：

上下文应该拆分，但底层模型最终看到的仍是一段 Token 序列。所谓拆分，是工程侧按来源、生命周期、权限和优先级管理信息，再由 Context Builder 为当前步骤组装最小充分上下文。

我会分成六个区：

  1. Policy： System 指令、权限、安全和输出契约，固定高优先级，不参与普通摘要。
  2. Task State： 当前目标、计划、步骤、变量、已完成事项和待审批项，结构化存储。
  3. Recent Context： 最近交互和当前步骤的原始工具结果。
  4. Compressed History： 已完成阶段的结构化摘要，保留事件和 artifact 引用。
  5. Retrieved Context： 按需召回的长期记忆、RAG 文档和代码片段，经过权限、时效、冲突与 Rerank。
  6. Tool Context： 当前候选工具的最小 schema；工具很多时渐进披露，而不是每轮发送全部定义。

每类设置独立 Token 预算，并为模型输出预留空间：

\[ B_{policy}+B_{state}+B_{recent}+B_{summary}+B_{retrieval}+B_{tools}+B_{output} \le B_{window} \]

多 Agent 场景还要做上下文隔离：子 Agent 只接收自己的任务、必要证据和产物契约，返回结构化结果与引用；Supervisor 不汇总全部内部对话。原始事件保存在外部存储，摘要丢失信息时可回读或重建。上下文工程的核心不是“切几段 Prompt”，而是让当前决策获得足够证据，同时避免无关历史、越权数据和重复工具信息。

不同模型压缩方法如何取舍？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐ (3/5)

不同压缩方法适合不同场景，不能只看压缩率，还要看精度、硬件支持和工程成本。

一、如果想快速落地，优先考虑量化

量化通常是性价比最高的第一选择。尤其是INT8、FP16/BF16等，在主流推理框架和硬件上支持较好；FP8主要依赖H100/H200等新一代GPU或其他支持FP8的硬件和框架，选型时需要确认具体后端能力。

适合场景： - 云端GPU推理 - CPU推理加速 - 大模型显存优化 - 端侧模型部署

二、如果模型明显冗余，可以考虑剪枝

剪枝适合参数冗余较大的模型，例如CNN、推荐模型或部分Transformer结构。

但要注意：非结构化剪枝不一定能在普通硬件上直接加速；即使稀疏率较高，实际收益也依赖稀疏格式、稀疏kernel、稀疏模式和硬件支持，例如NVIDIA的2:4结构化稀疏。结构化剪枝更容易带来真实推理收益。

三、如果要训练一个小模型，可以考虑蒸馏

蒸馏适合用大模型带小模型，尤其适合端侧部署、在线服务降本、BERT类模型压缩、大模型能力迁移等场景。

蒸馏通常需要训练数据和训练流程，工程成本比单纯量化更高。

四、如果是从零设计模型，可以考虑轻量化结构

如果业务一开始就明确要部署在手机、摄像头或嵌入式设备上，最好在模型设计阶段就考虑轻量化，而不是等模型训练完再压缩。

可以总结为：模型压缩不是单一技术，而是一组方法。量化最常用、剪枝适合去冗余、蒸馏适合大模型带小模型、轻量化结构适合从设计阶段降低复杂度。实际项目中经常组合使用，例如蒸馏 + 量化，或者剪枝 + 微调 + 量化。

不同版本的数据会一起参与处理，还是每次指定其中一个？

回答：

参与处理的版本由任务语义决定。单版本问答通常指定一个版本；版本对比显式指定基准版和目标版；跨版本演化分析可以选择多个版本，但必须保留时间顺序和各自身份。不能把所有版本放进同一个无差别检索范围后让模型自行猜测。

中途切换模型一定会有影响吗？具体可能有哪些影响？

回答：

不一定产生用户可见的错误。若在清晰步骤边界切换，完整状态可迁移，模型能力与协议兼容，任务可能正常继续；但不能承诺结果、成本和行为完全相同。

可能影响包括：上下文上限与 Tokenizer 不同导致预算变化；工具协议、Schema 支持和多模态格式不同；指令遵循、拒答、工具选择与规划策略改变；缓存无法复用导致延迟和费用变化；输出格式和语言风格变化。

连续生成中的隐藏状态或 KV Cache 通常不能直接跨不同模型复用，即使保留可见文本，也不代表延续完全相同的生成过程。若在有副作用工具执行中切换，风险还包括重复调用、迟到结果覆盖和动作状态不确定。

因此要区分可见状态兼容、执行状态一致与模型行为等价，分别验证。通过跨模型恢复集测试未完成计划、已调用工具、长上下文、取消与失败重试，量化成功率、重复副作用及延迟变化。

为什么 AIGC 时代仍然需要 3D 数字人？

AIGC 视频模型可以直接生成高保真人像视频，但 3D 数字人仍然非常重要，因为它提供了 2D 生成模型不容易稳定保证的能力：几何一致性、视角一致性、姿态可控、实时驱动、可编辑资产和工程可部署性。

在数字人系统中，3D 不是为了替代 2D 生成，而是作为一个强先验：

  • 几何先验：脸型、头部姿态、人体骨架、深度、法线、遮挡关系更稳定。
  • 运动先验：身体骨架、面部 BlendShape、手部关节可以被动作捕捉或音频驱动。
  • 渲染先验：相机、光照、材质、阴影可以被显式控制。
  • 资产先验：Mesh、贴图、Rig、骨骼动画可以进入 Unity、Unreal、WebGL、AR/VR 等实时引擎。
  • 生成约束：ControlNet、Adapter、视频扩散模型可以用深度图、法线图、UV、DensePose、SMPL 渲染图作为条件，减少身份漂移和肢体错误。

一句话总结：

2D 生成擅长真实感和内容多样性，3D 数字人擅长可控性、可解释性和跨视角一致性。AIGC 时代的主流工程路线通常是二者融合。

为什么 ArcFace 在人脸识别和 AIGC 身份保持中长期高频？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐⭐ (5/5)

ArcFace 把身份判别转化为超球面上的角度 margin 学习。其典型损失为：

L=-\log\frac{e^{s\cos(\theta_y+m)}}{e^{s\cos(\theta_y+m)}+\sum_{j\ne y}e^{s\cos\theta_j}}

$s$ 是缩放系数，$m$ 是角度 margin，$\theta_y$ 是样本 embedding 与真实类别权重的夹角。它的价值在于几何解释直接、类内更紧凑、类间更分离，推理时可以用归一化 embedding 做余弦比较。InsightFace 生态把这类身份表示沉淀为可复用的检测、识别和评估组件，因此在门禁、检索、数字人和肖像一致性评估中都很常见。

它不是“越高相似度越好”的万能指标：姿态、年龄、遮挡、肤色和生成风格都会影响 embedding，阈值和身份损失必须结合业务验证集、质量门控与人工偏好一起判断。

为什么 Sonic 强调 Global Audio Perception？

传统 audio-driven talking head 往往用局部音频窗口驱动当前帧：

\[ x_t = G(I_{\text{ref}}, A_{t-k:t+k}) \]

这对唇形同步足够，但对表情、头动、情绪和长句节奏不够。人说话时，点头、停顿、强调、情绪变化往往依赖更长时间范围的语音结构。

Global Audio Perception 的直觉是让模型看到更长的音频上下文：

\[ x_t = G(I_{\text{ref}}, A_{1:T}, t) \]

这样模型不仅知道当前音素，还知道当前处在一句话的开头、强调处、停顿处还是收尾处。

收益：

  • 头动和表情更自然。
  • 音频情绪与面部表达更一致。
  • 长视频中动作节奏不容易碎片化。

为什么max pooling 要更常用？什么场景下 average pooling 比 max pooling 更合适？

  • 作用：对输入的特征图进行压缩，一方面使特征图变小，简化网络计算复杂度；一方面进行特征压缩，提取主要特征。
  • 通常来讲，max-pooling的效果更好，虽然max-pooling和average-pooling都对数据做了下采样，但是max-pooling感觉更像是做了特征选择，选出了分类辨识度更好的特征，提供了非线性。 pooling的主要作用一方面是去掉冗余信息，一方面要保留feature map的特征信息，在分类问题中，我们需要知道的是这张图像有什么object，而不大关心这个object位置在哪，在这种情况下显然max pooling比average pooling更合适。在网络比较深的地方，特征已经稀疏了，从一块区域里选出最大的，比起这片区域的平均值来，更能把稀疏的特征传递下去。
  • average-pooling更强调对整体特征信息进行一层下采样，在减少参数维度的贡献上更大一点，更多的体现在信息的完整传递这个维度上，在一个很大很有代表性的模型中，比如说DenseNet中的模块之间的连接大多采用average-pooling，在减少维度的同时，更有利信息传递到下一个模块进行特征提取。
  • average-pooling在全局平均池化操作中应用也比较广，在ResNet和Inception结构中最后一层都使用了平均池化。有的时候在模型接近分类器的末端使用全局平均池化还可以代替Flatten操作，使输入数据变成一维向量。

为什么不直接把完整文档交给大模型处理，而要额外引入RAG？

回答：

为什么不能让大模型直接输出电机控制量？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐⭐ (4/5)

大模型通常不适合直接输出电机级控制量，原因有四点：

  1. 实时性不足：电机控制往往需要高频闭环，大模型推理延迟难以稳定满足。
  2. 精度不足：电机控制需要连续、平滑、精确的数值输出，大模型更擅长离散 token 和高层语义。
  3. 安全风险高：错误力矩、速度或方向可能直接造成碰撞和设备损坏。

更合理的架构是：

LLM/MLLM：任务理解与规划
VLA/策略模型：生成动作目标或轨迹片段
MPC/控制器：满足动力学约束并实时执行
安全模块：拦截危险动作并触发回退

因此，大模型在具身系统里更像“认知层”或“规划层”，而不是直接替代传统控制器。

为什么两个状态可以一遍遍历完成

回答：

因为两个新状态只依赖上一位置的两个旧状态，不依赖更早的完整历史。循环不变量是：处理完下标 \(i\) 后，max_end 和 min_end 分别准确描述以 \(i\) 结尾的最大、最小乘积，best 描述截至 \(i\) 的全局最大乘积。

初始化满足不变量；每轮枚举“重新开始”和“延长旧子数组”两种情况，保持不变量；循环结束后，best 就是所有可能结束位置中的最大值。每个位置进行常数次数的乘法与比较，因此只需要一遍遍历。

这里的常规 \(O(n)\) 时间分析把整数乘法当作常数操作。如果不限制整数位数，Python 大整数的乘法和存储开销会随结果位长增长，严格的位复杂度不能直接写成固定常数。

为什么传统 Softmax 不足以解决人脸识别？

难度评分：⭐⭐ (2/5) | 考察频率：⭐⭐⭐⭐⭐ (5/5)

为什么使用当前的切块策略？是否通过 Recall@K、MRR 等指标做过实验？

回答：

回答时先给决策依据，再给实验，而不是只报“Chunk=500、Overlap=50”。例如：文档以规范条款和会议议题为主要知识单元，因此先按标题层级和段落切分，超长段落再递归分块；召回使用子块，注入上下文时补充父段落，以兼顾定位精度和语义完整性。

Recall@K 衡量至少一个相关块是否进入前 K 个候选：

\[ \mathrm{Recall@K}=\frac{1}{|Q|}\sum_{q\in Q}\mathbf{1}\{R_q\cap TopK_q\neq\varnothing\} \]

MRR 更关注第一个相关结果出现的位置：

\[ \mathrm{MRR}=\frac{1}{|Q|}\sum_{q\in Q}\frac{1}{\operatorname{rank}_q} \]

实验需要固定 Query、相关性标注、Embedding、召回 K 和 Reranker，只改变切块变量，避免把多项优化的收益混在一起。除 Recall@K、MRR 外，还应看 nDCG、重复率、无答案 Query 的误召回、上下文 token、端到端引用支持率和延迟。

如果项目没有严格实验，不能编造曲线。可以坦诚当时依据少量样本和线上反馈选择，并说明现在会补建怎样的标注集和消融实验。严谨性来自可复现实验设计，而不来自漂亮但无法解释的数字。

为什么协方差矩阵半正定？

协方差矩阵 \(\Sigma = \mathbb{E}[(X-\mu)(X-\mu)^T]\)，对任意 \(v\)：

\[ v^T\Sigma v = \mathbb{E}[v^T(X-\mu)(X-\mu)^Tv] = \mathbb{E}[(v^T(X-\mu))^2] \ge 0 \]

所以协方差矩阵一定半正定。

为什么同源模型之间可以迁移

底层假设是外观与运动可以部分解耦：图像主干决定每帧大致长什么样，Motion Module 学习这些特征如何跨帧变化。这里的“部分”很重要，运动和外观并非真正独立。训练视频中的主体、场景、镜头运动会共同影响时间特征，迁移后仍可能出现身份漂移或动作不适配。

迁移前要检查三个条件

  • 结构是否兼容：基础模型版本、U-Net 层级、通道数和插入位置必须匹配。
  • 个性化改动是否过重：大幅合并权重或深度微调可能改变中间特征，导致运动模块失效或破坏画质。
  • 目标运动是否超出训练分布：通用短视频运动先验不等于复杂动作、长镜头和强遮挡都能稳定迁移。

为什么堆叠很多层以后，模型能够形成复杂能力？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐ (3/5)

每个 Block 都执行两类操作：跨位置通信与逐位置非线性变换。多层堆叠后，一个 Token 可以反复读取、变换并重新分发信息，逐步形成更抽象的上下文表示。

可以把层级计算理解为：

  • 较低层更容易保留词形、局部搭配和位置等基础信号；
  • 中间层组合句法、实体关系和上下文模式；
  • 较高层形成更贴近当前预测目标的抽象特征。

这是常见的经验性概括，不是每一层都有固定职责。模型能力来自架构、参数规模、训练数据和优化目标共同作用。堆叠层数只增加容量；如果数据不足、训练不稳定或目标不合适，并不会自动获得推理和知识能力。

另一个关键点是残差流。每层不是把上一层“清空重写”，而是在共享表示上叠加更新。因此信息可以跨很多层保留，也可以由不同子层逐步修改。

为什么大模型以 Token，而不是字符或完整单词作为基本处理单位？

回答：

完整单词词表会遭遇开放词汇问题：新词、拼写变化、复合词、代码标识符和多语言使词表无限膨胀，稀有词训练样本又很少。纯字符词表很小且不存在未登录词，但序列显著变长，注意力和解码成本上升，单个位置承载的语义较弱。

子词 Token 在词表大小、序列长度和泛化之间折中。高频词或词片段可以用较少 Token 表示，稀有词能退化成更小子词或字节，因此词表有限且几乎可覆盖任意输入。对中文，一个 Token 可能对应单字、词片段或 UTF-8 字节组合；对代码，常见关键字和空白模式也可能进入词表。

Tokenizer 仍有代价：不同语言的压缩率不均衡；文本中的微小变化可能改变切分；数字、字符操作和跨 Token 边界推理并不自然。字节级模型可以消除传统 tokenizer 的一部分偏置，但序列更长，需要更强的架构和训练权衡。

因此 Token 不是理论上唯一选择，而是当前 Transformer 计算预算下的工程折中。它同时影响上下文长度、推理费用、吞吐和多语言公平性。

为什么接入一种输入条件，不等于模型真正具备对应的任务能力？

难度评分：⭐⭐⭐⭐ (4/5) | 考察频率：⭐⭐⭐ (3/5)

  • 条件表示：编码结果必须保留任务需要的信息。参考图编码器如果只保留“人”或“狗”这类高层语义，却丢掉身份细节，模型最多生成语义相似的主体。

为什么文本提示（prompt）的构造会显著影响零样本精度？

难度评分：⭐⭐⭐ (3/5) | 考察频率：⭐⭐⭐ (3/5)

CLIP 的训练语料是完整的句子，推理时如果只给孤立的类别名，就和训练分布对不上，零样本精度因此对 prompt 写法很敏感，具体体现在三个方面：

  1. 裸标签和训练分布不匹配。 训练时和图像配对的文本大多是完整句子（"a photo of a golden retriever on the grass"），只有一个单词的情况很少。直接拿 "dog" 当类别文本，落在文本编码器很少见过的分布上，相似度估计不准。套上 "A photo of a {label}." 把标签包成句子，论文报告这一个模板就让 ImageNet 准确率提高 1.3%[1]。

  2. 一词多义要靠 prompt 消歧。 ImageNet 里的 "crane" 既有鹤也有起重机，Oxford-IIIT Pets 里的 "boxer" 指犬种，文本编码器却可能理解成拳击手。给模板补上领域上下文，如 "A photo of a {label}, a type of pet."，能把语义锚定到正确含义，CLIP 为不同数据集准备专用模板，原因也在这里[1]。

  3. prompt 集成进一步降低方差。 单个模板有偶然性，CLIP 为同一类别准备多个模板（"a photo of a {label}."、"a bad photo of a {label}."、"a cropped photo of the {label}." 等），分别编码后在嵌入空间取平均，再归一化，作为这一类的代表向量。ImageNet 上用了 80 个模板，比单个默认模板再提高 3.5%，与 prompt 工程合计提高近 5%[1]。论文用百分号表示这些提升，图 4 的说明则把 36 个数据集上的平均提升写作约 5 个点（points）。平均后的文本向量可以缓存，摊到大量预测上，推理成本和单个分类器相同。

既然类别向量是现场合成的分类器权重，写 prompt 也就是在设计分类器，写得越接近训练分布、语义越明确，类别向量的质量越高。后来 CoOp、CoCoOp 把人工模板换成可学习的连续 prompt 向量[10,11]，用少量样本学出提示，延续了这个思路。

面试速答：CLIP 训练时配对的多是完整句子，裸类别名和训练分布对不上，套上 "A photo of a {label}." 在 ImageNet 上就提高 1.3%。模板还能补领域上下文、消除一词多义；80 个模板做集成再提高 3.5%，合计近 5%。CoOp 等方法进一步把模板换成可学习向量。

为什么文档更新这里考虑使用 MQ，而不是直接在定时任务中处理？

回答：

定时任务适合发现变化，MQ 适合承接独立、耗时、可重试的异步工作。文档解析、Embedding 和索引写入耗时波动大，全部塞进扫描任务会使一次慢文档拖住后续扫描，部署重启也容易丢失进度。

代价是最终一致性、重复投递、乱序、运维和问题定位复杂度。低流量、任务很短、允许简单重跑的场景，数据库任务表配合定时 worker 就足够。选 MQ 应来自吞吐、可靠性与故障隔离需求，而不是架构层数越多越好。

定义分层图状态：

\[ state=(v,c,last) \]

其中 v 是当前点，c 是已经使用的魔法边数量，0 <= c <= k，last 为 1 表示上一条边是魔法边，为 0 表示不是。原图中的一个点会被复制成 2(k+1) 个状态点。

状态转移如下：

  • 普通边 u -> v、耗时 w：

$$ (u,c,last)\rightarrow(v,c,0),\quad cost=w $$

  • 魔法边 u -> v：只有 c < k 且 last = 0 时允许使用：

$$ (u,c,0)\rightarrow(v,c+1,1),\quad cost=0 $$

起点为 (s,0,0)，终点可以是 (t,c,0) 或 (t,c,1) 的任意一层，因此答案是所有 c 和 last 状态距离的最小值。自环和重边不需要特殊处理：自环按普通转移或魔法转移处理，重边逐条保留即可；如果题目把边视为无向边，则输入时把每条边加入两个方向。

为什么有符号INT数据类型可表示的负数比正数多1？

一句话总结

在有符号的整型数据类型中，用'0 00...0' 表示正负0； '1 00...0' 表示最小负数。

原理解释

整型数据类型通常使用有符号表示法，其中最高有效位用作符号位。以INT8为例，符号位占据了第一位，而剩下的7位用于表示数值。因此，正数范围是从00 000000（二进制）到01111111（二进制），转换为十进制即为0到127。负数范围是从10000000（二进制）到11111111（二进制），转换为十进制即为-128到-1。这种表示方式称为二进制补码。

二进制补码

正数：

  • 1 \(\rightarrow\) '0 0000001'

  • '0 0000001' \(\rightarrow\) 判断为正数直接转化为1。

负数：

  • -127 \(\rightarrow\) 127原码， '0 1111111' \(\rightarrow\) 取反，'1 0000000' \(\rightarrow\) +1， '1 0000001'

  • '1 0000001' \(\rightarrow\) 判断为负数 \(\rightarrow\)取反， '0 1111110' \(\rightarrow\) +1，‘0 1111111' \(\rightarrow\) 结合判断得出值为-127

为什么贪心是正确的

当一个箱子经过面前且满足 a[i] <= keys 时，立即打开它不会损害后续可行性：

  1. 这次操作只增加钥匙，不消耗会影响其他箱子的资源；
  2. 打开后增加的钥匙可能让本轮后续箱子立刻变得可开；
  3. 延迟打开不会带来更大的收益，反而可能错过同一轮的连锁增长。

因此，一轮扫描中遇到能开的箱子就立即打开，遇到暂时打不开的箱子就跳过并继续扫描。当传送带尚未走到端点时提前反转，相当于放弃当前方向后续所有可能打开的箱子；继续扫到端点不增加反转次数，钥匙数还只可能增加，所以提前反转不可能更优。这就证明了每轮完整地从一端扫到另一端存在最优解。

如果某一整轮没有打开任何箱子，钥匙数在轮前轮后完全相同。下一轮虽然顺序相反，但每个剩余箱子的需求都仍然大于当前钥匙数，因此也不可能打开任何箱子，必须判定无解。

二叉搜索树的前驱后继怎么找（迭代实现）？

下面给出二叉树的寻找前驱的迭代实现。

class TreeNode:
    def __init__(self, val=0, parent=None, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right
        self.parent = parent

def find_preprocessor(root, val):
    cur = self.root
    # 找到val的位置
    while cur and cur.val != val:
        if val < cur.val:
            cur = cur.left
        else:
            cur = cur.right
    if not cur:
        return None
    if cur.left:
        # 如果存在左子树，那么前驱就是左子树的最右节点
        cur = cur.left
        while cur.right:
            cur = cur.right
        return cur
    # 否则一直往上走，直到 cur != cur.parent.left
    pa = cur.parent
    while pa and pa.left != cur:
        cur = pa
        pa = cur.parent
    return pa

二叉搜索树的怎么删除一个节点？

二叉搜索树的删除操作没有那么简单，总共可以分为以下几种情况： 1. 删除的节点是叶子节点，直接删除即可。 2. 删除的节点只有一个子节点，那么直接将子节点替换到删除节点的位置即可。 3. 删除的节点有两个子节点，那么需要找到这个节点的右子树中的最小节点，将这个节点的值替换到删除节点的位置，然后删除这个最小节点即可。

    # 移植子树 v 到 u 的位置，并且调整关系
    if u.parent is None:
        root = v
    elif u == u.parent.left: 
        u.parent.left = v
    else:
        u.parent.right = v
    if v:
        v.parent = u.parent

        else:
            cur = cur.right
    if not cur:
        return None
    if cur.left is None:
        tranplant(root, cur, cur.right)
    elif cur.right is None:
        tranplant(root, cur, cur.left)
    else:
        y = cur.right
        while y.left: 
            y = y.left
        if y.parent != cur:
            tranplant(root, y, y.right)
            y.right = cur.right
            y.right.parent = y
        tranplant(root, cur, y)
        y.left = cur.left
        y.left.parent = y

交流环节：如何解决多轮对话的冷启动 和 业务约束遵循问题？

回答：

冷启动包含两层：新系统缺少高质量对话轨迹，新用户/新场景缺少状态。训练冷启动可以从业务规则、历史人工服务日志和专家流程构造 SFT 数据，再用多样化用户模拟器生成可验证轨迹；先训练基本意图、槽位、工具和终止能力，再进入 on-policy RL。数据必须脱敏、去重并按场景切分；不能把客服历史回复直接当成全部正确答案。上线前先做离线回放和 shadow evaluation，小流量灰度后再用真实失败案例迭代。

什么叫“快到上限了”？对话是怎么逐步叠加的？

回答：

“快到上限”不是简单看对话轮数，而是预测下一次请求会不会超过可用上下文预算。一次模型调用的 Token 预算至少包含：System 指令、工具 schema、历史消息、长期记忆/RAG 片段、当前用户输入，以及必须为模型输出预留的 Token。

可以写成：

\[ B_{\mathrm{used}}=B_{\mathrm{system}}+B_{\mathrm{tools}}+ B_{\mathrm{history}}+B_{\mathrm{retrieval}}+B_{\mathrm{query}} \]

只有满足 \(B_{\mathrm{used}}+B_{\mathrm{reserved\ output}}<B_{\mathrm{window}}\)，请求才是安全的。工程上还要保留安全余量，避免 tokenizer 估算误差、工具返回突增或模型自动推理预算占满窗口。

在常见的无状态 Chat API 中，对话确实是不断追加消息，并在下一轮把所需历史重新发送给模型。模型不会因为“上一轮见过”就天然记住；服务端会话、Prompt caching 或 KV Cache 可以降低传输/计算成本，但不能改变模型本次只能基于可见上下文决策的事实。

增长最快的往往不是用户对话，而是工具 schema、代码文件、搜索结果和日志。因此系统应在调用工具前估算潜在返回大小，限制日志行数、分页读取大文件，并把完整产物存外部对象存储，只向模型提供摘要和可按需展开的引用。

所以“快到上限”的正确实现是动态 Token Budgeter，而不是写死“第 10 轮总结”或固定使用窗口的 70%。不同轮次的信息量差异很大，轮数只能作为辅助信号。

什么是 3D-aware GAN？

3D-aware GAN 是指在生成图像时显式或隐式引入三维结构，使生成结果在视角变化下保持几何一致。

普通 2D GAN 只学习图像分布：

\[ z \rightarrow I \]

3D-aware GAN 则试图学习：

\[ z, c_{\text{camera}} \rightarrow I \]

同时内部有某种 3D 表示，例如 voxel、feature volume、implicit field、NeRF、tri-plane 或 mesh-aware feature。

它的目标不是只生成一张好看人脸，而是生成一个可以从不同相机视角渲染、身份和几何相对一致的人脸或人体。

什么是 HyDE？

HyDE（Hypothetical Document Embeddings，假设文档嵌入） 是一种检索增强方法。它先让模型根据用户问题生成一个“假设答案”或“假设相关文档”，再对这个假设文档生成嵌入向量，用该该向量去检索真实文档。

解决的问题是：用户 query 往往很短、口语化或缺少领域词，而假设答案可能更接近知识库中真实文档的表达方式。

风险是：假设答案偏离用户意图，会导致检索方向错误。为降低风险，可以结合原始 query 与 HyDE query 多路召回，并通过重排序和评估集验证效果。

什么是 Lost in the Middle？长上下文中的重要信息为什么容易被模型忽略？

回答：

Lost in the Middle 指模型处理长上下文时，对开头和结尾的信息利用往往优于中间信息，相关证据放在中部时任务性能下降。这不是“中间内容一定看不见”，而是一种位置相关的检索和利用偏差，强弱取决于模型、训练长度、任务和提示结构。

原因包括训练数据中关键信息位置分布不均、位置编码的外推与偏置、注意力竞争、长上下文中大量干扰项稀释相关证据，以及生成端更接近尾部指令。即使模型支持很大的最大窗口，也不代表能在所有位置等价地找出并正确组合证据。

缓解方法包括先检索/Rerank 后放入少量高相关证据；将任务、约束和关键证据放在清晰分区；对长文建立目录、摘要和结构化状态；对多个证据进行分段分析后再合并；必要时重复极关键约束，但避免制造冲突。不能只把证据全部放在开头，因为多轮任务的相关性会变化。

评估应把同一证据随机放在不同位置和不同干扰长度下，观察检索准确率与最终任务成功率。长上下文能力必须看“有效上下文”，而不只是标称窗口长度。

什么是 Plan-and-Solve？

Plan-and-Solve 要求模型先制定计划，再按计划执行任务。它适合多步骤推理、报告生成、代码修改、调试分析等任务。Plan-and-Solve 强调先明确任务分解和依赖关系，避免模型在没有整体规划时直接生成结论。

  4. 输出最终答案或结果；

什么是 token；如何节省 token

回答：

Token 是分词器将文本或其他模态输入编码后的离散单元，对应词表中的 ID。它可能是一个字、一个词的一部分、标点或若干字节，不能固定理解为一个汉字或一个单词。相同文本使用不同分词器，token 数量可能不同；图片和音频的计数方式则取决于具体模型与服务接口。

回答“节省 token”前先区分目标：减少上下文占用、降低费用、缩短首 token 延迟，还是减少完整响应耗时。它们相关但不完全等价。前缀缓存可能减少重复预填充计算或缓存部分计费，却不会自动扩大上下文窗口，也不等于输入在逻辑上不存在。

输入侧可以去除重复提示与无关历史，保留用户目标、约束、关键事实和未完成操作；长历史采用结构化摘要与按需记忆检索，工具结果只返回必要字段，对长日志分页或保存为可读取的产物。RAG 中先重排、去重，再按证据完整性装配上下文，保留出处位置和例外条件，不能只按分数截断到预算就忽略答案所需的关键证据。

输出侧明确所需格式与详略，给出合理的输出上限，简单分类和字段抽取避免生成冗长解释。但设置过低的上限可能截断 JSON 或推理结果，造成重试后反而更贵。调用链上减少无效循环、合并可以确定性处理的步骤，往往比压缩几个提示词更有效。

验证时用实际 tokenizer 或服务返回的用量统计，同时记录输入、输出、缓存命中、重试次数、任务正确率和端到端耗时。以相同任务质量为前提比较优化效果；如果删掉约束后 token 变少但答案错误，就不是有效优化。

什么是AutoEncoding自编码模型?

自编码模型（AutoEncoding Model，简称AE模型）是一种基于无监督学习范式的自然语言处理（NLP）模型。其核心思想在于通过编码器（Encoder）将输入数据压缩成一个低维的隐含表示（Latent Representation），随后再通过解码器（Decoder）从该隐含表示中重构出原始输入数据。这一过程不仅有助于数据的降维和特征提取，还能在一定程度上捕捉到输入数据中的内在结构和规律。

在AE模型的众多变体中，BERT（Bidirectional Encoder Representations from Transformers）无疑是最为知名且影响力深远的一个实例。BERT模型通过采用双向Transformer编码器，能够同时考虑输入文本的左右两侧上下文信息，从而生成更为丰富和精准的上下文表示。这些上下文表示在自然语言理解（NLU）任务中表现出色，例如文本分类、命名实体识别、情感分析等，显著提升了各项任务的性能指标。

尽管AE模型在文本表示学习方面具有显著优势，但其直接应用于文本生成任务时，相较于自回归模型（AR模型）而言，存在一定的局限性。AE模型的重构过程更侧重于保留输入数据的整体结构和语义信息，而非逐词生成新的文本序列。因此，在需要逐词预测和生成连续文本的应用场景中，AR模型通常更为直接和有效。

什么是AutoRegressive自回归模型?

AutoRegressive自回归模型（简称AR模型）是一种序列生成模型，在自然语言处理（NLP）领域具有广泛的应用。该模型的核心机制在于，它通过递归地预测序列中的下一个元素，从而构建出完整的序列结构。以GPT（Generative Pre-trained Transformer）模型为代表，AR模型在长文本生成任务中取得了显著成就，特别是在自然语言生成（NLG）领域，如文本摘要、机器翻译以及开放式问答等场景。

AR模型的核心特性在于其采用的单向注意力机制。这种机制使得模型在处理序列数据时，能够有效地捕捉到历史信息对当前预测的影响。然而，这也导致了模型在处理长距离依赖和上下文信息时存在一定的局限性。

通过编写 dockerfile，可以将应用程序、环境和依赖项打包成一个独立的容器镜像，使其可以在不同的环境和平台上运行，实现应用程序的可移植性和可扩展性。

什么是IndexShare？

IndexShare在DSA的基础上进一步优化索引器。

  • 相邻的若干稀疏注意力层共享同一份稀疏索引（top-k 位置集合），避免每层重复构建索引。
  • 每层的 Q/K/V、gather 出来的 KV、以及注意力权重，全部仍各自计算。

(1) 共享规则：每 \(g\) 层一组，组内只算一次索引

\[ \mathcal{S}^{(l)}_t\equiv\mathcal{S}^{(l_0)}_t,\quad l\in[l_0,\,l_0+g) \]

(2) 等价的掩码写法：

\[ M^{(g)}_{t,s}=\mathbf{1}_{s\in\mathcal{S}^{(l_0)}_t},\qquad o^{(l)}_t=\mathrm{softmax}\left(\frac{q^{(l)}_t k^{(l)\top}_s}{\sqrt{d_h}}+\log M^{(g)}_{t,s}\right)v^{(l)}_s \]
