认证、授权与对象级访问控制

认证确定调用者是谁，授权确定该身份可以对哪个资源执行什么操作。登录成功只完成身份检查，读取订单、修改文件或管理租户时仍需逐次校验对象与操作范围。

服务端不应信任客户端传入的用户 ID、角色或“管理员”字段。角色控制适合统一职责，属性或资源关系判断适合细粒度约束；实际系统常组合使用。测试越权时要覆盖水平越权、角色提升、租户边界和资源状态变化，而不只验证未登录请求是否返回错误。

参考资料：bregman-arie/devops-exercises 原文。

Session、Token 与 JWT 的撤销边界

Session 通常由服务端保存状态，客户端持有会话标识；Token 则以凭证表达访问资格，JWT 是一种可承载声明并签名的格式。JWT 的签名通常用于验证完整性和签发者，不会自动加密载荷，也不会自动实现退出登录后的立即撤销。

验证凭证时应检查预期算法、签发者、受众、过期时间和业务上下文。是否使用服务端会话、短期访问令牌、刷新令牌或撤销表，要根据即时失效、规模、跨服务和泄露影响选择。把 token 放在任何位置都不能替代传输保护、权限校验和日志脱敏。

参考资料：bregman-arie/devops-exercises 原文。

密码哈希、盐与慢速验证

密码验证通常应保存专门设计的密码哈希结果，而不是可逆加密的明文副本。独立随机盐使相同密码产生不同结果，削弱预计算表和跨用户批量比较的效果；盐不是用来保密的主密钥。

通用快速哈希适合完整性等用途，却不适合单独承担密码存储，因为攻击者可以高吞吐枚举。密码哈希方案要有可升级的参数与版本，并结合限速、泄露检测和多因素认证。若使用额外 pepper，应与数据库分开管理，其轮换和恢复也需要明确方案。

参考资料：bregman-arie/devops-exercises 原文；OWASP：密码存储。

对称加密、非对称加密、签名与摘要

对称加密用共享密钥保护内容机密性，非对称机制使用公私钥关系支持不同任务；数字签名用来验证来源与内容完整性，摘要将内容映射为固定长度表示。加密、签名和哈希解决的问题不同，不能把“算了 MD5”称为加密传输。

密钥交换、身份认证、完整性与重放保护需要组合设计。算法正确也不能弥补密钥泄露、随机数不足或错误的使用模式。实际业务应使用经过审查的协议和库，明确密钥生命周期，不自行拼接未经论证的密码协议。

参考资料：bregman-arie/devops-exercises 原文。

SQL 注入与参数化查询

SQL 注入发生在不可信数据被解释成查询结构时。参数化查询把 SQL 结构和参数值分开，使普通参数不被当成可执行语法；简单删除引号或拼接转义规则容易遗漏编码和语法边界。

表名、列名和排序方向等结构元素通常不能作为普通值参数绑定，应从明确允许的集合映射。还要控制数据库账号权限、异常信息和输入业务约束。参数化是核心防线之一，但不能替代授权，也不会自动阻止合法语法下的越权查询。

参考资料：bregman-arie/devops-exercises 原文；OWASP：SQL 注入防护。

XSS、输出编码与内容安全策略

XSS 使攻击者控制的内容在受信任页面的脚本或其他可执行上下文中生效。防护要匹配输出位置：HTML 文本、属性、URL 和 JavaScript 上下文的编码规则不同。避免把不可信文本直接交给危险 DOM 接口，比维护关键词黑名单更可靠。

确实允许富文本时，需要使用适合的清洗策略；自动转义框架也可能被显式绕过或不安全插件破坏。CSP 可降低部分攻击影响，但不能代替正确的数据流与输出处理。仅设置 HttpOnly 能降低部分 cookie 读取风险，并不阻止恶意脚本以用户身份发起操作。

参考资料：bregman-arie/devops-exercises 原文；OWASP：XSS 防护。

CSRF、Cookie 与跨站请求

CSRF 利用浏览器自动携带凭证的行为，诱导已登录用户向目标站点发起非预期请求。它与 XSS 的注入位置和信任边界不同，因此防护不能简单互换。

有副作用操作应使用适当方法，并结合 CSRF token、来源校验和合适的 Cookie SameSite 设置。SameSite 的适用行为依赖请求上下文，不能视作全部业务的唯一防线；CORS 主要约束脚本跨源读取及相关行为，也不等于通用 CSRF 防护。设计时应明确凭证如何携带及攻击者能构造什么请求。

参考资料：bregman-arie/devops-exercises 原文。

TLS、证书校验与传输保护边界

TLS 在连接中组合密钥协商、身份验证和受保护记录传输。证书链与主机名校验用于确认连接到预期身份，不能为“解决连接失败”而关闭证书验证。HTTPS 也只保护相应传输链路，应用端点和代理后的内部链路仍有各自边界。

TLS 不会判断业务请求是否被授权，也不保证浏览器展示的内容一定可信；恶意网站也能取得其域名的有效证书。排障时应区分信任链、域名、时间、协议和代理配置，不把全部错误都归为“证书过期”。

参考资料：bregman-arie/devops-exercises 原文。

最小权限、密钥与依赖供应链

最小权限让账号、进程和服务仅具备当前任务需要的能力，并限制使用范围与期限。密钥、数据库凭证和云权限不应随意写入代码、镜像层或日志；轮换、撤销和泄露后的影响评估必须可执行。

依赖与构建链也属于信任边界。应记录来源与版本，关注构建产物是否可追溯、依赖是否得到验证，以及流水线凭证能做什么。扫描工具只能发现其规则和数据覆盖的风险，不能把“扫描通过”当成系统没有漏洞的证明。

参考资料：bregman-arie/devops-exercises 原文。
