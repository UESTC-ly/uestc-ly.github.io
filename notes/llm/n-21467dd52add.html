一、学习目标

完成本课后，应能够：

  1. 解释什么是上下文窗口，以及它为什么通常用 Token 数量表示；
  2. 区分上下文窗口、模型参数中的知识和应用层记忆；
  3. 估算输入与输出占用的 Token 预算；
  4. 说明 Transformer 为什么必须加入位置信息；
  5. 理解绝对位置编码、相对位置编码、RoPE 和 ALiBi 的基本思想；
  6. 区分位置编码、Attention Mask 和 KV Cache；
  7. 在长文档问答、RAG 和多轮对话中设计合理的上下文管理策略。

二、什么是上下文窗口

上下文窗口（Context Window）是模型在一次推理过程中能够直接处理的 Token 范围。

它通常包含：

  • System Prompt；
  • 用户输入；
  • 历史对话；
  • Few-shot 示例；
  • RAG 检索结果；
  • 工具调用及其返回内容；
  • 当前正在生成的输出。

可以把上下文窗口理解为模型本次回答时的“工作台”。放在工作台上的内容，模型才能在当前计算中直接使用。

一个简化的 Token 预算约束是：

\[ N_{\text{system}}+N_{\text{history}}+N_{\text{retrieval}}+N_{\text{user}}+N_{\text{output}} \leq N_{\text{context}} \]

也可以简写为：

\[ N_{\text{input}}+N_{\text{output}}\leq N_{\text{context}} \]

其中：

  • \(N_{\text{input}}\)：本次请求中所有输入 Token 的数量；
  • \(N_{\text{output}}\)：模型生成内容所占的 Token 数量；
  • \(N_{\text{context}}\)：模型支持的上下文窗口上限。

不同模型和 API 对输入、输出上限的定义可能不同。有些平台还会为输出预留空间，因此实际开发时应以具体模型文档和 API 返回值为准。

示例

假设某模型的上下文窗口是 8,192 Token，本次请求中：

  • System Prompt：500 Token；
  • 历史对话：2,000 Token；
  • 检索资料：3,000 Token；
  • 当前问题：200 Token。

那么输入已经占用：

\[ 500+2000+3000+200=5700 \]

理论上剩余空间约为：

\[ 8192-5700=2492 \]

但实际应用通常还要保留安全余量，不能把预算刚好用满。

三、上下文窗口不等于模型的全部知识

需要区分三个概念。

1. 模型参数中的知识

模型在训练过程中把大量统计规律编码进参数。它不等于一个可以逐条查询的知识库，也不会因为一次普通对话就自动永久修改参数。

2. 当前上下文

当前请求中发送给模型的文本和其他信息。模型可以在本次推理中使用它们，但这些内容不会天然成为永久记忆。

3. 应用层记忆

应用把历史信息保存到数据库、文件或向量库，在未来请求中按需取回并重新放入上下文。这是一种外部系统能力，不是模型自动拥有的无限记忆。

三者的关系可以表示为：

模型参数：训练阶段形成的长期统计知识
当前上下文：本次推理可直接读取的工作区
应用记忆：由外部系统保存，并在需要时重新注入上下文

因此，聊天应用表现出“记得以前的内容”，通常是因为应用重新发送了历史消息或检索到了相关记忆。

四、上下文过长会发生什么

当输入与预期输出超过模型或 API 的限制时，常见结果包括：

  1. API 直接返回超限错误；
  2. 应用从开头或结尾截断部分内容；
  3. 系统压缩或总结较早的消息；
  4. 为输入保留过多空间，导致输出被提前截断；
  5. 虽未超过硬限制，但关键信息被大量无关内容干扰。

最后一种情况说明：

“能够放入上下文”不等于“模型一定能够同等有效地利用全部内容”。

长上下文中还可能出现：

  • 关键信息被淹没；
  • 位于中间的证据更难被稳定利用；
  • 相互冲突的内容增多；
  • 推理延迟和调用成本上升；
  • 注意力计算和 KV Cache 占用增加。

因此，上下文管理的目标不是无条件塞入更多文本，而是让模型看到足够、相关、清晰且可信的信息。

五、常见的上下文管理策略

1. 截断

只保留最近消息或最重要的内容。

优点：实现简单。
缺点：可能丢失早期的关键约束。

2. 滑动窗口

维护最近一段固定长度的 Token：

旧内容 ← 移出窗口
新内容 → 加入窗口

适合局部连续信息较重要的场景，但不适合必须长期保留早期事实的任务。

3. 对话摘要

将较早的多轮对话压缩为结构化摘要，例如：

用户目标：开发一个客服 RAG 系统
已确定技术：Python、FastAPI、PostgreSQL
稳定约束：回答必须引用知识库来源
待处理问题：重排序策略

摘要可以降低 Token 占用，但摘要过程可能遗漏信息，因此关键事实最好以结构化字段单独保存。

4. 分块处理

把长文档拆成多个 Chunk，分别处理，再合并结果。

常见流程：

长文档
  ↓
按标题、段落或 Token 数分块
  ↓
分别提取或总结
  ↓
汇总中间结果
  ↓
生成最终答案

5. RAG 检索

不把整个知识库都放进 Prompt，而是先检索与问题最相关的片段：

用户问题
  ↓
向量检索 / 关键词检索
  ↓
重排序
  ↓
选取少量相关片段
  ↓
放入上下文
  ↓
生成答案

RAG 的价值之一就是提高上下文的“有效信息密度”。

6. 分层总结

对于超长材料，可以先做局部总结，再对局部总结进行二次汇总：

原文分块 → 块级摘要 → 章节摘要 → 全文摘要

这种方法通常称为 Map-Reduce 或层次化总结。

六、为什么 Transformer 需要位置编码

Tokenizer 和 Embedding 能告诉模型“有哪些 Token”，但普通 Self-Attention 本身没有天然的序列顺序概念。

Self-Attention 的核心公式是：

\[ \operatorname{Attention}(Q,K,V) = \operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V \]

如果只对输入 Token 的顺序做同样的排列，而不给模型额外的位置信息，Attention 的输出也会随之排列。这种性质称为置换等变性（Permutation Equivariance）。

然而，自然语言中的顺序会改变含义：

小明批评了小王
小王批评了小明

两句话包含相似的 Token，但主语和宾语不同。因此，模型不仅要知道 Token 是什么，还必须知道：

  • Token 出现在哪个位置；
  • 两个 Token 相隔多远；
  • 一个 Token 位于另一个 Token 的前面还是后面。

位置编码的作用就是把这些位置信息引入 Transformer。

七、绝对位置编码

绝对位置编码为序列中的每个位置提供一个表示。

一种基本组合方式是：

\[ H_0=E_{\text{token}}+E_{\text{position}} \]

其中：

  • \(E_{\text{token}}\)：Token Embedding；
  • \(E_{\text{position}}\)：Position Embedding；
  • \(H_0\)：送入第一层 Transformer 的输入。

例如，Token “苹果”出现在位置 2 和位置 20 时，Token Embedding 可以相同，但加入的位置表示不同。

1. 可学习的绝对位置向量

模型维护一个位置矩阵：

\[ P\in\mathbb{R}^{L_{\max}\times d_{\text{model}}} \]

位置 \(p\) 对应：

\[ E_{\text{position}}=P[p] \]

这些向量像 Token Embedding 一样通过训练学习。

优点：

  • 实现简单；
  • 模型可以从数据中学习适合任务的位置表示。

局限：

  • 通常预先规定最大位置数量；
  • 对训练长度之外的位置不一定具有良好的外推能力。

2. 正弦—余弦位置编码

原始 Transformer 使用固定的正弦和余弦函数：

\[ PE(pos,2i)=\sin\left(\frac{pos}{10000^{2i/d_{\text{model}}}}\right) \]
\[ PE(pos,2i+1)=\cos\left(\frac{pos}{10000^{2i/d_{\text{model}}}}\right) \]

其中：

  • \(pos\)：Token 的位置；
  • \(i\)：向量维度索引；
  • \(d_{\text{model}}\)：隐藏向量维度。

不同维度使用不同频率：

  • 高频维度更敏感于短距离变化；
  • 低频维度可以描述更长距离的位置变化。

其优点是无需训练位置矩阵，并且位置模式具有规律性。

八、用 PyTorch 实现正弦位置编码

import math

import torch
import torch.nn as nn


class SinusoidalPositionalEncoding(nn.Module):
    def __init__(self, d_model: int, max_len: int = 5000):
        super().__init__()

        # pe: [max_len, d_model]
        pe = torch.zeros(max_len, d_model)

        # position: [max_len, 1]
        position = torch.arange(
            0, max_len, dtype=torch.float32
        ).unsqueeze(1)

        # 对应公式中的 10000^(-2i/d_model)
        div_term = torch.exp(
            torch.arange(0, d_model, 2, dtype=torch.float32)
            * (-math.log(10000.0) / d_model)
        )

        pe[:, 0::2] = torch.sin(position * div_term)
        pe[:, 1::2] = torch.cos(position * div_term)

        # 增加 batch 维度，形状变为 [1, max_len, d_model]
        pe = pe.unsqueeze(0)

        # 位置编码不是可训练参数，因此注册为 buffer
        self.register_buffer("pe", pe)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        # x: [batch_size, seq_len, d_model]
        seq_len = x.size(1)
        return x + self.pe[:, :seq_len]


batch_size = 2
seq_len = 6
d_model = 8

x = torch.randn(batch_size, seq_len, d_model)
position_encoder = SinusoidalPositionalEncoding(
    d_model=d_model,
    max_len=100,
)

output = position_encoder(x)

print("输入形状：", x.shape)
print("输出形状：", output.shape)

输出形状不变：

输入形状： torch.Size([2, 6, 8])
输出形状： torch.Size([2, 6, 8])

位置编码改变的是向量内容，而不是张量的形状。

九、相对位置编码

绝对位置编码关注：

当前 Token 位于第几个位置？

相对位置编码更关注：

当前 Token 与另一个 Token 相隔多远、方向如何？

例如：

Token A 位于位置 10
Token B 位于位置 13

它们的相对距离是：

\[ 13-10=3 \]

语言中的许多关系与相对距离密切相关。例如，修饰词常常与附近的名词关联，指代词可能需要关注前面若干位置的实体。

相对位置机制通常会把位置差 \(i-j\) 引入 Attention 分数或 Value 聚合过程。不同模型的具体公式并不完全相同。

相对于只使用绝对位置，相对位置方法通常更直接地表达 Token 之间的距离关系。

十、RoPE：旋转位置编码

RoPE（Rotary Position Embedding，旋转位置编码）被许多现代大语言模型采用。

它不是简单地把位置向量加到 Token Embedding 上，而是根据 Token 的位置，对 Query 和 Key 的部分维度进行二维旋转。

对一个二维向量，可以把位置 \(m\) 对应的旋转写成：

\[ R(m\theta)= \begin{bmatrix} \cos(m\theta) & -\sin(m\theta)\\ \sin(m\theta) & \cos(m\theta) \end{bmatrix} \]

然后对 Query 和 Key 进行旋转：

\[ q_m'=R(m\theta)q_m \]
\[ k_n'=R(n\theta)k_n \]

计算旋转后的点积时，其位置关系会与 \(m-n\) 有关：

\[ (q_m')^T k_n' = q_m^T R((n-m)\theta)k_n \]

这意味着 Attention 分数能够自然包含相对位置信息。

可以直观理解为：

Token 内容决定向量本身
Token 位置决定向量旋转的角度
旋转后 Q 与 K 的点积同时反映内容和相对位置

RoPE 的主要特点包括：

  • 直接作用于 Query 和 Key；
  • 能在 Attention 分数中表达相对位置；
  • 不需要为每个绝对位置单独学习一个向量；
  • 常与上下文长度扩展技术结合使用。

需要注意：使用 RoPE 不代表模型可以无限处理长文本。模型的训练长度、频率设置、注意力计算成本和推理资源仍然会限制有效上下文。

十一、ALiBi：Attention 线性偏置

ALiBi（Attention with Linear Biases）不显式生成位置 Embedding，而是在 Attention 分数中加入与距离有关的线性偏置。

可以简化表示为：

\[ S_{ij} = \frac{q_i k_j^T}{\sqrt{d_k}}-m\cdot |i-j| \]

在因果语言模型中，通常只考虑当前位置之前的 Token。距离越远，加入的惩罚越大。

其中 \(m\) 可以随不同注意力头而变化，使不同头具有不同的距离偏好。

直观上：

  • 一些注意力头更关注附近 Token；
  • 一些注意力头可以关注更远的 Token；
  • 位置信息直接影响 Attention 分数。

不同模型会选择不同的位置机制，并不存在适用于所有任务的唯一最佳方案。

十二、位置编码与 Causal Mask 的区别

二者都与顺序有关，但职责不同。

位置编码

告诉模型：

  • Token 在哪里；
  • Token 之间距离多远；
  • 前后顺序是什么。

Causal Mask

限制模型：

  • 生成当前位置时，不能读取未来 Token。

例如长度为 4 的序列：

位置 1：✓ × × ×
位置 2：✓ ✓ × ×
位置 3：✓ ✓ ✓ ×
位置 4：✓ ✓ ✓ ✓

Causal Mask 通常把未来位置的 Attention 分数设置为负无穷：

\[ S_{ij}=-\infty,\qquad j>i \]

经过 Softmax 后，未来位置的权重变为 0。

因此：

位置编码负责表示顺序，Causal Mask 负责限制信息可见范围。

二者不能相互替代。

十三、上下文窗口与位置编码的关系

上下文窗口和位置编码关系紧密，但不是同一个概念。

  • 上下文窗口规定模型一次能接收和处理多长的序列；
  • 位置编码让模型区分序列中不同位置及其相对关系。

一个模型要支持更长上下文，通常需要同时考虑：

  1. 位置机制能否表达更远的位置；
  2. 模型是否在足够长的序列上训练或继续训练；
  3. Attention 的计算量是否可接受；
  4. KV Cache 的显存是否足够；
  5. 长距离信息能否被模型稳定利用；
  6. 推理框架是否支持对应的最大长度。

仅修改“最大长度”配置，不一定能让模型可靠地理解更长文本。

十四、为什么长上下文成本高

对于标准 Self-Attention，长度为 \(n\) 的序列会形成一个 \(n\times n\) 的 Attention 矩阵。

其计算量通常近似为：

\[ O(n^2) \]

如果序列长度从 \(n\) 增加到 \(2n\)，Attention 矩阵元素数量会从：

\[ n^2 \]

增加到：

\[ (2n)^2=4n^2 \]

此外，自回归生成通常会缓存每层已经计算过的 Key 和 Value，这称为 KV Cache。

KV Cache 可以避免每生成一个新 Token 都重新计算全部历史 Token，但它本身会占用显存，而且占用通常随以下因素增长：

  • 上下文长度；
  • Transformer 层数；
  • KV Head 数量；
  • Head 维度；
  • Batch Size；
  • 数值精度。

需要特别注意：

KV Cache 提高生成效率，但不会自动扩大模型的上下文窗口，也不是永久记忆。

十五、长上下文外推

长度外推（Length Extrapolation）是指模型在比训练阶段更长的序列上仍能正常工作。

例如，模型主要在 4K Token 长度上训练，却希望推理时处理 16K Token。可能遇到：

  • 未见过的位置分布；
  • 位置关系失真；
  • 长距离注意力退化；
  • 输出质量下降；
  • 虽然技术上能输入，但信息利用能力不足。

针对 RoPE，常见的上下文扩展思路包括对位置索引或旋转频率进行缩放，并结合长序列继续训练或微调。

但必须区分：

可以提交更长输入
≠
可以同等准确地利用所有输入

评估长上下文模型时，不应只检查 API 是否接受长文本，还应测试：

  • 关键信息位于开头、中间和结尾时的表现；
  • 多个相似证据同时存在时能否正确选择；
  • 跨段落、跨章节推理能力；
  • 长输入下的延迟、成本和稳定性。

十六、AI 应用开发中的 Token 预算

实际应用应在调用模型之前分配 Token 预算。

假设：

\[ N_{\text{context}}=32768 \]

可以设计如下预算：

内容 预算
System Prompt 与固定规则 1,500
用户当前问题 1,000
对话摘要与近期历史 4,000
RAG 检索片段 18,000
工具返回结果 2,000
预留输出 5,000
安全余量 1,268

预算之和不应超过上下文窗口。

一个简化的程序可以先计算检索内容的可用空间：

def retrieval_budget(
    context_limit: int,
    system_tokens: int,
    history_tokens: int,
    user_tokens: int,
    tool_tokens: int,
    reserved_output_tokens: int,
    safety_margin: int = 256,
) -> int:
    used = (
        system_tokens
        + history_tokens
        + user_tokens
        + tool_tokens
        + reserved_output_tokens
        + safety_margin
    )
    return max(context_limit - used, 0)


budget = retrieval_budget(
    context_limit=32768,
    system_tokens=1500,
    history_tokens=4000,
    user_tokens=1000,
    tool_tokens=2000,
    reserved_output_tokens=5000,
)

print("可用于检索片段的 Token：", budget)

实际项目中，Token 数量应使用与目标模型匹配的 Tokenizer 计算，不能简单用字符数代替。

十七、RAG 中如何利用上下文窗口

RAG 并不是检索片段越多越好。一个更合理的流程是：

用户问题
  ↓
查询改写
  ↓
召回候选 Chunk
  ↓
重排序与去重
  ↓
按 Token 预算选择片段
  ↓
保留来源信息
  ↓
构造 Prompt
  ↓
模型回答并引用证据

选择片段时应综合考虑：

  • 与问题的相关度；
  • 来源可信度；
  • 内容是否重复；
  • Chunk 是否完整；
  • 多个片段之间是否冲突；
  • 剩余输出空间；
  • 是否包含回答所需的上下文边界。

如果检索片段过多，可能造成：

  • 有效证据被无关片段稀释；
  • Prompt 成本增加；
  • 模型更难判断冲突信息；
  • 留给输出的 Token 减少。

十八、多轮对话中的上下文管理

长期对话不应只依赖“把全部消息不断追加到 Prompt”。更稳健的结构可以是：

固定系统规则
+ 用户稳定偏好
+ 任务状态
+ 历史对话摘要
+ 最近若干轮原始消息
+ 当前问题
+ 按需检索的外部资料

其中：

  • 固定规则：尽量简洁、明确；
  • 稳定偏好：使用结构化字段保存；
  • 任务状态：记录已完成、待完成和关键决策；
  • 历史摘要：压缩较早对话；
  • 最近消息：保留局部语境和措辞细节；
  • 外部资料：只在与当前问题相关时检索。

这种设计比无限追加历史消息更节省 Token，也更容易控制信息质量。

十九、常见误区

误区 1：上下文窗口越大，模型一定越聪明

错误。窗口大小代表可接收的最大序列范围，不直接等于推理能力、知识准确性或长文本利用能力。

误区 2：把全部资料放进 Prompt 最安全

错误。无关、重复或冲突信息会降低有效信息密度，并增加成本和延迟。

误区 3：模型能在一次对话中看到内容，就会永久记住

错误。当前上下文通常只在本次请求或应用维护的会话中有效。永久保存需要外部记忆机制或训练流程。

误区 4：上下文窗口只计算用户输入

错误。System Prompt、历史消息、检索资料、工具结果和模型输出都可能占用预算。

误区 5：位置编码就是 Token Embedding

错误。Token Embedding 表示内容，位置编码表示位置或相对距离。

误区 6：位置编码和 Causal Mask 是一回事

错误。位置编码描述顺序；Causal Mask 阻止模型看到未来信息。

误区 7：KV Cache 可以让模型拥有无限上下文

错误。KV Cache 是推理缓存，会消耗显存，而且仍受模型和推理系统的最大长度限制。

误区 8：API 接受长输入，就说明模型能完美利用全部内容

错误。技术上的可输入长度和实际的有效利用长度并不完全相同，必须通过任务评测验证。

二十、知识链总结

原始文本
  ↓
Tokenizer
  ↓
Token ID
  ↓
Token Embedding
  +
位置信息（绝对位置、相对位置、RoPE、ALiBi 等）
  ↓
Transformer / Self-Attention
  ↓
在上下文窗口范围内建立 Token 之间的联系
  ↓
输出上下文相关表示或生成下一个 Token

本课最重要的关系是：

  1. 上下文窗口决定模型一次能够直接处理多少 Token；
  2. 位置编码告诉模型 Token 的位置、顺序或相对距离；
  3. Attention Mask决定某些 Token 是否允许关注另一些 Token；
  4. KV Cache保存生成过程中已经计算出的 Key 和 Value，以减少重复计算；
  5. RAG、摘要和外部记忆负责在有限窗口内提供最有价值的信息。

二十一、自测题

1. 什么是上下文窗口？

上下文窗口是模型在一次推理中能够直接处理的 Token 范围，通常包括输入内容和生成输出。

2. 为什么要为输出预留 Token？

因为输入和输出通常共享总上下文预算。如果输入占满窗口，模型就没有足够空间生成完整答案。

3. 上下文窗口与永久记忆有什么区别？

上下文是当前推理的工作区；永久记忆通常由数据库、文件或向量库等外部系统保存，并在以后重新注入上下文。

4. Transformer 为什么需要位置编码？

因为普通 Self-Attention 本身不能充分表示 Token 的先后顺序，而语言含义依赖位置和顺序。

5. 绝对位置与相对位置有什么区别？

绝对位置表示 Token 位于序列中的第几个位置；相对位置表示两个 Token 之间的距离和方向。

6. RoPE 的基本思想是什么？

根据 Token 位置旋转 Query 和 Key 的部分维度，使 Attention 点积自然包含相对位置信息。

7. 位置编码和 Causal Mask 有什么区别？

位置编码提供位置信息；Causal Mask 限制当前 Token 不能看到未来 Token。

8. 为什么长上下文会增加计算成本？

标准 Self-Attention 需要构造 \(n\times n\) 的注意力关系，复杂度通常近似为 \(O(n^2)\)；生成时 KV Cache 也会随上下文长度增加。

9. RAG 为什么不能无条件放入更多检索片段？

过多片段会增加 Token 成本，并可能引入无关、重复或冲突信息，降低有效信息密度。

10. KV Cache 是否会扩大上下文窗口？

不会。它主要用于缓存历史 Key 和 Value、减少重复计算，仍受模型和推理系统的最大长度限制。

二十二、实践题

  1. 选择一个具体模型，查阅其上下文窗口、最大输出长度和 Tokenizer；
  2. 准备一篇长文档，分别使用“直接截断”“分块总结”和“RAG 检索”回答同一问题；
  3. 记录每种方法的输入 Token、输出 Token、延迟和答案准确性；
  4. 把关键证据分别放在长文本的开头、中间和结尾，比较模型表现；
  5. 修改正弦位置编码示例，打印不同位置在前 8 个维度上的数值并观察变化规律。

二十三、本课小结

上下文窗口是大语言模型当前推理的有限工作区。Prompt、历史消息、检索资料、工具结果和模型输出都会占用 Token 预算。优秀的 AI 应用不会简单地把所有内容塞入窗口，而会通过截断、摘要、分块、检索、重排序和结构化记忆，提高上下文的信息密度。

Transformer 还需要位置机制来理解 Token 的顺序和距离。绝对位置编码描述 Token 所在的位置，相对位置机制更关注 Token 之间的距离；RoPE 通过旋转 Query 和 Key 引入相对位置，ALiBi 则把距离偏置加入 Attention 分数。

一句话总结：

上下文窗口决定模型一次能看多少内容，位置编码帮助模型理解这些内容按什么顺序排列，而上下文管理决定真正应该让模型看到什么。
